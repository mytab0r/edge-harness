# 0028. Соответствие «категория сигнала → тема Telegram» живёт на data-ветке

Дата: 2026-09-23
Статус: принято
Задачи: #1461 (категории), #1465 (хранение), #1463 (замер тем)

## Контекст

Все сигналы владельцу уходили в ОДИН поток: вопрос, требующий его решения,
шёл вперемешку с шумом конвейера. Владелец читает поток глазами, и решение в
нём тонет.

Замер #1463 (прогон `35741889145`) закрыл вопрос о возможности: темы Bot API
работают целиком — `createForumTopic`, `sendMessage` с `message_thread_id`,
`editForumTopic`, `unpinAllForumTopicMessages`, `deleteForumTopic`, все шесть
вызовов вернули `ok`. Переключатель в @BotFather не понадобился.

Осталось единственное недостающее звено: **тема создаётся один раз, а её
`message_thread_id` обязан пережить прогон job'а.** Без хранения каждый прогон
заводил бы темы заново, и чат владельца стал бы свалкой одноразовых тем — ровно
то состояние, ради ухода из которого всё и делается.

## Решение

Носитель — **data-ветка `data/telegram-topics`, файл `topics.json`**.

* Пишет `scripts/lib/data_branch_writer.py` (#882) — та же библиотека, что у
  `data/worktree-cleanup` и `data/pipeline-health`, с ретраем на гонку
  параллельных job'ов и громким отказом на отказ прав.
* Читают штатно с `raw.githubusercontent.com`: репозиторий публичный, токен не
  нужен, счётчик installation-токена не тратится. Перед СОЗДАНИЕМ темы (редкий
  путь) карта перечитывается авторитетно через API — у raw кэш порядка минут, и
  два одновременных job'а иначе завели бы по теме на категорию.
* Реестр категорий (`telegram_topics.CATEGORIES`) — там же, одним местом
  правды: `decision`, `breakage`, `pipeline`.
* Чат владельца (`TELEGRAM_CHAT_ID`) в файл НЕ попадает ни в каком виде:
  репозиторий публичный.

## Рассмотренные варианты

### Durable Object (морда) — отвергнут

Уже хранит состояние и умеет SQLite. Но отправители живут в GitHub Actions и
ходили бы в морду за id темы на каждый сигнал — то есть канал владельца стал бы
зависеть от живости морды.

Цена этой зависимости измерена, а не предположена: 2026-09-22/23 морда отвечала
Telegram'у 4xx на неперевариваемый апдейт, очередь вебхука встала, и владелец
не мог ни нажать кнопку, ни сообщить об этом — канал, которым чинят, был тем же
каналом, который сломался (#1477, #1471). Заводить ту же зависимость ещё раз —
значит подписаться на повторение инцидента.

### Закреплённое сообщение в чате — отвергнут

Хранилище внутри самого Telegram, читается тем же токеном, внешних
зависимостей нет вовсе. Отвергнут по одной причине: слот закрепления ОДИН и
принадлежит владельцу. Он закрепит что-нибудь своё — и соответствие исчезнет
молча, без единого сигнала. Тихая потеря состояния дороже лишнего файла в git.

## Последствия

**Хорошее.** Карта видна в истории git (когда и какая тема заведена). Чтение
бесплатно по бюджету API. Отправители не зависят от морды. Гонка обработана
библиотекой, уже оплаченной инцидентом #882.

**Плохое, названное вслух.** Карта не знает, какому чату принадлежит (chat_id —
секрет, в публичный репозиторий не попадает). После смены чата она хранит чужие
id. Это не тихая ошибка: отправка в несуществующую тему отказывает с
`description`, по которому `topic_is_gone` узнаёт «темы больше нет», запись
забывается (`message_thread_id: 0`), и следующий сигнал заводит тему заново.

**Тормоз и его газ.** Тема — не обязательство. Если её не удалось получить (чат
не форум, у бота нет прав `can_manage_topics`, сеть, исчерпан бюджет), сигнал
уходит В ОБЩИЙ ПОТОК с явной пометкой, ПОЧЕМУ он не в теме. Потерять сигнал
дороже, чем показать его не там. Газ на «чат не форум» ручной и назван: владелец
включает темы в настройках чата, после чего следующий же сигнал заводит тему сам.

## Чем принуждается

`scripts/ci/guards/telegram-topics-guard.sh` →
`scripts/lib/test_telegram_topics.py`:

* отправитель без категории или с категорией вне реестра — красный CI
  (Python-сторона разбирается AST'ом, bash-сторона исполняется по-настоящему);
* категория в реестре, которой никто не шлёт, — тоже красный: пустая тема в
  чате владельца это то же расхождение, только в другую сторону (нашла это
  сама гвардия на первом прогоне — категория `infra` была заведена и удалена);
* стенд поднимает настоящий `http.server` и настоящий `git init --bare`;
  недоступность — закрытый порт.

## Непроверено машиной

* **Что чат владельца включён как форум.** Замер #1463 создавал тему успешно,
  то есть на момент замера — да. Отдельной гвардии на это нет и быть не может:
  это настройка на стороне владельца, а не наш код. Отказ виден пометкой в
  сигнале.
* **Поведение при удалении темы владельцем в момент отправки.** Разбор
  `description` проверен на прод-формах Bot API, живого удаления в момент
  отправки мы не воспроизводили.
