# ADR 0024. Триаж застрявшего PR: метод ADR 0021 не покрывал очередь — четыре дефекта и правки

- **Дата:** 2026-09-14
- **Статус:** принято (задача #1218)
- **Смежное:** [ADR 0021](0021-stalled-pr-merge-conflict-triage.md) (шесть измеримых
  величин — этот ADR правит его дефекты, не отменяет), `scripts/orchestra/
  stalled_pr_triage.py` (носитель), `scripts/lib/decision_numbering.py` (#1078,
  переиспользуется для половины величины 7).

## Контекст

ADR 0021 задаёт шесть измеримых величин для триажа застрявшего PR («довести /
пересоздать / закрыть»). Написан на выборке из 19 PR — **все в конфликте с
main**. Применение к реальной очереди 2026-09-14 (38 открытых PR, из них
только 12 в конфликте) руками вскрыло четыре дефекта, каждый подтверждён
фактом на живых данных (см. «Проверка» ниже).

## Дефект 1. Таблица молчала по большей части очереди

Доминирующий случай очереди: величины 1–3 малы (не конфликтует, функциональных
пересечений с main нет), задача открыта, замены (величина 5) не проверяли, но
висит `ai:changes-requested` (величина 6). Строка «довести» ADR 0021 требует
дословно «величина 6 БЕЗ вердикта на доработку» — эта комбинация не покрыта ни
одной строкой таблицы. На выборке ADR 0021 (все 19 PR — DIRTY) она физически не
могла всплыть.

**Правка:** величина 6 перестаёт быть условием, которое решает
«довести/нет» — она становится признаком СЛЕДУЮЩЕГО ШАГА после сведения:

| Величины 1–3 | Величина 6 | Действие |
|---|---|---|
| малы | нет вердикта на доработку | **Довести** |
| малы | `ai:changes-requested`/`ai:failed` | **Довести и доработать находки** — сведение не блокируется, доработка называется явным следующим шагом |
| велики | нет вердикта на доработку | **Пересоздать** |
| велики | `ai:changes-requested`/`ai:failed` | **Пересоздать** — вердикт добавляет причину (сведение+доработка+повторное ревью дороже пересоздания), не меняет действие |

Величина 5 (эквивалент уже в main, подтверждённый чтением) и «задача закрыта
без замены» остаются самостоятельными исходами, перекрывающими всё
остальное — ADR 0021 был прав, что это они решают судьбу PR первыми.

## Дефект 2. Величины 4 и 6 — почти константы на срезе 2026-09-14

- Величина 4 (задача открыта?) — **36 из 36** PR с резолвящейся задачей
  открыты (два dependabot-PR задачи не имеют вовсе — это `task_state="none"`,
  отдельное от «закрыта» значение). Проверено GraphQL-батчем по всем 36
  номерам одним запросом.
- Величина 6 — `ai:changes-requested` у 35 из 38, `ai:ok` у одного (#920, сам
  в конфликте), без вердикта — у двух (#542, #1053 на момент утреннего
  снимка; к вечеру у #1053 тоже появился `ai:changes-requested`).

**Решение:** обе величины остаются в методе. Они не мертворождённые —
структурно способны различать (закрытая задача возможна, просто не случилась
на этом срезе), и с правкой дефекта 1 величина 6 больше не создаёт дыру, даже
когда она константна. Убирать величину, которая честно не различает СЕГОДНЯ,
но может завтра, — тот же класс ошибки, что жёсткий порог: ADR 0021 сам
предостерегал против решений по одной величине. Пометка честная: `decide()`
принимает `task_state` тремя значениями (`open`/`closed`/`none`) именно
потому, что «закрыта» ни разу не встретилась на этом срезе — код готов к
этому значению, просто не видел его в деле.

## Дефект 3. Величина 3 (дрейф main) в строках — врёт в обе стороны

ADR 0021 считал величину 3 как «строк, изменённых в main в файлах PR» делённое
на «строк, изменённых PR в тех же файлах», порог — половина. Инфлируется
несвязанными со смыслом изменениями (дописывание в конец файла) и занижается
для дешёвых по строкам, но смысловых коллизий (ADR 0021 сам документирует это
на #644).

**Правка:** величина 3 теперь — пересечение изменённых Python def/class-
регионов (AST, по общему merge-base) между PR-диффом и main-диффом, только в
файлах, которые трогают ОБЕ стороны (`functional_overlap` в
`stalled_pr_triage.py`). Строковый ratio (`line_drift_ratio`) оставлен
справочной величиной, не входит в `decide()`.

**Проверка (issue #1218):** #542 и #1053 — оба доведены ребейзом без единого
конфликта в течение дня, что и предсказывает функциональное пересечение
(**0** у обоих — merge-base каждого на момент проверки совпал с текущей
головой main, дрейф буквально нулевой). Обратный случай — #831 (реальный
конфликт, `scheduler.py`+`test_scheduler.py`): функциональное пересечение
**20** (шесть функций `scheduler.py`, четырнадцать тестов
`test_scheduler.py`) — величина 3 разделяет "дешёвую" пару от "дорогой" пары
начисто (0, 0 против 20). Найден и третий класс: #1020 — `git` считает PR
чистым (MERGEABLE), но функциональное пересечение **14** — величина 3 ловит
семантическую коллизию, которую сам git не видит.

## Дефект 4. Величины, которой не было: коллизия объявлений между PR и main

`docs/decisions`/`docs/research` уже закрыты `scripts/lib/decision_numbering.py`
(#1078). Тот же класс для `# Инвариант N` (`scripts/orchestra/
repo_invariants.py`) не был закрыт методом вовсе — частная задача #904/PR
#1201 решает ДРУГОЕ (назначение свободного номера внутри файла), не коллизию
между PR и main.

**Правка:** добавлена величина 7 — узкий, но обобщённый чек «PR добавляет
номер, который main ТОЖЕ независимо добавил с общего merge-base»:
- `declared_invariant_numbers`/`declaration_collisions`/
  `measure_invariant_collision` — свой, самостоятельный носитель для
  `repo_invariants.py` (не трогает сам файл, не дублирует #1201 — тот решает
  другой вопрос).
- `decision_doc_collision_pr_numbers` — переиспользует
  `decision_numbering.check_decision_doc_number_collisions` целиком для
  `docs/decisions`/`docs/research`, второй копии обхода git/gh не заводит.

Коллизия — не отдельная ветка действия («довести»/«пересоздать»/«закрыть»), а
**обязательное предупреждение поверх любого исхода**: сведение, которое
пройдёт молча, после мержа даст дубль номера.

**Проверка (issue #1218):** обе половины поймали живые коллизии в реальной
очереди 2026-09-14:
- Инварианты: #870→15, #883→18, #944→17 (main независимо добавил те же
  номера с общего merge-base каждого PR).
- `docs/decisions`: #944→0017 (main занял тем же числом другой ADR), #667→0018
  (аналогично) — числа, НЕ названные в тексте issue #1218, найдены только
  прогоном скрипта, что и было целью выноса метода в машину (см. ниже).

## Носитель

Метод вынесен в `scripts/orchestra/stalled_pr_triage.py`:
величины 1 (`is_conflicting`, реальный `git merge-tree --write-tree`, не
GitHub `mergeable` — тот считается асинхронно и может быть `null`), 2
(`commits_behind`), 3 (`measure_functional_overlap`), 4/6 (gh API — задача,
метки), 7 (`measure_invariant_collision` + `decision_doc_collision_pr_numbers`)
— машинные; решение — `decide()`, читает все входы вместе. Величина 5
(«есть ли уже эквивалент в main») сознательно НЕ автоматизирована — ADR 0021
прав, это чтение и суждение, `decide()` принимает её как опциональный вход.

Тесты — `scripts/orchestra/test_stalled_pr_triage.py`, 32 теста: чистые
функции (`decide`/`functional_overlap`/`declaration_collisions`) без git, и
поведенческие на настоящем временном git-репозитории (AGENTS.md,
«поведенческий тест находит то, чего структурный не видит») — включая живые
классы #542/#1053 (пересечение = 0) и #831 (пересечение > 0), живой класс
коллизии 870/883/944, и живую ловушку `--depth 1` (см. ниже).

CLI: `python scripts/orchestra/stalled_pr_triage.py queue` — величины
1,2,3,4,6,7 + решение по ВСЕЙ очереди (один запрос `pulls`, один GraphQL-батч
задач, дальше только локальный `git`, без сетевой цены на PR). `measure <PR>`
— только git-считаемые величины (1,2,3,7) для одного PR, без gh.

Не подключён к `repo_invariants.py`/CI как обязательная проверка этим PR —
это МЕТОД ТРИАЖА (решение о PR из очереди), не инвариант состояния
репозитория; повторяет решение ADR 0021 не гейтить merge этим механизмом.

## Побочная находка: ловушка поверхностного клона портит соседний инструмент

`decision_numbering.fetch_refs` делает `git fetch --depth 1` собственной
веткой `main` в изолированный неймспейс. На уже ПОЛНОМ (unshallow) дереве это
всё равно переводит `.git/shallow` в частично-мелкое состояние: shallow —
свойство КОММИТА, не ссылки, и если `main` и `refs/decision-numbering/main`
указывают на один и тот же коммит, фетч с `--depth 1` мелит его для ВСЕХ
ссылок разом, включая уже читаемый `origin/main` — последующий `git
merge-base origin/main ...` в этом же дереве падает пустым stderr. `stalled_pr_triage.
cmd_queue` лечит это порядком (вызов `decision_doc_collision_pr_numbers` —
последним, после всего git-обхода измерений) и восстанавливает глубину
(`ensure_unshallow`) до и после — не трогая сам `decision_numbering.py`
(вне рамок этой задачи, его контракт — работать НА шаллоу дереве CI, не
беречь чужую полную историю). Тест — `test_ensure_unshallow_grows_a_shallow_
clone_to_full_history` (настоящий bare-репозиторий, настоящий
`--no-local --depth 1` клон).

## Не подтверждено

- Величина 5 (эквивалент уже в main) не автоматизирована и не проверялась
  массово на очереди 2026-09-14 этим PR — `decide()` принимает её как
  `None` по умолчанию для всех строк прогона «до/после» выше; ручное чтение
  по каждому PR — вне объёма этой задачи.
- Функциональное пересечение (величина 3) считается только для `.py`-файлов
  (AST) — для JS/TS/markdown региона нет, пересечение по ним не участвует в
  `decide()`. Расширение на другие языки — не подтверждено, что нужно:
  доминирующий код конвейера (scheduler/pulse/repo_invariants) — Python.
- Не проверено, меняется ли распределение действий при повторном прогоне
  через неделю (очередь живая, PR мержатся/закрываются) — таблица «до/после»
  выше — снимок на 2026-09-14, не постоянная величина.
