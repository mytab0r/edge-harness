# ADR 0024. Триаж застрявшего PR: метод ADR 0021 не покрывал очередь — четыре дефекта и правки

- **Дата:** 2026-09-14
- **Статус:** принято (задача #1218)
- **Смежное:** [ADR 0021](0021-stalled-pr-merge-conflict-triage.md) (шесть измеримых
  величин — этот ADR правит его дефекты, не отменяет), `scripts/orchestra/
  stalled_pr_triage.py` (носитель), `scripts/lib/decision_numbering.py` (#1078,
  переиспользуется для половины величины 7).

## Контекст

ADR 0021 задаёт шесть измеримых величин для триажа застрявшего PR («довести /
пересоздать / закрыть»). Написан на выборке из 19 PR — **все в конфликте с
main**. Применение к реальной очереди 2026-09-14 (38 открытых PR, из них
только 12 в конфликте) руками вскрыло четыре дефекта, каждый подтверждён
фактом на живых данных (см. «Проверка» ниже).

## Дефект 1. Таблица молчала по большей части очереди

Доминирующий случай очереди: величины 1–3 малы (не конфликтует, функциональных
пересечений с main нет), задача открыта, замены (величина 5) не проверяли, но
висит `ai:changes-requested` (величина 6). Строка «довести» ADR 0021 требует
дословно «величина 6 БЕЗ вердикта на доработку» — эта комбинация не покрыта ни
одной строкой таблицы. На выборке ADR 0021 (все 19 PR — DIRTY) она физически не
могла всплыть.

**Правка:** величина 6 перестаёт быть условием, которое решает
«довести/нет» — она становится признаком СЛЕДУЮЩЕГО ШАГА после сведения:

| Величины 1–3 | Величина 6 | Действие |
|---|---|---|
| малы | нет вердикта на доработку | **Довести** |
| малы | `ai:changes-requested`/`ai:failed` | **Довести и доработать находки** — сведение не блокируется, доработка называется явным следующим шагом |
| велики | нет вердикта на доработку | **Пересоздать** |
| велики | `ai:changes-requested`/`ai:failed` | **Пересоздать** — вердикт добавляет причину (сведение+доработка+повторное ревью дороже пересоздания), не меняет действие |

Величина 5 (эквивалент уже в main, подтверждённый чтением) и «задача закрыта
без замены» остаются самостоятельными исходами, перекрывающими всё
остальное — ADR 0021 был прав, что это они решают судьбу PR первыми.

## Дефект 2. Величины 4 и 6 — почти константы на срезе 2026-09-14

- Величина 4 (задача открыта?) — **36 из 36** PR с резолвящейся задачей
  открыты (два dependabot-PR задачи не имеют вовсе — это `task_state="none"`,
  отдельное от «закрыта» значение). Проверено GraphQL-батчем по всем 36
  номерам одним запросом.
- Величина 6 — `ai:changes-requested` у 35 из 38, `ai:ok` у одного (#920, сам
  в конфликте), без вердикта — у двух (#542, #1053 на момент утреннего
  снимка; к вечеру у #1053 тоже появился `ai:changes-requested`).

**Решение:** обе величины остаются в методе. Они не мертворождённые —
структурно способны различать (закрытая задача возможна, просто не случилась
на этом срезе), и с правкой дефекта 1 величина 6 больше не создаёт дыру, даже
когда она константна. Убирать величину, которая честно не различает СЕГОДНЯ,
но может завтра, — тот же класс ошибки, что жёсткий порог: ADR 0021 сам
предостерегал против решений по одной величине. Пометка честная: `decide()`
принимает `task_state` тремя значениями (`open`/`closed`/`none`) именно
потому, что «закрыта» ни разу не встретилась на этом срезе — код готов к
этому значению, просто не видел его в деле.

## Дефект 3. Величина 3 (дрейф main) в строках — врёт в обе стороны

ADR 0021 считал величину 3 как «строк, изменённых в main в файлах PR» делённое
на «строк, изменённых PR в тех же файлах», порог — половина. Инфлируется
несвязанными со смыслом изменениями (дописывание в конец файла) и занижается
для дешёвых по строкам, но смысловых коллизий (ADR 0021 сам документирует это
на #644).

**Правка:** величина 3 теперь — пересечение изменённых РЕГИОНОВ между
PR-диффом и main-диффом относительно общего merge-base, только в файлах,
которые трогают ОБЕ стороны (`functional_overlap` в `stalled_pr_triage.py`):

- `.py` — AST def/class-регионы базового файла; начало региона — минимум
  по декораторам (правка только `@декоратора` — правка поведения функции);
- остальные файлы — **line-range fallback**: пересечение строк, задетых
  обеими сторонами, в КООРДИНАТАХ MERGE-BASE (минус-сторона hunk-заголовков),
  сгруппированное в непрерывные диапазоны. Режим каждого файла отдаётся в
  выводе (`overlap_mode_by_file`) — ноль из-за непосчитанного файла не
  выдаётся за «пересечений нет» молча.

Fallback закрывает живой класс первого прогона (назван в комментарии к
#1218): #395/#613/#920/#1057 конфликтуют в shell/yaml/json/markdown, и
величина 3 без fallback честно рапортовала им «код не пересекается», ничего
не измерив. В вечернем прогоне этого PR fallback нашёл пересечения там, где
AST-версия давала ноль: #667 (`docs/INDEX.md`), #613 (`repo-ci.yml`), #395
(`dsh-ci.sh`), #1057 (`docs/research`), а #944/#883/#896 — дополнительно к
своим `.py`-пересечениям.

Сверка регионов ведётся по БАЗОВЫМ координатам (находка ревью PR #1219):
плюс-сторона hunk'ов сдвигается удалениями выше по файлу, и правка функции
f засчитывалась бы соседней g — ложное «пересечение» ведёт к ложному
«пересоздать».

Строковый ratio (`line_drift_ratio`) сохранён как СПРАВОЧНАЯ величина:
считается машиной по общим файлам (`line_drift_main_lines` /
`line_drift_pr_lines` / `line_drift_ratio` в выводе каждого PR), в
`decide()` не входит. Не мёртвый код: машинный прогон обязан нести его
числом, а не формулой рядом с неприменяемой функцией (находка ревью
PR #1219).

**Проверка (issue #1218):** #542 и #1053 — оба доведены ребейзом без единого
конфликта в течение дня, что и предсказывало функциональное пересечение
(**0** у обоих на момент ребейза — merge-base каждого совпадал с головой
main, дрейф был буквально нулевым). Обратный случай — #831 (реальный
конфликт, `scheduler.py`+`test_scheduler.py`): функциональное пересечение
разделяет "дешёвую" пару от "дорогой" пары начисто (0, 0 против >0).
Найден и третий класс: #1020 — `git` считает PR чистым (MERGEABLE), но
функциональное пересечение **6** (вечерний прогон) — величина 3 ловит
семантическую коллизию, которую сам git не видит. Очередь живая: #1053,
доведённый ребейзом чисто днём, к вечернему прогону отстал на 2 коммита
main — и величина 3 нашла свежее пересечение
(`test_main_closes_reopened_task_before_acceptance_sees_it`) ДО того, как
очередной механический ребейз стёр бы его молча; факт «ребейз утром был
чист» это не отменяет — метод предсказывает следующий шаг.

## Дефект 4. Величины, которой не было: коллизия объявлений между PR и main

`docs/decisions`/`docs/research` уже закрыты `scripts/lib/decision_numbering.py`
(#1078). Тот же класс для реестра инвариантов (`scripts/orchestra/
repo_invariants.py`) на момент постановки #1218 не был закрыт вовсе; за время
работы слит PR #1201 (#904) — `scripts/lib/invariant_numbering.py`, арбитр
номеров инвариантов.

**Правка:** добавлена величина 7 — узкий, но обобщённый чек «PR добавляет
номер, который main ТОЖЕ независимо добавил с общего merge-base»:
- `measure_invariant_collision`/`declaration_collisions` — сравнение сторон
  ОТНОСИТЕЛЬНО MERGE-BASE для `repo_invariants.py`. ФОРМАТ записи
  (`N. check_имя — …`) парсится переиспользованием
  `invariant_numbering.parse_registry_entries` (#1201), второго парсера
  реестра нет; непустой файл без распознанных записей — громкий отказ через
  `_parse_full_registry_or_die` того же модуля (слепота парсера не имеет
  права выглядеть как «номер не занят»). Разделение труда с #1201 названо:
  арбитр сравнивает два дерева напрямую — «коллизия ЕСТЬ СЕЙЧАС» (гейт CI),
  величина 7 — «обе стороны независимо добавили один номер С ОБЩЕГО
  ПРЕДКА» (история независимости для решения о PR); поэтому PR↔PR-коллизия
  (например #1061 против #1136 на номере 19) — предмет арбитра #1201, не
  величины 7.
- `decision_doc_collision_pr_numbers` — переиспользует
  `decision_numbering.check_decision_doc_number_collisions` целиком для
  `docs/decisions`/`docs/research`, второй копии обхода git/gh не заводит.

Коллизия — не отдельная ветка действия («довести»/«пересоздать»/«закрыть»), а
**обязательное предупреждение поверх любого исхода**: сведение, которое
пройдёт молча, после мержа даст дубль номера. Половины величины названы
раздельно (инварианты / decision-номера), и reason формулируется по
сработавшей половине — «алерт не гадает» (находка ревью PR #1219).

**Проверка (issue #1218):** обе половины поймали живые коллизии в реальной
очереди 2026-09-14:
- Инварианты: #870→15, #883→18, #944→17 (main независимо добавил те же
  номера с общего merge-base каждого PR).
- `docs/decisions`: #944→0017 (main занял тем же числом другой ADR), #667→0018
  (аналогично) — числа, НЕ названные в тексте issue #1218, найдены только
  прогоном скрипта, что и было целью выноса метода в машину (см. ниже).

## Носитель

Метод вынесен в `scripts/orchestra/stalled_pr_triage.py`:
величины 1 (`is_conflicting` — реальный `git merge-tree --write-tree`, не
GitHub `mergeable`; вердикт — КОД ВОЗВРАТА: `0` чисто, `1` с непустым stdout
конфликт, `1` с пустым stdout или иной код — `GitError`, находка ревью
PR #1219: modify/delete-конфликт и отказ инструмента не имеют права
притворяться «чисто»), 2 (`commits_behind`), 3
(`measure_functional_overlap`: AST-регионы + line-range fallback + справочный
строковый ratio), 4/6 (gh API — задача, метки; отсутствующий ответ GraphQL —
`task_state="unknown"`, не «открыта»), 7 (`measure_invariant_collision` +
`decision_doc_collision_pr_numbers`) — машинные; решение — `decide()`,
читает все входы вместе. Величина 5 («есть ли уже эквивалент в main»)
сознательно НЕ автоматизирована — ADR 0021 прав, это чтение и суждение,
`decide()` принимает её как опциональный вход.

Тесты — `scripts/orchestra/test_stalled_pr_triage.py`, 47 теста: чистые
функции (`decide`/`functional_overlap`/`declaration_collisions`/
`intersecting_line_runs`/`region_word` и др.) без git, и поведенческие на
настоящем временном git-репозитории (AGENTS.md, «поведенческий тест находит
то, чего структурный не видит») — включая живые классы #542/#1053
(пересечение = 0) и #831 (пересечение > 0), сдвиговую ловушку плюс-стороны
хунков, modify/delete-конфликт на прод-форме вывода merge-tree, отказ
инструмента, line-range fallback для не-.py (живой класс #1026), живой
класс коллизии 870/883/944 на живом формате реестра и живую
ловушку `--depth 1` (см. ниже). Каждая правка по ревью доказана мутацией
(снятие фикса красит свой тест: rc-вердикт, минус-сторона, fallback,
прокидывание ratio, честный `unknown`, раздельные половины величины 7,
форма modify/delete, исход «довести и доработать»).

CLI: `python scripts/orchestra/stalled_pr_triage.py queue` — величины
1,2,3,4,6,7 + решение по ВСЕЙ очереди. Сеть: один запрос `pulls`, один
GraphQL-батч задач, фетч head'а каждого PR и один обход `decision_numbering`;
дальше только локальный `git` (merge-tree/diff/merge-base) — дорогих
gh-вызовов (контракты/комментарии/состояния по каждому PR) нет (находка
ревью PR #1219: фетч — тоже сеть, прежняя формулировка «без сетевой цены»
была неточной). Refspec фетча — с `+`: назначение приватное, force-push в
чужой открытый PR не должен валить весь обход очереди. `measure <PR>` —
только git-считаемые величины (1,2,3,7) для одного PR, без gh.

Не подключён к `repo_invariants.py`/CI как обязательная проверка этим PR —
это МЕТОД ТРИАЖА (решение о PR из очереди), не инвариант состояния
репозитория; повторяет решение ADR 0021 не гейтить merge этим механизмом.
Семантические коллизии реестра инвариантов гейтит арбитр #1201
(`invariant-numbering-guard.sh` в каталоге гвардий) — величина 7 остаётся
измерением для триажа, не дублем гейта.

## Побочная находка: ловушка поверхностного клона портит соседний инструмент

`decision_numbering.fetch_refs` делает `git fetch --depth 1` собственной
веткой `main` в изолированный неймспейс. На уже ПОЛНОМ (unshallow) дереве это
всё равно переводит `.git/shallow` в частично-мелкое состояние: shallow —
свойство КОММИТА, не ссылки, и если `main` и `refs/decision-numbering/main`
указывают на один и тот же коммит, фетч с `--depth 1` мелит его для ВСЕХ
ссылок разом, включая уже читаемый `origin/main` — последующий `git
merge-base origin/main ...` в этом же дереве падает пустым stderr. `stalled_pr_triage.
cmd_queue` лечит это порядком (вызов `decision_doc_collision_pr_numbers` —
последним, после всего git-обхода измерений) и восстанавливает глубину
(`ensure_unshallow`) до и после — не трогая сам `decision_numbering.py`
(вне рамок этой задачи, его контракт — работать НА шаллоу дереве CI, не
беречь чужую полную историю). Тест — `test_ensure_unshallow_grows_a_shallow_
clone_to_full_history` (настоящий bare-репозиторий, настоящий
`--no-local --depth 1` клон).

## Не подтверждено

- Величина 5 (эквивалент уже в main) не автоматизирована и не проверялась
  массово на очереди 2026-09-14 этим PR — `decide()` принимает её как
  `None` по умолчанию для всех строк прогонов выше; ручное чтение
  по каждому PR — вне объёма этой задачи.
- Line-range fallback не различает СМЫСЛ строк — это по-прежнему не AST:
  пересечение диапазонов в markdown/json/yaml — сигнал «пересоздать/читать»
  наравне с git-конфликтом, не доказательство смысловой коллизии функций.
  AST для других языков (JS/TS) не делалось — не подтверждено, что нужно:
