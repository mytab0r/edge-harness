# ADR 0021. Триаж застрявшего в конфликте PR: шесть измеримых величин

- **Смежное:** [ADR 0016](0016-parallel-work-on-shared-code-boundaries.md) (профилактика конкуренции; это — операция после конкуренции),

## Контекст

19 PR простояли 5–9 суток в состоянии конфликта с `origin/main`. Для каждого нужно было
решение: довести сведение, пересоздать ветку и переоформить заново, или закрыть как
неактуальный. Сотни попыток перебора порогов на возраст ветки, размер конфликта и
количество открытых коммитов не разделили безнадёжные ветки от живых без шума.

Результат: **пороги не работают, нужно измерить реальное состояние**.

## Проблема

Попытки выбрать действие по одному критерию (порог возраста или объёма) дают либо ложные срабатывания (автозакрытие живой работы), либо упускают безнадёжные ветки.

**Живой замер (2026-09-12):**

Пороги, которые казались разумными:

- **«Отстал больше 100 коммитов»** → ловит все 4 безнадёжных, но заодно 6 живых (PR #542 — 128, #579 — 119, #596 — 117, #613 — 116, #638 — 111, #654 — 103). Уничтожил бы живую работу.
- **«Больше 400 строк конфликта»** → ловит 3 из 4 безнадёжных, 4 ложных срабатывания, #644 (189 строк) пропускает совсем.

Ни один порог не разделил группы без шума.

## Решение

**Решение принимается по шести ИЗМЕРИМЫМ величинам, без выбора между гипотезами:**

1. **Число конфликтующих хунков и строк конфликта** — результат `git merge-tree --write-tree` против `origin/main`. Один хунк — часто разрешимо вручную; десять и больше — проверить величину 2.

2. **Отставание базы PR в коммитах** — сколько коммитов добавилось в `origin/main` с момента merge-base. Числитель для расчёта дрейфа (величина 3).

3. **Дрейф `main` в тех же файлах** — сколько строк изменилось в `origin/main` в файлах, которые трогает PR, с момента merge-base. Это смысловое расстояние. Если дрейф > половины изменений PR в тех же файлах → механическое сведение рискует вернуть дефект или стереть нужную замену.

4. **Открыта ли задача PR** — задача резолвится ЕДИНСТВЕННЫМ путём этого репозитория:
   `scripts/lib/task_ref.py::resolve_pr_task` читает номер из имени ветки
   `agent/<N>-<slug>` (`task_from_branch`), НЕ тело PR — директивы `Closes #N`/`Fixes #N`
   в теле PR запрещены контрактом (`scripts/git/pr-create`, `scripts/lib/task_ref.py`,
   PROTOCOL.md п.7) и механически отклоняются ДО открытия PR, поэтому их в теле нет и
   искать там нечего. Состояние самой задачи — Issues API (`open`/`closed`, с учётом
   `state_reason`). Закрытая задача косвенно говорит: авторы потеряли интерес, либо
   вариант был дорогой и посчитали, что лучше пересоздать. Открытая — сигнал, что работа
   ещё актуальна.

5. **Существуют ли уже в `main` артефакты, которые PR добавляет** — проверка гипотезы «работа сделана другим способом». Например, если PR добавляет функцию `make_session_note`, а в `main` уже есть та же функция — это либо дублирование, либо переделка с другим имением. Читать, проверить по смыслу, не по наличию.

6. **Несёт ли PR вердикт на доработку** — метки второго гейта (`ai:changes-requested` или
   `ai:failed`, см. `docs/agents/LABELS.md`/`scripts/lib/review_labels.py`) на ТЕКУЩЕМ head
   PR. После сведения (механического ребейза) новый прогон `ai-review` не гарантирован:
   если отпечаток диффа не изменился (`review_labels.diff_unchanged`), уже висящая метка
   сохраняется как есть — то есть вердикт, который PR несёт СЕЙЧАС, и есть его судьба
   после сведения, если содержательно диф не сдвинулся. Наличие такого вердикта продлит
   цикл — влияет на окончательную цену решения; пересоздание может оказаться дешевле, чем
   сведение + новый ревью.

## Правило: как шесть величин превращаются в действие

Соответствие «показания → действие» — не порог на одной величине, а прочтение ВСЕХ шести вместе:

| Показания | Действие |
|---|---|
| Величины 1–3 малы (конфликт разрешим, дрейф несущественный), задача 4 открыта, величина 5 не находит замены в main, величина 6 без вердикта на доработку | **Довести сведение** — механический или ручной ребейз, PR доезжает как есть. |
| Величина 5 находит эквивалент уже в `main` (дублирование подтверждено чтением, не только совпадением имени) | **Закрыть как неактуальный** — работа уже сделана, вне зависимости от величин 1–3. |
| Задача 4 закрыта (`state_reason=completed`/`not_planned`) И величина 5 не находит замены | **Закрыть как неактуальный** — автор потерял интерес или решил иначе; сведение чужой воли не заменяет. |
| Величины 1–3 велики (много хунков, дрейф превышает половину изменений PR в тех же файлах), задача 4 открыта, величина 5 не находит замены | **Пересоздать ветку** — механическое сведение по величине 3 рискует вернуть дефект или стереть нужную правку `main`; дешевле переписать PR поверх текущего `main`, чем распутывать смысловой дрейф. |
| Величина 6 несёт вердикт на доработку, а величины 1–3 уже велики | **Пересоздать**, не доводить — цена «сведение + повторный ai-review + доработка находок» в среднем дороже переписывания. |

**Разобранный пример (PR #644, 2026-09-12):** величины 1 — 2 хунка / 189 строк конфликта
(формально дёшево); величина 3 — `main` добавил `_SESSION_NOTE_SEQ`/
`_session_note_message_id` (PR #795/#794) в ту же функцию, которую PR #644 заменяет
целиком — смысловой дрейф, не подсчитываемый строками; величина 5 не находит эквивалента
(PR #644 решает другую задачу, не дублирует #794). Табличное правило по одним лишь
величинам 1/2 сказало бы «довести» — но величина 3 (смысловое столкновение, требует
ЧТЕНИЯ, см. «Что машине отдать нельзя» ниже) меняет вывод на «пересоздать»: механическое
сведение вернуло бы дефект холодной загрузки сессии (класс, чиненный трижды — #794,
#809/PR #868, #871/PR #872).

## Почему это работает

Каждая из этих величин отвечает на **разный вопрос**:

- (1) **«Конфликт разрешимый?»** — техническая возможность.
- (2–3) **«Откуда появилась базовая версия? Как много изменилось с тех пор?»** — устаревание и конкуренция.
- (4) **«Задача ещё активна?»** — деловой интерес.
- (5) **«Давно ли уже есть готовое?»** — дублирование и замена.
- (6) **«Какова полная цена решения?»** — инвестиция после сведения.

Пороги одного из них не работают, потому что каждый отвечает только на одну часть вопроса. **Решение требует ответов на все шесть.**

## Что машине отдать можно, что нельзя

**Машинно проверяемо** (числа, факты, API):
- Все шесть величин выше.
- Коллизия номеров инвариантов (номер объявлен в исходнике — grep, задача #904, отдельно от этого ADR).

**НЕ машине** (требует чтения и суждения):
- Смысловое столкновение. Живой пример (PR #644, см. «Правило» выше): дешёвый по строкам конфликт, но функция заменяется целиком, а `main` добавил фикс в ту же часть — CI не ловит, потому что это смысловое аннулирование, не синтаксический конфликт.
- Решение «этот механизм критичен, его не трогаем» — выбор приоритета.

Эти выборы живут в **задании агенту**, не в гвардии, и **называются честно**, не выдаются за проверку.

## Скрытая мина

Два PR (#883 и #870) независимо претендовали на один и тот же номер инварианта. Каждый по отдельности сводится успешно, вместе дают молча-неверный реестр в сигналах владельцу.

Это **регрессия приёма из ADR 0016** — номер инварианта это регистрация, но вручную назначаемая, не как каталог файлов. Решение: либо стабильный ключ (имя инварианта), либо порядковый номер, вычисляемый из реестра. Эта задача — отдельная (#904, упомянута в ADR 0016). Тот же класс на другом носителе (номера `docs/decisions`/`docs/research`, не `repo_invariants.py`) закрывает задача #1078 — на момент этого ADR её ADR ещё не слит в `main`, ссылка на конкретный файл не даётся намеренно (не подтверждён итоговый номер).

## Почему номер 0021, не 0018

0018/0019/0020 на момент этого PR заняты другими открытыми PR (номер вычислен инструментом
задачи #1078 — `scripts/lib/decision_numbering.py`, команда `next docs/decisions`, читает
main И все открытые PR, не только локальный каталог; на момент ЭТОГО ADR сам инструмент
ещё не слит в `main` — он живёт в открытом PR #1082, вызван локально из его ветки). Гэп в
номерах — ожидаемое следствие параллельной работы, не пропуск: до #1078 такой гэп нельзя
было объяснить машиной, после слияния #1082 — можно.

## Не подтверждено

- Существует ли чеклист для проверки смыслового столкновения (п. «Что машине отдать нельзя»), или это полностью вручную. Проверено только на одном примере (PR #644).
- Точный список номеров всех 19 PR замера 2026-09-12 (кроме шести живых, названных в разделе «Проблема», и четырёх безнадёжных, не названных поимённо) — не сохранён отдельным артефактом на момент этого ADR; раздел «Проблема» несёт то, что удалось восстановить.

## Адреса в коде и задачах

Триаж не привязан к одной задаче; это общий метод, применённый к каждому из 19 PR отдельно (задача #1034). Разбор конкретных 19 PR замера — не адресован отдельным артефактом (см. «Не подтверждено»).
