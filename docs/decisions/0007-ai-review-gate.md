# ADR 0007. AI-ревью как второй гейт: своя метка ai:*, двойное условие слияния

- **Дата:** 2026-08-31
- **Статус:** принято (реализовано в задаче #18)
- **Смежное:** [протокол агентов](../agents/PROTOCOL.md),
  [playbook воркера](../agents/WORKER-PLAYBOOK.md),
  ADR [0002](0002-loop-in-runner-not-do.md) (агент-цикл в раннере),
  задача #18

## Контекст

Детерминированное ревью (`scripts/review/check_pr.py`, workflow `pr-review`)
ловит секреты, файлы секретов, размер и некомпилируемые скрипты — и ставит
метку `review:ok`. Этого мало: «строка не похожа на секрет» ничего не говорит
о соответствии диффа ADR/спекам и о скрытых регрессиях. Владелец делегировал
эту часть ревью агенту (курс «автономный разработчик», эпик #17), ограничив
его trust-zone: **AI-ревьюер не постит в интернет и не имеет секретов** —
живое решение того же владельца в репо Harness (pr_loop.py + pr_review.md)
уже доказало паттерн: модель только отвечает текстом с машиночитаемым
вердиктом в последней строке, публикует доверенный код.

Требование задачи #18: после `review:ok` — содержательное ревью (соответствие
ADR/спекам, скрытые регрессии, предложения задач в беклог); вердикт —
метка-триггер для оркестратора; из ревью задачи заводятся в пул одной командой.

## Решение

**Два гейта — две метки, слияние требует обе.**

1. **Метки-вердикты AI-ревью — свой неймспейс:** `ai:ok` /
   `ai:changes-requested` / `ai:failed` (инфраструктурный сбой: модель
   недоступна, ответ сломан). Имена и формулировка гейта — одно место правды:
   [`scripts/lib/review_labels.py`](../../scripts/lib/review_labels.py),
   потребляют его `check_pr.py`, `scheduler.py` и `ai_review.py`.
2. **Оркестратор сливает при (`review:ok` ЛИБО `review:large`+`review:large-ok`,
   #702) И `ai:ok`**
   (`scheduler.merge_queue` → `review_labels.merge_label_gate`). «Та же
   метка-триггер» — тот же механизм (метка как условие слияния), что у первого
   гейта, но не та же строка: у каждого гейта свой автор вердикта, и смешение
   авторов в одной метке ломает диагностику «кто заблокировал PR».
3. **Trust-зона: граница доверия — между job'ами, а не между env.** Workflow
   `ai-review` состоит из двух job'ов. Job `review`: недоверенный DSH-шаг не
   получает GitHub-токенов вовсе; всё, что агент может испортить (файлы
   воркспейса, `$GITHUB_ENV`/`$GITHUB_PATH`, PATH), умирает вместе с
   виртуалкой job'а; права job'а — только чтение (contents/pull-requests/
   issues), поэтому даже случайно уцелевшие креды чекаута не могут постить.
   Job `verdict`: свежая машина, чекаут скриптов из `ref: main` (переписать
   исполняемый код из недоверенного job'а нельзя), свой GH_TOKEN с
   pull-requests:write. Ответ ревью переезжает между job'ами выводом
   доверенного шага — это данные, не код. Дополнение после живого прогона на
   PR #108: доверенный код чекаутится ТОЛЬКО из main, а дерево PR лежит
   рядом (`pr-head`) и для агента является данными — ревьюимый PR физически
   не может подсунуть скрипт под токен. `DEEPSEEK_API_KEY` нужен вызову
   модели и скрыт от шеллов агента самим DSH (scrub `*TOKEN*/*KEY*/*SECRET*`,
   проверено живым прогоном 2026-08-30, см. worker.yml). Разрез по env
   alone (один job, шаги без токена) отвергнут по итогам живого ревью PR #137:
   `$GITHUB_ENV` и workspace общие для шагов — непрямая prompt-инъекция через
   ревьюимый дифф получала шанс исполнить переписанный агентом код уже
   с токеном.
4. **Контракт вердикта — как в Harness:** последняя непустая строка ответа
   ровно `ВЕРДИКТ: approve|rework`; маркера нет, их два или он не последний —
   `error`: неоднозначность никогда не одобряет. `approve → ai:ok`,
   `rework → ai:changes-requested`, `error → ai:failed` + красный job
   (fail loud); повтор — `workflow_dispatch` с номером PR. **Дельта
   2026-09-09 (#210):** `rework` без единой находки (findings-проза, блок
   `ЗАМЕЧАНИЕ`, блок `ЗАДАЧА` — все три пусты) тоже считается нарушением
   контракта, а не валидным `ai:changes-requested`: живой случай — PR #206
   (run 33656180906), весь ответ модели `ВЕРДИКТ: rework\n`, PR встал с
   пустым комментарием. Такой ответ переквалифицируется в `error` (`ai:failed`
   + тот же авто-повтор #196) — см. `ai_review.py::rework_without_findings`,
   `ai-review-empty-rework-contract`.
5. **Вердикт привязан к head.** Гонку «оркестратор слил до/по протухшему
   вердикту» закрывают два механизма: verdict-шаг применяет вердикт только
   если head PR не сменился с момента gather; детерминированное ревью при
   каждом запуске (оно выполняется на каждый пуш) снимает все `ai:*`-метки —
   до появления свежей метки нового AI-ревью гейт слияния закрыт.
6. **Задачи в беклог — из самого ревью одной командой:** агент предлагает
   блоки `ЗАДАЧА: … КОНЕЦ ЗАДАЧИ`, транспорт переносит их в комментарий
   каноническими фенсами ```` ```задача ```` рядом с шапкой-фактами
   (`pr:`/`head:`/`reviewer:` — как в Harness, состояние живёт в PR);
   `python scripts/review/file_tasks.py --pr N` заводит их issue с меткой
   `task`, идемпотентно по заголовку открытой задачи. **Дельта 2026-09-06
   (#426):** каждый блок несёт обязательное поле `МАСШТАБ: хвост|отдельно`;
   фенсится (и заводится issue) только `отдельно`, `хвост` уходит прозой в
   PR без issue, отсутствие поля — fail loud (видимо в комментарии, не
   заведено автоматически) — см. `review-task-scope-split`.

## Отвергнутые варианты

- **Переиспользовать `review:ok` как единственную метку, AI меняет её сам**
  (снимает на старте ревью, ставит по вердикту). Два писателя на одной метке —
  ноль мест правды; краш между «снял» и «поставил» оставляет PR без вердикта
  навсегда; окно «review:ok стоит, AI ещё не начал» — до 15 минут (тик
  оркестратора) — допускает слив без второго гейта молча. Возврат: если
  GitHub даст атомарный «conditional label» — нет.
- **Вердикт как check-run (GitHub Checks).** Механизм чужой первому гейту
  (метки), требует `checks:write` и разбор статусов в merge_queue; выигрыша
  против метки нет, цена — вторая механика гейта в оркестраторе.
- **Состояние только в комментарии, как в Harness pr_loop (без меток).**
  У нас уже есть потребитель меток (merge_queue) и писатель на каждый пуш
  (check_pr) — метка дешевле и снимается структурно; комментарий оставлен как
  носитель фактов для file_tasks и аудита, не как гейт.
- **Дать агенту токен «на один комментарий».** Прямое нарушение trust-zone
  задачи #18; любой промах промпта превращается в пост от имени владельца.
- **Один workflow на оба гейта.** Последовательность «детерминированное →
  AI» уже выражена триггером `workflow_run` (завершение pr-review; метки
  GITHUB_TOKEN событий не создают — research/21); сливать их — значит
  повторять условие первого гейта внутри второго и терять независимый
  перезапуск каждого.

## Не подтверждено

- Стабильность контракта последней строки на GLM-5 в DSH-обёртке: паттерн
  доказан владельцем в Harness на `claude` CLI; на нашем стеке закроется
  живым прогоном на первом PR (пост-мерж проверка задачи #18). При series
  отказов контракта — ужесточение промпта или повтор, не смена контракта.

## Дельта 2026-09-05: п.5 — привязка к head сузилась до отпечатка диффа, снятие условное

**Повод.** П.5 в исходной редакции утверждал «детерминированное ревью при
каждом запуске снимает все `ai:*`-метки»: верно на момент принятия, но задача
#294 (диагноз по PR #292) вскрыла случай, где это правило было избыточно
строгим — чистое подтягивание `main` без конфликтов меняет `head` (новый
merge-коммит), но не патчи PR относительно base. Безусловный снос вердикта
на каждый такой пуш жёг AI-квоту вхолостую и требовал повторного дорогого
ревью кода, который уже проверен.

**Что изменилось.** `check_pr.py` снимает `ai:*`-метку, только если
отпечаток диффа (`review_labels.diff_fingerprint`, sha256 по отсортированному
списку `имя:статус:blob-sha` из `pulls/{n}/files`) действительно изменился
относительно того, что сохранён в шапке последнего AI-комментария
(`review_labels.diff_unchanged`) — см. `scripts/lib/review_labels.py`. Сам
workflow `ai-review.yml` при этом всё ещё стартует на каждый `workflow_run` от
`pr-review` (см.
`openspec/changes/archive/ai-verdict-survives-merge/specs/journal-tasks-hands/spec.md`),
но шаг `fingerprint` job'а `review` сверяет то
же условие (`ai_review.py::cmd_should_run`,
`review_labels.should_run_ai_review` — одно место правды с `check_pr.py`) и
отдаёт `go=false` до чекаута `pr-head`/`gather`/DSH, если дорогой прогон не
нужен: метка на месте, дифф не менялся, вердикт не `ai:failed`.

**Ручной путь пересмотра не глохнет** (находка 1 вердикта ai-review PR #294,
2026-09-05): сверка отпечатка — эвристика автоматического триггера, а не
условие самого гейта, поэтому `workflow_dispatch` обязан её игнорировать.
Владелец, не согласный с существующим `ai:ok`/`ai:changes-requested` на
неизменном диффе (например, хочет пересмотра без правки кода), иначе терял бы
единственный документированный путь повтора (п.4 этого ADR): ручной запуск
превращался бы в зелёный no-op без единой строчки ревью, а отпечаток без
нового пуша сдвинуть нечем даже пустым коммитом. Шаг `fingerprint` при
`github.event_name == 'workflow_dispatch'` вызывает `should-run --force` —
подкоманда отвечает `true` без обращения к сети, дорогой прогон идёт
безусловно. `ai:failed` как и раньше никогда не пропускает прогон (газ #196,
автоповтор по таймеру от отпечатка не зависит).

## Дельта 2026-09-06: безусловный `--force` на любом `workflow_dispatch` жёг деньги — сузился до явного входа + гонка «прогон уже летит»

**Повод.** Аудит 197 платных прогонов `ai-review` за 2026-09-05/06 нашёл
утечку: 44 из них (22%) — ручные `workflow_dispatch` под личным токеном
владельца, дублирующие уже идущий или уже завершённый прогон на том же PR,
БЕЗ `ai:failed` (единственного законного основания для повтора по этому ADR).
Причина — реализация предыдущей дельты 2026-09-05 сделала `--force`
безусловным для ЛЮБОГО `workflow_dispatch`, а не только для осознанного
намерения пересмотра: `cmd_should_run --force` печатает `true` без обращения
к сети целиком, то есть сверка отпечатка не выполнялась вовсе ни разу, когда
запуск был ручным — оркестратор не отличал «владелец хочет пересмотра» от
«кто-то нажал Run workflow по инерции поверх уже идущего или завершённого
прогона».

**Что изменилось.**

1. `--force` теперь ставится в `ai-review.yml` только при явном входе
   `force: true` (новый `workflow_dispatch.inputs.force`, `default: false`) —
   без него ручной запуск проходит ТУ ЖЕ сверку отпечатка, что и
   автоматический (`review_labels.should_run_ai_review`), и получает
   объясняющий отказ в stderr шага (`manual_dispatch_skip_reason`
   в `scripts/review/ai_review.py`): какой вердикт стоит, когда вынесен,
   что автоматический прогон придёт сам при изменении диффа, и как
   пересмотреть тот же дифф осознанно (`force: true`).
2. Отдельная гонка, которую сверка отпечатка не ловит: PR ещё БЕЗ вердикта
   (первое ревью), но прогон этого же PR уже летит прямо сейчас —
   `should_run_ai_review` честно ответил бы `true` (вердикта нет, прогон
   нужен), хотя второй одновременный прогон бессмыслен. Признак «прогон про
   PR N» — `run-name` самого workflow (`github.event.inputs.pr` у
   `workflow_dispatch`, `github.event.workflow_run.pull_requests[0].number`
   у `workflow_run`), так как `head_branch`/`head_sha` самого `ai-review`-рана
   всегда `main` (job чекаутит `main` первым шагом) независимо от триггера —
   матч по ним не отличает прогоны разных PR вовсе. Проверяется
   `review_labels.other_active_ai_review_runs` (API
   `actions/workflows/ai-review.yml/runs?status=in_progress|queued`) — ДО
   `--force`: второй прогон одновременно с уже летящим отклоняется, даже
   если вход нёс `force: true` явно.
3. `permissions.actions: read` добавлен в `ai-review.yml` — без него
   `GITHUB_TOKEN` job'а `review` получал бы `actions: none` (GitHub обнуляет
   не перечисленные в `permissions:` пункты), и запрос списка прогонов
   падал бы 403 на каждом ручном запуске.

**Три случая, которые обязаны продолжать работать после этой правки:**
`ai:failed` (автоповтор #196 от отпечатка не зависит — не проходит через
эту сверку вовсе), явный `force: true` (пересмотр того же диффа — но не
поверх летящего прогона), и отказ по занятости (второй прогон одновременно
с уже идущим — бессмыслен независимо от `force`).

## Дельта 2026-09-06: третья категория находок — чеклист некритичных замечаний в теле PR (#462)

**Повод.** Контракт п.4 разрешал `approve` при находках, которые «некритичны
для мержа», не называя, куда такая находка девается — она оставалась голой
прозой в комментарии. Замер по 29 просмотренным `approve`-вердиктам
(2026-09-06): 3 PR (#452, #285, #180) содержат явные некритичные находки
прозой («Два замечания, оба не блокируют мерж», «Единственное замечание (не
блокирующее)») — 5 штук суммарно, ни одна не стала ни блокером, ни задачей;
PR слился, замечание пропало вместе с прокруткой комментариев.

**Что изменилось.**

1. Контракт `ai_prompt.md` называет РОВНО три исхода находки, не два: блокирует
   мерж → проза (до 5, как раньше) → `rework`; некритично, но стоит сделать →
   блок `ЗАМЕЧАНИЕ: … КОНЕЦ ЗАМЕЧАНИЯ` (тот же стиль парсинга, что `ЗАДАЧА`);
   работа вне рамок PR → блок `ЗАДАЧА` (без изменений). Формулировка вердикта
   `approve` в контракте перестала звучать «замечаний нет или они некритичны»
   — теперь «блокирующих находок нет», некритичные явно вынесены отдельно.
2. Блоки `ЗАМЕЧАНИЕ` сливаются `scripts/review/ai_review.py::cmd_verdict` не
   в комментарий, а в ЧЕКЛИСТ ТЕЛА PR (`scripts/lib/review_checklist.py`,
   секция между HTML-маркерами `<!-- ai-review:checklist:begin/end -->`):
   тело — постоянный носитель, не тонет среди комментариев. Автор отмечает
   пункт нативным GitHub-чекбоксом в описании PR — второго механизма
   отметки нет и не создаётся. Повторный раунд ревью ДОПИСЫВАЕТ новые пункты
   по заголовку (дедупликация), уже отмеченные не трогает.
3. Слияние с незакрытым чеклистом НЕ блокируется (иначе некритичное стало бы
   критичным — тот же класс решения, что развёл `review:large` от
   `review:changes-requested`) и не теряется молча: `after_merge` в
   `scheduler.py` читает незакрытые пункты и заводит ОДНУ задачу-хвост со
   ссылкой на PR (`review_checklist.tail_issue_*`, идемпотентно по заголовку
   «Хвост чеклиста ревью PR #N») — не issue на каждый пункт.
4. Оценка ценности/приоритета задачи-хвоста — решение человека, не машины:
   задача наследует только ссылку на породивший PR и метку `task`, попадает
   в общий пул (сейчас — по возрасту; приоритет по графу блокировок из #367
   не смержен на момент этой дельты). Второй оценщик не изобретён.

## Дельта 2026-09-08: п.2 — гейт 1 засчитан и по `review:large`+`review:large-ok` (#702)

**Повод.** Живой случай PR #333/#618: `apply_large_ok` (`ai_review.py`)
ставит `review:large-ok` МЕТКОЙ, без нового пуша, а `pr-review.yml`
(`check_pr.py`, где формируется `review:ok`) реагирует только на
`opened/synchronize/reopened` — событие простановки своей же метки его не
перезапускает. `review:ok` мог не появиться никогда без постороннего пуша,
хотя размер уже принят и AI уже одобрил (`ai:ok`): `merge_label_gate`
требовал буквально `review:ok` и держал слияние закрытым бесконечно —
тормоз без газа.

**Что изменилось.** `merge_label_gate` (`scripts/lib/review_labels.py`)
засчитывает гейт 1 ЛИБО буквальным `review:ok`, ЛИБО связкой
`review:large`+`review:large-ok` — тот же порог, что `check_pr.py::size_gate`
уже применяет на момент простановки метки. `ai:ok` остаётся обязательным в
обоих случаях — п.2 в исходной редакции не ослаблен, только гейт 1 внутри
него получил второй, ранее недостижимый путь прохождения. Тот же предикат
управляет и выборочным подтягиванием ветки (`should_update_branch`), которое
делегирует решение `merge_label_gate` напрямую — починка одного места
закрывает оба симптома (PR не сливается И PR не подтягивает main).

**Известное расхождение, не починено этой дельтой:** commit-статус
`harness/review` (см. `docs/decisions/verdict-commit-status`) вычисляется
`review_status_state` из вердикт-метки на момент последнего пуша и не
перепубликуется, когда `review:large-ok` появляется отдельной меткой —
статус может остаться `failure`, пока `merge_label_gate` уже открыт. Не
блокирует сегодняшнее слияние (required status checks на этот контекст
ещё не включены), но станет тормозом без газа, если #345 включит
`harness/review` в `required_status_checks` раньше починки — заведено

## Дельта 2026-09-11: диффы сверх `LARGE_DIFF_HUGE_LINES` — суждение модели вместо эскалации владельцу (#939, отменяет #204 п.«escalate»/#901)

**Повод.** Мандат владельца 2026-09-11: единственное, что законно требует
его личного участия в этом конвейере, — креденшелы, которых нет в
Cloudflare/GitHub (деньги, необратимые действия). Размер диффа — не то и не
другое: содержание диффа модель и так читает целиком, вопрос «оправдан ли
объём» для неё не сложнее вопроса «есть ли скрытая регрессия». Исходная
редакция п.3 (эскалация владельцу диффов сверх `LARGE_DIFF_HUGE_LINES`,
`ai_review.py::huge_diff_escalation_text`) и её починка доставки (#884,
дельта в `scripts/orchestra/pulse_guard.py`) не сработали как задумано:
живые PR #870 (+2472) и #408 (+3548) простояли с `ai:ok`+`review:large` без
`review:large-ok` — issue #901 назвала это тормозом без газа (эскалация
привязана к моменту вынесения вердикта, а у этих PR вердикт УЖЕ вынесен,
нового ревью не будет, пока не сдвинется голова).

**Что изменилось.** Порог `LARGE_DIFF_HUGE_LINES` (2000 строк) СОХРАНЁН, но
перестал быть стоп-краном к человеку. Для диффов сверх него промпт
(`ai_prompt.md`, `$size_section`/`ai_review.py::size_question_section`)
задаёт ОТДЕЛЬНЫЙ явный вопрос о размере — оправдан ли объём содержанием
задачи, или он раздут случайно включёнными generated/vendored/lock-файлами,
мусором сборки, чужими правками. Контракт ответа несёт СВОЮ машиночитаемую
строку, симметричную по строгости строке `ВЕРДИКТ:`, но отдельную от неё
(`ai_review.py::parse_size_verdict`/`huge_diff_size_gate`):

    РАЗМЕР: оправдан
    РАЗМЕР: раздут: <что именно выкинуть>

`cmd_verdict` читает это суждение ДО выбора вердикт-метки и, если нужно,
переопределяет уже разобранный `ВЕРДИКТ:` модели (belt-and-suspenders —
модель может ошибиться и в самой строке `ВЕРДИКТ:`, когда пишет «раздут»):
«оправдан» ведёт себя как диапазон 800–2000 (approve даёт `review:large-ok`
автоматически); «раздут» форсирует `rework` с находкой (что выкинуть) —
автору есть что чинить и газ перезапросить ревью после чистки диффа;
отсутствие суждения там, где строка обязательна (нет вовсе, две сразу,
другая форма), — нарушение контракта, тот же класс, что пустой `rework` без
находок (#210): вердикт уходит как `error`/`ai:failed`, не тихий `approve`.
`large_ok_decision` (`ai_review.py`) больше не знает про этот порог вовсе —
решение по нему принято выше по стеку, ДО того, как эта функция вызвана.

Эскалация владельцу убрана из кода целиком: `huge_diff_escalation_text`,
`escalation_fully_failed` и вызов `pulse_guard.escalate` в `apply_large_ok`
удалены; `issues: write` и секреты `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`
сняты с job'а `verdict` в `ai-review.yml` (держались только ради этого
канала — гвардия `scripts/lib/test_job_permissions_issues_write_guard.py`
подтверждает мутацией, что класс #884 для этого job'а закрыт по существу,
не просто выведен из-под проверки).

**Разблокировка уже застрявших (#870/#408).** Правка политики сама по себе
их не трогает — вердикт `ai:ok` у них уже вынесен ДО правки, а
`should_run_ai_review` не назначит новый прогон на неизменном диффе (та же
дыра, что назвала #901). Газ — `scheduler.py::stuck_large_ok_pulls`,
периодический пульс: для каждого открытого PR с `ai:ok`+`review:large` без
`review:large-ok` форсирует ОДИН `workflow_dispatch ai-review.yml` с
`input force: true` (тот же путь, что уже даёт владельцу пересмотр
неизменного диффа, #294) — идемпотентно, маркер-комментарий в самом PR не
даёт повторить форс-прогон дважды. Свежий ответ модели пройдёт через уже
исправленный `huge_diff_size_gate` тем же путём, что и любой новый PR;
человек в этом пути не участвует. Issue #901 закрыта этой дельтой как
устаревшая (эскалация, которую она просила чинить доставкой, убрана из
кода вовсе).
