# ADR 0007. AI-ревью как второй гейт: своя метка ai:*, двойное условие слияния

- **Дата:** 2026-08-31
- **Статус:** принято (реализовано в задаче #18)
- **Смежное:** [протокол агентов](../agents/PROTOCOL.md),
  [playbook воркера](../agents/WORKER-PLAYBOOK.md),
  ADR [0002](0002-loop-in-runner-not-do.md) (агент-цикл в раннере),
  задача #18

## Контекст

Детерминированное ревью (`scripts/review/check_pr.py`, workflow `pr-review`)
ловит секреты, файлы секретов, размер и некомпилируемые скрипты — и ставит
метку `review:ok`. Этого мало: «строка не похожа на секрет» ничего не говорит
о соответствии диффа ADR/спекам и о скрытых регрессиях. Владелец делегировал
эту часть ревью агенту (курс «автономный разработчик», эпик #17), ограничив
его trust-zone: **AI-ревьюер не постит в интернет и не имеет секретов** —
живое решение того же владельца в репо Harness (pr_loop.py + pr_review.md)
уже доказало паттерн: модель только отвечает текстом с машиночитаемым
вердиктом в последней строке, публикует доверенный код.

Требование задачи #18: после `review:ok` — содержательное ревью (соответствие
ADR/спекам, скрытые регрессии, предложения задач в беклог); вердикт —
метка-триггер для оркестратора; из ревью задачи заводятся в пул одной командой.

## Решение

**Два гейта — две метки, слияние требует обе.**

1. **Метки-вердикты AI-ревью — свой неймспейс:** `ai:ok` /
   `ai:changes-requested` / `ai:failed` (инфраструктурный сбой: модель
   недоступна, ответ сломан). Имена и формулировка гейта — одно место правды:
   [`scripts/lib/review_labels.py`](../../scripts/lib/review_labels.py),
   потребляют его `check_pr.py`, `scheduler.py` и `ai_review.py`.
2. **Оркестратор сливает при `review:ok` И `ai:ok`**
   (`scheduler.merge_queue` → `review_labels.merge_label_gate`). «Та же
   метка-триггер» — тот же механизм (метка как условие слияния), что у первого
   гейта, но не та же строка: у каждого гейта свой автор вердикта, и смешение
   авторов в одной метке ломает диагностику «кто заблокировал PR».
3. **Trust-зона: граница доверия — между job'ами, а не между env.** Workflow
   `ai-review` состоит из двух job'ов. Job `review`: недоверенный DSH-шаг не
   получает GitHub-токенов вовсе; всё, что агент может испортить (файлы
   воркспейса, `$GITHUB_ENV`/`$GITHUB_PATH`, PATH), умирает вместе с
   виртуалкой job'а; права job'а — только чтение (contents/pull-requests/
   issues), поэтому даже случайно уцелевшие креды чекаута не могут постить.
   Job `verdict`: свежая машина, чекаут скриптов из `ref: main` (переписать
   исполняемый код из недоверенного job'а нельзя), свой GH_TOKEN с
   pull-requests:write. Ответ ревью переезжает между job'ами выводом
   доверенного шага — это данные, не код. Дополнение после живого прогона на
   PR #108: доверенный код чекаутится ТОЛЬКО из main, а дерево PR лежит
   рядом (`pr-head`) и для агента является данными — ревьюимый PR физически
   не может подсунуть скрипт под токен. `DEEPSEEK_API_KEY` нужен вызову
   модели и скрыт от шеллов агента самим DSH (scrub `*TOKEN*/*KEY*/*SECRET*`,
   проверено живым прогоном 2026-08-30, см. worker.yml). Разрез по env
   alone (один job, шаги без токена) отвергнут по итогам живого ревью PR #137:
   `$GITHUB_ENV` и workspace общие для шагов — непрямая prompt-инъекция через
   ревьюимый дифф получала шанс исполнить переписанный агентом код уже
   с токеном.
4. **Контракт вердикта — как в Harness:** последняя непустая строка ответа
   ровно `ВЕРДИКТ: approve|rework`; маркера нет, их два или он не последний —
   `error`: неоднозначность никогда не одобряет. `approve → ai:ok`,
   `rework → ai:changes-requested`, `error → ai:failed` + красный job
   (fail loud); повтор — `workflow_dispatch` с номером PR.
5. **Вердикт привязан к head.** Гонку «оркестратор слил до/по протухшему
   вердикту» закрывают два механизма: verdict-шаг применяет вердикт только
   если head PR не сменился с момента gather; детерминированное ревью при
   каждом запуске (оно выполняется на каждый пуш) снимает все `ai:*`-метки —
   до появления свежей метки нового AI-ревью гейт слияния закрыт.
6. **Задачи в беклог — из самого ревью одной командой:** агент предлагает
   блоки `ЗАДАЧА: … КОНЕЦ ЗАДАЧИ`, транспорт переносит их в комментарий
   каноническими фенсами ```` ```задача ```` рядом с шапкой-фактами
   (`pr:`/`head:`/`reviewer:` — как в Harness, состояние живёт в PR);
   `python scripts/review/file_tasks.py --pr N` заводит их issue с меткой
   `task`, идемпотентно по заголовку открытой задачи.

## Отвергнутые варианты

- **Переиспользовать `review:ok` как единственную метку, AI меняет её сам**
  (снимает на старте ревью, ставит по вердикту). Два писателя на одной метке —
  ноль мест правды; краш между «снял» и «поставил» оставляет PR без вердикта
  навсегда; окно «review:ok стоит, AI ещё не начал» — до 15 минут (тик
  оркестратора) — допускает слив без второго гейта молча. Возврат: если
  GitHub даст атомарный «conditional label» — нет.
- **Вердикт как check-run (GitHub Checks).** Механизм чужой первому гейту
  (метки), требует `checks:write` и разбор статусов в merge_queue; выигрыша
  против метки нет, цена — вторая механика гейта в оркестраторе.
- **Состояние только в комментарии, как в Harness pr_loop (без меток).**
  У нас уже есть потребитель меток (merge_queue) и писатель на каждый пуш
  (check_pr) — метка дешевле и снимается структурно; комментарий оставлен как
  носитель фактов для file_tasks и аудита, не как гейт.
- **Дать агенту токен «на один комментарий».** Прямое нарушение trust-zone
  задачи #18; любой промах промпта превращается в пост от имени владельца.
- **Один workflow на оба гейта.** Последовательность «детерминированное →
  AI» уже выражена триггером `workflow_run` (завершение pr-review; метки
  GITHUB_TOKEN событий не создают — research/21); сливать их — значит
  повторять условие первого гейта внутри второго и терять независимый
  перезапуск каждого.

## Не подтверждено

- Стабильность контракта последней строки на GLM-5 в DSH-обёртке: паттерн
  доказан владельцем в Harness на `claude` CLI; на нашем стеке закроется
  живым прогоном на первом PR (пост-мерж проверка задачи #18). При series
  отказов контракта — ужесточение промпта или повтор, не смена контракта.

## Дельта 2026-09-05: п.5 — привязка к head сузилась до отпечатка диффа, снятие условное

**Повод.** П.5 в исходной редакции утверждал «детерминированное ревью при
каждом запуске снимает все `ai:*`-метки»: верно на момент принятия, но задача
#294 (диагноз по PR #292) вскрыла случай, где это правило было избыточно
строгим — чистое подтягивание `main` без конфликтов меняет `head` (новый
merge-коммит), но не патчи PR относительно base. Безусловный снос вердикта
на каждый такой пуш жёг AI-квоту вхолостую и требовал повторного дорогого
ревью кода, который уже проверен.

**Что изменилось.** `check_pr.py` снимает `ai:*`-метку, только если
отпечаток диффа (`review_labels.diff_fingerprint`, sha256 по отсортированному
списку `имя:статус:blob-sha` из `pulls/{n}/files`) действительно изменился
относительно того, что сохранён в шапке последнего AI-комментария
(`review_labels.diff_unchanged`) — см. `scripts/lib/review_labels.py`. Сам
workflow `ai-review.yml` при этом всё ещё стартует на каждый `workflow_run` от
`pr-review` (см. `openspec/changes/ai-verdict-survives-merge/specs/
journal-tasks-hands/spec.md`), но шаг `fingerprint` job'а `review` сверяет то
же условие (`ai_review.py::cmd_should_run`,
`review_labels.should_run_ai_review` — одно место правды с `check_pr.py`) и
отдаёт `go=false` до чекаута `pr-head`/`gather`/DSH, если дорогой прогон не
нужен: метка на месте, дифф не менялся, вердикт не `ai:failed`.

**Ручной путь пересмотра не глохнет** (находка 1 вердикта ai-review PR #294,
2026-09-05): сверка отпечатка — эвристика автоматического триггера, а не
условие самого гейта, поэтому `workflow_dispatch` обязан её игнорировать.
Владелец, не согласный с существующим `ai:ok`/`ai:changes-requested` на
неизменном диффе (например, хочет пересмотра без правки кода), иначе терял бы
единственный документированный путь повтора (п.4 этого ADR): ручной запуск
превращался бы в зелёный no-op без единой строчки ревью, а отпечаток без
нового пуша сдвинуть нечем даже пустым коммитом. Шаг `fingerprint` при
`github.event_name == 'workflow_dispatch'` вызывает `should-run --force` —
подкоманда отвечает `true` без обращения к сети, дорогой прогон идёт
безусловно. `ai:failed` как и раньше никогда не пропускает прогон (газ #196,
автоповтор по таймеру от отпечатка не зависит).
