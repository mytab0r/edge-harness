# ADR 0025. Классификация классов дефектов — в источнике, не постфактум-кластеризацией

- **Дата:** 2026-09-14
- **Статус:** принято (задача #1237)
- **Смежное:** [issue #1172](https://github.com/mytab0r/edge-harness/issues/1172)
  (эталонный класс «недостижимый механизм», найден на 11-м инстансе),
  `scripts/lib/check_result.py` (#1096, носитель третьего состояния —
  тот же принцип переиспользован здесь), `scripts/orchestra/
  soft_failure_digest.py` (#1136, образец накопителя-по-порогу для
  follow-up #1240), `docs/research/30-rejected-alternatives.md` (сверено —
  дубля нет).

## Контекст

Класс дефекта «механизм физически не может сработать» проявился трижды за
одни сутки (2026-09-13): PR #1089 08:13Z, PR #1104 09:44Z, PR #1114 10:43Z —
все три находки поймал один и тот же AI-ревьюер, каждый раз ДРУГИМИ словами
(«тишина... не может сработать раньше возраста», «ветка... недостижима из
единственного прод-вызова», «стоп-класс... не подтверждён ни одним прогоном»).
Координатор завёл issue #1172 вручную только после ОДИННАДЦАТОГО инстанса,
~13 часов спустя третьего. Задача: механизировать обнаружение НОВОГО класса
дефекта так, чтобы конвергенция происходила на 3–4-м инстансе, не на 11-м —
без единого дополнительного обращения к модели (цена уже оплачена тем же
вызовом ai-review).

## Отклонённый вариант: постфактум-кластеризация находок

Первая идея — собирать все находки блокирующих вердиктов централизованно и
группировать их ПОСТФАКТУМ (word-overlap cosine, TF-IDF, эмбеддинги) —
без изменения контракта промпта, тем же приёмом, что
`scripts/orchestra/soft_failure_digest.py` группирует аннотации CI по
нормализованному тексту.

Отклонён численно, не мнением. Аналитик (2026-09-14) посчитал word-overlap
cosine на ПОДЛИННЫХ текстах трёх инстансов класса #1172 (см. `scripts/review/
test_defect_classes.py`, раздел «Живые тексты #1172», дословные абзацы) плюс
находку другого класса (#1185) как контроль:

| Пара | cosine | Факт |
|---|---|---|
| A1(#1089) – A2(#1104) | 0.094 | ОДИН класс |
| A1(#1089) – A3(#1114) | 0.019 | ОДИН класс |
| A2(#1104) – A3(#1114) | 0.013 | ОДИН класс ← минимум одноклассовых |
| A3(#1114) – B2(#1185) | 0.060 | РАЗНЫЕ классы ← БОЛЬШЕ минимума одноклассовых |

`min(одноклассовых) = 0.0125 < max(разноклассовых) = 0.060` — порога,
отделяющего «один класс» от «разных», у этой метрики НЕ СУЩЕСТВУЕТ. Причина
не в выборе метрики (cosine/TF-IDF/эмбеддинги дали бы качественно тот же
результат по этой же причине), а в природе данных: находка — оригинальная
проза живого ревьюера, класс по определению бьёт РАЗНЫЕ файлы и формулировки
(«недостижим» в #1089/#1104, «не выстрелит никогда» в #1114 — синонимы по
смыслу, не по словам), а нормализация «по файлу/функции» контрпродуктивна
(#1172 сам жил в `scheduler.py`, `harness.ts` и провайдерской цепочке
одновременно — три РАЗНЫХ файла, один класс).

Постфактум-кластеризация также требует ВТОРОГО обращения к модели
(эмбеддинги/суммаризация находок) либо теряет точность до непригодности —
оба исхода дороже или хуже классификации в источнике.

## Принятое решение: классификация в источнике, тем же вызовом модели

Модель ai-review, находя блокирующую проблему (п.1 контракта `ai_prompt.md`),
обязана назвать `КЛАСС: <slug>`, ВЫБИРАЯ из подставленного в тот же промпт
словаря известных классов и недавних кандидатов
(`scripts/review/defect_classes.py::render_prompt_section`), а не изобретая
формулировку заново. Нормализацию делает тот, кто и так видит семантику
находки в контексте всей системы — не regex постфактум.

### Три состояния, не два

`scripts/review/defect_classes.py::classify()` возвращает `ClassSignal` с
`state ∈ {not_named, candidate, known}` — тот же принцип, что
`scripts/lib/check_result.py` (#1096): «модель не назвала класс» ≠
«класс новый (кандидат)» ≠ «класс уже известен». Слияние любых двух из этих
трёх состояний давало бы ложный сигнал (не названный класс выглядел бы как
новый кандидат; новый кандидат тонул бы среди известных, и обратная связь
не работала бы).

### Носитель словаря — гибрид (обоснование выбора, issue #1237 требует его в PR)

- **Известные классы** — статический файл `scripts/review/defect_classes.json`,
  читается БЕЗ сети (cmd_gather и так делает много сетевых вызовов на PR).
  Повышение кандидата в известный класс (follow-up #1240) редактирует этот
  файл автоматическим PR, не прямым коммитом из параллельных ai-review job'ов:
  ai-review идёт ~109 раз/сутки (докстринг `soft_failure_digest.py`) —
  параллельный `git commit` в общий файл гонял бы в гонку записи, а PR через
  обычный мерж-конвейер репозитория сериализует правки тем же механизмом,
  что любой другой код.
- **Кандидаты** (замечены 1+ раз, не продвинуты) — НЕ файл (тот же довод
  острее: кандидат может появиться на КАЖДОМ rework-вердикте, не раз в
  сутки) — комментарии на отдельной issue-носителе (#1238): `POST
  .../comments` атомарен под конкуренцией параллельных ai-review job'ов,
  `git commit` — нет.
  Не переиспользован WATCHDOG_ISSUE (#120): находка ревью самого PR #1089
  (живой пример этого же класса #1172) — маркер, вытесненный из окна чтения
  штормом чужих комментариев (>100/час на #120 в реальном инциденте) — тот же
  риск здесь не нужен на носителе, чья единственная функция — быть читаемым
  срезом.
- Рассмотрена метка `defect-class` на задачах пула (альтернатива, названная
  в задании) — отклонена: кандидат по определению ЕЩЁ НЕ задача (задача
  заводится только при повышении, follow-up #1240), а issue-заголовки не
  дают точного машиночитаемого slug без парсинга прозы — тот же класс
  проблемы, который уже отклонён выше (постфактум-разбор прозы).

### Потолок размера

`MAX_CANDIDATES_SHOWN = 15` в промпте, `MAX_CANDIDATE_READ_PAGES = 5` на
чтение (тот же приём ограничения по свежим страницам, что
`review_labels.list_pages`/`pulse_guard.issue_marker_times`). Цена в токенах
на потолке (1 известный + 15 кандидатов, грубая оценка 4 символа/токен) —
около 550–700 токенов (см. `test_defect_classes.py::
test_render_prompt_section_token_cost_is_small`) — на порядок меньше
`context_pack`/`rules_section` промпта (десятки КБ каждый), не доминирующая
статья бюджета даже на потолке.

### Обратная совместимость (issue #1237, п.8)

Контракт ревью используется параллельно другими открытыми PR. Строка КЛАСС —
необязательное поле: старый ответ без неё разбирается как `state=not_named`
(третье состояние), не как нарушение контракта — verdict не переклассифицируется
в `error`. Проверено тестом `test_classify_not_named_when_answer_has_no_class_line`.

## Проверка на живых данных

`scripts/review/test_defect_classes.py::
test_three_real_pr1172_findings_collapse_to_one_slug_by_third_pr` —
дословные абзацы находок #1089/#1104/#1114, вручную размеченные по контракту
(см. оговорку в докстринге `defect_classes.py`, раздел «Не подтверждено»: это
СИМУЛЯЦИЯ решения модели автором PR, не живой вызов — первый настоящий
прогон в CI единственное честное подтверждение поведения самой модели).
Результат: три РАЗНЫХ PR, один slug (`недостижимый-механизм`) — накопитель
кандидатов (issue #1238) показывает `count=3` (три разных PR) уже после
третьего инстанса — там, где исторически потребовалось одиннадцать.

## Область этого PR

Контракт (`ai_prompt.md`) + словарь + разбор + тесты (issue #1237). Повышение
кандидата в задачу пула при достижении порога — ОТДЕЛЬНАЯ задача (issue
#1240, follow-up), по образцу `soft_failure_digest.py`
(`DIGEST_REPEAT_THRESHOLD=3`, порог по РАЗНЫМ прогонам/PR, не по сырым
повторам).

## Условие пересмотра

Первые несколько живых прогонов ai-review с этим контрактом покажут, реально
ли модель переиспользует slug вместо синонима (см. «Не подтверждено» выше) —
если конвергенция не происходит на практике (кандидаты множатся синонимами
несмотря на подставленный словарь), пересмотреть формулировку инструкции в
`ai_prompt.md` (сейчас: «переиспользуй ДОСЛОВНО») или добавить defence in
depth (нормализация регистра/окончаний перед сравнением slug'ов) — не
подгонять под уже известные три случая заранее.

## Не подтверждено

- Реальная модель (провайдер цепочки dsh) действительно выбирает
  существующий slug вместо изобретения синонима — механика (словарь +
  парсинг) проверена тестами на синтетических и подлинных ТЕКСТАХ находок,
  но не живым вызовом модели в CI (см. `defect_classes.py`, «Не
  подтверждено»).
- Носитель кандидатов (issue #1238) не тестирован на реальном объёме
  (issue только что заведена, пуста) — риск того же класса, что нашла
  находка ревью PR #1089 для #120 (маркер, вытесненный штормом), для #1238
  не исключён полностью, только снижен выбором ОТДЕЛЬНОГО носителя.

## Дельта 2026-09-14 (issue #1255): носитель кандидатов пересмотрен —
## гибрид «файл + issue #1238» заменён на «файл + комментарии-вердикты»

«Условие пересмотра» выше сработало на ПЕРВОМ ЖЕ живом прогоне с этим
контрактом (PR #1212, прогон 34857962308) — но не по названной там причине
(поведение модели). Модель контракт исполнила честно: `class: candidate=
маркер-позже-действия` ушло в шапку главного комментария. Сломался
структурный слой: отдельный маркер-`POST` на issue #1238 (описан выше,
раздел «Носитель словаря») падал `HTTP 403 Resource not accessible by
integration` — job `verdict` не несёт `issues: write` (снято мандатом
владельца 2026-09-11, #939, до этого PR никто не заметил конфликта прав).
issue #1238 осталась пустой навсегда — «риск не исключён» из раздела «Не
подтверждено» выше материализовался, но не тем риском, который называла
формулировка (не шторм чтения — отсутствие возможности писать вовсе).

Решение (issue #1255): убрать отдельную запись, не чинить право
(`issues: write` НЕ возвращается — мандат #939 в силе). Кандидат уже
публикуется как часть главного комментария (`pull-requests: write`, не
менялось, работает) — читатель (`recent_candidate_stats`) агрегирует
кандидатов ИЗ уже опубликованных комментариев-вердиктов ВСЕГО репозитория
(`GET /repos/{repo}/issues/comments`, доверенный автор, поле `class:` шапки),
не из отдельной issue. Носитель словаря стал не гибридом «файл + issue»,
а «файл + уже существующий поток комментариев» — второй операции записи,
которая могла бы разойтись с первой (silent-wrong класс, ровно этот
инцидент), больше не существует по построению.

Цена: то же число запросов API за тик (`MAX_CANDIDATE_READ_PAGES=5`,
не изменилось), но окно истории теперь ~19 часов при живом темпе
репозитория (636 комментариев/24ч, замер 2026-09-14), а не «вся история
маркеров», как хранила бы выделенная issue — см. докстринг
`defect_classes.py`, разделы «Носитель» и «Потолок размера». issue #1238
закрыта со ссылкой на эту дельту и issue #1255 (осиротевший носитель не
остаётся молча висеть, AGENTS.md, класс #1172).

Полный разбор — `scripts/review/defect_classes.py` (докстринг обновлён тем
же PR, что и эта дельта).
