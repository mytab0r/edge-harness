# 0018. Алерт «пульс не бьётся» живёт в DO (Cloudflare), не в GitHub Actions

Дата: 2026-09-13. Задача: #1103. Смежные: [#689](https://github.com/mytab0r/edge-harness/issues/689)
(независимый DO-пульс, `pulse_guard.py::decide_independent_pulse`),
[#693](https://github.com/mytab0r/edge-harness/issues/693)/[#713](https://github.com/mytab0r/edge-harness/issues/713)
(Cron Trigger — страховка для alarm()), [#1100](https://github.com/mytab0r/edge-harness/issues/1100)
(исчерпание квоты API — причина инцидента), [21-github-actions.md](../research/21-github-actions.md)
(`schedule` доставляется ~7% тиков).

## Контекст

Инцидент 2026-09-13: конвейер простоял 40+ минут и не ожил сам, движение
вернул ручной `workflow_dispatch`. Разбор (issue #1103) показал: авто-
восстановление УЖЕ существует и хорошо покрыто тестами —

- `alarm()` (`cf-worker/src/harness.ts`) перезакладывает будильник ПЕРВОЙ
  строкой, до какого-либо I/O — падение GitHub-вызовов не может убить
  цепочку тика;
- Cron Trigger (`wrangler.jsonc: triggers.crons: "*/5 * * * *"`,
  `src/index.ts::scheduled()` → `Harness#scheduledTick()`) — страховка,
  независимая от активности alarm(), проверяет каждые 5 минут через
  `pulseNeedsRecoveryDispatch()` (порог `2×selfOrchestrationMs` = 20 минут
  при текущих 10-минутных тиках, issue #812) и сама дёргает dispatch, если
  alarm() подвис;
- `pulse_guard.py::decide_independent_pulse`/`independent_pulse_check`
  (issue #689) сравнивает независимый DO-канал (`GH_DISPATCH_TOKEN`,
  `triggering_actor.login != "github-actions[bot]"`) с событийным
  (`wake_orchestra.sh`, тот же login) — обнаруживает, что ИМЕННО DO
  перестал дёргать оркестратор, пока событийный канал жив.

Дыра — не в возобновлении, а в ВИДИМОСТИ: `independent_pulse_check`
исполняется ВНУТРИ `scheduler.py`, то есть внутри самого пульса. Если оба
канала (независимый и событийный) молчат одновременно — как и случилось
2026-09-13 при исчерпании квоты API (#1100), когда рушился КАЖДЫЙ вызов
GitHub API, включая dispatch из самого DO, — `scheduler.py` не запускается
вовсе, и проверка, которая должна закричать, никогда не исполняется. Класс
уже назван в AGENTS.md: «проверка исполняется внутри пульса — при мёртвом
пульсе она молчит».

## Решение

Алерт живости пульса переносится в САМ DO: `Harness#tickPulseAlert()`
(`cf-worker/src/harness.ts`), вызывается из общего `#dispatchOrchestraTick`
— то есть срабатывает и из `alarm()`, и из `scheduledTick()`, ОБА живут в
Cloudflare-инфраструктуре (DO alarm, Cron Trigger), не в GitHub Actions.
Решение о тревоге/восстановлении — уже вычисленный `pulseHealthy()` (одно
место правды на «здоров ли пульс», без второй копии порога); дедуп перехода
здоров↔нездоров — новая таблица `pulse_alert` (флаг `alerted`, тот же
рецепт, что `storage_probe`/`storageReadyAlertDecision`, #575). Доставка —
тот же `#telegramApi`, что и решения владельца (#470/#471) и алерт
готовности хранилища (#575) — второй канал не заводится.

Этот алерт может сработать даже тогда, когда абсолютно ни один workflow
этого репозитория не запускается: он не читает GitHub API вообще (решение
целиком из уже записанного в SQLite DO состояния), поэтому не может
усугубить причину падения, если она — исчерпание квоты (#1100): 0
добавленных вызовов GitHub API/час.

### Отклонённые альтернативы

**Внешний cron вне GitHub и вне Cloudflare.** Дублирует уже существующий DO
alarm + Cron Trigger вторым независимым таймером ради того же вопроса
(«пульс жив?») — DO уже играет эту роль (issue #689/#693), решение было бы
третьей копией одного механизма. Требует новой инфраструктуры и секретов
вне двух уже используемых бесплатных платформ (AGENTS.md: «всё работает на
бесплатных планах», решение, стоящее денег/новой зависимости, требует
согласования).

**Отдельный GitHub Actions workflow-сторож на своём `schedule`.** Страдал бы
ТОЙ ЖЕ болезнью, которую чинит: `docs/research/21-github-actions.md`
измерил доставку `schedule` на этом репозитории — ~7% тиков (31 из ~465
ожидаемых за 116.3 ч). Watchdog, зависящий от того же ненадёжного
механизма, который уже назван корнем проблемы (issue #1103, «cron-страховка
фактически не работает»), — не решение, а тот же класс отказа в новой
обёртке.

**Повтор упавшего пульса средствами самого workflow (`workflow_run`/
ретрай-шаг).** Не помогает при ПОЛНОМ отказе: `workflow_run` триггерится
завершением ДРУГОГО workflow-прогона — если ни один прогон не стартует
вовсе (что и произошло 2026-09-13 при исчерпании квоты), триггеру не от
чего сработать. Собственный ретрай orchestra.yml (например Actions'
`retry`-механизм) тоже требует, чтобы job вообще запустился — та же
зависимость от живого GitHub Actions, которую алерт обязан пережить.

## Последствия

- Владелец получает Telegram-сообщение при ПЕРВОМ нездоровом тике пульса
  (не после N минут ожидания — реагирует немедленно, дедуп только против
  повторной отправки на каждый следующий нездоровый тик) и второе — при
  восстановлении. Текст называет факт (конкретный `detail` последнего тика
  или «тик давно не обновлялся» для ветки `pulseStale`) и план (что уже
  делает самовосстановление, что проверить, если за час не пришло
  подтверждение) — правила AGENTS.md «алерт не гадает» и «алерт обязан
  кончаться планом».
- `pulse_guard.py::independent_pulse_check` (#689) не удаляется и не
  дублируется этим изменением: он остаётся единственным способом отличить
  ИМЕННО независимый DO-канал от событийного, когда оркестратор всё же
  запускается. Новый алерт закрывает другой, более узкий по применимости,
  но более катастрофический случай — оба канала молчат одновременно.
- N минут до автоматического возобновления не меняется этим PR (существующий
  механизм не тронут): худший случай — Cron Trigger обнаруживает подвисший
  alarm не позднее одного своего тика (5 мин) после порога `2×selfOrchestrationMs`
  (20 мин при текущих 10-минутных тиках) — то есть первая резервная попытка
  не позже ~25 минут после реальной остановки alarm(). Если сама причина
  (исчерпание квоты API) не снята, каждая последующая попытка дедуплицируется
  тем же порогом (запись пульса при неудаче обновляет `ts`) — то есть
  повторные попытки идут не чаще одного раза в ~20 минут, не штурмом.
