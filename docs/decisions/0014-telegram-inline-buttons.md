# ADR 0014. Инлайн-кнопки решения владельца в Telegram: узкий webhook-секрет,
не второй канал записи

- **Дата:** 2026-09-06
- **Статус:** принято (реализовано в задаче #254); шаг владельца — завести
  секреты и вызвать `setWebhook`, см. «Миграция». **ИЗМЕНЕНО 2026-09-17**
  (PR #1254, #1251): `TELEGRAM_WEBHOOK_SECRET` получил вторую роль — ключ
  подписи `client_payload` решения; п.5 «без единого секрета» больше не
  действует в этой части, п.2 «одна роль» нарушен явно — см. «Изменение
  2026-09-17» в конце файла. **ИЗМЕНЕНО 2026-09-21** (PR #1414, #1413):
  п.7 «задачи без блока получают текстовый алерт» больше не действует —
  текстовый фолбэк владельцу убран, см. «Изменение 2026-09-21» в конце файла.
- **Смежное:** [ADR 0008](0008-narrow-dispatch-token.md) (узкий
  `GH_DISPATCH_TOKEN`), [ADR 0011](0011-inbox-issues-token.md) (тот же принцип
  «имя секрета = ширина»), задача #254, #470/#471 (`waiting:owner`:
  метка + поиск задач с машиночитаемым блоком «## Варианты владельца» +
  текстовая эскалация + комментарий-решение — слит раньше этого PR;
  `scripts/orchestra/waiting_owner_guard.py::waiting_owner_check` теперь
  зовёт `escalate(..., options=...)`, добавленный здесь, и отправляет
  реальное кнопочное сообщение, не только текстовый алерт)

## Контекст

Существующий маршрут `POST /api/messages/ingest` (задача #20, PR #173) уже
понимает форму Telegram-апдейта (`update_id`, `message.from/chat`), но
авторизован ОБЩИМ механизмом морды (Bearer `HANDS_TOKEN` / сессионная кука) —
эндпоинт админско-релейный, а не прямой вебхук: настоящий сервер Telegram не
может прислать ни то, ни другое. Прямая доставка вебхуком **не была
подключена** до этой задачи (сказано прямо в комментарии к `#postMessageIngest`)
— то, что раньше по ошибке приняли за «маршрут уже работает», означало только
«код умеет РАЗОБРАТЬ такую форму тела», не «Telegram может её прислать».

Второй факт: у морды (Cloudflare Worker) до этой задачи вообще не было
токена бота Telegram — все исходящие сообщения шлёт Python
(`scripts/orchestra/pulse_guard.py`) из GitHub Actions, где `TELEGRAM_BOT_TOKEN`
уже есть как секрет репозитория, но воркеру он не синхронизирован.

## Решение

**Реюз маршрута, не второй webhook; узкий синхронизируемый секрет для
авторизации Telegram, а не для остального API.**

1. `POST /api/messages/ingest` авторизуется ЛИБО обычным способом (Bearer/
   кука), ЛИБО заголовком `X-Telegram-Bot-Api-Secret-Token`, сверенным
   константным по времени сравнением с секретом `TELEGRAM_WEBHOOK_SECRET`
   (`setWebhook(secret_token=...)` — штатный механизм Telegram, не
   самодельный). Матчинг маршрута происходит ДО выбора способа авторизации:
   обход открывает ТОЛЬКО этот один маршрут, не остальной API — секрет
   вебхука по компрометации даёт меньше, чем `HANDS_TOKEN`.
2. Тот же секрет НЕ переиспользует `HANDS_TOKEN`: у секрета — одна роль,
   принцип ADR 0008 «имя секрета обязано означать его ширину» держится и
   здесь, несмотря на соблазн сэкономить один секрет. (Позже у самого
   `TELEGRAM_WEBHOOK_SECRET` появилась ВТОРАЯ роль — отдельным осознанным
   решением, не этим пунктом: см. «Изменение 2026-09-17» ниже.)
3. `TELEGRAM_BOT_TOKEN` (существующий секрет репозитория, используемый
   `pulse_guard.py`) синхронизируется ТАКЖЕ в секрет воркера — тот же
   секрет, новый потребитель, а не новый секрет. Нужен, чтобы морда сама
   звала `answerCallbackQuery`/`editMessageText` (Bot API требует токен в
   URL метода).
4. Все новые секреты воркера (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`,
   `TELEGRAM_CHAT_ID`) — опциональны для деплоя (тот же приём, что
   `GH_ISSUES_TOKEN`, ADR 0011): отсутствие красит `::warning::`, не
   останавливает `deploy-worker.yml`. Без `TELEGRAM_WEBHOOK_SECRET` ИЛИ
   `TELEGRAM_CHAT_ID` вебхук-путь закрыт наглухо — это объявленное
   «возможности нет», не тихая дыра.
5. **Применение решения переиспользует `GH_DISPATCH_TOKEN` (ADR 0008), не
   заводит новый секрет морды.** Callback несёт `callback_data` вида
   `wo:<issue>:<option>` (укладывается в лимит Bot API 64 байта с большим
   запасом); морда шлёт `repository_dispatch` (`event_type: owner-decision`)
   тем же токеном и тем же эндпоинтом, что и очередь задач/пульс —
   `GH_DISPATCH_TOKEN` не имеет права на Issues (ADR 0008), поэтому запись
   решения делает не сама морда, а тонкий job
   (`.github/workflows/owner-decision.yml`, только `issues:write` из
   `permissions`, `github.token`, без единого секрета — **изменено
   2026-09-17, см. «Изменение 2026-09-17» ниже: job теперь читает
   `TELEGRAM_WEBHOOK_SECRET` для проверки подписи**) —
   `scripts/orchestra/apply_owner_decision.py` оставляет комментарий первой
   строкой «РЕШЕНИЕ: N» — **тот же артефакт**, что и ручной ответ владельца
   (#470/#471). Снимает `waiting:owner` гвардия `waiting_owner_guard.py`
   (слита #471) на следующем пульсе `orchestra` — второй "apply"-путь здесь
   не заводится, кнопка лишь производит тот же текст, что мог бы напечатать
   владелец.
6. **Привязка вебхука к владельцу по `chat_id`** (находка ревью PR #486):
   `TELEGRAM_WEBHOOK_SECRET` аутентифицирует БОТА (что запрос от Telegram),
   не ОТПРАВИТЕЛЯ — после `setWebhook` морда получает апдейты из ЛЮБОГО
   чата, где боту написали. Новый секрет `TELEGRAM_CHAT_ID` (тот же, что уже
   держит `pulse_guard.py`) сверяется константным по времени сравнением в
   обеих ветках вебхук-пути (`message` и `callback_query`) — не задан или не
   совпал, путь закрыт 401 тем же приёмом, что у `TELEGRAM_WEBHOOK_SECRET`.
   Проверка применяется ТОЛЬКО к вызовам через вебхук-обход — вызывающий по
   Bearer/куке уже доверен внутренним токеном.
7. **Отправка кнопочного сообщения** (критерии приёмки #254 п.1 и п.5):
   `scripts/orchestra/pulse_guard.py::escalate` получил необязательный
   `options` — задан, `send_telegram` уходит с `reply_markup`
   (`build_decision_keyboard`). Единственный вызывающий —
   `waiting_owner_guard.py::waiting_owner_check` (#470/#471): открытая
   `waiting:owner`-задача с машиночитаемым блоком «## Варианты владельца» —
   `options` строится из подписей вариантов (`variant_option_labels`, без
   номера и без последствия — Telegram узкий экран), задачи без блока
   получали текстовый алерт (**изменено 2026-09-21**, PR #1414/#1413:
   текстовый фолбэк владельцу убран вовсе — см. «Изменение 2026-09-21»
   ниже). Обратная проверка (п.5 критерия)
   держится тем же путём: нет `waiting:owner`-задачи с вариантами — нечему
   вызвать `escalate(..., options=...)`, кнопочное сообщение не уходит.

## Рассмотренные альтернативы

- **Второй, отдельный вебхук-маршрут только для callback_query.** Отвергнуто:
  дублирует «единственный входящий вебхук Telegram» без выгоды — разбор всё
  равно нужен по типу апдейта (`message` vs `callback_query`), а два пути
  авторизации на два похожих маршрута тяжелее поддерживать, чем один маршрут
  с двумя способами авторизации.
- **Секрет вебхука = значение `HANDS_TOKEN`.** Отвергнуто по прямой аналогии
  с ADR 0008/0011: смешивает роль «полный доступ к API» с ролью «подтверди,
  что ты Telegram», компрометация одного канала не обязана компрометировать
  другой.
- **Морда сама пишет комментарий/снимает метку через `GH_ISSUES_TOKEN`.**
  Отвергнуто: `GH_ISSUES_TOKEN` — Issues:RW, технически хватило бы, но это
  завело бы ВТОРОЙ путь применения решения (морда пишет комментарий сама,
  минуя `waiting_owner_guard.py`) — риск разойтись форматом с ручным путём
  #470/#471. Транзит через `repository_dispatch` → тонкий job,
  переиспользующий `post_issue_comment`, держит один код, пишущий этот
  артефакт.
- **Кнопка снимает метку и закрывает решение мгновенно, без пульса
  `orchestra`.** Не реализовано: `waiting_owner_guard.py` (#470/#471, слит)
  снимает метку и оставляет подтверждение на СЛЕДУЮЩЕМ пульсе `orchestra`
  (до 15 минут задержки) — комментарий «РЕШЕНИЕ: N» не единственный сигнал
  системы, второй, мгновенный путь применения не заводится (тот же принцип,
  что у «второй apply-путь» в п.5 выше).

## Не входит

Полноценный диалог через Telegram (это #20/#173 и спека
`cloud-orchestrator-convergence`) — здесь только протокол решения (issue
#254, раздел «Не входит»). Живой сквозной прогон «нажатие кнопки → job
`owner-decision.yml` стартовал → комментарий появился» этой задачей тоже не
подтверждён — см. «Последствия».

## Миграция (шаги, которые есть только у владельца)

1. **Секреты вебхука** — GitHub веб-интерфейс (телефон подходит): Settings →
   Secrets and variables → Actions → New repository secret →
   `TELEGRAM_WEBHOOK_SECRET` (любая случайная строка, только
   `A-Z a-z 0-9 _ -`, 1–256 символов — ограничение самого Telegram) и
   `TELEGRAM_CHAT_ID` (chat_id владельца — `getUpdates` или переслать
   сообщение боту `@userinfobot`).
2. **Тот же деплой** синхронизирует `TELEGRAM_BOT_TOKEN` (уже существующий
   секрет) и новые `TELEGRAM_WEBHOOK_SECRET`/`TELEGRAM_CHAT_ID` в воркер —
   правки кода не требуют, следующий пуш в `cf-worker/**` или ручной
   `workflow_dispatch` `deploy-worker.yml`.
3. **Вызов `setWebhook`** — ОДИН запрос в браузере (в т.ч. с телефона, без
   терминала): `https://api.telegram.org/bot<TOKEN>/setWebhook?url=<HARNESS_URL>/api/messages/ingest&secret_token=<то же значение, что в шаге 1>`.
   `<TOKEN>` знает только владелец (значение секретов никогда не извлекается
   агентами). Проверка: `.../getWebhookInfo` в браузере отдаёт `url` и
   `last_error_date` пустым.

До шага 3 существующий путь (сообщения владельца, простой текст) продолжает
работать без изменений — ничего не сломано отсутствием вебхука.

## Последствия

- Класс «маршрут понимает форму Telegram, но никто не может её прислать
  легитимно» закрыт для сообщений и для нажатий кнопок одним и тем же
  секретом.
- Семь секретов воркера вместо четырёх: `HANDS_TOKEN`, `GH_DISPATCH_TOKEN`,
  `GH_ISSUES_TOKEN`, `SESSION_SECRET` → плюс `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_CHAT_ID` — цена принципа «одна роль,
  одно имя» (ADR 0008).
- Не подтверждено этой задачей: полный живой прогон «нажатие кнопки → job
  `owner-decision.yml` стартовал → комментарий появился» — `repository_dispatch`
  запускает воркфлоу только с файла на default branch (docs/research/21), то
  есть до мержа этого PR событие принимается (204), но job не стартует.
  DO-сторона проверена юнит-тестами (прод-форма `callback_query`), job-сторона
  (`apply_owner_decision.py`) — юнит-тестами с мутацией на `post_issue_comment`.

## Изменение 2026-09-17 (PR #1254, #1251): `TELEGRAM_WEBHOOK_SECRET` получает вторую роль

Пункт 5 выше требовал от `owner-decision.yml` работы «без единого секрета».
Правка #1251 (HMAC-подпись `client_payload`) добавила job'у чтение
существующего `TELEGRAM_WEBHOOK_SECRET`: `repository_dispatch` не проверяет,
каким токеном вызван, только scope — без подписи любой держатель Actions-write
(каждый агент этого репозитория) получает от job'а артефакт «РЕШЕНИЕ: N»,
неотличимый от нажатия кнопки (`apply_owner_decision.py::verify_signature`,
три РАЗНЫХ отказа, ни один не пишет комментарий).

**Принцип п.2 «у секрета — одна роль» здесь нарушен ЯВНО, не молча**
(класс дефекта «секрет-шире-имени», назван ревью PR #1254). Цена названа:
секрет известен третьей стороне — Telegram получает его через
`setWebhook(secret_token=...)` (п.1), — и с этой правкой компрометация роли
вебхука каскадом открывает роль «записать решение за владельца»: зная ОДИН
секрет, можно вычислить HMAC и вызвать dispatch напрямую. Дополнительная
честность о границе: подпись — НЕ изоляция от агентов. Actions-копию секрета
читает любой слитый workflow, а канал подделки артефакта у агента и так
открыт дешевле — комментарий «РЕШЕНИЕ: N» не аутентифицирован ничем
(принятый риск #1251, `AGENTS.md` «Атрибуция событий»). Назначение подписи —
чтобы происхождение артефакта («Источник: нажатие инлайн-кнопки») не врало
и цена подделки артефакта-кнопки была выше, чем у комментария: держатель PAT
без знания секрета подпись не вычислит.

**Почему принята вторая роль, а не заведён выделенный секрет.** Выделенный
`*_SIGNING_SECRET` был бы чище, но его значение обязан завести владелец
(значения секретов в этом репозитории знает только владелец, «Миграция»
выше); до его заведения кнопочный путь обязан оставаться красным
(fail-loud, `SignatureMissing` на каждое нажатие) — тормоз без
автоматического газа, который правила репозитория не принимают. Принятая
вторая роль оставляет систему в состоянии без нового тормоза.

**Условие возврата.** Владелец заводит `OWNER_DECISION_SIGNING_SECRET`
(репозиторий + синк в воркер, как у остальных секретов) — подпись ротируется
на него правкой ОДНОГО имени в трёх местах: `SIGNATURE_SECRET_ENV_VAR` в
`scripts/orchestra/apply_owner_decision.py`, env в
`.github/workflows/owner-decision.yml`, чтение env в
`cf-worker/src/harness.ts::#dispatchOwnerDecision`. Либо — если #1251 даст
пути комментария жёсткую границу (вариант 1/2 задачи: фильтр по
происхождению или отдельный владельческий признак) — вопрос ролей секретов
пересматривается вместе с ней.

## Изменение 2026-09-21 (PR #1414, #1413): текстовый фолбэк владельцу убран

Пункт 7 выше оставлял задачам без машиночитаемого блока вариантов «текстовый
алерт, как раньше». Восемь суток (2026-09-14…21) этот путь слал владельцу по
восемь неотвечаемых напоминаний «Нужен твой выбор» с просьбой назвать номер
из списка, которого нет, — по шести задачам (#1151, #1080, #1036, #1009,
#768, #668), и владелец написал, что не понял, кто у кого что запросил.
«Нужен твой выбор» без выбора — неправда («алерт не гадает»), а метка
`waiting:owner` держит задачу вне пула, и снять этот тормоз владелец
физически не может.

**Новый контракт:** вопрос адресуется владельцу ТОЛЬКО с кнопками — при
непустом `variant_option_labels` (блок есть И нумерация подряд `1..N`).
Оба состояния «вопрос не сформулирован» (блока нет; нумерация не подряд —
различает сам код, находка ai-review PR #1414) владельцу ничего не шлют:
громкая строка в прогоне + одноразовая пометка в задаче агенту
(сформулировать варианты либо перенумеровать; не нужно решение — снять
метку). Путь ОТВЕТА не менялся: комментарий «РЕШЕНИЕ: N» работает и без
блока — убран путь вопроса, не путь ответа. Механизм
`escalate(options=None)` в
`pulse_guard.py` сохранён для будущих вызывающих вне `waiting:owner`.
