# ADR 0005. Замер хвоста задержки dispatch: кампания, а не сеанс

- **Дата:** 2026-08-30
- **Статус:** принято (кампания реализована, данные собирает автоматика)
- **Смежное:** [ADR 0003](0003-dispatch-latency-verdict.md),
  [известные неизвестные](../research/99-open-questions.md),
  [GitHub Actions](../research/21-github-actions.md), задача #4

## Контекст

[ADR 0003](0003-dispatch-latency-verdict.md) принял задержку старта job'а как
приемлемую по 22 замерам одного короткого сеанса — с явной оговоркой: хвост
распределения (жалобы сообщества на многочасовые очереди) не пойман и не
опровергнут. Задача #4 требует 100+ замеров в разное время суток, включая
американский рабочий день. Это ≥24 часа разброса — ни одна воркер-сессия
(лимит job'а 6 ч, лимит DSH-прогона 150 мин) этого окно физически не покрывает.
Значит, замеры должна собирать автоматика, живущая дольше любого сеанса.

## Решение

**Автономная кампания в GitHub Actions** (`.github/workflows/dispatch-latency-probe.yml`
+ [`scripts/measure/dispatch_tail.py`](../../scripts/measure/dispatch_tail.py)):
cron каждые 15 минут отправляет `repository_dispatch` и замеряет задержку до
старта поднятого им job'а. Метрика и схема:

1. **Метрика — по серверным таймстампам GitHub, а не по часам морды.** Базовые
   22 замера считали «dispatch → первый heartbeat» по часам Durable Object;
   текущие «руки» (слайс dsh-in-job) шлют первый heartbeat спустя минуту
   бутстрапа — их latency_ms больше не измеряет очередь GitHub, а включает
   константу бутстрапа. Кампанская метрика: `latency_ms = run_started_at − sent_at`
   («диспатч отправлен → job начал выполняться») плюс `queue_ms =
   run_started_at − run_created_at` — чистое ожидание раннера по часам GitHub.
   Отличие от базовой метрики — единицы секунд бутстрапа; хвост (минуты-часы)
   в обеих метриках один и тот же. Сводка в
   [99-open-questions.md](../research/99-open-questions.md) честно их
   не смешивает.
2. **Dual-writer, один замер — ровно одна строка.** Измеряемый job сам
   записывает свою строку (`record`), зная свой `run_started_at` и `sent_at` из
   `client_payload`. Диспетчер (`dispatch`) только сторожит: за 600 с строка не
   появилась — пишет таймаут-строку (семантика базового скрипта 2026-08-28:
   таймаут — результат, в числовую сводку не входит). Дубль по `probe_id` не
   пишется — гонка «диспетчер записал таймаут, job опоздал на секунду»
   разрешается детерминированно.
3. **Весь пишущий путь кампании — PAT.** События от `GITHUB_TOKEN` в целом не
   запускают workflows (исключения — `workflow_dispatch`/`repository_dispatch`,
   но для диспатча через REST это исключение живьём не проверено; см.
   [21-github-actions.md](../research/21-github-actions.md)), а push ветки и
   создание PR от `GITHUB_TOKEN` не зажигают проверок точно. Один токен
   (`GH_DISPATCH_TOKEN`; после задачи #6 — широкий `GH_PIPELINE_PAT`: узкий
   dispatch-токен морды кампании не подходит, нужны issues и PR) на диспатч,
   push CSV, PR и комментарии — меньше
   зависимостей от непроверенных исключений.
4. **Данные живут на ветке `data/dispatch-latency-tail`**, каждый замер — коммит
   в `docs/research/data/dispatch-latency-tail.csv`. Черновик-PR на эту ветку
   открыт с первого замера: он же дашборд кампании и держатель задачи #4 в
   состоянии «в работе» (протокол не снимает назначение при живом PR). При
   достижении критерия (100+ замеров, ≥20 в бизнес-окне США пн–пт 13:00–24:00
   UTC, разброс ≥24 ч; предохранитель — 7 дней) кампания сама вписывает сводку
   в [99-open-questions.md](../research/99-open-questions.md) между маркерами,
   ребейзит ветку на main, переводит PR в готовность, комментирует задачу #4 и
   отключает свой workflow. Критерий выполняется на main мержем этого PR —
   без человека в контуре.

## Отвергнутые альтернативы

- **Замеры через морду (POST /api/tasks, DO-часы).** Плюс: непрерывность метрики
  с базовыми 22 замерами. Минусы решающие: текущие «руки» ставят первый
  heartbeat после минутного бутстрапа — метрику пришлось бы чинить правкой DO
  и клиента рук ради замера; кампания получала бы зависимость от задеплоенного
  воркера и его `GH_DISPATCH_TOKEN` (морда не настроена — кампания молча мертва;
   после задачи #6 у морды узкий токен — этой альтернативе он не подошёл бы
   вовсе: пришлось бы выписывать кампании отдельные права).
  Измеряемая величина — очередь GitHub, а не живость морды: выбрана метрика
  без посредника.
- **Замеры из воркер-сессии (продлить базовый замер 2026-08-28).**
  Сессия воркера короче требуемого окна разброса, а её шеллу недоступны
  секреты: DSH вырезает из окружения модельных shell-вызовов все переменные с
  именами `*TOKEN*/*KEY*/*SECRET*` (выяснено живым прогоном 2026-08-30: gh/git
  push из агента не авторизуются). Сеанс не может ни жить достаточно долго,
  ни авторизоваться — кампании не из чего строиться.
- **Вечный cron без самозапирания.** Расписание на публичном репозитории тихо
  умирает через 60 дней тишины, а бессрочный сбор данных — шум в ленте Actions
  несоразмерен пользе. Кампании даны критерий остановки, лимит 7 дней и
  `workflow disable` на финализации; повтор замера — `gh workflow enable` или
  новый прогон (скрипт сохранён).

## Последствия

- Кампания добавляет ~2 коротких запуска Actions каждые 15 минут на время
  сбора данных (публичный репозиторий — минуты не списываются; предел
  500 диспатчей/час не задет с запасом на три порядка).
- «Руки» слайса dsh-in-job не тронуты: их heartbeat остаётся живостью процесса,
  а не якорем метрики; сравнение с базовыми 22 замерами идёт по хвосту, а не по
  абсолюту медианы.
- Формулировка в [99-open-questions.md](../research/99-open-questions.md)
  меняется с «хвост не пойман» на результат кампании — между маркерами
  `<!-- dispatch-tail:begin/end -->`, чтобы финализация правила блок, а не весь
  файл.

## Дельта 2026-09-04: каденция — самоподдержка, cron — страховка

**Повод.** Кампания собирала ~6.5 замера/сутки вместо проектных 96. Диагноз по
истории runs за 116.3 ч: cron `*/15` создал 31 запуск из ~465 ожидаемых (6.7%),
все доставленные — success и все записали строку. Терялась доставка
schedule-события; по данным кампании это неотличимо от «всё по плану» (ноль
таймаутов и сбоев). Замер и выводы —
[21-github-actions.md](../research/21-github-actions.md), раздел «Замер schedule
на этом репозитории»; задержанные/потерянные schedule-раны при темпе
предохранителя дали бы финализацию с «критерий НЕ достигнут».

**Каденция.** Тик в конце (always()-шаг «Цепочка», `dispatch_tail.py chain`)
диспатчит следующий `workflow_dispatch` — dispatch-события за окно диагноза
доставлены 32/32. Cron остаётся страховкой смерти цепочки: четыре запуска в
сутки (04:37, 10:11, 16:37, 22:11 UTC — по два расписания, минуты вне четвертей
часа, где пик нагрузки schedule). Ограничители: `CHAIN_DELAY_S` и
сериализация тиков; цепочка не продолжается при достигнутом покрытии, исчерпанном
лимите и отсутствии workflow на main.

**Финализация ветвится по покрытию** (находка ревью #108): unmet-путь больше не
переводит PR в готовность и не просит закрыть задачу — PR остаётся черновиком,
задача открытой, путь продления назван явно (`CAMPAIGN_MAX_DAYS` в env на уровне
workflow, одно объявление на оба job'а — сознательное решение снаружи кода; без
него первый же тик после перезапуска снова финализирует: overdue считается от
первой строки CSV, а переопределение на уровне шага доходит только до тика —
probe досчитал бы до 7 дней и финализировал бы снова). Повторная
финализация идемпотентна: одинаковый блок сводки даёт пустой коммит, а не красный
тик. След тика, умершего до диспатча, пишется always()-шагом (`tick_failed`,
строка `dispatch_failed`); доставку schedule это не ловит по определению — она
видна сверкой истории runs.

**Маршрут сводки в main при закрытом PR** (ревью #108): если финализация
срабатывает, когда открытого PR на ветке данных уже нет (дельта смержена раньше
добора), она сама создаёт PR (`ensure_draft_pr`, при достигнутом покрытии —
сразу готовый) вместо `::warning::` в логе job'а: workflow к этому моменту уже
выключен, и никто, кроме неё, сводку в main не довезёт. Токен для пишущего пути
один — `GH_PIPELINE_PAT` (имя с задачи #6) во всех командах и шагах workflow;
`GH_TOKEN` в env шагов нужен только credential helper'у gh.

**Темп добора.** До мержа этой дельты тики исполняют старый код с main, поэтому
недостающие до критерия замеры сняты прямой отправкой тех же
`repository_dispatch`-проб (тот же `client_payload`, те же строители строк и
сторож таймаута) из сессий воркера с арендой задачи: `gh api
repos/…/dispatches` под PAT gh-сессии раннера — права `repo`/`workflow`, тот же
класс, что у `GH_PIPELINE_PAT`; значения secrets воркеру при этом не
раскрываются. Вся серия добора — 65 замеров с шагом ~2–4 мин в окне 2026-09-04
22:05 → 2026-09-05 01:44 UTC: сессия воркера-предшественница сняла пакет ~59
(22:05 → 00:47), вторая сессия добрала последние 6 до критерия (01:41 → 01:44,
строго по одной — следующая после строки предыдущей, чтобы ровно одна пересекла
границу покрытия без гонки финализаций). Остальные 35 замеров датасета —
доставленные schedule-тики и точечные пробы за четыре дня кампании. Плотная
серия смещает доли времени суток — сводка показывает это сама: строка
«интервалы между замерами» и разбивка бизнес-строк по дням UTC с пометкой
доминирования одного дня (52 из 71 бизнес-замеров — из этой серии). Метрика
строк от способа отправки не отличается.
