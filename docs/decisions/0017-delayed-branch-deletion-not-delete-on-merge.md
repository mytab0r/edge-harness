# ADR 0017. Уборка веток `agent/*` — отложенное удаление, не `delete_branch_on_merge`

- **Дата:** 2026-09-11
- **Статус:** принято
- **Смежное:** [Протокол мультиагентной работы](../agents/PROTOCOL.md) (ветка
  `agent/<N>-<slug>`), `scripts/git/task-branch`, `scripts/git/merged-branch-cleanup.py`,
  задача [#940](https://github.com/mytab0r/edge-harness/issues/940), PR
  [#937](https://github.com/mytab0r/edge-harness/pull/937) (гейт успеха
  воркера учитывает origin ветки).

## Контекст

312 живых веток `agent/*` на origin (замер 2026-09-11), из них 265 привязаны
к PR со статусом merged/closed старше 24 часов — уборщика не было вовсе.
Естественный первый вопрос: включить `delete_branch_on_merge` на репозитории
(GitHub снимает ветку сам сразу после слияния PR) — самое дешёвое решение,
одна настройка, без кода.

## Почему не `delete_branch_on_merge`

PR #937 (`scripts/lib/dsh-ci.sh::dsh_worker_run_is_success`) явно опирается
на факт `delete_branch_on_merge=false`, но НЕ через `git ls-remote` (это
неточно описывала более ранняя версия этого ADR — правка после находки
ревью PR #944): гейт сравнивает ДВА ЛОКАЛЬНЫХ снимка `git rev-parse HEAD`
одноразового чекаута воркера в пределах ОДНОГО job'а —
`WORKER_BRANCH_START_SHA` до запуска `dsh` (`scripts/worker/task.sh:467`) и
`WORKER_BRANCH_END_SHA` после (`scripts/worker/task.sh:563`), сверяет их
`dsh_worker_run_is_success` (`scripts/lib/dsh-ci.sh:1212`). Комментарий кода
на месте вызова называет причину выбора именно этого сигнала: он не зависит
от того, успел ли push дойти до origin (файловая песочница DSH иногда не
даёт писать в общий `.git` линкованного worktree, и воркер обходит её
отдельным клоном с прямым пушем в origin — тогда локальный `HEAD` основного
чекаута не двигается, но факт работы уже есть).

Само решение (не включать `delete_branch_on_merge`, убирать ветку отдельным
отложенным механизмом) от уточнения не меняется — линия рассуждения другая:
мгновенное удаление ветки СРАЗУ при слиянии рвёт связь между веткой
`agent/<N>-<slug>` и её рабочим деревом/чекаутом воркера, если слияние
случилось ВНУТРИ того же прогона воркера (частый случай — воркер сам мержит
небольшой PR) — второй чекаут/операция над уже удалённой на origin веткой
ловит отказ там, где ожидался успех, тот же класс риска, что и `ls-remote`
в исходной формулировке, просто на другом сигнале. Проверка
`gh api repos/{repo} --jq .delete_branch_on_merge` подтверждает текущее
значение `false`; менять его означало бы тихо сломать критерий успеха
только что принятого PR.

## Решение

Ветка `agent/*` не удаляется в момент слияния. Отдельный периодический
механизм (`scripts/git/merged-branch-cleanup.py`, шаг orchestra.yml «Уборка
веток agent/* после слияния (#940)», cron */15 мин) удаляет её ОТЛОЖЕННО —
не раньше `RETENTION_HOURS = 24` часов после того, как ПОСЛЕДНИЙ известный
PR на эту ветку перешёл в `merged`/`closed` (и ни один другой PR на ту же
ветку не остался `open` — ветка `agent/<N>-<slug>` в этом репозитории
переиспользуется при перезапуске задачи после закрытого PR, тот же приоритет
`open > merged/closed`, что уже применяет `scripts/git/worktree-cleanup.py`
для локальных рабочих деревьев).

24 часа — запас в 4 раза над максимальным временем job'а GitHub Actions на
этом плане (6 часов, `docs/research/21-github-actions.md`): к моменту, когда
отложенная уборка МОЖЕТ тронуть ветку, любой job воркера, чья работа опирается
на существование ветки на origin (прямой пуш из обходного клона мимо
песочницы, домержка PR внутри того же прогона), уже десятки раз успел
завершиться — отложенное удаление физически не может совпасть по времени с
ещё выполняющимся job'ом.

## Альтернатива, которую не выбрали

Удалять ветку сразу при слиянии, но только ПОСЛЕ того, как воркер отчитался
(например, ждать закрытия PR-комментария с отчётом воркера как триггер) —
отклонено: привязывает уборку веток к конкретной механике отчёта воркера
(хрупкая связь, ломается при любой правке формата отчёта), тогда как
привязка к возрасту PR-события (уже читается отовсюду) не требует знать
ничего о том, ЧТО именно происходило внутри job'а — эта же простота уже
доказана на `worktree-cleanup.py`.

## Вернуться, если

PR #937 отменят или его гейт (`dsh_worker_run_is_success`, сравнение
`WORKER_BRANCH_START_SHA`/`WORKER_BRANCH_END_SHA`) перестанет зависеть от
существования ветки `agent/*` на origin в пределах прогона воркера
(например, найдут более надёжный сигнал, не зависящий от неё) — тогда
`delete_branch_on_merge=true`
станет допустимым, и `merged-branch-cleanup.py` можно будет упростить до
чистки только `closed`-без-мержа веток (мгновенное удаление снимет
`merged`-случай само).
