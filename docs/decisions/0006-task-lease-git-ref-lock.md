# ADR 0006. Аренда задачи на git-ref `refs/locks/task-N`

- **Дата:** 2026-08-31
- **Статус:** принято
- **Задача:** [#121](https://github.com/mytab0r/edge-harness/issues/121)
- **Смежное:** [PROTOCOL](../agents/PROTOCOL.md),
  [ADR 0001](0001-push-model-not-tunnel.md) (модель «push, не туннель»),
  `scripts/lib/claim_task.py` (реализация)

## Контекст

Защита от двух исполнителей на одной задаче была дырявой по построению: выбор задачи в
`task.sh` — check-then-assign (TOCTOU), назначение не различает «кто» (все агенты — один
GitHub-логин), канал hands аренду GitHub вообще не берёт. Нужен атомарный серверный claim,
единый для всех каналов: worker auto/manual, hands (после #119), будущие пайплайны.

## Решение

Замок — серверный git-ref **`refs/locks/task-<N>`**, созданный через Git-дата-API GitHub
(`POST /repos/{o}/{r}/git/refs`). Создание ref'а атомарно на сервере: второй претендент
получает HTTP 422 «Reference already exists» и обязан завершиться зелёным no-op. Замок
указывает на коммит, созданный в момент claim'а (дерево наследуется от main) — **date этого
коммита и есть время начала аренды**, по нему считается TTL (`LOCK_TTL_HOURS = 24`, константа
в `claim_task.py`). Освобождение — `DELETE` того же ref'а: после слияния PR (post-merge
шаг оркестратора) и при снятии протухшего замка (обход `refs/locks/*` в scheduler).

Порядок claim: замок → назначение assignee → комментарий в задачу. Назначение — видимость,
не защита.

## Отвергнутые альтернативы

**Назначение assignee как замок.** Уже есть и уже не работает: все агенты — один логин
(см. [PROTOCOL, «Ограничения честности»](../agents/PROTOCOL.md)), «занята не воркером»
неразличимо с «занята мной». Атомарности нет: check-then-assign — это и есть сегодняшний
TOCTOU.

**Имя ветки агента как замок** (создание ветки атомарно). Атомарность настоящая, но: ветка
живёт в общем пространстве имён `refs/heads/*` — пул веток агентов замусоривается замками;
TTL не из чего считать (у ветки нет «времени взятия», а головы двигаются); освобождение
путается с работой (delete ветки = «задача брошена» или «PR готов»?); руки-hands получили бы
право создавать ветки только ради замка.

**Специальный DO/KV/файл-флаг в репо.** Всё, что добавляет новую инфраструктуру или
коммит-шум в рабочие ветки, дороже причины: замок нужен лишь как атомарный бит с TTL.
Ref — уже существующий примитив Git, с серверной атомарностью, датой (коммит) и дешёвым
удалением; рефы под `refs/locks/` не попадают в `git fetch --prune` обычных клонов и не
видны в пуле веток на GitHub.

**Блокировка на стороне issue (лейбл «claimed»).** Той же природы, что assignee: постановка
лейбла не атомарна относительно чтения, отдельного вызова API с условием «если нет» не
существует. 422 на повторный ref — единственная в этом наборе серверная гарантия.

## Последствия

- **Единственный вход** — `claim_task.claim()` / CLI `claim_task.py claim <N>`: каналы не
  выбирают задачу в обход. До мержа #119 существующие каналы (task.sh, hands) не тронуты;
  контракт врезки зафиксирован в #121.
- **Отказ — это зелёный no-op**: вызывающий (job воркера, hands-канал) завершается успехом
  с сообщением «задача занята». Инфраструктурный сбой — громкий (exit 2, `::error::`).
- **Осиротевшие коммиты**: проигравший гонку претендент успевает создать коммит замка до
  отклонённого POST ref'а — ссылок на него нет, мусор безвреден и не виден.
- **TTL-сборщик у оркестратора**: замок без освобождения снимается через `LOCK_TTL_HOURS = 24`
  (один такт с окном просрочки назначений `STALE_HOURS` — задача возвращается в пул целиком).
  Сборщик снимает только замок; назначение снимает существующий `reap_stale` — второго места
  правды для возврата assignee нет.
- **Не решает**: «дубль прогонов worker.yml» (два job'а на одном прогоне) — это отдельная
  гвардия в task.sh (стопгэп #121) и concurrency-группа; замок — про задачу, не про прогон.
- **Права**: создание/удаление `refs/locks/*` требует contents:write — есть и у
  GITHUB_TOKEN orchestra (permissions workflow), и у PAT воркера.
