# ADR 0001. Push-модель вместо WebSocket-туннеля

- **Дата:** 2026-08-28
- **Статус:** принято
- **Смежное:** [GitHub Actions](../research/21-github-actions.md),
  [Cloudflare Free](../research/20-cloudflare-free.md),
  [отвергнутое, п.3](../research/30-rejected-alternatives.md)

## Контекст

Морда живёт в Cloudflare и должна быть доступна всегда. Руки (git, тесты, исполнение команд)
физически не могут жить в Workers: `node:child_process` там нефункциональная заглушка, а
`node:fs` — виртуальная файловая система изолята, не диск с репозиторием.

Значит нужен внешний исполнитель и способ отдать ему работу. Раннер GitHub Actions сидит за
NAT: входящих соединений к нему нет, Durable Object до него не достучится.

## Рассмотренные варианты

**А. Reverse tunnel.** Job поднимается, сам открывает исходящий WebSocket к Durable Object и
тянет команды по мере поступления. Даёт per-command исполнение: агентский цикл живёт в
облаке, руки выполняют отдельные команды.

**Б. Push-модель.** Durable Object дёргает `repository_dispatch`, job поднимается под
конкретную задачу, выполняет её целиком и умирает. Связь односторонняя: job сам шлёт события
в DO обычным HTTP.

## Решение

Вариант Б.

## Причины

Вариант А отвергнут дважды, независимыми причинами — и это важно: устранение одной не
воскрешает его.

**Правовая.** GitHub Terms for Additional Products запрещают для GitHub-hosted раннеров
«any other activity unrelated to the production, testing, deployment, or publication of the
software project associated with the repository», а также «any activity that places a burden
on our servers, where that burden is disproportionate to the benefits provided to users».
Job, простаивающий на сокете в ожидании команд извне, попадает под это по смыслу. Явного
пункта про reverse tunnel нет, но санкции названы прямо: отключение репозитория,
«suspension or termination of your GitHub account».

**Экономическая.** Cloudflare: «Outgoing WebSockets do not hibernate», и исходящее соединение
защищает объект от вытеснения не более 15 минут. Постоянный туннель держит Durable Object в
памяти круглосуточно: 86 400 с × 0.128 GB = ~11 059 GB-s в сутки из 13 000 доступных на
бесплатном плане. 85% дневного бюджета на один сокет, второго уже не будет.

Дополнительно против А: потолок job'а 6 часов, эстафета к преемнику ничем не гарантирована по
времени, и постоянно занятый job съедает 1 из 20 слотов параллелизма.

## Последствия

**Принимаем:** между постановкой задачи и началом работы проходит время старта job'а.
GitHub его не документирует; по чужим замерам — секунды при тёплом пуле, десятки при
холодном, изредка часы в очереди. Для автономного цикла несущественно, для живого чата
заметно.

**Принимаем:** гранулярность работы — задача, а не команда. Job получает осмысленный кусок
работы целиком, а не отдельный вызов bash. Отсюда следует [ADR 0002](0002-loop-in-runner-not-do.md).

**Получаем:** схема укладывается в бесплатные планы обеих платформ и не нарушает ничьих
правил. Durable Object гибернирует между задачами и почти не тратит бюджет GB-s.

**Ограничение, о котором легко забыть:** внешние триггеры упираются во вторичный лимит
GitHub API — 80 запросов в минуту и 500 в час на content-generating операции, к которым
относится `dispatches`. Не 5000, как можно подумать по основному лимиту PAT.

## Когда пересмотреть

- Переход на self-hosted runner: ограничение «unrelated activity» сформулировано именно для
  GitHub-hosted, на своём железе оно не действует.
- Переход на Workers Paid: бюджет GB-s перестаёт быть узким местом, а Containers дают
  исполнителя без NAT-проблемы вообще.
