# ADR 0016. Конкуренция за код не устраняется приёмом регистрации: границы параллельной работы

- **Дата:** 2026-09-10
- **Статус:** принято (по замерам задач #879, #904)
- **Смежное:** [задача #749](https://github.com/mytab0r/edge-harness/issues/749) (регистрация как данные),
  [задача #879](https://github.com/mytab0r/edge-harness/issues/879) (конкуренция за scheduler.py)

## Контекст

Задача #749 ввела приём «регистрация как данные» для устранения конфликтов в `repo-ci.yml`: вместо того, чтобы N PR добавляли независимые строки в один файл (конфликты на каждом мерже), каждый PR кладёт гвардию в отдельный файл каталога `scripts/ci/guards/*.sh`, а реестр остаётся в коде, читающем каталог. Конфликты исчезли.

Через неделю после мержа #749 возникла гипотеза применить тот же приём к `scheduler.py` — горячему файлу 4017 строк, который тогда трогали 9 открытых PR (#879). Замер показал, что приём **не переносится напрямую**.

## Проблема

Приём работает **только** для независимых элементов (регистрация: каждая гвардия добавляется в конец списка, не пересекаясь с другими PR).

Для кода с взаимозависимостями (функции, состояние, порядок вызовов) конкуренция остаётся конкуренцией за **семантику**, не за **форму**.

**Живой замер (2026-09-10):**

Шесть открытых PR трогают `scripts/orchestra/scheduler.py`:

| Функция | PR, которые её правят |
|---|---|
| `main` | #870, #567, #408 |
| `dispatch_worker` | #870, #831, #408 |
| `dispatch_conflict_rework` | #831, #567 |
| `reap_stalled_worker_run` | #870, #831 |
| `unhealthy_pulls` | #644, #408 |
| `accept_merged_tasks` | #644, #542 |

Все шесть пересечений — разные PR правят одну и ту же **существующую** функцию, не добавляют новую рядом. Две характеристики этого класса конфликтов:

1. Они по смыслу: разные баги в одной функции, разные части поведения.
2. Они физически неизбежны: два PR, правящих РАЗНЫЕ строки одной и той же функции, задевают соседний контекст и конфликтуют при любом порядке слияния — это не артефакт хранения.

Приём #749 (каталог файлов) не переносится: нельзя вынести «половину `dispatch_conflict_rework`» в отдельный файл без введения дополнительной инфраструктуры (плагинной точки расширения, интерфейса), которая сегодня не нужна ни одному из шести PR — они правят существующую функцию, не добавляют новую.

## Сопутствующее наблюдение

После устранения конфликтов в `repo-ci.yml` конкуренция возникла на **другом** файле — `scripts/orchestra/repo_invariants.py` (задача #904). Номера инвариантов назначаются вручную, и параллельные PR берут один номер. Это **регрессия приёма**: номер это регистрация, но как регистрация вручную назначаемых целых чисел, а не как регистрация данных в каталоге.

Полный цикл: устранение конфликтов за `repo-ci.yml` → переезд конфликтов в `scheduler.py` (невозможно устранить приёмом) → конкуренция за ручное назначение номеров в `repo_invariants.py` (новая регистрация, тот же класс ошибки).

## Решение

**Параллельная работа на одном файле/функции требует:**

1. **Измерения объёма конфликтов перед рефакторингом** — разбивка больших файлов (scheduler.py 4017 строк, repo_invariants.py) по темам снимет конфликты МЕЖДУ темами (например задача о приёмке PR не должна конфликтовать с диспетчингом воркера) но не ВНУТРИ темы. Нужно измерить, какой процент от всех конфликтов объясняется между-тематическим наложением.
2. **Темп слияния, а не структура** — если конфликты ВНУТРИ одной темы неизбежны (содержательные пересечения), то рычаг это: (а) меньший размер PR (каждый PR трогает меньше функций), (б) более частое слияние (меньше времени для накопления параллельных веток), (в) последовательное планирование вместо параллельного, если конфликты систематические.
3. **Регистрация должна быть детерминирована** — если N PR добавляют элементы в список и нужна уникальность (номера инвариантов), номер не должен назначаться вручную. Либо это стабильный ключ (имя), либо порядковый номер, вычисляемый из реестра.

## Что это означает для архитектуры

**Приём «регистрация как данные» — это не универсальное лечение конкуренции.** Это решение для КОНКРЕТНОГО класса (независимые элементы, добавляемые в конец списка). Для кода с правками существующего поведения приём не работает.

**Параллельная работа на одном файле неизбежна**, когда:
- Файл реально горячий (много тем разработки затрагивают его).
- Темы независимы по смыслу, но не по структуре (задачи о разных вещах, разные баги в одной функции).

Решение — не приём структуры, а техника работы: темп слияния, размер PR, планирование. Эти решения нужны независимо от того, лежит ли код в одном файле или разбит на модули.

## Адреса в коде и задачах

- Задача #749: регистрация как данные для гвардий (успешная миграция, конфликтов нет).
- Задача #879: почему приём не переносится на scheduler.py (с честным замером конкуренции).
- Задача #904: ручное назначение номеров инвариантов (регрессия приёма на другом файле).
- Задача #762: механический ребейз (техника уменьшения конфликтов, часть решения).

## Когда пересмотреть

- Если измер (задача #879, п. «Возможный первый шаг») покажет, что доля между-тематических конфликтов на scheduler.py > 60% — разбивка на модули окупает риск рефакторинга.
- Если темп слияния на основной ветке стабилизируется < 20 минут между PR (сегодня есть часовые прогулки) — объём параллельной работы автоматически снизится.
