# ADR 0022. Связывание контекста между каналами: три точечных приёма вместо общего носителя

- **Дата:** 2026-09-14
- **Статус:** принято (задача #1203)
- **Смежное:** AGENTS.md «Вывод, оплаченный инцидентом, живёт в репозитории»,
  AGENTS.md «Инцидент оставляет инвариант, а не только фикс»,
  docs/agents/PROTOCOL.md (белые пятна, пул задач),
  scripts/lib/duplicate_guard.py (существующий, но не тот инструмент — см. «Отвергнуто»),
  issue #1172 (класс «недостижимый механизм»), issue #1200/#1201/#904 (готовое решение),
  issue #1092/#1093 (измеренные числа против оценки)

## Контекст

Задача #1203: «каналы не видят находок друг друга» — за сутки 2026-09-13/14 связь между
параллельными каналами (готовое решение той же подзадачи, класс, объясняющий частный случай,
измеренное число вместо оценки, ловушка среды) обеспечивал координатор вручную, читая отчёты и
перенося контекст в задания.
Постановка требует: установить, чего уже хватает; проверить
классификацию четырёх видов знания на живых данных; предложить носитель с ценой; назвать признак
релевантности; доказать на четырёх живых случаях дня, что механизм доставил бы нужное знание
нужному каналу и не выдал бы больше трёх нерелевантных элементов.

## Разбор четырёх заявленных случаев (проверено по первоисточникам, не по пересказу)

### 1. «Готовое решение» — #1200 против #904/PR #1201

decision_numbering.cmd_check красил main за коллизию со сторонним PR; invariant_numbering.py
(issue #904, PR #1201) спроектирован без этого дефекта с первого коммита и явно называет формулу
фикса. Проверка первоисточника: issue #1200 уже несёт в теле дословную цитату
scripts/lib/invariant_numbering.py::cmd_check, имена обоих тестов
(test_cmd_check_does_not_blame_main_for_a_foreign_open_pr_collision,
test_cmd_check_blames_main_for_an_intra_main_duplicate) и объяснение формулы (involved ==
main-only). Автор #1200 (канал, работавший над #904) записал решение в тело issue сам, до того как
кто-либо другой начал чинить #1200. Перенос уже состоялся — механизмом, который правила
репозитория и так предписывают («Вывод, оплаченный инцидентом, живёт в репозитории, а не в
комментарии», белое пятно как канал синхронизации, PROTOCOL.md). Дополнительного носителя не
требуется — требуется только чтобы исполнитель прочёл тело issue целиком, что уже входит в
правило «Прочти AGENTS.md и карту документации» (PROTOCOL.md, п.1 воркер-плейбука).

### 2. «Класс, объясняющий случай» — #1172 и ревизия #1184/#1188/#1176

Три независимых случая (#1085/#1089, #1103/#1104, #1084/#1114) пойманы ai-review, каждый на
своём PR — не переносом между каналами, а собственной аналитической способностью ревьюера,
применённой трижды независимо (докстринг #1172, столбец «Кто поймал» — везде ai-review).
Аггрегирующая issue #1172 появилась после всех трёх. Настоящий перенос произошёл позже: PR #1180
построил механический инструмент (scripts/orchestra/reachability_guard.py, операционализация
критерия из #1172), и issue #1184 — читая #1172 и применяя reachability_guard.py к текущему main
read-only — нашла три новых живых дефекта (инвариант 14, класс timed_out, такт пульса 20 мин
против заявленных 15). Перенос сработал через уже существующий приём репозитория: класс —
аггрегирующая issue — механический чекер — прогон чекера более поздним каналом. Это ровно то,
что AGENTS.md уже требует правилом «Инцидент оставляет инвариант, а не только фикс» — не новый
механизм, а дисциплина, которую этот случай подтверждает работающей.

### 3. «Измеренное число вместо оценки» — docs/research/33 (PR #1093) против PR #1165/#1173

Раздел 5 docs/research/33-worker-parallelism-limits.md (ветка PR #1093, ещё открыт) оценивал
узкое место как «писи», ~3130 строк/прогон. Раздел 10 того же файла (коммит 3d7d8a69) заменяет
оценку измеренным числом: rows_read около 150898/прогон, потолок около 33 прогонов/сутки —
источник назван явно: «PR #1165 (слит 2026-09-13T23:01Z), PR #1173 — фикс и гвардия rows_read» и
живой прогон quota-watch 21:49Z. Перенос состоялся через границу PR (документ ссылается на уже
слитый чужой PR по номеру и времени), но с задержкой: PR #1093 сначала писал раздел 5 на оценке,
потому что на тот момент PR #1165 ещё не был слит. Это не дефект носителя — это гонка «когда
именно измерение стало доступно». Правильная процедура (уже применённая авторами #1093) — при
малейшей возможности цитировать первоисточник измерения (лог quota-watch, конкретный прогон), а
не собственную оценку, и обновлять раздел, когда первоисточник появляется, — что и произошло.

### 4. «Ловушка среды» — поверхностный клон рабочего дерева

Единственный из четырёх случаев, для которого на момент начала этой задачи не нашлось никакого
носителя (grep по docs/ на «shallow»/«поверхностн»/«add-add» — 0 релевантных попаданий; gh
issue list --search / gh search issues по «shallow»/«поверхностн» — 0 совпадений по теме git-
клона). Подтверждено вживую этой же задачей: .claude/worktrees/1203-cross-channel-context,
свежесозданный scripts/git/task-branch, дал git rev-parse --is-shallow-repository равно true.
Правило репозитория «Вывод, оплаченный инцидентом, живёт в репозитории» здесь ещё не сработало —
находка была устной (передана этой задаче координатором в постановке), не записанной. Закрыто
этим PR — см. «Что сделано».

## Что уже хватает (проверено, не предположено)

- Долгоживущее знание (docs/research/, docs/decisions/, AGENTS.md) — работает, но структурно
  медленнее свежей находки (требует PR и мерж). Не инструмент для «час назад».
- Явные ссылки в теле issue/PR (Related: #N, цитаты файлов/функций/тестов) — рабочий, дешёвый,
  уже используемый канал (случай 1 — прямое доказательство). Никакого нового кода не требует,
  только дисциплина (уже предписанная PROTOCOL.md/AGENTS.md).
- Аггрегирующая issue класса плюс механический чекер (reachability_guard.py) — рабочий канал для
  случая «класс, объясняющий случай» (случай 2). Уже предписан AGENTS.md («Инцидент оставляет
  инвариант, а не только фикс»).
- scripts/lib/duplicate_guard.py — существует, посчитан и откалиброван (Jaccard по заголовку,
  порог 0.3), но решает другую задачу: не пускает дубль новой issue в момент её заведения,
  сравнивая заголовки. Собственный докстринг честно называет предел: реальная пара #518/#548
  (один дефект, разные слова) даёт score 0.18 — ниже порога, то есть даже в своей задаче ловит
  меньше половины похожих случаев по формулировке. Не то же самое, что «найти родственную issue
  по номеру класса, файлу или готовому решению» — расширение этого инструмента на «поиск по телу
  произвольной новой задачи» не даёт удовлетворительной точности без переработки метода (см.
  «Отвергнуто»).
- free_task.py::priority_reason — отвечает «почему эта задача здесь» по графу/меткам, не «что
  уже известно по этой теме». Не тот инструмент, расширять сюда не за чем: другая
  ответственность (порядок, не содержание).
- soft_failure_digest (PR #1136) — группирует повторяющиеся мягкие отказы CI по отпечатку
  текста. Другая предметная область (деградация, наблюдаемая в прогонах workflow), пересечения
  с переносом находок между каналами не найдено при чтении кода.

## Классификация видов знания — подтверждена, пятый не найден

Все четыре вида, названные постановкой, нашли ровно одно подтверждение каждый (разбор выше).
Пятый кандидат, рассмотренный и отклонённый: «область/файл уже занят параллельным PR»
(негативная информация «не трогай, там работают») — тоже наблюдался в этой самой задаче
(секция «КОНКУРЕНЦИЯ» задания), но это не новый вид: несёт его тот же приём («явная ссылка,
переданная координатором при постановке задачи»), плюс структурно уже покрыт
conflict_declared_tasks и меткой conflict оркестратора после факта столкновения. Отдельного
носителя не требует.

## Рассмотренные варианты и почему отклонены

1. Автоматический поиск по телу новой/начинаемой задачи среди всех открытых issues/PR
   (расширение duplicate_guard-подобной токенной схожести на произвольный текст, вызывается на
   каждый task-branch). Отклонено: (а) стоимость — task-branch/доводка PR происходит десятки
   раз в сутки (около 33 прогонов воркера плюс hands плюс ручные доводки), каждый вызов —
   минимум один gh issue list/search (квота search: 30/мин, отдельный маленький лимит — см.
   INFRA-GH.md, «не гонять поиск в цикле»); квота API уже исчерпывалась в день постановки этой
   задачи. (б) точность — собственный докстринг duplicate_guard.py документирует около 50%
   recall на title-схожести (0.53 ловит, 0.18 — нет, оба реальных случая инцидента); для случая
   2 (#1172) общий признак между инстансами — не общие слова заголовка и не общий файл (разные
   файлы: scheduler.py, cf-worker/src, цепочка провайдеров), а абстрактный класс — лексический
   поиск такую связь физически не находит. Для случая 1 признак — общий файл/функция, но это
   уже покрыто пунктом «явные ссылки» без нового кода. Реализация с неопределённой точностью в
   день, когда квота и так была тесной — плохой размен.
2. Инструктировать AI-ревьюера (ai_prompt.md) явно проверять список открытых issues с метками
   white-spot/impact:system перед вердиктом. Не отклонено полностью, но не реализовано этим PR:
   ревьюер уже имеет bash и gh доступ в песочнице (см. ai_prompt.md: «в репозитории можно
   запускать команды... проверяй подозрения, а не догадывайся») и уже независимо поймал все три
   исходных случая класса #1172 собственным анализом, без переноса от соседнего канала. Эффект
   добавления одной инструкции «проверь open issues с такими-то метками» непредсказуем без
   живого A/B (шум против пользы), а сам приём (класс плюс механический чекер) уже работает и
   не нуждается в этой добавке для случая 2. Оставлено как возможное будущее улучшение, не как
   решение этой задачи.
3. Общий «журнал находок» (третий кандидат постановки: файл-журнал, читаемый агентом при
   старте). Отклонено по тому же аргументу, что уже звучит в самой постановке: растёт и
   протухает, и дублирует уже существующий журнал — открытые issues пула сами по себе являются
   таким журналом (это и есть их функция по конвенции репозитория); заводить второй означало бы
   нарушить «одно место правды».

## Что сделано этим PR (узкая часть, дешёвая и с нулевой предельной стоимостью)

Единственный из четырёх случаев без существующего носителя на момент начала задачи — случай 4
(ловушка среды). Носитель для этого класса знания уже существует и печатается бесплатно (без
сетевого вызова, статический текст) на каждом входе в задачу: scripts/gh/infra_digest.sh,
вызывается из scripts/git/task-branch и scripts/worker/task.sh (оба входа в agent-ветку).
Закрыт ровно этот пробел, тем же самым, уже работающим носителем:

- scripts/gh/infra_digest.sh — новая строка о поверхностном клоне рабочего дерева и лечении
  (git fetch --unshallow origin).
- docs/agents/INFRA-GH.md — п.5 раздела «Первым делом — грабли» с полным разбором и живой датой
  обнаружения.

Цена: одна строка статического текста, печатается на каждом входе в задачу без единого нового
сетевого вызова (текст уже был частью существующего, обязательного к печати дайджеста).
Поддержка: нулевая — не протухает (это не число и не список из внешней системы, а инструкция
«если увидел X, сделай Y»). Риск шума: нулевой — печатается всегда целиком, независимо ни от
какого поиска, три строки не переполняют существующий уже пяти-шести-строчный дайджест.

## Проверка на четырёх живых случаях (числом, как того требует постановка)

|---|---|---|---|
| 1 | #1200 из #904/PR #1201 | Да — явная цитата в теле #1200 | Нет |
| 2 | #1172 -> #1184/#1188/#1176 | Да — класс плюс механический чекер (PR #1180) | Нет |
| 3 | docs/research/33 из PR #1165/#1173 | Да, с задержкой — ссылка на первоисточник после мержа | Нет (процедура уже верная) |

Ни разу не потребовалось нового поискового/автоматического механизма; трижды из четырёх знание

предельной стоимости канал.

## Главный риск, названный явно

Перенос всего подряд (постановка задачи прямо предупреждает об этом) хуже отсутствия переноса:
агент, получающий десятки «возможно релевантных» issue на каждый старт задачи, перестаёт их
читать — тот же класс, что уже случился с #1172 (проверка на прод-величинах: система, которая
предупреждает всегда, предупреждает ни о чём). Дешёвый и надёжный признак релевантности,
подтверждённый разбором выше, — не токенная схожесть заголовка и не общий файл (оба ловят
только часть из четырёх случаев), а явная, вписанная человеком или агентом ссылка на номер
issue/PR в теле находки: это дорого при записи (кто-то должен заметить связь и написать номер),
но дёшево и точно при чтении (не гадание, а адрес), и это единственный признак, который сработал
во всех подтверждённых случаях 1 и 2 этого разбора.

## Не подтверждено

- Не измерено, снизился ли бы шум ниже трёх нерелевантных элементов при попытке всё-таки
  реализовать автоматический поиск (вариант 1 из «Рассмотренные варианты») — оценка «признак
  физически не существует для случая 2» опирается на разбор состава инстансов (разные файлы),
  не на прогон реального инструмента с настроенным порогом.
- Не проверено, снизит ли добавление инструкции ai-ревьюеру (вариант 2) реальный recall на
  будущих случаях класса #1172 — предложение осталось нереализованным сознательно, эффект не
  измерен ни в одну, ни в другую сторону.
- Не подтверждено, есть ли за пределами этих четырёх случаев инцидент, где общий файл/функция
  (а не явная ссылка) был бы единственным доступным признаком связи, — тогда точечный
  file-path-поиск (см. случай 1) мог бы иметь смысл отдельно от общего «журнала находок»; в
  разобранных четырёх случаях он оказался избыточен (случай 1 уже нёс явную ссылку без него).

## Вернуться если

Появится измеренный на реальных данных случай, где (а) знание не несёт явной ссылки на номер и
(б) общий файл/функция — надёжный признак связи (в отличие от случая 2, где связь абстрактная).
Тогда узкий file-path-поиск, вызываемый только при заведении новой issue (тот же дешёвый момент,
что уже использует duplicate_guard.py, не на каждом task-branch), — следующий шаг, не общий
«контекст-бас».
