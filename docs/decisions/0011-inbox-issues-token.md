# ADR 0011. Инбокс создаёт issues под собственным узким GH_ISSUES_TOKEN

- **Дата:** 2026-09-05
- **Статус:** принято (реализовано в #173, задача #20); шаг владельца —
  создать PAT и залить секрет, см. «Миграция»
- **Смежное:** [ADR 0008](0008-narrow-dispatch-token.md) (разделение токенов
  морды и конвейера), [задача #20](https://github.com/mytab0r/edge-harness/issues/20),
  спека «Инбокс владельца» (openspec/specs/journal-tasks-hands.md, пп. 30–37)

## Контекст

Инбокс владельца (#20) превращает директиву из чата в задачу пула — то есть
создаёт issue с меткой `task`. Создавать его может только сущность с правом
на Issues. Раскладка прав такая:

- `GH_DISPATCH_TOKEN` (секрет воркера) — по ADR 0008 узкий fine-grained
  **Contents+Actions**, «issues, PR, метки — всё уехало на GH_PIPELINE_PAT».
  Использовать его на создание issues — заведомый 403 в проде и
  гвардируемый redflag («новое использование вне deploy-пути»).
- `GH_PIPELINE_PAT` (широкий PAT конвейера) — в морду возвращать его нельзя:
  это ровно класс «широкий PAT на интернет-поверхности», который ADR 0008
  закрыл.
- hands-job (DSH headless) права на Issues не имеет принципиально: токен
  аренды снимается до старта DSH, у агента в job'е прав на пуш и issues нет.
- Первая редакция инбокса (#173) читала несуществующий `GH_PIPELINE_PAT` с
  фолбэком на `GH_DISPATCH_TOKEN` — тайпчек красный, каждая директива в проде
  навсегда `failed` (обе находки AI-ревью #173).

## Решение

**Третий узкий секрет под собственным именем: `GH_ISSUES_TOKEN`.**

1. fine-grained PAT **только Issues: RW** на этот репозиторий. Имя означает
   ширину (принцип ADR 0008): у каждого секрета — одна роль и минимальный
   пермишен.
2. Живёт в секрете воркера; `deploy-worker.yml` синхронизирует его при каждом
   деплое **опционально**: секрет не задан — деплой не красится, ставится
   warning. Худший сценарий утечки — создание issue в публичном репозитории.
3. Пока секрет не задан, директивы инбокса не молчат и не падают: сообщение
   повторяется в `new` до `LIMITS.messageMaxAttempts`, затем честный
   `failed` с `issues_not_configured`; установка секрета сама доводит новые
   директивы (накопленные — по `retry_failed`).
4. Вызов GitHub API остаётся в DO — с правом, которому доверять можно. Это
   сознательное отличие от варианта «создание уносит job»: директива обязана
   попасть в пул сразу и видимо, а не через запуск DSH-агента, которому всё
   равно пришлось бы выдавать токен.

## Рассмотренные альтернативы

- **Директива → очередь задач (`POST /api/tasks`) → issue создаёт job.**
  Отвергнуто: очередь задач — механизм немедленного запуска DSH headless,
  а не пула; семантика «директива лежит в пуле и ждёт исполнителя» — это
  issue, а не hands-ран. Плюс job всё равно нужно было бы дать право на
  Issues (новая поверхность в `hands.yml`).
- **Отдельный секрет-фолбэк внутри `GH_DISPATCH_TOKEN`.** Отвергнуто прямо
  ADR 0008: имя секрета обязано означать его ширину, подсадка второй роли на
  то же имя — тот класс, который там закрыт.
- **`GH_PIPELINE_PAT` в морде.** Отвергнуто: возвращает закрытый класс
  «широкий PAT на интернет-поверхности».

## Миграция (шаг, который есть только у владельца)

1. Создать fine-grained PAT «только этот репозиторий, Issues: RW» (PAT
   создаются только в UI — делегировать нельзя).
2. `gh secret set GH_ISSUES_TOKEN` (значение не должно транзитом проходить
   через публичные поверхности).
3. Следующий деплой `deploy-worker.yml` сам синхронизирует секрет в воркер.
4. Проверка видимым результатом: директива в инбоксе →
   `POST /api/messages/process` → `issue_created` и issue с меткой
   `source:inbox` в пуле.

До шага 1 инбокс работает полностью, кроме создания issues: приём, разбор,
классификация, группировка, статусы — директивы копятся с честной ошибкой.

## Последствия

- Класс «создание issues сущностью без права на Issues» закрыт по построению:
  правое имя секрета читается в месте вызова, фолбэков нет.
- Три GitHub-токена в воркере/конвейере — цена принципа «имя = ширина»;
  реестр: `GH_DISPATCH_TOKEN` (Contents+Actions), `GH_ISSUES_TOKEN` (Issues),
  `GH_PIPELINE_PAT` (всё остальное, вне морды).
- Гвардия `scripts/lib/test_dispatch_token_usage.py` не сканирует TS-код
  морды на не-dispatch использования токенов — заведена задача из ревью #173
  (распространить гвардию на `cf-worker/src`).
