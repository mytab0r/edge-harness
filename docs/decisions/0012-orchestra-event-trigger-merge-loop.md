# ADR 0012. Событийный триггер оркестратора и цикл слияний за один прогон

- **Дата:** 2026-09-05
- **Статус:** принято (реализовано в #330, задача #297)
- **Смежное:** [задача #297](https://github.com/mytab0r/edge-harness/issues/297),
  `docs/research/21-github-actions.md` (раздел «Замер schedule на этом
  репозитории», раздел «Метка, поставленная GITHUB_TOKEN, не создаёт
  событий»), спека `openspec/specs/journal-tasks-hands.md` пп. 16, 18,
  дельта `branch-update-single-candidate`

## Контекст

`.github/workflows/orchestra.yml` держал `cron: "*/15 * * * *"` (96 прогонов/
сутки формально), но живая доставка расписания на этом репозитории измерена
в ~6.7% (31 из ~465 за 116.3 ч, `docs/research/21-github-actions.md`).
Пульс из Durable Object дублирует расписание собственным `workflow_dispatch`
и даёт основную массу реальных прогонов, но это тоже периодика, зависимая от
здоровья самого DO (2026-09-05 пульс вставал на часы из-за исчерпания квоты
`rows_read`). Одновременно `merge_queue()` сливает ровно один PR за запуск
(сериализация намеренная — после слияния меняется база остальных PR).
Комбинация «редкие прогоны + один PR за прогон» означает, что готовый к
слиянию PR ждёт часами даже когда конвейер формально здоров.

## Решение

1. **Событийный триггер — `workflow_dispatch` из самого конвейера ревью, не
   `labeled`.** `pr-review.yml` (job `review`) и `ai-review.yml` (job
   `verdict`) получают шаг `gh workflow run orchestra.yml --ref main` под
   `GH_TOKEN: ${{ github.token }}` в конце соответствующего job'а. Диспатч
   безусловный (не только при `*:ok`) — `changes-requested`/конфликт тоже
   может разблокировать очередь, а `orchestra.yml` сам дёшево решает, есть ли
   что сливать. `schedule` остаётся как страховка на случай, если событие
   потерялось, но на него больше не рассчитывают.
2. **Цикл слияний внутри одного прогона.** `main()` вызывает `merge_loop()`
   вместо одиночного `merge_queue()`: слить готовый → подтянуть следующего
   (`update_branch`) → дождаться проверок → слить, пока есть что сливать.
   Потолки — `MERGE_LOOP_MAX_MERGES = 5`, `MERGE_LOOP_TIMEOUT_SECONDS = 20 * 60`,
   пауза между непродуктивными проходами `MERGE_LOOP_POLL_SECONDS = 30`.
   Останов — любое из: потолок слияний, таймаут, проход без прогресса.
3. **Сериализация `update_branch` не сломана**, но переопределена на уровень
   прохода: `merge_queue()` по-прежнему обновляет не больше одной ветки за
   один свой проход (инвариант #252/#288), но слот сбрасывается заново
   каждый проход цикла, а не один раз на весь прогон — цикл способен
   обновить несколько разных PR подряд. Это возможно потому, что причина
   строгого ограничения «одно обновление на весь прогон» (в 2026-09-02
   подтягивание сбрасывало `ai:ok` безусловно на каждый пуш) больше не
   действует: `ai-verdict-survives-merge` (#252/#294) сохраняет `ai:ok` при
   чистом подтягивании main без изменения диффа PR.

## Рассмотренные альтернативы

- **`on: pull_request: types: [labeled]` на постановку `review:ok`/`ai:ok`.**
  Отвергнуто фактом, не предположением: этот же репозиторий уже измерил
  (2026-08-31, `docs/research/21-github-actions.md`) — `check_pr.py` ставит
  метку токеном job'а, `labeled` от PR #138 не сработал. Антирекурсия GitHub:
  события от `GITHUB_TOKEN`, кроме `workflow_dispatch` и
  `repository_dispatch`, не создают новый run. `workflow_dispatch` — уже
  подтверждённое живьём исключение (тем же способом `scheduler.py` дёргает
  `worker.yml`).
- **Учащение `cron` (например `*/5`).** Не устраняет проблему: измеренная
  доставка расписания — свойство платформы (GitHub Actions free-план
  разбрасывает scheduled-триггеры без гарантии интервала под нагрузкой),
  учащение номинального интервала не меняет процент реальной доставки.
- **Снять потолок `merge_loop` (сливать, пока не кончится очередь).**
  Отвергнуто: время job'а ограничено (6 часов на раннер, но лишний расход
  минут CI — реальная стоимость), а без потолка обрыв по таймауту раннера
  происходит без контролируемой точки останова и без диагностики «почему
  остановились».

## Что вне рамок

- Причина, по которой пульс DO не должен быть единственным источником
  регулярности, не устраняется этой дельтой — #297 убирает зависимость
  цикла слияний от периодики вообще (событие вместо такта), не чинит
  DO/квоты `rows_read` (отдельная тема, `do-rows-read-quota`).
- Egress GitHub API из воркера морды (#133) — не входит: событие в этой
  дельте создаёт GitHub Actions job (`gh workflow run` из `GH_TOKEN` внутри
  уже идущего рана), не морда напрямую.

## Условие возврата к расписанию как рабочему каналу

Если событийный диспатч на практике окажется ненадёжным (например
`gh workflow run` систематически падает или не создаёт run — см. задачу из
ревью #330 про проверку видимого результата диспатча), интервал `*/15`
остаётся резервным каналом без изменений — учащать его нет смысла (см.
альтернативы выше), но и убирать нельзя: это единственная страховка на
полную потерю события.

## Последствия

- Доставка запуска оркестратора перестаёт зависеть от periodic-триггеров;
  готовый к слиянию PR подтягивается в тот же проход, где выставлена метка
  ревью, а не ждёт следующего тика расписания/пульса.
- Несколько PR могут слиться за один прогон `orchestra.yml`, что увеличивает
  расход минут одного job'а, но снижает суммарное число прогонов и задержку
  до слияния.
- `openspec/specs/journal-tasks-hands.md` п.16 («один merge за запуск») и
  `openspec/changes/branch-update-single-candidate/specs/journal-tasks-hands/spec.md`
  помечены устаревшими ссылкой на эту дельту (см. правки в этом же PR).
