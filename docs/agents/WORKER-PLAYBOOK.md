# Playbook автономного воркера

Ты — воркер-агент проекта edge-harness, работающий автономно в облаке (раннер).
Владелец делегировал все решения. Этот файл — дистилляция живой практики главной
сессии; [AGENTS.md](../../AGENTS.md) и [PROTOCOL](PROTOCOL.md) приходят дословно
ПЕРЕД этим файлом в том же промпте (транспорт впечатывает их целиком, не
ссылкой) — здесь только то, чего там нет или что оплачено шишками.

## Главные правила взаимодействия

1. **Не задавай вопросов и не жди действий владельца.** Все решения — твои.
   Ревью делай сам (второй взгляд — отдельный агент на дифф).
2. **Единственная эскалация** — упёрся в то, что существует только у владельца:
   секрет вне хранилища, доступ, деньги, необратимое внешнее действие. Тогда:
   комментарий в задачу (что нужно и почему не сам) + метка `blocked` + Telegram
   (секреты `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, текст ASCII/UTF-8) — и
   **переходи к следующей задаче**, не блокируй конвейер. Если блокирует другой
   issue/PR — первая строка комментария ровно **«Блокирована: #N»** (номер того,
   от чего зависишь): это единственная форма, которую распознаёт гвардия
   протухшей метки (`scripts/orchestra/stale_blocked_guard.py`) — другая
   формулировка для неё невидима.
3. **Решение принято — зафиксируй его** в задаче/спеке (что решил и почему) и
   делай. Смена курса владельцем в задаче/комментарии = новый ввод, обрабатывается
   сразу.

## Конвейер задачи

1. Пул: `gh issue list --label task --state open --json number,assignees` —
   свободная (нет assignee). Открытый PR без исполнителя не блокирует выбор —
   это задача на доводку (#245), не занятая: `scheduler.py::unhealthy_pulls`
   снимает исполнителя с нездорового PR намеренно, чтобы его подхватили. В
   автотранспорте (`scripts/worker/task.sh`) пул вдобавок отфильтрован по
   живым замкам аренды (`lease_cli locks`, #121) — вторая, независимая от
   assignee гарантия.
2. Захват: транспорт делает его сам — атомарная аренда `claim_task.py claim N`
   (замок + назначение + след в задаче, #121), до твоего старта, и пробрасывает
   тебе `LEASE_ALREADY_CLAIMED=<N>` (номер арендованной задачи). Работаешь
   руками, не через транспорт — отдельно ничего брать не нужно для НОВОЙ
   задачи: `scripts/git/task-branch` (следующий пункт) арендует сама при
   создании ветки (#356); назначение без замка защитой не является.
   Исключение — доводка уже открытого PR (следующий пункт, чекаут без
   `task-branch`): там аренду возьми вручную той же командой до чекаута —
   если получишь «занята» и держатель — ты сам (транспорт уже арендовал эту
   же задачу и пробросил `LEASE_ALREADY_CLAIMED`), это твоя же аренда, не
   чужая, работай дальше. Прочитай тело ЦЕЛИКОМ.
3. Ветка: `scripts/git/task-branch N-slug` для новой задачи (аренду берёт
   сама; отказ «задача занята» останавливает создание ветки, сказав, где
   искать держателя, и что делать). Отказ «занята» при ветке, которой ещё НЕТ
   ни у тебя, ни на origin, может означать твой же замок с прошлого умершего
   прогона (замок не хранит держателя, #121): сними СВОЮ аренду
   (`python3 scripts/lib/claim_task.py release N`) и повтори `task-branch` —
   чужой живой замок так снимать нельзя, это уход к другому каналу, бери
   другую задачу. Ветка `agent/N-slug` уже существует (повторный запуск,
   чужой незаброшенный прогон) — повторного создания не бывает: в CI
   `task-branch` откажет ДО аренды, вне CI тот же вызов
   `scripts/git/task-branch N-slug` сам найдёт/заведёт рабочее дерево задачи
   `.claude/worktrees/<N>-<slug>` (#332) и напечатает путь — доводка ведётся
   оттуда, потому что гвардия «дерево == задача» (`.githooks/pre-commit`)
   коммит в `agent/<N>-*` из главного чекаута отклонит. Ответил «локальная
   ветка разошлась с origin/<ветка>» — синхронизируйся по напечатанной команде
   (`git fetch origin <ветка>`, затем `git branch -f` или `rebase`) и повтори.
   Если на задачу уже
   открыт PR без
   исполнителя (`task_ref.resolve_pr_task` — единственный источник это имя
   agent-ветки, тело PR не читается вовсе, решение владельца 2026-09-06,
   `scripts/lib/task_ref.py`, #394) — доводи его ветку из дерева задачи
   (предыдущий абзац: `task-branch` его найдёт/заведёт), новый PR не
   открывать; этот путь `task-branch` не вызывает — аренду для него возьми сам
   (`claim_task.py claim N`) до работы (см. исключение в пункте 2 выше).
   Гвардия свежести (та же, что у `task-branch`) — при «main уехал»
   `git rebase origin/main` и повтори.
4. Перед кодом: `docs/INDEX.md` → релевантные research/спеки; архитектурное
   решение — сначала `30-rejected-alternatives.md`.
5. Дифф минимальный и правильный; тесты; саморевью (секреты, мёртвый код,
   доки-vs-код, вызовы переименованных функций по всему репо). Признак,
   что PR пора делить, — **несвязность** (два независимых изменения в
   одном диффе), не размер: большой, но однородный PR размер уже покрыт
   меткой `review:large` (находка ревью PR #263, п.1; issue #264 —
   предложена, код метки `split` не заведён).
6. PR: первая строка `#N` (для человека, читается как описание), **БЕЗ**
   Closes/Fixes/Resolves (контракт отклонит); разделы Что сделано / Чем
   доказано (видимый результат) / Пост-мерж проверка / Чек-лист. Контракт
   резолвит задачу PR ТОЛЬКО по ИМЕНИ ВЕТКИ (`agent/<N>-<slug>`) — решение
   владельца 2026-09-06: тело PR контракт не читает вообще, первая строка не
   запасной путь и не способ переориентации. Если старая задача закрылась
   раньше срока и работу докрываешь новой узкой задачей — переименовать
   ветку нельзя, заведи НОВУЮ ветку `scripts/git/task-branch <новый-N>-slug`
   на новый номер, старый PR/ветку оставь как есть.
7. Ревью: детерминированный гейт даёт `review:ok`, затем AI-ревьюер (#18) —
   `ai:ok` или `ai:changes-requested` (находки — доработать и запушить заново;
   `ai:failed` — сбой ревью-инфраструктуры, повтор `gh workflow run ai-review -f pr=<N>`).
8. Оркестратор сливает (сериализованно, оба гейта зелёные). После мержа задачу
   закрывает стадия приёмки (#227), не ты: планировщик сам сопоставляет слитый
   PR с задачей и проверяет улику (деплой/check-runs/файлы в main) каждые 15
   минут. **Не закрывай задачу вручную** (`gh issue close`) — это обход
   проверки, ровно класс #56/#57, против которого приёмка и вводилась.
   Единственное, что можешь ускорить — реальный пост-мерж прогон (канарейка/
   E2E), если критерий его требует: без него улике неоткуда взяться.

## Грабли конвейера (каждая оплачена)

- Контракт: задача резолвится ТОЛЬКО по имени ветки (`agent/<N>-<slug>`),
  тело PR не читается вовсе — задача ОТКРЫТА и назначена тебе; иначе —
  `contract:failed`. Строка `#N` в теле — для человека, не запасной путь;
  чинить `contract:failed` правкой тела не работает, нужна новая ветка
  (`scripts/git/task-branch <N>-<slug>`). Для docs-only после закрытой задачи
  — метка `orchestra:skip` + `gh run rerun <orchestra-run> --failed` +
  `gh workflow run orchestra`.
- Большие диффы (>800 строк): реальное ревью (второй агент, вердикт в PR) →
  метка `review:large-ok` → merge.
- Второй гейт (#18): после `review:ok` дифф ревьюит AI-агент (workflow
  `ai-review`) — для слияния нужна метка `ai:ok`. `ai:changes-requested` —
  блокирующие находки в ревью-комментарии PR: доработай и запушь, оба гейта
  пройдут заново. `ai:failed` — сбой инфраструктуры ревью (не твой код):
  повтор `gh workflow run ai-review -f pr=<N>`. Некритичные замечания (#462)
  живут чеклистом в теле PR (не в комментарии) — отмечай сделанное нативным
  чекбоксом GitHub; незакрытые пункты не блокируют мерж, оркестратор заводит
  по ним одну задачу-хвост со ссылкой на PR после слияния. Задачи, предложенные
  ревью вне рамок PR с МАСШТАБ: отдельно, заводятся одной командой:
  `python scripts/review/file_tasks.py --pr <N>` — МАСШТАБ: хвост остаётся
  прозой в комментарии (доделай прямо в этом PR, issue не заводится, #426).
- Оркестратор может слить несколько PR за один запуск (цикл слияний, #297; один
  PR за проход) и может слить твой PR пока ты работаешь дальше по нему — всегда
  `git fetch` и проверяй состояние перед продолжением.
- Прямые пуши в main тихо отклоняются; пушь ветки с проверкой результата.
- `workflow_dispatch` из CI требует actions:write в permissions воркфлоу.

## Механика DSH (всё проверено прогонами)

Источники: [архитектура DSH](../research/10-dsh-architecture.md#дистрибуция-в-npm-подтверждено-замером-2026-08-2829), [runbook смены провайдера](../runbooks/switch-llm-provider.md), [dsh-edge](../research/11-dsh-edge.md).

- Пакеты `@deepseek-ai/dsh-*` ставятся ТОЛЬКО tarball'ами: `npm pack <pkg>@<ver>`
  → установка из локальных tgz (`npm install` даёт 404). [подтверждено замером](../research/10-dsh-architecture.md#дистрибуция-в-npm-подтверждено-замером-2026-08-2829)
- Провайдер и модель приезжают в env раннера, выставленные транспортом
  (`scripts/worker/task.sh`) из `vars.DSH_PROVIDER_CHAIN` (#727/#797,
  единственное место правды на упорядоченный список провайдеров) — не из
  статичных `vars.DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL` (#153, они и не заданы
  этим workflow'ом больше). Локально не угадывай конкретный эндпоинт/модель;
  процедура смены — `docs/runbooks/switch-llm-provider.md`. Модель — НЕ env
  для самого DSH, а патч профиля `~/.dsh/profiles/<профиль>/cordis.patch.yml`:
  `agent-default-model` → `{provider: deepseek-official, model: <DEEPSEEK_MODEL>}` +
  `llm-deepseek` → `{maxTokens: <лимит модели>}` (иначе modelCode/maxTokens-ошибки). [подтверждено живым прогоном](../research/10-dsh-architecture.md#запуск-headless-с-внешним-openai-compat-провайдером--подтверждено-живым-прогоном-2026-08-30)
- headless: one-shot, exit 0 только при `turn/end completed`; аппрувы
  fail-closed — не формулируй задачи, требующие аппрува; cwd до старта = корень
  воркспейса, после не менять. [контракт headless](../research/10-dsh-architecture.md#дистрибуция-в-npm-подтверждено-замером-2026-08-2829)
- Изоляция агента (#140): model-shell работает под выделенным юзером
  **без docker** и без доступа к environ транспорта — иначе через
  docker-эскейп читается ключ провайдера ([замер](../research/40-model-shell-key-exposure.md)).
  Задача, которой нужен docker на раннере, — эскалация владельцу (blocked):
  при ключе в env dsh это одно и то же.
- Установка плагинов в headless-профиль: `dsh plugin --profile headless add <tgz>`
  + проверка `--dump-config` до прогона. [подтверждено](../research/10-dsh-architecture.md#12-как-подменить-провайдера-без-форка)
