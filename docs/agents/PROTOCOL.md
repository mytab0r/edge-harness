# Протокол мультиагентной работы

Адресован агентам и людям. Как работать над репозиторием одновременно, не мешая друг
другу. Механизмы здесь — не договорённости, а enforced-правила: защита ветки, обязательные
проверки, concurrency-замок. Обойти их можно только правами администратора репозитория.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Worker-агент | любой агент или человек | берёт задачу из пула, делает, открывает PR |
| Оркестратор | workflow [`orchestra`](../../.github/workflows/orchestra.yml) | следит за пулом, возвращает просроченные задачи, метит конфликты, сливает PR по одному |
| Владелец | человек | заводит задачи, может всё; обход правил — только осознанно |

## Пул задач

Единственное место задач — **GitHub Issues с меткой `task`**. Не списки в чатах, не
локальные заметки: issue — атомарный, назначаемый, видимый всем агентам объект с API.

- Заводить задачу — шаблон «📋 Задача в пул» (цель + критерий готовности + площадь).
- **Взять задачу** = атомарная аренда
  `python3 scripts/lib/claim_task.py claim N` ([ADR 0006](../decisions/0006-task-lease-git-ref-lock.md),
  #121): серверный замок `refs/locks/task-N` + назначение + след в задаче.
  Два пайплайна (worker auto/manual, hands) на одну задачу невозможны:
  второй claim получает отказ и обязан закончиться зелёным no-op. Назначение
  (`gh issue edit N --add-assignee`) — видимость, НЕ защита: все агенты —
  один логин. Человек может назначать себя как раньше — на пайплайны это
  не влияет (их вход — только claim).
- Бросить задачу = снять аренду (`claim_task.py release N`) и назначение.
  Пропал молча — оркестратор вернёт задачу в пул через 24 часа без PR:
  снимет и протухший замок, и назначение (см. «Просроченные назначения»).

## Решение владельца как артефакт (#254/#470)

Задача, чей критерий требует явного выбора владельца между несколькими путями
(«владелец выбирает одно из трёх, не молчаливым дефолтом») — не должна лежать
в пуле молча. Живой случай, из-за которого заведена эта часть протокола: #370
провисела с ровно таким критерием, пока реализация одного из вариантов не
была слита ночью (PR #382) — владелец узнал только потому, что спросил сам.

Полный протокол (варианты в задаче + кнопки в Telegram + ответ, записанный в
репозиторий) предложен в #254 и РЕАЛИЗОВАН целиком (PR #486, ADR 0014,
дельта-спека `openspec/changes/telegram-inline-buttons/`): вебхук Telegram с
авторизацией `callback_query` подключён (секрет `TELEGRAM_WEBHOOK_SECRET` +
привязка к владельцу по `chat_id`, `cf-worker/src/harness.ts::
#postOwnerDecisionCallback`), а `scripts/orchestra/waiting_owner_guard.py`
шлёт кнопочное сообщение для задач с машиночитаемым блоком вариантов
(`pulse_guard.escalate(..., options=...)`). Комментарий-ответ остаётся
ПОЛНОЦЕННОЙ заменой нажатию («тот же результат достигается комментарием в
задаче руками») — оба пути равноправны, ни один не единственный.

**Метка `waiting:owner`.** Ставится тем, кто заводит или разбирает задачу
(`gh issue edit N --add-label waiting:owner`), либо автоматически —
`scripts/orchestra/waiting_owner_guard.py` находит машиночитаемый блок
вариантов (см. ниже) в теле уже заведённой задачи и метку не забыли, и сама
её ставит. Задача с этой меткой не берётся воркером/hands в работу —
`scripts/lib/claim_task.py::claim` отказывает в аренде тем же путём, что уже
отказывает `blocked`.

**Формат вариантов в теле задачи** — машиночитаемый блок, «кнопки» для
владельца:

```
## Варианты владельца
1. <фраза варианта> — <что произойдёт одной фразой>
2. <фраза варианта> — <что произойдёт одной фразой>
```

Не меньше двух пронумерованных строк с «—» (em-dash) между фразой и
последствием — один вариант не выбор. Заголовок ровно этими словами на своей
строке; блок кончается на следующем `## ` заголовке или конце тела. Формат
узкий нарочно (как маркер «Блокирована: #N» у `blocked`, #334): произвольная
проза с перечислением вариантов (пример — старое тело #370) не распознаётся,
задачу в таком виде размечает вручную тот, кто её заводит.

Номера — ПОДРЯД `1, 2, …, N`, без пропусков (находка ревью PR #486, второй
заход): кнопки нумеруются позицией в списке вариантов, письменный номер
«3.» при пропущенном «2.» разошёлся бы с кнопкой — нажатие «второй по счёту»
записало бы решение за другой вариант. Блок с непоследовательной нумерацией
по-прежнему валиден (метка ставится, критерий 4 держится), но кнопочное
сообщение не уходит — эскалация честно падает на текстовый алерт, владелец
отвечает комментарием, как раньше.

**Ответ владельца** — комментарий в САМУ задачу (issue, не PR), первая строка
которого — `РЕШЕНИЕ: <номер>` (номер — один из перечисленных вариантов, либо
любое число, если блок вариантов не размечен). Если владелец передумал —
второй комментарий с тем же маркером и другим номером считается решающим
(последний по времени маркер побеждает). `waiting_owner_guard.py` находит
маркер, снимает метку и оставляет подтверждающий комментарий тем же прогоном.
Нажатие инлайн-кнопки в Telegram (#254, PR #486) даёт тот же артефакт другим
путём: `repository_dispatch` → тонкий job (`owner-decision.yml`) →
`apply_owner_decision.py` пишет «РЕШЕНИЕ: N» тем же способом
(`post_issue_comment`) — второй "apply"-путь не заводится, снимает метку
всё та же гвардия `waiting_owner_guard.py`.

**Агент маркер «РЕШЕНИЕ: N» не пишет никогда** (находка AI-ревью PR #471):
все агенты работают под одним логином (см. «Ограничения честности» ниже),
гвардия технически не отличает владельца от агента по автору комментария —
единственная граница здесь дисциплина, не код. Написать этот маркер за
владельца — то же самое, что решить за него, ровно то, что вся эта схема
призвана предотвратить.

**Эскалация в Telegram** — тем же каналом, что уже есть (`pulse_guard.
escalate`, второй канал не заводится): комментарий в задачу + Telegram, текст
называет одной фразой, что решить, перечисляет варианты с последствием,
ссылку на задачу и порог повтора. Машиночитаемый блок вариантов с подряд
идущей нумерацией (см. выше) — сообщение уходит с инлайн-кнопками (#254, PR
#486, `escalate(..., options=...)` → `build_decision_keyboard`); иначе —
обычный текстовый алерт. Идемпотентно на эпизод (маркер «[решение
владельца: запрошено]»): повтор не раньше 24 ч без ответа — тот же порог, что
`scheduler.py::mark_stale_unclaimed` уже применяет к «нет исполнителя сутки»
(#427), второй порог правды не заводится. Реже — владелец не узнает вовремя;
чаще — 15-минутный пульс завалит канал.

## Как worker-агенту делать задачу

1. Прочти [AGENTS.md](../../AGENTS.md) и [карту документации](../INDEX.md).
   Особо — [отвергнутые варианты](../research/30-rejected-alternatives.md).
2. Захват задачи — атомарная аренда (замок + назначение + след в задаче).
   Ветка (следующий пункт) берёт её сама при создании НОВОЙ задачи — руками
   `claim_task.py claim N` вызывать не нужно. Исключение — доводка уже
   открытого PR без исполнителя (чекаут существующей ветки, без
   `task-branch`, см. WORKER-PLAYBOOK.md, пункт «Ветка»): там `task-branch`
   не вызывается вовсе, аренду возьми вручную той же командой до чекаута.
   Отказ «задача занята» — она уже делается другим каналом, бери следующую;
   но если это доводка своего же PR и держатель — ты сам (транспорт уже
   арендовал эту же задачу и пробросил `LEASE_ALREADY_CLAIMED`) — это твоя
   же аренда, не чужая, работай дальше. В автотранспорте (`scripts/worker/task.sh`,
   `scripts/hands/dsh_task.sh`) захват всё ещё явный и происходит раньше, до
   старта агента (дешёвый fail-fast до траты ресурсов) — эти каналы пробрасывают
   агенту `LEASE_ALREADY_CLAIMED=<N>` (номер арендованной задачи, не булев
   флаг), чтобы `task-branch` не арендовала повторно (claim не идемпотентен по
   актору — второй claim того же номера тем же держателем тоже отклоняется как
   «занято», #356). Если за один прогон создаётся вторая ветка на ДРУГОЙ номер,
   `task-branch` сверяет флаг с номером своей ветки и берёт аренду заново —
   пропуск возможен только при точном совпадении номера.
3. Ветка строго `agent/<N>-<slug>`, создаётся только скриптом
   `scripts/git/task-branch <N>-<slug>`: он доказывает свежесть `origin/main`
   через `git ls-remote` (оркестратор сливает PR на сервере — локальный main
   протухает молча), ставит гвардию `.githooks/pre-commit`, блокирующую коммиты
   от протухшей базы, и берёт аренду задачи (`claim_task.py claim N`, если её
   ещё не взял транспорт) — отказ аренды останавливает создание ветки, называя
   где искать держателя (assignee и комментарий 🔒 issue), что делать (взять
   другую задачу) и выход, если замок твой же с прошлого умершего прогона
   (`claim_task.py release N`); ветка, которая уже существует (локально или на
   origin), отклоняется ДО аренды — доводка существующей идёт чекаутом, не
   повторным запуском скрипта. Поломка пути аренды (`claim_task.py` rc=2) —
   предупреждение, ветка создаётся без аренды; полный офлайн/`gh` недоступен
   громко отказывает раньше — гвардия эпика (#376), офлайн-режима у входа в
   задачу нет. Голый `git checkout -b … origin/main` запрещён.
   Локальный main — только зеркало origin (`git pull --ff-only`), коммитить в него нельзя.
4. Прямые пуши в main отклоняются защитой **молча под `push -q`** — проверяй пуши без
   `-q`. На конфликтном PR проверки не запускаются вовсе («Checks awaiting conflict
   resolution») — сигнал перебазироваться, а не поломка CI. main ушёл вперёд, пока ты
   работал — обнови ветку (`gh api -X PUT .../pulls/N/update-branch`).
5. Тяжёлые локальные прогоны (wrangler dev, UI-канарейка) — **только в докере**
   (`cf-worker/Dockerfile` через `npm run dev:docker`), чтобы не копить осиротевшие
   процессы `workerd`/`node` на хосте. Хостовые `npm run dev` и `npm run canary`
   запрещены — они оставляют висячие процессы и ломаются на кодировках/EOL/портах Windows.
6. Работа по правилам репозитория: одно место правды, fail loud, тест кормится
   прод-формой. Белое пятно или противоречие, найденное по пути, — не чинить молча,
   а завести issue по шаблону «🕳️ Белое пятно / противоречие». **Заводи ЛЮБОЙ
   issue через `scripts/gh/issue-create`** (тот же интерфейс, что `gh issue
   create`, — обёртка проксирует аргументы без изменений), НЕ голым `gh issue
   create` напрямую: шаблон (`labels: [white-spot, task]`) применяется ТОЛЬКО
   к веб-форме, не к CLI/API-созданию — агент, вызывающий `gh issue create
   --label white-spot` из терминала по памяти о названии шаблона, реально
   ставит только `white-spot`, без `task`, и issue физически не видна пулу
   воркера (класс #179, живые случаи — issue #523 заведена ровно так, #425 —
   без единой метки вовсе). Обёртка отказывает ДО сетевого вызова, если среди
   `--label` нет `task` (класс #526). Это не заменяет обязанность знать, какой
   шаблон подходит по смыслу (white-spot/task) — обёртка только не даёт
   забыть механическую часть (саму метку `task`). Второй тормоз той же
   обёртки (#566): заголовок сверяется с уже ОТКРЫТЫМИ задачами пула
   (`scripts/lib/duplicate_guard.py`, токенная схожесть) — единственная
   сегодня защита от параллельной диагностики одного дефекта (аренда
   `claim_task.py`, #121) привязана к номеру задачи, а диагностика симптома
   начинается ДО того, как номер существует. Похожая открытая задача
   найдена → отказ со списком кандидатов; газ — `--confirm-not-duplicate
   "<почему не дубль>"`, причина попадает в тело новой issue. Живой случай,
   который это закрывает: 2026-09-06 три агента одной сессии независимо
   диагностировали один и тот же дефект (#518/#547/#564), два issue и три
   PR закрыты как дубликат уже после часов работы. Третий тормоз той же
   обёртки (#695): решение о приоритете (`area:process`, `scripts/lib/
   free_task.py::META_LABEL`) обязано быть явным — метка `area:process`
   среди `--label` сама является решением, иначе нужен `--not-process-ack
   "<причина>"`. Перед созданием печатается текущий верх группы приоритета
   (открытые `area:process`, тот же ключ сортировки, что `issue_priority_key`)
   — случай «та же проблема другими словами» ловится глазами, раз дедуп по
   схожести заголовка её не ловит и не может (разные слова про один дефект).
   Живой случай: 2026-09-07 #684/#685/#689 заведены с `area:orchestra`
   вместо `area:process` и встали в хвост очереди из 200 задач, хотя
   #194/#168/#226 в группе приоритета уже несли ту же проблему другими
   словами.
7. Открывай PR через `scripts/git/pr-create` (тот же интерфейс, что `gh pr
   create`, — обёртка проксирует аргументы без изменений), НЕ голым `gh pr
   create` напрямую: обёртка проверяет тело ДО отправки и откажет с
   объяснением, если оно нарушает правило ниже, а не покрасит контракт
   постфактум, когда PR уже открыт (issue #496 — 3 из 4 падений `contract`
   за 6 часов оказались именно этой формой, написанной по привычке из общей
   практики GitHub). PR по шаблону: ссылка на задачу — просто `#N`.
   **`Closes/Fixes/Resolves` запрещены**: GitHub закрыл бы задачу при
   слиянии, а критерий готовности задачи часто живёт ПОСЛЕ мержа (деплой,
   канарейка, E2E). Задачу закрывает стадия приёмки оркестратора (#227) по
   проверяемой улике, не исполнитель — не делай `gh issue close` сам.
   Контракт такие слова тоже отклоняет (обёртка — вход раньше, не замена
   контракту).
   Без задачи PR не слить. Мелочь вне пула — метка `orchestra:skip` на PR, это
   осознанный обход.
   Номер задачи для контракта берётся ТОЛЬКО ИЗ ВЕТКИ (`agent/<N>-<slug>`,
   п.3 выше) — единственный источник, решение владельца (2026-09-06): тело
   PR для этого вопроса не читается вообще, ни первой строкой, ни любым
   другим способом. Ветка называет уже закрытую задачу (докрытие после
   «закрытая задача не переоткрывается») — не переориентируйся, заведи
   НОВУЮ ветку `scripts/git/task-branch <M>-<slug>` на новый номер, старую
   не переименовывай. Резолвер — `scripts/lib/task_ref.py::resolve_pr_task`.
   Номер `<M>` не обязательно искать самому: оркестратор сам замечает такой
   PR (#543, `scripts/orchestra/scheduler.py::replace_closed_task_prs`),
   заводит узкую задачу-замену (`Related: #<старая>`) и метит тело/комментарий
   PR ссылкой на неё — переименование ветки/новый PR всё равно остаются за
   исполнителем (см. докстринг функции, почему это не делает сам оркестратор).
8. Жди ревью и оркестратора: после `review:ok` дифф ревьюит AI-ревьюер
   (workflow `ai-review`, второй гейт): содержательный комментарий в PR +
   вердикт `ai:ok`/`ai:changes-requested`. Ровно три исхода находки (#462,
   контракт `scripts/review/ai_prompt.md`) — проза, которая никуда не
   попадает, в контракте не предусмотрена:
   - блокирует мерж → проза в комментарии (до 5), вердикт `ai:changes-requested`
     — доработай по находкам и запушь: оба гейта пройдут заново;
   - некритично, но стоит сделать → блок ЗАМЕЧАНИЕ, ревьюер сливает его в
     чеклист ТЕЛА PR (не комментария); вердикт остаётся `ai:ok`, если
     блокирующих находок нет. Отмечай сделанные пункты нативным чекбоксом
     GitHub прямо в описании PR — второго механизма нет. Пункты, оставшиеся
     незакрытыми к моменту слияния, не блокируют его: оркестратор заводит
     ОДНУ задачу-хвост со ссылкой на этот PR (`scripts/lib/review_checklist.py`,
     `after_merge` в `scheduler.py`) — не issue на каждый пункт;
   - работа вне рамок PR → блок ЗАДАЧА, ревьюер обязан пометить `МАСШТАБ: хвост`
     (укладывается в уже изменённые этим PR файлы, нового дизайна/решения не
     требует — допиши прямо в этом PR) или `МАСШТАБ: отдельно` (затрагивает
     область, которую PR не трогал, либо нужно решение владельца) — задача
     #426, критерий в `scripts/review/ai_prompt.md`. Только «отдельно» уходит
     в беклог одной командой: `python scripts/review/file_tasks.py --pr <N>`.
     Сливает оркестратор, по одному, в порядке готовности. «Хвост» остаётся
     в комментарии как «доделай в этом PR» и issue не заводит — правило
     репозитория «чинить в том же PR, а не плодить задачи» распространяется
     и на находки самого AI-ревью. Блок без МАСШТАБ не угадывается молча
     (fail loud): виден в комментарии отдельным предупреждением, issue не
     создаётся — заведи вручную, если это реально отдельная работа.
9. После слияния задачу закрывает стадия приёмки оркестратора (#227) по
   проверяемой улике (деплой/check-runs/файлы в main) — не ты. Если критерий
   требует прогона после мержа (канарейка, E2E), которого сам оркестратор не
   делает, проведи его сам, чтобы улике было на что опереться.

## Что делает оркестратор

Скрипты: [`contract_check.py`](../../scripts/orchestra/contract_check.py),
[`scheduler.py`](../../scripts/orchestra/scheduler.py). Запуски сериализованы
concurrency-группой `orchestra` — два слияния никогда не идут параллельно.

- **Контракт PR**: ссылка на задачу есть, задача открыта и помечена `task`, назначен
  ровно один исполнитель, конкурирующего открытого PR на ту же задачу нет.
- **Просроченные назначения**: назначено 24 часа, PR не появился → назначение снято,
  задача в пуле, комментарий с причиной. В том же такте оркестратор снимает
  протухшие замки аренды (#121) со следом в задаче — задача возвращается в пул
  целиком (и без назначенного, и без замка).
- **Непринятые задачи** (#427): для задач, которые вообще никто не брал (а не
  просроченных назначений выше), отдельного механизма возврата нет — есть только
  видимость. Задача пула без исполнителя старше того же порога (24 часа)
  получает метку `stale-unclaimed` (`scheduler.py::mark_stale_unclaimed`) —
  метка не тормоз, ничего не закрывается и не переназначается сама. Снимается
  автоматически, как только задачу берут; решение «взять / переформулировать /
  закрыть как отпавшую» — ручное (реестр газа: [`docs/agents/LABELS.md`](LABELS.md)).
- **Конфликты**: PR, не сливающийся в main, получает метку `conflict` и комментарий —
  перебазировать автору.
- **Очередь слияний**: PR с зелёными проверками и чистым контрактом сливается squash'ем.
  **Один PR за проход**: после каждого слияния очередь пересчитывается следующим
  проходом — конфликтующие слияния невозможны по построению. Один запуск (событие
  вердикта или расписание-страховка) прогоняет цикл таких проходов подряд, пока есть
  что сливать, до потолка/таймаута (`merge_loop`, #297). Вердикты — два гейта:
  метка `review:ok` (детерминированное ревью, workflow `pr-review`) И метка `ai:ok`
  (AI-ревью диффа, workflow `ai-review`, задача #18 — содержательное ревью агентом
  без GitHub-токена: соответствие ADR/спекам, скрытые регрессии; [ADR 0007](../decisions/0007-ai-review-gate.md)).
  Вердикты привязаны к head: новый пуш снимает `ai:*` и переустанавливает
  `review:ok` — оба ревью проходят заново.
- **После слияния (стадия приёмки, #227)**: оркестратор сам закрывает задачи —
  но только по проверяемой улике, не по факту мержа. Каждый прогон сопоставляет
  открытые задачи пула со слитыми PR, чья ветка их НАЗЫВАЕТ (`agent/<N>-<slug>`),
  и решает по улике, вид которой зависит от состава изменённых файлов (деплой/
  скрипт/документация — подробности в
  [`openspec/changes/task-closure-after-proof/specs/journal-tasks-hands/spec.md`](../../openspec/changes/task-closure-after-proof/specs/journal-tasks-hands/spec.md),
  «Конвейер», п.18). Улика подтвердилась → задача закрыта с комментарием-уликой;
  провалилась → НЕ закрыта, assignee снят, причина в комментарии; сама проверка
  сломана (сеть/секрет/API) → эскалация владельцу (issue #120 + Telegram), задача
  не тронута; тело закрывающего PR несёт дисклеймер о неполноте (#335) → задача
  НЕ закрыта, исполнитель и замок сняты — задача возвращена в пул, докрытие
  отдельным PR (тот же исход, что и провал улики; подробности и пропуск эпиков —
  дельта-спека [`openspec/changes/acceptance-partial-pr-guard/specs/journal-tasks-hands/spec.md`](../../openspec/changes/acceptance-partial-pr-guard/specs/journal-tasks-hands/spec.md)).
  Исполнитель улику не заявляет и задачу сам не закрывает.
- **Запрет переоткрытия (#369)**: закрытая задача не переоткрывается никогда — GitHub
  не отклоняет reopen нативно, поэтому пульс сам находит задачу пула с
  `state_reason == "reopened"` (поле уже в списке `open_task_issues`, без
  дополнительного запроса) ДО стадии приёмки и закрывает её обратно с комментарием,
  называющим действие вместо: завести новую, более узкую задачу со ссылкой на эту как
  related. Проверяется раньше приёмки на том же пульсе — переоткрытая задача не
  успевает снова смэтчиться со старым слитым PR (класс #363:
  `scheduler.py::reject_reopened_tasks`, дельта-спека
  [`openspec/changes/reopen-rejected/specs/journal-tasks-hands/spec.md`](../../openspec/changes/reopen-rejected/specs/journal-tasks-hands/spec.md)).

⚠️ Расписание на публичном репозитории GitHub отключает после 60 дней без активности
репозитория — это задокументировано в [research/21](../research/21-github-actions.md).
Признак деградации: в Actions пропали отчёты orchestra. Лечение: любая активность или
ручной `workflow_dispatch`.

## Борда (GitHub Projects v2)

Владельцу нужен обзор зависимостей, дочерних задач, эпиков и вех, которого не даёт плоский
список Issues. Борда — **[edge-harness](https://github.com/users/mytab0r/projects/2)**,
нативный GitHub Projects v2 (не своя разработка), привязана к этому репозиторию. Пул задач
остаётся тем же, что и раньше (Issues с меткой `task`), борда — только вид поверх него;
не заводи задачи в проекте напрямую (draft items), заводи issue как обычно.

### Поле `Эпик`

Single-select классификатор верхнего уровня, шесть значений выведены из фактического
содержания открытых задач на момент создания борды:

- **Конвейер и оркестрация** — оркестратор, ревью-гейты (детерминированное + AI),
  безопасность CI-джобов вокруг ревью, автономный воркер, автоматизации/инбокс владельца.
- **Морда dsh-edge: версия и инфраструктура** — сама морда как DSH-хост, апгрейды
  зависимостей (TypeScript и т.п.), докер-политика для dev, дашборд и рендер сессий,
  бамп пина апстрима.
- **LLM-провайдеры и модели** — реестр провайдеров, дефолтная модель/провайдер,
  потолок ответа, различение сетевых сбоёв от квот.
- **Плагинная система** — dsh-edge как хост плагинов: дизайн, forge, PoC, runner-bridge,
  каталог плагинов, будущие интеграции внешних систем и автоматизации на плагинах.
- **Безопасность и токены** — узкие PAT вместо широких, изоляция секретов от
  дочерних процессов, гвардии против исполнения недоверенного кода под write-токеном.
- **Измерения и лимиты** — кампании замеров (задержка dispatch), квоты провайдеров и
  автовозобновление.

Новую задачу заводишь в пул — сам добавляешь её в проект (`gh project item-add 2
--owner mytab0r --url <issue-url>`) и проставляешь `Эпик` по смыслу (`gh project
item-edit`). Если задача не ложится ни в одно значение — это сигнал завести новый эпик
или обсудить с владельцем, а не пропускать поле.

### Зависимости — два механизма, не путать

GitHub различает у Issues декомпозицию (sub-issues) и порядок выполнения
(`blockedBy`/`blocking`) — оба нативно: sub-issues через REST, порядок
выполнения через GraphQL. Чтобы не завести два конкурирующих способа записи
одного факта, применяется ровно два правила, каждое — для своего класса связи:

1. **Sub-issues** — когда родитель это НЕ отдельная работа, а зонтик, под которым
   декомпозирована работа других задач (эпик issue или задача-реестр, которая физически
   распадается на подзадачи). Пример: #77 (эпик dsh-edge как DSH-хост) →
   #78, #80, #86, #95, #113, #114, #133, #43; #158 (реестр провайдеров) → #155, #157.
   Заводится через REST API (`gh api repos/mytab0r/edge-harness/issues/<родитель>/sub_issues
   -F sub_issue_id=<id дочерней issue>`, id — числовой `id`, не номер) — `gh issue` CLI
   такой команды не имеет.
2. **Нативный граф `blockedBy`/`blocking`** — когда это порядок выполнения, а не
   декомпозиция: задача A мешает нормально работать задаче B, но не является её
   родителем (задача #361, 2026-09-06 — заменяет прежнюю конвенцию «строка
   «Зависимости» в теле блокирующей задачи»: прозопарсинг того же запрещённого
   класса, что уже закрыт для контракта «PR → задача», #251/#259). Ставится
   одной командой тем, кто заметил факт зависимости — тот же паттерн, что
   sub-issues выше, не автоматика, не разбор текста:
   ```
   python scripts/lib/task_deps.py block <owner/repo> <заблокированная#> <блокирующая#>
   python scripts/lib/task_deps.py unblock <owner/repo> <заблокированная#> <блокирующая#>
   ```
   Читается `scripts/lib/free_task.py` при выборе свободной задачи: число
   ОТКРЫТЫХ задач, которые блокирует issue, — второй уровень приоритета
   (первый — метка `area:process`, docs/agents/LABELS.md). Живая проверка
   мутаций (`addBlockedBy`/`removeBlockedBy`) и REST vs GraphQL — находка
   ревью PR #367, вынесена из каталога активного change (архивируется после
   применения) в постоянный источник фактов о внешней системе:
   [`docs/research/21-github-actions.md`](../research/21-github-actions.md),
   раздел «Нативный граф зависимостей issue».

Не смешивай механизмы на одной паре задач: если это декомпозиция — sub-issue, если
порядок/блокировка — граф `blockedBy`/`blocking` через `task_deps.py`.

**Заведение задачи требует явного ответа, не пропуска (#371).** Граф пуст, пока
кто-то не поставит связь явно — сама по себе задача его не наполняет. Поэтому оба
поставщика пула отдельно требуют ответ «чем блокируется»:

- Шаблоны `.github/ISSUE_TEMPLATE/task.yml` и `white-spot.yml` — обязательное поле
  «Чем блокируется» (номера через пробел или «ничем»). Перенос в нативный
  `blockedBy` — АВТОМАТИЧЕСКИЙ с задачи #529: `declared_deps.py::auto_wire`
  разбирает структурный рендер поля (`### Чем блокируется\n\n<ответ>`) и
  переносит недостающие номера на ближайшем прогоне `repo-ci` после push в
  main (шаг workflow, не пульс — цена, см. design.md `auto-wire-declared-deps`).
  Ручная команда `task_deps.py block <owner/repo> <заблокированная#>
  <блокирующая#>` остаётся рабочей и нужна для задач БЕЗ поля вовсе (заведены
  до #387 или не из этого шаблона) и для связей, не выразимых полем формы.
- `scripts/review/file_tasks.py` (автозаведение из находок AI-ревью, сегодня основной
  поставщик пула) — контракт `ai_prompt.md` требует от модели строку `БЛОКИРУЕТСЯ: …`
  ПОСЛЕДНЕЙ перед `КОНЕЦ ЗАДАЧИ`; блок без неё отбрасывается целиком (`ai_review.
  parse_tasks`, громкое `::warning::`). Здесь перенос в нативный граф — АВТОМАТИЧЕСКИЙ:
  `file_tasks.py::wire_declared_dependency` ставит `blockedBy` в момент создания
  issue (номер уже известен), но только на номера, которые сейчас входят в открытый
  пул с меткой `task` — иначе печатает предупреждение и НЕ линкует (ложная связь
  опаснее отсутствующей, модель может ошибиться в номере).

**Метка `area:process` — тоже ручной шаг, не автоматика формы.** Дропдаун
«Площадь» в `task.yml`/`white-spot.yml` пишет выбор в ТЕЛО issue (GitHub
рендерит поле формы как `### Площадь\n\n<выбор>`), метку из выбора не
создаёт — issue forms не конвертируют значения полей в labels (находка
AI-ревью PR #387: `docs/agents/LABELS.md` называла постановщиком метки сам
дропдаун, хотя реально её ставит `gh issue edit --add-label area:process`
по этой же конвенции, что и остальные `area:*`, см. `scripts/lib/
collect_labels.py` докстринг). После заведения issue проверь дропдаун
«Площадь» в теле и, если выбран `area:process`, поставь метку явно —
без неё уровень 1 приоритета (`free_task.py::issue_priority_key`) эту
задачу не увидит.

Рассинхрон «тело называет открытую блокирующую issue прозой — граф её не знает» —
видимый, не молчаливый: `.github/workflows/repo-ci.yml` на каждый push/PR гоняет
`scripts/lib/declared_deps.py check`, печатает `::warning::` на каждую находку
(не проваливает гейт — эвристика по формулировкам прозы, ложные срабатывания
ожидаемы). Закрытие блокирующей задачи не требует ручного снятия `blockedBy`:
приоритет и находки рассинхрона читают только ОТКРЫТЫХ блокирующих
(`blocked_by_open`), закрытая исчезает из расчёта сама на следующем запросе.

### Вехи (milestones)

Заведены только там, где GitHub Issues разложились однозначно на реальный рубеж из
[`docs/agents/ROADMAP.md`](ROADMAP.md) (секции диаграммы Ганта). Сомнительная
принадлежность не угадывается — задача просто остаётся без вехи:

- **Ротация учёток (ProviderChain-порт)** — рубеж назван в ROADMAP, открытой задачи под
  него в пуле пока нет.
- **Security baseline (SECURITY/CodeQL/Dependabot)** — то же самое: рубеж назван, задача
  ещё не заведена.
- **AI-ревьюер диффа с вердиктом** — #18.
- **Разбор сообщений владельца → пул** — #20.

Новый рубеж в ROADMAP — заведи веху с тем же названием (`gh api repos/.../milestones`),
не своим текстом: расхождение имён между ROADMAP и бордой — то самое «два места правды»,
которое запрещено правилами репозитория.

## Белые пятна и противоречия

Нашёл противоречие (док ↔ код, спека ↔ поведение, два места правды) или утверждение
без улики — **заведи issue-шаблон «🕳️ Белое пятно / противоречие» немедленно**. Это
канал синхронизации агентов: остальные увидят проблему до того, как на неё обопрутся.
Правило репозитория «не знаешь — пиши "не подтверждено"» действует и здесь: запись
в issue лучше тихого сомнения. Заводи через `scripts/gh/issue-create --label
white-spot --label task --label area:process …` (см. п.6 выше, класс
#179/#526/#695) — не голым `gh issue create`. Белое пятно/противоречие — это
проблема самого процесса (доки/протокол/гвардии), поэтому решение о приоритете
почти всегда `--label area:process`; если конкретный случай не про процесс —
замени на явный `--not-process-ack "<причина>"`, иначе третий тормоз отклонит
вызов.

## Ограничения честности

- Все агенты, работающие от одного токена, для GitHub — один пользователь. Назначения
  фиксируются в issue как состояние, а не как личность: оркестратор разрешает конфликты
  по состоянию (дубли PR, просрочка), а не по логину.
- Защита ветки с `enforce_admins: false` оставляет владельцу прямой пуш. Агенту прямой
  пуш в main недоступен не потому что «нельзя», а потому что required checks не пройдут.
- Обход контракта существует ровно один — метка `orchestra:skip` на PR — и оставлен
  для мелочей; злоупотребление ею видно в истории PR.
