# Протокол мультиагентной работы

Адресован агентам и людям. Как работать над репозиторием одновременно, не мешая друг
другу. Механизмы здесь — не договорённости, а enforced-правила: защита ветки, обязательные
проверки, concurrency-замок. Обойти их можно только правами администратора репозитория.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Worker-агент | любой агент или человек | берёт задачу из пула, делает, открывает PR |
| Оркестратор | workflow [`orchestra`](../../.github/workflows/orchestra.yml) | следит за пулом, возвращает просроченные задачи, метит конфликты, сливает PR по одному |
| Владелец | человек | заводит задачи, может всё; обход правил — только осознанно |

## Пул задач

Единственное место задач — **GitHub Issues с меткой `task`**. Не списки в чатах, не
локальные заметки: issue — атомарный, назначаемый, видимый всем агентам объект с API.

- Заводить задачу — шаблон «📋 Задача в пул» (цель + критерий готовности + площадь).
- **Взять задачу** = атомарная аренда
  `python3 scripts/lib/claim_task.py claim N` ([ADR 0006](../decisions/0006-task-lease-git-ref-lock.md),
  #121): серверный замок `refs/locks/task-N` + назначение + след в задаче.
  Два пайплайна (worker auto/manual, hands) на одну задачу невозможны:
  второй claim получает отказ и обязан закончиться зелёным no-op. Назначение
  (`gh issue edit N --add-assignee`) — видимость, НЕ защита: все агенты —
  один логин. Человек может назначать себя как раньше — на пайплайны это
  не влияет (их вход — только claim).
- Бросить задачу = снять аренду (`claim_task.py release N`) и назначение.
  Пропал молча — оркестратор вернёт задачу в пул через 24 часа без PR:
  снимет и протухший замок, и назначение (см. «Просроченные назначения»).

## Как worker-агенту делать задачу

1. Прочти [AGENTS.md](../../AGENTS.md) и [карту документации](../INDEX.md).
   Особо — [отвергнутые варианты](../research/30-rejected-alternatives.md).
2. Захвати задачу: `python3 scripts/lib/claim_task.py claim N` — атомарная
   аренда (замок + назначение + след в задаче). Отказ «задача занята» —
   она уже делается другим каналом, бери следующую. В автотранспорте
   (`scripts/worker/task.sh`) захват происходит до старта агента.
3. Ветка строго `agent/<N>-<slug>`, создаётся только скриптом
   `scripts/git/task-branch <N>-<slug>`: он доказывает свежесть `origin/main`
   через `git ls-remote` (оркестратор сливает PR на сервере — локальный main
   протухает молча) и ставит гвардию `.githooks/pre-commit`, блокирующую коммиты
   от протухшей базы. Голый `git checkout -b … origin/main` запрещён.
   Локальный main — только зеркало origin (`git pull --ff-only`), коммитить в него нельзя.
4. Прямые пуши в main отклоняются защитой **молча под `push -q`** — проверяй пуши без
   `-q`. На конфликтном PR проверки не запускаются вовсе («Checks awaiting conflict
   resolution») — сигнал перебазироваться, а не поломка CI. main ушёл вперёд, пока ты
   работал — обнови ветку (`gh api -X PUT .../pulls/N/update-branch`).
5. Тяжёлые локальные прогоны (wrangler dev, UI-канарейка) — **только в докере**
   (`cf-worker/Dockerfile` через `npm run dev:docker`), чтобы не копить осиротевшие
   процессы `workerd`/`node` на хосте. Хостовые `npm run dev` и `npm run canary`
   запрещены — они оставляют висячие процессы и ломаются на кодировках/EOL/портах Windows.
6. Работа по правилам репозитория: одно место правды, fail loud, тест кормится
   прод-формой. Белое пятно или противоречие, найденное по пути, — не чинить молча,
   а завести issue-шаблон «🕳️ Белое пятно / противоречие».
7. PR по шаблону: ссылка на задачу — просто `#N`. **`Closes/Fixes/Resolves`
   запрещены**: GitHub закрыл бы задачу при слиянии, а критерий готовности задачи
   часто живёт ПОСЛЕ мержа (деплой, канарейка, E2E). Задачу закрывает стадия
   приёмки оркестратора (#227) по проверяемой улике, не исполнитель — не делай
   `gh issue close` сам. Контракт такие слова отклоняет.
   Без задачи PR не слить. Мелочь вне пула — метка `orchestra:skip` на PR, это
   осознанный обход.
8. Жди ревью и оркестратора: после `review:ok` дифф ревьюит AI-ревьюер
   (workflow `ai-review`, второй гейт): содержательный комментарий в PR +
   вердикт `ai:ok`/`ai:changes-requested`. `ai:changes-requested` — доработай
   по находкам и запушь: оба гейта пройдут заново. Предложенные ревью задачи
   в беклог заводятся одной командой:
   `python scripts/review/file_tasks.py --pr <N>`. Сливает оркестратор,
   по одному, в порядке готовности.
9. После слияния задачу закрывает стадия приёмки оркестратора (#227) по
   проверяемой улике (деплой/check-runs/файлы в main) — не ты. Если критерий
   требует прогона после мержа (канарейка, E2E), которого сам оркестратор не
   делает, проведи его сам, чтобы улике было на что опереться.

## Что делает оркестратор

Скрипты: [`contract_check.py`](../../scripts/orchestra/contract_check.py),
[`scheduler.py`](../../scripts/orchestra/scheduler.py). Запуски сериализованы
concurrency-группой `orchestra` — два слияния никогда не идут параллельно.

- **Контракт PR**: ссылка на задачу есть, задача открыта и помечена `task`, назначен
  ровно один исполнитель, конкурирующего открытого PR на ту же задачу нет.
- **Просроченные назначения**: назначено 24 часа, PR не появился → назначение снято,
  задача в пуле, комментарий с причиной. В том же такте оркестратор снимает
  протухшие замки аренды (#121) со следом в задаче — задача возвращается в пул
  целиком (и без назначенного, и без замка).
- **Конфликты**: PR, не сливающийся в main, получает метку `conflict` и комментарий —
  перебазировать автору.
- **Очередь слияний**: PR с зелёными проверками и чистым контрактом сливается squash'ем.
  **Ровно один за запуск**: после каждого слияния очередь пересчитывается следующим
  запуском — конфликтующие слияния невозможны по построению. Вердикты — два гейта:
  метка `review:ok` (детерминированное ревью, workflow `pr-review`) И метка `ai:ok`
  (AI-ревью диффа, workflow `ai-review`, задача #18 — содержательное ревью агентом
  без GitHub-токена: соответствие ADR/спекам, скрытые регрессии; [ADR 0007](../decisions/0007-ai-review-gate.md)).
  Вердикты привязаны к head: новый пуш снимает `ai:*` и переустанавливает
  `review:ok` — оба ревью проходят заново.
- **После слияния (стадия приёмки, #227)**: оркестратор сам закрывает задачи —
  но только по проверяемой улике, не по факту мержа. Каждый прогон сопоставляет
  открытые задачи пула со слитыми PR, которые их ОБЪЯВЛЯЮТ (первая строка тела),
  и решает по улике, вид которой зависит от состава изменённых файлов (деплой/
  скрипт/документация — подробности в
  [`openspec/changes/task-closure-after-proof/specs/journal-tasks-hands/spec.md`](../../openspec/changes/task-closure-after-proof/specs/journal-tasks-hands/spec.md),
  «Конвейер», п.18). Улика подтвердилась → задача закрыта с комментарием-уликой;
  провалилась → НЕ закрыта, assignee снят, причина в комментарии; сама проверка
  сломана (сеть/секрет/API) → эскалация владельцу (issue #120 + Telegram), задача
  не тронута. Исполнитель улику не заявляет и задачу сам не закрывает.

⚠️ Расписание на публичном репозитории GitHub отключает после 60 дней без активности
репозитория — это задокументировано в [research/21](../research/21-github-actions.md).
Признак деградации: в Actions пропали отчёты orchestra. Лечение: любая активность или
ручной `workflow_dispatch`.

## Борда (GitHub Projects v2)

Владельцу нужен обзор зависимостей, дочерних задач, эпиков и вех, которого не даёт плоский
список Issues. Борда — **[edge-harness](https://github.com/users/mytab0r/projects/2)**,
нативный GitHub Projects v2 (не своя разработка), привязана к этому репозиторию. Пул задач
остаётся тем же, что и раньше (Issues с меткой `task`), борда — только вид поверх него;
не заводи задачи в проекте напрямую (draft items), заводи issue как обычно.

### Поле `Эпик`

Single-select классификатор верхнего уровня, шесть значений выведены из фактического
содержания открытых задач на момент создания борды:

- **Конвейер и оркестрация** — оркестратор, ревью-гейты (детерминированное + AI),
  безопасность CI-джобов вокруг ревью, автономный воркер, автоматизации/инбокс владельца.
- **Морда dsh-edge: версия и инфраструктура** — сама морда как DSH-хост, апгрейды
  зависимостей (TypeScript и т.п.), докер-политика для dev, дашборд и рендер сессий,
  бамп пина апстрима.
- **LLM-провайдеры и модели** — реестр провайдеров, дефолтная модель/провайдер,
  потолок ответа, различение сетевых сбоёв от квот.
- **Плагинная система** — dsh-edge как хост плагинов: дизайн, forge, PoC, runner-bridge,
  каталог плагинов, будущие интеграции внешних систем и автоматизации на плагинах.
- **Безопасность и токены** — узкие PAT вместо широких, изоляция секретов от
  дочерних процессов, гвардии против исполнения недоверенного кода под write-токеном.
- **Измерения и лимиты** — кампании замеров (задержка dispatch), квоты провайдеров и
  автовозобновление.

Новую задачу заводишь в пул — сам добавляешь её в проект (`gh project item-add 2
--owner mytab0r --url <issue-url>`) и проставляешь `Эпик` по смыслу (`gh project
item-edit`). Если задача не ложится ни в одно значение — это сигнал завести новый эпик
или обсудить с владельцем, а не пропускать поле.

### Зависимости — два механизма, не путать

GitHub не различает у Issues отношение «блокирует» нативно, есть только sub-issues. Чтобы
не завести два конкурирующих способа записи одного факта, применяется ровно два правила,
каждое — для своего класса связи:

1. **Sub-issues** — когда родитель это НЕ отдельная работа, а зонтик, под которым
   декомпозирована работа других задач (эпик issue или задача-реестр, которая физически
   распадается на подзадачи). Пример: #77 (эпик dsh-edge как DSH-хост) →
   #78, #80, #86, #95, #113, #114, #133, #43; #158 (реестр провайдеров) → #155, #157.
   Заводится через REST API (`gh api repos/mytab0r/edge-harness/issues/<родитель>/sub_issues
   -F sub_issue_id=<id дочерней issue>`, id — числовой `id`, не номер) — `gh issue` CLI
   такой команды не имеет.
2. **Строка «Зависимости» в теле задачи** — когда это порядок выполнения, а не
   декомпозиция: задача A мешает нормально работать множеству других, но не является их
   родителем. Записывается **один раз, в теле блокирующей задачи** (одно место правды —
   не дублировать «зависит от #A» в каждой блокируемой). Пример: #147 (гейт `ai:ok` не
   стартует сам — блокирует весь пул PR), #134 (морда отстаёт от апстрима — блокирует
   любую задачу, которой нужна свежая версия).

Не смешивай механизмы на одной паре задач: если это декомпозиция — sub-issue, если
порядок/блокировка — строка в теле.

### Вехи (milestones)

Заведены только там, где GitHub Issues разложились однозначно на реальный рубеж из
[`docs/agents/ROADMAP.md`](ROADMAP.md) (секции диаграммы Ганта). Сомнительная
принадлежность не угадывается — задача просто остаётся без вехи:

- **Ротация учёток (ProviderChain-порт)** — рубеж назван в ROADMAP, открытой задачи под
  него в пуле пока нет.
- **Security baseline (SECURITY/CodeQL/Dependabot)** — то же самое: рубеж назван, задача
  ещё не заведена.
- **AI-ревьюер диффа с вердиктом** — #18.
- **Разбор сообщений владельца → пул** — #20.

Новый рубеж в ROADMAP — заведи веху с тем же названием (`gh api repos/.../milestones`),
не своим текстом: расхождение имён между ROADMAP и бордой — то самое «два места правды»,
которое запрещено правилами репозитория.

## Белые пятна и противоречия

Нашёл противоречие (док ↔ код, спека ↔ поведение, два места правды) или утверждение
без улики — **заведи issue-шаблон «🕳️ Белое пятно / противоречие» немедленно**. Это
канал синхронизации агентов: остальные увидят проблему до того, как на неё обопрутся.
Правило репозитория «не знаешь — пиши "не подтверждено"» действует и здесь: запись
в issue лучше тихого сомнения.

## Ограничения честности

- Все агенты, работающие от одного токена, для GitHub — один пользователь. Назначения
  фиксируются в issue как состояние, а не как личность: оркестратор разрешает конфликты
  по состоянию (дубли PR, просрочка), а не по логину.
- Защита ветки с `enforce_admins: false` оставляет владельцу прямой пуш. Агенту прямой
  пуш в main недоступен не потому что «нельзя», а потому что required checks не пройдут.
- Обход контракта существует ровно один — метка `orchestra:skip` на PR — и оставлен
  для мелочей; злоупотребление ею видно в истории PR.
