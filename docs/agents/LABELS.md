# Реестр меток — тормоз и его газ

Один файл, единственное место правды для GitHub-меток, которыми оперирует
конвейер. Заведён задачей #207: пять из шести собранных тормозов конвейера
оказались без объявленного способа их снять (#205, #204, #196) — не потому,
что газа не было никогда, а потому что его никто не назвал явно и рядом.

**Правило ведения**: строка обязательна для каждой метки, встречающейся в
коде; колонка «Газ» не может быть пустой — «вручную: роль, по сигналу X» это
осознанное объявление, а не пропуск. Значения меток-вердиктов ревью
(`review:*`, `ai:*`) читаются из существующего места правды
[`scripts/lib/review_labels.py`](../../scripts/lib/review_labels.py) — здесь
не дублируются строками.

Список меток на этой странице **не хардкожен**: его печатает
[`scripts/lib/collect_labels.py`](../../scripts/lib/collect_labels.py)
сканированием `scripts/`, `.github/workflows/`, `.github/ISSUE_TEMPLATE/`.
Гвардия [`scripts/lib/test_label_registry.py`](../../scripts/lib/test_label_registry.py)
сверяет вывод сборщика со строками этой таблицы на каждый CI-прогон
(`.github/workflows/repo-ci.yml`).

## Честный потолок

Гвардия покрывает только тормоза, **выраженные меткой**. Тормоз, зашитый
условием в коде — `return False`, `exit 1`, пауза диспатча без метки
(предохранитель конвейера, `scripts/orchestra/pulse_guard.py:282-314`) —
механически не проверяется: метки на нём нет, сканировать нечего. Такие
тормоза закрываются правилом «Тормоз без газа не принимается» в
[`AGENTS.md`](../../AGENTS.md) и вопросом в шаблоне PR, то есть дисциплиной
автора и ревьюера, а не автоматической проверкой. Не путать частичное
покрытие с полным.

| `orchestra:skip` | Человек, на PR — ручная постановка автором, обходящим контракт пула для мелочи | PR не связан с задачей пула (правка вне Issues) | Не тормоз, а обход тормоза: `scripts/orchestra/contract_check.py:76-78` пропускает проверку «PR ↔ задача» целиком | Сам является газом — не требует отдельного снятия; злоупотребление им видно в истории PR (`docs/agents/PROTOCOL.md:96-97`) | Осознанно ручной по построению |
| `conflict` | [`scripts/orchestra/scheduler.py:213-260`](../../scripts/orchestra/scheduler.py) (`mark_conflicts`/`_set_conflict_label`, ставится когда `mergeable_state == "dirty"`) | PR перестал сливаться в main без ручного разрешения | Пометка, не отдельная блокировка: реальный тормоз слияния — `mergeable_state` (`scheduler.py:421`, `merge_queue` пропускает PR не в `clean/unstable/has_hooks`), метка — видимый сигнал автору; сама метка вдобавок газ ко второму тормозу (#252) — делает PR кандидатом на серверное подтягивание ветки (`review_labels.should_update_branch`) | Автоматический: `mark_conflicts` (#270) сама же снимает метку следующим прогоном, когда `mergeable_state` явно подтверждён неконфликтным — один из `review_labels.CONFLICT_CLEAR_STATES` (`clean`/`unstable`/`has_hooks`/`behind`/`blocked`). `None`/`unknown` (вычисление ещё не завершилось) метку не снимают — снятие по ним прятало бы реальный конфликт. Снятие/постановка идут через `_set_conflict_label` — единственное место, которое сразу правит и сервер, и `pull["labels"]` в объекте, который main() передаёт дальше по прогону (класс «устаревшая метка в памяти», #252, второй заход) | Ребейз автором меняет `mergeable_state` на одно из `CONFLICT_CLEAR_STATES` (обычно `clean`) — следующий прогон `mark_conflicts` снимает метку без ручного вмешательства |
| `contract:failed` | [`scripts/orchestra/contract_check.py:52-56`](../../scripts/orchestra/contract_check.py) (`fail()`) | Контракт «PR ↔ задача из пула» нарушен (нет ссылки на задачу, задача чужая/закрыта, второй PR на ту же задачу) | Метка сигнальная — сама проверка контракта является required-статусом защиты ветки, блокирует слияние своим состоянием, не меткой | Автоматический: [`contract_check.py:157-160`](../../scripts/orchestra/contract_check.py) снимает метку в начале каждого следующего успешного прогона (новый пуш переисполняет контракт) | Условие: следующий прогон контракта на том же PR проходит без нарушений |
| `review:ok` | [`scripts/review/check_pr.py::verdict_for`](../../scripts/review/check_pr.py) через `scripts/lib/review_labels.py::REVIEW_OK` | Детерминированное ревью не нашло замечаний и дифф не крупный (или крупный, но принят `review:large-ok`) | Часть гейта слияния: `scheduler.py:437` (`merge_label_gate`) требует `review:ok` И `ai:ok` одновременно | Автоматический: следующий пуш перезапускает `check_pr.py`, который снимает и переставляет вердикт (блок вердикта `check_pr.py::main`) | Условие: новый прогон ревью проходит без находок |
| `review:changes-requested` | [`scripts/review/check_pr.py::verdict_for`](../../scripts/review/check_pr.py) через `REVIEW_CHANGES` | Ревью нашло замечания (секрет в диффе, конфликт-маркер, файл секретов, не компилируется) | Не входит в `merge_label_gate` напрямую — блокирует по факту отсутствия `review:ok` на этом PR | Автоматический: новый пуш переисполняет ревью и переставляет вердикт | Условие: находки устранены, следующий прогон чист |
| `review:large` | [`scripts/review/check_pr.py::verdict_for`](../../scripts/review/check_pr.py) через `REVIEW_LARGE` | Дифф больше `LARGE_DIFF_LINES` (800 строк) и `review:large-ok` ещё не выставлена (`check_pr.py::size_gate`) | Блокирует слияние тем же путём, что `review:changes-requested` — `review:ok` не выставляется, пока размер не принят | См. `review:large-ok` ниже — это единственный путь снятия | Порог: `LARGE_DIFF_LINES = 800` строк добавлений (`check_pr.py::LARGE_DIFF_LINES`) |
| `review:large-ok` | Автоматика: [`scripts/review/ai_review.py::apply_large_ok`](../../scripts/review/ai_review.py) ставит метку после вердикта `approve` на том же head (#204); вручную — владельцем для диффов за `LARGE_DIFF_HUGE_LINES` | Размер дифф-гейта принят осознанно: взгляд делегирован AI-ревью, решение — `ai_review.py::large_ok_decision` | Обходит `review:large`: `check_pr.py::size_gate` — при наличии метки verdict становится `review:ok` | Автоматический: новое AI-ревью на актуальном head повторяет вердикт и подтверждает размер; 2000+ строк (`LARGE_DIFF_HUGE_LINES`) автоматика не подтверждает — эскалация владельцу (`ai_review.py::huge_diff_escalation_text`); сама метка и есть газ, снимать нечего | Условие: вердикт AI `approve` на том же head, где висит `review:large` (#204; до #204 замер задачи #207 — #167 и #173 висели больше суток с ручным путём) |
| `ai:ok` | [`scripts/review/ai_review.py::cmd_verdict`](../../scripts/review/ai_review.py) через `review_labels.AI_OK` | AI-ревью вернуло вердикт `approve` на head, где ревью реально проведено, ИЛИ метка сохранена на более позднем head, чей дифф относительно base не изменился (`review_labels.py::diff_unchanged`) — метка может дожить до head, который сам никто не ревьюил (чистый merge-коммит подтягивания main, #252/#294) | Часть гейта слияния — `merge_label_gate` требует его вместе с `review:ok` | Автоматический, условие уточнено #252 и #294: триггер `ai-review.yml` — не метка, а `workflow_run` от завершения `pr-review` (события `GITHUB_TOKEN` меток не создают, антирекурсия GitHub), поэтому сохранение метки в `check_pr.py` само по себе прогон не останавливает. Отпечаток диффа PR (`review_labels.diff_fingerprint`) сверяется ДВАЖДЫ, но одним и тем же местом правды: `check_pr.py::ai_verdict_keep` решает, снимать ли метку, `ai_review.py::cmd_should_run` (шаг `fingerprint` в `ai-review.yml`, читает `review_labels.should_run_ai_review`) решает, идти ли в дорогой прогон вовсе. Дифф ИЗМЕНИЛСЯ → метка снята, `go=true`, свежий вердикт. Дифф НЕ изменился (подтягивание main без конфликтов меняет только head) → метка сохраняется И `go=false` — job `review` останавливается до чекаута/gather/DSH | Условие: новое AI-ревью на новом head с ИЗМЕНИВШИМСЯ диффом отвечает `approve`; при неизменном диффе прежний `approve` остаётся в силе, дорогой прогон не запускается |
| `ai:changes-requested` | [`scripts/review/ai_review.py::cmd_verdict`](../../scripts/review/ai_review.py) через `review_labels.AI_CHANGES` | AI-ревью вернуло вердикт `rework` | Блокирует по факту отсутствия `ai:ok` | Тот же путь, что `ai:ok` (#252, #294): пуш с ИЗМЕНИВШИМСЯ диффом снимает метку и запускает дорогой прогон (`go=true`); неизменный дифф (подтягивание main) метку сохраняет И не запускает прогон (`go=false`, `review_labels.should_run_ai_review`) | Условие: замечания устранены, новое ревью на новом head с изменившимся диффом |
| `ai:failed` | [`scripts/review/ai_review.py::cmd_verdict`](../../scripts/review/ai_review.py) через `review_labels.AI_FAILED` | Ответ модели не соответствует контракту вердикта (нет строки `ВЕРДИКТ:`, их больше одной, транспорт DSH упал) | Блокирует по факту отсутствия `ai:ok`; замер задачи #207: 84% прогонов этого гейта — ручной повторный запуск, закрывается #196 | Пуш с изменившимся диффом снимает метку и перезапускает ревью как обычно (#252). Пуш БЕЗ изменения диффа (подтягивание main) ТОЖЕ перезапускает прогон: `review_labels.should_run_ai_review` пропускает дорогой прогон по совпавшему отпечатку только для `ai:ok`/`ai:changes-requested` — `ai:failed` из этого пропуска исключён по построению и НИКОГДА не отвечает `false`, поэтому новый пуш всегда запускает `ai-review.yml` заново, даже если дифф не менялся. Таймер #196 ([`scripts/orchestra/scheduler.py::trigger_ai_review`](../../scripts/orchestra/scheduler.py)), который перезапускает `ai-review.yml` ПО ТАЙМЕРУ (`AI_REVIEW_RETRY_AFTER_MINUTES` с момента последней перестановки `review:ok`) — ОТДЕЛЬНЫЙ, независимый путь автоповтора, а не компенсация за пропуск по неизменному диффу: такого пропуска для `ai:failed` не существует вовсе, оба пути (новый пуш и таймер) запускают прогон | Условие: новый прогон на изменившемся диффе отвечает по контракту, ИЛИ таймер #196 запускает ручной `workflow_dispatch` повтор на том же диффе. До #196 автоповтора без нового пуша не было — это и есть находка задачи #196, не #207 |
| `update-available` | [`scripts/orchestra/upstream_drift.py`](../../scripts/orchestra/upstream_drift.py) (`_set_drift_label`, ставится вместе с маркер-комментарием `[дрейф пина: …]` в #134) | Релиз апстрима `pawaca/dsh-edge` семверно новее пина в `dsh-edge/upstream.json` (или пин вообще не на теге релиза) — морда отстаёт, нужен бамп пина (#134) | Пометка, не блокировка: ни один гейт слияния её не читает; это сигнал владельцу и агентам, что пора делать бамп (ручной PR с полным прогоном деплоя, разбор чейнджлога — #161) | Автоматический: тот же прогон пульса снимает метку (`_drop_drift_label`), как только пин снова стоит на новейшем стабильном релизе — бамп смержен, метка снята без ручного действия. Известный размен: метку, снятую вручную ВО ВРЕМЯ активного дрейфа, вернёт только новый сигнал (следующий релиз) — мутирующий вызов на каждый пульс ради этого не делается | Условие: сверка `decide_drift` отвечает `ok` — пин на новейшем стабильном теге апстрима |
