# Протокол openspec: когда, из чего, когда считается сделанным

Адресован агентам и людям. Отвечает на вопросы, которые новый агент иначе решает чтением
исходника инварианта и по аналогии с соседними каталогами: когда `openspec/changes/<id>/`
обязателен, из каких файлов он состоит, что именно значит «сделано», кто и чем архивирует,
и что происходит с дельта-спекой после. Факты ниже — измерены на этом репозитории
2026-09-07 (44 каталога в `openspec/changes/`, 10 в `openspec/changes/archive/`), не общая
теория openspec.

## Когда change обязателен

Нетривиальная работа — изменение поведения системы, а не косметика — идёт через
`openspec/changes/<change-id>/`, не ad-hoc правкой (правило верхнего уровня — `AGENTS.md`,
раздел «Работа с документацией»: «Меняешь поведение системы → дельта-спека в
`openspec/changes/<change-id>/`»). Формального автоматического порога «это уже
нетривиально» в репозитории нет — граница держится на суждении автора PR и ревью,
как и у любого правила из `AGENTS.md`, для которого явно сказано «часть решений машиной
не проверяется» (см. AGENTS.md, «Решение — это механизм, а не текст»).

Не идёт через change: точечный багфикс без изменения контракта (пример: узкие issue
`#610`/`#616`, чинящие детали `pulse_guard.py::failure_watch` уже ПОСЛЕ того, как change
`failure-watch` сам был реализован и слит — свежий proposal/design/tasks под них не
заводился, потому что контракт функции не менялся, только её надёжность).

## Из чего состоит change

| Файл | Обязателен? | Что в нём | Факт по репозиторию |
|---|---|---|---|
| `proposal.md` | Да, всегда | Название, класс проблемы, ссылка на задачу пула (`Задача: #N.` или `Задачи: #N, #M.` первым абзацем), ссылка на дельта-спеку и на design.md, если есть | 44 из 44 |
| `design.md` | Нет | Развилка вариантов и почему выбран текущий — нужен, когда решение неочевидно | 14 из 44 |
| `tasks.md` | Нет (но становится нормой для новых change) | Разбивка на пункты с `- [ ]`/`- [x]`, исполнитель и критерий приёмки на каждый | 17 из 44 (проверь на месте: `ls openspec/changes/*/tasks.md`) |
| `specs/<capability>/spec.md` (или `specs/<capability>.md`) | Нет | Дельта-спека: что меняется в поведении системы конкретно этим change, в терминах требований (ADDED/MODIFIED/REMOVED — см. существующие файлы как образец формы) | 33 из 44 несут свою копию внутри себя; общий источник правды один — `openspec/specs/journal-tasks-hands.md` (см. ниже) |

Формат абзаца-декларации задачи важен механически: инвариант 4 (ниже) читает именно
первый абзац, начинающийся с «Задач», а не первое `#N` во всём файле — прочая проза
change может ссылаться на чужие номера (родительский эпик, зависимость, история PR) без
риска быть принятой за собственную задачу.

## Что считается завершением

Механическая проверка — `scripts/orchestra/repo_invariants.py::check_unarchived_complete_changes`
(инвариант 4, докстринг функции — источник истины построчно). Два **независимых** условия,
любое из двух достаточно:

1. **Быстрый путь.** `tasks.md` существует, и в нём отмечен КАЖДЫЙ чекбокс (нужен хотя бы
   один). Годится для change, заведённых после того, как `tasks.md` стал частью процесса.
   На 2026-09-07 таких — 0 (проверено запуском инварианта на живом репозитории): везде,
   где `tasks.md` есть, в нём остались неотмеченные пункты.

2. **Второй путь**, только для каталогов БЕЗ `tasks.md` вообще (27 из 44 на 2026-09-07,
   плюс `task-rework-loop`, чей `tasks.md` не содержит ни одного чекбокса, — этот путь
   для него тоже недоступен, `tasks.md` у него существует). Условие: `proposal.md`
   декларирует задачу, эта задача закрыта с `state_reason=completed` (не `not_planned` —
   брошенная работа не значит сделанную), И ни один открытый PR не ссылается на путь
   `openspec/changes/<id>` буквально (по подстроке в title+body, не по эвристике GitHub
   Search — та матчит нечётко, проверено экспериментом 2026-09-07: `gh pr list --search`
   вернул PR, чьё тело не содержит искомой подстроки вовсе).

   Путь 2 **не применяется**, если `tasks.md` существует, даже с незакрытыми
   чекбоксами — иначе реальная незавершённая работа (пример: `dsh-edge-plugin-system`,
   7 из 44 пунктов не отмечены) ложно считалась бы готовой из-за того, что её эпик-issue
   давно закрыт `completed`.

   **Известная граница пути 2** (честно, не подтверждено автоматикой): change, чья ОРИГИНАЛЬНАЯ
   задача закрыта `completed`, но код той же области продолжает получать точечные
   доработки узкими issue БЕЗ ссылки на путь change (см. пример `failure-watch` выше в
   разделе «Когда change обязателен») — путь 2 такой change пометит завершённым, хотя
   разработка кода вокруг него объективно продолжается. Это не баг критерия, а его прямая
   граница по конструкции (условие сформулировано как «нет открытого PR на ПУТЬ change»,
   не «нет открытого PR, трогающего тот же код») — при архивации такого каталога решение
   остаётся за тем, кто архивирует: заголовок нарушения в отчёте называет номер задачи,
   этого достаточно, чтобы свериться перед `git mv`.

Инвариант 4 включён в `CI_GATING` (обязательная проверка `test`, `.github/workflows/repo-ci.yml`)
только частично — см. следующий раздел.

## Кто и чем архивирует

Два механизма, оба переносят `openspec/changes/<id>/` в `openspec/changes/archive/<id>/`
через `git mv` (сохраняет историю) и правят входящие markdown-ссылки на старый путь в том
же коммите:

- **Автоматический** — `scripts/orchestra/archive_complete_changes.py`, вызывается job'ом
  `archive-fixup` (`.github/workflows/repo-ci.yml`) на каждое событие `pull_request`.
  Умышленно проверяет ТОЛЬКО быстрый путь (`tasks.md` полностью отмечен) — второй путь
  сюда не передаётся (см. докстринг файла и его тест
  `test_main_calls_checker_with_fast_path_only`), потому что подключение второго пути
  означало бы автокоммит и автопуш `git mv` по backlog'у без единого ревью на ближайшем
  же чужом PR. Сработал ровно один раз за всю историю репозитория:
  `openspec/changes/storage-readiness -> openspec/changes/archive/storage-readiness`
  (коммит `87d245ae`, «openspec: автоархивация полностью выполненных change (инвариант 4, #493)»).
- **Ручной** — `git mv openspec/changes/<id> openspec/changes/archive/<id>` плюс правка
  входящих ссылок руками, отдельным PR. Так перенесены остальные 9 из 10 записей в
  `archive/`.

### Backlog и план массовой архивации

Второй путь (см. выше) на 2026-09-07 находит 23 каталога, удовлетворяющих критерию
завершённости, у которых `tasks.md` никогда не было. Это реальный, годами копившийся
долг, а не регрессия свежего PR — поэтому инвариант 4 **временно наблюдательный**
(не в `CI_GATING`, см. `repo_invariants.py`, комментарий у константы `CI_GATING`):
включить его сразу означало бы покрасить обязательную проверку `test` разом на всех
открытых PR репозитория из-за чужого долга (тот же класс нарушения, от которого уже
отказались для инвариантов 1 и 5 — AGENTS.md, «Тормоз без газа не принимается»).

План разбора долга без гигантского PR (не выполняется в рамках этого change,
только называется): архивировать каталоги отдельными PR малыми пачками (3-5 за раз,
подобранные по смежности — например, все telegram-* одним PR, все task-*/branch-*
другим), каждая пачка — простой `git mv` без изменений кода, что делает ревью
формальностью (можно сливать без задержки на AI-ревью, если контракт репозитория это
допускает для чисто-документационных PR — проверить перед первой пачкой). После того как
второй путь перестанет находить нарушения (или найденные сознательно исключены с
пояснением, как `failure-watch` выше), вернуть инвариант 4 в `CI_GATING` правкой
константы — условие обратного включения названо там же, где условие снятия
(`GATING_RELEASE_CONDITION`).

## Что происходит с дельта-спекой после завершения

**Как должно работать.** Единственный источник правды о текущем поведении системы —
`openspec/specs/journal-tasks-hands.md` (сегодня 370 строк, единственный файл каталога).
Дельта-спека внутри `openspec/changes/<id>/specs/` описывает ИЗМЕНЕНИЕ поведения этим
конкретным change; когда change завершён и слит, его дельта обязана быть отражена в
центральном файле — иначе источник правды не описывает то, что реально работает в
проде. Момент переноса — до или вместе с архивацией (`git mv` в `archive/` — это
консервация истории решения, не место, откуда ещё раз кто-то прочитает актуальное
поведение).

**Как работает сейчас — честно, механизма нет.** Ни одна дельта-спека не переносится в
`openspec/specs/journal-tasks-hands.md` автоматическим или формализованным ручным шагом,
привязанным к завершению change. Файл действительно редактируется вместе с частью PR
(видно по git-истории: правки, сопровождающие конкретные задачи, например коммит с
сообщением «дельта-спека свёрнута в openspec/specs §28.1/§28.2» при завершении
`auto-wire-declared-deps`) — но это решение автора конкретного PR, не проверяемое
правило: 33 из 44 активных change несут собственную копию дельты, ВСЕ 10
заархивированных унесли свою дельту в `archive/` как есть, без последующей сверки с
центральным файлом. Нет гвардии, которая заметила бы расхождение между тем, что дельта
обещала, и тем, что попало (или не попало) в центральный файл.

**Оценка: автоматизируемо или ручная редакторская работа.** ЧАСТИЧНО автоматизируемо —
и это две разные по сложности задачи, не одна:

- *Обнаружить расхождение* (спека архивирована, но её содержание не найдено в
  центральном файле) — механически реализуемо: гвардия по существенным заголовкам
  разделов дельты (не всему тексту — дельта и центральный файл почти никогда не
  дословно совпадают) может отметить «дельта `<id>` заархивирована, но раздел про неё в
  `journal-tasks-hands.md` не обнаружен» как наблюдательный сигнал, по образцу
  остальных инвариантов `repo_invariants.py`. Стоимость: обычная (та же форма, что
  инвариант 7 — паттерн по тексту, честный потолок вроде отсутствия смысловой сверки).
- *Само слияние текста* (переписать формулировку дельты под структуру и стиль уже
  существующего документа, разрешить противоречия между тем, что дельта обещала
  вначале, и тем, что реально реализовано после ревью и реворков) — это редакторское
  суждение, не текстовая операция. Механическое слепое приписывание текста дельты в
  конец центрального файла дало бы противоречивый, задвоенный источник правды хуже
  текущего отсутствия слияния — тот же класс риска, что и слепая массовая архивация
  выше. Автоматизировать стоит только обнаружение, не само редактирование.
