# Переключение LLM-провайдера (морда + раннеры)

Кому: владельцу. Когда: кончилась квота у текущего провайдера, нужен другой
OpenAI-compatible эндпоинт.

**Главное, что надо знать до начала: этот раздел — про слот раннеров и штатного
`deepseek-official` (задача #158), не про Settings → Models в морде.** Раннеры
и штатный адаптер `dsh-llm-deepseek` держат один слот через переменные деплоя
(`vars`/секреты) — переключение здесь всегда **замена**, GLM исчезнет из пикера
до обратного переключения. Имена переменных (`DEEPSEEK_*`) — унаследованные,
значение может быть любым OpenAI-compatible эндпоинтом.

Второй провайдер **в самой морде** (для чата, не для раннеров) добавляется без
передеплоя через штатный Settings → Models — кнопки ожили после плагина
`provider-registry` (#378, [research/11](../research/11-dsh-edge.md)), см.
[README плагина](../../plugins-src/provider-registry/README.md). Смешивать эти
два механизма не нужно: раннеры продолжают читать `DEEPSEEK_*` из деплоя, морда —
из своего реестра.

## Цепочка провайдеров (#727) — основной путь для ai-review, ручная процедура ниже больше не единственная

**С #823 (openspec/changes/llm-provider-usage-manifest) назначение «какой
канал какой цепочкой пользуется» смотри в
[`docs/agents/LLM-PROVIDER-USAGE.md`](../agents/LLM-PROVIDER-USAGE.md) и
правь в `config/provider-usage.json`** — манифест приоритетнее
`vars.DSH_PROVIDER_CHAIN` ниже, если файл присутствует (что он и делает после
этого change); `vars.DSH_PROVIDER_CHAIN` остаётся описанным здесь как
фоллбэк переходного периода (файла манифеста нет вовсе) и как формат
ЭЛЕМЕНТА цепочки, который манифест переиспользует без изменений.

Раньше исчерпание квоты требовало ручного прохода по всем шагам ниже (ключ,
4×`gh variable set`, редеплой) на КАЖДОЕ переключение — владелец прямо
потребовал этого не делать. Теперь `ai-review.yml` сам перебирает провайдеров
из `vars.DSH_PROVIDER_CHAIN` (JSON-массив, ОДНО место правды для порядка) —
`quota_exhausted` и повторяемый транспортный отказ (`HTTP_404`/`EMPTY_RESPONSE`/
`RATE_LIMIT`) переключают на следующего провайдера ВНУТРИ одного прогона, без
участия человека. Ошибка контракта вердикта (модель ответила не по формату) в
переход не попадает вовсе — это отдельная забота `ai_review.py::parse_verdict`,
цепочка её не видит: иначе один сломанный PR сжёг бы все учётки подряд.

**Формат `vars.DSH_PROVIDER_CHAIN`** — упорядоченный JSON-массив, порядок =
приоритет:

```json
[
  {"name": "NVIDIA", "base_url": "https://integrate.api.nvidia.com/v1",
   "model": "nvidia/nemotron-3-ultra-550b-a55b", "secret_env": "NVIDIA_API_KEY", "max_output_tokens": 131072},
  {"name": "GLM", "base_url": "https://api.z.ai/api/coding/paas/v4",
   "model": "glm-5.3-flash", "secret_env": "DEEPSEEK_API_KEY", "max_output_tokens": 131072}
]
```

Порядок на момент написания (NVIDIA первым) — не эстетика: GLM/z.ai исчерпан
до 2026-09-10 (см. врез в начале раздела), NVIDIA сейчас рабочий — первым
пробовать заведомо исчерпанного смысла нет, каждый прогон терял бы один
быстрый отклонённый вызов впустую. После сброса порядок можно вернуть, если
нужно, тем же `gh variable set` — само по себе ничего переставлять не будет
(чейн не запоминает «кто оживал» и всегда начинает с индекса 0).

`secret_env` — имя переменной окружения, в которую `ai-review.yml` уже кладёт
ключ этого провайдера (`secrets.DEEPSEEK_API_KEY`/`secrets.NVIDIA_API_KEY` —
литерально, оба сразу, не через индексацию: цепочке нужны ключи ВСЕХ
провайдеров одновременно, а не одного активного). Добавить провайдера в
цепочку — завести секрет его ключа (`gh secret set <ИМЯ>`), передать его тем
же именем в `env:` шага «Ревью агентом» `.github/workflows/ai-review.yml` и
дописать элемент в JSON:

```bash
gh variable set DSH_PROVIDER_CHAIN --body '<весь JSON-массив одной строкой>'
```

Редеплоя морды это НЕ требует — правит только раннеров, ре-деплой нужен
только для смены провайдера МОРДЫ (см. «Что где объявлено» и разделы ниже).

**Id модели проверяется реестром, не только глазами (#737).** Живая цена
невнимания: `nvidia/nemotron-3-super-120b-a12b` был вписан в
`vars.DSH_PROVIDER_CHAIN` без единой сверки с `/v1/models` (шаг 1 ниже) —
дал 37 минут молчания на прогоне (`rc=1`, ни одного байта в stderr), пока
цепочка ждала диагностики, которой провайдер не дал. Теперь
`dsh_run_with_provider_chain` (`scripts/lib/dsh-ci.sh`) сверяет `model`
каждого элемента с реестром подтверждённых id
(`scripts/lib/confirmed-provider-models.json` — хэш строки, не сама строка,
класс #153) и **пропускает** провайдера с неподтверждённым id, не тратя на
него ни секунды: сообщение называет факт прямо. Добавляя провайдера в
цепочку — сначала сверь id шагом 1 ниже, потом допиши запись в реестр
(`model_sha256`, `confirmed_at`, `evidence`), и только потом
`gh variable set DSH_PROVIDER_CHAIN`.

**Классификация отказа без диагностики (#737).** `rc≠0` при пустом (или
состоящем только из пробелов) stderr по умолчанию — ПЕРЕКЛЮЧАЕМЫЙ класс:
заведомо-нелечимый сменой провайдера отказ (битый ключ, нарушение контракта
вердикта, битый аргумент) всегда печатает диагностику, тишина неотличима от
временного транспортного сбоя. Сообщение в логе (`::warning`/`::error`)
всегда называет код возврата и, если применимо, факт «stderr пуст —
диагностику дать не может» — не утверждает распознанный класс там, где
классификатор не увидел ничего.

**Все провайдеры цепочки исчерпаны разом** — `ai:failed`, комментарий вердикта
называет факт: «все провайдеры исчерпаны, ближайший сброс `<дата>`, действие —
ждать сброса вне CI или добавить провайдера». Автоповтор оркестратора (#196) не
дёргает `ai-review.yml` вслепую в ту же квоту: `scheduler.py::trigger_ai_review`
читает дату сброса из шапки комментария (`reset-at:`) и эскалирует владельцу
(issue #120 + Telegram) вместо холостого повтора, пока дата не наступила.

**Область охвата — все три канала: `ai-review.yml`, `worker.yml` (#797) и
`hands.yml` (#805).** `worker.yml`/`scripts/worker/task.sh` и
`hands.yml`/`scripts/hands/dsh_task.sh` подключены тем же механизмом
(`dsh_run_with_provider_chain`, `scripts/lib/dsh-ci.sh`) — шаг «плагин стрима»
(`dsh-hands-streamer`) по-прежнему монтируется ДО каждой попытки цепочки, но
профиль теперь ЗАТРАВЛИВАЕТСЯ первым провайдером цепочки (chain[0]) ДО этого
монтажа: `dsh plugin add` видит уже существующий `cordis.patch.yml` и не
перезаписывает его дефолтом (`initProfile` пишет файлы профиля только при
отсутствии — research/10-dsh-architecture.md), а сама цепочка на шаге прогона
перепатчивает профиль заново на каждую попытку — это ПОЛНАЯ перезапись файла
патча, монтаж плагина (отдельный слой `dsh.profile.bundles`, независимый от
`cordis.patch.yml` — «Порядок слоёв», research/10-dsh-architecture.md) этим не
затрагивается. У рук был дополнительный риск, которого нет у `worker.yml`:
bootstrap-событие журнала уходит ДО первой попытки цепочки, когда известен
только `chain[0]`. Решено механизмом, не пропуском (#805): `bootstrap` теперь
называет `chain[0]` явно как первого кандидата, не как факт «эта модель
ответила»; факт, какой провайдер реально обслужил вызов, уходит уже
существующим безусловным событием `agent_answer` новыми полями
`provider`/`model` — подробности `openspec/changes/archive/llm-provider-chain-failover/
tasks.md`, «Гейт 4».

**Морда — вне цепочки принципиально.** У неё один слот адаптера (см. врез выше),
цепочка из нескольких провайдеров туда физически не помещается — переключение
морды остаётся ручным, шаги 2–4 ниже.

## Быстрый провайдер Claude (anthropic-oauth-pool, #838) — перед цепочкой, не в ней

Плагин `dsh-anthropic-oauth-pool` (подписка Claude владельца) монтируется
НЕЗАВИСИМО от suite ротации учёток (`vars.PLUGINS_SUITE_URL`, снята вместе
со сломанным combo-router — #790/#216) во всех трёх каналах
(`worker.yml`/`hands.yml`/`ai-review.yml`), гейт — секреты
`ANTHROPIC_OAUTH_1`/`ANTHROPIC_OAUTH_2` (JSON `~/.claude/.credentials.json`
целиком: `{"claudeAiOauth": {"accessToken", "refreshToken", ...}}`). Ни один
секрет не задан → пул не подключается, поведение (цепочка/одиночный
провайдер) не меняется.

**Не элемент `DSH_PROVIDER_CHAIN`.** Пул регистрирует себя в
`llm-pi-ai.providers` с `api: anthropic-messages` — другим протокольным
диалектом, чем `openai-completions`, на котором держится вся цепочка
(`llm-deepseek`-адаптер шлёт OpenAI-формат на любой `DEEPSEEK_BASE_URL`).
Подстановка пула элементом цепочки отправила бы OpenAI-запрос на
Anthropic-эндпоинт — не сработает структурно. Вместо этого
`dsh_run_with_pool_then_chain` (`scripts/lib/dsh-ci.sh`) пробует пул ПЕРВЫМ
ОДНИМ вызовом (сам пул уже перебирает свои аккаунты на 429/401/403 внутри
одного HTTP-запроса), при отказе — откатывается на штатную
`dsh_run_with_provider_chain` без изменений. Обоснование и разбор
несовместимости протоколов — `openspec/changes/anthropic-oauth-pool-standalone/design.md`.

## Как опознать, что переключаться пора (ручной путь — только морда, вне цепочки принципиально)

Квота провайдера кончилась — это видно в хвосте stderr DSH в логе job'а, отдельной
строкой, а не в общем «job failed»:

```
dsh: RATE_LIMIT: Weekly/Monthly Limit Exhausted. Your limit will reset at <дата>
```

Замеренный случай: прогоны `worker.yml` 2026-08-31 20:46/21:16/21:31 — все три красные
с этой строкой, сброс лимита 2026-09-04 20:54. Признак отличается от «модели нет»
(`modelCode does not exist`) и от «слишком большой ответ» (`INVALID_REQUEST` про
max tokens) — лечатся они по-разному, поэтому и различать их надо по строке, а не по
цвету job'а. Квота считается на аккаунт провайдера, а не на модель: смена модели того же
провайдера от `RATE_LIMIT` не спасает.

**Это не единственная форма `RATE_LIMIT`.** Короткое окно (живой случай —
`dsh: RATE_LIMIT: Rate limit reached for requests`, без «Weekly/Monthly Limit
Exhausted») — переживается автоматически всеми тремя каналами DSH: ревью
(`scripts/review/ai_dsh.sh`, #419), автономным воркером
(`scripts/worker/task.sh`) и руками (`scripts/hands/dsh_task.sh`) — общий
механизм `dsh_run_with_retry` в `scripts/lib/dsh-ci.sh` (#422) ретраит с
экспоненциальной паузой и своим бюджетом ожидания у каждого канала (30 мин у
ревью и воркера, 10 мин у рук — короче, потому что канал интерактивный, а
собственный job живёт всего 30–70 мин), ручное вмешательство не нужно.
Различать их всё равно надо по тексту строки, а не по факту падения job'а —
только «Weekly/Monthly Limit Exhausted» означает «переключайся или жди
сброса»; короткая форма, не снятая за отведённый бюджет ретрая (`ai:failed`
у ревью; у воркера/рук — комментарий в задаче и Telegram, различающие
«провайдер в лимите» от «агент не справился», #422), — сигнал, что квота
исчерпана настолько плотно, что уже похожа на длительную, и тоже кандидат на
переключение по этому раннбуку. У воркера и рук исчерпание бюджета (или
недельная/месячная квота) СРАЗУ возвращает занятую задачу в пул (снимает и
замок, и назначение — `claim_task.py release-full`), не дожидаясь
24-часового TTL-сборщика: вина не в задаче.

## Что где объявлено

| Что | Где живёт | Кто читает |
|---|---|---|
| Базовый URL | `vars.DEEPSEEK_BASE_URL` | раннеры + морда (при деплое) |
| Модель | `vars.DEEPSEEK_MODEL` | раннеры + морда (при деплое) |
| Ключ | `secrets.DEEPSEEK_API_KEY` | раннеры + морда (при деплое) |
| Имя группы в пикере | `vars.DSH_EDGE_PROVIDER_NAME` | только морда |
| Каталог моделей пикера | `vars.DSH_EDGE_MODEL_CATALOG` | только морда |

Механика морды: значения не читаются из окружения в рантайме, а патчатся в
собранный бандл на деплое (`deploy-dsh-edge.yml`, шаг «Патч каталога моделей») и
кладутся в секреты воркера. Значит **после правки переменных нужен ре-деплой морды.**
Раннеры читают переменные при каждом запуске — им ре-деплой не нужен.

## Шаги

### 1. Узнать точный id модели (обязательно, не угадывать)

Публичный листинг NVIDIA без ключа отдаёт 451, поэтому id проверяется ключом:

```bash
curl -s https://integrate.api.nvidia.com/v1/models -H "Authorization: Bearer $NVIDIA_API_KEY"
```

В ответе найти нужную модель. Ожидаемое семейство Nemotron-3: `nano`, `super`,
`ultra`. Id вида `nvidia/nemotron-3-ultra-550b-a55b` — **экстраполяция** по образцу
уже работавшего `nvidia/nemotron-3-super-120b-a12b`, а не подтверждённый факт:
сверить с ответом выше буква в букву.

### 2. Положить ключ (делает владелец лично)

```bash
gh secret set DEEPSEEK_API_KEY
```

Команда спросит значение в терминале. Значение ключа не попадает ни в репозиторий,
ни в историю команд, ни в переписку.

### 3. Переставить переменные

```bash
gh variable set DEEPSEEK_BASE_URL --body 'https://integrate.api.nvidia.com/v1'
gh variable set DEEPSEEK_MODEL --body '<id из шага 1>'
gh variable set DSH_EDGE_PROVIDER_NAME --body 'NVIDIA'
gh variable set DSH_EDGE_MODEL_CATALOG --body '[{"id":"<id из шага 1>","name":"Nemotron-3 Ultra 550B","contextWindow":1000000}]'
```

### 4. Ре-деплой морды

```bash
gh workflow run deploy-dsh-edge.yml
```

### 5. Проверить видимый результат, а не зелёный шаг

Зелёный workflow ничего не доказывает. Доказательства, по возрастанию силы:

```bash
curl -s https://dsh-edge.mytab0r.workers.dev/api/health
```

— ожидается `"status":"ready"` и сменившийся `deploymentId`. Дальше — открыть морду
и **отправить реальный ход**: пикер моделей должен показывать новую группу, а агент —
ответить. Последнее: запустить hands-задачу и убедиться, что ход дошёл до
`turn/end completed`, а не упал на первом вызове модели.

## Откат на GLM

Тем же путём, значения прежние:

```bash
gh secret set DEEPSEEK_API_KEY   # ключ z.ai
gh variable set DEEPSEEK_BASE_URL --body 'https://api.z.ai/api/coding/paas/v4'
gh variable set DEEPSEEK_MODEL --body 'glm-5.3-flash'
gh variable set DSH_EDGE_PROVIDER_NAME --body 'GLM'
gh variable set DSH_EDGE_MODEL_CATALOG --body '[{"id":"glm-5","name":"GLM-5","contextWindow":200000},{"id":"glm-5.3","name":"GLM-5.3","contextWindow":1000000},{"id":"glm-5.3-flash","name":"GLM-5.3-Flash","contextWindow":1000000},{"id":"glm-4.7","name":"GLM-4.7","contextWindow":200000}]'
gh workflow run deploy-dsh-edge.yml
```

## Грабли, оплаченные заранее

**Потолок ответа зашит под GLM.** `DEEPSEEK_MAX_OUTPUT_TOKENS=131072` в конфиге
воркера морды и `DSH_MAX_TOKENS=131072` в раннере — это подтверждённый докой предел
GLM (`max_tokens` 1…131072). Для моделей NVIDIA публично не задокументирован, у
Nemotron-3 Ultra другая архитектура (Mamba-Attention MoE). **Если запросы начнут
отвергаться с ошибкой про max tokens — это первое, что надо проверить.**

**Ключ один на всех.** Морда и раннеры читают один и тот же секрет
`DEEPSEEK_API_KEY`. Расщепить провайдера между мордой и раннерами нельзя без
правки кода — и смысла мало: квота считается на аккаунт провайдера, а не на
потребителя.

**Частичная синхронизация — 401 на каждом ходе.** Менять base URL, ключ и модель
надо вместе. Оставленный старый ключ при новом URL даёт отказ на каждом
обращении, и выглядит это как «морда сломалась», а не как «конфиг рассинхронен»
(случай #80).

**Между шагами 2 и 3 есть окно рассинхрона.** Ключ уже новый, а `vars` ещё старые
(или наоборот) — запущенная в этот момент задача упадёт на авторизации у
провайдера. Падение громкое (401, не тихая подмена модели), так что данные не
портятся, но задачи в это окно запускать не надо: делай шаги 2 и 3 подряд.

## Учёт остатка квоты провайдера — что доступно (дополнено 2026-09-05, #324)

Владелец потребовал сборщик ВСЕХ квот, на которых стоит харнес
(`scripts/measure/quotas.py`). Для z.ai/GLM (текущий провайдер,
`api.z.ai/api/coding/paas/v4`) результат отрицательный, и это тоже результат,
а не пропуск: документированного REST-эндпоинта «остаток квоты/баланс» у
z.ai не найдено (проверено 2026-09-05 — `docs.z.ai/api-reference` рендерится
JS-фреймворком без серверной отдачи содержимого страниц через простой GET;
прямой запрос по догадке `.../api/paas/v4/usage` не отвечает содержательно).
Единственный подтверждённый сигнал остатка квоты — уже описанная выше строка
`RATE_LIMIT: ... reset at <дата>` в stderr ответа модели. `quotas.py` не
опрашивает z.ai — печатает эту причину как «нет данных» вместо тихого
пропуска источника.

**Следующий шаг, если понадобится точнее:** проверить у владельца, отдаёт ли
личный кабинет z.ai (веб, не API) остаток квоты и есть ли там export/webhook;
альтернатива — считать `RATE_LIMIT` из логов job'ов задним числом (сколько раз
