# Ребейз и миграция схемы: контекстный патч не мигрирует структуру

> Измерено 2026-09-10, замер #890/#895, решено #897. Смежное: [GitHub Actions](21-github-actions.md), правила работы в [AGENTS.md](../../AGENTS.md)

## Проблема

При переходе на новую схему хранения данных (например регистрация гвардий: из добавления строк в `repo-ci.yml` к файлам в каталоге `scripts/ci/guards/*.sh`), ребейз старой ветки PR проходит **без конфликта**, но новая схема **не применяется** на переезжаемом коде. Результат: PR остаётся в рукописной старой форме, и CI после ребейза падает на проверке новой схемы.

## Почему

Git применяет патч **контекстно**: при ребейзе старой ветки с эпохой +15 строк (рукописный способ) на новый main, где этот способ удалён, git находит соседний контекст и применяет патч как есть. Схема хранения — это **структура**, а не содержимое; патч работает на уровне текста файла, не на уровне сущностей. Конфликт бы появился только если бы старый способ физически конфликтовал с новым (например удалённые строки и добавленные в том же месте) — но это не так.

## Живой случай (2026-09-10, задача #879)

14 открытых PR добавляют шаги регистрации гвардии старым рукописным способом в `repo-ci.yml`. При механическом ребейзе `mechanical_rebase.py`:
- Все 14 проходят резолюцию `git rebase` без конфликтов — успех по git-версии.
- Но 20 суммарно добавленных шагов остаются в рукописной форме (нужны в каталоге файлов).
- CI гвардии `ci_guard_registration_guard` красит каждый такой PR на следующем проходе.

Итог: устранение **текстовых** конфликтов (рукописные строки в одном файле) породило **проблему структурную** — неправильная форма остаётся молча, CI краснеет уже после успешного ребейза.

## Решение

**Добавить транслятор между ребейзом и пушем.** Функция `scripts/lib/guard_step_translator.py` перенос рукописного шага (name, run, working-directory) в файл каталога `scripts/ci/guards/<file>.sh`, вызывается из `scripts/orchestra/mechanical_rebase.py` как отдельный коммит между `attempt_rebase("resolved")` и `push_rebased`.

Поведение:
- Успешный перенос → коммит в той же ветке, затем пуш (ветка оказывается на шаг впереди).
- Если форма не распознана или неполна → предупреждение в логе (`UnsupportedStepError`), пуш без остановки (перенос не может ухудшить уже решённое разрешение конфликта).
- Для каждого PR `ci_guard_registration_guard` всё равно будет писать, как именно перенести, если транслятор пропустил форму.

## Вывод для архитектуры

**Приём «регистрация как данные» работает ТОЛЬКО для независимых элементов.** Когда элементы независимы (каждая новая гвардия добавляется в конец списка, не пересекаясь с другими PR), конфликты текстовые (соседние строки) и разрешаются ребейзом. Когда N PR правят одну и ту же функцию (`scheduler.py`, PR #879), это настоящая конкуренция, и приём неприменим.

При переходе на новую схему для кода с правками обязателен транслятор, иначе старая форма остаётся в ребейзенных PR.

## Что не подтверждено

- Сложность транслятора для других схем миграции (в PR #897 решалась конкретно для гвардий); общая формула «как писать трансляторы» не разработана.
- Нужна ли специальная гвардия, проверяющая полноту миграции (чтобы ни один переезжаемый PR не остался в старой форме) — сейчас гвардия регистрации просто красит PR, не специфично про эпоху миграции.
