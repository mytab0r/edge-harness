# git grep -E: диалект регулярок и две ловушки PCRE

Замер 2026-09-22 (issue #1436), живым `git grep` на временном репозитории —
не по документации и не по памяти. Повод: гвардия «Класс закрыт» в теле PR
(`scripts/lib/mutation_claim.py`, ADR
[0026](../decisions/0026-verify-agent-claims-machine-check.md)) проверяет
заявление автора вызовом `git grep -nE <паттерн>`, то есть **POSIX ERE с
GNU-расширениями**, а пишут паттерны люди и агенты, привыкшие к Python `re`.

## Стенд

Временный репозиторий, по файлу на случай:

```
only-digit.txt      «5»
only-letter-d.txt   «d»
only-upper-d.txt    «D»
tags.txt            «<a><b>»
plain.txt           «xyz»
```

## Ловушка 1 — громкая: расширения группы

```
$ git grep -nE '(?:a|b)'
fatal: command line, '(?:a|b)': Invalid preceding regular expression   (rc=128)
$ git grep -nE '(?i)abc'   → то же
$ git grep -nE '(?=a)'     → то же
$ git grep -nE '(?!a)'     → то же
```

Падает честно, но текст не называет ни причину («это ERE, а не PCRE»), ни
лечение («убери `?:`»). Читатель, не знающий разницы диалектов, начинает
править экранирование — то есть гадать. Живой случай: PR #1434, прогон
35674153855, шаг `test`.

Замена: `(?:…)` → обычная `(…)`; у `(?i)`, `(?=`, `(?!` аналога в ERE нет,
паттерн надо переписать.

## Ловушка 2 — тихая, и она опаснее

`git grep -nE` НЕ падает, считает совпадения и отдаёт правдоподобное число,
которое ничего не значит. Гейт при этом «подтверждает» заявление, которого
автор не делал.

### `\d` матчит букву «d», а не цифру

```
$ git grep -nE '\d'   -- only-digit.txt only-letter-d.txt only-upper-d.txt
only-letter-d.txt:1:d          ← файл со строкой «5» НЕ совпал
$ git grep -nE '\D'   → only-upper-d.txt:1:D
$ git grep -nE '[0-9]' → only-digit.txt:1:5
```

Замена: `[0-9]` и `[^0-9]`.

### Ленивые квантификаторы молча жадны (или молча необязательны)

```
$ git grep -oE '<.*?>' -- tags.txt
tags.txt:<a><b>                ← PCRE вернул бы «<a>»
$ git grep -nE 'q+?xyz' -- plain.txt
plain.txt:1:xyz                ← ни одного «q» в строке нет
```

`?` после квантификатора прочитан как «предыдущее необязательно». Лениво в
ERE не выражается вовсе — переписывай через отрицающий класс: `<[^>]*>`
вместо `<.*?>`.

## Что работает как ожидается (НЕ чинить)

GNU-расширения `git grep -E` поддерживает, и отвергать их значило бы гнать
автора переписывать рабочий паттерн:

```
$ git grep -nE '\s'         → совпало по пробелам, не по букве «s»
$ git grep -nE '\w'         → класс словесных символов
$ git grep -nE '\bliteral\b'→ границы слова работают
$ git grep -nE 'a{2,3}'     → интервальный квантификатор
$ git grep -nE '[[:digit:]]'→ POSIX-класс
```

## Поправка к формулировке задачи #1436

Задача просила отвергать «как минимум `(?:`, `(?i)`, `(?=`, `(?!`, `\d`,
`\w`, `\s`, `\b`», поставив все восемь в один ряд как «падает». Замер
показал другое: `\w`/`\s`/`\b` работают правильно (отвергать нельзя), а
главная опасность — ленивые квантификаторы — в задаче не названа вовсе,
именно потому что они молчат.

## Носитель

`scripts/lib/mutation_claim.py::ere_pattern_problems`, вызывается из
`ClassClosedClaim.__post_init__` — объект с ловушкой физически не
существует, обойти проверку, собрав claim руками, нельзя. Тесты:
`scripts/lib/test_mutation_claim.py`, секция «#1436».

## Что не подтверждено

- Версия git на раннере GitHub Actions может отличаться от той, на которой
  снят замер; поведение `\d` как литерала — свойство POSIX ERE, а не версии,
  но конкретный текст `fatal: …` теоретически может измениться. Проверка
  ловушек от текста git не зависит: она разбирает сам паттерн.
- Полный список PCRE-конструктов, которые ERE принимает с другим смыслом, не
  составлялся — закрыты те, что реально встречаются в паттернах этого
  репозитория плюс найденные замером. Появится новый — он и попадёт сюда.
