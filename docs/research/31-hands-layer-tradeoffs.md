# «Руки» персистентно или эфемерно: развилка по деньгам (2026-09-09)

> Исследовано 2026-09-09, по прямому вопросу владельца: «Я думал, наш CF-харнес должен
> был использовать codespace, разве нет? Может мы наколхозили и половина вещей могла бы
> решаться иначе?». Смежное: [Cloudflare Free](20-cloudflare-free.md),
> [GitHub Actions](21-github-actions.md), [отвергнутые варианты](30-rejected-alternatives.md)
> (пункты 3, 4, 11, 17 — там же полные обоснования каждого варианта, здесь — только синтез
> и развилка для решения).

## TL;DR

- **Нет, Codespaces не решается иначе бесплатно.** У Codespaces свободный тариф —
  120 core-hours/мес на аккаунт, не безлимитен для public repo, как у Actions. Замер
  сегодняшней нагрузки одного `worker.yml` экстраполируется в ~609 core-hours/мес —
  в 10 раз больше свободного лимита. Переход на Codespaces при текущей нагрузке —
  это переход на ~$49/мес, а не на бесплатный слой. Подробности и источники —
  `30-rejected-alternatives.md`, пункт 17.
- **«Половина вещей решалась бы иначе» верно только для ОДНОГО механизма и только на
  ОДНОМ платном варианте.** Детектор зависания (issue 815) целиком существует потому, что
  Actions/Codespaces не дают DO прямого канала к исполнителю — DO вынуждена гадать о
  здоровье job'а по статусу GitHub API. Cloudflare Containers снимает эту причину
  корнем (DO вызывает контейнер напрямую, как RPC). Codespaces и self-hosted её НЕ снимают
  автоматически — там та же зависимость от косвенных сигналов, watchdog придётся строить
  заново под другую платформу.
- **Сброс бюджета (issue 817) и предохранитель диспатча (issue 120) не зависят от слоя
  исполнения вообще.** Это логика оркестратора («N подряд падений — пауза», «попытка во
  время аварии не считается»), и она нужна при любом исполнителе — Actions, Codespaces,
  Containers, self-hosted. Миграция инфраструктуры их не отменяет.
- **Одна часть боли — не архитектурное ограничение Actions, а политика, и её можно
  проверить без миграции куда-либо.** `worker.yml` держит один общий
  `concurrency: group: worker` (файл `.github/workflows/worker.yml`, строки 26-29)
  сознательно — комментарий называет причину: «два прогона соперничали бы за одни
  свободные задачи». Но `scripts/lib/claim_task.py` (issue 121) уже даёт атомарную аренду
  задачи через git-ref lock — то есть механизм, который должен закрывать ровно эту гонку,
  существует независимо от concurrency-группы. Не подтверждено, дублирует ли групповая
  блокировка защиту аренды, или несёт вторую причину (например, контроль суммарного
  $-бюджета LLM при нескольких параллельных попытках) — стоит уточнить у владельца ДО
  любой инфраструктурной миграции: если единственная причина — гонка за задачами, то
  параллельный воркер возможен на сегодняшней инфраструктуре бесплатно, без смены
  платформы вовсе (по образцу `hands.yml`, где `concurrency: group: hands-<task_id>`
  уже параллелит по task_id).

## Развилка для владельца — таблица по деньгам

## Как читать эту таблицу

**Единственная строка, которая была прямым белым пятном до этого исследования, —
Codespaces.** До вопроса владельца 2026-09-09 вариант не встречался в
`30-rejected-alternatives.md` вовсе (документ, который по правилу AGENTS.md обязан
называть все рассмотренные и отвергнутые варианты слоя «руки») — не потому что его
проверили и отвергли, а потому что его не рассматривали. Полный разбор — новый пункт 17
там же.

**Cloudflare Containers остаётся технически лучшим вариантом**, ровно как это уже было
зафиксировано в `30-rejected-alternatives.md` п.4 (2026-08-28) — это исследование
перепроверило цену ($5/мес актуальна, живой запрос к доке 2026-09-09) и не нашло причин
менять вывод. Разница с прошлым разом в том, что теперь есть конкретные живые инциденты
этой недели (815, 817, 120), которые Containers снимает корнем, а не патчем — раньше
довод был умозрительным («технически лучше»), теперь он предметный («вот эти issue
физически не могли бы возникнуть в этой форме»).

**Self-hosted runner — вариант с наименьшей правкой кода**, потому что он не меняет
протокол диспетчеризации (`repository_dispatch`/`workflow_dispatch` остаются теми же
REST-вызовами, меняется только метка `runs-on:`). Это делает его дешёвым для эксперимента
относительно объёма работы, но не отменяет: (а) нужно содержать машину, (б) нужно
аккуратно развести self-hosted (только наши dispatch-задачи) и GitHub-hosted (всё, что
трогает недоверенный PR-код), иначе ровно то предупреждение GitHub про публичные
репозитории материализуется.

## Что стало бы ненужным — по механизмам, а не вообще

| Механизм | Actions (статус-кво) | Codespaces | CF Containers | Self-hosted |
|---|---|---|---|---|
| Детектор зависшего рана (issue 815: порог длительности, отмена + возврат задачи в пул) | Нужен — единственный сигнал есть/нет прогресса — длительность `in_progress` по GH API | Нужен в другой форме — Codespaces не даёт DO более дешёвого сигнала здоровья, чем Actions; watchdog придётся писать заново под lifecycle REST Codespaces | Не нужен в текущей форме — DO вызывает контейнер как RPC, видит ответ/таймаут синхронно, вопрос «жив ли ещё исполнитель» перестаёт быть отдельной задачей поверх стороннего API | Нужен, но НАШИМИ средствами (systemd watchdog, health-check процесса) — не хуже и не лучше Actions по конструкции, просто наш периметр ответственности |
| Сброс бюджета авто-ребейза после аварии (issue 817) | Нужен | Нужен (не связан с платформой) | Нужен (не связан с платформой) | Нужен (не связан с платформой) |
| Предохранитель диспатча после серии падений (issue 120) | Нужен как policy контроля качества/провайдера | Нужен | Нужен (сама механика «череда падений — сигнал о задаче/провайдере, а не об инфраструктуре» одинакова везде) | Нужен |
| Один активный воркер (`concurrency: group: worker`) | Сегодня — да, по конфигу; под вопросом, обязателен ли он архитектурно (см. TL;DR про `claim_task.py`) | Снимается по построению (Codespaces — независимые ресурсы, не общий Actions-слот), но упирается в ещё более тесный денежный потолок — параллелить нечем не по политике, а по деньгам | Снимается по построению — DO может поднять N контейнеров, каждый со своим адресом | Снимается по построению — можно зарегистрировать N self-hosted раннеров |
| Свежий checkout на каждый прогон, нет персистентного worktree | Дано платформой (каждый job — чистая машина) — не проблема, а следствие модели, которую сознательно выбрали (ADR 0001) | Персистентный диск между stop/start — придётся МЕНЯТЬ существующий дизайн (task-branch/worktree сейчас предполагает «клонируй заново»), не только выигрыш | Диск ephemeral — то же ограничение, что у Actions, только явно задокументированная засада («fresh disk on wake»), не сюрприз | Персистентный диск, наш — то же преимущество, что у Codespaces, без денежного потолка |

## Рекомендация

Технической необходимости мигрировать нет — статус-кво (push-модель на Actions)
работает, боль этой недели (issues 815, 817, 120) уже чинится точечно и без денег, и это
правильный первый шаг вне зависимости от решения по инфраструктуре: три механизма нужны
на любой платформе.

Развилка — по готовности платить, а не по технике:

- **$0/мес (без изменений).** Остаться на Actions. Проверить у владельца гипотезу про
  `concurrency: group: worker` — если единственная причина серилизации это гонка за
  задачами пула, а не $-контроль скорости расхода LLM-бюджета, параллельный воркер
  возможен бесплатно уже сегодня, тем же приёмом, что `hands.yml` (concurrency-группа по
  task_id вместо общей). Это не отменяет ни issue 815 (детектор зависания), ни 817/120 —
  они остаются нужны при любом числе параллельных воркеров.
- **$5/мес.** Cloudflare Containers/Sandbox SDK. Единственный вариант, снимающий issue
  815 корнем, а не патчем, и единственный без ToS-риска вообще. Цена уже была принята
  владельцем как условие возврата к п.4 «Согласимся на $5/мес» (`30-rejected-alternatives.md`).
  Самая большая разовая перестройка кода из всех вариантов, но форма перестройки уже
  намечена (см. таблицу выше и исходный п.4).
- **Около $5-9/мес плюс время на администрирование.** Self-hosted runner. Наименьшая
  правка кода, единственный вариант, легально допускающий классический долгоживущий
  процесс (снимает ToS-часть отказа от WS-туннеля из п.3), но добавляет постоянную
  операционную ответственность (патчинг, security-периметр для публичного репозитория) и
  требует аккуратного разделения self-hosted/GitHub-hosted раннеров по типу задачи.
- **Codespaces — не рекомендуется ни при каком бюджете из рассмотренных.** При нынешней
  нагрузке дороже Containers примерно в 10 раз (~$49/мес против $5), не убирает ни один
  из трёх живых механизмов боли этой сессии сам по себе, и требует построить с нуля
  API «выполнить задачу», которого платформа не даёт. Возвращаться к варианту стоит,
  только если появится причина ценить именно персистентный диск выше всего остального
  (см. условие возврата в п.17 `30-rejected-alternatives.md`) — сегодня такой причины нет.

## Что не подтверждено

1. Причина `concurrency: group: worker` — гонка за задачами или контроль скорости
   расхода LLM-бюджета (или обе). Комментарий в `worker.yml` называет только первую.
   `claim_task.py` (issue 121, git-ref lock) уже атомарно защищает от гонки за задачами
   независимо от concurrency-группы Actions — если это единственная причина, снятие
   группы (или сужение её до per-task, по образцу `hands.yml`) даёт параллельный воркер
   бесплатно уже сегодня. Не проверено намеренно (задача — только дизайн/оценка, без
   изменения кода) — проверка гипотезы и решение за владельцем.
2. Фактический перерасход Cloudflare Containers сверх включённого usage $5/мес при
   нынешней нагрузке репозитория. `30-rejected-alternatives.md` п.4 даёт только структуру
   тарифа (биллинг за каждые 10мс активности); проекция в доллары при текущем профиле
   `worker.yml`/`hands.yml` не сделана — потребовала бы либо живого прогона на
   Containers, либо оценки по CPU-профилю DSH headless, которой нет.
3. Точное время cold-start/resume для Codespaces (создание нового vs возобновление
   остановленного) — официальная документация числа не даёт (см. п.17 в
   `30-rejected-alternatives.md`).
4. Держится ли ограничение self-hosted runner («should almost never be used for public
   repositories») именно для узкого workflow, изолированного от событий PR из форков.
   Формулировка GitHub — общая рекомендация, не различает по типу workflow; вывод «можно
   безопасно, если PR CI остаётся на GitHub-hosted» — наша логика из механики угрозы
   (untrusted code на раннере), не прямая цитата под этот частный случай.
5. Актуальная цена VPS (Hetzner CX22 или аналог) на момент реального решения —
   `30-rejected-alternatives.md` п.3 уже фиксирует расхождение источников (историческая
   цена запуска против роста в источниках 2026 года), пересмотреть перед фактическим
   выбором self-hosted.
