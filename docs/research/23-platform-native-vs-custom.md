# Что взять вместо своего: своё написанное vs готовое от платформы

> Исследовано 2026-09-05. Смежное: [GitHub Actions](21-github-actions.md) и
> [Cloudflare Free](20-cloudflare-free.md) — там факт-аудит («используем / не
> используем / недоступно»); здесь — разбор именно тех строк, где мы написали своё,
> хотя платформа предлагает готовое, с обоснованием взять/не брать по каждому пункту.

Повод: месяц своей реализации очереди слияний (`scripts/orchestra/scheduler.py`)
при не заданном вопросе «а нет ли нативного пути». Ответ по конкретно этому пункту
уже нашёлся отдельной задачей (#339) — нативная GitHub Merge Queue **недоступна**
на этом репозитории (владение пользователем, не организацией; см.
[ADR 0013](../decisions/0013-native-merge-queue-not-available.md)). Значит своя
очередь обоснована ограничением платформы,
а не ленью проверить. Ниже — тот же вопрос по остальным местам, где своё решение
дублирует то, что теоретически могла бы дать платформа.

## 1. Merge Queue → своя очередь: обосновано ограничением, не берём

**У нас.** `merge_queue()`/`merge_loop()` в `scheduler.py`: триггер событийный
(`labeled` и другие события PR в `orchestra.yml`), `*/15` — только страховочный
прогон на случай пропущенного события (ADR 0012/#330). Проверка готовности PR по
меткам (`review:ok`+`ai:ok`), слияние по одному через `PUT .../pulls/{n}/merge`,
потом выборочный `update-branch` остальных (#252).

**Платформа предлагает.** Ruleset-правило `merge_queue` — серийное слияние с
ре-тестом каждого PR против актуального main, без ручного опроса и без гонок
update-branch/ai-review, которые и породили #208/#252/#189.

**Вердикт.** Не берём — **недоступно**, не «не выбрали». Условие невыполнимо без
смены владельца репозитория с пользовательского аккаунта на организацию (см. ADR
0013, «Вернуться, если»). Тройные грабли своей реализации (#208, #252, #189)
остаются актуальной проблемой независимо от этого вывода — лечить их доработкой
`scheduler.py`, не ожиданием смены владения.

## 2. Метки-вердикты (`review:ok`/`ai:ok`) → Commit Status API: канал статусов уже взят (#345), остаток — required checks + auto-merge

**У нас.** Два гейта (`pr-review.yml`, `ai-review.yml`) выносят вердикт
(`review:ok`/`review:changes-requested`, `ai:ok`/`ai:changes-requested`/`ai:failed`)
и публикуют его **двумя каналами** (#345/#346): меткой через `gh issue edit` и
[Commit Status API](https://docs.github.com/en/rest/commits/statuses)
(`POST /repos/{owner}/{repo}/statuses/{sha}`, контексты `harness/review` и
`harness/ai-review`, `scripts/lib/review_labels.py::post_commit_status`, право
`statuses: write` в обоих workflow; задокументировано в
[INFRA-GH](../agents/INFRA-GH.md)). Статус вычисляется из **той же переменной
вердикта**, что и метка, — второго источника истины нет; история ретраев
остаётся в комментариях (маркер `AI_REVIEW_RETRY_MARKER`, #196/#208), статус её
не дублирует. Но **принятие решения о слиянии пока живёт только в метках**:
гейт целиком в `scripts/lib/review_labels.py::merge_label_gate` (вызывается из
`scheduler.py`), проверяется событийно при каждом проходе `merge_loop` (см. §1).
GitHub при решении «можно ли смержить» статусы не спрашивает: в
`required_status_checks.contexts` по-прежнему `["test","contract"]` (живой
запрос 2026-09-07), `harness/*` туда не включены.

**Платформа предлагает.** Второй шаг того же Commit Status API-пути: добавить
оба контекста в `required_status_checks.contexts` branch protection — тогда
нативное правило «требуй свежий статус на каждый новый коммит» само закроет
класс «протухший вердикт после нового пуша» (#291/#334 в другом виде), а
`allow_auto_merge` взял бы на себя саму механику слияния: не нужен был бы прогон
`scheduler.py` вовсе, слияние происходило бы силами самого GitHub, в момент,
когда последний статус становится `success`.

**Вердикт.** Канал статусов **взят** (#345) — реализована именно та оговорка
этого документа прежней редакции («придётся оставить комментарий отдельно и
статус отдельно»); `merge_label_gate` остаётся единственным местом решения до
переключения, метки не убираются. Остаток кандидата — **отдельная задача**, не
одностраничная замена, потому что:
- публикации статусов мало: надо добавить `harness/review`+`harness/ai-review`
  в `required_status_checks.contexts` — это правка защиты ветки, у владельца,
  вручную, после подтверждения живым прогоном статусного канала (в проде с
  #345);
- `allow_auto_merge` **выключен владельцем**: живой запрос 2026-09-07 →
  `false` (на 2026-09-05 был `true`). Настройки репозитория не версионируются —
  комментарии кода #345 «уже включён» от этого уже разошлись с живым значением.
  Включать его осмысленно только **после** required contexts, иначе он сливал бы
  PR сразу после `test`+`contract`, до вердиктов;
- гонки без очереди никуда не деваются: auto-merge может смержить два готовых PR
  почти одновременно, и третий разъедется с main до своего `update-branch` (#252)
  — тот класс, который решала бы Merge Queue (недоступна, §1). Оценка этого
  риска — ядро отдельной задачи, не побочная деталь.

Это самая многообещающая находка «взять вместо своего» в этом аудите — её
остаток реально мог бы убрать целый класс гонок (#208, #252). Записана как
кандидат, не как решение: реализация — отдельная задача с отдельным критерием
готовности.

## 3. Пульс из Durable Object (`alarm()`) → Cron Triggers Cloudflare: alarm остаётся основным, Cron взят страховкой (#693)

**У нас.** `Harness.alarm()` перезакладывает следующий будильник, затем дёргает
`workflow_dispatch` оркестратора и проверяет отставание морды dsh-edge от npm —
весь пульс работает **внутри** конкретного DO-инстанса, с прямым доступом к его
`ctx.storage` (курсоры, счётчики, состояние отставания). С 2026-09-08 (решение по инциденту #693 от 2026-09-07) рядом стоит второй канал:
`"triggers": { "crons": ["*/5 * * * *"] }` в `wrangler.jsonc` (#693/#696) — Cron Trigger,
раз в 5 минут дёргающий тот же DO поверх воркера.

**Платформа предлагает.** Cron Trigger на воркер — тоже бесплатно на Free (5
триггеров/аккаунт, минимум раз в минуту), тоже «alarm = 1 request» по экономике.

**Вердикт.** Исходный вердикт этого разбора (2026-09-05) был «не берём»: Cron Trigger
будит **воркер**, не конкретный DO-объект — у воркера нет своего состояния между тиками
(это и есть причина, по которой состояние живёт в DO, а не в воркере, см.
[ADR 0002](../decisions/0002-loop-in-runner-not-do.md) по аналогичной логике для
агент-цикла), и cron-хендлеру понадобился бы лишний `fetch` к DO ради того же
результата, который `alarm()` даёт одним вызовом. Инцидент #693 (2026-09-07) вскрыл
класс отказа, где этот расчёт не работает: подвисший `alarm()` **без внешнего трафика
не самовосстанавливается вовсе** — не хватает как раз независимого от трафика источника
тактов, каким является Cron Trigger. Поэтому решением #693/#696 Cron взят — но как
**страховка, не замена**: `alarm()` остаётся основным механизмом пульса (ближе к
данным, без лишнего прыжка), cron добавляет гарантию «наихудшее время починки ≤25
минут» независимо от трафика (обоснование числом — в комментарии `wrangler.jsonc`).
Лишний прыжок (воркер → DO) принят сознательно, только для страховочного тика.

## 4. Аренда задачи через git-ref-замок → альтернатив в API нет: уже правильно взято

**У нас.** [ADR 0006](../decisions/0006-task-lease-git-ref-lock.md): аренда задачи —
атомарное обновление git-ref (`refs/...`) с проверкой ожидаемого текущего SHA
(git as compare-and-swap), а не отдельная база блокировок.

**Платформа предлагает.** У GitHub нет отдельного API «распределённой блокировки»
уровня issue/PR — единственный атомарный примитив с проверкой текущего состояния,
который тут действительно есть, это сам Git Data API (`PATCH /git/refs/{ref}` с
проверкой текущего SHA, откуда и растёт идея git-ref-замка). Issue-assignment
(`assignees`) — судя по устройству REST API, не атомарен относительно гонки двух
воркеров: два запроса `add-assignee` подряд должны оба вернуть успех, второй не
узнает о первом (**не подтверждено** — в доках атомарность не оговаривается ни в
одну сторону, живого теста не было; см. «Что не подтверждено» ниже).

**Вердикт.** Здесь замена не нужна — то, что уже сделано (git-ref как CAS-примитив),
**и есть** взятая из платформы возможность, не самопальная поверх неё. Отмечено для
полноты, чтобы этот пункт не всплыл заново как «а вдруг мы придумали своё колесо».

## 5. CSV кампании задержки в git-ветке → R2: не сейчас, объём не оправдывает

**У нас.** `dispatch-latency-probe.yml` пишет строки CSV прямо в git-ветку
`data/dispatch-latency-tail` (см. [research/21](21-github-actions.md)) — по одной
строке на доставленный тик.

**Платформа предлагает.** R2: 10 GB бесплатно, нулевой egress, не растит историю
git-репозитория.

**Вердикт.** Не берём сейчас. Замер кампании 2026-08-31→2026-09-04 — **31 строка**
за 116 часов (см. research/21, доставка `schedule` ~7%). При таком объёме миграция
на R2 ничего не выигрывает и добавляет новую зависимость (bucket, binding, права
записи из job'а под другим токеном) ради экономии байт, которых нет. Пересмотреть,
если кампания станет непрерывной и объём вырастет на порядки — тогда рост git-истории
репозитория (а не только CI job) станет реальной ценой.

## Что не подтверждено

| Утверждение | Статус |
|---|---|
| Гонка issue-assignment: два запроса `add-assignee` подряд оба вернут успех, второй не узнает о первом (§4) | **не подтверждено**: [REST reference по assignees](https://docs.github.com/en/rest/issues/assignees) атомарность относительно параллельных запросов не оговаривает ни в одну сторону; живого теста с двумя параллельными `add-assignee` на этом репозитории не делалось. Вердикт §4 на этом утверждении не держится: git-ref-замок выбран потому, что он **есть** нативный CAS-примитив, а не потому, что assignment сломан — если тест когда-нибудь покажет обратное, вывод §4 не меняется |
