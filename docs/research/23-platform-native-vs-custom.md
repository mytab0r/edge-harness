# Что взять вместо своего: своё написанное vs готовое от платформы

> Исследовано 2026-09-05. Смежное: [GitHub Actions](21-github-actions.md) и
> [Cloudflare Free](20-cloudflare-free.md) — там факт-аудит («используем / не
> используем / недоступно»); здесь — разбор именно тех строк, где мы написали своё,
> хотя платформа предлагает готовое, с обоснованием взять/не брать по каждому пункту.

Повод: месяц своей реализации очереди слияний (`scripts/orchestra/scheduler.py`)
при не заданном вопросе «а нет ли нативного пути». Ответ по конкретно этому пункту
уже нашёлся отдельной задачей (#339) — нативная GitHub Merge Queue **недоступна**
на этом репозитории (владение пользователем, не организацией; ADR — задача #340,
файловая ссылка не даётся здесь, чтобы не разойтись с фактическим номером —
`0012` в главной ветке уже занят `0012-orchestra-event-trigger-merge-loop.md`).
Значит своя очередь обоснована ограничением платформы,
а не ленью проверить. Ниже — тот же вопрос по остальным местам, где своё решение
дублирует то, что теоретически могла бы дать платформа.

## 1. Merge Queue → своя очередь: обосновано ограничением, не берём

**У нас.** `merge_queue()`/`merge_loop()` в `scheduler.py`: опрос раз в 15 минут,
проверка готовности PR по меткам (`review:ok`+`ai:ok`), слияние по одному через
`PUT .../pulls/{n}/merge`, потом выборочный `update-branch` остальных (#252).

**Платформа предлагает.** Ruleset-правило `merge_queue` — серийное слияние с
ре-тестом каждого PR против актуального main, без ручного опроса и без гонок
update-branch/ai-review, которые и породили #208/#252/#189.

**Вердикт.** Не берём — **недоступно**, не «не выбрали». Условие невыполнимо без
смены владельца репозитория с пользовательского аккаунта на организацию (см. ADR
0012, «Вернуться, если»). Тройные грабли своей реализации (#208, #252, #189)
остаются актуальной проблемой независимо от этого вывода — лечить их доработкой
`scheduler.py`, не ожиданием смены владения.

## 2. Метки-вердикты (`review:ok`/`ai:ok`) → Commit Status API: не берём сейчас, но это реальный кандидат

**У нас.** Два гейта (`pr-review.yml`, `ai-review.yml`) выставляют **метки**
(`review:ok`/`review:changes-requested`, `ai:ok`/`ai:changes-requested`/`ai:failed`)
через `gh issue edit --add-label`. Метки — не required status checks: GitHub не
видит их при решении «можно ли смержить». Гейт по ним живёт целиком в
`scripts/lib/review_labels.py::merge_label_gate`, опрашивается раз в 15 минут.

**Платформа предлагает.** [Commit Status API](https://docs.github.com/en/rest/commits/statuses)
(`POST /repos/{owner}/{repo}/statuses/{sha}`) создаёт **статус с произвольным
`context`** (`state: success|failure|pending`) на конкретный SHA — без GitHub App,
достаточно PAT со скоупом `repo:status` (у нас уже есть `GH_PIPELINE_PAT` c `repo`).
Такой статус **можно** добавить в `required_status_checks.contexts` branch
protection — тогда GitHub нативно не даст смержить PR без обоих вердиктов, и
**включённый** (но сейчас не используемый) `allow_auto_merge` смог бы взять на себя
саму механику мержа: не нужен был бы опрос `scheduler.py` раз в 15 минут вовсе,
слияние происходило бы событийно, в момент, когда последний статус становится
`success`.

**Вердикт.** **Не берём в рамках этой задачи — это отдельная задача**, не
одностраничная замена. Что нужно решить, прежде чем менять:
- обе метки заводятся сейчас с прозой и историей ретраев (маркер-комментарий
  `AI_REVIEW_RETRY_MARKER`, #196/#208) — статус API не хранит эту историю сам,
  придётся оставить комментарий отдельно и статус отдельно;
- required status check **не снимается** обратно так же просто, как метка —
  правило GitHub «требуй свежий статус на каждый новый коммит» само по себе решает
  проблему «протухшего вердикта после нового пуша» (issue #291/#334 в другом виде),
  но эту логику надо построить заново, не унаследовать от текущей;
- `allow_auto_merge` слил бы PR **сразу**, как только оба статуса зелёные — это
  убирает наш текущий шаг «выборочный `update-branch` остальных открытых PR
  после мержа» (#252) как отдельную ручную операцию, но нужно продумать, не
  начнёт ли параллельный мерж нескольких готовых PR устраивать те же гонки,
  которые решала бы Merge Queue (которой у нас нет) — то есть при заимствовании
  auto-merge без queue остаётся риск двух PR, смержившихся почти одновременно и
  разъехавшихся с main до того, как поспеет `update-branch` третьего.

Это самая многообещающая находка «взять вместо своего» в этом аудите — она реально
могла бы убрать целый класс гонок (#208, #252). Записана как кандидат, не как
решение: реализация — отдельная задача с отдельным критерием готовности.

## 3. Пульс из Durable Object (`alarm()`) → Cron Triggers Cloudflare: не берём, обоснованно

**У нас.** `Harness.alarm()` перезакладывает следующий будильник, затем дёргает
`workflow_dispatch` оркестратора и проверяет отставание морды dsh-edge от npm —
весь пульс работает **внутри** конкретного DO-инстанса, с прямым доступом к его
`ctx.storage` (курсоры, счётчики, состояние отставания).

**Платформа предлагает.** Cron Trigger на воркер — тоже бесплатно на Free (5
триггеров/аккаунт, минимум раз в минуту), тоже «alarm = 1 request» по экономике.

**Вердикт.** Не берём. Cron Trigger будит **воркер**, не конкретный DO-объект — у
воркера нет своего состояния между тиками (это и есть причина, по которой состояние
живёт в DO, а не в воркере, см. [ADR 0002](../decisions/0002-loop-in-runner-not-do.md)
по аналогичной логике для агент-цикла). Чтобы прочитать/обновить состояние пульса,
cron-хендлер всё равно обязан был бы сделать `fetch` к тому же DO-инстансу — то есть
Cron Trigger добавил бы лишний прыжок (воркер → DO) ради того же результата, который
`alarm()` даёт одним вызовом. Разница не в деньгах и не в лимитах — в лишнем шаге
без выигрыша.

## 4. Аренда задачи через git-ref-замок → альтернатив в API нет: уже правильно взято

**У нас.** [ADR 0006](../decisions/0006-task-lease-git-ref-lock.md): аренда задачи —
атомарное обновление git-ref (`refs/...`) с проверкой ожидаемого текущего SHA
(git as compare-and-swap), а не отдельная база блокировок.

**Платформа предлагает.** У GitHub нет отдельного API «распределённой блокировки»
уровня issue/PR — единственный атомарный примитив с проверкой текущего состояния,
который тут действительно есть, это сам Git Data API (`PATCH /git/refs/{ref}` с
проверкой текущего SHA, откуда и растёт идея git-ref-замка). Issue-assignment
(`assignees`) — не атомарен относительно гонки двух воркеров: два запроса
`add-assignee` подряд оба вернут успех, второй не узнает о первом.

**Вердикт.** Здесь замена не нужна — то, что уже сделано (git-ref как CAS-примитив),
**и есть** взятая из платформы возможность, не самопальная поверх неё. Отмечено для
полноты, чтобы этот пункт не всплыл заново как «а вдруг мы придумали своё колесо».

## 5. CSV кампании задержки в git-ветке → R2: не сейчас, объём не оправдывает

**У нас.** `dispatch-latency-probe.yml` пишет строки CSV прямо в git-ветку
`data/dispatch-latency-tail` (см. [research/21](21-github-actions.md)) — по одной
строке на доставленный тик.

**Платформа предлагает.** R2: 10 GB бесплатно, нулевой egress, не растит историю
git-репозитория.

**Вердикт.** Не берём сейчас. Замер кампании 2026-08-31→2026-09-04 — **31 строка**
за 116 часов (см. research/21, доставка `schedule` ~7%). При таком объёме миграция
на R2 ничего не выигрывает и добавляет новую зависимость (bucket, binding, права
записи из job'а под другим токеном) ради экономии байт, которых нет. Пересмотреть,
если кампания станет непрерывной и объём вырастет на порядки — тогда рост git-истории
репозитория (а не только CI job) станет реальной ценой.
