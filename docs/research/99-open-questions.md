**✅/⚠️ Сбрасывается ли CPU-бюджет на Free до 10 ms — для этого аккаунта: нет.**
Пробник (отдельный воркер, синхронный цикл фиксированной длины): успешные invocation
с CPU **порядка секунды** (P99 аналитики — 2.0 с), 1102 «exceeded» приходит только
на больших величинах. Если этот аккаунт на Free — документная формулировка «10 ms
на invocation» к реальности не применяется в лоб. **Оговорка:** прочитать план аккаунта
через API не вышло (`subscriptions` вернул пусто) — сверить план в дашборде и перенести
вывод в [20-cloudflare-free.md](20-cloudflare-free.md). Попутно поймано поведение
workerd: `Date.now()`/`performance.now()` **не двигаются во время синхронного кода** —
цикл «по времени» в воркере бесконечен; цикли только по счётчику.
См. [22-cf-testing-toolchain.md](22-cf-testing-toolchain.md).

держится, переживает гибернацию объекта и получает broadcast из других invocation'ов

## Cloudflare

**Сброс CPU-бюджета в Durable Object на бесплатном плане.** Документировано, что каждое
входящее сообщение сбрасывает доступное CPU-время, и что величина берётся из лимита плана.
Прямой фразы «на Free сбрасывается до 10 ms» нет — это вывод из связки двух страниц.
*Как проверить:* задеплоить DO, скормить ему нагрузку с известной стоимостью CPU, снять
метрики. — **✅ Измерено 2026-08-28: см. блок «Измерено» выше.**

**Работает ли `limits.cpu_ms` на Free.** Параметр документирован как способ поднять потолок
с 30 секунд; разрешения повышать лимит на бесплатном плане доки не дают, но и запрета не
формулируют.

**Доступен ли WebSocket Hibernation API на Free.** Запрета нет, явного разрешения тоже.
Косвенная улика: dsh-edge заявляет, что direct-режим работает на Workers Free, а он
использует `ctx.acceptWebSocket`. — **✅ Подтверждено живым деплоем 2026-08-28, см.
блок «Измерено» выше.**

**Точное значение idle-timeout, после которого Cloudflare рвёт WebSocket.** Доки говорят
«when no data is transmitted … for a period of time», число не называют. Кастомный timeout —
только Enterprise. *Практический вывод:* держать client-side heartbeat в любом случае.

**Лимит числа одновременных WebSocket именно для Free.** Известен лимит на объект (32 768),
плановой разбивки нет.

**Storage на один Durable Object: 10 GB или 1 GB.** Документация противоречит сама себе —
таблица лимитов даёт 10 GB без разделения планов, FAQ пишет «1 GB on the Free plan».
*Пока считаем 1 GB.*

**Нужна ли банковская карта для активации R2.** В доках не сказано.

## GitHub

**Задержка между `repository_dispatch` и стартом job'а.** Не документирована вообще: ни
SLA, ни типичное значение. Единственная косвенная зацепка — для `schedule` GitHub признаёт,
что событие «can be delayed during periods of high loads».
*Эмпирика третьих лиц* (не GitHub, порядок величины): около 6 секунд при попадании в тёплый
пул, около 25 при холодном провижининге. В community-обсуждениях есть жалобы на зависания в
очереди на часы. Хвост распределения тяжёлый и **ничем не ограничен**: 24-часовая отмена по
очереди относится к self-hosted раннерам, для GitHub-hosted аналога в документации нет —
только 35 дней на весь workflow run.
*Это главный практический риск архитектуры.* Замерить на своём репозитории и записать сюда
реальное распределение.

**Разрешены ли долгие исходящие соединения из job'а технически.** Ни разрешения, ни запрета
в доках нет — не подтверждено в обе стороны. Вопрос отчасти академический: схема с
постоянным соединением отвергнута по Terms, а не по технике.

**Платный ли приватный форк публичного репозитория.** Бесплатность привязана к видимости
репозитория, в котором идёт run; отдельной формулировки для этого случая нет.
