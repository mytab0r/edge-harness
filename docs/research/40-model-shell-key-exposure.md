# Утечка ключа провайдера через model-shell и её закрытие

> Замерено живым прогоном из model-shell 2026-09-05 (задача #140, раннер
> GitHub Actions `ubuntu-latest`, ядро 6.17.0-1022-azure, docker 28.0.4,
> DSH 0.1.1-rc.2) и повторено/дополнено 2026-09-10 (замеры 2а и 5, включая
> инструментированный прогон точной пары в repo-ci). Смежное:
> [архитектура DSH](10-dsh-architecture.md),
> [отвергнутые варианты](30-rejected-alternatives.md).

## TL;DR

- **Вектор из названия задачи (чтение `/proc/<pid-dsh>/environ` напрямую) —
  измерен в обе стороны, итог зависит от конфигурации.** В старой
  конфигурации (dsh — прямой потомок job-цепочки раннера) чтение из
  model-shell не подтверждено (замеры 2 и 2а) — но механизм запрета не
  атрибутирован, и опираться на него нельзя. В новой конфигурации (изоляция:
  dsh через sudo-exec, ключ через env_keep) вектор **ПОДТВЕРДИЛСЯ** (замер 5):
  same-uid потомок читает environ родителя, и env_keep доставляет ключ в этот
  читаемый environ — READABLE, `DEEPSEEK_API_KEY` present-nonempty, ровно
  продакшн exec-цепочка (launcher → timeout → dsh), bash- и node-образы.
- **Тот же класс подтвердился через docker-сокет** (замер 3; сокет доступен
  model-shell на GitHub-раннерах по умолчанию): контейнер `--pid=host
  --cap-add SYS_PTRACE --security-opt apparmor=unconfined` читает environ
  **любого** процесса хоста, включая dsh. Заявка «агент ключ не видит» без
  изоляции неверна.
- **Закрытие (реализовано) — ключ вообще не живёт в env dsh** («передача
  ключа только адаптеру», вторая ветка критерия #140): РЕАЛЬНЫЙ
  base_url+ключ держит локальный прокси в домене транспорта
  (`dsh_provider_proxy_start` в `scripts/lib/dsh-ci.sh`, врезан во все три
  обёртки: worker / hands / ai-review); dsh получает
  `DEEPSEEK_BASE_URL=http://127.0.0.1:<порт>` и подменный ключ через
  env_keep; `dsh_agent_run` подменяет значения при каждом запуске домена
  агента и синхронизирует файл состояния прокси — совместимо с цепочкой
  провайдеров (#727). Прочитав environ dsh, модель получает только подмену;
  environ самого прокси — другой uid, его чтение запрещено ядром
  (гарантия, а не свойство среды; доказывается prepare 8б на каждом прогоне).
  Вторая ветка — uid-изоляция из критерия: dsh идёт под выделенным юзером
  без группы docker (`dsh_agent_isolation_prepare`): docker-эскейп закрыт
  uid-барьером, environ транспорта (другой uid) нечитаем.
- **Принятая граница**: GitHub PAT владельца в `~/.config/gh/hosts.yml`
  читается моделью **по построению** — единственный канал gh-авторизации,
  переживший env-вырезание (решение осознанное, см. «Остаточный риск»).
- **Дополнительно замерено**: на всём дереве model-shell стоит
  `NoNewPrivs: 1` (замер 2а) — эскалация sudo/setuid из model-shell
  невозможна физически.

## Замер

### 1. Env-вырезание DSH работает (подтверждение старого факта)

`env` model-shell: ни одного имени с подстрокой `KEY`/`TOKEN`/`SECRET`;
`DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL` при этом на месте. Вырезание
`*KEY*/*TOKEN*/*SECRET*` из model-shell вызовов — подтверждено (совпадает с
живым прогоном 2026-08-30 в [10-dsh-architecture.md](10-dsh-architecture.md)).

### 2. Прямой `/proc/<pid-dsh>/environ` — НЕ подтвердился, механизм НЕ атрибутирован

| Что читали | Результат |
| --- | --- |
| environ собственного потомка model-shell | **читается** (канал работает в принципе) |
| environ dsh (родитель model-shell), `timeout`, bash-обёрток, `Runner.Worker` | **Permission denied** |

Первая версия объяснения — yama `ptrace_scope=1` («environ доступен только
потомкам чтеца») — контрольными экспериментами на том же ядре
(6.17.0-1022-azure, ptrace_scope=1) **опровергнута**: same-uid не-потомок
(orphan, setsid-сиблинг) environ читает. Полная эмпирическая матрица этой
среды (все процессы CoreDumping: 0 — свойство цепочки job сохраняется через
exec):

| Читали | Результат |
| --- | --- |
| model-shell → environ dsh (родитель, node) | **DENIED** |
| model-shell → environ dsh (дядя, повтор) | **DENIED** |
| дочерний bash → environ родителя-башика | READABLE |
| родитель → environ потомка | READABLE |
| племянник → environ дяди (некровный same-uid) | **DENIED** |
| дочерний процесс → environ родителя после sudo-exec (CI-пробник) | READABLE |

Механизм, объясняющий ВСЕ строки сразу, не найден (dumpable по отдельности не
объясняет: parent→child читается при том же CoreDumping: 0). Честная
формулировка: «ребро model-shell→dsh в среде раннера закрыто — измеренный факт;
правило закрытия не известно; на него нельзя опираться как на гарантию».
Изоляция #140 на него не опирается; prepare зондирует прокс-пару в каждом
прогоне и печатает результат в лог (`::note::`) — тормозом не является, потому
что свойство среды из репо не настраивается (правило «тормоз без газа»).

### 2а. Повторный якорь 2026-09-10 (worker run 34498185823, старая конфигурация)

Замер 2 повторен живьём из model-shell очередного worker-прогона (до мержа
изоляции — та же job-цепочка): вырезание `*KEY*` подтверждено
(`DEEPSEEK_API_KEY` в env model-shell отсутствует, `DEEPSEEK_BASE_URL`/
`DEEPSEEK_MODEL` на месте); environ dsh (прямой родитель model-shell),
`timeout` и bash-обёртки транспорта — **DENIED**, включая same-uid чтение
environ самого `task.sh`. Строки замера 2 воспроизведены.

Новый измеренный факт: **на всём дереве model-shell стоит `NoNewPrivs: 1`**
(`/proc/self/status`; `sudo -n` отказывает с «The "no new privileges" flag is
set» — обход через sudo/setuid-бинарники невозможен физически). Кто ставит
флаг (исполнение shell-инструмента в dsh) — до системного вызова не
атрибутировано, свойство замерено на dsh 0.1.1-rc.2. Следствие для threat-
модели: из model-shell недостижимы ни sudo-каналы транспорта, ни повышение
привилегий вообще — но это тоже свойство конфигурации dsh, не гарантия
изоляции ключа (см. «Остаточный риск»).

Контрольный эксперимент в контейнере (ubuntu:24.04, `--security-opt
apparmor=unconfined`, то же ядро, ptrace_scope=1): та же sudo-exec цепочка с
env_keep даёт READABLE + значение доставлено — ядерная семантика exec-цепочки
сама по себе ребро НЕ закрывает; DENIED старой конфигурации — свойство
окружения job-цепочки раннера, а не ядра.

### 3. Docker-эскейп — подтвердился

model-shell входит в группу `docker` (дефолт образа раннера), сокет
`/var/run/docker.sock` доступен. Прогон из model-shell:

| Флаги контейнера | Чтение environ dsh |
| --- | --- |
| `--pid=host` (дефолтные caps, apparmor) | denied |
| `--pid=host --cap-add SYS_PTRACE` | denied (docker-default AppArmor блокирует ptrace) |
| `--pid=host --cap-add SYS_PTRACE --security-opt apparmor=unconfined` | **прочитано** |

Во прочитанном environ dsh: `DEEPSEEK_API_KEY` (непустой), `GH_TOKEN`,
`HANDS_TOKEN`, `TELEGRAM_BOT_TOKEN`, `DSH_EDGE_ACCESS_KEY`. Значения в лог
замера не печатались — только имена переменных и факт непустоты.

Агент управляет всеми флагами запуска контейнера, поэтому первые два отказа в
таблице для модели угроз «модель против ключа» ничего не дают.

### 4. Смежное: PAT в hosts.yml

`~/.config/gh/hosts.yml` (PAT владельца, под которым работают push/PR) читается
model-shell. Это не утечка этого замера, а принятая конструкция (#119-эпоха):
env-канал (`GH_TOKEN`) DSH вырезает из model-shell, и агент остался бы без gh;
file-канал — единственный, который переживает вырезание. Зафиксировано как
осознанная граница, не как дефект к немедленному закрытию.

### 5. Точная пара в новой конфигурации — ПОДТВЕРДИЛСЯ (2026-09-10, repo-ci)

Инструментированный живой прогон точной пары из названия задачи в новой
(изолированной) конфигурации: stand-in dsh запущен той же продакшн-командой
`dsh_agent_run timeout …` (exec-цепочка sudo → launcher → timeout → fork →
exec образа), его прямой потомок (роль model-shell) читает
`/proc/<pid-standin>/environ`. Ключ — фейстурный (`guard-fake-key`), механика
доставки та же: env_keep доказан prepare (8а). Запуск: repo-ci run
34506905079, шаг «Изоляция адаптера модели от model-shell (класс #140)».

| Читали (в домене агента, uid агента) | Результат |
| --- | --- |
| stand-in dsh, bash-образ (родитель чтеца) | **READABLE, DEEPSEEK_API_KEY present-nonempty** |
| `timeout` (дед чтеца) | **READABLE, DEEPSEEK_API_KEY present-nonempty** |
| stand-in dsh, node-образ (как живой dsh) | **READABLE, DEEPSEEK_API_KEY present-nonempty** |

Вывод: env_keep-проводка ключа в изолированной конфигурации **сама открывает
вектор из названия задачи** — DENIED старой конфигурации был свойством среды
job-цепочки, которое sudo-exec не наследует. Изоляция uid (docker, cross-uid
environ) при этом держится; крашит только наличие ключа в читаемом environ.
Отсюда закрытие — ключ не должен существовать в env dsh вовсе (см. «Закрытие»).

## Закрытие (реализовано в этом репозитории)

Одно место правды — `dsh_provider_proxy_start` / `dsh_agent_isolation_prepare`
/ `dsh_agent_run` в `scripts/lib/dsh-ci.sh`; врезано во все три обёртки DSH
(класс #93/#94: фикс обязан быть в каждой обёртке):

1. **Пользователь**: `dsh-agent` (переопределяется `DSH_AGENT_USER`),
   идемпотентно, без группы docker (если состоял — исключается с warning'ом).
2. **Прокси-держатель ключа (замер 5)**: РЕАЛЬНЫЙ base_url+ключ не покидают
   домен транспорта — их держит локальный прокси (127.0.0.1, поднимает
   транспорт, файл состояния 0600). dsh получает локальный эндпоинт и
   подменный ключ через env_keep; `dsh_agent_run` подменяет значения при
   каждом запуске и синхронизирует файл состояния (цепочка #727 меняет
   провайдера между попытками — прокси ходит к текущему). SSE пропускается
   потоком, отказ прокси красит job громко (провайдер недоступен).
3. **env_keep** (`DEEPSEEK_*`, `HANDS_SPOOL`, `GH_REPO`): файл валидируется
   `visudo -cf` до установки. Через границу транспорт → агент ключ
   провайдера больше не идёт вовсе (8д доказывает отсутствие реального
   значения в env агента). `GH_TOKEN`/`HANDS_TOKEN`/`TELEGRAM_*`/
   `DSH_EDGE_ACCESS_KEY` в env dsh не попадают (транспорту нужны, агенту —
   нет); секреты не ходят через argv (`/proc/*/cmdline` читаем всеми) и не
   через файлы в домене агента.
4. **Воркспейс и каталог спула** передаются агент-юзеру (`chown`); спул
   стрим-плагина пишет сам dsh, транспорт читает (644). gh-конфиг
   зеркалируется в дом агента (режим `gh`); для ai-review/hands режим
   `nogh` — зеркало сносится и отсутствие проверяется (граница #18).
5. **Доказательства до запуска dsh** (fail loud, каждое громкое): прокси
   запущен и здоров (иначе отказ); env_keep проводит значения агенту; на
   настоящем uid-барьере environ транспорта не читается (8б) и РЕАЛЬНОГО
   ключа в env агента нет, подменный — есть (8д); docker у агента —
   `permission denied` (8в); живой замер ребра same-uid печатается в лог
   (8г, `::note::` — среда из репо не настраивается, правило «тормоз без
   газа»); gh авторизован (или hosts.yml отсутствует).
6. **Гвардии**: `scripts/lib/test/agent-isolation.guard.sh` в repo-ci
   (настоящий sudo, одноразовый юзер, свойства как факты окружения — включая
   живой замер точной пары замера 5 и механику прокси: upstream-заглушка
   видит реальный ключ, агенту едет подмена) + smoke bash-клиентов (проводка:
   прогон dsh обязан идти через `dsh_agent_run`, патч — в дом агента).

## Остаточный риск (осознанный)

- **Ребро «дочерний шелл читает environ родителя» (same-uid) — READABLE**
  (замер 5): после прокси это читаемое environ НЕ содержит ключа (подмена
  проверяется 8д на каждом прогоне), но само ребро остаётся открытым — всё,
  что попадёт в env dsh в будущем, модель прочитает. Правило: секреты в
  env_keep-список не добавлять; новые каналы ключа — только через прокси.
- **Прокси доступен агенту как HTTP-сервис**: модель может звонить в него
  напрямую и тратить квоту провайдера (без ключа она это и так может
  легальными вызовами модели — «Квота вместо ключа» ниже). Значение ключа
  прокси не возвращает; порт слушает только 127.0.0.1.
- **Файл состояния прокси (0600, домен транспорта)** — единственное место
  хранения реального base_url+ключа на раннере; читается только uid
  транспорта (DAC + кросс-uid environ/файлы — ядерная гарантия, доказывается
  8б).
- **PAT в hosts.yml читаем моделью** — по построению, см. замер 4. Дешёвого
  закрытия нет: любой канал, читаемый dsh, читается и model-shell (один uid).
  Меняет дело только вынос ключей с раннера.
- **Квота вместо ключа**: агент не может прочитать ключ, но может тратить
  квоту провайдера легальными вызовами модели через свою задачу. Это штатная
  работа агента, не утечка.
- **Дом транспорта открыт на проход (711)**: агенту нужен проход до
  воркспейса и спула, лежащих под `/home/runner`; все world-readable файлы
  там же агент теперь тоже читает (защищены только 600-файлы). Секреты в дом
  транспорта класть нельзя; файл состояния прокси — 600.
- **Отказ прокси** — соединение агента с провайдером рвётся (connection
  refused), прогон падает громко; повтор прогона поднимает прокси заново
  (жизненный цикл — на один job).
- **Задача, которой нужен docker на раннере** — тормоз без привычного газа:
  эскалация владельцу (метка `blocked`). Газ — вынос ключа с раннера (прокси
  на другой машине / платная песочница, см. [отвергнутые, п.4](30-rejected-alternatives.md)):
  решение владельца, не воркера. Локальные «тяжёлые прогоны в докере»
  ([PROTOCOL](../agents/PROTOCOL.md), п.5) — про машину владельца, раннер агента
  docker не требует.
- **Не подтверждено**: устойчивость дефолтов раннера во времени (ptrace-политика,
  состав групп, AppArmor, dumpable-эффекты, NoNewPrivs на model-shell).
  Подготовка не полагается на них как на защиту — она проверяет факты каждый
  прогон и падает/предупреждает громко при изменении окружения.
