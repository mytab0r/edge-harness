# Утечка ключа провайдера через model-shell и её закрытие

> Замерено живым прогоном из model-shell 2026-09-05 (задача #140, раннер
> GitHub Actions `ubuntu-latest`, ядро 6.17.0-1022-azure, docker 28.0.4,
> DSH 0.1.1-rc.2). Смежное: [архитектура DSH](10-dsh-architecture.md),
> [отвергнутые варианты](30-rejected-alternatives.md).

## TL;DR

- **Вектор из названия задачи (чтение `/proc/<pid-dsh>/environ` напрямую) на
  GitHub-раннерах НЕ подтвердился**: у model-shell нельзя читать environ
  родительского dsh — ядро (yama `ptrace_scope=1`, дефолт Ubuntu) разрешает
  чтение environ только собственных потомков.
- **Тот же класс подтвердился через docker-сокет** (он доступен model-shell на
  GitHub-раннерах по умолчанию): контейнер
  `--pid=host --cap-add SYS_PTRACE --security-opt apparmor=unconfined` читает
  environ **любого** процесса хоста, включая dsh. В environ dsh лежат
  `DEEPSEEK_API_KEY`, `GH_TOKEN`, `HANDS_TOKEN`, `TELEGRAM_BOT_TOKEN`,
  `DSH_EDGE_ACCESS_KEY`. Заявка «агент ключ не видит» без изоляции неверна.
- **Закрытие — «отдельный uid» из критерия задачи**: dsh стартует под
  выделенным непривилегированным пользователем **без группы docker**
  (`dsh_agent_isolation_prepare` в `scripts/lib/dsh-ci.sh`, все три обёртки:
  worker / hands / ai-review). Секреты едут к dsh через sudoers `env_keep`
  (память sudo), не через argv и не через файлы.
- **Принятая граница**: GitHub PAT владельца в `~/.config/gh/hosts.yml` читается
  моделью **по построению** — это единственный канал gh-авторизации, который
  переживает env-вырезание DSH. Модель обязана уметь открывать PR; патрулировать
  это здесь нечем и не нужно (решение осознанное, см. «Остаточный риск»).

## Замер

### 1. Env-вырезание DSH работает (подтверждение старого факта)

`env` model-shell: ни одного имени с подстрокой `KEY`/`TOKEN`/`SECRET`;
`DEEPSEEK_BASE_URL`/`DEEPSEEK_MODEL` при этом на месте. Вырезание
`*KEY*/*TOKEN*/*SECRET*` из model-shell вызовов — подтверждено (совпадает с
живым прогоном 2026-08-30 в [10-dsh-architecture.md](10-dsh-architecture.md)).

### 2. Прямой `/proc/<pid-dsh>/environ` — НЕ подтвердился

| Что читали | Результат |
| --- | --- |
| environ собственного потомка model-shell | **читается** (канал работает в принципе) |
| environ dsh (родитель model-shell), `timeout`, bash-обёрток, `Runner.Worker` | **Permission denied** |

Механика: yama `ptrace_scope=1` (файл `/proc/sys/kernel/yama/ptrace_scope`)
разрешает доступ к environ только по связи «потомок чтеца». dsh — родитель
model-shell, поэтому чтение запрещено ядром независимо от совпадения uid.

### 3. Docker-эскейп — подтвердился

model-shell входит в группу `docker` (дефолт образа раннера), сокет
`/var/run/docker.sock` доступен. Прогон из model-shell:

| Флаги контейнера | Чтение environ dsh |
| --- | --- |
| `--pid=host` (дефолтные caps, apparmor) | denied |
| `--pid=host --cap-add SYS_PTRACE` | denied (docker-default AppArmor блокирует ptrace) |
| `--pid=host --cap-add SYS_PTRACE --security-opt apparmor=unconfined` | **прочитано** |

Во прочитанном environ dsh: `DEEPSEEK_API_KEY` (непустой), `GH_TOKEN`,
`HANDS_TOKEN`, `TELEGRAM_BOT_TOKEN`, `DSH_EDGE_ACCESS_KEY`. Значения в лог
замера не печатались — только имена переменных и факт непустоты.

Агент управляет всеми флагами запуска контейнера, поэтому первые два отказа в
таблице для модели угроз «модель против ключа» ничего не дают.

### 4. Смежное: PAT в hosts.yml

`~/.config/gh/hosts.yml` (PAT владельца, под которым работают push/PR) читается
model-shell. Это не утечка этого замера, а принятая конструкция (#119-эпоха):
env-канал (`GH_TOKEN`) DSH вырезает из model-shell, и агент остался бы без gh;
file-канал — единственный, который переживает вырезание. Зафиксировано как
осознанная граница, не как дефект к немедленному закрытию.

## Закрытие (реализовано в этом репозитории)

Одно место правды — `dsh_agent_isolation_prepare` / `dsh_agent_run` в
`scripts/lib/dsh-ci.sh`; врезано во все три обёртки DSH (класс #93/#94:
фикс обязан быть в каждой обёртке):

1. **Пользователь**: `dsh-agent` (переопределяется `DSH_AGENT_USER`),
   идемпотентно, без группы docker (если состоял — исключается с warning'ом).
2. **Секреты — только через sudoers `env_keep`** (`DEEPSEEK_API_KEY`,
   `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`, `HANDS_SPOOL`, `GH_REPO`): файл
   валидируется `visudo -cf` до установки. Секреты не ходят ни через argv
   (`/proc/*/cmdline` читаем всеми), ни через файлы (домен агента читает сам
   агент). `GH_TOKEN`/`HANDS_TOKEN`/`TELEGRAM_*`/`DSH_EDGE_ACCESS_KEY` в env dsh
   больше не попадают вовсе (транспорту они нужны, агенту — нет).
3. **Воркспейс и каталог спула** передаются агент-юзеру (`chown`); спул стрим-
   плагина пишет сам dsh, транспорт читает (644). gh-конфиг зеркалируется в дом
   агента (режим `gh`); для ai-review режим `nogh` — зеркало сносится и
   отсутствие проверяется (граница доверия #18 сохраняется).
4. **Доказательства до запуска dsh** (fail loud): env_keep проводит секрет
   агенту; на настоящем uid-барьере environ транспорта не читается; docker у
   агента — `permission denied`; gh авторизован (или hosts.yml отсутствует).
5. **Гвардии**: `scripts/lib/test/agent-isolation.guard.sh` в repo-ci (настоящий
   sudo, одноразовый юзер, свойства как факты окружения) + smoke bash-клиентов
   (проводка: прогон dsh обязан идти через `dsh_agent_run`, патч — в дом агента).

## Остаточный риск (осознанный)

- **PAT в hosts.yml читаем моделью** — по построению, см. замер 4. Дешёвого
  закрытия нет: любой канал, читаемый dsh, читается и model-shell (один uid).
  Меняет дело только вынос ключей с раннера.
- **Квота вместо ключа**: агент без docker не может прочитать ключ, но может
  тратить квоту провайдера легальными вызовами модели через свою задачу. Это
  штатная работа агента, не утечка.
- **Задача, которой нужен docker на раннере** — тормоз без привычного газа:
  эскалация владельцу (метка `blocked`). Газ — вынос ключа с раннера (прокси на
  другой машине / платная песочница, см. [отвергнутые, п.4](30-rejected-alternatives.md)):
  решение владельца, не воркера. Локальные «тяжёлые прогоны в докере»
  ([PROTOCOL](../agents/PROTOCOL.md), п.5) — про машину владельца, раннер агента
  docker не требует.
- **Не подтверждено**: устойчивость дефолтов раннера во времени (yama, состав
  групп, AppArmor). Подготовка не полагается на них как на защиту — она
  проверяет факты каждый прогон и падает громко при изменении окружения.
