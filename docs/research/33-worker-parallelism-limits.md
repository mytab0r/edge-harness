# 33. Пропускная способность конвейера: можно ли поднять параллелизм воркера выше 1

> Исследовано 2026-09-13 по задаче #1073. Обновлено 2026-09-14 (разделы 10–11) по PR #1165/[#1173](https://github.com/mytab0r/edge-harness/pull/1173) (PR #1173 на момент этой правки ещё открыт, не в main).
> Смежное: [21. GitHub Actions](21-github-actions.md), [20. Cloudflare Free](20-cloudflare-free.md),
> [30. Отвергнутые варианты](30-rejected-alternatives.md).

## Вывод одной фразой

**N=1 обоснована сейчас.** GitHub-нативная сериализация в worker.yml (concurrency: group: worker) блокирует реальный параллелизм структурно (раздел 2). Отдельно, по хронологии: до фикса #1165 связывающим лимитом квоты были **чтения DO** (rows_read), не писи, вопреки исходной оценке разделов 5–6 — причина найдена и устранена (раздел 10). Сейчас, после фикса, фактическое узкое место — **отказы воркера и длительность прогона** (раздел 8), характеристика «потолок ~33 прогона/сутки» относится к ДО-фиксному прогону и требует переизмерения (раздел 10).

## 1. Контекст и вопрос (#1073)

`worker_runs_active` (`scripts/orchestra/scheduler.py:2542`) возвращает True при любом прогоне `worker.yml` в статусе `in_progress`/`queued`; три диспетчера (`dispatch_worker`, `dispatch_conflict_rework`, `dispatch_ai_review_rework`) читают этот флаг — итог: конвейер выполняет ровно одну единицу работы одновременно. Задача #1073 поставила вопрос: раз аренда задач (`claim_task.py`, замок `refs/locks/task-<N>`, #121) уже атомарна, не перестраховка ли гейт «один воркер» поверх уже решённой проблемы состязания за задачу. Критерий готовности — каждый из пяти пунктов ниже закрыт фактом, не суждением:

1. общий чекаут/рабочее дерево — конкурируют ли параллельные прогоны за состояние (раздел 3);
2. квоты провайдеров — выдержит ли цепочка N одновременных сессий (раздел 4);
3. лимиты GitHub Actions на бесплатном плане (раздел 7);
4. квота DO rows_read/rows_written — множит ли N чтения морды (разделы 5–6, уточнено разделом 10);
5. покрывает ли аренда ВСЕ разделяемые ресурсы, или только назначение задачи (раздел 7).

## 2. GitHub-нативная сериализация: concurrency: group: worker

`.github/workflows/worker.yml:26-29`:

```yaml
concurrency:
  group: worker
  cancel-in-progress: false
```

Комментарий в файле называет причину буквально: «Один воркер на репозиторий: два прогона соперничали бы за одни свободные задачи» — то есть исходное обоснование гейта СОВПАДАЕТ с гипотезой задачи #1073 («перестраховка поверх аренды»), а не называет отдельную, независимую от аренды причину. Это структурный факт: пока группа `worker` в файле стоит без изменений, N остаётся равным 1 независимо от того, что покажут разделы 3–7 — поднять параллелизм нельзя, не тронув эту строку (и `timeout-minutes: 340`, `scripts/worker/task.sh`, которые считают бюджет одной последовательной попытки, не N параллельных).

## 3. Общий чекаут / рабочее дерево (пункт 1 критерия)

Каждый прогон `worker.yml` — свежий `ubuntu-latest`-раннер с `actions/checkout@v7` в собственном эфемерном workspace; между параллельными job'ами GitHub Actions не делит файловую систему раннера. Общего ЛОКАЛЬНОГО состояния между гипотетическими N параллельными прогонами нет.

Общий ресурс — не файловая система раннера, а СЕРВЕРНЫЕ git-ref'ы на `origin`: ветки `agent/<N>-*` и локи `refs/locks/task-<N>`. Гвардия `.githooks/pre-commit` (свежесть базы) и аренда задачи (`claim_task.py`) уже защищают эту часть — см. раздел 7 про то, что именно покрывает аренда. Отдельного риска «состязание за чекаут», не сводимого к аренде задачи, не найдено.

## 4. Квоты провайдеров цепочки (пункт 2 критерия)

`config/provider-usage.json`, `chains.default-chain` — 8 провайдеров, у каждого свой `secret_env` (GLM/`DEEPSEEK_API_KEY`, OpenRouter-2/`OPENROUTER_2_API_KEY`, Ollama-1..3/раздельные ключи, NVIDIA-NIM-1/2, OpenRouter-1) — отдельные API-ключи, значит отдельные лимиты запросов у большинства шагов цепочки.

Общая точка соперничества — ПЕРВЫЙ провайдер цепочки, GLM: он стоит первым умышленно («владелец — лучшее качество, долгая квота», #857) и потому получает основную долю попыток при N=1. При N>1 два параллельных воркера пошли бы на GLM ОДНОВРЕМЕННЫМИ вызовами, а квота этого провайдера отслеживается ОДНИМ персистентным флагом (`vars.DSH_PROVIDER_QUOTA_UNTIL`, `scripts/lib/dsh-ci.sh::dsh_provider_quota_gate_skip`) — не per-параллельным-вызову счётчиком. Это не измерено на живом трафике (провайдер не пробит параллельной нагрузкой ни разу), но структурно: трекер квоты рассчитан на последовательные вызовы, поведение под двумя одновременными попаданиями в 429 у первого провайдера цепочки — открытый риск, не факт, полученный экспериментом.

## 5. Оценка квоты DO при N=1 (пункт 4 критерия, часть — исходная оценка до замера)

Из `docs/research/20-cloudflare-free.md` (замер #678, единственное место правды по этим числам — см. правило «одно место правды»):

- `rows_written`: оценка ≈3 130/прогон → потолок 100 000 / 3 130 ≈ **31 прогон/сутки** (`20-cloudflare-free.md:378-381`).
- `rows_read`: прежние 222 941/прогон (19 прогонов, замер 09-11) → после меры батчинга (K=30с) оценка ≈46 450/прогон → потолок 5 000 000 / 46 450 ≈ **оценочно ~100+ прогонов/сутки** (`20-cloudflare-free.md:468-470`).

При этих ОЦЕНКАХ (не измеренных на живом прогоне после меры) связывающим лимитом казались rows_written (~31/сутки), а не rows_read (~100+/сутки) — вывод раздела 6. Живой снимок 2026-09-13T07:15Z (`quota-watch` прогон 34744247391) на момент замера показывал `rows_written` 12.7%, `rows_read` 17.3% суточной квоты — обе доли далеки от исчерпания при N=1 (раздел 8).

**Это единственная развилка, которую раздел 10 опровергает измерением**: реальная цена rows_read после включённого в этот же день трафика (150 898/прогон) оказалась В ТРИ РАЗА выше оценки этого раздела, и связывающим лимитом на практике стали чтения, а не писи.

## 6. Три пути ускорения (пункт 4 критерия, продолжение) — оценка до замера

Три пути обсуждались как ускоряющие пропускную способность DO при том же N=1:

1. **Батчинг heartbeat-чтений** (K=30с вместо ~6с) — мера, давшая оценку раздела 5 (46 450 вместо 222 941 rows_read/прогон); ФАКТИЧЕСКИ реализована в PR #1165, но по другой причине (дескриптор сессии, не heartbeat-интервал — раздел 10).
2. **Снижение rows_written** батчингом финального слива транскрипта — не реализовано отдельно, оценка 3 130/прогон уже стояла как потолок раздела 5.
3. **Шардинг задач на N независимых воркеров** (сам вопрос #1073) — по оценке раздела 5 упёрся бы в потолок rows_written (~31 прогон/сутки при N=1, кратно меньше при N>1, если каждый параллельный воркер пишет независимо) раньше, чем в rows_read (~100+/сутки) — то есть ПОДНИМАТЬ N при этой оценке имело смысл ограничивать записями, не чтениями.

Итог раздела: до реального замера квота DO не выглядела структурным блокером N=1 (доли одна десятая — одна пятая суточного лимита по обоим счётчикам), рост N виделся ограниченным `rows_written`. Раздел 10 показывает, что эта модель была неверна: реальный ограничитель — чтения, а не писи, и после фикса #1165 квота вообще перестала быть первым узким местом (раздел 8) — им стали отказы воркера и длительность прогона.

## 7. Лимиты GitHub Actions и аренда задач (пункты 3 и 5 критерия)

**Лимит GitHub Actions (пункт 3).** Free-план даёт **20 одновременных job'ов на аккаунт** (`docs/research/21-github-actions.md:54`, считается по всему аккаунту, не по репозиторию). Для любого N, обсуждаемого здесь (2–3 параллельных воркера), это не ограничитель — упор в 20 наступит на порядок раньше квот DO или бюджета времени одного job'а.

**Что покрывает аренда (пункт 5).** `scripts/lib/claim_task.py` — атомарный лок `refs/locks/task-<N>` на СЕРВЕРНЫЙ git-ref, защищает ровно один ресурс: назначение конкретной задачи ровно одному каналу («сначала замок (защита), потом назначение assignee и комментарий в задачу — видимость, не защита», докстринг модуля). Аренда НЕ покрывает и не задумана покрывать:
- общую квоту провайдера первого шага цепочки (раздел 4) — при N>1 два воркера с РАЗНЫМИ задачами могут одновременно арендовать разные задачи и одновременно обратиться к одному и тому же провайдеру;
- общую суточную квоту DO rows_read/rows_written (разделы 5–6, 10) — она глобальная на аккаунт Cloudflare, не привязана к задаче;
- рипер зависших прогонов `WORKER_STALL_MINUTES` (раздел 9) — это отдельный механизм, действующий на уровне прогона job'а, не задачи.

Итог: гипотеза задачи #1073 («аренда уже решает состязание, гейт `worker` — перестраховка сверху») верна ТОЛЬКО для пункта 1 (общий чекаут/рабочее дерево, раздел 3) — там действительно нет отдельного риска сверх аренды. Для пунктов 2 и 4 (разделы 4, 5–6, 10) аренда не защищает соответствующий разделяемый ресурс — если N>1 будет принято, эти два ресурса требуют отдельного механизма (per-провайдерная сериализация первого шага цепочки; переизмерение квоты DO под параллельной нагрузкой), не только аренды задачи.

## 8. Поправка (2026-09-13T07:15Z): квота НЕ узкое место, отказы воркера

quota-watch прогон 34744247391: rows_written 12.7%, rows_read 17.3% (не узкое место по оценкам раздела 5). Реальные узкие места: отказы воркера, длительность прогона. N=1 обоснована GitHub-сериализацией (раздел 2), не квотой.

## 9. Разрыв контура доводки: один исполнитель + вердикт позже завершения

Живой пример: 5 PR по 7 часов ожидания. Механизм адресной доводки делит единственного воркера. **Важно**: рипер по `WORKER_STALL_MINUTES=295` (scheduler.py:2492) стреляет только ВЫШЕ легитимного максимума бюджета (270 мин две попытки + RATE_LIMIT); прежний порог 255 этот баг был, был поправлен в #1067. Честную долгую работу рипер не зовёт зависшей — претензия #1141/#1160 к тому, что первичный механизм голая длительность, не явный бюджет цепочки.

## 10. КРИТИЧНОЕ: реальное узкое место — rows_read чтения, не писи (2026-09-13, замер 21:49Z)

**Измеренная цена прогона** (не оценка):
- **rows_read: ≈150 898 на прогон** → потолок ≈**33 прогона/сутки**
- rows_written: ≈2 219 на прогон → потолок ≈45 прогонов/сутки

**Связывающий лимит на момент этого замера**: чтения, не писи. Это опровергает оценку разделов 5–6, где писи (rows_written, ~31 прогон/сутки) казались более тесным ограничителем, чем чтения (~100+ прогонов/сутки по оценке).

**Проверка**: 18 прогонов × 150 898 ≈ 54.3% суточной квоты (измерено на 21:49Z quota-watch) — совпадает с прямым замером.

**Причина найдена и устранена**: наш патч #1163/PR #1165 (слит 23:01Z того же дня) освобождал дескриптор сессии после каждой пачки событий (~191 пачка за прогон), и следующая пачка заново вычитывала всю историю. Фикс: дескриптор остаётся открытым, история не перечитывается.

**Гвардия ещё не в main.** PR #1173 (`agent/1161-ingest-cold-load-guard`) на момент этой правки **открыт**, не слит — гвардия из него в main не попала. Тест `dsh-edge/test/ingest-resident-safety.test.mjs`, который упоминается в связи с этим фиксом, пришёл в main вместе с #1165 (коммит d239e324), а не с #1173: это тест на сам фикс диспоуза хэндла, не гвардия на «холодная загрузка сессии ingest платится один раз, не на каждый батч» из отдельной задачи #1161, которую несёт PR #1173.

**Подтверждение суточного снижения ещё НЕ получено.** Оно требует свежего замера `quota-watch` за полные сутки (23:01Z→23:01Z следующего дня) ПОСЛЕ слияния #1165 — на момент этой правки такого замера ещё нет, приведённые 150 898/прогон и 18×150 898≈54.3% — это ДО-фиксные цифры (замер 21:49Z того же дня, ДО слияния фикса в 23:01Z). См. пункт 1 раздела «Не подтверждено».

**N=2 при до-фиксной цене — нельзя**: два исполнителя дали бы 145–148% квоты ЧТЕНИЙ (не писей, как ошибочно утверждалось в разделе 6) на ДО-фиксной цене прогона. После фикса #1165 цену нужно переизмерить — этот вывод не переносится автоматически на пост-фиксный прогон.

## 11. Смежные барьеры, о которых стоит упомянуть

1. **#1141/#1160**: суммарное время прогона не ограничено. `DSH_TIMEOUT_SECS` действует на одну попытку провайдера, цепочка перебирает 8 провайдеров → потолок ≈16 часов. Живой случай (прогон 34757182001, ≥200 мин) подтверждает: рипер его не трогал. Первичный механизм — голая длительность, не явный бюджет цепочки.

2. **#1149**: патч-серия дш-edge разошлась с апстримом 0.14.0, дала два прод-инцидента. Рассмотреть rebasing или контролируемый апгрейд.

## Итоговый вердикт

N=1 обоснована:
1. **GitHub-сериализация** (раздел 2): поднять гейт scheduler.py без правки worker.yml:26-29 не даст результата — это самостоятельная причина, не только квота.
2. **Квота чтений (хронология)**: до фикса #1165 связывающим лимитом были чтения (потолок ~33 прогон/сутки, раздел 10), причина устранена, но гвардия ещё не в main (открыт PR #1173) и суточное подтверждение после фикса ещё не снято (раздел 10) — текущую пост-фиксную цену прогона называть числом преждевременно.
3. **Организационное**: разрыв контура доводки (раздел 9), не решаемо параллелизмом.
4. **Разделяемые ресурсы вне аренды** (раздел 7): квота первого провайдера цепочки и суточная квота DO не защищены арендой задачи — при N>1 нужен отдельный механизм для обоих.

Дальнейшая работа: суточный замер по чтениям после PR #1165 (и отдельно — после слияния #1173), диагностика отказов воркера (failure-rate ~67%), решение структуры доводки — уже разложены по #1079/#1080/#1083 (см. Related задачи #1092), дублирующих задач здесь не заводится.

## Не подтверждено

1. Эффект PR #1165 на живом трафике за полные сутки (23:01Z→23:01Z следующего дня) — оценка была, суточное измерение ПОСЛЕ фикса ещё не снято (раздел 10 обновлён этой правкой, чтобы не читаться как «уже подтверждено»).
2. Точные корни 67% failure-rate воркера — расследовано структурно (отказы), не по видам.
3. Справедливость порога 295 в scheduler.py под разные режимы работы и дефекты — проверен по живому случаю, не доказано исчерпывающе.
4. Поведение трекера квоты первого провайдера цепочки (`vars.DSH_PROVIDER_QUOTA_UNTIL`) под двумя ОДНОВРЕМЕННЫМИ вызовами (раздел 4) — не проверено экспериментом, только структурным чтением кода.
