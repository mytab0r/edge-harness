# Отвергнутые варианты и почему

> Исследовано 2026-08-28. Каждый вариант отвергнут по названной причине, а не по вкусу.
> Смежное: [Cloudflare Free](20-cloudflare-free.md), [GitHub Actions](21-github-actions.md), [архитектура DSH](10-dsh-architecture.md)

Документ существует ради одной цели: чтобы через полгода никто — ни человек, ни агент —
не предложил заново то, что уже разобрано и закрыто уликой. Если хочется предложить пункт
из списка ниже, сначала проверь условие возврата: оно названо явно у каждого варианта.
Не выполнено условие — предложение не новое, а забытое.

## 1. Мигрировать текущий Python-харнес на DSH целиком

**Что это.** Отказаться от собственного набора решений и перенести весь цикл самразработки
на DSH: стадии — плагинами фреймворка, провайдеры — через штатный `llm-pi-ai`.

**Чем привлекало.** Одна платформа вместо набора своих решений: не нужно поддерживать
собственный роутер, собственный планировщик стадий и собственные гвардии — всё штатное.

**Почему отвергнуто.** Считать надо не то, что приобретаем, а то, что придётся переписать.
У существующего харнеса уже работает:

- `ProviderChain` с fallback и **персистентным** cooldown, причём с классификацией отказов,
  а не единым таймаутом: usage limit → парсинг «resets at 3am»; rate limit / 429 → 15 мин;
  overloaded / 529 → 5 мин; credit balance → 6 ч; invalid api key → 24 ч;
- protected paths с Telegram-апрувами;
- бюджет-гарды ($3/прогон, месячный потолок);
- gate #2 с уликами; спек-гвардии.

Миграция = переписать ~1236 строк `core/selfdev.py` плюс провайдеров плюс гвардии на TS
плагинами фреймворка в состоянии **developer preview** — ради ровно одной отсутствующей
вещи, веб-морды. Хуже того, главный мотив миграции не выполняется даже формально:
`llm-pi-ai` у DSH — пул **выбора**, а не роутер. Автоматического fallback и ротации учёток
там нет, то есть «заменить 9router» этим нельзя. Мы бы отдали работающую классификацию
отказов и не получили взамен ничего из того, ради чего шли.

**Вернуться если.** DSH выйдет из developer preview **И** в нём появится штатная ротация
учёток. Оба условия, не одно: dev-preview без ротации не решает задачу, а ротация в
dev-preview — фундамент, который завтра поменяет API.

## 2. Веб-морда живёт только внутри job'а

**Что это.** Не разделять фронт и руки: агент-цикл и UI поднимаются вместе в раннере,
морда доступна на время жизни job'а.

**Чем привлекало.** Почти нулевая цена и — главное — схема уже работает, ничего нового
строить не надо.

**Почему отвергнуто.** Отвергнуто владельцем по существу задачи, а не по технике: морда,
доступная только пока жив job, бессмысленна. Нельзя ни зайти посмотреть состояние, ни
поставить задачу ровно тогда, когда рук нет, — а именно это и есть сценарий использования.
Цель прямо противоположная схеме: **морда всегда жива, руки поднимаются по требованию.**
Вариант предлагает инверсию цели, поэтому дешевизна тут не аргумент.

**Вернуться.** Никогда — противоречит цели. Если этот вариант снова кажется разумным,
значит потеряна формулировка цели, а не найдено новое решение.

## 3. WebSocket-туннель Durable Object → долгоживущий job (reverse tunnel)

**Что это.** Job поднимается и держит исходящее WS-соединение к Durable Object; DO шлёт в
туннель команды, job исполняет их по одной и отвечает. Обратный туннель решает проблему
NAT: наружу из раннера соединяться можно, внутрь — нет.

**Чем привлекало.** Схема закрывает всё сразу: агент-цикл в облаке, руки по требованию,
per-command исполнение без перезапуска окружения на каждую команду.

**Почему отвергнуто.** Дважды, двумя независимыми причинами — важно, что провал любой из
них уже достаточен.

**(а) Правовая — GitHub Terms for Additional Products.** Дословно, и именно про
GitHub-hosted runners: запрещена «any other activity unrelated to the production, testing,
deployment, or publication of the software project associated with the repository», а также
«any activity that places a burden on our servers, where that burden is disproportionate to
the benefits provided to users». Санкции названы там же и они не косметические:
«termination of jobs, restrictions in your ability to use GitHub Actions, disabling of
repositories … or in some cases, suspension or termination of your GitHub account».
Job, простаивающий на WS в ожидании внешних команд, попадает под это по смыслу.
**Оговорка:** явного пункта про «reverse tunnel» в тексте нет — это чтение по смыслу, а не
цитата под наш случай. Но ставить аккаунт против удобства схемы — плохой размен.

**(б) Экономическая — Cloudflare Free.** Документация Durable Objects дословно:
«Hibernation is only supported when a Durable Object acts as a WebSocket server. Outgoing
WebSockets do not hibernate.» То есть именно наш режим (DO как клиент туннеля) гибернацию
не получает. Сверх того, активное исходящее соединение защищает объект от eviction
«for up to 15 minutes per connection». Постоянный туннель = объект всегда в памяти:

```
86 400 с/сутки × 0.128 GB = ~11 059 GB-s/сутки
из 13 000 GB-s дневного бюджета Free  →  ~85 % на ОДИН сокет
```

Восемьдесят пять процентов дневного бюджета за одно соединение, которое ничего не делает.

**Плюс операционные потолки.** Жёсткий потолок job'а — 6 ч; эстафета между job'ами не
гарантирована по времени; один из 20 слотов занят постоянно.

**Вернуться если.** Перейдём на self-hosted runner (ограничение про «unrelated activity»
сформулировано именно для GitHub-hosted, на своём железе оно не применяется) **или** на
платный CF, где бюджет GB-s не жмёт. Заметь: эти два условия снимают разные причины —
self-hosted снимает (а), но не (б); платный CF снимает (б), но не (а).

## 4. Cloudflare Containers / Sandbox SDK как «руки»

**Что это.** Настоящий Linux-контейнер под управлением Workers: DO дёргает контейнер
напрямую, внутри git и Python 3.11.

**Чем привлекало.** Технически это лучший вариант «рук» из всех рассмотренных. Нативно для
CF — DO вызывает контейнер напрямую, проблема NAT не возникает вовсе. Биллинг CPU по факту:
ожидание ответа LLM почти бесплатно, ~$0.06–0.13 за час активной сессии. Задержка старта
1–3 с против недокументированных десятков секунд у GH Actions.

**Почему отвергнуто.** Требует Workers Paid: в таблице прайсинга колонка Free — **N/A по
всем ресурсам** (память, CPU, диск). Документация формулирует это через включённый объём:
«Containers are billed for every 10ms that they are actively running at the following rates,
with included monthly usage as part of the $5 USD per month Workers Paid plan». Вход $5/мес,
а принятое решение — оставаться на бесплатном плане. Причина отказа целиком в этом и ни в
чём другом: технически вариант выигрывает.

**Засада на будущее — записать сейчас, чтобы не наступить потом.** «All disk is ephemeral.
When a Container instance goes to sleep, the next time it is started, it will have a fresh
disk as defined by its container image.» Значит worktree обязан уезжать в git или R2 **до**
засыпания. Проектировать это надо сразу, а не после первой потери работы.

**Вернуться если.** Согласимся на $5/мес. Тогда это лучший вариант «рук» — лучше GH Actions
и по задержке, и по легальности (своя инфраструктура, никакого ToS про «unrelated activity»).

## 5. Dynamic Workers (бывш. Worker Loaders) — режим «isolated» dsh-edge

**Что это.** Worker, порождающий другие Worker'ы во время исполнения: изолированное
выполнение кода по требованию, старт за миллисекунды.

**Чем привлекало.** Быстрая безопасная песочница прямо в Workers, без контейнеров.

**Почему отвергнуто.** Дословно из changelog: «Dynamic Workers are now in open beta for all
paid Workers users». На Free недоступно — вопрос закрыт до смены плана.

**Вернуться.** Вместе с п.4, при переходе на Paid. Отдельно рассматривать смысла нет:
условие возврата ровно то же.

## 6. Агент-цикл целиком внутри Durable Object на Free

**Что это.** Перенести цикл в DO, оставив рукам только исполнение отдельных команд.

**Чем привлекало.** Красивое разделение: «фронт делает то, что может делать фронт»,
руки поднимаются только под конкретную команду и сразу умирают.

**Почему отвергнуто.** Workers Free даёт **10 ms CPU на invocation**, и каждое входящее
WS-сообщение — отдельный invocation. Разбор стрима от модели — это активный CPU: ожидание
сети в лимит не засчитывается, а вот парсинг чанков засчитывается полностью. Держать цикл
в DO на Free = укладывать обработку каждого чанка в 10 мс. Это работа на грани, причём
грань не наша: изменится формат стрима или размер чанка — и цикл начнёт падать по причине,
на которую мы не влияем. Отвергнуто не потому, что невозможно, а потому что запас нулевой.

**Вернуться если.** Paid: там 30 с CPU по умолчанию и до 5 мин через `limits.cpu_ms`
(`"limits": { "cpu_ms": 300000 }`). С таким запасом вариант снова становится разумным.

## 7. LiteLLM Proxy как пул провайдеров

**Что это.** Готовый прокси-пул: несколько deployment'ов с одним `model_name` и разными
`api_key`, поверх — стратегии выбора, кулдауны, фолбэки и бюджеты.

**Чем привлекало.** По функциям это самое сильное решение из всех рассмотренных, и с
большим отрывом:

- стратегии: simple-shuffle, latency-based, usage-based, least-busy, cost-based, weighted,
  custom;
- кулдаун: `allowed_fails` (по умолчанию 3 отказа/мин) → `cooldown_time` (по умолчанию 5 с),
  немедленный кулдаун на 429;
- фолбэки: `fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks`;
- бюджеты: `max_budget` / `budget_duration` / `tpm_limit` / `rpm_limit` на ключ, пользователя
  и команду.

**Почему отвергнуто.** Python — на Workers не встанет **в принципе**, только контейнер или
VM. Это не «сложно настроить», это несовместимость раннтайма, и обсуждать её бессмысленно.
Сверх того, даже при наличии контейнера тянется хвост зависимостей: Postgres обязателен
(`DATABASE_URL`) для ключей, бюджетов и spend-логов; Redis обязателен при более чем одном
инстансе. Лицензия MIT, но с карв-аутом: каталог `enterprise/` под отдельной лицензией.

**Вернуться если.** Появится контейнер, в котором LiteLLM и так живёт (то есть п.4 или п.11
уже принят). Отдельно ради LiteLLM контейнер заводить не стоит — это хвост, а не голова.

## 8. Portkey AI Gateway на Workers

**Что это.** OSS-шлюз на TS/Hono с мульти-ключевой маршрутизацией, разворачиваемый как Worker.

**Чем привлекало.** Единственный OSS-шлюз, который **реально едет на Workers**, и это
проверено файлом, а не обещанием README: в корне репозитория лежит `wrangler.toml` с
`name = "rubeus"`, `main = "src/index.ts"` и `compatibility_flags = [ "nodejs_compat" ]`,
деплой — `npm run deploy`. Лицензия MIT. Мульти-ключ работает на **сырых** ключах, а не
только на облачных слагах: `Targets{apiKey?, provider?, weight?, retry?, overrideParams?}`,
`StrategyModes = loadbalance | fallback | single | conditional`,
`Strategy.onStatusCodes?: Array<number>`. Конфиги вида
`{"strategy":{"mode":"loadbalance"},"targets":[...]}` и
`{"strategy":{"mode":"fallback","on_status_codes":[429,503]}}`.

**Почему отложено (не отвергнуто).** Формулировка важна: вариант рабочий, причина отказа —
отсутствие нужды, а не дефект. Существующий 9router уже делает ротацию и cooldown; менять
его не на что, выигрыша нет, а риск замены работающего компонента есть. Плюс одна
неприятная оговорка: бюджеты и рейт-лимиты документированы как «Available on Enterprise
Self Hosting plan only. Requires 1.17.0 or higher version of the Gateway». Что именно из
cost controls работает в бесплатной сборке — не подтверждено, и это надо проверять до
любого переезда, а не после.

**Вернуться если.** Решим убрать питоновский компонент из цепочки и оставить на CF только
воркеры. Тогда Portkey — первый кандидат, и начинать надо с проверки оговорки про бюджеты.

## 9. Cloudflare AI Gateway как ротатор учёток

**Что это.** Штатный шлюз CF перед провайдерами: Universal Endpoint, Dynamic Routing, BYOK.

**Чем привлекало.** Fallback между провайдерами (Universal Endpoint, `cf-aig-step`),
Dynamic Routing с нодами Rate Limit и Budget Limit, кэш и аналитика стоимости — бесплатно.

**Почему отвергнуто для ЭТОЙ задачи.** BYOK действительно хранит несколько ключей одного
провайдера, но выбор между ними **ручной**: по умолчанию используется алиас `default`, иначе
нужен заголовок `cf-aig-byok-alias`. А через Unified Billing, дословно, «only the default
alias is consulted». Автоматической ротации с кулдауном на 429 — того единственного, ради
чего мы сюда шли, — нет. Механизм для разделения dev/prod и для staged-ротации, а не для
отказоустойчивости.

**Вернуться.** Как надстройка ради кэша, аналитики и spend-limit — в любой момент: это
бесплатно и не требует кода. Именно как надстройка, не как ротатор.
**Не подтверждено:** может ли Model-нода в Dynamic Routing пришпилить конкретный
BYOK-алиас. Если да — вывод по ротации стоит пересмотреть, это единственная лазейка.

## 10. Прочие OSS-гейтвеи

Рассмотрены и отклонены пакетом — каждый по своей причине, но ни одна не лечится настройкой.

| Проект | Стек / лицензия | Что умеет | Почему нет |
|--------|-----------------|-----------|------------|
| Bifrost | Go, Apache 2.0 | Взвешенный выбор среди ключей, иерархические бюджеты | На Workers не едет |
| Helicone ai-gateway | Rust, **GPL-3.0** | Балансировка между провайдерами | Балансирует провайдеров, **не ключи** — задача другая; плюс лицензия |
| one-api | Go, MIT | Мультипровайдерный шлюз | На Workers не едет |
| llmgateway | TS | — | AGPLv3 + проприетарный Enterprise; Workers не заявлен |
| OpenRouter | хостед | BYOK с несколькими ключами | OSS-сервера нет; перебор ключей **приоритетный, не round-robin**; комиссия 5 % |

**Про лицензию Helicone — уточнение, стоившее проверки.** В README заявлен Apache, и это
сбивает: в монорепозитории `Helicone/helicone` файл LICENSE действительно Apache 2.0.
Но интересующий нас `ai-gateway` — **отдельный репозиторий**, и его LICENSE — GNU General
Public License v3. Проверять надо LICENSE того репозитория, который собираешься брать,
а не README соседнего.

## 11. Собственная VPS вместо всего этого

**Что это.** Отказаться от связки Workers + job и просто арендовать сервер, где всё живёт
постоянно.

**Чем привлекало.** Hetzner CX22 (2 vCPU / 4 GB / 40 GB) — порядка нескольких евро в месяц,
то есть при работе 24/7 дешевле GH Actions на порядок. Персистентный диск (нет засады из
п.4), никаких лимитов CPU (нет засады из п.6), никакого ToS про «unrelated activity»
(нет засады из п.3). Одним решением снимаются три отдельные проблемы.

**Почему отвергнуто пока.** Цель — бесплатно. Это единственная причина, и её стоит называть
честно: вариант проигрывает не по технике, а по принятому ограничению.

**Вернуться если.** Откажемся от требования «бесплатно». И тогда — важно — сравнивать надо
**VPS против CF Containers**, а не VPS против Free. Как только $5/мес перестают быть
табу, Free выбывает из сравнения, и вопрос становится «какая платная схема лучше»,
где у VPS сильные аргументы (см. три засады выше).

## 12. Ловушка при поиске плагинов remote-execution

Не вариант, а предупреждение будущему исследователю: этот поиск выглядит перспективным и
таковым не является. Записано, чтобы не потратить второй день на тот же обход.

Рубрика «Remote & Mobile» в awesome-dsh-plugin (~60 плагинов) издали выглядит горой готовых
решений для удалённого исполнения. На деле это почти целиком удалённый **ДОСТУП** к
локально работающему харнесу: телефон, Tailscale, Telegram-мосты. Исполнение во всех случаях
остаётся на машине владельца — то есть ровно та часть, которую мы ищем, отсутствует.

Реально пусто по запросам: GitHub Actions как среда исполнения агента, Modal, Daytona,
Firecracker, devcontainer. По D1 / R2 / KV как бэкенду session persistence — тоже не найдено
ничего. Отсутствие результата здесь — установленный факт, а не недоискали.

## 13. Cloudflare Workers AI как LLM-провайдер агента

**Что это.** Кончилась квота у внешнего провайдера — временно перевести агента на
Workers AI: у проекта уже есть `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`, в каталоге
CF есть модели семейства Nemotron (в сгенерированных типах воркера видно
`@cf/nvidia/nemotron-3-120b-a12b`), а у Workers AI есть OpenAI-совместимый путь. То есть
переключение выглядело как «сменить три переменные, нового ключа не надо вовсе».

**Чем привлекало.** Ноль новых секретов и ноль работы: самый дешёвый по действиям
способ оживить конвейер на время простоя основного провайдера.

**Почему отвергнуто (владелец, 2026-09-01).** Бесплатная суточная аллокация Workers AI
рассчитана на редкие инференсы внутри воркера, а не на агентский цикл. Агент DSH за один
ход делает несколько вызовов с большим контекстом и инструментами — аллокация уходит **за
минуту**, после чего либо отказ, либо начисление платы. Требование «всё работает на
бесплатных планах» это ломает сразу, а не постепенно, поэтому вариант не годится даже как
временный: он не выигрывает даже те три дня, ради которых рассматривался.

**Что делать вместо.** Временный провайдер — тот же класс, что основной: внешний
OpenAI-совместимый эндпоинт с осмысленной квотой (NVIDIA NIM,
`https://integrate.api.nvidia.com/v1`, модель семейства Nemotron-3). Процедура —
[runbook переключения провайдера](../runbooks/switch-llm-provider.md).

**Когда вернуться.** Для агентского цикла — никогда. Для редких служебных инференсов
внутри воркера (короткая классификация, эмбеддинг, разметка) вариант не рассматривался
и может быть уместен — это другая задача.

## Что выбрано в итоге

Морда — **Workers Assets**: статика всегда жива, ничего не стоит и не зависит от того, есть
ли сейчас руки. Журнал, сессии, очередь и heartbeat — **Durable Object с SQLite**: одно
место состояния, переживающее и job, и перезапуск морды. Руки — **job по
`repository_dispatch`**: поднимается по требованию, живёт минуты, работает над своим
репозиторием и умирает, то есть остаётся ровно тем, чем GitHub Actions и должен быть по
своему ToS (п.3), и не превращается в простаивающий туннель. Агент-цикл целиком внутри
job'а, **не в DO** — из-за 10 ms CPU на invocation на Free (п.6): цикл живёт там, где у него
есть процессорное время. Принятая плата за всё это названа прямо и принята сознательно —
**недокументированная задержка старта job'а**: мы меняем секунды ожидания на нулевую
стоимость и отсутствие правовых рисков.

## Что не подтверждено

Пункты ниже вошли в решения, но уликой не закрыты. Если какой-то из них станет
принципиальным — проверять до, а не после.

1. **Чтение GitHub ToS про reverse tunnel — по смыслу, а не по букве.** Процитированные
   запреты («unrelated activity», «disproportionate burden») реальны и проверены, но
   явного пункта про долгоживущий idle-job на WebSocket в тексте нет. Наш вывод — толкование.
2. **Дата changelog Cloudflare про 15-минутную защиту от eviction (заявлено 19.06.2026).**
   Сам факт «исходящее соединение защищает объект от eviction for up to 15 minutes per
   connection» подтверждён документацией Durable Objects; конкретная дата записи не сверена.
3. **Цена Hetzner CX22.** Фигурировавшие €3.79/мес — историческая цена запуска. Источники
   2026 года указывают на повышение (называется в том числе €7.99/мес после апреля 2026),
   официальная страница тарифов при проверке точную цифру по CX22 не отдала. На вывод это
   не влияет: VPS остаётся сопоставим по деньгам с $5/мес CF Containers, а решает всё
   требование «бесплатно», а не разница в пару евро. Актуальную цену смотреть перед
   решением.
4. **Cost controls в бесплатной сборке Portkey.** Бюджеты и рейт-лимиты документированы как
   Enterprise Self Hosting; что именно из них работает в OSS-сборке — не проверено.
5. **Может ли Model-нода в Dynamic Routing (CF AI Gateway) пришпилить конкретный
   BYOK-алиас.** Единственная известная лазейка к автоматической ротации учёток на CF;
   если подтвердится — вывод п.9 подлежит пересмотру.
