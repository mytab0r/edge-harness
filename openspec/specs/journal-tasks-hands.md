# Спека: канал конвейера, пульс, морда ↔ руки

Источник поведения: морда dsh-edge (source-build, патчи в `dsh-edge/patches/`),
писатели в `scripts/lib/dsh-edge-pipeline.sh`, пульс-воркер `cf-pulse/`,
проверено интеграциями `dsh-edge/pipeline-integration/` и `dsh-edge/ingest-integration/`,
канарейками деплоя и тестами. Эта спека — требования, по которым любое изменение
поведения обязано пройти.

Журнал edge-harness (DO с SQLite, `POST /api/events`, WebSocket replay, очередь
`POST /api/tasks`, heartbeat) списан вместе с воркером (#86): спека и история —
в git (`openspec/changes/edge-harness-decommission/`, история этого файла).
Каналы, которые он держал, определены ниже.

## Канал статусов конвейера (сессия морды)

1. Единственный канал статусов конвейера — сессия `harness-pipeline` в
   воркспейсе `/workspace/edge-harness` морды dsh-edge; статусы лежат в
   хранилище DO и видны в чате. Сессия создаётся идемпотентно
   (create-or-reuse + `session.rename` «Конвейер edge-harness») и никогда не
   архивируется.
2. Статус — событие `user/message` с `source.kind = "harness-pipeline-status"`;
   текст сообщения — строгий однострочный JSON-рекорд
   `{task_id, kind, data, source, ts, emitted}`: `task_id`/`kind` непустые
   строки, `data` — объект или null. Идентификация статуса — по `source.kind`,
   не по разбору текста; рекорд, не разобравшийся как JSON, не статус.
3. Повторная доставка отличима по `emitted` (uuid). Дубли статуса не вредят:
   читатель берёт последнее событие по `task_id`.
4. Писатели: `scripts/plugins/plugin_status.sh` (kind `plugin_status`,
   task_id `plugin:<id>`), `scripts/plugins/integration_status.sh`
   (kind `integration_status`, task_id `integration:<id>`), клиент рук
   `scripts/hands/dsh_task.sh` (жизненный цикл job: `job_start`,
   `bootstrap`, `agent_answer`, `agent_error`, `stream_note`, `job_end`,
   task_id = id задачи).
5. Градация fail loud: финальный статус (`ready`/`failed`/`job_end`) обязан
   доехать до канала — иначе exit 1 красит job; событие жизненного цикла job
   (`PIPELINE_HARD`) — тоже; промежуточный статус деплоя при недоступной морде
   — warning без покраски (морду в этот момент чинят). Отсутствие конфигурации
   (`DSH_EDGE_URL`/`DSH_EDGE_ACCESS_KEY`) — громкий отказ «не настроено»,
   отличный от сетевого сбоя.
6. Чтение — `GET /api/harness/events?task_id=<id>&after=<id>&limit=<n>` на
   воркере морды (патч 0005). Ответ в форме прежнего журнала:
   `{events: [{id, task_id, seq, ts, source, kind, data}, …], has_more,
   next_after}`; `id`/`seq` = канонический seq события сессии (монотонный),
   `after` — курсор по нему. Заголовки `x-has-more`/`x-next-after` дублируют
   тело.
7. `has_more` означает «есть ещё ПОДХОДЯЩИЕ по task_id события», а не «есть
   нечитанные события сессии»: ложное продолжение заставляет каждого читателя
   ходить лишние страницы, потерянное — терять хвост статусов.
8. Маршрут только для чтения (не GET — отказ); `task_id` обязателен (400 без
   него); неавторизованный запрос не отвечает 200 (auth морды стоит до
   маршрута). Ответ, не совпавший по форме (п.6), — ошибка читателя, а не
   «статусов нет».

## Сессии раннеров

9. Транскрипт хода работы агента-раннера виден в нативном UI морды: клиент
   создаёт сессию `harness-<id>` («#N: задача») и дренирует канонические
   события через `POST /api/sessions/:id/ingest` (патч 0004). Успешный прогон
   с нулём доставленных событий транскрипта — красный job (#119).
10. Текст задачи приезжает в payload диспетча (`client_payload.task_text`
    repository_dispatch'а или `inputs.task_text` ручного прогона), а не из
    хранилища. Нет текста — громкий отказ до начала работы.

## Пульс-воркер (harness-pulse)

11. Пульс оркестрации живёт в DO `Pulse` минимального инфра-воркера
    `cf-pulse` и держит alarm-цепочку: конструктор закладывает первый тик,
    `alarm()` перезакладывает следующий **до** любой работы — сбой сети не
    обрывает цепочку. Интервал — 15 минут (константа в `cf-pulse/src/config.ts`
    — единственное место правды).
12. На каждом тике пульс дёргает `workflow_dispatch` `orchestra.yml`. GitHub
    cron на репо не тикает/деградирует (#73, #269) — без пульса конвейер стоит.
    Отказ диспетча не роняет пульс: ошибка уходит в observability.
13. Самообновление морды (#73): на каждом тике пульс сверяет версию
    `GET /api/health` морды с последней стабильной в npm
    (`registry.npmjs.org/dsh-edge/latest`). Расхождение при истёкшем троттле
    (4 ч, пометка попытки пишется в storage ДО диспетча — упавший деплой не
    превращает пульс в штурм) → `workflow_dispatch` `deploy-dsh-edge.yml`.
14. Сбой сверки (сеть, реестр, неожиданный формат) не роняет пульс: тик уже
    перезаложен, ошибка уходит в observability. Чистое решение
    (`dshEdgeUpdateDecision`) покрыто тестами (`cf-pulse/test/`).
15. Канарейка деплоя пульса доказывает не HTTP 200, а взведённый будильник
    (`next_alarm_at` в ответе `/api/health`): деплой, не оставивший живого
    пульса, — красный job.
16. Токен диспетча пульса — узкий `GH_DISPATCH_TOKEN` (fine-grained,
    Contents+Actions на этот репозиторий, ADR 0008). Гвардия узости стоит в
    `deploy-pulse.yml` и обязана стоять ДО деплоя: красная гвардия останавливает
    установку широкого токена, а не констатирует её задним числом.
17. Репозиторий диспетча приходит в пульс из окружения (`GH_REPO`), не зашит в
    код (тест гвардит).

## Списание воркера edge-harness

18. Воркер edge-harness удалён из CF; его канал (`HARNESS_URL` + `HANDS_TOKEN`)
    не имеет права вернуться в активный код (`scripts/`, `.github/workflows/`,
    `cf-pulse/`, `plugins-src/`, `dsh-edge/`) иначе как через сознательную
    правку гвардий: repo-ci красит возврат, decommission-worker — отменяет
    списание при живых ссылках.
19. Удаление воркера из CF выполняется `decommission-worker.yml` только после
    всех предпосылок: (а) в активном коде нет ссылок на журнал, (б) морда жива,
    (в) канарейка канала записала и прочитала статус через
    `/api/harness/events` — доказательство работы цикла без воркера. Воркера
    уже нет — повторный прогон зелёный no-op.

## Конвейер (оркестратор)

20. PR сливается только при: зелёные обязательные проверки, метка
    `review:ok`, отсутствие конкурирующего открытого PR на ту же задачу.
21. Слияния сериализованы (concurrency `orchestra`, один merge за запуск).
22. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки обновляются из main токеном с правом зажигать проверки.
23. Задача закрывается исполнителем ПОСЛЕ пост-мерж проверки, с приложением
    улик в задаче. Ключевые слова авто-закрытия (`Closes|Fixes|Resolves #N`)
    в теле PR запрещены: контракт отклоняет такой PR (GitHub закрыл бы задачу
    при слиянии), оркестратор задачи не закрывает никогда — мерж доказывает
    PR, а не готовность задачи. После слияния оркестратор ставит на задачу
    напоминание о пост-мерж проверке.

## Автономный воркер (конвейер пула)

24. Пульс оркестратора: если в пуле есть свободная задача (метка `task`, открыта,
    без assignee и без открытого PR на неё) и нет worker-рана в статусе
    `in_progress`/`queued` — ровно один `workflow_dispatch` `worker.yml` за
    запуск. Сбой диспатча не роняет планировщик: слияния важнее подряда
    воркеру.
25. Свободных задач нет → job воркера зелёный без действий: «делать нечего» —
    не ошибка, а штатный простой конвейера.
26. Захват задачи воркером — назначение, подтверждённое фактом на задаче (не
    кодом возврата шага). Работа идёт в ветке `agent/N-slug` от свежего
    origin/main (вход — `scripts/git/task-branch`), исполняет её DSH headless;
    транспорт (scripts/worker/task.sh) не принимает за агента содержательных
    решений.
27. Итог запуска воркера оценивается по видимому артефакту, а не по коду
    возврата: открытый PR → комментарий в задачу (ссылка + хвост отчёта) и
    Telegram, job зелёный; эскалация по playbook (метка `blocked` — то, что
    есть только у владельца) → комментарий и Telegram, job зелёный; иначе →
    комментарий с хвостом лога и Telegram, job красный. Все наружные тексты
    проходят маскирование секретов до отправки.
