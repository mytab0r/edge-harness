# Спека: журнал, задачи, heartbeat (морда ↔ руки)

Источник поведения: реализация в `cf-worker/src/harness.ts` + `api-spec.json`
(маршруты), проверено тестами `cf-worker/test/` и канарейками. Эта спека —
требования, по которым любое изменение поведения обязано пройти.

## Журнал событий

1. Событие идентифицируется парой `(task_id, seq)`; `UNIQUE(task_id, seq)` в БД.
   Повторная доставка батча (ретрай сети, повторный запуск job) не создаёт дублей.
2. `seq` job'а — положительные числа начиная с 1, уникальные в рамках задачи.
   Клиент рук засевает счётчик максимумом с сервера — повторный запуск job'а
   той же задачи продолжает нумерацию, а не теряет события.
3. Системные события (`task_queued`, `task_dispatched`, `dispatch_failed`,
   `first_heartbeat`) пишутся с отрицательными seq и `source=system`.
4. Replay: `GET /api/events?after=<id>&limit=`, опционально `?task_id=`.
   Ответ несёт `has_more`/`next_after` и заголовки `x-has-more`/`x-next-after`.
5. Любой другой код ответа API — JSON `{"error": {"code", "message"}}`; коды
   стабильны и проверяются тестами, тексты локализуются в `src/messages.ts`.

## Живой поток

6. `GET /api/events.live?after=<id>` — WebSocket только на приём
   (`acceptWebSocket`, гибернация). Клиентская запись закрывается кодом 1008.
7. Без `Upgrade: websocket` маршрут отвечает 400 `need_websocket_upgrade`.
8. События с `id <= after` повторно не доставляются; рассылка — всем живым
   сокетам, умирающий сокет не влияет на остальных.

## Статус рук

9. «Руки живы» = есть запись heartbeat и `now - ts < HEARTBEAT_FRESH_MS`
   (константа в `src/config.ts` — единственное место правды).
10. Событие `job_end` гасит «руки живы» немедленно, не дожидаясь порога.

## Очередь задач

11. `POST /api/tasks` создаёт задачу (`queued`) и дёргает
    `repository_dispatch` (event_type `harness-task`, payload `{task_id}`).
12. Без `GH_DISPATCH_TOKEN`/`GH_REPO` ответ честный: 201 +
    `dispatch: "not_configured"` — «возможности нет» отличается от «сломана».
13. Первая heartbeat-отметка задачи фиксирует `latency_ms`
    («dispatch → первый heartbeat») — данные замера ADR 0003.
14. Переходы статуса задачи: `queued → dispatched` (успешный dispatch),
    `→ running` (`job_start`), `→ done|failed` (`job_end`, `result`).

## Watchdog зависших задач

14.1. Задача, висящая в `dispatched` дольше `LIMITS.staleDispatchMs` без признаков
рук, видна в `status.stale_dispatch` (количество и возраст старшей) — морда
показывает это как ненормальное состояние.
14.2. Система НЕ переспавнивает и не лечит зависшую задачу сама (design.md,
«чего дизайн намеренно не решает») — только индикация и данные для решения.
14.3. Порог объявлен один раз в `src/config.ts`; требование протестировано
состариванием задачи через SQL DO (`runInDurableObject`).

## Аутентификация

19. Браузер входит обменом: `POST /api/session` с `Authorization: Bearer <HANDS_TOKEN>`
    отвечает подписанной сессионной кукой `harness_session` (HMAC-SHA256 от
    `SESSION_SECRET` над сроком жизни; HttpOnly, SameSite=Strict, Secure; TTL —
    `SESSION.ttlMs` в `src/config.ts`, единственное место правды). Сам HANDS_TOKEN
    в браузере не хранится и повторно не передаётся (образец — dsh-edge,
    `docs/research/11-dsh-edge.md`). `DELETE /api/session` сбрасывает куку
    (Max-Age=0); у HttpOnly-куки это умеет делать только сервер.
20. Запросы к `/api/*` авторизуются либо сессионной кукой (браузер, включая
    WebSocket — кука уходит с апгрейдом сама), либо `Authorization: Bearer`
    (job, `scripts/hands`). Единственное исключение — webhook-вход
    автоматизаций `POST /api/webhooks/<id>` (#116): аутентификация подписью
    `X-Harness-Signature: sha256=<hex HMAC-SHA256(raw body,
    AUTOMATION_WEBHOOK_SECRET)>` — у внешнего отправителя нет ни куки, ни
    Bearer; без подписи/с неверной — 401 и событие в журнале. Ни один запрос
    к `/api/*` не несёт токен в URL.
21. Запрос с `?token=` отклоняется громко: 400 `query_token_removed`, даже если
    значение совпадает с HANDS_TOKEN — класс «токен в URL → логи CF и история
    браузера» закрыт целиком, а не только для WS.
22. Отсутствующая, протухшая или подделанная кука без валидного Bearer — 401
    `unauthorized`. Без `SESSION_SECRET` обмен отвечает 500
    `session_secret_missing` («возможности нет» отличается от «сломана»).

> **П.18 ниже устарел.** Актуальное поведение (стадия приёмки закрывает

15. PR сливается только при: зелёные обязательные проверки, метка
    `review:ok`, отсутствие конкурирующего открытого PR на ту же задачу.

> **П.16 ниже устарел.** Актуальное поведение (цикл слияний внутри одного

> `schedule`, #297) — в дельта-спеке
> [`orchestra-event-merge-loop/specs/journal-tasks-hands/spec.md`](../changes/orchestra-event-merge-loop/specs/journal-tasks-hands/spec.md);
> вливается сюда только при архивации change'а.

16. Слияния сериализованы (concurrency `orchestra`, один merge за запуск).
17. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки обновляются из main токеном с правом зажигать проверки.

    ### Резолвер «PR → задача» для контекста AI-ревью (#259)

    17.1. Задача, которую AI-ревью (второй гейт) показывает модели как контекст
        PR, — результат ОДНОГО резолвера (`scripts/lib/task_ref.resolve_pr_task`):
        имя agent-ветки `agent/<N>-<slug>`, затем декларация номера первой
        строкой тела PR (`declared_tasks`, то же правило, что и в п.17). Любое
        упоминание номера в прозе описания (`task_ref.extract_task_refs`/
        `references_task`) для этого вопроса не годится — этим классом бага
        ai_review.py путал задачу PR с первым попавшимся числом в тексте (живой
        замер: #253 судили по #120 вместо объявленного #227, #248 — по #119
        вместо #201, #247 — по #43, #263 — по #4). Ни один источник не дал
        числа → у PR нет задачи из пула для контекста ревью, это не ошибка.
        Правила `reap_stale`/`unhealthy_pulls`/`after_merge` намеренно
        продолжают использовать широкую семантику упоминания — сужение там
        было бы регрессией, не улучшением.

    17.2. Контракт не выполняет ни одного изменяющего вызова (авто-назначение
        исполнителя, сверку дубликата PR) над задачей, признанной непригодной.
        Пригодность считается ОДИН раз, до любых действующих вызовов
        (`contract_check.task_eligibility_problems`): задача существует как
        issue (не PR), открыта, несёт метку `task`, не несёт `blocked`.
        Непригодна хотя бы по одной причине — контракт только докладывает
        причину(ы), дальше по этой задаче не действует вовсе (живой случай:
        авто-назначение на уже закрытую задачу до этого пункта, PR #359).

18. Задача закрывается исполнителем ПОСЛЕ пост-мерж проверки, с приложением
    улик в задаче. Ключевые слова авто-закрытия (`Closes|Fixes|Resolves #N`)
    в теле PR запрещены: контракт отклоняет такой PR (GitHub закрыл бы задачу
    при слиянии), оркестратор задачи не закрывает никогда — мерж доказывает
    PR, а не готовность задачи. После слияния оркестратор ставит на задачу
    напоминание о пост-мерж проверке.

## Самообновление морды

23. DO-пульс на каждом тике сверяет версию морды dsh-edge (публичный
    `GET /api/health` — поле `version`) с последней стабильной в npm
    (`registry.npmjs.org/dsh-edge/latest`).

    ### Сигнал дрейфа пина (#134)

    23.1. Пульс оркестратора на каждом прогоне сверяет пин source-build морды
        (`dsh-edge/upstream.json`) с релизами апстрима (теги `pawaca/dsh-edge`):
        сравнивается то, что реально определяет версию морды, — пин, а не
        npm-latest (сверка п.23 диспатчит деплой, который при непустом
        манифесте пересобирает тот же пин и версию изменить не может).
    23.2. Релиз апстрима семверно новее тега пина (или пин вообще не на теге
        релиза) — сигнал: комментарий-маркер `[дрейф пина: <тег>]` в задачу
        #134, метка `update-available`, Telegram. Один сигнал на релиз: новый
        релиз — новая цель маркера — новый сигнал; на ту же цель повторов нет.
    23.3. Метка `update-available` снимается тем же прогоном автоматически,
        когда пин снова стоит на новейшем стабильном релизе (газ метки —
        docs/agents/LABELS.md). Сбой самой сверки (сеть, API, форма пина,
        усечение страницы тегов) не роняет планировщик, но не молчит: ⚠️-строка
        в отчёте пульса — сломанная сверка прячет дрейф так же надёжно, как её
        отсутствие.

24. Расхождение при истёкшем троттле → `workflow_dispatch`
    `deploy-dsh-edge.yml`. Пометка попытки пишется в storage до диспетча —
    упавший деплой не превращает пульс в штурм (троттл — константа в
    `src/config.ts`, единственное место правды).
25. Сбой сверки (сеть, реестр, неожиданный формат) не роняет пульс: тик
    перезакладывается до проверки, ошибка уходит в observability. Морда и
    очередь задач при этом продолжают работать.

## Автономный воркер (конвейер пула)

26. Пульс оркестратора: если в пуле есть свободная задача и нет worker-рана в
    статусе `in_progress`/`queued` — ровно один `workflow_dispatch`
    `worker.yml` за запуск. Свободная = открыта, метка `task`, без assignee;
    открытый PR без исполнителя задачу из пула НЕ исключает — она остаётся
    кандидатом как задача на доводку существующего PR (#245). Финальное
    решение «свободна ли задача» принимает воркер атомарным claim'ом (#121);
    фильтр планировщика — экономия прогона, не защита. Диспатч разрешён
    только при неактивном предохранителе конвейера (#120). Сбой диспатча не
    роняет планировщик: слияния важнее подряда воркеру.
27. Свободных задач нет → job воркера зелёный без действий: «делать нечего» —
    не ошибка, а штатный простой конвейера. Тот же зелёный no-op — при отказе
    claim'а («занята другим каналом», #121) и при живом другом прогоне
    воркера (гвардия дублей): работу делает тот, кто первый захватил.
28. Захват задачи воркером — атомарная аренда (ADR 0006, #121):
    `scripts/lib/claim_task.py claim` серверно создаёт замок
    `refs/locks/task-N` и тем же вызовом ставит назначение и след в задаче.
    Назначение — видимость, а не защита; защита от гонки каналов — замок,
    проигравший гонку получает отказ. Работа идёт в ветке `agent/N-slug` от
    свежего origin/main (вход — `scripts/git/task-branch`); если на задачу
    уже открыт PR без исполнителя, воркер доводит его ветку, второй PR не
    открывает (#245). Исполняет задачу DSH headless; транспорт
    (scripts/worker/task.sh) не принимает за агента содержательных решений.
29. Итог запуска воркера оценивается по видимому артефакту, а не по коду
    возврата: открытый PR → комментарий в задачу (ссылка + хвост отчёта) и
    Telegram, job зелёный; эскалация по playbook (метка `blocked` — то, что
    есть только у владельца) → комментарий и Telegram, job зелёный; иначе →
    комментарий с хвостом лога и Telegram, job красный. Все наружные тексты
    проходят маскирование секретов до отправки.

## Инбокс владельца (#20)

30. Приём: `POST /api/messages/ingest` понимает плоскую форму (source,
    source_msg_id, chat_id, sender_id, sender_name, text) и сырой Telegram
    update (update_id, message/from/chat). Идентификаторы нормализуются в
    строки: Telegram шлёт их числами, и без нормализации реальный апдейт
    падает мимо `UNIQUE(source, source_msg_id)`.
31. Ключ идемпотентности: явный `source_msg_id`, иначе `update_id` (ключ
    ретраев Telegram), иначе `message.message_id`; без идентификатора — 400
    `need_source_msg_id` (идемпотентность без ключа невозможна — молча
    генерировать одноразовый id значит терять ретраи в дублях). Повтор приёма
    возвращает существующую строку (`exists`), дубли не создаются. Правило
    одно для обоих приёмных маршрутов — `ingest` и ручной
    `POST /api/messages`.
32. Маршрут админско-релейный и авторизуется как все `/api/*` (пп. 20–22).
    Прямая доставка вебхуком Telegram не подключена — для неё нужен свой
    секрет; релей/админ шлёт update'ы сам.
33. Разбор ведёт пульс DO на каждом тике (водитель назван, ручной
    `POST /api/messages/process` — администрирование и повтор). Захват
    атомарный (`new → processing` условным UPDATE): двойная обработка
    исключена. Запись финального статуса и возврат в `new` — CAS по моменту
    захвата (`processing_ts`): проходка, потерявшая владение (ватчдог вернул
    сообщение в очередь), чужой результат не перезаписывает. Классификация
    детерминированная: directive / chat / doc_edit / raw; серия от одного
    отправителя в пределах `LIMITS.messageGroupWindowMs` связывается
    (`grouped_with`).
34. Директива и правка доков (`doc_edit`) → issue под узким `GH_ISSUES_TOKEN`
    (только Issues:RW, ADR 0011) с метками `task`+`source:inbox` — у каждой
    директивы (включая императивы о доках) есть issue-след в пуле, kind
    сообщения уезжает в тело issue. Не заданный токен, сеть, 5xx/429 —
    повторяемая ошибка:
    сообщение возвращается в `new` до `LIMITS.messageMaxAttempts` попыток,
    затем честный `failed` с ошибкой. Прочие 4xx — `failed` сразу (штурм
    бесполезного повторения не нужен). Газ после устранения причины —
    `POST /api/messages/process {"retry_failed": true}` (обнуляет попытки).
    Вызов GitHub ограничен `LIMITS.messageIssueFetchTimeoutMs` — заведомо
    меньше порога ватчдога (гвардится тестом): висящий вызов не доживает до
    ретрая другой проходки. Публичный текст issue маскируется тем же классом
    паттернов секретов, что и остальные наружные тексты (`dsh-ci.sh::redact`:
    nvapi-/sk-/ghp_/github_pat_), причём ДО усечения заголовка — усечённый
    секрет короче минимума паттерна уже не маскируется и утекает хвостом;
    в GitHub уходит именно усечённый заголовок (потолок 80 символов —
    заведомо ниже 422-потолка GitHub в 256, иначе разобраемое сообщение
    честно failed по кривой форме); факт маскирования виден в
    `result.secrets_redacted`. Командные слова директив — один список для
    классификатора и чистки заголовка (`DIRECTIVE_WORDS`).
35. `raw` никогда не возвращается в очередь: классификатор детерминирован,
    повтор не меняет вердикт, а копящийся сырьём `new` голодало бы. Неразобранное
    уходит в `ignored` на ручной триаж (видно в списке и счётчиках).
    `chat` — `done` с пометкой `classified_for_manual_review`:
    автоматического ответа в фазе 1 нет, дальнейшее решает триаж.
36. Ватчдог: `processing` дольше `LIMITS.messageStuckProcessingMs` — пульс
    возвращает сообщение в `new` (изолят умер посреди внешнего вызова);
    исчерпанный кап попыток проверяется на этом же пути — такой `processing`
    получает честный `failed` со `stuck_reclaimed` (газ тот же —
    `retry_failed`), вечный круг reclaim → claim исключён.
    Ни одно сообщение владельца не зависает навсегда; все статусы видны в
    `GET /api/messages` и в `status.messages`.
37. Пагинация списка согласована с сортировкой: выдача newest-first
    (`ts DESC, id DESC`), курсор `after` — по id (строго `< after`),
    `has_more`/`next_after` в теле и заголовках; обход списка без дублей и
    пропусков, в том числе при равных `ts`.
