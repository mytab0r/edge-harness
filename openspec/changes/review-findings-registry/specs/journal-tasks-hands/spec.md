# Дельта-спека: журнал (journal-tasks-hands) — реестр находок ревью вместо задачи-хвоста (#1262, объединяет #1217)

## REMOVED: Задача-хвост незакрытого чеклиста при слиянии

Было (openspec/changes/review-remark-checklist/specs/journal-tasks-hands/spec.md,
#462): `after_merge` заводил РОВНО ОДНУ задачу пула («Хвост чеклиста ревью
PR #N», `create_pool_issue`) со ссылкой на PR и перечнем незакрытых пунктов,
идемпотентно по заголовку.

Снято: замер 2026-09-14 (#1262) показал 0 закрытых из 110 заведённых —
задача пула стоит аренды/ветки/PR/прогона воркера ради находки ценой в одну
строку комментария; тайбрейк приоритета пула (номер issue) ставит хвост в
конец его же тира по построению, поднятие приоритета (#1178) вытеснило
барьерные задачи (#1179 — контрмера). `scheduler.py::after_merge` БОЛЬШЕ НЕ
зовёт `create_pool_issue` для чеклиста — гвардия
`test_scheduler.py::test_after_merge_never_calls_create_pool_issue_for_review_findings`
доказывает мутацией.

## ADDED: Реестр незакрытых находок ревью, ключ — файл

Требование: незакрытые пункты чеклиста ревью (`review_checklist.
unresolved_findings`, третья категория находок #462) переносятся при
слиянии PR в файловый реестр (`scripts/lib/review_findings.py`), а не в
задачу пула. Ключ записи — путь затронутого файла, не PR и не раунд ревью:
находка привязана к области кода, а не к процессу её обнаружения.

Носитель — JSON (`findings.json`) на выделенной ветке данных
`data/review-findings` (не `main` — «прямой пуш в main не проходит
обязательные проверки», тот же класс решения, что `data/pipeline-health`,
#882). Запись — GitHub Contents API (GET текущего blob + PUT нового
содержимого), единственная точка мутации — `scheduler.py::after_merge`
(`contents: write` есть у workflow `orchestra` целиком, НЕТ у job'а
`ai-review`/`verdict`, #939 явно не возвращает `issues: write` и подавно не
даёт `contents: write`).

Каждая запись реестра: `{id, file, title, detail, source_pr, opened_at,
status}`. `id` — последовательный счётчик реестра (не UUID — должен быть
коротким и произносимым моделью). `status` — `open`/`closed`.

Сценарий: PR #200 сливается с 2 незакрытыми пунктами чеклиста, один несёт
`ФАЙЛ: scripts/lib/foo.py`, другой — без файла → реестр получает ОДНУ новую
запись (file=`scripts/lib/foo.py`), вторая остаётся видна только в чеклисте
слитого PR (не теряется, но и не переносится — `after_merge` отчитывается
числом `skipped`).

## ADDED: Обязательное поле ФАЙЛ у блока ЗАМЕЧАНИЕ

Требование: контракт `ai_prompt.md` для блока `ЗАМЕЧАНИЕ` несёт ВТОРОЙ
обязательной строкой `ФАЙЛ: <путь>` (тот же приём, что `МАСШТАБ` у блока
`ЗАДАЧА`, #426) — `scripts/lib/review_checklist.py::parse_remarks`/
`REMARK_FILE_RE`. Отсутствие строки не отбрасывает блок целиком (проза
находки не теряется, живёт в чеклисте тела PR как раньше), но лишает
находку возможности попасть в реестр при слиянии — `file=None` явно
пропускается `review_findings.sync_after_merge` и учитывается в `skipped`.

## ADDED: Выписка находок реестра по файлам PR в промпте ревью

Требование: `ai_review.py::cmd_gather` собирает выписку открытых находок
реестра, чей `file` совпадает с одним из файлов диффа текущего PR
(`ai_review.py::findings_section`, читает реестр через Contents API,
`contents: read` достаточно — новых прав job'у не требуется), и подставляет
её в промпт плейсхолдером `$findings_section`. Сбой чтения реестра (сеть,
битый JSON) не роняет `gather` — деградирует на явное «недоступно», не
молчит «находок нет» (`review_findings.render_unavailable`, тот же приём,
что `defect_classes_section`).

Сценарий: реестр несёт открытую находку `[5] Устаревший порог — path.py`;
PR трогает `path.py` → промпт получает секцию с этой находкой; PR не трогает
`path.py` → секция для этого PR её не содержит вовсе (находка не
подсвечивается зря).

## ADDED: Закрытие находки реестра — НАХОДКА-ЗАКРЫТА и маркер тела PR

Требование: модель, видя в выписке находку, которую код уже чинит, помечает
её строкой `НАХОДКА-ЗАКРЫТА: <id>` в ответе (не блок-забор — одна строка на
находку, тот же стиль, что `КЛАСС:`). `ai_review.py::cmd_verdict` разбирает
эти строки (`review_findings.parse_resolved_ids`) и сливает id в маркер ТЕЛА
PR (`<!-- ai-review:resolved-findings:… -->`,
`review_findings.merge_resolved_marker`, объединение — не перезапись, id из
прошлых раундов не теряются, если новый раунд их не повторил). Комментарий
вердикта упоминает закрытые id прозой для человека, машинного факта в шапке
комментария не несёт (одно место правды — тело PR).

`scheduler.py::after_merge` при слиянии читает маркер ИЗ УЖЕ ПОЛУЧЕННОГО
`pull["body"]` (без отдельного сетевого запроса) и закрывает соответствующие
записи реестра (`review_findings.close_findings`) в ТОЙ ЖЕ мутации, что
перенос новых незакрытых пунктов.

Сценарий: находка `[5]` открыта по `path.py`; PR, чинящий `path.py`, получает
в выписке эту находку, модель отвечает `НАХОДКА-ЗАКРЫТА: 5`; тело PR получает
маркер; при слиянии `status` находки `[5]` в реестре становится `closed`.
Неисправленная находка (модель не упомянула id) остаётся `open` и всплывёт
снова при следующем PR, трогающем `path.py`.
