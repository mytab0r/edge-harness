# review-findings-registry: файловый реестр незакрытых находок ревью вместо задачи-хвоста (#1262, объединяет #1217)

Задачи: #1262, #1217. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md). Развилка
решений — [design.md](design.md).

## Зачем

Замер 2026-09-14 (#1262, ревизия пула): `scheduler.py::after_merge` заводит
«Хвост чеклиста ревью PR #N» через `create_pool_issue` на каждом слиянии с
неотмеченным чеклистом (#462). 110 таких задач открыты, **0 когда-либо
взято в работу** (0 назначенных, 0 веток `agent/<хвост>-*`, 85/110 несут
`stale-unclaimed`). Приток ~19/сутки, ~27% всего пула. Находки при этом не
мусор: из 18 прочтённых целиком (~64 находки) пустых нет, из 12 машинно
проверенных утверждений против `main` 11 живы. Суммарно потеряно бы 412
находок при слепом закрытии.

Тайбрейк приоритета пула — номер issue по возрастанию: хвост по построению
всегда самая свежая issue, то есть всегда в конце своего тира — очередь до
него не доходит никогда при текущем темпе притока/закрытия. Обратное уже
испытано: `checklist_tail_labels.py` (#1178) поднял 62 хвоста приоритетом
`area:process` — очередь забилась хвостами, барьерные задачи
(#1161/#1172/#1149/#1141/#1160/#1109) ушли в конец, потребовался НОВЫЙ тир
приоритета `impact:system` (PR #1179) специально чтобы обойти хвосты. Дефект
не в приоритете, а в НОСИТЕЛЕ: находка ценой в одну строку комментария стоит
аренды, ветки, PR, критерия приёмки и прогона воркера — самого дефицитного
ресурса конвейера (18 прогонов/сутки, `concurrency: group: worker`).

Родственный класс — #1217 (живой случай PR #542): находка ревью не переживает
следующий раунд ревью ТОГО ЖЕ PR (второй вердикт не повторил находку первого
круга — она пропала бы, если бы канал не прогнал тесты сам). Обе задачи — один
класс дефекта («находка ревью теряется»), проявляющийся в двух разных точках
жизненного цикла PR (до слияния и после); один реестр закрывает обе точки —
второй реестр рядом создал бы второй источник правды об одном и том же факте.

## Что делается

- Единый файловый реестр незакрытых находок, ключ — затронутый файл, не PR
  и не раунд ревью: `scripts/lib/review_findings.py`, JSON на выделенной
  ветке данных `data/review-findings` (тот же класс решения, что
  `data/pipeline-health`, #882 — не main, «прямой пуш в main не проходит
  обязательные проверки»). Запись — GitHub Contents API (GET текущего
  blob + PUT), не git-клон: файл маленький, а Contents API уже используется
  этим же процессом для похожей проверки (`scheduler.py::docs_missing`).
- Контракт `ai_prompt.md` — блок `ЗАМЕЧАНИЕ` получает обязательное второе
  поле `ФАЙЛ: <путь>` (тот же приём, что `МАСШТАБ` у блока `ЗАДАЧА`); модель
  получает выписку открытых находок реестра по файлам PR
  (`$findings_section`, `ai_review.py::findings_section`) и закрывает
  исправленные строкой `НАХОДКА-ЗАКРЫТА: <id>` — не переоткрывая их заново.
- `scripts/orchestra/scheduler.py::after_merge` БОЛЬШЕ НЕ зовёт
  `create_pool_issue` для чеклиста: незакрытые пункты
  (`review_checklist.unresolved_findings`, структурная форма с файлом)
  переносятся в реестр через `review_findings.sync_after_merge` — ЕДИНСТВЕННАЯ
  точка мутации (`contents: write` есть у workflow `orchestra` целиком, НЕТ у
  job'а `ai-review`/`verdict`, #939 не возвращает `issues: write` и подавно
  не даёт `contents: write`).
- Закрытые id живут МАРКЕРОМ В ТЕЛЕ PR (`<!-- ai-review:resolved-findings:…
  -->`, `review_findings.merge_resolved_marker`), не в комментарии: тот же
  выбор носителя, что чеклист `ЗАМЕЧАНИЕ` — `after_merge` уже читает
  `pull["body"]` без отдельного сетевого запроса на каждое слияние;
  сканирование истории комментариев ради этого поля стоило бы лишнего GET на
  каждое слияние и завело бы второе место правды о том же факте.
- Пункты без `ФАЙЛ` (чеклист, начатый до этой правки, или блок без
  обязательного поля) не ключуются реестром — остаются видны только в
  чеклисте самого PR; `after_merge` считает и показывает это в отчёте
  (`skipped`), не теряет тихо (то же правило репозитория «половина находки
  хуже отсутствия», применённое здесь в обратную сторону — без файла реестру
  некуда вернуть находку при следующем ревью).
- Миграция 110 существующих задач-хвостов — часть этой же работы, см.
  [tasks.md](tasks.md) и `scripts/lib/migrate_review_findings.py`. Закрывать
  задачи МОЖНО ТОЛЬКО ПОСЛЕ того, как реестр наполнен их содержимым — обратный
  порядок уничтожает 412 живых находок.
- Метки хвостов (`area:process` у 62 из 110, `checklist-tail:inherited`)
  массово НЕ трогаются: реестр их обессмысливает, а правка была бы отменена
  своей же миграцией (закрытие issue не требует снятия метки).
  `checklist-tail-triage.yml`/`checklist_tail_labels.py` помечены
  вестигиальными (docs/agents/INFRA-GH.md, docs/agents/LABELS.md) — донашивают
  110 существующих, кандидат на удаление отдельной задачей после миграции.

## Почему не проверка приоритета (#1178/#1179 уже пробовали)

См. «Зачем» выше — оба состояния (без приоритета/с приоритетом) уже измерены
и оба плохи. Эта правка не трогает приоритет пула вовсе: реестр не участвует
в пуле, значит вопрос приоритета для новых находок больше не встаёт.

## Стоимость выписки в промпте

`findings_section` добавляет РОВНО те находки, чей `file` совпадает с одним
из файлов диффа этого PR — не весь реестр целиком. На типичном PR (1-10
файлов) и типичной плотности находок (медиана ~2237 знаков на находку,
живой замер #1262) выписка добавляет от одной строки («находок нет») до
нескольких абзацев — на 1-2 порядка меньше, чем уже идущие в промпт
`rules_section` (весь `AGENTS.md`+`PROTOCOL.md` дословно) и `context_pack`
(полный diff).

Риск «файл, задетый очень многими находками» — НЕ гипотеза: живой прогон
миграции (`migrate_review_findings.py plan`, 2026-09-14, реальные 111
хвостов/415 находок) без потолка дал 194 находки без точного файла →
**1611** записей broadcast (медианный фанаут 15 файлов на находку, максимум
**100** — PR #409). Broadcast на такое число файлов — уже не «выписка по
файлу», а шум в промпте любого PR, тронувшего любой из сотни файлов, и
закрытие одной копии не снимает остальные. Решено НЕ спекулятивным потолком
на находки в выписке (что предлагалось изначально), а потолком САМОГО
broadcast при миграции (`MAX_BROADCAST_FANOUT = 20`,
`migrate_review_findings.py`): PR с фанаутом свыше потолка уходит в ручной
разбор целиком, не частично — с потолком реальный прогон даёт 221 exact +
194×(≤20) broadcast, максимум фанаута ограничен построением. Живая
эксплуатация (не миграция) этому риску не подвержена вовсе — там `ФАЙЛ:` у
блока `ЗАМЕЧАНИЕ` всегда РОВНО один путь, broadcast как механизм существует
только в миграционном скрипте.

## Что происходит с находкой в файле, который никто не трогает

Честно: лежит в реестре вечно, до тех пор пока файл снова не попадёт в
ревьюируемый диффе. Механизма принудительного периодического пересмотра
реестра эта правка не заводит — тот же выбор, что у чеклиста тела PR (#462):
находка возвращается, когда её область снова становится актуальной, не по
таймеру. Если это окажется проблемой на практике (реестр копит находки по
файлам, которые перестали меняться, но остаются важными), это отдельная,
измеримая позже задача — не гадание сейчас.

## Что вне рамок

- Автоматическая переоценка ценности/приоритета находок реестра — как и у
  прежнего механизма, решение человека (proposal.md #462), машины здесь нет.
- Регулярный аудит реестра (сколько находок висит дольше N дней) — не
  измеряется здесь; при необходимости — отдельная узкая задача поверх уже
  готового `findings.json`.
- Удаление `checklist-tail-triage.yml`/`checklist_tail_labels.py` — только
  ПОСЛЕ миграции 110 задач, отдельной задачей (см. tasks.md, последний пункт).
