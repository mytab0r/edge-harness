# design: носитель реестра находок ревью (#1262/#1217)

## Развилка 1 — где живёт реестр

| Вариант | Плюс | Минус | Решение |
|---|---|---|---|
| Issue пула (текущее — задача-хвост) | Уже есть инфраструктура (create_pool_issue) | Именно это и есть измеренный дефект — 0/110 закрытых, пул — самый дефицитный ресурс | Отвергнут (это и есть проблема, не решение) |
| Комментарий на постоянную issue-«доску» | Видим в UI GitHub | Требует парсинга прозы комментария при каждом ревью PR — то же самое, что #1217 уже показал ненадёжным (вердикт не гарантированно повторяет прошлые находки); issues:write снова нужен job'у verdict — прямо запрещено мандатом #939 | Отвергнут |
| Файл в main, обновляемый PR-ом | Виден в обычном дифф-ревью, версионируется git-историей | Каждое обновление реестра — отдельный PR = отдельный ai-review прогон = именно тот расход, который мы пытаемся убрать; либо обход через прямой пуш в main — запрещено правилом репозитория | Отвергнут |
| **Файл на выделенной ветке данных `data/review-findings`** | Не main (не требует PR на каждое изменение, правило «прямой пуш в main не проходит обязательные проверки» относится к main, не к произвольной ветке); прецедент есть — `data/pipeline-health` (#882); пишет ТОЛЬКО `orchestra.yml` (единственный writer, concurrency-группа `orchestra` уже сериализует все его прогоны — гонки физически нет) | Не виден в обычном PR-дифф-ревью (это фича, не баг — реестр не должен провоцировать ревью самого себя) | **Выбран** |

## Развилка 2 — как писать (git clone+push vs Contents API)

`data_branch_writer.py` (используется `pipeline_health.py`) — полноценный
git-клон в `$RUNNER_TEMP`, append+push с ретраем на гонку конкурентного
писателя. Для реестра находок это избыточно: единственный писатель
(`scheduler.py` в `orchestra.yml`, concurrency-группа сериализует ВСЕ его
прогоны — второй параллельный писатель физически не существует), файл
маленький (JSON на несколько сотен записей, не растущий лог), retry-на-гонку
здесь был бы кодом, доказывающим отсутствующую опасность.

Выбран путь короче: GitHub Contents API (`GET .../contents/{path}?ref=...`
+ `PUT .../contents/{path}`), тот же примитив, что уже использует этот же
процесс (`scheduler.py::docs_missing` читает `contents/{file}?ref=main`
тем же способом). Один GET, одна проверка условия «есть что писать»,
один PUT — без git-клона, без временной директории, без второго транспорта
рядом с уже существующим `gh()`.

## Развилка 3 — где живёт факт «находка закрыта»: шапка комментария или тело PR

Первая версия правки клала `resolved-findings: <ids>` в шапку
ревью-комментария (`build_comment`, тот же стиль, что `diff:`/`provider:`/
`reason:`). Отклонено ПОСЛЕ первой реализации: `after_merge` тогда обязан
был бы делать ОТДЕЛЬНЫЙ сетевой запрос (`review_labels.latest_ai_comment`,
постраничный обход `issues/{pr}/comments`) НА КАЖДОЕ слияние, даже если
слитый PR не несёт ни одной находки — расход, которого не было у старого
кода (там сетевой вызов шёл ТОЛЬКО под условием `if unresolved:`).

Перенесено в маркер ТЕЛА PR (`<!-- ai-review:resolved-findings:N,M -->`,
`review_findings.merge_resolved_marker`) — тот же выбор носителя, что уже
сделан для чеклиста `ЗАМЕЧАНИЕ` (#462): `after_merge` УЖЕ получает
`pull["body"]` без отдельного запроса (он есть в объекте PR, который и так
читается для решения о слиянии). Оба факта (незакрытые пункты чеклиста и
закрытые id находок) теперь читаются из ОДНОГО уже полученного объекта —
ноль дополнительных сетевых вызовов на слияние без единой находки, ровно
столько же, сколько было у старого кода. Комментарий по-прежнему упоминает
закрытые id прозой (`build_comment`) — для человека, не для машины: второй
машинный источник того же факта не заводится (одно место правды).

## Развилка 4 — обязательность поля ФАЙЛ у блока ЗАМЕЧАНИЕ

Альтернатива — определять файл находки эвристически (первый файл из диффа,
упомянутый в тексте находки). Отвергнута: ненадёжна (проза находки может
упоминать несколько файлов или ни одного буквально), и уже есть работающий
прецедент того же класса решения — `МАСШТАБ` у блока `ЗАДАЧА` (#426):
обязательное структурное поле, отсутствие которого не трактуется молча,
контракт не угадывает. Выбрано: `ФАЙЛ:` вторым полем блока, тот же принцип
парсинга. Пункт без файла не теряется целиком (тот же принцип, что
незакрытый блок ЗАМЕЧАНИЕ/ЗАДАЧА отбрасывается целиком, а не наполовину) —
здесь наоборот, полдела (заголовок+тело) сохраняются в чеклисте PR, теряется
только связь с реестром, что честно посчитано (`skipped`) и видно в отчёте.

## Развилка 5 — миграция 110 существующих хвостов: точный файл или эвристика

410+ находок в существующих задачах-хвостах — свободная проза без
структурного поля `ФАЙЛ` (они заведены ДО этой правки). Три пути:
1. Регэксп-извлечение пути файла из текста находки (многие тела прямо
   называют файл, пример из ревизии: `cf-worker/src/harness.ts`,
   `dependabot_alert_watch.py`).
2. Там, где путь не находится текстом — привязка ко ВСЕМ файлам,
   изменённым породившим PR (broadcast) — находка гарантированно
   всплывёт при следующем ревью любого из этих файлов, ценой более
   широкого показа, чем «точно тот один файл».
3. Отдельный псевдо-путь `_legacy/pr-<N>` — отклонён: такой путь никогда
   не встретится в диффе реального PR, находка фактически ЗАМОРАЖИВАЕТСЯ
   навсегда, что нарушает «ноль потерянных» так же, как старое молчаливое
   закрытие, просто с более честной записью в JSON.

Выбрана комбинация 1→2: сначала точный путь (если находится и существует
в дереве репозитория на момент миграции), иначе broadcast на все файлы PR.
Число по каждой ветке — часть отчёта миграции (`scripts/lib/
migrate_review_findings.py`), не гадание постфактум.
