# Design: детектор регрессии здоровья конвейера, привязанный к слиянию

## 1. Достаточен ли нынешний набор метрик? (проверка, не гипотеза)

`scripts/measure/pipeline_health.py::worker_success_rate` уже существует и
измеряет ровно ту величину, которую владелец спросил («была бы видна доля
успешных прогонов воркера?») — но снимается РАЗ В КАЛЕНДАРНЫЕ СУТКИ
(`should_snapshot` — гейт «не чаще раза в сутки», design.md архивного change
`pipeline-health-self-audit`, §2.2) на COUNT-окне (`WORKER_SUCCESS_WINDOW=30`
последних прогонов, не по времени). `health_regression.py::classify_metric`
дополнительно требует streak ≥ `MIN_REGRESSION_STREAK_DAYS=3` ДНЕЙ подряд и
минимум `MIN_SAMPLES_FOR_BASELINE=5` снятых точек истории.

Ответ на прямой вопрос владельца: **нет, недостаточен для класса регрессии
#878.** Причины две, независимые:

1. Даже если бы снимок случился в идеальный момент (сразу после инцидента),
   для перехода `insufficient_data` → `regression` потребовалось бы 3 дня
   подряд деградации ПОСЛЕ того, как накопится 5 точек истории — на дату
   инцидента (2026-09-10/11) истории снимков практически не существовало.
2. Даже без streak-порога, снимок раз в сутки в лучшем случае ловит
   регрессию на СЛЕДУЮЩИЕ сутки — для инцидента, который начался в 22:54 и
   был обнаружен человеком в 08:xx (~9ч), это опоздание того же порядка, что
   и обнаружение человеком, никакого выигрыша.

Вывод: не нужен НОВЫЙ снимаемый-и-хранимый показатель — нужна ДРУГАЯ
частота вычисления УЖЕ существующей величины. `pipeline_health.collect()`
technически может быть вызван чаще, но снимок пишет строку JSONL на
git-ветку — 96 записей/сутки вместо одной прямо противоречит документированному
мотиву гейта (design.md архивного change: «иначе пульс писал бы новую строку
каждые 15 минут»). Решение здесь — НЕ трогать снимок вовсе, а считать
time-boxed (не count-window) success-rate НА ЛЕТУ прямо в момент проверки,
без записи истории: источник (Actions API) сам по себе всегда свежий.

### Почему не расширять набор до 4-5 метрик, а добавить одну

Владелец просил 3-5 метрик с обоснованием каждой. Здесь — ОДНА новая
величина (time-boxed worker success-rate), потому что она — единственная из
существующего набора, которая (а) прямо измеряет заявленный симптом (доля
успешных прогонов воркера) и (б) физически может считаться из уже читаемых
данных без нового источника. Остальные 5 метрик набора (`merge_throughput`,
`pr_age_p95`, `backlog_total`, `pulse_cadence_ratio`, `do_rows_read_pct`)
измеряют другие классы деградации (пропускная способность очереди, возраст
PR, стоимость DO) — ни один физически не двинулся бы в ответ на регрессию
#878 (сам факт открытия PR воркером не изменился, изменилась только оценка
успеха ЭТОГО прогона) — добавлять их в это rolling-сравнение было бы
раздуванием без пользы, ровно то, от чего владелец предостерёг.

## 2. Алгоритм детектора

```
recent  = success-rate(worker.yml, [now - OBSERVATION_WINDOW_HOURS, now))
baseline = success-rate(worker.yml, [now - OBSERVATION_WINDOW_HOURS - BASELINE_LOOKBACK_HOURS,
                                      now - OBSERVATION_WINDOW_HOURS))
deviation = health_regression.deviation_pct(recent, baseline, "lower_is_worse")
insufficient_data — если recent_n < MIN_SAMPLES_RECENT или baseline_n < MIN_SAMPLES_BASELINE
fire        — deviation >= ESCALATION_THRESHOLD_PCT (100%, тот же порог, что health_regression)
regression  — deviation >= REGRESSION_THRESHOLD_PCT (50%, тот же порог)
ok          — иначе
```

Пороги REGRESSION/ESCALATION взяты ИЗ `health_regression.py` (импорт, не
копия чисел) — «регрессия» и «пожар» в одном репозитории значат одно и то же
отклонение независимо от того, суточный это снимок или часовое окно.

### Почему окна именно такой длины (честно: не выведены из данных, см. §5)

- `OBSERVATION_WINDOW_HOURS = 6` — на реальном каденсе прогонов `worker.yml`
  этого репозитория (интервал от единиц минут до полутора часов, замер
  2026-09-08..11) 6ч почти всегда дают ≥3 прогона (`MIN_SAMPLES_RECENT`).
  Меньшее окно (2-3ч) на реальной истории инцидента ещё не набирает нужного
  числа прогонов к моменту, когда деградация уже видна (см. §4 — на +3-4ч
  recent-окно ещё содержит успехи ДО мержа).
- `BASELINE_LOOKBACK_HOURS = 72` (окно ДО recent-окна) — длиннее наблюдательного,
  чтобы редкий всплеск успехов/провалов не считался «нормой», короче недели —
  цикл разработки этого конвейера явно быстрее недельного (десятки слияний в
  сутки).
- `ATTRIBUTION_LOOKBACK_HOURS = 2 * OBSERVATION_WINDOW_HOURS` (12ч) — окно
  поиска подозреваемых слияний ПЕРЕД `now`, шире recent-окна, потому что
  слияние непосредственно ПЕРЕД началом recent-окна тоже могло вызвать
  наблюдаемое падение (эффект целиком лежит внутри recent-окна, момент
  слияния — чуть раньше его границы).

## 3. Подозреваемые — почему список, а не один PR (проверено на реальных числах)

Дословный вывод `gh api search/issues` (снято 2026-09-11) для окна
2026-09-10T16:54Z..2026-09-11T04:54Z (12ч вокруг PR #878) — ШЕСТЬ слияний:
#771 (20:33), #895 (21:12), #890 (21:22), #640 (22:06), #878 (22:54), #862
(01:41). Ручная попытка исключить «невиновных» через сравнение
собственного pre-merge окна каждого PR с baseline (design.md, «эвристика
предикейтс») даёт неустойчивый результат при таком каденсе: например, #640
слит за 48 минут до #878 — их СОБСТВЕННЫЕ 6-часовые окна «после» почти
целиком совпадают с одним и тем же набором прогонов, различить их по чистой
временной корреляции невозможно НИКАКОЙ статистикой без анализа содержимого
диффа. Решение: детектор называет всех шестерых, явной строкой «корреляция
по времени, НЕ причинность» — честно, не изображая точность, которой нет.

## 4. Доказательство на реальной истории (issue #967, дословный вывод)

Прогон `scripts/orchestra/test_merge_health_watch.py::
test_real_history_878_regression_detected_within_hours` кормит `evaluate()`
ДОСЛОВНЫМ выводом `gh api .../worker.yml/runs` за 2026-09-08..11 (87
прогонов). Результат по часам после слияния PR #878 (22:54:34Z):

| Часов после слияния | Статус | recent (rate/n) | baseline (rate/n) | отклонение |
|---|---|---|---|---|
| 0 | insufficient_data | 100.0%/2 | 46.2%/80 | — |
| 1 | insufficient_data | 100.0%/2 | 46.2%/80 | — |
| 2 | ok | 66.7%/3 | 46.2%/80 | 0.0% |
| 3 | ok | 50.0%/4 | 46.2%/80 | 0.0% |
| 4 | ok | 50.0%/4 | 46.2%/80 | 0.0% |
| **5** | **fire** | **0.0%/4** | **47.6%/82** | **100.0%** |
| 6 | fire | 0.0%/5 | 47.6%/82 | 100.0% |

**Вывод: детектор поймал бы регрессию #878 через 5 часов после слияния** — на
запланированном часовом cron первый прогон, застающий этот момент, назвал бы
`fire` не позднее 6-го часа. Суточный снимок на тот же инцидент не успел бы
среагировать быстрее следующих суток (§1) — выигрыш на порядок.

Честно: на +2..4ч детектор ещё говорит `ok` — recent-окно в эти часы всё ещё
содержит два успешных прогона (21:14, 21:43), случившихся ДО слияния, но
попадающих в 6-часовое скользящее окно вместе с первыми провалами. Это не
дефект окна, а прямое следствие его длины (шире часа) — цена выбора
`OBSERVATION_WINDOW_HOURS=6` вместо, скажем, 2ч: чуть медленнее реагирует,
зато не тонет в шуме единичных прогонов (баланс, а не идеал).

## 5. Реакция на регрессию — три варианта, выбор и почему

Владелец назвал три варианта и попросил обосновать выбор, ориентируясь на
уже работающий образец (`deploy-dsh-edge.yml`: канарейка красная → `wrangler
rollback` → повторная канарейка подтверждает откат → эскалация).

**(a) Авто-revert подозреваемого PR.** Отвергнуто для ЭТОГО класса
регрессии. Образец `deploy-dsh-edge.yml` откатывает ДЕПЛОЙ (артефакт с
доказанно рабочей предыдущей версией — предыдущий деплой уже прошёл
канарейку) на предыдущую версию, про которую ИЗВЕСТНО, что она работала.
У регрессии класса #878 такой гарантии нет: откат кода вернул бы систему в
состояние ДО #878 — то есть вернул бы баг, который #878 как раз чинил
(воркер засчитывал успех по чужому предсуществующему PR, класс #876). Хуже
того, при нескольких подозреваемых (§3, шесть PR в окне) авто-revert должен
был бы выбрать ОДИН — то есть либо гадать (запрещено «Алерт не гадает»),
либо откатывать ВСЕ шесть, из которых минимум четыре, вероятно, невиновны.
Технически применим тот же приём (`if: failure() && ...`, `continue-on-error`,
подтверждение результата после действия) — но не сюда, там, где «предыдущая
версия была доказанно рабочей», не там, где «предыдущее ПОВЕДЕНИЕ конвейера
было доказанно рабочим» (это не одно и то же для эволюционирующего критерия
успеха).

**(b) Задача высшего приоритета с адресным расследованием.** Выбрано.
Механизм приоритета уже существует и используется по назначению
(`free_task.py::issue_priority_key`, `area:process` — тир 1, «задача меняет
правила/механику совместной работы... приёмка после мержа» — расследование
регрессии критерия успеха воркера подпадает под это определение буквально).
Следующий свободный воркер берёт такую задачу РАНЬШЕ обычных задач пула, без
второй инфраструктуры приоритета. «Адресный диспатч» (прямой
`workflow_dispatch worker.yml -f task=N`) сознательно НЕ реализован —
это территория `scheduler.py` (диспетчер задач воркера), которую эта задача
не вправе трогать (issue #967, граница территории); тир-1 приоритет уже даёт
пикап на следующем тике оркестратора (каденс 15 мин) — тот же порядок
скорости, что прямой диспатч, без второго пути дублирования диспетчера.

**(c) Временное отключение затронутого механизма.** Отвергнуто для ЭТОГО
случая по той же причине, что (a): «затронутый механизм» здесь — сам
критерий успеха воркера (`dsh_worker_run_is_success`, #878). Отключить его —
значит вернуться к permissive-критерию ДО #878, то есть к исходному багу.
Не общее правило «(c) всегда плохо» — для ДРУГОГО класса регрессии (например,
внешний провайдер начал массово таймаутить, конвейер отвечает штатно) временно
выключить зависящий от него шаг было бы разумно; здесь неприменимо структурно.

### Газ и защита от цикла (обязательное требование владельца)

- **Газ.** Критерий готовности задачи-расследования — следующий прогон
  детектора видит `ok` по тому же окну (метрика вернулась к baseline);
  задача закрывается ЧЕЛОВЕКОМ/агентом по факту фикса, НЕ автоматически —
  тот же принцип, что уже принят у `health_audit.py` (design.md архивного
  change, §4: «критерий готовности — метрика вернулась к baseline,
  проверяется следующим снимком, не декларацией исполнителя»), не новое
  решение.
- **Защита от цикла.** Реакция этого детектора — создание/комментирование
  issue и отправка сообщения (Telegram/issue-комментарий). НИ ОДНО из этих
  действий не порождает git-событие (push/merge) — физически не может
  повторно триггернуть сам себя или другой автоматический откат. Это СИЛЬНЕЕ
  защиты, которую несёт образец `deploy-dsh-edge.yml` (там `wrangler
  rollback` — тоже не git-операция, но деплой воркера теоретически мог бы
  среагировать на что-то ещё; здесь такого риска нет вовсе по конструкции
  канала).

## 6. Дедуп и потолок алертов (не спам при затянувшемся инциденте)

Дедуп по отпечатку `merge-health:worker_success_rate:<календарный час recent-окна>`
(подстрока в теле открытой issue с меткой `area:process`) — тот же приём, что
`health_audit.py::find_open_task` (поиск по отпечатку), другая единица
времени: там сутки (детекция суточная), здесь час (детекция часовая).
Повторный `fire` в течение того же часа — не новая задача, комментарий-улика
в уже открытую. Эскалация (issue #120 + Telegram) не имеет отдельного
дедупа сверх этого — при активном инциденте владелец предпочитает частые
сигналы редким пропущенным (тот же выбор, что у `pulse_guard.escalate`
в остальном конвейере).

## Не подтверждено

1. Пороги `OBSERVATION_WINDOW_HOURS`/`BASELINE_LOOKBACK_HOURS`/
   `MIN_SAMPLES_RECENT`/`MIN_SAMPLES_BASELINE`/`ATTRIBUTION_LOOKBACK_HOURS` —
   выбраны по разумной аналогии и проверены на ОДНОМ реальном инциденте
   (#878), не выведены статистически из множества независимых регрессий —
   такой истории физически не существует. Подбор по факту следующих
   инцидентов — отдельная, не сделанная здесь работа (тот же честный статус,
   что и у порогов `health_regression.py`).
2. Эвристика исключения «невиновных» подозреваемых по их собственному
   pre-merge окну — рассмотрена и НЕ реализована (§3): на реальных числах
   этого репозитория даёт неустойчивый результат. Если понадобится точнее —
   нужен анализ содержимого диффа (какие файлы/пути мог задеть каждый PR),
   которого этот детектор сегодня не делает и не пытается имитировать.
3. Связь конкретного прогона `worker.yml` с конкретным диапазоном коммитов
   PR (не только с фактом «слияние произошло раньше по времени») — Actions
   API такого поля не даёт напрямую; не выдумано, не реализовано.
