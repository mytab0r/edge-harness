# Дельта-спека: журнал (journal-tasks-hands) — инвариант 23, производитель задач пула без измеримого потребителя (#1277)

Реализация: `scripts/lib/pool_issue.py` (маркер производителя),
`scripts/lib/producer_orphan_watch.py` (классификатор/пороги/вердикт),
`scripts/orchestra/repo_invariants.py::check_pool_producer_orphaned`
(инвариант 23). Пороги — константы `producer_orphan_watch.py`, обоснованы
живым замером в докстринге модуля, не задублированы литералом здесь.

## ADDED: обязательный признак производителя у `create_pool_issue`

Требование: `pool_issue.create_pool_issue` принимает обязательный
именованный параметр `producer` (непустая строка формата `[a-z0-9][a-z0-9-]*`)
и отказывает RuntimeError'ом ДО сетевого вызова, если он пуст или не
соответствует формату — тот же приём, что уже применён к `labels` без
`task` (#526): пропуск признака производителя структурно невозможен для
любого нового вызывающего.

Требование: значение `producer` проставляется скрытым HTML-комментарием
`<!-- pool-issue-producer: <id> -->` первой строкой тела создаваемой issue.
Комментарий не рендерится GitHub'ом (обычный markdown HTML-comment), но
читается обратно как обычный текст поля `body` любым потребителем API
(REST/GraphQL/Search — везде одно и то же поле).

Требование: `pool_issue.extract_producer(body)` — единственная точка
обратного чтения маркера; возвращает `None`, если маркер отсутствует
(issue заведена до внедрения признака, либо не через `create_pool_issue`,
либо HTML-комментарий стёрт ручной правкой тела — три причины,
неразличимые по одному только отсутствию маркера).

## ADDED: классификатор производителя (маркер + заморожённая legacy-эвристика)

Требование: `producer_orphan_watch.classify_producer(issue)` — единая
точка классификации issue → id производителя. Маркер тела (через
`pool_issue.extract_producer`) — первичный и единственный признак,
устойчивый к переименованию заголовка/метки issue. Для issue без маркера
(заведены до внедрения) — заморожённая эвристика `_legacy_classify` по
заголовку/метке; эта эвристика НЕ распространяется на новых
производителей и не пополняется дальше замера на дату внедрения.

Требование: производитель `review-findings` (`scripts/review/file_tasks.py`)
не распознаётся legacy-эвристикой в принципе — заголовок и тело такой
issue пишет модель AI-ревью и по построению неотличимы от произвольной
ручной задачи с той же меткой `task`. Это зафиксированный факт (не пробел
реализации, который предполагается когда-нибудь закрыть эвристикой).

## ADDED: пороги и три исхода вердикта (issue #1096)

Требование: `producer_orphan_watch.compute_stats(issues, now)` считает по
каждому из `PRODUCER_IDS` (девять) за скользящее окно `WINDOW_DAYS=30`:
`total`/`closed`/`open_count`/`ever_taken`/`oldest_open_hours`.
Производитель без единой issue за окно ВСЁ РАВНО присутствует в
результате с `total=0` — не выпадает из отчёта молча.

Требование: `producer_orphan_watch.evaluate_producer(stats)` возвращает
`check_result.CheckResult` — три исхода, не два:
  - `total < MIN_SAMPLE_SIZE` (10) → `unknown()` — недостаточно данных
    (производитель либо не работал вовсе, либо слишком молод).
  - `close_rate <= DEAD_CLOSE_RATE_MAX` (10%) при `oldest_open_hours <
    24` → `unknown()` — доля закрытия низкая, но единственной свежей
    открытой задаче не могло хватить времени быть взятой; НЕ
    преждевременный вердикт «мёртв».
  - `close_rate > DEAD_CLOSE_RATE_MAX` → `ok()`.
  - иначе (объём выше порога, доля на/ниже порога, возраст выше порога)
    → `violation([{producer, total, closed, close_rate, open_count,
    ever_taken, oldest_open_hours}])`.

## ADDED: инвариант 23 репозитория

Требование: `repo_invariants.check_pool_producer_orphaned(repo, now)`
фетчит задачи пула за окно (`search/issues`, `created:>=...`, класс
инвариантов 14/18 — тот же приём) и возвращает `dict[producer,
CheckResult]` — вердикт на каждого производителя отдельно, не один
общий вердикт на всех девять. Транспортный отказ ЦЕЛОГО фетча даёт
`unknown()` каждому производителю с общей причиной (различить «этот
конкретно здоров» от «мы вообще ничего не увидели» здесь нельзя — общий
вход для всех девяти, в отличие от инвариантов с фетчем по кандидату).

Требование: `build_report` печатает отдельную строку на каждого из
девяти производителей (💚/🚨/❓ по `check_result.status_emoji`) — третье
состояние видно построчно, не схлопывается в общий 💚/🚨 всего
инварианта. `findings[23]` несёт только реальные `violation()` (список
словарей нарушителей) — используется `CI_GATING`/`ESCALATING_INVARIANTS`
по истинности списка тем же приёмом, что остальные инварианты этого
файла.

Требование: инвариант 23 — ЭСКАЛИРУЮЩИЙ (`ESCALATING_INVARIANTS`), НЕ в
`CI_GATING`. Эскалация (`escalate_if_new`) дедуплицирует по множеству id
мёртвых производителей — тот же набор молчит, новый мёртвый или пропажа
старого из списка даёт ровно одну новую эскалацию.
