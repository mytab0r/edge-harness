# Дельта-спека: journal-tasks-hands (contract-task-from-branch, #394)

Уточняет п.17 главной спеки `openspec/specs/journal-tasks-hands.md`: контракт
резолвит задачу PR через тот же узкий механизм, что и резолвер AI-ревью
(п.17.1), а не отдельным прямым чтением декларации тела.

17. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки обновляются из main токеном с правом зажигать
    проверки.

    17.0. Задача PR для контракта (решение владельца 2026-09-06, второй
        заход после `task_ref.pr_task_candidates`) — единственный источник,
        `task_ref.resolve_pr_task(pull)`: имя agent-ветки
        (`agent/<N>-<slug>`). Тело PR для этого вопроса не читается вообще
        — ни первой строкой, ни любым другим способом. Ветка называет уже
        закрытую задачу (докрытие после «закрытая задача не
        переоткрывается») — контракт не переориентируется чтением тела, а
        докладывает непригодность («задача закрыта — возьми открытую или
        заведи новую»); правильная починка — НОВАЯ ветка
        `scripts/git/task-branch <M>-<slug>` на новый номер, старую
        переименовать нельзя (живые PR на 2026-09-06, требующие новой
        ветки: #388, #384, #359, #167). Симметрично — «другой открытый PR на
        ту же задачу» (правило 5 выше по тексту) — это PR, чья ветка
        называет тот же номер, не любое упоминание в теле. Отказ («задача не
        определена») называет действие: назвать ветку `agent/<N>-<slug>`
        через `scripts/git/task-branch` — единственный путь, не «основной
        источник среди нескольких».

### Резолвер «PR → задача» для контекста AI-ревью (#259)

17.1. Задача, которую AI-ревью (второй гейт) показывает модели как контекст
    PR, — результат ОДНОГО резолвера (`scripts/lib/task_ref.resolve_pr_task`,
    #394): имя agent-ветки `agent/<N>-<slug>`, тело PR не читается вовсе
    (то же правило, что и в п.17.0). Любое упоминание номера в прозе
    описания (`task_ref.extract_task_refs`/`references_task`) для этого
    вопроса не годится — этим классом бага ai_review.py путал задачу PR
    с первым попавшимся числом в тексте (живой замер: #253 судили по
    #120 вместо объявленного #227, #248 — по #119 вместо #201, #247 —
    по #43, #263 — по #4). Ни ветка, ни тело не дали числа → у PR нет
    задачи из пула для контекста ревью, это не ошибка. Правила
    `reap_stale`/`unhealthy_pulls`/`after_merge` намеренно продолжают
    использовать широкую семантику упоминания — сужение там было бы
    регрессией, не улучшением.

17.2. Контракт не выполняет ни одного изменяющего вызова (авто-назначение
    исполнителя, сверку дубликата PR) над задачей, признанной непригодной.
    Пригодность считается ОДИН раз, до любых действующих вызовов
    (`contract_check.task_eligibility_problems`): задача существует как
    issue (не PR), открыта, несёт метку `task`, не несёт `blocked`.
    Непригодна хотя бы по одной причине — контракт только докладывает
    причину(ы), дальше по этой задаче не действует вовсе (живой случай:
    авто-назначение на уже закрытую задачу до этого пункта, PR #359).
    Исключений нет: ни один запасной источник не подхватывает задачу
    вместо непригодной из ветки (см. п.17.0).

### Приёмка: слитый PR регистрируется под задачей своей ветки (#394)

17.3. `scheduler.py::merged_pr_map` (Task#N → слитый PR для стадии приёмки,
    #227) регистрирует слитый PR под номером из `task_ref.resolve_pr_task`
    (имя agent-ветки, тело не читается). Ветка после реворка называет уже
    закрытую задачу — карта видит только её; докрытие новой задачей в теле
    в карту не попадает, правильная починка — новая ветка на новый номер
    (см. п.17.0).
