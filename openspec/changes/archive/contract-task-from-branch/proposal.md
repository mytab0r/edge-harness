# contract-task-from-branch: контракт резолвит задачу PR через одно место правды

Задача: #394.

## Проблема (замер, не догадка)

`scripts/lib/task_ref.py` с #259 (`pr-task-resolver`) документирует
`resolve_pr_task(pull, closing_issue=None)` дословно как «единственную точку
входа» на вопрос «какая задача у этого PR» — иерархия: имя agent-ветки →
`closing_issue` → декларация первой строкой тела. `scripts/review/ai_review.py`
и часть `scripts/orchestra/scheduler.py` (принятие в приёмке, #320/#325) уже
резолвят через него.

`scripts/orchestra/contract_check.py` — нет: до этого change он звал
`task_ref.declared_tasks(body)` напрямую, мимо резолвера. Итог — два разных
источника правды для одного факта: ревью резолвит задачу PR по ветке,
контракт — по прозе первой строки тела.

Живая цена (лог 2026-09-06, PR #388): ветка `agent/256-task-rework-loop`,
первая строка тела на тот момент — «Задача #256 (task-rework-loop). Реализует
пп.1-2» (не голый `#256`) — контракт покраснел «В теле PR нет ссылки на
задачу», хотя и ветка, и (по смыслу) тело её называли. Владелец получил это
письмом и указал прямо на дыру: правило «номер берётся из имени ветки»
выработано и проверяется где-то, но не здесь.

## Живой замер по всем открытым PR (2026-09-06, 30 штук)

Резолв по ветке успешен для 30 из 30 (100%), запасной путь (декларация тела
без ветки) не понадобился ни разу, необъяснённых PR нет. Но обнаружено
**расхождение ветка↔тело у 4 PR** (#388, #384, #359, #167) — не ошибка, а
легитимный класс: правило репозитория «закрытая задача не переоткрывается»
(введено 2026-09-06) требует докрытия НОВОЙ узкой задачей, объявленной первой
строкой тела, а ветку переименовать нельзя (`scripts/git/task-branch`
создаёт её один раз). Наивный переход на «ветка всегда побеждает» сломал бы
контракт именно для этих 4 живых PR: он резолвил бы их к уже ЗАКРЫТОЙ старой
задаче и заваливал бы `task_eligibility_problems` там, где сегодня (по
декларации тела) всё зелено.

## Решение

1. `task_ref.py` получает `pr_task_candidates(pull)` — оба узких источника
   (ветка, декларация тела) как СПИСОК кандидатов без схлопывания в один
   ответ, в отличие от `resolve_pr_task` (тот схлопывает, ветка приоритетна
   всегда, годится для контекста ревью/приёмки, где нужен один номер без
   сети). Кандидаты нужны отдельно именно там, где решение зависит от
   ПРИГОДНОСТИ каждого (сеть — `gh issue`), а не от одной лишь надёжности
   источника.
2. `contract_check.py` резолвит задачу через `task_ref.pr_task_candidates`:
   пробует кандидатов по порядку (ветка первой) и берёт первого, для
   которого задача пригодна (`task_eligibility_problems`). Прямых вызовов
   `task_ref.declared_tasks` для вопроса «какая задача у PR» в контракте
   больше нет.
3. То же используется для симметричной проверки «есть ли уже открытый PR на
   эту задачу» — чужой PR ловится, если задача среди ЕГО кандидатов (ветка
   или декларация), не только по декларации тела.
4. `scripts/lib/free_task.py::declared_pr_for_task` (используется
   `scripts/worker/task.sh` для «довести существующий PR, не открывать
   второй») переведён на тот же `pr_task_candidates` — иначе воркер не нашёл
   бы уже открытый PR по номеру задачи-преемницы после реворка.
5. `scripts/orchestra/scheduler.py::merged_pr_map` (приёмка, #227) тоже
   переведён на `pr_task_candidates`, но регистрирует слитый PR под КАЖДЫМ
   узким кандидатом, не только первым — иначе задача-преемница после
   реворка никогда не находила бы свой слитый PR и не закрывалась бы
   приёмкой (пул спрашивает только про ОТКРЫТЫЕ задачи — запись под старой
   закрытой безвредна, просто никогда не запрашивается).
6. Отказ контракта называет конкретное действие: назвать ветку через
   `scripts/git/task-branch <N>-<slug>` (основной источник) или, если ветка
   не такой формы, поставить номер первой строкой тела.
7. Декларация первой строкой тела остаётся рабочим соглашением — не
   ослаблена и не отменена (правило #251/#312 о её строгом парсинге не
   трогается), но перестаёт быть единственным источником: она запасной путь
   (PR без agent-ветки) и одновременно единственный сигнал переориентации
   при реворке. `AGENTS.md`/`docs/agents/PROTOCOL.md`/
   `docs/agents/WORKER-PLAYBOOK.md`/шаблон PR обновлены, чтобы называть
   ветку основным источником, а первую строку — вторичным.

## Что осознанно НЕ меняется

- `task_ref.declared_tasks`/`declares_task` — парсинг тела не смягчается
  (правило #251/#312 остаётся: декларация — только первая непустая строка,
  начинающаяся с `#` и сразу цифрой).
- `scheduler.py::pr_references_issue` (`reap_stale`/`unhealthy_pulls`) и
  широкая часть `after_merge` (напоминание про пост-мерж проверку по ЛЮБОМУ
  упоминанию задачи) продолжают использовать `extract_task_refs`/
  `references_task` — осознанный выбор, задокументированный в их
  докстрингах (#259, `pr-task-resolver`), не трогается.
- `resolve_pr_task` сам не меняется (остаётся чистой функцией без сети) —
  добавлена соседняя функция `pr_task_candidates`, а не переделан его
  контракт.

## Критерий готовности (заменён пересмотром ниже)

- `contract_check.py` не вызывает `task_ref.declared_tasks`/`declares_task`
  напрямую — только через `task_ref.pr_task_candidates`.
- Живой случай PR #388 (ветка `agent/256-...`, тело «Задача #256
  (task-rework-loop)...») проходит контракт (тест на прод-форме).
- Живой класс реворка (#388/#384/#359/#167: ветка называет закрытую задачу,
  тело — открытую-преемницу) проходит контракт и находится приёмкой/
  `declared-pr` (тесты на прод-форме тел).
- Сообщение «задача не определена» называет действие (имя ветки/декларация
  тела), не просто «нет ссылки».
- Документация (`AGENTS.md`, `PROTOCOL.md`, `WORKER-PLAYBOOK.md`, шаблон PR)
  называет ветку основным источником, декларацию тела — запасным.

## Пересмотр 2026-09-06: владелец отменяет декларацию тела как источник

Решение владельца, окончательное: «номер задачи берётся ТОЛЬКО из имени
ветки… тело PR не читается вообще». `pr_task_candidates` (весь раздел
«Решение» выше) снята вместе с обоснованием, которое её породило — развилка
и причина отмены зафиксированы в `design.md`, «Пересмотр 2026-09-06».
Действующий критерий готовности (заменяет весь раздел выше):

- `task_ref.py`: только `resolve_pr_task(pull)` = `task_from_branch(ref)`,
  без `closing_issue`, без `pr_task_candidates`. `declared_tasks`/
  `declares_task` удалены — производственных вызывающих не осталось.
- `contract_check.py`/`free_task.py::declared_pr_for_task`/
  `scheduler.py::merged_pr_map`/`after_merge` резолвят задачу PR только через
  ветку; ни один из них не читает `pull["body"]` для этого вопроса.
- Живой класс реворка (#388/#384/#359/#167) проваливает контракт на закрытой
  задаче ветки — без переориентации на тело (тест на прод-форме,
  доказывающий именно ЭТО, не прежнее поведение).
- Сообщение «задача не определена» называет одно действие: завести ветку
  `scripts/git/task-branch <N>-<slug>` — не «или поставь номер в тело».
- Документация (`AGENTS.md` цепочкой через `PROTOCOL.md`/
  `WORKER-PLAYBOOK.md`, шаблон PR, `openspec/specs/journal-tasks-hands.md`)
  называет ветку единственным источником, без «запасного пути».
- Прогон по всем открытым PR репозитория на 2026-09-06 (31 шт.): у всех 31
  задача определяется по ветке; 7 из них (#388, #384, #359, #325, #237,
  #231, #167) называют веткой уже ЗАКРЫТУЮ задачу — из них 4 (#388, #384,
  #359, #167) до этого пересмотра резолвились по телу на открытую
  задачу-преемницу и требуют новой ветки для продолжения; это отдельный
  разговор с владельцем, не предмет автоматической починки здесь.

## Разговор с владельцем состоялся: 5 PR переведены на новую ветку

Повторный прогон в тот же день нашёл пятый живой случай того же класса
(#231→#407, не только #388/#384/#359/#167) — итог 5, не 4. Владелец решил:
для уже открытых PR, чья ветка называет закрытую задачу, а тело называет
её открытую преемницу, — завести НОВУЮ ветку на новый номер и открыть новый
PR, старый закрыть со ссылкой (переименование существующей ветки
отклонено как способ — живой эксперимент показал, что GitHub закрывает
открытый PR при переименовании его ветки вместо переориентации, см.
design.md). Выполнено: #408 заменяет #388, #409 заменяет #384, #410
заменяет #359, #411 заменяет #167, #412 заменяет #231 (тот же коммит,
diff идентичен). Повторный прогон резолвера по 29 открытым PR после этого:
29/29 по ветке, 0 без ответа, 0 расхождений ветка↔тело.
