# Design: contract-task-from-branch

Контекст, замер, полный список решений — proposal.md. Здесь — почему выбрана
именно эта форма (`pr_task_candidates` + список вместо одного числа) и что
было отвергнуто.

## Почему не просто «contract_check зовёт resolve_pr_task»

Первая, самая простая версия этого change — заменить
`task_ref.declared_tasks(body)` на `task_ref.resolve_pr_task(pull)` один в
один. Отклонена по результату живого замера (см. proposal.md, «Живой замер
по всем открытым PR»): 4 из 30 открытых PR репозитория на 2026-09-06 (#388,
#384, #359, #167) устроены так, что ветка называет уже ЗАКРЫТУЮ задачу
(«закрытая задача не переоткрывается», докрытие оформлено новой узкой
задачей в теле). `resolve_pr_task` всегда предпочитает ветку — простая
замена сломала бы контракт именно для этих 4 живых PR: он резолвил бы их к
закрытой задаче и заваливался бы на `task_eligibility_problems`, хотя сегодня
(по декларации тела) все четыре зелёные.

Это не гипотетический край случая: 13% открытых PR репозитория в момент
замера. Игнорировать — значит воспроизвести ровно тот же класс, который
чинит этот change, только с другим направлением победителя (тело против
ветки вместо ветки против тела).

## Почему `pr_task_candidates`, а не расширение `resolve_pr_task`

`resolve_pr_task` — чистая функция без сети (докстринг `task_ref.py`
объясняет почему: тестируется прод-формой тела PR без `gh`). Чтобы понять,
что ветка называет ИМЕННО ЗАКРЫТУЮ задачу (а не просто предпочесть тело
всегда), нужен сетевой факт — `gh issues/N` → `state`. Встраивать сеть в
`resolve_pr_task` значит слить резолвер и HTTP-клиента в одну функцию,
которую нельзя протестировать без сети (то же возражение, что уже
зафиксировано в design.md #259 против «резолвер сам дёргает gh api»).

Поэтому: `pr_task_candidates(pull)` остаётся чистой (те же два узких
источника, что и raньше, просто не схлопнутые в один ответ), а РЕШЕНИЕ,
какого кандидата использовать, если первый непригоден, — за вызывающим
кодом, у которого есть сеть (`contract_check.py`, `scheduler.py`). Резолвер
и сетевой клиент разделены, как и в #259.

## Почему `merged_pr_map` регистрирует ОБА кандидата, а не выбирает одного

`contract_check.py` должно принять РОВНО ОДНО решение (кому что назначить,
на что ругаться) — там уместен «первый пригодный кандидат». `merged_pr_map`
— это таблица поиска (Task#N → слитый PR), и вопрос другой: «под каким
числом accept_merged_tasks сможет найти этот PR». Поскольку
`accept_merged_tasks` смотрит только в `pool` (открытые задачи), а закрытая
задача, которую называет устаревшая ветка, туда не входит — регистрация под
обоими числами не создаёт риска ложного закрытия: только ОДНА из двух
записей когда-либо будет запрошена. Выбор «взять только первого кандидата»
здесь был бы избыточно осторожным и просто не работал бы для класса реворка
(задача-преемница никогда не находила бы свой слитый PR).

## Почему это не «декларация первой строкой смягчена»

Правило #251/#312 (`declared_tasks` — строго первая непустая строка,
начинающаяся с `#` и сразу цифрой) не тронуто ни строкой: `pr_task_candidates`
вызывает `declared_tasks` как есть. Меняется только то, ЧТО спрашивается
(один источник vs список кандидатов с проверкой пригодности), не как
парсится сам текст.

## Отвергнутая альтернатива: убрать декларацию тела вовсе

Рассмотрено и отклонено (первый заход, см. пересмотр ниже): раз ветка почти
всегда достаточна (30/30 живых открытых PR резолвятся по ней), можно было бы
объявить декларацию тела мёртвой и убрать её из контракта совсем. Отклонено
по двум причинам: (1) она остаётся ЕДИНСТВЕННЫМ сигналом переориентации при
реворке — без неё не было бы механизма сказать «эта задача больше не та, что
в названии ветки», и класс реворка (уже 13% открытых PR) остался бы без
решения; (2) она остаётся единственным источником для PR без agent-ветки
(ручной пуш, будущие боты) — таких сегодня 0 из 30, но контракт не должен на
этом основании отказывать им в работе молча.

## Пересмотр 2026-09-06: решение владельца отменяет `pr_task_candidates`

Владелец рассмотрел ровно эту развилку и распорядился окончательно, без
исключений: «номер задачи берётся ТОЛЬКО из имени ветки… не надо вообще
туда смотреть» (тело PR). Обе причины отказа выше сняты явно, не молча:

1. Переориентация при реворке — не решается чтением тела. PR, чья ветка
   называет закрытую задачу, не пытается угадать номер-преемник — контракт
   докладывает «задача закрыта», а исполнитель заводит НОВУЮ ветку
   (`scripts/git/task-branch <M>-<slug>`) на новый номер. Класс реворка
   (#388, #384, #359, #167 на 2026-09-06) остаётся без автоматической
   починки внутри этого PR — это называно отдельно (не спрятано): владелец
   принимает эту цену явно, а не как побочный эффект.
2. PR без agent-ветки (ручной пуш) — теперь тоже «задачи нет», а не «ищем в
   теле». Живых PR такого вида на 2026-09-06 — 0 из 31 открытых, цена
   гипотетическая, не наблюдаемая.

Реализация: `pr_task_candidates` удалена; `resolve_pr_task` возвращает
только `task_from_branch`, без параметра `closing_issue` (снят как мёртвый —
живой GraphQL-замер по 8 последним слитым PR репозитория вернул пустой
`closingIssuesReferences` у каждого: Closes/Fixes/Resolves запрещены
контрактом, GitHub нечего связывать формально; повторный замер 2026-09-06 по
10 последним слитым PR подтвердил то же самое). `declared_tasks`/
`declares_task` удалены вместе с ней — производственных вызывающих не
осталось ни у одной функции.

## Живой класс: 5 PR (не 4), ветка называет закрытую задачу — что с ними делать

Повторный прогон резолвера по 29 открытым PR на 2026-09-06 после снятия
`pr_task_candidates` нашёл 5 расхождений ветка↔тело, не 4: помимо
#388/#384/#359/#167 (названы в proposal.md) — ещё #231 (ветка называет
закрытую #111, тело объявляет открытую #407). Без починки все пять
провалили бы контракт («задача закрыта») до тех пор, пока их ветки называют
старый номер.

**Отклонённый способ: переименование ветки на GitHub (`POST
.../branches/{branch}/rename`)** — казалось дешевле всего: тот же PR, тот
же номер, та же история ревью/CI, меняется только имя ветки. Проверено
живым экспериментом на #388 (`agent/256-task-rework-loop` →
`agent/391-task-rework-loop`): вызов отработал, GitHub подтвердил
переименование и даже оставил редирект по старому имени (`GET
branches/{старое-имя}` отдаёт данные НОВОЙ ветки) — но открытый PR #388 при
этом закрылся (`state: closed, merged: false`), а не переориентировался на
новое имя головы. Судя по поведению, «умная» миграция открытых PR при
переименовании ветки в реальности работает только для DEFAULT-ветки
репозитория (там, где GitHub перепривязывает и protection rules, и base
всех PR) — для обычной ветки это по сути create+delete, и удаление ветки,
на которую смотрит открытый PR, штатно закрывает его. Реопен через API
(`gh pr reopen`) в этом состоянии отклоняется («Could not open the pull
request») — чинится, только если вернуть старое имя ветки (переименование
обратно), тогда `gh pr reopen` снова срабатывает. Способ отклонён для ЛЮБОЙ
не-default ветки этого репозитория.

**Применённый способ**: для каждого из 5 — создать НОВУЮ ветку с тем же
коммитом через Git Refs API (`POST git/refs`, без изменения старой ветки),
открыть новый PR с неё, закрыть старый PR комментарием со ссылкой на новый.
Диф идентичен (тот же коммит), история PR исходного не удаляется (виден в
closed), газ на закрытую задачу снят: #408 (было #388), #409 (#384), #410
(#359), #411 (#167), #412 (#231). Дороже, чем гипотетическое переименование
(новый номер PR, потеря нитки ревью-комментариев старого), но единственный
способ, который не закрывает работу без замены.
