# contract-eligibility-gate: пригодность задачи проверяется ДО изменяющего вызова, не рядом с ним

Прямой запрос владельца (живой лог прогона, PR #359, 2026-09-06); задачи пула
на эту правку нет — PR идёт с меткой `orchestra:skip` (контракт называет её
осознанным обходом для мелочей вне пула, `docs/agents/LABELS.md`).

Дельта-спека: [specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md)
(п.17.2 в главной спеке).

## Зачем

Живой лог `contract` на PR #359:

```
contract: авто-назначение mytab0r на #131
##[error]Задача #131 закрыта — возьми открытую или заведи новую.
contract: FAIL (1 нарушений)
```

Контракт СНАЧАЛА назначил владельца на задачу, ПОТОМ сказал, что задачу брать
нельзя — авто-назначение уже никто не отменит автоматически (следующий прогон
контракта видит `assignees` не пустым и печатает уже другую, более запутанную
причину отказа). Корень — `scripts/orchestra/contract_check.py`: проверка
`issue["state"] != "open"` только добавляла строку в `problems`, а
авто-назначение (`gh -X POST .../assignees`) стояло в той же ветке if/else и
не смотрело на `problems` вообще — то же самое верно для отсутствия метки
`task`. Правило («задача непригодна — руки прочь») было объявлено в
докстринге, но не было тем, что реально проверяет код перед действием.

## Что делается

`task_eligibility_problems(issue, issue_number)` — единая функция, которая
считает пригодность задачи ОДИН раз: существует ли она как issue (не PR),
открыта, несёт метку `task`, не несёт `blocked` (новое условие — эскалация
playbook держит существующее назначение, но авто-назначение на задачу,
ждущую владельца, ничем не лучше назначения на закрытую). `main()` обязан
проверить эту функцию ДО единственного изменяющего вызова над issue_number
(`assignees` POST) — непригодна → только копим причину в `problems`, ни один
`gh(-X ...)` над этой issue не выполняется. Пригодна → как раньше: авто-
назначение свободной задачи, сверка занятости, поиск дубликата PR.

Полный список изменяющих вызовов в `contract_check.py` (для доказательства,
что уязвим был только один):

- `fail()`: labels POST + comments POST — выполняются ПОСЛЕ того, как
  `problems` уже финализирован (это и есть сам провал, не преждевременное
  действие).
- `issues/{N}/assignees` POST — единственный уязвимый вызов, исправлен здесь.
- `issues/{pr}/labels/contract:failed` DELETE — выполняется только если
  `problems` пуст (после `if problems: fail()`, которая завершает процесс
  `sys.exit(1)` и не возвращает управление).

## Соседи того же класса — проверены, не тронуты

- `scripts/orchestra/scheduler.py` — прочитан целиком (1594 строки); паттерн
  «нарушение записано → действие выполняется всё равно» не найден: каждая
  функция либо решает и действует (без промежуточного списка находок), либо
  `continue`/`break` останавливает обработку конкретного кандидата раньше
  мутирующего вызова. Тот же класс, но другой набор мест, уже описан в #357 и
  чинится отдельным открытым PR #358 — не дублируется здесь.
- `scripts/review/check_pr.py` — вердикт-метка (`verdict_for`) вычисляется ИЗ
  списка находок и ставится ОДНА, после всех проверок; findings и вердикт не
  расходятся.
- `scripts/review/ai_review.py` — то же: `parse_verdict`/`apply_large_ok`
  проверяют состояние (голова PR не уехала) ДО каждого изменяющего вызова;
  собственных «problems, накопленных и проигнорированных» нет.
- `scripts/lib/free_task.py` — чистая логика без сетевых вызовов вовсе.

## Что вне рамок

- Авто-назначение автора PR на свободную задачу как таковое: под одним
  логином агенты неотличимы, поэтому назначение — сигнал «задача занята», не
  «кем». Менять эту механику владелец не поручал — предложение с
  обоснованием оставлено в отчёте разработчика, реализация не входит в этот
  change.
- #359 (структурная гвардия транскрипта) — закрывается отдельно, новой узкой
  задачей со ссылкой на #131 (не переоткрывается — правило «закрытая задача
  не переоткрывается никогда»), не входит в этот change.
