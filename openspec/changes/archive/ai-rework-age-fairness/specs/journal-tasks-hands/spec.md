(пп. 26–29 базовой спеки, `openspec/specs/journal-tasks-hands.md`) — п.26

исходный контракт `dispatch_ai_review_rework` целиком — она описывает ТОЛЬКО
поведение, изменённое issue #1253 (PR #1260): порядок обхода очереди,

одновременно (тот же приём, что уже применяет `quota-continuous-watch`) —
номер пункта присваивается при архивации, сверяться с доменной спекой на тот
момент, не с числом здесь.

## ADDED: Очередь доводки `ai:changes-requested` идёт от старейшего вердикта к новейшему

Реализация: `scheduler.py::dispatch_ai_review_rework`, `ai_changes_labeled_at`,
`_label_event_times`.

Требование: кандидаты на авто-доводку по находкам ai-review (PR с меткой
`ai:changes-requested`, без метки `conflict` — та обслуживается отдельной
очередью `dispatch_conflict_rework`) обходятся НЕ в сыром порядке, в котором
их отдаёт `GET /pulls?state=open` (новые PR первыми), а отсортированными по
возрасту ТЕКУЩЕГО эпизода вердикта — по моменту ПОСЛЕДНЕЙ простановки метки
`ai:changes-requested` (`ai_changes_labeled_at`, момент последнего события
`labeled` в таймлайне PR с этим именем метки; `max()`, не `min()` — метка
могла сниматься и ставиться заново несколькими прогонами ai-review, важен
именно текущий эпизод). PR, чья ветка не называет задачу в форме
`agent/N-slug` (`task_ref.resolve_pr_task` вернул `None`), сортировкой не
платит — обходится первым, до всех отсортированных, дешёвым пропуском без
запроса таймлайна. Один диспатч `worker.yml` за проход планировщика — при
нескольких кандидатах получает его СТАРЕЙШИЙ по возрасту эпизода метки, не
первый по списку API и не самый свежий по `created_at` PR.

При равенстве `ai_changes_labeled_at` у двух и более кандидатов порядок
между ними не специфицирован этим требованием отдельно (сортировка Python
стабильна и сохраняет исходный порядок `open_pulls()` для равных ключей —
поведение, не проверенное отдельным тестом).

Общая часть чтения «когда метка появилась» — `_label_event_times(repo,
pr_number, label_name)`: сырые `created_at` всех событий `labeled` с данным
именем метки в таймлайне PR. Один и тот же цикл по таймлайну обслуживает
`ai_changes_labeled_at`, `conflict_labeled_at` и `conflict_first_labeled_at`
— общий код, не три копии.

Сценарий: PR #560 (задача #474) получил `ai:changes-requested` 2026-09-03,
PR #561 (задача #475) — 2026-09-06; оба в бюджете доводки, оба без метки
`conflict` -> при снимке одного и того же прохода планировщика,
где `open_pulls()` вернул #561 раньше #560, диспатч `worker.yml` получает
задачу #474 (более старый вердикт), не #475.

Сценарий: PR несёт `ai:changes-requested`, но его ветка не в форме
`agent/N-slug` -> авто-доводка недоступна, наблюдение называет причину явно
(«ветка не называет задачу»), таймлайн этого PR за возрастом не читается.

## MODIFIED: Решение об эскалации бюджета доводки не гейтится занятостью воркера

Реализация: `scheduler.py::dispatch_ai_review_rework`, ветка `attempts >=
AI_REWORK_MAX_ATTEMPTS`.

Требование: исчерпание бюджета авто-доводки на текущем отпечатке диффа
(`ai_rework_attempts(...) >= AI_REWORK_MAX_ATTEMPTS`) больше не проверяет
`worker_runs_active(repo)` перед тем, как решить, публиковать ли эскалацию
владельцу. Единственные условия, останавливающие эскалацию на этой ветке:
маркер эскалации на этом отпечатке уже опубликован (идемпотентность),
`ai:changes-requested` уже снят при перепроверке, PR уже закрыт/слит, или
исход собственного последнего прогона `worker.yml` этой задачи ещё не
известен (см. следующее требование). Гейт занятости воркера
(`dispatched or worker_runs_active(repo)`) остаётся в силе только для
РЕАЛЬНОГО диспатча `worker.yml` — решение «звать ли воркера снова» и решение
«эскалировать ли владельцу» это два разных, независимо принимаемых решения:
эскалация — комментарий в PR плюс `pulse_guard.escalate` (issue #120 +
Telegram), она не занимает и не освобождает воркер, поэтому её не должна
откладывать чужая занятость.

До этого change оба решения проверялись одним общим гейтом — если воркер
был занят (типичное состояние: интервалы простоя 3-16 минут почти всегда
заняты чем-то), эскалация откладывалась пульс за пульсом безо всякой связи
со своим собственным условием готовности.

Сценарий: PR #1020 (задача #782) исчерпал бюджет доводки на текущем
отпечатке, собственный последний прогон `worker.yml` этой задачи завершился
`success` час назад, но воркер ПРЯМО СЕЙЧАС занят ЧУЖИМ прогоном (другая
задача, `in_progress`) -> эскалация владельцу публикуется в этом же проходе,
несмотря на занятость воркера; диспатч нового `worker.yml` при этом не
уходит (эскалация не диспетчит воркер).

## ADDED: Признак «исход собственного последнего прогона ещё не известен» — по терминальности статуса, не по перечислению нетерминальных

Реализация: `scheduler.py::dispatch_ai_review_rework`, проверка
`run.get("status") != "completed"` перед определением `run_conclusion`.

Требование: перед тем, как эскалировать исчерпание бюджета доводки, код
обязан различать три факта, а не два:

1. атрибуции последнего прогона `worker.yml` этой задачи нет вовсе
   (`last_worker_run(...)` вернул `None`) — законная эскалация с текстом
   «не атрибутирован»;
2. атрибуция есть, и прогон УЖЕ завершился (`status == "completed"`) —
   `conclusion` прогона (`success`/`failure`/`cancelled`/`timed_out`/…)
   определяет дальнейшее решение (инфраструктурный повтор без эскалации,
   если `conclusion` в `FAILURE_CONCLUSIONS`, иначе законная эскалация с
   честным текстом, называющим сам `conclusion`);
3. атрибуция есть, но прогон ЕЩЁ НЕ завершился (`status != "completed"`) —
   эскалация ОТКЛАДЫВАЕТСЯ до известного исхода; это НЕ находка «атрибуции
   нет» и не повод эскалировать.

Различение факта 3 от факта 1 обязано идти по проверке ТЕРМИНАЛЬНОСТИ
статуса (`status != "completed"`), а не по перечислению нетерминальных
значений (`status in ("in_progress", "queued")` и т.п.) — перечисление
неполно по построению: у GitHub Actions нетерминальных статусов больше
(`requested`, `waiting`, `pending`, возможно другие, не документированные
исчерпывающе), и `conclusion` не заполнен ГАРАНТИРОВАННО ни для одного из
них — только `"completed"` гарантирует заполненный `conclusion` (прод-форма
GitHub Actions API). Реализация, различающая факты 1 и 3 перечислением
нетерминальных статусов, при статусе, отсутствующем в списке, ошибочно
трактует «исход ещё не известен» как «атрибуции нет» и эскалирует
преждевременно.

Это требование сформулировано как общее правило (не место-специфичный
фикс): любой код, решающий «известен ли исход прогона GitHub Actions по его
`status`/`conclusion`», обязан проверять `status == "completed"` как признак
терминальности, а не перечислять нетерминальные значения.

Сценарий: последний прогон `worker.yml` задачи #782 атрибутирован, его
`status` — `"waiting"` (нетерминальный статус, отсутствующий в белом списке
`("in_progress", "queued")`) -> эскалация ОТКЛАДЫВАЕТСЯ с наблюдением
«эскалация отложена до известного исхода (status='waiting')», не
публикуется с текстом «не атрибутирован».

Сценарий: тот же прогон переходит в `status == "completed"`,
`conclusion == "success"` -> на следующем проходе (при неизменном отпечатке
диффа) эскалация публикуется с текстом, называющим факт «worker.yml
отработал успешно, keep-path — повторный ai-review на этот отпечаток не
запускался».

## ADDED: Инвариант 22 — PR с `ai:changes-requested`, которому доводку не звали ни разу (наблюдательный)

Реализация: `repo_invariants.py::check_ai_rework_never_dispatched`,
константа `AI_REWORK_NEVER_DISPATCHED_AFTER_MINUTES = 1440`, реестр —
`repo_invariants.py:314-331`, подключение в `build_report` — пункт `[22]`.

Требование: инвариант 22 находит PR, у которых ОДНОВРЕМЕННО верно:

- метка `ai:changes-requested` стоит, метки `conflict` нет (своя очередь —
  `dispatch_conflict_rework`, вне области этого инварианта);
- с момента ТЕКУЩЕГО эпизода метки (`ai_changes_labeled_at`) прошло больше
  `AI_REWORK_NEVER_DISPATCHED_AFTER_MINUTES` (1440 минут, 24 часа);
- ни один комментарий PR, опубликованный не раньше начала ТЕКУЩЕГО эпизода
  метки (`created_at` комментария `>= labeled_at`), не содержит
  `scheduler.AI_REWORK_MARKER` (маркер, который `dispatch_ai_review_rework`
  публикует в PR при КАЖДОМ диспатче, независимо от исхода попытки) —
  проверка читает ВСЮ доступную историю комментариев PR
  (`pulse_guard.all_issue_comments`), но считает только те, что не старше
  начала текущего эпизода: маркер, опубликованный в ПРОШЛОМ эпизоде метки
  (до её снятия и повторной простановки), находку не глушит.

`ai_changes_labeled_at(...) is None` (таймлайн не отдал событие простановки
метки) — не находка: инвариант не гадает о возрасте, которого не может
подтвердить.

Отличие от инварианта 3 (`check_stuck_review_gate`) одной фразой: инвариант
3 ловит PR БЕЗ вердикта `ai:*` вообще (гейт 2 ещё не отработал) и намеренно
пропускает любой PR с уже вынесенным `ai:*`-вердиктом; инвариант 22 — ровно
обратный случай, PR С вердиктом `ai:changes-requested`, которому адресный
диспатч доводки ни разу не звонил. «Доводка звалась хоть раз, но не
помогла» (бюджет `AI_REWORK_MAX_ATTEMPTS` уже исчерпан и по нему уже
принято решение — эскалация или инфраструктурный повтор) — ДРУГОЕ
состояние, НЕ находка инварианта 22: за него отвечает сам
`dispatch_ai_review_rework` (см. требования выше), второй тормоз на то же
состояние здесь не заводится.

Инвариант наблюдательный: НЕ входит ни в `CI_GATING` (не блокирует
обязательную проверку `test`), ни в `ESCALATING_INVARIANTS` (не шлёт
отдельный алерт владельцу помимо строки в общем отчёте `build_report`) —
тот же статус, что у инвариантов 8/9/10/12/14 на момент внедрения каждого
из них (свежий инвариант без накопленной истории ложных срабатываний).

Порог `AI_REWORK_NEVER_DISPATCHED_AFTER_MINUTES = 1440` — замер живой
популяции 2026-09-14 (read-only прогон по `ai_changes_labeled_at`/
`AI_REWORK_MARKER` для 22 открытых PR с `ai:changes-requested` без
`conflict`; 17 из них ни разу не получали маркер доводки). Возраст текущего
эпизода метки у этих 17 распадается на два кластера с зазором:
«формирующийся бэклог сразу после включения сортировки» — 0.2-438.8 минут
(до ~7.3 часов, разгребается сам за считаные часы при серийном слоте
воркера — флагать эту фазу находкой было бы тем же «тормозом без газа», от
которого уже отказались для инвариантов 1/4/5/9); «реальный многодневный
застой» — 2894.0-11899.6 минут (~2.0-8.3 суток, живые случаи —
PR #1033/#1028/#919/#261). Порог 1440 минут лежит строго в зазоре между
кластерами (> 438.8, < 2894.0). На момент внедрения даёт 4 находки: #261,
#919, #1028, #1033.

Сценарий: PR #261 несёт `ai:changes-requested` с 2026-09-06T09:13:49Z, на
момент проверки прошло больше 1440 минут, ни один комментарий PR не
содержит `AI_REWORK_MARKER` -> находка: `{"pr": 261, "age_minutes": ...,

засчитывается, инвариант видит рецидив, а не молчит на нём.

Сценарий: PR несёт ОБЕ метки, `ai:changes-requested` и `conflict` -> не
