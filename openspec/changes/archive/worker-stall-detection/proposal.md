# worker-stall-detection: зависший (но по GH ещё in_progress) прогон worker.yml не блокирует пул (#815)

Задача: #815. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Живой инцидент 2026-09-09: прогон `worker.yml` #34339807907 (проба
предохранителя, стартовала ДО фикса #795, застряла на баге #794) провисела
в статусе `in_progress` около трёх часов. `concurrency: {group: worker,
cancel-in-progress: false}` (`.github/workflows/worker.yml:26-29` — один
воркер на репозиторий) держал `scheduler.py::worker_runs_active()==True` всё
это время, блокируя ОДНОВРЕМЕННО: обычный `dispatch_worker`,
`dispatch_conflict_rework` И восстановление предохранителя (пробы 2/3 из
watchdog-задачи #120 были анонсированы, но не смогли стартовать —
`worker_runs_active` видел «занято»). Единственной границей была жёсткая
280-минутная стенка самого job'а (`worker.yml:41`) — до неё зависший прогон
держал весь пул почти без пользы.

Корень: `worker_runs_active()` считал воркер активным ТОЛЬКО по
GitHub-статусу (`in_progress`/`queued`), без учёта длительности или
признаков жизни — детектора класса «жив по GH API, но агент застрял» не
было вовсе.

## Что делается

- `scheduler.py::_run_is_stalled`/`stalled_worker_run` — прогон `in_progress`
  дольше `WORKER_STALL_MINUTES` (200) считается зависшим. Порог обоснован
  замером живых длительностей `worker.yml` (100 последних прогонов,
  2026-09-09): успешные прогоны с реальной DSH-работой достигают МАКСИМУМ
  151.1 мин (пять раз из выборки — соответствует 150-минутному таймауту DSH
  за попытку, `worker.yml:34-40`), медиана таких прогонов ≈ 73 мин; порог из
  первичного диагноза инцидента (60–90 мин) не подтвердился на этой
  выборке — отменял бы ~40% реально работающих прогонов, поэтому итоговый
  порог взят заметно выше наблюдаемого максимума легитимного success (151.1),
  не его медианы, и заметно ниже 280-минутного жёсткого таймаута.
- `worker_runs_active()` — зависший `in_progress` не блокирует диспатч.
  Все три диспетчера, читающие эту функцию (`dispatch_worker`,
  `dispatch_conflict_rework`, восстановление предохранителя — оно тоже
  проходит через `dispatch_worker`, отдельного гейта у него нет), получают
  исправление одной точкой правды.
- `scheduler.py::reap_stalled_worker_run` (новый шаг `main()`, рядом с
  `reap_stale`/`claim_task.collect_stale`) — доводит находку до конца:
  отменяет зависший прогон (`gh api .../actions/runs/<id>/cancel`,
  best-effort) и освобождает аренду задачи, которую он держал, СРАЗУ, не
  дожидаясь обычных 24ч `reap_stale`/`claim_task.collect_stale`. Задача
  определяется структурным признаком (не парсингом прозы — класс запрещён
  AGENTS.md): среди открытых незаблокированных назначенных задач без
  открытого PR (тот же критерий, что уже применяет `reap_stale`) берётся
  та, чьё timeline-событие `assigned` не старше момента старта прогона
  (`last_assigned_at` — общий с `reap_stale` источник признака аренды,
  вынесен отдельной функцией во избежание второго обхода одного и того же
  таймлайна).
- Признак свежести heartbeat (морда DO пишет heartbeat каждые 60с,
  `cf-worker/src/harness.ts::handsAreAlive`, endpoint `/api/status`) в этот
  гейт НЕ подключён: `orchestra.yml` не получает `HARNESS_URL`/`HANDS_TOKEN`
  в своём окружении сегодня, добавление живого сетевого вызова в гейт,
  используемый несколькими диспетчерами за пульс, — отдельное решение
  владельца, вне рамок этого фикса. Деградация честная и единственный
  сигнал — длительность `in_progress`, признак грубее heartbeat (не отличает
  «завис» от «редкая долгая легитимная работа за порогом»), но не молчит:
  сообщение действия называет длительность и порог явно, не гадает.

## Что вне рамок

- Подключение heartbeat (`HANDS_TOKEN`/`HARNESS_URL` в окружении
  `orchestra.yml`, живой запрос `/api/status`) как более точного признака —
  решение владельца, отдельная задача при необходимости.
- Второй порог правды под пробу предохранителя не заводится: она
  диспетчируется через тот же `dispatch_worker`, значит уже получает фикс
  этим же изменением, без отдельной проводки в `pulse_guard.py::conveyor_gate`.
