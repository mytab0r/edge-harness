## ADDED: Порог зависания зависшего (но по GH ещё in_progress) прогона

Требование: прогон `worker.yml` в статусе `in_progress`, идущий дольше
`WORKER_STALL_MINUTES` (200, `scheduler.py`) от `run_started_at`
(fallback — `created_at`), не блокирует ни один из трёх диспетчеров, чьё
решение о новом `workflow_dispatch` зависит от «активен ли воркер»:
обычный `dispatch_worker`, авто-расшивку конфликтов
(`dispatch_conflict_rework`) и пробный диспатч предохранителя конвейера
(#120) — последний диспетчируется через тот же `dispatch_worker`, отдельного
гейта у него нет. Прогон `queued` порогом не тронут (он ещё не начал
работать — вопрос очерёдности, не зависания).

Требование: порог обоснован замером живых длительностей прогонов
`worker.yml`, не взят с потолка. Успешные прогоны с реальной работой
достигают максимума ≈151 мин (соответствует 150-минутному таймауту DSH за
попытку внутри `worker.yml`); порог обязан быть заметно ВЫШЕ этого
максимума (не медианы) и заметно НИЖЕ 280-минутного жёсткого таймаута
job'а — оба запаса проверяемы числом в комментарии рядом с константой.

Требование: признак — грубее свежести heartbeat (не отличает «завис» от
«редкая легитимная работа за порогом»), деградация честная: сообщение
действия называет длительность прогона и порог явно, не предлагает
читателю гадать между причинами (AGENTS.md: «алерт не гадает» — здесь
частичное соответствие, т.к. сама причина зависания системой не
устанавливается, но факт «дольше X мин без heartbeat/сети наружу» назван,
а не спрятан за общим «занято»).

## ADDED: Отмена и освобождение аренды зависшего прогона

Требование: как только прогон признан зависшим (см. выше), оркестратор
пытается отменить его (`gh api .../actions/runs/<id>/cancel`, best-effort —
неуспех отмены не откатывает решение «не блокирует диспатч», см. предыдущий
пункт) — иначе снятие гейта без реальной отмены оставило бы новый
`workflow_dispatch` в очереди позади старого прогона той же
concurrency-группы (`worker.yml`: `group: worker, cancel-in-progress:
false`), не решая исходную проблему.

Требование: задача, арендованная зависшим прогоном (если такая
определяется), освобождается ПОЛНОСТЬЮ (назначение и замок аренды, не
только одно из двух) сразу в этом же пульсе — не ждёт обычных 24 часов
`reap_stale`/`claim_task.collect_stale`. Задача определяется структурным
признаком, не парсингом прозы: среди открытых незаблокированных назначенных
задач без открытого PR (тот же критерий, что `reap_stale` уже применяет)
берётся та, чьё timeline-событие `assigned` не старше момента старта
зависшего прогона — `task.sh` берёт аренду в первые секунды job'а, задолго
до тяжёлой DSH-работы, поэтому это надёжный структурный признак «эта задача
принадлежит этому прогону».

Требование: если ни одна задача не коррелирует со старта зависшего
прогона (адресный прогон на задачу с уже открытым PR, либо аренда сгорела
до следа) — прогон всё равно отменяется, а сообщение действия честно
называет факт «арендованная им задача не определена», не молчит и не
гадает.

Сценарий: прогон worker.yml идёт `in_progress` 218 минут (порог 200
превышен), задача #815 арендована через 39с после старта прогона (событие
`assigned` в её таймлайне), открытого PR по ней ещё нет -> оркестратор
отменяет прогон, снимает у задачи #815 и назначение, и замок аренды,
оставляет след-комментарий с номером прогона и причиной, задача становится
доступна для новой аренды в этом же пульсе.

Сценарий: тот же зависший прогон, но ни одна открытая назначенная задача не
имеет `assigned`-события не старше момента его старта (адресная доводка PR,
уже открытого до зависания) -> прогон всё равно отменяется, действие
сообщает «арендованная им задача не определена», ни одна задача не
трогается.

Сценарий: прогон worker.yml идёт `in_progress` 60 минут (ниже порога) ->
поведение не отличается от действовавшего до этой правки — воркер считается
активным, диспатч не идёт.
