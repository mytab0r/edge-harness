# reference-closure: приёмка по ссылке — второй источник PR→задача и автозакрытие задач, заявленных чужим слитым PR (#1042)

Задача: #1042. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Стадия приёмки (`scheduler.py::accept_merged_tasks`, #227) резолвит «какая
задача у ЭТОГО PR» только по имени ветки (`task_ref.resolve_pr_task`, #394)
— и это правильно: вопрос «чей это PR» решается одним узким способом. Но
есть второй, измеренный на живом материале факт «какие задачи закрыл слитый
PR»: тело закрывающего PR прозой называет номер ДРУГОЙ задачи как покрытую
(два прохода ручной ревизии 2026-09-12: 3 из 5 закрытий класса «предмет уже
слит, задача осталась открыта» — #507 через PR #986, #661 через PR #952,
#786 через PR #841). Инвариант 1 (`check_reopened_after_merge`) такие задачи
находит, но эскалирует в #120 — потребителя, который бы закрывал их по
улике, не было.

Широкие источники для НЕОБРАТИМОГО действия не годятся: `extract_task_refs`
(любое `#N`) — живой урок #90; открытый корень `закры[а-я]*` отклонён
экспериментом на теле PR #986 («зависит закрытие #806» — существительное —
ложно совпало бы, а PR прямо пишет, что #806 не закрывается этим PR);
`Closes/Fixes/Resolves` запрещены контрактом (#953). Источник связи —
строгий список русских глагольных форм (`also_closes_targets`): русские
слова GitHub как директиву не распознаёт никогда (фиксированный английский
список ключевых слов) — автозакрытия при мерже здесь нет СТРУКТУРНО, конфликт
с #953 невозможен по построению.

## Что делается

- `scripts/lib/task_ref.py::also_closes_targets` — второй, строгий резолвер
  «какие ЧУЖИЕ задачи этот PR явно закрывает».
- `scripts/orchestra/reference_closure.py` — потребитель: машинные проверки
  (открыта, `task`, не эпик, не #120, без исполнителя, без конкурирующего
  открытого PR, не «уже обработано»), материальная улика по категориям
  штатной приёмки (`classify_acceptance`/`deploy_evidence`/
  `script_evidence`/`docs_missing` — только читаются), плюс
  «коммит слияния — предок main» (класс #925) и текстовый признак
  мутационного доказательства для добавленных гвардий каталога (#749).
  Закрытие ПЕРВЫМ, маркер-комментарий вторым — сбой PATCH повторяется
  следующим прогоном, а не замораживает кандидата (находка ревью PR #1046).
- Шаг «Приёмка по ссылке» в workflow `orchestra` — носитель вызова
  (класс «потребитель без вызова — мёртвый код», находка ревью PR #1046):
  после планировщика, гейт квоты `steps.quota.outputs.skip`, continue-on-error
  — как у соседних шагов job'а.
- Потолок 5 закрытий за прогон (газ, обоснование в докстринге модуля);
  наблюдаемость — каждый кандидат печатается закрытым или пропущенным
  с причиной; сбой проверки улики — эскалация #120 (тот же канал, что у
  штатной приёмки).

## Честная граница

- Собственная задача ветки закрывающего PR исключена — её закрывает штатная
  приёмка, второй механизм на ту же пару (задача, PR) не заводится.
- #1021/#967 (ложный `ACCEPTANCE_PARTIAL_MARKER` на own-task PR) — правка
  `scheduler.py::partial_disclaimer`, вне территории #1042 (файл занят
  параллельными PR), см. тело задачи.
- «Критерий по существу» (#389), «отменено владельцем» (#901), «дубль
  класса» (#720/#752, #750/#766) — сознательно не формализуются, работа роли.

## Проверено

- `python -m pytest scripts/orchestra/test_reference_closure.py -q` — зелёный;
  `python -m pytest scripts/lib -q` и `scripts/orchestra -q` — зелёные.
- Мутации: снять исключение own_task → дублирование штатной приёмки красит

  проводки краснеет.
