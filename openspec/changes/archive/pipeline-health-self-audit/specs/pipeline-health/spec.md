# Дельта-спека: pipeline-health (новая способность) — снимок метрик + регрессия + само-аудит

Новая способность, не расширение `journal-tasks-hands`: цель другая (детекция
ЗЕЛЁНОЙ, но ухудшающейся системы, не механика пула задач/PR как таковая) —
design.md, раздел «Что уже есть», разводит три существующих детектора
(реактивных к КРАСНОМУ) и этот механизм явно.

## ADDED: Снимок метрик здоровья конвейера

Требование: раз в календарные сутки (UTC) конвейер (пульс `orchestra`)
собирает снимок из 6-7 дешёвых метрик — merge throughput (PR слито за
сутки), PR age p50/p95 открытых PR, backlog пула по состояниям (свободна/в
работе/blocked/stale-unclaimed), worker success-rate (rolling
`WORKER_SUCCESS_WINDOW` прогонов `worker.yml`), каденс пульса `orchestra`
(тиков за 24ч против ожидаемого по интервалу cron), стоимость DO
(`rows_read`, % от суточного лимита — опционально, честное «нет данных» без
токенов Cloudflare) и остаток GitHub rate-limit (`scripts/measure/
pipeline_health.py::collect`). Каждый источник — тот же список/вызов,
что остальной конвейер уже читает этим же пульсом (0 доп. запросов), кроме
`merge_throughput` (1 `search/issues` в сутки) и DO cost (1 GraphQL-запрос
в сутки, минуя DO) — design.md §1.

Сценарий: пульс `orchestra` срабатывает четвёртый раз за сутки (интервал
15 мин) — снимок НЕ снимается повторно (`should_snapshot` проверяет дату
последней строки на ветке данных), сетевые вызовы сборщика не выполняются.

Требование: снимок хранится JSONL-строкой на отдельной git-ветке
`data/pipeline-health` (не main — не засоряет историю снимками; не таблица
DO SQLite — бюджет DO узкий, #575), append-only, одна строка на сутки.
Гонка двух параллельных писателей разрешается git push retry с повторным
чтением уже записанной строки (`append_snapshot_and_push`).

Сценарий: два прогона `orchestra` попадают в снятие снимка одновременно —
первый пушит успешно, второй видит после `fetch`/`checkout` уже записанный
день той же даты и не дублирует строку.

## ADDED: Детектор регрессии

Требование: `scripts/orchestra/health_regression.py::classify_metric`
считает по каждой из 6 регрессионных метрик (merge throughput, PR age p95,
backlog всего, worker success-rate, каденс пульса, DO cost) baseline —
медиану значений за последние `BASELINE_WINDOW_DAYS` (14) снятых точек — и
сравнивает сегодняшнее значение с порогом отклонения
`REGRESSION_THRESHOLD_PCT` (50%) В ХУДШУЮ для метрики сторону. Три честных
исхода: `insufficient_data` (меньше `MIN_SAMPLES_FOR_BASELINE`=5 снятых
точек), `ok` (отклонение ниже порога либо не держится
`MIN_REGRESSION_STREAK_DAYS`=3 дня подряд), `regression`/`fire` (держится).

Сценарий: история метрики содержит 4 точки — классификатор возвращает
`insufficient_data` с причиной, не «всё хорошо» и не ложную тревогу.

Требование: `regression` эскалируется до `fire`, если сегодняшнее
отклонение >= `ESCALATION_THRESHOLD_PCT` (100%) ИЛИ регрессия держится >=
`ESCALATE_AFTER_DAYS` (7) дней — один расчёт с двумя порогами (как
`pulse_guard.decide_gate_state`), не отдельные if-цепочки.

Сценарий: метрика деградировала на 60% и держится 3 дня — `regression`
(обычный приоритет); метрика деградировала на 100%+ — `fire` (эскалация)
независимо от того, сколько дней это длится.

## ADDED: Само-аудит — заведение задач без спама

Требование: `scripts/orchestra/health_audit.py::run_self_audit` для каждой
метрики в статусе `regression`/`fire` ищет открытую задачу с отпечатком
`regression:<метрика>` (подстрока «Отпечаток: `<fp>`» в теле открытых issues
с меткой `self-audit`) — нашёл: комментарий с новой уликой (не дублируется,
если улика за тот же день уже оставлена); не нашёл и суточный потолок
`SELF_AUDIT_DAILY_CAP` (= число регрессионных метрик, 6) не исчерпан —
заводит задачу через `scripts/lib/pool_issue.py::create_pool_issue` (метки
`task`+`self-audit`); потолок исчерпан — эскалация владельцу тем же каналом,
что `pulse_guard.escalate` (issue-комментарий в #120 + Telegram), не более
раза в сутки, задача НЕ заводится.

Сценарий: регрессия по `merge_throughput` уже завела задачу #900 вчера,
сегодня та же регрессия продолжается — комментарий с новыми числами в #900,
вторая задача не создаётся.

Требование: статус `fire` заводит задачу как обычно И немедленно эскалирует
её тем же каналом (issue-комментарий + Telegram) — различение «улучшение»/
«пожар» одной функцией с двумя порогами (design.md §3.2), не гаданием.

Требование: механизм НЕ закрывает автоматически ни задачи, ни PR, ни ветки —
только заводит/комментирует задачи регрессии (design.md §4, сверено с
отказом владельца от автозакрытия, `scheduler.py:3583-3609`). Критерий
готовности задачи — метрика вернулась к baseline (проверяется следующим
снимком) либо владелец решил, что это новая норма (порог/baseline
пересматривается руками, design.md §4.3).

## Не подтверждено (перенесено из design.md/proposal.md)

Пороги (`BASELINE_WINDOW_DAYS`, `REGRESSION_THRESHOLD_PCT`,
`MIN_REGRESSION_STREAK_DAYS`, `ESCALATION_THRESHOLD_PCT`,
`ESCALATE_AFTER_DAYS`, `SELF_AUDIT_DAILY_CAP`) названы по аналогии с уже
существующими порогами конвейера, ни один не выведен из данных этого
репозитория — история снимков не существовала на момент реализации.
Подбор по факту первых недель эксплуатации — отдельная работа.
