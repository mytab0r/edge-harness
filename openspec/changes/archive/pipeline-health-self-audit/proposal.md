# Proposal: само-аудит здоровья конвейера — детектор регрессии + непрерывный дешёвый снимок метрик

Задача: #822. Реализация design.md ниже (proposal/design написаны разведкой,
задача заведена и реализация начата отдельным проходом — `tasks.md` рядом
называет разбивку и исполнителя каждого пункта).

## Summary

В конвейере уже есть три механизма, которые сами превращают ИЗВЕСТНЫЙ КЛАСС
падения в задачу пула: `scripts/orchestra/pulse_guard.py::failure_watch` (#477,
красный прогон workflow -> задача `ci-failure`), `scripts/orchestra/stall_detector.py`
(#201, устойчивый симптом простоя в отчёте пульса -> задача `auto-detected`),
`scripts/orchestra/upstream_drift.py` (#134, дрейф апстрима -> задача плюс PR). Все три
реагируют на КРАСНОЕ — упавший прогон, красную проверку, застрявшую задачу.
Ни один не видит ЗЕЛЁНУЮ, но ухудшающуюся систему: конвейер продолжает
успешно мержить PR, но реже; PR продолжают проходить ревью, но дольше; воркер
продолжает открывать PR, но чаще проваливается. Этот класс регрессии сейчас
не измеряется и не детектируется вовсе — единственный способ его заметить
сегодня — разовый ручной замер (scripts/measure/*.py, дёрнутый человеком по
поводу инцидента) или чтение docs/research/20-cloudflare-free.md постфактум.

Документ отвечает на вопрос владельца «почему мы автоматически не ведём
замеры и не имеем механизмов их получения» дизайном (не кодом) минимального
дешёвого снимка метрик, схемы детекции регрессии без ложных тревог, и
механизма само-аудита, который заводит задачи улучшения через уже
существующий pool_issue.create_pool_issue, не изобретая второй канал.

## Problem / motivation

- Существующие детекторы реактивны к падению, не к деградации (обобщённый
  класс, сформулированный в задании этого анализа). Замер (AGENTS.md,
  «Инцидент оставляет инвариант»): из ~15 дефектов конвейера 2026-09-02/03
  ни один не найден системой — все нашли люди, читая логи.
- Метрики здоровья либо разовые (scripts/measure/quotas.py,
  do_rows_read.py, dispatch_tail.py, label_churn_203.py — вызываются
  вручную или по workflow_dispatch), либо не существуют вовсе (merge
  throughput, PR age p50/p95, backlog по состояниям, worker success-rate как
  временной ряд — нигде не считаются и не хранятся; см. design.md, раздел
  «Что уже есть»).
- Пять кусков этой задачи уже лежат в пуле как stale-unclaimed: сквозной
  замер канала (#348), время цикла/граф блокировок (#224), два среза
  дашборда пула в морде (#407, #377), стоимость события DO (#678) — годами
  не взятые, потому что каждый по отдельности не формулирует, что с числом
  делать дальше. Этот дизайн называет недостающую связку: снимок -> регрессия
  -> задача, без которой сами по себе цифры остаются красивой таблицей.
## Scope

**In:**
- Минимальный набор метрик здоровья конвейера и дешёвый (не бьющий по лимитам
  DO/GitHub) способ их снятия на регулярной основе.
- Схема хранения снимка и алгоритм детекции регрессии (не гадание, честный
  потолок ложных тревог по образцу stall_detector/обобщённого класса).
- Механизм периодического само-аудита, заводящего задачи улучшения через
  pool_issue.create_pool_issue, с дедупом и суточным потолком по образцу
  failure_watch/stall_detector.
- Классификация «что машинно-безопасно чистить» против «что остаётся
  суждением человека», с явной сверкой с отвергнутым владельцем автозакрытием
  чужих PR (scripts/orchestra/scheduler.py:3583-3609) и общий принцип этого
  файла — приёмка никогда не закрывает автоматически то, что может оборвать
  чужую незавершённую работу.
- Явная связь с существующими stale-unclaimed задачами #348/#224/#407/#377/
  #678: какие становятся подзадачами этого цикла, какие — нет.

**Out (сознательно, не в этом change):**
- Реализация кода — только дизайн.
- Дашборд в морде dsh-edge (#407/#377) — потребитель снимка метрик, не его
  источник; дизайн называет, что дашборду нужны данные, которые этот change
  производит, но сам дашборд — отдельная работа.
- Автоматическое исправление найденных регрессий (само-аудит заводит задачу,
  чинит воркер — тот же принцип разделения, что у stall_detector: «решает
  воркер, детектор только замечает»).
- Авто-закрытие чужих PR, веток или задач по признаку «выглядит ненужным» —
  отвергнуто владельцем, не предлагается заново (см. design.md, раздел
  «Сознательно отвергнуто»).
- Удаление кода по признаку покрытия тестами — не машинно-безопасно (см.
  design.md), остаётся находкой для человека, не автодействием.
## Impacted domains

- scripts/orchestra/ (scheduler.py, pulse_guard.py — новый модуль-сосед по
  образцу stall_detector.py/upstream_drift.py).
- scripts/measure/ (расширение существующих разовых замерщиков до
  переиспользуемых источников снимка, не замена).
- cf-worker/src/harness.ts — под вопросом: хранить ли снимок в DO SQLite
  или вне DO (см. design.md, там же явно названо, что решение не выбрано).
- docs/agents/LABELS.md — новая метка происхождения задач само-аудита, если
  design.md решит заводить отдельную от auto-detected.
- openspec/changes/archive/ — #348/#224/#407/#377/#678, решение по каждой в
  design.md.

## Acceptance criteria

Для дизайна (этот change не содержит кода, но design.md обязан ответить
проверяемо):

1. Список метрик в design.md несёт для каждой метрики: источник (файл/API),
   стоимость снятия в терминах существующих лимитов (DO CPU/rows, GitHub API
   вторичный лимит), и ссылку на то, читается ли она уже сегодня каким-то
   кодом конвейера — не гадание, file:line.
2. Схема регрессии называет конкретный алгоритм (baseline плюс порог/тренд) и
   явно — минимальный размер выборки, при котором сигнал не подаётся
   («недостаточно данных» как честный третий исход, не «всё зелено» и не
   ложная тревога).
3. Механизм само-аудита называет: дедуп-ключ, суточный или иной потолок,
   канал заведения задачи (существующий pool_issue.create_pool_issue), и как
   он отличает «улучшение» (обычный приоритет) от «пожара» (эскалация тем же
   каналом, что pulse_guard.escalate).
4. Раздел про чистку явно делит примеры на «безопасно машиной» и «суждение
   человека», с обоснованием каждого пункта, и явно называет, что
   автозакрытие PR или задач НЕ предлагается — по прямому решению владельца.
5. Раздел «Связь со stale-задачами» проходится по каждой из #348/#224/#407/
   #377/#678 (и по #683, найденному в задании) и говорит «становится частью»
   или «вне» с причиной.
6. Разделы «Не подтверждено» и «Сознательно отвергнуто» присутствуют и не
   путают эти два класса (недоказанный факт против решённого вопроса).

## Risks / unknowns

- Где хранить снимок (новая таблица DO SQLite против git-артефакта вроде
  data/dispatch-latency-tail, ADR 0005) — решение в design.md, но само
  решение не проверено на затраты рабочим прогоном (не сделан прототип).
- Регрессия по метрикам с низкой и нерегулярной частотой событий (мерджи в
  выходные, PR открываются волнами) — эвристика порога может дать ложные
  срабатывания на малой выборке; конкретные числа порогов в design.md
  помечены как «подобрать эмпирически», не «выведены математически».
- Пересечение обязанностей с #224 (граф блокировок и приоритет) — тот же
  источник данных (issues API), риск дублирования логики чтения, если делать
  раздельно от той задачи; названо явно в design.md.
