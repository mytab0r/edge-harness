## 1. Минимальный набор метрик и откуда каждая берётся дёшево

Критерий отбора: метрика попадает в список, только если (а) она отвечает на
вопрос «здоровье конвейера ухудшается или нет» и (б) её можно снять БЕЗ
нового постоянного опроса, использующего данные, которые пульс `orchestra`
и так уже читает КАЖДЫЙ прогон (каждые ~15 мин, cron orchestra.yml + событийный
будильник, ADR 0012), либо данные, которые GraphQL Cloudflare отдаёт ОДНИМ
запросом раз в сутки (внешний вызов из GH Actions job, НЕ бьёт по бюджету DO
вовсе — этот вызов не проходит через Durable Object, а идёт напрямую в
Cloudflare Analytics API, см. do_rows_read.py/quotas.py — уже так делают).

| Метрика | Источник (file:line) | Уже читается сегодня? | Предельная стоимость |
|---|---|---|---|
| Merge throughput (PR слито / сутки) | GitHub Search API `is:pr is:merged merged:>=ДАТА` ИЛИ инкремент внутри scheduler.after_merge (scripts/orchestra/scheduler.py, вызывается на каждый мерж пула) | Частично: after_merge уже видит каждый мерж внутри своего прогона (см. merge_telegram_text, pulse_guard.py:791-802), но не накапливает счётчик суток | 1 доп. GH REST/Search запрос раз в сутки на снятие среза, либо 0 доп. запросов при инкрементном счётчике в существующем after_merge |
| PR age p50/p95 (открытые PR) | `GET /repos/.../pulls?state=open` — тот же список, что scheduler читает для merge_queue/unhealthy_pulls (scripts/orchestra/scheduler.py, review_labels.list_pages) | Да, список открытых PR уже в памяти каждого пульса | 0 доп. запросов — переиспользование уже полученных данных внутри того же прогона |
| Backlog по состояниям задач (свободна/в работе/blocked/stale-unclaimed) | `GET /repos/.../issues?labels=task` — тот же вызов, что scheduler.open_task_issues делает каждый пульс | Да | 0 доп. запросов |
| Worker success-rate (rolling N дней) | `recent_runs(repo, "worker.yml", per_page=100)` — та же функция, что pulse_guard.count_consecutive_failures уже вызывает (pulse_guard.py:808-815), но берёт только префикс подряд идущих; нужна доп. агрегация по всему окну | Частично: сырые данные уже получены, агрегат по rolling success-rate — новый расчёт над теми же данными | 0 доп. запросов (то же recent_runs, другая свёртка результата) |
| Каденс пульса orchestra (сколько реальных тиков за 24 ч против ожидаемых) | `orchestra_tick_runs` (pulse_guard.py:661-676) — уже считает реальные тики через серверный фильтр `?event=` | Да, используется decide_heartbeat/heartbeat_check | 0 доп. запросов, используется существующий результат |
| Стоимость DO (rows_read/written за сутки, % от лимита) | `do_rows_read.py` (Cloudflare GraphQL Analytics, `durableObjectsPeriodicGroups`) | Да, но по workflow_dispatch, не по расписанию | 1 GraphQL-запрос/сутки — внешний вызов из job'а, не CPU/rows-квота самого DO |
| GitHub API остаток (rate_limit) | `gh api rate_limit` (scripts/lib/rate_guard.py, issue #454) — подтверждено 2026-09-06: НЕ тратит собственную квоту | Да, уже читается в orchestra/ai-review/test как ранняя проверка | 0 доп. запросов сверх существующих, снимается попутно |

**Явно НЕ вошло в минимальный набор** (кандидаты, отвергнутые для ПЕРВОЙ
версии — не навсегда, см. design.md §5 про #224):
- Время цикла задача->PR->мерж поштучно (не агрегат) — это предмет отдельной
  задачи #224 (граф блокировок и Гант), не минимального снимка здоровья;
  агрегатный merge throughput выше — достаточный прокси для регрессии, не
  подменяет #224.
- Стоимость конкретного SQL-запроса внутри DO (не только суммарный
  rows_read/written) — упирается в тот же пробел, что уже назван «не
  подтверждено» в research/20 (пп. 10-11): нет инструмента читать метрику
  per-SQL, только по DO целиком. Не строим на неподтверждённом.

## 2. Где хранится снимок и как считается регрессия

### 2.1 Хранилище — git-артефакт, НЕ новая таблица DO SQLite (решение, не факт)

Выбор в пользу git-артефакта (по образцу data/dispatch-latency-tail, ADR 0005:
отдельная git-ветка с CSV, не main — не засоряет историю коммитами снимков),
а не новой таблицы в cf-worker/src/harness.ts. Причины:

1. **Бюджет DO уже узкое место** (docs/research/20-cloudflare-free.md,
   раздел «DO SQLite» — «узкое место — 100 000 записей строк в день, не
   объём»). Инцидент #575 показал, что даже одна забытая некэшированная
   таблица (messages) без ретеншена превращает 100% суточного rows_read в
   149.8%. Добавлять НОВУЮ таблицу в DO, которая пишется раз в сутки (даже
   1 строка) — небольшая цена сама по себе, но каждая новая таблица в схеме
   DO — это ещё один RETENTION_TABLES-пункт, который нужно не забыть
   (cf-worker/src/harness.ts:164-186), и ещё один потенциальный полный скан
   при неосторожном будущем запросе (тот же класс, что #320/#575 уже дважды
   подпаливал).
2. **Вычисление снимка происходит на стороне GH Actions (Python), не внутри
   DO** — метрики выше уже читаются оттуда (scheduler.py работает в job'е,
   не в DO). Если писать снимок в DO, это добавляет сетевой хоп
   (Actions -> DO -> запись -> потом снова Actions -> DO -> чтение для
   сравнения) без выгоды: DO не нужен как посредник для данных, которые сам
   же не производит.
3. **Ревьюируемость.** Git-артефакт виден в PR (если коммитится в основную
   историю) или как append-only лог на отдельной ветке (если часто) — то же
   решение, что уже принято для dispatch-latency-tail. Данные в DO SQLite
   не видны никому, кроме как через отдельный debug-эндпоинт.

Механика: отдельная git-ветка `data/pipeline-health` (не main), один CSV
(или JSONL — предпочтительнее CSV, потому что снимок будет расти набором
полей и JSONL с добавлением поля не ломает старые строки, тогда как CSV
требует either фиксированной схемы, либо переусложнённого парсинга).
Одна строка/сутки, добавляется коммитом от orchestra (тот же принцип, что
dispatch_tail.py уже делает — коммит на выделенную ветку, не на main).

**Стоимость по лимитам:** 1 git push/сутки — не бьёт ни по одному лимиту из
исследованных (не GitHub API rate limit в смысле REST-вызовов; push через
git — отдельный канал, не 5000/500-часовой REST-счётчик).

### 2.2 Каданс снятия — раз в сутки, не на каждый пульс

Снимок считается ВНУТРИ уже существующего пульса orchestra (не отдельным
workflow/cron — research/21 показал: голый `schedule` на этом репозитории
доставляет ~7% тиков, ADR раздел «Замер schedule», поэтому НЕ полагаемся на
отдельный cron для надёжности снятия; используем уже надёжный канал —
событийный будильник + существующий 5-минутный cron DO, issue #693), но
ВЫПОЛНЯЕТСЯ только если с последнего снимка в data/pipeline-health прошли
календарные сутки (UTC) — проверка: последняя строка файла на ветке данных
старше текущей даты. Тот же приём, что уже документирован в research/20 для
`do_rows_read.py --days N` («снимать НА следующий день ИЛИ позже»).

Без этого гейта пульс писал бы новую строку каждые 15 минут — 96 строк/сутки
вместо одной, git-история захламляется, а «снимок дня» становится
бессмысленным (день ещё не закрылся). Гейт — простая проверка даты, не
требует отдельного состояния сверх самого файла данных.

### 2.3 Схема регрессии

**Baseline — скользящее окно, не фиксированный порог.** Фиксированный порог
(«merge throughput < 2/день — тревога») не переживает изменение фактического
темпа работы (число параллельных агентов меняется, задачи меняются по
размеру) — он либо слишком строг в тихие периоды, либо бесполезен в горячие.
Вместо этого — сравнение с ТРЕНДОМ этого же ряда:

```
baseline = медиана значений метрики за последние BASELINE_WINDOW_DAYS дней
           (по умолчанию 14 — компромисс: короче 7 дней ловит случайный
           плохой день как "норму", длиннее 30 - реагирует слишком медленно
           на настоящую деградацию; число ПОДБИРАЕТСЯ ЭМПИРИЧЕСКИ на первых
           неделях эксплуатации, не выведено математически - см. proposal.md
           "Risks/unknowns")
регрессия, если today_value отклоняется от baseline более чем на
REGRESSION_THRESHOLD_PCT (по умолчанию 50% в "плохую" сторону метрики —
для merge throughput/success-rate это падение, для PR age/backlog - рост)
```

**Честный третий исход — "недостаточно данных".** Как и stall_detector
(STALL_PERSIST_MINUTES — разовый блип не заводит задачу), регрессия здесь
ДОЛЖНА продержаться не один снимок, а MIN_REGRESSION_STREAK_DAYS подряд
(по умолчанию 3) — иначе один плохой день (выходные, разовый инцидент уже
пойманный failure_watch отдельно) даёт ложную тревогу поверх уже
существующего сигнала. Плюс: baseline не считается вовсе, если в окне
BASELINE_WINDOW_DAYS меньше MIN_SAMPLES_FOR_BASELINE точек (по умолчанию 5)
— молодой снимок (первые дни после внедрения) не может иметь "тренда", и
детектор обязан явно сказать "недостаточно истории для baseline", а не
подставить 0/None как норму (тот же класс "fail loud, не silent-wrong",
AGENTS.md).

**Честный потолок, названный прямо (как и у #519/stall_detector):** этот
детектор ловит регрессию ТОЛЬКО в метриках из §1 — то есть только то, что
уже наблюдаемо дёшево. Регрессия, не отражающаяся ни в одной из шести
метрик (например: конкретный агент стал качественнее/хуже писать код, но
объём и скорость слияний не изменились), детектором не поймана и не может
быть поймана этим дизайном — как и stall_detector, который "видит только
отчёт СВОЕГО прогона" (docstring stall_detector.py, "Честный потолок").

## 3. Механизм само-аудита: заведение задач без спама

### 3.1 Дедуп-ключ и потолок — по образцу failure_watch/stall_detector, СВОЙ счётчик

Отпечаток регрессии: `regression:<имя_метрики>` (например
`regression:merge-throughput`, `regression:pr-age-p95`,
`regression:worker-success-rate`) — по одному классу на метрику, не на
конкретное числовое значение (числовое значение меняется каждый день, класс
"эта метрика деградирует" — нет). Поиск открытой задачи с тем же отпечатком —
тот же приём, что `stall_detector.find_open_task`
(scripts/orchestra/stall_detector.py:272-278): подстрока
"Отпечаток: `<fp>`" в теле открытых issues с новой меткой (см. §3.3).

**Свой суточный потолок**, НЕ общий со STALL_DAILY_CAP/FAILURE_WATCH_DAILY_CAP
— то же обоснование, что уже разведено в докстринге
pulse_guard.py:378-406 для failure_watch относительно stall_detector: разные
предметные области (регрессия ЗДОРОВЬЯ конвейера — не то же самое, что
красный прогон или застрявшая задача), общий бюджет означал бы, что
несколько метрик, деградировавших одновременно (реалистичный сценарий —
все метрики связаны одним и тем же корневым инцидентом), выжирают весь
бюджет и маскируют следующий класс. Максимум 6 метрик в §1 -> потолок можно
поставить равным их числу (SELF_AUDIT_DAILY_CAP = 6) без риска "бесконечного
роста пула": по построению не может быть открыто больше 6 задач регрессии
одновременно (по одной на метрику), любая новая задача по уже занятой
метрике — комментарий к существующей, не новая issue.

### 3.2 Отличие "улучшение" от "пожара"

Не гадание (по правилу AGENTS.md "Алерт не гадает") — а прямая функция того,
НАСКОЛЬКО метрика отклонилась и как долго:

- **Обычный приоритет** (задача заводится с меткой `task` + `self-audit`,
  без эскалации в Telegram) — регрессия только что продержалась
  MIN_REGRESSION_STREAK_DAYS дней, отклонение в диапазоне
  [REGRESSION_THRESHOLD_PCT; ESCALATION_THRESHOLD_PCT) (например 50%-100%).
- **Пожар** (тот же канал эскалации, что pulse_guard.escalate — issue-
  комментарий + Telegram) — отклонение >= ESCALATION_THRESHOLD_PCT (по
  умолчанию 100%, то есть метрика минимум вдвое хуже baseline) ИЛИ регрессия
  держится дольше ESCALATE_AFTER_DAYS (по умолчанию 7, по аналогии с
  ESCALATE_AFTER_HOURS=48 у stall_detector, но здесь единица - сутки, потому
  что снимок раз в сутки, а не поминутный пульс) без закрытия задачи.

Это НЕ два разных детектора - один и тот же расчёт (§2.3) с двумя порогами,
как decide_gate_state pulse_guard.py:519-543 уже возвращает несколько
исходов ('closed'/'first'/'probe'/'open') из одного набора чисел, а не
отдельными if-цепочками без общего критерия.

### 3.3 Метка происхождения

Новая метка `self-audit` (не переиспользуем `auto-detected` от stall_detector
и не `ci-failure` от failure_watch) — по правилу docs/agents/LABELS.md
("реестр меток - место правды, а не примеры"): класс сигнала другой
(регрессия ЗДОРОВЬЯ, не симптом простоя и не провал прогона), и раздельная
метка даёт раздельный дедуп-поиск (open_auto_tasks аналог, фильтр по своей
метке) без риска, что три разных детектора начнут путать друг друга при
поиске "уже открытой задачи по этому классу". Требует правки
docs/agents/LABELS.md при реализации - здесь только называется, не
делается.

### 3.4 Тело задачи - обязательные разделы (по образцу stall_detector._render_body)

- Отпечаток (машиночитаемая строка для дедупа).
- Числа: baseline, сегодняшнее значение, отклонение в процентах, сколько
  дней подряд.
- Ссылка на снимок (файл/коммит на ветке data/pipeline-health) - "нет
  цитаты из данных - нет задачи", тот же принцип, что уже требует
  stall_detector.docstring ("Каждый Signal несёт дословную строку отчёта
  как улику").
- Честный потолок: "детектор ТОЛЬКО заметил числовую регрессию, причину и
  фикс ищет исполнитель" - копия формулировки stall_detector §"Честный
  потолок" (docstring), не новая формулировка того же принципа.

## 4. Что безопасно чистить машиной, а что остаётся суждением человека

### 4.1 Машинно-безопасно (критерий: действие обратимо ИЛИ бьёт только по
артефакту, который сам конвейер же и произвёл, никогда не по чужой
незавершённой работе)

| Что чистить | Почему безопасно | Статус |
|---|---|---|
| Рабочие деревья `.claude/worktrees/<N>-*` без живого агента и с уже слитым/закрытым PR | Уже реализовано и осторожно: удаляет ТОЛЬКО при одновременно (а) ветка называет задачу, (б) её PR не open (сигнал через `gh pr list`, не факт существования ветки на origin — этот репозиторий ветку после мержа не удаляет), (в) дерево чистое, (г) нет несмерженных коммитов (issue #891, `scripts/git/worktree-cleanup.py`, подключено в `scripts/git/task-branch`). ### 4.2 Суждение человека (критерий: действие необратимо ИЛИ затрагивает
работу, которую детектор не может отличить от "ещё не законченной")

| Что НЕ чистить машиной | Почему |
|---|---|
| Открытые PR (свои или чужие), выглядящие "устаревшими" | Прямо отвергнуто владельцем (коммит 2026-09-06, scheduler.py:3583-3609 - эпик с закрытыми sub-issues получает МАРКЕР + комментарий "требует ручного закрытия", не auto-close). Этот дизайн НЕ предлагает завести другой механизм авто-закрытия PR под другим именем ("само-аудит чистит хвосты") - это был бы тот же запрещённый класс с косметически другим триггером |
| "Мёртвый код" по признаку покрытия тестами | Отсутствие тестового покрытия НЕ равно "код не используется" - может быть код для редкого пути (обработка ошибки, которая случается раз в месяц), код для будущей фичи с уже написанным контрактом, код, вызываемый динамически (importlib.util.spec_from_file_location - этот самый репозиторий активно использует такой паттерн подключения модулей, статический анализ покрытия его не увидит). Решение "удалить" требует понимания НАМЕРЕНИЯ автора кода - суждение, не метрика |
| Устаревшие ветки БЕЗ PR (заброшенные agent/N-* без открытого/слитого/закрытого PR) | Отличить "агент забросил работу" от "агент ещё работает, PR будет позже" по внешним признакам (age ветки) ненадёжно - тот же класс риска, что уже назван в правиле "Тормоз без газа не принимается": исполнитель мог быть неактивен часами по внешней причине (пауза предохранителя, квота провайдера), не по забросу |
| stale-unclaimed задачи пула старше N дней | "Никто не взял задачу" - НЕ признак "задача не нужна" (может быть низкий приоритет, явно объявленный владельцем - живой пример: issue #224 несёт раздел "Приоритет: Низкий - по прямому указанию владельца"). Авто-закрытие по возрасту закрыло бы намеренно отложенную работу |
| Дельта-спеки в openspec/changes/*, не влитые в journal-tasks-hands.md | docs/agents/OPENSPEC-PROTOCOL.md прямо называет это "редакторским суждением, не текстовой операцией" ("Само слияние текста... это редакторское суждение... Механическое слепое приписывание... дало бы противоречивый, задвоенный источник правды хуже текущего отсутствия слияния") - тот же вывод этот дизайн не пересматривает |

### 4.3 Сверка со сравнением "тормоз без газа"

Само-аудит - НОВЫЙ тормоз (задача заводится, кто-то должен её взять) и
обязан по правилу AGENTS.md ("Тормоз без газа не принимается") называть
газ явно: газ здесь - воркер берёт задачу `self-audit` как любую другую
задачу пула (та же механика, что `task`+`auto-detected`/`ci-failure`), и
задача закрывается ЛИБО фиксом (метрика вернулась к baseline - проверяется
следующим снимком, не декларацией воркера), ЛИБО решением владельца "это
не регрессия, а новая норма" (тогда порог/baseline пересматривается руками,
не автоматически - подобно тому, как STALL_DAILY_CAP поднимается руками при
временном всплеске, pulse_guard docstring). Автоматического возврата нет,
и это называется прямо, а не маскируется: то же честное признание, что уже
есть у ESCALATE_AFTER_HOURS/ESCALATE_AFTER_DAYS - ручной газ, но названный.

## Не подтверждено

1. **Числа порогов** (BASELINE_WINDOW_DAYS=14, REGRESSION_THRESHOLD_PCT=50,
   MIN_REGRESSION_STREAK_DAYS=3, ESCALATION_THRESHOLD_PCT=100,
   ESCALATE_AFTER_DAYS=7, SELF_AUDIT_DAILY_CAP=6) - все НАЗВАНЫ по аналогии
   с уже существующими порогами (STALL_PERSIST_MINUTES,
   AI_REVIEW_MAX_ATTEMPTS и т.д.), ни один не выведен из данных этого
   репозитория: временного ряда метрик ещё не существует, снять эмпирику
   не на чем до того, как снимок начнёт копиться. Подобрать по факту первых
   недель - явно названная работа, не сделанная здесь.
2. **Стоимость 1 git push/сутки на отдельную ветку данных** - по аналогии с
   уже работающим dispatch_tail.py/data/dispatch-latency-tail (тот же
   паттерн), но НЕ измерена отдельно для ЭТОГО нового потока данных -
   разумно предположить ту же цену (пренебрежимо малую), но это перенос
   вывода с одного случая на другой, не отдельный замер.
3. **Почему `delete_branch_on_merge` сейчас `false`.** Могло быть осознанным
   решением (например, чтобы уборщик worktree'ов или другой механизм ещё
   читал ветку после мержа перед удалением дерева) или просто дефолтом,
   который никто не трогал. Не выяснено чтением кода/доков - до включения
   этой настройки стоит проверить, не полагается ли какой-то скрипт на то,
   что ветка после мержа ещё существует какое-то время (`scripts/git/
   worktree-cleanup.py`, #891, читает `origin/main` для сверки коммитов
   запасным путём, когда апстрим-ветка уже упразднена, - **потенциальная
   коллизия**, не проверено экспериментом).
4. **CSV vs JSONL для снимка** - названо предпочтение (JSONL легче
   расширять по полям), но не проверено на реальном объёме (365 строк/год -
   тривиально малый файл для обоих форматов, разница чисто в удобстве
   поддержки, не в лимитах).
5. **Пересечение с #224 по чтению issues/PR API** - названо как риск в
   proposal.md, конкретная форма общего модуля (если оба будут
   реализовываться) не спроектирована - решение "не дублировать" названо,
   код общего ридера - нет.

## Сознательно отвергнуто

Сверено с docs/research/30-rejected-alternatives.md на предмет "не предлагать
забытое заново" - прямых пересечений с 16 пунктами того документа не найдено
(та таблица - про архитектуру CF/GitHub-раннера, этот дизайн - про
логику детекции поверх уже принятой архитектуры). Отдельно, специфично для
ЭТОГО домена:

1. **Автозакрытие "устаревших" PR/веток/задач как способ "чистки"** -
   отвергнуто владельцем (scheduler.py:3583-3609, коммит 2026-09-06) для
   эпиков; этот дизайн распространяет тот же принцип на ВСЁ подряд (PR,
   ветки, stale-unclaimed задачи) по аналогии, не по отдельному
   высказыванию владельца про каждый из этих трёх случаев - экстраполяция,
   а не факт трёх отдельных решений. Названо честно: единственный
   ПРЯМОЙ прецедент отказа - про эпики, остальное - разумное расширение
   того же принципа, требующее подтверждения при реализации, если кто-то
   решит его оспорить.
2. **Постоянно живой опрашиватель метрик (демон/долгий job)** - отвергнуто
   по той же причине, что и вся архитектура push-модели
   (docs/research/30-rejected-alternatives.md, пп. 2-3, 6): "морда живёт
   всегда, руки поднимаются по требованию" - снимок метрик считается ВНУТРИ
   уже существующего короткого пульса orchestra, не отдельным
   долгоживущим процессом.
3. **Хранение снимка в новой таблице DO SQLite** - не отвергнуто владельцем
   явно (не было такого решения ДО этого дизайна), а отвергнуто ЭТИМ
   дизайном по причинам §2.1 (бюджет rows/новый RETENTION-пункт,
   ревьюируемость) - то есть это решение design.md, не факт из истории
   репозитория; если бюджет DO окажется НЕ узким местом на практике
   (например Paid-план), пересмотр уместен.
