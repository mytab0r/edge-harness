# Дельта-спека: журнал (journal-tasks-hands) — заметка-итог несёт identified message (#794)

## MODIFIED: Конвейер (оркестратор)

38. Заметка-итог в сессию раннера `harness-<N>` (`runner-session-outcome-notes`,
    #480) — событие `assistant/message`, `data.message` теперь несёт ПОЛНУЮ
    форму, требуемую хранилищем (`@deepseek-ai/dsh-session::assertMessageEventShape`,
    проверено живым вызовом на пинованной версии `0.1.2-rc.1`), не только
    `role`/`content`:

    - `id` — непустая строка, составной и детерминированный формат
      `harness-note:<session_id>:<GITHUB_RUN_ID>:<счётчик процесса>` (тот же
      приём, что апстрим сам применяет для миграции легаси-сообщений без
      identity, `legacyMessageId`); уникален и в пределах одного запуска
      `scheduler.py` (счётчик), и между запусками (`GITHUB_RUN_ID`).
    - `role: "assistant"` (было и раньше).
    - `source: {kind: "model", provider: "orchestra-scheduler", model:
      "session-note"}` — заметка не результат вызова модели, но
      `assertMessageEventShape` требует `source.kind === "model"` и
      непустые `provider`/`model` для этого типа события; значения честно
      называют источник (сам оркестратор), не выдают заметку за настоящий
      ответ провайдера.

    До этой правки отсутствие `id` не мешало ЗАПИСИ (приёмный роут и
    хранилище на запись форму сообщения не проверяют вовсе) — событие
    падало ТОЛЬКО при следующей холодной загрузке той же сессии
    (`session event at seq N lacks an identified message`), делая мерж/
    приёмку/возврат в пул выглядящими успешными, пока задним числом не
    ломался прогон, резюмирующий ту же сессию (`worker.yml`).

## ADDED: Приёмный роут ingest (`dsh-edge/patches/0004-harness-ingest.patch`)

39. `normalizeHarnessIngestEvent` отказывает громко (`400`, до записи в
    сессию) на:

    - `user/message`/`assistant/message`/`tool/result` без непустого
      строкового `data.id` (`user/message`) или `data.message.id`
      (`assistant/message`/`tool/result`);
    - `assistant/message`, чьё `data.message` не несёт `role: "assistant"`
      либо `source` без `kind: "model"` и непустых `provider`/`model`.

    Честная граница: `tool/result` получает только проверку `id` — полная
    форма (`source.kind === "tool"`, `callId`, единственный `tool-result`-
    блок с совпадающим `toolCallId`) НЕ проверяется здесь: ни один писатель
    в этом репозитории не производит `tool/result` через ingest сегодня, и
    проверка без реального продюсера противоречила бы правилу «тест кормит
    прод-форму данных, а не пересказ» — оставлено явным пробелом в коде для
    следующего писателя этого типа.
