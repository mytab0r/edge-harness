# design.md: session-note-identified-message (#794)

## Развилка 1 — id один достаточен?

Проверено живым вызовом реального пинованного пакета
(`@deepseek-ai/dsh-session@0.1.2-rc.1`, `npm pack` + `adoptSessionEvent`):

```
(a) текущая форма scheduler.py (нет id):    THROWS -> session event at seq 13 lacks an identified message
(b) id добавлен, source нет:                THROWS -> session event at seq 13 message has invalid source
(c) id + role + source{kind,provider,model}: OK (принято)
```

Вывод: `assertMessageEventShape` для `assistant/message` требует ВСЮ форму
(`id`, `role === "assistant"`, `source.kind === "model"`,
`source.provider`/`source.model` — непустые строки, `hasProviderModel`), не
только `id`. Решение: писатель кладёт полную форму (c), не только `id` —
иначе фикс не закрывает падение, только переносит его на другое поле.

`provider`/`model` для системной (не model-порождённой) заметки — литералы
`"orchestra-scheduler"`/`"session-note"`: честно называют источник, не
выдают заметку за настоящий ответ провайдера (значения не обязаны совпадать
с реальным LLM-провайдером — `assertMessageEventShape` требует только
непустые строки, семантика поля не проверяется рантаймом).

## Развилка 2 — формат `message.id`

Апстрим сам решает ту же задачу для сообщений без identity, мигрированных из
легаси-формы (`dsh-session-persistence/lib/index.js::legacyMessageId`):
`` `legacy-message:${id}:${seq}` `` — составной, детерминированный, не
случайный. Тот же приём здесь: `` `harness-note:${session_id}:${run_id}:${counter}` ``.

- `session_id` — уже детерминирован (`harness-<номер задачи>`).
- Реальный `seq` события неизвестен писателю — сервер назначает его внутри
  `session.append`, ingest не видит номер по конструкции роута.
- `GITHUB_RUN_ID` — уникален МЕЖДУ запусками `scheduler.py` (эта функция
  вызывается только изнутри workflow'а `orchestra`, переменная в GitHub
  Actions задана всегда для реального прогона).
- Счётчик процесса (`itertools.count()`, модульный, не на вызов
  `append_session_notes`) — уникален В ПРЕДЕЛАХ одного запуска: `main()`
  зовёт `append_session_notes` из трёх разных мест за один пульс
  (`after_merge`/`unhealthy_pulls`/`accept_merged_tasks`), и одна и та же
  сессия может получить заметку из более чем одного места за один пульс —
  счётчик обязан быть общим на весь процесс, не локальным для функции.

`Date.now()`-подобная случайность как ЕДИНСТВЕННЫЙ источник не нужна: два
детерминированных компонента (run_id + процесс-счётчик) уже дают
уникальность без часов. `'local'` вместо `GITHUB_RUN_ID` — честная метка
«вызвано вне Actions» (локальный прогон/тест), не тайбрейкер: в этом режиме
функция и так не пишет в реальную морду (`DSH_EDGE_URL`/`DSH_EDGE_ACCESS_KEY`
не заданы за пределами CI).

## Развилка 3 — объём проверки на входе (normalizeHarnessIngestEvent)

`assertMessageEventShape` требует РАЗНУЮ форму для трёх типов
(`user/message`, `assistant/message`, `tool/result`). Решено:

- `user/message`, `assistant/message`, `tool/result` — все получают проверку
  непустого `id` (буквально то, чего не хватало, дешёво, одна строка).
- `assistant/message` дополнительно получает полную проверку (`role`,
  `source.kind === "model"`, `provider`/`model`) — это единственный тип,
  который реально пишет писатель этого репозитория (`scheduler.py`), и
  единственный, для которого есть прод-форма для теста (реальный писатель +
  `dsh-edge/ingest-integration/check.mjs`).
- `tool/result` НЕ получает полную проверку (`source.kind === "tool"`,
  `callId`, форма единственного `tool-result`-блока и совпадение
  `toolCallId`) — ни один писатель этого репозитория не производит
  `tool/result` через ingest сегодня; проверка без реального продюсера —
  «тест кормит прод-форму данных, а не пересказ» наоборот: пришлось бы
  придумывать форму, а не снимать её с реального вызова. Оставлено
  явным комментарием в коде — известный пробел для следующего писателя.

## Развилка 4 — порядок деплоя, риск разрыва

`scheduler.py` — обычный скрипт в дереве репозитория, действует на
СЛЕДУЮЩЕМ тике `orchestra.yml` после мержа (cron */15 мин, по факту
интервалы от 0 до нескольких часов, #269). `dsh-edge/patches/**` триггерит
`deploy-dsh-edge.yml` НЕМЕДЛЕННО на push в main (`paths: dsh-edge/**`) —
клон апстрима, патч-серия, сборка, интеграционные проверки, деплой; по
устройству остальных шагов того же workflow (`pnpm install`, кодогенерация,
сборка, `verify`) это несколько минут, не секунды.

Оба изменения landят в ОДНОМ коммите (этот PR) — разнести их по времени
специально нельзя и не нужно. Возможные направления гонки:

- **Морда обновилась ПЕРВОЙ, писатель ещё старый** (окно между мержем и
  следующим тиком `orchestra.yml`, если деплой морды успел раньше): новый
  строгий `normalizeHarnessIngestEvent` отклонит старую форму заметки 400-й.
  `append_session_notes` уже перехватывает `RuntimeError` от `_morde_ingest`
  и красит `hard_failure` — прогон получает громкий, но НЕ фатальный сигнал
  (мерж/приёмка/возврат в пул уже состоялись и не откатываются, тот же
  контракт, что и у недоступности морды). Это переходное, самоограниченное
  состояние: окно закрывается на первом же следующем тике `orchestra.yml`
  (минуты — десятки минут), после чего писатель уже новый.
- **Писатель обновился первым, морда ещё старая**: старый
  (нестрогий) валидатор ничего не проверяет сверх `message`+`content` —
  новые поля (`id`/`source`) лишние, но не запрещённые, событие проходит
  как раньше. Направление безопасно.

Полностью бесшовного порядка при двух независимых механизмах деплоя
(hot-reload скрипта на каждом тике vs CI-сборка) не существует — единственная
опасная сторона гонки (новая морда + старый писатель) уже ограничена
best-effort обработкой ошибки (не валит мерж, красит прогон, самоограничена
временем до следующего тика) — тот же класс, что и предохранитель #572,
не новая дыра.

## Восстановление испорченных сессий (harness-257/215/710)

`dsh-session-persistence::migrateLegacyMessageEvent` — единственный
встроенный путь апгрейда старых сообщений — ЯВНО отказывается трогать
события, УЖЕ несущие ключ `message` (наш случай: `data.message` уже есть,
просто без `id`):

```js
case "assistant/message": {
  if (Object.hasOwn(data, "message") || !Object.hasOwn(data, "content") || !Object.hasOwn(data, "provenance")) return event
  ...
}
```

Комментарий апстрима прямым текстом: «Current-looking malformed events
remain untouched so validation rejects them instead of disguising
corruption as legacy data» — то есть отсутствие пути ремонта для этого
конкретного случая порчи СОЗНАТЕЛЬНОЕ решение апстрима, не пробел
реализации. Единственный оставшийся путь — прямая правка сохранённого
JSONL (`session.jsonl.zstd`) в обход валидации пакета: вставить `id` (и
`source` для assistant/message) в конкретную строку конкретного `seq`
руками/скриптом. Это доступ на уровне хранения Durable Object (не через
штатный API морды) и живой мутирующий вызов на проде — вне рамок этого PR
(нет доступа, задача явно это исключает). Решение — заводить ли отдельную
задачу на восстановление — за владельцем.
