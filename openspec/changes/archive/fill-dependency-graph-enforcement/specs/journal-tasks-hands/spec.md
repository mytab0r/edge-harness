# Дельта-спека: journal-tasks-hands — наполнение и обязательность графа зависимостей

Продолжает `openspec/changes/task-priority-blocking-graph/specs/
journal-tasks-hands/spec.md` (расширяет `openspec/specs/journal-tasks-hands.md`,
раздел «Автономный воркер (конвейер пула)»). Носитель графа (`blockedBy`/
`blocking`, `scripts/lib/task_deps.py`) не меняется — эта дельта про то, ЧТО
его наполняет и ЧТО делает пропуск заполнения видимым.

## ADDED: Заведение задачи требует явного ответа о зависимостях

Оба поставщика открытого пула не принимают заведение задачи без явного
ответа «чем блокируется» (номера issue или «ничем» — оба варианта
допустимы, пропуск поля недопустим):

- Шаблоны `.github/ISSUE_TEMPLATE/task.yml`/`white-spot.yml` — обязательное
  текстовое поле формы. Значение остаётся человекочитаемым следом в теле
  созданной issue; веб-форма НЕ переносит его в нативный `blockedBy`
  автоматически (GitHub не валидирует содержимое поля на сервере для
  программных создателей issue — см. design.md `task-priority-blocking-graph`,
  развилка б) — перенос остаётся ручным шагом `task_deps.py block`.
- `scripts/review/file_tasks.py` (автозаведение из находок AI-ревью) —
  контракт `ai_prompt.md`/`ai_review.py::parse_tasks` требует строку
  `БЛОКИРУЕТСЯ: #N … | ничем` последней перед `КОНЕЦ ЗАДАЧИ`; блок без
  неё отбрасывается целиком (полутзадача хуже отсутствия), громкое
  предупреждение в лог ревью. Значение переносится в нативный `blockedBy`
  АВТОМАТИЧЕСКИ, в момент создания issue (`wire_declared_dependency`) —
  но только на номера, входящие в ТЕКУЩИЙ открытый пул с меткой `task`;
  номер вне пула (закрыт/не существует/не задача) не линкуется, печатается
  предупреждение — ложная связь опаснее отсутствующей.

Сценарий: AI-ревью предлагает задачу с `БЛОКИРУЕТСЯ: #55`, #55 — открытая
задача пула → `file_tasks.py` создаёт issue И ставит `blockedBy` одной
командой, приоритет блокирующей (#55) увеличивается на следующем запросе
пула без ручного действия.

Сценарий: AI-ревью предлагает задачу с `БЛОКИРУЕТСЯ: #999`, #999 не входит
в открытый пул с меткой `task` → issue создаётся, связь НЕ ставится, в лог
идёт предупреждение — задача заведена, граф не тронут ложной связью.

Сценарий: блок ответа модели не содержит строку `БЛОКИРУЕТСЯ:` вовсе (старый
формат промпта или отклонение модели от контракта) → блок отбрасывается
целиком на этапе `parse_tasks`, задача НЕ попадает в комментарий-предложение
и не заводится — не полузадача.

## ADDED: Рассинхрон текста и графа — видимый сигнал, не молчаливое состояние

`scripts/lib/declared_deps.py::find_desync` сравнивает формулировки
зависимости в теле открытой задачи («после #N», «зависит от #N»,
«блокируется #N», «заблокирован(а) #N», «блокер — #N», «до закрытия #N»)
с нативным `blocked_by_open`: названная, всё ещё ОТКРЫТАЯ задача пула без
соответствующего `blockedBy` — находка. Ссылка на уже закрытую/несуществующую/
не-task issue находкой не считается — приоритет и так фильтрует такие по
состоянию, регистрация не изменила бы ничего.

`.github/workflows/repo-ci.yml` гоняет проверку на каждый push/PR,
печатает `::warning::` на каждую находку — НЕ проваливает обязательный
гейт `test` (детектор эвристический, ложные срабатывания на формулировках
прозы вне контекста зависимости ожидаемы и не должны блокировать
несвязанные PR).

Сценарий: тело открытой задачи A содержит «блокер — #B» (структурная
формулировка), у A нет нативного `blockedBy` на B, B открыт и в пуле →
`declared_deps.py check` печатает предупреждение с готовой командой
`task_deps.py block <repo> A B`.

Сценарий: тело задачи A содержит «после слияния» (внутри скобки) и,
через закрывающую скобку, дальше упоминает #B в другом, несвязанном
предложении → НЕ находка (граница скобки/предложения не пересекается
окном поиска — живой замер на этом репозитории поймал и исправил именно
этот класс ложного срабатывания при разработке).
