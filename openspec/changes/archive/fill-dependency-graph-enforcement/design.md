# Design: fill-dependency-graph-enforcement

Контекст и правило — `proposal.md`. Здесь — развилки и почему выбрана
конкретная.

## Развилка (а): миграция существующих зависимостей — пакетно или по одной

Кандидатов, найденных сканированием тел+комментариев 113 открытых задач
формулировками «после #N», «зависит от #N», «блокируется #N», «блокирует
#N», «заблокирован #N», «до закрытия/слияния/мержа #N» (плюс отдельный
полнотекстовый поиск GitHub по тем же формулировкам, включая комментарии) —
около 40 упоминаний прочитано целиком. Из них подтверждены и проставлены
РОВНО ДВА:

- `#254 ← #170` («Также зависит от #170» — оба открыты).
- `#258 ← #133` («Единственный настоящий блокер — #133» — оба открыты).

Остальные ~38 отвергнуты при чтении по одной из трёх причин:

1. **Формулировка не о межзадачной зависимости.** Пример: #224 «после
   #182» — про то, когда была обновлена документация, не про порядок
   выполнения; #243 «Поглощает часть #227 (закрытие задач после
   слияния) и часть #201» — «после» относится к слиянию ВНУТРИ скобки,
   #201 — следующий пункт перечисления «поглощает часть X и часть Y».
2. **Названный блокер уже закрыт** (#268←#265, #115→#105, #111→#105,
   #86←#80) — связь ничего не меняет: приоритет и детектор рассинхрона
   читают только `blocked_by_open`/`blocked_by` среди ОТКРЫТЫХ, закрытый
   блокер уже отфильтрован по состоянию. Регистрация ради регистрации —
   не выгода, только шум в графе.
3. **Слово общего языка, не термин зависимости** («блокирует» про
   гейт/лейбл CI, не про issue; «не блокирует мерж» — явное ОТРИЦАНИЕ
   зависимости).

**Решение: только чтением, по одной, никогда пакетно по регэкспу.**
Регэксп — инструмент ПОИСКА кандидата, не источник истины: ложная связь
поднимает в приоритете не ту задачу (прямое требование владельца), и
дешевле не найти реальную связь, чем записать выдуманную.

## Развилка (б): где стоит перенос «заявлено в теле» → нативный `blockedBy`

Тот же вопрос, что уже решён в design.md #361 для ОБЩЕГО случая
(«воркфлоу, конвертирующий текст issue» — отклонён, потому что GitHub не
валидирует форму для программных создателей). Здесь — частный случай:
`file_tasks.py` уже ЗНАЕТ структурный, обязательный, только что
провалидированный (`ai_review.parse_tasks`) ответ модели — это НЕ
свободная проза, а поле с фиксированным форматом (`БЛОКИРУЕТСЯ: #N … |
ничем`), тот же класс, что `task_ref.declared_tasks` (структурная позиция
— последняя строка блока, — не любое упоминание). Разница с #361
достаточна, чтобы автоматизировать именно этот путь.

Два варианта переноса: (1) прямо в `file_tasks.py::file_task`, в момент
создания issue — номер новой задачи уже известен; (2) отдельным
периодическим обходом пула (сканировать все task-issues, искать
`БЛОКИРУЕТСЯ:` в теле, сверять с графом).

**Выбор (1).** Дешевле — не нужен второй проход пула по расписанию,
нет окна устаревания (обход раз в N минут узнал бы о новой задаче не
сразу), и код уже там, где есть и текст, и только что созданный номер.
(2) как отдельный периодический сканер был бы дублированием (2) с
`declared_deps.py` (см. развилку в), разница только в том, кто ПИШЕТ, а
не только предупреждает — не заводить два похожих обходчика.

Для ЧЕЛОВЕЧЕСКОГО пути (шаблон issue) перенос остаётся РУЧНЫМ
(`task_deps.py block`) — форма не структурная (свободный текстовый ввод,
формат не валидируется GitHub на сервере), тот же аргумент, что и в
design.md #361 против автоматической конвертации прозы.

## Развилка (в): рассинхрон-детектор — писать связь или только предупреждать

`declared_deps.py::find_desync` находит кандидатов ТЕМ ЖЕ классом эвристики,
что и разовая миграция (развилка а) — а миграция показала: подтверждается
чтением только ~1 из 20 кандидатов. Автоматически ПИСАТЬ найденное в граф
означало бы конвейер, производящий ложные связи пакетно — именно то, что
запрещено правилом этого change и прямым требованием владельца.

**Выбор: только предупреждение (`::warning::` в CI), никогда не пишет.**
Находка — подсказка человеку/агенту («проверь и, если реально, поставь
`task_deps.py block`»), не факт. Это же решает вопрос блокировки
обязательного гейта: жёсткий отказ (`exit 1`) на эвристике с доказанной
частотой ложных срабатываний ~19 из 20 — тормоз, у которого нет
предсказуемого газа для автора корректного текста, не попавшего ни в одну
из шести распознаваемых формулировок (см. proposal.md, Out).

## Развилка (г): где живёт детектор — `repo-ci.yml` (per-push) или пульс orchestra

Кандидата два: обязательный гейт `repo-ci.yml` (уже проверяет другие
репозиторные инварианты той же природы — класс #179 «white-spot без
task») и периодический пульс `orchestra.yml`/`pulse_guard.py`.

**Выбор: `repo-ci.yml`.** Причина — цена: `pulse_guard`/DO SQLite квота
`rows_read` (5 млн строк/сутки) уже была ИСЧЕРПАНА 2026-09-03 (#320,
"full-scan tasks на каждый heartbeat") — периодический тик, добавляющий
ещё один проход по пулу на КАЖДЫЙ heartbeat, увеличивает то же узкое
место. `repo-ci.yml`, напротив: один проход на push/PR (не по
расписанию), только GitHub GraphQL — ни одного обращения к DO/CF SQLite.
Дешевле по факту, не только по интуиции.

## Что делает выбор неверным (пересмотреть при новом факте)

- Если частота ложных срабатываний детектора рассинхрона упадёт
  (например, регистр формулировок станет уже настолько стандартным, что
  ложных находок не будет несколько месяцев подряд) — можно пересмотреть
  строгость (warning → error), но не раньше отдельного измерения.
- Если GitHub API начнёт разрешать конфигурировать граф `blockedBy` прямо
  через issue forms (сегодня недоступно — только `addBlockedBy`/
  `removeBlockedBy` мутации, не форма) — развилка (б) для человеческого
  пути пересматривается.

## Газ (проверка по факту, не предположению)

Задание прямо просило проверить: «связь `blockedBy` — тормоз, задача не
может быть взята». Чтение `scripts/lib/free_task.py` (текущее состояние,
включая #361) показывает: `blocked_by_open` ВОЗВРАЩАЕТСЯ
`task_deps.fetch_pool`, но НЕ используется НИГДЕ в `free_candidates`
(фильтр свободы) и НЕ используется в `issue_priority_key` (приоритет
читает только `blocking_open` — сколько эта задача блокирует, не чем она
сама блокирована). Значит сегодня `blockedBy` — НЕ тормоз для выбора
задачи вообще: заблокированную задачу воркер по-прежнему может взять,
изменяется только приоритет ЕЁ БЛОКИРУЮЩЕЙ (ту, что чаще выбирается
раньше). Это соответствует явному решению #361 (proposal.md, Out:
«Исключение заблокированных задач из пула — ORDERING-фича, не
EXCLUSION-фича... не трогается»).

Газ поэтому нужен только для того единственного механизма, который
РЕАЛЬНО читается — `blocking_open` (сколько ОТКРЫТЫХ задач блокирует
issue): он пересчитывается ЖИВЬЁМ на каждом запросе `fetch_pool`
(`_is_open` фильтрует состояние узла на лету, не кэш) — закрытие
блокируемой задачи автоматически уменьшает счётчик у блокирующей на
следующем запросе, без ручного действия. Уже доказано мутацией в
`test_task_deps.py`/`test_free_task.py` (#361). Физическое удаление
самого ребра `blockedBy` при закрытии блокирующей стороны НЕ требуется:
открытое/закрытое состояние issue уже единственный источник правды «снят
ли тормоз» — второй флаг для того же факта было бы вторым местом правды
(запрещено `AGENTS.md`).

Если владелец захочет превратить `blockedBy` в реальный EXCLUSION-тормоз
(воркер не берёт заблокированную задачу) — это отдельное, явное решение
вне объёма этой задачи (#361 сознательно оставил его нерешённым), и его
газ придётся проектировать заново: `free_candidates` должен будет читать
`blocked_by_open` и наверняка эскалировать владельцу случай «все
свободные задачи заблокированы» (тот же класс, что уже решён для очереди
предохранителя #120).
