# Design: приоритет пула — развилки и почему выбран текущий вариант

Задача #224. Решения ниже сделаны самостоятельно исполнителем по улике на
живом пуле (по прямому поручению — «реши сам, обоснуй числами») и не
требуют решения владельца: везде есть измеримая улика на этом же
репозитории, различающая варианты.

## Развилка 1: «сейчас красный» выше `area:process` или наоборот?

**Варианты:**
- (а) `area:process` остаётся уровнем 0 (как в #361), «сейчас красный»
  встраивается ВНУТРИ него как под-уровень.
- (б) «Сейчас красный» становится уровнем 0, `area:process` — уровнем 1
  (выбрано).

**Довод за (б):** `ci-failure`/`self-audit` — измеримый, накапливающийся
факт (конвейер стоит с КАЖДЫМ новым прогоном, пока это открыто); `area:process`
— классификация природы задачи (протокол/гвардии/приоритет), важная, но не
обязательно означающая, что что-то СЕЙЧАС ломается. Живой пример: #629
(«CI: orchestra.yml падает») не блокирует ни одной другой задачи в графе и
не несёт `area:process` — вариант (а) держал бы её на позиции #219 из 303;
вариант (б) поднимает на #4 (после трёх задач, которые её транзитивно
приближают). Оркестратор — механизм слияния ВСЕЙ остальной работы; пока он
красный, простаивает не одна ветка, а вся очередь мержей — то самое
измерение «стоимость простоя», которое #224 просит учитывать явно.

**Проверено, не осталось непроверенным:** ни одна из 6 `ci-failure`-задач
на момент замера не несла `area:process` одновременно — конфликта
приоритетов (какой уровень главнее у одной и той же задачи) в данных нет,
решать оба варианта на пересечении не пришлось.

## Развилка 2: прямой счётчик `blocking_open` или транзитивный вес?

**Выбрано:** транзитивный (`task_deps.transitive_blocking_counts`),
обобщение прямого. **Довод:** живой пример #716→#736→#735 и #770→#741→#782
(замер 2026-09-12) — прямой счётчик даёт обоим вес 1, транзитивный — 2,
и это меняет порядок внутри уровня `area:process` (114 задач, из которых
различить прямым счётчиком можно было только 7). Чем глубже граф будет
заполняться (#720 в перспективе), тем важнее не терять цепочки длиной
больше 1.

**Граница:** `transitive_blocking_counts` — это `max(вес по рёбрам,
blocking_open)`, не чистый вес по рёбрам. Причина: рёбра строятся из
`blocked_by_open` УЖЕ ПРИСУТСТВУЮЩИХ в выборке issue (`fetch_pool`
фильтрует по одной метке за раз) — если блокируемая цель сама не входит в
эту выборку (другая метка, или её вообще не тянули), ребро до неё не
видно, а прямое поле `blocking_open` (отдаёт сам GraphQL, независимо от
присутствия цели в выборке) о ней знает. Без `max` транзитивный вес мог бы
оказаться МЕНЬШЕ прямого счётчика — тихий регресс относительно #361, а не
обобщение поверх него. Обнаружено регрессией существующих тестов #361 при
первой реализации (см. tasks.md) — не домыслено заранее, а поймано
прогоном.

## Развилка 3: граф разрежен (#720) — приоритет ждёт заполнения или работает уже сейчас?

**Варианты:**
- (а) Приоритет остаётся вырожденным, пока #720 не решит проблему
  заведения связей на входе.
- (б) Приоритет спроектирован так, что работает и на разреженном графе, не
  дожидаясь #720 (выбрано).
- (в) В этом же PR — обратное заполнение графа регэкспом по прозе тел уже
  открытых 199 задач («Связано: #N», «блокирует #N» и т.п.).

**Довод за (б), против (в):** `docs/agents/PROTOCOL.md` и
`scripts/lib/declared_deps.py` уже называют принцип для этого класса
задач — «ложная связь опаснее отсутствующей» — применительно к структурному
полю формы; для вольной прозы 177 старых issue уверенность в номере ещё
ниже (нет структурного якоря вида `### Чем блокируется`). Массовая мутация
графа (потенциально сотни `addBlockedBy`) по эвристике на живых issues
необратима дешевле, чем отказ от неё: ошибочная связь обнаруживается
только повторным ручным разбором, а её эффект (искажённый приоритет)
реален для всех последующих запусков воркера. Вместо (в) — уровень 1
(«сейчас красный») вообще не зависит от графа, а уровень 3 (транзитивный
вес) деградирует к 0 для задач без связей, не искажая уровни 1/2 и не
блокируя выбор (см. `graph_is_empty` — предупреждение, не отказ).
Экономика (б) дешевле и без риска (в): ничего не пишется в GitHub, только
чтение уже существующего графа.

**Не решено этим change (честно, не «выдумано отсутствие проблемы»):**
#720 сам по себе (заведение связей НА ВХОДЕ, для новых issue) — отдельная
задача, не в объёме этого change; здесь только доказано, что приоритет не
обязан ждать её решения, чтобы быть полезным уже сейчас.

## Развилка 4: разбивать `area:process` на суб-уровни?

**Рассмотрено и отклонено.** Единственный кандидат-признак различения
внутри `area:process` — транзитивный вес (уже используется, уровень 3).
Любое дальнейшее деление потребовало бы новой метки/суждения («эта
процессная задача важнее той») — то есть данных, которых сегодня нет, и
которые нельзя вывести из существующих фактов без домысливания. Решение:
не заводить новую метку без данных, стоящих за ней (тот же принцип, что
`AGENTS.md`: «не знаешь — пиши "не подтверждено"», не выдумывай).
