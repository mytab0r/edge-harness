# Propose: приоритет пула — «механизм сейчас красный» и транзитивный вес графа, не два вырожденных уровня

## Summary

Задача #224. Продолжает #361 (архивирован как `task-priority-blocking-graph`):
тот change ввёл граф блокировок и метку `area:process` как два уровня
приоритета. #224 требует, чтобы порядок работ был ОБЪЯСНИМ — «для любой
открытой задачи можно получить ответ, почему она на этом месте, фактом» —
и чтобы вырожденные уровни (метка на большой доле пула, почти пустой граф)
перестали быть уровнями. Замер на живом пуле 2026-09-12 (303–304 открытых
задачи с меткой `task`) показал оба дефекта:

- Уровень 1 (`area:process`) стоит на 114 задачах (38%) — не различает
  внутри себя почти никого (только 7 из 114 имели ненулевой прямой
  `blocking_open`).
- Уровень 2 (граф) почти пуст: из 303 только 20 несли открытые блокирующие,
  18 блокировали хоть одну открытую напрямую.
- Следствие: реальный порядок работ = номер issue = дата заведения — ровно
  то, против чего заведена #224.

## Problem / motivation

### Замер (сделан этим change)

Живой пул 303 открытых задач (`task_deps.fetch_pool(repo, 'task')`, один
пагинированный GraphQL-проход):

- 6 задач несут метку `ci-failure` (провал `worker.yml`/`orchestra.yml`/
  `deploy-*.yml`, классифицированный как наш дефект). НИ ОДНА не помечена
  `area:process` и ни одна не имела прямых блокируемых (`blocking_open=0`) —
  старой схемой (#361) они конкурировали по номеру среди ~190 обычных
  задач, несмотря на то, что представляют измеримый, ПРОДОЛЖАЮЩИЙСЯ простой
  конвейера.
- Issue #665 («починить 500 на ingest-эндпоинте морды») не несёт ни
  `ci-failure`, ни `area:process`, но НАПРЯМУЮ блокирует три открытые
  `ci-failure`-задачи (#577, #675, #981). Старой схемой она стояла на
  позиции #116 из 303 (ниже всех 114 `area:process`-задач, включая те, что
  не блокируют ничего). Аналогично #610 блокирует #629 (`ci-failure`),
  стояла на позиции #124.
- Транзитивность: #716 и #770 (оба `area:process`) блокируют напрямую по
  одной задаче, каждая из которых сама блокирует ещё одну — прямой счётчик
  `blocking_open` даёт им вес 1, хотя закрытие любого из них в конечном
  счёте приближает закрытие ДВУХ задач, не одной.

### Почему это не расширяет out-of-scope #361

#361 сознательно ограничился прямым счётчиком блокировок и единственной
метой-меткой как первым уровнем — это задокументированное решение, не
дефект. #224 — отдельная задача пула с собственным критерием приёмки
(«объяснимость», «вырожденные уровни перестают быть уровнями»), которая
явно ссылается на #361 как на опору, а не переоткрывает её.

## Правило

Приоритет свободной задачи — четыре уровня, в этом порядке:

1. Задача сама несёт метку «механизм конвейера сейчас красный»
   (`ci-failure`/`self-audit`, `scripts/lib/free_task.py::BROKEN_LABELS`)
   ИЛИ транзитивно блокирует такую (`task_deps.blockers_of`, обратный BFS
   по нативному графу `blockedBy`). Факт, не самооценка: конвейер измеримо
   стоит, пока это открыто.
2. Метка `area:process` (задача про сам процесс работы), если задача не
   попала в уровень 1.
3. Транзитивный вес графа блокировок (`task_deps.transitive_blocking_counts`
   — обобщение прямого `blocking_open` #361 на всю цепочку, не только
   прямых соседей).
4. Номер issue как тайбрейк (proxy даты создания, без изменений с #361).

Для любой задачи `scripts/lib/free_task.py::priority_reason` отвечает
фактом: тир, какая метка/цепочка его дала, транзитивный вес и конкретные
номера, чем сама задача заблокирована. Не гадание («либо A, либо B») —
конкретные номера или явное «неизвестно» там, где сигнала физически нет.

## Scope

### In

- `scripts/lib/task_deps.py` — `transitive_blocked`/`transitive_blocking_counts`/
  `blockers_of`: чистые функции над уже прочитанным пулом (`blocked_by_open`
  каждой issue), без второго сетевого обхода. `transitive_blocking_counts`
  не может быть МЕНЬШЕ прямого `blocking_open` (граница: блокируемая цель
  может не входить в тот же выбранный по метке список issue — тогда ребро
  до неё не строится, а прямое поле GraphQL всё равно о ней знает).
- `scripts/lib/free_task.py` — `BROKEN_LABELS`, `_urgent_numbers`,
  `issue_priority_key` (четыре уровня вместо трёх), `priority_reason` (новая
  функция объяснимости), CLI-режим `why <N> <issues.json>`. Имена
  `oldest_free`/`prioritized_free`/`priority_top`/CLI-глагол `oldest-free`
  сохранены — старое поведение (#361) остаётся частным случаем нового ключа
  при пустом графе/без меты/без поломки, доказано существующими тестами без
  изменений.
- `docs/agents/LABELS.md`, `docs/agents/PROTOCOL.md`,
  `openspec/specs/journal-tasks-hands.md` (п.26) — обновлены под новую схему.

### Out

- Связка с #720 (объявление связи не спрашивают при заведении — 177 из 199
  тел без машиночитаемой связи): приоритет здесь СОЗНАТЕЛЬНО спроектирован
  работающим и на разреженном графе (уровень 1 не зависит от графа вовсе,
  уровень 3 деградирует к 0, но не ломает уровни 1/2). Массовое обратное
  заполнение графа регэкспом по прозе старых issue («Связано: #N» и т.п.) НЕ
  делается этим change — риск ложной связи (`docs/agents/PROTOCOL.md`:
  «ложная связь опаснее отсутствующей») на ~300 живых issues необратим
  дешевле, чем сам приоритет, устойчивый к разрежённому графу. #720 остаётся
  отдельной задачей о заведении новых связей на входе, не о ретроактивном
  заполнении регэкспом.
- Диаграмма Ганта, оценка длительности задач, замер времени цикла (часть
  первоначального текста #224) — отдельный объём, не затронут этим change;
  критерий приёмки этого change — объяснимость и невырожденность уровней,
  не Гант.
- Разделение `area:process` на суб-уровни (например «критично для
  приоритета» vs «протокольная мелочь») — рассмотрено и отклонено: нет
  дополнительной метки/данных, различающих задачи ВНУТРИ `area:process`
  без домысливания; вместо неё используется уже объективный сигнал
  (транзитивный вес), который убирает часть вырожденности честно, оставляя
  тай-брейк по номеру там, где сигнала физически нет (не выдуманная дата —
  явно объявленное «неизвестно», см. `priority_reason`).

## Impacted domains

- `scripts/lib/free_task.py`, `scripts/lib/task_deps.py`.
- `docs/agents/LABELS.md`, `docs/agents/PROTOCOL.md`,
  `openspec/specs/journal-tasks-hands.md` (п.26).
- Потребители БЕЗ изменений (проверено тестами): `scripts/worker/task.sh`
  (контракт CLI `oldest-free`/`conflict-tasks` не менялся), `scripts/gh/

  `scripts/orchestra/scheduler.py::merge_queue`/`dispatch_worker`
  (`free_task.prioritized_free(named_pool)` — та же сигнатура).

## Acceptance criteria

1. Для любой открытой задачи `free_task.py::priority_reason`/CLI `why`
   отвечает фактом (тир, конкретные номера, транзитивный вес), не гаданием.
2. Порядок воспроизводим: два прогона на неизменных данных дают одинаковый
   результат (чистые функции, без побочных эффектов).
3. Замер на живом пуле (303–304 задачи) до/после приложен числом и
   объясняет минимум 5 задач конкретно (см. design.md).
4. Мутация: снятие проброса `_urgent_numbers` через `task_deps.blockers_of`
   красит минимум 3 теста (`test_tier0_propagates_*`,
   `test_priority_reason_names_transitively_blocked_broken_task`);
   восстановление фикса возвращает их в зелёное.
5. Обратная совместимость: все 41 существующий тест `test_free_task.py`
   (до этого change) и потребители (`task.sh`, `issue-create`) остаются
   зелёными без изменений в их коде.
