# worker-two-slots: до двух параллельных прогонов worker.yml вместо одного (#827)

Задача: #827. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Узкое место, измеренное на живом репозитории: `.github/workflows/worker.yml`
(до этой правки) держал `concurrency: {group: worker, cancel-in-progress:
false}` — ровно один воркер на весь репозиторий. Оркестратор откладывает
расшивку конфликтных PR и новые задачи по одной, пока единственный воркер
занят («⏸️ PR #N в конфликте, но воркер занят — расшивка отложена» на
несколько PR за проход). Дренаж бэклога (18 сброшенных конфликтных PR + новые
задачи) серийный и медленный.

## Замер цены перед решением

- **GitHub Actions**: публичный репозиторий — минуты бесплатны/безлимитны
  (docs/research/21-github-actions.md). Concurrent job limit — 20 на Free-план
  (аккаунт, не репозиторий); `GITHUB_TOKEN` живьём отдаёт 5000 запросов/час на
  этот репозиторий (тот же research, замер 2026-09-09). N=2 не приближается ни
  к одному из этих потолков.
- **Провайдер-квота (главный риск)**: цепочка `DSH_PROVIDER_CHAIN`
  (NVIDIA→GLM, `docs/runbooks/switch-llm-provider.md`) — NVIDIA-квота уже была
  узким местом (руннеры падали на исчерпании квоты, цепочка чинилась в тот же
  день, что и этот change). Точных данных о лимите запросов в минуту (RPM)
  NVIDIA/GLM в репозитории НЕТ ни в одном research-документе — зафиксирован
  только вид отказа (`RATE_LIMIT: Weekly/Monthly Limit Exhausted`), не порог.
  В отсутствие этого числа решение принято консервативно: **N=2, не 3+**, с
  готовностью откатить назад (снизить `WORKER_MAX_CONCURRENCY`), если
  исчерпание квоты начнёт коррелировать с параллельными прогонами —
  `dsh_run_with_provider_chain` уже переключает провайдера при
  `quota_exhausted` внутри одного прогона, откат не требует нового кода.
- **Лиза задачи (#121, `claim_task.py`)**: атомарность обеспечена
  git-ref-локом на СЕРВЕРЕ GitHub (создание `refs/locks/task-N` атомарно
  независимо от числа одновременных вызывающих) — механизм не завязан на
  «один воркер», уже проверен конкурентным тестом
  `scripts/lib/test_claim_task.py::test_race_two_claims_one_wins_other_refused`
  (два параллельных `claim()` на один номер — ровно один побеждает). Новый
  тест не требуется, только явная проверка при этом change, что вывод
  остаётся верным.

## Что делается

- `.github/workflows/worker.yml`: новый вход `slot` (`1` или `2`, по
  умолчанию `1` — тот же слот, что раньше был единственным при ручном
  запуске). `run-name` несёт номер слота открытым текстом (REST не отдаёт
  workflow_dispatch inputs ни в одном поле готового прогона, только
  `display_title`, вычисленный из `run-name`). `concurrency.group` зависит от
  входа (`worker-${{ inputs.slot }}`) — до двух независимых
  concurrency-групп, каждая по-прежнему сериализует прогоны ВНУТРИ своего
  слота (тот же мьютекс, что раньше был один на репозиторий).
- `scheduler.py`: `WORKER_MAX_CONCURRENCY = 2`. Новые функции:
  `active_worker_runs` (единый источник занятости — in_progress без зависших
  + queued), `free_worker_slot` (номер свободного слота 1..N или `None`).
  `worker_runs_active` — семантика НЕ изменилась («хотя бы один активен»,
  используется `mechanical_rebase.py` и эскалацией `dispatch_conflict_rework`
  как консервативный признак «воркер может пушить в любую ветку прямо
  сейчас», это репо-wide факт, не про конкретный слот). Четыре диспетчера,
  реально отправляющие `workflow_dispatch` (`dispatch_worker` — 2 точки,
  `dispatch_conflict_rework` — 1 точка, `dispatch_ai_review_rework` —
  1 точка), переведены на `free_worker_slot`:
  свободен хотя бы один слот — dispatch уходит туда (`-f inputs[slot]=N`);
  оба заняты — прежнее поведение (наблюдение, без действия).
  `stalled_worker_runs` (было `stalled_worker_run`, единственное число) и
  `reap_stalled_worker_run` (#815) обобщены на ДО `WORKER_MAX_CONCURRENCY`
  одновременно зависших прогонов — раньше проверялся только первый в списке
  (`per_page=1`), с двумя слотами зависание в одном не должно маскироваться
  живым прогоном в другом.

## Проверено

- `python -m pytest scripts/orchestra/test_scheduler.py -q` — 314 тестов,
  зелёные (11 адаптированы под новую семантику «слот, не бинарный
  занят/свободен», 12 новых тестов на `free_worker_slot`/оба слота
  busy/свободный слот/два зависших прогона одновременно).
- `python -m pytest scripts/orchestra/test_mechanical_rebase.py -q` —
  зелёные (читает `worker_runs_active` неизменной семантики).
- `python -m pytest scripts/lib -q` — зелёные (гвардия пагинации,
  `test_pagination_guard.py`, обновлена под переименованные функции).
- Мутация 1: `WORKER_MAX_CONCURRENCY = 1` — 6 тестов на свободный
  слот/dispatch во второй слот краснеют.
- Мутация 2: `stalled_worker_runs` обрезан до первого найденного (`[:1]`) —
  `test_reap_stalled_worker_run_handles_both_slots_independently` краснеет
  (второй зависший прогон в другом слоте не обрабатывается).

## Что вне рамок

- Поднятие выше N=2 — требует измеренного числа RPM/квоты NVIDIA, которого
  сегодня нет; поднимать вслепую владелец прямо запретил.
- `task.sh`/`claim_task.py` не менялись: атомарность лизы уже не зависела от
  числа воркеров (git-ref-лок на сервере), отдельного изменения не требуется.
