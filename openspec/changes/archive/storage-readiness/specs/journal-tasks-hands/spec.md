# Дельта-спека: готовность хранилища (#575, PR #587)

Расширяет `openspec/specs/journal-tasks-hands.md`: новый подраздел «Готовность
хранилища» сразу после «Самообновления морды» (до «Автономного воркера»).
Нумерация продолжает ряд 23.x «Самообновления морды» (заняты 23.1–23.4
сигналом дрейфа пина #134) — тот же приём, что у «Watchdog зависших задач»
(14.1–14.3) и ретеншена `do-sqlite-retention` (14.4–14.11): подраздел живёт на
номере якорного пункта раздела. Соседняя дельта #586 (`do-sqlite-retention`)
номера 23.x не трогает — коллизии при архивации обеих дельт в базовую спеку
нет.

## ADDED: живой зонд готовности хранилища

23.5. Маршрут `GET /api/ready`: РОВНО ОДИН живой SQL-раундтрип
    (`SELECT 1 FROM heartbeat LIMIT 1` — всегда существующая таблица SCHEMA,
    `LIMIT 1`, не скан) со стабильным контрактом `{ok:true}`. Авторизация как
    у всех `/api/*` (пп. 20–22). Отказ хранилища (включая исчерпание суточной
    квоты `rows_read`/`rows_written`, #320) — тот же ответ
    `storageErrorResponse`, что и на любом другом маршруте: одно место правды
    классификации, не вторая копия. Это зонд, а не `/api/status`: статус тоже
    выполняет живые SQL и тоже краснеет при отказе хранилища, но гоняет пачку
    запросов на каждый вызов (включая `MAX(id)` по `events`, растущему с
    историей) и отдаёт тяжёлый ответ состояния. Версионный `/api/health`
    морды dsh-edge (п.23, сравнение версий) зондом не является и не меняется.

Сценарий: Дано — хранилище принимает операции. Когда — `GET /api/ready` с
валидной авторизацией. Тогда — 200 и тело `{ok:true}`.

Сценарий: Дано — таблица `heartbeat` снесена (аналог отказа любого SQL на
исчерпании квоты). Когда — `GET /api/ready`. Тогда — ответ 5xx с телом
`{"error":{"code","message"}}` в той же форме, что у остальных маршрутов.

## ADDED: пульс непрерывно зондирует хранилище и алертит переход один раз

23.6. DO-пульс на каждом тике `alarm()` выполняет зонд 23.5 (без HTTP-обёртки,
    прямо тем же живым раундтрипом) — единственный непрерывный 24/7 монитор
    хранилища: деплойная канарейка (`deploy-dsh-edge.yml`) видит живость
    только в момент деплоя, failure-watch (`pulse_guard.py`) — на упавшие
    workflow, а исчерпание квоты бьёт в середине дня без того и другого.
    Гарантия не зависит от `GH_DISPATCH_TOKEN`/`GH_REPO`/`TELEGRAM_BOT_TOKEN`:
    без секретов тик продолжает замечать отказ — алерту просто некуда идти
    («возможности нет» отличается от «не заметил»).

23.7. Telegram-алерт владельцу (тем же каналом, что решения #470/#471, новый
    канал не заводится) уходит РОВНО ОДИН раз на переход healthy↔unhealthy,
    не каждый тик. Дедуп перехода персистентен — флаг `alerted` в таблице
    `storage_probe` (одна строка, id=1; переживает выгрузку DO из памяти) — и
    держится на ИТОГЕ ЗАПИСИ флага (`rowsWritten` условного UPDATE
    `WHERE alerted = 0` при аварии / `WHERE alerted = 1` при восстановлении),
    не на чтении прошлого исхода: при исчерпании `rows_read` (#320) падают
    все SELECT, включая чтение `storage_probe`, и дедуп на чтении спамил бы
    ⚠️ каждый тик до полуночного сброса — ровно в том классе, ради которого
    алерт заведён (блокирующая находка ревью PR #587). Запись флага сама не
    удалась (класс глубже — `rows_written`) — алерт этого тика пропускается с
    громким логом, а не шлётся без дедупа: без записанного флага «шлём/не
    шлём» решать не по чему, и пропустить один тик честнее, чем спамить;
    первый удавшийся тик догоняет (флаг остаётся 0 — тот тик видит
    `rowsWritten = 1`). Решение о переходе — чистая функция
    `storageReadyAlertDecision(ok, rowsWritten)`.

Сценарий: Дано — хранилище отказало (например, таблица зонда снесена).
Когда — прошли два тика пульса подряд. Тогда — Telegram получил ровно один
⚠️-алерт, не два.

Сценарий: Дано — хранилище отказывало и алерт ушёл. Когда — хранилище
восстановилось и прошёл тик. Тогда — ровно один ✅-алерт о восстановлении;
следующие здоровые тики молчат.

Сценарий: Дано — запись дедуп-флага невозможна (аналог исчерпания
`rows_written`). Когда — прошли два тика с отказавшим хранилищем. Тогда —
тик не падает, алертов нет (пропуск тика с громким логом); вернувшаяся запись
флага — следующий тик шлёт алерт один раз.
