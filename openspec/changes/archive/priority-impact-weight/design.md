# Design: выбор между четырьмя вариантами (задача #1178)

Задача сама называет четыре варианта и просит обосновать выбранный. Ниже —
сравнение по двум осям, которые реально решают: **цена** (что нужно
написать/поддерживать) и **риск** (какой класс ошибки вариант вносит).

## Развилка

### Вариант 1 — метка веса `impact:system` (ВЫБРАН)

Задача, снимающая измеренный системный барьер, получает явную метку.
Приоритет читает её как отдельный уровень строго между «сейчас красный»
(факт) и `area:process` (обычная мета).

- **Цена**: одна константа, одна функция-предикат (`_is_impact`,
  зеркало `_is_meta`), один новый уровень в кортеже сравнения — тот же
  паттерн, что уже даёт `area:process`/`ci-failure`. Нулевая инфраструктура
  сверх существующей (метка — GitHub-примитив, читается тем же
  `labels`-полем, что уже тянет `fetch_pool`).
- **Риск**: зависит от честности/внимательности того, кто заводит или
  разбирает задачу — метку можно забыть поставить, и свежий барьер снова
  утонет молча. Смягчение: `docs/agents/PROTOCOL.md` называет обязанность
  явно (тот же приём, что уже применён к `area:process` после находки
  AI-ревью PR #387); дальнейшее ужесточение (принудительный явный ответ
  при заведении, по образцу `--not-process-ack` для `area:process`,
  #695) вынесено в отдельную задачу (#1181, заведена этим же PR) —
  не расширяем scope #1178 сверх того, что доказано живым прогоном.

### Вариант 2 — признак по содержанию (число-предел + ссылка на замер)

Тело задачи парсится на регэксп вида «потолок», «X/сутки», «не
ограничено» + ссылка на issue с живым замером; наличие даёт вес.

- **Цена**: регэксп плюс эвристика «это ссылка на живой замер, а не на
  что угодно» — по сложности сопоставим с `declared_deps.py`
  (эвристический разбор прозы «Связано: #N»), который уже существует и
  явно назван НЕ авторитетным источником графа (только предупреждение,
  не блокировка) именно потому, что эвристика по прозе ненадёжна.
- **Риск**: ДВА класса ошибок сразу — false negative (барьерная задача
  сформулирована иначе, не содержит ни одного из ключевых слов — тот же
  провал, что и сейчас) и false positive (обычная задача случайно
  упоминает число и слово «потолок» не в этом смысле — получает вес без
  основания). Хуже варианта 1 по обеим осям: дороже написать, менее
  надёжно работает. Отклонён.

### Вариант 3 — явный реестр номеров барьеров в конфиге

Короткий список issue-номеров в конфиг-файле, единственное место правды,
пересматриваемое при каждом слиянии барьерной задачи.

- **Цена**: файл конфига + правило ведения (кто и когда правит список) +
  газ (кто снимает номер из списка, когда барьер снят) — три новых
  обязательства сопровождения там, где вариант 1 использует существующий
  примитив GitHub (метка снимается/ставится тем же способом, что и любая
  другая метка репозитория, разметка не требует отдельного PR в код).
- **Риск**: список стареет молча — отсутствие номера в списке не
  отличимо от «не барьер» и от «забыли добавить», ровно тот же класс,
  который `AGENTS.md` называет «решение — механизм, а не текст без
  проверки» применительно к спискам без гвардии. Метка (вариант 1) в
  этом отношении не лучше сама по себе (та же зависимость от честности
  заводящего), но НЕ требует отдельного PR/ревью на каждое изменение
  списка — она ставится/снимается `gh issue edit` в момент разбора самой
  задачи, без второго технического шага. Отклонён по цене сопровождения.

### Вариант 4 — инверсия тай-брейка «свежие раньше» внутри уровня `area:process`

Вместо метки — поменять порядок сравнения номеров issue внутри уровня
`area:process` на обратный (больше номер — раньше).

- **Цена**: минимальная — один символ (`-issue["number"]` вместо
  `issue["number"]`) в `issue_priority_key`. Самый дешёвый вариант из
  четырёх.
- **Риск**: затрагивает уровень ЦЕЛИКОМ, не только барьерные задачи.
  Живой пример вреда: на замере #1178 в уровне `area:process` есть и
  барьерные задачи, и обычные многолетние `area:process`-долги без
  измеренного веса (например, задачи про протокол/гвардии, заведённые
  давно и не имеющие отдельного признака важности). Инверсия подняла бы
  ЛЮБУЮ свежую задачу этого уровня над ЛЮБОЙ старой — включая случайную
  мелкую доработку протокола, заведённую вчера, которая обогнала бы
  многолетний долг без всякого основания. Владелец явно отметил риск
  («грубо ломает разумное "старые долги не забываем"») — согласен с этой
  оценкой, отклонён.

## Итог

Вариант 1 — единственный, который решает ИМЕННО барьерные задачи, не
трогая порядок там, где отличающего признака нет (уровень `area:process`
без `impact:system` продолжает сортироваться по номеру, как раньше —
доказано тестом `test_impact_label_tiebreak_by_number_preserved_within_tier`).
Цена ниже вариантов 2/3, риск ниже варианта 4.
