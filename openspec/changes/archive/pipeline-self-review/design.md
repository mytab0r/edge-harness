Общий признак всех пяти: у каждого есть заранее объявленный список того, что
именно он ищет. Ничто из них не задаёт открытый вопрос над сырыми данными.
Это ROOT CAUSE, который называет владелец: не «нет данных», а «нет вопроса».

## 1. Периодичность — обоснование числа

Три references, уже существующие в конвейере:

- `orchestra.yml` (пульс оркестратора) — каждые 15 минут, **96 раз/сутки**.
  Дешёвый: чтение уже открытых сущностей, без вызова модели по умолчанию
  (вызов модели там — только диспатч `ai-review`, не сам пульс).
- `ai-review.yml` — по событию (после `pr-review`) плюс ручные повторы;
  живой замер владельца в задаче упоминает **~50 дорогих прогонов/сутки**.
  Контекст одного вызова — дифф ОДНОГО PR (килобайты).
- `merge-health-watch.yml` — раз в час, **24 раза/сутки**, но БЕЗ вызова
  модели (чистая арифметика над уже прочитанными Actions/Issues API).

Саморевизия — дороже одного `ai-review` по контексту (весь дайджест периода:
прогоны восьми workflow, корреляция слияние→до/после, churn меток, снимки
здоровья, сводка пула — ~60 КБ промпта на живом прогоне, см. §3) и ДОЛЖНА
быть реже, чтобы не удваивать нагрузку на и так занятую цепочку провайдеров
(`config/provider-usage.json`, тот же `default-chain`, что уже несёт
`ai-review`/`worker`/`hands`). Выбрано **раз в 6 часов — 4 прогона/сутки**:

- Меньше 10% от объёма `ai-review` (4 против ~50) — цепочка не удваивается
  ощутимо.
- Окно сырых данных (`SELF_REVIEW_WINDOW_HOURS = 72`) шире интервала между
  прогонами (6ч) на порядок — соседние прогоны перекрываются: пропуск ОДНОГО
  прогона по инфраструктурной причине (403/сеть/квота) не теряет находку
  целиком, она попадёт в окно следующего. Дедуп по отпечатку не даёт
  повторному наблюдению того же факта задвоить задачу.
- 4 раза в сутки — это ~2 раза за обычный рабочий день владельца: достаточно
  часто, чтобы находка не протухла до неактуальности, и достаточно редко,
  чтобы не превратиться во второй `ai-review` по частоте.

**Цена одного прогона `gather` числом (живой замер 2026-09-12, окно 72ч —
ПРОДАКШН-конфигурация, инструментирован каждый вызов `gh()`/`list_timeline`
внутри `gather_digest`).** Итог: **111 запросов GitHub REST API за один
прогон**. Разбивка (нисходяще):

| Источник | Запросов | Комментарий |
|---|---:|---|
| Таймлайны недавно тронутых issues/PR (`gather_label_churn`) | 40 | Потолок `LABEL_CHURN_MAX_ISSUES`, каждый — 1 запрос при коротком таймлайне |
| `orchestra.yml` | 8 | Высокочастотный — 700 прогонов за 72ч, 7-8 страниц |
| `pulls` (открытые + слитые, `gather_pool_summary`+`fetch_recent_merges`) | 5 | |
| `issues` (открытые задачи + список «недавно тронутых» для churn) | 5 | |
| `ai-review.yml` | 4 | 341 прогон за 72ч |
| `pr-review.yml` | 3 | 275 прогонов за 72ч |
| `worker.yml`/`hands.yml`/`deploy-worker.yml`/`deploy-dsh-edge.yml`/`conflict-mechanical-rebase.yml` | 5 (по 1) | Низкочастотные — одна страница покрывает окно |
| Единичные таймлайны отдельных issues (#782 и т.п.) | ~2 | Часть потолка 40 выше |

До оптимизации (см. §3.2 — исключение `WATCHDOG_ISSUE` из кандидатов churn)
число было **162**: единственный таймлайн, потребовавший **10 страниц** —
issue #120 (watchdog), чья история — сотни комментариев-эскалаций за месяцы
жизни задачи-статуса, из которых почти ни один не `labeled`/`unlabeled`.
Цена отфильтровывалась ПОСЛЕ полной оплаты, поэтому #120 исключён из
кандидатов явно (§3.2).

111 запросов на прогон, 4 прогона/сутки — **444 запроса/сутки** только на
`gather`. Бюджет `GITHUB_TOKEN` — 1000 запросов/час НА РЕПОЗИТОРИЙ, общий на
ВСЕ workflow одновременно (`docs/research/21-github-actions.md`); один прогон
`gather` (111 запросов, несколько минут) занимает **~11% ЧАСОВОГО бюджета**,
разделяемого с чем угодно ещё, что молотит в тот же час (пульс оркестратора
каждые 15 мин, ai-review по событию). Не критично при текущей нагрузке
(измеренный потолок `rate_guard.py` для orchestra — 300 запросов/проход,
здесь треть от этого числа, и self-review не кластеризуется сама с собой —
следующий прогон только через 6 часов), но НЕ бесплатно — если нагрузка
конвейера вырастет на порядок, эту цифру придётся пересматривать.

## 2. Устройство: трёхшаговый трест-контур

Копирует форму `ai-review.yml` (ADR 0007), не изобретает новую:

```
gather (доверенный, read-only)  →  investigate (НЕ доверенный, DSH, без токена)  →  apply (доверенный, write)
```

Граница доверия — МЕЖДУ job'ами (тот же довод, что комментарий в
`ai-review.yml`): недоверенный шаг `investigate` не получает ни
`GH_TOKEN`, ни `GH_PIPELINE_PAT` — модель обрабатывает уже собранный текст
(данные), не может дотянуться до сети иначе. Всё, что он может испортить
(файлы воркспейса), умирает вместе с виртуалкой job'а. `apply` заново
чекаутит `main` — код, который парсит и решает, всегда доверенный.

`investigate` переиспользует `scripts/review/ai_dsh.sh` БЕЗ ИЗМЕНЕНИЙ:
скрипт уже общий (гоняет `$AI_WORK/prompt.md` через цепочку провайдеров,
пишет `$AI_WORK/answer.txt`), ничего специфичного для ревью PR внутри него
нет — это одна из причин, почему новый workflow не трогает
`scripts/review/*` вовсе.

## 3. Сырые данные: что входит, что нет, и по какой цене

| Источник | Функция | Цена (адаптивная, см. §1) |
|---|---|---|
| Прогоны 8 workflow за окно, покрывающие окно ЦЕЛИКОМ | `gather_workflow_digest`/`fetch_workflow_runs_window` | Постранично до границы окна ИЛИ `WORKFLOW_RUNS_MAX_PAGES=8` (§3.1) — 19 запросов на реальном 72ч-окне |
| Корреляция слияние→до/после | `gather_merge_correlation`/`fetch_recent_merges` | До `MERGE_LOOKUP_MAX_PAGES=5` страниц (реально 4 на 72ч-окне) + 0 доп. запросов на сам расчёт (переиспользует прогоны workflow, уже прочитанные выше) |
| Churn меток | `gather_label_churn` | 1 + до 40 запросов (см. §3.2) |
| Комментарии watchdog-issue #120 | `gather_watchdog_comments` | Постраничный обход одной issue (уже используется `pulse_guard`) |
| Снимки `data/pipeline-health` | `gather_health_snapshots` | 1 запрос (`pipeline_health.fetch_history`, переиспользован, не вторая копия) |
| Сводка пула (счётчики по меткам) | `gather_pool_summary` | 2 запроса (issues+pulls, тот же обход, что `scheduler` уже делает) |

Итог — **111 запросов на прогон** (72ч, продакшн-окно, живой замер §1).
Живой размер промпта — **~60 КБ**. Отслеживаемые workflow — надмножество
`pulse_guard.WATCHED_WORKFLOWS` плюс `ai-review.yml`/`pr-review.yml` (их
провал/петля не виден предохранителю конвейера вовсе).

### 3.1. Пагинация прогонов workflow: находка ДОРАБОТКИ по запросу владельца

Первая версия читала ОДНУ страницу (`per_page=100`) на workflow — для
низкочастотных workflow (worker.yml, deploy-*) этого достаточно, но для
высокочастотных (`orchestra.yml`, `ai-review.yml`, `pr-review.yml`) одна
страница физически МЕНЬШЕ, чем число прогонов за `SELF_REVIEW_WINDOW_HOURS
=72` часа — регрессия, случившаяся раньше самого свежего дня, срезалась
молча ещё ДО построения агрегата (не только в списке `recent`, как считалось
на первой приёмке). Живой замер (2026-09-12, окно 72ч): `worker.yml` — 68
прогонов (1 страница), `deploy-dsh-edge.yml` — 10 (1), `deploy-worker.yml`
— 7 (1), `conflict-mechanical-rebase.yml` — 20 (1), `hands.yml` — 0 (1), но
`orchestra.yml` — 700 прогонов (нужно 7-8 страниц), `ai-review.yml` — 341
(4), `pr-review.yml` — 275 (3). Итого 19 запросов на восемь workflow вместо
8 — `fetch_workflow_runs_window` читает страницы АДАПТИВНО (останавливается
на границе окна ИЛИ на короткой странице), `WORKFLOW_RUNS_MAX_PAGES=8` —
броня сверху, а не рабочий режим.

### 3.2. Churn меток: находка, случившаяся ПРИ РЕАЛИЗАЦИИ, не после

Первая версия `gather_label_churn` читала `GET /repos/{repo}/issues/events`
репозиторным обходом (`review_labels.list_pages`, без фильтра по времени —
этот эндпоинт **не поддерживает `since`**, отдаёт события от старых к новым).
На живой попытке 2026-09-12 процесс не ответил за десятки секунд и был убит
руками (`Stop-Process`) — при истории репозитория в тысячи событий полный
обход постранично читает ВСЮ историю на каждый прогон, независимо от окна.

Исправление — тот же приём, что уже применяет `scripts/measure/
label_churn_203.py` для открытых PR (таймлайн по issue), но с границей:
`GET /issues?state=all&sort=updated&direction=desc&since=...` (этот
эндпоинт **поддерживает** `since` по `updated_at`) даёт до 100 недавно
тронутых issues/PR ОДНИМ запросом, дальше таймлайн смотрится только у
первых `LABEL_CHURN_MAX_ISSUES = 40` — общая цена ограничена сверху
`1 + 40` запросами вне зависимости от размера истории репозитория.

Это ПРЯМАЯ иллюстрация правила «Право достроить себе инструмент» из
задания: гипотеза «нужен репозиторный churn меток» упёрлась в отсутствие
дешёвого способа его измерить, и вместо того чтобы отступить, механизм
получил рабочую, ограниченную по цене реализацию — на этом самом PR, до
того как задача ушла в пул.

**Второй раунд той же находки (доработка по запросу владельца, §1):** живой
замер общей цены прогона (162 запроса) показал, что ОДИН таймлайн —
`WATCHDOG_ISSUE` (#120) — стоил **10 страниц** сам по себе: у задачи-статуса
сотни комментариев-эскалаций за месяцы жизни, а `list_timeline` несёт ВСЕ
события (комментарии тоже), не только `labeled`/`unlabeled` — фильтр
отбрасывал почти всё уже ПОСЛЕ полной оплаты запроса. Исправление —
`gather_label_churn` исключает `WATCHDOG_ISSUE` из кандидатов ДО применения
потолка `max_issues`: его собственные комментарии уже несёт
`gather_watchdog_comments` отдельным, более дешёвым каналом (окно публикации,
не вся история задачи), вторая проекция того же issue не добавляла сигнала.
Цена прогона упала со 162 до 111 запросов (§1) без потери ни одной находки
(§5 — все три эталона по-прежнему видны после этой правки).

## 4. Контракт находок и жёсткий фильтр факта

```
### НАХОДКА
ЗАГОЛОВОК: <фраза>
КЛАСС: дефект | белое-пятно | знание | инструмент
ФАКТ: <проверяемый факт из приведённых данных>
ПОЧЕМУ_ВАЖНО: <фраза>
БЛОКИРУЕТСЯ: <номера или "ничем">
### КОНЕЦ НАХОДКИ
```

`has_verifiable_fact` — эвристика (не доказательство корректности факта,
только формы): длина ≥15 символов И (цифра, либо отсылка к команде/ссылке
— `` ` ``/`http`/`gh `). Живой антипример, ради которого фильтр писан
дословно в задании — issue #962: находка без единого числа/команды/ссылки,
чистая гипотеза, дошедшая до пула и закрытая как невалидная.

Блок без ВСЕХ пяти полей отбрасывается целиком при разборе (`parse_findings`)
— частичный контракт не контракт (тот же принцип, что «вердикт обязан
нести тело», AGENTS.md).

## 5. Доказательство работоспособности: живой прогон (первый заход + доработка)

### 5.0. Первый заход (окно 120ч) — 2 из 3 найдено, (а) названо честно как пропуск

Первая приёмка (`--hours 120`) нашла (б) и (в) чисто/по существу, но НЕ
нашла (а): агрегат по worker.yml показывал повышенный процент провалов
(58/100), но список `recent` (тогда — потолок 20 самых свежих прогонов НА
УЖЕ ПОЛУЧЕННОЙ ОДНОЙ странице, см. §3.1) не доставал до момента регрессии.
Причина была названа честно, не подогнана — и владелец потребовал закрыть
именно этот пробел, а не оставить «2 из 3» как приемлемый результат: класс
«наше изменение сделало систему хуже» — САМЫЙ важный по смыслу задания
(регрессия видна только в СРАВНЕНИИ до/после, не в моменте, как остальные
два эталона). Доработка ниже — прямой ответ на это требование.

### 5.1. Доработка: адаптивная пагинация + `merge_correlation` (§3.1, §3.2)

Команда (реальный репозиторий, не фикстура, окно `--hours 72` — продакшн):

```
python scripts/orchestra/self_review.py gather --repo mytab0r/edge-harness --out ...
```

Вывод: `self-review gather: окно 2026-09-09T13:34:41+00:00..2026-09-12T13:34:41+00:00,
промпт 60274 байт -> ...`

### 5.2. Находит (б) — петля меток на #782 — ЧИСТО, без изменений

`digest["label_churn"]` (без подсказки номера issue заранее, только правило
«ищи toggles >= 4 за окно»):

```json
[
  {"issue": 782, "label": "waiting:owner", "toggles": 59, "last_at": "2026-09-12T12:25:37Z"},
  {"issue": 810, "label": "stale-unclaimed", "toggles": 14, "last_at": "2026-09-12T00:04:39Z"},
  {"issue": 902, "label": "ai:changes-requested", "toggles": 8, ...}
]
```

#782 — первая строка, отрыв почти в 4 раза от второго места. Не пострадало
от доработки (churn-канал не менялся содержательно, только цена — §3.2).

### 5.3. Находит (в) — красный деплой dsh-edge — по-прежнему, без изменений

`digest["workflow_runs"]["deploy-dsh-edge.yml"]`: `total_in_window: 10,
by_conclusion: {"success": 4, "failure": 6}` — окно 72ч короче первого
захода (120ч), но соотношение (большинство прогонов красные) видно
однозначно и без подсказки, как и в первом заходе.

### 5.4. ТЕПЕРЬ находит (а) — регрессия после #878, дословно

`digest["merge_correlation"]` несёт запись:

```json
{
  "pr": 878,
  "title": "#876: успех воркера требует rc/провайдера/новых коммитов этого прогона, не только PR",
  "merged_at": "2026-09-10T22:54:34Z",
  "workflow": "worker.yml",
  "before_total": 4,
  "before_success_rate": 0.75,
  "after_total": 6,
  "after_success_rate": 0.0,
  "delta": -0.75
}
```

Дословно, без домысливания: за 8 часов ДО слияния #878 — 3 успеха из 4
прогонов worker.yml (75%); за 8 часов ПОСЛЕ — 0 успехов из 6 (0%). Открытый
вопрос («заметный перепад может значить, что именно это слияние сделало
систему хуже», см. текст `OPEN_QUESTION`) находит это БЕЗ подсказки номера
PR заранее — сигнал следует из чисел одной записи дайджеста.

**Как подобрано окно (честно, не скрыто).** Прогнано 3/4/6/8/12 часов
против ЭТОГО ЖЕ реального инцидента:
- 3ч/4ч/6ч — `compute_before_after` возвращает `None` (меньше
  `MIN_RUNS_PER_SIDE=3` прогонов с одной из сторон) — сигнала НЕТ вовсе.
- 12ч — сигнал ЕСТЬ, но РАЗМЫТ: after-окно уже захватывает начавшееся
  восстановление (13 прогонов «до» при 30.8% успеха, 12 «после» при 16.7%
  — дельта всего -0.141, НИЖЕ `MERGE_CORRELATION_THRESHOLD=0.25`, сигнал
  теряется).
- 8ч — набирает минимум с обеих сторон И ловит именно острую фазу до
  начала восстановления (дельта -0.75). Выбрано `BEFORE_AFTER_HOURS=8`.

Честная оговорка: это ПОДОБРАННЫЙ параметр против известного инцидента, не
теоретически выведенный — граница названа в самом коде (`BEFORE_AFTER_HOURS`,
докстринг) и здесь: для инцидента другой формы (например, регрессия,
проявляющаяся через сутки после мержа) 8ч могут промахнуться.

**Рейтинг находки.** #878 занял 13-е место по модулю дельты среди 48
пар (слияние, workflow), набравших достаточно данных за ту же ночь (окно
72ч содержит 60 слияний всего, из них 34 проходят порог заметности) —
живое подтверждение фразы координатора «в ту ночь подозреваемых было 13»
(измерено в PR #970): ночь 2026-09-09/11 была объективно шумной по мержам,
и #878 — один из МНОГИХ кандидатов с похожим по силе перепадом, не
единственный. `MERGE_CORRELATION_TOP_N=20` подобран с запасом над
измеренным рангом (13), не подогнан ровно под него.

**Самоуказывающая находка.** В том же списке присутствует PR #937 с
дельтой +0.867 (успех подскочил с 13.3% до 100% сразу после мержа) —
заголовок дословно: «#935: гейт успеха воркера учитывает origin ветки, не
только локальный HEAD (регрессия #878)». Открытый вопрос находит ФИКС
регрессии с прямой ссылкой на номер инцидента в заголовке ДАЖЕ если сам
#878 не входит в первые несколько строк списка — это не заменяет находку
§5.4 (обе присутствуют одновременно в реальном дайджесте), но показывает,
что сигнал избыточен: путь к причине открыт больше чем одним способом.

### 5.5. Итог честно, после доработки

Все три эталона — в дайджесте живого прогона одновременно, без подсказки
класса заранее: (б) чисто, (в) по существу верно, (а) — новым сигналом
`merge_correlation`, параметр которого подобран против реального инцидента
и назван честно как подобранный, не выведенный теоретически. Корреляция
по времени не равна причинности (§5.4, «как подобрано окно») — открытый
вопрос сам получает эту оговорку текстом (`OPEN_QUESTION`), решение
«виновно ли слияние» модель принимает, а не механизм.

## 6. Тормоза и газ

- **Суточный потолок** `SELF_REVIEW_DAILY_CAP = 3` — свой счётчик (Search
  API, `label:self-review created:>=<полночь UTC>`), не общий с соседними
  детекторами (тот же принцип, что уже документирован в `pulse_guard.py`
  для `FAILURE_WATCH_DAILY_CAP`/`STALL_DAILY_CAP`: разные предметные
  области, общий счётчик значил бы, что шумный день одного детектора
  выедает бюджет другого). Газ — автоматический, окно 24ч уезжает само.
  Отсечённые находки не теряются молча — эскалация тем же каналом, что
  предохранитель конвейера (`pulse_guard.escalate`, issue #120 + Telegram).
- **Дедуп в два слоя** — точный отпечаток (класс+токены заголовка) среди
  self-review issues `state=all` (открытых И закрытых — не даёт находке,
  однажды закрытой как невалидной, вернуться на следующем прогоне) +
  токенная похожесть по всему открытому пулу (`duplicate_guard.py`, тот же
  инструмент, что уже применяет `scripts/gh/issue-create`).
- **Отказ транспорта красит прогон.** `GatherTransportError` — если ВСЕ
  отслеживаемые workflow не прочитались (403/сеть), это фатальная ошибка
  gather, а не пустой дайджест. Аналогично сводка пула (`gather_pool_summary`)
  падает громко при отказе, а не подставляет нули.
- **Наблюдаемость.** `summarize_decisions` печатает точное число находок на
  каждой стадии (разобрано/заведено/отброшено без факта/дублей/отсечено
  потолком) — молчание без причины исключено по построению (`main` всегда
  печатает эту строку, даже когда создано 0 задач).

## 8. Не подтверждено

1. Реальный прогон трёхшагового workflow целиком (с настоящим вызовом
   модели через `ai_dsh.sh`) не проведён в рамках этой задачи — воспроизведён
   только шаг `gather` (детерминированный, без LLM) против живого
   репозитория; шаг `investigate` проверен транспортно (тот же скрипт, что
   уже работает в `ai-review.yml` многие сотни прогонов) и не выполнен здесь
   заново отдельно, чтобы не тратить квоту цепочки на ещё один прогон в
   процессе разработки.
2. `BEFORE_AFTER_HOURS=8` — параметр, подобранный против ОДНОГО известного
   инцидента (§5.4). Названо честно как границу, не теоретический вывод:
   регрессия другой формы (более медленная, проявляющаяся не сразу) может
   требовать другого окна — это открытый вопрос для следующего прогона
   саморевизии, не скрытый недостаток текущего.
3. Цена прогона (111 запросов/72ч, §1) измерена ОДИН раз на текущем
   состоянии репозитория (2026-09-12) — растущий пул (сейчас 303 открытых
   задачи, 60 слияний/72ч) означает, что оба главных источника цены
   (`gather_label_churn`'s 40 таймлайнов, `fetch_workflow_runs_window`'s
   адаптивная пагинация `orchestra.yml`) будут расти вместе с активностью
   конвейера — потолки (`LABEL_CHURN_MAX_ISSUES`, `WORKFLOW_RUNS_MAX_PAGES`)
   ограничивают рост сверху, но не гарантируют, что 111 останется актуальным
   числом навсегда.
