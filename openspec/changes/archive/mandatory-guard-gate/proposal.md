# mandatory-guard-gate: обязательный локальный гейт гвардий перед `git push`

Задача: #1280. Класс дефекта: исполнитель пушит работу, не прогнав гвардии
каталога `scripts/ci/guards/`, хотя нужная гвардия уже существует, уже
обязательна на серверном чеке `test` и уже способна поймать ровно ту ошибку,
которую делает исполнитель.

## Улика

PR #893, коммит `a14deb87ef2f05fd81566310482b57d6cff6218c`: обязательный чек
`test` покраснел в 21:33:57Z на гвардии класса #749 (рукописная регистрация
шага гвардии в `.github/workflows/repo-ci.yml` вместо файла каталога
`scripts/ci/guards/<имя>.sh`); живой вердикт ai-ревью с той же находкой
опубликован только в 21:46:16Z — на 13 минут позже. Тот же класс #749
повторился ещё в трёх PR подряд (#733, #789, #823) до #893.

Обратная проверка (см. `tasks.md`, критерий приёмки): чекаут ровно этого
коммита и прогон СУЩЕСТВОВАВШЕЙ на тот момент гвардии
`scripts/ci/guards/ci-guard-registration.sh` подтверждает — она красная
именно на этом коммите, с текстом, называющим точную причину («Найден НОВЫЙ
ручной шаг в repo-ci.yml: … — переведи в scripts/ci/guards/<имя>.sh»).
Механизм уже существовал и уже работал бы, если бы кто-то его спросил до
пуша.

## Почему напоминанием текстом это не лечится

Исполнитель получает `AGENTS.md`+`PROTOCOL.md`+`WORKER-PLAYBOOK.md` дословно
в каждом задании (~27 000 токенов правил, `scripts/worker/task.sh`) и всё
равно нарушает повторно один и тот же класс. Решение по правилу этого же
репозитория («Решение — это механизм, а не текст») — гейт, который
физически нельзя пройти мимо, не двадцать восьмая тысяча токенов инструкции.

## Решение

1. `.githooks/pre-push` — новый git-хук, зовёт
   `scripts/lib/pre_push_guard_gate.py`. `core.hooksPath=.githooks` уже
   безусловно ставится `scripts/git/task-branch` (и на пути автономного
   воркера, и на пути локальных рабочих деревьев) — новый файл каталога
   подхватывается автоматически, без единой правки `task-branch`/`task.sh`.
2. `scripts/lib/pre_push_guard_gate.py` — два режима (`full` внутри
   `GITHUB_ACTIONS=true`, `local` иначе), третье состояние через
   `scripts/lib/check_result.py` («гейт не смог запуститься» ≠ «прошёл» ≠
   «нашёл нарушение»), аварийный выход `GUARD_GATE_SKIP_ACK="<причина>"`.
3. `scripts/ci/run_guards.sh` — необязательный `GUARD_CATALOG_SKIP` (список
   имён гвардий через пробел), нужен только режиму `local`: две гвардии
   (`decision-doc-numbering-guard`, `invariant-numbering-guard`) через общий
   `decision_numbering.py::fetch_refs` делают `git fetch --depth 1`
   (ловушка #1228) — измерено: единичный локальный прогон полного каталога
   перевёл `git rev-parse --is-shallow-repository` false → true, замусорив
   ОБЩИЙ `.git` всех рабочих деревьев задачи. CI-вызов (`bash scripts/ci/
   run_guards.sh` без переменной) не меняется — полный каталог, как и
   раньше.
4. Новая гвардия каталога `scripts/ci/guards/pre-push-guard-gate-guard.sh`
   — поведенческий тест `scripts/git/test/pre-push-guard-gate.test.sh`
   (реальный `git push` на bare origin, 5 случаев) + юнит-тесты
   `scripts/lib/test_pre_push_guard_gate.py`.
5. Доводка ai-ревью PR #1285: префлайт окружения перед прогоном каталога
   (`gh auth status`) — красные без аутентификации гвардии (7 из 82
   каталога требуют gh/GH_TOKEN, замер grep'ом 2026-09-15, среди них
   `declared-deps-guard`) не выдаются за красный код: заранее
   недостоверный прогон возвращает ТРЕТЬЕ состояние («НЕ СМОГ запустить»)
   с фактом, а не `violation`. Потолок времени прогона (900 c при
   измеренных 76–81 c — см. «Замер стоимости») — подвисшая гвардия не
   подвешивает пуш навсегда. В full-режиме внешний `GUARD_CATALOG_SKIP`
   изымается из окружения — «полный» каталог нельзя молча ужать
   переменной.

## Замер стоимости шага — числа, не ощущения

Требование задачи «замерить стоимость прогона каталога, при дороговизне —
отбор с числовым обоснованием», 2026-09-15, 82 файла каталога:

- **full** (без исключений, режим воркера): **81 c** — шаг «Каталог
  гвардий scripts/ci/guards — перебор» job `test` на head этого PR (run
  34909630823, started 2026-09-14T23:41:13Z, completed 23:42:34Z, API
  Actions); посчитано суммой по гвардиям на Linux-раннере воркера с
  тёплым pip-кэшем — **76 c** (последовательный перебор, тот же порядок,
  что у `run_guards.sh`).
- **local** (скип двух гвардий): те же ~**72 c** — исключение экономит
  2,3 c (`invariant-numbering-guard`) + 2,2 c (`decision-doc-numbering-guard`),
  ~6% прогона. Цена НЕ является причиной исключения — причина ловушка
  #1228 (мутирующий `git fetch --depth 1` в общем `.git`), см. «Решение»
  п. 3; числа лишь подтверждают: скипом много не сэкономить, скипается
  ровно необходимое.
- Windows-хост владельца (интерактивный local) НЕ замерен — не
  подтверждено; ожидаемо дороже Linux-раннера.

**Решение по числам: full остаётся БЕЗ отбора.** Полный каталог — меньше
минуты, на порядок дешевле ОДНОГО круга доводки (повторный запуск воркера
+ живой вызов модели ревью; 59% слитых PR требовали ≥1 круга, в среднем
1.35). Гейт добавляет ≈81 c на пуш (после пуша каталог и так гоняет
обязательный чек `test` — эта цена не новая); при ~20 прогонах воркера в
сутки и 1–2 пушах на прогон — порядка получаса раннерного времени в сутки
против измеренной цены кругов доводки. Отбор ради ~6% вернул бы класс
#749 ровно на момент пуша — смысл гейта противоположный. **Порог
пересмотра числовой:** если полный прогон каталога превысит 600 c, отбор
становится обязательным и решение пересматривается этими же числами.

## Честные границы

- Git-хук — обычный отслеживаемый файл: рабочее дерево, заведённое ДО
  появления этого коммита в своей ветке, физически не увидит
  `.githooks/pre-push` на диске, пока не перебазируется на свежий
  `origin/main`. Это не новая дыра — тот же класс уже касается любого файла
  каталога гвардий; обязательный серверный чек `test` (branch protection)
  не читает локальное состояние рабочего дерева и остаётся последней
  инстанцией независимо от возраста дерева.
- `git push --no-verify` обходит любой git-хук — это свойство git, не
  дыра этого механизма: цель — не сделать обход технически невозможным
  (никакой локальный хук этого не может), а убрать типовой случай «никто не
  подумал спросить гвардию», который и есть измеренная причина 59% циклов
  доводки. Специально обходящий гейт исполнитель — не тот случай, который
  чинит эта задача (его продолжает ловить обязательный серверный чек).
- Локальная зелёность каталога зависит от внешнего окружения (находка
  ai-ревью PR #1285): без `gh`-аутентификации/сети краснеют гвардии, не
  относящиеся к изменению исполнителя (7 из 82 каталога требуют
  gh/GH_TOKEN — замер grep'ом, 2026-09-15). Гейт различает механически:
  префлайт `gh auth status` перед прогоном — при отказе возвращается
  ТРЕТЬЕ состояние с фактом («gh не аутентифицирован, код N» / «gh CLI
  не найден» / «не ответил за 30 c»), а прогон каталога не выполняется
  вовсе; красный каталог при ПРОЙДЕННОМ префлайте — достоверный
  `violation`. Остаток, который префлайтом не покрыт и не называется
  покрытым: сетевые сбои конкретного внешнего сервиса и недоступные
  записи вне репозитория (живой случай 2026-09-15: тест
  `provider-latency-model-discovery-guard` краснел на записи в
  `$GITHUB_STEP_SUMMARY` в окружении, где этот путь не записываем) —
  против такого недостоверного красного остаётся аварийный выход
  `GUARD_GATE_SKIP_ACK`, это объявленная граница.
