# worker-silence-stall-detector: тишина сессии harness-<N> ловит зависшего воркера раньше возраста (#1085)

Задача: #1085. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Единственный признак зависшего прогона `worker.yml` — возраст
(`WORKER_STALL_MINUTES`, `scheduler.py::_run_is_stalled`/`stalled_worker_run`,
issue #815/#877/#1067). Собственный докстринг признаёт его границу: «отличить
зависший прогон от легитимно медленного, оставаясь ниже стены job'а,
невозможно» — потому что признак один, и это возраст. Воркер — один на
репозиторий (`concurrency: group: worker`), поэтому зависший прогон блокирует
ОДНОВРЕМЕННО обычный `dispatch_worker`, `dispatch_conflict_rework` и
восстановление предохранителя конвейера, пока не истечёт весь порог.

Живой случай (2026-09-13): прогон 34739313568 стоял `in_progress` дольше 2ч35м
на момент замера, рипер тронул его только на 255-й/295-й минуте (порог менялся
за время работы над задачей, см. ниже) — воркер репозитория недоступен ни
новым задачам, ни доводке PR, ни разбору конфликтов почти пять часов на
живом примере (run 34757182001, 2026-09-13T12:28→17:23).

Воркер уже пишет построчный транскрипт хода работы в сессию `harness-<N>`
морды dsh-edge (#119) — той же ценой (drain каждые 30с), что уже оплачена
(~98% суточных rows_written/rows_read DO, docs/research/20-cloudflare-free.md).
Растущий `seq` этой сессии — прямое, бесплатное доказательство «агент
работает», доступное задолго до истечения возрастного порога.

## Что делается

- `scheduler.py::_session_progress_tip` — максимальный `seq` хвоста сессии
  `harness-<N>` через `session.history {sessionId, maxMessages:1}` (морда
  dsh-edge, тот же транспорт и креденшлы, что `archive_runner_sessions`/
  `append_session_notes` уже используют, — ни нового секрета, ни нового
  провода). Деградация (нет конфигурации, логин не прошёл, сессии нет,
  событий нет, сеть) — честная, `(None, причина)`, не гадание.
- `scheduler.py::_worker_silence_reason` — сравнение текущего `seq` с
  ПОСЛЕДНИМ известным значением по этому `run_id`, хранимым как ОДИН
  комментарий-маркер в WATCHDOG_ISSUE (#120), редактируемый на месте
  (`edit_issue_comment`/PATCH, тот же приём, что #1100 уже применяет для
  `quota_alert`) — не плодит историю на каждый растущий пульс. Растёт `seq` —
  жив; не растёт `WORKER_SILENCE_MINUTES` (150 мин) подряд — завис.
- `scheduler.py::reap_stalled_worker_run` — приоритет между двумя ножами:
  пока признак тишины ДОСТУПЕН (задача коррелирована, морда отвечает),
  решение принимает ОН один (растёт — жив без возрастного потолка вовсе,
  до жёсткой стены GitHub; не растёт порог — завис раньше возрастного
  предела). Возраст (`WORKER_STALL_MINUTES`) — ФОЛЛБЭК на случай, когда
  признак тишины недоступен (задача не коррелирована, морда/сеть/маркеры
  отказали) — прежнее поведение как есть.
- `_stalled_run_task_number` резолвится КАЖДЫЙ пульс с первого (не с
  возраста ≥150) — иначе база для сравнения появляется не раньше 150-й
  минуты, и тишина не может сработать раньше 300-й, то есть позже
  возрастного потолка (находка ai-review PR #1089, блокирующая, дважды).

## Не в рамках (см. #1141)

Суммарное ВРЕМЯ цепочки провайдеров (`dsh_run_with_provider_chain`,
`DSH_TIMEOUT_SECS=7200` на ОДНУ попытку × до 8 записей цепочки ≈16ч в худшем
случае) — отдельный рычаг той же проблемы, решается отдельной задачей #1160
(бюджет времени всей цепочки). Разница: этот change ловит прогон, который
ПЕРЕСТАЛ писать события вовсе (реально завис); #1160 ограничивает легитимно
РАБОТАЮЩУЮ, но неограниченно долгую цепочку retry. Оба рычага независимы и
не заменяют друг друга — следующий агент не должен сливать их в один
механизм.
