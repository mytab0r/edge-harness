# Дельта-спека: журнал (journal-tasks-hands) — тишина сессии harness-<N> ловит зависшего воркера

Опирается на существующий п.26 раздела «Автономный воркер (конвейер пула)» и
дельту `archive/worker-stall-detection` (#815, возрастной признак) — см.
`scheduler.py::_session_progress_tip`/`_worker_silence_reason`/
`reap_stalled_worker_run` (issue #1085) за реализацией.

## MODIFIED: Порог зависания — два признака вместо одного

Было (#815/#877/#1067): единственный признак — возраст прогона
`in_progress` дольше `WORKER_STALL_MINUTES` от `run_started_at`. Признак
честно грубый: не отличает «завис» от «редкая легитимная долгая работа».

Стало: ДВА признака, с приоритетом.

1. **Тишина сессии `harness-<N>`** — главный нож, когда доступен. Воркер
   пишет построчный транскрипт хода работы в сессию `harness-<task_number>`
   морды dsh-edge (#119); `seq` этой сессии — растущее целое. Прогон, чья
   задача коррелирована (см. ниже) и чья сессия отвечает: `seq` растёт →
   прогон жив, ВОЗРАСТНОЙ ПОТОЛОК НЕ ПРИМЕНЯЕТСЯ вовсе, сколько бы прогон
   ни шёл (до жёсткой стены GitHub — `timeout-minutes` самого `worker.yml`,
   вне контроля этого признака); `seq` не растёт `WORKER_SILENCE_MINUTES`
   (150 минут) подряд → прогон признан зависшим раньше возрастного потолка.

   Требование (найдено ai-review PR #1089, третий раунд): «маркера для
   этого `run_id` не найдено» — НЕ равнозначно «прогон жив». Генуинное
   первое наблюдение (прогон младше `WORKER_SILENCE_BASELINE_GRACE_MINUTES`,
   30 минут — база физически не могла ещё появиться) действительно
   трактуется как «жив, база только создаётся». Но если прогон уже СТАРШЕ
   этого порога, а маркера всё ещё нет — это НЕ подтверждение жизни, а
   деградация признака: маркер либо не был записан, либо выпал из окна
   чтения (`max_pages`, см. ниже) под шторм других комментариев в #120.
   Решение в этом случае остаётся за возрастным потолком, как при любой
   другой недоступности признака — не создаётся новая «база» задним числом.

   Обоснование порога: `DSH_TIMEOUT_SECS` (`task.sh`, 7200с=120 мин) —
   легитимный потолок ОДНОЙ попытки провайдера, в течение которого сессия
   вправе не оставить ни одного видимого события (worst case — попытка
   виснет на сетевом вызове до собственного таймаута). `WORKER_SILENCE_
   MINUTES = 150` = 120 + 30 мин запаса.

   База для сравнения (последний известный `seq` по `run_id`) появляется
   СРАЗУ, как только у прогона есть коррелированная задача — НЕ дожидаясь
   какого-либо возраста: иначе тишина не могла бы сработать раньше
   удвоенного порога, то есть позже возрастного потолка (найдено ai-review
   PR #1089).

2. **Возраст (`WORKER_STALL_MINUTES`)** — фоллбэк, когда признак тишины
   НЕДОСТУПЕН: задача не коррелирована (адресный прогон на PR с уже открытым
   PR, аренда сгорела до следа), морда/сеть/маркеры прогресса отказали.
   Поведение — как в #815/#877/#1067, без изменений: прогон `in_progress`
   дольше порога от `run_started_at` считается зависшим, действие называет
   и длительность, и порог явно.

Требование: деградация признака тишины (нет конфигурации DSH_EDGE_URL/
DSH_EDGE_ACCESS_KEY, логин не прошёл, сессии нет, событий нет, маркеры не
читаются/не пишутся) НЕ трактуется ни как «жив», ни как «завис» — строка в
отчёте называет причину деградации явно (AGENTS.md, «алерт не гадает»),
решение остаётся за возрастным порогом.

## ADDED: Маркер прогресса воркера в WATCHDOG_ISSUE

Требование: последний известный `seq` сессии по каждому активному `run_id`
хранится РОВНО ОДНИМ комментарием в WATCHDOG_ISSUE (#120), редактируемым на
месте (`PATCH .../issues/comments/{id}`) при каждом росте `seq` — не новым
комментарием на каждый пульс (тот же приём, что #1100 уже применяет для
`quota_alert.record_reading`). Момент «последний раз видели рост» — поле
`updated_at` этого комментария (GitHub обновляет его при PATCH).

Требование: маркер читается из ограниченного окна последних страниц
комментариев (`max_pages`, тот же приём, что `quota_alert`/`issue_marker_times`
уже применяют) — стоимость одного тика не растёт с историей WATCHDOG_ISSUE.

## Не меняется

Отмена зависшего прогона (`gh api .../actions/runs/<id>/cancel`,
best-effort) и полное освобождение аренды коррелированной задачи (замок +
назначение) — тот же механизм, что #815 ввёл, независимо от того, КАКОЙ из
двух признаков дал `reason`.
