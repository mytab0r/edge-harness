# api-quota-gate-measures-the-applied-counter: гейт квоты мерил не тот счётчик и стоял не у тех шагов (#1437)

Задача: #1437. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Прогон 35715554412, PR #1449, job `test` — дословно из лога:

```
10:24:21  rate_guard: квота ок (5000/5000) для job'а «repo-ci-invariants»
10:27:02  ##[error]repo_invariants: … HTTP 403: API rate limit exceeded for installation
10:29:54  ##[error]upstream-namespace-collision: … HTTP 403: API rate limit exceeded for installation
```

Два независимых дефекта в одном прогоне:

1. **Измеритель читает не тот бак.** `remaining` РАВЕН `limit` — на счётчике,
   который прочитал гейт, не потрачено ничего, пока применяемый уже пуст.
   Версия «за две минуты выбрали 5000» этим равенством отбрасывается.
2. **Гейт прикручен к одному шагу из тридцати.** Шаг инвариантов был
   пропущен корректно — и `test` всё равно покраснел на соседнем шаге,
   который про гейт не знал.

Обязательная проверка краснеет причиной, к которой автор PR не имеет
отношения, а следующий агент чинит НЕ ТО: сигнал указывает на его дифф.

## Замер, а не рассуждение

Два источника остатка на одном токене в один момент (агентская сессия,
2026-09-22 10:35 UTC, воспроизведено дважды подряд):

```
gh api rate_limit             → limit 15000, remaining 15000, used 0,   reset 1790076800
gh api -i repos/<owner>/<repo>→ limit 15000, remaining 14592, used 408, reset 1790075485
```

Разные `used` И разные `reset` — два счётчика, не два чтения одного. Сам
эндпоинт `rate_limit` исключён из лимитирования и поэтому не может измерять
то, что лимитируется.

Масштаб второго дефекта — числом: 29 шагов в 17 workflow читают API токеном
job'а мимо гейта (замер `scripts/lib/api_quota_gate_guard.py` на дереве PR).

## Что делается

1. `rate_guard` читает ОБА источника, печатает их рядом в каждом прогоне и
   решает по МЕНЬШЕМУ остатку.
2. Гейт в `repo-ci.yml::test` переезжает первым шагом job'а; все шаги этого
   job'а, читающие API, встают за одно условие.
3. Гвардия `api_quota_gate_guard` держит класс закрытым: незакрытый шаг либо
   за гейтом, либо в реестре с причиной; мёртвая запись реестра краснеет так
   же, как незакрытый шаг.

## Честный потолок

Что заголовки `X-Ratelimit-*` отражают применяемый бак именно для
`github.token` внутри Actions — НЕ подтверждено: замер выше сделан на PAT из
агентской сессии. Поэтому решение принимается по минимуму, а оба числа
печатаются: первый же прогон с 403 даст сравнение в логе. Это сознательно
слабее, чем «починили измеритель», и сказано так, а не иначе.

Оставшиеся 28 записей реестра — не закрыты. Они разбираются отдельными
узкими задачами, по одной на workflow, чтобы каждая несла свой замер:
гасить шаг, чьё участие в исчерпании не измерено, значит чинить
незамеренное.
