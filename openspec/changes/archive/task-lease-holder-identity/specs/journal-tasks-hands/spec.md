# Дельта-спека: замок аренды знает держателя (#1190)

Расширяет дельты `task-lease-claim` («Захват задачи любым каналом») и
`task-branch-lease` (там же отклонена альтернатива «идемпотентный claim по
держателю» — эта дельта вводит держателя ДРУГОЙ природы, см. `design.md`
этого change, не отменяет то решение).

## ADDED: Держатель замка — не логин, а прогон/дерево

Требование: коммит замка `refs/locks/task-<N>` несёт вторую строку тела
`holder: <id>` — идентификатор конкретного прогона/рабочего дерева
(`claim_task.current_holder()`), не GitHub-логин (`actor`, один на всех
каналов и ничего не различающий). Источник, в порядке приоритета: явный
`CLAIM_HOLDER` → `run:<GITHUB_RUN_ID>:<GITHUB_JOB>` (CI, уникален на прогон
И job: run id один на все job'ы запуска, суффикс различает их — находка
ревью PR #1206) →
`tree:<путь рабочего дерева>` (локально, устойчив для одного агента по
правилу «одно дерево — один агент») → `proc:<hostname>:<pid>` (запасной
рубеж).

`claim()` при отказе создания рефа (422 «already exists») читает держателя
ТЕКУЩЕГО замка и возвращает один из трёх исходов:

- **свой** (`existing_holder == holder`) — идемпотентный успех, БЕЗ снятия и
  пересоздания рефа: тот же прогон/дерево реально продолжает держать то, что
  уже держал;
- **чужой** (`existing_holder` — другая строка) — отказ, называющий
  держателя в тексте (`ClaimResult.detail`, `ClaimResult.holder`);
- **неизвестный** (замок старого формата, созданного до этой дельты, без
  строки `holder:`) — честное третье состояние: отказ (безопасный дефолт —
  снимать чужой/неопределённый замок вслепую нельзя), но формулировка иная:
  «держатель неизвестен», не «держит вот этот».

Сценарий (критерий готовности issue #1190, воспроизведён поведенческим
тестом на реальных git-рефах, `scripts/lib/test_claim_task_real_refs.py`):
канал A берёт замок на задачу N → канал B пытается взять тот же замок —
получает отказ с именем держателя A → канал A берёт повторно (например,
после короткого сбоя сети внутри своего же прогона) — успех, замок не
трогается.

## ADDED: Release проверяет владение опционально

Требование: `claim_task.release(repo, task, holder=None, force=False)`.
`holder=None` (умолчание) — поведение НЕ меняется этой дельтой: force-снятие
без проверки владения, для путей, авторитетных независимо от держателя
(post-merge оркестратора, TTL-сборщик `collect_stale`) — `scheduler.py`
продолжает звать `release(repo, task)` без изменений сигнатуры вызова.
`holder=<id>, force=False` — снятие только если замок держит именно этот
`holder`; иначе `ForeignLockError` (называет держателя, либо честно —
«неизвестен» для замка старого формата). `force=True` — явный обход проверки
для того, кто уверен, что имеет право (газ для тормоза, AGENTS.md «Тормоз без
газа не принимается»): раньше единственным действием при путанице было
слепое снятие чужого замка (сам инцидент #1190), теперь оно безопасно по
умолчанию, а обход — поимённый, не тихий.

CLI `claim_task.py release <N> [--force]`: без `--force` передаёт
`current_holder()` (снимает только свой замок, отказ `ForeignLockError` даёт
CLI-код `EXIT_BUSY`, не `EXIT_ERROR` — это отказ по правилу владения, не
поломка инструмента); `--force` — старое поведение, без проверки. CLI
`status` печатает держателя каждого живого замка (или «НЕИЗВЕСТЕН (старый
формат)» для рефов без записи).

Сценарий: канал B по ошибке вызывает `claim_task.py release N` или
`release-full N`, полагая замок своим, но его держит канал A — CLI отказывает,
называя держателя A, и НЕ трогает НИ замок, НИ назначение канала A (проверка
владения стоит до любой мутации, находка ревью PR #1206: раньше `release-full`
снимал назначение до отказа; само исправление живого случая #1190: раньше
единственным действием было тихое снятие чужого замка).

## MODIFIED: Обратная совместимость с замками старого формата

Требование (было implicit в `task-lease-claim`: замок нёс только TTL-коммит
без держателя — теперь формат расширен): живые git-рефы `refs/locks/task-<N>`,
созданные ДО этой дельты (коммит без строки `holder:`), читаются новым кодом
без падения — `_parse_holder` возвращает `None`, что даёт третье состояние
(«неизвестный держатель») везде, где решение зависит от держателя (claim при
отказе, release с явным `holder`). Принудительная миграция или перезапись
существующих замков не производится: они естественно освобождаются
существующими путями (TTL-сборщик, post-merge release, ручной
`release --force`).
