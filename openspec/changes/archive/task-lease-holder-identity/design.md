# design: чем является «держатель» замка

## Развилка: чем идентифицировать держателя

Кандидаты (названы в issue #1190):

1. **Логин (`actor`/`GITHUB_ACTOR`).** Уже использовался как «видимость»
   (assignee, комментарий). Отклонён как идентификатор владения: один логин
   на ВСЕХ агентов (см. AGENTS.md, «Атрибуция событий») — не различает канал A
   от канала B вовсе. Это и есть причина, по которой issue формулирует
   проблему как «не смог установить, кто держит».
2. **Имя ветки `agent/<N>-<slug>`.** Отклонён как идентификатор ПРОГОНА: имя
   ветки определяется номером задачи, не прогоном — два разных прогона на ОДНУ
   задачу (ровно сценарий гонки, который замок обязан ловить) получат ОДНО и
   то же имя ветки. Различать по имени ветки значило бы не различать вовсе.
3. **`GITHUB_RUN_ID`.** Годится ИДЕАЛЬНО для CI (worker/hands): новый на
   каждый запуск workflow, уникален по построению. Не существует вне CI —
   локальный/внешний агент (`task-branch`, ручной вызов) его не имеет.
4. **Путь рабочего дерева.** Годится для локального/внешнего канала: правило
   «одно дерево — один агент» (AGENTS.md, `.githooks/pre-commit`, класс #332)
   уже даёт устойчивое сопоставление «путь ↔ агент» — тот же агент, тот же
   worktree, повторный вызов из него читается как «свой» ПРАВИЛЬНО (это и
   есть желаемая идемпотентность: перезапуск того же канала после сбоя должен
   узнавать свой же замок). В CI неприменим: воркер работает в одноразовом
   чекауте, путь один и тот же для РАЗНЫХ прогонов (см. `scripts/worker/
   task.sh`, шаг 4 — `GITHUB_ACTIONS=true` не заводит worktree).
5. **Комбинация (выбрано).** `current_holder()`: `CLAIM_HOLDER` (явный
   override для тестов/будущих каналов) → `run:<GITHUB_RUN_ID>` (CI) →
   `tree:<cwd>` (локально) → `proc:<hostname>:<pid>` (честный запасной рубеж,
   не идемпотентен между вызовами, но не падает). Каждый источник корректен
   ровно в своей области (CI vs локально) — совмещение не создаёт новой
   путаницы, потому что области не пересекаются: `GITHUB_RUN_ID` задан ⟺
   `GITHUB_ACTIONS=true` (тот же признак, что уже используют task-branch и
   AGENTS.md «Атрибуция событий» для «job vs действие человека»).

## Почему это НЕ повторяет отклонённую ранее альтернативу

`task-lease-claim`/`task-branch-lease` уже рассматривали и отклонили
«идемпотентный claim по держателю» — но там держателем предлагался `actor`
(логин), и опасность была названа точно: «этот же прогон уже взял этот же
номер» неотличимо от «другой прогон под тем же логином только что взял тот
же номер», раз идентификатор — логин. Формулировка данной дельты меняет САМ
идентификатор, не воскрешает отклонённый вариант: `run:<id>`/`tree:<path>`
различают именно прогон/дерево, а не логин, поэтому два РАЗНЫХ канала под
одним логином получают РАЗНЫЕ `holder` по построению — путаница, из-за
которой был отклонён вариант с логином, здесь не воспроизводится.

## Развилка: что делать с замком старого формата (без `holder:`)

Варианты: (а) трактовать как «свой» (разрешить тихий re-claim) — отклонено:
это и есть исходный инцидент #1190 (снятие/переоткрытие чужого замка без
проверки); (б) трактовать как «чужой» с общей формулировкой отказа —
отклонено: сообщение соврало бы, называя конкретного держателя там, где его
установить нельзя, а вызывающий код (агент, читающий сообщение) не отличил
бы «есть кто-то конкретный» от «неизвестно, но что-то есть»; (в) третье
состояние с честной формулировкой (выбрано) — соответствует прямому
требованию issue («не молчаливый успех и не тихий отказ»).

## Развилка: `release()` — проверять владение всегда или опционально

Проверка владения ВСЕГДА (ломает обратную совместимость: `scheduler.py` зовёт
`release(repo, task)` из авторитетных путей — post-merge, TTL-сборщик, — где
владение НЕ должно быть условием; задача завершена/протухла независимо от
того, кто именно держит замок прямо сейчас) — отклонено: потребовало бы
менять сигнатуру вызовов в `scheduler.py` (файл занят параллельным PR,
#1089/#1136 — трогать его здесь и рискованно, и не нужно по существу).
Выбрано: `holder=None` (умолчание) — старое поведение без изменений;
`holder=<id>` — опциональная проверка, включаемая ЯВНО вызывающим кодом (CLI
`release <N>` включает её по умолчанию для СЕБЯ, передавая
`current_holder()`). Один код, два режима использования, ни один из
существующих вызовов не меняет поведение без явного участия.
