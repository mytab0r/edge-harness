# Дельта-спека: журнал (journal-tasks-hands) — дайджест мягких отказов (#1121)

Реализация: `scripts/orchestra/soft_failure_digest.py`, шаг «Дайджест мягких
отказов (#1121)» в `.github/workflows/orchestra.yml`. Пороги — константы
модуля (одно место правды, номера строк не фиксируются).

## ADDED: Скан аннотаций и условных шагов пяти workflow

Требование: каждый полный скан (гейт `digest_due`, не каждый тик
оркестратора) читает завершённые прогоны `worker.yml`, `hands.yml`,
`ai-review.yml`, `orchestra.yml`, `deploy-dsh-edge.yml` за окно
`DIGEST_WINDOW_HOURS` часов (постранично, до короткой страницы — полный
скан НЕ обрезается молча первой страницей, класс #308). Прогоны
`pull_request`-события `orchestra.yml` (job `contract`, не `orchestra`)
исключены — не относятся к деградации самого конвейера.

Требование: для каждого прогона читаются аннотации Checks API уровня
`warning`/`failure` (check-runs ЭТОГО прогона — фильтр по `check_suite_id`,
не все check-runs на sha), группируются по (workflow, job, нормализованный
текст без id/hex/чисел). Аннотации читаются НЕЗАВИСИМО от `conclusion`
job'а/степов — переживают маскировку `continue-on-error`.

Требование: для каждого прогона читаются `conclusion` всех шагов (Jobs
API), но канал B ограничен ДВУМЯ фильтрами, не одним: (1) шаг обязан
нести явный `if:` в исходнике workflow (читается локально с диска, 0
сетевых вызовов, `load_conditional_steps`) — иначе безусловный шаг,
пропущенный лишь из-за раннего обрыва job'а другим отказавшим шагом (не
своим `if:`), ложно считается «условным» (живой замер: «Run actions/
checkout@v7» — success 178 раз БЕЗ единого `skipped`-исхода по СВОЕЙ
причине); (2) среди occurrences этого шага `skipped` обязан быть
БОЛЬШИНСТВОМ, не-skipped — МЕНЬШИНСТВОМ (живой замер: `if: steps.facts.
outputs.go == 'true'` ai-review.yml — штатное решение, срабатывающее в
БОЛЬШИНСТВЕ прогонов, иначе тонуло бы в одной таблице с автооткатом прода,
который срабатывает редко). Совпадение обоих фильтров — отдельная запись
на (workflow, job, имя шага, conclusion), группирующая каждое НЕ-skipped
вхождение. Job Jobs API сопоставляется с job'ом YAML по `name`/ключу
(`match_job_key`: exact или матричная форма «<display> (…)») — при
расхождении (переименование, явный `name:`, матрица) канал B для этого
job'а пропускается НЕ молча: наблюдение «job из Jobs API не сопоставлен
ни с одним job'ом исходника» печатается один раз на workflow за скан.

Требование: таблица со ВСЕМИ найденными группами (не только над порогом)
печатается в step summary каждого полного скана — видимость всей картины
не зависит от решения завести задачу.

## ADDED: Эскалация повторяющихся групп

Требование: группа с `count >= DIGEST_REPEAT_THRESHOLD` за окно, чей
отпечаток ещё не встречен в теле ни одной ОТКРЫТОЙ issue с меткой
`soft-failure`, заводит новую задачу (`task`+`soft-failure`) с фактом
(число повторов, первый/последний прогон, ссылки, текст образца) и
отпечатком в HTML-комментарии тела. Суточный потолок
`SOFT_FAILURE_DAILY_CAP` (свой счётчик, не общий с `ci-failure`/
`dependabot-alert`) — исчерпание не заводит задачу, эскалирует #120+
Telegram один раз в календарный день на переход, не на каждый пульс.

Требование: дедуп — по ОТКРЫТЫМ issues, не по маркеру-комментарию #120:
закрытая задача (причина устранена/признана нормой) НЕ запирает класс
навсегда — вернувшаяся причина заводит НОВУЮ задачу. Газ — ручной (нет
внешнего источника состояния, который сам подтвердил бы «класс устранён»,
в отличие от dependabot alert state): человек/агент закрывает задачу, когда
причина устранена или признана нормой.

Требование: гейт цикла (`digest_due`) ограничивает частоту полного скана
(не на каждый тик оркестратора, ~каждые 15 минут) — дешёвый маркер-чек
(`issue_marker_times`, `max_pages` ограничен) решает, готов ли следующий
полный скан; heartbeat-маркер пишется тихим комментарием (не Telegram)
после каждого полного скана.

## ADDED: Квота-гейт и честный сигнал провала (находка ревью PR #1136)

Требование: перед полным сканом (когда гейт цикла уже сказал «пора»)
проверяется остаток квоты `github.token` (`gh api rate_limit`, не тратит
собственную квоту) против `SOFT_FAILURE_QUOTA_THRESHOLD` — свой порог, не
общий с `rate_guard.DEFAULT_THRESHOLD` (тот калиброван под сам orchestra,
не под смету полного скана дайджеста, ~700-750 вызовов). Квоты не хватает
— скан НЕ начинается в этом тике (не тратит остаток бюджета, соседи того
же часа не голодают), heartbeat не пишется — гейт цикла останется открыт,
следующий обычный тик (~15 мин) попробует снова. Тот же шаг workflow несёт
и обычный `if: steps.quota.outputs.skip != 'true'` (тот же гейт, что у
соседних дорогих шагов job'а `orchestra`) — двойная защита: раннее
исключение ДО запуска скрипта и повторная проверка ВНУТРИ него на случай,
когда обычный порог (300) уже пропустил тик, а более дорогая смета
дайджеста (900) — ещё нет.

Требование: полный провал чтения (ни один из пяти workflow не прочитан)
отличим от «прочитано, групп нет» — обе ситуации раньше давали одинаковый
текст «Группы не найдены» и одинаковый heartbeat, закрывающий гейт на
`DIGEST_INTERVAL_HOURS` (ложь маскировала себя на 12 часов, именно когда
исчерпание квоты #1100 делает такой провал вероятнее). При полном провале:
heartbeat не пишется, текст называет факт («скан НЕ удался — прочитано
0/N workflow»), `main()` возвращает ненулевой код — `continue-on-error`
удерживает job зелёным. Текст печатается с workflow-command-префиксом
`::warning::` В НАЧАЛЕ строки (находка ревью PR #1136, третий круг:
эмодзи-префикс не становится аннотацией Checks API — GitHub требует
директиву строго в начале строки) — только так шаг получает НАСТОЯЩУЮ
аннотацию с отличимым текстом («скан НЕ удался», не «Process completed
with exit code N»), которую канал A этого же дайджеста поймает на
следующем скане, не схлопнув с уже отслеженной группой continue-on-error
job'а `orchestra` (рекурсивная проверка «наблюдатель не смог посмотреть» —
тот же класс, что #1096).

## ADDED: Классификация класса причины (эвристика, находка координатора #1115)

Требование: таблица и тело заведённой задачи несут столбец/строку «класс»
— результат `pulse_guard.classify_failure_cause(sample)` (единственное
место правды инфра/дефект-сигнатур, не вторая копия списка): `infra` →
«инфраструктура», `stale_base` → «устаревшая база», иначе →
«дефект/наблюдение». Эвристика, не факт — нераспознанное классифицируется
как «дефект/наблюдение» по умолчанию (fail loud стороной «не прощаем
молча», см. докстринг `classify_failure_cause`), не как «инфраструктура».
Список сигнатур закрытый (`pulse_guard.INFRA_ERROR_SIGNATURES`) — этот
change его не расширяет (файл занят параллельными PR на момент правки).
Живая находка (отчёт PR #1136): дословный текст `gh` CLI «API rate limit
exceeded for installation» изначально НЕ совпадал ни с одной сигнатурой —
улика для #1115. Закрыто PR #1177 (слит раньше этой доводки): сигнатура
добавлена в `pulse_guard.py`, столбец «класс» теперь видит и этот случай
как инфраструктуру без правки этого модуля (контракт
`classify_failure_cause` не менялся — растёт только список сигнатур,
переиспользование безопасно).

## ADDED: Инвариант 20 — `continue-on-error` обязан иметь читателя (критерий 4 #1121)

Номер 20, не 17/18/19: к моменту разрешения конфликта этого PR с main
(сутки спустя мержа) номер 17 оказался занят параллельным #1076
(`check_frontend_deploy_stale`), 18 — уже существующим `check_pipeline_
status_marker_impersonation` (#1101) — оба слиты раньше этой доводки. 19
изначально казался свободным, но живой прогон `invariant_numbering.py
check` на следующей доводке (по триажу застрявших PR) нашёл коллизию с ещё
не смёрженным параллельным PR #1061/#925 (`check_ci_failure_closed_but_
main_red`), независимо занявшим тот же номер — переехал на первый реально
свободный, 20.

Требование: `repo_invariants.check_continue_on_error_readers` (файловый скан
`.github/workflows`, без сети) находит каждый `continue-on-error: true`
(шаг или job) и требует для него ЛИБО (a) принадлежности к
`DIGEST_WORKFLOWS` этого дайджеста — импорт, не вторая копия списка (канал
A читает аннотации, переживающие маскировку; канал B — условные шаги),
ЛИБО (b) записи в реестре `CONTINUE_ON_ERROR_READERS` с названием
конкретного механизма-читателя. Запись «читателя нет» в реестр внести
нельзя — только имя реального читателя или отсутствие записи (тогда это
нарушение). Неразбираемый YAML — отдельный класс нарушения `unreadable`:
непроверяемое состояние не имеет права выглядеть здоровым.

Требование: инвариант наблюдательный (не в `CI_GATING`) — включение
готовым долгом покрасило бы обязательную проверку у всех открытых PR;
газ — `GATING_RELEASE_CONDITION[20]`, снимается осознанной правкой
константы после того, как долг назван читателем или входит в
`DIGEST_WORKFLOWS`. Реестр защищён от протухания: каждый ключ
`CONTINUE_ON_ERROR_READERS` обязан указывать на живой шаг с
`continue-on-error: true` в реальном workflow этого репозитория.

## ADDED: Метка `soft-failure` в приоритете пула (критерий из чеклиста ревью PR #1136)

Требование: `soft-failure` входит в `BROKEN_LABELS` (`scripts/lib/
free_task.py`) — тот же уровень приоритета 0, что `ci-failure`/
`self-audit`: задача, заведённая дайджестом, сигнализирует «конвейер
деградирует прямо сейчас», а не рядовой долг на уровне 3 среди сотен
открытых issue.

## ADDED: Окно суточных метрик снимка — завершённые сутки, не «сегодня» (критерий 5 #1121)

Требование: метрики со семантикой «за сутки» (`merge_throughput` в
`pipeline_health.py`, `do_rows_read_pct` в `quotas.py`) считаются по
ЗАВЕРШЁННЫМ суткам UTC (`completed_utc_day`), не по календарным «сегодня»
— снимок здоровья снимается первым тиком пульса после полуночи (~00:06
UTC), когда «сегодня» ещё не накопило данных, и оба числа были
структурными нулями трое суток подряд (`health_regression` молчит: 0
против 0 — не регрессия). Поле `window_day` в снимке называет сутки,
за которые считана метрика, машинно (не совпадает с датой снятия).
Окно DO-метрики уходит параметром `rows_read_window` в
`quotas.collect_cloudflare` (фильтр `date_geq`+`date_leq`) — дефолт
«сегодня» у отчёта квот/`quota_watch` НЕ тронут: их семантика («сколько
сегодняшнего лимита уже выбрано») другая и намеренная, путать эти два
окна — не цель этой правки.

## Сценарии

Сценарий: worker.yml несёт аннотацию `warning` с текстом «dsh: NO_ADAPTER:
no adapter registered for provider "anthropic-pool"» на 4 прогонах подряд
за окно — группа (worker.yml, job «task», нормализованный текст) с count=4
над порогом — заводит задачу, если отпечатка ещё нет среди открытых
`soft-failure`.

Сценарий: шаг «Автооткат прода при красной канарейке/смоуке»
(`deploy-dsh-edge.yml`) — `skipped` в 3 прогонах, `success` в 1 за окно —
условный шаг, 1 запись в группе (workflow, job, «Автооткат прода...»,
success); ниже порога в этом объёме, но метод обнаружения сработал (сам
шаг не оставляет ни одной аннотации).

Сценарий: задача по классу X закрыта человеком после фикса; тот же класс X
возвращается через неделю — дедуп по открытым issues не находит совпадения
(старая задача закрыта) — заводится НОВАЯ задача, сигнал не потерян.

## ADDED: Частичный провал ВНУТРИ прочитанного workflow (находка ревью PR #1136, пятый круг, блокер 1)

Требование: «workflow целиком не прочитан» (список прогонов упал) и
«workflow прочитан, но чтение check-runs/jobs/аннотаций упало на части его
прогонов» — разные факты, оба обязаны быть НАЗВАНЫ в heartbeat'е (единственном
месте, которое гейт цикла читает гарантированно), не рассыпаться ⚠️-строками
step summary. `collect_window` считает такие частичные отказы ПО workflow
(`partial_reads_failed: dict[workflow, count]`, независимо от
`workflows_ok`/`workflows_read`) — `soft_failure_digest` передаёт их в
`mark_heartbeat(unread=...)` вместе с полностью непрочитанными workflow,
одним списком.

## ADDED: Эскалация по возрасту последнего успешного скана (находка ревью PR #1136, пятый круг, блокер 2)

Требование: внутренние отказы `escalate_groups` (список открытых
`soft-failure` issues, счётчик суточного потолка, само создание задачи,
чтение маркера потолка) печатаются с workflow-command-префиксом
`::warning::` (не эмодзи `⚠️`) — тот же приём, что уже применён к полному
провалу скана (третий круг): настоящая аннотация Checks API, которую канал A
этого же дайджеста способен поймать на следующем скане, а не тихая строка
step summary.

Требование: `escalate_stale_scan` — отдельная эскалация ПО ВОЗРАСТУ
последнего успешного heartbeat'а (`DIGEST_HEARTBEAT_MARKER`), не по факту
конкретного внутреннего отказа: скан не выполнялся успешно дольше
`STALE_SCAN_THRESHOLD_HOURS` (2×`DIGEST_INTERVAL_HOURS`) — эскалация в
issue-статус + Telegram, раз в календарный день (свой маркер
`STALE_SCAN_MARKER`, тот же приём, что `SOFT_FAILURE_CAP_MARKER`). Вызывается
ПЕРВЫМ в `soft_failure_digest`, ДО гейта цикла и квота-гейта — иначе
устойчивое исчерпание квоты держало бы оба гейта в состоянии «пропускаю»
бесконечно, и застой самого дайджеста никогда бы не сообщился. Ни одного
heartbeat'а в истории вовсе (первый скан ещё не случился, либо деградация
старше окна чтения маркеров) — не эскалируется: неотличимо от «только что
заведён», алерт не гадает.

## MODIFIED: Инвариант 20 видит не только литеральный `true` (некритичная находка ревью PR #1136, пятый круг)

Требование: `check_continue_on_error_readers` засчитывает `continue-on-error`
активным при ЛЮБОМ значении, кроме `False`/отсутствия ключа (`None`), не
только при буквальном YAML `true` — форма `continue-on-error: "${{ … }}"`
(GitHub Actions вычисляет выражение в рантайме, PyYAML отдаёт обычную строку)
или строка `'true'` в кавычках больше не выпадают из проверки молча.
