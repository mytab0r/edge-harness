# Дельта-спека: журнал (journal-tasks-hands) — доводка ai:changes-requested лечит Исходы 2/3 бонус-заходом, не эскалацией (#1274)

Опирается на существующие требования `dispatch_ai_review_rework`
(`ai-rework-age-fairness`, archived, issue #1253/#1260 — сортировка очереди,
развязка эскалации от занятости воркера, признак «исход собственного
прогона ещё не известен») и на исходный контур (issue #1027, без
собственной дельта-спеки). Эта дельта меняет ТОЛЬКО обработку Исходов 2 и 3
после исчерпания бюджета (`attempts >= AI_REWORK_MAX_ATTEMPTS`) и окно
поиска атрибуции — остальные требования тех change (сортировка, развязка,
признак терминальности статуса, инвариант 22) не меняются.

## MODIFIED: Окно поиска атрибуции расширяется якорем диспатча

Реализация: `scheduler.py::last_worker_run(repo, task_number, *,
since=None)`, `pulse_guard.py::recent_runs(..., page=None)`,
`pulse_guard.LAST_RUN_LOOKUP_PAGES = 5`.

Требование: `last_worker_run` без `since` (по умолчанию `None`) сохраняет
старое поведение — последние 10 прогонов `worker.yml`
(`recent_runs(..., per_page=10)`). С `since` (нижняя граница — обычно
момент последнего диспатча авто-доводки на этом отпечатке,
`ai_rework_dispatched_at`) поиск идёт постранично, по 100 прогонов на
страницу, пока не будет пройдена ровно одна из двух границ:

- найден прогон, атрибутированный задаче — возвращается
  немедленно, дальнейшие страницы не запрашиваются;
- очередная страница целиком старше `since` (`created_at` последнего —
  самого старого — элемента страницы меньше `since`) — поиск прекращается,
  атрибуции в этом окне нет;
- либо пройдено `pulse_guard.LAST_RUN_LOOKUP_PAGES` страниц (потолок — 500
  прогонов, при серийном слоте `worker.yml` это 15-27 суток истории,
  AGENTS.md: ~18-33 прогона/сутки) без совпадения по любой из первых двух
  причин — поиск прекращается, атрибуции нет.

Требование (цена чтения, блокирующая находка ai-review PR #1276 — класс
«цена читателя не должна расти с историей задачи», #1100/#607): след аренды
ВСЕЙ страницы лежит в одном и том же списке комментариев задачи, поэтому
постраничный поиск читает историю комментариев задачи ОДИН раз на страницу
(`run_claimed_in_comments` — матчинг готового списка), не на каждый прогон
страницы (`run_claimed_task` остаётся для одиночных потребителей). Без этого
потолок чтений одного решения — 500 фетчей истории задачи вместо прежних 10.

`dispatch_ai_review_rework` вызывает `last_worker_run` ВСЕГДА с якорем
(`since=ai_rework_dispatched_at(...)`) — фиксированные 10 записей в этом
call site больше не используются.

`dispatch_conflict_rework::last_worker_run_conclusion` и
`resume_series_by_merge` продолжают вызывать `last_worker_run` БЕЗ якоря
(старое поведение, 10 записей) — эта дельта их не меняет.

Сценарий: диспатч авто-доводки на отпечатке произошёл в момент T, между T и
моментом перепроверки прошло 43 прогона `worker.yml` по ДРУГИМ задачам —
искомый прогон (клеймящий текущую задачу, `created_at` близко к T) НЕ входит
в последние 10 записей `recent_runs`, но входит в страницу 2 расширенного
поиска (100 записей на странице, целевой прогон там) -> `last_worker_run(...,
since=T)` возвращает его, честный `conclusion` (например, `'failure'`)
используется решением, вместо ложного `None`.

## MODIFIED: Исход 2 (успешный прогон, отпечаток не изменился) — один бонус-заход перед эскалацией

Реализация: `scheduler.py::dispatch_ai_review_rework`, ветка
`run_conclusion == "success"`; маркеры `pulse_guard.
AI_REWORK_SECOND_CHANCE_MARKER`, `pulse_guard.AI_REWORK_REBUTTAL_MARKER`.

Требование: первое обнаружение `run_conclusion == "success"` на исчерпанном
бюджете НЕ эскалирует. Вместо этого код проверяет маркер
`{AI_REWORK_SECOND_CHANCE_MARKER} fp:{fingerprint}` в комментариях PR
(полная история, без ограничения по времени). Если маркер ещё не стоял —
код публикует ОДИН комментарий, несущий ОДНОВРЕМЕННО: `AI_REWORK_MARKER
fp:{fingerprint}` (дедуп-анкер, как у обычного дисПатча), сам
`AI_REWORK_SECOND_CHANCE_MARKER fp:{fingerprint}` и явный контракт прозой —
прочитать последний вердикт ai-review и весь тред PR; если согласен —
исправить и запушить новый коммит; если НЕ согласен — оставить отдельный
комментарий, НАЧИНАЮЩИЙСЯ с маркера `AI_REWORK_REBUTTAL_MARKER`, с причиной;
молчание при несогласии не годится. Затем следует обычный адресный дисПатч
`worker.yml` (снятие assignee/замка, `inputs[task]`) — задание доставляется
БЕЗ правки `task.sh`/`worker.yml`: режим доводки уже инструктирует агента
прочитать `gh pr view --comments` целиком, новый комментарий орке­стратора
входит в этот же тред.

Требование: второе подряд обнаружение `run_conclusion == "success"` на ТОМ
ЖЕ отпечатке (маркер `AI_REWORK_SECOND_CHANCE_MARKER` для этого
`fingerprint` уже стоит) — законная эскалация. Текст обязан:

- называть факт «worker.yml отработал успешно ВТОРОЙ раз подряд на этом
  отпечатке (второй заход нёс явное требование исправить находку или
  возразить), отпечаток диффа снова не изменился»;
- если агент оставил возражение — процитировать его дословно (до 400
  символов). Возражение — комментарий PR, опубликованный не раньше момента
  бонус-дисПатча, ПОХОЖИЙ на начинающийся с `AI_REWORK_REBUTTAL_MARKER`
  (`rebuttal_is_genuine`: маркер возражения встречается в теле не позже
  маркера дисптча `AI_REWORK_MARKER`, а лучше — вовсе без него). Блокирующая
  находка ai-review PR #1276: прежний фильтр «в теле НЕТ
  `AI_REWORK_MARKER`» выбрасывал подлинное возражение, цитирующее
  комментарий-дисПатч, — цитата несёт маркер дисптча, хотя сам комментарий
  начинается с маркера возражения, как и требует контракт; логином автора
  различать нельзя (все агенты — один логин, AGENTS.md «Атрибуция
  событий»), телом — можно, контракт письма фиксирован;
- если возражения нет — честно сказать «без объяснения (агент не оставил
  возражения)», не молчать об этом факте и не изобретать причину.

Требование (fail loud, там же): если чтение возможных возражений упало
(`RuntimeError`), решение откладывается до следующего прохода с
наблюдением — молча идти к эскалации с «без объяснения» значило бы
утверждать непроверенный факт.

Сценарий: PR несёт `ai:changes-requested`, бюджет доводки исчерпан
(`attempts >= AI_REWORK_MAX_ATTEMPTS`), последний прогон `worker.yml`
атрибутирован и завершён `conclusion='success'`, маркер
`AI_REWORK_SECOND_CHANCE_MARKER` для текущего `fingerprint` в комментариях
PR отсутствует -> дисПатч `worker.yml` (задача освобождается), комментарий
несёт контракт «исправь или возрази», эскалации нет.

Сценарий (продолжение): следующий проход планировщика видит тот же
`fingerprint` (отпечаток не изменился), последний прогон снова `success`,
маркер `AI_REWORK_SECOND_CHANCE_MARKER` уже стоит -> эскалация, текст
называет «ВТОРОЙ раз подряд», ищет возражение агента.

## MODIFIED: Исход 3 (атрибуции нет) — один бесплатный повтор перед эскалацией, эскалация называет дефект атрибуции

Реализация: `scheduler.py::dispatch_ai_review_rework`, ветка
`run_conclusion is None`; маркер `pulse_guard.
AI_REWORK_UNATTRIBUTED_RETRY_MARKER`.

Требование: первое обнаружение `run_conclusion is None` (расширенное окно
поиска, см. выше, честно не нашло атрибуции) на исчерпанном бюджете НЕ
эскалирует. Код проверяет маркер `{AI_REWORK_UNATTRIBUTED_RETRY_MARKER}
fp:{fingerprint}` в комментариях PR; если не стоял — публикует его (в том же
комментарии, что и `AI_REWORK_MARKER`) и выполняет ОБЫЧНЫЙ адресный дисПатч,
как при инфраструктурном отказе Исхода 1 (бюджет НЕ засчитывается — тот же
довод: попытка, о которой нет доказательства, что она была честной пробой
находок, не должна списываться с бюджета эскалации).

Требование: второе подряд обнаружение `run_conclusion is None` на ТОМ ЖЕ
отпечатке (маркер уже стоит) — законная эскалация, НО не раньше, чем
завершился собственный бонусный повтор (блокирующая находка ai-review
PR #1276 — класс «эскалация-до-итога-прогона», та же дверь, что #1260):
бонусный повтор по конструкции не оставляет следа аренды, значит дефер
`status != "completed"` по атрибутированному прогону его не видит. Пока
существует прогон `worker.yml`, начавшийся не раньше времени маркера повтора
и ещё не завершённый (`unattributed_retry_in_flight`; атрибуция тут
невозможна по определению ветки — «наш ли это повтор» различается
единственным доступным фактом, временем), решение откладывается с
наблюдением, не эскалирует. Газ дефера — тот же факт, что и тормоз: прогон
завершился → следующий проход разбирает итог этой же веткой (появился след —
исход решён по нему; следа нет — законная эскалация дефекта атрибуции).

Текст эскалации ОБЯЗАН называть
дефект атрибуции («ДВА прогона worker.yml подряд не оставили следа аренды
даже в расширенном окне поиска… проверь вручную, шёл ли вообще прогон
worker.yml по задаче #N за это время и почему он не оставил следа»), а НЕ
«посмотри находки ai-review» — находки в этом сценарии, возможно, никто не
читал, вопрос не в них.

Требование (цена чтения, некритичная находка ai-review PR #1276): проба
`pending_unattributed_retry` и ветка Исхода 3 читают ОДИН и тот же маркер
повтора — прочитанное пробой переиспользуется, второго чтения комментариев
PR нет.

Требование: проверка входа в решающую ветку («бюджет исчерпан ИЛИ уже
висит непогашенный маркер бонусного повтора Исхода 3») не сводится к
`attempts >= AI_REWORK_MAX_ATTEMPTS`. Бонусный повтор Исхода 3 по
определению не оставляет `WORKER_GIT_STEP_MARKER` (это и есть «атрибуции
нет»), а `ai_rework_attempts` считает попытки ИМЕННО по этому маркеру —
после бонусного повтора `attempts` остаётся `0` независимо от того, сколько
раз повторился тот же исход. Без отдельной проверки (`pending_unattributed_
retry`: `attempts < AI_REWORK_MAX_ATTEMPTS` И маркер `AI_REWORK_
UNATTRIBUTED_RETRY_MARKER` для текущего `fingerprint` уже стоит) код
диспатчил бы новый заход бесконечно, никогда не доходя до эскалации.

Сценарий: PR несёт `ai:changes-requested`, бюджет исчерпан, расширенный
поиск атрибуции (все доступные страницы, вся история якоря) не находит НИ
ОДНОГО прогона, клеймящего задачу, маркер `AI_REWORK_UNATTRIBUTED_RETRY_
MARKER` для текущего `fingerprint` отсутствует -> дисПатч `worker.yml`,
комментарий несёт маркер и текст «повтор — прошлый прогон не оставил следа
аренды…», эскалации нет.

Сценарий (продолжение): следующий проход — тот же `fingerprint`, поиск
атрибуции снова возвращает `None` (ни один прогон, включая бонусный,
никогда не отметился git-шагом), маркер уже стоит, бонусный повтор уже
ЗАВЕРШИЛСЯ (нет незавершённого прогона после маркера) -> эскалация с текстом
про дефект атрибуции, а не про находки. Пока же после маркера есть
незавершённый прогон — тот же проход откладывает решение с наблюдением
(«не завершился»), не эскалирует.

## Что не меняется

Исход 1 (`conclusion in FAILURE_CONCLUSIONS`, автоповтор без эскалации,
#1027), признак «исход собственного прогона ещё не известен» (`status !=
"completed"`, #1253), сортировка очереди по возрасту (#1253), развязка
эскалации от занятости воркера (#1253), ветка `else` (атрибутированный
`conclusion` вне `FAILURE_CONCLUSIONS` и не `'success'` — `timed_out`/
`startup_failure`, эскалирует с первого раза без бонус-захода) — не
предмет этой дельты.
