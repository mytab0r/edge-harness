# Design: детектор регрессии здоровья конвейера, привязанный к слиянию

## Ревизия 2 (критик, отдельная сессия ревью PR #970) — сводка

Критик прогнал этот код на реальных данных и нашёл две группы дефектов,
обе исправлены (детали — соответствующие разделы ниже):

1. **Мотивирующее утверждение §1/§5 было ложным.** Первая версия
   утверждала «`pulse_guard` не поймал регрессию, потому что успехи изредка
   вклинивались и не давали счётчику подряд идущих отказов взвестись». По
   журналу #120 это неверно: предохранитель (`WORKER_FAILURE_PAUSE_AFTER=3`)
   СРАБОТАЛ на третьем подряд отказе (03:09:34Z = мерж+4ч15м, раньше этого
   детектора) и был трижды в ту же ночь погашен `RESUME_MARKER`
   (`scheduler.resume_series_by_merge`) слияниями ТРЁХ РАЗНЫХ задач
   (#862/#409/#344) — предохранитель сработал СТРОГО по своему контракту
   («слияние задачи, над которой шёл красный прогон, чинит причину серии»);
   контракт просто структурно не может увидеть регрессию класса #878, где
   сломан не конкретный прогон/задача, а сам критерий успеха, общий для ВСЕХ
   задач. Вывод: этот детектор нужен как ДОПОЛНЕНИЕ (агрегат по всем
   прогонам, игнорирующий границы задач — то, чего предохранитель, привязанный
   к задаче, не может в принципе), не замена. Открытая, вне рамок этого
   change работа над самим предохранителем — issue #972.
2. **Пороги v1 были нерабочими.** Относительное отклонение recent-окна от
   соседнего baseline (пороги — импорт `health_regression.py`) дало 17
   ложных срабатываний из 41 здорового часа (41%) на реальной истории
   `worker.yml`: baseline этого репозитория хронически ~48-50%, не
   благополучные 90%+, поэтому относительное отклонение тонет в шуме.
   Заменено на АБСОЛЮТНЫЙ порог recent-rate, свои константы (не импорт —
   «смысл» отклонения для суточных снимков и часовых прогонов разный).
   На независимой кросс-проверке (119 часовых тиков) — 6 ложных из 119
   (5.0%), поимка #878 сохранена (+7ч, было +5ч на нерабочих порогах v1).
   `baseline` остался в `Verdict` только как контекст отчёта, решение
   `fire`/`ok` от него больше не зависит — снимает и риск самозаглушения
   (baseline-окно, вобравшее сам инцидент, больше не размывает решение).

Разделы §2/§4/§6 ниже переписаны под ревизию 2.

## 1. Достаточен ли нынешний набор метрик? (проверка, не гипотеза)

`scripts/measure/pipeline_health.py::worker_success_rate` уже существует и
измеряет ровно ту величину, которую владелец спросил («была бы видна доля
успешных прогонов воркера?») — но снимается РАЗ В КАЛЕНДАРНЫЕ СУТКИ
(`should_snapshot` — гейт «не чаще раза в сутки», design.md архивного change
`pipeline-health-self-audit`, §2.2) на COUNT-окне (`WORKER_SUCCESS_WINDOW=30`
последних прогонов, не по времени). `health_regression.py::classify_metric`
дополнительно требует streak ≥ `MIN_REGRESSION_STREAK_DAYS=3` ДНЕЙ подряд и
минимум `MIN_SAMPLES_FOR_BASELINE=5` снятых точек истории.

Ответ на прямой вопрос владельца: **нет, недостаточен для класса регрессии
#878.** Причины две, независимые:

1. Даже если бы снимок случился в идеальный момент (сразу после инцидента),
   для перехода `insufficient_data` → `regression` потребовалось бы 3 дня
   подряд деградации ПОСЛЕ того, как накопится 5 точек истории — на дату
   инцидента (2026-09-10/11) истории снимков практически не существовало.
2. Даже без streak-порога, снимок раз в сутки в лучшем случае ловит
   регрессию на СЛЕДУЮЩИЕ сутки — для инцидента, который начался в 22:54 и
   был обнаружен человеком в 08:xx (~9ч), это опоздание того же порядка, что
   и обнаружение человеком, никакого выигрыша.

Вывод: не нужен НОВЫЙ снимаемый-и-хранимый показатель — нужна ДРУГАЯ
частота вычисления УЖЕ существующей величины. `pipeline_health.collect()`
technически может быть вызван чаще, но снимок пишет строку JSONL на
git-ветку — 96 записей/сутки вместо одной прямо противоречит документированному
мотиву гейта (design.md архивного change: «иначе пульс писал бы новую строку
каждые 15 минут»). Решение здесь — НЕ трогать снимок вовсе, а считать
time-boxed (не count-window) success-rate НА ЛЕТУ прямо в момент проверки,
без записи истории: источник (Actions API) сам по себе всегда свежий.

### Почему не расширять набор до 4-5 метрик, а добавить одну

Владелец просил 3-5 метрик с обоснованием каждой. Здесь — ОДНА новая
величина (time-boxed worker success-rate), потому что она — единственная из
существующего набора, которая (а) прямо измеряет заявленный симптом (доля
успешных прогонов воркера) и (б) физически может считаться из уже читаемых
данных без нового источника. Остальные 5 метрик набора (`merge_throughput`,
`pr_age_p95`, `backlog_total`, `pulse_cadence_ratio`, `do_rows_read_pct`)
измеряют другие классы деградации (пропускная способность очереди, возраст
PR, стоимость DO) — ни один физически не двинулся бы в ответ на регрессию
#878 (сам факт открытия PR воркером не изменился, изменилась только оценка
успеха ЭТОГО прогона) — добавлять их в это rolling-сравнение было бы
раздуванием без пользы, ровно то, от чего владелец предостерёг.

## 2. Алгоритм детектора (ревизия 2 — абсолютный порог, не относительное отклонение)

```
recent = success-rate(worker.yml, [now - OBSERVATION_WINDOW_HOURS, now))
baseline = success-rate(worker.yml, [now - OBSERVATION_WINDOW_HOURS - BASELINE_LOOKBACK_HOURS,
                                      now - OBSERVATION_WINDOW_HOURS))   # только контекст отчёта
insufficient_data — recent_n < MIN_SAMPLES_RECENT
fire               — recent_rate <= FIRE_RATE_THRESHOLD_PCT (10.0%) И recent_n >= MIN_SAMPLES_RECENT (5)
ok                 — иначе
```

Только ДВА решающих исхода (`fire`/`ok`) плюс честный `insufficient_data` —
промежуточный `regression` из v1 сознательно снят: свип показал, что более
мягкий порог (например, recent<=25%) добавляет 12 ложных из 41 (29%) без
проверенной пользы.

`baseline` вычисляется и несётся в `Verdict` ТОЛЬКО для текста отчёта
(человеку для сравнения) — в решении `fire`/`ok` не участвует. Пороги —
СВОИ константы этого модуля, НЕ импорт из `health_regression.py`: v1
заявляла «регрессия и пожар в одном репозитории значат одно и то же
отклонение независимо от того, суточный это снимок или часовое окно» — это
оказалось ложным заявлением на реальных данных (см. «Ревизия 2» выше):
относительное отклонение от соседнего baseline для суточных снимков и
часовых прогонов — разные статистики с разными свойствами шума.

### Почему окна именно такой длины (эмпирически, свип на реальной истории)

- `OBSERVATION_WINDOW_HOURS = 8` — свип диапазона 4/6/8/10/12ч даёт лучший
  баланс между шумом на здоровых данных (5.0% ложных на 119 тиках при 8ч) и
  скоростью поимки #878 (+7ч при 8ч, против «никогда» при 12ч — окно шире
  инцидента размывает recent-rate ниже порога недостаточно).
- `FIRE_RATE_THRESHOLD_PCT = 10.0` — свип диапазона 0-10% дал одинаковый
  результат на контрольном окне критика (FP=1/41, детект +7ч); порог поднят
  от строгих 0% до 10% ради небольшого запаса без изменения этих свойств.
- `MIN_SAMPLES_RECENT = 5` — свип `min_recent=5` даёт 13 ложных на здоровом
  119-тиковом окне из старой (широкой) выборки; `min_recent=8` убирает
  срабатывание на #878 вовсе («никогда») — 5 выбран как минимум, ещё
  сохраняющий поимку инцидента.
- `BASELINE_LOOKBACK_HOURS = 72` (контекст отчёта, не решение) — длиннее
  наблюдательного, чтобы редкий всплеск успехов/провалов не считался
  «нормой», короче недели — цикл разработки этого конвейера явно быстрее
  недельного (десятки слияний в сутки).
- `ATTRIBUTION_LOOKBACK_HOURS = 2 * OBSERVATION_WINDOW_HOURS` (16ч) — окно
  поиска подозреваемых слияний ПЕРЕД `now`, шире recent-окна, потому что
  слияние непосредственно ПЕРЕД началом recent-окна тоже могло вызвать
  наблюдаемое падение (эффект целиком лежит внутри recent-окна, момент
  слияния — чуть раньше его границы).

Честно: свип по всему разумному пространству порогов ОТНОСИТЕЛЬНОГО дизайна
v1 (observation 6-12ч, baseline 72ч, min_samples 3-10, оба порога 50%/100%
из `health_regression`) НИ ОДНОЙ комбинации не дал одновременно приемлемый
шум И своевременную поимку #878 — само семейство «относительное отклонение
от baseline» не годилось для этой статистики, не только конкретные числа
внутри него (независимая проверка issue #967, помимо контрольного окна
критика).

## 3. Подозреваемые — почему список, а не один PR (проверено на реальных числах)

Дословный вывод `gh api search/issues` (снято 2026-09-11, ревизия 2: окно
атрибуции теперь `2 * OBSERVATION_WINDOW_HOURS = 16ч`, а не 12ч из v1) для
окна 2026-09-10T13:54:34Z..2026-09-11T05:54:34Z (16ч, `now` = мерж #878 +7ч,
момент первого `fire` по §4) — ПЯТНАДЦАТЬ слияний, не шесть, как заявляла v1
(v1 считала по вдвое узкому окну 12ч и, отдельно, недосчитала фикстуру —
критик получил на эквивалентном запросе 15 PR, не 6): #872, #771, #895,
#890, #903, #640, #878, #893, #862, #412, #409, #922, #921, #344, #617 (по
времени слияния). Ручная попытка исключить «невиновных» через сравнение
собственного pre-merge окна каждого PR с baseline (design.md, «эвристика
предикейтс») даёт неустойчивый результат при таком каденсе: например, #640
слит за 48 минут до #878 — их СОБСТВЕННЫЕ окна «после» почти целиком
совпадают с одним и тем же набором прогонов, различить их по чистой
временной корреляции невозможно НИКАКОЙ статистикой без анализа содержимого
диффа. Решение: детектор называет всех пятнадцать, явной строкой «корреляция
по времени, НЕ причинность» — честно, не изображая точность, которой нет.

**Вывод: детектор поймал бы регрессию #878 через 7 часов после слияния** — на

`fire` не позднее 8-го часа. Медленнее, чем нерабочие пороги v1 заявляли
(5ч), но с многократно лучшим соотношением сигнал/шум — относительный
дизайн v1 давал 17 ложных из 41 здорового часа (41%), этот — 6 из 119

слияния, вперемешку с первыми провалами; недостаточная выборка (0-4ч) и
`ok` при recent-rate выше 10% (5-6ч) — оба честные исхода, не дефект. Цена
`OBSERVATION_WINDOW_HOURS=8`: чуть медленнее реагирует, зато не тонет в
шуме единичных прогонов (свип §2 показал, что уже, скажем, 12ч не ловит
инцидент вовсе — баланс, а не идеал).

## 5. Реакция на регрессию — три варианта, выбор и почему

Владелец назвал три варианта и попросил обосновать выбор, ориентируясь на
уже работающий образец (`deploy-dsh-edge.yml`: канарейка красная → `wrangler
rollback` → повторная канарейка подтверждает откат → эскалация).

**(a) Авто-revert подозреваемого PR.** Отвергнуто для ЭТОГО класса
регрессии. Образец `deploy-dsh-edge.yml` откатывает ДЕПЛОЙ (артефакт с
доказанно рабочей предыдущей версией — предыдущий деплой уже прошёл
канарейку) на предыдущую версию, про которую ИЗВЕСТНО, что она работала.
У регрессии класса #878 такой гарантии нет: откат кода вернул бы систему в
состояние ДО #878 — то есть вернул бы баг, который #878 как раз чинил
(воркер засчитывал успех по чужому предсуществующему PR, класс #876). Хуже
того, при нескольких подозреваемых (§3, шесть PR в окне) авто-revert должен
был бы выбрать ОДИН — то есть либо гадать (запрещено «Алерт не гадает»),
либо откатывать ВСЕ шесть, из которых минимум четыре, вероятно, невиновны.
Технически применим тот же приём (`if: failure() && ...`, `continue-on-error`,
подтверждение результата после действия) — но не сюда, там, где «предыдущая
версия была доказанно рабочей», не там, где «предыдущее ПОВЕДЕНИЕ конвейера
было доказанно рабочим» (это не одно и то же для эволюционирующего критерия
успеха).

**(b) Задача высшего приоритета с адресным расследованием.** Выбрано.
Механизм приоритета уже существует и используется по назначению
(`free_task.py::issue_priority_key`, `area:process` — тир 1, «задача меняет
правила/механику совместной работы... приёмка после мержа» — расследование
регрессии критерия успеха воркера подпадает под это определение буквально).
Следующий свободный воркер берёт такую задачу РАНЬШЕ обычных задач пула, без
второй инфраструктуры приоритета. «Адресный диспатч» (прямой
`workflow_dispatch worker.yml -f task=N`) сознательно НЕ реализован —
это территория `scheduler.py` (диспетчер задач воркера), которую эта задача
не вправе трогать (issue #967, граница территории); тир-1 приоритет уже даёт
пикап на следующем тике оркестратора (каденс 15 мин) — тот же порядок
скорости, что прямой диспатч, без второго пути дублирования диспетчера.

**(c) Временное отключение затронутого механизма.** Отвергнуто для ЭТОГО
случая по той же причине, что (a): «затронутый механизм» здесь — сам
критерий успеха воркера (`dsh_worker_run_is_success`, #878). Отключить его —
значит вернуться к permissive-критерию ДО #878, то есть к исходному багу.
Не общее правило «(c) всегда плохо» — для ДРУГОГО класса регрессии (например,
внешний провайдер начал массово таймаутить, конвейер отвечает штатно) временно
выключить зависящий от него шаг было бы разумно; здесь неприменимо структурно.

### Газ и защита от цикла (обязательное требование владельца)

- **Газ.** Критерий готовности задачи-расследования — следующий прогон
  детектора видит `ok` по тому же окну (метрика вернулась к baseline);
  задача закрывается ЧЕЛОВЕКОМ/агентом по факту фикса, НЕ автоматически —
  тот же принцип, что уже принят у `health_audit.py` (design.md архивного
  change, §4: «критерий готовности — метрика вернулась к baseline,
  проверяется следующим снимком, не декларацией исполнителя»), не новое
  решение.
- **Защита от цикла.** Реакция этого детектора — создание/комментирование
  issue и отправка сообщения (Telegram/issue-комментарий). НИ ОДНО из этих
  действий не порождает git-событие (push/merge) — физически не может
  повторно триггернуть сам себя или другой автоматический откат. Это СИЛЬНЕЕ
  защиты, которую несёт образец `deploy-dsh-edge.yml` (там `wrangler
  rollback` — тоже не git-операция, но деплой воркера теоретически мог бы
  среагировать на что-то ещё; здесь такого риска нет вовсе по конструкции
  канала).

## 6. Дедуп и потолок алертов (не спам при затянувшемся инциденте)

Ревизия 2 (критик): дедуп по отпечатку `merge-health:worker_success_rate:
<календарный час>` был мёртв в проде — cron `17 * * * *` даёт ровно один
прогон в календарный час, значит ветка «комментарий в существующую задачу»
никогда не исполнялась бы (второй прогон того же часа физически не
случается), а собственный тест v1 кормил `_fingerprint` тем же `now`, что и
создание задачи — тестировал несуществующий сценарий. Тот же класс уже
оплачен: `pulse_guard.py` документирует `FAILURE_WATCH_DAILY_CAP=5` именно
потому, что дедуп без суточного потолка «плодил бы задачи в пул» (живые
дубли #578/#580/#589/#592/#598).

Исправлено: отпечаток `merge-health:worker_success_rate` ФИКСИРОВАННЫЙ, без
временнОй составляющей — один открытый PR-расследование на ВЕСЬ инцидент,
сколько бы часов он ни длился, повторный `fire` в любой последующий час
комментирует ту же задачу (не заводит вторую). Дедуп самого комментария
(не завести улику дважды за один календарный день) — через
`pulse_guard.issue_marker_times`, тот же приём, что у остального конвейера.
Отдельно — суточный потолок `MERGE_HEALTH_DAILY_CAP=3` НА СОЗДАНИЕ новых
задач этим механизмом (`_tasks_created_since`, тот же приём, что
`health_audit.audit_tasks_created_since` — считает по факту СОЗДАНИЯ, не
текущей открытости) — свой счётчик, не общий с `pulse_guard.
FAILURE_WATCH_DAILY_CAP` (разные источники задач, design.md, «Пересечение
с существующими детекторами» — эта область не пересекается с
failure_watch/self-audit). Эскалация (issue #120 + Telegram) не имеет
отдельного дедупа сверх этого — при активном инциденте владелец
предпочитает частые сигналы редким пропущенным (тот же выбор, что у
`pulse_guard.escalate` в остальном конвейере).

## Не подтверждено

1. Пороги `OBSERVATION_WINDOW_HOURS`/`FIRE_RATE_THRESHOLD_PCT`/
   `MIN_SAMPLES_RECENT`/`BASELINE_LOOKBACK_HOURS`/`ATTRIBUTION_LOOKBACK_HOURS` —
   выбраны эмпирически свипом на истории ОДНОГО реального инцидента (#878) и
   проверены на здоровых окнах 41ч/119ч (2.4%/5.0% ложных, независимо
   воспроизведено при ревью PR #970), не выведены статистически из
   множества независимых регрессий — такой истории физически не существует.
   Подбор по факту следующих инцидентов — отдельная, не сделанная здесь
   работа (тот же честный статус, что и у порогов `health_regression.py`).
2. Эвристика исключения «невиновных» подозреваемых по их собственному
   pre-merge окну — рассмотрена и НЕ реализована (§3): на реальных числах
   этого репозитория даёт неустойчивый результат. Если понадобится точнее —
   нужен анализ содержимого диффа (какие файлы/пути мог задеть каждый PR),
   которого этот детектор сегодня не делает и не пытается имитировать.
3. Связь конкретного прогона `worker.yml` с конкретным диапазоном коммитов
   PR (не только с фактом «слияние произошло раньше по времени») — Actions
   API такого поля не даёт напрямую; не выдумано, не реализовано.
4. Частота срабатывания `RESUME_MARKER` как альтернативный/дополняющий
   сигнал того же класса регрессии (см. «Ревизия 2» выше) — рассмотрена,
   не реализована здесь, вынесена в issue #972 (территория `pulse_guard.py`/
   `scheduler.py`, занятая параллельным PR #950 на момент находки).
