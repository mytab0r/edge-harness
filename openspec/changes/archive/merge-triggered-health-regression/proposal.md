# Proposal: детектор регрессии здоровья конвейера, привязанный к слиянию (часы, не сутки)

Задача: #967. Реализация design.md ниже, разбивка — tasks.md рядом.

## Summary

Владелец 2026-09-11: «В чём проблема сделать её саморазвивающейся?» —
установленный ответ: у системы нет функции оценки себя и нет отката по ней.
Развитие — цикл «изменил себя → измерил → закрепил/откатил». Первое звено
(агенты пишут фиксы) работает, второго и третьего не было.

Живое доказательство необходимости — не гипотеза: PR #878 (слит
2026-09-10T22:54:34Z, задача #876) ужесточил критерий успеха воркера.
Прошёл ревью/тесты/слияние и превратил рабочие прогоны в ложно-красные —
`worker.yml` за 72ч до слияния показывает 39/82 успешных (47.6%), за первые
6ч после — 0/5 (0%). Регрессию заметил человек утром, ~9ч спустя.

Ревизия 2 (критик, отдельная сессия ревью PR #970): первая версия этого
абзаца утверждала «`pulse_guard` не поймал, потому что успехи изредка
вклинивались и не давали счётчику подряд идущих отказов взвестись» — это
было ФАКТИЧЕСКИ НЕВЕРНО, проверено по журналу #120: предохранитель
(`WORKER_FAILURE_PAUSE_AFTER=3`) СРАБОТАЛ на третьем подряд отказе
(03:09:34Z = мерж+4ч15м) и был трижды в ту же ночь погашен
`scheduler.resume_series_by_merge` (`RESUME_MARKER`) слияниями ТРЁХ РАЗНЫХ
задач (#862/#409/#344) — предохранитель работал строго по своему контракту
(«слияние задачи, над которой шёл красный прогон, чинит причину серии»),
просто этот контракт структурно не видит регрессию класса #878: сломан не
конкретный прогон/задача, а сам критерий успеха, общий для ВСЕХ задач —
только взгляд, агрегирующий по всем прогонам независимо от задачи (то, что
считает этот механизм), может увидеть такой узор. Открытая, вне рамок этого
change работа над самим предохранителем — issue #972 (частота
`RESUME_MARKER` за короткое окно как более узкий и дешёвый сигнал того же
класса; территория `pulse_guard.py`/`scheduler.py` занята параллельным PR
#950 на момент находки).

Существующий суточный снимок `pipeline_health.py`/`health_regression.py`
(openspec/changes/archive/pipeline-health-self-audit) тоже не поймал
регрессию — снимок гейтован «не чаще раза в календарные сутки UTC», по
построению не мог бы среагировать быстрее чем на следующий день, а
`MIN_SAMPLES_FOR_BASELINE=5` снятых ДНЕЙ на дату инцидента ещё не набрался.
Фикс (#937/#935) на момент подачи этого предложения ещё не слит — регрессия
остаётся живой.

Этот change добавляет второе и третье звено цикла для КОНКРЕТНОГО класса
регрессии — падение доли успешных прогонов `worker.yml`, привязанное по
времени к недавнему слиянию: (1) метрика, движущаяся в пределах часов, а не
суток; (2) детектор, сравнивающий «до» и «после» относительно окна слияний и
называющий подозреваемых по имени, не гадающий одного; (3) реакция —
задача-расследование высшего приоритета через уже существующий механизм
приоритезации (`area:process`), не второй канал.

## Problem / motivation

- Суточный снимок ловит регрессию не быстрее чем через сутки-двое (гейт
  `should_snapshot` + streak `MIN_REGRESSION_STREAK_DAYS=3` у существующего
  `health_regression.py`) — для класса регрессии «сломан сам критерий успеха
  воркера» это слишком поздно: за это время воркер успевает потерять десятки
  реальных прогонов, каждый из которых ложно закрывается провалом.
- `pulse_guard`'s предохранитель СРАБОТАЛ (см. Summary, ревизия 2), но был
  трижды погашен `RESUME_MARKER` разных задач за ту же ночь — контракт
  предохранителя привязан к ЗАДАЧЕ, чинить общесистемный критерий успеха
  структурно не может (issue #972, вне рамок этого change). Ни `stall_detector`,
  ни `upstream_drift` тоже не видят этот класс: метрика здоровья
  (`pipeline_health.py`) не снята достаточно часто, чтобы суточная регрессия
  успела набрать streak.
- У репозитория уже есть образец рабочего автоотката (`deploy-worker.yml`
  через `deploy-dsh-edge.yml`: канарейка красная после деплоя → `wrangler
  rollback` → повторная канарейка подтверждает откат → эскалация). Для
  класса «критерий успеха самого конвейера» тот же приём (откатить код)
  структурно опасен: у #878 откат вернул бы исходный баг, который #878 как
  раз чинил (воркер до фикса засчитывал успех по чужому предсуществующему
  PR). Нужен другой третий шаг цикла — не копия чужого решения без разбора.

## Scope

**In:**
- Time-boxed (не count-window) метрика worker success-rate, считаемая на
  лету из уже читаемого `pulse_guard.recent_runs` — без записи второй копии
  истории на диск/git-ветку.
- Детектор «recent-окно (8ч) против АБСОЛЮТНОГО порога» с честными тремя
  исходами (`insufficient_data`/`ok`/`fire`) — ревизия 2: относительное
  отклонение recent от соседнего baseline (пороги, скопированные из
  `health_regression.py`) на реальной истории `worker.yml` даёт 17 ложных
  срабатываний из 41 здорового часа (41%) — хронический baseline этого
  репозитория ~48-50%, не благополучные 90%+, поэтому относительное
  отклонение тонет в шуме. Замена — АБСОЛЮТНЫЙ порог recent-rate (свои
  константы, не импорт из `health_regression.py` — «смысл» относительного
  отклонения для суточных снимков и часовых прогонов РАЗНЫЙ), проверенная
  сипом на реальных данных: 5.0% ложных на 119 здоровых часовых тиках при
  сохранённой поимке #878 (+7ч). `baseline` остаётся в отчёте ТОЛЬКО как
  контекст для человека, в решении `fire`/`ok` не участвует (см. design.md,
  «Ревизия 2»).
- Список подозреваемых слияний в окне атрибуции (`pipeline_health.
  search_merged_prs`) — ВСЕ PR окна, не угадывание одного; честно назван
  потолок метода (корреляция по времени, не причинность).
- Реакция: эскалация тем же каналом, что остальной конвейер
  (`pulse_guard.escalate`), плюс задача-расследование `task`+`area:process`
  (приоритет уровня 1 у уже существующего `free_task.py::issue_priority_key`)
  — без второй инфраструктуры приоритета и без прямого workflow_dispatch
  (тот дублировал бы `scheduler.py`, вне территории этой задачи). Дедуп по
  ФИКСИРОВАННОМУ отпечатку (один открытый PR-расследование на весь инцидент,
  не один на каждый час) плюс свой суточный потолок (`MERGE_HEALTH_DAILY_CAP`,
  тот же класс тормоза, что `pulse_guard.FAILURE_WATCH_DAILY_CAP`).
- Отдельный workflow `merge-health-watch.yml` (часовой cron) — не правка
  `orchestra.yml`/`scheduler.py`/`pulse_guard.py`/`repo_invariants.py` (эти
  файлы заняты параллельной работой на момент подачи, issue #967 называет
  границу явно).

**Out (сознательно, не забыто):**
- Автоматический `git revert` подозреваемого PR — см. design.md, «Почему не
  авто-revert»: риск вернуть старый баг перевешивает скорость для ЭТОГО
  класса регрессии (критерий успеха конвейера). Другой класс регрессии
  (например, поломка внешнего провайдера, а не логики оценки) мог бы
  оправдать другой выбор — не рассматривается здесь.
- Исключение подозреваемых по эвристике «их собственное окно до уже было
  плохим» — на разреженных данных `worker.yml` этого репозитория (медиана
  интервала между прогонами — единицы-десятки минут, но каденс скачет) даёт
  неустойчивые результаты (проверено вручную на реальных числах ночи
  2026-09-10/11, design.md, «Не подтверждено»).
- Подбор точных порогов по историческим данным — истории этой метрики (в
  часовом разрезе) физически не существует дольше суток на момент подачи.
- Правка `scripts/orchestra/scheduler.py`, `repo_invariants.py`,
  `pulse_guard.py`, `scripts/review/*`, `.github/workflows/orchestra.yml`,
  `scripts/measure/dispatch_tail.py` — чужая территория параллельной работы.

## Честные границы (называются явно, не смягчаются)

1. Метрика не поймает регрессию, никак не отражённую ни в одной измеряемой
   величине (пример: тихо испорченный текст документации, изменение,
   не влияющее на исход прогона worker.yml).
2. «Метрика упала после слияния» — корреляция по времени, не причинность:
   подозреваемый называется подозреваемым, не виновным. При нескольких
   слияниях в окне атрибуции все перечисляются, выбор одного не делается.
3. Для более точной атрибуции (например, отличить PR, чей дифф структурно
   не мог повлиять на исход worker.yml) нужны данные, которых конвейер
   сегодня не собирает (связь конкретного прогона с конкретным коммитом
   диффа, не только с head_sha репозитория на момент старта) — не
   реализовано, не выдумано.
