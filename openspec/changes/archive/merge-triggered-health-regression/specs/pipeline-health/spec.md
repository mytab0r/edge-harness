# Дельта-спека: pipeline-health — детектор регрессии, привязанный к слиянию

Расширяет способность `pipeline-health` (archived: `pipeline-health-self-audit`)
новым, БЫСТРЫМ путём обнаружения одного конкретного класса регрессии —
падения worker success-rate в пределах часов после слияния, — не заменяет
существующий суточный снимок/детектор/само-аудит. Оба механизма работают
параллельно: суточный ловит медленный дрейф по шести метрикам, этот —
резкий обвал одной метрики, привязанный к событию слияния.

## ADDED: Time-boxed выборка слитых PR по произвольному окну времени

Требование: `scripts/measure/pipeline_health.py::search_merged_prs` строит
запрос `search/issues` с квалификатором `merged:` в формате полного ISO8601
с временем (`YYYY-MM-DDTHH:MM:SS..YYYY-MM-DDTHH:MM:SS`), не только датой
суток — окно атрибуции детектора регрессии измеряется часами, день целиком
слишком грубая единица.

Сценарий: окно атрибуции 12ч захватывает несколько слияний одной ночи —
запрос возвращает ровно те PR, чьё `pull_request.merged_at` попадает в
полуоткрытый интервал `[start, end)`, не весь день целиком.

## ADDED: Детектор регрессии worker success-rate, привязанный к слиянию

Требование: `scripts/orchestra/merge_health_watch.py::evaluate` считает
success-rate `worker.yml` в двух ЧАСОВЫХ (не count-based, не суточных)
окнах, оба кончающихся в момент запуска `now`: recent
(`OBSERVATION_WINDOW_HOURS=6`) и baseline (`BASELINE_LOOKBACK_HOURS=72`
часов ДО начала recent-окна). Ничего не пишет на диск/git-ветку — источник
(Actions API) читается заново на каждый запуск, второй копии истории
снимков не заводится.

Сценарий: за последние 6 часов из 5 завершённых прогонов `worker.yml` ни
одного успешного, при этом baseline за предыдущие 72 часа — 47.6% успешных
(82 прогона) — отклонение 100%, статус `fire`.

Требование: три честных исхода одним расчётом (порядок как в
`health_regression.classify_metric`, значения порогов — импорт оттуда же,
не копия): `insufficient_data` (recent или baseline не набрали минимума
прогонов), `ok` (отклонение ниже `REGRESSION_THRESHOLD_PCT`), `regression`
(держится, ниже `ESCALATION_THRESHOLD_PCT`), `fire` (держится, выше
`ESCALATION_THRESHOLD_PCT`).

Сценарий: сразу после слияния (recent-окно ещё не набрало
`MIN_SAMPLES_RECENT=3` завершённых прогонов) — `insufficient_data` с
причиной в тексте, не ложное `ok` и не ложная тревога.

## ADDED: Подозреваемые слияния — список, не угадывание одного

Требование: при статусе `regression`/`fire` `suspects_from_search` возвращает
ВСЕ PR, слитые в окне атрибуции `[now - ATTRIBUTION_LOOKBACK_HOURS, now]`
(`ATTRIBUTION_LOOKBACK_HOURS = 2 * OBSERVATION_WINDOW_HOURS`), отсортированные
по времени слияния — не один «самый вероятный» PR. Отчёт (`render_report`)
называет отклонение число-к-числу (baseline vs recent) и явным текстом
«корреляция по времени, НЕ причинность».

Сценарий: в окне атрибуции слито шесть PR подряд с интервалами меньше часа —
все шесть перечисляются в отчёте с номером и временем слияния, ни один не
выбирается как «виновный».

Требование: результат `search/issues`, обрезанный первой страницей (`total_count`
больше числа полученных `items`), помечается флагом `truncated` — отчёт
называет это явно, не выдаёт частичный список за полный.

## ADDED: Реакция — эскалация и задача-расследование высшего приоритета

Требование: на `regression`/`fire` `run_watch` (1) эскалирует тем же каналом,
что остальной конвейер (`pulse_guard.escalate` — issue-комментарий в #120 +
Telegram, не второй канал), и (2) заводит/дополняет задачу пула с метками
`task`+`area:process` через `pool_issue.create_pool_issue` — `area:process`
даёт тир-1 приоритет уже существующему `free_task.py::issue_priority_key`,
без новой инфраструктуры приоритета и без прямого `workflow_dispatch worker.yml`
(территория `scheduler.py`, вне границ этого механизма).

Сценарий: регрессия обнаружена впервые в этом календарном часе — заводится
новая задача с телом, называющим числа (baseline/recent/отклонение) и список
подозреваемых.

Сценарий: та же регрессия продолжается в пределах того же календарного
часа — новый прогон детектора комментирует уже открытую задачу тем же
отпечатком (`merge-health:worker_success_rate:<час>`), вторая задача не
заводится.

Требование: механизм НЕ делает `git revert` подозреваемого PR и НЕ
отключает автоматически критерий успеха воркера — реакция ограничена
issue-каналом (эскалация + задача), обоснование — design.md, «Почему не
авто-revert»/«Почему не (c)». Критерий готовности задачи — следующий прогон
детектора видит `ok` по тому же окну; задача закрывается человеком/агентом
по факту фикса, не автоматически (тот же принцип, что архивный
`pipeline-health-self-audit`, «Требование: механизм НЕ закрывает
автоматически...»).

## Не подтверждено (перенесено из design.md)

Пороги (`OBSERVATION_WINDOW_HOURS`, `BASELINE_LOOKBACK_HOURS`,
`MIN_SAMPLES_RECENT`, `MIN_SAMPLES_BASELINE`, `ATTRIBUTION_LOOKBACK_HOURS`)
проверены на одном реальном инциденте (PR #878), не выведены статистически
из множества независимых регрессий — такой истории для часовой метрики
физически не существует на момент реализации. Эвристика исключения
«невиновных» подозреваемых по их собственному pre-merge окну рассмотрена и
сознательно не реализована (design.md §3) — на реальных числах этого
репозитория даёт неустойчивый результат при плотном каденсе слияний.
