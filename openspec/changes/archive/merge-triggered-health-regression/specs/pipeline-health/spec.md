# Дельта-спека: pipeline-health — детектор регрессии, привязанный к слиянию

Расширяет способность `pipeline-health` (archived: `pipeline-health-self-audit`)
новым, БЫСТРЫМ путём обнаружения одного конкретного класса регрессии —
падения worker success-rate в пределах часов после слияния, — не заменяет
существующий суточный снимок/детектор/само-аудит. Оба механизма работают
параллельно: суточный ловит медленный дрейф по шести метрикам, этот —
резкий обвал одной метрики, привязанный к событию слияния.

## ADDED: Time-boxed выборка слитых PR по произвольному окну времени

Требование: `scripts/measure/pipeline_health.py::search_merged_prs` строит
запрос `search/issues` с квалификатором `merged:` в формате полного ISO8601
с временем (`YYYY-MM-DDTHH:MM:SS..YYYY-MM-DDTHH:MM:SS`), не только датой
суток — окно атрибуции детектора регрессии измеряется часами, день целиком
слишком грубая единица.

Сценарий: окно атрибуции 16ч захватывает несколько слияний одной ночи —
запрос возвращает ровно те PR, чьё `pull_request.merged_at` попадает в
полуоткрытый интервал `[start, end)`, не весь день целиком.

## ADDED: Детектор регрессии worker success-rate, привязанный к слиянию

Требование: `scripts/orchestra/merge_health_watch.py::evaluate` считает
success-rate `worker.yml` в двух ЧАСОВЫХ (не count-based, не суточных)
окнах, оба кончающихся в момент запуска `now`: recent
(`OBSERVATION_WINDOW_HOURS=8`) и baseline (`BASELINE_LOOKBACK_HOURS=72`
часов ДО начала recent-окна, ТОЛЬКО контекст отчёта, см. ниже). Ничего не
пишет на диск/git-ветку — источник (Actions API) читается заново на каждый
запуск, второй копии истории снимков не заводится.

Сценарий: за последние 8 часов из 5 завершённых прогонов `worker.yml` ни
одного успешного (recent-rate 0.0% <= `FIRE_RATE_THRESHOLD_PCT=10.0%`) —
статус `fire`, независимо от того, каким был baseline.

Требование: решение принимается ТОЛЬКО абсолютным порогом recent-rate, не
относительным отклонением от baseline (ревизия 2 — относительное
отклонение, скопированное из суточного `health_regression.py`, дало 17
ложных срабатываний из 41 здорового часа на реальных данных этого
репозитория; абсолютный порог — 6 из 119, 5.0%). Два честных решающих
исхода: `insufficient_data` (recent-окно не набрало `MIN_SAMPLES_RECENT=5`
завершённых прогонов), `fire` (recent-rate <= `FIRE_RATE_THRESHOLD_PCT=10.0%`
И выборка достаточна), `ok` (иначе). `baseline_rate`/`baseline_n` считаются и
несутся в `Verdict` только для текста отчёта — участия в решении не
принимают, и решение честно не портится, если страница Actions API
обрезана (`baseline_truncated`).

Сценарий: сразу после слияния (recent-окно ещё не набрало
`MIN_SAMPLES_RECENT=5` завершённых прогонов) — `insufficient_data` с
причиной в тексте, не ложное `ok` и не ложная тревога.

Сценарий: baseline за предыдущие 72 часа хронически плохой (например,
48%) — при recent-rate выше 10% решение всё равно `ok`: плохой baseline не
маскирует и не портит решение (снимает риск самозаглушения относительного
дизайна v1, при котором baseline, вобравший сам инцидент, дал бы ложный
`ok`).

## ADDED: Подозреваемые слияния — список, не угадывание одного

Требование: при статусе `fire` `suspects_from_search` возвращает ВСЕ PR,
слитые в окне атрибуции `[now - ATTRIBUTION_LOOKBACK_HOURS, now]`
(`ATTRIBUTION_LOOKBACK_HOURS = 2 * OBSERVATION_WINDOW_HOURS = 16`),
отсортированные по времени слияния — не один «самый вероятный» PR. Отчёт
(`render_report`) называет числа (recent-rate, baseline-контекст) и явным
текстом «корреляция по времени, НЕ причинность».

Сценарий: в окне атрибуции слито пятнадцать PR подряд с интервалами
меньше часа (реальная ночь 2026-09-10/11) — все пятнадцать перечисляются в
отчёте с номером и временем слияния, ни один не выбирается как
«виновный».

Требование: результат `search/issues`, обрезанный первой страницей (`total_count`
больше числа полученных `items`), помечается флагом `truncated` — отчёт
называет это явно, не выдаёт частичный список за полный.

## ADDED: Реакция — эскалация и задача-расследование высшего приоритета

Требование: на `fire` `run_watch` (1) эскалирует тем же каналом, что
остальной конвейер (`pulse_guard.escalate` — issue-комментарий в #120 +
Telegram, не второй канал), и (2) заводит/дополняет задачу пула с метками
`task`+`area:process` через `pool_issue.create_pool_issue` — `area:process`
даёт тир-1 приоритет уже существующему `free_task.py::issue_priority_key`,
без новой инфраструктуры приоритета и без прямого `workflow_dispatch worker.yml`
(территория `scheduler.py`, вне границ этого механизма).

Требование: дедуп по ФИКСИРОВАННОМУ отпечатку `merge-health:
worker_success_rate` (не зависит от часа/дня — ревизия 2: отпечаток с
календарным часом был мёртв в проде, cron даёт один прогон в час, ветка
«прогон того же часа» никогда не исполнялась бы) — один открытый
PR-расследование на ВЕСЬ инцидент. Отдельно — суточный потолок
`MERGE_HEALTH_DAILY_CAP=3` на СОЗДАНИЕ новых задач этим механизмом (свой
счётчик, не общий с `pulse_guard.FAILURE_WATCH_DAILY_CAP`).

Сценарий: регрессия обнаружена впервые — заводится новая задача с телом,
называющим числа (recent-rate/n, baseline-контекст) и список подозреваемых.

Сценарий: та же регрессия продолжается часами позже — новый прогон
детектора комментирует уже открытую задачу тем же фиксированным
отпечатком, вторая задача не заводится; комментарий-улика — не чаще
одного раза в календарный день (`pulse_guard.issue_marker_times`).

Сценарий: суточный потолок задач этого механизма исчерпан, а `fire`
продолжается — новая задача НЕ заводится, но эскалация (issue #120 +
Telegram) всё равно уходит с явным текстом «потолок исчерпан» — тормоз не
скрывает сам факт продолжающегося инцидента.

Требование: механизм НЕ делает `git revert` подозреваемого PR и НЕ
отключает автоматически критерий успеха воркера — реакция ограничена
issue-каналом (эскалация + задача), обоснование — design.md, «Почему не
авто-revert»/«Почему не (c)». Критерий готовности задачи — следующий прогон
детектора видит `ok` по тому же окну; задача закрывается человеком/агентом
по факту фикса, не автоматически (тот же принцип, что архивный
`pipeline-health-self-audit`, «Требование: механизм НЕ закрывает
автоматически...»).

## Не подтверждено (перенесено из design.md)

Пороги (`OBSERVATION_WINDOW_HOURS`, `FIRE_RATE_THRESHOLD_PCT`,
`MIN_SAMPLES_RECENT`, `BASELINE_LOOKBACK_HOURS`, `ATTRIBUTION_LOOKBACK_HOURS`)
подобраны эмпирическим свипом на истории одного реального инцидента
(PR #878) и проверены на здоровых окнах 41ч/119ч (2.4%/5.0% ложных), не
выведены статистически из множества независимых регрессий — такой истории
для часовой метрики физически не существует на момент реализации.
Эвристика исключения «невиновных» подозреваемых по их собственному
pre-merge окну рассмотрена и сознательно не реализована (design.md §3) —
на реальных числах этого репозитория даёт неустойчивый результат при
плотном каденсе слияний. Частота срабатывания `RESUME_MARKER` предохранителя
как дополняющий сигнал того же класса регрессии — рассмотрена, не
реализована здесь, вынесена в issue #972 (design.md, «Ревизия 2»).
