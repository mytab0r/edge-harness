# Design: окно `merge_throughput`

## 1. Выбор окна — полные предыдущие сутки против скользящих 24ч

Две развилки, обе меряют «сутки», обе имеют цену (AGENTS.md требует называть обе, не
выбирать молча):

| Вариант | За | Цена |
|---|---|---|
| **Полные предыдущие сутки** `[вчера 00:00, сегодня 00:00)` UTC — **выбрано** | Детерминировано ДАТОЙ, не временем снимка: снимок в 00:06 UTC и гипотетический снимок в 23:50 UTC того же дня-по-расписанию считают ОДНО И ТО ЖЕ число за один и тот же календарный день. Напрямую воспроизводимо прямым запросом `merged:YYYY-MM-DD..YYYY-MM-DD` — тем же запросом, каким этот баг был пойман (см. proposal.md, улика). | Число «сегодняшних» слияний снимок никогда не покажет сразу — оно появится только на СЛЕДУЮЩЕМ снимке, то есть с задержкой до 24ч. |
| Скользящие 24ч до момента снимка | Без задержки — «вчера плюс сегодня-до-сейчас» видно сразу. | Гейт `should_snapshot` гарантирует только «раз в календарные сутки», НЕ гарантирует точное время снимка — окно ездит вместе с фактическим временем срабатывания пульса. Два снимка на соседних календарных днях могут перекрыть общий отрезок времени дважды (двойной счёт) или пропустить отрезок между ними (недосчёт). Число, которое оно даёт, НЕЛЬЗЯ сверить прямым запросом `merged:D..D` — теряется ровно то свойство, ради которого чинится этот баг (аудируемость). |

Решение: **полные предыдущие сутки**. Задержка в 24ч — приемлемая цена: снимок и так
снимается раз в сутки (`should_snapshot`), сам класс метрики уже даёт задержку по
конструкции; воспроизводимость числа прямым запросом важнее скорости появления.

Подпись: границы окна несутся В САМОМ снимке (`merge_throughput_window_start/_end`,
ISO8601), не только в докстринге кода — значение обязано быть проверяемо без чтения
исходника на момент снятия снимка.

## 2. Решение по старой истории

Три варианта (proposal.md называет решение, здесь — обоснование):

1. **Пересчитать задним числом** (данные доступны — `search/issues` отвечает на любой
   исторический день). Отвергнуто В ЭТОЙ задаче: запись пересчитанных строк на
   `data/pipeline-health` — операция поверх git-ветки данных вне обычного суточного
   пульса (`snapshot_and_store`), требует `GH_PIPELINE_PAT` и осмысленно вне протокола
   «агент не пишет в прод-ветки из сессии разработки» (см. задание). Механически ничто
   не мешает написать такой backfill отдельным, отдельно review'ing PR — не сделано
   здесь сознательно, не потому что невозможно.
2. **Пометить старые записи негодными** — выбрано. Различитель уже структурный:
   `merge_throughput_window_start`/`_end` присутствуют ТОЛЬКО в строках, посчитанных
   после этого фикса. Отсутствие поля — сам по себе честный, машиночитаемый признак
   «эта точка — брак измерения», без дополнительной записи на ветку данных.
3. **Начать новый ряд** (отдельное поле/имя метрики) — отвергнуто: удваивает схему ради
   того же различения, которое уже даёт вариант 2 дешевле (наличие/отсутствие двух
   полей), без выигрыша в ясности.

Механизм принуждения: `scripts/orchestra/health_regression.py::classify_metric` (единственный
известный потребитель истории `merge_throughput`, строит на ней медиану-baseline) теперь
отбрасывает точки без `merge_throughput_window_start` через `_is_reliable_sample` — старые
нули НЕ вклиниваются в baseline и не занижают порог будущей регрессии молча.

## 3. Таблица соседей — та же болезнь окна?

Проверены ВСЕ 6-7 полей снимка `pipeline_health.build_snapshot` тем же вопросом:
совпадает ли фактическое окно измерения с тем, что подписывает поле `date`/имя поля.

| Метрика | Окно | Подпись | Совпадают? |
|---|---|---|---|
| `merge_throughput` | БЫЛО: «сегодня, 00:00..момент снимка» (частичные сутки) | `date`: день снимка, поле без суффикса окна | **НЕТ — чинится этим change** |
| `backlog_free/in_progress/blocked/stale_unclaimed/total` | Точка во времени: список ОТКРЫТЫХ задач НА МОМЕНТ снимка | `date`: день снимка | ДА — мгновенный снимок состояния, окна как такового нет |
| `pr_age_p50_hours`/`pr_age_p95_hours` | Точка во времени: возраст ОТКРЫТЫХ PR на момент снимка | `date`: день снимка | ДА — то же, мгновенный снимок |
| `worker_success_rate` | Скользящее окно последних `WORKER_SUCCESS_WINDOW` (30) ЗАВЕРШЁННЫХ прогонов (счётное, не календарное) | `date`: день снимка; само поле не заявляет «за сутки» | ДА — честно «rolling», не претендует на календарный день |
| `pulse_ticks_24h`/`pulse_cadence_ratio` | Скользящие 24ч ДО момента снимка | `date` + суффикс `_24h` в имени поля | ДА — суффикс имени поля сам называет окно, `date` — не единственная подпись |
| `do_rows_read_pct` | С 00:00 UTC (сброс квоты Cloudflare) до момента снимка | `date`: день снимка, «% от суточного лимита» | Формально ДА (то же окно, что и определение самой квоты — сброс происходит в то же время), но снимок раз/сутки СРАЗУ ПОСЛЕ сброса структурно слеп к пикам ПРЕДЫДУЩЕГО дня — родственный, не идентичный дефект (алиасинг частоты дискретизации, не окно-против-подписи). **Заведён отдельно, issue #1278, не чинится здесь.** |
| `gh_rate_remaining_pct` | Мгновенное значение (сам rate-limit Cloudflare... GitHub сбрасывается ежечасно) | `date`: день снимка | ДА — честно мгновенное, никогда не претендовало на «за сутки» |

Итог: из 7 метрик окно-против-подписи по буквальному классу («поле называет сутки,
измеряет часть суток») нашлось РОВНО у одной — `merge_throughput`, что и чинит этот
change. `do_rows_read_pct` несёт соседнюю, но отдельную болезнь (алиасинг дискретизации),
заведена узкой задачей #1278 со ссылкой на этот change.

## 4. Ряд за последние пять суток — было/стало

«Было» — значение, реально записанное в `data/pipeline-health.jsonl` в строке с этой
датой (старая формула). «Стало» — реальное число слияний ЗА ЭТОТ календарный день
(прямой запрос `gh api search/issues q=repo:mytab0r/edge-harness+is:pr+merged:D..D`,
снято 2026-09-15) — то есть то число, которое НОВАЯ формула покажет в снимке,
датированном СЛЕДУЮЩИМ днём (окно «предыдущие сутки», см. §1: значение за 09-11
появляется в снимке `date=2026-09-12`, не `date=2026-09-11`).

| День (слияний) | Было (снимок этого же дня, старая формула) | Стало (реальное число за день, появится в снимке следующего дня) |
|---|---|---|
| 2026-09-10 | 9 | 14 |
| 2026-09-11 | 0 | 16 |
| 2026-09-12 | 0 | 20 |
| 2026-09-13 | 0 | 24 |
| 2026-09-14 | 1 | 19 |

Даже день 09-10, формально не «ноль», занижен — снимок брался в первые минуты суток и
не видел 5 слияний, случившихся позже того же дня.

## Не подтверждено

- Обновлённые пороги `health_regression.py` под новую (правильную) шкалу
  `merge_throughput` — baseline, построенный из старых «здоровых» суток, был не выведен
  из ЭТИХ данных (proposal `pipeline-health-self-audit` уже честно называл пороги
  неподтверждёнными); пересчёт baseline под правильную шкалу — отдельная, не сделанная
  здесь работа, тот же класс, что и раньше.
- Cloudflare Analytics способность отдать `rows_read` за произвольный прошедший день
  (нужно для #1278) — не исследовано в этом change.
