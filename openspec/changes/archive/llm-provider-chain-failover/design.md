# Дизайн: где живёт упорядоченный список провайдеров

## Развилка

Требование #727, п.3: «упорядоченный список провайдеров объявляется ОДИН раз
(переменной репозитория или конфигом в репозитории — выбери и обоснуй)».

### Вариант А — файл в дереве репозитория (например `scripts/lib/llm-provider-chain.json`)

Плюсы: ревьюится диффом как обычный код, версионируется git-историей.

Минусы (решающие): гвардия класса #153
(`scripts/lib/test/provider-default.guard.sh`) сканирует `.github/workflows`,
`scripts/**`, `docs/agents/**` на литералы прежних дефолтов
(`api\.z\.ai|integrate\.api\.nvidia\.com|glm-[0-9]|nemotron|deepseek-v[0-9]`) —
цель гвардии ровно та же, что у этой задачи: не дать провайдеру/модели
разъехаться по нескольким местам кода. Файл цепочки с реальными URL/моделями
внутри `scripts/` создал бы ВТОРОЕ место, где эти литералы легитимны, и либо
ломает гвардию (ложное срабатывание на каждый PR), либо требует расширять
allowlist гвардии — то же самое расширение поверхности, которого гвардия
существует, чтобы избежать.

### Вариант Б — переменная репозитория `vars.DSH_PROVIDER_CHAIN` (выбран)

Прямое продолжение решения #153: «провайдер и модель объявлены РОВНО в одном
месте — `vars` репозитория, а не в коде». Прецедент такой же формы уже есть —
`vars.DSH_EDGE_MODEL_CATALOG` хранит JSON-массив каталога моделей морды.
Гвардия #153 не видит содержимое `vars` вообще (сканирует только файлы
репозитория) — конфликта нет по построению, а не по везению.

Минусы, принятые осознанно: значение не ревьюится диффом PR (правится
`gh variable set` отдельной командой, вне истории коммитов) — тот же
компромисс, с которым репозиторий уже живёт для `DEEPSEEK_BASE_URL`/
`DEEPSEEK_MODEL`/`DSH_EDGE_MODEL_CATALOG`. `INFRA-GH.md` документирует состав
переменных по имени (без значений, см. #153-гвардию `test_infra_gh_inventory`
о причине), актуальное значение смотрится командой `gh variable get`, не
читается из документации.

## Секреты цепочки — литеральные имена, не индексация через vars

PR #725 (issue #716, параллельный канал) вводит `vars.DSH_PROVIDER_KEY_SECRET`
— имя ОДНОГО активного секрета для ручного переключения через `secrets[vars.…]`.
Цепочке нужны ключи ВСЕХ провайдеров одновременно (перебор внутри одного
прогона, не переключение между прогонами) — оба секрета
(`secrets.DEEPSEEK_API_KEY`, `secrets.NVIDIA_API_KEY`) передаются в `env:`
литерально, а JSON называет ИМЯ переменной окружения (`secret_env`), из
которой чейн читает значение через bash-индирекцию `${!secret_env}`. Это не
дублирует механизм #725 — оба применяются к разным вопросам («какой секрет
сейчас активен для ручного свитча» vs «какие секреты доступны цепочке для
автоперебора») и физически не пересекаются кодом.

## Cross-run состояние «провайдер X исчерпан до даты Y» — не заведено

Рассмотрено и отклонено писать `vars`/файл-стейт из самого job'а
(`gh variable set` после каждого отказа) ради пропуска заведомо исчерпанного
провайдера на СЛЕДУЮЩЕМ прогоне без единого пробного вызова. Отклонено по
двум причинам: (1) job `review` в `ai-review.yml` намеренно без GitHub-токена
(trust-zone #18) — заводить туда токен ради записи переменной непропорционально
расширяет поверхность; (2) стоимость пропущенной оптимизации мала — попытка
против уже исчерпанного провайдера возвращает быстрый отказ (не тратит
реальную квоту, квота и так исчерпана), единственная цена — секунды на HTTP-
раунд-трип. Вместо этого cross-run знание используется ТОЛЬКО на уровне
«весь чейн исчерпан → не долби автоповтором» — читается из уже существующего
канала (шапка комментария вердикта), см. proposal.md, «Отвергнутые варианты».
