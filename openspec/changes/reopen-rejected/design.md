# Design: reopen-rejected

Контекст и правило — `proposal.md` этого изменения. Здесь — почему GitHub не
может закрыть эту задачу нативно, какой сигнал детектирует переоткрытие, где
именно живёт проверка и почему PR #366 стал мёртвым кодом, а не просто
неверным.

## Нативная возможность GitHub — проверено фактом, её нет

Искали три пути, все отклонены:

1. **Repo-настройка «запретить reopen».** Нет такого поля ни в
   `Settings → General`, ни в REST/GraphQL API репозитория (проверено по
   схеме `PATCH /repos/{owner}/{repo}` — список полей не содержит ничего
   про reopen issues). Branch protection относится к pull request'ам и
   веткам, не к issues.
2. **Lock conversation (`gh api -X PUT .../lock`).** Ограничивает НОВЫЕ
   комментарии участников без write-доступа к репозиторию. Не мешает смене
   `state` — участник с write (а в этом репозитории агенты и владелец делят
   один и тот же токен, см. `docs/agents/PROTOCOL.md`, «Ограничения
   честности») по-прежнему может переоткрыть локнутую issue. Даже если бы
   мешало — залочило бы и легальные комментарии тоже, это грубее, чем нужно.
3. **GraphQL `issue.viewerCanUpdate`/webhook на `reopened` с отклонением на
   стороне GitHub.** GitHub не даёт отклонить входящее REST/UI-действие
   синхронно (нет pre-receive хука для issues, в отличие от git push);
   единственный способ отреагировать — уже ПОСЛЕ того, как reopen
   состоялся, событием или опросом.

Вывод: носитель правила обязан быть нашим кодом, реагирующим постфактум, а
не настройкой, предотвращающей действие. Дальше — вопрос, каким постфактум-
сигналом ловить переоткрытие дешевле всего.

## Развилка сигнала: `state_reason` vs timeline `reopened`

### (а) `state_reason` в list-ответе issues (выбрано)

`GET /repos/{owner}/{repo}/issues?state=open&labels=task` — тот же запрос,
что уже делает `open_task_issues` — отдаёт `state_reason` на КАЖДОЙ issue
без дополнительного обращения. Значение `"reopened"` означает «текущее
открытое состояние достигнуто событием reopened» (в отличие от `null` —
issue открыт с рождения, событие reopened никогда не происходило).
Проверено фактом на живых #111/#114/#115/#158 (закрыты и переоткрыты
человеком 2026-09-05): поле остаётся `"reopened"` и после последующих
assign/unassign — соседние события его не сбрасывают.

Цена: не подтверждено, сохраняется ли `state_reason` после ЛЮБОГО другого
типа последующего события (например, повторного редактирования тела issue)
— проверялось только для assign/unassign, потому что это единственные
события, реально случившиеся с этими четырьмя issue после переоткрытия.
Если окажется, что какое-то действие сбрасывает `state_reason` обратно в
`null` без реального повторного закрытия — детектор перестанет видеть
такую issue. Риск принят: `state_reason` — задокументированное поле
GitHub REST (Issue object schema), не догадка по недокументированному
поведению, и такой сброс означал бы баг в самом GitHub API, а не в этой
проверке.

Стоимость на пульсе: **нулевая** для issue, которую никто не трогал —
никакого отдельного запроса, поле уже в ответе, который `open_task_issues`
и так делает на каждом пульсе для других целей (dispatch/reap/accept).

### (б) Событие `reopened` в timeline (`issues/{n}/timeline`)

`review_labels.list_timeline` уже даёт пагинированный обход, и timeline
действительно отдаёт событие `event: "reopened"` (проверено фактом на живой
#111: `{"event": "reopened", "actor": "mytab0r", "created_at": "..."}`,
`GET issues/111/timeline`). Работоспособно, но требует ОДНОГО
дополнительного запроса на КАЖДУЮ issue пула на КАЖДОМ пульсе, чтобы
отличить «была переоткрыта» от «нет» — застраховаться от пропуска можно
только вычитыванием всего timeline, а не последних N событий (переоткрытие
могло случиться давно, а дальше issue долго живёт с другими событиями).
При пуле в районе сотни задач это лишняя сотня запросов каждые 15 минут
ради сигнала, который список issues отдаёт бесплатно.

Единственное, для чего timeline всё же нужен в этом изменении — НЕ нужен
вовсе: комментарий-отказ не обязан называть, КЕМ и КОГДА была переоткрыта
issue, чтобы выполнить своё назначение (сообщить готовое действие). Если
в будущем понадобится более информативный комментарий (например, накрутить
предупреждение при третьем нарушении одним и тем же автором) — тогда
`review_labels.list_timeline` даст точный ответ, но только для issue,
УЖЕ отмеченной `state_reason == "reopened"` в (а) — не для всего пула
разом.

### Почему не приняли (б)

Стоимость (б) растёт линейно с размером пула на каждом пульсе, стоимость
(а) — постоянна (одно поле в уже существующем ответе). Раз (а) полностью
покрывает единственную задачу этого изменения («увидеть, что issue была
переоткрыта, и закрыть её обратно»), вводить (б) значило бы платить за
информацию, которая здесь не используется.

## Где живёт проверка

`scripts/orchestra/scheduler.py`, шаг пульса `main()`, а не:

- **`repo_invariants.py`** — такого файла в репозитории нет (проверено
  `git ls-tree` по `origin/main`); это, возможно, имя из другого контекста
  или нереализованный замысел. Заводить новый модуль под одну функцию,
  когда весь остальной пул/приёмка/оркестрация уже живёт в `scheduler.py`,
  было бы вторым местом правды для одного и того же понятия «пул задач».
- **Отдельный workflow/job** — сигнал (`state_reason`) читается из ТОГО ЖЕ
  ответа, что `open_task_issues` уже получает для других шагов пульса;
  отдельный job дублировал бы вызов и терял бы порядок (принципиально
  важно выполниться ДО `accept_merged_tasks`, иначе воспроизводится баг
  #363 — переоткрытая issue снова матчится со старым `merged_pr_map`).

Вызов размещён между `pool = open_task_issues(repo)` и
`accept_merged_tasks(...)`, с пересчётом `pool`, если что-то было закрыто —
тот же шаблон, что уже применяет `accept_merged_tasks` для своего
собственного повторного вызова ниже по файлу (`if accept_lines: pool = …`).

## PR #366 — мёртвый код, не ошибка

Тело PR #366 (`acceptance-reopen-guard`, ветка `agent/363-accept-ok-docs-guard`)
дословно: «найдя маркер — приёмка молча уходит, не трогая evidence/PATCH/
assignee/lock: переоткрытие человеком или агентом уважается, приёмка с ним
не спорит». Формулировка верна для мира, где reopen — легальное действие.
При правиле «переоткрытие отклоняется автоматически» этот мир не наступает:
`reject_reopened_tasks` закрывает issue обратно РАНЬШЕ, чем
`accept_merged_tasks` успевает её увидеть в открытом состоянии в ТОМ ЖЕ
пульсе (порядок вызовов в `main()`), а на следующем пульсе issue уже не
входит в `open_task_issues` вовсе (`state=open` фильтр). Сценарий, для
которого писался guard #366 (переоткрытая issue доживает до
`accept_merged_tasks` со старым `merged_pr_map`), становится недостижим по
построению — не «маловероятен», а невозможен, пока `reject_reopened_tasks`
вызывается раньше `accept_merged_tasks` на каждом пульсе (инвариант, который
защищает интеграционный тест этого изменения,
`test_main_closes_reopened_task_before_acceptance_sees_it`).

Решение: закрыть PR #366, не сливать и не переписывать его под новую
формулировку — держать мёртвый код ради «а вдруг пригодится» противоречит
правилу репозитория «меньше кода», а сама находка #363 (ветка `ok`/`docs`
без дедупликации) полностью решается тем, что дедуплицировать стало
нечего: переоткрытая issue не доживает до повторного матчинга.
