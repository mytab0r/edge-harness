# reopen-rejected: закрытая задача не переоткрывается никогда (#369)

Задача: #369. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).
Развилка вариантов и почему выбран текущий — [design.md](design.md).

## Зачем

Решение владельца, дословно: «нахуя мы даем возможность переоткрывать закрытые
таски? Если закрыли то всё, создавайте новую. Предыдущую явно не просто так
закрыли, если что то забыли, то будет отдельная более точная и менее объёмная
задача как related».

До этой задачи переоткрытие закрытой issue было обычным путём: GitHub не
запрещает его никак, и по крайней мере один открытый PR (#366,
`acceptance-reopen-guard`, задача #363) был написан так, чтобы ЯВНО уважать
переоткрытие человеком или агентом — «приёмка с ним не спорит». При новом
правиле переоткрытий не существует вовсе, и направление того PR стало
неверным (закрыт этим же изменением, см. ниже).

Живой случай, показавший цену отсутствия правила: #131 переоткрывали трижды
за время работы над PR #359, и до появления любого guard'а приёмка
(`accept_merged_tasks`, #227) закрывала её обратно за 20–80 секунд каждый
раз, споря сама с собой на каждом пульсе. #366 предлагал чинить это
подчинением автоматики переоткрытию; это изменение делает обратное —
автоматика подчиняет себе переоткрытие.

## Что делается

Новый шаг пульса оркестратора, `scripts/orchestra/scheduler.py::reject_reopened_tasks`,
вызывается в `main()` ДО `accept_merged_tasks`, на том же снимке `pool`
(`open_task_issues`):

- Issues API уже отдаёт `state_reason` в самом list-ответе (без
  дополнительного запроса на issue, тот же приём, что `is_epic_issue`
  использует для `sub_issues_summary`). `state_reason == "reopened"`
  однозначно значит «текущее открытое состояние достигнуто событием
  reopened» — проверено фактом на живых #111/#114/#115/#158 (закрыты и
  переоткрыты человеком 2026-09-05, поле пережило последующие
  assign/unassign).
- Найдя такую issue — закрывает её обратно (`PATCH state=closed`) с
  комментарием-отказом, называющим готовое действие: завести НОВУЮ, более
  узкую задачу со ссылкой на эту как related — не переоткрывать снова.
  Снимает assignee/lock (`claim_task.release`), если реопен успел их
  вернуть.
- Дедупликации не требуется: закрытая issue выходит из `state=open` фильтра
  `open_task_issues` и второй раз в `pool` не попадёт — новое переоткрытие
  после этого обрабатывается как новое (и снова корректное) нарушение, а
  не повтор старого.
- `main()` пересчитывает `pool` сразу после этого шага, ЕСЛИ он что-то
  закрыл — `accept_merged_tasks` видит уже очищенный пул и никогда не
  встречает переоткрытую issue со старым `merged_pr_map` (тот самый сценарий,
  который защищал #366 — здесь он не наступает по построению, а не
  улаживается постфактум).

GitHub не умеет запретить reopen нативно — проверено фактом: нет ни
repo-настройки, ни API-поля под это; Lock conversation (`gh issue lock`)
ограничивает только НОВЫЕ комментарии участников без write-доступа и не
трогает возможность сменить state — сама owner-учётка (или любой участник с
write, а агенты все под одним токеном — см. `docs/agents/PROTOCOL.md`,
«Ограничения честности») по-прежнему может переоткрыть. Носитель правила —
не запрет на входе, а обнаружение и обратное действие на пульсе.

## Что с PR #366 и задачей #363

- **PR #366 закрыт** (не смёржен) с пояснением: его guard существует именно
  для того, чтобы «переоткрытие человеком или агентом уважалось», а при
  новом правиле такого легального сценария больше нет — этот же PR (#369),
  закрывая переоткрытую issue обратно ДО `accept_merged_tasks`, делает
  сценарий, который #366 защищал, недостижимым по построению (issue
  закрывается раньше, чем успевает снова смэтчиться со старым
  `merged_pr_map`). Guard #366 не был бы неверным сам по себе — он был бы
  МЁРТВЫМ кодом, защищающим состояние, которое больше никогда не
  возникает.
- **Задача #363** (источник PR #366) закрыта: находка в ней верна
  (`accept_merged_tasks` действительно не дедуплицировал ветку `ok`/`docs`),
  но направление фикса, которое она заказывала, устарело вместе с решением
  владельца. Остаток описан в этой задаче (#369) — closed-as-superseded, не
  reopened.

## Последствия правила задним числом

Четыре задачи, переоткрытые владельцем 2026-09-05 (#111, #114, #115, #158),
приведены в соответствие правилу вручную (до появления автоматики) —
разбор по каждой в комментариях к PR/issue, преемники заведены только там,
где остаток работы реален (не ради симметрии).

## Проверено

- `python -m pytest scripts/orchestra/test_scheduler.py -q` — все тесты
  зелёные (135, из них 6 новых на `reject_reopened_tasks`/интеграцию с
  `main()`).
- `python -m pytest scripts/orchestra -q` — весь пакет зелёный (229).
- Мутация 1: убрать пересчёт `pool` после `reject_reopened_tasks` в `main()`
  — интеграционный тест краснеет (`accept_merged_tasks` видит непересчитанный
  пул с переоткрытой задачей).
- Мутация 2: снять проверку `state_reason == "reopened"` — тест на обычную
  (не переоткрытую) задачу краснеет (лишний вызов `gh`, которого не должно
  быть вовсе).
- `python -m py_compile scripts/orchestra/scheduler.py scripts/orchestra/test_scheduler.py`.

## Что вне рамок

- Машиночитаемая семантическая проверка «эта задача больше не требует
  работы» — не предмет этого изменения (тот же принцип, что и у
  `task-closure-after-proof`/`acceptance-partial-pr-guard`).
- Полный аудит всех когда-либо переоткрытых задач в истории репозитория —
  разобраны только четыре, переоткрытые владельцем 2026-09-05 и явно
  названные в задаче #369.
