# Дельта-спека: журнал (journal-tasks-hands) — закрытая задача не переоткрывается (#369)

## ADDED: Конвейер (оркестратор)

39. Закрытая задача из пула не переоткрывается никогда (решение владельца):
    остаток работы оформляется НОВОЙ, более узкой задачей со ссылкой на
    закрытую как related, не переоткрытием. GitHub не отклоняет reopen
    нативно (нет ни repo-настройки, ни API-поля; Lock conversation трогает
    только комментарии, не state) — носитель правила: пульс оркестратора.

    39.1. Шаг пульса (`scheduler.py::reject_reopened_tasks`) вызывается в
        `main()` ДО `accept_merged_tasks`, на снимке `pool`
        (`open_task_issues`). Находит issue с `state_reason == "reopened"`
        (поле уже в list-ответе issues API — без дополнительного запроса) и
        закрывает её обратно (`PATCH state=closed`) с комментарием-отказом,
        называющим готовое действие (завести новую узкую задачу со ссылкой
        на эту как related). Снимает assignee и замок аренды (#121), если
        переоткрытие успело их вернуть.

    39.2. `WATCHDOG_ISSUE` (#120, постоянный канал эскалации) исключён из
        проверки — тот же приём, что уже защищает его в `accept_merged_tasks`.

    39.3. Дедупликации не требуется: закрытая issue выходит из `state=open`
        фильтра `open_task_issues` и второй раз в `pool` этого или
        следующего пульса не попадёт. Новое переоткрытие после этого —
        новое (и снова корректно отклоняемое) нарушение, а не повтор
        старого.

    39.4. `main()` пересчитывает `pool` сразу после этого шага, если он
        закрыл хотя бы одну задачу, — `accept_merged_tasks` видит уже
        очищенный пул и не может смэтчить переоткрытую задачу со старым
        `merged_pr_map` в том же пульсе (класс #363: приёмка отменяла
        переоткрытие за 20–80 секунд до появления этой проверки).

    39.5. Сбой на комментарии или PATCH (сеть/API) не роняет обход
        остальных задач пула — та же гарантия, что уже даёт `accept_merged_tasks`
        соседним веткам.
