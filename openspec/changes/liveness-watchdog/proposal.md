# liveness-watchdog: сторож живости механизмов, не мониторинг падений (#510/#519)

Задача: #519. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Боль владельца

«Мы всё это время убили на стабильность автономного воркфлоу, вроде все
кейсы покрыли, но до сих пор что-то отваливается и перестаёт работать, а мы
не в курсе и опять что-то чиним».

## Образцовый случай (#510, разобран 2026-09-06)

`scripts/gh/wake_orchestra.sh` попал в main с режимом 100644 — без бита
исполнения (PR #458). Шаг «Разбудить оркестратор» в `pr-review.yml`/
`ai-review.yml` падал с `Permission denied` на КАЖДОМ прогоне. Событийный
триггер (#297, ADR 0012) не работал вовсе — оркестратор жил только на
расписании: последний событийный прогон 12:33, следующий не пришёл до
14:45 — два часа очередь стояла. **Ни одна проверка этого не заметила**:
шаг не обязательный (`continue-on-error: true`), красным не светится, в
отчёты не попадает. Нашёл владелец, спросив «как успехи».

## Граница с failure_watch (#477, PR #488 — открыт, не архивирован)

`failure_watch` (`pulse_guard.py`) ловит УПАВШИЕ прогоны (`conclusion=failure`,
классификация причины по логу `##[error]`). Этот change — про механизмы,
которые НЕ падают, а молча ничего не делают: шаг зелёный или
`continue-on-error`, прогон в целом success, а ожидаемое действие
(диспатч, слияние, эскалация) не произошло. Разные признаки обнаружения:
`failure_watch` читает `conclusion`/логи упавших job'ов; этот сторож
сравнивает МОМЕНТ повода (например, завершение `ai-review.yml`) с МОМЕНТОМ
ожидаемого следствия (тик `orchestra.yml` с `event=workflow_dispatch`) —
других данных failure_watch не читает и не должен.

## Инвентаризация: что уже есть, что нет

Сплошной прочёс механизмов автономного конвейера (см. таблицу в issue #519)
показал: БОЛЬШИНСТВО ключевых механизмов уже несут признак живости и
эскалацию, просто не собраны в одну таблицу и не названы этим термином:

- Автослияние — `scheduler.stale_ready_pulls` (#269): готовый PR не слит
  дольше `UNHEALTHY_PR_AFTER_MINUTES` → `escalate`.
- Авторасшивка конфликтов — `scheduler.dispatch_conflict_rework` (#474):
  ребейз не сошёлся → `escalate` (`CONFLICT_ESCALATION_MARKER`).
- Приёмка — `repo_invariants.check_reopened_after_merge` (инвариант 1):
  задача без исполнителя со слитым PR → `escalate_if_new`.
- Автоповтор ревью — `scheduler.trigger_ai_review` (газ) +
  `repo_invariants.check_stuck_review_gate` (инвариант 3, наблюдение) →
  `escalate_if_new`.
- Общий детектор устойчивого простоя — `stall_detector.py` (#201): любой
  повторяющийся отпечаток причины в отчёте пульса дольше порога устойчивости.

**Пробел, который эта дельта закрывает** — ровно класс #510: пропавший
пульс планировщика ЦЕЛИКОМ (`pulse_guard.heartbeat_check`, #120/#133) уже
проверяется, но он видит «жив», если сработал ЛЮБОЙ из двух легитимных
каналов (`schedule` ИЛИ `workflow_dispatch`). Ни один существующий
механизм не проверяет ИМЕННО событийный канал отдельно от расписания —
поэтому расписание два часа маскировало сломанный будильник, и
`heartbeat_check` молчал по построению, не по дефекту.

**Оставшиеся пробелы (не в этой дельте, см. tasks.md и issue #519)**:
деплой морды по мержу `dsh-edge/**` (#374) — тихий логический промах без
исключения не отличим текущими средствами от «файлы не совпали»; инбокс
(#173) — нужен отдельный замер перед реализацией.

## Что делается

`scripts/orchestra/pulse_guard.py::event_wake_check` (вызывается из
`scheduler.main()` сразу после `heartbeat_check`):

- Применимость (не ложная тревога, главное требование): проверяется ТОЛЬКО
  когда `ai-review.yml`/`pr-review.yml` реально завершились в окне
  `[EVENT_WAKE_GRACE_MINUTES, EVENT_WAKE_STALE_AFTER_MINUTES]` = `[5, 30]`
  минут назад — то есть было ЧТО будить. Холостая очередь (нет свежих
  прогонов ревью) — 2 дешёвых вызова `recent_runs` и ни одного больше
  (гвардия холостого хода, тот же приём, что `stale_ready_pulls`).
- Сигнал: если применимо и НЕТ ни одного прогона `orchestra.yml` с
  `event=workflow_dispatch` не раньше момента повода — `stale`, канал
  `escalate()` (комментарий в задачу-статус #120 + Telegram), дедуп по
  паре маркеров (`EVENT_WAKE_MARKER`/`EVENT_WAKE_RESUMED_MARKER`, приём
  `episode_reopened`, симметричный `HEARTBEAT_NO_TICKS_MARKER`/
  `HEARTBEAT_TICKS_RESUMED_MARKER`).
- Цена: 2 запроса `recent_runs` на КАЖДЫЙ пульс (holостой ход), +1 запрос
  только когда применимо (нашёлся повод) — не заводит нового постоянного
  сетевого канала, переиспользует уже существующий `recent_runs`/`escalate`.
