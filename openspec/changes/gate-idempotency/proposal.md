# gate-idempotency: гейты конвейера идемпотентны — без повторных комментариев и без перестановки неизменившихся меток

Задача: #203. Оба гейта на каждом прогоне безусловно повторяли изменяющие
вызовы, даже когда решение не менялось: `contract_check.py::fail` POST-ил
заново одинаковый комментарий провала, `check_pr.py` снимал и ставил
вердикт-метку (`unlabeled`+`labeled` одного значения в таймлайне PR).
Подтверждённые дубли на живом репозитории: PR #162 — 10 идентичных
комментариев контракта (перепроверено `gh api` 2026-09-06 — исходная задача
#203 называла 5, промежуточный замер этого proposal называл 9; оба уже
устарели, дубли продолжали копиться), #173/#191 — по 3; PR #162 — 11 циклов
`unlabeled`+`labeled` за 01.09–02.09 при неизменном вердикте.
`orchestra.yml` слушает `on: pull_request: [labeled]` — лишний своп метки
означает лишний прогон конвейера, а в истории PR настоящее событие тонет
среди повторов.

Замер до (живой репозиторий, `scripts/measure/label_churn_203.py`, окно
2026-09-05T03:00..2026-09-06T03:00Z, 29 открытых PR): **213 событий
`labeled` за сутки** (= столько прогонов job'а `contract` они порождают),
из них 88 — `review:ok` при 74 `unlabeled review:ok` (реальных смен вердикта
в `review:changes-requested` — 1, в `review:large` — 10: подавляющая часть
перестановок — чистый шум), плюс 9 `contract:failed`.

## Решение

1. `scripts/lib/review_labels.py` — одно место правды дополнено:
   - `REVIEW_VERDICTS` — кортеж вердикт-меток гейта 1;
   - `verdict_label_changes(current, verdict, verdicts)` — единственное
     место решения «что переставлять»: вердикт не изменился → `([], False)`
     — вызывающий не выполняет ни одного изменяющего вызова; сменился →
     чужие вердикты снимаются, актуальный ставится. Метки вне `verdicts`
     (`review:large-ok`, `ai:*`, `conflict`) не трогаются — у них свои газы;
   - `latest_trusted_comment` — общий обход «найти свой прошлый
     комментарий» (постранично + фильтр доверия `_is_trusted_verdict_author`);
     `latest_ai_comment` переведён на него без изменения поведения;
   - `CONTRACT_FAIL_HEADER` / `REVIEW_FINDINGS_HEADER` — первые строки
     «своих» комментариев, одна копия строки на сборщика тела и на матчер;
   - `comment_update_action(existing, new_body)` → `post`/`patch`/`None`;
   - `latest_comment_by_header(repo, pr, gh, header)`.
2. `scripts/orchestra/contract_check.py::fail` (Факт 1): тот же текст
   нарушения уже висит доверенным комментарием → публикация молчит;
   изменился → существующий комментарий обновляется (PATCH); нет своего →
   POST как раньше. Метка `contract:failed` ставится по-прежнему всегда
   (POST labels идемпотентен на стороне GitHub). Первый заголовок строки
   байт-в-байт прежний — дубли на существующих PR опознаются.
3. `scripts/review/check_pr.py` (Факт 2): своп вердикт-метки — через
   `verdict_label_changes`; находки-комментарий — идемпотентно, тем же
   механизмом, что и комментарий контракта.
4. `scripts/review/ai_review.py::cmd_verdict` — тот же класс в гейте 2:
   своп `ai:*` через `verdict_label_changes(..., AI_VERDICTS)`.
   Комментарий AI-ревью НЕ дедуплицируется осознанно: каждый прогон
   ai-review — отдельное дорогое событие и запись ревью с шапкой
   `head:`/`diff:` (попытка N автоповтора — отдельное событие во времени).
5. Идемпотентность не превращается в молчание: смена вердикта переставляет
   метку, изменившийся текст нарушения публикуется (обновлением), чужой
   комментарий с тем же текстом публикацию не глушит (свой комментарий
   ищется только среди доверенных `github-actions[bot]` — оба workflow
   ходят под `github.token`; класс подделки из вердикта ai-review PR #294).

## Ограничения

- Замер «после» (тот же скрипт по тому же окну) делает пост-мерж проверка
  владелец/следующий воркер — сами события исчезают только у прогонов,
  начавшихся после мержа.
- События меток от `GITHUB_TOKEN` не триггерят workflow (антирекурсия,
  research/21) — выигрыш в прогонах `contract` относится к событиям от
  иных контекстов (PAT владельца, ручные действия) и к headroom лимита
  триггеров; выигрыш в шуме таймлайна — для всех.
