## Развилка: строковый ключ vs сквозной номер + арбитр

Issue #904 предлагал два направления: (а) убрать номер вовсе в пользу стабильного
строкового ключа (имя функции), (б) оставить номер, но вычислять его машиной и ловить
коллизии до мержа.

### Цена миграции на строковый ключ (посчитано на живом `repo_invariants.py`, 2026-09-14)

Мест, знающих число (не «часть», а весь список, посчитанный `grep`/чтением файла):

- Докстринг-реестр модуля — 18 нумерованных записей.
- `CI_GATING: frozenset[int]`, `GATING_RELEASE_CONDITION: dict[int, str]` — числовые ключи.
- `ESCALATING_INVARIANTS: tuple[int, ...]` — `(1, 3, 12, 15, 16, 17, 18)`.
- `CHECK_RESULT_MIGRATED_INVARIANTS: frozenset[int]`.
- `build_report()`: `findings[N] = ...` + печать строки `[N]` — по одной паре на инвариант
  (≥18 пар).
- `run_escalations()`: блок эскалации на каждый эскалирующий инвариант (7 блоков), с
  текстом «инвариант N» внутри тела алерта, уходящего в issue #120 и Telegram.
- `test_repo_invariants.py` — десятки прямых обращений к номерам в именах тестов и
  ассертах.
- Текст уже закрытых/открытых issue и PR, где число используется как ссылка («инвариант
  12», «инвариант 17») — не имеет обратной силы, механической миграции не подлежит.

### Решение: НЕ мигрировать сейчас

Причины:

1. `repo_invariants.py`/`test_repo_invariants.py` заняты ДВУМЯ параллельными PR (#1136,
   #1189) прямо в момент этой работы — правка такого масштаба физически не сольётся без
   конфликта с обоими.
2. Часть ссылок (алерты, уже отправленные владельцу в Telegram/issue #120) необратима —
   смешанная нумерация (часть по номеру, часть по ключу) хуже сквозной с арбитром.
3. Прецедент того же класса (#1078, `docs/decisions`/`docs/research`) решил идентичную
   развилку тем же способом — не менять схему, добавить арбитра. Симметрия: одна и та же
   развилка, одно и то же решение, другой носитель.

Дешёвая правка сейчас — арбитр (`scripts/lib/invariant_numbering.py` +
`scripts/ci/guards/invariant-numbering-guard.sh`): один новый файл-модуль, один новый файл
гвардии, ноль правок занятых файлов. Польза равна цели #904: коллизия видна ДО мержа, а не
после.

Если/когда #1136 и #1189 сольются и `repo_invariants.py` освободится — переоценка схемы
(например, номер = номер задачи, гарантирующий уникальность по построению) остаётся
открытым вопросом, не закрытым этим PR.

## Устройство: переиспользование `decision_numbering.py`, не вторая реализация

Носитель здесь ДРУГОЙ, чем у #1078: не каталог пронумерованных файлов, а нумерованный
список ВНУТРИ ОДНОГО файла (докстринг-реестр `repo_invariants.py`, строки вида `N.
check_имя_функции`). Это не позволяет переиспользовать
`parse_numbered_files`/`ls_tree_files_under_root`/`added_files_under_root` как есть — те
сравнивают списки файлов каталога, не строки одного файла.

Переиспользовано импортом (без копии, «Одно место правды», AGENTS.md):

- `find_number_collisions` — чистое ядро сравнения, ничего специфичного для файлов:
  принимает `{источник: {номер: [идентификатор]}}`, работает с любым строковым
  идентификатором (имя файла или имя функции — не важно).
- `run_git`, `fetch_refs`, `_local_ref`, `GitError`/`GhError`, `gh`, `open_pull_refs`,
  `build_refs`, `current_branch`, `self_source_name` — газовые/git-примитивы, не
  специфичны для каталогов.

Написано заново (специфично для реестра-в-файле, не в каталоге):

- `REGISTRY_ENTRY_RE`/`parse_registry_entries` — парсинг строк реестра из ТЕКСТА файла.
- `read_blob_at_ref` (`git show <ref>:<path>`) вместо `ls_tree_files_under_root`.
- `added_registry_entries` (`git diff --unified=0 A B -- path`, только `+`-строки,
  совпавшие с форматом реестра) вместо `added_files_under_root` — та же причина (не
  засчитывать унаследованные от main записи как «добавленные» сторонним PR), тот же
  приём (два отдельных рефа, без тройной точки — работает на shallow-клоне
  `actions/checkout@v7` без `fetch-depth: 0`).

## Живой дефект, найденный в уже слитом `decision_numbering.py` — не мой файл, не чиню здесь

При подготовке этого PR обнаружено: обязательная проверка `test` красная НА КАЖДОМ push в
`main` (`repo-ci.yml`, run 34803174089, 2026-09-14) из-за
`decision-doc-numbering-guard.sh` — на push-событии `self_name` резолвится в буквальное
`"main"`, и main считается «участником» коллизии между уже слитым номером ADR и номером,
который независимо занял сторонний, ЕЩЁ НЕ смёрженный открытый PR (`docs/decisions` 0017
против PR #944, 0018 против PR #667). Сам push, вызвавший прогон, к этой коллизии не имеет
отношения — тормоз не снимается, пока сторонний PR не решит свою судьбу (AGENTS.md,
«тормоз без газа не принимается»).

Не чиню `decision_numbering.py` этим PR — файл не входит в объём #904, инцидент заведён
отдельным issue. `invariant_numbering.py` спроектирован БЕЗ этого дефекта с первого
коммита: `cmd_check` считает `main` виновным ТОЛЬКО в коллизии внутри самого себя
(`involved == {"main"}`) — коллизия main против стороннего, ещё не смёрженного PR остаётся
на совести того PR (его собственный прогон покраснеет сам). См. докстринг
`invariant_numbering.cmd_check` — там же доказательство поведенческими тестами
(`test_cmd_check_does_not_blame_main_for_a_foreign_open_pr_collision`,
`test_cmd_check_blames_main_for_an_intra_main_duplicate`).
