# cloud-orchestrator-convergence: оркестратор живёт в облаке, три канала — один вход

Задача: #258.

Дата: 2026-09-03. Спека **C** из трёх параллельных (владелец развёл площади явно):
A — жизненный цикл задачи (состояния `ready/.../done/dropped`, бюджет реворков) —
пишется параллельно, change-id на момент написания этого файла не создан, ссылка
не проставлена сознательно (не гадать чужой id); B — контракты передачи между
ролями — та же оговорка. Эта спека — **где физически живёт оркестратор, как три
канала связи сходятся в одну точку, и как связаны состояние проекта (GitHub) и
состояние системы (DO)**. Пересечения с A/B названы явно в разделе «Границы».

Прочитано перед написанием: `AGENTS.md`, `docs/INDEX.md`,
`docs/research/30-rejected-alternatives.md` (целиком, особо п.6), `docs/decisions/`
(0001-0010), `docs/agents/PROTOCOL.md`, `docs/agents/ROADMAP.md`,
`openspec/specs/journal-tasks-hands.md`, `docs/research/10/11/12/21`, живой
GitHub (`gh api`, PR #173, issues #20, #133, #201, #207, #243, #244).

## Проблема

Дословно от владельца 2026-09-03: «там, где ты пишешь "я", должно быть не тут, у
меня в локальной сессии, а там, в облаке»; три канала (морда, Telegram, локальная
сессия) должны вести к одному и тому же «менеджеру проекта»; состояние проекта
(задачи/PR/лейблы/зависимости — GitHub) и состояние системы (сессии/события/
heartbeat — DO) должны быть связаны, а не расходиться.

Класс проблемы: слово «оркестратор» сегодня совпадает по имени с тремя разными
вещами, ни одна из которых не отвечает запросу владельца:

1. **Локальная сессия** (эта) — рассуждающий агент с полным контекстом
   репозитория, но целиком вне облака и вне журнала: результат — файлы на диске
   владельца и, в лучшем случае, ручной коммит/PR. Ничего не появляется «там»
   автоматически.
2. **`scripts/orchestra/scheduler.py`** — облачный, событийно-по-расписанию
   (`orchestra.yml`, cron 15 мин + self-wake alarm DO, `cf-worker/src/config.ts::HEARTBEAT.selfOrchestrationMs`),
   но **целиком механический**: прочитан полностью — каждая функция это сравнение
   с порогом или проверка факта GitHub API (слияние, конфликты, просрочка,
   предохранитель, повтор AI-ревью по таймеру, возврат нездоровых PR, детектор
   простоя `stall_detector.py`). Ни одного обращения к LLM.
3. **`scripts/review/ai_review.py`** — единственный сегодня облачный
   **рассуждающий**, событийный, без сохранённого состояния джоб
   (`workflow_run` -> `gather` (доверенный, GH_TOKEN) -> DSH-агент (недоверенный,
   без токена, только рассуждает) -> `verdict` (доверенный) -> умирает), но с
   ОДНОЙ задачей — ревью диффа PR, не общего назначения.

Ни один не является тем «я», которое просит владелец: сущностью, читающей
произвольное сообщение из ЛЮБОГО из трёх каналов, понимающей его, решающей, что
сделать (завести задачу, ответить, поправить документ, ничего не делать), и
отвечающей туда, откуда пришёл вопрос — через существующие единственные места
правды (GitHub Issues/PR, DO журнал), без нового хранилища состояния.

### 2. Где сегодня принимается решение оркестратора

Механические решения (правило -> действие, ЛЮБОЙ пульс, без LLM) уже в облаке —
`scripts/orchestra/scheduler.py` целиком: слияние, конфликты, просрочка, предохранитель,
петля `review:ok`-без-вердикта, возврат нездоровых PR, детектор устойчивого простоя
(`stall_detector.py`, #201). Класс «если факт X — делай Y» решён и переносить некуда.

Решения, требующие ПОНИМАНИЯ СМЫСЛА, сегодня в облаке НЕ принимаются нигде:

- ответ на произвольный вопрос владельца — либо парковка (`chat` -> `done`
  с `note: "classified_for_manual_review"`, `raw` -> `ignored` с
  `needs_manual_triage`), либо делает локальная сессия руками;
- превращение сырого текста в осмысленную задачу (заголовок, декомпозиция) —
  либо владелец уже пишет в готовой форме (`/task ...`), либо локальная сессия;
- дедупликация ПО СМЫСЛУ (не по строке) — issue #243 прямо называет её
  нерешённой и относит к классу «нужно суждение, которого нет в данных»
  (дословно из #243: «Не заводить агента с суждением там, где хватает правила...
  Агент нужен только там, где требуется решение, которого нет в данных»);
- любая архитектурная/исследовательская работа (эта самая задача — пример) —
  делает исключительно локальная сессия;
- «эта задача больше не актуальна» (issue #243) — явно требует суждения, не
  автозакрытия по таймеру.

Единственный прецедент облачного суждения — `ai_review.py`: событие
(`workflow_run`) -> джоб без сохранённого состояния -> недоверенный шаг DSH
рассуждает и отвечает текстом -> доверенный шаг разбирает ответ по контракту
(машиночитаемая строка `ВЕРДИКТ: approve|rework`) и постит вердикт наружу.
Память не хранится, весь результат — снаружи (комментарий + метка PR).
**Это шаблон, на который встаёт предлагаемый оркестратор, а не новая
архитектура.**

### 3. Связь состояний GitHub <-> DO

- Единственная связь сегодня — детерминированный ключ `harness-<N>` (N — номер
  GitHub Issue), собираемый на стороне job'а/воркера
  (`scripts/lib/dsh-edge-session.sh`, [runner-sessions-in-dsh-morde](../runner-sessions-in-dsh-morde/proposal.md)).
- **Из сессии видна задача**: да, ОДНОСТОРОННЕ и текстом — заголовок сессии
  закреплён как `#N: задача` (`session.rename` с `source:{kind:"user"}`,
  [research/12](../../../docs/research/12-dsh-edge-session-api.md)). Не
  гиперссылка — видимый текст в списке сессий морды.
- **Из задачи видна сессия**: НЕТ. Проверено: ни `dsh-edge-session.sh`, ни
  `scripts/worker/task.sh`, ни `scheduler.py` не постят в Issue ссылку/упоминание
  сессии `harness-<N>` или URL морды.
- Дублирование: счётчик статусов сообщений живёт только в `messages` (DO,
  `cf-worker/src/harness.ts`, поле `Status.messages`); факт «по сообщению создана
  задача» — в JSON-поле `result` той же строки; сама задача — обычный GitHub
  Issue (`task, source:inbox`). Обратной машиночитаемой ссылки «Issue -> id
  сообщения» нет: тело issue содержит человекочитаемый заголовок
  `## Сообщение владельца (inbox #N)` (заголовок собирается в payload
  `#dispatchIssueCreation`,
  `cf-worker/src/harness.ts`), это связь ТОЛЬКО в одну сторону и только текстом.
- Итог: связь GitHub<->DO существует в ДВУХ независимых парах
  (`Issue<->сессия морды`, `Issue<->сообщение DO`), обе однонаправленные и текстовые,
  ни одна не структурное поле — обе расходятся молча при переименовании/архивации
  одной стороны без другой.

  строки); регистрацию делает `.github/workflows/telegram-webhook.yml`

  события в сессию через `ingest`, но сегодня это делают только job'ы КОНКРЕТНОЙ

- Egress `api.github.com` из **`dsh-edge`** (не `cf-worker`!) заблокирован и
  измерен (#133, `state: open`); контрольный факт — тот же PAT из GitHub Actions
  job получает 200 на тот же endpoint. `cf-worker` — другой воркер, другой egress:
  `repository_dispatch`/`workflow_dispatch` из cf-worker доказаны
  (`cf-worker/src/harness.ts::attemptOrchestraDispatch`/
  `::#checkDshEdgeUpdate`/`::#postTask`/`::#dispatchIssueCreation` — искать
  по имени функции, номера строк дрейфуют между ребейзами); прямого
  `POST /issues` из cf-worker по ADR 0015 больше не существует (находка
  ревью PR #262, пятый раунд — прежняя редакция этой строки описывала
  смёрженный план PR #173, позже заменённый ADR 0015).
  Не путать эти два egress при проектировании.

## Границы

**In scope:** единая точка входа сообщений (очередь); диспетчер (что поднимает
оркестратор-джоб и когда, с батчингом под лимит 500 dispatch/час); модель
исполнения оркестратора (без состояния, где физически, чем ограничен);
идентичность ответа (канал ответа = канал происхождения, с конкретным адресатом,
не просто фактом отправки); аутентификация владельца на каждом канале; связь
GitHub<->DO без дублирования; честный потолок.

**Out of scope:**
- состояния/переходы задачи, бюджет реворков, метрики цикла — спека A;
- формат артефакта на стадии и чеклист приёмки между ролями — спека B;
- regex-классификация текста (`directive/doc_edit/chat/raw`) — уже в PR #173, не
  переписывается. Адресата (оркестратор) получает ТОЛЬКО ветка `chat` —
  сегодня тупиковая (`done` с `classified_for_manual_review`): требование 3
  `specs/orchestrator-dispatch/spec.md`. `raw` остаётся на ручном триаже
  (`ignored`, `needs_manual_triage`) и диспетчеру не подставляется — он его
  «не увидит никогда» (там же, «Честно про kind='raw'»); расширение
  классификатора на широкий `raw` — отдельная задача пула #1198 (находка
  ревью PR #262, девятый раунд: прежняя редакция этой строки обещала
  адресата обеим тупиковым веткам, противореча собственной дельте п.35);
- конкретные инварианты `repo_invariants.py` (#244, закрыта 2026-09-06) и
  реестр меток (#207, закрыта 2026-09-04) — слиты в main (обновлено
  находкой ревью PR #262, десятый раунд: на момент написания спеки обе
  значились «в работе»), не дублируются, только называется точка интеграции;
- починка парсинга `ВЕРДИКТ:` в `ai_review.py` — параллельный change
  `input-schema-not-output-parsing`. Зависимость «без неё второй гейт не
  даёт `ai:ok`, PR не сливается» описывала до-мержное состояние PR #173:
  смержен 2026-09-05 (`tasks.md`, 0a), риск несмерженности снят. Сам
  change остаётся открытым предусловием 0b — устойчивость парсинга
  вердиктов, не блокировка конкретного PR.

## Пересечения — кому оставить

- Спека A владеет состояниями артефакта; здесь — только факт «кто физически
  меняет состояние» (оркестратор-джоб как один из исполнителей перехода, наравне
  с воркером и мерж-оркестратором).
- Спека B владеет форматом артефакта между стадиями; сюда передаётся только
  «откуда сообщение и что от него требуется» (ответ/задача/правка документа), без
  диктовки формы задачи.
- Реестр жизненных циклов (#243) и инварианты (#244) не переписываются — названы
  как источники находок, стекающихся в ту же точку, что и сообщения владельца
  (design.md, «Единая очередь»).

## Acceptance criteria

1. По каждому из трёх каналов назван факт «есть/нет/где код» с проверяемой
   ссылкой (file:line или вывод `gh api`) — выполнено в замерах выше.
2. `design.md` называет минимум три архитектурные развилки с ценой и явным
   условием пересмотра.
3. Дельта-спека (`specs/orchestrator-dispatch/spec.md`) содержит проверяемые
   сценарии (Given/When/Then) для: приёма сообщения по каждому каналу,
   диспетчеризации, идентичности ответа, аутентификации, связи GitHub<->DO.
4. `tasks.md` называет минимальный первый шаг отдельно от полного объёма, с
   обоснованием.
5. Раздел «Честный потолок» называет минимум одну вещь, недостижимую бесплатно,
   с названной ценой.

## Риски / неизвестности

- PR #173 смёржен 2026-09-05 (`tasks.md`, 0a) — эта спека проектирует
  поверх смёрженного кода, риск несмерженности снят. Остаётся риск
  РЕВАЛИДАЦИИ: существенная переработка кода инбокса потребует ревалидации
  таблицы «есть/нет» (находка ревью PR #262 — прежняя редакция описывала
  #173 как не слитый вторым гейтом).
- Создание issue из DO уже идёт через dispatch (ADR 0015: `#dispatchIssueCreation`
  -> `repository_dispatch` `inbox-issue` -> job `inbox-issue.yml` штатным
  `github.token` -> callback `#postIssueCreated`) — «фолбэк» из прежней
  редакции этого пункта («если прямой REST заблокирован — уйти на dispatch»)
  и есть сегодняшняя реализация; развилки «прямой REST vs dispatch» не
  существует (находка ревью PR #262, пятый раунд: прежняя редакция
  описывала заменённый мир ADR 0011). Вывод «egress `cf-worker` ≠ egress
  `dsh-edge`» не меняется — доказательство egress cf-worker: сами
  `repository_dispatch`/`workflow_dispatch` (`attemptOrchestraDispatch`/
  `#checkDshEdgeUpdate`/`#postTask`/`#dispatchIssueCreation`).
- Владелец не подтвердил бюджет — если честный потолок (design.md) неприемлем,
  часть решения требует пересмотра варианта архитектуры (развилка 1).
