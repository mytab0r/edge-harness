# Дельта-спека: orchestrator-dispatch

Новый домен (в `openspec/specs/` пока нет спеки-родителя для оркестратора —
единственная существующая, `journal-tasks-hands.md`, описывает журнал/задачи/
heartbeat и не покрывает суждение). После применения change'а этот файл
переносится в `openspec/specs/orchestrator-dispatch.md` как источник правды.

**Пересечение с базовой спекой названо явно, не молчаливым «новый домен
не покрывает»** (находка ревью PR #262, второй раунд, п.1): жизненный цикл
самой строки `messages` (статусы, захват, `chat` → `done`) уже описан
`journal-tasks-hands.md` пп. 33/35 — этот change его МЕНЯЕТ, дельта против
конкретных пунктов — в `../journal-tasks-hands/spec.md` рядом. Здесь, в
новом домене, описывается только само СУЖДЕНИЕ (кто и как решает, что делать
дальше) — то, чего в базовой спеке действительно нет.

Требования пронумерованы заново (домен новый); каждое несёт сценарий в форме
Given/When/Then для проверки. Формат текста сообщения, регэксп-классификация
`directive/doc_edit/chat/raw` и создание Issue для `directive` — вне этой
спеки (уже реализовано PR #173, не переопределяется).

## Единая очередь сообщений

1. Сообщение, поступившее по каналу с очередью (Telegram-вебхук, RPC морды
   dsh-edge), в конечном счёте представлено ровно одной строкой в ровно
   одном хранилище (`messages` Harness DO). Локальная сессия — не этот
   случай: она читает состояние GitHub нативно (issues/PR) без адаптера и
   без записи в `messages` (см. требование 7 — правка находки AI-ревью
   PR #262, второй раунд: ссылка на «требование 6» была битой, и
   универсальная формулировка «по любому из трёх каналов» тут же
   противоречила себе для локальной сессии).

   Сценарий (условно — находка ревью PR #262, второй раунд, п.4;
   ревизия 2026-09-14, седьмой раунд, п.1: транспорт морды — не вопрос
   замера, а решение о пути записи, `design.md` «Канал морды»;
   `session_id` не существует как колонка `messages` и на HEAD; сценарий
   действует после реализации канала морды, до этого — один канал,
   Telegram): Дано —
   сообщение пришло в Telegram и в морду за один и тот же интервал времени.
   Когда — оба обработаны диспетчером. Тогда — в `messages` ровно две
   строки (по одной на канал), обе с непустым `source` и `chat_id`/
   `session_id` (колонка `session_id` заводится тем же PR, что реализует
   этот канал — сегодня в схеме `messages` её нет, `cf-worker/src/harness.ts`),
   и НИ ОДНА не хранится где-либо ещё (нет второй копии текста сообщения в
   отдельной таблице/файле).

2. Приём сообщения по любому каналу не блокирует и не ждёт ответа оркестратора
   — запись в очередь и обработка разделены во времени (событие → диспетч →
   отдельный джоб).

   Сценарий: Дано — Telegram-вебхук получил сообщение. Когда — DO записал
   строку в `messages` и вернул `201` вызывающей стороне (Telegram).
   Тогда — HTTP-ответ вебхука приходит до того, как оркестратор-джоб успел
   бы стартовать (диспетч — асинхронный `fire-and-forget`, не `await` ответа
   джоба).

## Диспетчер поднимает оркестратор-джоб по событию

3. Разбор, классифицировавший сообщение как требующий суждения
   (`kind='chat'`), инициирует `workflow_dispatch`/
   `repository_dispatch` НА ТОМ ЖЕ тике разбора — тот же паттерн, что уже
   доказан (`cf-worker/src/harness.ts::attemptOrchestraDispatch`/
   `::#checkDshEdgeUpdate`/`::#postTask` — искать по имени функции, номера
   строк дрейфуют между ребейзами). Момент диспетча назван точно (находка
   ревью PR #262, третий раунд, п.1 — прежний сценарий вешал диспетч на
   завершение `#postMessageIngest`, где `kind` всегда `'raw'`: `#putMessage`
   вставляет строку захардкоженным `'raw', 0, 'new'`, а `chat` появляется
   только при захвате в `#processSingleMessage`, то есть на тике; «дано
   `kind='chat'`» и «когда ingest завершился» не выполняются одновременно
   никогда). Классификация НЕ переезжает на ingest: разбор — с ОДНИМ
   водителем (п.33 базовой спеки, оговорка к нему в
   `../journal-tasks-hands/spec.md`), второй драйвер разбора — тот класс
   отложенного рецидива, против которого правила репозитория. Чтобы «на том
   же тике» не выродилось в полное ожидание 15-минутного темпа (ровно за это
   отвергнут вариант B развилки 2 в design.md), приём свежего сообщения
   закладывает ОДНОРАЗОВЫЙ ближний alarm (порядка существующей
   `HEARTBEAT.selfOrchestrationFirstMs`, и только если уже заложенный тик
   не раньше): ускоряется ТОТ ЖЕ тик разбора — второй механизм, второй
   классификатор и второй захват не появляются. `kind='doc_edit'`
   в это множество НЕ входит: на `main` он уже мержен как механический
   путь наравне с `directive` (`#processSingleMessage` — оба ведут в
   создание issue), и диспетчить его ЕЩЁ и сюда значило бы завести issue
   МЕХАНИЧЕСКИМ путём и одновременно поднять джоб оркестратора по тому же
   сообщению — двойное действие на одно сообщение (находка AI-ревью
   PR #262). Если суждение над `doc_edit` понадобится позже — это отдельное
   решение с явным гашением механического пути, не молчаливое добавление в
   список kind'ов здесь.

   Честно про `kind='raw'` (находка AI-ревью PR #262, второй раунд):
   `#classifyMessage` узок — chat-регэксп
   ловит только вопросительный знак или начало «как/почему/что думаешь/
   мнение/вопрос»; всё остальное свободное сообщение владельца, не
   подошедшее ни под директиву, ни под правку дока, ни под этот узкий
   вопрос, падает в `raw` и уходит в `ignored` на РУЧНОЙ триаж — диспетчер
   этой спеки его не увидит никогда. Это самый большой класс произвольных
   сообщений, и это молчаливое сужение обещания «оркестратор понимает
   ЛЮБОЕ сообщение» из `proposal.md`. Явный выбор ЭТОЙ спеки: `raw`
   ОСТАЁТСЯ на ручном триаже — минимальный шаг диспетчирует только то, что
   классификатор уже уверенно называет суждением (`chat`), расширение
   классификатора на широкий `raw` — отдельная задача пула (#1198) с
   отдельным критерием (риск ложных срабатываний диспетча на шум).

   Сценарий: Дано — сообщение принято (`#postMessageIngest`), записано
   `#putMessage` как `raw`/`new`, одноразовый alarm ускорил ближайший тик.
   Когда — тик DO (`alarm()` -> `#processInbox` -> `#processSingleMessage`)
   захватил сообщение и классифицировал его как `chat`. Тогда — НА ТОМ ЖЕ
   тике инициирован HTTP-запрос на
   `POST /repos/{repo}/actions/workflows/orchestrator-message.yml/dispatches`
   (или `repository_dispatch` с отдельным `event_type`) — НЕ уже
   существующий `orchestra.yml` (15-минутный пульс, тот же класс диспатча,
   но другой workflow, этот change его не трогает), best-effort (сбой
   диспетча не роняет разбор — по образцу `dispatch_worker` в
   `scheduler.py`), а сообщение остаётся в захваченном `processing` и ждёт
   результат джоба (владение окном — требование 4).

4. Диспетч использует ТУ ЖЕ модель попыток, что уже есть у `messages`
   (`attempts`/`LIMITS.messageMaxAttempts`, инкремент при захвате) — новый
   параллельный счётчик (`MESSAGE_DISPATCH_MAX_ATTEMPTS` в
   `pulse_guard`/`orchestra.yml`) НЕ заводится: второй драйвер одной
   очереди — тот класс отложенного рецидива, против которого правила
   репозитория (находка AI-ревью PR #262). Неудачный диспетч ведётся как
   повторяемая ошибка issue-пути: захват возвращается в `new`, подбор
   следующим тиком; терминальный `failed` — уже существующий кап
   `LIMITS.messageMaxAttempts` через уже существующий `#reclaimStuckMessages`;
   газ ручной, тот же, что у остальных зависших сообщений: `retry_failed`
   возвращает в `new`. Отдельной эскалации Telegram для этого класса не
   заводится — она дублировала бы уже видимое в `/api/messages` состояние
   `failed`.

   Владение окном диспетча (находка ревью PR #262, третий раунд, п.2 —
   прежняя редакция переиспользовала ватчдог как есть, и полный круг
   джоба «очередь GitHub Actions + рассуждение + запись результата»,
   изредка часы по «Честному потолку» design.md, переживал бы следующий
   тик: реclaim в `new`, повторный dispatch, второй ответ владельцу, а на
   третьей попытке — `failed` со `stuck_reclaimed`, пока первый джоб ещё
   мог вернуться с ответом; это тот же класс «двойное действие на одно
   сообщение», которым обосновано исключение `doc_edit`, и тот же класс,
   для которого код уже держит гвардию «таймаут заведомо меньше ватчдога»
   в `config.ts::LIMITS.messageIssueDispatchTimeoutMs`):
   - джоб при старте и на каждом длинном шаге ПРОДЛЕВАЕТ захват (CAS по
     своему моменту захвата — тем же механизмом, что запись результата,
     `#finishMessage`); захват, продлеваемый живым джобом, ватчдог не
     трогает: порог `LIMITS.messageStuckProcessingMs` отсекает мёртвые
     захваты, а не медленные живые;
   - НОСИТЕЛЬ ВЛАДЕНИЯ НАЗВАН (находка ревью PR #262, седьмой раунд,
     п.2): продление обновляет `processing_ts` (то же поле, по которому
     ватчдог п.36 считает возраст и п.33 делает CAS) и ВОЗВРАЩАЕТ ДЖОБУ
     новое значение владения; все последующие CAS джоба — включая
     финальную запись результата — ведутся по НОВОМУ значению, а не по
     моменту первоначального захвата. Иначе «CAS по своему моменту
     захвата» ломается уже на втором продлении: живой, всё сделавший
     джоб не прошёл бы CAS и молчал — ровно повторный dispatch и второй
     ответ, против которых требование написано. Отдельного поля владения
     не заводится — пп. 33/36 базовой спеки остаются буквальными без
     дополнительных дельт;
   - ГАРАНТИЯ ПРОДЛЕНИЯ НАЧИНАЕТСЯ СО СТАРТА ДЖОБА (находка ревью
     PR #262, шестой раунд, п.1): джоб физически не может продлевать
     захват до того, как стартовал. Джоб, застрявший в очереди GitHub
     Actions ДОЛЬШЕ порога ватчдога, теряет захват до своего первого
     продления — путь такой задержки назван как есть: повторные dispatch
     до капа `LIMITS.messageMaxAttempts`, затем видимый `failed` со
     `stuck_reclaimed`, газ — ручной `retry_failed`. Механизм с заведомо
     бОльшим порогом ватчдога для dispatched-сообщений сознательно НЕ
     заводится: у него нужен был бы отдельный газ для джоба, умершего до
     старта, — второй порог правды;
   - ответ в канал отправляется ТОЛЬКО после успешной CAS-записи
     результата: джоб, потерявший владение (продления прекратились,
     ватчдог вернул сообщение в `new`, тик пере-dispatchил его второму
     джобу), молчит — владелец получает ОДИН ответ, от действующего
     владельца захвата. Отдельная дедупликация по id сообщения на стороне
     джоба не заводится — её роль играет сам CAS владения;
   - окно «ноль ответов» названо (находка ревью PR #262, шестой раунд):
     неудача отправки в канал ПОСЛЕ успешной CAS-записи не откатывает
     результат — сообщение остаётся `done`, а неотправка фиксируется в
     `messages.result` (исход отправки), поэтому окно «результат записан,
     владелец ничего не получил» ВИДНО в состоянии строки; повторная
     доставка — ручной газ (перечитать сообщение и отправить результат
     заново), не молчаливая потеря.

   Сценарий: Дано — сообщение `kind='chat'` захвачено тиком в
   `processing`, диспетч не удался (сеть/5xx). Когда — захват честно
   возвращён в `new` по образцу `issue_retry`, очередной тик DO
   (`alarm()` -> `#processInbox`) подбирает сообщение снова. Тогда —
   `attempts` уже инкрементирован самим захватом, повторный диспетч
   инициируется из этого же тика — без второго счётчика.

   Сценарий: Дано — диспетч/джоб по сообщению падает стабильно (например,
   `orchestrator-message.yml` красный), кап попыток `LIMITS.messageMaxAttempts`
   достигнут. Когда — `#reclaimStuckMessages` (уже существующая
   гвардия зависших `processing`) видит исчерпанный кап на очередном тике.
   Тогда — сообщение переходит в терминальный `failed` со
   `stuck_reclaimed` (уже реализованное поведение, не новое); газ ручной,
   `retry_failed`.

   Сценарий (медленный живой джоб — гарантия уже стартовавшего): Дано —
   dispatch принят, джоб стартовал и успел продлить захват в пределах
   порога `LIMITS.messageStuckProcessingMs`, работа идёт дольше порога.
   Когда — очередной тик DO запускает `#reclaimStuckMessages`. Тогда —
   продлённый захват не реclaimится: ни повторного dispatch, ни второго
   ответа владельцу, `attempts` не растут.

   Сценарий (очередь дольше порога — защита НЕ действует, названо честно,
   находка ревью PR #262, шестой раунд, п.1): Дано — джоб стартовал из
   очереди ПОЗЖЕ порога `LIMITS.messageStuckProcessingMs` (гарантированного
   потолка очереди GitHub-hosted нет — research/21), первый тик ватчдога
   реclaimил сообщение до его первого продления. Когда — опоздавший джоб
   вернулся с ответом. Тогда — его CAS не проходит, он молчит; сообщение
   к этому моменту пере-dispatchено, `attempts` растут до капа, при
   исчерпании — видимый `failed` со `stuck_reclaimed`, газ — ручной
   `retry_failed`. Спека НЕ обещает доставки в этом случае — она видима
   (статус/счётчики), не молчалива.

   Сценарий (второе продление после первого — находка ревью PR #262,
   седьмой раунд, п.2): Дано — джоб продлил захват один раз, владение у
   него значения `T1` (обновлённый `processing_ts`), работа продолжается.
   Когда — джоб продлевает захват второй раз и затем пишет финальный
   результат. Тогда — второе продление вернуло владение `T2`, финальный
   CAS ведётся по `T2` и ПРОХОДИТ; ватчдог между продлениями видит
   возраст от `T1`/`T2`, а не от первоначального захвата, и не
   реclaimит.

   Сценарий (потеря владения): Дано — джоб не смог продлить захват,
   ватчдог вернул сообщение в `new`, тик пере-dispatchил его второму
   джобу. Когда — первый джоб всё же вернулся с ответом и пишет результат
   CAS'ом по СВОЕМУ моменту захвата. Тогда — CAS не проходит (владение
   потеряно), и джоб НЕ отправляет ответ в канал; владелец получает ровно
   один ответ — от второго джоба.

5. Дневной темп сообщений, требующих диспетча, не превышает лимит
   GitHub-триггеров (500/час, `docs/research/21-github-actions.md`); при
   приближении к лимиту диспетчер батчит несколько сообщений в один
   dispatch, а не шлёт по одному.

   Сценарий: Дано — за минуту накопилось 20 новых сообщений, требующих
   суждения. Когда — диспетчер отрабатывает очередной цикл. Тогда — сделан
   ОДИН dispatch с несколькими id сообщений в `client_payload` (до 10
   top-level свойств, лимит `repository_dispatch`), а не 20 отдельных
   вызовов.

## Оркестратор без сохранённого состояния

6. Оркестратор-джоб не имеет памяти между запусками: любое решение
   опирается только на данные, читаемые заново из GitHub (issues/PR/labels)
   и DO (`/api/status`, `/api/messages`) в момент запуска.

   Сценарий: Дано — джоб оркестратора обработал сообщение и упал/был убит
   ДО записи результата. Когда — тот же джоб (или его повтор) запускается
   заново по тому же сообщению. Тогда — повторный запуск не полагается ни на
   какое состояние процесса первой попытки (переменные, файлы вне
   контрольного чекаута) — читает те же источники правды заново и приходит к
   тому же или согласованному решению; идемпотентность результата
   обеспечивается статусом сообщения (`processing` -> `done`/`failed`) и
   CAS-владением окном диспетча (требование 4), а не
   памятью джоба.

7. Локальная сессия (если используется как терминал оркестратора вручную) не
   является требованием для работы облачного пути — облачный оркестратор
   функционирует и отвечает без участия локальной сессии.

   Сценарий: Дано — локальная сессия владельца не запущена (машина выключена).
   Когда — приходит сообщение в Telegram. Тогда — оркестратор-джоб всё равно
   стартует и отвечает — без обращения к локальной машине владельца.

## Идентичность ответа

8. Ответ оркестратора уходит в тот же канал и тому же адресату, откуда
   пришло исходное сообщение, используя поле, сохранённое при приёме
   (`chat_id` для Telegram — реализуется этим change; `session_id`/RPC для
   морды — УСЛОВНО, находка ревью PR #262, второй раунд, п.4: колонка
   `session_id` в `messages` не существует, канал морды гейтится решением
   о пути записи (`design.md` «Канал морды»), эта часть требования
   реализуется вместе с требованием 9, не раньше).

   Сценарий: Дано — сообщение пришло из Telegram-чата с `chat_id=X`, не
   совпадающего с дефолтным `TELEGRAM_CHAT_ID` эскалаций. Когда —
   оркестратор сформировал ответ. Тогда — `sendMessage` уходит именно в
   `chat_id=X` (функция отправки принимает `chat_id` параметром, не читает
   его из константы окружения).

9. Ответ на сообщение из морды dsh-edge появляется в чате морды, а не только
   в GitHub/Telegram. Требование УСЛОВНО, но условие — РЕШЕНИЕ, не замер
   (находка ревью PR #262, седьмой раунд, п.1 — прежняя редакция гейтила
   «замером 0c», отвеченным репозиторием: `research/20` — 1042 для
   `*.workers.dev`, `research/12` — причина 403 снята, #133 закрыт):
   гейт — явный выбор пути записи из морды в журнал (service binding
   `HARNESS_SERVICE` против прямого GitHub из морды), `design.md`
   «Канал морды»; до решения требование не реализуется.

   Сценарий: Дано — сообщение пришло через RPC морды (`session.prompt`).
   Когда — оркестратор сформировал ответ. Тогда — ответ доставлен в ТУ ЖЕ
   сессию морды через `ingest`-примитив (`scripts/lib/dsh-edge-session.sh`
   или его развитие), видим владельцу в UI чата без обращения к GitHub.

10. Действие, видимое во всех каналах одинаково (например, «создана задача
    #N»), не расходится по формулировке между каналами: текст ответа строится
    из одних и тех же полей результата (номер задачи, статус), не
    дублируется независимым текстом в каждом адаптере.

    Сценарий: Дано — оркестратор создал Issue #500 по сообщению из Telegram.
    Когда — формируется ответ. Тогда — тот же результат (`issue_number=500`,
    `issue_url`), уже сохранённый в `messages.result`, форматируется в текст
    ответа — не запрашивается и не формулируется заново отдельным кодом для
    каждого канала.

## Аутентификация владельца на каждом канале

11. Вебхук Telegram отклоняет запросы, не подтверждённые секретом заголовка
    или не соответствующие известному `chat_id`, до того, как сообщение
    попадёт в очередь как «сообщение владельца». **УЖЕ РЕАЛИЗОВАНО**
    (находка ревью PR #262, пятый раунд — прежняя редакция называла это
    предстоящей работой): гейт слит (#254, ADR 0014, PR #486) —
    `#telegramWebhookAuthorized` (constant-time сверка
    `X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_WEBHOOK_SECRET`) плюс
    `#ownerChatAuthorized` (401 до записи строки, если `chat_id` не
    совпал с владельцем), регистрацию делает
    `.github/workflows/telegram-webhook.yml`. Живой статус регистрации
    вебхука у Telegram — `proposal.md`, «Не подтверждено», в объём этого
    change не входит.

    Сценарий: Дано — POST на `/api/messages/ingest` (гейт стоит на этом
    эндпоинте; эндпоинта `/api/messages/webhook`, названного прежней
    редакцией сценария, не существует) с валидным JSON, но БЕЗ заголовка
    `X-Telegram-Bot-Api-Secret-Token` (или с `chat_id`, не совпадающим с
    доверенным). Когда — вебхук обрабатывает запрос. Тогда — запрос
    отклонён (401) ДО записи строки в `messages`, и это отклонение
    проверяемо тестом на прод-форме данных (реальный Telegram update JSON,
    как того требует правило репозитория «тест кормится прод-формой»).

12. Морда dsh-edge не требует дополнительной проверки — используется
    существующая owner-кука; эта спека не ослабляет и не дублирует её.

    Сценарий: Дано — RPC-запрос без валидной куки `__Host-dsh_edge_owner`.
    Когда — запрос доходит до dsh-edge. Тогда — отклонён штатным механизмом
    морды (уже так сегодня, до этой спеки) — оркестратор не получает
    сообщение вовсе, ему не нужно проверять авторство повторно.

## Связь GitHub<->DO без дублирования

13. Issue, созданный оркестратором (или уже существующим механизмом PR #173)
    из сообщения, несёт машиночитаемую ссылку на исходное сообщение;
    инварианты (#244) могут проверить пару в обе стороны без дополнительного
    похода в DO за текстом.

    Сценарий: Дано — оркестратор создал Issue из сообщения `id=42`. Когда —
    инвариант читает тело Issue. Тогда — находит строку
    `<!-- inbox-message: 42 -->`, парсит id регулярным выражением, сверяет с
    `messages.id=42` и не находит рассинхрона (оба указывают друг на друга).

14. Сессия раннера `harness-<N>`, если задача обсуждалась через оркестратор,
    доступна из Issue `#N` не только как заголовок сессии, но и как явное
    упоминание в Issue (комментарий или поле), без необходимости знать
    формулу ключа `harness-<N>` заранее.

    Сценарий: Дано — задача `#N` получила сессию раннера. Когда — владелец
    открывает Issue `#N` в GitHub. Тогда — видит комментарий/упоминание,
    указывающее на сессию морды (минимум — session-id текстом; полная форма —
    кликабельная ссылка, если dsh-edge отдаёт постоянный URL — см.
    «Не подтверждено» в `design.md`).

15. Ни одно новое требование этой спеки не создаёт третьего хранилища
    состояния сообщений/сессий/задач: единственные места правды остаются
    GitHub (issues/PR/labels) и Harness DO (`messages`, `tasks`, `events`).

    Сценарий: Дано — реализация по этой спеке завершена. Когда — считается
    число мест, где хранится статус обработки сообщения. Тогда — их РОВНО
    ОДНО (`messages.status` в DO), а не отдельная таблица/файл у
    оркестратора.
