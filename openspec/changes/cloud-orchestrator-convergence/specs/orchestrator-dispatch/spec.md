# Дельта-спека: orchestrator-dispatch

Новый домен (в `openspec/specs/` пока нет спеки-родителя для оркестратора —
единственная существующая, `journal-tasks-hands.md`, описывает журнал/задачи/
heartbeat и не покрывает суждение). После применения change'а этот файл
переносится в `openspec/specs/orchestrator-dispatch.md` как источник правды.

Требования пронумерованы заново (домен новый); каждое несёт сценарий в форме
Given/When/Then для проверки. Формат текста сообщения, регэксп-классификация
`directive/doc_edit/chat/raw` и создание Issue для `directive` — вне этой
спеки (уже реализовано PR #173, не переопределяется).

## Единая очередь сообщений

1. Любое сообщение, поступившее по любому из трёх каналов (Telegram-вебхук,
   RPC морды dsh-edge, прямое действие локальной сессии), в конечном счёте
   представлено ровно одной строкой в ровно одном хранилище (`messages`
   Harness DO для Telegram/морды; для локальной сессии — адаптер не нужен,
   см. требование 6). **Нога морды (RPC dsh-edge -> `messages`) — тот же
   неподтверждённый транспорт, что и в требовании 9 (design.md, "Канал
   морды — открытый спайк"): реализуется только после замера 0c
   (`tasks.md`) — проходит ли исходящий `fetch` из воркера dsh-edge на
   адрес `cf-worker`. До замера требование 1 действует полностью для
   Telegram и локальной сессии; для морды — не реализуется.**

   Сценарий: Дано — сообщение пришло в Telegram и в морду за один и тот же
   интервал времени. Когда — оба обработаны диспетчером. Тогда — в `messages`
   ровно две строки (по одной на канал), обе с непустым `source` и `chat_id`/
   `session_id`, и НИ ОДНА не хранится где-либо ещё (нет второй копии текста
   сообщения в отдельной таблице/файле). Применимо к ноге морды только после
   замера 0c (см. выше).

2. Приём сообщения по любому каналу не блокирует и не ждёт ответа оркестратора
   — запись в очередь и обработка разделены во времени (событие → диспетч →
   отдельный джоб).

   Сценарий: Дано — Telegram-вебхук получил сообщение. Когда — DO записал
   строку в `messages` и вернул `202`/`201` вызывающей стороне (Telegram).
   Тогда — HTTP-ответ вебхука приходит до того, как оркестратор-джоб успел
   бы стартовать (диспетч — асинхронный `fire-and-forget`, не `await` ответа
   джоба).

## Диспетчер поднимает оркестратор-джоб по событию

3. Запись нового сообщения со статусом, требующим суждения (`chat`/`doc_edit`
   либо явная метка «нужен оркестратор»), немедленно инициирует
   `workflow_dispatch`/`repository_dispatch` того же паттерна, что уже
   доказан (`cf-worker/src/harness.ts:238,1140,1188`).

   Сценарий: Дано — новое сообщение с `kind='chat'` записано в `messages` со
   статусом `new`. Когда — DO завершает обработку `#postMessageWebhook`/RPC.
   Тогда — в течение того же вызова DO инициирован HTTP-запрос на
   `POST /repos/{repo}/actions/workflows/orchestrator.yml/dispatches` (или
   `repository_dispatch` с отдельным `event_type`), best-effort (сбой
   диспетча не роняет приём сообщения — по образцу `dispatch_worker` в
   `scheduler.py`).

4. Если немедленный диспетч не удался или сообщение осталось необработанным
   дольше порога, очередной пульс `orchestra.yml` подбирает его как
   подстраховку — без дублирования обработки. Повтор ОГРАНИЧЕН: потолок
   попыток `MESSAGE_DISPATCH_MAX_ATTEMPTS` (по образцу существующего в main
   `AI_REVIEW_MAX_ATTEMPTS`, `scripts/orchestra/pulse_guard.py:83` — тормоз
   без потолка это класс дефекта, за который репозиторий уже платил,
   #196/#205) и терминальный статус `failed` при исчерпании — не бесконечный
   повтор каждые 15 минут против общего бюджета 500 dispatch/час.

   Сценарий: Дано — сообщение в статусе `new` старше `N` минут (диспетч не
   удался или был потерян). Когда — срабатывает очередной пульс
   `orchestra.yml`, попыток диспетча по этому сообщению меньше
   `MESSAGE_DISPATCH_MAX_ATTEMPTS`. Тогда — сообщение диспетчится повторно
   РОВНО ОДИН раз за пульс, счётчик попыток инкрементируется, и переход
   `new -> processing` в `messages` делает повторный подбор тем же или
   параллельным пульсом невозможным (идемпотентность по полю `status`, тот
   же приём, что `merge_queue`/`worker_runs_active` в `scheduler.py`).

   Сценарий: Дано — джоб оркестратора по сообщению падает стабильно
   (например, `orchestrator.yml` красный), попыток диспетча уже
   `MESSAGE_DISPATCH_MAX_ATTEMPTS`. Когда — срабатывает очередной пульс.
   Тогда — сообщение НЕ диспетчится в `MESSAGE_DISPATCH_MAX_ATTEMPTS+1`-й
   раз: статус переходит в терминальный `failed`, эскалация владельцу тем
   же каналом, что уже существует (`pulse_guard.escalate`, Telegram,
   `scripts/orchestra/pulse_guard.py:400`) — тормоз без штурма общего
   бюджета, с названным газом (ручное вмешательство владельца снимает
   `failed` и возвращает в `new`).

5. Дневной темп сообщений, требующих диспетча, не превышает лимит
   GitHub-триггеров (500/час, `docs/research/21-github-actions.md`); при
   приближении к лимиту диспетчер батчит несколько сообщений в один
   dispatch, а не шлёт по одному.

   Сценарий: Дано — за минуту накопилось 20 новых сообщений, требующих
   суждения. Когда — диспетчер отрабатывает очередной цикл. Тогда — сделан
   ОДИН dispatch с несколькими id сообщений в `client_payload` (до 10
   top-level свойств, лимит `repository_dispatch`), а не 20 отдельных
   вызовов.

## Оркестратор без сохранённого состояния

6. Оркестратор-джоб не имеет памяти между запусками: любое решение
   опирается только на данные, читаемые заново из GitHub (issues/PR/labels)
   и DO (`/api/status`, `/api/messages`) в момент запуска.

   Сценарий: Дано — джоб оркестратора обработал сообщение и упал/был убит
   ДО записи результата. Когда — тот же джоб (или его повтор) запускается
   заново по тому же сообщению. Тогда — повторный запуск не полагается ни на
   какое состояние процесса первой попытки (переменные, файлы вне
   контрольного чекаута) — читает те же источники правды заново и приходит к
   тому же или согласованному решению; идемпотентность результата
   обеспечивается статусом сообщения (`processing` -> `done`/`failed`), а не
   памятью джоба.

7. Локальная сессия (если используется как терминал оркестратора вручную) не
   является требованием для работы облачного пути — облачный оркестратор
   функционирует и отвечает без участия локальной сессии.

   Сценарий: Дано — локальная сессия владельца не запущена (машина выключена).
   Когда — приходит сообщение в Telegram. Тогда — оркестратор-джоб всё равно
   стартует и отвечает — без обращения к локальной машине владельца.

## Идентичность ответа

8. Ответ оркестратора уходит в тот же канал и тому же адресату, откуда
   пришло исходное сообщение, используя поле, сохранённое при приёме
   (`chat_id` для Telegram, `session_id`/RPC для морды).

   Сценарий: Дано — сообщение пришло из Telegram-чата с `chat_id=X`, не
   совпадающего с дефолтным `TELEGRAM_CHAT_ID` эскалаций. Когда —
   оркестратор сформировал ответ. Тогда — `sendMessage` уходит именно в
   `chat_id=X` (функция отправки принимает `chat_id` параметром, не читает
   его из константы окружения).

9. Ответ на сообщение из морды dsh-edge появляется в чате морды, а не только
   в GitHub/Telegram. **Реализуется ТОЛЬКО ПОСЛЕ подтверждения транспорта
   замером 0c (`tasks.md`) — до замера это требование не реализуется, канал
   морды остаётся открытым спайком (design.md).**

   Сценарий: Дано — замер 0c подтвердил, что `fetch` из воркера dsh-edge на
   `cf-worker` проходит, И сообщение пришло через RPC морды (`session.prompt`).
   Когда — оркестратор сформировал ответ. Тогда — ответ доставлен в ТУ ЖЕ
   сессию морды через `ingest`-примитив (`scripts/lib/dsh-edge-session.sh`
   или его развитие), видим владельцу в UI чата без обращения к GitHub.

10. Действие, видимое во всех каналах одинаково (например, «создана задача
    #N»), не расходится по формулировке между каналами: текст ответа строится
    из одних и тех же полей результата (номер задачи, статус), не
    дублируется независимым текстом в каждом адаптере.

    Сценарий: Дано — оркестратор создал Issue #500 по сообщению из Telegram.
    Когда — формируется ответ. Тогда — тот же результат (`issue_number=500`,
    `issue_url`), уже сохранённый в `messages.result`, форматируется в текст
    ответа — не запрашивается и не формулируется заново отдельным кодом для
    каждого канала.

## Аутентификация владельца на каждом канале

11. Вебхук Telegram отклоняет запросы, не подтверждённые секретом заголовка,
    до того, как сообщение попадёт в очередь как «сообщение владельца».
    Гейт — РОВНО секрет заголовка, не `chat_id` (design.md, «Идентичность и
    аутентификация владельца» — находка ревью PR #262: гейт по `chat_id`
    конфликтовал бы с требованием 8, где ответ уходит в `chat_id`, отличный
    от дефолтного `TELEGRAM_CHAT_ID`).

    Сценарий: Дано — POST на `/api/messages/webhook` с валидным JSON, но БЕЗ
    заголовка `X-Telegram-Bot-Api-Secret-Token` (значение `chat_id` в теле —
    любое, произвольное). Когда — вебхук обрабатывает запрос. Тогда —
    запрос отклонён (4xx) ДО записи строки в `messages`, и это отклонение
    проверяемо тестом на прод-форме данных (реальный Telegram update JSON,
    как того требует правило репозитория «тест кормится прод-формой»).

12. Морда dsh-edge не требует дополнительной проверки — используется
    существующая owner-кука; эта спека не ослабляет и не дублирует её.

    Сценарий: Дано — RPC-запрос без валидной куки `__Host-dsh_edge_owner`.
    Когда — запрос доходит до dsh-edge. Тогда — отклонён штатным механизмом
    морды (уже так сегодня, до этой спеки) — оркестратор не получает
    сообщение вовсе, ему не нужно проверять авторство повторно.

## Связь GitHub<->DO без дублирования

13. Issue, созданный оркестратором (или уже существующим механизмом PR #173)
    из сообщения, несёт машиночитаемую ссылку на исходное сообщение;
    инварианты (#244) могут проверить пару в обе стороны без дополнительного
    похода в DO за текстом.

    Сценарий: Дано — оркестратор создал Issue из сообщения `id=42`. Когда —
    инвариант читает тело Issue. Тогда — находит строку
    `<!-- inbox-message: 42 -->`, парсит id регулярным выражением, сверяет с
    `messages.id=42` и не находит рассинхрона (оба указывают друг на друга).

14. Сессия раннера `harness-<N>`, если задача обсуждалась через оркестратор,
    доступна из Issue `#N` не только как заголовок сессии, но и как явное
    упоминание в Issue (комментарий или поле), без необходимости знать
    формулу ключа `harness-<N>` заранее.

    Сценарий: Дано — задача `#N` получила сессию раннера. Когда — владелец
    открывает Issue `#N` в GitHub. Тогда — видит комментарий/упоминание,
    указывающее на сессию морды (минимум — session-id текстом; полная форма —
    кликабельная ссылка, если dsh-edge отдаёт постоянный URL — см.
    «Не подтверждено» в `design.md`).

15. Ни одно новое требование этой спеки не создаёт третьего хранилища
    состояния сообщений/сессий/задач: единственные места правды остаются
    GitHub (issues/PR/labels) и Harness DO (`messages`, `tasks`, `events`).

    Сценарий: Дано — реализация по этой спеке завершена. Когда — считается
    число мест, где хранится статус обработки сообщения. Тогда — их РОВНО
    ОДНО (`messages.status` в DO), а не отдельная таблица/файл у
    оркестратора.
