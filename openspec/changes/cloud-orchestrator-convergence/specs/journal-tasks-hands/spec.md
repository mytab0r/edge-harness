# Дельта-спека: `openspec/specs/journal-tasks-hands.md` (находка ревью PR #262, второй раунд, п.1)

Этот change меняет поведение, уже описанное базовой спекой (пп. 33/35), не
только добавляет новое — правило репозитория (по образцу
`openspec/changes/owner-inbox/specs/journal-tasks-hands/spec.md`, откуда
выросла базовая секция «Инбокс владельца») требует MODIFIED-дельту против
существующего пункта, а не отдельный «новый домен», который тихо
разошёлся бы с базовым файлом после архивации.

## MODIFIED: п.35 — `chat` перестаёт быть тупиковым

Было (`openspec/specs/journal-tasks-hands.md`, п.35): «`chat` — `done` с
пометкой `classified_for_manual_review`: автоматического ответа в фазе 1
нет, дальнейшее решает триаж».

Стало: `chat` (см. требование 3
`specs/orchestrator-dispatch/spec.md` этого же change) диспетчит
оркестратор-джоб вместо немедленного `done`. Финальный статус (`done`
с результатом, либо новый терминальный статус ответа оркестратора)
проставляется ПОСЛЕ того, как джоб отработал — не в момент
классификации, как раньше. Владение окном диспетча — у джоба: он
продлевает захват (продление обновляет `processing_ts` и возвращает
джобу новое значение владения; все последующие CAS джоба, включая
финальную запись результата, ведутся по нему — находка ревью PR #262,
седьмой раунд, п.2), ватчдог п.36 снимает
только захваты, которые не продлевались; ответ в канал отправляется
только после успешной CAS-записи результата (требование 4
`specs/orchestrator-dispatch/spec.md`). `raw` в это множество НЕ входит
и сохраняет поведение п.35 без изменений: уходит в `ignored`, ручной
триаж как и было (находка ревью PR #262, первого раунда, п.3 — сужение
оставлено явным решением, не молчаливым: `raw` — самый широкий класс
нераспознанного текста, диспетчить его наравне с `chat` означало бы
отправлять оркестратору шум).

Сценарий: сообщение классифицировано как `chat` -> пульс DO на том же
тике инициирует `repository_dispatch` (`event_type: harness-message`)
тем же путём, что `directive`/`doc_edit`
создают issue, — с ожиданием ответа и разбором исхода (находка ревью
PR #262, пятнадцатый раунд: прежнее «асинхронным
`fire-and-forget`» разошлось и с кодом — `#processSingleMessage` ждёт
`#dispatchIssueCreation` и разбирает исход — и с требованием 3 этой же
спеки, предписывающим разобрать состояние строки после вызова);
механизм закреплён требованием 3
`specs/orchestrator-dispatch/spec.md`, без «или» (находка ревью
PR #262, десятый раунд: прежняя редакция оставляла развилку
«или `workflow_dispatch`»); после приёма
сообщения тик ускоряется одноразовым alarm'ом — MODIFIED п.33 ниже
-> статус `messages` проставляется джобом через CAS владения
(`done` — после успешной CAS-записи результата; исход отправки в канал —
отдельное поле `result`: окно «ноль ответов» требования 4
`specs/orchestrator-dispatch/spec.md`; `failed` — по уже существующей
модели попыток) — не сразу при классификации.

Сценарий: сообщение классифицировано как `raw` -> поведение НЕ меняется:
`ignored`, счётчики, ручной триаж — как в базовой спеке до этого change.

## MODIFIED: п.33 — диспетч добавляется как ДЕЙСТВИЕ того же водителя разбора

Стало (формулировка пункта после применения этого change): разбор ведёт
пульс DO на каждом тике (водитель назван, ручной
`POST /api/messages/process` — администрирование и повтор); захват
атомарный (`new -> processing` условным UPDATE), запись финального
статуса и возврат в `new` — CAS по моменту захвата (`processing_ts`) —
без изменений. Пульс DO остаётся единственным ШТАТНЫМ
драйвером перехода `new -> processing` и захвата сообщения; ручной
`POST /api/messages/process` — тот же захват руками, не второй штатный
драйвер (находка ревью PR #262, пятнадцатый раунд: «ЕДИНСТВЕННЫМ» без
«штатным» противоречило бы собственному упоминанию ручного пути в этом
же пункте — на HEAD он ведёт тот же `#processInbox` с тем же захватом).
Требование 3
`specs/orchestrator-dispatch/spec.md` добавляет ВТОРОЕ действие на том же
тике — диспетч `repository_dispatch` (`event_type: harness-message`)
для
`chat`, не второй захват и не второй классификатор. Один водитель
разбора, одно
дополнительное действие после разбора — два места правды для «кто
разбирает» не появляется.

Уточнение о темпе (находка ревью PR #262, третий раунд, п.1): приём
сообщения (`#postMessageIngest`) сам его НЕ разбирает — `#putMessage`
вставляет строку захардкоженным `raw`/`new`, классификация происходит
только на тике пульса. Чтобы диспетч `chat` не ждал полного темпа тика
DO (`HEARTBEAT.selfOrchestrationMs`, сегодня 10 минут; находка ревью
PR #262, десятый раунд: прежняя редакция называла темп «15-минутным»,
приписывая инбоксу пульс `orchestra.yml`, который инбокс не водит),
приём свежего сообщения закладывает ОДНОРАЗОВЫЙ
ближний alarm (порядка `HEARTBEAT.selfOrchestrationFirstMs`, только если
уже заложенный тик не раньше). Это ускорение ТОГО ЖЕ водителя, не второй
водитель: у одноразового alarm'а нет ни своего классификатора, ни своего
захвата — просыпается тот же пульс с тем же `#processInbox`.
