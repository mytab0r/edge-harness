- [ ] 0c. Замер: проходит ли исходящий `fetch` из воркера dsh-edge на адрес

обхода («морда -> cf-worker», см. design.md выше) в статусе «не

автоматической доставки в чат нет и не появится до реализации требования

заводится следующим PR по #133, не блокирует archive этого change.

## Минимальный первый шаг

**Цель:** «написал в Telegram — и в проекте что-то произошло», за минимум
работы поверх уже смёрженного PR #173.

Из всего описанного в `design.md` минимальный шаг, дающий эту пользу первым:

1. Закрыть дыру аутентификации вебхука (design.md, требование 11) — иначе
   любое дальнейшее действие оркестратора строится поверх непроверенного
   входа, а это уже небезопасно даже без реasoning-джоба (сегодняшний
   `directive`-путь PR #173 уже создаёт Issues от имени владельца без
   проверки источника).
2. Расширить `pulse_guard.send_telegram` параметром `chat_id` (default —
   текущий `TELEGRAM_CHAT_ID`, обратная совместимость с `pulse_guard.escalate`
   и `WORKER-PLAYBOOK.md` сохраняется).
3. Новый workflow `orchestrator.yml` по образцу `ai-review.yml`
   (`gather` -> DSH headless reasoning -> `verdict`/action, без сохранённого
   состояния), триггер — `repository_dispatch` с новым `event_type`
   (например `harness-message`, по аналогии с существующим `harness-task`,
   `cf-worker/src/config.ts:69-75`).
4. DO дёргает этот dispatch немедленно при записи сообщения с
   `kind IN ('chat','doc_edit')` — расширение `#postMessageWebhook`, по
   образцу уже существующих трёх вызовов dispatch в `harness.ts`.
5. Джоб отвечает: читает сообщение (`GET /api/messages/:id`), формирует
   ОДИН ход рассуждения (DSH headless, без git/PR — это не код-таск),
   постит ответ в `chat_id` сообщения через расширённый `send_telegram`, и
   пишет `messages.result`/`status=done` через `POST /api/messages/:id`
   (если такого метода записи результата нет — добавить, минимальный).

Почему именно это, а не остальное:
- **Не выбрана связка GitHub<->DO (design.md, требования 13-14)** — она
  улучшает наблюдаемость, но не даёт нового пользовательского эффекта
  «написал — что-то произошло»; без неё первый шаг уже демонстрируем.
- **Не выбран путь через морду (design.md, требование 9)** — Telegram-путь
  короче: не требует расширения `dsh-edge-session.sh` для диалога общего
  назначения (сегодня только per-task транскрипт), а вебхук с очередью уже
  есть в PR #173 почти целиком.
- **Не выбрана подстраховка пульсом (design.md, требование 4)** — полезна
  для надёжности, но не нужна, чтобы ПЕРВЫЙ раз увидеть эффект; добавляется
  сразу после, до того как на неё начнут полагаться.
- **Не выбрано усложнение `directive`-пути** (декомпозиция сложных
  директив) — это территория контракта спеки B, и сегодняшний regex-путь уже
  рабочий для простых случаев.

## Полный объём (после минимального шага)

- [ ] Подстраховка пульсом: `orchestra.yml` подбирает сообщения `new` старше
      порога (design.md, диспетчер, вариант B как fallback), С потолком
      попыток `MESSAGE_DISPATCH_MAX_ATTEMPTS` и терминальным `failed` +
      эскалацией при исчерпании (спека, требование 4 — находка ревью
      PR #262, без потолка стабильно падающий джоб штурмует бюджет
      500/час каждые 15 минут бесконечно). Видимый результат: тест на
      симуляции «диспетч из DO не удался» показывает подбор следующим
      пульсом без дублирования; отдельный тест на фикстуре «N падений
      подряд» показывает переход в `failed` и остановку повторов после
      `MESSAGE_DISPATCH_MAX_ATTEMPTS`, доказано мутацией (снять потолок ->
      тест краснеет).
- [ ] Батчинг диспетча при всплеске сообщений (design.md, требование 5).
      Видимый результат: тест с 20 сообщениями за минуту показывает один
      dispatch с несколькими id, не 20 вызовов.
- [ ] Ответ в морду dsh-edge для сообщений, пришедших через RPC морды
      (design.md, требование 9). Видимый результат: живой прогон — сообщение
      в чате морды получает ответ в той же сессии.
- [ ] Машиночитаемая связь Issue -> сообщение (design.md, GitHub<->DO,
      требование 13). Видимый результат: `repo_invariants.py` (#244) может
      сверить пару без похода в DO за текстом — добавить как один из
      инвариантов следующей волны (не эта спека реализует #244, но открывает
      для него данные).
- [ ] Обратная связь Issue -> сессия раннера (design.md, требование 14).
      Предваряется спайком: подтвердить/опровергнуть наличие постоянного
      deep-link URL сессии в UI dsh-edge (сейчас «не подтверждено»).
- [ ] ADR, фиксирующий выбор архитектуры (развилки 1-3 из `design.md`) —
      `docs/decisions/00XX-cloud-orchestrator.md`, по образцу существующих
      ADR 0002/0009.
- [ ] `docs/agents/ROADMAP.md` — новый узел «Оркестратор в облаке» в секции
      «Оркестрация»; `docs/INDEX.md` — ссылка на новый ADR и на эту спеку
      после архивации change'а.
