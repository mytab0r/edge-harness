## Минимальный первый шаг

**Цель:** «написал в Telegram — и в проекте что-то произошло», за минимум
работы поверх уже смёрженного PR #173.

Из всего описанного в `design.md` минимальный шаг, дающий эту пользу первым:

- [x] 1. ~~Построить публичный вебхук Telegram СРАЗУ с гейтом секрета заголовка~~ —
   **УЖЕ СДЕЛАНО** (находка ревью PR #262, пятый раунд: пункт оставался от
   до-мержного состояния): гейт слит (#254, ADR 0014, PR #486) —
   `#telegramWebhookAuthorized` (constant-time сверка
   `X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_WEBHOOK_SECRET`) +
   `#ownerChatAuthorized` (привязка `chat_id` владельца, 401 до записи
   строки), регистрацию делает `.github/workflows/telegram-webhook.yml`
   (#490). Спецификация гейта — требование 11 дельта-спеки. Остаток —
   живой статус регистрации у Telegram (`proposal.md`, «Не подтверждено»),
   отдельного кода не требует.
- [ ] 2. Расширить `pulse_guard.send_telegram` параметром `chat_id` (default —
   текущий `TELEGRAM_CHAT_ID`, обратная совместимость с `pulse_guard.escalate`
   и `WORKER-PLAYBOOK.md` сохраняется).
- [ ] 3. Новый workflow `orchestrator-message.yml` по образцу `ai-review.yml`
   (`gather` -> DSH headless reasoning -> `verdict`/action, без сохранённого
   состояния), триггер — `repository_dispatch` с новым `event_type`
   `harness-message` (по аналогии с существующим `harness-task` — поле
   `dispatchEventType` в объекте `GITHUB`, `cf-worker/src/config.ts` —
   искать по имени поля, не по строке): механизм ЗАКРЕПЛЁН требованием 3
   дельта-спеки, без «или» (находка ревью PR #262, десятый раунд —
   прежняя редакция оставляла развилку «или `workflow_dispatch`»);
   `repository_dispatch` выбран потому, что батчинг требования 5 кладёт id
   сообщений списком в `client_payload`, а у `workflow_dispatch` вместо
   него только строковые `inputs`; тот же класс вызова, что уже доказан —
   `#postTask` (`harness-task`), `#dispatchIssueCreation` (`inbox-issue`),
   `#dispatchOwnerDecision` (`owner-decision`; искать по имени
   функции, не по строке). Имя выбрано подальше от уже диспетчимого
   `orchestra.yml`
   (15-минутный пульс) — пара имён на «or» была бы готовым классом
   перепутанного грепа/диспетча (находка ревью PR #262, восьмой раунд);
   `orchestra.yml` этот change не трогает.
- [ ] 4. DO дёргает этот dispatch НА тике разбора, который после приёма
   сообщения ускоряется одноразовым alarm'ом (приём пишет строку
   `raw`/`new` — классификация, как и весь разбор, живёт на тике,
   п.33 базовой спеки; расширение — ветка `chat` в `#processSingleMessage`
   плюс одноразовый alarm в `#putMessage`; НЕ `doc_edit` — тот уже мержен
   как механический путь наравне с `directive`, см. proposal.md/design.md,
   находка ревью PR #262; сам момент — находка ревью PR #262, третий
   раунд, п.1)
   — расширение `#putMessage`/`#processSingleMessage`, по образцу
   уже существующих ПЯТИ вызовов dispatch в `harness.ts`
   (`attemptOrchestraDispatch`, `#checkDshEdgeUpdate`, `#postTask`,
   `#dispatchIssueCreation`, `#dispatchOwnerDecision`; счётчик исправлен
   находкой ревью PR #262, десятый раунд — прежняя редакция считала
   четыре).
- [ ] 5. Джоб отвечает: читает сообщение (`GET /api/messages/:id`), формирует
   ОДИН ход рассуждения (DSH headless, без git/PR — это не код-таск),
   продлевает захват на длинных шагах (CAS по своему моменту захвата),
   пишет `messages.result`/`status=done` через CAS-запись (если такого
   метода записи результата нет — добавить, минимальный, с действием
   продления захвата), и только после УСПЕШНОЙ CAS-записи постит ответ
   в `chat_id` сообщения через расширённый `send_telegram` — джоб,
   потерявший владение (ватчдог реclaimил сообщение), молчит
   (спека, требование 4; находка ревью PR #262, третий раунд, п.2).
   Неудача отправки после CAS-записи не откатывает результат: исход
   отправки фиксируется в `messages.result`, окно «результат записан,
   владелец не ответил» видимо (спека, требование 4; находка ревью
   PR #262, шестой раунд).

Почему именно это, а не остальное:
- **Не выбрана связка GitHub<->DO (спека, требования 13-14)** — она
  улучшает наблюдаемость, но не даёт нового пользовательского эффекта
  «написал — что-то произошло»; без неё первый шаг уже демонстрируем.
- **Не выбран путь через морду (спека, требование 9)** — Telegram-путь
  короче: не требует расширения `dsh-edge-session.sh` для диалога общего
  назначения (сегодня только per-task транскрипт), а вебхук с очередью уже
  есть в PR #173 почти целиком.
- **Не выбран возврат захвата в `new` при неуспешном диспетче
  (спека, требование 4)** — продление захвата джобом и ответ только
  после успешной CAS-записи уже входят в минимальный шаг (п.5 выше: без
  них первый же инкремент несёт гонку двойного ответа против джоба из
  очереди Actions, которая «изредка часы» — не экзотика при 10-минутном
  ватчдоге). Отложены только полные сценарии/тесты требования 4 (см.
  «Полный объём», «Владение окном диспетча») и подбор захвата, вернувшегося
  в `new` после неуспешного диспетча, следующим тиком — они улучшают
  надёжность повторного диспетча, но не нужны, чтобы ПЕРВЫЙ раз увидеть
  эффект (находка ревью PR #262, восьмой раунд, п.1: прежняя редакция
  bullet'а противоречила самому пункту 5, который эти пункты уже
  реализует).
- **Не выбрано усложнение `directive`-пути** (декомпозиция сложных
  директив) — это территория контракта спеки B, и сегодняшний regex-путь уже
  рабочий для простых случаев.

## Полный объём (после минимального шага)

- [ ] Диспетч на тике DO + одноразовый alarm ускорения после приёма
      (спека, требования 3-4; находка ревью PR #262, третий раунд, п.1):
      тик `alarm()` (`#processInbox` — искать по имени функции) —
      ЕДИНСТВЕННЫЙ водитель диспетча `chat`, НЕ отдельный код в
      `orchestra.yml` и НЕ второй счётчик попыток (переформулировано
      находкой ревью PR #262, второй раунд: `MESSAGE_DISPATCH_MAX_ATTEMPTS`
      дублировал бы уже существующую модель
      `messages.attempts`/`LIMITS.messageMaxAttempts`/
      `stuck_reclaimed`/`retry_failed` — второй драйвер одной очереди, тот
      класс отложенного рецидива, против которого правила репозитория).
      Видимый результат: тест на симуляции «диспетч с тика не удался
      (сеть/5xx)» показывает возврат захвата в `new` и подбор следующим
      тиком DO без дублирования (идемпотентность по `status`); тест на
      фикстуре «`attempts` исчерпан» показывает переход в `failed` со
      `stuck_reclaimed` через уже существующий `#reclaimStuckMessages`,
      без нового кода; тест «после приёма свежего сообщения заложен
      одноразовый alarm раньше уже заложенного тика» показывает задержку
      диспетча порядка секунд, а не полного темпа тика DO
      (`HEARTBEAT.selfOrchestrationMs`, сегодня 10 минут; находка ревью
      PR #262, десятый раунд — прежняя редакция называла темп
      «15-минутным» по пульсу `orchestra.yml`, который инбокс не водит).
- [ ] Владение окном диспетча — медленный джоб (спека, требование 4;
      находка ревью PR #262, третий раунд, п.2 + шестой раунд, п.1).
      Видимый результат: тест на сценарии «медленный живой джоб» (джоб
      стартовал и успел продлить захват в пределах
      `LIMITS.messageStuckProcessingMs`, работа идёт дольше порога)
      показывает, что ватчдог захват не реclaimит — ни повторного
      dispatch, ни второго ответа; тест на сценарии «очередь дольше
      порога» (джоб стартовал ПОЗЖЕ первого реclaimа, продлевать уже
      нечего) показывает ЧЕСТНЫЙ путь: повторные dispatch до капа, затем
      `failed` со `stuck_reclaimed` — гарантия на этот случай НЕ
      обещается; тест на сценарии «потеря владения» (продления
      прекратились, ватчдог вернул в `new`, сообщение пере-dispatchено)
      показывает, что CAS-запись результата первого джоба не проходит и
      ответ в канал НЕ уходит — владелец получает ровно один ответ; тест
      на окно «ноль ответов» (CAS прошёл, отправка в канал упала)
      показывает, что статус остаётся `done` с исходом отправки в
      `messages.result` — окно видимо, не молчаливо.
- [ ] Батчинг и минутная пауза диспетча (спека, требование 5; якорь
      исправлен: требования нумерованы в дельта-спеке, не в design.md —
      тот же класс неверных якорей, что index.js в пятом раунде).
      Видимый результат: три теста — ниже порогов (счётчик скользящего
      часа 12, счётчик скользящей минуты 0, 20 сообщений) показывает
      20 отдельных dispatch'ей — ни батчинг, ни пауза не включаются
      раньше порогов; на часовом пороге (счётчик достиг 400/час, минутный
      ниже 64) показывает ОДИН dispatch с id сообщений в
      `client_payload`, не 20 вызовов; на минутном пороге (счётчик
      скользящей минуты достиг 64) показывает НОЛЬ dispatch'ей этого
      тика и подбор сообщений следующим тиком после освобождения
      скользящей минуты (находка ревью PR #262, тринадцатый раунд —
      требование 5 обязало механизм нести и минутную границу лимита
      80/мин, не только часовую).
- [ ] Ответ в морду dsh-edge для сообщений, пришедших через RPC морды
      (спека, требование 9). Видимый результат: живой прогон — сообщение
      в чате морды получает ответ в той же сессии.
- [ ] Машиночитаемая связь Issue -> сообщение (спека, раздел
      «Связь GitHub<->DO», требование 13). Видимый результат:
      `repo_invariants.py` (#244) может
      сверить пару без похода в DO за текстом — добавить как один из

- [ ] Обратная связь Issue -> сессия раннера (спека, требование 14).

- [ ] ADR, фиксирующий выбор архитектуры (развилки 1-3 из `design.md`) —
