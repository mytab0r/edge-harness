### Канал морды — предпосылки пересмотрены, путь записи остаётся решением (находка ревью PR #262, седьмой раунд, п.1)

Третья стрелка на диаграмме выше не имеет названного механизма перехода
границы origin. Две предпосылки прежней редакции этого раздела
репозиторий с тех пор ответил, и спека больше не строится на
опровергнутых фактах:

- **Причина 403 #133 — НЕ блок egress-IP.** `docs/research/12-dsh-edge-session-api.md`,
  «Причина 403 задачи #133 установлена (2026-09-11)»: GitHub отклонял
  запрос без заголовка `User-Agent`; фикс в HEAD
  (`plugins-src/runner-bridge/server/core.js::githubFetch`, `core.js:65`),
  #133 закрыт. Гипотеза «IP/colo-абьюз-фильтр» снята как неверная —
  плагин морды СЕГОДНЯ может действовать в GitHub напрямую.
- **Fetch из воркера dsh-edge на `cf-worker` — измерен, ответ «нет».**
  `docs/research/20-cloudflare-free.md`, «Worker не может `fetch()` другой
  Worker на `*.workers.dev` того же аккаунта — ошибка 1042» (#501):
  subrequest на публичный маршрут `*.workers.dev` того же аккаунта
  возвращает 404 `error code: 1042`. Рабочий транспорт того же
  назначения существует — service binding `HARNESS_SERVICE`
  (`dsh-edge/patches/0005-harness-status-proxy.patch`, в проде): READ-ONLY
  прокси статусов морде.

Что из этого следует: физического запрета на канал морды больше нет —
остались ОТКРЫТЫЕ РЕШЕНИЯ, а не измерения: (1) писать ли сообщение из
чата морды в журнал через service binding
(`HARNESS_SERVICE` -> `POST /api/messages/ingest`), если прямой GitHub из
морды снова работает; (2) держится ли ограничение 1042 на custom domain
(`research/20`, «Не подтверждено»). Эти решения — отдельная узкая задача
со ссылкой на #258 (не этот change): прежняя формулировка «спайк с
замером» отправила бы следующего агента перемерять отвеченный вопрос
(класс #215). `session.prompt` в helper-сессию и ADR 0009 остаются
непрецедентными для этой задачи: маршрут заказа плагина живёт ВНУТРИ
dsh-edge и границу «чат -> журнал» не пересекает.

Ключевое свойство: оркестратор — джоб, а не служба. Между вызовами не помнит
ничего; всё состояние читает заново из GitHub (issues/labels/PR) и DO
(`/api/status`, `/api/messages`). Это не новый принцип, а перенос уже
действующего в `scripts/review/ai_review.py` (`gather`/`DSH`/`verdict`,
доверенность разрезана по шагам, комментарий/метка — единственный
переживающий джоб след) на произвольные сообщения вместо диффа PR.

## Развилка 1: где физически рассуждает оркестратор

| Вариант | Цена | Вердикт |
|---|---|---|
| **A. GitHub Actions job, событийный, без состояния (как `ai_review.py`)** | Бесплатно на публичном репо (`docs/research/21-github-actions.md`); задержка старта не документирована, эмпирика секунды-десятки, изредка часы в очереди (там же); job живёт минуты и умирает | **Выбран** |
| B. Рассуждение внутри Harness DO (агент-цикл в самом DO) | 10 ms CPU/инвокацию на Free — уже отвергнуто (`docs/research/30-rejected-alternatives.md`, п.6; `docs/decisions/0002-loop-in-runner-not-do.md`) | Отвергнут повторно, условие возврата не изменилось (Paid: 30с/5мин CPU) |
| C. Постоянный процесс на VPS/CF Containers | Ломает «бесплатно» (от $5/мес), требует согласования владельца (`docs/research/30-rejected-alternatives.md`, п.4 и п.11) | Отвергнут ДО согласования владельцем; к рассмотрению, если ограничение снято |
| D. Рассуждение внутри самой dsh-edge (её собственный агент-цикл, уже работающий в чате) | Не Linux/нет git+pytest (`docs/research/11-dsh-edge.md`); архитектурно то же ограничение CPU, что у варианта B, только у чужого приложения. Нога «egress в GitHub заблокирован (#133)» снята (находка ревью PR #262, седьмой раунд: причина 403 — отсутствовавший `User-Agent`, фиксирован в HEAD, `research/12`) — dsh-edge остаётся отвергнутой на оставшихся двух ногах | Отвергнут: dsh-edge остаётся КАНАЛОМ (ingress/egress текста), не движком решений |

Условие пересмотра A -> C: не деньги на память — память уже есть бесплатно
(dsh-edge хранит историю сессий в Durable Object с SQLite, `/api/health` ->
`"storage":"durable-object-sqlite-vfs"` — живой замер владельца 2026-09-03,
дословно в комментариях #133 (`gh api repos/mytab0r/edge-harness/issues/
133/comments`); факт перенесён в `docs/research/12-dsh-edge-session-api.md`,
«Память сессии: раннер vs облако» — снятое возражение, #133). Пересмотр
нужен, только если владелец захочет ФОНОВОЕ рассуждение без входящего
триггера (проактивность) — вот тогда действительно нужен постоянный процесс,
то есть $5/мес (Workers Paid/Containers); джоб-на-сообщение покрывает «ответить
на входящее», не «думать в фоне».

## Развилка 2: как диспетчер узнаёт о новом сообщении

| Вариант | Цена | Вердикт |
|---|---|---|
| **A. DO дёргает `workflow_dispatch`/`repository_dispatch` на тике разбора, который после приёма сообщения ускоряется одноразовым alarm'ом** | Один HTTP-запрос из DO — паттерн трижды доказан (искать по имени функции, номера строк дрейфуют между ребейзами): `cf-worker/src/harness.ts::attemptOrchestraDispatch` (пульс orchestra), `::#checkDshEdgeUpdate` (deploy-dsh-edge), `::#postTask` (repository_dispatch `harness-task`); укладывается в лимит 500 dispatch/час (`docs/research/21`) при обычном темпе чата | **Выбран** — задержка до диспетча порядка секунд после приёма, не полный темп тика DO (сегодня 10 минут, `HEARTBEAT.selfOrchestrationMs`) |
| B. Ждать очередной пульс `orchestra.yml` (cron 15 мин) | НЕ «ноль кода»: `scripts/orchestra/scheduler.py` инбокс не читает (`/api/messages` — ноль обращений) и диспетчит только `worker.yml`/`ai-review.yml` — вариант B это НОВЫЙ код в `scheduler.py`, отдельное решение (находка ревью PR #262, десятый раунд: прежняя редакция звала его «уже существующим» с ценой «ноль нового кода» и обещала, что он «остаётся подстраховкой») | Отклонён как ЕДИНСТВЕННЫЙ механизм: 15 минут не выглядят как «что-то произошло», а подстраховкой инбокса он НЕ стоит — стоящая подстраховка другая, это собственный тик DO (см. ниже) |
| C. GitHub-native webhook (issue/comment) как триггер | Каналы входа — Telegram/dsh-edge/локальная сессия, не GitHub-события | Не рассматривается для входа; используется штатно там, где уже есть (`ai-review.yml` на `workflow_run`) |

Где физически происходит диспетч (находка ревью PR #262, третий раунд,
п.1 — прежняя редакция вешала его на завершение `#postMessageIngest`, где
`kind` всегда `'raw'`, и «немедленно» было недостижимо): диспетч живёт НА
тике разбора DO (`alarm()` -> `#processInbox`,
`cf-worker/src/harness.ts`) — там же, где классификация (`#processSingleMessage`),
потому что разбор ведёт один водитель (п.33 базовой спеки, MODIFIED-дельта
п.33 в
`specs/journal-tasks-hands/spec.md` этого change), а «немедленно» на
ingest сделало бы из приёма второй драйвер разбора. Роль приёма — не
разобрать, а ускорить: `#putMessage` свежего сообщения закладывает
ОДНОРАЗОВЫЙ ближний alarm (порядка существующей
`HEARTBEAT.selfOrchestrationFirstMs`, только если уже заложенный тик не
раньше) — задержка до диспетча порядка секунд, не полный темп тика DO
(сегодня 10 минут, `HEARTBEAT.selfOrchestrationMs`; вариант B — пульс
`orchestra.yml` — инбокс вообще не водит). Повтор ОГРАНИЧЕН
уже существующей моделью попыток `messages` (`attempts`/
`LIMITS.messageMaxAttempts`) — второй, параллельный счётчик
(`MESSAGE_DISPATCH_MAX_ATTEMPTS` в `pulse_guard`/`orchestra.yml`) НЕ
заводится: у очереди `messages` уже есть жизненный цикл (`attempts` ->
кап -> `failed` со `stuck_reclaimed` от `#reclaimStuckMessages` -> газ
`retry_failed`) — второй драйвер одной и той же очереди это ровно тот
класс отложенного рецидива, против которого правила репозитория (находка
AI-ревью PR #262, п.2; исходная формулировка требования 4 предлагала его
завести — переформулирована).

Владение окном диспетча (находка ревью PR #262, третий раунд, п.2):
полный круг джоба «очередь GitHub Actions (изредка часы — см. «Честный
потолок») + рассуждение + запись результата» длиннее порога ватчдога
`LIMITS.messageStuckProcessingMs` — без модели владения ватчдог
реclaimил бы ЖИВОЙ джоб: повторный dispatch, второй ответ владельцу, а
на третьей попытке `failed`, пока первый джоб ещё мог вернуться. Модель:
джоб при старте и на длинных шагах продлевает захват (CAS по своему
моменту захвата — тем же механизмом, что `#finishMessage`), ватчдог
снимает только захваты без продлений; продление обновляет `processing_ts`
и возвращает джобу новое значение владения — все последующие CAS,
включая финальную запись, ведутся по нему (пп. 33/36 базовой спеки
остаются буквальными); ответ в канал джоб отправляет
ТОЛЬКО после успешной CAS-записи результата — джоб, потерявший владение,
молчит, и владелец получает один ответ (требование 4 спеки, сценарии
«медленный живой джоб» и «потеря владения»). Без этого медленный, но
живой джоб получал бы двойника — тот же класс «двойное действие на одно
сообщение», что и исключение `doc_edit`. Честная граница (находка ревью
PR #262, шестой раунд, п.1): продление начинается со СТАРТА джоба — джоб,
застрявший в очереди дольше порога ватчдога, теряет захват до первого
продления, и его путь — повторные dispatch до капа, видимый `failed`,
ручной `retry_failed`; спека на этот случай доставки не обещает.

Граница модели по внешним действиям (находка ревью PR #262, пятнадцатый
раунд, класс «гарантия-шире-механизма»): CAS владения гейтит запись
результата и отправку — но не внешние действия джоба ДО записи
(созданная задача, правка дока — прямые исходы постановки, требование 10
спеки). Без гейта потерявший владение джоб успел бы создать задачу, а
второй джоб по требованию 6 сделал бы то же ещё раз. Поэтому требование 4
спеки обязывает джоб гейтить каждое внешнее действие проверкой владения
непосредственно перед ним и честно называет остаточное окно тем же
классом, что п.34 базовой спеки для inbox-issue: проверка и действие —
два раздельных вызова, окно сжато до длительности одного API-вызова, но
не закрыто; след дубля — машиночитаемая ссылка на сообщение в теле
задачи (требование 13 спеки), дубль гасится вручную.

Условие пересмотра A -> B (находка ревью PR #262, восьмой раунд —
критерий 2 proposal.md требует условие пересмотра у КАЖДОЙ развилки, не
только у 1 и 3; ревизия 2026-09-18, десятый раунд — прежняя редакция
называла подстраховкой 15-минутный пульс `orchestra.yml`, который у
инбокса не стоит: `scheduler.py` инбокс не читает): пересмотр нужен,
если на живых метриках одноразовый alarm + dispatch с тика на практике
окажется ненадёжным (например, задержка диспетча систематически
растягивается на минуты вместо секунд, или доля неудачных dispatch
выше, чем покрывает существующий кап попыток). Газ на этот случай УЖЕ
СТОИТ и это не `orchestra.yml`: собственный тик DO — `alarm()` каждые
`HEARTBEAT.selfOrchestrationMs` (сегодня 10 минут, `cf-worker/src/config.ts`,
понижен с 15 задачей #812) — на каждом тике перезапускает
`#reclaimStuckMessages` + `#processInbox` и переподбирает сообщение,
возвращённое в `new` (`cf-worker/src/harness.ts`, комментарий «Инбокс
владельца (#20): тот же пульс — ватчдог зависших и водитель разбора»);
это субстрат самого варианта A, поэтому отказ одноразового alarm'а
деградирует темп до обычного тика, а не теряет сообщение. Превращение
`orchestra.yml`/`scheduler.py` в драйвер диспетча инбокса — новый код в
`scheduler.py`, отдельное решение, не запасной путь.

## Развилка 3: адресат ответа

| Вариант | Цена | Вердикт |
|---|---|---|
| **A. Ответ пишется туда, откуда взято сообщение, по полям, уже сохранённым в `messages`** (`chat_id` для Telegram через параметризованный `send_telegram(chat_id, text)`; сессия dsh-edge через примитив `dsh-edge-session.sh`; локальная сессия — адаптер не нужен, она сама терминал) | Требует расширить `pulse_guard.send_telegram` параметром `chat_id` (сегодня жёстко один `TELEGRAM_CHAT_ID`) — точечная правка существующей функции | **Выбран** |
| B. Единый фиксированный канал ответа (всегда Telegram, независимо от источника) | Дешевле, но нарушает прямое требование владельца («что тут, что в морде, что в ТГ — всё одно и то же») | Отклонён |

Условие пересмотра: не найдено — это прямое требование владельца, отказ от него
меняет саму постановку задачи.

## Единая очередь — расширение существующей таблицы, не новая сущность

`messages` (`cf-worker/src/harness.ts`, PR #173) уже несёт `source`, `chat_id`,
`sender_id`, `text`, `kind`, `status`. Предложение:

- `kind = 'chat'` перестаёт быть тупиковым: вместо
  `note: "classified_for_manual_review"` — захват на тике разбора
  (`status='processing'`) и диспетч джоба; финальный статус ставит джоб
  через CAS владения (см. «Владение окном диспетча» выше).
- `kind = 'doc_edit'` НЕ входит в это множество (находка AI-ревью PR #262:
  прежняя редакция этого пункта описывала до-мержное состояние PR #173).
  На `main` `doc_edit` уже смержен как механический путь наравне с
  `directive` — `#processSingleMessage` ведёт оба в создание issue.
  Диспетчить `doc_edit` ЕЩЁ и сюда
  создало бы issue механическим путём и одновременно подняло бы джоб
  оркестратора по тому же сообщению — двойное действие на одно сообщение.
- `directive` и `doc_edit` остаются механическим путём (issue создаётся
  regex'ом, как сегодня) — оркестратор НЕ вмешивается в то, что уже
  работает; подключается только там, где сегодня тупик (`chat`).
  Усложнение (декомпозиция сложных директив) — предмет контракта спеки B,
  не этой.
- Локальная сессия и находки наблюдателей (#201/#207/#244) НЕ идут через
  Telegram-специфичную схему `messages` — они уже нативно живут в GitHub
  Issues (`auto-detected` и другие метки). Оркестратору-джобу отдельный вход
  для них не нужен: он читает пул задач напрямую (как уже делает `worker.yml`)
  — это не третий канал, а обычное чтение состояния GitHub.

## Идентичность и аутентификация владельца

- **Telegram.** Вход — `POST /api/messages/ingest` (`#postMessageIngest`),
  ТРИ способа авторизации (находка ревью PR #262, пятый раунд: прежняя
  редакция этого раздела описывала до-мержное состояние — «вебхук ещё
  предстоит построить» — и цитировала комментарий кода, которого на HEAD
  больше нет):
  1. обычная админская авторизация (Bearer/кука, `#authorized`) — релей;
  2. вебхук-секрет: заголовок `X-Telegram-Bot-Api-Secret-Token` сверяется
     с `TELEGRAM_WEBHOOK_SECRET` constant-time (`#telegramWebhookAuthorized`) —
     штатный механизм Telegram Bot API, аутентифицирует БОТА;
  3. привязка к владельцу: `chat_id` апдейта сверяется с
     `TELEGRAM_CHAT_ID` (`#ownerChatAuthorized`, 401 ДО записи строки) —
     аутентифицирует ОТПРАВИТЕЛЯ, потому что секрет вебхука у апдейтов
     любого чата, где боту написали, один и тот же.
  Оба слоя (2+3) — ровно та рекомендация, которую этот документ делал
  заранее: слиты (#254, ADR 0014, PR #486), регистрацию делает
  `.github/workflows/telegram-webhook.yml` (#490). Реализовано
  требованием 11 дельта-спеки; не подтверждён только живой статус
  регистрации вебхука у Telegram — `proposal.md`, «Не подтверждено».
- **Морда dsh-edge.** Уже аутентифицирована штатно: RPC доступен только с
  кукой владельца (`__Host-dsh_edge_owner`, `docs/research/12-dsh-edge-session-api.md`) —
  сообщение уже прошло фильтр «это точно владелец» на уровне морды.
  Дополнительно ничего не требуется.
- **Локальная сессия.** Терминал владельца; аутентификация вне зоны
  ответственности этой спеки — владелец аутентифицирован тем, что сессия у
  него на машине.

## Связь GitHub<->DO без дублирования

Замер (`proposal.md`, п.3) нашёл ДВЕ однонаправленные текстовые связи.
Предложение:

- При создании Issue из сообщения (payload `#dispatchIssueCreation`,
  `cf-worker/src/harness.ts` — ADR 0015: прежняя редакция этого пункта
  звала функцию `#createIssue` прямого REST-вызова, на HEAD заменённую
  dispatch-механизмом; будущее расширение оркестратором — тот же payload)
  тело issue получает МАШИНОЧИТАЕМУЮ
  строку вида `<!-- inbox-message: <id> -->` (HTML-комментарий, не
  рендерится, парсится regex'ом) — рядом с уже существующим человекочитаемым
  заголовком `## Сообщение владельца (inbox #<id>)`, не
  вместо него. Это даёт `repo_invariants.py` (#244) и будущим проверкам
  возможность сверять пару `messages.result.issue_number` <-> `issue.body` в
  обе стороны без изменения видимого текста.
- Сессия `harness-<N>` получает при создании (`dsh_edge_session_begin`,
  `scripts/lib/dsh-edge-session.sh`) дополнительный шаг: комментарий в Issue
  `#N` со ссылкой на сессию морды. **Не подтверждено**: отдаёт ли dsh-edge
  постоянный deep-link URL конкретной сессии в UI — нужно проверить до
  реализации; при отсутствии такого URL закрывается частично (упоминание
  session-id текстом, не кликабельной ссылкой).
- Ни то, ни другое не создаёт третьего хранилища состояния — только делает
  существующие односторонние упоминания двусторонними и машиночитаемыми.

## Честный потолок

- **Near-real-time, а не мгновенно.** Задержка до диспетча = время до
  ближайшего тика разбора DO: после приёма сообщения одноразовый alarm
  ускоряет тик до порядка секунд, без него — полный темп тика DO, сегодня
  10 минут (`HEARTBEAT.selfOrchestrationMs`; 15 минут — это cron
  `orchestra.yml`, который инбокс не водит; находка ревью PR #262,
  третий раунд, п.1: прежняя редакция обещала «немедленно», что на
  ingest недостижимо — `kind` там всегда `raw`; десятый раунд: прежняя
  редакция называла этот темп «15-минутным», приписывая инбоксу пульс
  `orchestra.yml`).
  Дальше — задержка старта GitHub Actions job'а, недокументированная
  (`docs/research/21-github-actions.md`; эмпирика
  секунды-десятки, изредка часы в очереди) — «написал в Telegram» не
  гарантирует ответ за секунды, только «обычно быстро, формально не позже
  35 дней».
- **Медленный живой джоб: защита начинается со старта джоба (находка
  ревью PR #262, третий раунд п.2 + шестой раунд п.1).** Полный круг
  «очередь + рассуждение + запись результата» может пережить несколько
  тиков ватчдога; без продления захвата джобом сообщение реclaimилось бы
  в `new`, диспетчилось вторично и на третьей попытке уходило в `failed`,
  пока первый джоб ещё жив. Модель владения (джоб продлевает захват,
  ответ — только после успешной CAS-записи результата) — требование 4
  спеки. Честная граница: продление физически начинается со СТАРТА джоба,
  поэтому джоб, застрявший в очереди Actions дольше порога ватчдога
  (`LIMITS.messageStuckProcessingMs`), теряет захват до первого продления —
  путь такой задержки: повторные dispatch до капа, видимый `failed`,
  ручной `retry_failed` (механизм с бОльшим порогом для
  dispatched-сообщений сознательно не заводится — ему нужен был бы
  отдельный газ для джоба, умершего до старта).
- **Без памяти между сообщениями в рамках одного джоба.** Каждый вызов
  оркестратора видит ТОЛЬКО то, что лежит в GitHub/DO на момент запуска.
  Многоходовый диалог («уточни предыдущий ответ») требует, чтобы предыдущий
  обмен был читаем оркестратором из тех же мест правды (история `messages`,
  история сессии морды, предыдущие issue-комментарии) — это разговор ЧЕРЕЗ
  журнал, не разговор с живым процессом, ровно как обозначено в исходной
  постановке владельца.
- **Аутентификация Telegram — секрет, не физическая невозможность.** Любой,
  кто получит секрет заголовка ИЛИ узнает `chat_id`, управляет проектом от
  имени владельца — то же свойство, что и у уже существующего
  `TELEGRAM_CHAT_ID` (владение секретом = владение каналом), не новая
  слабость, но и не решаемая бесплатно иначе, чем секретом.
- **Память между сообщениями не требует денег — она уже есть.** Ранняя версия
  этого документа ошибочно объявляла «нет памяти между сообщениями» причиной,
  по которой облачный оркестратор невозможен без платного тарифа; это снято
  (#133). Морда dsh-edge хранит историю сессий в Durable Object с SQLite и уже
  сегодня — сохраняющий состояние собеседник в облаке, бесплатно. «Настоящий
  потолок — не память, а действие» прежней редакции тоже снят (находка ревью
  PR #262, седьмой раунд, п.1): 403 у морды был не egress-блоком, а
  отсутствовавшим `User-Agent` (`research/12`, фикс в `core.js:65`, #133
  закрыт 2026-09-11) — плагин морды сегодня может действовать в GitHub.
  Оставшийся потолок канала морды — не физика, а НЕСДЕЛАННАЯ ПРОВОДКА:
  произвольное сообщение чата морды не имеет названного пути в журнал
  (решение о пути записи — «Канал морды» выше).

  **Ноги канала морды — по состоянию на 2026-09-14 (находка ревью
  PR #262, седьмой раунд, п.1 — прежняя редакция называла вторую ногу
  «не измеренной»).** (1) `cf-worker -> api.github.com`/
  `repository_dispatch` — ДОКАЗАНО, `cf-worker/src/harness.ts::attemptOrchestraDispatch`/
  `::#checkDshEdgeUpdate`/`::#postTask` (искать по имени функции, не по
  номеру строки), живые вызовы в проде. (2) `морда dsh-edge -> cf-worker`
  публичным fetch — НЕВОЗМОЖНО и ИЗМЕРЕНО: subrequest на `*.workers.dev`
  того же аккаунта — 404 `error code: 1042` (`research/20`, #501). Рабочий
  транспорт того же назначения — service binding `HARNESS_SERVICE`
  (патч `dsh-edge/patches/0005-harness-status-proxy.patch`, в проде):
  READ-ONLY прокси статусов, `GET /api/harness/events`; запись сообщения
  в журнал через binding — ОТКРЫТОЕ РЕШЕНИЕ (см. «Канал морды» выше),
  не измерение.

  Постоянный, фоново рассуждающий процесс без входящего триггера (варианты
  B/C развилки 1) по-прежнему недостижим бесплатно — но это вопрос
  проактивности, не памяти.
- **Создание Issue из DO — уже dispatch-опосредованное** (находка ревью
  PR #262, пятый раунд: прежняя редакция этого пункта описывала мир
  ADR 0011 — «прямой `POST /issues` из DO не подтверждён, если
  заблокирован — уйти на dispatch» — и предлагала фолбэком то, что на
  HEAD уже реализовано). По ADR 0015 DO не зовёт Issues API вовсе:
  `#dispatchIssueCreation` шлёт `POST /repos/{repo}/dispatches`
  (`event_type: inbox-issue`), issue создаёт job
  `.github/workflows/inbox-issue.yml` штатным `github.token`, callback
  `#postIssueCreated` замыкает петлю. Для оркестратора вывода два:
  egress `cf-worker -> GitHub` доказан самим работающим dispatch-каналом
  (≠ egress `dsh-edge`, #133), а ответ джоба в `messages.result` пишется
  через DO API, без нового похода в GitHub.
