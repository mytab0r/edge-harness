## ADDED: WIP-лимит перед взятием новой задачи

Требование: диспатч `worker.yml` на задачу, у которой ЕЩЁ НЕТ открытого PR
(настоящая новая задача), запрещён, пока число открытых PR, реально ждущих
доработки (`ai:changes-requested`, `conflict` или `contract:failed` —
черновики и PR ботов не в счёт), больше или равно `WIP_LIMIT`. Порог
обоснован замером на живом репозитории (темп слияний, время жизни PR,
закон Литтла — комментарий в `scheduler.py` рядом с константой).

Требование: это ограничение НЕ распространяется на задачу, у которой уже
есть открытый PR (доводка, #245) — независимо от того, закрыт WIP-лимит или
нет, оркестратор вправе диспетчить воркера адресно (`worker.yml` input
`task`) на такую задачу. Закрытый WIP-лимит без свободной задачи с открытым
PR означает, что диспатча не будет вовсе — доводить нечего.

Требование: газ обязателен и автоматический (AGENTS.md) — слияние или
закрытие PR ниже `WIP_LIMIT` снимает ограничение на выбор новой задачи
следующим же прогоном, без ручного участия. Состояние эпизода (открыт/
закрыт) переживает перезапуск оркестратора — маркер в комментариях
watchdog-задачи (#120), тот же приём, что предохранитель конвейера.

Требование: если ограничение на выбор новой задачи держится дольше
`WIP_GATE_STUCK_HOURS` — отдельный сигнал владельцу тем же каналом, что
предохранитель конвейера. Сигнал означает не «доводка стоит» (воркер всё
это время диспетчируется на неё), а «доводка идёт, но не успевает за
темпом появления находок ревью».

Сценарий: в пуле одновременно свободны задача #95 (новая, PR не
открывался) и задача #89 (открытый PR #500 висит с `ai:changes-requested` —
`unhealthy_pulls` сняла исполнителя, #245), WIP-лимит достигнут -> воркер
диспетчируется адресно на #89 (input `task=89`), #95 не берётся, пока
лимит не снимется.

Сценарий: в пуле свободна только задача #95 (новая, ни у одной свободной
задачи пула нет открытого PR), WIP-лимит достигнут -> диспатча не
происходит вовсе, отчёт называет причину («доводить нечего»).

Сценарий: WIP-лимит не достигнут (открытых PR, ждущих доработки, меньше
`WIP_LIMIT`) -> поведение не отличается от действовавшего до этой правки —
воркер диспетчируется без указания конкретной задачи, сам выбирает
старейшую свободную (`free_task.oldest_free`).
