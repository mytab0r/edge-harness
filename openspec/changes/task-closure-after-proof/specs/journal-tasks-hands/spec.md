18. Ключевые слова авто-закрытия (`Closes|Fixes|Resolves #N`) в теле PR
    запрещены: контракт отклоняет такой PR (GitHub закрыл бы задачу при
    слиянии) — мерж доказывает PR, а не готовность задачи (кейс #56/#57).
    Закрытие идёт стадией приёмки (#227): каждый прогон планировщика
    сопоставляет открытые задачи пула со слитыми PR, которые их ОБЪЯВЛЯЮТ
    (первая строка тела, то же соглашение, что у авто-назначения в
    контракте), и решает по проверяемой улике, вид которой зависит от
    состава изменённых файлов слитого PR:
      - **деплой** (задет `cf-worker/`) — зелёный `deploy-worker.yml` (его
        последний шаг — канарейка UI на проде) ПОСЛЕ мержа и `GET /api/health`
        деплойнутой морды отвечает 200;
      - **скрипт/инструмент** (остальной код) — все check-runs головы PR
        зелёные (тот же критерий, что у очереди слияния);
      - **документация** (только `docs/**`, `openspec/**`, `*.md`) —
        наблюдаемого результата в рантайме по природе нет: задача закрывается
        с явным обоснованием, единственная проверка — файлы со статусом
        `added`/`modified`/новый путь `renamed` физически на месте в main;
        `removed` не проверяется — отсутствие такого файла и есть результат
        мержа (легальная чистка, например архивация `openspec/changes/*` в
        `openspec/specs/` — это удаления вперемешку с добавлениями), а не
        пропавшая улика.
    Три исхода, ни один не тихий: улика подтвердилась → задача закрыта с
    комментарием-уликой; улика провалилась → задача НЕ закрыта, assignee
    снят, комментарий с причиной (доработка, не тихое закрытие); проверка
    самой улики сломана (сеть, секрет, API — не «улики нет», а «возможность
    сломана») → эскалация владельцу (issue #120 + Telegram), задача не
    трогается. Идемпотентность провала — комментарий-маркер с номером PR: та
    же пара (задача, PR) не проверяется повторно, пока не появится новая
    работа. Задача, чьё ТЕКУЩЕЕ назначение относится к уже слитому PR
    (назначена не позже времени мержа), не попадает под просроченное
    назначение «PR не появился» (см. `reap_stale`) — работа появилась и
    слита, дальнейшую судьбу решает улика приёмки, а не возраст назначения.
    Исключение не постоянно: если приёмка провалила улику и задачу отдали
    новому исполнителю ПОСЛЕ мержа, это новое назначение подчиняется обычному
    таймеру `reap_stale` как любое другое — старый слитый PR не делает номер
    задачи невидимым для reap навсегда.
    Постоянное исключение — задача #120 (`WATCHDOG_ISSUE`): это канал
    эскалации pulse_guard (heartbeat/pause маркеры), не разовая работа. PR,
    реализовавший предохранитель, объявляет #120 первой строкой и давно слит
    с зелёными проверками, поэтому сопоставление «открытая задача ↔ слитый
    PR, объявляющий её» находит его для ЛЮБОГО прогона; стадия приёмки
    пропускает #120 безусловно, не проверяя улику вовсе — закрытие этого
    канала приёмкой было бы тихой порчей эскалации побочным эффектом, а не
    «не та задача провалилась».
