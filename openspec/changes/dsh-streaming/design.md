# Дизайн: dsh-streaming

Смежное: [proposal](proposal.md), [dsh-in-job](../dsh-in-job/design.md),
[спека журнала](../../specs/journal-tasks-hands.md),
[архитектура DSH](../../../docs/research/10-dsh-architecture.md) — раздел
«Шов подписки на события сессии», [отвергнутые варианты](../../../docs/research/30-rejected-alternatives.md).

Все утверждения о DSH ниже — из чтения tarball'ов `@deepseek-ai/dsh-*`
0.1.1-rc.2 (скачаны `npm pack` 2026-08-30); файлы-улики процитированы
по месту.

## Форма

```
dsh --profile headless "<task>"                      (Node 24, job)
  └─ плагин dsh-hands-streamer (bundle-слой профиля)
       ctx.on("session/event")  ──фильтр/caps──▶ NDJSON-спул $RUNNER_TEMP
       ctx.on("session/flush")  ──write-through─┘   (файл НАШ, не формат DSH)

dsh_task.sh (bash) ◀── фоновый drain-цикл (интервал ~1 с)
  ├─ новые строки спула → redact → journal-seq → батч ≤50
  ├─ POST /api/events (ретраи мягкие: батч ждёт следующего цикла)
  └─ финальный drain перед job_end — жёсткий (как в слайсе 1)

DO журнал ──▶ морда: replay GET /api/events + live GET /api/events.live
```

Транспорт не меняется: наружу из job — только HTTP-посты в DO
([ADR 0001](../../../docs/decisions/0001-push-model-not-tunnel.md)),
никаких долгоживущих соединений. Сервер журнала не меняется вовсе:
`session_event` проходит существующий `POST /api/events` без правок
(валидация kind там — «непустая строка», ограничений на словарь нет;
`cf-worker/src/harness.ts:303-306`).

## Решения

**Шов подписки — `ctx.on("session/event", ...)`, как у штатной персистенции.**
Эталон — `PersistenceCoordinator.installWritePath()`
(`dsh-session-persistence/lib/index.js:1132-1163`): четыре подписки
`session/created` / `session/event` / `session/flush` / `session/disposed`.
Свойства шва, на которых держится дизайн:

- firehose observe-only: «the hot path never blocks on I/O», сбои листенера
  изолированы per-listener и гасятся в `ctx.logger.warn`
  (`dsh-session/lib/index.js:1411-1415, 1287-1296`) — сломанный стример
  не может уронить агента, он деградирует до предупреждений в логах DSH;
- конструкторные сиды на firehose не выходят («constructor seeds do not
  emit», `dsh-session/lib/index.js:1329-1350`) — для fresh-сессии
  dsh-headless (`session-<uuid>` каждый прогон,
  `dsh-headless/lib/index.js:71`) вся сессия живая, ограничение не стреляет;
- словарь событий — `SessionEventMap` (`dsh-session/lib/types/types.d.ts`):
  `turn/start|end`, `step/start|end`, `user/message`, `assistant/message`,
  `tool/call {name, arguments}`, `tool/result {message, error?}`; `seq`
  события непрерывен с 0, `time` — epoch ms. Наш спул несёт их дословно —
  пересказа формата DSH не создаём.

**Монтаж плагина — bundle-пакет через штатный `dsh plugin`.** Пакет
`dsh-hands-streamer` (исходники в `scripts/dsh-hands-streamer/`) объявляет в
манифесте `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`; job ставит
его `dsh plugin --profile headless add <tgz>` (форвардер в pnpm внутри
каталога профиля; path/tarball spec легальны — `dsh/lib/plugin-9h8shc4d.js`),
патч бандла делает `- insert:` строки `hands-streamer` (синтаксис как в
`dsh-headless/cordis.patch.yml`). Факт монтажа доказывается
`dsh --profile headless --dump-config` до старта прогона, не на веру.
Версия плагина — из чекаута репозитория, отдельный пин не нужен:
tarball собирается из того же коммита, что и клиент.

**Транспорт — спул-файл + drain в bash, плагин HTTP не умеет.**
Решающий аргумент — счётчик journal-seq и редакция секретов должны оставаться
в ОДНОМ владельце (см. отвергнутые). Плагин пишет NDJSON-строки
`{v, session_id, seq, time, type, data}` синхронным append с `\n`
(`appendFileSync`): порядок гарантирован, буферизация не нужна, объём мал
(фильтр отсекает единственный потоковый тип). Пустая последняя строка без
`\n` (обрыв записи) дренируется как «незавершённый хвост» — та же семантика
committed-prefix, что в сканере upstream (`dsh-session-persistence-jsonl/lib/index.js:229-258`,
«ignoring a final record without a newline as a torn tail»).

**`session/flush` — только write-through в спул, никогда не сеть.**
`sessions.flush()` в dsh-headless (`lib/index.js:94`) ждёт все
`session/flush`-листенеры и бросает первую ошибку
(`dsh-session/lib/index.js:1791-1808`). Если бы наш листенер ждал HTTP,
transient-сбой журнала уронил бы ЗАВЕРШЁННЫЙ прогон агента через чужой барьер.
Поэтому листенер
стримера делает только слив буфера в файл; сетевую доставку и её ретраи ведёт
bash, у которого финальная гарантия своя — «job_end уходит только после
принятого журналом флаша» (слайс 1, без изменений).

**Фильтр — allowlist, не denylist.** В спул идут ровно:
`turn/start`, `turn/end` (с `reason` — видимый исход хода),
`step/start`, `step/end`, `user/message`, `assistant/message` (текст, `usage`,
`interrupted`), `tool/call` (`name`, `arguments`), `tool/result` (текст
result-блока, `error`). Всё прочее (`assistant/chunk`, `request/header`,
`request/context`, `todo/write`, типы плагинов) — мимо. Allowlist защищает
бюджет строк журнала (100k/сутки — ограничение из AGENTS.md) от любого
нового потокового типа upstream: незнакомое событие молча не проходит по
построению. Счётчики отброшенного по типам плагин копит в файл статистики
(рядом со спулом), bash один раз в конце публикует их как `stream_note`
(level debug) — видимость без строк на каждое событие.

**Caps на payload — в плагине, одном месте.** Тексты `assistant/message`
до 48 000 символов, `arguments` и текст `tool/result` до 16 000; при обрезке
в payload попадает `truncated: true` и исходный размер — усечение заявлено,
не замаскировано. Числа — константы в исходнике плагина; потолки сервера
(батч 50, тело 1 MiB — `cf-worker/src/config.ts`) drain соблюдает нарезкой.

**Кто владеет счётчиком seq — bash, как и было.** Journal-seq задачи
засевается с сервера и растёт в порядке дренирования
([спека, п.2](../../specs/journal-tasks-hands.md)). Два независимых писателя
(bash + плагин) с самосеяными счётчиками гонялись бы за одной парой
`UNIQUE(task_id, seq)` — проигравший тихо терял бы события на
`INSERT OR IGNORE`. Один писатель = класс коллизии не существует. Цена —
задержка ~1 с (интервал drain-цикла), для живого наблюдения человеком это
не токен-стрим.

**Дедупликация при ретрае job'а.** Каждая сессия — новый `session_id`
(randomUUID в dsh-headless), события нового прогона получают свежие
journal-seq после посева — дублей по построению нет, повторное исполнение
задачи видимо в журнале как новая сессия (правило слайса 1 сохраняется).
Повторная доставка батча внутри прогона гасится `UNIQUE(task_id, seq)`
на сервере — существующая механика, не новая.

**Активация плагина — по env, отказ — громкий.** Плагин читает
`HANDS_SPOOL` (путь спула, задаёт dsh_task.sh в `$RUNNER_TEMP`); переменной
нет → плагин no-op с warn (чужой ручной запуск headless не должен ломаться).
Обратная сторона контракта — в bash: если прогон завершился успешно, а из
спула не дренировано ни одного `session_event`, job краснеет с `agent_error`
«стрим не доставил событий». Молчаливая деградация слоя доказательств
прогресса — тот же silent-wrong, что «зелёный job без результата»; ручной
прогон без плагина через наш клиент невозможен, клиент всегда задаёт
`HANDS_SPOOL`.

**Отставание стрима и отказы транспорта.** Drain-цикл дренирует спул до
пуста каждый тик, батчами ≤50; сбой поста середины прогона — мягкий: батч
остаётся в спуле, цикл повторяет со следующим тиком (спул и есть буфер),
heartbeat продолжает тикать. Окончательная проверка — финальный drain с
жёсткими ретраями слайса 1: не принят журналом → красный job без `job_end ok`.
Рост спула ограничен фильтром и caps; аварийный клапан в плагине —
`MAX_EVENTS` на сессию (превышение: запись прекращается, в статистику пишется
`capped: true`, bash публикует warn) — деградация объявлена, не тихая.

**Слои доказательств после слайса.** Durable-улика прогресса — события
`session_event` в DO SQLite: `{session_id, session_seq, type}` при каждом
`turn/step/tool`. Heartbeat остаётся уликой первого слоя (процесс жив) и
прогрессом не считается — теперь это проверяемо: у наблюдателя есть два
независимых факта («руки живы» и «возраст последнего события сессии»), и
расхождение между ними видно. Session_seq в payload — ключ сопоставления
с durable-логом DSH на диске раннера при разборе инцидентов.

## Отвергнутые варианты

**Плагин постит HTTP прямо в журнал.** Прямое нарушение одного места правды
дважды: счётчик seq пришлось бы делить между bash и Node (гонка посева →
тихие потери на `INSERT OR IGNORE`), а редакцию `nvapi-`/`sk-` — дублировать
в Node. Плюс ретраи/батчи/финальная гарантия написаны и проверены в bash —
второй транспорт это вторая реализация тех же свойств. И главное:
`session/flush`-листенер с сетью внутри роняет завершённый прогон на
transient-сбое через барьер `sessions.flush()` dsh-headless.

**Tail session-файла DSH.** Отвергнут ещё дизайном dsh-in-job («формат файла —
внутренняя деталь DSH… клиент, привязанный к нему, ломается тихо»); tarball-исследование
добавило: файл — zstd-контейнер со внутренними упаковками (`packChunkRuns`),
и это не шов вовсе. Наш спул — не тот вариант: контракт наш собственный,
версионируется полем `v`, о формате хранилища DSH не знает ничего.

**Стрим `assistant/chunk` (токен-за-токеном).** Сотни-тысячи событий на прогон
против бюджета 100k строк/сутки DO — и морде нужен ход, а не сырой поток.
Возврат: только с серверной агрегацией (отдельный канал мимо журнала), которой
сейчас нет и ради слайса 2 не строится.

**Серверный эндпоинт выдачи seq (allocation API).** Решает ту же гонку
писателей, что и «один писатель», но меняет сервер и его спеку ради задачи,
у которой один писатель и так. Возврат: появится второй настоящий писатель
в journal-seq-пространство.

**Второй WS-канал морды мимо журнала.** Журнал — единственное место правды с
replay и live-рассылкой; дубль-канал = второй источник, рассинхрон которого
надо будет лечить. Морда получает стрим существующим `GET /api/events.live`.

## Чего дизайн намеренно не решает

- Богатая проекция сессии в морде (дерево turn/step, карточки инструментов,
  разница диалогов). Слайс даёт минимальный читаемый рендер `session_event`;
  полноценный UI — отдельно, данных для него контракт уже несёт.
- События субагентов и мульти-сессий: dsh-headless создаёт одну сессию за
  прогон; payload несёт `session_id`, так что расширение не потребует смены
  контракта, но проекция N сессий не проектируется.
- `todo/write`, `approval/*`, `llm/retry` в стриме: allowlist их не пускает;
  вернуться можно одной строкой allowlist, когда морда научится их рисовать.
- Интерактивность и follow-up — контракт dsh-headless не меняется.
- Экономика `pnpm` на раннере (corepack enable) — механика job'а, см. tasks.

## Не подтверждено

- **Живой монтаж bundle-плагина в профиль headless.** Механика прочитана в
  tarball CLI (`lib/plugin-9h8shc4d.js`: pnpm-форвардер, reconcile
  `dsh.profile.bundles`), но прогон `dsh plugin --profile headless add <tgz>`
  + `--dump-config` не выполнялся. Первый шаг реализации — именно эта
  проверка; фолбэк, если bundle-слой headless-профиля не подхватывается:
  оверлей `--patch <path>` (слой сильнее профиля, задокументирован в
  `dsh/lib/bin.js`).
- **pnpm на раннере.** `dsh plugin add` требует pnpm (форвардер); доступность
  через corepack на setup-node 24 не проверялась. Проверка — тем же первым
  шагом.
- **Scope-фильтрация для root-level подписки в нашем месте дерева.** Паттерн
  списан с работающего upstream-плагина (персистенция подписывается так же
  из корня и получает события всех сессий), но наш плагин монтируется другим
  слоем — подтверждается первым же прогоном: события появились в спуле.
- **Реальные размеры полезной нагрузки.** Caps выставлены консервативно
  (48k/16k/16k); распределение размеров замерит первый прогон — если обрезки
  частые, пересмотреть, опираясь на статистику `stream_note`.
- **Чекпоинт-политика DSH** (`dsh-session-checkpoint-policy`): как часто
  upstream сам зовёт `sessions.flush()` внутри прогона — пакет не читался.
  На дизайн не влияет (наш листенер от сети не зависит), но частота
  write-through'ов спула в барьере не измерена.
