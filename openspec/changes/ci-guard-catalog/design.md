# design: каталог гвардий (#749)

## Форма: каталог, не манифест

Issue #749 сам предпочитает каталог («конфликты физически невозможны, два
PR трогают разные файлы») и допускает манифест только «если каталог
упирается в что-то названное». Измерено — не упирается:

- Каждый существующий рукописный шаг — самодостаточный командный блок
  (`pip install …` + `pytest …`, либо `node --test …`, либо `bash …`).
  Manifest (JSON/YAML со списком команд) заставил бы либо инлайнить
  многострочные команды строкой (теряя читаемость и подсветку bash),
  либо продолжать держать команды в отдельных файлах — тогда манифест был
  бы лишним уровнем косвенности поверх уже-каталога.
- Одна строка манифеста, добавляемая каждым PR, — это то же самое поле
  конфликта, что и сейчас (одна строка в общем файле, а не ноль строк).
  Каталог даёт буквально ноль строк общего файла на новую гвардию.

Итог: каталог `scripts/ci/guards/*.sh`, один файл — одна гвардия,
исполняется целиком (`bash "$script"`) единственным шагом-перебором
`scripts/ci/run_guards.sh` в `repo-ci.yml`.

## Как несутся `if:`/`env:` существующих шагов

Единый замер этого change (методика — `proposal.md`, «Зачем»;
воспроизводится `python scripts/lib/ci_guard_registration_guard.py` +
разбором `env`/`if` того же `yaml.safe_load`-документа): job `test` несёт
**95 шагов**, **92** с `run:`. Из этих 92 нетривиальные `if:`/`env:` несут
**6** (`env: GH_TOKEN` рукописных шагов, не считая `env:` шага-перебора —
см. ниже) и **2** (`if:`) — пересекаются не полностью:

| Шаг | `if:` | `env:` |
|---|---|---|
| Белые пятна без метки task (#179) | — | `GH_TOKEN` |
| Рассинхрон тела задачи и графа зависимостей (#371) | — | `GH_TOKEN` |
| Автоперенос поля «Чем блокируется» (#529) | `github.event_name == 'push'` | `GH_TOKEN` |
| Коллизия имён с апстримом | — | `GH_TOKEN` |
| Квота GitHub API — ранняя проверка (инварианты) | — | `GH_TOKEN` |
| Инварианты состояния репозитория — живой снимок | `steps.quota.outputs.skip != 'true'` | `GH_TOKEN` |

(Ревью PR #771, major 4: прежняя версия этого раздела мерила «5 из 67» —
множество, ограниченное только именем шага; правильное множество — «6/2 из
92», и ни один из этих шести/двух не входит в замороженный на момент ЭТОГО
PR `ALLOWLIST`/95-92-строчную детекцию по имени, что и было причиной
недосчёта. 95/92, не 94/91: ребейз этого PR на `main` подхватил независимо
слитый #732, добавивший ещё одну гвардию — учтена в `ALLOWLIST` тем же
коммитом, см. `ci_guard_registration_guard.py`.) Остальные шаги с `run:` —
голый `run:` без условий и переменных.

**`env: GH_TOKEN`** (везде значение — `${{ github.token }}`, публичный
токен без секрета) несётся `env:` шага-перебора «Каталог гвардий … —
перебор (#749)» (не уровня `job test` — ревью PR #771, minor 6: ни одна
гвардия каталога на момент этого PR не читает `gh api`, а job-level `env:`
расширял бы радиус до всех 95 шагов job без единого потребителя):
`bash "$script"` внутри `scripts/ci/run_guards.sh` — дочерний процесс
именно этого шага, поэтому переменная доходит до любого файла каталога,
которому в будущем понадобится `gh api`, без per-файловой метаданной и без
job-level радиуса. Точечные `env:` у существующих рукописных шагов НЕ
убраны этим PR (не мигрируются) — не второе место правды по значению (то
же самое `github.token`), временное дублирование до отдельной уборки при их
миграции.

**`if: github.event_name == 'push'`** несётся самим файлом гвардии:
`$GITHUB_EVENT_NAME` — штатная переменная окружения раннера GitHub Actions,
доступна любому шагу без дополнительной проводки. Будущий файл
`scripts/ci/guards/wire-declared-deps.sh` мог бы начинаться с
`[ "$GITHUB_EVENT_NAME" = "push" ] || { echo skip; exit 0; }`.

**`if: steps.quota.outputs.skip != 'true'`** — единственный случай, НЕ
обобщаемый без спекулятивной инфраструктуры: условие зависит от OUTPUT
конкретного соседнего шага (`id: quota`) этого же job, а не от переменной
окружения раннера. Перенос потребовал бы либо (а) специального канала
«job-level shared state», которым сегодня не пользуется ни один другой шаг,
либо (б) параметра каталога «эта гвардия гейтится квотой» — оба варианта
строятся ради ОДНОГО случая, что запрещено правилом репозитория «не строй
абстракцию заранее» (AGENTS.md, «Меньше кода»). Шаг остаётся рукописным в
`repo-ci.yml`, честно назван (не молчит) здесь и в `scripts/ci/run_guards.sh`.

## Миграция остатка (77 шагов ALLOWLIST)

**Не одним PR.** Перенос всех 77 разом — дифф на порядок больше
`LARGE_DIFF_LINES` (800) и гарантированный конфликт с каждым из открытых
PR, трогающих `repo-ci.yml` (эти PR правят СВОИ несколько строк внутри
файла — при полном переписывании файла конфликтует с ЛЮБОЙ их правкой, не
только с соседними строками).

**Этот PR переносит одну гвардию** (протухшая метка `blocked`, #334) —
минимальный дифф внутри `repo-ci.yml` (удаление 12 строк одного шага +
добавление одного нового шага-перебора), плюс ДВЕ новые гвардии, которые
дописываются ТОЛЬКО в каталог (ноль строк `repo-ci.yml`) — то самое
доказательство критерия приёмки.

**Порядок для будущей миграции остатка** (не выполняется этим change,
только называется, как и предписывает issue #749, раздел «Оговорка про
миграцию»): начинать с гвардий, которых НЕТ ни в одном из 17 открытых PR
(измерено ниже — таких большинство), и только затем — гвардий, которые
открытые PR *добавляют* (не трогают чужую), чтобы миграция не рождала
конфликт с чужой работой, которую сама и призвана исключить.

**14 из 17 — конфликт; 3 из 17 — чисто.** Но тот же замер `git merge-tree
--write-tree origin/main <branch>` (ветка против ПРОСТОГО main, без единой
правки этого PR) даёт **ровно те же 14 из 17** конфликтующих — то есть
верное утверждение здесь ровно одно: **этот PR не добавляет ни одного
нового конфликта** сверх уже существующего baseline (те же 14 веток
конфликтуют что до, что после этого PR). Это НЕ значит, что `repo-ci.yml`
не участвует в этих 14 конфликтах, — по факту участвует: у 7 из 14
(`git diff --name-only origin/main...<branch>` пересечено со списком файлов
конфликта) `repo-ci.yml` — один из конфликтующих файлов, и у четырёх из них
(#328, #571, #596, #640) это ЕДИНСТВЕННЫЙ конфликтующий файл — то есть у
этих четырёх веток конфликт исчезнет только КОГДА-ТО после ручного/
автоматического ребейза, но не раньше, и обоснование PR («каталог убирает
конфликты, а не переносит их») по-прежнему держится ТОЛЬКО на «не добавляет
новых», не на «эти 14 не связаны с repo-ci.yml вовсе» (прежняя формулировка
здесь была неверна фактически и подрывала собственную мотивировку PR —
ревью PR #771, major 11). Из трёх чистых веток минимум одна (#453) сама
входит в список 17, трогающих `repo-ci.yml`, — её собственная правка не
пересекается с удалением одного шага и добавлением job-level `env`/шага-
перебора, которые делает этот PR.

## Критерий приёмки — факт, не рассуждение

Три коммита PR (проверяются `git show --stat <commit>`):

1. Механизм + миграция одной гвардии — единственный коммит, трогающий
   `repo-ci.yml` (удаление старого шага, добавление `env`/шага-перебора).
2. `scripts/ci/guards/ci-guard-registration.sh` (гвардия механизма,
   `scripts/lib/ci_guard_registration_guard.py`) — **ноль строк
   `repo-ci.yml`** в diffstat.
3. `scripts/ci/guards/run-guards-mechanism.sh` (smoke самого перебора) —
   **ноль строк `repo-ci.yml`** в diffstat.

Мутация (issue #749, «удалить элемент источника — проверка исчезает»)
доказана прогоном `scripts/ci/test/run-guards.smoke.sh` на синтетическом
каталоге: добавление/удаление `*.sh`-файла добавляет/убирает
соответствующую проверку из вывода перебора; падение одной гвардии
красит весь прогон; пустой каталог красит CI явно (а не проходит нулём
проверок молча).

## Гвардия на рецидив

`scripts/lib/ci_guard_registration_guard.py` статически сверяет шаги job
`test`, распознанные как регистрация гвардии ЛЮБЫМ из двух признаков —
соглашение именования ИЛИ содержимое `run:` (pytest/`node --test`/
тестовый-или-guard-файл; второй признак — ревью PR #771, блокирующая 2:
только именем обходился переименованием шага, живая мутация «Проверка/
Канарейка/Инвариант/Мутационный тест …» и шаг без `name:` давали `EXIT=0`)
— с замороженным `ALLOWLIST` (77 записей) и отдельным
`INFRA_EXEMPT_STEP_NAMES` (ровно 1 — сам шаг-перебор: не гвардия, а
механизм её запуска, назван так, чтобы НЕ совпасть ни с одним из двух
признаков). `ALLOWLIST_RATCHET_MAX=77` — верхняя граница «только вниз»
(major 5): без неё текст отказа читался как приглашение решить находку
дешёвым дописыванием строки в `ALLOWLIST` вместо переноса гвардии в
каталог. Мутация: дописать шаг `- name: Гвардия …` (или шаг с содержимым
pytest/node --test под ЛЮБЫМ именем, или шаг вовсе без `name:`) в фикстуру
`repo-ci.yml` без записи в `ALLOWLIST` → `check_no_undeclared_step`
находит; убрать запись `ALLOWLIST`, оставив шаг устаревшим, → тоже
находит; вырастить `ALLOWLIST` сверх `ALLOWLIST_RATCHET_MAX` → тоже
находит (тройная сверка, тот же приём, что `test_label_registry.py`/
`test_infra_gh_inventory.py`). Доказано
`scripts/lib/test_ci_guard_registration_guard.py` (19 тестов, включая
сценарий двойного прогона — гвардия и в каталоге, и рукописным шагом под
именем вне соглашения).

## Совместимость с orphan_test_guard (#583)

`scripts/lib/orphan_test_guard.py::iter_workflow_run_steps` читает только
`.github/workflows/*.yml` — тест, чей `pytest`/`node --test` вызов лежит
ТОЛЬКО внутри файла каталога, не был бы виден и попал бы в «осиротевшие»
ложно. Добавлены `iter_guard_catalog_steps` (читает `scripts/ci/guards/*.sh`
как псевдо-шаги) и `_catalog_runner_is_wired` (включает их в покрытие,
только если `scripts/ci/run_guards.sh` реально вызван каким-то шагом
workflow — иначе каталог не подключён к CI вовсе, и «покрыт» было бы ложным
зелёным). Доказано прогоном (не рассуждением):
`python scripts/lib/orphan_test_guard.py` на живом репозитории после
миграции — 77 тестовых файлов, 0 сирот (число живое — растёт с каждым
новым тестовым файлом репозитория, здесь важен факт «0 сирот», не
конкретное значение); мутация в
`scripts/lib/test_orphan_test_guard.py::
test_build_report_covers_test_invoked_only_inside_catalog_file` — тест,
подключённый только каталогом, зелёный; тот же тест без подключённого
перебора — снова орфан.

## INFRA-GH.md

Таблица workflow в `docs/agents/INFRA-GH.md` описывает файлы
`.github/workflows/*.yml`, не отдельные шаги — этот change не добавляет
новый workflow-файл (только новый шаг существующего `repo-ci.yml`), поэтому
таблицу трогать не пришлось; `scripts/lib/test_infra_gh_inventory.py`
подтверждает (зелёный без изменений файла). Одна строка добавлена в
`docs/agents/INFRA-GH.md` под существующей записью `repo-ci.yml` — упоминание
каталога `scripts/ci/guards/` как места регистрации гвардий, чтобы
следующий агент не читал 60+ шагов, ища, куда добавить новую проверку.
