# design: каталог гвардий (#749)

## Форма: каталог, не манифест

Issue #749 сам предпочитает каталог («конфликты физически невозможны, два
PR трогают разные файлы») и допускает манифест только «если каталог
упирается в что-то названное». Измерено — не упирается:

- Каждый существующий рукописный шаг — самодостаточный командный блок
  (`pip install …` + `pytest …`, либо `node --test …`, либо `bash …`).
  Manifest (JSON/YAML со списком команд) заставил бы либо инлайнить
  многострочные команды строкой (теряя читаемость и подсветку bash),
  либо продолжать держать команды в отдельных файлах — тогда манифест был
  бы лишним уровнем косвенности поверх уже-каталога.
- Одна строка манифеста, добавляемая каждым PR, — это то же самое поле
  конфликта, что и сейчас (одна строка в общем файле, а не ноль строк).
  Каталог даёт буквально ноль строк общего файла на новую гвардию.

Итог: каталог `scripts/ci/guards/*.sh`, один файл — одна гвардия,
исполняется целиком (`bash "$script"`) единственным шагом-перебором
`scripts/ci/run_guards.sh` в `repo-ci.yml`.

## Как несутся `if:`/`env:` существующих шагов

Живой замер (2026-09-08, `.github/workflows/repo-ci.yml`, job `test`, 67
шагов, совпадающих с именованием гвардии `Тест…/Гвардия…/Smoke…/Юнит-тест…`
— перебор `yaml.safe_load`, не текстовый греп): **5 из 67** несут
нетривиальные `if:`/`env:`:

| Шаг | `if:` | `env:` |
|---|---|---|
| Белые пятна без метки task (#179) | — | `GH_TOKEN` |
| Рассинхрон тела задачи и графа зависимостей (#371) | — | `GH_TOKEN` |
| Автоперенос поля «Чем блокируется» (#529) | `github.event_name == 'push'` | `GH_TOKEN` |
| Коллизия имён с апстримом | — | `GH_TOKEN` |
| Инварианты состояния репозитория — живой снимок | `steps.quota.outputs.skip != 'true'` | `GH_TOKEN` |

Остальные 62 — голый `run:` без условий и переменных.

**`env: GH_TOKEN`** (4 из 5, везде значение — `${{ github.token }}`,
публичный токен без секрета) несётся подъёмом на уровень `job test` (этот
change добавляет `env: GH_TOKEN: ${{ github.token }}` в `test:`) — каждый
файл каталога, которому нужен `gh api`, читает переменную окружения
напрямую, без per-файловой метаданной. Точечные `env:` у пяти существующих
шагов НЕ убраны этим PR (не мигрируются) — не второе место правды по
значению (то же самое `github.token`), временное дублирование до отдельной
уборки при их миграции.

**`if: github.event_name == 'push'`** (1 из 5) несётся самим файлом
гвардии: `$GITHUB_EVENT_NAME` — штатная переменная окружения раннера GitHub
Actions, доступна любому шагу без дополнительной проводки. Будущий файл
`scripts/ci/guards/wire-declared-deps.sh` мог бы начинаться с
`[ "$GITHUB_EVENT_NAME" = "push" ] || { echo skip; exit 0; }`.

**`if: steps.quota.outputs.skip != 'true'`** (1 из 5) — единственный
случай, НЕ обобщаемый без спекулятивной инфраструктуры: условие зависит от
OUTPUT конкретного соседнего шага (`id: quota`) этого же job, а не от
переменной окружения раннера. Перенос потребовал бы либо (а) специального
канала «job-level shared state», которым сегодня не пользуется ни один
другой шаг, либо (б) параметра каталога «эта гвардия гейтится квотой» —
оба варианта строятся ради ОДНОГО случая из 67, что запрещено правилом
репозитория «не строй абстракцию заранее» (AGENTS.md, «Меньше кода»). Шаг
остаётся рукописным в `repo-ci.yml`, честно назван (не молчит) здесь и в
`scripts/ci/run_guards.sh`.

## Миграция остатка (66 шагов)

**Не одним PR.** Перенос всех 66 разом — дифф на порядок больше
`LARGE_DIFF_LINES` (800) и гарантированный конфликт с каждым из открытых
PR, трогающих `repo-ci.yml` (эти PR правят СВОИ несколько строк внутри
файла — при полном переписывании файла конфликтует с ЛЮБОЙ их правкой, не
только с соседними строками).

**Этот PR переносит одну гвардию** (протухшая метка `blocked`, #334) —
минимальный дифф внутри `repo-ci.yml` (удаление 12 строк одного шага +
добавление одного нового шага-перебора), плюс ДВЕ новые гвардии, которые
дописываются ТОЛЬКО в каталог (ноль строк `repo-ci.yml`) — то самое
доказательство критерия приёмки.

**Порядок для будущей миграции остатка** (не выполняется этим change,
только называется, как и предписывает issue #749, раздел «Оговорка про
миграцию»): начинать с гвардий, которых НЕТ ни в одном из 17 открытых PR
(измерено ниже — таких большинство), и только затем — гвардий, которые
открытые PR *добавляют* (не трогают чужую), чтобы миграция не рождала
конфликт с чужой работой, которую сама и призвана исключить.

## Критерий приёмки — факт, не рассуждение

Три коммита PR (проверяются `git show --stat <commit>`):

1. Механизм + миграция одной гвардии — единственный коммит, трогающий
   `repo-ci.yml` (удаление старого шага, добавление `env`/шага-перебора).
2. `scripts/ci/guards/ci-guard-registration.sh` (гвардия механизма,
   `scripts/lib/ci_guard_registration_guard.py`) — **ноль строк
   `repo-ci.yml`** в diffstat.
3. `scripts/ci/guards/run-guards-mechanism.sh` (smoke самого перебора) —
   **ноль строк `repo-ci.yml`** в diffstat.

Мутация (issue #749, «удалить элемент источника — проверка исчезает»)
доказана прогоном `scripts/ci/test/run-guards.smoke.sh` на синтетическом
каталоге: добавление/удаление `*.sh`-файла добавляет/убирает
соответствующую проверку из вывода перебора; падение одной гвардии
красит весь прогон; пустой каталог красит CI явно (а не проходит нулём
проверок молча).

## Гвардия на рецидив

`scripts/lib/ci_guard_registration_guard.py` статически сверяет имена
шагов job `test`, совпадающие с соглашением именования гвардий, с
замороженным `ALLOWLIST` (66 оставшихся + 1 инфраструктурный список — сам
шаг-перебор назван так, чтобы НЕ совпасть с соглашением, иначе гвардия
путала бы себя с собой). Мутация: дописать шаг `- name: Гвардия …` в
фикстуру `repo-ci.yml` без записи в `ALLOWLIST` → `check_no_undeclared_step`
находит; убрать запись `ALLOWLIST`, оставив шаг устаревшим, → тоже
находит (двусторонняя сверка, тот же приём, что `test_label_registry.py`/
`test_infra_gh_inventory.py`). Доказано
`scripts/lib/test_ci_guard_registration_guard.py` (9 тестов).

## Совместимость с orphan_test_guard (#583)

`scripts/lib/orphan_test_guard.py::iter_workflow_run_steps` читает только
`.github/workflows/*.yml` — тест, чей `pytest`/`node --test` вызов лежит
ТОЛЬКО внутри файла каталога, не был бы виден и попал бы в «осиротевшие»
ложно. Добавлены `iter_guard_catalog_steps` (читает `scripts/ci/guards/*.sh`
как псевдо-шаги) и `_catalog_runner_is_wired` (включает их в покрытие,
только если `scripts/ci/run_guards.sh` реально вызван каким-то шагом
workflow — иначе каталог не подключён к CI вовсе, и «покрыт» было бы ложным
зелёным). Доказано прогоном (не рассуждением):
`python scripts/lib/orphan_test_guard.py` на живом репозитории после
миграции — 76 тестовых файлов, 0 сирот; мутация в
`scripts/lib/test_orphan_test_guard.py::
test_build_report_covers_test_invoked_only_inside_catalog_file` — тест,
подключённый только каталогом, зелёный; тот же тест без подключённого
перебора — снова орфан.

## INFRA-GH.md

Таблица workflow в `docs/agents/INFRA-GH.md` описывает файлы
`.github/workflows/*.yml`, не отдельные шаги — этот change не добавляет
новый workflow-файл (только новый шаг существующего `repo-ci.yml`), поэтому
таблицу трогать не пришлось; `scripts/lib/test_infra_gh_inventory.py`
подтверждает (зелёный без изменений файла). Одна строка добавлена в
`docs/agents/INFRA-GH.md` под существующей записью `repo-ci.yml` — упоминание
каталога `scripts/ci/guards/` как места регистрации гвардий, чтобы
следующий агент не читал 60+ шагов, ища, куда добавить новую проверку.
