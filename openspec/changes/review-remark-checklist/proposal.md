# review-remark-checklist: третья категория находок ревью — чеклист некритичных замечаний в теле PR (#462)

Задача: #462. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Контракт `scripts/review/ai_prompt.md` знал два исхода находки: блокирующая
(проза, до 5, вердикт `rework`) и работа вне рамок PR (блок `ЗАДАЧА` → issue).
Формулировка вердикта `approve` разрешала находки прозой, если они
«некритичны для мержа», не называя, куда такая находка девается — она
оставалась голой прозой в комментарии, PR сливался, замечание пропадало.

Замер по 29 просмотренным `approve`-вердиктам (2026-09-06, живая выборка PR
#452/#402/#384/#331/#285/#283/#284/#282/#229/#228/#227/#214/#211/#209/#200/
#198/#193/#191/#190/#188/#186/#184/#181/#180/#177/#176/#172/#165/#154): 3 PR
(#452, #285, #180) содержат явные некритичные находки прозой («Два замечания,
оба не блокируют мерж», «Единственное замечание (не блокирующее)») — 5 штук
суммарно, ни одна не стала ни блокером, ни задачей.

## Что делается

- Контракт `ai_prompt.md` называет РОВНО три исхода находки, не два: блокирует
  мерж → проза (до 5), вердикт `rework`; некритично, но стоит сделать → блок
  `ЗАМЕЧАНИЕ: <заголовок> / тело / КОНЕЦ ЗАМЕЧАНИЯ` (тот же стиль парсинга,
  что `ЗАДАЧА`/`КОНЕЦ ЗАДАЧИ`); работа вне рамок PR → блок `ЗАДАЧА` (не
  меняется). Формулировка вердикта `approve` в контракте — «блокирующих
  находок нет», а не «замечаний нет или они некритичны».
- Новое место правды `scripts/lib/review_checklist.py`: парсинг блока
  ЗАМЕЧАНИЕ, слияние пунктов в чеклист ТЕЛА PR (секция между HTML-маркерами,
  невидимыми в рендере), подсчёт незакрытых пунктов на момент слияния.
  Общее для `ai_review.py` (пишет при вердикте) и `scheduler.py` (читает при
  слиянии) — не две копии формата.
- `ai_review.py::cmd_verdict` сливает предложенные ЗАМЕЧАНИЯ в тело PR через
  `gh api -X PATCH .../pulls/N` (не через комментарий — тело единственный
  постоянный носитель чеклиста, второе хранилище не создаётся). Уже
  отмеченные автором пункты не перезаписываются: новые дописываются по
  заголовку (дедупликация).
- Автор отмечает пункт нативным чекбоксом GitHub в описании PR — механизм
  уже существует в GitHub (клик по `- [ ]` в теле issue/PR редактирует тело),
  второй механизм отметки не создаётся.
- Слияние с незакрытым чеклистом НЕ блокируется: перевело бы некритичное в
  критичное и вернуло бы конвейер к вечным кругам (тот же класс решения, что
  развёл `review:large` от `review:changes-requested`, ADR 0007). И не
  теряется молча: `scheduler.py::after_merge` читает незакрытые пункты через
  `review_checklist.unresolved_items` и заводит ОДНУ задачу-хвост со ссылкой
  на PR (`review_checklist.tail_issue_title/tail_issue_body`), идемпотентно
  по заголовку «Хвост чеклиста ревью PR #N» — не issue на каждый пункт.
- Документация (`docs/agents/PROTOCOL.md`, `WORKER-PLAYBOOK.md`,
  `docs/agents/LABELS.md`, `docs/decisions/0007-ai-review-gate.md`) описывает
  ровно три исхода находки ревьюеру и автору.

## Оценка ценности и приоритета задачи-хвоста — честно

Машинной оценки ценности находок нет и не изобретается здесь. Задача-хвост
наследует только то, что доказуемо по построению — ссылку на породивший PR
и метку `task`; приоритет в общем пуле задач сейчас определяется возрастом
(`scripts/orchestra/scheduler.py::oldest_free`); приоритет по графу
блокирующих задач предложен отдельным незавершённым изменением (#367, не
смержено на момент этого изменения) и сюда не привязывается — задача-хвост
не получает специального приоритета сверх обычного места в пуле. Оценка
ценности находки («стоит ли вообще делать») — решение человека, принимаемое
при разборе пула тем, кто берёт задачу, либо владельцем — не автоматикой.

## Проверено

- `python -m pytest scripts/lib/test_review_checklist.py scripts/review/test_ai_review.py
  scripts/orchestra/test_scheduler.py scripts/lib/test_label_registry.py -q`.
- Мутация 1: закомментировать перенос отмеченных пунктов в `merge_checklist`
  (вернуть все пункты неотмеченными) — тест на сохранение чекбокса между
  раундами краснеет.
- Мутация 2: убрать проверку идемпотентности по заголовку в `after_merge`
  (`tail_title in open_titles`) — тест на повторный вызов `after_merge`
  красит дублирующий POST issue.
- Мутация 3: убрать вызов `findings_of(..., remarks)` (вернуть старую
  сигнатуру без remarks) — тест на отсутствие дублирования текста замечания
  в свободной прозе комментария краснеет.

## Что вне рамок

- Регулярный (не одноразовый) замер доли находок, ушедших в чеклист против
  прозы/задач — не измеряется здесь, разовый замер выше только доказывает
  наличие дыры.
- Изменение формата блока `ЗАДАЧА` (поле `МАСШТАБ`, задача #426/PR #433) —
  не тронуто этим изменением, ортогонально: ЗАМЕЧАНИЕ — новый, отдельный тип
  блока, не расширение ЗАДАЧА.
