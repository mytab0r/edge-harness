# Дельта-спека: инбокс владельца (#20)

Расширяет `openspec/specs/journal-tasks-hands.md` новым разделом «Инбокс
владельца (#20)» (пп. 30–37). Сложен в базовую спеку одновременно с
реализацией (PR #173).

## ADDED: приём сообщений (пп. 30–32)

Требование: `POST /api/messages/ingest` принимает плоскую форму и сырой
Telegram update; идентификаторы, приходящие числами (update_id, message_id,
from.id, chat.id), приводятся к строкам до записи и до сравнения ключей.

Требование: ключ идемпотентности — `source_msg_id`, иначе `update_id`, иначе
`message.message_id`; без любого из них — 400 `need_source_msg_id`. Повторный
приём (ретрай источника) возвращает существующую строку (`status: "exists"`),
дубль не создаётся. Правило одно для обоих приёмных маршрутов — `ingest` и
ручной `POST /api/messages`.

Требование: маршрут авторизуется как все `/api/*`; `auth: false` у маршрутов
спеки не существует.

## ADDED: разбор и жизненный цикл (пп. 33–37)

Требование: водитель разбора назван — пульс DO на каждом тике; ручной
`POST /api/messages/process` не единственный триггер. Захват сообщения
атомарный: ровно один обработчик переводит `new → processing`. Запись
финального статуса и возврат в `new` — CAS по моменту захвата: проходка,
потерявшая владение, чужой результат не перезаписывает и второй issue не
«выигрывает» молча.

Требование: директива создаёт issue через `GH_ISSUES_TOKEN` (узкий,
Issues:RW, ADR 0011) с метками `task`, `source:inbox`. `GH_DISPATCH_TOKEN`
для этого не используется никогда (ADR 0008: у него нет права на Issues).
Не заданный токен, сеть и 5xx/429 — повторяемые: сообщение возвращается в
`new`; после `LIMITS.messageMaxAttempts` попыток — `failed` с последней
ошибкой. Прочие 4xx — `failed` немедленно. `retry_failed` возвращает `failed`
в `new` с обнулёнными попытками. Каждый вызов GitHub ограничен
`LIMITS.messageIssueFetchTimeoutMs` — заведомо меньше порога ватчдога
(инвариант гвардится тестом).

Требование: текст публичного issue (заголовок и тело) проходит маскирование
секретов тем же классом паттернов, что `dsh-ci.sh::redact`
(nvapi-/sk-/ghp_/github_pat_; паритет гвардится test_redact_parity.py),
причём ДО усечения заголовка — усечённый секрет короче минимума паттерна
уже не маскируется; факт маскирования — в `result.secrets_redacted`. Командные слова директив — один список
(`DIRECTIVE_WORDS`) для классификатора и чистки заголовка.

Требование: `raw` уходит в `ignored` (не возвращается в `new`);
`chat`/`doc_edit` завершаются `done` с пометкой
`classified_for_manual_review`.

Требование: `processing` старше `LIMITS.messageStuckProcessingMs` возвращается
пульсом в `new`. Ни одно сообщение не находится в невидимом зависшем
состоянии: статусы считаются в `status.messages`.

Требование: пагинация списка согласована с сортировкой — newest-first
(`ts DESC, id DESC`), курсор `after` выбирает `id < after`; обход без дублей
и пропусков, включая равные `ts`.

Сценарий: ретрай Telegram-апдейта с тем же числовым `update_id` → та же
строка, `exists`.

Сценарий: директива при не заданном токене → три разбора → `failed` с
`issues_not_configured`; после установки секрета новые директивы создают
issue с первого разбора, накопленные `failed` — по `retry_failed`.

Сценарий: серия из трёх сообщений одного отправителя в пределах окна → у 2-го
и 3-го `grouped_with` указывает на предыдущее, триаж видит цепочку.
