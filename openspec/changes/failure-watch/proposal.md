# failure-watch: пульс оркестратора замечает провалы ключевых workflow и доводит до действия (#477)

Задача: #477. Код: `scripts/orchestra/pulse_guard.py::failure_watch`, вызывается
из `scheduler.py::main()` рядом с `heartbeat_check`. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Владелец: «Кто-то мониторит ошибки? Я хочу, чтобы был механизм самофикса и
такие ошибки не пропадали в логах раннера, а обрабатывались кем-то».
Замер цены (2026-09-02/03, AGENTS.md): около пятнадцати дефектов конвейера за
двое суток — ни один не был найден системой, все нашлись чтением логов; красный
прогон ключевого workflow (`worker.yml`, `hands.yml`, `orchestra.yml`,
`deploy-worker.yml`, `deploy-dsh-edge.yml`) оставался строкой в Actions без
сигнала, задачи и разбора.

## Что делается

Каждый пульс оркестратора, до всей остальной работы (тот же довод, что у
`heartbeat_check`):

- **Дешёвый опрос** — `status=completed&per_page=20` по каждому из пяти
  отслеживаемых workflow (одна страница на workflow, логи прогонов подряд не
  выгружаются); вывод фильтруется клиентским набором
  `FAILURE_WATCH_RUN_CONCLUSIONS` (failure + timed_out, без cancelled —
  серверный `status=failure` не отдаёт `timed_out` вовсе); окно свежести
  `FAILURE_WATCH_WINDOW_MINUTES` (30 мин, кратно 15-минутному пульсу),
  измеряется от `updated_at` прогона — момента провала, не постановки в
  очередь (`created_at`): долгий воркер по замыслу пашет десятки минут, и по
  `created_at` его свежий провал лежал бы вне окна на каждом пульсе —
  пульс не заводит сущности по уже неактуальной причине.
- **Факт, не гипотеза** — последняя содержательная строка `##[error]` из лога
  упавшего job'а; boilerplate раннера («Process completed with exit code N»)
  пропускается — живой замер на прогоне 34027035455 показал, что иначе фактом
  называется код выхода, а не причина, и отпечаток схлопывает разные дефекты
  одного job'а в один класс.
- **Классификация** (`classify_failure_cause`, закрытый список сигнатур,
  fail loud по умолчанию — нераспознанное считается дефектом):
  `infra` (лимиты/сеть — лечится ожиданием: один тихий след в #120 на класс,
  без Telegram и без задачи), `stale_base` (устаревшая база — газ уже назван
  в #474/task-branch: только наблюдение), `defect` — задача в пул (метки
  `task` + `ci-failure`) с точной причиной.
- **Один сигнал на класс** — дедуп по отпечатку класса причины
  (`failure_fingerprint`: workflow + job + нормализованная строка ошибки),
  не по run id; для `infra` — маркер в #120, для `defect` — поиск среди
  открытых issues с меткой `ci-failure`.
- **Разграничение с автодетектором простоя (#201)** — прогоны
  `event=pull_request` failure_watch не разбирает: красный прогон PR-события —
  это красный обязательный чек на PR, его устойчивую причину заводит
  автодетектор (`check:red:<имя>`); вторая задача `ci-failure` на тот же
  дефект — ровно тот спам, который запрещает критерий #477 (находка ревью
  PR #488, раунд 2).
- **Без факта задачи нет** — лог job'а не прочитался: громкое наблюдение (⚠️),
  устойчивый случай подберёт автодетектор #201 (класс `warn:`); задача по
  грубому фолбэк-факту «шаги: …» мигала бы во второй задачей, когда лог на
  следующем пульсе прочитается (находка ревью PR #488).
- **Потолок логов на прогон** — разбирается до
  `FAILURE_WATCH_MAX_JOBS_PER_RUN` (3) упавших job'ов (лог job'а — дорогой
  запрос), остальные названы поимённо в наблюдении — хвост не прячется молча
  (тот же класс, что #308).

## Чего изменение не делает

Не лечит дефекты само: однозначного автоматического лечения у дефектов
(красный тест, отсутствующий файл) нет — честно заводится задача с точной
причиной, а не имитируется автоматика. Ребейз устаревшей базы — единственный
однозначный самофикс в этой области — уже газ другой автоматики (#474,
авто-ребейз конфликтных PR; `task-branch`/pre-commit сами просят
`git rebase origin/main`): failure_watch узнаёт класс и уступает, с этой
автоматикой не пересекается.

## Тормоза и газ

Нового тормоза нет: `infra`/`stale_base` — только наблюдения; `defect` заводит
обычную задачу пула, слияния не блокирует. От спама — окно свежести, дедуп по
отпечатку класса, потолок job'ов на прогон и исключение PR-событий.

## Отвергнутые варианты

Нет в `docs/research/30-rejected-alternatives.md`: периодический опрос Actions
API из пульса — тот же класс «дешёвый опрос уже читаемого источника», что и
существующие шаги оркестратора (recent_runs, heartbeat), новой инфраструктуры
не заводит. Внутренние развилки (дедуп по auto-detected-задачам вместо
исключения PR-событий; задача по фолбэк-факту) разобраны в докстринге
`failure_watch` и в дельта-спеке.
