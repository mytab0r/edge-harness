# Дельта-спека: журнал (journal-tasks-hands) — гвардия непрочитанных провалов ключевых workflow (#477)

Реализация: `scripts/orchestra/pulse_guard.py::failure_watch`, вызывается из
`scheduler.py::main()` рядом с `heartbeat_check`. Все пороги — константы
модуля `pulse_guard.py` (одно место правды).

## ADDED: Гвардия непрочитанных провалов ключевых workflow

Требование: каждый пульс оркестратора дешёвым запросом (`status=completed`
с клиентским фильтром по выводу `FAILURE_WATCH_RUN_CONCLUSIONS`, одна
страница `per_page=100` на workflow, без выгрузки логов всех прогонов подряд)
проверяет свежие провалы каждого из `WATCHED_WORKFLOWS` (`worker.yml`,
`hands.yml`, `orchestra.yml`, `deploy-worker.yml`, `deploy-dsh-edge.yml`).
Выводы решены явно: `failure` и `timed_out` — провал (прогон, убитый
собственным капом `timeout-minutes` — worker.yml 280 — провал в смысле
#477, а серверный фильтр `status=failure` его не отдаёт); `cancelled` — НЕ
провал (отмена — осознанное действие человека/автоматики, разбор
отменённого прогона заводил бы задачи на нормальную работу конвейера).
Разбирается самый свежий провал workflow в пределах окна свежести
`FAILURE_WATCH_WINDOW_MINUTES` (30 мин, кратно 15-минутному пульсу); окно
измеряется от `updated_at` прогона — у завершённого красного прогона это
момент провала, тогда как `created_at` — момент постановки в очередь, и
долгий воркер (worker.yml по замыслу пашет десятки минут), упавши только
что, по `created_at` лежал бы вне окна на каждом пульсе. Провал старше окна
не порождает ни задачи, ни сигнала — пульс не заводит сущности по уже
неактуальной причине, и закрытая задача по нему не переаводится бесконечным
циклом; реран старого прогона обновляет `updated_at` (прогон снова
«свежий»), но ПОКА открыта задача этого класса (defect) или стоит маркер в
#120 (infra) — повторного сигнала не даёт: дедуп смотрит на них, не на
свежесть. После закрытия задачи реран того же прогона в окне заведёт новую
задачу на ту же причину — это ограниченное окном переоткрытие эпизода
(причина снова красит свежий прогон), а не безусловная гарантия «сигнала
второго не будет».

Требование: причина называется фактом, не гипотезой — последняя
СОДЕРЖАТЕЛЬНАЯ строка лога упавшего job'а, снятая в два прохода: (1)
предпочтительно последняя строка с `##[error]`; (2) если аннотированной
содержательной строки нет — последняя содержательная строка plain-хвоста
упавшего шага: содержательные причины большинства падений живут в stderr
БЕЗ аннотации (bash печатает «line N: ... No such file or directory» простой
строкой — живой замер на прогоне 34027035455; вывод git push и текст хуков
тоже plain), а в orchestra.yml нет ни одного `::error`. Boilerplate раннера
(«Process completed with exit code N», строки завершения раннера) и
обёртки-не-факты («Воркер не справился: … код N» — факт падения обёртки, не
причины; нормализация цифр делала бы из неё один отпечаток на любую причину
агентского провала) пропускаются в обоих проходах. ДО обоих проходов лог
обрезается по первому вхождению заголовка автоматической секции teardown
Actions («Post job cleanup.», #610): содержимое этой секции (чистка
credentials checkout'а) проходит фильтры boilerplate/wrappers как валидный
факт, но печатается ПОСЛЕ настоящей причины падения на каждом прогоне и
несёт частично уникальный UUID — без обрезки одна и та же причина порождала
разные fingerprint на каждом прогоне при одинаковом заголовке задачи (живой
случай: пять issue «CI: orchestra.yml падает — orchestra», #578/#580/#589/
#592/#598).

Требование: провал классифицирован закрытым списком сигнатур
(`classify_failure_cause`), нераспознанное — `defect` (fail loud по
умолчанию, не прощаем молча непонятное): `infra` (лимиты/сеть) — один тихий
след в #120 на класс, без Telegram и без задачи, повторный класс молчит;
`stale_base` (устаревшая база) — только наблюдение: газ уже назван (#474 —
авто-ребейз конфликтных PR, `task-branch`/pre-commit), failure_watch чужую
автоматику не дублирует; `defect` — задача в пул (метки `task` +
`ci-failure`) с фактом: workflow, job, упавшие шаги, содержательная строка лога,
ссылка на прогон.

Требование: один сигнал на класс провала — дедуп по отпечатку класса причины
(`failure_fingerprint`: workflow + job + нормализованная строка ошибки),
не по run id: тот же баг на новом прогоне дедупится. Закрытая задача дедуп не
держит: новый провал того же класса после её закрытия — новый эпизод и новая
задача (окно свежести отделяет его от старого прогона).

Требование: второй слой дедупа — по ТОЧНОМУ заголовку задачи (`CI: <workflow>
падает — <job_name>`, #610), поверх дедупа по fingerprint выше. Заголовок для
пары workflow+job детерминирован и одинаков на каждом прогоне, а fingerprint
чувствителен к точному тексту извлечённого факта — расходящийся факт при
одной и той же причине (см. обрезку teardown-секции выше) порождал разные
fingerprint под ОДНИМ и тем же заголовком и заводил вторую issue вместо
сигнала на первую (живой случай #578/#580/#589/#592/#598). Открыта issue с
тем же заголовком и НОВЫМ fingerprint — вторая задача НЕ заводится: вместо
неё пишется комментарий на существующую issue с отпечатком нового класса
(`FAILURE_FINGERPRINT_MARKER`, тем же форматом, что маркер в теле задачи).
Другой дефект ТОГО ЖЕ job'а с открытой issue по этому заголовку получает не
свою задачу, а комментарий на чужую — это осознанное сужение семантики
класса (заголовок — единица дедупа второго слоя, не только fingerprint).
Повторный комментарий на том же прогоне не пишется: перед постом
дедуп ищет маркер отпечатка среди уже оставленных КОММЕНТАРИЕВ этой issue
(`issue_marker_times`, тот же приём, что `stall_detector.py`) — свежий провал
остаётся в окне `FAILURE_WATCH_WINDOW_MINUTES` несколько пульсов подряд, и
без этой проверки каждый пульс писал бы байт-в-байт одинаковый комментарий
(находка ревью PR #612). Текст комментария не утверждает «новый прогон» —
только факт другого отпечатка под тем же заголовком.

Требование: прогоны `event=pull_request` не разбираются — красный прогон
PR-события является красным обязательным чеком на PR, и его устойчивую
причину уже заводит автодетектор простоя (#201, отпечаток `check:red:<имя>`);
исключение закрывает класс «один дефект — две задачи» (`ci-failure` +
`check:red`) без сопоставления несопоставимых отпечатков двух детекторов.

Требование: содержательная строка лога недоступна (лог не прочитался,
строки нет) — задача НЕ заводится: фолбэк-факт «шаги: …» грубее и мигает во
вторую задачу, когда лог на следующем пульсе читается; остаётся громкое
наблюдение со ссылкой на прогон, устойчивый случай такого простоя подбирает
автодетектор #201 (класс `warn:`).

Требование: на одном красном прогоне разбирается не более
`FAILURE_WATCH_MAX_JOBS_PER_RUN` (3) упавших job'ов (лог job'а — дорогой
запрос, каждый — отдельный кандидат класса), остальные названы поимённо в
наблюдении — хвост не прячется молча.

Требование: сбой чтения (список провалов, job'ы, лог, открытые задачи) не
роняет обход остальных workflow и сам пульс — наблюдение с причиной, тот же
fail-loud-класс, что у остальных шагов планировщика.

Сценарий: в #120 свежий красный прогон hands.yml, в plain-хвосте лога
`dsh: RATE_LIMIT: …` → классифицировано `infra`, один тихий след в
#120 с маркером класса, задачи нет; повторный пульс по тому же классу —
наблюдение «уже сигналили», новых комментариев нет.

Сценарий: свежий красный прогон worker.yml, plain-хвост лога упавшего job'а
содержит `scripts/worker/task.sh: … infra_digest.sh: No such file or
directory` (последняя ##[error]-строка — boilerplate раннера) → классифицировано `defect`, заведена одна задача (метки `task` +
`ci-failure`) с точной причиной и ссылкой на прогон; следующий пульс по тому
же отпечатку задачу не дублирует.

Сценарий: красный `contract` на PR (прогон orchestra.yml с
`event=pull_request`) — failure_watch молчит: задача на этот класс заводит
автодетектор простоя (#201) после порога устойчивости; дубликат `ci-failure`
на тот же красный прогон не появляется.

Сценарий: устаревшая база (`main уехал вперёд` в plain-строке лога —
вывод git push/хука без аннотации) —
наблюдение «газ уже назван в #474», без задачи и без сигнала; ребейз делает
существующая автоматика расшивки конфликтов, failure_watch с ней не
пересекается.

Сценарий: упавший job, чей лог не читается, в свежем красном прогоне →
наблюдение «содержательная строка лога недоступна (шаги: …) — задачу не
заводим без
факта»; задача заводится следующим пульсом, когда лог прочитается и строка
назовет причину.

Сценарий (#610): открыта issue «CI: orchestra.yml падает — orchestra» с
fingerprint A; новый пульс на том же job'е классифицирует `defect` с
fingerprint B (расходящийся факт после обрезки teardown-секции или другой
дефект того же job'а) — вторая issue с тем же заголовком не заводится,
на существующую issue уходит один комментарий с отпечатком B. Следующие
пульсы того же прогона (тот же fingerprint B, issue ещё открыта) комментарий
не повторяют — маркер `FAILURE_FINGERPRINT_MARKER` с этим отпечатком уже
есть среди комментариев issue.

## ADDED: Эскалация суточного потолка автозаведения не красит прогон (#610)

Требование: суточный потолок автозаведения (`stall_detector.STALL_DAILY_CAP`)
исчерпан — сигнал «нужен человек» видим владельцу (комментарий в
`WATCHDOG_ISSUE` + Telegram, один раз в календарные сутки, маркер несёт
ISO-дату), но НЕ поднимает hard-failure и не красит прогон orchestra.yml:
инвариант «наблюдатель провалов не реагирует на свою инфраструктуру
мониторинга» — если бы исчерпание потолка красило прогон, тот же пульс
(`failure_watch` выше) завёл бы задачу «CI: orchestra.yml падает» НА ЭТУ ЖЕ
эскалацию, замкнутый цикл (тот же живой случай #578/#580/#589/#592/#598,
который #610 закрывает для заголовков issue). Это НЕ отменяет и не
переопределяет поведение архивной дельта-спеки stall-detector («потолок не
тонет молча, а кричит строкой отчёта») — строка отчёта остаётся, добавлен
видимый канал (issue+Telegram) без изменения красноты прогона.
