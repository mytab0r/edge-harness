Опирается на существующий раздел «Автономный воркер (конвейер пула)» (пп. 26–29
базовой спеки) — см. `scheduler.py::dispatch_conflict_rework` за реализацией.
Требование п.26 про доводку открытого PR без исполнителя (#245) не меняется —
эта дельта добавляет НОВЫЙ класс задач, попадающих в ту же доводку: конфликтные.

## ADDED: Автоматическая расшивка конфликтных PR

Требование: PR с меткой `conflict` (`mergeable_state=dirty`, обнаруживает
`mark_conflicts`) не ждёт человека. Оркестратор снимает assignee и замок
задачи, которой принадлежит PR (`task_ref.resolve_pr_task` по имени
agent-ветки — тот же признак, что #245/#394), и диспетчит `worker.yml`
АДРЕСНО на эту задачу (вход `task`) — второй путь доводки не заводится,
переиспользуется тот же, что уже доводит PR с `ai:changes-requested`/
красным чеком.

Требование: признака «механический дрейф main или содержательный конфликт»
ДО попытки не существует — GitHub REST отдаёт только `mergeable_state`
(dirty/clean), не конфликтующие ханки. Поэтому бюджет прост: РОВНО одна
авто-попытка ребейза на PR, лифтайм-счётчик (маркер в комментариях PR,
переживает перезапуск оркестратора, тот же приём, что счётчик авто-повторов
ai-review). Ребейз сошёлся — `mark_conflicts` сама снимает метку `conflict`
следующим проходом (mergeable_state пересчитался в неконфликтное), это и
есть постфактум-признак «был дрейф». Не сошлось за одну попытку — эскалация
владельцу тем же каналом, что предохранитель конвейера, с файлами-
кандидатами (пересечение файлов, изменённых PR, и файлов, изменённых в main
с момента base-коммита PR, — эвристика, не точные конфликтующие строки,
честно помечена как таковая), идемпотентно (маркер эскалации с номером PR).
Перед самой эскалацией `mergeable_state` перечитывается заново — метка
`conflict` намеренно переживает `None`/`unknown` (`mark_conflicts`: «не
знаю» не значит «нет конфликта»), и без перепроверки эскалация могла бы
объявить «остаётся в конфликте» в окне между успешным ребейзом (прогон уже
закончился) и пересчётом состояния сервером (ещё не вернулся из
`None`/`unknown`).

Требование: эскалация не торопится, пока единственная попытка ещё
физически идёт (`worker_runs_active`) — маркер попытки ставится в момент
диспатча, а сам `worker.yml` может идти до 280 минут; без этой гвардии
следующий тик планировщика (каждые 15 мин) увидел бы «бюджет исчерпан» и
объявил бы «не сошлось» раньше, чем прогон вообще успел завершиться.

Требование: идемпотентность диспатча — тот же гейт, что у обычного пульса
воркера (`worker-ран` в `in_progress`/`queued`): пока прошлый прогон жив,
второй `workflow_dispatch` не уходит. В одном ПРОХОДЕ планировщика уходит не
более одного `workflow_dispatch` `worker.yml` суммарно — расшивка конфликта
и обычный пульс новой/доводимой задачи (п.26) взаимно исключают друг друга
в пределах одного прохода.

Сценарий: PR #500 (задача #90) получил метку `conflict` предыдущим проходом,
авто-попыток ещё не было -> оркестратор снимает assignee+замок задачи #90,
запускает `worker.yml` с `task=90`; PR не закрывается, ветка та же.

Сценарий: PR #500 остаётся `dirty` после одной авто-попытки -> вторая
попытка не уходит, эскалация владельцу с перечнем файлов-кандидатов
(например «cf-worker/src/config.ts, docs/agents/LABELS.md»), задача #90 не
трогается (остаётся у последнего исполнителя — эскалация не забирает
работу).

Сценарий: PR #500 получил `conflict`, но его ветка не в форме `agent/N-slug`
(ручной PR, бот) -> расшивка недоступна, отчёт называет причину явно, задача
не ищется.
