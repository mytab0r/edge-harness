# conflict-auto-rebase: оркестратор сам расшивает конфликты PR (#474)

Задача: #474. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`mark_conflicts` ставила метку `conflict` и комментарий на PR с
`mergeable_state=dirty` и на этом останавливалась — тормоз без газа
(AGENTS.md): PR висел, пока кто-то не пошлёт агента на `git rebase
origin/main` вручную. Живой пример на момент постановки задачи — #387,
#327 (у обоих ещё и выбран бюджет авто-повторов ревью — без ребейза не
сдвинулись бы никогда). Причина конфликта почти всегда одна — main уходит
вперёд (55 слияний/сутки на живом репозитории), а разрешение —
механическое (ребейз со сведением обеих сторон).

## Что делается

`scheduler.py::dispatch_conflict_rework` подхватывает PR с меткой
`conflict` сама, без человека:

- снимает assignee и замок задачи (тот же приём, что `unhealthy_pulls` уже
  применяет к нездоровым PR не-conflict классов — `conflict` там намеренно
  исключён как «свой цикл ручного разрешения»; эта функция и есть тот цикл,
  теперь автоматический);
- запускает `worker.yml` АДРЕСНО на задачу этого PR (вход `task`, тот же
  путь, что уже доводит открытые PR, #245/#394 — второй путь не
  изобретался);
- бюджет — РОВНО одна ЗАСЧИТАННАЯ авто-попытка ребейза на PR, лифтайм-счётчик
  (тот же приём, что `AI_REVIEW_MAX_ATTEMPTS`/`ai_review_retry_count`;
  уточнено #588 по находкам ревью PR #597: попыткой считается только прогон,
  ДОШЕДШИЙ до git-шага — отметка «`[worker: git-шаг]` worker run N» в
  комментариях ЗАДАЧИ; счётчик читает эти комментарии как постоянный след,
  не окно свежих прогонов Actions, где попытка терялась через ~2–3 часа
  живой истории; инфра-сбой до git-шага бюджет не сжигает — PR получает
  повторный адресный диспатч вместо эскалации).
  Признака «механический дрейф или содержательный
  конфликт» ДО попытки не существует — GitHub REST отдаёт только
  `mergeable_state`, не конфликтующие ханки; поэтому решение владельца
  простое: одна попытка, не сошлось — эскалация;
- исчерпан бюджет — эскалация владельцу (`pulse_guard.escalate`, тот же
  канал, что предохранитель конвейера #120) с файлами-кандидатами
  (`conflict_overlap_hint` — пересечение файлов, изменённых PR, и файлов,
  изменённых в main с момента base-коммита PR; эвристика, не точные
  конфликтующие строки, честно помечена как таковая в тексте эскалации).
  Идемпотентно — маркер эскалации с номером PR в watchdog-задаче. Перед
  самой эскалацией `mergeable_state` перечитывается заново (находка ревью
  PR #478) — метка `conflict` намеренно переживает `None`/`unknown`
  (`mark_conflicts`), и без перепроверки эскалация могла бы соврать
  «остаётся в конфликте» в окне между успешным ребейзом и пересчётом
  состояния сервером;
- текст эскалации называет ФАКТ, не диагноз («алерт не гадает», AGENTS.md,
  находка ревью PR #478, второй раунд): единственное подтверждённое —
  `mergeable_state=dirty` после одной ЗАСЧИТАННОЙ попытки, причина отсюда не
  различается (инфраструктурный сбой воркера/квота/таймаут дают тот же
  итог, что настоящий содержательный конфликт) — `last_worker_run_conclusion`
  называет conclusion последнего прогона, атрибутированного этой задаче
  (переиспользует `run_claimed_task`/`recent_runs`), честно «не
  атрибутирован», если следа нет;
- гонка «эскалация раньше времени» (найдена живым прогоном #408, см. ниже):
  пока единственная попытка ещё физически идёт (`worker_runs_active`),
  эскалация ждёт — иначе следующий тик планировщика (15 мин) объявил бы
  «не сошлось» раньше, чем 280-минутный `worker.yml` вообще успел
  завершиться.

Идемпотентность диспатча — `worker_runs_active` (тот же гейт, что у
обычного `dispatch_worker`): воркер один на репозиторий. `main()`
пропускает обычный `dispatch_worker` этим же проходом, если расшивка
конфликта уже ушла — «ровно один `workflow_dispatch` воркера за пульс» не
должно превратиться в два.

`scripts/worker/task.sh`: явное указание в промпте continuation-режима —
после `git rebase origin/main` обычный `git push` отклонится
(non-fast-forward), нужен `git push --force-with-lease` (не голый
`--force`). Отдельная находка того же живого прогона (crash на
`scripts/gh/infra_digest.sh` при доводке очень старой ветки) уже
независимо найдена и исправлена архитектурно в основной ветке (issue
#476, изоляция continuation-режима в отдельный git worktree) — эта правка
подхвачена ребейзом, второй, более узкий фикс не заводился.

`scripts/lib/free_task.py::conflict_declared_tasks` — четвёртая находка
ревью PR #478 (блокирующая): освобождённая задача была видна и generic-
пульсу воркера (`free_task()` без `--task`) в обход бюджета «ровно одна
попытка» — если адресный прогон падал по квоте/крашу до повторного
захвата (`task.sh::release-full`), задача временно свободна, и generic-
пульс мог взять её снова, уже ПОСЛЕ эскалации владельцу. `free_candidates`/
`oldest_free` получили параметр `excluded` (задачи, чей объявленный PR
несёт `conflict`); `task.sh::free_task()` вызывает новую подкоманду CLI
`conflict-tasks` перед `oldest-free`.

## Сброс лифтайм-бюджета после известной инфра-аварии (issue #817)

Живой случай 2026-09-08: авария #794 (порча записи журнала валила
`worker.yml` девять прогонов подряд) сожгла единственную попытку
`CONFLICT_REWORK_MAX_ATTEMPTS=1` на 18 PR одновременно (241/328/344/395/
408/409/542/567/571/579/596/607/613/617/638/640/667/787) — попытки
успели пройти git-шаг (`WORKER_GIT_STEP_MARKER`, значит формально
засчитаны), но упали по инфраструктуре аварии, а не по сложности
ребейза. Владелец решил: дать этим PR честную повторную попытку через
durable-механизм («попытка во время известной инфра-аварии не жжёт
бюджет»), не разовую правку счётчика и не подъём политики
`CONFLICT_REWORK_MAX_ATTEMPTS` — будущие аварии того же класса используют
тот же приём, а не новый ручной обход.

Механизм — `pulse_guard.CONFLICT_BUDGET_RESET_MARKER =
"[conflict-budget-reset:"` (маркер-ПРЕФИКС, причина — свободный текст
после двоеточия): публикуется комментарием в ЗАДАЧУ, тот же канал, что
`conflict_rework_attempts` уже читает (`all_issue_comments(task_number)`,
второй канал не заводится). `conflict_rework_attempts` берёт
`max(conflict_first_labeled_at, время ПОСЛЕДНЕГО маркера сброса)` как
эффективную границу отсчёта попыток — `issue_marker_times` (уже
существующая утилита `pulse_guard`, читает маркеры как есть) даёт список
времён публикации, `max()` даёт идемпотентность «несколько маркеров сброса
не суммируются в накопленный сдвиг, считается только последний». Реальная
защита от бесконечного цикла не обходится: после сброса снова считается
РОВНО одна попытка, следующий провал ведёт к обычной эскалации, не к
безлимитным повторам.

Маркер опубликован на всех 18 задачах из списка выше (не на #522/#656 —
на hold; не на #612 — задача закрыта; не на #644/#654 — ещё в пределах
исходного бюджета) с причиной «#794-outage 2026-09-08: единственная
попытка провалилась по инфре, не по сложности».

## Что вне рамок

- Точное определение конфликтующих строк (не файлов) — потребовало бы
  локальный git-клон внутри scheduler.py; вне единственного источника
  состояния этого файла (`gh api`), не заводится.
- Второй порог правды на количество ПАРАЛЛЕЛЬНЫХ расшивок — не существует
  как сценарий: воркер физически ведёт один прогон за раз (concurrency-
  группа `worker`).
