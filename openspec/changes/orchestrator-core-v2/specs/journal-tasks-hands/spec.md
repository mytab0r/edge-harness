# Дельта-спека: журнал (journal-tasks-hands) — снимок наблюдаемого состояния задача/PR (#1287)

Это ПРОЕКТНАЯ дельта: она описывает поведение, которое design.md
этого же change специфицирует для будущей реализации, не поведение,
уже работающее в проде. Пункты ниже нумеруются продолжением
`openspec/specs/journal-tasks-hands.md` (последний существующий пункт —
41) и переносятся в центральный файл ТОЛЬКО после того, как реализация
слита и признак завершения (design.md, раздел 9) достигнут хотя бы
частично для затронутых пунктов — до этого момента они описывают целевое
поведение, не текущее.

## ADDED: Конвейер (оркестратор) — снимок состояния задача/PR

42. Класс `Harness` (тот же Durable Object, что уже хранит `messages`/
    `tasks`/`pulse`) получает две новые таблицы SQLite: `task_snapshots`
    и `pr_snapshots`, ключ — `(repo, number)`. Пишет только реконсилятор
    (`scripts/orchestra/scheduler.py`, workflow `orchestra.yml`), читают
    все остальные консьюмеры состояния задача/PR через новые маршруты
    `GET /api/tasks-snapshot`/`GET /api/pr-snapshot` (список и по одному
    номеру, тот же паттерн `rest: true`, что уже несёт `/api/tasks/`).
    Авторизация — тот же Bearer `HANDS_TOKEN`, что уже проверяет
    `/api/heartbeat`; второго секрета не заводится.

43. Наблюдаемое состояние (стадии, флаги, evidence-поля) пересчитывается
    из GitHub ЦЕЛИКОМ каждый такт оркестратора (level-triggered): потеря
    содержимого таблиц снимка не считается потерей данных, только потерей
    кэша — при следующем такте наблюдаемое состояние восстанавливается
    полностью из GitHub. Граница честности: гарантия распространяется
    ТОЛЬКО на наблюдаемое состояние; эпизодные поля пункта 47 из одного
    GitHub невосстановимы — их контракт восстановления назван в самом
    пункте 47 и в design.md (раздел 3.8, правило 3), а не
    декларирован этим пунктом (находка ревью: прежняя формулировка
    «ни одно решение конвейера не хранится ТОЛЬКО в снимке» была ложной
    для половины собственной таблицы пункта 47).

44. Запись в снимок — ТОЛЬКО при изменении вычисленных `stage`/флагов
    сущности относительно уже сохранённой строки (edge-triggered write
    поверх level-triggered read) — не безусловно каждый такт. Обоснование
    числами — `design.md`, раздел 3 (аккаунтный лимит Cloudflare Free
    `rows_written` — 100 000/сутки, разделяемый с воркером `dsh-edge`,
    который на измеренный день потратил 59 025 из 100 000 = 59% лимита
    аккаунта; 97.7% — доля от использованного за день, знаменатель —
    использованное, не лимит).

45. Терминальность стадии — атрибут значения стадии (`is_terminal(stage)`,
    таблица соответствия в одном месте), не список статусов, поддерживаемый
    руками в нескольких потребителях. Задача несёт стадии `pool` / `leased`
    / `has_pr` (нетерминальные), `done` / `abandoned` (терминальные),
    `reopened_invalid` (нетерминальное, самокорректирующееся). PR несёт
    стадии `no_task` / `draft` / `awaiting_gate1` / `awaiting_gate2` /
    `ready` (нетерминальные), `merged` / `closed` (терминальные). Полный
    перечень легальных переходов — `design.md`, раздел 2.

46. Ортогональные флаги сущности (`conflict`, `checks_red`, `needs_rework`,
    `gate2_error` с `reason_tag`, `contract_ok`, `stale_ready` для PR;
    `blocked`, `waiting_owner`, `stale_unclaimed`, `lease_stale` для
    задачи) не являются стадиями и не размножают их число — они гейтят
    переходы и политику, каждый несёт собственное поле-evidence.

47. Идемпотентные счётчики повторов и меток времени, ранее кодировавшиеся
    текстовыми маркерами в комментариях issue/PR (`design.md`, раздел 4.1
    — `RESUME_MARKER`, `CONFLICT_REWORK_MARKER`, `AI_REVIEW_RETRY_MARKER`,
    `HEARTBEAT_*` и аналогичные), читаются из полей снимка вместо разбора
    истории комментариев на каждом тике. Человекочитаемые заголовки
    комментариев (`design.md`, раздел 4.2) продолжают публиковаться как
    текст — миграции подлежит только идемпотентность решения "уже
    делали/не делали", не сам текст сообщения человеку. ГАЗ против
    молчаливой потери эпизодного состояния (находка ревью: эти поля из
    одного GitHub невосстановимы, поэтому пункт 43 на них не
    распространяется): (а) публикация маркерных строк продолжается как
    источник восстановления ПОСЛЕ перевода читателей на снимок и
    срезается ОТДЕЛЬНЫМ шагом Этапа 8, не самим переводом; (б) неудавшаяся
    запись эпизодного поля повторяется следующим тактом (сравнение —
    против сохранённой строки), каждая неудача печатает причину в отчёте
    такта; (в) срезание публикации допустимо только после одноразового
    громкого ребилда счётчиков из истории комментариев с пометкой rebuild
    в строке снимка и с тестом «пустой снимок -> один тик по живой
    истории восстанавливает счётчики; второй тик их не меняет».

48. Контракт чтения снимка консьюмером вне такта писателя: якорь
    свежести — строка-пульс писателя (синглтон `pipeline_snapshot`, один
    upsert за такт); `updated_ts` строки сущности остаётся evidence
    последнего ИЗМЕНЕНИЯ (edge-triggered запись, п.44) и признаком
    свежести НЕ является. Консьюмер обязан трактовать отсутствующую или
    старше двух тактов писателя (30 минут) строку-пульс как третье
    состояние «снимок не смотрел» для всей таблицы — не «нарушений нет»
    и не нулевое значение (fail loud, тот же контракт, что
    `scripts/lib/check_result.py`). Проверки, чья сигнализация зависит от
    «прямо сейчас», в пуш-прогоне repo-ci сохраняют прямой пересчёт, если
    задача Этапа 3 не решит провести секреты вместе с этим
    freshness-гейтом. Гейт `contract` (`orchestra.yml`, события
    `pull_request`) снимок НЕ читает — прямое вычисление в момент
    события, секреты DO в pull_request-job не проводятся (профиль
    назван в `design.md`, раздел 5, пункт 7).
