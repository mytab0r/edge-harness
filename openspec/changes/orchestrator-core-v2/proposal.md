# orchestrator-core-v2: единая модель наблюдаемого состояния задача/PR

Задача: #1287.

## Summary

Сегодня состояние PR и состояние задачи не существуют как значение —
каждый потребитель (scheduler.py, repo_invariants.py, contract_check.py,
pulse_guard.py, stalled_pr_triage.py, mechanical_rebase.py,
checklist_tail_labels.py, диагностика scripts/gh/queue.py и pr_blockers.py)
заново вычисляет его из сырых полей GitHub (labels, mergeable_state,
check-runs, таймлайн, текст комментариев, имя ветки) каждый раз, когда ему
это нужно. Копий вычисления шесть-семь, файлов минимум восемь. Три
задокументированных инцидента расхождения (#303, #432, #740) и минимум один
живой (2026-09-04, scheduler.py::pr_references_issue сняла чужую аренду
задачи #90 по случайному упоминанию номера в теле PR #181) — прямое
следствие того, что одна и та же сущность существует в N независимых
прочтениях, не в одном.
Это проект (openspec change), не реализация: он вводит понятия наблюдаемое
состояние, снимок, реконсилятор и переносит 16 именованных точек чтения на
общий снимок, поэтапно, без остановки конвейера (2 десятка слияний в
сутки). Дизайн опирается на уже работающий в этом же репозитории образец —
машину состояний messages/tasks в cf-worker/src/harness.ts (CAS по моменту
захвата, ватчдог на зависшую обработку, терминальный отказ после
исчерпания попыток) — и на уже начатую в этом репозитории миграцию
трёхзначного результата (scripts/lib/check_result.py, issue #1096):
«не смог посмотреть» — отдельное от «нарушений нет» состояние, не то же
самое пустое значение.

## Problem / motivation

- Структурная причина. У домена GitHub нет ни одной транзакции и ни одного
  нашего поля состояния — 8+ рабочих процессов (агенты, боты, владелец)
  пишут в одни и те же issues/PR конкурентно. Единственный способ
  запомнить, что мы уже решили, сегодня — текстовые маркеры в комментариях
  (43 именованные константы MARKER только в scripts/orchestra, без учёта
  версий с номером PR/эпохи в самой строке — реально маркеров больше
  полусотни) и метки, которые парсятся заново на каждом тике.
- Измеренная цена (замер другого канала, 2026-09-15): 2 817 строк ядра
  против 6 261 строки обвеса, существующего только из-за того, что
  состояние выводится в 6 местах, — обвес вдвое больше ядра. Из 18
  инвариантов repo_invariants.py 7 существуют только затем, чтобы стеречь
  расхождение копий состояния. Рост не выходит на плато: 76 новых
  файлов-гвардий за 15 суток, тест-гвардий плюс 4 за время самого разбора.
- Живые примеры расхождения (все — в коде репозитория, не гипотеза):
  - #303/#432 — scheduler.last_gate1_labeled_at и
    repo_invariants.last_gate1_labeled_at были двумя независимыми копиями
    одной логики поиска метки в таймлайне (review_labels.py:845-849);
    #432 отдельно — смешение «гейт 1 вынес вердикт» и «гейт 1 открыл
    слияние» в двух разных потребителях сделало AI-ревью невидимым для
    review:large PR (review_labels.py:147-171).
  - #740 — отпечаток «этот дифф уже проверен» одно время вычислялся по sha
    блоба (следует за каждой правкой файла в main, не только за правками
    автора PR), другое — по patch (устойчив к чужим правкам); расхождение
    молча продлевало жизнь протухшему ai:ok (review_labels.py:436-473).
  - Живой инцидент 2026-09-04 — scheduler.py::pr_references_issue (широкая
    семантика «упомянут где угодно») сняла аренду задачи #90, потому что
    номер #90 встретился в прозе тела совершенно другого PR #181; узкая
    семантика task_ref.resolve_pr_task (по имени ветки) этой ошибки не
    подвержена, но используется не везде (scheduler.py:472-498).
## Scope

In. Проект (design + delta-спека + план миграции) для:

1. Понятий наблюдаемое состояние / желаемое состояние (политика) /
   реконсилятор / снимок — как они ложатся на существующую пару Durable
   Object (cf-worker/src/harness.ts, класс Harness) плюс GitHub Actions job
   (scripts/orchestra/scheduler.py, workflow orchestra.yml).
2. Перечня состояний задачи и PR, легальных переходов, терминальности как
   поля (не поддерживаемого вручную списка).
3. Судьбы 50+ текстовых маркеров: какие схлопываются в поля снимка, какие
   остаются текстом и почему.
4. 16 именованных точек чтения состояния — поимённо, file:line, порядок
   переезда с обоснованием и способом доказать эквивалентность старого и
   нового пути на каждом шаге.
5. Проверки лимитов Cloudflare Free для этой конкретной нагрузки — числами,
   не оценкой на глаз (см. design.md, раздел «Честность снимка и лимиты»).
6. Ответа на два возражения владельца, зафиксированных в design.md (раздел
   «Отвергнутые формы ядра»): (а) зачем новая таблица, если у раннера уже
   есть канал к Cloudflare; (б) почему ядро не форма плагина DSH.
7. Признака завершения замены и границы «что не входит в ядро».

Out.

- Код самого ядра (реализация — отдельные задачи по tasks.md этого change,
  каждая со своим PR).
- Квоты LLM-провайдеров, деплой, security baseline, гигиена исходников —
  отдельная область (примерно 26 тыс. строк), не читает и не пишет
  состояние задача/PR, границу называет design.md явно.
- Миграция самого домена journal-tasks-hands (очередь/heartbeat/inbox
  внутри Harness DO) — снимок реконсилятора живёт рядом, в новых таблицах
  того же DO, существующие таблицы (messages, tasks, pulse) не трогаются
  этим change.
- Замена аренды (git-ref lock, ADR 0006) и эскалации владельцу — оба
  остаются как есть, дизайн их не меняет.
## Impacted domains

scripts/orchestra/ (scheduler.py, repo_invariants.py, pulse_guard.py,
contract_check.py, mechanical_rebase.py, stalled_pr_triage.py,
checklist_tail_labels.py), scripts/lib/ (review_labels.py, task_ref.py,

существующем классе Harness), .github/workflows/orchestra.yml (новая
проводка существующих секретов HANDS_TOKEN/HARNESS_URL), документация
(openspec/specs/journal-tasks-hands.md, docs/research/30-rejected-alternatives.md).

## Acceptance criteria

1. design.md называет полный перечень состояний задачи и PR с легальными
   переходами; терминальность — читаемое поле (is_terminal(stage)), не
   список строк, поддерживаемый руками в N файлах — проверяется чтением
   самого design.md, механической гвардии на design.md не требуется.
2. design.md даёт числовой ответ на вопрос, укладывается ли полный
   пересчёт снимка в лимиты CF Free, с реальными измеренными числами из
   docs/research/20-cloudflare-free.md (rows_read/rows_written,
   account-wide), а не оценкой на глаз — и явно называет порог, при
   котором конструкция ломается, и что делать тогда.
3. Таблица 50+ маркеров: для каждой группы маркеров (не обязательно
   поштучно на все 43+ константы) названо, схлопывается ли она в поле
   снимка или остаётся текстом, с причиной.
4. 16 точек чтения перечислены поимённо (file:line на момент написания), с
   порядком переезда и способом проверки эквивалентности на каждом шаге
   (тест на реальных фикстурах прод-формы, не пересказ).
5. Названы: что не входит в ядро (граница явная, с числом строк не входящих
   областей) и признак завершения замены (проверяемое условие «обвес
   выведен из употребления», не «часть перенесена»).
6. Два возражения владельца (см. Scope, п.6) закрыты фактами с file:line и
   числами, не мнением — раздел design.md «Отвергнутые формы ядра» либо
   оставляет решение, либо честно называет открытый вопрос владельцу.
7. tasks.md разбит на этапы, каждый — отдельная задача-заявка в пул с
   критерием приёмки, включая ходячий скелет первым этапом (одна пара
   задача/PR через новый путь целиком, остальное — старым), по образцу
   openspec/changes/walking-skeleton/.
## Risks / unknowns

- CPU на инвокацию DO (10 мс, Free) для батч-записи снимка — измерено
  Этапом 0 (design.md, раздел 3.6, 2026-09-15): 0.0107-0.0127 мс/операцию
  на реальном workerd+SQLite (локально, не на задеплоенном edge), запас
  6-800x от лимита на всём реалистичном диапазоне батча (1-136 сущностей).
  CPU не является узким местом; узкое место — rows_written (раздел 3.3/3.4),
  вывод не изменился. Живое подтверждение на задеплоенном проде (`wrangler
  tail`) — после мержа+деплоя, не сделано этим этапом (разработчик не
  деплоит в прод сам).
- Разбор политики merge_queue/wip_gate как чистых функций от снимка —
  сегодня они читают gh встроенно по ходу вычисления (не принимают готовый
  снимок аргументом); перенос на снимок требует рефакторинга сигнатур,
  объём которого не оценён этим change (задача реализации).
- Совместимость снимка с параллельно открытыми PR других агентов — на
  момент этого проекта в репозитории 29+ открытых PR и 80+ рабочих деревьев
  (scripts/git/worktree-cleanup.py); часть из них меняет те же файлы
  (scheduler.py, repo_invariants.py). Порядок переезда (design.md)
  начинается с read-only диагностики намеренно, чтобы конфликтовать с
  чужими PR как можно позже.
