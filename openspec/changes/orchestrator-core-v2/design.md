## 1. Семь понятий — уточнение черновика

1. **Сущность.** Задача = GitHub Issue с меткой task. PR = GitHub Pull
   Request. Контент (тело, комментарии, диффы) остаётся в GitHub — снимок
   не дублирует текст, только выводы (стадия, флаги, несколько
   идентификаторов и меток времени, нужных политике).

2. **Наблюдаемое состояние.** Не одно "текущее значение", а СТРУКТУРА с
   несколькими полями (см. раздел 2) — попытка свернуть всё в один enum
   уже провалилась однажды тем же способом, каким провалился гейт 1/гейт 2
   в #432: PR одновременно несёт вердикт гейта 1, вердикт гейта 2,
   mergeable_state, набор check-runs и флаг конфликта, и это НЕЗАВИСИМЫЕ
   измерения (ADR 0021 отдельно называет шесть независимо измеряемых
   величин для одного лишь триажа застрявшего PR) — сплющивание их в один
   код состояния потеряло бы ровно ту информацию, из-за нехватки которой
   #432 не различал "гейт 1 решил" от "гейт 1 открыл слияние". Наблюдаемое
   состояние — ОДНА функция build_observed(repo, entity) на тип сущности,
   читающая GitHub целиком и возвращающая иммутабельную запись; все её
   поля документированы в разделе 2. Ключевое отличие от сегодняшнего кода
   не в ЧИСЛЕ полей (оно почти не меняется), а в том, что ОДНА функция
   вычисляет их все РАЗ за такт, и остальной код читает готовую запись, а
   не пересчитывает подмножество полей заново.

3. **Желаемое состояние (политика).** Чистая функция decide(observed,
   snapshot) -> Action | None на сущность. Существующие чистые предикаты
   (review_labels.merge_label_gate, review_labels.should_update_branch,
   review_labels.should_run_ai_review) УЖЕ написаны в этой форме — они не
   переписываются с нуля, а собираются под одну сигнатуру, принимающую
   ObservedPR вместо разрозненных аргументов (labels, mergeable_state,
   check-runs по отдельности).

4. **Реконсилятор.** Один проход на сущность: прочитал (build_observed),
   сверил (decide), совершил не более ОДНОГО изменяющего действия к
   GitHub (пост комментария, метка, merge, dispatch), затем записал факт
   перехода в снимок (см. раздел 2, только если стадия/флаги изменились —
   см. раздел 3 про экономию записи). Это НЕ новый цикл — это
   scheduler.py:main(), уже устроенный как один проход по пулу задач и
   списку PR; реконсилятор — рефакторинг его внутренностей на общую
   структуру данных, не новый процесс и не новый триггер.

5. **Снимок состояния.** Две новые таблицы task_snapshots и pr_snapshots в
   SQLite УЖЕ СУЩЕСТВУЮЩЕГО Durable Object edge-harness (класс Harness,
   cf-worker/src/harness.ts) — не новая база данных, не новый сервис (см.
   раздел 7.1 — это прямой ответ на первое возражение владельца). Пишет
   только реконсилятор (scheduler.py, workflow orchestra.yml), читают все
   остальные консьюмеры (repo_invariants.py, pulse_guard.py,
   stalled_pr_triage.py, диагностика scripts/gh/) вместо повторного
   пересчёта из GitHub.

6. **Аренда.** Без изменений — git-ref lock (ADR 0006, scripts/lib/
   claim_task.py) остаётся единственным механизмом взаимного исключения на
   захват задачи. Реконсилятор ЧИТАЕТ факт аренды (жив ли ref, назначен ли
   assignee) как часть ObservedTask, но не заменяет сам механизм.

7. **Эскалация.** Без изменений — pulse_guard.escalate (issue #120 +
   Telegram) остаётся каналом. Меняется только ВХОД: сегодня каждый вызов
   escalate сопровождается своим текстовым маркером-дедупликатором
   (раздел 4); после миграции решение "уже сообщали в этом эпизоде"
   читается из снимка (поле last_escalated_ts/эпоха), не парсится из
   истории issue #120 заново.

## 2. Перечень состояний и легальные переходы

Решение по форме (обосновано в п.1.2 выше): каждая сущность несёт ОДИН
дискретный лайфстейт (stage, малое число значений, терминальность —
атрибут значения) плюс НЕСКОЛЬКО ортогональных булевых флагов с
доказательствами (evidence — откуда взят факт). Флаги не размножают число
стадий: они гейтят переходы и политику, но сами по себе стадией не
являются. Это тот же приём, что harness.ts уже применяет к messages:
основной status (new/processing/done/failed/ignored) плюс отдельные
поля attempts/kind/priority, не двадцать стадий на все их комбинации.

### 2.1 Задача (issue с меткой task)

STAGE (терминальность — атрибут, не список):

| stage | terminal | описание |
|---|---|---|
| pool | нет | открыта, меток task, нет активной аренды |
| leased | нет | открыта, активная аренда (живой git-ref lock) и/или assignee |
| has_pr | нет | открыта, существует открытый PR, чья ветка резолвится на неё (task_ref.resolve_pr_task) |
| done | да | closed, state_reason=completed |
| abandoned | да | closed, state_reason=not_planned |
| reopened_invalid | нет (промежуточное, самокорректируется) | state_reason=reopened после того, как была closed — незаконное состояние, требует немедленного возврата в done/abandoned |

Легальные переходы:

```
pool -> leased            (claim_task.py claim)
leased -> pool             (release / просроченная аренда >24ч, scheduler.reap_stale)
leased -> has_pr           (открыт PR, чья ветка называет эту задачу)
has_pr -> leased           (PR закрыт без слияния / заменён другой задачей, replace_closed_task_prs)
has_pr -> done              (accept_merged_tasks подтвердил улику)
{pool,leased,has_pr} -> done       (владелец закрыл issue руками — GitHub ставит
                                   state_reason=completed; живые прецеденты —
                                   #111/#114/#115/#158; тот же terminal done,
                                   что и у приёмки, источник события различает)
{pool,leased,has_pr} -> abandoned  (владелец закрывает issue как not_planned, в любой момент)
{done,abandoned} -> reopened_invalid  (внешний reopen — GitHub не отклоняет нативно)
reopened_invalid -> done     (reject_reopened_tasks закрывает обратно голым
                              state=closed без state_reason — GitHub проставляет
                              completed; исхода «как был» код сегодня не читает
                              и не восстанавливает)
```

Флаги (не стадии, читаются как булевы поля ObservedTask):
- blocked (метка blocked, + список номеров блокирующих issue из
  blockedBy) — гейтит claim_task.py::claim.
- waiting_owner (метка waiting:owner) — гейтит claim.
- stale_unclaimed (пул без исполнителя дольше порога, scheduler.
  mark_stale_unclaimed) — информационный, не тормоз сам по себе.
- lease_stale (замок старше TTL) — сигнал для reap_stale, не отдельная
  стадия: сегодняшний watchdog остаётся, просто читает snapshot вместо
  пересчёта таймлайна заново.

### 2.2 PR

STAGE:

| stage | terminal | описание |
|---|---|---|
| no_task | нет (вне ядра) | ветка не резолвится task_ref.resolve_pr_task — PR не управляется этим ядром вовсе (боты вроде dependabot) |
| draft | нет | черновик GitHub |
| awaiting_gate1 | нет | нет ни review:ok, ни review:large (или review:large без review:large-ok) |
| awaiting_gate2 | нет | гейт 1 пройден, нет финального вердикта гейта 2 (ai:ok/ai:changes-requested) |
| ready | нет | оба гейта открыты (review_labels.merge_label_gate is None), не draft |
| merged | да | смердж произошёл |
| closed | да | закрыт без слияния (в т.ч. заменён replace_closed_task_prs) |

Легальные переходы (упрощённо; полный граф — в реализации, это проект):

```
opened -> {no_task | draft | awaiting_gate1}
draft -> awaiting_gate1           (ready_for_review)
awaiting_gate1 -> awaiting_gate1   (review:changes-requested, новый пуш — цикл доработки)
awaiting_gate1 -> awaiting_gate2   (review:ok, либо review:large+review:large-ok)
awaiting_gate2 -> awaiting_gate2   (ai:changes-requested / ai:failed retryable — цикл доработки)
awaiting_gate2 -> ready            (ai:ok)
ready -> awaiting_gate1            (новый пуш сбрасывает оба вердикта, review_labels.ai_verdicts_to_drop)
ready -> merged                    (scheduler.merge_queue)
{любая нетерминальная} -> closed   (закрыт руками/заменён)
```

Флаги (ортогональные, каждый со своим evidence-полем в снимке):
- conflict — mergeable_state подтверждённо dirty (review_labels.
  CONFLICT_CLEAR_STATES называет обратное множество). "Не знаю"
  (None/unknown) НЕ снимает флаг — это отдельное значение (см. п.3).
- checks_red — есть непройденный check-run вне самих гейтов ревью
  (scheduler.pr_bad_checks).
- needs_rework — ЦЕЛЕВОЙ состав флага снимка: метки из
  `scheduler.REWORK_LABELS` (scheduler.py:4035): `ai:changes-requested`,
  `conflict` ИЛИ `contract:failed` (тот же состав вычисляет
  `pr_needs_rework`, scheduler.py:4062 — агрегат wip и приоритет
  dispatch-каналов считают именно его). `review:changes-requested` в флаг
  НЕ входит — цикл доработки гейта 1 выражается стадией `awaiting_gate1`
  (выше), не этим флагом. ЧЕСТНО О ЖИВОМ РАСХОЖДЕНИИ: слитый Этап 0
  (`build_observed_pr`, scheduler.py:484) сегодня кладёт во флаг ДРУГОЙ
  состав — {review:changes-requested, ai:changes-requested}; это
  временная граница скелета, а не целевое определение. Этап 4
  ОБЯЗАН свести состав флага к `REWORK_LABELS` (одно место правды с
  решающим слоем, который флаг обслуживает) — сведение входит в критерий
  эквивалентности Этапа 4 наравне с переносом источника данных; до
  схождения этих двух определений флаг снимка не потребляется
  решающими функциями.
- gate2_error — ai:failed, с evidence-полем reason_tag (quota_exhausted /
  rate_limit_retry_budget_exceeded / transport_error / contract_violation
  — те же четыре значения, что уже даёт review_labels.reason_tag).
- contract_ok — ровно один открытый PR ссылается на задачу, назначен ровно
  один исполнитель (contract_check.py) — при contract_ok=false стадия
  всё равно вычисляется (снимок остаётся честным), но политика запрещает
  merge.
- stale_ready — стадия ready держится дольше порога без слияния
  (scheduler.stale_ready_pulls) — сигнал для эскалации, не отдельная
  стадия.

### 2.2.1 Пробел: `ready` + `checks_red=true` без названного действия (issue #1296)

Комбинация `stage=ready` (оба гейта уже открыты) одновременно с
`checks_red=true` (обязательный check-run вне гейтов ревью — например
`test` — красный) представима в модели раздела 2.2 как ортогональная пара
стадия+флаг, но ни таблица легальных переходов выше, ни план миграции
(tasks.md, Этап 4) не называют для неё ДЕЙСТВИЯ. Единственные переходы,
названные из `ready`, — `ready -> merged` (успешное слияние) и
`ready -> awaiting_gate1` (новый пуш сбросил вердикты); ни один не
покрывает случай "оба вердикта стоят, слияние блокирует чек, а PR не
получил нового пуша".

`needs_rework` (флаг, которым в старом коде считается очередь доработки —
scheduler.REWORK_LABELS, scheduler.py:4035 / pr_needs_rework,
scheduler.py:4062) определён здесь как в ЖИВОМ КОДЕ — множество
{ai:changes-requested, conflict, contract:failed}; `review:changes-requested`
в него НЕ входит (вердикт гейта 1 живёт в стадии awaiting_gate1, раздел
2.2), и `checks_red` тоже НЕ входит — ни до, ни после Этапа 4. Улика этой
улики не меняется от расхождения слитого скелета (см. §2.2): PR #1263 не
несёт НИ ОДНОЙ метки ни одного из двух составов — не обслужен он при
обоих. Этап 4 (tasks.md) мигрирует источник данных для
`checks_red`/`needs_rework` И сводит состав флага к `REWORK_LABELS`
(см. §2.2) — он не трогает решающий код
(`dispatch_conflict_rework`/`dispatch_ai_review_rework`/`wip_gate`/
`dispatch_worker` в сегодняшнем scheduler.py), который читает эти флаги и
решает, какой PR получит адресный `workflow_dispatch`. Раздел 1, п.3
("Существующие чистые предикаты... собираются под одну сигнатуру")
буквально означает, что весь этот решающий код ПЕРЕЖИВАЕТ миграцию как
есть, багами включительно — Этап 4 не является местом, где эта
конкретная комбинация получает обработку, если её не назвать явно здесь.

Живая улика (эксперимент координатора, issue #1296, 2026-09-14/15): PR
#1263 (задача #1261) — `review:ok`+`ai:ok` (stage=ready), check-run `test`
= `failure` (`checks_red=true`), задача уже свободна (`unhealthy_pulls`
сняла аренду по своему порогу `UNHEALTHY_PR_AFTER_MINUTES=120`) — простоял
без единого прогона `worker.yml` 2ч42м подряд, при закрытом WIP-гейте (18
PR с `needs_rework=true` ≥ лимита 12). Причина: `needs_rework` эту PR не
считает (флаг не про красный чек), единственный оставшийся канал
(`dispatch_worker`, адресный fallback на уже открытый PR при закрытом
WIP-гейте) стоит НИЖЕ по приоритету, чем `dispatch_conflict_rework`/
`dispatch_ai_review_rework` — при живой очереди `needs_rework`-PR (ровно
those 18) эти два канала почти на каждом такте находят себе кандидата
раньше, чем очередь доходит до `dispatch_worker`. Это воспроизводится
одинаково и до, и после миграции данных Этапа 4 — потому что миграция не
меняет ЭТУ логику, только то, откуда она читает булевы значения.

Недостающая легальная запись (добавление к таблице переходов выше):

```
ready(checks_red=true)  -> ready(checks_red=true)   (адресный dispatch worker.yml на исправление
                                                       чека — приоритет наравне с conflict/needs_rework,
                                                       бюджет попыток НА ОТПЕЧАТОК диффа, эскалация
                                                       владельцу при исчерпании — тот же приём decide(),
                                                       что уже даёт needs_rework/conflict, но КЛЮЧ
                                                       другой: checks_red, не needs_rework)
ready(checks_red=true)  -> ready(checks_red=false)  (чек стал зелёным сам или после фикса — обычный
                                                       путь дальше к merged)
```

Куда это ложится: не задача Этапа 4 как сформулирована сейчас (она про
источник данных, не про политику) — это ОТДЕЛЬНАЯ задача политики для
комбинации `ready + checks_red`, и место ей — Этап 7.5 (decide_pr,
раздел 5.2.4), куда она СУЖЕНА из Этапа 4: в самом Этапе 4 осталась только
регресс-фикстура PR #1263, реализация действия переезжает в decide_pr.
До реализации Этапа 7.5 эта комбинация остаётся необслуженной точно
так же, как в сегодняшнем scheduler.py.

### 2.3 Почему не один общий enum на 20+ значений

Отвергнуто явно (не молчаливое упрощение): PR с review:large+ai:failed
одновременно неотличим был бы от PR с review:changes-requested+ai:failed,
если бы оба схлопывались в один код "заблокирован" — а политике нужно
различать их (первому нужен только gate2-ретрай, второму — новый пуш
автора). Тот же класс потери информации уже случился один раз (#432,
review_labels.py:160-167: смешение "гейт 1 решил" и "гейт 1 открыл
слияние" в одном предикате сделало AI-ревью невидимым для review:large
PR на полгода). Малый stage + независимые флаги с явным evidence — прямая
контрмера этому классу дефекта, не эстетический выбор.

## 3. Честность снимка и лимиты CF Free — числами

### 3.1 Правило: level-triggered READ, edge-triggered WRITE

Наблюдаемое состояние пересчитывается из GitHub ЦЕЛИКОМ каждый такт
(level-triggered) — задание прямо требует этого, и это даёт нужное
свойство: потеря таблицы снимка не страшнее потери кэша ДЛЯ
НАБЛЮДАЕМОГО СОСТОЯНИЯ (стадии, флаги, evidence). Граница честности
(находка ревью, закрыто здесь): ЭПИЗОДНЫЕ поля (счётчики попыток,
дедупы, метки последней эскалации — раздел 4.1, п.47 спеки) из одного
GitHub невосстановимы после срезания публикации маркеров, для них
контракт восстановления назван отдельно в разделе 3.8 и в п.47 спеки —
формулировка «ни один бит решения не живёт только в DO» верна только
для наблюдаемой половины таблицы. НО это касается ТОЛЬКО чтения GitHub — само
по себе оно не бьёт по лимитам CF (GitHub API — не Cloudflare ресурс).
Запись снимка в DO — отдельное решение, и здесь есть жёсткое ограничение,
подтверждённое измерением этого же репозитория (раздел 3.2): снимок
ПИШЕТСЯ в DO только тогда, когда вычисленные stage/флаги отличаются от
уже сохранённых (сравнение — один SELECT перед решением, дёшево по
rows_read). Полный слепой upsert всех сущностей каждый такт — измеримо
не проходит по бюджету (см. 3.3), поэтому это не оптимизация, а жёсткое
архитектурное требование.

### 3.2 Измеренные факты (не оценка на глаз)

Источник — docs/research/20-cloudflare-free.md, разделы про инцидент
#320 и замер #678 (2026-09-11/12, run 34661127775):

- Лимиты Free, ACCOUNT-WIDE (не по namespace, не по DO-классу):
  rows_read 5 000 000/сутки, rows_written 100 000/сутки.
- 2026-09-11: аккаунт целиком израсходовал 60 382 rows_written (60.4% от
  лимита) и 4 235 878 rows_read (84.7% от лимита) — из ДЕВЯТИ воркеров
  аккаунта (docs/agents/INFRA-CF.md: аккаунт общий с другими проектами
  владельца, наших — два).
- Разбивка по namespace тем же прогоном: dsh-edge (приём транскрипта
  агентских сессий, namespace a59c9e7e...) — 59 025 rows_written
  (59 025/100 000 = 59.0% лимита аккаунта; 97.7% — доля ОТ
  ИСПОЛЬЗОВАННОГО за день, 59 025/60 382 — знаменатель называется
  в каждой формулировке этого документа, находка ревью о миграции
  неверного знаменателя, закрыто здесь) и 4 202 953 rows_read (99.2%
  аккаунта, ИЗ 4 235 878). Наш
  собственный edge-harness (heartbeat воркера, namespace 646b270e...) —
  1 308 rows_written (1.3% аккаунта) и 32 925 rows_read (0.66% аккаунта).
  Третий (не наш) DO аккаунта — 49 rows_written, 0 rows_read.
- Вывод из этих чисел: узкое место аккаунта — dsh-edge, приём транскрипта
  агентских сессий, СОВСЕМ ДРУГОЙ воркер и другая DO-таблица, не
  edge-harness. Собственная нагрузка edge-harness сегодня — единицы
  процентов от бюджета. Но лимит ОБЩИЙ на аккаунт: новый писатель на
  edge-harness делит остаток бюджета с dsh-edge, а не получает отдельный
  потолок 100 000/5 000 000 себе одному.

### 3.3 Прогноз нагрузки реконсилятора при слепой (не edge-triggered) записи

При тике раз в 15 минут (96 тактов/сутки, текущий cron orchestra.yml) и
популяции сущностей на момент этого проекта (106 открытых задач с меткой
task + порядка 30 открытых PR, по факту репозитория на 2026-09-15, из
которых 80+ рабочих деревьев и 29 открытых PR подтверждены живым обходом
worktree-cleanup при взятии этой ветки) — около 136 сущностей.

Цена одной строки записи в DO SQLite этого репозитория ИЗМЕРЕНА на другом
писателе (событие транскрипта — 6 rows_written/событие,
docs/research/20-cloudflare-free.md:367); используем ту же порядковую
величину как верхнюю оценку для UPSERT+запись перехода одной сущности (в
реальности проще одной строки — не подтверждено, консервативная оценка).

Слепая запись ВСЕХ сущностей каждый такт: 136 x 96 x 6 = 78 336
rows_written/сутки — 78% ОДНОГО ТОЛЬКО лимита аккаунта, при том что
dsh-edge в замеренный день уже потратил 60 382 (60%) на свою нагрузку.
Сложение двух чисел (78 336 + 60 382 = 138 718) превышает суточный лимит
аккаунта почти на 39% — конструкция ломается уже на первый день
эксплуатации, если писать каждый такт безусловно.

### 3.4 Прогноз при edge-triggered записи (принятое решение)

Реальная частота ИЗМЕНЕНИЙ состояния, а не популяция сущностей, — то, что
считает бюджет. После починки #203 (идемпотентная простановка меток)
замер label_churn (scripts/measure/label_churn_203.py, окно
2026-09-05T03:00..2026-09-06T03:00Z) даёт около 11 реальных смен вердикта
за сутки при 213 сырых событиях labeled — то есть подавляющая часть
событий уже сегодня НЕ являются сменой состояния. Задача явно называет
объём слияний "до двух десятков PR в сутки" — консервативно считаем на
порядок больше переходов, чем смен вердикта: 24 слияния x 4 стадийных
перехода в среднем (opened -> awaiting_gate1 -> awaiting_gate2 -> ready ->
merged) плюс сопоставимое число переходов задач (pool -> leased -> has_pr
-> done) — около 300-500 переходов/сутки с запасом.

500 переходов x 6 rows_written = 3 000 rows_written/сутки. Сравнение,
чтобы масштаб читался: этот НОВЫЙ бюджет сопоставим по порядку с
СЕГОДНЯШНЕЙ собственной записью edge-harness (heartbeat — 1 308/сутки в
замеренный день); сумма нового и сегодняшнего — порядка 4 300 rows_
written/сутки на весь edge-harness namespace, то есть 4.3% АККАУНТНОГО
лимита —
даже если dsh-edge продолжит потреблять свои 60-98%, у edge-harness
остаётся комфортный запас. rows_read (сравнение снимка перед решением о
записи) — 136 SELECT x 96 тактов = 13 056/сутки, 0.26% лимита 5 000 000,
пренебрежимо даже на фоне 84.7%, съедаемых dsh-edge.

### 3.5 Порог, при котором ломается, и что делать тогда

Ломается конструкция при ДВУХ независимых условиях, любое из двух:

1. Реальная частота переходов вырастет на два порядка (десятки тысяч
   переходов в сутки) — при сегодняшнем темпе слияний (до 24/сутки) это
   потребовало бы кратного роста активности конвейера, не видно на
   горизонте, но метрика простая: если label_churn (реальные смены, не
   сырые labeled-события) начнёт расти пропорционально числу PR, а не
   оставаться на уровне единиц-десятков в сутки — сигнал пересмотреть.
2. dsh-edge реально исчерпает 100 000 rows_written аккаунта (сегодня 60%
   в среднем, но не измерен худший день) — тогда ЛЮБАЯ запись
   edge-harness, включая уже существующий heartbeat, откажет по
   storage_quota_exceeded (контракт уже описан, cf-worker/api-spec.json,
   маршрут ready). Смягчение — то же, что уже применяется к другим
   писателям DO: батчить события транскрипта крупнее (см. research/20,
   раздел про K=30с) или физически развести dsh-edge и edge-harness DO по
   разным CF-аккаунтам (не рассмотрено этим change — не наша область,
   dsh-edge ведёт отдельный поток задач).

### 3.6 CPU на инвокацию (10 мс, Free) — измерено (2026-09-15, Этап 0)

**Адрес кода измерения.** Разработка Этапа 0 (ходячий скелет снимка,
включая `cf-worker/test/snapshot.spec.ts` и функцию `#postSnapshot` в
`cf-worker/src/harness.ts`) начиналась в ЭТОМ же PR, но по требованию
ревью (вердикт rework AI-ревью этого же PR на промежуточную голову —
находка «смешение проекта и реализации Этапа 0», ревью-комментарий в
PR #1290) вырезана отсюда в ходе доработки и переехала целиком в
отдельный PR #1299 («Ходячий скелет снимка задача/PR: таблицы+маршруты
Harness DO, build_observed_pr/task, замер CPU (Этап 0, #1298)» — задача
#1298). PR #1299 СЛИТ в main (squash-коммит `1feb02b`). Все координаты
код-артефактов в этом документе даны по дереву `main`, включающему
это слияние и слитые после него PR (#1033, #831, #1254; дерево
`e00c220`, замер координат 2026-09-18: scheduler.py — 6511 строк,
harness.ts — 3033).
Числа ниже ИЗМЕРЕНЫ на этом коде (то же дерево) и воспроизводимы
из main: `npm test` в `cf-worker/`.

10 мс CPU на invocation — жёсткий потолок Free
(docs/research/20-cloudflare-free.md:527-549), и он считает СИНХРОННУЮ
работу между await'ами, не время ожидания сети. Пакетный SELECT+UPDATE для
условной записи до нескольких десятков изменившихся сущностей за один
HTTP-вызов — это несколько SQL-операций подряд внутри одного invocation,
аналогично уже существующему #reclaimStuckMessages (harness.ts, цикл по
списку кандидатов в одном invocation) и #processInbox (цикл по limit
сообщений).

**Метод.** Прямой деплой на живой edge Cloudflare этим PR НЕ делался
(правило репозитория — разработчик не деплоит в прод сам, деплой только
через ревьюженный `deploy-worker.yml` после слияния). Вместо этого —
`cf-worker/test/snapshot.spec.ts`, реальный рантайм workerd + реальный DO
SQLite (`@cloudflare/vitest-plugin`, тот же движок, что на проде, локально,
без сети) — `runInDurableObject` выполняет ТУ ЖЕ последовательность SQL
(SELECT существующей строки + условный `INSERT...ON CONFLICT`), что и
`#postSnapshot`, для батча из N сущностей ВНУТРИ ОДНОГО измеряемого блока.
Честная находка методологии: на реалистичных размерах батча (1..136)
`performance.now()` в этом рантайме квантуется до целых миллисекунд —
разница часто читается как 0.000 мс. Чтобы получить число точнее кванта,
throughput измерен на N=10000 (заведомо больше design §3.3, батч велик
специально, чтобы измерение не зависело от гранулярности таймера) и
разделён на N — тот же приём, что применяется к любому короткому коду.

**Числа** (см. `cf-worker/test/snapshot.spec.ts`, describe «Замер CPU» —
строки 175 и 272 файла; воспроизводимо: `npm test` в `cf-worker/` из main,
код измерения слит PR #1299, squash-коммит `1feb02b`):

| N (упсертов в одном invocation) | Суммарное время | На операцию |
|---|---|---|
| 10000, новые строки (SELECT-miss + INSERT) | 127 мс | 0.0127 мс |
| 10000, no-op (SELECT-hit, без записи) | 107 мс | 0.0107 мс |

Экстраполяция на реалистичные размеры батча (design §3.3/§3.4, консервативно
по верхней цене 0.0125 мс/операция):

| Батч | Экстраполяция | Доля лимита 10 мс |
|---|---|---|
| 1 (сам ходячий скелет) | ~0.013 мс | 0.13% |
| 6 (реалистичный тик, §3.4) | ~0.075 мс | 0.75% |
| 30-50 («несколько десятков», формулировка открытого вопроса) | 0.4-0.6 мс | 4-6% |
| 136 (слепая полная запись, верхняя граница §3.3, архитектурно отвергнута) | ~1.7 мс | 17% |

**Вывод.** Батч-запись снимка укладывается в лимит 10 мс CPU/invocation с
запасом от ~6x (136 упсертов, худший теоретический случай) до ~800x
(1 упсерт, сам ходячий скелет) — CPU НЕ является узким местом этой
конструкции ни при каком реалистичном размере батча. Узкое место
по-прежнему rows_written (раздел 3.3/3.4) — вывод проекта не изменился,
предпосылка задания подтвердилась числом, не оценкой. Честная граница:
число получено на локальном workerd, не на задеплоенном edge — сетевые
задержки/шедулинг реального трафика Cloudflare сюда не входят (они и не
входят в CPU-бюджет invocation'а ни там, ни здесь — считается именно
синхронный участок, который в обоих случаях исполняет один и тот же движок
SQLite). Живое подтверждение `wrangler tail` на задеплоенном проде — законная
часть ПРИЁМКИ Этапа 0, идущая после слияния и деплоя
`deploy-worker.yml` (деплой делает workflow, не разработчик —
разработчик этапа не деплоит сам; последовательность приёмки:
слияние -> deploy-worker.yml -> замер на проде = закрытие пункта (г)
Этапа 0), см. tasks.md Этап 0.

### 3.7 Реальная частота переходов — измерено (2026-09-15, Этап 0-1)

**Источник и метод.** Раздел 3.4 обосновывал политику edge-triggered оценкой
"300-500 переходов/сутки", выведенной из одного замера `label_churn_203.py`
за один день (2026-09-05/06) плюс экстраполяции от темпа слияний.
tasks.md ("Явные незавершённости") требует измерения по логам за
представительный период (минимум 7 суток) до того, как Этап 4-6 зафиксирует
edge-triggered запись как окончательную политику — ниже это измерение.

Источник данных — репозиторный поток событий `GET /repos/{repo}/
issues/events` (issue И PR разом, постранично, `per_page=100`, сортировка
по убыванию времени), НЕ per-сущностные обходы таймлайнов: один этот
эндпоинт даёт `labeled`/`unlabeled`/`assigned`/`unassigned`/`closed`/
`reopened`/`ready_for_review`/`merged` репозиторно, без N+1 запроса на
каждую задачу/PR. Цена всего измерения — 175 вызовов `gh api` (одна
пагинация до нужной глубины), это не создаёт заметной нагрузки на часовой
лимит (`gh api rate_limit`, `resources.core.limit` 5000/час — измерение
не расходует квоту, которой пользуется оркестратор).

Команда (воспроизводимо; N = 1..175, пока `created_at` последнего элемента
страницы не старше `now - 14 дней`):
```
gh api "repos/mytab0r/edge-harness/issues/events?per_page=100&page=N"
```

Охват фактически получился шире заявленного минимума: 17 500 событий,
`2026-08-31T21:31:33Z .. 2026-09-15T02:52:42Z` — 14.22 суток, из них 14
ПОЛНЫХ календарных суток (01.09-14.09) взяты для итоговых чисел ниже (два
неполных дня по краям окна исключены из усреднения, чтобы не занижать
среднее).

**Что считается переходом** (design.md раздел 2.1/2.2, те же признаки, что
называет задание): смена вердикта гейта 1/2 (`review:ok`/
`review:changes-requested`/`review:large`/`review:large-ok`, `ai:ok`/
`ai:changes-requested`/`ai:failed`), конфликт (`conflict`), провал
контракта (`contract:failed`), блокировка/ожидание владельца (`blocked`/
`waiting:owner`) - все восемь меткой `labeled`/`unlabeled`; плюс
структурные события `closed`/`reopened`/`assigned`/`unassigned`/
`ready_for_review`/`merged`. Из подсчёта ИСКЛЮЧЕНЫ намеренно: служебные
метки вне модели раздела 2 (`area:*`, `stale-unclaimed`,
`checklist-tail:inherited`, `auto-detected`, `white-spot`) и метка `task`
сама по себе (она про вход сущности в домен, не про переход внутри
таблицы 2.1).

**1. Переходов в сутки - среднее и пик.** По 14 ПОЛНЫМ суткам (01.09-14.09):
- "сырых" переходов, как их видит таймлайн GitHub, без учёта того, что
  реконсилятор тикает раз в 15 минут, - среднее **533.6/сутки**, пик
  **1408/сутки** (2026-09-06).
- то же самое, сгруппированное ПО ФАКТУ работы реконсилятора: пара
  (сущность, 15-минутный такт) даёт не более ОДНОЙ строки записи,
  независимо от числа сырых переходов этой сущности в этом такте
  (`.github/workflows/orchestra.yml:43`, `cron: "*/15 * * * *"`) - среднее
  **297.2/сутки**, пик **712/сутки** (тот же день, 2026-09-06).
  Коэффициент коалесации - 1.79x (7500 сырых / 4188 пар сущность+такт за
  весь период): почти половина сырых переходов схлопывается в одну запись
  просто потому, что несколько меток одной сущности меняются в один и тот
  же 15-минутный интервал.

Оценка раздела 3.4 (300-500/сутки) подтвердилась почти точно для СРЕДНЕГО
(533.6 против верхней границы прежней оценки 500) - но ПИК (1408)
превышает верхнюю границу прежней оценки почти в 3 раза. Бюджет считает
пик, не среднее (раздел 3.5: "бюджет суточный, и его выбивает худший
день") - именно пик решает, укладывается ли политика, не среднее.

**2. Строк записи для двух политик** (те же 14 полных суток):

| Политика | 1 rows/upsert (реалистичная цена, раздел 3.3: "в реальности проще одной строки") | 6 rows/upsert (консервативный потолок раздела 3.3, взят с ДРУГОГО писателя - dsh-edge транскрипт, не подтверждён для схемы task_snapshots/pr_snapshots) |
|---|---|---|
| Edge-triggered, коалесация по такту (реальная архитектура; среднее 297.2, пик 712) | среднее 297 / пик 712 | среднее 1783 / пик **4272** |
| "Наивная" - запись на каждый сырой переход отдельно, БЕЗ учёта такта (среднее 533.6, пик 1408) | среднее 534 / пик 1408 | среднее 3201 / пик **8448** |

Разница между политиками (коалесация против наивной) - коэффициент 1.79x,
не порядок величины сам по себе; но при консервативном множителе 6
разница между лучшей и худшей клеткой таблицы (712 против 8448) -
более чем десятикратная. Оба множителя (1 и 6) остаются НЕ измеренными
для этой конкретной схемы (раздел 3.3 честно называет 6 верхней оценкой
"не подтверждено") - числа переходов (297-1408) измерены точно, множитель
rows/upsert - по-прежнему оценка.

**3. Остаток бюджета.** На день замера #678 (2026-09-11,
`docs/research/20-cloudflare-free.md`) аккаунт использовал 60 382 из
100 000 rows_written (60.4% лимита); dsh-edge из них - 59 025 (97.7% ОТ
ИСПОЛЬЗОВАННОГО В ТОТ ДЕНЬ - уточнение формулировки раздела 3.2: это не
97.7% лимита целиком, 59 025/100 000 = 59.0% лимита). Свободный остаток в
тот день: **100 000 - 60 382 = 39 618 rows_written**.

Бюджет НЕ исчерпан ни при одном измеренном сценарии. Даже наихудший
случай (наивная политика, консервативный множитель 6, пиковый день) -
8 448 rows_written/сутки - это 21.3% от остатка 39 618. Реальная
(edge-triggered) политика на пике при том же консервативном множителе -
4 272 (10.8% остатка); при реалистичном множителе 1 - 712 (1.8% остатка).
Вывод раздела 3.4 ("edge-triggered укладывается в бюджет") подтверждён
числом на измеренном пиковом дне, не только на среднем.

**4. Форма распределения.** НЕ равномерная. По суткам разброс от 144 до
712 coalesced-записей (почти 5x) - тяжёлые дни (02, 03, 05, 06 сентября)
датами совпадают с уже задокументированными в AGENTS.md эпизодами
интенсивной параллельной работы нескольких каналов (тот же класс, что
постмортем правила "Не подтягивай ветку без содержательной причины":
"сто прогонов ai-review.yml за 14 часов", 2026-09-01/03) - то есть часть
измеренного пика может отражать уже частично исправленный класс лишнего
трафика, а не устойчивый паттерн будущей нагрузки. Если так, это смещает
измеренный пик В СТОРОНУ завышения, не занижения - консервативно в пользу
вывода "бюджет укладывается".

Внутри суток тоже не гладко: топ-час даёт 149 сырых переходов против
среднего часового ~22 (533.6/24) - почти семикратный всплеск на пике часа.
На уровне 15-минутного такта (это и есть частота самого реконсилятора)
худший такт задел **31 разную сущность разом** (2026-09-03T23:15 UTC) -
то есть худший ОДИН вызов оркестратора обязан записать до 31 строки (186
при консервативном множителе 6). Это не создаёт отдельной проблемы ни для
суточного бюджета rows_written (сумма всё равно мала), ни для CPU/
инвокацию (раздел 3.6 уже измерил запас ~6x на батче 136, а 31 - почти
вчетверо меньше) - потому что лимит Cloudflare Free считает rows_written
за СУТКИ, а не за минуту/такт (`docs/research/20-cloudflare-free.md` не
называет отдельного per-minute лимита на rows_written). Вспышка внутри
одной минуты бьёт по CPU/инвокацию (уже с запасом), не по суточной квоте.

**Честно не подтверждено этим измерением:**
- **`checks_red`** (красный обязательный чек вне гейтов ревью, design.md
  раздел 2.2) - GitHub НЕ хранит репозиторный поток смен статуса check-run
  (только текущее состояние через Checks API и лог workflow-прогонов);

  (297-534/сутки в среднем, 712-1408 на пике) СИСТЕМАТИЧЕСКИ
  НЕДООЦЕНИВАЮТ реальную частоту переходов, а не переоценивают - живая
  находка issue #1296 (design.md раздел 2.2.1) именно про эту комбинацию.
  Отдельный замер потребовал бы обхода Check Runs API по каждому PR/
  коммиту (N+1 запросов) - не сделан в рамках этого измерения по той же
  причине экономии часовой квоты API, которую называет задание.
- Аренда git-ref (pool/leased, `claim_task.py`) не эмитит событий
  GitHub API вовсе - `assigned`/`unassigned` использованы как прокси,
  могут расходиться с реальным моментом взятия/освобождения аренды.
- 39 618 остатка бюджета - снимок ОДНОГО дня (#678), не подтверждён как
  худший день dsh-edge (тот же открытый риск уже назван разделом 3.5,
  этим измерением не закрывается).
- Период охвата - 14.22 суток фактически (14 полных календарных), больше
  заявленного минимума 7 суток, но не более представительный, чем
  позволяет сам возраст репозитория (см. раздел 10, п.5) - это измерение
  наследует ту же оговорку о представительности выборки.

**Вывод.** Политика edge-triggered (разделы 3.1, 3.4) укладывается в
бюджет rows_written с запасом на измеренном периоде, включая измеренный

### 3.8 Контракт чтения снимка консьюмером вне такта писателя (находка ревью, закрыто здесь)

Снимок пишется ТОЛЬКО тактом оркестратора (cron */15). Консьюмеры,
живущие в других прогонах (repo-ci на каждый push/PR,
conflict-mechanical-rebase, checklist-tail-triage), сегодня судят о мире
по СВЕЖЕМУ прямому пересчёту; после переезда на снимок без названного
контракта они судили бы по замороженному — а когда такт встанет (класс
инцидента #255: сутки простоя при сплошь зелёных прогонах), стерегущие
расхождение гвардии молча докладывали бы замороженное как текущее.
Доктрина check_result.py («не смог посмотреть» ≠ «нарушений нет»),
процитированная в proposal.md, обязана применяться и к собственному
снимку. Контракт из трёх правил:

1. **Freshness в строке.** Каждая строка снимка несёт `updated_ts` (в
   слитой схеме Этапа 0 уже есть) и id такта писателя. Консьюмер вне
   такта писателя обязан проверить свежесть: строка отсутствует ИЛИ
   старше двух тактов писателя (30 минут) — это ТРЕТЬЕ состояние «снимок
   не смотрел», а не «нарушений нет» и не «нулевое значение»: инвариант
   печатает причину и НЕ докладывает ни нарушения, ни его отсутствия
   (fail loud, громкий пробел — тот же контракт, что `check_result.py`).
2. **Профиль решает способ чтения.** Проверки, чья сигнализация зависит
   от «прямо сейчас» (stuck review gate, wasted ai-review runs, worker
   false success), в пуш-прогоне repo-ci сохраняют ПРЯМОЙ пересчёт
   (секреты в repo-ci не проводятся, точка 6 мигрирует только для
   orchestra-прогона) — либо, если задача Этапа 3 решит проводить
   секреты, обязана провести И freshness-гейт из правила 1; выбор
   назван в критерии Этапа 3, по умолчанию — прямой пересчёт в пуш-
   прогоне (проще и не делает инвариант зависимым от живости такта).
3. **Эпизодные поля — газ против молчаливой потери.** Поля раздела 4.1
   (`conflict_rework_attempts`, `ai_retry_count`, `ai_retry_exhausted_at`,
   `last_escalated_ts`, `pipeline_state`) НЕ восстанавливаются из одного
   GitHub, поэтому: (а) публикация текстовых маркеров ПРОДОЛЖАЕТСЯ как
   источник восстановления до признака завершения замены — срезается
   отдельным шагом Этапа 8, а не самим Этапом 7; (б) неудавшаяся запись
   эпизодного поля не съедается edge-триггером — сравнение идёт против
   СОХРАНЁННОЙ строки, несохранённое изменение повторяется следующим
   тактом, каждая неудача печатает причину в отчёте такта (issue #120);
   (в) срезание публикации маркеров в Этапе 8 допустимо только после
   одноразового ГРОМКОГО ребилда счётчиков из истории комментариев с
   пометкой rebuild в строке снимка и с гвардией: тест «снимок пуст ->
   один тик по живой истории восстанавливает счётчики; второй тик их не
   меняет». Без этого газа потерянная запись означала бы бюджет,
   не исчерпывающийся никогда (бесконечные авто-повторы), и потерянный
   дедуп (шторм эскалаций) — оба молча.

## 4. Судьба 50+ маркеров

Инвентарь (метод — тот же, что в proposal.md, одно место правды на
метод: `^[A-Z_]*MARKER[A-Z_]* *=`, тестовые файлы исключены, замер по
текущему дереву `e00c220`, 2026-09-18): **68 определений, 65 уникальных
имён в scripts/orchestra, ещё 5 в scripts/lib** (не считая маркеров, чей
текст собирается динамически с номером PR внутри —
например CONFLICT_ESCALATION_MARKER/AI_REWORK_ESCALATION_MARKER несут
номер PR ВНУТРИ строки, то есть фактически это семейство маркеров, не
один) — оценка владельца "больше пятидесяти" подтверждается с учётом этих
семейств. Цифра «43» в прежней редакции этого раздела и цифра «63»
в прежней редакции proposal считались на более старых деревьях и по
разным областям (proposal — только orchestra, здесь — orchestra+lib),
что и создало видимое противоречие «подмножество больше надмножества»
(находка ревью, закрыто здесь): оба файла отныне несут один замер
с методом и датой.

Маркеры делятся на три группы по судьбе, не поштучно на все 65+:

### 4.1 Схлопываются в поле снимка (структурное состояние)

Маркеры, кодирующие "мы уже совершили действие X для этой сущности в этом
эпизоде" — то есть ИМЕННО то, для чего снимок и создаётся. Примеры:
- pulse_guard.RESUME_MARKER / PAUSE_MARKER / PROBE_MARKER (серия
  пауза/проба/возобновление конвейера) -> поле pipeline_state в
  отдельной таблице pipeline_snapshot (не per-PR, глобальный синглтон,
  как уже сегодня issue #120 несёт один "текущий" эпизод).
- pulse_guard.CONFLICT_REWORK_MARKER / CONFLICT_ESCALATION_MARKER ->
  pr_snapshots.conflict_rework_attempts (int) +
  pr_snapshots.conflict_escalated_at (timestamp), читаются PR-снимком
  напрямую вместо grep по комментариям issue #120.
- pulse_guard.AI_REVIEW_RETRY_MARKER / AI_REVIEW_EXHAUSTED_MARKER ->
  pr_snapshots.ai_retry_count + pr_snapshots.ai_retry_exhausted_at.
- pulse_guard.AI_REWORK_MARKER / AI_REWORK_ESCALATION_MARKER -> тот же
  паттерн, отдельные поля.
- pulse_guard.HEARTBEAT_MARKER / HEARTBEAT_NO_TICKS_MARKER /
  HEARTBEAT_TICKS_RESUMED_MARKER / DO_PULSE_MARKER /
  DO_PULSE_RESUMED_MARKER -> pipeline_snapshot.heartbeat_state (три
  значения: ok/no_ticks/do_pulse_lost) — тот же класс задачи, что уже
  решает check_result.py: различать "молчит потому что всё хорошо" от
  "молчит потому что наблюдатель ослеп".

Признак группы: маркер существует ТОЛЬКО как способ узнать "уже делали
или нет" — и это ровно то, ради чего вводится снимок. После миграции
grep-по-комментариям заменяется на SELECT из снимка; САМА публикация
маркерных строк при этом не срезается Этапом 7 — она остаётся источником
восстановления эпизодных полей до отдельного шага срезания в Этапе 8
(газ и правило срезания — раздел 3.8, правило 3).

### 4.2 Остаются текстом (человекочитаемый след для людей/агентов)

Маркеры/строки, чья функция — оставить читаемый след в issue/PR для
человека или следующего агента, а не служить входом для машинного решения.
Признак: их удаление не сломало бы НИ ОДНОЙ функции decide()/build_observed,
сломало бы только читаемость истории. Примеры: CONTRACT_FAIL_HEADER,
REVIEW_FINDINGS_HEADER (review_labels.py:795-796) — заголовки комментариев,
под которые ищется "уже опубликовано ли это" через comment_update_action
(идемпотентность публикации, #203) — ЭТА функция идемпотентности мигрирует
в снимок (поле last_comment_hash), но сам ТЕКСТ комментария/заголовок
остаётся как есть — человек должен видеть прозу, не код состояния.
Аналогично DEPENDABOT_WATCH_CAP_MARKER (dependabot_alert_watch.py:120) и
CAP_EXHAUSTED_MARKER (health_audit.py:79; тот же маркер-суффикс живёт
отдельной константой и в stall_detector.py:187) —
дата в маркере это часть текста для человека ("потолок на сегодня
исчерпан"), а факт "исчерпан ли потолок сегодня" схлопывается в поле
(группа 4.1), даже если строка-уведомление продолжает публиковаться.

### 4.3 Не мигрируют вовсе (не относятся к домену задача/PR)

WORKER_GIT_STEP_MARKER, POST_JOB_CLEANUP_MARKER — это markers ВНУТРИ
одного запуска job'а воркера (не про состояние PR/задачи между тактами
реконсилятора, а про то, где именно упал job в момент падения) — область
worker-liveness/watchdog (docs `_worker_silence_reason`, `stalled_worker_run`),
не домен этого проекта (см. раздел 6, "что не входит").

## 5. 16 точек переезда — поимённо, в порядке миграции

Порядок обоснован ОДНИМ принципом: сначала read-only диагностика (ломает
только вывод человеку, не решение конвейера, легко откатить), затем
observers/инварианты (влияют на эскалацию, не на действие), затем сами
решающие функции scheduler.py (влияют на реальное действие — метка,
merge, dispatch), в последнюю очередь — функции с недавней историей
расхождения (#303/#432/#740 — самый высокий риск регресса при переносе,
переносятся последними, когда приём уже проверен на менее рискованных
точках). Проводка читателей (замечание ревью, закрыто здесь): писатель снимка —
только `orchestra.yml` (orchestra.yml:117-118, слитый Этап 0); ЧИТАТЕЛИ
снимка живут и в других workflows — `repo-ci.yml` (инварианты
repo_invariants.py, точки 6 и 9), `conflict-mechanical-rebase.yml`
(точка 4) и `checklist-tail-triage.yml` (точка 3, cron "23,53 * * * *")
— сегодня эти workflows секретов `HANDS_TOKEN`/`HARNESS_URL` не
получают, и этапы, переводящие их на чтение снимка, обязаны в том же
PR провести ту же проводку (те же две строки env, ноль новых секретов)
ИЛИ явно ограничить точку чтением только в orchestra-прогоне. Выбор НЕ
оставлен на усмотрение задачи молча — названо правило по профилю job'а
(находка ревью о третьем читателе, закрыто здесь): cron/push-прогоны

не проводятся НИКОГДА, точка остаётся прямым вычислением (профиль точки
7 назван в самом п.7). Свежесть для читателей вне такта писателя —
отдельный контракт (updated_ts и третье состояние), назван в разделе 3.8.

### 5.1 Почему именно этот порядок, одной фразой на каждый переход риска

read-only (1-3) -> read-with-local-recheck (4-5) -> observers дублирующие
scheduler (6-7) -> derived-флаги scheduler (8) -> исторически расходившиеся
двойники (9-10) -> агрегаты и суженные семантики (11-13) -> решающий
комбинатор (14) -> реальное действие (15) -> эскалация владельцу (16).
Каждый следующий шаг переносится только после того, как предыдущий прожил
не менее одного полного цикла слияний без регресса (критерий приёмки
конкретной задачи-этапа, tasks.md).

### 5.2.3 Почему это не придирка к формулировке, а отсутствующая середина

Раздел 9 (признак завершения), пункт 1, требует, чтобы все 16 точек
раздела 5 были переключены на чтение снимка, как часть определения
завершённости. Но раздел 5 никогда не включал решающий слой — значит
пункт 1 достижим целиком, а dispatch_conflict_rework,
dispatch_ai_review_rework, wip_gate, dispatch_worker и эскалационные
решатели pulse_guard.py могут пережить это условие без единого
изменения. Это ровно класс дефекта, который правило AGENTS.md
(«Решение — это механизм, а не текст») называет «написано верно, но
недостижимо по построению»: критерий завершения ссылается на список,
который по своей области определения не может обнаружить эту дыру,
сколько бы её ни находили заново отдельными живыми инцидентами (issue
1296 не первый и не последний такой случай при текущей формулировке).

раздел 9 переписан), не только констатация проблемы.

### 5.2.4 Исправление: decide_pr и decide_pool как явные точки конвергенции решающего слоя

Введены ДВЕ (не одна — раздел 1 пункт 4 ошибочно подразумевал единственный
decide() на сущность, что не годится для решений уровня пула, см. ниже)
точки конвергенции, дополняющие 16 точек раздела 5, а не заменяющие их.

decide_pr(observed, snapshot) единственное место, решающее, что делать
с одним PR, читающее все его флаги снимка (conflict, checks_red,
needs_rework, gate2_error, stale_ready и так далее) через одну явную,
исчерпывающую, приоритетную таблицу «условие — действие», не через
раздельные функции, каждая из которых проверяет своё условие независимо
и не видит остальных. Поглощает решающую (не источниковую) часть
dispatch_conflict_rework, dispatch_ai_review_rework, задачу из
параграфа 2.2.1 (ready плюс checks_red), а также решение об эскалации из
stuck_large_ok_pulls, unhealthy_pulls-как-решателя, stale_ready_pulls-
как-решателя и per-PR маркерных эскалаторов pulse_guard.py (конфликт,
ai-rework). Таблица приоритета одна, версионируется как данные (список
пар предикат-по-флагам и действие сверху вниз, первое совпадение
побеждает), не код, разбросанный по функциям, — именно это делает находку
класса issue 1296 структурно невозможной: необслуженная комбинация
(СТАДИЯ, флаги) — находка ревью, закрыто здесь: сама #1296 была парой
stage=ready + checks_red, одной оси флагов мало — это пропущенная строка
в одной таблице, находимая статическим анализом (экспоненциальный
перебор ПАР «стадия x комбинация булевых флагов» против таблицы
приоритета в тесте: 7 стадий x 2 в степени N комбинаций для N флагов,
N сегодня порядка 6-7, то есть 448-896 пар — вычислимо в юнит-тесте
целиком), а не отсутствующей веткой в четвёртой по счёту функции,
которую никто не проверяет на полноту всех комбинаций сразу.

decide_pool(снимки всех PR, снимки всех задач, порог wip_limit) отдельная
точка для решений уровня пула, а не одной сущности: сколько PR сейчас в
доработке (агрегат над снимком, не поле снимка — раздел 2.2, флаг
needs_rework уже это называет), стоит ли открывать диспетч новой задачи.
Поглощает wip_gate (гейт) и dispatch_worker. Это не тот же решатель, что
decide_pr, и не должен схлопываться в него — попытка свернуть агрегатное
решение в per-сущностную сигнатуру была бы той же ошибкой потери
информации, что раздел 2.3 уже отверг для наблюдения (один PR не может
сам решить, открывать ли диспетч новой задачи, это зависит от состояния
всех PR разом). Две точки конвергенции, не одна, и это ответ на буквальный
вопрос координатора, сходится ли план к одному решателю: нет, к двум, по
структурной причине (сущность против пула), названной явно, а не к N без
предела, как сейчас.

эквивалентны старому вычислению):

17. scheduler.py (dispatch_conflict_rework, dispatch_ai_review_rework,
    wip_gate, dispatch_worker) плюс pulse_guard.py (per-PR эскалационные
    решатели, конфликт и ai-rework) сворачиваются в decide_pr плюс
    decide_pool (раздел 5.2.4). Критерий эквивалентности жёстче, чем у
    точек 1-16: не «старая и новая функция дают одинаковый результат на
    одной фикстуре», а «таблица приоритета decide_pr даёт непустое
    действие на каждой паре «стадия x комбинация флагов» (7 стадий x
    2 в степени N), где старый код
    давал действие хотя бы от одного из четырёх и более решателей, и не
    даёт неожиданного действия там, где старый код молчал» — тест
    перебором комбинаций, не набором точечных фикстур (фикстуры issue
    303, 432, 740, 1296 входят как именованные случаи внутри этого
    перебора, не как отдельный список).
## 6. Что НЕ входит в ядро

Явная граница, чтобы следующий агент не потащил в ядро всё подряд:

- **Квоты LLM-провайдеров** (ProviderChain, cooldown, ротация ключей) —
  отдельный домен, не читает состояние задача/PR, читает только квоты
  провайдеров (DSH_PROVIDER_QUOTA_UNTIL, provider_quota_state.py).
- **Деплой** (deploy-worker.yml, deploy-dsh-edge.yml, канарейки) — не
  участвует в решении "мержить ли PR", участвует ПОСЛЕ (улика деплоя для
  приёмки задачи, scheduler.py::deploy_evidence/dsh_edge_deploy_evidence)
  — эта функция ЧИТАЕТ снимок как один из источников (merged_at, sha), но
  сам деплой не переезжает.
- **Security baseline** (gitleaks, CodeQL, Dependabot alert watch) —
  отдельная область, пересекается с ядром только в одной точке
  (dependabot_alert_watch.py читает открытые PR так же, как остальные
  консьюмеры) — эта одна точка мигрирует в общем порядке п.5, сам
  security-код не переносится.
- **Гигиена исходников** (worktree-cleanup.py, mechanical_rebase.py как
  целый модуль, decision_numbering.py) — используют снимок как источник
  (см. п.4, 5), но их собственная логика (git-операции, патч-серии) не
  относится к ядру состояния.
- **DSH-агентский цикл и dsh-edge морда** (транскрипт сессий, session API)
  — снимок реконсилятора живёт в ДРУГОМ Durable Object namespace
  (edge-harness, не dsh-edge), архитектурно и по бюджету не пересекается
  (раздел 3.2) кроме общего аккаунтного лимита CF.

Суммарная оценка объёма вне ядра (по замеру задания) — около 26 тыс.
строк; ядро (снимок + реконсилятор + политика + перенесённые точки
чтения) оценивается заданием в 2 817 строк кода БЕЗ тестов. Оценка
итога с составом, названным явно (находка ревью: прежняя формулировка
«плюс тесты (коэффициент 1.29x) — 8 500-9 000» не сходилась с
собственной формулой, закрыто заменой на проверяемую арифметику):
коэффициент 1.29x — измеренное отношение тест/код этого репозитория
(60 292 строки test_*.py / 46 747 строк нетестового Python в scripts,
замер 2026-09-18); итого 2 817 x (1 + 1.29) = ~6 450 строк кода+тестов
(2 817 кода + ~3 630 тестов) — меньше одного сегодняшнего
test_scheduler.py (10 109 строк).

## 7. Два возражения владельца — проверены фактами

Обе предпосылки, переданные владельцем как решённые ("таблица в DO SQLite"
из задания), проверены заново в ходе этого проекта. Вывод по каждой — ниже,
с адресами.

### 7.1 "Зачем новая база, если у раннера уже есть канал к CF-инфре"

**Факт 1 — ДВА разных Cloudflare Worker'а существуют в этом аккаунте, не
один** (docs/agents/INFRA-CF.md, таблица bindings):
- `edge-harness` — НАШ собственный воркер, класс DO `Harness`
  (cf-worker/src/harness.ts), хранит journal/tasks/heartbeat/messages.
  Секреты: `HANDS_TOKEN`, переменная `HARNESS_URL`.
- `dsh-edge` — форк апстрима pawaca/dsh-edge, класс DO
  `DshEdgeInstance`, хранит транскрипты агентских сессий. Секреты:
  `DSH_EDGE_ACCESS_KEY`, переменная `DSH_EDGE_URL`.

**Факт 2 — раннер (worker.yml/hands.yml, job, выполняющий ОДНУ задачу) уже
имеет HTTP-доступ к ОБОИМ**, подтверждено построчно:
`.github/workflows/worker.yml:136-137` прокидывает и `HANDS_TOKEN`/
`HARNESS_URL` (для `POST /api/heartbeat`, уже работает в проде), и
`DSH_EDGE_URL`/`DSH_EDGE_ACCESS_KEY` (для транскрипта сессии в морде
dsh-edge). Формулировка возражения верна для РАННЕРА.

**Факт 3 — канал оркестратора к НАШЕМУ собственному edge-harness: на
момент написания design.md (2026-09-15) его НЕ БЫЛО, к моменту этой
правки он УЖЕ ПРОВЕДЁН слитым Этапом 0.** Хронология одного факта:
- 2026-09-15 (проверено grep'ом, тогда): `.github/workflows/orchestra.yml`
  прокидывал `GH_TOKEN`, `ORCHESTRA_PAT`,
  `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, `DSH_EDGE_URL`/
  `DSH_EDGE_ACCESS_KEY` (для архива сессий раннеров и заметок-итогов
  после мержа, в текущем дереве это scheduler.py:2540-2744
  `_morde_rpc`/`archive_runner_sessions`/
  `append_session_notes`) — и НЕ `HANDS_TOKEN`/`HARNESS_URL` (grep — ноль
  совпадений).
- сейчас (дерево, по которому даны координаты этого документа): те же
  секреты проведены Этапом 0 — PR #1299, squash-коммит `1feb02b`,
  `.github/workflows/orchestra.yml:117-118` (`HANDS_TOKEN`/`HARNESS_URL`
  в env шага scheduler, best-effort: не заданы — запись снимка честно
  печатает причину в лог и не блокирует слияния).

**Вывод.** Предпосылка владельца частично неверна в направлении, обратном
опасению: канал к CF-инфре для *раннера* уже существует и уже
используется (это не аргумент против design.md — design.md не изобретает
новый канал для раннера, реконсилятор живёт не в раннере). Канал для
*оркестратора* к НАШЕМУ собственному DO — единственному месту, где имеет
смысл хранить снимок реконсилятора — заведён именно так, как этот раздел
предписывал, и ровно тем же путём (Этап 0, #1299): те же самые секреты
`HANDS_TOKEN`/`HARNESS_URL`, что `worker.yml` уже использует (нулевые
новые секреты, тот же паттерн авторизации Bearer, что у
`/api/heartbeat`), и `Harness` DO получил две новые таблицы
(`task_snapshots`, `pr_snapshots`) в УЖЕ существующем SQLite storage
того же класса — не новую Durable Object, не новый namespace, не новый
воркер. "Новая таблица" в буквальном смысле (`CREATE TABLE`) — да,
потребовалась; "новая база" в смысле нового сервиса, нового биллинга,
новой инфраструктуры — нет, это те же файлы (`cf-worker/src/harness.ts`,
`#postSnapshot` — harness.ts:2153), тот же деплой (`deploy-worker.yml`),
тот же класс.

**Почему не хранить снимок ВМЕСТО этого в dsh-edge** (альтернативная
форма первого возражения — "раз у раннера УЖЕ есть канал к dsh-edge,
может, туда"): dsh-edge — upstream-форк без собственной схемы под наш
контролем (см. `dsh-edge/PATCHES.md`, патч-серия поверх пина, гвардия
`mechanical_rebase.py`) и без dynamic plugin loading (раздел 7.2) — любая
наша таблица там либо живёт в патче поверх апстрима (тот же риск, что
раздел 7.2 называет для плагина: третий источник правды, конфликтующий с
апстримными миграциями схемы при каждом бампе пина), либо противоречит
структуре, которую апстрим считает своей. Плюс dsh-edge уже потребляет
~59% аккаунтного лимита rows_written (59 025/100 000 в замеренный
день; 97.7% — доля от использованного, раздел 3.2) — класть туда ЕЩЁ
одного писателя было бы прямо противоположно цели "не упереться в
лимит".

### 7.2 "Почему не форма плагина DSH"

**Что такое плагин DSH и где он выполняется** (docs/research/10-dsh-architecture.md:8,
149,273,454-475,673-693): DSH построен на Cordis ("Everything is a
Plugin", 247 пакетов), плагин — код, монтируемый в дерево плагинов
ОДНОГО профиля агента (`dsh plugin --profile <name> add <spec>`) и
исполняющийся ВНУТРИ Node-процесса headless-агента, поднятого ОДНИМ
job'ом на ОДНУ задачу (worker.yml/hands.yml, `task.sh`). Время жизни
плагина = время жизни процесса dsh для этой задачи: минуты-часы, не
постоянно. Пример из этого же репозитория — `dsh-anthropic-oauth-pool`
(research/32): плагин ротирует Claude OAuth-учётки ВНУТРИ вызовов модели
ОДНОЙ агентской сессии — узкая, in-session забота (выбор/cooldown ключа
для LLM-запроса), не межсущностная реконсиляция по всему репозиторию.

**Почему это структурно не годится для реконсилятора:**

1. **Реконсилятору нужно тикать независимо от того, работает ли
   какой-либо агент прямо сейчас.** Задача реконсилятора — обойти ВСЕ
   открытые задачи/PR каждые 15 минут по расписанию (`orchestra.yml`,
   cron), включая часы, когда ни один worker/hands job не запущен вовсе
   (замер research/20-cloudflare-free.md, 09-11: `hands.yml` не
   запускался с 2026-09-05, `worker.yml` — 19-20 раз/сутки, то есть
   большую часть суток НИ ОДНОГО агентского процесса не существует).
   Плагин, монтированный в профиль агента, живёт СТРОГО в рамках сессии
   этого агента — держать его живым "на всякий случай, пока не начнётся
   следующая задача" означало бы держать постоянно живой job, а это —
   тот же класс, что уже отвергнут трижды в
   `docs/research/30-rejected-alternatives.md` (п.2 "морда живёт только
   внутри job'а", п.3 WS-туннель, п.6 агент-цикл в DO) по одной и той же
   причине: нечто, кому нужно работать НЕПРЕРЫВНО/ПЕРИОДИЧЕСКИ, нельзя
   хостить внутри процесса, который по конструкции эфемерен и существует
   только "по требованию". Довод переносится дословно.
2. **У dsh-edge (Cloudflare-воркер, где физически живёт морда/DO) НЕТ
   динамической загрузки плагинов вовсе** — прямая цитата из
   research/11-dsh-edge.md:151-159: "Подключение сторонних плагинов:
   механизма нет... Апстрим сам это знает: issue `pawaca/dsh-edge#43`
   cordis-plugin-loader — открытый спайк, то есть динамической загрузки
   плагинов в Edge пока нет в принципе." Единственный способ добавить
   поведение в САМ dsh-edge worker — патч-серия поверх пинового клона
   апстрима (`dsh-edge/PATCHES.md`, `mechanical_rebase.py`), что
   формально ближе к форку, чем к плагину, и требует ребейза при каждом
   бампе пина (уже случалось: "auto-bump пина апстрима до
   dsh-edge-v0.14.1"). Если бы ядро реконсилятора жило там, каждый бамп
   пина рисковал бы конфликтом в критичной логике мержа PR — цена,
   которую сегодняшний scheduler.py (наш код, без апстрима) не платит
   вовсе.
3. **Плагин агентского профиля не имеет доступа к состоянию ВСЕГО
   репозитория по построению** — его контекст (`ctx` Cordis) даёт
   сервисы текущей сессии (shell, fs, LLM, session-store), а не список
   всех открытых PR/задач; чтобы получить этот список, плагину пришлось
   бы делать ТЕ ЖЕ самые вызовы `gh api`, что делает `scheduler.py`
   сегодня — то есть плагин не убирает код, а перекладывает его в TS
   внутри чужого раннтайма, ничего не выигрывая по объёму.

**Что из ядра МОГЛО БЫ лечь в форму плагина, честно:** ничего из
2 817 строк ядра (снимок, реконсилятор, политика, лизинг задачи) не
привязано к контексту одной агентской сессии. Единственный код, УЖЕ
идущий этим путём сегодня, — обратное направление: `scheduler.py`
(оркестратор, НЕ плагин) выступает HTTP-клиентом dsh-edge session API
(`_morde_rpc`/`archive_runner_sessions`/`append_session_notes`,
scheduler.py:2540-2744) — то есть внешний вызывающий код обращается к
готовому API морды, а не встраивается в неё. Это уже правильная форма
интеграции и design.md её не меняет.

**Честный риск, если бы всё же засунуть ядро в плагин** (называется прямо,
как того требует задание): это стало бы ТРЕТЬИМ местом правды рядом с
Python (`scripts/orchestra/`) и воркером (`cf-worker/src/harness.ts`) —
ровно тот класс дефекта, ради закрытия которого весь этот проект
существует (шесть-семь копий состояния схлопываются в одну; плагин добавил
бы копию логики на ТРЕТЬЕМ раннтайме — TS внутри Cordis, отдельном и от
scheduler.py, и от harness.ts). Дополнительно эта копия жила бы в
патч-серии над чужим апстримом (п.2 выше), то есть была бы ХРУПЧЕ обеих
существующих. Решение: не переносить.

**Вывод раздела 7.** Оба возражения владельца проверены предметно; первое
скорректировало план (использовать УЖЕ существующий секрет-канал
`HANDS_TOKEN`/`HARNESS_URL`, а не изобретать новый, и явно назвать, что
"новая таблица" — не "новая база"), второе не прошло проверку: форма ядра
как DSH-плагина противоречит и структуре самого DSH (эфемерность сессии,
отсутствие динамической загрузки на dsh-edge), и цели всего проекта
(не плодить третью копию состояния).

## 8. Альтернативные формы ядра — рассмотрены и отвергнуты (пополнение реестра)

По правилу AGENTS.md ("Не переисследуй документированное") и формату
`docs/research/30-rejected-alternatives.md` — эти два варианта либо уже
покрыты существующими записями реестра дословно переносимым доводом, либо
достаточно узкие, чтобы не заводить новый номер записи в самом реестре
этим change (перенос в реестр — отдельная правка документации, названная
в tasks.md, не эта дельта-спека).

| # | Вариант | Почему нет | Возврат |
|---|---|---|---|
| A | Снимок — в dsh-edge DO вместо edge-harness DO | dsh-edge уже потребляет ~59% аккаунтного лимита rows_written — 97.7% от использованного за день (раздел 3.2); отсутствие контроля над схемой (патч-серия поверх апстрима, раздел 7.1) | Если dsh-edge станет НАШИМ кодом без апстрима (маловероятно) |
| B | Реконсилятор — форма плагина DSH (Cordis) | Плагин живёт в рамках эфемерной агентской сессии, реконсилятору нужно тикать независимо от неё (тот же довод, что уже закрыл `docs/research/30-rejected-alternatives.md` пп.2/3/6); у dsh-edge нет динамической загрузки плагинов вовсе | Никогда для этой роли; для in-session забот (провайдер, инструменты) плагин остаётся правильной формой и не пересматривается |
| C | Слепая полная запись снимка каждый такт (без edge-triggered write) | Численно не проходит по аккаунтному бюджету rows_written уже на первый день (раздел 3.3: 78 336/сутки только от снимка + 60 382 от dsh-edge > 100 000 лимита) | Если аккаунтный лимит вырастет (платный план) — но тогда снимается и мотив "бесплатно", отдельное решение владельца |

Оба новых варианта (A, B) при желании владельца оформляются отдельным PR
как дополнение к `docs/research/30-rejected-alternatives.md` (задача в
tasks.md) — не делается в рамках этой дельта-спеки, чтобы не смешивать
"проект нового ядра" с "правка реестра общих решений".
