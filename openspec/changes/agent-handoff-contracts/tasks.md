# Tasks: контракты передачи между стадиями

Порядок ниже — не произвольный список, а зависимость: пункты 1-3
(стадия 6) разблокируют пункт 4-5 (стадия 7); пункты 6-8 (стадия 3) и
9 (стадия 1) независимы от первой четвёрки и друг от друга — можно
делать параллельно, если есть вторая пара рук. Пункт 10 (расширение
детектора) — последний по построению: не на чем проверить живым прогоном,
пока 1-5 не работают, И зависит от отдельного открытого PR #248 (см.
пункт 10 ниже) — если #248 не сольётся, пункт 10 снимается, пункты 1-9
не затрагиваются.

## Раздел orchestrator/developer: стадия 6 — приёмка (начинать первой)

1. **Вычислить множество задач, ожидающих приёмки, как отдельную функцию
   в `scheduler.py`** (переиспользовать логику `after_merge:446-481`,
   не дублировать). Видимый результат: unit-тест кормит функцию списком
   открытых `task` issues с известными PR-мержами и получает то же
   множество номеров, что сейчас вычисляет `after_merge` для комментария.
2. **Добавить диспетчеризацию tester по этому множеству** тем же каналом,
   что `dispatch_worker` (workflow_dispatch с параметром задачи/режима),
   ОБЯЗАТЕЛЬНО с идемпотентностью (design.md, "Кто запускает tester" —
   находка ревью PR #261): по одной задаче за цикл пульса,
   `worker_runs_active` блокирует диспетч, пока текущий tester-ран не
   завершится, задача выходит из очереди по факту `GATE #2`-комментария
   или закрытия issue. Видимый результат: живой прогон оркестратора на
   репозитории с хотя бы одной задачей из 41 (замер 2) запускает
   tester-ран, наблюдаемый в `gh run list`; тест-гвардия на fixture с
   несколькими задачами в очереди доказывает мутацией, что за один цикл
   запускается ровно один прогон, не N.
3. **Формат ответа tester -> issue-комментарий и закрытие issue при
   PASS.** Видимый результат: на одной реальной задаче из текущих 41
   открытых с уже слитым PR проведена приёмка вручную по новому
   маршруту, issue закрыт с PASS-комментарием, приложена ссылка на
   прогон.

## Раздел librarian: стадия 7 — закрытие (после раздела выше)

4. **Создать `openspec/changes/archive/` и процедуру переноса** (скрипт
   или чеклист librarian — решить по месту при apply, не здесь).
   Видимый результат: хотя бы один из 15 существующих change (с уже
   закрытыми задачами на момент apply) физически перемещён в
   `archive/<id>/`, `git log` показывает коммит переноса.
5. **Влить delta specs первого заархивированного change в
   `openspec/specs/<domain>/spec.md`.** Видимый результат: файл
   `openspec/specs/<domain>/spec.md` существует и содержит требования из
   перенесённого change с историей (кто/когда влил).

## Раздел critic/orchestrator: стадия 3 — сверка с запросом (параллельно)

6. **Расширить формат вердикт-документа стадии analyze-gate** (уже
   частично существует — `openspec/changes/dsh-edge-provider-registry/
   reviews/analyze-2026-09-01-pass2.md`) полем «адрес заявленного факта
   проверен: да/нет/не применимо» на каждое утверждение о внешней
   системе. Видимый результат: шаблон/чеклист вердикт-документа лежит в
   `docs/agents/` или в самой delta-спеке этого change, с примером
   заполнения.
7. **Вписать стадию 3 в `docs/agents/WORKER-PLAYBOOK.md` и
   `docs/agents/PROTOCOL.md` как обязательный шаг между analyst и
   developer.** Видимый результат: правка видна диффом, оба файла
   ссылаются на чеклист из design.md этого change, а не дублируют текст.
8. **Живая проверка на новом change**: следующий openspec change,
   заведённый после apply этого change, проходит через вердикт-документ
   стадии 3 до того, как developer берёт `tasks.md`. Видимый результат:
   файл `openspec/changes/<новый-id>/reviews/analyze-*.md` существует до
   первого коммита реализации (порядок коммитов в git log это показывает).

## Раздел orchestrator: расширение детектора простоя (последним, УСЛОВНО)

10. **Условие входа: PR #248 (issue #201, `scripts/orchestra/
    stall_detector.py`) слит в main.** На момент написания этого change
    #248 открыт, файла на main нет (проверено `git ls-tree origin/main`).
    Если #248 не сольётся до начала этого пункта — пункт снимается или
    откладывается, остальные девять задач этого tasks.md не зависят от
    него. Если слит: добавить в `after_merge` (или соседний обход) печать
    строки `⚠️ #N: приёмка не проведена <H> ч после мержа PR #M` в отчёт
    пульса, и, если нужен отдельный отпечаток, — regex в `extract_signals`
    (`stall_detector.py`, сверить точный номер строки по слитому коду, а
    не по этому change). Видимый результат: тест-гвардия (по образцу
    `test_stall_detector.py`) кормит детектор синтетическим отчётом с
    такой строкой и проверяет отпечаток `handoff:stage6-unclaimed`;
    мутация (снять регэксп/строку) — тест краснеет.
