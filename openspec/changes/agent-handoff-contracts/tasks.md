## Раздел orchestrator/developer: стадия 6 — приёмка (начинать первой)

1. **Вычислить множество задач, ожидающих приёмки, как отдельную функцию
   в `scheduler.py`** (переиспользовать логику сбора `task_numbers` внутри
   `after_merge` — `scheduler.py:809-830` при сверке по HEAD 2026-09-06,
   не дублировать; строки в этом репозитории дрейфуют быстрее, чем живёт
   задача — находка ревью PR #261, п.1 — при расхождении искать по имени
   функции, не по номеру). Видимый результат: unit-тест кормит функцию списком
   открытых `task` issues с известными PR-мержами и получает то же
   множество номеров, что сейчас вычисляет `after_merge` для комментария.
2. **Добавить диспетчеризацию tester по этому множеству** тем же каналом,
   что `dispatch_worker` (workflow_dispatch с параметром задачи/режима),
   ОБЯЗАТЕЛЬНО с идемпотентностью (design.md, "Кто запускает tester" —
   находка ревью PR #261, п.2): по одной задаче за цикл пульса,
   `worker_runs_active` блокирует диспетч, пока текущий tester-ран не
   завершится. Задача СЧИТАЕТСЯ «ждёт приёмки» (входит в множество на
   диспетч), пока последний `GATE #2`-комментарий по ней (если есть)
   СТАРШЕ последнего мержа PR, объявляющего задачу, либо PASS-комментария
   ещё нет вовсе — явный предикат, а не «есть любой GATE #2-комментарий»
   (тот принял бы задачу FAIL → доработка → повторный мерж навсегда
   исключённой старым FAIL). Видимый результат: живой прогон оркестратора на
   репозитории с хотя бы одной задачей из 41 (замер 2) запускает
   tester-ран, наблюдаемый в `gh run list`; тест-гвардия на fixture с
   несколькими задачами в очереди доказывает мутацией, что за один цикл
   запускается ровно один прогон, не N.
3. **Формат ответа tester -> issue-комментарий и закрытие issue при
   PASS.** Видимый результат: на одной реальной задаче из текущих 41
   открытых с уже слитым PR проведена приёмка вручную по новому
   маршруту, issue закрыт с PASS-комментарием, приложена ссылка на
   прогон.

## Раздел librarian: стадия 7 — закрытие (после раздела выше)

4. **Назвать и подключить процедуру переноса в уже существующий
   `openspec/changes/archive/`** (каталог создан и наполняется с
   2026-09-06 независимо от этого change, 5 записей на дату написания —
   недостающая работа — сам триггер/чеклист librarian, не `mkdir`,
   скрипт или чеклист librarian — решить по месту при apply, не здесь).
   Видимый результат: ещё один из открытых на момент apply change (с уже
   закрытыми задачами `tasks.md`) физически перемещён в `archive/<id>/`
   ЭТОЙ процедурой (не вручную, как предыдущие 5), `git log` показывает
   коммит переноса.
5. **Влить delta specs первого перенесённого этой процедурой change в
   domain spec его домена.** Если домен уже существует как плоский файл
   (`openspec/specs/<domain>.md`, пример — `journal-tasks-hands.md`) —
   дописать туда; только для НОВОГО домена завести
   `openspec/specs/<domain>/spec.md`. Видимый результат: файл домена
   содержит требования из перенесённого change с историей (кто/когда
   влил), новой каталожной формы рядом с плоской не появилось для
   существующего домена.

## Раздел critic/orchestrator: стадия 3 — сверка с запросом (параллельно)

6. **Расширить формат вердикт-документа стадии analyze-gate** (уже

   заполнения.
7. **Вписать стадию 3 в `docs/agents/WORKER-PLAYBOOK.md` и
   `docs/agents/PROTOCOL.md` как обязательный шаг между analyst и
   developer; тем же диффом добавить сноску к запрету `gh issue close`
   (`WORKER-PLAYBOOK.md:68`) — единственное отличие: закрытие по
   `GATE #2: PASS` (стадия 7) делает планировщик оркестратора тем же
   путём, что #227, не агент.** Видимый результат: правка видна диффом,
   оба файла ссылаются на чеклист из design.md этого change, а не
   дублируют текст; запрет на `gh issue close` для агентов остаётся
   в силе, сноска не читается как его отмена.
8. **Живая проверка на новом change**: следующий openspec change,
   заведённый после apply этого change, проходит через вердикт-документ
   стадии 3 до того, как developer берёт `tasks.md`. Видимый результат:
   файл `openspec/changes/<новый-id>/reviews/analyze-*.md` существует до
   первого коммита реализации (порядок коммитов в git log это показывает).
9. **Назвать и подключить механизм, который ЗАСТАВЛЯЕТ пройти стадию 3**
   (находка ревью PR #261, п.4 — «тормоз без газа»: без этого пункта 6-8
   остаются конвенцией, которую можно пропустить молча; находка второго
   раунда, п.3 — ключ «тело/ветка ссылается на tasks.md» противоречит уже
   слитому #394, где `task_ref.resolve_pr_task` тело PR не читает вовсе).
   Дешёвый детерминированный вариант — расширить `scripts/orchestra/
   contract_check.py` (уже enforced-гейт стадий 4/5): ключом взять СПИСОК
   ИЗМЕНЁННЫХ ФАЙЛОВ PR — если среди них есть путь под
   `openspec/changes/<id>/` (тот же `<id>`, что резолвится по имени ветки
   правилом #394), PR обязан иметь в дереве хотя бы один файл
   `openspec/changes/<id>/reviews/analyze-*.md` — иначе новое нарушение
   контракта (по образцу правил 1-5 в докстринге модуля), PR не уходит в
   очередь слияния. Правило применяется и к спековым PR (меняют только
   openspec-файлы без кода) — явно, не молчаливым исключением; этот самый
   PR обязан приложить собственный `reviews/analyze-*.md` до слияния.
   Видимый результат: тест-гвардия кормит `contract_check.py` фикстурой
   PR без `reviews/analyze-*.md` при наличии диффа под `openspec/changes/
   <id>/` того же change — красная (нарушение найдено); фикстура с
   файлом — зелёная; мутация (снять проверку) красит тест.
