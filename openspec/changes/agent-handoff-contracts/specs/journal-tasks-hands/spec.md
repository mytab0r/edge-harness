18. Задача закрывается ПО ОДНОМУ ИЗ ДВУХ путей. Ключевые слова
    авто-закрытия (`Closes|Fixes|Resolves #N`) в теле PR запрещены всегда:
    контракт отклоняет такой PR (GitHub закрыл бы задачу при слиянии) —
    мерж доказывает PR, а не готовность задачи. Первый путь, уже
    реализованный независимо от этого change (#227, `accept_merged_tasks`,
    слит отдельным PR #253 ДО ревью этого change): оркестратор сам
    закрывает задачу по МЕХАНИЧЕСКОЙ проверяемой улике (деплой,
    check-runs, файлы в main) — без tester, это его нормальная работа, не
    обход проверки. Второй путь, который добавляет этот change: после
    слияния оркестратор диспетчеризует прогон tester по задаче (тем же
    каналом, что `dispatch_worker`) — tester прогоняет acceptance criteria
    КОНКРЕТНОЙ задачи из `proposal.md` (`GATE #2: PASS/FAIL`,
    `specs/agent-handoff/spec.md`, "Приёмка после мержа диспетчеризуется
    автоматически") и публикует вердикт тем же путём, каким сейчас
    публикуется напоминание. Пути независимы: `accept_merged_tasks` может
    закрыть задачу раньше, чем отработает tester-прогон — это не
    регрессия, задача, закрытая по проверяемой улике, не нуждается, чтобы
    её закрывал ещё и tester; для задач, чей критерий проверяем только
    acceptance-прогоном (а не фактом наличия файла/деплоя), tester-путь
    остаётся единственным.

Единственное реальное изменение этого change: напоминание `after_merge`
дополняется автоматическим запуском tester по тому же множеству задач
(не заменяет ручной путь — человек по-прежнему может провести пост-мерж
проверку и закрыть issue сам, до того как отработает автоматический
прогон, или до того как её закроет `accept_merged_tasks`). Утверждение
прежней редакции «оркестратор не закрывает задачи никогда» снято как
неверное (находка AI-ревью PR #261): #227 уже закрывает задачи
оркестратором по проверяемой улике на `main`, независимо от этого change.
Домовая спека (`openspec/specs/journal-tasks-hands.md:152`) при этом
всё ещё несёт старый текст п.18 (её не обновил ни этот change, ни #227) —
это предсуществующее расхождение спеки с кодом, отдельное от находки
ревью; данная дельта при архивации заменит домовый текст на редакцию
выше, что и закроет расхождение.
