# Дельта-спека: контракты передачи между стадиями работы над задачей

Новый домен — `openspec/specs/agent-handoff/spec.md` пока не существует
(этот change его создаёт при archive). Требования ниже формулируются как
дельта к пустому domain spec.

## ADDED: Шаблон задачи несёт три обязательных поля стадии 1

Требование: `.github/ISSUE_TEMPLATE/task.yml` содержит, помимо
существующих «Цель»/«Критерий готовности»/«Площадь»/«Контекст», три новых
обязательных поля: «Зачем» (мотивация, отдельно от цели), «Что не так
сейчас» (наблюдаемый факт, а не будущее решение), «Неизвестные» (список
или явное «неизвестных нет» — поле не может быть пустым по смыслу).

Сценарий: агент создаёт задачу через шаблон, оставляет поле «Неизвестные»
пустым -> шаблон (`required: true` на textarea с валидацией непустоты
через workflow-проверку, аналогично существующим required-чекбоксам) не
даёт создать issue без явного текста в поле.

Сценарий: analyst открывает issue, где поле «Что не так сейчас»
пересказывает «Критерий готовности» другими словами (циклическое
определение) -> при сверке стадии 3 (или раньше, при первом чтении)
critic/analyst помечает это находкой «поле не отвечает на свой вопрос»,
задача не считается готовой к анализу без исправления.

## ADDED: Стадия «Сверка с запросом» перед реализацией

Требование: для каждого openspec change перед тем, как developer берёт
`tasks.md` в работу, critic производит вердикт-документ
`openspec/changes/<id>/reviews/analyze-<дата>.md`, сверяющий
`proposal.md`/`design.md` с исходным текстом issue стадии 1. Каждое
утверждение о состоянии внешней системы или чужого артефакта
сопровождается либо проверенным адресом (file:line/лог/вывод команды),
либо явной пометкой «не проверено».

Сценарий: `design.md` change содержит утверждение «X уже подключено,
дублировать не нужно» без ссылки на проверенный адрес -> critic
на стадии 3 выставляет вердикт `rework` с находкой, указывающей именно
на непроверенное утверждение (не общей фразой); change не переходит к
стадии 4, пока адрес не проверен или утверждение не помечено «не
проверено».

Сценарий: `design.md` содержит только проверенные утверждения (с
адресами) -> вердикт-документ фиксирует «расхождений с запросом
владельца не найдено», change переходит к стадии 4.

Сценарий (симметрия с #210): вердикт `rework` на стадии 3 без единого
названного расхождения -> вердикт считается нарушением контракта (тот же
класс дефекта, что #210 для AI-ревью PR), change не должен застревать без
объяснения, что чинить.

## ADDED: Приёмка после мержа диспетчеризуется автоматически

Требование: после того, как `scheduler.py::after_merge` определяет
множество `task_numbers`, для которых слитый PR закрывает работу, тот же
пульс (или ближайший следующий) инициирует прогон tester по каждому
номеру — тем же каналом диспетчеризации, что уже диспетчерит воркера
(`dispatch_worker`), без создания второго транспорта.

Сценарий: PR слит, `after_merge` определяет `task_numbers = [205]` ->
в течение одного цикла оркестратора запускается tester-прогон по задаче
#205 -> результат (`GATE #2: PASS/FAIL`) публикуется комментарием в issue
#205 тем же путём, что сейчас использует напоминание `after_merge`.

Сценарий: tester возвращает `GATE #2: FAIL` -> issue #205 остаётся
открытой и НЕ уходит в очередь на закрытие/архив; комментарий содержит
`file:line`/`output`/`expected vs actual` (формат `tester.md`).

Сценарий: tester возвращает `GATE #2: PASS` по всем acceptance ->
issue #205 закрывается (тем же способом, что сейчас требует ручного
`gh issue close`, `WORKER-PLAYBOOK.md:48`), с ссылкой на PASS-комментарий.

## ADDED: Закрытие change диспетчеризуется после приёмки

Требование: каталог `openspec/changes/archive/` существует. Когда все
задачи `tasks.md` конкретного change закрыты (по стадии 6) и delta specs
готовы к слиянию, librarian вливает их в `openspec/specs/<domain>/spec.md`
и перемещает change в `openspec/changes/archive/<id>/`.

Сценарий: change со всеми закрытыми задачами `tasks.md`, но domain spec
ещё не существует -> librarian создаёт `openspec/specs/<domain>/spec.md`
из delta specs, а не архивирует change без слияния (запрет
`librarian.md:21-24` соблюдён).

Сценарий: change с хотя бы одной открытой задачей `tasks.md` ->
librarian не архивирует, оставляет комментарий с причиной (номер
открытой задачи).

## ADDED: Расширение детектора простоя классом «стадия без обработчика»

Требование: `scripts/orchestra/stall_detector.py` распознаёт строки вида
`⚠️ #N: приёмка не проведена <H> ч после мержа PR #M` (публикуемые
источником, добавленным этим change рядом с `after_merge`) как отпечаток
`handoff:stage6-unclaimed` — тем же общим механизмом (`extract_signals`,
дедупликация, суточный потолок, эскалация), что уже покрывает простои
конвейера PR.

Сценарий: задача с мержем без приёмки держится дольше
`STALL_PERSIST_MINUTES` -> заводится задача пула с уликами и меткой
`auto-detected` (существующий путь `detect_and_act`), она НЕ дублирует
существующий инструмент диспетчеризации tester (эта задача — сигнал
«диспетчер сам не сработал», а не замена диспетчера).

Сценарий: тот же отпечаток повторяется до истечения суточного потолка ->
новая задача НЕ заводится, добавляется комментарий с новой уликой в уже
открытую (существующее поведение `find_open_task`, без изменений).
