# Контракты передачи работы между ролями-агентами

Не задача, а класс проблемы: цепочка «владелец -> консультант -> аналитик ->
сверка -> разработчик -> гейты -> приёмка -> закрытие» существует НАПОЛОВИНУ.
Три из семи стадий не хендлятся никем; ещё одна хендлится только текстом
уведомления без исполнителя. Каждая недостающая стадия -- не абстрактный
риск, а измеренная в этом же репозитории стоимость (см. «Замеры»).

## Зачем

Владелец сформулировал требование 2026-09-03 (дословно в задаче на этот
change): каждая стадия конвейера должна иметь явного обработчика, вход
одной стадии -- критерий выхода предыдущей, а новый, не предусмотренный
случай -- распидаливаться приоритетно, а не тонуть молча. Сейчас это не
так: AGENTS.md, docs/agents/PROTOCOL.md и docs/agents/WORKER-PLAYBOOK.md
описывают пул задач, ветки, PR-контракт и два гейта ревью подробно и
enforced-но -- но между «владелец сформулировал идею» и «PR открыт» лежат
две стадии (запрос, сверка с запросом), которых в этих документах нет
вовсе, а после мержа PR -- две стадии (приёмка, закрытие), у которых есть
только напоминание без исполнителя.

## Замеры (не мнение — цифры этого репозитория)

**1. Стоимость отсутствия стадии 3 — измерена, но не в том масштабе, что
в исходной постановке.** Владелец в задаче на этот change привёл цифру
«полгода ротация не подключена». Проверка по датам самого репозитория это
не подтверждает, и я обязан сказать об этом прямо, а не молча подставить
чужую цифру: первый коммит репозитория — `2026-08-28 14:39:56 +0300`
(`git log --reverse`), issue #47 (задача, породившая `dsh-in-job/proposal.md`
с утверждением «combo-router — ротация учёток уже построена, не дублируем»,
`proposal.md:24`, и `design.md:39-41` «они для этого и построены») заведена
`2026-08-29T00:40:25Z`. Владелец скорректировал курс в issue #158
(`2026-09-01T10:29:38Z`, «внешний роутер в цепочке НЕ используется вовсе…
воспроизводится своим плагином DSH», зафиксировано в `docs/INDEX.md:82-88`).
**Реально измеренный интервал — трое суток, не полгода**, и `#158` на момент
написания этого предложения (2026-09-03) всё ещё **открыт**: ротация не
подключена спустя пять суток после того, как расхождение обнаружили. Цифра
«полгода», возможно, относится к наблюдению владельца за пределами истории
git этого репозитория (репозиторий физически не мог существовать полгода —
ему 6 дней) — это стоит уточнить у владельца отдельно, здесь зафиксировано
как расхождение, а не молча принято. И трёх суток на недоказанное
архитектурное утверждение, доехавшее до `proposal.md` и `design.md` без
проверки адреса артефакта, достаточно, чтобы стадию 3 считать дорогой в её
отсутствие: **ноль механизмов её обнаружили**, нашёл владелец лично.

**2. Стоимость отсутствия стадий 6/7 — измерена напрямую.**
`gh search issues --repo mytab0r/edge-harness --state open --match comments
"приложи улики" --limit 200` (текст ровно той строки, что публикует
`after_merge` при слиянии PR, привязанного к задаче) возвращает **41**
открытую задачу. Открытых задач с меткой `task` всего **89**
(`gh api .../issues?state=open&labels=task`). То есть **46% открытого
пула — это уже слитая работа, ожидающая приёмки и закрытия**, которых
никто не делает: комментарий существует, действия по нему — нет.
Одновременно `openspec/changes/` содержит **15** директорий изменений,
`openspec/changes/archive/` не существует: ноль архивировано за всю
историю репозитория, при том что стадии 4-5 (реализация, гейты) для
многих из этих change отработали (в репозитории есть смешанные PR по
нескольким из этих change).

**3. Механизм «состояние без обработчика» — предлагается, ещё не слит.**
**Не подтверждено на main, проверено `git ls-tree`:** `git ls-tree
origin/main -- scripts/orchestra/stall_detector.py` не находит файл вовсе —
модуль существует ТОЛЬКО в неслитой ветке `agent/201-stall-detector` (issue
#201, «Самолечение: оркестратор превращает новую причину простоя в задачу
пула с уликами», реализация — открытый PR #248, на момент написания этого
предложения не слит). Если бы он был слит, это был бы единственный
работающий пример именно этого механизма в репозитории: неизвестный
отпечаток причины простоя -> задача пула с уликами, дедупликация по
отпечатку, суточный потолок, эскалация владельцу при зависании. Он
покрывал бы только простои КОНВЕЙЕРА PR (`check:red:*`, `gate:no-ai-verdict`,
`worker:no-pr`, `gate:pipeline-paused`, `archive:*`, общий `warn:*`) —
и не видел бы «стадия N осталась без обработчика», потому что не читает
состояние openspec-change или задач, ожидающих приёмки/закрытия: он читает
только уже готовый текстовый отчёт `scheduler.main()`. Известные
некупированные исходы это подтверждают уже сегодня, независимо от #248:
воркер знает два исхода из трёх легитимных (issue #226, открыт), AI-ревью
ставит `rework` без единого замечания и проходит как валидный ответ
(issue #210, открыт, PR #206). Ни один из этих кейсов не породил
автозаведённую задачу через #201, потому что механизм #201 сегодня не
существует на main вовсе (а в случае слияния #248 смотрел бы только на
отчёт оркестратора, а эти два дефекта живут в других скриптах —
`scripts/worker/task.sh`, `scripts/review/ai_review.py` — чей вывод в
отчёт оркестратора не попадает).

**Зависимость этого change от #201/#248 — явно.** Раздел "Что берёт этот
change" ниже и design.md строят расширение поверх кода, которого сегодня
нет на main. Если PR #248 не сольётся (или сольётся с другими именами
функций/строк), ADDED-требование "Расширение детектора простоя классом
«стадия без обработчика»" (delta-спека) и пункт 10 `tasks.md` снимаются
или откладываются до слияния и сверки адресов по факту слитого кода —
это НЕ блокирует стадии 1, 3, 6, 7, которые от #201/#248 не зависят.

## Границы с параллельной спекой о жизненном цикле задачи

Параллельно пишется спека про состояния задачи
(`ready/in-progress/in-review/rework(n)/needs-spec/waiting/verifying/done/dropped`),
конечный бюджет реворков и метрики цикла. Эта спека **не переопределяет
состояния** и не вводит вторую модель состояний рядом с первой (это было
бы новым «два места правды» — прямо запрещено `AGENTS.md`). Разделение:

- **Состояния задачи** (что происходит с ОДНОЙ задачей во времени, включая
  предельное число реворков) — собственность соседней спеки.
- **Контракт передачи между стадиями** (что именно СДАЁТСЯ на переходе
  между ролями и по какому чеклисту ПРИНИМАЕТСЯ) — собственность этой
  спеки.

Пересечение названо явно, чтобы не разойтись: переходы `needs-spec ->
ready` и `verifying -> done` в соседней спеке — это ровно стадии 3 и 6/7
здесь, только с разных сторон одного и того же события. Рекомендация:
соседняя спека объявляет состояние задачи, эта спека объявляет чеклист,
которым состояние подтверждается. Если оба change реализуются, `design.md`
соседней спеки должен ссылаться на чеклисты приёмки отсюда, а не
дублировать их текстом.

**Пересечение с уже слитой спекой (не соседней, а действующей).**
`openspec/specs/journal-tasks-hands.md` п.18 (change `task-closure-after-
proof`, #61) уже нормативно закрывает часть стадии 6/7: "задача
закрывается исполнителем ПОСЛЕ пост-мерж проверки… оркестратор задачи не
закрывает никогда… после слияния оркестратор ставит на задачу
напоминание". Стадии 6/7 этого change не отменяют это правило, но
расширяют его — напоминание становится ещё и триггером автоматического
прогона tester, а "исполнитель" включает tester как отдельную роль, не
только автора PR. Это MODIFIED, не ADDED, поэтому дельта-спека этого
change содержит отдельный файл `specs/journal-tasks-hands/spec.md`
(домен уже существующей спеки), не только новый домен
`specs/agent-handoff-contracts/spec.md` — иначе после archive (tasks.md
п.7 соседней спеки и librarian-процедура здесь) в источнике правды
остались бы два независимых текста о том, кто и когда закрывает задачу.

## Scope

**In:**
- Контракт (артефакт + чеклист приёма) для каждой из семи стадий.
- Расширение `stall_detector.py` (#201/PR #248 - НЕ слит на момент
  написания, см. "Замеры" п.3) на класс сигналов «стадия без назначенного
  обработчика», без второго параллельного детектора - условно, если #248
  сольётся первым (см. зависимость там же).
- Правило метрик: метрика без решения, которое по ней принимается —
  удаляется; назначение владельца метрики (роль + стадия).
- Явный ответ, какие стадии не автоматизируются и почему (честный
  потолок), с обоснованием, ложится ли недостающая стадия на
  существующий тип агента или требует новой роли (обоснование — не
  заводить роль молча).
- Порядок внедрения: с чего начать, чтобы конвейер заработал хотя бы
  наполовину.

**Out:**
- Модель состояний задачи, конечный бюджет реворков, метрики цикла —
  собственность параллельной спеки.
- Реализация кода: этот change — только propose (`proposal.md`,
  `design.md`, delta specs, `tasks.md`). Код появляется отдельным
  change/PR после утверждения.
- Правка `openspec/changes/dsh-in-job/*` по факту находки в замере 1 —
  отдельная задача (там нужна сверка адреса `combo-router`, а не
  переписывание этого change).

## Acceptance criteria

1. Для каждой из семи стадий в `design.md` названы: роль (из существующих
   шести типов агентов — analyst/developer/tester/critic/librarian/
   orchestrator — либо явно обоснованная новая роль), вход, артефакт,
   чеклист приёма (перечень разделов/условий, не расплывчатое «спека
   полная»), поведение при непринятии (кто и куда возвращает).
2. Раздел «Метрики» перечисляет только метрики, у каждой из которых
   назван: владелец (роль+стадия), решение, которое по ней принимается,
   и условие вывода из обращения.
3. Раздел «Состояние без обработчика» ссылается на конкретные строки
   `stall_detector.py` и описывает добавляемый класс сигналов, не второй
   детектор.
4. `tasks.md` даёт видимый результат на каждую задачу и явный порядок
   выполнения (что первым, чтобы конвейер заработал хотя бы наполовину).
5. Delta-спека содержит проверяемые сценарии (Given/When/Then или
   эквивалент), не описание в общих словах.

## Risks / unknowns

- **Не подтверждено:** цифра «полгода» из исходной постановки задачи —
  git-история репозитория (6 дней) её не подтверждает; возможно,
  относится к наблюдению владельца вне этого репозитория. Нужно уточнить
  у владельца, что именно измерялось, прежде чем ссылаться на неё дальше.
- **Не подтверждено:** есть ли у владельца готовая формулировка для роли
  «консультант» (стадии 1 и 3) — в реестре типов агентов
  (`C:\Users\magic\.claude\agents\`) нет типа `pm`, хотя постановка задачи
  упоминает «проджектёра, следящего за порядком, приоритетами и
  назначением» как отдельную функцию. Не предполагать — назвать явно в
  `design.md`: это роль главной (оркестрирующей) сессии, а не новый
  агент-тип, см. `design.md`.
- **Риск:** расширение `stall_detector.py` новым классом сигналов требует
  доступа к состоянию, которое сейчас не попадает в отчёт `scheduler.py`
  (например, «PR слит N часов назад, задача не закрыта» — сейчас это
  ТЕКСТ комментария `after_merge`, не строка отчёта пульса). Чтобы #201
  увидел это как сигнал, `after_merge` или отдельный обход должен начать
  печатать такую строку в отчёт — граница, которую надо явно решить в
  `design.md`, не в реализации.
- **Не подтверждено, прямая зависимость:** `scripts/orchestra/
  stall_detector.py` не существует на `origin/main` (проверено `git
  ls-tree`) — он лежит только в открытом PR #248 (issue #201). Это
  предложение и design.md ссылаются на него как на существующий механизм
  условно, для описания расширения; если #248 не сольётся или сольётся с
  другими именами/номерами строк, ADDED-требование о детекторе (delta-спека)
  и пункт 10 `tasks.md` снимаются или откладываются до сверки по факту
  слитого кода. Остальные шесть задач `tasks.md` от этой зависимости не
  страдают.
