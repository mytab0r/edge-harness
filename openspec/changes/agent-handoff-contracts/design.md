# Design: контракты передачи между стадиями

## Модель

Каждая стадия — узел с ровно тремя обязанностями: принять артефакт
предыдущей стадии по чеклисту, произвести свой артефакт, отдать его
следующей по её чеклисту. «Чеклист приёма» стадии N+1 = «критерий
готовности» стадии N — это не два документа, а один, читаемый с двух
сторон (требование владельца из постановки задачи выполнено буквально).

**Не подтверждено из репозитория — реестр вне git.** Роли ниже опираются
на реестр шести типов агентов, который живёт на машине владельца
(`C:\Users\magic\.claude\agents\*.md`: `orchestrator.md`, `analyst.md`,
`critic.md`, `developer.md`, `tester.md`, `librarian.md`) — НЕ в этом
репозитории, недоступен ни ревьюеру, ни воркеру на Actions runner. Чтобы
чеклисты ниже не поплыли молча при следующей правке реестра на машине
владельца, нужные фрагменты процитированы прямо здесь, дословно, с датой
снятия цитаты (2026-09-04). Перенос реестра в репозиторий — отдельная
задача (см. "Полезное вне рамок PR" в ревью этого PR), не блокирует этот
change: обоснование ролей ниже работает и по цитате.

Роли — только из этого реестра шести типов: orchestrator, analyst,
developer, tester, critic, librarian.

- `orchestrator.md:3` (frontmatter `description`): "Главный агент — ведёт
  OpenSpec change: explore → propose → apply → archive; spawns
  под-агентов, верифицирует, сводит."
- `orchestrator.md:10`: "Координирующий агент. Не делает руками, а ведёт
  change через OpenSpec lifecycle."
- `critic.md:12-19` (Analyze-gate): "Read-only проверка `proposal.md +
  design.md + tasks.md + delta specs`: proposal отвечает «зачем/что/
  out-of-scope»? design фиксирует ADR и trade-offs? tasks достаточно
  мелкие и делятся по потокам? delta specs реально вливаются в source of
  truth? acceptance проверяемы или расплывчаты?"
- `tester.md:22-23` (Принципы): "1. PASS = реальный прогон с выводом, не
  чтение кода."
- `tester.md:27-34` (Формат): блок `GATE #1: PASS/FAIL — reason` /
  `GATE #2: PASS: <проверка> → <наблюдаемый результат>` / `FAIL: <вход> →
  <actual> вместо <expected>` / `Итог: N PASS / M FAIL · archive-ready:
  yes/no`.
- `librarian.md:12-19` (Archive обязанности), пп.1 и 4: "1. Влить
  `openspec/changes/<id>/specs/<domain>/spec.md` в
  `openspec/specs/<domain>/spec.md`." … "4. Проверить, что `tasks.md`
  весь закрыт."
- `librarian.md:21-24` (Не делать), п.1: "Не архивировать change с
  открытыми задачами."
- `librarian.md:26-30` (Done-check): "tasks closed / specs archived /
  git status understood / temporary artifacts handled".
- `analyst.md:27-34` (Proposal format): "Summary / Problem-motivation /
  Scope: In/Out / Impacted domains / Acceptance criteria / Risks-unknowns
  / References: file:line / issue / logs".

Роль «консультант» из постановки задачи — это **не новый агент-тип**, а
функция главной (оркестрирующей) сессии в диалоге с владельцем: она уже
действует под тем же профилем, что оркестратор (`orchestrator.md:3`:
"spawns под-агентов, верифицирует, сводит"), только разговаривает с
человеком, а не только с change. Заводить седьмой тип агента ради стадий
1 и 3 нет оснований: обе укладываются на существующие `orchestrator`
(стадия 1 — постановка, ведение диалога) и `critic` (стадия 3 —
adversarial-сверка, ровно то, для чего критик и собран, `critic.md:12-19`
выше, analyze-gate уже существует, просто не вызывается). «Проджектёр,
следящий за порядком, приоритетами и назначением, который распидаливает
новый кейс» из постановки задачи — это существующий `orchestrator`
(`orchestrator.md:10` выше) плюс `stall_detector.py` (#201, реализация —
PR #248, НЕ слит на момент написания, см. proposal.md "Замеры" п.3) как
его предполагаемый исполнительный механизм, а не отдельная роль.

## Таблица стадий

### Стадия 1 — Запрос

- **Роль:** orchestrator (главная сессия, в диалоге с владельцем).
- **Вход:** реплика владельца (свободный текст, любой канал).
- **Артефакт:** GitHub issue с меткой `task` по шаблону `task.yml`,
  дополненному тремя обязательными полями (см. delta-спека): «Зачем»
  (зачем это нужно, не что сделать), «Что не так сейчас» (наблюдаемый
  разрыв между текущим и желаемым), «Неизвестные» (explicit — список
  того, что НЕ выяснено; пустой список надо писать явно словом
  «неизвестных нет», не оставлять поле пустым — так гвардия отличает
  «не подумали» от «подумали и пусто»).
- **Чеклист приёма (analyst):**
  1. Поле «Зачем» отвечает на вопрос «почему это важно», а не повторяет
     «Цель» другими словами.
  2. Поле «Что не так сейчас» описывает наблюдаемое поведение/факт, а не
     будущее решение.
  3. Поле «Критерий готовности» проверяем видимым результатом (совпадает
     с существующим required-чекбоксом шаблона).
  4. Поле «Неизвестные» заполнено (списком или явным «нет»).
- **Что при непринятии:** analyst не начинает анализ; комментирует issue
  вопросом по конкретному отсутствующему полю (не общим «уточните») и
  возвращает её в состояние «ждёт владельца» (соседняя спека жизненного
  цикла задачи описывает это состояние; здесь достаточно факта возврата).

### Стадия 2 — Анализ

- **Роль:** analyst.
- **Вход:** issue стадии 1, принятая по чеклисту.
- **Артефакт:** `openspec/changes/<id>/{proposal.md,design.md,tasks.md,
  specs/<domain>/spec.md}` — как в этом change.
- **Чеклист приёма (critic, стадия 3):**
  1. `proposal.md` отвечает на зачем/что/out-of-scope (уже требование
     `analyst.md:27-34`).
  2. Каждая задача `tasks.md` имеет проверяемый видимый результат
     (не «шаг прошёл»).
  3. Delta specs реально формулируются как дельта к существующему
     `openspec/specs/<domain>/spec.md` (или явно говорят «новый домен»).
  4. Acceptance criteria проверяемы способом, а не декларацией.
  5. Ссылки на факты — `file:line`, а не пересказ по памяти.
- **Что при непринятии:** critic возвращает `proposal.md`/`design.md` со
  списком расхождений (формат `critic.md:29-38`, вердикт `rework`).
  Правило симметрично issue #210: `rework` без единого расхождения по
  списку выше не считается валидным вердиктом (см. delta-спека) — тот же
  класс дефекта, что уже пойман в AI-ревью, не повторяем его здесь заново.

### Стадия 3 — Сверка с запросом (сейчас отсутствует — главная находка)

- **Роль:** critic.
- **Вход:** артефакт стадии 2 ПЛЮС исходный текст запроса владельца
  (issue стадии 1, дословно, не пересказ).
- **Артефакт:** вердикт-документ `openspec/changes/<id>/reviews/
  analyze-<дата>.md` (конвенция уже существует — см.
  `openspec/changes/dsh-edge-provider-registry/reviews/
  analyze-2026-09-01-pass2.md`, использовать её, не изобретать новую) со
  списком расхождений «спека говорит X, владелец в issue говорил Y» и
  явным полем «адрес заявленного факта проверен: да/нет/не применимо»
  — это прямой ответ на замер 1 (`combo-router` без проверенного адреса).
- **Чеклист приёма (orchestrator, решение о переходе к стадии 4):**
  1. Каждое утверждение `proposal.md`/`design.md` о состоянии ВНЕШНЕЙ
     системы или чужого артефакта («X уже построено», «Y не нужен») либо
     подтверждено ссылкой на проверенный адрес (file:line, лог, вывод
     команды), либо помечено «не проверено» — по правилу AGENTS.md
     («Не знаешь — пиши "не подтверждено"»); голая уверенность без
     адреса — находка critic, не пропуск.
  2. Вердикт `approve`/`rework` сопровождается списком расхождений при
     `rework` (см. правило симметрии выше, стадия 2).
  3. Если расхождений нет — явная строка «расхождений с запросом
     владельца не найдено», не молчание.
- **Что при непринятии:** issue возвращается analyst с конкретным списком
  расхождений; `proposal.md` не идёт в реализацию, пока список не закрыт.

### Стадия 4 — Реализация

- **Роль:** developer.
- **Вход:** `tasks.md`, принятый стадией 3.
- **Артефакт:** PR по контракту `docs/agents/PROTOCOL.md:49-53`
  (`#N` первой строкой, без Closes/Fixes/Resolves, разделы «Что
  сделано»/«Чем доказано»/«Пост-мерж проверка»/«Чек-лист» —
  `WORKER-PLAYBOOK.md:40-42`).
- **Чеклист приёма (существующие гейты, стадия 5):** уже enforced,
  без изменений в этом change — `scripts/orchestra/contract_check.py`.
- **Что при непринятии:** `contract_check.py` ставит `contract:failed`,
  PR не уходит в очередь слияния (существующий механизм, не меняется).

### Стадия 5 — Гейты

- **Роль:** детерминированный гейт (`check_pr.py`) + AI-гейт
  (`ai_review.py`).
- **Вход:** PR стадии 4.
- **Артефакт:** метки `review:ok`+`ai:ok` (или `rework`-путь).
- **Чеклист приёма (scheduler.py::merge_queue):** уже enforced, без
  изменений — `review_labels.merge_label_gate`.
- **Что при непринятии:** уже enforced — `review:changes-requested` /
  `ai:changes-requested`, авто-повтор при новом пуше; #196 уже чинит
  зависшие вердикты. Единственная НЕ закрытая находка в этом периметре —
  issue #210 (rework без замечаний), но она в area:review, не в области
  этого change; здесь только зафиксирована ссылкой в стадии 2 (правило
  симметрии).

### Стадия 6 — Приёмка (сейчас без исполнителя — вторая главная находка)

- **Роль:** tester.
- **Вход:** слитый PR (сигнал: `after_merge` уже публикует комментарий —
  этот же факт становится триггером диспетчеризации, см. tasks.md).
- **Артефакт:** комментарий tester в issue, формат `tester.md:27-34`
  (`GATE #2: PASS/FAIL — evidence`), с реальным прогоном
  (`tester.md:23`: «PASS = реальный прогон с выводом, не чтение кода»).
- **Чеклист приёма (librarian, стадия 7):**
  1. Acceptance criteria из `proposal.md` прогнаны, не пересказаны.
  2. Хотя бы один PASS содержит наблюдаемый артефакт (деплой отвечает,
     файл на месте, канарейка зелёная) — не «шаг CI success».
  3. Побочные эффекты проверены (`tester.md:23`, п.3).
- **Что при непринятии:** issue НЕ закрывается, комментарий tester —
  FAIL с `file:line`/`output`/`expected vs actual`; задача возвращается
  в работу (developer донастраивает, не закрывает issue).
- **Кто запускает tester:** сейчас — никто (замер 2 в proposal.md,
  46% пула). Минимальный первый шаг — `orchestra.yml` диспетчерит
  `worker.yml` в режиме tester по тем же номерам задач, что уже
  вычисляет `after_merge` (`task_numbers`, `scheduler.py:446-481`) —
  это не новый канал диспетчеризации, а переиспользование существующего
  (`dispatch_worker`, `scheduler.py:521-545`), см. tasks.md.
- **Идемпотентность (иначе — дубли-прогоны на каждый пульс, находка
  ревью PR #261).** Множество «ждёт приёмки» само по себе не убывает
  автоматически, пока tester не ответит или issue не закрыта - без
  явного условия выхода диспетчер запускал бы tester заново каждый цикл
  на все 41 задачи хвоста разом. Правило: 1) диспетчер обрабатывает
  очередь по одной задаче за цикл пульса (тот же принцип "ровно один
  `workflow_dispatch` за запуск", что уже применяется к `dispatch_worker`
  для обычного воркера); 2) `worker_runs_active` (уже существующая
  проверка активного рана) распространяется на tester-режим - активный
  tester-ран по любой задаче блокирует диспетч следующего, пока текущий
  не завершится; 3) задача выходит из очереди «ждёт приёмки» как только
  tester опубликовал `GATE #2` (комментарий - наблюдаемый факт для
  следующего цикла) или issue закрыта. Специального дедуп-хранилища не
  заводится - используется то же множество, что уже вычисляет
  `after_merge`, минус те, у кого уже есть комментарий tester этого
  цикла.

### Стадия 7 — Закрытие (сейчас не существует — третья главная находка)

- **Роль:** librarian.
- **Вход:** issue со свежим `GATE #2: PASS` от tester (стадия 6).
- **Артефакт:** 1) `openspec/changes/<id>/` перемещён в
  `openspec/changes/archive/<id>/` (каталог создаётся этим change —
  сейчас отсутствует физически); 2) delta specs влиты в
  `openspec/specs/<domain>/spec.md` (`librarian.md:13`); 3) issue закрыт
  с ссылкой на PASS-комментарий tester.
- **Чеклист приёма (никого дальше — терминальная стадия; самопроверка
  librarian по `librarian.md:26-30`):**
  1. `tasks.md` полностью закрыт.
  2. specs влиты, история в domain spec обновлена.
  3. git status понятен (временные артефакты убраны).
- **Что при непринятии:** librarian сам себе гейт — `librarian.md:21-24`
  явно запрещает архивировать change с открытыми задачами; если условие
  не выполняется, librarian не действует и оставляет комментарий с
  причиной (тем же каналом, что и остальные роли).

## Механизм «состояние без обработчика»

**Зависимость от неслитого PR, названа явно (см. proposal.md "Замеры" п.3
и "Риски"):** `scripts/orchestra/stall_detector.py` не существует на
`origin/main` — проверено `git ls-tree origin/main --
scripts/orchestra/stall_detector.py` (пусто). Файл лежит только в открытом
PR #248 (issue #201). Всё, что написано в этом разделе, — это НЕ описание
существующего расширения, а план, применимый ТОЛЬКО если/когда #248
сольётся первым. Если #248 не сольётся (или сольётся с другими именами
функций/строк), это ADDED-требование (delta-спека) и пункт 10 `tasks.md`
снимаются или откладываются до сверки адресов по факту слитого кода —
остальные шесть задач `tasks.md` от этого не зависят.

Не проектировался бы второй детектор — расширялся бы `scripts/orchestra/
stall_detector.py`, потому что (по коду ветки `agent/201-stall-detector`)
это ровно тот механизм: незнакомый отпечаток причины -> задача пула с
уликами, дедупликация, суточный потолок, эскалация (docstring
`stall_detector.py:1-84` в этой ветке).

**Что добавлялось бы.** Один новый класс отпечатка,
`handoff:no-checklist-owner:<стадия>`, и один новый источник строк отчёта:
сегодня `extract_signals` (в ветке PR #248 — функция начинается на строке
162, не 159/192, сверить точный номер при слиянии) разбирает только то,
что уже печатает `scheduler.main()` — а «PR слит, задача не закрыта N
часов» живёт ТЕКСТОМ комментария в issue (`after_merge`, `scheduler.py:454`
и далее в текущем дереве main), в отчёт пульса не попадает вовсе. Чтобы
расширение из #248 увидело это, нужно ровно одно изменение по месту, а не
новая инфраструктура: `after_merge` (или отдельный проход по открытым
`task` issues с меткой "уже есть слитый PR", то же множество, что уже
вычисляет `reap_stale`/`unhealthy_pulls` по аналогии) начинает печатать
строку вида `⚠️ #N: приёмка не проведена <H> ч после мержа PR #M` в отчёт
пульса — такую строку `extract_signals` (по коду ветки #248) уже умеет
ловить общим `warn:<...>` путём без доработки регэкспов, а специфичный
разбор (`_STALE_RE`-подобный) добавляется, если понадобится отдельный
отпечаток `handoff:stage6-unclaimed`.

**Правило расширения, а не дублирования (для соседних будущих находок
того же класса, применимо после слияния #248):** новый вид «стадия N без
обработчика» добавляется как 1) новая regex-проверка в `extract_signals`
(если нужен отдельный отпечаток) ИЛИ 2) просто новая строка `⚠️/🚨` в
существующем источнике отчёта (если общий `warn:<...>` достаточен) —
никогда как отдельный python-модуль рядом. Одно место правды для
«незнакомая причина простоя -> задача», сформулированное самим #201
(докстрока ветки `agent/201-stall-detector`, `stall_detector.py:14-16`):
«своя ответственность, свой модуль — вся логика, пороги и честный потолок
там» относится к разбору отчёта пульса ЦЕЛИКОМ, а не к каждому источнику
строк по отдельности.

## Метрики

Правило: метрика без решения, которое по ней принимается, — удаляется.
Владелец метрики называется явно (роль + стадия), потому что «кто-то
следит» без имени — то же самое, что никто.

| Метрика | Уже собирается? | Решение, которое по ней принимается | Владелец (роль/стадия) |
|---|---|---|---|
| Доля открытых `task` с уже слитым PR (46%, замер 2) | Нет — посчитана вручную `gh search` для этого change | Диспетчеризация tester (стадия 6): растёт -> приоритет автоматизации стадии 6 выше стадии 7 | orchestrator (стадия «пульс», расширение отчёта) |
| Число незаархивированных change (15, замер) | Нет | Когда > 0 длительное время — сигнал, что librarian недогружен/не диспетчерится | orchestrator |
| Возраст отпечатка простоя (`STALL_PERSIST_MINUTES`) | Условно - да в ветке PR #248 (`stall_detector.py:112` в этой ветке, не слито на main) | Завести автозадачу | orchestrator (владелец по факту слияния #248, не меняется этим change) |
| Число расхождений, найденных critic на стадии 3 (новая) | Нет — заводится этим change | Если стабильно 0 на N подряд change — либо запрос стал качественнее (стадия 1 работает), либо critic формален (нужен аудит) — оба вывода actionable | critic (публикует в вердикт-документе стадии 3), orchestrator (читает тренд раз в N change) |
| Задержка между мержем PR и закрытием issue (нужно завести) | Нет | Порог для эскалации «приёмка не проведена» (см. расширение #201 выше) | orchestrator |

**Метрики, которые НЕ заводятся этим change** (нет решения — не
метрика): «сколько всего PR слито», «сколько строк добавлено» — красивые
числа без привязанного действия; если появится решение, которое по ним
принимается, заводить отдельно с тем же владельцем.

**Кто выводит метрику из обращения:** роль-владелец метрики (колонка
выше) — при следующем архиве change или ревью `design.md`, если решение,
привязанное к метрике, перестало существовать (например, порог убрали
или автоматизировали иначе). Механизм вывода — не отдельный скрипт, а тот
же процесс review-gate (critic), которым принимаются изменения design.md:
метрика без решения — находка critic на любом следующем change, который
её касается.

## С чего начать

Гипотеза владельца — стадии 3 и 6. Измеренные данные её **подтверждают,
но с разным весом**, и порядок внутри пары важен:

**Начинать со стадии 6 (приёмка), не со стадии 3.** Причины по замеру,
не по интуиции:

1. **Масштаб уже измерим и велик.** 46% открытого пула (41/89) — это
   готовая, оплаченная работа, зависшая без единого недостающего кода:
   `after_merge` уже вычисляет ровно то множество задач, которое нужно
   диспетчеризовать (`task_numbers`, `scheduler.py:446-481`), и уже есть
   канал диспетчеризации воркера по свободным задачам
   (`dispatch_worker`, `scheduler.py:521-545`). Стадия 6 не требует
   нового агента-типа (tester уже есть), не требует нового транспорта
   (worker.yml уже раннер), не требует нового шаблона issue — только
   диспетчер, вызывающий существующего tester на уже вычисленном списке.
   Это САМАЯ маленькая единица работы на САМЫЙ большой измеренный эффект.
2. **Стадия 3 дороже по инженерии и дешевле по частоте.** Замер 1 —
   единичный, хоть и дорогой (недоказанное утверждение доехало до кода за
   3 дня и стоит уже 5 дней простоя). Но частота стадии 3 = частота
   NOVYX openspec change (единицы в неделю по текущему темпу — 15 change
   за 6 дней жизни репозитория, то есть 2-3 в день, не все с
   архитектурными утверждениями о внешних системах). Стадия 6 срабатывает
   на КАЖДЫЙ смерженный PR — а таких за то же время прошло десятки (46%
   от 89 задач). Правило «чинить то, что срабатывает чаще» здесь не
   абстракция, а числа этого репозитория.
3. **Стадия 6 разблокирует стадию 7.** Librarian не может архивировать
   change с открытыми задачами (`librarian.md:22`) — то есть даже если
   сегодня завести librarian-диспетчер, архивировать будет нечего, пока
   задачи открыты именно из-за отсутствия стадии 6. Стадии 6 и 7 —
   последовательная зависимость, не параллельная пара: начинать надо с
   более ранней.

**Порядок внедрения (детали и видимый результат — в tasks.md):**
1. Стадия 6 — диспетчер tester по слитым PR (наибольший эффект/работа).
2. Стадия 7 — диспетчер librarian, разблокированный шагом 1.
3. Стадия 3 — вердикт-документ critic перед реализацией (дороже по
   инженерии полноценного review-gate, но именно она предотвращает
   следующий замер-1-класса инцидент, а не разгребает уже накопленный
   долг).
4. Стадия 1 — расширение `task.yml` тремя полями (самая дешёвая правка,
   не блокирует остальное, можно делать в любой момент параллельно).
5. Расширение `stall_detector.py` — после того, как стадии 6/7 реально
   работают И PR #248 слит (см. "Зависимость от неслитого PR" выше): до
   этого нечего детектировать как «зависло», механизм не на чем проверить
   живым прогоном, а без #248 базового модуля нет вовсе.

## Честный потолок — что не автоматизируется

- **Стадия 1 (запрос) не автоматизируется по существу.** Формулировка
  «зачем» и признание того, что было непонятно на входе, — суждение
  владельца; шаблон структурирует форму, не заменяет содержание. Здесь
  автоматизация — это чеклист полноты полей, не оценка качества мысли.
- **Стадия 3 (сверка) не автоматизируется до состояния «без ложных
  срабатываний».** critic — LLM-агент; он может пропустить расхождение
  (как AI-ревью иногда пропускает регрессии) или найти мнимое. Это
  снижает риск, не убирает его: правило «недоказанное утверждение помечай
  "не проверено"» опирается на дисциплину промпта критика, а не на
  формальную проверку кода.
- **Эскалация владельцу остаётся необходимой, а не резервной.** Пороги
  `ESCALATE_AFTER_HOURS`/`STALL_DAILY_CAP` (в ветке PR #248 —
  `stall_detector.py:121`/`:117` соответственно, не слито на main)
  существовали бы именно потому, что автоматика решает задачи в среднем
  случае и упирается в потолок в остальных — по замыслу самого #201
  («Честный потолок» в его docstring), это свойство всей системы, не
  дефект этого change.
- **Если сломан сам оркестратор/детектор — самолечения нет.** Ровно
  формулировка #201 (в ветке PR #248, не слито на main —
  `stall_detector.py:69-76` в этой ветке): пульс, который должен
  заметить свою собственную смерть, заметить её не может — это закрывает
  только внешний сторож (#194) и heartbeat (#120), оба вне периметра
  этого change.
