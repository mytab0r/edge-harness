# Развилки zombie-run-watch: почему так, а не иначе

Материал подробнее — в докстринге модуля
(`scripts/orchestra/zombie_run_watch.py`); здесь только развилки и почему
выбран текущий путь.

## Газ: переэмиссия событий против повторного rerun

`gh run rerun` отказывает («This workflow is already running») — run числится
живым, не имея ни одного job'а. Единственный проверенный живым случаем
(#1088, 2026-09-13) газ — `gh pr close && gh pr reopen`: head SHA не
меняется, все обязательные workflow получают `reopened` (входит в дефолтный
набор типов `pull_request`). Под `GITHUB_TOKEN` это был бы тихий no-op
(события от `GITHUB_TOKEN` не зажигают workflow-прогоны, класс #18/#929/#955)
— close/reopen идут под PAT владельца, а в боевом прогоне без PAT — громкий
отказ до действия (ревью PR #1212, круг 5), не fallback.

## Одно действие на head_sha против цикла retry

Автоматический газ деструктивнее обычного (перепрогоняет все обязательные
чеки PR) и адресует отказ GitHub, а не наш код: повтор вслепую может
зациклиться. Поэтому ровно одна попытка на `head_sha` (дедуп-маркер,
два носителя), рецидив и вхолостую-переэмиссия — эскалация человеку.

## Различение ожидания concurrency-группы: данные, а не порог и не hardcode

Развилка (ревью PR #1212, круги 4–5):

- *Ничего не делать, порог 15 минут отфильтрует* — отвергнуто: ожидание
  группы бывает дольше порога (quota-watch: PR-триггер «практически
  постоянно» + собственный cron в общей группе, `cancel-in-progress:
  false`, job до 10 минут) — газ бил бы по здоровым PR.
- *Hardcode-исключение workflow с группами* (промежуточная версия этого же
  PR) — отвергнуто: 2 из 8 РЕАЛЬНЫХ зомби #1106 — прогоны workflow именно с
  группами (34748469982 quota-watch, 34748469975 dsh-edge-pr-smoke);
  безусловное исключение сделало бы сторож вечно немым для трети класса —
  тот же «зомби навсегда при сплошь зелёных прогонах сторожа», против
  которого вводился PAT.
- *Выбрано*: различение по данным — версия workflow-файла НА HEAD_SHA
  (Contents API) классифицируется построчным парсером; workflow-level
  `concurrency` без `cancel-in-progress: true` газится только при свободной
  группе того же workflow (нет in_progress-прогонов). Занятая группа —
  легитимное ожидание (газ откладывается), свободная + queued/0-jobs дольше
  порога — зомби. Job-level группы игнорируются: реальный зомби 34748469966 —
  прогон orchestra.yml с job-level группами. Версия на head, не на main:
  PR-локальные правки workflow исполняются на PR, сверка с main промахнулась
  бы мимо них.

Ограничения названы честно: занятость группы аппроксимируется по
`workflow_id` (точной занятости групп API не отдаёт) — для параметризованных
per-PR/per-task групп чужой in_progress-прогон того же workflow может
отложить газ на пульс; ложного газа аппроксимация не создаёт. Ведёт ли
ожидание JOB-уровневой группы к `queued`/0-jobs — не подтверждено; в этом
репозитории job-level группы стоят на вторых джобах. Построчный разбор yml в
runtime — без PyYAML (в окружении сторожа его нет), консервативно; в CI
сверяется с PyYAML на всех реальных workflow.

## Потолок цены: на /jobs-вызовах, после осмысления кандидатов

Потолок ДО группировки резал сырой список по возрасту — а permanent-зомби
слитых PR всегда старейшие, и живой зомби открытого PR вытеснялся (ревью
PR #1212, круг 4). Выбрано: группировка и отбраковка — до потолка; бюджет
`MAX_JOBS_CHECKS_PER_PULSE` — на дорогих /jobs-вызовах, старейшие первыми,
остаток переносится на следующий пульс с наблюдением.

## Порядок действия: действие до маркера

Маркер-дедуп, записанный ДО действия, при отказе посередине навсегда глушит
газ («переэмиссия уже была», попытка потрачена впустую — ревью PR #1212,
круг 2). Выбрано: close→reopen первыми, маркер-отчёт — только после успеха;
три формы отказа обработаны по-разному (см. дельта-спеку).
