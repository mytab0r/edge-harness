# pulse-external-alert: DO само кричит владельцу, если пульс не бьётся (#1103)

Задача: #1103. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md). Решение и
отклонённые альтернативы: [ADR 0018](../../../docs/decisions/0018-pulse-alert-lives-in-do.md).

## Боль владельца

Живой инцидент 2026-09-13: конвейер простоял 40+ минут, движение вернул
ручной `workflow_dispatch`. Автоматическое возобновление (`alarm()` +
Cron Trigger, issue #693/#713) уже существует и покрыто тестами — реальная
дыра в ВИДИМОСТИ: единственный существующий сторож живости независимого
DO-пульса, `pulse_guard.py::independent_pulse_check` (issue #689),
исполняется ВНУТРИ `scheduler.py`, то есть внутри самого пульса. Когда
причина падения — исчерпание квоты GitHub API (#1100), рушится КАЖДЫЙ вызов
API, включая dispatch из самого DO, — `scheduler.py` не запускается вовсе,
и проверка, которая должна закричать, не исполняется. Класс уже назван в
AGENTS.md: «проверка исполняется внутри пульса — при мёртвом пульсе она
молчит».

## Что делается

`Harness#tickPulseAlert()` (`cf-worker/src/harness.ts`), вызывается из
общего `#dispatchOrchestraTick` — то есть срабатывает и из `alarm()`
(тикает каждые `HEARTBEAT.selfOrchestrationMs`), и из `scheduledTick()`
(Cron Trigger, каждые 5 минут). Оба живут в Cloudflare-инфраструктуре, не в
GitHub Actions — алерт может дойти до владельца, даже если ни один workflow
этого репозитория не запускается вовсе.

- Решение о тревоге/восстановлении — уже вычисленный `pulseHealthy()`
  (одно место правды на «здоров ли пульс», без второй копии порога).
- Переход, не каждый тик: дедуп — новая таблица `pulse_alert` (флаг
  `alerted`), тот же приём, что `storage_probe`/`storageReadyAlertDecision`
  (#575) — функция принятия решения переиспользуется напрямую, второй
  копии не заводится.
- Доставка — тот же `#telegramApi`, что и решения владельца (#470/#471) и
  алерт готовности хранилища (#575).
- Текст называет факт — конкретный `detail` пульса, который тик только что
  сам записал (`pulseAlertText`, чистая функция, не ветвится по возрасту:
  на пульсе с `ts: now` ветка «тик давно не обновлялся» недостижима,
  находка ревью PR #1104) — и план (что уже делает самовосстановление, что
  проверить, если за час не пришло подтверждение) — правила AGENTS.md
  «алерт не гадает» и «алерт обязан кончаться планом».
- 0 добавленных вызовов GitHub API/час: решение целиком из уже записанного
  в SQLite DO состояния — алерт не может усугубить причину падения, если
  она в исчерпании квоты API.

## Чем доказано

`cf-worker/test/pulse-alert.spec.ts` (прод-форма — реальный `403` GitHub на
`workflow_dispatch` И на `/runs`, как в живом инциденте, где рушился КАЖДЫЙ
вызов API): серия из восьми подряд падающих тиков → ровно один
incident-алерт с проверкой содержимого текста, не восемь; восстановление →
ровно один recovery-алерт; тот же путь со стороны Cron Trigger
(`scheduledTick()`); `TELEGRAM_CHAT_ID` не задан — тик не падает и не
звонит; таблица `pulse_alert` недоступна — тик не падает и не спамит,
первый удавшийся тик догоняет. `cf-worker/test/pulse.spec.ts` — прямой
юнит-тест чистой `pulseAlertText` (находка ревью PR #1104). Две мутации
(снятие вызова `#tickPulseAlert`; снятие fallback на `detail: null`) красят
ровно ожидаемые тесты; восстановление возвращает все зелёными (см. tasks.md,
дословный вывод).

## Что вне рамок

- Изменение `HEARTBEAT.selfOrchestrationMs` или порогов `pulseNeedsRecoveryDispatch`/
  `pulseStale` — не трогается, N минут до автовозобновления не меняется этим change'ом.
- `pulse_guard.py::independent_pulse_check` (#689) — не удаляется, не
  дублируется: остаётся единственным способом различить независимый и
  событийный каналы, когда оркестратор всё же запускается.
- Честный потолок наблюдаемости, если резервный dispatch scheduledTick()
  успевает восстановиться в ТОМ ЖЕ тике, где обнаружил подвисший alarm —
  incident-алерт тогда не пишется вовсе (issue #1143, найдено ревью PR
  #1104, не закрыто здесь).
