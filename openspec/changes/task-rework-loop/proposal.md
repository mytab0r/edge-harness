# task-rework-loop: конечный цикл реворка — бюджет, needs-spec, а не беклог

Задача владельца: сформулирована в чате 2026-09-03, issue в пуле пока не
заведена этим change — заводится как часть tasks.md (п.0).

## Класс проблемы

scripts/orchestra/scheduler.py::unhealthy_pulls (слито PR #200) снимает
исполнителя с задачи, у которой PR держит ai:changes-requested или красный
обязательный чек дольше UNHEALTHY_PR_AFTER_MINUTES (120 мин,
scripts/orchestra/pulse_guard.py:94). Комментарий явно говорит "доработай
существующий PR, не переделывай с нуля" - но до PR #247 это было
невыполнимо: scripts/worker/task.sh::free_task (до фикса #245/#247)
исключал из пула любую задачу с открытым PR, поэтому возвращённая задача
становилась невыбираемой ни автоматически, ни вручную - "свободна навсегда,
но недостижима". PR #247 (слит, коммит 8c0c635, замер внутри PR: было ложно
заблокировано 16 задач) чинит именно это: задача без исполнителя, но с
открытым PR, теперь выбирается воркером и ведёт к чекауту существующей
ветки, без второго PR.

Что #247 не делает и что делает этот change. #247 убирает механическую
блокировку повторного выбора. Он не ограничивает, сколько раз задача может
пройти по кругу "взята - PR - ai:changes-requested - возврат в пул - снова
взята - тот же PR" - а без потолка это ровно то поведение, которое не
устроило владельца: задача крутится в ревью бесконечно, вместо того чтобы
либо доехать до done, либо явно уйти на переформулировку. Этот change
вводит (1) конечный бюджет круга реворка, измеренный по факту, а не
выдуманный, (2) состояние needs-spec - не тупик, а работа аналитика с
объявленным условием возврата, (3) правило, что задача в
needs-spec/waiting не попадает обратно в пул автоматически, пока условие
не снято.

## Посылка каркаса - подтверждена замером

Ключевая гипотеза владельца: повторный реворк - сигнал о неясном требовании,
а не о качестве исполнения; после нескольких кругов выход должен вести в
аналитику, а не обратно в общий пул.

.../issues/<N>/timeline, событие labeled с именем review:changes-requested

на доработку) - 28 PR: 17 слитых за последние 24 часа (окно от текущего

поведение (несколько кругов - нормально, много - патология) видно на
данных, а не придумано.

Оговорка честно. n=28 - один репозиторий, одна неделя истории, ранняя
стадия проекта (первые сутки многоагентной работы). Порог REWORK_BUDGET по
этому замеру - начальное значение с планом уточнения (design.md,
"Метрики", п.1), не окончательная константа.

## Что берёт этот change, что остаётся другим задачам

- #247 (слит, коммит 8c0c635) - механика продолжения ветки/выбора задачи с
  открытым PR. Этот change не дублирует её: бюджет и needs-spec строятся
  НАД #247, предполагая её слитой (зависимость в tasks.md).
- #243 (жизненный цикл артефактов) - общий каркас состояний для задачи, PR,
  openspec-предложения, документа, включая дедупликацию и авто-закрытие
  done. Этот change детализирует ровно один участок каркаса #243 - "PR:
  открыт -> вердикты -> слит | закрыт без слияния" - вплоть до условий
  выхода из петли вердиктов. done (закрытие после пост-мерж проверки) -
  существующее поведение task-closure-after-proof (уже применено), этот
  change его не меняет, только передаёт эстафету в verifying. Таксономия
  "закрыта не мержем" (устарела/отклонена/дубликат) - #243, не здесь: этот
  change лишь гарантирует, что needs-spec/waiting не тупик, а решение
  "закрыть насовсем" остаётся за человеком/#243.
- #224 (порядок работ из графа блокировок) - вычисление приоритета. Этот
  change требует, чтобы выход из needs-spec/waiting включал пересмотр
  приоритета как шаг чек-листа, но не строит движок приоритезации - до
  #224 это ручное решение аналитика/владельца, отражённое комментарием.

## Scope

In:
- Состояния ready -> in-progress -> in-review -> rework(n) -> verifying и
  боковые needs-spec, waiting (переиспользует существующую метку blocked,
  без новой метки - см. design.md) с объявленным условием выхода из
  каждого.
- Бюджет кругов реворка - новый порог REWORK_BUDGET в
  scripts/orchestra/pulse_guard.py, рядом с прочими порогами предохранителя.
- Метка needs-spec (новая) на ЗАДАЧЕ + правило, что она исключает задачу из
  автоматического выбора (scripts/lib/free_task.py), заодно закрывающее тот
  же класс для существующей метки blocked (см. design.md - сегодня
  free_task.free_candidates фильтрует только по assignees, метки не
  смотрит вовсе).
- Решение по закрытию PR при исчерпании бюджета (design.md, вариант выбран
  и обоснован) - вместо вечно висящего PR вроде #164.
- Правило приоритезации доводки над новым стартом при выборе свободной
  задачи (tie-break в free_task.py) - недостающий кусок "толкать вперёд, не
  сбрасывать в общий беклог".
- Что делать с уже открытыми зависшими PR (#164, #173, #166, #162) -
  миграция в needs-spec этим же изменением (design.md, раздел "Миграция").
- Метрики: определение, источник данных, что решается по каждой (раздел
  ниже).

Out:
- Механика продолжения ветки/сессии - #247, не переизобретается.
- Полное резюме состояния DSH-агента (ctx.agents.resume с восстановлением
  $DSH_HOME/sessions/... между эфемерными раннерами) - инфраструктуры для
  этого нет (замер в design.md), строить её не в рамках этого change.
- Общий жизненный цикл openspec-предложений, дедупликация задач,
  авто-архивация openspec/changes/ - #243.
- Вычисление приоритета из графа блокировок - #224.
- Исправление того, что PR с review:changes-requested (гейт 1, не гейт AI)
  никогда не попадает под unhealthy_pulls, потому что pr_is_unhealthy
  сегодня проверяет только ai:changes-requested и красные чеки, не
  review:changes-requested - замером это не потребовалось (0 из 28 PR
  держали review:changes-requested), но само по себе это отдельный, сейчас
  неактивный тормоз без объявленного зазора. Не подтверждено, что это
  реальная проблема - фиксируется как находка, не чинится здесь.
- #231, #167 - открытые PR, зависшие не из-за цикла реворка (conflict без
  ребейза, review:large без review:large-ok) - другой класс дефекта,
  бюджет реворка на них не действует (0 кругов у обоих). Не мигрируются
  этим change; если владелец хочет - отдельная задача.

## Acceptance criteria

1. Для любого PR из измеренного набора применение нового правила
   воспроизводимо: rework_cycle_count(PR) >= REWORK_BUDGET детерминированно
   даёт тот же список задач на миграцию, что приведён в design.md
   ("Миграция"), - проверяется тестом на реальных телах PR (мутация:
   снизить REWORK_BUDGET до 3 -> список расширяется на #108, #181; поднять
   до 9 -> список сужается до #166, #173, #164).
2. Задача с меткой needs-spec не выбирается free_task.oldest_free, даже без
   назначенного исполнителя - тест на реальных данных (issue из needs-spec
   не в кандидатах).
3. Снятие needs-spec требует и снятия метки, и комментария с маркером
   (design.md - формат маркера) - задача без маркера не считается вышедшей
   из needs-spec тестом-гвардией реестра меток (test_label_registry.py
   расширяется строкой).
4. docs/agents/LABELS.md содержит строку needs-spec с непустой колонкой
   "Газ" - гвардия test_label_registry.py проходит.
5. Каждое состояние из таблицы design.md имеет и исполнителя перехода, и
   код/место, где переход написан (или явно помечено "требует PR" в
   tasks.md, если код ещё не написан).

## Риски / неподтверждённое

- n=28 мало. Порог REWORK_BUDGET - начальное значение, план уточнения в
  design.md ("Метрики", п.1).
- Резюме DSH-агента. Не подтверждено (но и не похоже на верное по
  устройству персистентности, docs/research/10-dsh-architecture.md:180-207)
  - сериализуется только сессионный лог на диске раннера, а раннер
  эфемерный и ничего не переносит между job'ами (нет actions/cache или
  actions/upload-artifact для $DSH_HOME/sessions, проверено grep по
  scripts/ и worker.yml). Значит "резюме сессии" в смысле памяти агента
  сегодня недоступно ни при каком выборе - это факт инфраструктуры, а не
  решение дизайна.
- Закрытие PR при исчерпании бюджета не удаляет ветку (стандартное
  поведение GitHub API PATCH .../pulls/{n} с state=closed - не
  подтверждено дословно по документации в рамках этого замера, но нет
  оснований для другого поведения: удаление ветки - отдельное действие
  DELETE /git/refs/..., здесь не вызывается). Проверить перед тем, как код
  на это опираться.
- Число открытых задач без исполнителя, реально ставших needs-spec, за
  пределами измеренных 28 PR не известно - метрика 3 ("доля needs-spec") на
  момент этого предложения нулевая по построению (механизм ещё не
  существует), первое значение появится после внедрения.
