# tasks.md: task-rework-loop

Зависимость всей ветки задач: PR #247 слит первым (проверка перед стартом
любой задачи ниже - `gh pr view 247 --json state,mergedAt`). Без него
free_task не подхватывает продолжение ветки, и needs-spec/бюджет опираются
на несуществующую механику.

## 0. Завести задачу пула

Исполнитель: любой агент/человек. Приёмка: issue с меткой task, ссылающийся
на этот change (`openspec/changes/task-rework-loop/`), тело содержит
краткую формулировку из proposal.md "Класс проблемы" и ссылку на #245/#247.

## 1. REWORK_BUDGET в pulse_guard.py

Исполнитель: воркер/агент. Правка: константа REWORK_BUDGET=5 с комментарием
(design.md п.2, дословно обоснование из proposal.md "Посылка каркаса") рядом
с UNHEALTHY_PR_AFTER_MINUTES. Функция rework_cycle_count(repo, pr_number) -
чтение timeline, подсчёт labeled с именем review:changes-requested или
ai:changes-requested. Приёмка: тест на реальных телах PR из таблицы
proposal.md ("Посылка каркаса") - rework_cycle_count(166)==10,
rework_cycle_count(239)==1 и т.д. (кормится сохранённым JSON-фикстюром
timeline, не живым API - тест детерминирован без сети).

## 2. Метка needs-spec + вход (scheduler.py)

Исполнитель: воркер/агент. Правка первая (закрывает известный разрыв,
specs/journal-tasks-hands/spec.md "Известный разрыв" - настоящий дефект,
не обходится): pr_is_unhealthy (scheduler.py:1052, на момент написания)
сегодня признаёт нездоровым PR только по review_labels.AI_CHANGES и
красным обязательным чекам - добавить review_labels.REVIEW_CHANGES в то
же условие, причина возврата отличается в тексте ("метка
review:changes-requested" против "метка ai:changes-requested"), чтобы
дальнейшее ветвление по бюджету видело оба гейта, как и rework_cycle_count.
Приёмка первой правки: тест на мутации - снять добавленную ветку ->
тест на fixture с PR, несущим только review:changes-requested (без
ai:changes-requested), краснеет (PR не признаётся нездоровым); вернуть -
зеленеет. Проверить перед реализацией текущий номер строки (scheduler.py
меняется параллельно другими PR - #248/#366/#358 на момент этого change
трогают другие функции того же файла, но номера строк смещаются от любого
слияния).

Правка вторая: unhealthy_pulls ветвится - причина
"вердикт ревью" (не красный чек) И rework_cycle_count >= REWORK_BUDGET ->
новая функция route_to_needs_spec (design.md п.4: снять assignee, поставить
needs-spec, закрыть PR с комментарием, оставить комментарий-разбор в issue,
вызвать pulse_guard.escalate тем же идемпотентным приёмом, что
stale_ready_pulls/#269 - design.md п.4, действие 5).
Причина "красный чек" ИЛИ rework_cycle_count < REWORK_BUDGET -> прежнее
поведение unhealthy_pulls не меняется. Приёмка: тест на мутации - снять
ветвление (route_to_needs_spec никогда не вызывается) -> тест, доказывающий
переход в needs-spec на fixture с 5 циклами, краснеет; вернуть - зеленеет;
отдельный тест на мутации для вызова escalate (снять вызов -> тест,
проверяющий факт вызова/маркер в WATCHDOG_ISSUE на fixture, краснеет).

Смежность с #201 (stall-detector, открыт как PR #248 на момент этого
change): stall_detector строит отпечаток из строк отчёта unhealthy_pulls
(`check:red:<имя>`, комментарий с сайта). Новая причина "метка
review:changes-requested" и новый маршрут needs-spec - новый вид строки
отчёта; проверить при реализации, не ломает ли это существующий разбор
отпечатков stall_detector (не блокирует эту задачу, но исполнитель обязан
проверить, а не предположить совместимость).

## 3. free_task.py: исключение needs-spec/blocked + приоритет доводки

Исполнитель: воркер/агент. Правка: free_candidates исключает issues с
меткой needs-spec ИЛИ blocked (design.md п.5, закрытие класса для
существующей blocked - не только новой needs-spec); сортировка - сначала
группа "есть declared_pr_for_task" (по номеру issue), затем "нет PR" (по
номеру issue). ОБЯЗАТЕЛЬНО тем же PR: scripts/worker/task.sh:130
(`gh issue list --json number,assignees,title`) добавляет `labels` в
список полей - иначе free_candidates получает issues без ключа `labels` и
фильтр молча не будет работать в проде при зелёных тестах на fixture
(proposal.md, Impacted domains). Приёмка: тест test_free_task.py
расширяется тремя случаями (needs-spec исключена, blocked исключена,
задача с открытым PR без исполнителя выбирается раньше задачи с меньшим
номером без PR) - мутация каждого доказана (снять фильтр/сортировку ->
тест красный); плюс проверка, что task.sh реально передаёт `labels` в
JSON, потребляемый free_task.py (grep/статическая проверка полей `--json`
в CI, не только юнит-тест на fixture).

## 4. Выход из needs-spec: гвардия маркера

Исполнитель: воркер/агент. Решить конкретную форму гвардии по итогам
design.md п.8 (третий пункт - неопределённость архитектуры проверки: реестр
меток vs. отдельный инвариант последовательности событий) и реализовать.
Минимум: скрипт/тест, который на реальном issue (или fixture с временной
линией событий) отличает "needs-spec снята с маркером [needs-spec: снято]"
от "needs-spec снята без маркера" и красит второй случай. Приёмка: два
fixture (с маркером, без) дают разные вердикты гвардии.
