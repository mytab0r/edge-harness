# design.md: task-rework-loop

## 1. Состояния и переходы

Ни у задачи (GitHub Issue), ни у PR нет поля "состояние" - оно всегда
вычисляется из комбинации issue.state, issue.assignees, issue.labels, факта
и состояния открытого PR (labels, mergeable_state). Таблица ниже - это
наблюдаемое условие для каждого имени состояния, не новое поле в базе
данных.

| Состояние | Наблюдаемое условие | Кто выполняет переход | Ветка | Сессия dsh-edge (морда) |
|---|---|---|---|---|
| ready | issue open, label task, assignees пуст, needs-spec и blocked отсутствуют, нет открытого PR, объявляющего задачу (task_ref.declared_tasks) | free_task.oldest_free выбирает; воркер/человек берёт assign | нет | нет |
| in-progress | issue open, assignee назначен, PR ещё не открыт | scripts/worker/task.sh, шаг DSH headless | agent/N-slug, создана scripts/git/task-branch | создаётся dsh_edge_session_begin, id harness-N |
| in-review | issue open (assignee может быть снят - см. rework(n)), открыт PR, объявляющий задачу, PR не unhealthy (нет ai:changes-requested/review:changes-requested, нет красных обязательных чеков) | scheduler.py: merge_queue ждёт review:ok И ai:ok | та же ветка | та же сессия harness-N (id идемпотентен, не пересоздаётся) |
| rework(n) | PR unhealthy (ai:changes-requested ИЛИ review:changes-requested ИЛИ красный обязательный чек); n = число вердиктов "нужны правки" по этому PR с момента его открытия | Пока моложе UNHEALTHY_PR_AFTER_MINUTES: агент того же запуска правит сам. После порога: unhealthy_pulls снимает исполнителя (см. п.2 ниже - новое ветвление по бюджету) | та же ветка (после #247 подхватывается воркером через declared-pr, git checkout -B той же ветки) | та же сессия harness-N |
| needs-spec | issue open, assignees пуст, label needs-spec, PR (если был) закрыт без слияния с комментарием-разбором | scheduler.py: новая функция route_to_needs_spec (см. п.2), срабатывает когда n больше или равно REWORK_BUDGET | ветка не удаляется (историческая), новая работа - новый PR | сессия harness-N не трогается (архив не делается - задача не done) |
| waiting | issue open, label blocked (существующая метка) ИЛИ тело задачи содержит строку "Зависимости: #M" на открытую задачу (существующий механизм PROTOCOL.md) | Воркер (эскалация blocked) или автор (Зависимости) | не определено (может не быть ветки вовсе) | не определено |
| verifying | PR слит (после review:ok И ai:ok), issue open, ждёт пост-мерж проверки (существующее поведение after_merge - комментарий-напоминание) | Существующий task-closure-after-proof, не меняется | ветка удаляется по факту слияния (стандартное поведение GitHub, не подтверждено дословно) | архивируется scheduler.archive_runner_sessions после слияния (#119) |
| done | issue closed исполнителем с уликами пост-мерж проверки | Исполнитель (task-closure-after-proof) | нет | заархивирована |
| dropped (не вводится этим change, см. #243) | issue closed без слияния (устарела/отклонена/дубликат) | Владелец/аналитик вручную, таксономия - #243 | нет | нет |

Что нового вводит этот change: переход rework(n) -> needs-spec (вместо
rework(n) -> ready по кругу без ограничений), метка needs-spec, правило
исключения needs-spec/blocked из free_task, переход needs-spec -> ready.
Остальные строки таблицы - существующее поведение, приведено для полноты
картины (иначе таблица нечитаема как цепочка).

Оговорка к строкам in-review/rework(n) (см. п.2 ниже, "известный разрыв"):
наблюдаемое условие говорит "ai:changes-requested ИЛИ
review:changes-requested", но переход rework(n) -> needs-spec написан
поверх unhealthy_pulls, чей pr_is_unhealthy (scheduler.py:1052-1064) сегодня
возвращает причину только по ai:changes-requested и красным обязательным
чекам - review:changes-requested не проверяет. Таблица описывает
наблюдаемое УСЛОВИЕ (по факту меток на PR), а не гарантирует, что каждое
из них сегодня приводит к фактическому переходу - сверяй с п.2 при
реализации tasks.md п.2, не с этой таблицей.

## 2. Бюджет реворка - где считать и где хранить порог

Что считаем. rework_cycle_count(repo, pr_number) - число событий timeline с
event равно labeled и label.name в списке [review:changes-requested,
ai:changes-requested] для конкретного PR. Источник - GitHub timeline API,
уже используемый паттерн в scheduler.py (last_review_ok_labeled_at читает
тот же endpoint). Дополнительного маркера-комментария заводить не нужно:
GitHub уже хранит эту историю нативно, комментарий-счётчик (как
AI_REVIEW_RETRY_MARKER) был бы вторым местом правды без надобности.

Почему не красные обязательные чеки. pr_is_unhealthy() сегодня объединяет
две причины (метка ai:changes-requested и красные проверки) в один return.
Бюджет реворка считает только вердикты ревью (оба гейта), не красные чеки:
красный чек может быть флаки-тестом или инфраструктурным сбоем CI, не
сигналом "требование неясно". Смешивание причин занизило бы доверие к
порогу - PR с гоняющимся flaky-тестом получил бы штраф, не относящийся к
качеству постановки задачи. unhealthy_pulls продолжает возвращать такую
задачу в пул по кругу без бюджета (существующее поведение не меняется для
этой ветки причины); бюджет применяется только когда причина - вердикт
ревью.

Почему сброс не нужен, а жизнь счётчика - на один PR. В отличие от
count_consecutive_failures в pulse_guard.py (который считает подряд идущие
красные прогоны workflow и сбрасывается первым success, потому что цикл
продолжает идти после успеха), здесь успех (оба вердикта зелёные) завершает
цикл слиянием - сбрасывать нечего, цикл не продолжается после успеха. Если
задача уходит в needs-spec и возвращается, работа начинается с нового PR
(см. п.4 "Закрытие PR" ниже) - у нового PR своя, чистая история timeline,
значит счётчик естественно "сбрасывается" по факту нового номера PR, без
явного кода сброса. Это решение объявлено, а не подразумевается: не
переиспользуем старый закрытый PR через reopen именно потому, что reopen
сохранил бы старую историю label-событий, и rework_cycle_count немедленно
снова превысил бы бюджет для того же PR-номера.

Порог. Новая константа в scripts/orchestra/pulse_guard.py (то же место, где
уже живут UNHEALTHY_PR_AFTER_MINUTES, AI_REVIEW_MAX_ATTEMPTS - одно место
правды для порогов конвейера):

```python
# Круги "требуются правки" (review:changes-requested + ai:changes-requested
# по timeline PR) на ОДИН PR, после которых задача уходит в needs-spec
# вместо возврата в пул на ещё один заход. Порог измерен 2026-09-03
# (openspec/changes/task-rework-loop/proposal.md, раздел "Посылка каркаса"):
# среди 17 PR, слитых за предыдущие сутки, максимум кругов реворка - 4;
# среди зависших без движения к зелёному вердикту - минимум 8. Порог
# поставлен на 1 круг выше максимума успешного слияния, с запасом до
# минимума зависшего (5 меньше 8) - НАЧАЛЬНОЕ значение, n=28 мало для точной
# калибровки (см. "Метрики" ниже, план уточнения).
REWORK_BUDGET = 5
```

## 3. Развилка: как продолжается реворк - варианты и цена

(а) Полное резюме DSH-агента. ctx.agents.resume с resumeSessionId
восстанавливает разговор из session.jsonl.zstd на диске
(DSH_HOME/sessions/...). Раннер GitHub Actions - эфемерная ВМ: диск
уничтожается между job'ами, а persistence-слой (packages/bundle/base,
cordis.patch.yml) пишет именно на локальный DSH_HOME. Ни worker.yml, ни
scripts/lib/dsh-ci.sh, ни scripts/lib/dsh-edge-session.sh не восстанавливают
DSH_HOME/sessions с внешнего носителя (нет actions/cache, нет
actions/upload-artifact, нет синка в R2/git - проверено grep по scripts/ и
.github/workflows/worker.yml). Чтобы (а) заработал, пришлось бы строить
новую инфраструктуру: сохранение session.jsonl.zstd после каждого запуска
(куда - artifact, R2, git LFS) и восстановление перед следующим. Это
отдельный кусок работы сопоставимого размера с #119 (сессии раннера в
морде), не текущего change.

(б) Возврат в общий пул, новый воркер начинает с нуля. Было текущим
(багованным) поведением до PR #247: free_task исключал задачи с открытым
PR, значит "начать с нуля" на практике означало открыть второй PR на ту же
задачу - contract_check.py такое отклоняет, поэтому реальный итог был
"задача недостижима". После #247 такой сценарий больше физически не
возникает: свободная задача с открытым PR теперь ведёт к чекауту
существующей ветки, не к новой. Вариант (б) в чистом виде (новая ветка,
игнорируя старую работу) сейчас невозможен по построению #247 - его не
нужно отдельно запрещать, разработка это уже сделала.

(в) Гибрид - выбран. Ветка продолжается (#247: git fetch + git checkout -B
той же ветки), морда-сессия продолжается (session.create с sessionId
harness-N идемпотентен - session.rename не создаёт новую запись, просто
переименовывает существующую, dsh-edge-session.sh:112-121), а DSH-агент
стартует свежим one-shot вызовом headless с промптом, явно называющим номер
PR и требующим прочитать последний вердикт (task.sh уже это делает после
#247: route_pr_step велит прочитать gh pr view CONTINUE_PR_NUMBER
--comments и последний вердикт, исправить по нему и запушить в ту же
ветку).

Почему (в), а не (а). Дело не в предпочтении, а в том, что (а) технически
недоступен без новой инфраструктуры (см. выше - факт, не выбор).
Если/когда персистентность сессий между job'ами появится (предпосылка:
значимая доля рабочих сессий регулярно упирается в лимит контекста даже при
свежем брифе - см. "Условие пересмотра" ниже), пункт (а) стоит переоценить.

Условие пересмотра. Если после внедрения бюджета окажется, что доля кругов
rework(n) с n от 2 и выше систематически проваливает review повторно с теми
же находками (агент "забывает" контекст между запусками сильнее, чем
экономит бриф) - это сигнал, что "свежий бриф" недостаточен и нужен вариант
(а). Замер: доля PR, где повторный вердикт ai:changes-requested указывает
на ту же находку, что и предыдущий (сравнение текста комментариев
ai-review) - не собирается сегодня, добавить при появлении признаков
проблемы.

Явно про "не гадать" по вопросу владельца - возобновлять переполненную
сессию или начинать новую с кратким брифом. Ответ - не выбор предпочтения,
а факт устройства системы: возобновлять сегодня нечего (состояние агента не
пережило конец предыдущего процесса), поэтому "начать новую с кратким
брифом" - единственный вариант, который вообще существует. Вопрос "полезно
ли возобновлять переполненную сессию" станет актуальным только если/когда
появится инфраструктура (а).

## 4. needs-spec: вход, выход, закрытие PR

Вход (scheduler.py, точка врезки - unhealthy_pulls, ветвление ПЕРЕД
существующим unassign). Условие: причина нездоровья - вердикт ревью (не
красный чек, см. п.2), rework_cycle_count(pr) >= REWORK_BUDGET. Действия
одной транзакцией отчёта (как и остальные шаги unhealthy_pulls):
1. Снять assignee с issue (как и сегодня).
2. Поставить label needs-spec на issue.
3. Комментарий в issue: перечисляет ВСЕ вердикты "нужны правки" по этому PR
   (номер круга, дата, ссылка на комментарий-вердикт), явно называет "бюджет
   REWORK_BUDGET исчерпан", и явно ставит вопрос аналитику: что неясно в
   формулировке задачи, какой блокер держит её, какой ресёрч нужен - без
   ответа на этот вопрос задача не может выйти из needs-spec (см. "Выход"
   ниже). Это и есть проверяемый признак из требования владельца п.4 - не
   "кто-то посмотрел", а факт: список находок, которые нужно разобрать,
   зафиксирован текстом.
4. Закрыть PR (gh api -X PATCH .../pulls/{n} -f state=closed) с комментарием
   в PR: "закрыт - бюджет реворка исчерпан (rework_cycle_count=N), задача
   #M ушла в needs-spec, ветка сохранена (не удалена), продолжение - новый
   PR после уточнения". Ветка НЕ удаляется автоматически - её удаление не
   вызывается этим кодом (см. "Риски" в proposal.md - не подтверждено
   дословно по документации, что закрытие PR без явного DELETE
   /git/refs/... само по себе не трогает ветку, но нет оснований для
   другого поведения).
5. Эскалация владельцу: `pulse_guard.escalate(repo, WATCHDOG_ISSUE, text)` -
   тот же канал и тот же приём идемпотентности (маркер с номером задачи в
   тексте, проверка `issue_marker_times` перед повторной посылкой), что уже
   использует `stale_ready_pulls` (issue #269, scheduler.py:1164-1211) для
   другого инварианта "тормоз без видимого газа". Без этого шага needs-spec
   был бы обнаружим только тем, кто явно листает issues с этой меткой -
   комментарий в issue (п.3) фиксирует факт, но не толкает уведомление
   наружу, а бюджет реворка, в отличие от долго висящего needs-spec
   (см. "Метрики" п.2 ниже), должен быть виден владельцу СРАЗУ в момент
   исчерпания, не только когда кто-то спустя недели заметит накопление.

Почему закрываем PR, а не оставляем висеть. Ровно жалоба владельца из
исходной постановки задачи (#243: "#164 регрессивен и не может быть слит
без переработки, но и не закрыт") - открытый PR, который никогда не попадёт
в очередь слияния, потому что его же правки к этому не ведут, - это
подвешенное состояние без объявленного выхода, то самое "тормоз без газа"
(#207), применённое к PR. Закрытие - честная запись факта: "эта попытка
исполнения не доехала до готовности, code остался в git-истории, работа
продолжится ПОСЛЕ уточнения требования, не поверх этой же попытки".

Выход из needs-spec (аналитик - человек или агент с полномочием судить,
не оркестратор: правило "агент только там, где нужно суждение, которого
нет в данных", то же, что в #243 и #224). Условие ПРОВЕРЯЕМО:
1. Комментарий в issue с маркером [needs-spec: снято] и текстом, который
   называет ОДНО из: обновлённая формулировка критерия готовности (текст
   правки), явно названный блокер со ссылкой (issue/PR/внешняя система),
   ссылка на ресёрч (docs/research/... или новый файл), который снимает
   неясность.
2. Метка needs-spec снята.
3. (Часть выхода, не отдельный шаг) Приоритет пересмотрен - см. "Границы с
   #224" в proposal.md: до появления автоматического приоритезатора это
   ручная правка любого имеющегося поля приоритета (или явная строка в
   комментарии "приоритет: <значение>, потому что <причина>" - до тех пор,
   пока #224 не даст единый механизм).
Оба пункта 1 и 2 обязательны одновременно - гвардия test_label_registry.py
(расширяется, см. tasks.md) проверяет, что снятие needs-spec без маркера в
истории комментариев считается нарушением реестра меток (по аналогии с
существующей проверкой "у каждой метки объявлен газ", только здесь газ
дополнительно верифицируется по факту использования, не только по
документации - это расширение существующей гвардии, не новый механизм).

После выхода: issue возвращается в ready (метка needs-spec снята,
assignees пуст) - free_task.oldest_free увидит её на общих основаниях.
Ветка старого PR по-прежнему существует в remote, но НЕ переиспользуется
через reopen (см. п.2, почему) - новый заход открывает новый PR (новая
ветка agent/N-slug2 либо та же ветка под новым PR, если ветка не была
удалена и не разошлась с main до конфликта - решение на усмотрение
исполнителя нового захода, не фиксируется этим design).

## 5. free_task.py: исключение needs-spec/blocked, приоритет доводки

Сегодня (после #247/#279) free_task.free_candidates фильтрует ТОЛЬКО по
issue.assignees - пустой список ассайни делает issue кандидатом,
независимо от меток. Для существующей метки blocked это НЕ живая дыра в
`reap_stale`/`unhealthy_pulls`: `scheduler.py::_issue_is_blocked` уже
используется как ранний выход в обеих функциях (reap_stale:236,
unhealthy_pulls:1072) - blocked-задача не теряет назначение по STALE_HOURS
и не попадает под бюджет реворка, пока метка стоит. Реальный пробой класса -
именно free_task.py: единственное место выбора свободной задачи, где фильтр по
меткам ОТСУТСТВУЕТ целиком. Этот change закрывает класс "метка есть, а
путь выбора её не проверяет" применительно к выбору задачи одним
изменением одного файла:

free_candidates(issues) исключает issue, если issue.labels содержит
needs-spec ИЛИ blocked - независимо от issue.assignees.

Приоритет доводки. free_task.oldest_free сегодня сортирует по номеру issue
(старейшая первой) без различия "свежая задача" / "задача на доводку
существующего PR". Требование владельца - "толкать вперёд, не сбрасывать в
общий беклог" - означает, что задаче, у которой уже есть открытый PR без
исполнителя (rework(n), ждёт продолжения), нужен приоритет НАД совершенно
новой задачей, даже если у новой задачи номер меньше: недоделанная работа
дешевле для завершения, чем начатая с нуля, и висит она с уже потраченным
контекстом ревьюеров. Правило: free_candidates сортирует СНАЧАЛА по
наличию declared_pr_for_task (есть открытый PR - выше), ЗАТЕМ по номеру
issue внутри каждой группы. Это НЕ полноценная приоритезация (#224 - не
здесь), а единственный tie-break, прямо вытекающий из принципа "доделать
раньше, чем начать" - минимальное правило, не требующее графа блокировок.

## 6. Метрики

Для каждой: определение, источник данных СЕЙЧАС (без нового
инструментирования, где возможно), что решается по значению.

**1. Кругов реворка на PR (опережающий показатель качества постановки
задач).** Определение и источник - rework_cycle_count из п.2 (GitHub
timeline, событие labeled). Данные есть уже сегодня для каждого PR, ничего
доинструментировать не нужно. Решение: значение >= REWORK_BUDGET на
конкретном PR - триггер needs-spec (п.4); СРЕДНЕЕ/МЕДИАНА по всем закрытым
PR за период - сигнал пересмотреть REWORK_BUDGET (см. план уточнения ниже).
Фактический замер за последние сутки приведён в proposal.md ("Посылка
каркаса"): среди 17 слитых PR медиана - 1 круг, максимум - 4; среди 11
открытых - есть 4 PR с 8-10 кругами.

**2. Время в каждом состоянии.** Источник частично есть: issue/PR timeline
даёт метки времени переходов через события assigned/unassigned/labeled/
closed/merged (пример уже используется в scheduler.py:
last_review_ok_labeled_at, reap_stale читает assigned-события). Из этого
вычислимо время ready->in-progress (assigned), in-progress->in-review
(создание PR - created_at PR), rework(n)-длительность (между labeled
ai:changes-requested и следующим review:ok/слиянием). НЕ вычислимо без
доинструментирования: время needs-spec->ready ДО этого change, потому что
состояния needs-spec не существовало - первые данные появятся после
внедрения (то же ограничение уже названо в proposal.md, "Риски"). Решение
по значению: длинный хвост в rework(n) относительно медианы - кандидат на
пересмотр UNHEALTHY_PR_AFTER_MINUTES (120 мин, отдельный порог, не
REWORK_BUDGET); долгое needs-spec (недели без маркера снятия) -
эскалация владельцу по аналогии с существующим WATCHDOG_ISSUE/#120.

**3. Доля задач, дошедших до needs-spec (оценка качества формулировок).**
Определение: count(issues с меткой needs-spec когда-либо стоявшей) /
count(issues, взятых в работу за период). Источник ПОСЛЕ внедрения -
собственный след механизма (комментарии-маркеры + метка); ДО внедрения
данных нет (needs-spec не существует) - метрика стартует с нуля, это
честно названо в proposal.md "Риски". Решение: доля растёт выше некоторого
порога (кандидат: 20-30% активных задач одновременно в needs-spec,
округление условно - без данных точный порог не поставить, п.1 "не
выдумывать" применяется и здесь) - сигнал не "поднять REWORK_BUDGET" (это
лечило бы симптом), а "формулировки задач в пуле систематически хуже
пороговых" - работа для аналитика на входе (шаблон задачи, критерий
готовности), не для этого механизма.

**4. Доля переоткрытых после done (преждевременное закрытие).** Источник
есть сегодня: GitHub issue timeline, событие reopened (issue.state history)
- запрос по всем закрытым issues репозитория с фильтром label=task,
event=reopened. Не собрано в рамках этого change (не входит в замер
"кругов реворка на PR" из требования задачи), но технически доступно тем же
инструментом (gh api .../issues/N/timeline), без нового кода. Решение:
ненулевая доля - сигнал, что критерий готовности в задачах формулируется
нестрого или пост-мерж проверка (task-closure-after-proof) делается
формально - это уже вне рамок этого change (task-closure-after-proof
existing), но данные для решения доступны тем же способом.

**5. Слияний в сутки (пропускная способность).** Источник есть сегодня:
GitHub REST /repos/.../pulls?state=closed, фильтр merged_at за окно суток
(тот же вызов, которым в этом change собран список 17 слитых PR за
предыдущие сутки). Решение: пропускная способность падает при растущей доле
needs-spec (метрика 3) - ожидаемо и не тревожно (needs-spec отфильтровывает
неготовую к исполнению работу ДО того, как она жжёт ревью-циклы); падает
БЕЗ роста доли needs-spec - сигнал другого класса проблем (конвейер,
воркеры, инфраструктура - не эта задача).

**План уточнения REWORK_BUDGET (честно, n=28 мало).** После накопления
данных за 2-4 недели работы под новым механизмом: пересчитать распределение
кругов реворка отдельно для PR, дошедших до слияния, и отдельно для тех,
что ушли в needs-spec. Если медиана успешных сблизится с REWORK_BUDGET
(сегодня разрыв двукратный: 4 против 8) - поднять порог; если ни один
успешный PR не подбирается к порогу снизу - можно осторожно понижать
(экономит циклы ревью на явно тонущих PR раньше).

## 8. Открытые вопросы / не подтверждено (сверх перечисленного в proposal.md)

- Кто физически выполняет разовую миграцию п.7 - оркестратор новым
  workflow_dispatch-триггером, разовый скрипт, или ручной проход владельца/
  аналитика по четырём PR. Не решено этим design - решение в tasks.md как
  отдельный пункт с явным исполнителем.
- Нужна ли метка needs-spec ТАКЖЕ на PR (не только на issue) для видимости
  в списке PR - решение п.4 ставит только комментарий на PR (PR закрывается,
  открытых PR с needs-spec не остаётся) - если практика покажет, что
  закрытые PR с этой историей плохо ищутся, можно добавить метку на PR
  как чисто косметическое улучшение поиска, без изменения логики.
- test_label_registry.py сегодня проверяет только НАЛИЧИЕ строки в реестре
  для каждой встречающейся в коде метки (соответствие collect_labels.py
  таблице LABELS.md) - расширение "маркер снятия обязателен" (п.4, выход из
  needs-spec) требует НОВОЙ проверки другого рода (не реестр меток, а
  инвариант последовательности событий на конкретной issue) - возможно,
  это отдельная гвардия, не расширение существующей. Уточнить в tasks.md
  при реализации, не решать здесь архитектурно заранее.
