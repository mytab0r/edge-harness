# Дельта-спека: журнал (journal-tasks-hands) - конечный цикл реворка

Опирается на существующие пункты раздела "Конвейер (оркестратор)" (п.15-18)
и "Автономный воркер (конвейер пула)" (п.26-29) - см. design.md,
task-rework-loop, за подробным разбором наблюдаемых условий по состояниям.
Предполагает слитым PR #247 (продолжение ветки при выборе задачи с открытым
PR без исполнителя) - без него ниженазванные требования не имеют почвы для
исполнения.

## ADDED: Бюджет кругов реворка на PR

Требование: у количества кругов реворка на одном PR есть верхняя граница
REWORK_BUDGET (константа scripts/orchestra/pulse_guard.py, рядом с прочими
порогами конвейера - design.md п.2 обосновывает значение 5 замером).
Круг реворка - событие timeline PR event=labeled с именем
review:changes-requested или ai:changes-requested. Красные обязательные
чеки в счётчик НЕ входят (design.md п.2 - другой класс причины, флаки-тест
не равен неясному требованию).

Сценарий: PR держит ai:changes-requested дольше UNHEALTHY_PR_AFTER_MINUTES
(120 мин) четвёртый раз подряд (rework_cycle_count=4, REWORK_BUDGET=5) ->
существующее поведение unhealthy_pulls не меняется: исполнитель снимается,
задача доступна на доводку (после #247 - воркер продолжает ту же ветку).

Сценарий: тот же PR получает пятый ai:changes-requested
(rework_cycle_count=5=REWORK_BUDGET) -> вместо возврата в пул задача уходит
в needs-spec (см. следующее требование), PR закрывается.

## ADDED: Состояние needs-spec

Требование: задача (issue с меткой task) получает метку needs-spec, когда
rework_cycle_count её текущего PR достигает REWORK_BUDGET. В состоянии
needs-spec: assignee снят, PR, приведший к needs-spec, закрыт (не слит) с
комментарием, объясняющим причину и перечисляющим все круги реворка,
issue получает комментарий с тем же перечнем и явным вопросом аналитику
(design.md п.4).

Требование: задача с меткой needs-spec ИСКЛЮЧЕНА из автоматического выбора
воркером (scripts/lib/free_task.py::free_candidates), независимо от
состояния issue.assignees. То же правило распространяется на существующую
метку blocked - закрытие класса "метка есть, а фильтр выбора её не
проверяет", не только нового случая (design.md п.5).

Требование: выход из needs-spec обязателен через ДВА одновременных условия
- снятие метки needs-spec И комментарий в issue с маркером
[needs-spec: снято], называющий одно из: обновлённую формулировку критерия
готовности, явно названный блокер со ссылкой, ссылку на ресёрч, снимающий
неясность (design.md п.4). Один из двух признаков без другого не считается
выходом.

Сценарий: аналитик уточняет формулировку задачи, снимает needs-spec, но не
оставляет комментарий с маркером [needs-spec: снято] -> гвардия реестра
меток (расширение test_label_registry.py) считает выход неполным, задача
остаётся видна как незакрытый needs-spec-эпизод в отчёте (см. tasks.md для
конкретной реализации проверки).

Сценарий: задача выходит из needs-spec корректно (оба условия выполнены) ->
issue возвращается в пул на общих основаниях (free_task.oldest_free видит
её кандидатом), работа продолжается НОВЫМ PR (не reopen старого, закрытого
при входе в needs-spec) - design.md п.2 объясняет, почему reopen не
используется (унаследованная история label-событий немедленно вернула бы
rework_cycle_count к порогу).

## ADDED: Приоритет доводки над новым стартом

Требование: при выборе свободной задачи free_task.oldest_free
приоритизирует задачи, у которых уже есть открытый PR без исполнителя
(продолжение rework(n) через #247), НАД задачами без какого-либо PR - даже
если у последних меньше номер issue. Внутри каждой из двух групп сортировка
остаётся по номеру issue (старейшая первой).

Сценарий: в пуле одновременно свободны задача #50 (новая, PR не открывался)
и задача #12 (открыт PR без исполнителя - вернулась из rework) -> воркер
выбирает #12 первой, несмотря на меньший номер #12 против #50 (оба условия
номерные - тай-брейк именно по наличию PR, не по номеру).

## MODIFIED: Автономный воркер (конвейер пула), п.26

Существующая формулировка п.26 ("свободная задача... без открытого PR на
неё") противоречит поведению после PR #247 (свободная задача = нет
assignee, открытый PR не исключает) - это расхождение существует независимо
от данного change (белое пятно на момент слияния #247, не создано здесь) и
должно быть закрыто самим PR #247 или отдельной правкой спеки. Данный
change ДОБАВЛЯЕТ к формулировке: свободная задача дополнительно не должна
нести метки needs-spec или blocked (см. "Состояние needs-spec" выше) - это
уточнение актуально независимо от того, когда именно текст п.26 будет
приведён в соответствие с #247.
