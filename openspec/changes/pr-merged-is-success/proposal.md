# pr-merged-is-success: слитый PR — успех воркера, не провал (#539)

Задача: #539 (перенос работы PR #415 — задачу #413 закрыл побочный эффект
строки-примера в теле коммита `03bf142f` squash-слияния PR #429 через 2
секунды после мержа, не приёмка и не человек; содержание не решено в main,
см. #750). Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`scripts/worker/task.sh` проверял успех прогона ТОЛЬКО открытым PR по ветке
задачи (`gh pr list --state open`). Если DSH за один вызов открывал PR и сам
же доводил его до слияния (полный автономный цикл: review:ok + ai:ok +
merge), проверка не находила PR именно потому, что работа доведена лучше
ожидаемого, и воркер печатал ложный провал «dsh завершился с кодом 0 без
открытого PR» — живой случай, прогон 34002439672, задача #170, PR #402.

## Что делается

- `scripts/lib/pr_outcome.py` — единственное место правды на различение
  исходов PR ветки задачи по `gh pr list --head <branch> --state all --json
  number,state,additions,deletions,changedFiles,url`: «нет вообще» и «закрыт
  без слияния» и «открыт без диффа» — провал (fail loud, тот же промпт мог
  быть исполнен мимо PR); «открыт с диффом» и «слит» — оба успех.
  `changedFiles` в запросе и в classify() — находка ревью PR #415: PR,
  меняющий только бинарники или делающий чистое переименование, имеет
  нулевой текстовый дифф (`additions+deletions==0`), но реальная работа
  есть — «пусто» только когда `changedFiles` тоже 0.
- `scripts/worker/task.sh` печатает «PR $verb: $pr_url — job зелёный», где
  `verb` — «открыт» или «слит» (не жёстко «открыт», как раньше).
- Комментарий в задаче и Telegram-отчёт воркера (см.
  `telegram-pr-open-merged-reports`, #170) используют ту же переменную
  `verb` — формулировка «PR открыт — #M…» дополнена веткой «PR слит — #M…»
  для случая, когда воркер застал уже смёрженный PR.

## Проверено

- `python -m pytest scripts/lib/test_pr_outcome.py -q` — 13 тестов зелёные
  (Docker Linux, т.к. Windows-хост не резолвит extension-less shebang-скрипт
  `gh` из PATH в дочернем процессе `subprocess.run` — окружение, не дефект
  этого PR); мутация `_is_empty` (снял проверку `changed_files == 0`)
  красит гвардию (1 упал).
- `bash scripts/lib/test/dsh-clients.smoke.sh` — полностью зелёный
  (`SMOKE: все клиенты целы — гвардия класса зелёная`), в т.ч. сценарий
  `worker-auto` (happy path). Находка ревью PR #415 (заглушка `gh pr list`
  не матчилась на реальную сигнатуру task.sh без `changedFiles` в паттерне и
  canned-ответе) — почин­ена: мутация (откат `changedFiles` в паттерне и
  payload) воспроизводит ровно тот ложный провал, что описал ревьюер
  (`Воркер не справился: dsh завершился с кодом 0 без PR по ветке
  agent/123-smoke`), фикс красит гвардию зелёной обратно.

## Что вне рамок

- Случай #89 (ветка детерминирована из номера и заголовка задачи, PR по
  той же ветке может принадлежать другой, более старой попытке) — критерий
  «PR по ветке существует» превращает такой случай из ложного красного в
  ложный зелёный; отдельная находка, не блокирует это изменение (названа
  ревью, не устраняется здесь).
