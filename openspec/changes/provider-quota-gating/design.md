# Design: provider-quota-gating

## Носитель состояния

Кандидаты и почему не они:

1. **Файл в репозитории** (как `config/provider-usage.json`). Отвергнут:
   квота — это факт времени (пишется каждые несколько минут, когда цепочка
   бьётся об исчерпанные провайдеры), а не факт конфигурации. Каждая запись
   — коммит, каждый коммит — новый прогон `repo-ci`/`ai-review`/`orchestra`
   (push на main триггерит их), реального контента для ревью нет — то же
   «сто холостых прогонов» из AGENTS.md «Не подтягивай ветку без
   содержательной причины», только источником стал бы сам механизм гейта.
2. **Durable Object / журнал харнеса** (см. AGENTS.md, «Мозг»). Отвергнут:
   DO этого репозитория обслуживает СОВСЕМ ДРУГОЙ Cloudflare Worker (морду
   dsh-edge / Harness), не GitHub Actions напрямую — писать туда из
   `scripts/orchestra/scheduler.py` означало бы новый HTTP-канал с новой
   авторизацией (`DSH_EDGE_ACCESS_KEY`) ради одного словаря из ≤10
   провайдеров, тогда как `gh variable set` уже есть, уже авторизован
   (`ORCHESTRA_PAT`) и уже читается ВСЕМИ тремя consumer'ами без единой
   новой зависимости (тот же путь, что `vars.DSH_PROVIDER_CHAIN`).
3. **Артефакт GitHub Actions** (upload-artifact/download-artifact между
   прогонами). Отвергнут: артефакты живут в рамках ОДНОГО workflow run
   (retention отдельный, но нет native способа «прочитать последний
   артефакт с любого прошлого прогона любого из трёх workflow» без
   дополнительного API-обхода Actions API на каждый запуск — дороже и
   медленнее, чем один `vars.*`, который Actions runtime уже инжектирует в
   контекст `${{ vars.* }}` бесплатно, без единого API-вызова).
4. **Репо-переменная `vars.DSH_PROVIDER_QUOTA_UNTIL`** (JSON
   `{provider_name: reset_iso}`) — **выбрано**. Обоснование:
   - Читается КОНТЕКСТОМ workflow (`${{ vars.DSH_PROVIDER_QUOTA_UNTIL }}`),
     без единого API-вызова и БЕЗ ТОКЕНА — тот же механизм, что уже несёт
     `vars.DSH_PROVIDER_CHAIN` в `ai-review.yml`/`worker.yml`/`hands.yml`
     (см. `.github/workflows/*.yml`, все три уже прокидывают
     `DSH_PROVIDER_CHAIN: ${{ vars.DSH_PROVIDER_CHAIN }}` в `env:`).
     Значит `ai-review.yml` (недоверенная зона, ШАГ БЕЗ GitHub-токена,
     #18) читает состояние БЕСПЛАТНО и не приобретает НИКАКОГО нового
     права — это ключевое отличие от альтернативы «сам DSH-шаг вызывает
     `gh api`», которая потребовала бы токен именно там, где его
     специально нет.
   - Запись — `gh variable set`/`gh api -X PATCH .../actions/variables/...`
     нужен только тому, кто МЕНЯЕТ значение: `GH_PIPELINE_PAT`
     (=`ORCHESTRA_PAT` в `orchestra.yml`) — широкий personal-scope PAT,
     уже используемый пульсом для меток/дispatch/update-branch. Ни
     `ai-review.yml`, ни `worker.yml`, ни `hands.yml` не получают новых
     прав — они попадали в свои job'ы, читая `vars.*`, ДО этого change и
     продолжают читать после.
   - Не растёт: словарь ограничен числом провайдеров цепочки (сегодня
     9 в `default-chain`), обновляется редко (раз на эпизод квоты), не
     задевает ни один известный лимит `vars` (48 KB на переменную — с
     запасом).

## Что читает, что пишет — граница доверия

```
┌──────────────────────────────┐        читает        ┌──────────────────────┐
│ ai-review.yml (БЕЗ токена)    │ ────────────────────▶ │                       │
│ worker.yml (GH_PIPELINE_PAT)  │ ────────────────────▶ │ vars.DSH_PROVIDER_    │
│ hands.yml (HANDS_TOKEN)       │ ────────────────────▶ │ QUOTA_UNTIL           │
└──────────────────────────────┘                        │ {provider: reset_iso} │
                                                          └───────────▲───────────┘
                                                                      │ пишет
                                                          ┌───────────┴───────────┐
                                                          │ orchestra.yml (пульс)  │
                                                          │ GH_PIPELINE_PAT        │
                                                          │ scheduler.py::         │
                                                          │ trigger_ai_review →    │
                                                          │ provider_quota_state.  │
                                                          │ save_quota_state       │
                                                          └───────────────────────┘
```

Все три consumer'а читают одинаково (контекст `vars.*` в YAML, ноль кода
на чтение — сама Actions runtime подставляет значение). Пишет только пульс.
`ai-review.yml` физически не может писать в эту переменную: у его
DSH-шага НЕТ ГИТХАБ-ТОКЕНА ВООБЩЕ (это его определение как недоверенной
зоны, #18) — записать `vars.*` можно только через `gh api`/REST с
токеном, имеющим `actions:write`; у шага «Ревью агентом» в `env:` нет ни
`GH_TOKEN`, ни `GITHUB_TOKEN` (проверено — см. `.github/workflows/ai-review.yml`,
секция «НЕдоверенный шаг: НИКАКОГО GitHub-токена в env»). Это не
дисциплина, а физика — токена нет, вызов `gh api` откажет с 401/403 до
того, как что-либо запишется. Гвардия (`test_provider_quota_state_guard.py`)
проверяет это по СТРУКТУРЕ (нет `gh variable set` ни в одном `.yml`, и
`save_quota_state` не вызывается за пределами `scripts/orchestra/**`) —
не только по факту отсутствия токена в текущей версии файла.

## Чтение: `dsh_run_with_provider_chain` (`scripts/lib/dsh-ci.sh`)

Новая функция `dsh_provider_quota_gate_skip(name, state_json)`:

```bash
dsh_provider_quota_gate_skip() { # name state_json -> 0=пропустить, 1=пробовать
  local name=$1 state_json=$2 reset_iso reset_epoch now_epoch
  DSH_QUOTA_GATE_RESET=""
  [ -n "$state_json" ] || return 1
  reset_iso=$(jq -r --arg n "$name" '.[$n] // empty' <<<"$state_json" 2>/dev/null) || return 1
  [ -n "$reset_iso" ] || return 1
  reset_epoch=$(date -u -d "$reset_iso" +%s 2>/dev/null) || { ::warning:: нераспознанная дата; return 1; }
  now_epoch=$(date -u +%s)
  [ "$now_epoch" -lt "$reset_epoch" ] && { DSH_QUOTA_GATE_RESET="$reset_iso"; return 0; }
  return 1
}
```

Вызывается в цикле `dsh_run_with_provider_chain` ПЕРЕД проверкой секрета/
подтверждённости модели (самый дешёвый гейт первым — не тратит `jq`-разбор
на провайдера, который всё равно пропущен). При срабатывании:
`i=$((i+1)); continue` — ТА ЖЕ форма, что уже применяют существующие
gate'ы (секрет не передан, модель не подтверждена, #737) — `DSH_CHAIN_TRIED`
несёт имя с пометкой `(пропущен: квота до <дата>)`, `DSH_CHAIN_RESET_HINT`
получает `name: reset_iso` — то же поле, которое уже использует
`ai_review.build_comment`/`scheduler.trigger_ai_review` для сообщения «кто
когда вернётся». Поскольку это `continue`, а не `stop=1`, цикл идёт
дальше — «все провайдеры исчерпаны» (`all_providers_exhausted`) по-прежнему
считается ТОЛЬКО когда `i >= count` (весь список пройден, включая
пропущенных по квоте) — тот же код, что уже существовал, гейт квоты не
меняет условие остановки.

Валидность JSON в `vars.DSH_PROVIDER_QUOTA_UNTIL` проверяется ОДИН раз в
начале `dsh_run_with_provider_chain` (не на каждой итерации): переменная
не задана — `state_json=""`, гейт не срабатывает НИКОГДА (обратная
совместимость — старое поведение для тех, кто ещё не завёл переменную);
задана, но не JSON-объект — `::warning::`, тот же fail-open (работоспособность
цепочки важнее гейта квоты — сломанное состояние не должно ронять прод).

## Алерт уже не гадает (проверено, не переписано с нуля)

Правило AGENTS.md «Алерт не гадает» уже соблюдено существующим кодом:
`DSH_RUN_FAILURE_REASON=all_providers_exhausted` устанавливается СТРОГО
когда цикл дошёл до конца списка (`i >= count`), не когда «первый
провайдер квотирован» — остальные провайдеры к этому моменту либо
ответили неуспехом сами, либо были пропущены гейтом (и это тоже полноценный
проход по списку, не досрочный обрыв). `scheduler.py::trigger_ai_review`
эскалирует по этой причине, называя МИНИМАЛЬНУЮ из всех известных дат
сброса (`min(reset_dates)`), а не дату первого по списку — это тоже уже
так (`parse_reset_hint_dates`/`min(reset_dates)`, #727). Единственное
усиление этим change: пропущенные ПО ПЕРСИСТЕНТНОМУ СОСТОЯНИЮ провайдеры
(без реальной попытки в этом прогоне) теперь тоже несут известную дату
сброса в `DSH_CHAIN_RESET_HINT` — раньше дата появлялась только если
провайдер был РЕАЛЬНО опрошен в ЭТОМ прогоне и вернул `reset at ...` в
своём ответе; после этого change дата видна и когда провайдер вообще не
трогался (пришла из состояния, а не из живого ответа).

## Запись: `scripts/orchestra/provider_quota_state.py`

Чистые функции (без сети — тестируются юнитами без моков gh):

- `QUOTA_VAR_NAME = "DSH_PROVIDER_QUOTA_UNTIL"` — одно место правды на имя
  переменной (читают `dsh-ci.sh` буквальным `vars.DSH_PROVIDER_QUOTA_UNTIL`
  в трёх workflow-файлах, пишет этот модуль — гвардия
  `test_provider_quota_state_guard.py` проверяет, что имя совпадает
  везде).
- `parse_reset_hint_pairs(reset_hint: str) -> dict[str, datetime]` —
  разбирает «Name: date; Name2: date2» (та же прод-форма, что уже парсит
  `scheduler.parse_reset_hint_dates`, обе формы дат: ISO и «YYYY-MM-DD
  HH:MM:SS» без зоны). **Единственное место, разбирающее эту строку** —
  `scheduler.parse_reset_hint_dates` теперь ДЕЛЕГИРУЕТ сюда
  (`list(parse_reset_hint_pairs(...).values())`), а не дублирует формат
  дат второй раз (класс «одно место правды», AGENTS.md).
- `merge_reset_hints(state, reset_hint, now) -> (new_state, changed)` —
  добавляет/обновляет записи с датой строго В БУДУЩЕМ (прошлые даты не
  пишутся — незачем захламлять состояние тем, что уже неактуально).
- `expire_stale(state, now) -> (new_state, expired_names)` — снимает
  записи, чей `reset_iso` уже прошёл ИЛИ не разбирается вовсе (мусор
  лучше снять, чем множить). Это и есть газ «срок прошёл» из AGENTS.md
  «Тормоз без газа».
- `load_quota_state(repo, gh_func) -> dict[str, str]` — `gh api
  repos/{repo}/actions/variables/{QUOTA_VAR_NAME}`; переменной нет (404)
  → `{}` (нормальное состояние «квот не помним», не ошибка); значение не
  JSON-объект → `RuntimeError` (это уже ошибка конфигурации, о ней надо
  знать, но она НЕ должна ронять `trigger_ai_review` целиком — вызывающий
  ловит и печатает наблюдение, не поднимает исключение выше).
- `save_quota_state(repo, state, gh_func)` — `PATCH`, при 404 (переменной
  ещё не существует) — `POST` создаёт её.

## Точка вызова: `scheduler.py::trigger_ai_review`

Пульс уже читает `reset-at`-факт из шапки последнего комментария
ai-review (`facts.get("reset-at", "")`, строка, где вычисляется
`reset_dates` — существующий код #727). Ровно там же, когда факт непуст,
вызывается `sync_provider_quota_state(repo, reset_hint, now)`:
загружает состояние, снимает протухшее, мержит новый факт, сохраняет
ЕСЛИ что-то изменилось (не на каждый тик — незачем плодить PATCH-вызовы,
когда состояние не поменялось). Наблюдение добавляется в общий список
`observations`, который пульс и так печатает в `GITHUB_STEP_SUMMARY`.

Почему именно здесь, а не отдельным проходом по всем открытым PR: это
единственное МЕСТО, где пульс УЖЕ фетчит и парсит `reset-at`-факт (не
новый сетевой вызов ради этого change) — тот самый довод владельца «у
пульса уже есть чтение логов прогонов и reset-хинты». Честная граница
(не расширяется в этом change, см. proposal.md «Out»): состояние
обновляется только из вердиктов ai-review, у которых уже гейт 1 пройден
и есть `ai:failed` — worker/hands читают ту же персистентную переменную
и от этого выигрывают (общая цепочка, общая квота одного и того же
аккаунта провайдера), но САМИ не пишут состояние; ai-review работает
чаще всех трёх каналов (на каждый push/PR), поэтому практически он же и
успевает зафиксировать `reset-at` первым.

## Гвардия и мутационное доказательство

1. **Смоук** (`scripts/lib/test/dsh-provider-chain.smoke.sh`, новый
   сценарий): `DSH_PROVIDER_QUOTA_UNTIL='{"PRIMARY":"<будущая дата>"}'`,
   `SMOKE_MODE_primary_model` НЕ устанавливается (дефолт "ok" — если бы
   гейт не сработал, PRIMARY ответил бы успехом) → ожидается
   `DSH_CHAIN_PROVIDER=SECONDARY`, `DSH_CHAIN_TRIED` содержит PRIMARY с
   пометкой «пропущен», реальный `dsh()`-вызов для PRIMARY не происходит.
   Мутация: закомментировать вызов `dsh_provider_quota_gate_skip` в цикле
   — сценарий покраснеет (`DSH_CHAIN_PROVIDER=PRIMARY`, не SECONDARY).
2. **Смоук, дата в прошлом**: тот же провайдер, `reset_iso` вчера →
   пробуется как обычно (доказывает, что гейт не держит вечно).
3. **Юнит-тесты** `scripts/orchestra/test_provider_quota_state.py` —
   `parse_reset_hint_pairs`/`merge_reset_hints`/`expire_stale` чистыми
   входами/выходами (без сети), плюс `load_quota_state`/`save_quota_state`
   с фейковым `gh_func`.
4. **`test_scheduler.py`** — новые тесты на `trigger_ai_review`, что
   PATCH уходит с правильным телом при новом `reset-at`, что протухшие
   записи снимаются, что при пустом `reset-at` переменная НЕ трогается
   вовсе (ноль сетевых вызовов на неё).
5. **Гвардия границы** `scripts/lib/test_provider_quota_state_guard.py` —
   ни один `.github/workflows/*.yml` не содержит `gh variable set
   DSH_PROVIDER_QUOTA_UNTIL`; `save_quota_state(` не вызывается за
   пределами `scripts/orchestra/**`.

## Не подтверждено

- Модель `glm-5` (запись `ZAI` в `config/provider-usage.json`) НЕ
  подтверждена живым запросом `/v1/models` с `ZAI_1_API_KEY` (класс #737)
  — у apply-агента нет доступа к значению секрета. Запись — безопасный
  no-op (`dsh_model_confirmed` её пропустит) до подтверждения; следующий
  шаг — владелец или агент с доступом к секрету повторяет
  `docs/runbooks/switch-llm-provider.md`, «Узнать точный id модели», и
  дописывает hash в `scripts/lib/confirmed-provider-models.json`.
- Лимит размера/частоты записи `vars.*` через REST API — не проверено
  живым прогоном для ЭТОГО конкретного использования (ожидается редкая
  запись, раз на эпизод квоты — не должно приблизиться к лимитам, но это
  предположение, не измерение).
- Успех-триггерное снятие записи (см. proposal.md «Out») — не покрыто:
  если провайдер восстановился РАНЬШЕ объявленной даты сброса, состояние
  всё равно продержит гейт до `reset_iso`. Не регрессия (раньше вообще не
  было персистентности), но не полное покрытие «провайдер снова успешен»
  из формулировки задачи — покрыта только часть «ИЛИ срок прошёл».
