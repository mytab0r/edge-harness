# Персистентное квота-осознанное гейтирование цепочки провайдеров

Задача: #857.

Design: [design.md](design.md).

## Summary

Чейн-раннер (`dsh_run_with_provider_chain`, `scripts/lib/dsh-ci.sh`) уже
переключает провайдеров по классу отказа (429/квота, HTTP_404,
EMPTY_RESPONSE, #727) — но состояние живёт только в памяти ОДНОГО
эфемерного job'а. Каждая новая джоба (ai-review/worker/hands) снова тратит
первую попытку на провайдера, чью квоту предыдущий прогон УЖЕ увидел
исчерпанной с известной датой сброса. Это предложение вводит персистентное
состояние квоты (репо-переменная `vars.DSH_PROVIDER_QUOTA_UNTIL`,
`{provider: reset_iso}`), которое чейн-раннер читает ДО попытки (пропускает
исчерпанного, не тратя вызов) и которое пишет только пульс оркестратора
(увидел `reset-at` в вердикте ai-review → записал; срок сброса прошёл →
снял запись). Заодно — переставить `GLM`(`glm-5.3-flash`) первым в
`config/provider-usage.json` (владелец: лучшее качество, самая долгая
квота), добавить второй z.ai-аккаунт `ZAI`(`glm-5`) вторым — безопасно
ТОЛЬКО вместе с гейтированием выше.

## Problem / Motivation

Живой лог (комментарий вердикта `ai:failed`, #727): «цепочка провайдеров
исчерпана целиком... сброс: GLM: 2026-09-10 08:51:55». Это ценная
информация — она УЖЕ вычисляется и публикуется. Но следующий прогон
ai-review/worker/hands, стартовавший через минуту после этого, снова
пробует GLM первым (если он стоит первым в цепочке) или тратит время на
провайдера, который сам чейн уже знает как временно нерабочего — знание
не пережило конец job'а. Два прямых следствия:

1. **Трата попытки/времени.** Если владелец хочет держать лучшего по
   качеству провайдера первым (GLM/`glm-5.3-flash`), каждый прогон в окне
   исчерпанной квоты тратит один медленный отклонённый вызов и, в
   зависимости от класса ответа, может не переключиться на следующего
   вовсе, если провайдер отвечает не тем классом, что ожидает
   `dsh_chain_should_advance`.
2. **AGENTS.md «Тормоз без газа не принимается».** Знание «этот провайдер
   квотирован до даты X» — это ТОРМОЗ (не пробовать провайдера), но без
   персистентного носителя у него нет ГАЗА, применимого МЕЖДУ прогонами:
   газ (переключение через дату) существует только внутри памяти одного
   job'а и исчезает вместе с ним.

## Scope

### In

- Персистентный носитель состояния квоты: репо-переменная
  `vars.DSH_PROVIDER_QUOTA_UNTIL` (JSON `{provider_name: reset_iso}`).
  Обоснование выбора носителя — design.md, «Носитель состояния».
- Чтение состояния — `scripts/lib/dsh-ci.sh::dsh_run_with_provider_chain`,
  ДО попытки каждого провайдера: `now < reset_iso` → пропуск (не тратит
  вызов, не считается отказом), лог называет провайдера и дату. Доступно
  ЛЮБОМУ каналу, включая недоверенный `ai-review.yml` (только чтение —
  граница доверия #18 не расширяется).
- Запись состояния — ТОЛЬКО код пульса оркестратора
  (`scripts/orchestra/provider_quota_state.py`, вызывается из
  `scheduler.py::trigger_ai_review`, у которого уже есть ORCHESTRA_PAT и
  уже читаемые `reset-at`-факты из вердиктов ai-review). Газ: провайдер
  снова успешен ЛИБО срок сброса прошёл → запись снимается (мутационно
  доказано).
- Переупорядочение `config/provider-usage.json` (единственный сегодня
  ЖИВОЙ источник цепочки для всех трёх каналов, манифест приоритетнее
  `vars.DSH_PROVIDER_CHAIN`, #823): `GLM` первым, `ZAI`(`glm-5`, второй
  z.ai-аккаунт `ZAI_1_API_KEY`) вторым. Остаток цепочки (заведён #848 по
  измеренной латентности) не трогается.
- Правка алерта «все провайдеры исчерпаны» (правило «алерт не гадает»):
  проверка, что он эмитится ТОЛЬКО когда реально ни один провайдер не
  остался живым (уже так — см. design.md, «Алерт уже не гадает»), и
  усиление — пропущенные по квоте провайдеры тоже несут дату возврата в
  сообщении.
- Тест/инвариант класса: провайдер с будущим `reset_iso` не пробуется
  (мутационное доказательство — смоук), запись состояния — только код
  `scripts/orchestra/**` (гвардия по исходнику).

### Out

- Anthropic OAuth pool / комбо-роутер (ротация ключей внутри ОДНОГО
  провайдера, #215) — другой механизм на другом уровне, не трогается.
- Подтверждение модели `glm-5` реестром #737 — требует живого запроса
  `/v1/models` с `ZAI_1_API_KEY`, которого у апply-агента нет; запись
  добавлена в манифест как безопасный no-op до подтверждения (см. design.md
  «Не подтверждено»), само подтверждение — отдельный шаг (владелец или
  агент с доступом к секрету).
- Успех-триггерное снятие записи ДО истечения `reset_iso` (например, по
  факту `provider:` в успешном вердикте ai-review) — не реализовано в этом
  change: время-based истечение уже покрывает обязательный газ («срок
  прошёл»), «провайдер снова успешен» как ДОПОЛНИТЕЛЬНЫЙ, более ранний
  триггер снятия — возможное расширение, не блокирует эту задачу.

## Acceptance criteria

- [ ] `scripts/lib/dsh-ci.sh::dsh_run_with_provider_chain` пропускает
      провайдера, чей `reset_iso` в `vars.DSH_PROVIDER_QUOTA_UNTIL` ещё не
      наступил — доказано смоуком (`dsh-provider-chain.smoke.sh`),
      мутация (снял код — сценарий покраснел).
- [ ] `scripts/orchestra/provider_quota_state.py` — чистые функции
      (parse/merge/expire) + IO (load/save через `gh`), юнит-тесты.
- [ ] `scheduler.py::trigger_ai_review` пишет состояние из `reset-at`-факта
      вердикта и снимает протухшие записи — тесты на `FakeGh`.
- [ ] Гвардия границы доверия: запись состояния — только код
      `scripts/orchestra/**`, ни один workflow не зовёт `gh variable set
      DSH_PROVIDER_QUOTA_UNTIL` напрямую.
- [ ] `config/provider-usage.json`: `GLM` первым, `ZAI` вторым, инвариант 11
      и `test_provider_usage_registry.py` зелёные (таблица
      пересчитана `collect_provider_usage.py`).
- [ ] `docs/agents/LLM-PROVIDER-USAGE.md`/`docs/runbooks/switch-llm-provider.md`
      обновлены под новый порядок и механизм.
