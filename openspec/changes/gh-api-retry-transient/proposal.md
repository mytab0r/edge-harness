# gh-api-retry-transient: повтор транзиентного обрыва gh api не стоит вычисленного вердикта (#770)

Задача: #770. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Транзиентный обрыв `gh api` (обрыв транспорта — `unexpected end of JSON
input`, 5xx, 429) обрабатывался как содержательный отказ (401/403/404/422):
ни повтора, ни различения класса не было ни в одной точке. Цена —
асимметричная: в `ai_review.py::cmd_verdict` вердикт к моменту обрыва уже
ВЫЧИСЛЕН (модель ответила, разбор состоялся) — обрыв на публикации терял
именно его, требуя повторного живого вызова модели (оплата заново) плюс
ручное вмешательство, потому что `scheduler.trigger_ai_review` читает
только метку `ai:*` и не запускает автоповтор, если метка уже стоит.

Живой случай: прогон 34950741729 (PR #1290, шаг `verdict`,
2026-09-15T09:25:31Z) — `##[error]ai-review: gh api -X: unexpected end of
JSON input`, обрыв на публикации уже вычисленного вердикта.

## Что делается

- `scripts/lib/gh_retry.py` — одно место правды на весь репозиторий:
  `classify_gh_error(rc, stderr) -> TRANSIENT | FATAL | UNKNOWN` (по
  структурному факту — код возврата `gh` (`gh help exit-codes`) и
  разобранный HTTP-статус из stderr, не по совпадению текста) и
  `call_gh_with_retry(argv, run=…, sleep=…)` — повтор с экспоненциальной
  выдержкой (форма — `pulse_guard.probe_backoff_minutes`) ТОЛЬКО для
  TRANSIENT, потолок `GH_RETRY_MAX_ATTEMPTS=4` (пороги — константы одним
  местом, там же).
- `ai_review.py::gh()`/`::run_gh()` вызывают `call_gh_with_retry` вместо
  голого `subprocess.run` — единственная точка, ничего в остальном коде не
  меняется (сигнатуры и поведение при FATAL идентичны прежним).
- `cmd_verdict`: вердикт вычисляется ДО первого сетевого вызова (парсинг
  `--answer` — чистая функция); всё, что после, обёрнуто так, что
  исчерпание повтора (`gh_retry.GhCallExhausted`) поднимает `RuntimeError`,
  чьё сообщение несёт САМ вызов, класс отказа, число попыток за время И
  уже вычисленный вердикт (значение + метка) — следующий читатель не
  обязан звать модель заново, чтобы его узнать.
- Порядок смены метки-вердикта (`ai:*`) — новая метка `POST` ПЕРВОЙ,
  старые снимаются `DELETE` ПОСЛЕ: обрыв между двумя вызовами (после
  исчерпания повторов) оставляет PR с ДВУМЯ ai:*-метками на короткое
  время, не с НОЛЬ — предыдущий порядок мог оставить PR вообще без
  вердикт-метки.

## Что вне рамок

- Криterий 4 issue #770 в полном объёме (признак полноты записи
  комментария-вердикта на текущем head как источник `has_verdict` в
  `scheduler.trigger_ai_review`, вместо одной метки) — issue сама называет
  выбор механизма НЕ сделанным и упирающимся в #740 (отпечаток диффа), не
  ставит эту связь в граф блокировки. Сделанная здесь часть критерия 4 —
  порядок POST/DELETE, не оставляющий PR совсем без ai:*-метки при обрыве
  между вызовами; полный признак «комментарий на этом head существует» —
  отдельная, более узкая доработка, вне рамок этой правки.
- Остальные 14 из 16 копий `subprocess.run(["gh", …])` без обёртки
  (`pulse_guard.gh`, `scripts/gh/net.py`, `check_pr.py`, `claim_task.py` и
  др., перечислены в issue #770) — эта правка проводит носитель через ДВЕ
  точки живого случая (`ai_review.py::gh()`/`::run_gh()`), не через все 16:
  сама issue называет задачу «провести носитель в непокрытые точки», не
  «написать повтор», и не требует одного PR на всё сразу.
