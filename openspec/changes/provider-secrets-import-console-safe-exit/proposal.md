# provider-secrets-import-console-safe-exit: печать отчёта не маскирует успешную запись под exit 1

Задача: #791.
Дельта-спека: `specs/provider-secrets-import/spec.md` — новая узкая
спека-капабилити для `scripts/lib/provider_secrets_import.py` (файл ранее не
описывался ни в одной дельте, см. «Отношение к другим change» ниже).

## Класс закрываемой ошибки

Живой прогон (Windows, консоль cp1251): `scripts/lib/provider_secrets_import.py`
успешно выполняет всю работу (идемпотентная ветка, состояние репозитория не
меняется — сухой прогон; либо реальная запись `gh secret set`/`gh variable set`
при `--apply`), после чего `print(render_report(...))` падает
`UnicodeEncodeError` на символе `→`, который несёт docstring-строка внутри
самого отчёта. Код возврата — 1.

Это лжёт в обе стороны:

- в режиме сухого прогона: ничего не изменено, отдан провал — читается как
  «операция не удалась»;
- в режиме `--apply`: внешние вызовы (`gh secret set`/`gh variable set`) УЖЕ
  выполнены к моменту печати отчёта, отчёт не показан, `exit 1` — оператор
  решит, что запись не применилась, и полезет чинить целое, хотя чинить
  нечего.

`AGENTS.md` называет это явно: «Fail loud, не silent-wrong» — «возможности нет»
и «возможность есть, но сломана» — разные сообщения, лечатся по-разному;
здесь добавляется третий случай — «возможность БЫЛА и сработала, но лжёт о
себе как о провале».

## Решение

Два независимых слоя защиты в `main()`:

1. **Кодировка на входе.** Канонический `scripts/lib/console_utf8.py::
   ensure_utf8_stdio()` переключает `sys.stdout`/`sys.stderr` на UTF-8
   (`errors="backslashreplace"` — тот же обработчик, что CPython уже
   применяет к stderr по умолчанию) — один раз при импорте файла (bootstrap-
   блок) и ещё раз явно первой строкой `main()` (нужно для потоков, которые
   подменяют ПОСЛЕ импорта — например тестовый io.TextIOWrapper). На
   практике устраняет причину падения целиком, не только для символа `→`.
2. **Атомарность кода возврата — отдельным пунктом, не тем же механизмом.**
   Печать финального отчёта обёрнута `try/except UnicodeEncodeError`: сбой
   печати ПОСЛЕ необратимых действий (`set_secret`/`set_variable` при
   `--apply`, выполняются раньше в `main()`) не превращает успешную запись в
   `exit 1` — код возврата остаётся 0, а факт сбоя печати уходит громким
   сообщением в stderr вместе с текстом отчёта (не теряется молча). Это
   защита на случай, если слой 1 недоступен/не сработал (экзотический поток
   без `reconfigure`) — не основной путь, но гарантия, доказанная отдельным
   тестом и отдельной мутацией.

## Отношение к другим change (коллизии, названные явно)

- **Issue #723 / PR #726** — тот же корневой класс (Windows не использует
  UTF-8 для stdout по умолчанию), вводит канонический хелпер
  `scripts/lib/console_utf8.py::ensure_utf8_stdio()` для ~24 точек входа.
  На момент первого варианта этого change (#791) `provider_secrets_import.py`
  в PR #726 не входил, и в файле жила временная приватная копия
  `_ensure_utf8_stdout()` — названная в докстринге как подлежащая замене
  после слияния #726. #726 смёржен первым (PR #726, задача #723) и в момент
  ребейза этой ветки принёс bootstrap-блок `console_utf8` в
  `provider_secrets_import.py`; приватная копия выброшена, `main()` теперь
  зовёт канонический `console_utf8.ensure_utf8_stdio()` напрямую — второго
  источника правды на сам механизм reconfigure не осталось.
- **PR #781** (`agent/777-gate-rework-followup`) уже смёржен в main и правит
  тот же файл (`classify_snapshot`/`classify_probe`/`rank_account`/
  `select_accounts`/`probe_provider`, сигнатура `render_report`) в области
  ранжирования тиров — этот change ту область не трогает, только печать
  отчёта и код возврата в `main()`.

- Правка тиров ранжирования 401/403/429 — область PR #781.
