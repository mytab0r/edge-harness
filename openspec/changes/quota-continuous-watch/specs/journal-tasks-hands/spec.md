# Дельта-спека: журнал (journal-tasks-hands) — непрерывный сторож квот харнеса (#605)

Секция «Пульс оркестрации» домовой спеки
(`openspec/specs/journal-tasks-hands.md`) пополняется несколькими
незаархивированными дельтами одновременно — номер у этого пункта
присваивается при архивации, сверяться с доменной спекой на тот момент,
не с числом здесь. Реализация: `.github/workflows/quota-watch.yml`,
`scripts/measure/quota_watch.py`, `scripts/measure/quota_alert.py`.

## ADDED: Непрерывное наблюдение за квотами харнеса (алерт с дедупом, автозадача, самонаблюдение)

1. **Каденция.** Сторож тикает на `pull_request`
   (opened/synchronize/reopened/labeled — основной и надёжный носитель:
   измеренная доставка cron `*/15` на этом репозитории ~6.7%, события —
   32/32, `docs/research/21-github-actions.md`) и по cron
   `3,18,33,48 * * * *` как страховке тихих часов. Интервал каденции —
   15 минут (`CHECK_INTERVAL_MINUTES`), обоснован профилем дня инцидента
   2026-09-06: окно между «порог пробит» и «квота исчерпана» на пиковом
   темпе ≈21 минута. Прогоны сериализованы concurrency-группой
   (`quota-watch`, `cancel-in-progress: false`); формулировка «максимум
   один выполняющийся и один ожидающий прогон» — из документации GitHub
   Actions, локальным замером не подтверждена; проверенный здесь факт —
   завершённые прогоны группы не перекрываются по времени (гейт каждого
   видит завершённого предыдущего), а ожидающие тики при шторме старше
   одного теряются (документированное поведение GitHub) — каденцию это не
   ломает: основной носитель, поток PR-событий, приносит следующий тик
   через минуты.
2. **Троттлинг — только по реальным запускам замера.** Дорогой CF-замер
   выполняется, только если последний РЕАЛЬНЫЙ запуск шага замера старше
   окна троттлинга; «реальный запуск» = шаг замера прошлого прогона получил
   `conclusion` `success` ИЛИ `failure` в Jobs API — `skipped` (гейт не
   пустил) и прогоны, умершие до шага замера, окно НЕ открывают. Решение
   об измерении — один шаг-гейт (`gate_main`) с `proceed` в
   `$GITHUB_OUTPUT`; шаг замера существует отдельно и запускается по
   `if:`. Дешёвая проверка — одна метрика `rows_read`; полный срез
   `quotas.py` — не чаще раза в час. (Возраст запуска — `attempt_age` —
   НЕ тот же возраст, что у канала простоя, см. п.6.)
3. **Алерт — по переходу, задача — действие.** Один канал решения
   (`quota_alert.check_and_alert`) для дешёвой проверки и полного среза,
   один ключ ресурса (`cf_do_rows_read_day` для `rows_read`): сигнал уходит
   только при переходе `ok`→`breach` (или если первое наблюдение застало
   ресурс в breach), не на каждый прогон. На breach сторож сам заводит
   задачу (`scripts/gh/issue-create`, метки `task`/`area:process`/
   `auto-detected`/`quota-breach`) или дополняет уликой найденную гвардией
   дублей; «найденной» считается только задача ПРО ТОТ ЖЕ ресурс (метка
   ресурса в заголовке кандидата) — похожие задачи других ресурсов не
   глотают улику, своя задача заводится с `--confirm-not-duplicate`.
   Задача НЕ закрывается автоматически при возврате метрики ниже
   порога (суточный счётчик Cloudflare сбрасывается сам — это не «причина
   устранена»), переход breach→ok оставляет уведомление.
4. **Несостоявшееся действие не пишет маркер; вердикт доставки не
   выбрасывается.** Если заведение задачи не состоялось, маркер breach НЕ
   записывается — следующий прогон повторяет попытку вместо молчания по
   дедупу до случайного breach→ok. Замер, не состоявшийся вовсе (нет
   кредов, упал CF-вызов), краснит прогон ненулевым кодом — зелёный шаг без
   данных слепил бы троттлинг и проверку простоя навсегда. Вердикт доставки
   breach-канала применяется к самому прогону теми же предикатами
   `pulse_guard`, что и у канала простоя (п.6): отказ обоих каналов И
   отказ носителя дедупа («Telegram доставлен, след в #120 не записан» —
   маркер состояния не появился, каждый следующий тик повторит страницу и
   попытку действия) краснят шаг, тексты ошибок различают формы отказа;
   сочетание «Telegram не доставлен, след оставлен» зелёное намеренно
   (маркер записан, мгновенный пуш продублирован постоянным следом).
   Отказ ТИХОЙ записи носителя дедупа (первое наблюдение ресурса, заставшее
   его в норме: маркер без эскалации) различим вызывающим тем же предикатом
   носителя — вердикт строит `pulse_guard.carrier_write_verdict` той же
   лексикой, что `escalate`, и его литералы рождаются там же, рядом с
   предикатами (found: ревью PR #607, head 345a64f — отказ тихой записи был
   различим только строкой лога, и носитель дедупа мог стоять сломанным
   неограниченно долго при зелёных прогонах).
5. **Дедуп живёт на свежих страницах #120.** Все чтения маркеров сторожа
   (состояние ресурса, эпизоды простоя) ограничены
   `MARKER_SCAN_PAGES = 1` свежей страницей комментариев — стоимость тика
   постоянна и не растёт с историей задачи-статуса. Честная цена:
   открытый эпизод старше ~100 комментариев #120 даст ОДИН повторный
   сигнал на ~сутки затяжного эпизода (каждый алерт несёт свежий маркер и
   тем самым возвращает дедуп на первую страницу — самозаживление),
   не тишину.
6. **Сторож следит за собой: простой УСПЕШНОГО замера.** У троттлинга и
   канала простоя — ДВА разных возраста одного скана истории: троттлинг
   считает любой запуск шага замера (`success`/`failure` — CF-вызов
   тратился), канал простоя — только последний УСПЕШНЫЙ замер. Отсутствие
   успешного замера дольше `MEASUREMENT_STALE_MINUTES` (ревизия #1184:
   пересчитан от реально измеренной каденции триггера `quota-watch.yml`,
   не от кратности `CHECK_INTERVAL_MINUTES`) —
   громкий сигнал в общий канал (`pulse_guard.escalate`: Telegram + #120),
   вердикт доставки которого применяется к самому прогону: отказ обоих
   каналов ИЛИ отказ носителя дедупа (страница ушла, а открывающий маркер
   эпизода в #120 не записан — следующий тик повторит её) краснит прогон;
   сочетание «Telegram не доставлен, след оставлен» зелёное намеренно
   (маркер записан, мгновенный пуш продублирован постоянным следом) —
   с эпизодным дедупом (пара маркеров
   `STALE_MARKER`/`STALE_RESOLVED_MARKER`), явным закрытием эпизода
   ТОЛЬКО точным свежим успехом (свежие failure-прогоны эпизод не
   закрывают и сигнал не гасят — устойчивый отказ замера, например
   протухший CF-токен, обязан дать громкий сигнал через порог, found:
   ревью PR #607, head eae35fc) и текстом, называющим
   классифицированную причину, а не гипотезы; если чтение истории #120
   для дедупа недоступно, пометка «дедуп пропущен» с причиной уходит В
   САМ текст эскалации (получатель знает, что повтор страницы может быть
   дедуп-пропуском, а не новым эпизодом), а не только в лог прогона
   (found: ревью PR #607, head 345a64f — чеклист). Скан истории останавливается
   досрочно, как только нижняя граница возраста успеха пересекла порог
   простоя (все более свежие прогоны осмотрены, успеха в них нет) —
   стоимость тика ограничена окном простоя, а не страницей/лукбеком, из
   общего бюджета github.token (1000 запросов/час на репозиторий).
   Страницы истории листаются, пока нижняя граница не пересечёт порог
   простоя, с жёстким потолком `MEASUREMENT_SCAN_MAX_PAGES` (found: ревью
   PR #607, head 345a64f — одной страницы 30 прогонов в шторме
   PR-событий ~1 прогон/мин недостаточно: страница покрывает ~15–30 минут
   и скользит, порог простоя не достигался никогда, устойчивый отказ
   замера оставался тихим); честный остаток потолка — устойчивый шторм
   плотнее ~2 прогонов/мин, при нём `SCAN_CEILING` ниже порога означает
   тихий тик, и это названо в коде и тестах, а не спрятано.
   Сигнал подавляется, только
   если исполняемая копия workflow ДОСТОВЕРНО отличается от `main`
   (неслитый код не будит владельца); недоступность проверки версии —
   НЕ подавление, сигнал уходит с честной пометкой.
7. **Слепая зона скана истории — отдельные исходы, не «холодный старт».**
   Скан истории различает (относительно success_age): `SCAN_COLD_START`
   (в окне нет ни одного завершённого прогона — молчание),
   `SCAN_EXACT` (возраст успешного замера точен),
   `SCAN_ALL_WINDOW`/`SCAN_CEILING` (успешного замера нет среди
   просмотренных прогонов; при `SCAN_CEILING` исчерпан потолок страниц
   `MEASUREMENT_SCAN_MAX_PAGES` на полных страницах без остановки по
   возрасту — история продолжается), `SCAN_STALE_PROVEN` (досрочная
   остановка на пороге простоя: все прогоны свежее осмотрены, успеха в
   них нет, следующие страницы даже не запрашиваются) —
   возраст в нижнеграничных исходах публикуется как НИЖНЯЯ ГРАНИЦА
   простоя. Нижняя граница на пороге простоя и выше — эскалация с
   формулировкой «точный возраст не установлен»; ниже порога — тихий тик,
   эпизод простоя НЕ закрывается (свежесть не доказана). Шаги части
   прогонов окна, которые не удалось осмотреть, при отсутствии найденного
   замера дают «история недоступна» (безопасные дефолты), не «замера нет».
8. **Границы наблюдения.** Класс «прегоны workflow не случаются вовсе»
   изнутри прогона невидим и покрывается внешним инвариантом (задача
   #679, `scripts/orchestra/repo_invariants.py`), не этим сторожем.
   Причина исчерпания квоты (расход) этим change не чинится — сторож
   переводит находку в действие.

## MODIFIED: Тренд, третье состояние и собственная каденция GitHub-лимита (#1100)

Живой инцидент 2026-09-13: сторож увидел `gh_rest_rate_limit_hour` в 07:03
(6.1%, "ok") и промолчал 83 минуты до фактического исчерпания токена
прогонов (`orchestra.yml`: "API rate limit exceeded for installation") —
состояние держалось "ok" всю дорогу, порог пробился в последние минуты.
Разбор нашёл и независимый структурный дефект дедупа по переходу (п.3/п.5
выше): эндпоинт GitHub «List issue comments» не поддерживает `sort`/
`direction` — страница 1 растущей истории #120 ВСЕГДА самая старая, не
свежая (проверено живьём: `page=1` при 952 комментариях вернул комментарий
от 2026-08-31). Значит `MARKER_SCAN_PAGES = 1` (п.5) буквально читало
страницу 1, а не свежую — дедуп ВСЕГДА видел «маркера нет» и объявлял
каждый тик «первым наблюдением» (114 копий одной записи в #120 за двое
суток вместо одного перехода).

1. **Свежая страница вычисляется, а не берётся буквальной `page=1`.**
   `pulse_guard.all_issue_comments(max_pages=N)` теперь читает метаданные
   issue (поле `comments`, один дешёвый вызов) и вычисляет НАСТОЯЩУЮ
   последнюю страницу вместо `page=1..N`. Стоимость `max_pages`-чтения —
   на 1 вызов метаданных дороже прежнего (ошибочного) поведения; п.5 выше
   («стоимость тика не растёт с историей задачи») остаётся верным —
   стоимость по-прежнему константна, не зависит от объёма истории #120,
   просто константа стала на единицу больше.
2. **Три состояния дедупа, не два: ok / approaching / breach.**
   `quota_alert.classify_state(pct, threshold, projected_minutes, horizon)`
   добавляет `approaching` — по ДВУМ последовательным числовым показаниям
   (`last_reading`/`record_reading`) считается скорость роста и проекция
   «через сколько минут порог будет пробит»; approaching срабатывает
   РАНЬШЕ, чем pct сам пересечёт порог. Горизонт (`TREND_HORIZON_MINUTES`) —
   45 минут, обоснован НЕЗАВИСИМО от каденции триггера (ревизия #1184: это
   риск-профиль экстраполяции тренда метрики, не такт срабатывания —
   искусственная связка с `MEASUREMENT_STALE_MINUTES` из п.6 снята,
   подтверждение — реконструкция инцидента #1100 в test_quota_alert.py).
   Approaching эскалирует
   (Telegram + след в #120) БЕЗ автозаведения задачи (в отличие от breach,
   п.3) — тренд может развернуться сам, не дойдя до порога; переход
   approaching→ok несёт текст «рост остановился, порог не был достигнут»,
   отличный от текста breach→ok (порог реально пробивался, задача на
   разбор упоминается).
3. **Числовой носитель тренда — один комментарий на ресурс, редактируется
   на месте.** `record_reading` правит (`pulse_guard.edit_issue_comment`,
   PATCH) уже существующий носитель вместо нового комментария на каждый
   тик — иначе воспроизводился бы тот же класс дефекта, что дал 114
   дублей маркера состояния. Честная деградация: PATCH не двигает
   `created_at`, листание страниц идёт по порядку СОЗДАНИЯ — носитель,
   созданный один раз, рано или поздно физически съезжает за окно
   `MARKER_SCAN_PAGES` по мере роста #120 независимо от частоты
   редактирования. Самоисцеление за один тик: `last_reading`, не нашедший
   съехавший носитель, теряет ровно один сэмпл тренда в этом тике (падает
   на чистый pct>=threshold), но `record_reading` заводит НОВЫЙ носитель у
   хвоста истории — следующий тик снова находит его.
4. **Собственная, независимая от CF-гейта каденция для GitHub-лимита.**
   Токен, который исчерпался в инциденте (`GH_TOKEN: github.token`), уже
   измерялся (п.2, полный срез `quotas.py`), но только внутри `full_sweep`
   — не чаще раза в час, хотя `gh api rate_limit` не расходует сам себя
   (документировано GitHub, проверено живьём — 3 подряд вызова личным PAT
   дали `used=0/5000` все три раза). Новый шаг workflow
   `github-rate-limit` (без `if:`, не гейтится CF-троттлингом) измеряет
   REST/GraphQL лимит на каждом тике с СОБСТВЕННЫМ, независимым
   троттлингом (`RATE_LIMIT_MIN_INTERVAL_MINUTES = CHECK_INTERVAL_MINUTES`
   по последнему `last_reading`, не через Jobs API — чтение бесплатно,
   троттлить историю прогонов незачем). Точное число лимита этого токена
   не подтверждено однозначно (документация GitHub — 1000/час/репозиторий,
   живой замер этого же репозитория — 5000/час, `docs/research/
   21-github-actions.md`, «Live-замер 2026-09-09», issue #812) — на
   механику не влияет, pct считается от реального `limit` в ответе.
5. **Воспроизведение.** На исторических точках issue #1100 (6.1% @ 07:03 —
   реальный факт из лога прогона; 100% @ 08:26 — акцептанс-критерий issue;
   промежуточные точки — честно помеченная линейная интерполяция, поскольку
   реальных промежуточных показаний не существовало из-за самого бага)
   approaching срабатывает в 07:33 — за 53 минуты до исчерпания и за 46
   минут до первого реального отказа оркестратора (08:19). Критерий:
   `test_quota_alert.py::test_reproduction_1100_trend_fires_before_exhaustion`.
