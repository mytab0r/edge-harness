# Дельта-спека: журнал (journal-tasks-hands) — непрерывный сторож квот харнеса (#605)

Секция «Пульс оркестрации» домовой спеки
(`openspec/specs/journal-tasks-hands.md`) пополняется несколькими
незаархивированными дельтами одновременно — номер у этого пункта
присваивается при архивации, сверяться с доменной спекой на тот момент,
не с числом здесь. Реализация: `.github/workflows/quota-watch.yml`,
`scripts/measure/quota_watch.py`, `scripts/measure/quota_alert.py`.

## ADDED: Непрерывное наблюдение за квотами харнеса (алерт с дедупом, автозадача, самонаблюдение)

1. **Каденция.** Сторож тикает на `pull_request`
   (opened/synchronize/reopened/labeled — основной и надёжный носитель:
   измеренная доставка cron `*/15` на этом репозитории ~6.7%, события —
   32/32, `docs/research/21-github-actions.md`) и по cron
   `3,18,33,48 * * * *` как страховке тихих часов. Интервал каденции —
   15 минут (`CHECK_INTERVAL_MINUTES`), обоснован профилем дня инцидента
   2026-09-06: окно между «порог пробит» и «квота исчерпана» на пиковом
   темпе ≈21 минута. Прогоны сериализованы concurrency-группой
   (`quota-watch`, `cancel-in-progress: false`) — перекрывшиеся тики
   невозможны по построению, а не по договорённости.
2. **Троттлинг — только по реальным замерам.** Дорогой CF-замер
   выполняется, только если последний РЕАЛЬНЫЙ замер старше окна
   троттлинга; «реальный» = шаг замера прошлого прогона получил
   `conclusion` `success` ИЛИ `failure` в Jobs API — `skipped` (гейт не
   пустил) и прогоны, умершие до шага замера, окно НЕ открывают. Решение
   об измерении — один шаг-гейт (`gate_main`) с `proceed` в
   `$GITHUB_OUTPUT`; шаг замера существует отдельно и запускается по
   `if:`. Дешёвая проверка — одна метрика `rows_read`; полный срез
   `quotas.py` — не чаще раза в час.
3. **Алерт — по переходу, задача — действие.** Один канал решения
   (`quota_alert.check_and_alert`) для дешёвой проверки и полного среза,
   один ключ ресурса (`cf_do_rows_read_day` для `rows_read`): сигнал уходит
   только при переходе `ok`→`breach` (или если первое наблюдение застало
   ресурс в breach), не на каждый прогон. На breach сторож сам заводит
   задачу (`scripts/gh/issue-create`, метки `task`/`area:process`/
   `auto-detected`/`quota-breach`) или дополняет уликой найденную гвардией
   дублей; задача НЕ закрывается автоматически при возврате метрики ниже
   порога (суточный счётчик Cloudflare сбрасывается сам — это не «причина
   устранена»), переход breach→ok оставляет уведомление.
4. **Несостоявшееся действие не пишет маркер.** Если заведение задачи не
   состоялось, маркер breach НЕ записывается — следующий прогон повторяет
   попытку вместо молчания по дедупу до случайного breach→ok. Замер,
   не состоявшийся вовсе (нет кредов, упал CF-вызов), краснит прогон
   ненулевым кодом — зелёный шаг без данных слепил бы троттлинг и проверку
   простоя навсегда.
5. **Дедуп живёт на свежих страницах #120.** Все чтения маркеров сторожа
   (состояние ресурса, эпизоды простоя) ограничены
   `MARKER_SCAN_PAGES = 1` свежей страницей комментариев — стоимость тика
   постоянна и не растёт с историей задачи-статуса. Честная цена:
   открытый эпизод старше ~100 комментариев #120 даст ОДИН повторный
   сигнал на ~сутки затяжного эпизода (каждый алерт несёт свежий маркер и
   тем самым возвращает дедуп на первую страницу — самозаживление),
   не тишину.
6. **Сторож следит за собой: простой замера.** Отсутствие реального замера
   дольше `MEASUREMENT_STALE_MINUTES` (3×интервал) — громкий сигнал в
   общий канал (`pulse_guard.escalate`: Telegram + #120) с эпизодным
   дедупом (пара маркеров `STALE_MARKER`/`STALE_RESOLVED_MARKER`), явным
   закрытием эпизода при возобновлении замера и текстом, называющим
   классифицированную причину, а не гипотезы. Сигнал подавляется, только
   если исполняемая копия workflow ДОСТОВЕРНО отличается от `main`
   (неслитый код не будит владельца); недоступность проверки версии —
   НЕ подавление, сигнал уходит с честной пометкой.
7. **Слепая зона скана истории — отдельные исходы, не «холодный старт».**
   Скан истории различает: `SCAN_COLD_START` (в окне нет ни одного
   завершённого прогона — молчание), `SCAN_EXACT` (возраст замера точен),
   `SCAN_ALL_WINDOW`/`SCAN_CEILING` (замера нет среди просмотренных
   прогонов; при `SCAN_CEILING` страница полна и история продолжается) —
   возраст в нижнеграничных исходах публикуется как НИЖНЯЯ ГРАНИЦА
   простоя. Нижняя граница на пороге простоя и выше — эскалация с
   формулировкой «точный возраст не установлен»; ниже порога — тихий тик,
   эпизод простоя НЕ закрывается (свежесть не доказана). Шаги части
   прогонов окна, которые не удалось осмотреть, при отсутствии найденного
   замера дают «история недоступна» (безопасные дефолты), не «замера нет».
8. **Границы наблюдения.** Класс «прегоны workflow не случаются вовсе»
   изнутри прогона невидим и покрывается внешним инвариантом (задача
   #679, `scripts/orchestra/repo_invariants.py`), не этим сторожем.
   Причина исчерпания квоты (расход) этим change не чинится — сторож
   переводит находку в действие.
