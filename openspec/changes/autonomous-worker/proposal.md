# autonomous-worker: воркер сам берёт задачу из пула и делает её полноценным DSH

Задача: #89. Курс владельца 2026-08-30 — автономный разработчик. Playbook
(#87/#88) уже описывает правила; этот change воплощает их в конвейере: воркер
работает без человека между «задача в пуле» и «PR открыт».

## Решение

1. `scripts/worker/task.sh` — транспорт и отчётность, ничего содержательного за
   агентом: выбор свободной задачи (метка `task`, открыта, без assignee, без
   открытого PR) → назначение с проверкой по факту → ветка `agent/N-slug`
   каноническим `scripts/git/task-branch` → промпт (тело задачи + критерий
   готовности + `docs/agents/WORKER-PLAYBOOK.md` целиком + маршрут протокола) →
   `dsh --profile headless` (таймаут 150 мин, GLM-патч профиля из общей lib) →
   пост-обработка по видимому артефакту: открытый PR → комментарий в задачу +
   Telegram + зелёный job; эскалация (`blocked`) → то же, зелёный; иначе —
   комментарий с хвостом лога + Telegram + красный job.
2. `.github/workflows/worker.yml` — `workflow_dispatch` (input `task` —
   конкретная задача, пусто = свободная), concurrency `worker` (один воркер),
   timeout 240. Git/gh агента — под PAT владельца (`GH_DISPATCH_TOKEN`) через
   `gh auth setup-git`; `GITHUB_TOKEN` воркфера намеренно без contents:write.
3. `scripts/orchestra/scheduler.py` — пульс: свободная задача + нет активного
   worker-рана → ровно один dispatch `worker.yml` за запуск; best-effort,
   оркестратор не роняется (до мержа workflow на main dispatch честно 404).
4. `scripts/lib/dsh-ci.sh` — общее место правды рук и воркера: пины версий,
   integrity tarball'ов, GLM-патч профиля, redact (закрыт класс «второй пин
   DSH» — раньше это жил только в `scripts/hands/dsh_task.sh`).

## Спека

- `openspec/specs/journal-tasks-hands.md` — новый раздел «Автономный воркер
  (конвейер пула)» (п.26–29): пульс-диспатч, зелёный простой, захват
  назначением, оценка по артефакту.

## Что вне рамок

- Живой прогон на реальной задаче — пост-мерж проверка (workflow должен
  оказаться на main, иначе dispatch не сработает).
- Ревью PR воркера вторым агентом и слияния — как для любого PR, силами
  оркестратора и существующего review-конвейера.
- Несколько параллельных воркеров — concurrency `worker` намеренно один;
  расширение потребует распределения задач без гонки.
