# Дельта-спека: журнал (journal-tasks-hands) — приёмка не закрывает частичные и родительские задачи (#335)

## ADDED: Конвейер (оркестратор)

18.1. Приёмка (`accept_merged_tasks`, #227) перед закрытием задачи по улике
    проверяет два дополнительных условия, оба — до обращения к
    `classify_acceptance`/улике (#335):

    - **Дисклеймер о неполноте в теле закрывающего PR**: список маркеров в
      одном месте (`scheduler.py::PARTIAL_DISCLAIMER_MARKERS`) — «не
      реализован», «остаётся открыт-», «стопгэп», «propose-фаза», «перенесён/
      -а/-о в #». Найден маркер → задача НЕ закрывается, приёмка оставляет
      комментарий «критерий требует проверки человеком» (идемпотентно, тот же
      маркер-паттерн, что у существующих веток `fail`/`pending`). Декларация
      первой строкой (`task_ref.declared_tasks`) отвечает «к какой задаче
      относится PR», не «закрывает ли он её целиком» — для задач, разбитых на
      несколько PR, это разные вопросы, и без этой проверки приёмка закрывала
      задачу вопреки собственному тексту PR (живой случай #297/PR #303).
    - **Родительская задача (эпик)**: два признака, оба уже в ответе issues
      API без дополнительного запроса — заголовок с префиксом «ЭПИК»
      (соглашение репозитория) и незакрытые нативные sub-issues
      (`sub_issues_summary.total > completed`, #202). Эпик пропускается молча
      (тем же приёмом, что и `WATCHDOG_ISSUE`) — реализация эпика обычно
      распределена по нескольким PR на дочерние задачи, слитый PR, объявляющий
      эпик первой строкой, не значит «эпик готов целиком» (живой случай #115).

    Оба условия — минимально достаточная защита, не полное решение: риск
    ложного срабатывания (маркер относится к чужому упомянутому issue, не к
    объявленному) признан и принят намеренно ради остановки текущей порчи
    пула; точный справочник машиночитаемых критериев в теле задачи — предмет
    отдельного шага (обсуждается в #335).
