# Дельта-спека: журнал (journal-tasks-hands) — приёмка не закрывает частичные и родительские задачи (#335)

## ADDED: Конвейер (оркестратор)

18.1. Приёмка (`accept_merged_tasks`, #227) перед закрытием задачи по улике
    проверяет два дополнительных условия, оба — до обращения к
    `classify_acceptance`/улике (#335):

    - **Дисклеймер о неполноте в теле закрывающего PR**: список маркеров в
      одном месте (`scheduler.py::PARTIAL_DISCLAIMER_MARKERS`) — «не
      реализован», «остаётся открыт-», «стопгэп», «propose-фаза», «перенесён/
      -а/-о в #» («ё» нормализуется в «е» с обеих сторон сравнения — живые
      тела PR пишут «перенесен» без «ё»). Найден маркер, и задачу не
      объявляет ещё один открытый PR (см. ниже) → задача НЕ закрывается,
      снимает исполнителя и замок claim_task — задача возвращена в пул.
      Декларация первой строкой (`task_ref.declared_tasks`) отвечает «к какой
      задаче относится PR», не «закрывает ли он её целиком» — для задач,
      разбитых на несколько PR, это разные вопросы, и без этой проверки
      приёмка закрывала задачу вопреки собственному тексту PR (живой случай
      #297/PR #303).

      Сигнал владельцу (`scheduler.py::escalate`, issue + Telegram, живой
      случай #335/#382 — прежний текст называл только решение, не вопрос,
      критерий и варианты) называет: прямую ссылку на задачу и на PR;
      цитату дисклеймера (`disclaimer_quote` — реальное предложение из тела
      PR, не голое слово-маркер); причину, почему не решает автоматика
      (маркер-подстрока, не структурированный критерий — точный критерий
      по схеме ещё не сделан, задача #355); три готовых варианта с
      конкретным действием («с телефона»): закрыть задачу кнопкой Close
      issue, если она сделана целиком; ничего не делать, если нужна
      доработка (задача уже в пуле); завести узкую задачу-довесок с меткой
      `task`, если нужен отдельный узкий кусок. Если задачу уже объявляет
      другой открытый PR (`task_ref.resolve_pr_task`, тот же приём, что и у
      проверки «другой открытый PR» в ветке `ok`/`docs` ниже, #358) —
      докрытие уже в работе: эскалация владельцу не нужна вовсе, приёмка
      оставляет тихую пометку и не трогает исполнителя/замок.
    - **Родительская задача (эпик)**: два признака, оба уже в ответе issues
      API без дополнительного запроса — заголовок с префиксом «ЭПИК»
      (соглашение репозитория) и незакрытые нативные sub-issues
      (`sub_issues_summary.total > completed`, #202). Автозакрытие запрещено
      всегда — реализация эпика обычно распределена по нескольким PR на
      дочерние задачи, слитый PR, объявляющий эпик первой строкой, не значит
      «эпик готов целиком» (живой случай #115). Но когда все нативные
      sub-issues уже закрыты (`sub_issues_summary.total == completed`, оба
      `> 0`) — открытость эпика больше не тормоз-функция (как у
      `WATCHDOG_ISSUE`, который остаётся открытым по назначению), а
      незавершённая работа: приёмка ставит разовый идемпотентный
      комментарий-маркер `[приёмка: эпик завершён]` («все N дочерних
      sub-issues закрыты — требует ручного закрытия»), не закрывая issue сама
      (находка AI-ревью PR #342 — молчание навсегда означало бы, что
      завершённый эпик никто не увидит). Сигнал уходит тем же каналом
      `escalate` (issue + Telegram), что и дисклеймер выше, с прямой ссылкой
      на задачу — тот же класс «требует ручного решения», один канал.

    Оба условия — минимально достаточная защита, не полное решение (развилка
    вариантов и цена каждого — [design.md](../../design.md)): риск ложного
    срабатывания (маркер относится к чужому упомянутому issue, не к
    объявленному) признан и принят намеренно ради остановки текущей порчи
    пула; машиночитаемое поле критерия приёмки в теле PR/задачи вместо
    разбора прозы — предмет отдельного шага, задача пула
    [#355](https://github.com/mytab0r/edge-harness/issues/355).
