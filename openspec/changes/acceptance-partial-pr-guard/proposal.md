# acceptance-partial-pr-guard: приёмка не закрывает частично выполненные и родительские задачи (#335)

Задача: #335. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Стадия приёмки (`scripts/orchestra/scheduler.py::accept_merged_tasks`, #227) читает
только ПЕРВУЮ строку тела слитого PR (`task_ref.declared_tasks`) как ответ на вопрос
«какую задачу закрыть» — и закрывает её по зелёной улике, не читая остальное тело.
Декларация отвечает «к какой задаче относится PR», не «закрывает ли он её целиком»:
для крупных задач, разбитых на несколько PR, это разные вопросы.

Аудит закрытых за 2026-09-04 нашёл 10 ошибочно закрытых задач; пять — не этот класс
(баг разбора прозы, исправлен в #312), пять — этот класс:

- **#297**: PR #303 объявляет `#297` первой строкой, а прозой пишет «эта часть —
  открытая #297» и «#269 остаётся открытой до решения #297» — приёмка закрыла
  задачу вопреки собственному дисклеймеру PR.
- **#158**: PR #159 объявляет `#158`, тело — «Propose-фаза, кода нет», диф только
  спека; «Пост-мерж проверка: не применимо: propose-фаза» — задача про реализацию,
  а не про спеку, закрыта преждевременно.
- **#112**: PR #123 объявляет `#112` первой строкой, заголовок и тело сами называют
  правку «стопгэп» («закрыть стопгэп-часть #112 уликой») — часть задачи, а не вся.
- **#115**: эпик (заголовок «ЭПИК: …») — приёмка закрыла родительскую задачу по
  мержу PR на один из её плагинов, хотя эпик состоит из нескольких независимых
  кусков и один из них валит прод-деплой (два красных прогона `deploy-dsh-edge.yml`).
- **#131/#20**: тот же класс «критерий задачи не выполнен целиком, а декларация
  первой строки читается как «выполнен»» — вне рамок этого PR (не разбираются
  повторно здесь, только реестр в #335).

## Что делается

Минимально достаточная защита СЕЙЧАС (полная — машиночитаемые критерии в теле
задачи, обсуждается в #335 как следующий шаг):

1. **Дисклеймер о неполноте** (`scheduler.py::partial_disclaimer`) — список
   маркеров в ОДНОМ месте (`PARTIAL_DISCLAIMER_MARKERS`): «не реализован»,
   «остаётся открыт-», «стопгэп», «propose-фаза», «перенесён/-а/-о в #». Найден
   маркер в теле закрывающего PR → приёмка НЕ закрывает задачу, оставляет
   комментарий «критерий требует проверки человеком» (идемпотентно, тот же
   маркер-паттерн, что у `ACCEPTANCE_FAIL_MARKER`/`ACCEPTANCE_PENDING_MARKER`) —
   fail loud вместо тихого закрытия (правило репозитория «молча неверное дороже
   падения»).
2. **Эпик не закрывается автоматом** (`scheduler.py::is_epic_issue`) — два
   дешёвых признака без дополнительного запроса (уже есть в ответе issues API):
   заголовок с префиксом «ЭПИК» (соглашение репозитория, проверено фактом на
   #116/#77/#17/#115) и незакрытые нативные sub-issues (`sub_issues_summary`,
   #202) — ни один не покрывает оба случая сам по себе (#115 — эпик по
   заголовку, но `sub_issues_summary` у него нулевой). Пропуск молчаливый, тем
   же приёмом, что уже применяется к `WATCHDOG_ISSUE`: это структурное решение
   «эпики приёмка не трогает никогда», не неуверенность.

Гвардия: тест на прод-форме — реальные тела PR #303/#159/#123, доказано мутацией
(`scripts/orchestra/test_scheduler.py`, разделы «дисклеймер о неполноте» и «эпик»).

## Что вне рамок

- Упоминание задачи как блокирующей в других открытых задачах («упомянута как
  блокирующая») — не реализовано: требует обхода ВСЕХ открытых задач на каждую
  проверяемую пару, не дёшево при текущем размере пула; отложено до следующего
  шага (машиночитаемые критерии, обсуждается в #335).
- Разбор #131/#20 по существу (эпик/декларация/что угодно ещё) — отдельно от
  этого PR, только переоткрытие с проверкой факта.
- Полная семантическая проверка «улика достаточна» — остаётся на совести
  исполнителя и ревью, автомат может только напоминать (тот же принцип, что и в
  `task-closure-after-proof`).
