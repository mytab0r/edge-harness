# Дельта-спека: журнал (journal-tasks-hands) — два периодических потребителя сирот: хвост чеклиста наследует область, алерты Dependabot заводят задачи (#961)

Реализация: `scripts/orchestra/checklist_tail_labels.py` (workflow
`.github/workflows/checklist-tail-triage.yml`) и
`scripts/orchestra/dependabot_alert_watch.py` (workflow
`.github/workflows/dependabot-alert-watch.yml`). Пороги — константы
соответствующих модулей (одно место правды, номера строк не фиксируются).

## ADDED: Наследование `area:*` хвостом чеклиста ревью

Требование: каждый пульс отдельного periodic workflow читает открытые задачи
с меткой `task`, чей заголовок матчит формат `tail_issue_title`
(`review_checklist`), и для каждой ещё не разобранной (без маркера
`checklist-tail:inherited`) резолвит PR из заголовка → родительскую задачу
пула единственным источником правды — имя agent-ветки
(`task_ref.resolve_pr_task`); тело PR не читается вовсе. Метки `area:*`
родительской задачи, которых у хвоста ещё нет, переносятся на хвост одним
вызовом вместе с маркером; служебные метки конвейера (ревью-гейты, аренда,
`blocked`) наследованию не подлежат — только `area:*`.

Требование: маркер `checklist-tail:inherited` ставится на КАЖДЫЙ разобранный
хвост, включая честный случай «у родительской задачи нет `area:*`-меток» —
это решённый случай, а не забытый; повторная обработка такого хвоста возможна
только явным снятием маркера (объявленный газ, `docs/agents/LABELS.md`).

Требование: отчёт различает три исхода по данным, которые уже есть в области
видимости, — «унаследовал {метки}», «область {метки} родителя уже стоит на
хвосте», «у родителя нет `area:*`-меток» — и не схлопывает их в одну строку с
ложным фактом («Алерт не гадает», AGENTS.md).

Требование: периферийный сбой (PR этого хвоста, родительская задача, вызов
добавления меток) — ⚠️-наблюдение по конкретному хвосту БЕЗ маркера: хвост
остаётся неразобранным, следующий пульс повторит. Транзиентный сбой чтения
PR (502/503/лимит) НЕ схлопывается с честным «ветка не agent-формы»: первый —
повторяемая ошибка без маркера, второй — `None` от резолвера и маркер
навсегда; иначе один 502 навсегда хоронит хвост, а строка отчёта утверждает
причину, которой код не знает. Сбой чтения СПИСКА хвостов уходит наверх и
красит прогон (ненулевой код возврата `main`) — единственный сигнал «жив ли
механизм вообще» (право issues/pull-requests read, транспорт).

Сценарий: хвост «Хвост чеклиста ревью PR #942» без маркера, PR #942 → ветка
`agent/939-*` → задача #939 несёт `area:process` → хвост получает
`area:process` + маркер одним вызовом; повторный пульс хвост не трогает.

Сценарий: у родителя не было `area:*` → хвост получает только маркер, отчёт
говорит «нет `area:*`-меток» (не «уже стоит»); область, полученная родителем
ПОЗЖЕ, переносится только после ручного снятия маркера.

Сценарий: `pulls/942` отвечает HTTP 502 → ⚠️ «сбой» по этому хвосту, маркер
не ставился ни в какой момент, остальные хвосты пульса обработаны.

## ADDED: Алерты Dependabot → задачи пула

Требование: каждый пульс отдельного periodic workflow читает открытые алерты
Dependabot (`state=open`, постранично; право `vulnerability-alerts: read` у
`GITHUB_TOKEN`) и заводит задачу пула (метки `task` + `dependabot-alert`) на
каждый алерт, номер которого ещё не отслежен. Текст задачи называет
пакет/severity/manifest-путь и `first_patched_version` — факт из ответа API,
не гипотеза; для алерта без выпущенного фикса текст говорит это прямо.

Требование: дедуп по номеру алерта в ДВА слоя над одним уже прочитанным
списком открытых задач с меткой (тот же приём, что failure_watch #610):
маркер `<!-- dependabot-alert-number: N -->` в теле И номер, прочитанный из
детерминированного заголовка задачи (`Dependabot alert #N: …`). Потеря
HTML-комментария правкой тела не делает алерт неотслеженным и вторую задачу
не заводит.

Требование: суточный потолок `DEPENDABOT_WATCH_DAILY_CAP` (5) новых задач на
календарные сутки, считается по факту СОЗДАНИЯ задач с меткой
(`state=all`, включая закрытые), не по текущей открытости. Исчерпание не
теряет отсечённое молча: каждый отсечённый алерт назван поимённо в отчёте,
плюс эскалация #120+Telegram ровно ОДИН раз на календарные сутки (дедуп
маркером с датой), сколько бы алертов ни отсеклось в одном пульсе.

Требование: нечитаемый счётчик потолка НЕ считается нулём — сбой чтения
счётчика отменяет ЗАВЕДЕНИЕ задач в этом пульсе (⚠️, алерты остаются на
следующий пульс; тот же приём, что `pulse_guard.failure_watch` на
нечитаемом счётчике), эскалация исчерпания при этом не уходит: потолок не
подтверждён, утверждать «исчерпан» — гадание. Нечитаемый список отслеженных
задач (слой дедупа) аналогично пропускает ВЕСЬ пульс завода/закрытия:
не знаем состав `tracked` — не гадаем, что он пуст.

Требование: газ — задача, чей алерт не среди открытых, закрывается сама по
ПЕРЕЧИТАННОМУ реальному алерту (точечное чтение по номеру, не только
«исчез из списка open»), с комментарием, называющим новое состояние.
Расхождение источников (список сказал «не open», точечное чтение отвечает
`open`) закрытию не подлежит: ⚠️ о расхождении, задача остаётся до
следующего пульса (класс «два источника разошлись», #687). Порядок — сначала
закрытие, потом комментарий: упавшее закрытие не оставляет открытую задачу с
лгущим комментарием «закрываю», который каждый следующий пульс постил бы
заново; упавший комментарий после успешного закрытия — ⚠️ без повтора.

Требование: сбой первичного чтения списка алертов уходит наверх — прогон
красный (ненулевой код возврата `main`). 403 без выданного права
`vulnerability-alerts: read` обязан красить прогон, а не становиться тихим ⚠️
в зелёном step summary НАВСЕГДА (постмортем #255: «конвейер простоял сутки
при сплошь зелёных прогонах»); право живёт только на default-ветке, поэтому
живой замер возможен только после мержа — пост-мерж проверка в теле PR #964.

Сценарий: открыт алерт #1, в пуле нет задачи с его номером → заведена одна
задача с маркером и метками `task`+`dependabot-alert`; повторный пульс
(и пульс после правки тела, потерявшей маркер, но с тем же заголовком)
вторую задачу не заводит.

Сценарий: за сутки уже заведено 5 задач-алертов, пришёл шестой → задачи нет,
отчёт называет #6 поимённо, в #120 уходит одна эскалация с маркером дня;
второй отсечённый алерт в том же пульсе второй эскалации не даёт; в
следующие календарные сутки потолок пуст сам — ручного снятия нет.

Сценарий: чтение `issues?state=all` (счётчик) отвечает 503 → ни одна задача
в этом пульсе не заводится, ⚠️ с причиной, эскалации нет; следующий пульс
считает счётчик заново и заводит.

Сценарий: алерт #1 закрыт как fixed, задача #500 отслеживает его →
точечное чтение отвечает `fixed` → PATCH `state=closed`, затем комментарий
«состояние: `fixed`»; повторного комментария на следующих пульсах нет —
закрытая задача не в open-списке.

Сценарий: списочный обход не видит алерт #1, точечное чтение отвечает
`open` → ⚠️ о расхождении источников, задача #500 остаётся открытой, ни
PATCH, ни комментарий не уходят.
