# orphan-consumers-watch: потребители для двух производителей без потребителя — хвост чеклиста ревью и алерты Dependabot (#961)

Задача: #961. Дельта-спека: [specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Аудит владельца 2026-09-11 нашёл двух «сирот» — производитель события есть,
потребителя нет:

**A. Хвост чеклиста ревью не наследует область.** `scheduler.py::after_merge`
заводит задачу «Хвост чеклиста ревью PR #N» с единственной меткой `task`,
хотя тело каждой такой задачи (`review_checklist.tail_issue_body`) прямо
обещает «Область и приоритет — как у породившего PR». Замер: 46 таких задач
за 5 дней, закрыто — 0: без `area:*` хвост конкурирует по номеру issue среди
всего свободного пула (`scripts/lib/free_task.py::issue_priority_key`
поднимает только `area:process` и блокирующие задачи), до находок очередь не
доходит.

**B. Алерты Dependabot не заведены в пул.** GitHub копит алерты сам (замер
2026-09-11: 1 открытый, `high`, пакет `sharp`), но в коде конвейера канал не
заведён вовсе (`git grep "dependabot/alerts"` по `scripts/` был пуст) — тот
же класс «производитель без потребителя», что уже закрыт для провалов CI
(#477, `pulse_guard.failure_watch`), только для другого источника фактов.

## Что делается

Два периодических потребителя, по одному на сироту. Оба — отдельные
workflows, не шаги `orchestra.yml` (тот же приём независимости, что у
остальных сторожей: свой планировщик, своя concurrency-группа, не общий
fail-domain с очередью слияний):

- **A. `checklist-tail-triage.yml` → `scripts/orchestra/checklist_tail_labels.py`**
  — резолвит PR хвоста → родительскую задачу (`task_ref.resolve_pr_task`,
  единственный источник — имя agent-ветки, тело PR не читается вовсе,
  решение владельца 2026-09-06) → её `area:*`-метки → переносит недостающие
  на хвост. Идемпотентность — маркер `checklist-tail:inherited`: разобранный
  хвост (включая честный случай «у родителя не было `area:*`») больше не
  разбирается обычным пульсом. Это не машинная оценка ценности (запрещена
  докстрингом `review_checklist.py`) — буквальный перенос уже принятого
  родителем решения. Правка `scheduler.py` (наследовать в момент создания
  хвоста, а не постфактум) — намеренная отсрочка: файл занят параллельными
  PR; место правки названо с точностью до строк в докстринге модуля, задача
  заведена из ревью PR #964. До той правки периодический проход —
  единственный путь наследования, после — страховка на случай сбоя сети в
  момент создания.
- **B. `dependabot-alert-watch.yml` → `scripts/orchestra/dependabot_alert_watch.py`**
  — заводит задачу (метки `task` + `dependabot-alert`) на каждый открытый
  алерт, ещё не отслеженный пулом; текст задачи называет
  пакет/severity/manifest-путь и версию фикса, которую уже предлагает
  Dependabot (`first_patched_version`) — факт, не гипотеза. Дедуп по номеру
  алерта (уникален, не переиспользуется GitHub) в ДВА слоя над одним
  обходом открытых задач (#610): маркер в теле ПЛЮС номер из
  детерминированного заголовка. Суточный потолок
  `DEPENDABOT_WATCH_DAILY_CAP = 5` по факту создания (`state=all`), массовый
  bump зависимостей не заливает пул; исчерпание эскалирует #120+Telegram
  ровно один раз на календарный день. Газ: каждый пульс перечитывает
  алерт каждой отслеженной задачи по номеру — перестал быть `open`
  (fixed/dismissed/auto_dismissed), задача закрывается сама.

Права: чтение алертов требует явного `permissions: vulnerability-alerts:
read` у `GITHUB_TOKEN` — отдельное право именно для этого эндпоинта,
задокументировано GitHub (флаг `vulnerability-alerts-permission`, `fpt: '*'`).
Живого замера права под `GITHUB_TOKEN` ДО мержа нет — честно «не
подтверждено» (`workflow_dispatch` с ветки PR GitHub не даёт); если право не
выдано, эндпоинт отвечает 403, и сбой первичного чтения красит сам прогон
(ненулевой код возврата), а не тонет тихим ⚠️ в зелёном step summary —
проверка переносится в пост-мерж тело PR #964.

## Тормоза и газ

Слияния не блокирует ни один из двух: потребители только заводят/закрывают
обычные задачи пула и ставят маркер идемпотентности. Тормоз с газом здесь
один — суточный потолок B: газ автоматический (окно 24ч уезжает само с
каждым пульсом), эскалация повторяется не чаще раза в календарные сутки,
отсечённые номера названы поимённо. Маркер A не тормоз, но и он не живёт
без названного газа: снятие метки руками (`gh issue edit --remove-label`) —
объявленная команда «переобработать» (docs/agents/LABELS.md).

Сбои разделены по значимости: сбой ПЕРВИЧНОГО чтения (список алертов, список
хвостов — единственный сигнал «жив ли механизм») красит прогон ненулевым
кодом; периферийный сбой (счётчик потолка, отдельный хвост/алерт/задача) —
⚠️-наблюдение без завода/закрытия в этом пульсе, следующий пульс повторит.
Нечитаемый счётчик потолка НИКОГДА не считается нулём: предохранитель,
действующий как «потолка нет» ровно в момент собственной слепоты, — тот же
класс silent-wrong, что постмортем #255.

## Отвергнутые варианты

В `docs/research/30-rejected-alternatives.md` оба потребителя отсутствуют:
периодический дешёвый опрос уже читаемого Issues/Alerts API — тот же класс,
что существующие сторожа конвейера, новой инфраструктуры не заводит. Шаг
внутри `orchestra.yml` отвергнут: общая concurrency-группа и общий fail-domain
с очередью слияний. Машинная оценка ценности хвостов отвергнута самим
`review_checklist.py` («решение человека») — здесь только перенос фактов.
Ежедневный дайджест одним issue вместо задачи на алерт отвергнут: задачи пула
— единственная форма, которую берут `free_task`/воркер; алгоритм дайджеста
завёл бы второй параллельный след вместо интеграции в конвейер.
