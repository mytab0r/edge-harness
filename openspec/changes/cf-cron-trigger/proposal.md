# cf-cron-trigger: Cloudflare Cron Trigger — независимый источник тактов для DO-пульса (#693)

Задача: #693. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Боль владельца

У конвейера не было источника тактов, не зависящего от его собственной
активности. DO-будильник (`cf-worker/src/harness.ts::alarm()`) 2026-09-07
выдал ≤2 диспатча оркестратора за ~20.5 часа при ожидаемых ~82 (измерение —
issue #689). Причина названа в #689 и НЕ чинилась там: если обе попытки
`ctx.storage.setAlarm` в `alarm()` падают (например исчерпание суточной
квоты `rows_written`, класс #320), `alarm()` выходит БЕЗ нового будильника;
восстановление — только `#ensureHeartbeat()` из конструктора DO, то есть
требует внешнего трафика к объекту. Трафика нет — мертво НЕОГРАНИЧЕННО
долго. GitHub `schedule` у `orchestra.yml` доставляется лишь у ~5-7% тиков
(`docs/research/21-github-actions.md`) — не альтернатива.

## Решение

Cloudflare Cron Trigger как внешние часы для `cf-worker`
(`docs/research/20-cloudflare-free.md`, «Cron Triggers на Free»: 5
триггеров/аккаунт, минимум 1 минута). Тик по расписанию (`*/5 * * * *`,
`cf-worker/wrangler.jsonc` `triggers.crons`) — это RPC-вызов к тому же
Durable Object (`cf-worker/src/index.ts::scheduled()` → `Harness#scheduledTick()`),
который пересоздаёт объект, если он был выгружен из памяти, и тем самым
перезакладывает будильник через уже существующий `#ensureHeartbeat()` —
чинит и такт, и невосстановимость одной мерой, без второй копии
dispatch-логики (`#dispatchOrchestraTick`, общий для `alarm()` и
`scheduledTick()`).

## Ключевой инвариант (находка ревью PR #696)

Такт оркестратора — теперь не только `alarm()`:

1. Cron-тик (каждые 5 минут) ВСЕГДА перезакладывает будильник через
   `await this.#ensureHeartbeat()` первой операцией — независимо от того,
   нужен ли на этом тике dispatch. Это чинит именно тот класс отказа,
   который описан в «Боль владельца»: alarm потерял себя, трафика к DO нет —
   cron это трафик, которого раньше не было.
2. Cron-тик дёргает `workflow_dispatch` (через тот же
   `#dispatchOrchestraTick`, что и `alarm()`) ТОЛЬКО когда чистая функция
   `pulseStale()` говорит, что здоровый `alarm()` подвис (успешный тик не
   обновлялся ≥ 2×`HEARTBEAT.selfOrchestrationMs`). Здоровый alarm тикает
   сам — cron в подавляющем большинстве вызовов не пишет ни одной строки,
   не дублирует dispatch в ту же минуту.
3. Отказ dispatch'а (`dispatch_ok: false`) — по-прежнему забота обычного
   `alarm()` на его собственном тике: `pulseStale()` нарочно возвращает
   `false` для этой ветки, страховка её не подхватывает и не путает с
   зависшим alarm'ом.

## Честная граница наблюдаемости

Если сам RPC-вызов (`env.HARNESS.get(id).scheduledTick()` в
`src/index.ts::scheduled()`) падает ДО того, как `scheduledTick()` успел
что-либо записать в pulse — `/api/status` не увидит и этого тика вовсе;
единственный след — Cloudflare Logs (`wrangler tail`/дашборд). Живой прогон
самого крона до деплоя не проверяется — только прод-форма
(`cloudflare:test`, `cf-worker/test/harness.spec.ts`).

## Бюджет триггеров

Единственный ДРУГОЙ владелец Cron Triggers на этом аккаунте — dsh-edge; его
конфиг деплоя (`.github/workflows/deploy-dsh-edge.yml`) `triggers` не
заводит вовсе. «Занят 1 из 5» подтверждено.

## Граница с #689 (do-pulse-watchdog)

#689 — только видимость факта смерти независимого канала
(`pulse_guard.independent_pulse_check`, метка данных
`triggering_actor.login`), не чинит `alarm()`. Эта задача — сам фикс (второй
независимый источник тактов вне DO), который #689 прямо называет отдельной
задачей. Не дублирует #689: тот сторож продолжает следить за отсутствием
`workflow_dispatch` от владельца токена; этот change чинит причину, из-за
которой такой дispatch мог не случиться неограниченно долго.

## Что вне рамок

- Изменение интервала `HEARTBEAT.selfOrchestrationMs` самого `alarm()`.
- Второй независимый будильник вне Cloudflare (например внешний cron-сервис)
  — Cron Trigger уже покрывает нужный класс отказа дешевле.
