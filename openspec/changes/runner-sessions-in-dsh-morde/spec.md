# Дельта-спека: журнал (journal-tasks-hands) и шов сессии раннера

## MODIFIED: Транскрипт сессии

Требование: транскрипт сессии раннера (сообщения, think, вызовы тулов) живёт
В DSH-сессии морды (воркспейс «edge-harness», имя «#N: задача»); журнал
edge-harness события сессии больше не получает и хранит только жизненный цикл
job (`job_start`, `bootstrap`, `agent_answer`, `stream_note`, `agent_error`,
`job_end`, heartbeat). Механизм один — дрен спула dsh-hands-streamer в
`POST /api/sessions/:id/ingest` морды.

Сценарий: раннер стартовал задачу → сессия создана/переиспользована в морде до
начала прогона; отказ создания — красный job.

Сценарий: прогон успешен, транскрипт пуст → красный job
(`stream_plugin_not_mounted` / `stream_no_events`), «не настроено» и «сломано»
различаются сообщениями.

Сценарий: слияние PR задачи → сессия `harness-<N>` архивируется оркестратором;
в активном списке морды остаются только живые задачи; архив читаем.

## ADDED: Проверка рендера транскрипта (#131)

Требование: после успешного дрена событий сессии в морду раннер (worker/hands,
единое место правды — `scripts/lib/dsh-edge-session.sh`) обязан прочитать
сохранённые события обратно (`GET /api/sessions/:id/events`) и проверить два
инварианта: (1) каждое `assistant/message` несёт непустые
`message.source.provider`/`.model`; (2) каждый `tool/call` находит парный
content-блок `{type:'tool-call', id==callId}` в каком-либо `assistant/message`
того же прогона. Нарушение — громкий warning в логе job'а (у hands —
дополнительно поле `transcript_render.issues` в `stream_note` журнала),
best-effort: не блокирует успешный прогон, поскольку не является частью
контракта ingest-маршрута (тот уже проверяется отдельно).

Сценарий: демо-наблюдение владельца (провайдер/модель-заглушка, «unavailable»
в деталях тула) — воспроизведено формой батча `dsh-edge/ingest-integration/
check.mjs` (assistant/message без content-блока tool-call), не сетевым сбоем;
структурная проверка ловит эту форму на каждом реальном прогоне.

## ADDED: Ingest-маршрут морды (патч 0004)

Требование: деплой dsh-edge обязан предоставлять аутентифицированный
`POST /api/sessions/:id/ingest`, принимающий батч канонических событий в форме
спула; неизвестный тип события — 400; батч флашится до ответа
(«принято = сохранено»); события видны живым подписчикам и в replay.

Сценарий: канарейка деплоя логинится, создаёт сессию-канарейку, инжестит батч,
архивирует её; любая неудача — красный деплой.
