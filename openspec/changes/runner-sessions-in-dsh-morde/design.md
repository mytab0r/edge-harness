# Дизайн: runner-sessions-in-dsh-morde

Задача: #119. Факты о dsh-edge — [research/12](../../../docs/research/12-dsh-edge-session-api.md).

## Развилки и выбор

### 1. Как сессия раннера попадает в морду: нативные RPC + один патч

Нативного «создать/переименовать/заархивировать» достаточно для скелета
(workspace.create идемпотентен, sessionId можно задать самому → create-or-reuse,
rename ставит пиннящийся заголовок с source kind user, который FirstPromptTitle
не перезаписывает). Для транскрипта апстримного API нет — события пишет только
агент-цикл. Варианты:

- **Спавнить в раннере настоящий DSH-прокси в DO** — отвергнуто: это и есть
  запрещённый реверс-туннель ([30-rejected-alternatives, п.3](../../../docs/research/30-rejected-alternatives.md)).
- **`session.prompt` с текстом транскрипта** — отвергнуто: запускает ход
  LLM-модели морды (деньги, чужая модель, ложные ответы в чате).
- **REST-маршрут импорта (выбрано)** — минимальный патч по прецеденту серии:
  append через штатные `Session.append` + `sessions.flush`, то есть события
  проходят ту же каноническую валидацию и персистенцию, что и нативные.
- **Клиентский плагин морды** — отвергнуто: рендер из своих данных = второй UI,
  а хранение всё равно требует серверного шва.

### 2. Кто маппит события: патч, не раннер

Спул уже несёт каноническую форму. Маппинг (allowlist, перенумерация turn,
surfaceOp) живёт в DO: (а) перенумерация требует чтения хранимого лога —
сервер знает базу, раннер нет; (б) одна точка правды валидации; (в) ретраи
батчей идемпотентны по позиции курсора, а не по содержимому.

### 3. Один механизм транскрипта

Журнальный стрим #112 (session_event в /api/events) снимается: дрен уходит в
морду целиком, журналу остаётся жизненный цикл job. Дельта-спека journal —
в этом change. Обратная совместимость чтения старых session_event в журнале
не ломается (write-путь просто перестаёт писать).

### 4. Идемпотентность и дубли

Ключ сессии детерминирован: `harness-<номер задачи>` (hands: `harness-<N>` из
`issue-<N>`, иначе sanitized TASK_ID). create-or-reuse делает ретрай/рестарт
безопасным; перезапущенный раннер дописывает заход новым turn'ом с
перенумерацией. Утечка дубликатов возможна только при «сервер принял батч,
но ответ потерялся» — журнальной дедупликации (UNIQUE seq) в морде нет,
вероятность оценена как приемлемая для просмотрщика (след в отчёте, см.
«Не подтверждено»).

### 5. Auth раннера

Кука владельца морды через `POST /api/auth/login` с `secrets.DSH_EDGE_ACCESS_KEY`
(тот же секрет, что у воркера dsh-edge; GH-secret добавляется владельцем
пост-мерж). Bearer HANDS_TOKEN не подходит принципиально: морда принимает
только свою куку ([research/12](../../../docs/research/12-dsh-edge-session-api.md)).

## Форма запроса ingest

```
POST /api/sessions/<sessionId>/ingest   (кука владельца; 1 MiB / ≤256 событий)
{"events":[{"type":"turn/start","data":{"turn":1}}, …]}
→ 200 {"appended":N,"lastSeq":M}
ошибки: 400 (allowlist/форма), 404 (нет сессии), 409 (BUSY — живой нативный ход),
413 (превышены потолки)
```

## Не подтверждено

- Визуальный рендер `tool/call`/`tool/result` в UI (replay API отдаёт; глазами
  проверит живая канарейка/владелец после мержа).
- Доля потерянных-после-приёма ответов (дубликаты батчей) — не измерялась.
- Поведение при одновременном ingest и нативном ходе в одну сессию: BUSY
  подтверждён по коду `openAgentForTurn`, живого прогона гонки не было.
