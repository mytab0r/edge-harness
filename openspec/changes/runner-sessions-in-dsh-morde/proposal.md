# runner-sessions-in-dsh-morde: сессии агентов-раннеров в нативной DSH-морде

Задача: #119. Директива владельца 2026-08-31: пока ход работы агента не виден
в морде, раннеры не гоняются (worker.yml disabled вручную). Смежное:
[dsh-streaming](../dsh-streaming/proposal.md) — стрим #112, который этот механизм
замещает (один механизм транскрипта, не два), и [dsh-edge-plugin-system](../dsh-edge-plugin-system/proposal.md)
— прецедент патч-серии.

## Зачем

Сегодня сессии раннеров живут эфемерно в job'е (DSH_HOME) и в морде невидимы:
в DSH UI видны только родные DO-сессии. Владелец не может открыть чат «что
делает агент по задаче #105» — сердце директивы «морда жива всегда, руки
поднимаются по требованию». Журнал edge-harness даёт стрим событий (слайс 2
dsh-streaming), но это второй, собственный UI-слой поверх чужой морды.

## Что делает

1. **Патч `0004-harness-ingest.patch`** к dsh-edge (применяется на деплое,
   [PATCHES](../../../dsh-edge/PATCHES.md)): `POST /api/sessions/:id/ingest` —
   батч канонических событий `{events:[{type,data}]}` в форме спула раннера;
   allowlist = allowlist спула; перенумерация turn поверх хранимого лога;
   поверхностные события встают в хвост (`surfaceOp:'append'`); батч флашится
   до ответа; публикация живым подписчикам — штатный late-event путь стора.
2. **Библиотека `scripts/lib/dsh-edge-session.sh`**: логин кукой владельца,
   RPC-конверт, `dsh_edge_session_begin` (workspace «edge-harness» + сессия
   `harness-<N>` + имя «#N: задача», идемпотентно), дрен спула → ingest,
   `dsh_edge_session_archive`.
3. **Раннеры**: worker `task.sh` и hands `dsh_task.sh` создают сессию на старте,
   монтируют dsh-hands-streamer (у воркера — новый шаг с pnpm-гвардией), дренируют
   спул в сессию во время прогона; журнал edge-harness с этого момента хранит
   ТОЛЬКО жизненный цикл job (job_start/bootstrap/answer/job_end) — транскрипт
   уезжает в морду. Отказы громкие: нет конфигурации, нет сессии, пустой
   транскрипт при успешном прогоне — красный job, с отдельным сообщением для
   «не настроено» и «сломано».
4. **Архив после слияния**: `scheduler.py` в `after_merge` архивирует
   `harness-<N>` для каждой задачи из тела PR (сессии может не быть — норма;
   морда недоступна — ⚠️ в отчёте оркестратора).
5. **Деплой-канарейка** `deploy-dsh-edge.yml` проверяет шов на живом проде:
   логин → сессия-канарейка → ingest → архив. Оркестратору и раннерам нужны
   `vars.DSH_EDGE_URL` и `secrets.DSH_EDGE_ACCESS_KEY` (имена — по
   docs/research/12).

## Критерий (по задаче)

- [x] Проект/воркспейс «edge-harness», имя сессии «#N: задача» — нативные RPC,
      проверено живым продом и локальной интеграцией.
- [x] Транскрипт полный: сообщения, think (reasoning-блоки), вызовы тулов —
      один механизм (сессия морды) вместо стрима #112.
- [x] Архив после слияния, архив не удаляется.
- [x] Отказ громкий (job красный), «не настроено» ≠ «сломано».
- [ ] Живая канарейка деплоя зелёная — после мержа (шаг в deploy workflow).
