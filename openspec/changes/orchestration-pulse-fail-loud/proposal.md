# orchestration-pulse-fail-loud: пульс оркестрации перестаёт молчать при сбое dispatch'а (#269)

Задача: #269. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Симптом

`.github/workflows/orchestra.yml` заявляет `cron: "*/15 * * * *"`, а
DO-пульс (`cf-worker/src/harness.ts`, `HEARTBEAT.selfOrchestrationMs`) должен
дублировать его собственным `workflow_dispatch` каждые 15 минут — GitHub'овский
`schedule` на этом репозитории ненадёжен: замер (116.3 ч, ADR 0005/`docs/research/21`,
раздел «Замер schedule на этом репозитории») показал доставку **31 из ~465**
ожидаемых тиков (**~6.7%**), то есть потерю ~93% событий, а не «schedule не
тикает вовсе». Задача #269 фиксирует конкретное окно: **7** прогонов по
расписанию за сутки вместо 96. В обоих случаях PR, полностью готовый к
слиянию (обе метки-гейта, все обязательные проверки зелёные), ждал слияния
часами, пока владелец не дёргал `workflow_dispatch` руками.

## Причина, найденная фактом

`Harness.alarm()` (`cf-worker/src/harness.ts`) ДЕЙСТВИТЕЛЬНО перезакладывает
следующий тик первой строкой, до какого-либо I/O — эта часть цепочки не рвётся.
Но сам dispatch orchestra.yml не проверял статус ответа GitHub вовсе:

```ts
try {
  await fetch(`${GITHUB.apiBase}/repos/${repo}/actions/workflows/${HEARTBEAT.orchestraWorkflow}/dispatches`, {...});
} catch (error) {
  console.log(`heartbeat dispatch failed: ...`);
}
```

`fetch()` не бросает на HTTP-ошибках — только на сетевых. Любой не-204 ответ
GitHub (403 — вторичный rate-limit GitHub ИЛИ блок egress Cloudflare Workers,
оба возможны и не различены этим кодом; 404 протухшего токена/репозитория; и
так далее) успешно резолвится и тихо трактуется как «успех» — тот же класс
силент-неправды, что уже был закрыт в `#postTask` (там `response.status !== 204`
проверяется явно), но не был закрыт здесь. Какой из кандидатов стоял за
конкретными провалами — см. «Что вне рамок», честный диагноз без гадания.
Этот путь тонул в `console.log`, который никто не смотрит между дедами.

**Подтверждено кодом:** дефект существует и воспроизводится (см. тест
`test/pulse.spec.ts` — 403/404 давали `ok:true` до правки). **Не подтверждено:**
какой именно код ответа (или сетевая ошибка) стоял за конкретными
многочасовыми провалами 2026-09-03/04 — production-логи `console.log`
(`wrangler tail`) для ретроспективы недоступны, доступны только `gh api`
метаданные прогонов (`event`, `created_at`, без тела ответа GitHub на
dispatch). Эта дельта делает следующий такой провал видимым немедленно через
`status.last_pulse.detail`, а не устанавливает причину прошлого.

## Что делается

- `attemptOrchestraDispatch()` — единственное место, где dispatch orchestra
  считается успешным: HTTP 204, и никакой другой код. Функция никогда не
  бросает, исход упакован в `{ ok, detail }`; `fetchImpl` инъецируется —
  тесты не ходят в реальный GitHub.
- Исход каждого тика — видимый durable-артефакт: таблица `pulse` (одна
  строка), поля `status.last_pulse` (`ts`, `dispatch_ok`, `detail`) и
  предвычисленный `status.pulse_healthy` (чистая функция `pulseHealthy`,
  тестируется отдельно от хранилища — образец `handsAreAlive`).
- Морда показывает бейдж «пульс не бьётся» тем же паттерном, что watchdog
  зависших задач (`status.stale_dispatch`).
- Гвардия-мутация (issue #269, docs заказчика): тест ловит именно «alarm не
  переустановился после сбоя dispatch'а» — доказано переносом `setAlarm()`
  ниже проверки токена (красный тест) и восстановлением (зелёный).

## Что вне рамок

- Сама причина отказов dispatch'а не устраняется этой дельтой — устраняется
  видимость отказа. Диагноз честно неполный: главный подозреваемый —
  измеренный (не гипотетический) блок 403 на весь `api.github.com` из egress
  Cloudflare Workers (`docs/research/21`, «GitHub API из egress Cloudflare
  Workers: измеренный блок 403», замер 2026-08-31) — задача #133; вторичный
  rate-limit GitHub (500 content-generating запросов/час при параллельном
  потоке PR-событий от нескольких агентов) — вторая версия, менее вероятная и
  тоже не измеренная под конкретное окно. Ни одна из двух причин не
  подтверждена именно для многочасовых провалов 2026-09-03/04: `wrangler
  tail` историю не хранит, а `gh api` не отдаёт тело ответа GitHub на
  dispatch. Перенос цикла слияний с канала `schedule` на канал с измеренной
  доставкой — отдельная задача #297.
- `#checkDshEdgeUpdate` (самообновление морды, #73) уже проверял `res.ok`
  корректно — не тронут.
