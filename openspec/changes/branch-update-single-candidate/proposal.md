# branch-update-single-candidate: один кандидат за слияние + метка не отстаёт от сервера (#252)

Задача: #252 (тот же класс, что закрыла `selective-branch-update`, второй заход —
диагностика владельца по логу прогона оркестратора 33904096031, 2026-09-04).
Дельта-спека: [specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`selective-branch-update` (#252, первый заход) сделала подтягивание веток
выборочным: `review_labels.should_update_branch` пропускает PR без обоих
вердикта и без метки `conflict`. Разбор реального прогона нашёл два новых
способа, которыми лишние PR всё равно подтягиваются или ре-ревьюятся.

### 1. Устаревшая метка в памяти (`scheduler.mark_conflicts`)

`mark_conflicts` снимает/ставит метку `conflict` через `gh api DELETE/POST`,
но не обновляла `pull["labels"]` в переданном объекте. `main()` передаёт тот
же список `pulls` дальше — в `unhealthy_pulls`, `merge_queue`, оттуда в
`update_remaining_pulls`. `review_labels.should_update_branch` там читает
устаревшую метку `conflict`, которую API уже удалил секундами раньше.

Замер 2026-09-04 18:06 (лог 33904096031): слияние #284 подтянуло #283, #282
(законно, у обоих оба вердикта) и ещё #253, #248 — у которых `ai:ok` не
было вовсе, только устаревшая `conflict`. Шесть прогонов ревью за минуту
вместо двух.

### 2. `update_remaining_pulls` подтягивает всех прошедших предикат разом

Предикат `should_update_branch` сузил МНОЖЕСТВО кандидатов, но не число
подтягиваний за вызов: если после слияния предикату соответствуют сразу
несколько PR (типичный случай — несколько PR одновременно получили оба
вердикта), `update_remaining_pulls` подтягивает их ВСЕХ одним проходом.
Подтягивание — это push, меняющий head: он сам может сбросить `ai:ok`
подтянутого PR (тот же механизм, из-за которого предикат вообще нужен) —
тот же цикл, что до #252, только уже на отфильтрованном множестве.

## Что делается

- `scripts/orchestra/scheduler.py::_set_conflict_label` — новая функция,
  единственное место, которое одновременно правит метку `conflict` на
  сервере (`gh api POST/DELETE`) и в `pull["labels"]` переданного объекта.
  `mark_conflicts` вызывает только её — постановка и снятие метки больше не
  могут разойтись между сервером и памятью прогона.
- `scripts/orchestra/scheduler.py::update_remaining_pulls` — максимум ОДИН
  успешно подтянутый кандидат за вызов (та же дисциплина, что уже у
  `merge_queue`: «ровно один PR за запуск», сериализация через возврат
  после первого действия). Предикат и порядок кандидатов не меняются.
  Кандидаты, пропущенные из-за занятого слота, получают отдельную строку в
  отчёте («уже обновлён этим запуском») — не молчаливый пропуск: следующий
  прогон оркестратора подтянет их (тот же газ без состояния, что у
  `should_update_branch` — предикат читает live labels).

## Что вне рамок

- Сам предикат `review_labels.should_update_branch` и `merge_label_gate` —
  не меняются, это фикс проводки состояния и частоты вызова, не условия.
- Полное удаление self-heal подтягивания рассматривалось и отклонено с
  уликой (замер владельца): `merge_queue` тоже подтягивает behind-PR, но
  возвращается сразу после первого слияния (#252, п.17), поэтому осматривает
  только часть списка за проход; прогоны оркестратора идут раз в 2–4.5 часа
  вместо заявленных 15 минут (#269, независимый дефект расписания, не
  предмет этой дельты). Самообновление веток существовало ещё до #196
  (коммиты 2026-08-28), и владельцу пришлось 11 раз руками гонять
  `update-branch` после трёх слияний без него — эмпирика против удаления.
- Гвардия на содержательно пустой/отрицательный PR, направления 1/3 issue
  #252 (пропуск AI-ревью при неизменном диффе, перенос вердикта) — не входят,
  как и в первом заходе.
