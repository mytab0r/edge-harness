17. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки подтягиваются из main серверным токеном (с правом
    зажигать проверки) ВЫБОРОЧНО — только PR, у которого либо уже стоят оба
    вердикта из п.15 (`review:ok` И `ai:ok` — он реально близок к слиянию),
    либо PR помечен `conflict` (подтягивание может расшить конфликт).
    PR без обоих вердиктов, в доработке или с `ai:changes-requested`
    автоматически не подтягивается — одно место правды предиката,
    `review_labels.should_update_branch`, общее для обеих точек вызова
    (после слияния и при `mergeable_state == "behind"` в очереди слияния).

    Метка `conflict`, которую этим же прогоном ставит или снимает
    `mark_conflicts`, не может остаться устаревшей для предиката: постановка
    и снятие идут через единственную функцию (`scheduler._set_conflict_label`),
    которая правит и сервер (`gh api POST/DELETE`), и объект PR из того же
    списка, что `main()` передаёт дальше в очередь слияния и в подтягивание
    остальных. Раньше метка снималась/ставилась только на сервере — предикат
    читал устаревшее значение из памяти прогона (замер 2026-09-04, лог
    оркестратора 33904096031: слияние #284 подтянуло #253/#248 без `ai:ok`
    только из-за неотражённого снятия `conflict`).

    Из PR, прошедших предикат, за весь прогон планировщика подтягивается
    НЕ БОЛЕЕ ОДНОГО — не за вызов одной функции. Слот общий для ОБЕИХ точек
    вызова из п.17 (после слияния и behind-ветка очереди слияния) и живёт
    внутри самого `update_branch` (единственная функция, откуда уходит
    `gh pr update-branch`), а не локальной переменной в каждой точке вызова
    отдельно — иначе вторая точка обходила бы лимит первой тем же прогоном.
    Дисциплина п.16 (на момент этой дельты — «ровно один PR за запуск» у
    слияний; после `orchestra-event-merge-loop`/#297 — потолок
    `MERGE_LOOP_MAX_MERGES` за проход цикла, п.16 спеки помечен устаревшим)
    про другое действие — `merge`, не `update-branch` — и на подтягивание
    веток не распространяется; это отдельный, но той же формы лимит.
    Слот `update_branch` из этого пункта по-прежнему один за ПРОХОД (проход —
    вызов `merge_queue()` внутри цикла), это не менялось #297. Подтягивание —
    push, меняющий head, а это само способно сбросить `ai:ok` следующего
    кандидата тем же циклом, который и делает нужным предикат выше.
    Кандидаты сверх первого получают отдельную строку отчёта (не молчаливый
    пропуск) с указанием, что их подтянет следующий прогон.

    Газ (обязателен, автоматический): предикат не хранит состояния — он
    читает текущие labels PR при каждом прогоне оркестратора. Как только PR
    получает оба вердикта из п.15 или помечается `conflict`, САМЫЙ
    СЛЕДУЮЩИЙ прогон снова начинает его подтягивать без ручного
    вмешательства — то же самое верно для кандидата, которому не хватило
    общего слота «один за прогон» в этот раз: следующий прогон обнуляет
    слот и видит кандидата заново.
