# Дельта-спека: journal-tasks-hands (contract-task-from-branch, #394)

Уточняет п.17 главной спеки `openspec/specs/journal-tasks-hands.md`: контракт
резолвит задачу PR через тот же узкий механизм, что и резолвер AI-ревью
(п.17.1), а не отдельным прямым чтением декларации тела.

17. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки обновляются из main токеном с правом зажигать
    проверки.

    17.0. Задача PR для контракта — `task_ref.pr_task_candidates(pull)`:
        имя agent-ветки (`agent/<N>-<slug>`) первым кандидатом, декларация
        первой строкой тела (`task_ref.declared_tasks`) вторым, без
        повторов. Контракт пробует кандидатов по порядку и берёт первого,
        для которого задача пригодна (issue, не PR; открыта; помечена
        `task`; не помечена `blocked`) — не обязательно первого в списке.
        Живой случай: задача закрыта раньше срока («закрытая задача не
        переоткрывается»), докрытие оформлено НОВОЙ узкой задачей,
        объявленной первой строкой тела — ветка (создаётся один раз,
        `scripts/git/task-branch`) продолжает называть старую закрытую;
        контракт обязан подхватить пригодную задачу из тела, а не отказать
        на закрытой из ветки (замер 2026-09-06: 4 из 30 открытых PR
        репозитория в этом состоянии). Симметрично — «другой открытый PR на
        ту же задачу» (правило 5 выше по тексту) — это PR, у которого та же
        задача среди ЕГО кандидатов, не только в декларации тела.
        Прямого чтения `task_ref.declared_tasks`/`declares_task` для вопроса
        «какая задача у PR» в контракте нет — только через
        `pr_task_candidates`.
        Отказ («задача не определена») называет действие: назвать ветку
        `agent/<N>-<slug>` через `scripts/git/task-branch` (основной
        источник) либо, если ветка не такой формы, поставить номер задачи
        первой строкой тела.

### Резолвер «PR → задача» для контекста AI-ревью (#259)

17.1. Задача, которую AI-ревью (второй гейт) показывает модели как контекст
    PR, — результат ОДНОГО резолвера (`scripts/lib/task_ref.resolve_pr_task`):
    имя agent-ветки `agent/<N>-<slug>`, затем декларация номера первой
    строкой тела PR (`declared_tasks`, то же правило, что и в п.17.0). Любое
    упоминание номера в прозе описания (`task_ref.extract_task_refs`/
    `references_task`) для этого вопроса не годится — этим классом бага
    ai_review.py путал задачу PR с первым попавшимся числом в тексте (живой
    замер: #253 судили по #120 вместо объявленного #227, #248 — по #119
    вместо #201, #247 — по #43, #263 — по #4). Ни один источник не дал
    числа → у PR нет задачи из пула для контекста ревью, это не ошибка.
    Правила `reap_stale`/`unhealthy_pulls`/`after_merge` намеренно
    продолжают использовать широкую семантику упоминания — сужение там
    было бы регрессией, не улучшением.

    17.1.1. `resolve_pr_task` схлопывает источники в ОДИН ответ (ветка
        приоритетна всегда) — годится там, где нужен единственный номер без
        сети (контекст ревью, поиск PR-преемника в приёмке). `pr_task_candidates`
        (п.17.0) не схлопывает: контракту и приёмке нужны ОБА узких
        кандидата отдельно, потому что решение, какой из них использовать,
        зависит от пригодности задачи (сетевой факт — состояние issue),
        которую сам резолвер не проверяет.

17.2. Контракт не выполняет ни одного изменяющего вызова (авто-назначение
    исполнителя, сверку дубликата PR) над задачей, признанной непригодной.
    Пригодность считается ОДИН раз, до любых действующих вызовов
    (`contract_check.task_eligibility_problems`): задача существует как
    issue (не PR), открыта, несёт метку `task`, не несёт `blocked`.
    Непригодна хотя бы по одной причине — контракт только докладывает
    причину(ы), дальше по этой задаче не действует вовсе (живой случай:
    авто-назначение на уже закрытую задачу до этого пункта, PR #359).
    Если непригоден только ПЕРВЫЙ кандидат (обычно ветка) и есть второй
    (обычно декларация тела), который пригоден, — используется второй
    (см. п.17.0, переориентация в реворке).

### Приёмка: слитый PR регистрируется под каждым кандидатом (#394)

17.3. `scheduler.py::merged_pr_map` (Task#N → слитый PR для стадии приёмки,
    #227) регистрирует слитый PR под КАЖДЫМ кандидатом из
    `pr_task_candidates`, не только первым: приёмка ищет PR по номеру
    ОТКРЫТОЙ задачи пула, а закрытая задача, которую называет устаревшая
    ветка после реворка, туда не входит — вторая запись безвредна, находится
    только запись под настоящим (актуальным) номером.
