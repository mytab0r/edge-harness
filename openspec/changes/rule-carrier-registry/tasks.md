# tasks.md: rule-carrier-registry (ходячий скелет)

Три пункта (считая обязательный «завести задачу пула» и завершающий
«перенести дельту в источник правды» — оба стандартная административная
рамка, не содержание скелета) — это скелет, не миграция. Весь код и ОДИН
шаг CI — в единственном содержательном пункте 1, не разделены на
несколько: разделять схему/валидатор и харнес/CI на отдельные пункты для
двух правил в реестре не даёт параллельности (харнес зависит от
загрузчика, загрузчик без харнеса не доказывает ничего), а лишь оставляло
бы окно, где новый `test_*.py` уже в дереве, но ещё не подключён ни к
одному шагу `repo-ci.yml` — ровно та находка разбора («ORPHAN-TEST-OK не
может быть способом отложить подключение»), которую этот план обязан не
воспроизвести.

## 1. Реестр правил — ходячий скелет: схема, валидатор, мутация одного правила, подключение к CI

- [ ] `docs/agents/rules/README.md` — формат шапки (`id`, `statement`,
      `carrier`, `proof_test`, `status`) и таблица согласованности по
      `status` (design.md, раздел A) и `scripts/lib/rule_registry.py` —
      загрузчик (`load_rules()`) + `validate(rule)`: обязательность всех
      пяти полей, `id` = имя файла, резолвинг `carrier` для Python через
      `ast.parse` (функция/класс/константа верхнего уровня либо
      `Class.method`), резолвинг `proof_test` через
      `pytest --collect-only -q <node>` (код 0, ровно одна строка узла в
      выводе — design.md, раздел C, «Проверенные факты о pytest»),
      абсолютный пол (`total_rules_loaded() > 0`, иначе `RuntimeError` —
      директория непуста, но распарсено 0 правил, это поломка загрузчика,
      не «нечего проверять»).
- [ ] `scripts/lib/test_rule_registry.py` — тесты валидатора на
      ИЗОЛИРОВАННЫХ фикстурах (временная директория с игрушечными
      файлами правил, не боевые записи из `docs/agents/rules/`, чтобы
      тест не зависел от их будущих правок): отсутствующее поле → отказ;
      `id` ≠ имя файла → отказ; `status: none` разрешает `carrier`/
      `proof_test` в форме `"none: ..."`/`"none"`; `status: proven` с
      нерезолвящимся `carrier` → отказ; `proof_test`, резолвящийся в 0
      или 2+ узлов → отказ; директория с файлами, но 0 распарсенных
      правил → `RuntimeError`; отсутствующая или пустая директория
      правил → `RuntimeError` тоже (44.3: окна «до первой записи» нет).
      Один из этих тестов — узел
      `test_validate_rejects_missing_statement` — становится
      `proof_test` записи из следующего пункта.
- [ ] Две боевые записи реестра: `docs/agents/rules/
      rule-registry-requires-core-fields.md` (`status: proven`, `carrier:
      scripts/lib/rule_registry.py::validate`, `proof_test:
      scripts/lib/test_rule_registry.py::test_validate_rejects_missing_statement`)
      и `docs/agents/rules/relative-markdown-links.md` (`status: none`,
      `carrier: "none: гейт не заведён"`, тело со ссылкой на
      `AGENTS.md:212-213`).
- [ ] `scripts/lib/mutation_harness.py`, режим `--rule <id>` (design.md,
      раздел C): health-check `proof_test` на текущем дереве (не `exit=0`
      → «носитель нездоров», это НЕ мутация); проверка адресата мутанта
      ДО применения (`git apply --numstat`, патч не применяется):
      каждый файл патча — файл `carrier`, файл `proof_test` в патче
      запрещён, иначе «мутант устарел» (design.md, раздел C, шаг 2);
      `git apply docs/agents/rules/mutants/<id>.diff` (не применился →
      «мутант устарел»); повторный `proof_test` с разбором кода выхода
      (`1` → доказано; `0` → «мутант выжил»; `2/3/4/5` → «харнес не смог
      проверить: pytest exit=<N>», отдельная категория, не «доказано» и
      не «выжил»); `git apply -R` ВСЕГДА в `finally`, включая путь, где
      предыдущий шаг упал. Без `git worktree` — мутация и откат работают
      прямо в рабочем дереве (design.md обосновывает упрощение для
      одного мутанта). Неизвестный `--rule <id>` — явная ошибка на
      stderr с перечнем известных id и ненулевой код выхода, не тихий
      `exit 0`. Пустой/недогруженный реестр (0 распарсенных правил при
      непустой директории) — красный результат ПЕРЕД обработкой любого
      конкретного `--rule`.
      `docs/agents/rules/mutants/rule-registry-requires-core-fields.diff`
      — реальный unified diff, убирающий проверку «`statement` непустой»
      внутри `rule_registry.py::validate` (патчит носитель, не
      `test_rule_registry.py` — design.md, раздел C, «Формат мутанта»).
- [ ] `scripts/lib/test_mutation_harness.py` — самотест на изолированной
      fixture (временный git-репозиторий во `tmp_path`, свои игрушечные
      carrier/test/mutant-файлы — не боевое дерево репозитория, чтобы
      порча мутанта в тесте не рисковала настоящим рабочим деревом):
      здоровый носитель + валидный мутант → «доказано»; изначально
      красный `proof_test` → «нездоров», не «доказано»; неприменимый
      мутант (патч на несуществующую строку) → «мутант устарел»;
      мутант-заглушка (no-op diff, ничего не меняющий по существу) →
      «мутант выжил»; мутант, правящий чужой файл (не файл `carrier`) →
      «мутант устарел»; мутант, правящий сам файл `proof_test` →
      «мутант устарел», не «доказано» (44.4.4); переименование
      `proof_test`-файла между
      health-check и мутацией → «харнес не смог проверить: pytest
      exit=4»; неизвестный `--rule <id>` → явная ошибка, ненулевой код;
      пустой реестр (0 файлов на диске) → красный результат независимо
      от `--rule`.
