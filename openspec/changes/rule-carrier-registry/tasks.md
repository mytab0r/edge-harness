# tasks.md: rule-carrier-registry

Разметка файлов ниже — по замыслу: каждый пункт создаёт СВОИ новые файлы,
пересечения с соседним пунктом по файлам нет, кроме явно помеченных
последовательных зависимостей и пунктов 11–12 (правка «горячих» файлов
`scripts/orchestra/repo_invariants.py` и `.github/workflows/repo-ci.yml` —
делать последними, непосредственно перед мержем, с ребейзом на свежий
`origin/main`, по аналогии с тем, как другие change в этом репозитории
обращаются с горячими файлами).

Зависимости: 2 и 3 требуют схему из 1 (парсер `rule_registry.py` уже
существует); 4 требует схему из 1; 9–10 требуют, чтобы миграция (5–8) дала
100% покрытие 40 правил (design.md, «Миграция», п.6); 11 не зависит от
остального технически, но по смыслу полезна после 8 (иначе сироты ещё не
размечены и гвардия сразу красная без объявленного газа — `AGENTS.md`,
«Тормоз без газа не принимается»); 12 требует 3+4 готовыми и протестированными
локально; 13 не зависит ни от чего кроме 2; 14 требует 12+13 слитыми.

## 1. Схема реестра, валидатор, два иллюстративных правила

Исполнитель: воркер/агент. Новые файлы: `docs/agents/rules/_sections.yml`
(список секций `id → заголовок + вступительный абзац`, design.md раздел B),

`scripts/lib/rule_registry.py` (загрузчик: читает все `docs/agents/rules/
*.md` кроме `_sections.yml`/`README.md`/`mutants/**`, парсит YAML-шапку +
тело, возвращает список записей), `scripts/lib/test_rule_registry.py`
(гвардия схемы: обязательные ключи, `scope` ⊆ `{human, worker, reviewer,
hands, system}`, `id` совпадает с именем файла, согласованность
`carrier_status`/`carrier`/`proof` по таблице design.md раздела A, ссылка
в `carrier` резолвится в реально существующий файл/символ на момент
проверки). Плюс два иллюстративных файла реестра на уже существующих,
доказанных носителях — `docs/agents/rules/task-ref-single-resolver.md`
(правило из `AGENTS.md:203-206`, носитель
`scripts/lib/task_ref.py::resolve_pr_task`) и `docs/agents/rules/
pagination-guard-required.md` (правило из `AGENTS.md:206-208`, носитель
`scripts/lib/test_pagination_guard.py`) — оба ставятся с `carrier_status:
pending` на этом шаге (proof появится в п.2), не `proven` раньше времени.
Приёмка: `python -m pytest scripts/lib/test_rule_registry.py -q` зелёный
на этих двух файлах; мутация гвардии (снять проверку обязательности
`scope` → тест на файле с пустым `scope` красный; вернуть — зелёный).

## 2. Мутационный харнес + первые два мутанта

Исполнитель: воркер/агент. Зависит от 1 (использует `rule_registry.py`).
Новые файлы: `scripts/lib/mutation_harness.py` (design.md раздел C:
`git worktree add --detach`, `git apply <mutant>.diff`, запуск
`proof_test`, `git worktree remove`; режимы `--rule <id>`, `--changed
--base <ref>`, `--all`), `scripts/lib/test_mutation_harness.py`
(самотест харнеса на фикстуре — маленький выдуманный «носитель» и мутант в
`scripts/lib/testdata/`, не боевое правило, чтобы тест харнеса не зависел
от содержания реестра), `docs/agents/rules/mutants/
task-ref-single-resolver.diff`, `docs/agents/rules/mutants/
pagination-guard-required.diff` — реальные мутанты для двух правил из п.1,
после написания которых их `carrier_status` в файлах правил меняется на
`proven`, а `proof` — на `mutation:docs/agents/rules/mutants/<id>.diff`
(правка тех же двух файлов правил, не создание новых — не конфликтует ни
с чем, п.1 уже слит). Приёмка: `python scripts/lib/mutation_harness.py
--rule task-ref-single-resolver` и `--rule pagination-guard-required`
оба заканчиваются кодом 0 (мутант доказанно ловится); намеренная порча
мутанта (сделать его no-op, например заменить содержательную строку на
пустую) даёт код ≠0 с сообщением «мутант выжил» — это и есть доказательство,
что харнес различает «поймал» и «не поймал», а не всегда зелёный.
