# rule-carrier-registry: правило → носитель → доказательство → исполнитель

Задача владельца: спроектировать развязку между нормативным текстом
(`AGENTS.md` + `docs/agents/PROTOCOL.md`) и тем, что реально исполняет и
проверяет правило. Issue в пуле не заведена этим change (владелец открывает
PR сам, задача — п.0 tasks.md).

## Класс проблемы

Правило, написанное прозой, и правило, которое нельзя нарушить — разные
вещи, и сегодня в репозитории нет механизма, который бы отличал одно от
другого на масштабе всего свода. Пять измерений одного и того же класса
(разбор `AGENTS.md` + `docs/agents/PROTOCOL.md`, 2026-09-07):

1. **Носитель есть не у всех.** 40 нормативных правил, исполняемый носитель
   (гвардия/шаг CI/hook) — у 24, из них доказан красным прогоном на реальном
   входе — только у 7. У 16 носителя нет вовсе, в том числе:
   - R29, «секреты не попадают в репозиторий» (`AGENTS.md:219-225`) — ни
     `gitleaks`, ни `trufflehog`, ни `detect-secrets` не встречаются ни в
     одном `.github/workflows/*.yml`; репозиторий публичный;
   - R27, «ссылки — относительный markdown, не wiki-links»
     (`AGENTS.md:212-213`) — механизируется одним grep-гейтом, но такого
     гейта нет.

2. **Носитель, который сам не доказан.** Класс «гвардия есть, но красный
   случай не воспроизведён автоматически, только словесная инструкция в
   докстринге "поменяй X руками — покраснеет"»:
   `scripts/lib/test_task_ref_usage_guard.py`,
   `scripts/lib/test_pagination_guard.py`, `scripts/lib/test_label_registry.py`.
   Сам инвариант репозитория «Тормоз без газа не принимается»
   (`AGENTS.md:127-136`) — того же рода: текстовое правило про правила,
   без механической проверки, что оно само выполняется каждым новым
   тормозом. Это и есть корень наблюдения «свежие гвардии рождаются
   слепыми» — гвардия проходит код-ревью зелёной, потому что рецензент
   поверил докстрингу, а не воспроизвёл мутацию.

3. **До облачного исполнителя доходит не свод правил, а его случайный
   срез.** `scripts/worker/task.sh` собирает промпт воркера на строках
   299–327 и вшивает в него `docs/agents/WORKER-PLAYBOOK.md` целиком через
   `cat` (`task.sh:326`, файл ~13 817 байт). Из `AGENTS.md` (~24 710 байт) и
   `docs/agents/PROTOCOL.md` (~44 686 байт) в промпт не попадает НИ БАЙТА
   содержимого — только markdown-ссылка на них внутри плейбука
   (`WORKER-PLAYBOOK.md:5`), которую воркер обязан сходить прочитать сам
   (и не обязан этого делать, если решит, что плейбука достаточно).

4. **Часть правил не доходит вообще ни до одного канала.** Grep по
   `task.sh` и `WORKER-PLAYBOOK.md` даёт ноль совпадений на: «issue только
   через `scripts/gh/issue-create`» (`AGENTS.md:31-35`), «работать в
   `openspec/changes/<id>`» (`AGENTS.md:217`), «закрытая задача не
   переоткрывается» (`AGENTS.md:36-42`).

5. **Одно правило — три версии разными словами.** «PR только через
   `scripts/git/pr-create`» и «`Closes/Fixes/Resolves` запрещены» объявлены в
   `docs/agents/PROTOCOL.md:161` и `:167-173`, в `AGENTS.md` их текста нет
   вовсе, а `task.sh` (собирает промпт исполнителю) сочиняет для них третью,
   самостоятельную формулировку (`task.sh:296`,
   `"Closes/Fixes/Resolves ЗАПРЕЩЕНЫ — контракт отклонит такой PR"`) —
   ровно тот класс, который правило репозитория «Одно место правды»
   (`AGENTS.md:82-83`) запрещает, применённый к самому своду правил.

Отдельно от текста правил — устройство каналов, в которые правила должны
попадать:

6. Третий канал исполнения, `scripts/hands/dsh_task.sh:147-170`, отдаёт
   агенту сырой `TASK_TEXT` из журнала без единого правила репозитория —
   самый бедный по доставке из трёх (worker/review/hands).
7. Промпт ревьюера (`scripts/review/ai_prompt.md:7-12`) несёт свой отдельный
   короткий список правил и не ссылается ни на `AGENTS.md`, ни на
   `PROTOCOL.md` — платный гейт судит дифф, не зная правил проекта, которые
   этот дифф обязан соблюдать.

## Цена бездействия

- **Правило без носителя неотличимо от пожелания.** Пример уже оплачен:
  правило «PR по шаблону, Closes/Fixes/Resolves запрещены»
  (`PROTOCOL.md:167-173`) существует с момента написания протокола, но
  фактическую защиту дал только `scripts/git/pr-create` (обёртка,
  issue #496) — до неё запрет жил только в тексте, который исполнитель мог
  прочитать или нет.
- **Правило без доказательства падает молча, когда перестаёт работать.**
  Живой случай: семантика `task_ref` жила в докстринге, пока `ai_review.py`
  не взял не ту функцию — четыре PR судились по неверной задаче месяцами,
  прежде чем гвардия (`scripts/lib/test_task_ref_usage_guard.py`) вообще
  появилась в CI (`AGENTS.md:203-206`); докстринг-инструкция «мутируй руками,
  проверь» не гоняется автоматически, то есть регресс той же формы завтра
  снова не будет замечен до следующего инцидента.
- **Починенный случай не закрывает класс.** Скан `.github/workflows` только
  по суффиксу `*.yml` (файл `*.yaml` проходит мимо) чинился дважды (задача
  #146: `scripts/lib/collect_labels.py:112`,
  `scripts/lib/test_infra_gh_inventory.py:41`) и остаётся живым ещё в трёх
  местах — `scripts/lib/exec_bit_guard.py:120`,
  `scripts/lib/orphan_test_guard.py:161`,
  `scripts/lib/test_pr_body_label_release_reachable.py:169` — потому что
  «починил случай — закрой класс» (`AGENTS.md:63-65`) само не имеет
  носителя: чинящий не обязан пройтись по остальным вхождениям класса,
  ничто его не заставляет.
- **Облачный исполнитель работает по значительно более узкому своду, чем
  тот, что написан для человека.** Пока доставка правил в промпт зависит от
  того, вспомнил ли автор `task.sh` вписать конкретную фразу вручную (как
  это уже произошло с `Closes/Fixes/Resolves`, п.5 выше), каждое новое
  правило в `AGENTS.md`/`PROTOCOL.md` по умолчанию НЕ действует на
  воркера/ревьюера/руки, пока кто-то отдельно не подтянет его текст в три
  разных файла тремя разными руками.

## Что уже сложилось и на чём строить

В репозитории уже два равноправных уровня носителей, оба рабочие:

- `scripts/orchestra/repo_invariants.py` — снимки состояния (issues/PR/
  openspec), формат `check_<имя>(данные) -> list[dict]`, плюс `CI_GATING` и
  `GATING_RELEASE_CONDITION` (`repo_invariants.py:193-212`), где `main()`
  падает громко, если у гейтящего инварианта не назван газ
  (`repo_invariants.py:951-958`).
- Россыпь `scripts/**/test_*_guard.py` — гвардии по исходному коду
  (регэксп/AST-сканирование конкретного класса нарушения).

Этот change не заводит третий параллельный реестр — он даёт обоим уровням
общий фронт: единый машиночитаемый реестр правил, из которого
генерируются документы для людей и промпты для трёх каналов исполнения, а
доказательством связи «правило ↔ носитель» становится не текст докстринга,
а воспроизводимый красный прогон.

## Scope

In:
- Формат и место хранения единого реестра правил (id, формулировка, scope,
  carrier, proof) — design.md, раздел A.
- Генерация `AGENTS.md` и промптов трёх каналов (worker/review/hands) из
  реестра, с гейтом «сгенерируй и сравни» — design.md, раздел B.
- Мутационный харнес как единственная форма доказательства «носитель
  реально ловит нарушение» — design.md, раздел C.
- Храповик долга по 16 правилам без носителя, с честным разделением
  «носителя нет пока» / «механизировать нельзя» — design.md, раздел D.
- Правило обратной связности: носитель без правила в реестре — тоже
  дефект, решение без раздувания `AGENTS.md` прозой на инцидент —
  design.md, раздел E.
- Порядок миграции всех 40 правил в реестр, без замены существующего кода
  оркестрации (`repo_invariants.py`, `test_*_guard.py`) — design.md,
  «Миграция», и tasks.md.

Out (см. design.md, «Что мы не делаем и почему»):
- Реализация самого реестра, генератора, харнеса и гвардий — это тексты
  задач в tasks.md для будущих исполнителей, не код этого change.
- Правки `cf-worker/**`, `.github/workflows/{deploy-worker,inbox-issue,
  repo-ci}.yml`, `scripts/lib/{review_labels,test_pagination_guard,
  exec_bit_guard,orphan_test_guard,test_pr_body_label_release_reachable}.py`,
  `scripts/orchestra/{contract_check,pulse_guard,repo_invariants,
  scheduler}.py`, `scripts/review/{ai_review,check_pr}.py`,
  `docs/agents/LABELS.md`, `dsh-edge/{verify-ingest-allowlist,
  smoke-edge-plugins}.mjs` — заняты параллельными агентами; design.md
  называет точки подключения к ним как задачи для будущего исполнителя,
  не трогает их этим change.
- Переоценка `REWORK_BUDGET`, приоритезация задач, любые константы других
  открытых change — не в рамках.
- Полный перенос текста всех 40 правил в файлы реестра руками этого
  change — только формат и первые опорные примеры (см. tasks.md, миграция
  разбита на исполняемые куски для отдельных агентов).

## Acceptance criteria

1. Design.md называет физический формат и путь реестра, обоснование
   конфликтоустойчивости при параллельном редактировании (много агентов
   одновременно правят разные правила).
2. Design.md называет конкретные workflow и шаги CI, куда подключаются:
   гейт «сгенерируй и сравни», мутационный харнес (per-PR выборочно + по
   расписанию полным прогоном), храповик долга.
3. Design.md отдельно перечисляет правила без носителя (16), с разбивкой
   «носителя нет пока» vs «механизировать нельзя» и причиной для каждого
   случая второго рода.
4. Design.md называет механизм для 7 уже найденных «носителей-сирот» (гвардия
   без правила в реестре) — не требующий прозы в `AGENTS.md` на каждый
   инцидент.
5. tasks.md — исполняемый чек-лист, разбитый так, что ни один пункт не
   требует правки того же файла, что и параллельный пункт (кроме явно
   помеченных последовательных шагов над «горячими» файлами).
6. Ни один файл вне `openspec/changes/rule-carrier-registry/` не изменён
   этим change (кроме случаев, где сам процесс git требует иного — таких
   нет).

## Риски / неподтверждённое

- Оценка стоимости мутационного прогона (design.md, раздел C) — замер
  локальный, на Windows/Git Bash, репозиторий 7.1 МиБ без `.git`/
  `node_modules`; фактическое время на раннере GitHub Actions (Ubuntu,
  холодный чекаут) не измерено этим change — план: замерить на первом
  реальном прогоне харнеса (tasks.md, отдельный пункт).
- Число «40 нормативных правил» и «24 носителя» — подсчёт вручную по двум
  файлам (`AGENTS.md`, `docs/agents/PROTOCOL.md`), не автоматизирован;
  граница «что считать отдельным правилом» местами дискуссионна (например,
  один абзац может нести два требования). Это не меняет порядок величины
  вывода (носителя нет у существенной доли правил), но точное число может
  на 1–2 разойтись при повторном подсчёте другим человеком.
- Полный список всех 40 правил с их id/scope/carrier/proof не приведён в
  этом proposal — он и есть содержание миграции (tasks.md), делать его
  вручную здесь означало бы писать код/данные продукта в документе
  предложения, а не проектировать механизм.
