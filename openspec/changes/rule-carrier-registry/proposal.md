# rule-carrier-registry: правило → носитель → доказательство (ходячий скелет)

Задача: #648. Ветка `agent/648-rule-carrier-registry-v2`. Это третья
версия (v3) этого change: первая
(ветка `design/rule-carrier-registry`, без задачи пула — нарушение
контракта, найдено первым разбором) и вторая (design v2, эта же ветка)
получили от враждебного разбора вердикт «переделывать» дважды подряд
(14 и 18 блокеров) по одной и той же причине — design проектировал
реестр, генератор, два храповика, ночной прогон и канарейку дублирования
прозы одним предложением, и каждый механизм цеплял три соседних настолько
плотно, что рвался на стыках при независимой проверке. Решение владельца
процесса: перестать проектировать всё сразу и сдать ходячий скелет —
минимальный работающий цикл «правило → носитель → доказательство» на
ОДНОМ правиле, прежде чем расширять на остальные 39.

## Класс проблемы

Правило, написанное прозой, и правило, которое нельзя нарушить — разные
вещи. Разбор `AGENTS.md` + `docs/agents/PROTOCOL.md` (2026-09-07) находил
пять граней этого класса; две уже закрыты отдельной, более узкой работой
(issue #650, PR #654 — на момент этого текста PR открыт, не слит: `gh pr
view 654` даёт `state: OPEN`, `scripts/worker/task.sh` (сборка промпта,
`cat "$PLAYBOOK_FILE"`) до сих пор вшивает в промпт воркера только
`WORKER-PLAYBOOK.md` целиком, без байта
`AGENTS.md`/`PROTOCOL.md` — намерение PR #654 уже объявлено, факт в коде
ещё не наступил). Раз одна из пяти граней («правило не доходит ни до
одного канала» + «доставка обеднена по каналам») решается тем PR-ом
отдельно, оправдание ЭТОГО change сужается до трёх граней:

1. **Носитель есть не у всех.** 40 нормативных правил, исполняемый
   носитель (гвардия/шаг CI/hook) — у 24 (ручной подсчёт из v2, точность
   ±1-2 — этот текст не переизмерял), доказан красным прогоном на
   реальном входе — у 7. Носителя нет вовсе у 16: например
   `relative-markdown-links` (AGENTS.md, «Работа с документацией»: запрет
   `[[wiki-links]]` не проверяет ни один гейт репозитория — проверено
   ревью по текущему дереву). Пример «секреты» из v2 сюда больше не
   годится и переехал в грань 2: носитель у правила ПОЯВИЛСЯ (#634 —
   `.github/workflows/secret-scan.yml` гоняет `gitleaks` на диапазон
   коммитов каждого PR и еженедельно всю историю, `.gitleaks.toml` в
   корне), а не отсутствовал.
2. **Носитель, который сам не доказан.** Гвардия есть, но красный случай
   не воспроизведён автоматически — только словесная инструкция в
   докстринге «поменяй X руками — проверь, что покраснело»:
   `scripts/lib/test_task_ref_usage_guard.py`,
   `scripts/lib/test_pagination_guard.py`. Живой случай цены: семантика
   `task_ref` жила в докстринге, пока `ai_review.py` не взял не ту функцию
   — четыре PR судились по неверной задаче месяцами, прежде чем гвардия
   вообще появилась в CI (`AGENTS.md`, «Решение — это механизм, а не
   текст»). Туда же — правило о секретах из грани 1: носитель есть
   (`secret-scan.yml`, #634), мутационного доказательства нет.
3. **Одно правило — несколько формулировок.** «PR только через
   `scripts/git/pr-create`» и «`Closes/Fixes/Resolves` запрещены» объявлены
   в `docs/agents/PROTOCOL.md`, а `scripts/worker/task.sh` сочиняет для
   второго собственную, третью формулировку в промпте воркера — тот же
   класс, что правило репозитория «Одно место правды» запрещает,
   применённый к своду правил.

**Этот change (ходячий скелет) закрывает только грань 2** — и только для
ОДНОГО правила, чтобы доказать, что механизм мутационного доказательства
вообще работает на реальном входе, прежде чем расширять его на остальные.
Грани 1 и 3 остаются нетронутыми этим change — они не отменены, просто не
входят в скелет (см. «Out» ниже, без обещания сроков).

## Что уже сложилось и на чём строить

В репозитории уже два равноправных уровня носителей: снимки состояния
(`scripts/orchestra/repo_invariants.py`, формат `check_<имя>(данные) ->
list[dict]`) и гвардии по исходному коду
(`scripts/**/test_*_guard.py`, регэксп/AST-сканирование конкретного
класса нарушения). Этот change не заводит третий параллельный слой — он
даёт машиночитаемую запись «вот правило, вот его носитель, вот файл,
доказывающий связь мутацией» для ОДНОГО уже существующего носителя из
второго уровня.

## Scope

**In (ровно три вещи, больше ничего):**

1. **Инвентарь.** Файл-на-правило `docs/agents/rules/<id>.md` (YAML-шапка
   + тело). Обязательные поля шапки: `id`, `statement`, `carrier`,
   `proof_test`, `status` (`proven`/`unproven`/`none`); поле вне пяти
   известных — отказ. Валидатор схемы
   (`scripts/lib/rule_registry.py` + `test_rule_registry.py`):
   обязательность полей, `id` = имя файла, резолвимость `carrier` (Python
   `file::symbol` через `ast`) и `proof_test` (pytest node id, РОВНО один
   собранный тест), согласованность полей со `status`, существование
   `docs/agents/rules/mutants/<id>.diff` для каждой proven-записи,
   громкая ошибка с именем файла на каждый нераспарсившийся
   файл-кандидат — design.md,
   раздел A.
2. **Мутационная проверка одного правила.** `scripts/lib/
   mutation_harness.py`, режимы `--rule <id>` (одно правило; для
   записи не-`proven` — явная ошибка) и `--all-proven` (перебор всех
   proven-записей — его зовёт CI): здоровье носителя на
   немутированном дереве, проверка адресата мутанта, применение мутанта,
   повторный прогон, разбор кода выхода pytest, откат по флагу
   «патч применён» (отказ отката — отдельный громкий исход) —
   design.md, раздел C.
   Правило-скелет: `rule-registry-requires-core-fields` (см. ниже, «Выбор
   правила для скелета»).
3. **Один файл каталога гвардий.** `scripts/ci/guards/
   rule-carrier-registry.sh` с тремя командами — оба новых test-файла,
   `rule_registry.py --check` и `mutation_harness.py --all-proven` —
   созданный ТЕМ ЖЕ пунктом
   tasks.md, что создаёт код (не отдельным последним пунктом плана).
   Рукописный шаг в repo-ci.yml не вариант: гвардия регистрации (#749,
   `scripts/lib/ci_guard_registration_guard.py`) красит новый рукописный
   тестовый шаг (проверено прогоном при правке по ревью), регистрация
   гвардии — данные (файл каталога), шаг-перебор «Каталог гвардий
   scripts/ci/guards» исполняет каждый файл сам; repo-ci.yml этим change
   не правится.

**Выбор правила для скелета.** Мутация доказывает собственную запись
реестра о валидаторе схемы: правило «запись реестра обязана нести
непустые id/statement/carrier/status, согласованные с status» —
`carrier: scripts/lib/rule_registry.py::validate` (носитель — код
валидатора, создаваемый этим же change, не тест), `proof_test:
scripts/lib/test_rule_registry.py::test_validate_rejects_missing_statement`
(отдельный, не мутируемый тест). Мутант ослабляет `validate()` (убирает
одну проверку), не трогает измеритель — прямое исправление находки
разбора «мутант правил сам тест, из-за чего тест после мутации проходил и
мутант считался выжившим навсегда» (design.md, раздел A, «Самоприменимость»).
Носитель дешёвый (пара unit-тестов на десятки строк кода, без внешних
зависимостей, без сканирования всего `scripts/`) и заведомо живой —
он пишется и сразу проверяется в рамках той же задачи, а не унаследован
от чужого, потенциально дрейфующего файла с сотнями посторонних тестов
(антипаттерн, замеренный design.md на `scripts/orchestra/
test_scheduler.py` — 249 тестов, до 19.4 с на один).

**Второй иллюстративный файл** — `relative-markdown-links`
(AGENTS.md, «Работа с документацией», `status: none`,
`carrier: "none: гейт не заведён"`) — показывает, что схема одинаково
честно описывает и доказанное, и недоказанное правило, не подделывая
`proven` там, где носителя нет.

**Out (выпилено целиком из этого change, не «отложено» — без обещания
сроков):**

- **Отбор по `scope`/каналам и всё производное** (промпт-проекции,
  `scope_reason`, `rule_delivery_ratchet.py`, генерация `AGENTS.md`/трёх
  промптов, гейт «сгенерируй и сравни»). Причина: окно модели канала
  заявлено 1 000 000 токенов (не подтверждено независимым замером —
  источника в `docs/research/` и `config/provider-usage.json` нет);
  `AGENTS.md` (30 161 байт)
  + `PROTOCOL.md` (51 095 байт) = 81 256 байт (замер 2026-09-11), то есть
  ≈ 21 700 токенов в пропорции замера 2026-09-07 (69 679 байт → 18 635
  токенов) — порядка 2% даже заявленного окна; вывод Out не зависит от
  точного числа: десятки килобайт прозы влезают с запасом.
  посылка «полный текст не влезает» была ложной на порядки. Правила уже
  доставляются каналам отдельной, более узкой работой (issue #650, PR
  #654 — см. «Класс проблемы» о текущем факт-состоянии). Проекции реестра
  печатали бы КОРОТКУЮ форму (`statement`, не тело) — это УМЕНЬШИЛО бы
  фактическую доставку по сравнению с вшиванием полного текста, и вернуло
  бы в `docs/agents/WORKER-PLAYBOOK.md` второй источник правды, который
  PR #654 из него убирает.
- **Оба храповика** (долг по `pending+infeasible`, доставка по каналам).
  При двух правилах в реестре ратчет нечего защищать — храповик на
  выборке из двух записей либо тривиально зелен, либо ловит любое
  изменение как «регресс», давая ложный сигнал. Возвращается, когда есть
  объём правил, оправдывающий сравнение с `base`.
- **Ночной прогон `rule-mutation-sweep.yml`.** При одном мутанте
  расписание не даёт нового сигнала сверх того, что уже даёт CI на каждом
  PR.
- **Инвариант обратной связности** (носитель без правила в реестре) и его
  включение в `CI_GATING`. Требует сканировать весь `scripts/**/
  test_*_guard.py` — за пределами скелета из одного правила, и правит
  занятый параллельными агентами `repo_invariants.py`.
- **Канарейка дублирования прозы** (раздел F design v2). Узкий, но
  отдельный носитель, не нужный для доказательства, что цикл
  «правило → мутация → красный/зелёный» вообще работает.
- **Метка `rules-registry:skip`.** Она была газом для храповиков и
  генератора, которых в скелете больше нет — газ без тормоза не нужен.
- **Миграция всех 40 правил.** В инвентарь заводится ровно 2 записи —
  одна с живым носителем для мутации, одна `status: none` для примера.
  Перенос остальных 38 — предмет будущих задач ПОСЛЕ того, как скелет
  подтвердит, что механизм работает.

## Acceptance criteria

1. `docs/agents/rules/README.md` и `scripts/lib/rule_registry.py`
   называют и проверяют ровно 5 обязательных полей шапки (поле вне пяти
   известных — отказ), таблицу согласованности со `status` и существование
   `mutants/<id>.diff` для proven-записей.
2. `mutation_harness.py --rule rule-registry-requires-core-fields`
   на живом дереве: код 0, вывод содержит «доказано»; временная порча
   мутанта (no-op) даёт код ≠0 и текст «мутант выжил»; временное
   переименование `proof_test`-файла даёт код ≠0 и текст «харнес не смог
   проверить: pytest exit=4», не «доказано» и не «выжил»; сломанный
   откат при применённом мутанте даёт код ≠0 и текст «откат не удался» —
   не тихий успех и не «доказано».
3. Файл каталога `scripts/ci/guards/rule-carrier-registry.sh` содержит
   ровно три команды (оба новых test-файла, `rule_registry.py --check`,
   `mutation_harness.py --all-proven`) и исполняется шагом-перебором
   «Каталог гвардий» — живой прогон CI на PR этого change зелёный,
   `.github/workflows/repo-ci.yml` не изменён, маркер `ORPHAN-TEST-OK`
   не используется.
4. Ни один файл вне `openspec/changes/rule-carrier-registry/` (кроме
   файлов, перечисленных в Impacted domains — их правит РОВНО задача 1
   tasks.md) не изменён этим change до слияния кода.
5. `--rule <неизвестный id>` и `--rule` для записи не-`proven` (включая
   `proof_test: "none"`) дают явную ошибку с ненулевым кодом выхода
   (не «нечего делать, 0» и не «носитель нездоров»); реестр с нулём
   загруженных правил при непустой директории — красный результат в любом
   режиме; отсутствующая или пустая директория `docs/agents/rules/` —
   красный тоже (47.3, без окна «до первой записи»); понижение
   единственной proven-записи в `unproven` красит `--all-proven` (пол
   нуля proven, 47.5), не зелёным счётчиком.

## Риски / неподтверждённое

- **Нумерация дельта-спеки.** `openspec/specs/journal-tasks-hands.md`
  заканчивается на 37 (проверено этим текстом). Занятость top-level
  номеров открытыми changes пересчитана по текущему дереву при правке по
  ревью (`grep -oE '^[0-9]+\.'` по каждой открытой дельте, 2026-09-11):
  38 — четыре changes, 39 — `reopen-rejected`, 40–42 задвоены/затроены
  (`stale-unclaimed-visibility`, `gate-idempotency`,
  `ai-failed-retry-budget`, `ai-review-concurrent-dedup`,
  `corrupted-session-cold-load-recovery`), 43–45 — `do-pulse-watchdog`,
  46 — `cf-cron-trigger`, 50 — `orchestrator-pulse-interval-tuning`.
  Предыдущий текст этой дельты брал 44 и утверждал «42–45 свободны» — на
  момент проверки это было так, к моменту правки 44 занят
  `do-pulse-watchdog`: подтверждение собственного тезиса, что подсчёт
  живёт только свежим прогоном, не памятью. Эта дельта берёт **47**
  (свободны 47–49). Коллизия системная (решается на архивации), номер
  рабочий, подлежит перенумерации при архивации (tasks.md, пункт 2).
- **Подсчёт «40 правил / 24 носителя / 7 доказанных»** — ручной, из v2,
  не переизмерен этим текстом; скелет не зависит от точности этого числа
  (в инвентарь заводится 2 записи, не 40).
- **Состояние PR #654** может измениться (слиться) к моменту исполнения
  этого change — если да, ссылка на «намерение объявлено, факт не
  наступил» в «Классе проблемы» устареет; это не меняет объём Out (отбор
  по scope остаётся не нужен скелету независимо от судьбы #654).
