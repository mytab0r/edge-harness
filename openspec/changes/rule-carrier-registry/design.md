# design.md: rule-carrier-registry

## 0. Словарь

- **Правило** — одно проверяемое утверждение из `AGENTS.md`/
  `docs/agents/PROTOCOL.md` («PR открывается только через
  `scripts/git/pr-create`», не целый абзац с обоснованием).
- **Носитель (carrier)** — исполняемый механизм, который делает нарушение
  правила невозможным или видимым: гвардия в CI, git-хук, шаг workflow,
  проверка внутри уже существующего инварианта.
- **Доказательство (proof)** — воспроизводимый факт, что носитель реально
  красится на реальном нарушении (не докстринг с инструкцией «попробуй
  сам»). Единственная принятая форма — мутационный прогон (раздел C).
- **Канал исполнения (scope)** — кому правило адресовано и в чей промпт/
  документ оно обязано попасть: `human`, `worker` (`scripts/worker/task.sh`),
  `reviewer` (`scripts/review/ai_prompt.md`), `hands`
  (`scripts/hands/dsh_task.sh`), либо `system` — правило существует только
  как машинная проверка и ни в один промпт не проецируется (раздел E).

## A. Реестр: файл-на-правило, не монолитный YAML

**Решение: `docs/agents/rules/<id>.md`, один файл на правило, YAML-шапка +
markdown-тело.**

Шапка — минимальный машиночитаемый контракт:

```yaml
---
id: pr-only-via-pr-create
statement: "PR открывается только scripts/git/pr-create, не голым gh pr create"
scope: [worker, hands, human]
section: pipeline-contract       # группировка для генератора AGENTS.md, см. B
carrier: "scripts/git/pr-create::main"   # file::symbol, не file:line — см. «Возражения»
carrier_status: proven           # proven | pending | infeasible
proof: "mutation:docs/agents/rules/mutants/pr-only-via-pr-create.diff"
---
```

Тело файла — прежний развёрнутый текст правила (обоснование, номера
инцидентов, ссылки) практически без изменений: перенос, не пересказ.

**Почему файл-на-правило, а не один `rules.yaml` со списком записей.**
Требование задачи прямо называет условие выбора: реестр будут править
параллельно много агентов. У монолитного файла ровно один физический
объект — любые две одновременные правки (агент A добавляет носитель
правилу №12, агент B пишет новое правило №41 в конец того же списка)
задевают тот же файл и тот же участок (конец списка/соседние строки),
Git-мердж текстового YAML-массива не понимает семантику записи и конфликтует
на границах элементов чаще, чем кажется (пробел/запятая на предыдущей
строке). У файла-на-правило это структурно невозможно: два агента, правящие
разные `id`, правят разные inode, PR не пересекаются никогда, а PR,
правящий существующее правило, конфликтует только с другим PR, правящим
**то же самое** правило — ровно та гранулярность конфликта, которая нужна.
Это не новый для репозитория приём, а перенос уже действующей конвенции:
`openspec/changes/<id>/` — папка на предложение, `docs/decisions/000N-*.md` —
файл на ADR, `docs/research/NN-*.md` — файл на тему. Монолитный `docs/agents/
LABELS.md` — единственный пример обратного в репозитории, и он оправдан
только потому, что его правит не рой параллельных агентов, а редкие точечные
PR плюс автоматический коллектор (`collect_labels.py`), сверяющий ОДНО
направление (код → таблица). Здесь направление обратное и авторов много
одновременно — довод не переносится.

Итог: 40 файлов вместо одного, зато нулевая цена координации по умолчанию.
tasks.md разбивает миграцию по этим же файлам-границам (раздел «Миграция»
ниже) — каждый пункт создаёт свои новые файлы и не пересекается с соседним.

Схема шапки валидируется гвардией `scripts/lib/test_rule_registry.py`
(новый файл, tasks.md): обязательные ключи, `scope` — подмножество
`{human, worker, reviewer, hands, system}`, `id` совпадает с именем файла,
`carrier`/`carrier_status`/`proof` согласованы (см. таблицу ниже), ссылка в
`carrier`/`proof` резолвится (файл и символ реально существуют на момент
проверки — иначе носитель может быть переименован без замеченного разрыва
связи, тот же класс дефекта, что и весь этот change призван закрыть).

| carrier_status | что означает | что обязано быть заполнено |
|---|---|---|
| `proven` | носитель есть, мутация доказывает | `carrier` — `file::symbol`; `proof` — `mutation:<путь к диффу>` |
| `pending` | носитель либо есть без доказательства, либо механизируем, но не сделан | `carrier: none` ИЛИ `file::symbol` без мутанта; `proof: none: <почему пока нет>` |
| `infeasible` | сознательно решено не механизировать | `carrier: "none: <причина>"`, причина — почему автоматическая проверка невозможна или неоправданно дорога (см. раздел D) |

## B. Генерация: AGENTS.md и три промпта — проекции реестра

**AGENTS.md.** Секции («Правила, оплаченные чужими ошибками» и т.п.) —
хэндрайтенный, стабильный список секций с вводным текстом в
`docs/agents/rules/_sections.yml` (новый файл: `id секции → заголовок +
вступительный абзац`, единственное место правды порядка). Генератор
(`scripts/lib/gen_rules_docs.py`, новый файл) идёт по секциям в объявленном
порядке, внутри каждой — по правилам с `section: <id>` в порядке,
объявленном в `_sections.yml` (явный список id правил на секцию, не
алфавит — алфавит развалил бы повествовательную связность, которая
сегодня есть между соседними абзацами AGENTS.md), и печатает тело каждого
файла как есть. Части `AGENTS.md`, которые не являются правилами
(«Что здесь строится», таблица слоёв, вводные абзацы) — не генерируются,
остаются хэндрайтенными в шаблоне-обвязке, куда генератор вставляет только
секции с правилами. Итог: `AGENTS.md` перестаёт быть местом, где текст
пишут напрямую, но визуально не меняется в момент миграции (то же
содержание, тот же порядок — просто источник переехал).

**Три промпта.** `AGENTS.md` целиком (69 КБ вместе с PROTOCOL.md) не
влезает ни в один промпт по бюджету контекста — отбор обязателен, и он
идёт по `scope`, не по объёму:

- `scripts/worker/task.sh` (канал worker) — сегодня строки 299–327 собирают
  промпт, включают `WORKER-PLAYBOOK.md` целиком через `cat`. Генератор
  печатает КОРОТКУЮ форму (`statement`, не всё тело) всех правил с
  `worker` в `scope`, группируя по `section`, и вставляет результат между
  маркерами
  `<!-- RULES:BEGIN scope=worker --><!-- RULES:END -->`
  внутри `docs/agents/WORKER-PLAYBOOK.md` (сам плейбук остаётся
  хэндрайтенным вокруг маркеров — он уже содержит контекст, которого нет в
  реестре: пошаговый маршрут, специфика раннера). `task.sh:326` продолжает
  вшивать плейбук целиком через `cat` без изменений — маркеры внутри уже
  сгенерированного файла, самому `task.sh` про реестр знать не нужно.
- `scripts/review/ai_prompt.md` (канал reviewer) — сегодня не ссылается ни
  на `AGENTS.md`, ни на `PROTOCOL.md` вовсе (proposal.md, п.7). Тот же
  приём: маркеры `<!-- RULES:BEGIN scope=reviewer -->` внутри самого
  `ai_prompt.md`, короткая форма правил с `reviewer` в `scope` — минимум,
  который позволяет ревьюеру ловить нарушения «PR не по шаблону»,
  «Closes/Fixes/Resolves», «второй источник правды» и т.п. как содержательные
  находки, а не только как то, что заметит `contract_check.py` постфактум.
- `scripts/hands/dsh_task.sh` (канал hands) — сегодня доставляет ноль правил
  (proposal.md, п.6). Маркеры вставляются в новый небольшой файл
  `scripts/hands/RULES-PREAMBLE.md` (генерируемый целиком, без
  хэндрайтенной обвязки — этому каналу пока не нужен отдельный playbook),
  который `dsh_task.sh` подмешивает перед `TASK_TEXT` в вызов DSH headless;
  правка самого `dsh_task.sh` — один `cat`/конкатенация, тот же приём, что
  уже применён в `task.sh:326`.

**Гейт «сгенерируй и сравни» — точка подключения.** Новый шаг в
`.github/workflows/repo-ci.yml`, job `test` (правка — задача tasks.md для
исполнителя, не этого change, файл занят параллельными агентами):

```yaml
- name: Реестр правил сгенерирован из docs/agents/rules (lock-gate)
  run: |
    python scripts/lib/gen_rules_docs.py --check
```

`--check` генерирует все проекции во временную директорию и делает `diff`
с закоммиченными `AGENTS.md`, `docs/agents/WORKER-PLAYBOOK.md`,
`scripts/review/ai_prompt.md`, `scripts/hands/RULES-PREAMBLE.md`; расхождение
— это тот же паттерн, что lock-файлы пакетных менеджеров: печатает diff и
падает с сообщением `запусти 'python scripts/lib/gen_rules_docs.py --write'
и закоммить результат`. Это единственный способ разойтись: примешивать
текст правила руками в промпт (как `task.sh:296` сегодня сочиняет
собственную формулировку `Closes/Fixes/Resolves`) становится невозможно
без того, чтобы CI не заметил рассинхрон в первом же PR.

## C. Доказательство — мутационный харнес

**Формат мутанта.** Для правила с `carrier_status: proven` рядом лежит
`docs/agents/rules/mutants/<id>.diff` — unified diff, применяемый поверх
рабочего дерева, нарушающий ровно тот инвариант, который называет правило
(пример: для «страница GitHub API без обхода», мутант убирает `page=` из
одного разрешённого `ALLOWED_SINGLE_PAGE_CALLS` в `scripts/lib/
test_pagination_guard.py`, либо добавляет новый неразрешённый одностраничный
вызов в фикстуру — конкретная форма мутанта решается при написании
конкретного `.diff`, не этим design). Шапка правила называет также
`proof_test` — какой pytest-путь обязан покраснеть (по умолчанию —
файл-гвардия, чей `file::symbol` указан в `carrier`).

**Механизм (`scripts/lib/mutation_harness.py`, новый файл).**
1. `git worktree add --detach <tmp> HEAD` — изолированная копия дерева на
   текущем коммите (не полное копирование файлов: `git worktree` делит
   объекты с основным репозиторием, дешевле и не тащит `node_modules`,
   которых во `worktree` без `npm install` и не будет).
2. `git -C <tmp> apply <mutant>.diff` — если патч не применяется (дрейф
   кода), это тоже красный результат: правило либо устарело, либо мутант
   не обновлён вместе с кодом — падать тем же сообщением, не молчать.
3. Запуск `proof_test` внутри `<tmp>` (`python -m pytest <tmp>/<путь> -q`).
   Обязано завершиться НЕ нулём (тест покраснел на мутанте) — иначе мутант
   выжил, это и есть находка «носитель не ловит нарушение», красит прогон.
4. `git worktree remove <tmp> --force`.

**Что гоняется на каждом PR (выборочно).** Шаг в `repo-ci.yml`, job `test`
(снова — задача исполнителя, не правка этим change):

```yaml
- name: Мутации правил, задетых этим диффом
  run: |
    python scripts/lib/mutation_harness.py --changed \
      --base "origin/${{ github.base_ref || 'main' }}"
```

`--changed` вычисляет `git diff --name-only <base>...HEAD`, берёт только
правила, чей `carrier`-файл входит в список изменённых, и мутирует только
их. Типичный PR трогает 0–2 таких файла — цена близка к нулю относительно
уже существующего набора `test_*_guard.py`, гоняемого в `repo-ci.yml`
сегодня.

**Что гоняется по расписанию (полный прогон).** Новый workflow
`.github/workflows/rule-mutation-sweep.yml` (новый файл — не входит в список
занятых параллельными агентами файлов, можно завести этим change как ЧАСТЬ
tasks.md для будущего исполнителя):

```yaml
on:
  schedule:
    - cron: "0 3 * * *"   # раз в сутки — вне пиковой активности агентов
  workflow_dispatch: {}
jobs:
  sweep:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python scripts/lib/mutation_harness.py --all
```

Полный прогон ловит класс «носитель разучился ловить нарушение, потому что
рядом поменялся код, но ни один PR не задел файл самого носителя напрямую»
(тот же класс, что нашла бы гвардия при переименовании функции, но с гарантией
раз в сутки, а не только при точечном PR).

**Стоимость (замер локально, Windows/Git Bash, репозиторий 7.1 МиБ без
`.git`/`node_modules`, не GitHub Actions — см. «Риски» в proposal.md):**

- `git worktree add --detach` + `git worktree remove`: ≈0.6 с суммарно
  (замер: `0.385s add + 0.208s remove`).
- Один запуск `python -m pytest <файл-гвардия> -q`: ≈0.83 с (замер, `scripts/
  lib/test_pagination_guard.py`, включая старт интерпретатора и сбор теста).
- Итого на один мутант: ≈1.5–2 с (плюс `git apply` <0.1 с).
- Носителей с реальным тестовым файлом сегодня — 24 (перечень
  `scripts/**/test_*_guard.py` и подобных, см. `proposal.md`); при одном
  мутанте на носитель полный прогон — 24 × ~2 с ≈ **менее минуты**
  локально. На раннере GitHub Actions с холодным чекаутом и Python-стартом
  разумно закладывать множитель ×3–5 на накладные расходы окружения —
  оценка **до 5 минут** на полный прогон, что укладывается в отдельный
  workflow по расписанию, а не в обязательный гейт каждого PR (для которого
  и выбран выборочный режим `--changed`).
- Если на одно правило понадобится несколько мутантов (несколько независимых
  веток одного инварианта — так уже устроены существующие гвардии, у
  `pr_is_unhealthy`, например, несколько причин красного), число мутантов
  растёт линейно, стоимость остаётся в том же порядке величины (сотни, не
  тысячи прогонов) — при 40 правилах и по 3 мутанта на правило это 120
  прогонов ≈ 4 минуты локально / до ~15–20 минут на раннере, всё ещё разумно
  для суточного расписания.

## D. Храповик долга по правилам без носителя

**Что считается долгом.** Число файлов реестра с `carrier_status: pending`
(не `infeasible` — это разные вещи, разведены явно полем, см. раздел A).
`infeasible` не входит в счёт долга вовсе: это не «пока не сделали», а
осознанное решение, зафиксированное причиной в самом файле правила (пример
— решение о трактовке приоритета человеком, `AGENTS.md:196-198`, «часть
решений машиной не проверяется... это называется вслух, а не выдаётся за
гвардию» — само правило уже формулирует свой `infeasible`-статус,
переносится в реестр с той же причиной).

**Механизм ratchet (`scripts/lib/rule_carrier_ratchet.py`, новый файл).**
Не хранит число-порог руками (не по образцу `REWORK_BUDGET` — там порог
калиброван замером и должен жить как объявленная константа; здесь порог —
это факт «сколько долга было на прошлом коммите», а не решение). Скрипт:

1. Считает `pending_count(HEAD)` — число файлов `docs/agents/rules/*.md` с
   `carrier_status: pending` на текущем дереве.
2. Считает `pending_count(base)` тем же способом, читая
   `git show <base>:<путь>` для каждого файла реестра, каким он был на
   `origin/main` (`base` — параметр, тот же `base_ref`, что и в мутационном
   гейте).
3. `pending_count(HEAD) > pending_count(base)` — красный результат,
   сообщение называет ИМЕНА добавленных в долг правил (не просто число —
   правило репозитория «Алерт не гадает», `AGENTS.md:138-148`, применённое
   к этому же гейту): `новый pending без носителя: <id1>, <id2> — либо
   добавь carrier, либо обоснуй infeasible`.
4. `pending_count(HEAD) <= pending_count(base)` — зелёно, снижение не
   требует отдельного шага «поднять порог» (в отличие от порогов вроде
   `REWORK_BUDGET`, здесь нечего поднимать — планка это прошлое состояние
   `main`, она сама подтягивается вниз с каждым слиянием, снижающим долг).

Это самоподдерживающийся храповик без отдельной ручной константы, которую
нужно не забыть поправить — тот же класс дефекта, которого стоило избежать,
судя по замеру `docs/agents/LABELS.md` про `review:large-ok`
(«текстовая проверка "газ назван" не эквивалентна "газ работает"»):
константа, которую нужно помнить поправить руками, имеет тенденцию
отставать.

**Точка подключения.** Тот же шаг `repo-ci.yml`, job `test`, что и гейт
генерации (раздел B) — оба дешёвые (чтение файлов + `git show`, без сети),
естественно живут рядом одним новым шагом «Реестр правил: не расти долгом»
(задача tasks.md для будущего исполнителя файла).

## E. Обратная связность: носитель без правила в реестре

Разведка нашла 7 таких носителей: `exec_bit_guard`, `orphan_test_guard`,
`epic_guard`, `do_hotpath_aggregate`, `dsh_edge_pnpm`,
`branch_protection_watch`, `upstream_drift`. Решение — не переписывать это
прозой в `AGENTS.md` (раздувание на каждый инцидент — тот самый антипаттерн,
которого правило «Инцидент оставляет инвариант, а не только фикс»,
`AGENTS.md:150-161`, и так не требует: оно требует инвариант в
`repo_invariants.py`, не абзац в `AGENTS.md`).

**Каждый такой носитель получает свою запись в реестре с `scope: [system]`
и `section: incident-invariant`.** `statement` — формулировка условия,
которое несёт сам код (например, для `dsh_edge_pnpm`: «standalone `dsh-edge`
собирается только `pnpm`, не `npm install` поверх патч-серии — класс #43»).
`carrier` указывает на существующий файл/функцию, `proof` — на уже
существующий тест этого класса (`test_dsh_edge_pnpm_guard.py` и т.п. —
если тест уже мутационно не доказан, `carrier_status: pending`, как у
любого другого правила, без исключения для этой категории). Генератор
(раздел B) НЕ печатает `section: incident-invariant` правила ни в `AGENTS.md`,
ни в один из трёх промптов (`scope` не содержит ни одного из `human/worker/
reviewer/hands`) — они существуют в реестре только как машиночитаемая
запись для гвардии обратной связности и для мутационного харнеса, `AGENTS.md`
не растёт ни строкой.

**Гвардия обратной связности** — новая `check_*`-функция в

упомянутый ни одним `carrier`, это находка. Как и остальные инварианты
`repo_invariants.py`, добавляется НЕ в `CI_GATING` сразу (по образцу
существующего решения владельца для новых инвариантов, `repo_invariants.py:

## Миграция 40 правил

Порядок — по риску и по естественной группировке (файловая независимость
между шагами разбирает tasks.md подробно):

1. **Инфраструктура сначала, без единого перенесённого правила.** Схема
   (раздел A), генератор (B), мутационный харнес (C), ratchet (D) — на
   ПУСТОМ или почти пустом реестре (1–2 иллюстративных файла), чтобы
   механизм был проверен на себе, прежде чем на него полагаются 40 правил.
2. **7 уже доказанных правил** (`task_ref` guard, pagination guard, label
   registry guard и т.п. — proposal.md, «уже сложилось») переносятся первыми:
   для них `carrier`/`proof` уже фактически существуют, перенос — заполнение
   шапки и написание/подтверждение мутанта, наименьший риск регресса
   поведения промптов (эти правила и так уже где-то присутствовали текстом).
3. **17 правил с носителем без доказательства.** Перенос текста +
   `carrier_status: pending` + `proof: none: "носитель есть
   (file::symbol), мутант не написан"` — честно, без вымышленного
   `proven`. Написание мутантов для них — отдельные, более мелкие задачи
   после того, как харнес уже проверен на п.2.
4. **16 правил без носителя.** Каждое размечается `pending` или
   `infeasible` с причиной (раздел D). Явно вынесенные в задании R29
   (секреты) и R27 (относительные ссылки) — кандидаты на быстрый перевод
   `pending → proven` тем же change/следующей узкой задачей: оба
   механизируемы одним CI-шагом (`gitleaks`/`grep` на wiki-links
   соответственно), эта работа — не в рамках данного change (раздел
   Scope/Out в proposal.md), но реестр обязан честно показать их как ближайший,
   самый дешёвый прирост покрытия.
5. **7 носителей-сирот** (раздел E) — заводятся в реестр параллельно с
   любым из шагов 2–4 (не зависят от них), но их гвардия обратной
   связности (E) включается последней, после того как все семь размечены.
6. **Подключение генератора к реальным файлам** (`AGENTS.md`,
   `WORKER-PLAYBOOK.md`, `ai_prompt.md`, новый `RULES-PREAMBLE.md`) — после
   того, как реестр покрывает 100% из 40 (иначе генератор в момент
   переключения молча укоротил бы `AGENTS.md`, вырезав ещё не перенесённые
   правила — фактически откат содержания, который нужно не допустить: до
   полного покрытия `gen_rules_docs.py --check` работает в режиме
   «дополнение», сверяя только уже перенесённые секции, а не весь файл
   целиком — переключение на строгий полнофайловый `diff` — последний шаг
   миграции, отдельным пунктом tasks.md).
7. **Подключение CI-гейтов** (генерация, мутации, ratchet, обратная
   связность) — после п.6, чтобы не гейтить PR на инфраструктуре, которая
   ещё не покрывает 100% случаев.

## Возражения

**Против буквального `carrier: file:line`.** Задание прямо просит поле
`carrier: file:line исполняемого носителя`. Design хранит `file::symbol`
(имя функции/константы/файла-обёртки), а не номер строки, и это не
косметика: репозиторий уже дважды документировал ровно эту проблему на
собственном опыте. `scripts/orchestra/repo_invariants.py:176-179` прямым
текстом объясняет, почему собственный код инварианта 3 ссылается на
`scheduler.trigger_ai_review` в форме `file::symbol`, а не строкой: «номера
строк гниют, класс уже закрывался этим переходом». `openspec/changes/
task-rework-loop/tasks.md:38-41` независимо констатирует тот же факт для
другого файла: «Проверить перед реализацией текущий номер строки
(`scheduler.py` меняется параллельно другими PR ... номера строк смещаются
от любого слияния)». Реестр правил живёт в репозитории, где параллельно
открыто по 5–15 PR на «горячий» файл (`repo-ci.yml` — 15, `scheduler.py` —
7, по вводным этой задачи) — `carrier: file:line`, записанный сегодня,
устареет за часы, и гвардия схемы реестра (раздел A) будет либо ловить
ложные срабатывания на каждом чужом слиянии, либо (что хуже) научится
не проверять актуальность номера и станет тем самым «носителем, который сам
не доказан» — второй пункт проблемы, которую весь этот change призван
закрыть. `file::symbol` резолвится в актуальную строку ТОЛЬКО в момент
рендера человекочитаемого вида (например, в отчёте гвардии обратной
связности, раздел E) — сам реестр номера не хранит и не может разойтись с
кодом при чужом, не относящемся к правилу, слиянии. Итоговая позиция:
согласен с намерением задания (носитель обязан указывать точное место), не
согласен с буквальной формой поля — `file::symbol` достигает той же цели
без унаследованного и уже документированного в этом же репозитории дефекта.

## Что мы НЕ делаем и почему

- **Не заменяем `repo_invariants.py`/`test_*_guard.py` новым единым
  движком проверок.** Реестр — слой ССЫЛОК на существующие носители
  (`carrier` указывает на уже написанный код), не переписывание этого кода
  под новый интерфейс. Оба существующих уровня (снимки состояния / гвардии
  по исходнику) остаются собственными файлами со своей логикой; реестр не
  знает, КАК устроена проверка внутри, только ГДЕ она лежит и КАКИМ
  мутантом доказывается.
- **Не переносим в реестр архитектурную прозу `AGENTS.md`** («Что здесь
  строится», таблица трёх слоёв, объяснение free-плана). Реестр — только
  для проверяемых утверждений (правил), не для контекста, объясняющего,
  почему система устроена так, как устроена. Граница уже проведена в самом
  `AGENTS.md` заголовками разделов — раздел B использует именно эту
  границу, не изобретает новую.
- **Не пишем сами 40 файлов реестра в рамках этого change.** Design
  проектирует формат и порядок; фактический перенос текста 40 правил —
  содержание задач tasks.md для будущих исполнителей, каждая — отдельный
  новый файл, без пересечения по файлам между агентами (см. tasks.md).
- **Не трогаем ни один из файлов, перечисленных как занятые параллельными
  агентами** (`cf-worker/**`, `.github/workflows/{deploy-worker,
  inbox-issue,repo-ci}.yml`, `scripts/lib/{review_labels,
  test_pagination_guard,exec_bit_guard,orphan_test_guard,
  test_pr_body_label_release_reachable}.py`, `scripts/orchestra/
  {contract_check,pulse_guard,repo_invariants,scheduler}.py`, `scripts/
  review/{ai_review,check_pr}.py`, `docs/agents/LABELS.md`, `dsh-edge/
  {verify-ingest-allowlist,smoke-edge-plugins}.mjs`) — точки подключения к
  ним названы явно (workflow-шаги, `check_*`-функция), но правка — задача
  tasks.md для исполнителя ПОСЛЕ того, как эти файлы освободятся, не
  предложение менять их сейчас.
- **Не вводим второй ratchet для `proof` (мутационно доказано / нет).**
  D специфицирует храповик ровно там, где просит задание — на
  `carrier_status: pending` (16 правил без носителя). Отдельный счётчик
  «носитель есть, мутации нет» (17 правил, раздел «Миграция», п.3) —
  честно виден в реестре полем `proof: none: ...`, но не гейтится ростом:
  превращать это во второй обязательный храповик — расширение задания,
  не его буквальное исполнение; если владелец захочет — это узкая
  следующая задача поверх уже работающей инфраструктуры.
- **Не решаем, какой конкретно мутант писать для каждого из будущих 40
  правил.** Раздел C фиксирует формат и механизм запуска; содержание
  каждого `.diff`-файла — задача, требующая понимания конкретного
  инварианта, решается по одному правилу за раз в tasks.md, не пачкой
  здесь.
- **Не заводим GitHub issue и не открываем PR этим change** — по прямому
  указанию постановки задачи; `tasks.md`, п.0, заводит issue как первый
  исполняемый шаг для того, кто продолжит работу.
