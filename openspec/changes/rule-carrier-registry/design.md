# design.md: rule-carrier-registry (ходячий скелет)

Этот design описывает ТОЛЬКО три вещи из proposal.md: инвентарь (раздел A),
мутационное доказательство одного правила (раздел C — нумерация букв
сохранена от v2 для навигации по истории change, разделы B/D/E/F/G/H v2
удалены целиком, не переименованы в «зарезервировано»). Всё, что было в
этих разделах v2 и сюда не попало, — в «Что мы НЕ делаем и почему» ниже.

## 0. Словарь

- **Правило** — одно проверяемое утверждение из `AGENTS.md`/`PROTOCOL.md`
  либо нормативное требование из `openspec/specs/` (до архивации change —
  из дельта-спеки этого change). Первая же запись скелета
  (`rule-registry-requires-core-fields`) — требование дельта-спеки, а не
  прозаики двух файлов: без этой оговорки определение ложно уже на первой
  записи реестра.
- **Носитель (carrier)** — исполняемый код, который делает нарушение
  правила видимым: в этом скелете — функция Python (`file::symbol`, файл
  и точка входа реальны и резолвятся через `ast`).
- **Доказательство (proof)** — воспроизводимый факт, что носитель реально
  красится на реальном нарушении. Единственная принятая форма —
  мутационный прогон (раздел C). Докстринг с инструкцией «поменяй руками,
  проверь» не считается доказательством.
- **`proof_test`** — конкретный pytest node id (`file.py::test_name`), не
  голый путь к файлу: файл-гвардия может нести не относящиеся к правилу
  тесты, «упал файл» не то же самое, что «упал тест, доказывающий именно
  это правило».
- **`status`** — одно из трёх значений записи реестра (не `carrier_status`
  из v2 — то же понятие, упрощённое название и таблица, см. раздел A):
  `proven` (носитель есть, мутация доказывает), `unproven` (носитель есть,
  мутация не написана/не доказана), `none` (носителя нет вовсе). Три
  значения имеют НЕпересекающиеся тела записи: носителя нет — это `none`,
  точка; форма `"none: <причина>"` у `carrier` допустима только при
  `status: none`. Два статуса с одинаковым телом записи — это два
  неотличимых статуса: при миграции остальных 38 правил авторы будут
  выбирать между ними наугад, и любая будущая статистика
  proven/unproven/none — ради различения реестр и задуман — превратится
  в шум.
- **Носитель нездоров (harness unhealthy)** — состояние, отдельное от
  трёх значений `status`: `proof_test` красный ДО применения мутанта (на
  чистом дереве). Это находка о самом измерительном инструменте, не о
  правиле — постоянно красный `proof_test` иначе «доказывал» бы любого
  мутанта фактом, что он и так был красным.

**Канал/`scope` в этой версии design не существует.** v2 нёс поле `scope`
(кому правило адресовано) и весь производный аппарат (генератор проекций,
храповик доставки, `scope_reason`) — proposal.md, Out, объясняет почему
это выпилено (посылка «не влезает» была ложной на два порядка, доставка
уже решается отдельной задачей #650/PR #654). Схема этого скелета не
несёт поля `scope` вовсе — не «пустое множество по умолчанию», а
отсутствующее поле, потому что распределение по каналам не входит в
предмет этого change.

## A. Реестр: файл-на-правило, 5 полей

**Решение: `docs/agents/rules/<id>.md`, один файл на правило, YAML-шапка +
markdown-тело.** Причина файла-на-правило (не единого `rules.yaml`)
переносится из v2 без изменений: параллельные PR, правящие РАЗНЫЕ `id`,
правят разные inode и не пересекаются никогда; PR, правящий существующее
правило, конфликтует только с другим PR, правящим то же самое правило.
Двух записей в этом скелете достаточно, чтобы доказать формат, но приём
рассчитан на рост без переделки.

```yaml
---
id: rule-registry-requires-core-fields
statement: "Запись реестра правил обязана нести непустые id/statement/carrier/status, согласованные с status; проверяет rule_registry.py::validate"
carrier: "scripts/lib/rule_registry.py::validate"
proof_test: "scripts/lib/test_rule_registry.py::test_validate_rejects_missing_statement"
status: proven
---
```

**Пять обязательных полей, не больше.** `id` (совпадает с именем файла
без `.md`), `statement` (короткая формулировка), `carrier` (`file::symbol`
либо `"none: <причина>"`), `proof_test` (pytest node id либо `"none"`),
`status` (`proven`/`unproven`/`none`). Поля v2 — `scope`, `section`,
`order`, `carrier_status` (переименовано и упрощено в `status`),
`scope_reason`, `duplicate_signatures` — не входят в схему скелета: они
обслуживали генератор проекций и храповики, которых здесь нет (см. «Что
мы НЕ делаем»).

**Таблица согласованности `status` ↔ остальные поля:**

| `status` | `carrier` | `proof_test` |
|---|---|---|
| `proven` | `file::symbol`, файл и символ резолвятся | pytest node id, резолвится РОВНО в один собранный тест (`pytest --collect-only -q <id>`, код 0, ровно одна строка узла в выводе — см. раздел C про фактический формат вывода) |
| `unproven` | `file::symbol` (носитель есть; `"none: …"` при `unproven` недопустим — носителя нет, это `none`) | резолвящийся node id, если уже известен, иначе литерал `"none"` |
| `none` | литерал, начинающийся с `"none: "` | литерал `"none"` |

Валидатор — `scripts/lib/rule_registry.py`: функция `validate()` и режим
CLI `--check` живут в нём; `scripts/lib/test_rule_registry.py` — только
тесты валидатора, CLI в тест-файле нет (атрибуция по tasks.md, п. 1, и
acceptance 1 proposal.md). Валидатор отклоняет запись, где: `id` ≠
имя файла; любое из пяти полей отсутствует или пусто; пара
`status`/`carrier`/`proof_test` не соответствует таблице; `carrier` в
форме `file::symbol` не резолвится (файла нет, символа верхнего уровня с
таким именем нет по `ast.parse`); `proof_test` не резолвится РОВНО в один
pytest-узел. Резолвинг проверяется только для форм, разрешённых таблицей
при данном `status`: у литералов `"none: …"`/`"none"` резолвить нечего и
проверка не выполняется — иначе валидатор был бы шире таблицы и 47.1.

**Резолвинг `carrier` — только Python, только в этом скелете.** `file::
symbol` резолвится через `ast.parse(файл)`, поиск функции/класса/константы
верхнего уровня с именем `symbol` (либо `Class.method` одним уровнем
вложенности). **Форма для носителя-шага workflow (`path.yml#step-id`) не
реализована этим скелетом** — честное признание, не «решено, но не
задокументировано»: в `.github/workflows/repo-ci.yml` ровно один шаг
несёт `id:` (шаг `id: quota`; файл горячий, номера строк здесь не
хранятся — тот же класс, что «Возражения» ниже про `file:line`), и оба
правила скелета — не workflow-носители, резолвинг для этой формы не нужен
скелету и не написан. Правило, чей `carrier` захочет указать на шаг
workflow, — задача будущего расширения, не входит в этот change.

**Абсолютный пол против тихого нуля.** `rule_registry.py` красит ЛЮБОЙ
«ноль», окна валидности нет: (а) `docs/agents/rules/` не существует или
пуст — красный БЕЗУСЛОВНО; оговорки «валиден только до первого коммита
миграции» больше нет — загрузчик и первые записи приезжают одним деревом,
окно пусто уже с первого коммита, а режим, молча зелёный на отсутствующей
директории, нельзя было бы спасти ничем, кроме соседней команды шага CI, —
тот же «тихий ноль», только с отложенным началом; (б) директория непуста,
но загрузчик вернул 0 распарсенных правил — ВСЕГДА поломка загрузчика
(битый YAML, не тот путь). Оба случая — громкий `RuntimeError`/ненулевой
код, не «нечего проверять». `--check` (режим CLI валидатора) и
`mutation_harness.py --rule <id>` (раздел C) оба обязаны проверить
`total_rules_loaded() > 0` ПЕРЕД тем, как обрабатывать конкретное
правило.

## C. Доказательство — мутационный харнес на одном правиле

**Формат мутанта.** `docs/agents/rules/mutants/<id>.diff` — unified diff,
применяемый поверх рабочего дерева, нарушающий ровно тот инвариант,
который называет правило. Для `rule-registry-requires-core-fields` мутант
правит `scripts/lib/rule_registry.py::validate` — убирает проверку
«`statement` непустой» — то есть патчит НОСИТЕЛЬ (код валидатора), а не
измеритель (`test_rule_registry.py`). Это прямое исправление находки
разбора v2: там мутант для аналогичной самоприменимой записи
(`rule-registry-schema-validated`, carrier указывал на
`test_rule_registry.py::<тест>`) правил САМ ТЕСТ, снимая в нём проверку —
после такой мутации тест естественно продолжал «проходить» (ему больше
нечего было проверять), и мутант считался бы выжившим НАВСЕГДА при любом
состоянии `validate()`, доказательство было фиктивным по конструкции.
Здесь `carrier` и `proof_test` — заведомо разные файлы (`rule_registry.py`
vs `test_rule_registry.py`), физически невозможно случайно мутировать
измеритель вместо носителя. Но «физически невозможно» верно только для
ЭТОГО правила по раскладке файлов; класс из разбора v2 (мутант правит сам
`proof_test`) обязан ловиться механизмом, а не везением с раскладки:
дифф, ломающий сам тест, на «мутированном» дереве даёт exit 1 и ложное
«доказано» — ровно та ложно-зелёная система, за которую v2 вернули.
Правило репозитория «инцидент оставляет инвариант» требует здесь
механизма — это шаг 2 ниже: харнес проверяет состав патча ДО его
применения.

**Механизм (`scripts/lib/mutation_harness.py`, режим `--rule <id>`).**
Скелет НЕ использует `git worktree` — упрощение, объявленное явно, не
скрытое: раздел C v2 предлагал изолированную копию дерева через `git
worktree add --detach HEAD` ради безопасности параллельной разработки
(агент мутирует своё дерево, пока где-то параллельно идёт другая работа
над тем же чек-аутом). Для скелета из ОДНОГО мутанта, гоняемого на
одноразовом раннере CI (чистое дерево, никто им параллельно не
пользуется) либо разработчиком локально перед коммитом, цена изоляции
`git worktree` не окупается сложностью — мутация применяется прямо в
рабочем дереве и гарантированно откатывается, когда применялась (шаг 5:
откат по флагу «патч применён», отказ отката — громкий отдельный исход),
тот же приём, что
v2 называл режимом `--local`. Возврат к изолированному `git worktree`
(`--all`/`--changed` из v2) — задача расширения ПОСЛЕ того, как реестр
несёт больше одного мутанта и появляется реальный параллелизм, которому
изоляция нужна.

Шаги:
1. **Здоровье.** `python -m pytest -q <proof_test>` на текущем дереве.
   Обязан завершиться кодом `0`. Если нет — результат категории «носитель
   нездоров» (не мутация, не находка о правиле): «`proof_test` для `<id>`
   красный ДО мутации — почини сам тест, это не находка о носителе».
2. **Адресат мутанта, до применения.** `git apply --numstat
   docs/agents/rules/mutants/<id>.diff` — печатает состав патча, ничего
   не применяя. КАЖДЫЙ файл в выводе обязан совпадать с файлом из
   `carrier`; файл из `proof_test` в выводе запрещён. Нарушение любого
   из двух условий — категория «мутант устарел» («патч для `<id>` не
   соответствует записи реестра — правит чужой файл или измеритель»), не
   «доказано» и не «мутант выжил»: без этого шага мутант, правящий сам
   `proof_test`, давал бы на «мутированном» дереве exit 1 и ложное
   «доказано».
3. **Применение мутанта.** `git apply docs/agents/rules/mutants/<id>.diff`.
   Ненулевой код — категория «мутант устарел»: «патч для `<id>` не
   применился — код-носитель изменился несовместимо с мутантом».
4. **Повторный прогон.** `python -m pytest -q <proof_test>` на мутированном
   дереве. Разбор кода выхода pytest (проверено прогоном на этом
   репозитории, не по памяти — см. «Проверенные факты о pytest» ниже):
   - `1` — тест собран и упал → **доказано**: «`<id>` proven — мутация
     поймана».
   - `0` — мутант ВЫЖИЛ: «carrier не ловит мутацию для `<id>`» — красный
     результат содержательной находки (носитель дырявый), не поломки
     харнеса.
   - `2`/`3`/`4`/`5` — харнес не смог провести проверку: «харнес не смог
     проверить `<id>`: pytest exit=`<N>`» — НЕ засчитывается ни как
     «доказано», ни как «мутант выжил» (переименование `proof_test`-файла
     даёт `exit=4`, синтаксическая ошибка импорта — `exit=2`; ни то, ни
     другое не имеет права молча превратить правило в `proven` навсегда).
5. **Откат — только если применял.** `git apply -R
   docs/agents/rules/mutants/<id>.diff` выполняется по флагу «патч был
   применён» (шаг 3 вернул код 0): на путях «мутант устарел» и «адресат
   не тот» (шаги 2–3) патч не применялся, reverse-apply откатывать
   нечего — попытка откатить неоткатываемое упала бы сама и замаскировала
   категорийный диагноз текстами, которые приёмка сверяет дословно.
   Отказ ОТКАТА на пути, где патч применён (reverse-apply дал ненулевой
   код), — отдельный громкий ненулевой исход: «откат не удался — рабочее
   дерево осталось мутированным, откатись руками (`git checkout --` /
   `git apply -R`)». Не «доказано», не «мутант выжил», не проглоченная
   ошибка: дерево мутировано, и результат обязан об этом кричать.

**Проверенные факты о pytest (прогон на этом дереве, не по памяти):**
- `pytest -q <node>` НЕ печатает строку `collected N items` вовсе (только
  `.`/`F` на тест плюс итоговую строку `1 passed in 0.07s` —
  проверено на `scripts/lib/test_pagination_guard.py`). Харнес не
  парсит текст вывода для подсчёта тестов — ему это и не нужно: `proof_test`
  по построению (раздел A) резолвится РОВНО в один узел, поэтому «то же
  число тестов на здоровье и на мутации» тривиально выполняется как 1=1,
  без разбора stdout. Код возврата — единственное, что харнес читает
  (`subprocess.run(...).returncode`), текст вывода — только для
  диагностики человеком.
- `pytest --collect-only -q <node>` печатает ТРИ строки при существующем
  узле: сам node id, пустую строку, `1 test collected in 0.04s` — не одну
  строку `collected N items`, которой в реальном выводе нет. Валидатор
  раздела A требует код `0` и ровно одну строку вида `<file>::<test>` в
  выводе (первую непустую строку), это и есть проверка «резолвится РОВНО
  в один узел».
- Несуществующий узел (`Path::nonexistent_test`) или несуществующий файл
  дают код `4` и строки `ERROR: not found: ...` / `no tests collected in
  0.04s` — подтверждает, что `exit=4` в разделе C — это «ошибка
  использования, включая несуществующий путь», ровно как названо, не
  гипотеза.

**`--rule <неизвестный id>`.** Явная ошибка на stderr («правило `<id>` не
найдено в реестре, известны: `<список id>`») и ненулевой код выхода — НЕ
«нечего делать, код 0». Молчаливый успех на опечатке в имени правила был
бы тем же классом дефекта («тихий ноль»), что раздел A уже закрывает для
пустого реестра.

**`--rule` для записи не-`proven`.** Правило, которое ЕСТЬ в реестре, но
чьё `status` не `proven` (вторая запись скелета, `relative-markdown-links`,
— `status: none`, `proof_test: "none"`), — явная ошибка с ненулевым кодом
(«`<id>`: status `<значение>` — доказывать нечего»), БЕЗ запуска pytest.
Наивный прогон `pytest -q none` вернул бы `exit=4`, и харнес выдал бы
«носитель нездоров — почини сам тест» — ложную инструкцию для честно
записанного правила: «нездоров» — это красный тест СУЩЕСТВУЮЩЕГО
измерителя, а не отсутствие измерителя.

**База/фикс-ветка скелету не нужна.** Критик экспериментально показал,
что `git fetch --no-tags --prune --depth=1 origin <base>` на shallow-
клоне НЕ создаёт `refs/remotes/origin/<base>` (`git merge-base
origin/<base> HEAD` даёт `fatal: Not a valid object name`), а
`FETCH_HEAD` с тремя точками даёт `no merge base`, код 128 — работают
только двухточие и `git show FETCH_HEAD:<путь>`. Это находка была
критична для v2, потому что раздел D/раздела 43.3 v2 сравнивали
`unproven_count`/`delivered_count` между `HEAD` и `base` — оба ratchet
выпилены этим скелетом (proposal.md, Out), и единственный оставшийся шаг
CI (раздел C, режим `--rule <id>`) работает целиком на текущем дереве:
здоровье, мутация, повтор, откат — ни один шаг не читает `base`, не
делает `git fetch`, не вычисляет `git diff <base>...HEAD`. Ответ на
вопрос «нужна ли скелету база» — нет, и это не недосмотр: раздел
«Возражения» ниже не нужен для функции, которую скелет не выполняет,
поэтому база просто не упоминается больше нигде в этом design.

## Возражения

**Против буквального `carrier: file:line`.** Design хранит `file::symbol`
(имя функции/класса), не номер строки — перенесено из v2 без изменений,
причина та же: `scripts/orchestra/repo_invariants.py` уже
документирует «номера строк гниют» на собственном опыте репозитория (это
и мотивировало переход инварианта 3 на `file::symbol`);
`openspec/changes/task-rework-loop/tasks.md` независимо констатирует тот
же факт для другого файла. Реестр правил живёт в репозитории, где параллельно
открыто по 5–15 PR на «горячий» файл (`repo-ci.yml` — 15 на момент
постановки задачи v2) — `carrier: file:line`, записанный сегодня,
устареет за часы. `file::symbol` резолвится в актуальную строку только
при рендере человекочитаемого вида, сам реестр номера не хранит.

## Что мы НЕ делаем и почему

Каждый пункт — раздел v2, выпиленный этим скелетом целиком, без замены на
«урезанную версию того же», и без обещания срока возврата:

- **Генерация `AGENTS.md`/трёх промптов из реестра, гейт «сгенерируй и
  сравни»** (v2, раздел B). Требует поля `scope`, которого нет в схеме
  скелета (раздел 0). Доставка правил каналам — предмет отдельной работы
  (issue #650/PR #654), а не этого change (proposal.md, «Класс проблемы»).
- **Оба храповика** — долг по `pending+infeasible` (v2, раздел D) и
  доставка по каналам (v2, раздел G). Ratchet сравнивает `base` и `HEAD`
  по количеству записей реестра — при двух записях в реестре сравнение
  либо тривиально зелено, либо ловит ЛЮБОЕ изменение как регресс (ложный
  сигнал на выборке из двух). Возвращается вместе с ростом числа правил,
  когда сравнение с `base` начинает что-то значить статистически, — и,
  раз он возвращается, тогда же встаёт вопрос про `git fetch`/`merge-base`,
  разобранный критиком (раздел C, «База/фикс-ветка скелету не нужна»
  выше) — эта работа сознательно откладывается ДО того момента, а не
  решается здесь наперёд без нужды.
- **Ночной прогон `rule-mutation-sweep.yml`** (v2, раздел C). При одном
  мутанте, гоняемом на каждом PR, расписание не добавляет сигнала:
  единственный носитель, который расписание могло бы поймать
  дополнительно (сломался код рядом, но ни один PR не тронул сам файл
  носителя), при ОДНОМ носителе так же надёжно ловится следующим PR,
  который тронет `rule_registry.py` — то есть почти всегда, раз это
  единственный файл-носитель в реестре.
- **Инвариант обратной связности** (v2, раздел E — носитель без правила в
  реестре). Требует сканировать весь `scripts/**/test_*_guard.py`,
  сверяя с множеством ВСЕХ `carrier` реестра — при 2 записях реестра
  находка «носитель без правила» верна почти для КАЖДОГО носителя
  репозитория (их там десятки), что не находка, а состояние «миграция не
  завершена», уже видимое человеку из самого факта «в реестре 2 файла».
  Механическая проверка этого станет содержательной, когда миграция
  покроет существенную долю правил, не раньше. Правит `repo_invariants.py`
  — занятый параллельными агентами файл, скелет его не трогает вовсе.
- **Канарейка дублирования прозы** (v2, раздел F). Отдельный, узкий
  носитель (сканирование `PROTOCOL.md`/`task.sh`/`dsh_task.sh` на
  `duplicate_signatures`) — не нужен для доказательства, что цикл
  «правило → мутация → доказательство» вообще работает; полезен, когда в
  реестре есть правило, для которого известна конкретная сигнатура
  дублирования (пока таких правил в реестре 0 из 2).
- **Метка `rules-registry:skip`** (v2, раздел H). Была объявленным газом
  для трёх обязательных гейтов (генерация, мутация, ratchet) — генерации
  и ratchet больше нет, единственный оставшийся гейт (мутация одного
  правила) — детерминированная чистая проверка без внешнего состояния:
  газ по построению («почини `mutation_harness.py`/`rule_registry.py`,
  закоммить — шаг зеленеет»), отдельная метка-выключатель не нужна для
  одного дешёвого шага так же, как её не заводят для любого одиночного
  `pytest`-шага в `repo-ci.yml` сегодня.
- **Миграция всех 40 правил.** Инвентарь несёт 2 записи. Остальные 38 —
  задача расширения после того, как этот скелет подтвердит цикл живым
  прогоном CI (это и есть цель ходячего скелета: доказать механизм на
  малом, прежде чем нести на нём вес всего свода).
