# design.md: rule-carrier-registry

## 0. Словарь

- **Правило** — одно проверяемое утверждение из `AGENTS.md`/
  `docs/agents/PROTOCOL.md` («PR открывается только через
  `scripts/git/pr-create`», не целый абзац с обоснованием).
- **Носитель (carrier)** — исполняемый механизм, который делает нарушение
  правила невозможным или видимым: гвардия в CI, git-хук, шаг workflow,
  проверка внутри уже существующего инварианта.
- **Доказательство (proof)** — воспроизводимый факт, что носитель реально
  красится на реальном нарушении (не докстринг с инструкцией «попробуй
  сам»). Единственная принятая форма — мутационный прогон (раздел C).
- **`proof_test`** — конкретный pytest node id (`file.py::test_name`, не
  голый путь к файлу), который обязан покраснеть на мутанте. Обязательное
  поле шапки (раздел A), не подразумеваемое умолчание: файл-гвардия часто
  несёт десятки не относящихся к правилу тестов (замер раздела C —
  `test_scheduler.py`, 249 тестов), и «упал файл» — не то же самое, что
  «упал конкретный тест, доказывающий именно это правило».
- **Носитель нездоров (harness unhealthy)** — состояние, отдельное от
  `proven`/`pending`/`infeasible`: `proof_test` красный ДО применения
  мутанта (на чистом дереве). Это не находка о правиле, а поломка самого
  измерительного инструмента — раздел C разводит эти два разных красных
  исхода явно, иначе постоянно красный тест «доказывает» любого мутанта
  простым фактом, что он и так был красным.
- **Канал исполнения (scope)** — кому правило адресовано и в чей промпт/
  документ оно обязано попасть: `human`, `worker` (`scripts/worker/task.sh`),
  `reviewer` (`scripts/review/ai_prompt.md`), `hands`
  (`scripts/hands/dsh_task.sh`), либо `system` — правило существует только
  как машинная проверка и ни в один промпт не проецируется (раздел E).
  Отсутствие поля `scope` в шапке — не «правило никому не адресовано», а
  ошибка данных: валидатор (раздел A) требует поле явно и непустым: если
  автор не уверен, куда адресовать правило, безопасное значение по
  умолчанию — «все каналы человека» (`[human, worker, reviewer, hands]`),
  не пустой список, который молча вычеркнул бы правило из всех промптов
  (раздел G).

## A. Реестр: файл-на-правило, не монолитный YAML

**Решение: `docs/agents/rules/<id>.md`, один файл на правило, YAML-шапка +
markdown-тело.**

Шапка — минимальный машиночитаемый контракт:

```yaml
---
id: pr-only-via-pr-create
statement: "PR открывается только scripts/git/pr-create, не голым gh pr create"
scope: [worker, hands, human]
section: pipeline-contract       # группировка для генератора AGENTS.md, см. B
order: 30                        # позиция внутри section — см. B, заменяет _sections.yml
carrier: "scripts/git/pr-create::main"   # file::symbol, не file:line — см. «Возражения»
carrier_status: proven           # proven | pending | infeasible
proof_test: "scripts/lib/test_pr_create_guard.py::test_rejects_bare_gh_pr_create"
proof: "mutation:docs/agents/rules/mutants/pr-only-via-pr-create.diff"
---
```

Тело файла — прежний развёрнутый текст правила (обоснование, номера
инцидентов, ссылки) практически без изменений: перенос, не пересказ.

**`proof_test` — обязательное поле, не производное от `carrier`.** Первая
версия design опускала это поле, подразумевая по умолчанию «файл-гвардия,
чей `file::symbol` указан в `carrier`» — на практике это ломается: у
`carrier`-файлов с несколькими тестами (`scripts/orchestra/test_scheduler.py`
— 249 тестов, раздел C) «весь файл как proof» означает гонять 249 тестов
ради доказательства одного правила, и раздутый по стоимости прогон —
не единственная цена: файл может краснеть по СОВСЕМ другой причине (тест
№37 упал по несвязанному регрессу), и харнес засчитает это как «мутация
поймана», хотя поймал не тот тест. `proof_test` обязан быть узлом pytest
(`file.py::test_name`, при необходимости `::TestClass::test_name`), не
путём к файлу целиком; валидатор (см. ниже) резолвит его через
`pytest --collect-only -q <proof_test>` и требует РОВНО одного собранного
теста — ни ноль (опечатка в имени), ни больше одного (путь остался
файловым).

**Почему файл-на-правило, а не один `rules.yaml` со списком записей.**
Требование задачи прямо называет условие выбора: реестр будут править
параллельно много агентов. У монолитного файла ровно один физический
объект — любые две одновременные правки (агент A добавляет носитель
правилу №12, агент B пишет новое правило №41 в конец того же списка)
задевают тот же файл и тот же участок (конец списка/соседние строки),
Git-мердж текстового YAML-массива не понимает семантику записи и конфликтует
на границах элементов чаще, чем кажется (пробел/запятая на предыдущей
строке). У файла-на-правило это структурно невозможно: два агента, правящие
разные `id`, правят разные inode, PR не пересекаются никогда, а PR,
правящий существующее правило, конфликтует только с другим PR, правящим
**то же самое** правило — ровно та гранулярность конфликта, которая нужна.
Это не новый для репозитория приём, а перенос уже действующей конвенции:
`openspec/changes/<id>/` — папка на предложение, `docs/decisions/000N-*.md` —
файл на ADR, `docs/research/NN-*.md` — файл на тему. Монолитный `docs/agents/
LABELS.md` — единственный пример обратного в репозитории, и он оправдан
только потому, что его правит не рой параллельных агентов, а редкие точечные
PR плюс автоматический коллектор (`collect_labels.py`), сверяющий ОДНО
направление (код → таблица). Здесь направление обратное и авторов много
одновременно — довод не переносится.

Итог: 40 файлов вместо одного, зато нулевая цена координации по умолчанию.
tasks.md разбивает миграцию по этим же файлам-границам (раздел «Миграция»
ниже) — каждый пункт создаёт свои новые файлы и не пересекается с соседним.

Схема шапки валидируется гвардией `scripts/lib/test_rule_registry.py`
(новый файл, tasks.md): обязательные ключи (включая `proof_test`, `order`
— оба неопциональны, см. ниже и раздел B), `scope` — НЕПУСТОЕ подмножество
`{human, worker, reviewer, hands, system}` (пустой `scope` — ошибка
валидации, не «правило нигде не публикуется», см. раздел G), `id` совпадает
с именем файла, `carrier`/`carrier_status`/`proof`/`proof_test`
согласованы (см. таблицу ниже), ссылка в `carrier` резолвится (файл и
символ реально существуют на момент проверки — иначе носитель может быть
переименован без замеченного разрыва связи, тот же класс дефекта, что и
весь этот change призван закрыть), ссылка в `proof_test` резолвится РОВНО
в один собранный pytest-тест (`pytest --collect-only -q <proof_test>`,
код 0 и ровно одна строка в выводе `<file>::<test>`).

| carrier_status | что означает | что обязано быть заполнено |
|---|---|---|
| `proven` | носитель есть, мутация доказывает | `carrier` — `file::symbol`; `proof_test` — резолвящийся pytest node id; `proof` — `mutation:<путь к диффу>` |
| `pending` | носитель либо есть без доказательства, либо механизируем, но не сделан | `carrier: none` ИЛИ `file::symbol` без мутанта; `proof_test` — тот же node id, если он уже известен, иначе `none`; `proof: none: <почему пока нет>` |
| `infeasible` | сознательно решено не механизировать | `carrier: "none: <причина>"`, `proof_test: none`, причина — почему автоматическая проверка невозможна или неоправданно дорога (см. раздел D) |

`infeasible` не снижает долг храповика на бумаге: раздел D считает долг
суммой `pending + infeasible`, а не одним `pending` — см. там, почему
иначе `pending → infeasible` был бы бесплатным способом обнулить счётчик
одной строкой причины.

## B. Генерация: AGENTS.md и три промпта — проекции реестра

**AGENTS.md.** Секции («Правила, оплаченные чужими ошибками» и т.п.) —
хэндрайтенные заголовки и вступительные абзацы прямо в `AGENTS.md` (без
изменений в момент миграции), тело каждой секции оборачивается маркерами
`<!-- RULES:BEGIN section=<id> --> ... <!-- RULES:END -->` (design уже
называет этот приём, tasks.md п.11). Порядок секций — порядок маркеров в
самом `AGENTS.md` (правка структуры документа — редкое ручное решение
человека, не рутинная миграция очередного правила, поэтому цена
координации по расположению маркеров низкая по своей природе, не по
случайности). Порядок правил ВНУТРИ секции — поле `order: <целое>` в
шапке самого правила (см. пример шапки выше), не отдельный список.

**Почему `order` в самом правиле, а не общий индекс (`_sections.yml`
отвергнут).** Первая версия design несла список `id секции → заголовок` И
отдельный явный список id правил на секцию в одном файле
`_sections.yml` — тот самый монолит, который раздел A отверг для самого
реестра, только перенесённый на уровень выше. Три конкретных отказа:
(1) правило, забытое в списке `_sections.yml`, не печатается НИГДЕ, при
этом схема правила (раздел A), `--check` и храповик (раздел D) остаются
зелёными — файл правила синтаксически валиден сам по себе, просто не
упомянут в постороннем списке; НИЧЕГО не проверяет обратное соответствие
«каждый файл реестра либо в каком-то списке, либо целенаправленно
исключён»; (2) принадлежность правила секции была бы объявлена ДВАЖДY —
полем `section:` внутри правила и позицией в списке `_sections.yml` —
прямое нарушение «Одно место правды» (design.md сам ссылается на это
правило в разделе A, обосновывая файл-на-правило); (3) пункты 1, 5, 6, 7,
8 tasks.md все правят один и тот же `_sections.yml` при каждой миграции
очередного правила — тот же монолитный конец списка, из-за которого
раздел A отверг единый `rules.yaml`, обещанная нулевая цена координации не
наступает. Решение: генератор проверяет ПОЛНОТУ сам — берёт множество ВСЕХ
файлов `docs/agents/rules/*.md` (кроме `mutants/**`/`README.md`), группирует
по `section`, сортирует внутри группы по `order` (конфликт двух правил с одинаковым `order` в одной секции —
ошибка валидатора, не тихий недетерминированный порядок), и печатает
содержимое между маркерами каждой секции, только если для неё есть
маркер с таким `section=<id>` в `AGENTS.md`; правило, ссылающееся на
`section: <id>`, для которого маркера в `AGENTS.md` нет вовсе, — находка
валидатора («правило ссылается на несуществующую секцию»), не молчаливый
пропуск. Так «правило потерялось» и «секция неизвестна» — оба видимые,
механические факты, а не побочный эффект несинхронного списка.

Генератор (`scripts/lib/gen_rules_docs.py`, новый файл) идёт по секциям в
порядке маркеров в `AGENTS.md`, внутри каждой — по правилам в порядке
`order`, и печатает тело каждого файла как есть между маркерами секции.
Части `AGENTS.md`, которые не являются правилами («Что здесь строится»,
таблица слоёв, вводные абзацы) — не генерируются, остаются хэндрайтенными
вне маркеров без изменений. Итог: `AGENTS.md` перестаёт быть местом, где
текст правил пишут напрямую (содержимое между маркерами — generated-
артефакт), но визуально не меняется в момент миграции (то же содержание,
тот же порядок — просто источник переехал).

**Три промпта.** Отбор по `scope`, а не по объёму — и обоснование ЭТОГО
решения не бюджет контекста. Первая версия design утверждала, что
`AGENTS.md` целиком (~69 КБ вместе с `PROTOCOL.md`, сумма двух измеренных
размеров из proposal.md) «не влезает ни в один промпт по бюджету
контекста» — грепом по репозиторию не нашлось ни одной объявленной
константы токенного бюджета (ни у одного из трёх каналов), то есть это
было утверждение-догадка, выданное за факт (нарушение же собственного
правила репозитория «Не знаешь — пиши "не подтверждено"»). Фактический
бюджет промпта — предмет параллельной задачи (см. раздел «Что мы НЕ
делаем», пункт про доставку правил): она измеряет реальный лимит и
решает, влезает ли текст целиком. Отбор по `scope` в ЭТОМ design нужен
независимо от ответа на вопрос про байты — по причине relevance, не
влезания: ревьюеру не нужны правила канала `worker` про `task-branch`, а
воркеру — правила канала `reviewer` про формат вердикта; смешивание
раздувает промпт нерелевантным текстом и рассеивает внимание модели на
объём, который её не касается, даже если технически помещается целиком.
Отбор конкретен:

- `scripts/worker/task.sh` (канал worker) — сегодня строки 299–327 собирают
  промпт, включают `WORKER-PLAYBOOK.md` целиком через `cat`. Генератор
  печатает КОРОТКУЮ форму (`statement`, не всё тело) всех правил с
  `worker` в `scope`, группируя по `section`, и вставляет результат между
  маркерами
  `<!-- RULES:BEGIN scope=worker --><!-- RULES:END -->`
  внутри `docs/agents/WORKER-PLAYBOOK.md` (сам плейбук остаётся
  хэндрайтенным вокруг маркеров — он уже содержит контекст, которого нет в
  реестре: пошаговый маршрут, специфика раннера). `task.sh:326` продолжает
  вшивать плейбук целиком через `cat` без изменений — маркеры внутри уже
  сгенерированного файла, самому `task.sh` про реестр знать не нужно.
- `scripts/review/ai_prompt.md` (канал reviewer) — сегодня не ссылается ни
  на `AGENTS.md`, ни на `PROTOCOL.md` вовсе (proposal.md, п.7). Тот же
  приём: маркеры `<!-- RULES:BEGIN scope=reviewer -->` внутри самого
  `ai_prompt.md`, короткая форма правил с `reviewer` в `scope` — минимум,
  который позволяет ревьюеру ловить нарушения «PR не по шаблону»,
  «Closes/Fixes/Resolves», «второй источник правды» и т.п. как содержательные
  находки, а не только как то, что заметит `contract_check.py` постфактум.
  **Экранирование `$`.** `ai_review.py::cmd_verdict` (или соседняя функция
  сборки промпта) рендерит `ai_prompt.md` через
  `string.Template(...).safe_substitute(...)` — любой буквальный `$` в
  тексте правила (например, `$100`, `${VAR}` как пример команды) либо
  пытается подставиться как плейсхолдер, либо (для `$$`) схлопывается в
  один `$`. Генератор ОБЯЗАН экранировать текст правила при вставке в
  `ai_prompt.md` — заменять каждый `$` на `$$` перед записью между
  маркерами (`string.Template` требует именно такого экранирования для
  буквального доллара) — иначе правило с `$` в тексте молча исказится
  при первом же реальном ревью, а не при генерации, то есть найдётся
  человеком в проде, не тестом.
- `scripts/hands/dsh_task.sh` (канал hands) — сегодня доставляет ноль правил
  (proposal.md, п.6). Маркеры вставляются в новый небольшой файл
  `scripts/hands/RULES-PREAMBLE.md` (генерируемый целиком, без
  хэндрайтенной обвязки — этому каналу пока не нужен отдельный playbook),
  который `dsh_task.sh` подмешивает перед `TASK_TEXT` в вызов DSH headless;
  правка самого `dsh_task.sh` — один `cat`/конкатенация, тот же приём, что
  уже применён в `task.sh:326`.

**Гейт «сгенерируй и сравни» — точка подключения.** Новый шаг в
`.github/workflows/repo-ci.yml`, job `test` (правка — задача tasks.md для
исполнителя, не этого change, файл занят параллельными агентами):

```yaml
- name: Реестр правил сгенерирован из docs/agents/rules (lock-gate)
  run: |
    python scripts/lib/gen_rules_docs.py --check
```

`--check` генерирует все проекции во временную директорию и делает `diff`
с закоммиченными `AGENTS.md`, `docs/agents/WORKER-PLAYBOOK.md`,
`scripts/review/ai_prompt.md`, `scripts/hands/RULES-PREAMBLE.md`; расхождение
— это тот же паттерн, что lock-файлы пакетных менеджеров: печатает diff и
падает с сообщением `запусти 'python scripts/lib/gen_rules_docs.py --write'
и закоммить результат`. Это единственный способ разойтись: примешивать
текст правила руками в промпт (как `task.sh:296` сегодня сочиняет
собственную формулировку `Closes/Fixes/Resolves`) становится невозможно
без того, чтобы CI не заметил рассинхрон в первом же PR.

## C. Доказательство — мутационный харнес

**Формат мутанта.** Для правила с `carrier_status: proven` рядом лежит
`docs/agents/rules/mutants/<id>.diff` — unified diff, применяемый поверх
рабочего дерева, нарушающий ровно тот инвариант, который называет правило
(пример: для «страница GitHub API без обхода», мутант убирает `page=` из
одного разрешённого `ALLOWED_SINGLE_PAGE_CALLS` в `scripts/lib/
test_pagination_guard.py`, либо добавляет новый неразрешённый одностраничный
вызов в фикстуру — конкретная форма мутанта решается при написании
конкретного `.diff`, не этим design). Шапка правила называет также
обязательное поле `proof_test` — pytest node id, который обязан покраснеть
(раздел A; НЕ бывает «по умолчанию файл-гвардия целиком» — см. там же,
почему подразумеваемое умолчание отвергнуто).

**Мутант правила о секретах и других носителях, которых пока нет.**
`carrier_status: proven` для правила «секреты не попадают в репозиторий»
(раздел «Миграция», п.4) рано или поздно потребует фикстуры с
похожей-на-секрет строкой — а собственный гейт репозитория
(`scripts/review/check_pr.py::SECRET_PATTERNS`) сканирует ЛЮБОЙ diff PR
и откажет коммиту, добавляющему такую фикстуру, раньше, чем мутационный
харнес вообще запустится. `check_pr.py` в списке занятых параллельными
агентами файлов (proposal.md, Out) — этот design не правит его. Носитель
проблемы: мутант ослабляет ПРАВИЛО ОБНАРУЖЕНИЯ (код: убирает один паттерн
из списка/выключает одну проверку), а не имитирует ДАННЫЕ нарушения
(строку, похожую на настоящий секрет) — так устроены остальные мутанты
этого design (пример пагинации выше: мутант правит код-разрешение, не
подсовывает поддельный урл). Если конкретному будущему носителю (например
`gitleaks`) для доказательства всё же нужна fixture-строка, она обязана НЕ
совпадать ни с одним паттерном `SECRET_PATTERNS` (список короткий и
специфичный — `ghp_`/`github_pat_`/`AKIA`/`xox`/PEM-заголовок/
`TOKEN|SECRET|KEY|PASSWORD=`; `gitleaks` по умолчанию ловит значительно
более широкий набор форматов, так что fixture заведомо вне этого
короткого списка существует) — записано как ограничение прямо в теле
файла правила `secrets-not-committed.md`, не решается этим design.

**Механизм (`scripts/lib/mutation_harness.py`, новый файл).**
1. `git worktree add --detach <tmp> HEAD` — изолированная копия дерева на
   текущем коммите (не полное копирование файлов: `git worktree` делит
   объекты с основным репозиторием, дешевле и не тащит `node_modules`,
   которых во `worktree` без `npm install` и не будет).
2. **Проверка здоровья ДО мутации.** Запуск `proof_test` внутри `<tmp>` на
   немутированном дереве. Обязан завершиться кодом `0`. Если нет —
   красный результат категории «носитель нездоров» (раздел 0), НЕ
   «мутант пойман»/«мутант выжил»: постоянно красный `proof_test` иначе
   доказывал бы ЛЮБОГО мутанта одним фактом, что он и так был красным
   (измерено на машине владельца: `python -m pytest
   scripts/orchestra/test_scheduler.py -q` даёт 4 failed из-за cp1251 —
   это не находка о правилах, это нездоровый харнес, красящий CI отдельным,
   явно поименованным сообщением: `proof_test для <id> красный ДО мутации —
   почини сам тест, это не находка о носителе`).
3. `git -C <tmp> apply <mutant>.diff` — если патч не применяется (дрейф
   кода), это тоже красный результат, категория «мутант устарел»: правило
   либо устарело, либо мутант не обновлён вместе с кодом — падать тем же
   явным сообщением, не молчать и не путать с «мутант выжил».
4. Запуск `proof_test` внутри `<tmp>` на мутированном дереве, тем же
   инвойсом `python -m pytest -q "<proof_test>"`. Разбор кода выхода —
   не «любой ненулевой», pytest использует диапазон кодов для разных
   классов отказа (0 все прошли; 1 часть тестов упала; 2 прервано;
   3 внутренняя ошибка; 4 ошибка использования командной строки, в т.ч.
   несуществующий путь; 5 ни одного теста не собрано):
   - код `1` — тест пойман (мутация доказана; собранных тестов при этом
     обязано быть РОВНО столько же, сколько на шаге 2, иначе часть
     тестов пропала между прогонами — тоже находка, не тихое совпадение
     кодов);
   - код `0` — мутант ВЫЖИЛ: носитель не ловит собственное нарушение,
     это и есть содержательная находка мутационного тестирования, красит
     прогон с сообщением «carrier не ловит мутацию для <id>»;
   - коды `2`/`3`/`4`/`5` — харнес не смог провести проверку (не «носитель
     плохой», а «прогон не состоялся»): красит прогон ОТДЕЛЬНЫМ
     сообщением «харнес не смог проверить <id>: pytest exit=<N>», не
     засчитывается ни как «доказано», ни как «мутант выжил» — переименование
     файла-гвардии (даёт `exit=4`, путь не найден) или синтаксическая ошибка
     импорта (`exit=2`) не имеют права молча превращать состояние правила в
     `proven` НАВСЕГДА, что было ровно так в первой версии design
     («ненулевой код выхода» принимал 2/3/4/5 наравне с 1).
5. `git worktree remove <tmp> --force`.

**Локальная проверка ДО коммита (`--local`).** `git worktree add --detach
<tmp> HEAD` берёт последний КОММИТ, не рабочее дерево — исполнитель,
пишущий новое правило/носитель/мутант, не может проверить связку, пока не
закоммитил, хотя приёмка каждого пункта tasks.md прямо требует локального
прогона до PR. Решение — отдельный режим `--rule <id> --local`, который
работает БЕЗ `git worktree`, прямо в рабочем дереве: health-check
(`proof_test` как есть), `git apply <mutant>.diff` НА МЕСТЕ, `proof_test`,
затем ОБЯЗАТЕЛЬНО `git apply -R <mutant>.diff` в `finally` (откат
применяется всегда, даже при падении на середине) — рабочее дерево
временно мутируется и гарантированно восстанавливается, ценой того, что
`--local` не даёт изоляции `git worktree` (нельзя гонять параллельно с
другой работой в том же дереве). CI НИКОГДА не использует `--local` —
`--changed`/`--all` в `repo-ci.yml`/ночном workflow всегда работают через
изолированный `git worktree` на `HEAD`, как описано выше; `--local` —
только инструмент разработчика для проверки ДО коммита.

**Что гоняется на каждом PR (выборочно).** Шаг в `repo-ci.yml`, job `test`
(снова — задача исполнителя, не правка этим change):

```yaml
- name: Свежая база для диффа правил (без fetch-depth:0 на весь чекаут)
  run: git fetch --no-tags --prune --depth=1 origin "${{ github.base_ref || 'main' }}"
- name: Мутации правил, задетых этим диффом
  run: |
    python scripts/lib/mutation_harness.py --changed \
      --base "origin/${{ github.base_ref || 'main' }}"
```

`--changed` вычисляет `git diff --name-only <base>...HEAD`, берёт только
правила, чей `carrier`-файл входит в список изменённых, и мутирует только
их (за исключением «тяжёлых» — см. «Стоимость» ниже). Типичный PR трогает
0–2 таких файла — цена близка к нулю относительно уже существующего
набора `test_*_guard.py`, гоняемого в `repo-ci.yml` сегодня.

**Тихий ноль в `--changed`.** Ноль подходящих правил под изменённые файлы
— НОРМАЛЬНЫЙ, ожидаемый исход большинства PR (выше), поэтому шаг не может
слепо красить любой ноль (это сломало бы почти все PR). Опасный ноль —
другой: реестр не загрузился вовсе (путь `docs/agents/rules/` не
существует, YAML не парсится, обёртка `rule_registry.py` вернула пустой
список по ошибке, а не по факту «файлов правда нет»). Шаг обязан различать
эти два нуля явно: ПЕРЕД сравнением с изменёнными файлами
`mutation_harness.py` печатает и утверждает `total_rules_loaded > 0`
(кроме самого первого коммита миграции, где реестр пуст по построению
— на этом этапе шаг ещё не подключён в `CI_GATING`, раздел
«Миграция», п.9); если `total_rules_loaded == 0` при УЖЕ подключённом
гейте — красный результат «реестр правил не загрузился (0 файлов) — это
не «нечего мутировать», а поломка загрузчика». `--changed` с нулём
совпадений при непустом реестре — зелёный, с явным сообщением «0 правил
задето этим диффом», не тихий пропуск шага.

**Что гоняется по расписанию (полный прогон).** Новый workflow
`.github/workflows/rule-mutation-sweep.yml` (новый файл — не входит в список
занятых параллельными агентами файлов, можно завести этим change как ЧАСТЬ
tasks.md для будущего исполнителя):

```yaml
on:
  schedule:
    - cron: "0 3 * * *"   # раз в сутки — вне пиковой активности агентов
  workflow_dispatch: {}
permissions:
  contents: read
  issues: write   # заводит/комментирует находку — см. «потребитель» ниже
jobs:
  sweep:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0   # разовый ежесуточный прогон — цена не размножена на 33 открытых PR
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install pytest pyyaml
      - run: python scripts/lib/mutation_harness.py --all
```

Полный прогон ловит класс «носитель разучился ловить нарушение, потому что
рядом поменялся код, но ни один PR не задел файл самого носителя напрямую»
(тот же класс, что нашла бы гвардия при переименовании функции, но с
гарантией раз в сутки, а не только при точечном PR). `--all` при пустом
или отсутствующем `docs/agents/rules/` — тот же «опасный ноль», что и
выше: красный результат «реестр не загрузился», не тихий зелёный no-op
(в отличие от `--changed`, у `--all` вообще нет легитимного сценария
«ноль — это нормально»: полный прогон существует ИМЕННО чтобы проверить
весь реестр, ноль здесь всегда означает поломку, миграция и открытие
файла `docs/agents/rules/README.md` в п.1 tasks.md гарантируют, что
директория создаётся раньше, чем sweep-workflow заводится, раздел
«Миграция»). **Потребитель красного результата** (иначе тормоз без
газа, `AGENTS.md:127-136`): красный `workflow_dispatch`/`schedule`-прогон
заводит/комментирует issue с меткой `task` через `scripts/gh/issue-create`
(тот же приём, что `pulse_guard.py` уже применяет к другим ночным
находкам, `scripts/orchestra/pulse_guard.py::escalate`) — не просто
красный чек, который никто не обязан открывать; добавление
`rule-mutation-sweep.yml` в `WATCHED_WORKFLOWS` (`pulse_guard.py:180-183`)
— отдельная строка tasks.md (правка файла занятого параллельным агентом,
после освобождения).

**Стоимость: пересчитана по фактическому разбросу, не по самой дешёвой
гвардии.** Замер локально (Windows/Git Bash, репозиторий 7.1 МиБ без
`.git`/`node_modules`, не GitHub Actions — см. «Риски» в proposal.md) даёт
на порядок разные числа в зависимости от файла:

| Файл | Тестов | Время файла | Время одного теста |
|---|---|---|---|
| `scripts/lib/test_pagination_guard.py` | 1 | 0.09–0.83 с (со стартом интерпретатора) | ≈0.83 с |
| `scripts/orchestra/test_repo_invariants.py` | 47 | 0.39 с | ≈0.008 с |
| `scripts/orchestra/test_scheduler.py` | 249 | 126.72 с | до 19.4 с (самый тяжёлый) |

Первая версия design считала стоимость по строке `test_pagination_guard.py`
(0.83 с) и применяла её ко ВСЕМ будущим носителям — если бы `proof_test`
по-прежнему по умолчанию указывал на файл целиком (раздел A уже отменяет
это умолчание), три правила с носителем в `scheduler.py` (его сейчас
правят 7 открытых PR) при выборочном режиме `--changed` добавляли бы
`3 × 126.72 с ≈ 6.3 минуты` к КАЖДОМУ PR, трогающему этот файл — то есть
именно к самым частым PR репозитория, а не к редким. Обязательное поле
`proof_test` (раздел A, node id вместо файла) устраняет САМ КЛАСС этой
дороговизны для новых правил вперёд, но не может задним числом
гарантировать, что КОНКРЕТНЫЙ выбранный тест дешёвый: пример из таблицы
показывает, что даже один тест внутри тяжёлого файла может стоить 19.4 с
(вероятно из-за импорта/фикстур самого модуля, не из-за тела теста).

**Бюджет и порог, объявленные числом.** Харнес меряет время выполнения
`proof_test` на шаге здоровья (baseline, до мутации) и относит правило к
одной из двух категорий по факту, не по ручной метке в файле правила:
- **лёгкое** (baseline ≤ 5 с) — участвует и в `--changed` (per-PR), и в
  ночном `--all`;
- **тяжёлое** (baseline > 5 с) — участвует ТОЛЬКО в ночном `--all`;
  `--changed` пропускает его с явной строкой в выводе «`<id>` тяжёл
  (baseline `<N>` с > 5 с) — доказательство только по ночному прогону»,
  это не тихий пропуск, а объявленный компромисс: сломанный носитель,
  чей proof целиком лежит в `scheduler.py`, не будет пойман тем же PR, что
  его сломал, только в течение следующих ≤24 часов ночным sweep — риск
  называется явно, не прячется за общей формулировкой «выборочный режим
  дешёвый».

Порог 5 с — между измеренным «нормальным» файлом (`test_pagination_guard.py`
≈0.83 с, `test_repo_invariants.py` ≈0.008 с/тест) и измеренным «тяжёлым
выбросом» (19.4 с) — выбран с запасом на холодный старт интерпретатора на
раннере (не откалиброван по production-данным, это стартовое число;
пересматривается тем же способом, что и `REWORK_BUDGET` — по факту, если
окажется тесным или слишком щедрым, задача tasks.md п.17 меряет реальные
числа на раннере и это первая точка, где порог имеет смысл поправить).

**Бюджет per-PR (`--changed`, лёгкие правила).** Типичный PR — 0–2
изменённых carrier-файла (design.md выше), каждый лёгкий (≤5 с) —
добавленная задержка **цель: ≤30 секунд** на PR, что укладывается в
существующий набор шагов `repo-ci.yml`.

**Бюджет ночного прогона (`--all`, все правила, включая тяжёлые).**
Пессимистичный пересчёт на конечных ~40 правилах, без предположения, что
все они лёгкие: если 5 правил окажутся тяжёлыми (сравнимо с worst-case
19.4 с) и 35 лёгкими (≈1 с, с запасом сверх измеренных 0.008–0.83 с) —
`5 × 19.4 + 35 × 1 ≈ 132 с ≈ 2.2 минуты` локально; множитель ×3–5 на
накладные расходы раннера (холодный чекаут, старт Python) даёт
**оценку 7–11 минут** на полный ночной прогон — **бюджет ночного гейта:
цель ≤15 минут**; если по факту (tasks.md п.17, реальный `run_id`) прогон
превышает бюджет — решение (разбить на матрицу job'ов, поднять cron-
интервал) откладывается до момента, когда это измерено, не решается
здесь наперёд.

**Символьное резолвление `carrier`/`proof_test` по типам носителей.**
Задание просит `file:line`, design (раздел «Возражения») настаивает на
`file::symbol` — но резолвинг СИМВОЛА устроен по-разному для разных
языков и типов носителя, и design обязан назвать это явно, не считать
единой процедурой:
- **Python** — `path/to/file.py::function_or_class_or_CONST` — резолвится
  через `ast.parse` (имя функции/класса/константы верхнего уровня, либо
  `Class.method` через один уровень вложенности).
- **Bash** — `path/to/script::function_name` — резолвится регэкспом
  `^function_name\s*\(\)\s*\{` или `^function\s+function_name\b` (пример
  из шапки-примера раздела A: `scripts/git/pr-create::main` — bash-функция
  `main()`).
- **`.mjs`/`.ts`** — `path/to/file.mjs::exportedName` — резолвится
  регэкспом на `export (async )?function exportedName`/`export const
  exportedName`.
- **YAML/workflow-степ — отдельная форма, не `file::symbol`.** У шага
  workflow нет символа в смысле языка программирования — есть только имя
  шага (`name:`), а оно часто русская проза («Белые пятна без метки task
  (класс #179)», `repo-ci.yml:57`) и гниёт от перевода/правки текста так
  же, как номер строки. Форма для этого случая:
  `path/to/workflow.yml#<step-id>`, где `<step-id>` — обязательный
  ключ `id:` у самого шага (у шага, который становится `carrier`, `id:`
  обязателен — если его нет, схема реестра (раздел A) отказывает: «носитель
  указывает на шаг workflow без `id:` — добавь `id:` шагу, это часть
  контракта носителя», не пытается угадывать шаг по номеру строки или по
  тексту имени).
- Значение поля `carrier`/`proof_test` начинается с указания языка/типа
  неявно — по расширению файла до `::`/`#`; валидатор (раздел A) выбирает
  процедуру резолвинга по расширению; расширение, для которого процедуры
  нет (например `.go`, если он появится в репозитории) — отказ валидатора
  с явным текстом «резолвинг для `.go` не реализован», не тихое «не нашёл,
  но не важно».

## D. Храповик долга по правилам без носителя

**Что считается долгом.** Сумма `pending_count + infeasible_count` —
ОБА статуса «не доказано мутацией», не только `pending`. Первая версия
design считала долгом один `pending` и явно исключала `infeasible` из
счёта — дыра: `carrier_status` меняется одной строкой в PR (`pending` →
`infeasible` + причина), и это НЕ требует ни носителя, ни мутанта, ни
дополнительного поля — единственная защита от «долг падает переклейкой
ярлыка, а не работой» — считать оба статуса вместе. `pending → infeasible`
(и наоборот) не меняет сумму — это честная перемаркировка, не рост и не
падение долга, ратчет на неё не реагирует, только PR-ревью (как у любой
другой правки текста). Сумма падает РОВНО тогда, когда правило переходит
в `proven` — только это реальная работа (носитель + мутант написаны и
доказали связь), только это разрешено засчитывать как погашение долга.

**Второй счётчик — общее число файлов реестра (защита от удаления).**
Отдельно от `pending + infeasible`, ratchet считает
`total_count = |docs/agents/rules/*.md|` (кроме `mutants/**`/`README.md`).
Дыра, которую это закрывает: удаление файла `proven`-правила снижает
`pending_count` НИКАК не меняя его (`pending` не считал `proven`), но и не
краснит НИЧЕГО в первой версии design — сгенерированный `AGENTS.md`
молча теряет абзац (`--check` сравнивает с НОВЫМ сгенерированным выводом,
оба уже без абзаца — совпадают), схема зелена (нет файла — нет ошибки
схемы), единственный существующий детектор — инвариант обратной
связности раздела E, и он сознательно НЕ гейтящий. `total_count(HEAD) <
total_count(base)` — красный результат: «реестр потерял <N> файлов
правил с прошлого коммита на main: <id1>, <id2> — удаление правила из
реестра требует явного решения, не побочного эффекта правки соседнего
файла». Это не отдельная ручная константа (тот же принцип, что у
`pending + infeasible` — база сама сдвигается с каждым слиянием), и не
блокирует ЗАКОННОЕ удаление (правило признано ошибочным/дублирующим) —
для него это тот же ratchet, что и для роста `pending`: сообщение
называет удалённые id, PR-автор либо восстанавливает файл, либо ratchet
осознанно принимается, потому что PR добавляет НОВЫЙ mutation harness
run, доказывающий, что причина удаления — не тихая порча (тот же прогон,
что доказывает `proven`, доказывает и обоснованность удаления —
дополнительной ручной кнопки «подтверди удаление» не заводится, дешевле
считать нулём такого рода PR и полагаться на ревью, как на любой другой
разрушающий диф).

**Механизм ratchet (`scripts/lib/rule_carrier_ratchet.py`, новый файл).**
Не хранит число-порог руками (не по образцу `REWORK_BUDGET` — там порог
калиброван замером и должен жить как объявленная константа; здесь порог —
это факт «сколько долга было на прошлом коммите», а не решение). Скрипт:

1. Считает `unproven_count(HEAD) = pending_count + infeasible_count` и
   `total_count(HEAD)` — оба на текущем дереве.
2. Считает те же два числа для `base` тем же способом, читая
   `git show <base>:<путь>` для каждого файла реестра, каким он был на
   `origin/main` (`base` — параметр, тот же `base_ref`, что и в мутационном
   гейте; получение свежего `base` — тем же `git fetch --depth=1`, что и в
   разделе C, не требует `fetch-depth: 0` на весь чекаут).
3. `unproven_count(HEAD) > unproven_count(base)` ИЛИ
   `total_count(HEAD) < total_count(base)` — красный результат, сообщение
   называет ИМЕНА затронутых правил (не просто число — правило репозитория
   «Алерт не гадает», `AGENTS.md:138-148`, применённое к этому же гейту):
   `новый pending/infeasible без proven: <id1>, <id2> — либо добавь carrier
   и мутант, либо обоснуй infeasible` и/или `реестр потерял правила:
   <id3> — восстанови файл или объясни удаление в теле PR`.
4. Оба неравенства ложны — зелёно, снижение не требует отдельного шага
   «поднять порог» (в отличие от порогов вроде `REWORK_BUDGET`, здесь
   нечего поднимать — планка это прошлое состояние `main`, она сама
   подтягивается вниз/вверх с каждым слиянием).
5. **Тихий ноль при пустом реестре.** `docs/agents/rules/` отсутствует или
   пуст на ОБОИХ снимках (`HEAD` и `base`) даёт `0 > 0` и `0 < 0` — оба
   ложны, ratchet тривиально зелен, что корректно ТОЛЬКО до того, как
   первый файл правила вообще появился в `main` (раздел «Миграция», п.1).
   После этого момента `total_count(base) == 0` при
   `total_count(HEAD) == 0` — само по себе краткое временное окно, но
   гейт добавляется в `CI_GATING` НЕ раньше, чем `total_count(base) > 0`
   (раздел «Миграция», п.9) — до этой точки шаг существует, но не
   гейтящий, тот же порядок, что у остальных инвариантов `repo_invariants.py`.

Это самоподдерживающийся храповик без отдельной ручной константы, которую
нужно не забыть поправить — тот же класс дефекта, которого стоило избежать,
судя по замеру `docs/agents/LABELS.md` про `review:large-ok`
(«текстовая проверка "газ назван" не эквивалентна "газ работает"»):
константа, которую нужно помнить поправить руками, имеет тенденцию
отставать.

**Точка подключения.** Тот же шаг `repo-ci.yml`, job `test`, что и гейт
генерации (раздел B) — оба дешёвые (чтение файлов + `git show`, без сети),
естественно живут рядом одним новым шагом «Реестр правил: не расти долгом»
(задача tasks.md для будущего исполнителя файла).

## E. Обратная связность: носитель без правила в реестре

Разведка нашла 7 таких носителей: `exec_bit_guard`, `orphan_test_guard`,
`epic_guard`, `do_hotpath_aggregate`, `dsh_edge_pnpm`,
`branch_protection_watch`, `upstream_drift`. Решение — не переписывать это
прозой в `AGENTS.md` (раздувание на каждый инцидент — тот самый антипаттерн,
которого правило «Инцидент оставляет инвариант, а не только фикс»,
`AGENTS.md:150-161`, и так не требует: оно требует инвариант в
`repo_invariants.py`, не абзац в `AGENTS.md`).

**Каждый такой носитель получает свою запись в реестре с `scope: [system]`
и `section: incident-invariant`.** `statement` — формулировка условия,
которое несёт сам код (например, для `dsh_edge_pnpm`: «standalone `dsh-edge`
собирается только `pnpm`, не `npm install` поверх патч-серии — класс #43»).
`carrier` указывает на существующий файл/функцию, `proof` — на уже
существующий тест этого класса (`test_dsh_edge_pnpm_guard.py` и т.п. —
если тест уже мутационно не доказан, `carrier_status: pending`, как у
любого другого правила, без исключения для этой категории). Генератор
(раздел B) НЕ печатает `section: incident-invariant` правила ни в `AGENTS.md`,
ни в один из трёх промптов (`scope` не содержит ни одного из `human/worker/
reviewer/hands`) — они существуют в реестре только как машиночитаемая
запись для гвардии обратной связности и для мутационного харнеса, `AGENTS.md`
не растёт ни строкой.

**Гвардия обратной связности** — новая `check_*`-функция в
`scripts/orchestra/repo_invariants.py` (правка — задача tasks.md для
будущего исполнителя, файл сейчас занят параллельным агентом): сканирует
`scripts/**/test_*_guard.py` и `check_*` из самого `repo_invariants.py`,
берёт множество путей/символов, сверяет с множеством всех `carrier` из
`docs/agents/rules/*.md` (независимо от `scope`) — путь/символ гвардии, не
упомянутый ни одним `carrier`, это находка.

**Она же ловит УДАЛЕНИЕ правила** (не только его отсутствие с самого
начала): если файл правила удалили, а код-носитель остался — тот же
самый скан находит путь/символ носителя без соответствующего `carrier` в
реестре, тем же одним проходом. Раздел D добавляет отдельный,
независимый счётчик (`total_count` не может УМЕНЬШИТЬСЯ) именно потому,
что этот инвариант E сознательно НЕ гейтящий (см. ниже) — до его
включения единственная защита от удаления должна работать уже сейчас,
без ожидания освобождения `repo_invariants.py`.

**Объявленное условие включения в `CI_GATING`** (не «когда починим» —
`AGENTS.md`, «Тормоз без газа не принимается», применённое к этому же
инварианту, по образцу уже существующей записи для инварианта 3,
`repo_invariants.py:172-193`): как и остальные инварианты
`repo_invariants.py`, добавляется НЕ в `CI_GATING` сразу (по образцу
существующего решения владельца для новых инвариантов, `repo_invariants.py:
79-94` — сначала замер долга числом на живом репозитории, потом
включение). Проверяемое условие для ЭТОГО инварианта: `check_orphan_
carrier(данные) == []` (ноль находок) на `main` В ТЕЧЕНИЕ 3 дней подряд
ПОСЛЕ того, как разведанные 7 сирот получили свои записи (раздел
«Миграция», п.5) — то же самое «сначала замер долга числом, потом
включение», но с конкретным числом (0) и конкретным окном (3 дня), а не
неопределённым «когда-нибудь потом». До этого момента инвариант печатается
в отчёте (наблюдательно), не роняет CI — тот же класс, что инварианты 1,
2, 5 сегодня (`repo_invariants.py`, наблюдательны с 2026-09-03, что само
по себе не аргумент «можно оставить навсегда»: разница в том, что для
ТЕХ трёх условие включения не названо явно нигде, а для этого — названо
здесь, и наблюдательный статус не бессрочен по построению документа, а
привязан к измеримому условию, которое кто-то обязан проверить, когда
миграция (раздел «Миграция», tasks.md) слита).

## F. Обратное направление: правило → текст вне реестра

**Проблема, которую раздел B честно не закрывает.** Гейт «сгенерируй и
сравни» ловит расхождение между реестром и ЧЕТЫРЬМЯ конкретными
сгенерированными файлами (`AGENTS.md`, `WORKER-PLAYBOOK.md`,
`ai_prompt.md`, `RULES-PREAMBLE.md`) внутри объявленных маркеров. Он НЕ
ловит и не может ловить нормативную прозу, написанную где угодно ЕЩЁ:

- `docs/agents/PROTOCOL.md` (44 969 байт на момент этого design — крупнее
  самого `AGENTS.md`) не генерируется вообще и не входит в scope этого
  change (proposal.md, Out); именно там живёт трижды продублированный
  запрет `Closes/Fixes/Resolves`, разобранный в proposal.md как пример
  класса проблемы.
- `openspec/specs/journal-tasks-hands.md` — 37 пронумерованных нормативных
  требований, крупнейший нормативный корпус репозитория, целиком вне
  scope.
- Строковые литералы прямо в скриптах, собирающих промпт: `task.sh:291`
  (`route_intro`), `task.sh:296` (`route_pr_step`, сочиняющая собственную
  формулировку `Closes/Fixes/Resolves`) — код, не документ, `--check`
  раздела B их не видит в принципе, потому что не рендерит и не диффует
  исходники скриптов.
- Плейбук и `ai_prompt.md` ВНЕ объявленных маркеров (текст до/после блока
  `RULES:BEGIN/END`) — гейт диффует только содержимое между маркерами,
  редактор может дописать абзац рядом, `--check` этого не заметит.

**Решение: узкий, честно ограниченный носитель для уже найденного случая,
плюс явное признание, что общий детектор не входит в этот change.**
Полный детектор «любая новая нормативная проза где угодно в репозитории»
эквивалентен NLP-классификатору намерения текста — за пределами того, что
может сделать регэксп/AST-гвардия, и не решается этим change (нет способа
механически отличить «нормативное правило» от «описательный абзац» без
семантики). Вместо обещания механизировать всё направление (первая версия
design утверждала это прямо и было неверно), design ограничивается
конкретным, уже найденным классом дублирования:

- Новое опциональное поле шапки `duplicate_signatures: [<regex>, ...]` —
  список regex-паттернов, которыми правило может быть НЕЗАВИСИМО
  переформулировано в известных местах-нарушителях. Для правила
  `pr-only-via-pr-create` это, например,
  `r"Closes/Fixes/Resolves\s+ЗАПРЕЩЕН"` (буквально фраза из
  `task.sh:296`).
- Новая гвардия `scripts/lib/test_duplicate_prose_guard.py` (новый файл,
  tasks.md) сканирует ЗАКРЫТЫЙ, явно перечисленный список файлов вне
  реестра (`docs/agents/PROTOCOL.md`, `scripts/worker/task.sh`,
  `scripts/hands/dsh_task.sh`) на совпадение с `duplicate_signatures` ЛЮБОГО
  правила реестра — находка красит CI с сообщением «`<file>:<line>`
  формулирует `<rule-id>` заново, вместо ссылки на реестр».
  Список файлов — статический, руками расширяемый (не автообнаружение
  ВСЕХ файлов репозитория — это и был бы недостижимый общий детектор).

**Явное признание, что дублирование НЕ закрывается полностью.** После
этого узкого носителя `PROTOCOL.md` и `journal-tasks-hands.md` ЦЕЛИКОМ
остаются вне механической проверки: новое правило, добавленное туда без
регистрации в `docs/agents/rules/`, не будет замечено НИКЕМ автоматически
— то же самое «правило не отличимо от пожелания», которое этот change
призван закрыть, просто сдвинутое на один уровень: сегодня ЛЮБОЕ правило
может быть добавлено без носителя, после этого change — правило,
добавленное МИМО реестра в `PROTOCOL.md`, всё ещё может быть добавлено
без реестровой записи. Единственная защита — процессная, не механическая:
`docs/agents/PROTOCOL.md` явно помечается комментарием в начале файла
(«новые нормативные требования сюда не добавляются — заводи запись в
`docs/agents/rules/`, см. design.md rule-carrier-registry»), и ревью PR,
трогающих `PROTOCOL.md`/`journal-tasks-hands.md`, ловит это человеком, как
и сегодня. Это осознанный компромисс, не молчание: полное закрытие
направления «правило → текст» для ВСЕХ существующих и будущих файлов —
отдельная, будущая задача (мигрировать `PROTOCOL.md`/спеку в реестр
целиком, что само по себе больше по объёму, чем миграция `AGENTS.md`
этим change), а не часть этого design.

## G. Отбор по `scope`: храповик доставки и защита от неверной разметки

**Проблема.** Отбор по `scope` (раздел B) не проверяется ни на что, кроме
принадлежности объявленному множеству `{human, worker, reviewer, hands,
system}` (раздел A). Ошибка миграции — правило нужно исполнителю, но
размечено `scope: [human]` — не ловится НИЧЕМ: схема валидна (`human` —
легальное значение), генерация зелена (правило корректно НЕ печатается в
`WORKER-PLAYBOOK.md`, потому что `worker` действительно не в `scope`),
CI зелен. Правило тихо исчезает из промпта исполнителя при полностью
зелёном конвейере — ровно тот класс дефекта, который весь этот change
призван устранить, только на один уровень глубже (не «носителя нет», а
«носитель есть, но правило до него не доходит»).

**Отсутствие `scope` — не «все каналы» по тихому умолчанию, а ошибка
данных** (уже зафиксировано в разделе 0: поле обязательно и непусто).
Но обязательность поля не защищает от НЕВЕРНОГО, а не отсутствующего
значения — сужение множества `scope` относительно «естественного»
(правило похоже на общее, но размечено единственным узким каналом) само
по себе не ошибка синтаксиса, поэтому нужен отдельный сигнал:

- **Храповик доставки (`scripts/lib/rule_delivery_ratchet.py`, новый
  файл, часть D по механике, отдельный файл по ответственности)** —
  считает, для каждого канала `c ∈ {human, worker, reviewer, hands}`,
  число правил реестра с `c` в `scope`: `delivered_count(c)`. Эта величина
  НЕ ИМЕЕТ ПРАВА УМЕНЬШИТЬСЯ между `base` и `HEAD` (тот же механизм
  сравнения с `git show <base>:<путь>`, что и в разделе D) — падение
  числа правил, доставленных в канал `c`, красный результат: «канал
  `<c>` получает на `<N>` правил меньше, чем на main: `<id1>` — сужение
  `scope` требует причины в теле PR, не тихого уменьшения». Это НЕ
  запрещает законное сужение (правило действительно оказалось нерелевантно
  каналу) — как и у ratchet раздела D, PR-ревью — газ для осознанного
  снижения, автоматика ловит ТОЛЬКО тихое/случайное.
- **Сужение `scope` относительно значения по умолчанию требует
  поля-причины.** Шапка правила несёт необязательное поле
  `scope_reason: "<почему сужено"` — валидатор (раздел A) требует его
  НЕПУСТЫМ, если `scope` — собственное подмножество
  `{human, worker, reviewer, hands}` (то есть не включает все четыре
  человеко-ориентированных канала); `system`-only правила (раздел E)
  освобождены от этого требования (у них `scope_reason` не нужен — их
  сужение до `[system]` — не сужение доставки, а другая категория записи
  целиком, объяснённая разделом E).

Оба механизма — храповик по числу и обязательная причина по факту —
дополняют друг друга: причина ловит ОСОЗНАННОЕ, но недокументированное
сужение в момент миграции; храповик ловит СЛУЧАЙНОЕ уменьшение позже
(например, правку `scope` без понимания, что это уменьшает доставку в
уже работающий канал).

## H. Газ для новых гейтов

**«Тормоз без газа не принимается» (`AGENTS.md:127-136`), применённое к
трём новым обязательным шагам этого change** (генерация-сравнение,
мутации, храповик — раздел B/C/D): каждый — детерминированная чистая
проверка (без сети, без внешнего состояния), поэтому у КАЖДОГО есть
автоматический газ по построению — «почини баг в
`gen_rules_docs.py`/`mutation_harness.py`/`rule_carrier_ratchet.py` (или
в файле правила, который он проверяет) и закоммить — шаг зеленеет на
следующем прогоне», тот же класс газа, что у любого другого детерминиро-
ванного теста в CI (никто не заводит отдельный «аварийный выключатель»
для упавшего `pytest`).

**Отдельный риск — не «шаг неверно красит одно PR», а «баг в самом
generated-скрипте блокирует ВСЕ PR, трогающие любой из четырёх
сгенерированных файлов, пока фикс не смёржен».** Для этого сценария
нужен газ для ЧУЖОГО PR, не только для того, что нашёл баг — по образцу
уже существующего в репозитории `orchestra:skip` (`docs/agents/LABELS.md`,
label на PR, обходит `contract_check.py` целиком, сам является газом, не
требует отдельного снятия). Новая метка `rules-registry:skip` (задача
tasks.md для владельца `docs/agents/LABELS.md`, файл занят) —
поставленная человеком на конкретный PR — пропускает все три новых шага
ДЛЯ ЭТОГО PR; злоупотребление видно в истории PR, тем же способом, что и
у `orchestra:skip`. Это НЕ снимает гейт репозиторно (в отличие от
общего disable-флага, который легко забыть выключить обратно) — каждый
следующий PR по-прежнему гейтится, пока баг жив, что и есть корректное
поведение: баг чинится один раз, а не обходится на каждом PR по
отдельности вручную.

## Миграция 40 правил

Порядок — по риску и по естественной группировке (файловая независимость
между шагами разбирает tasks.md подробно):

1. **Инфраструктура сначала, без единого перенесённого правила.** Схема
   (раздел A), генератор (B), мутационный харнес (C), ratchet (D) — на
   ПУСТОМ или почти пустом реестре (1–2 иллюстративных файла), чтобы
   механизм был проверен на себе, прежде чем на него полагаются 40 правил.
2. **7 уже доказанных правил** (`task_ref` guard, pagination guard, label
   registry guard и т.п. — proposal.md, «уже сложилось») переносятся первыми:
   для них `carrier`/`proof` уже фактически существуют, перенос — заполнение
   шапки и написание/подтверждение мутанта, наименьший риск регресса
   поведения промптов (эти правила и так уже где-то присутствовали текстом).
3. **17 правил с носителем без доказательства.** Перенос текста +
   `carrier_status: pending` + `proof: none: "носитель есть
   (file::symbol), мутант не написан"` — честно, без вымышленного
   `proven`. Написание мутантов для них — отдельные, более мелкие задачи
   после того, как харнес уже проверен на п.2.
4. **16 правил без носителя** (см. «Приложение» ниже — рабочий список,
   уточняется при самой миграции). Каждое размечается `pending` или
   `infeasible` с причиной (раздел D). Два конкретных правила из этого
   списка — «секреты не попадают в репозиторий»
   (`secrets-not-committed`, `AGENTS.md:219-222`) и «ссылки — относительный
   markdown, не wiki-links» (`relative-markdown-links`, `AGENTS.md:212-213`)
   — кандидаты на быстрый перевод `pending → proven` следующей узкой
   задачей: оба механизируемы одним CI-шагом (`gitleaks`/`grep` на
   wiki-links соответственно). Дальше в тексте этого design они называются
   этими двумя слугами (id файла реестра), не отдельной буквенно-числовой
   нумерацией («R27»/«R29» из устного разбора, приведшего к этой
   переделке) — намеренно: у репозитория уже есть числа задач (issue) и
   теперь будут id файлов реестра; третья, самостоятельная нумерация
   (`R<N>`) была бы третьим именем для одной и той же вещи, ровно тот
   класс, что правило «Одно место правды» запрещает, если её ни разу не
   зафиксировать формально. Эта работа (сами гейты gitleaks/grep) — не в
   рамках данного change (раздел Scope/Out в proposal.md), но реестр
   обязан честно показать оба правила как ближайший, самый дешёвый прирост
   покрытия.
5. **7 носителей-сирот** (раздел E) — заводятся в реестр параллельно с
   любым из шагов 2–4 (не зависят от них).
6. **Самоприменимость: реестр для 4 механизмов реестра.** После того как
   схема (1), харнес (2), генератор (3) и ratchet (4-инфраструктурный, не
   путать с нумерацией миграции) существуют — каждый получает свою запись
   `scope: [system]`, `section: incident-invariant` и мутант, доказывающий
   его собственный `carrier_status: proven` тем же харнесом, которым он
   доказывает чужие правила (proposal.md, находка «самоприменимость
   провалена» — записи реестра создаются в тех же задачах, что и код
   механизмов, не откладываются на потом текстовой инструкцией
   «сними проверку руками»).
7. Гвардия обратной связности (E) включается по объявленному условию
   (раздел E — 0 находок 3 дня подряд ПОСЛЕ того, как 7 сирот из п.5
   размечены), не «после всего сразу».
8. **Подключение генератора к реальным файлам** (`AGENTS.md`,
   `WORKER-PLAYBOOK.md`, `ai_prompt.md`, новый `RULES-PREAMBLE.md`) — после
   того, как реестр покрывает 100% из 40 (иначе генератор в момент
   переключения молча укоротил бы `AGENTS.md`, вырезав ещё не перенесённые
   правила — фактически откат содержания, который нужно не допустить).
   **Никакого промежуточного «режима дополнения» не заводится**: первая
   версия design предлагала сверять `--check` только с уже перенесёнными
   секциями до полного покрытия — это в точности тот же паттерн «тихого
   нуля», что раздел C закрывает для харнеса (сравнение пустого/частичного
   множества с самим собой всегда совпадает, зелено означает «ничего не
   проверено», а не «всё в порядке»). Вместо частичного режима: генератор
   НЕ подключается к реальным файлам вообще до этой точки (п.3 tasks.md
   уже тестирует его только на фикстурах) — здесь нечего закрывать тихим
   нулём, потому что до п.8 `--check` для реальных файлов не запускается
   НИКЕМ, а не запускается-и-врёт.
9. **Подключение CI-гейтов** (генерация, мутации, ratchet, обратная
   связность) — после п.8, чтобы не гейтить PR на инфраструктуре, которая
   ещё не покрывает 100% случаев.

**Доставка правил в промпты (три канала) — предшествующая задача, НЕ
шаг этой миграции.** Проектной параллельно (на момент этого design)
ведётся отдельная, более узкая работа: измерить фактический бюджет
промпта каждого канала и, если текст `AGENTS.md`+`PROTOCOL.md` влезает
целиком, вшить оба файла в промпты трёх каналов одной-двумя строками
конкатенации плюс гвардия на присутствие текста — точечное закрытие
находки «0 байт правил доходит до исполнителя» (proposal.md, п.3),
быстрее, чем ждёт весь этот change. Точный номер/ссылка на неё — не
установлен на момент написания этого текста (не найден поиском по
открытым issue/PR на дату design; задача tasks.md — подставить реальную
ссылку, как только она находится, до архивации этого change). Раздел
«Что мы НЕ делаем» ниже фиксирует, почему реестр всё ещё нужен ПОСЛЕ
того, как та задача сольётся.

## Возражения

**Против буквального `carrier: file:line`.** Задание прямо просит поле
`carrier: file:line исполняемого носителя`. Design хранит `file::symbol`
(имя функции/константы/файла-обёртки), а не номер строки, и это не
косметика: репозиторий уже дважды документировал ровно эту проблему на
собственном опыте. `scripts/orchestra/repo_invariants.py:176-179` прямым
текстом объясняет, почему собственный код инварианта 3 ссылается на
`scheduler.trigger_ai_review` в форме `file::symbol`, а не строкой: «номера
строк гниют, класс уже закрывался этим переходом». `openspec/changes/
task-rework-loop/tasks.md:38-41` независимо констатирует тот же факт для
другого файла: «Проверить перед реализацией текущий номер строки
(`scheduler.py` меняется параллельно другими PR ... номера строк смещаются
от любого слияния)». Реестр правил живёт в репозитории, где параллельно
открыто по 5–15 PR на «горячий» файл (`repo-ci.yml` — 15, `scheduler.py` —
7, по вводным этой задачи) — `carrier: file:line`, записанный сегодня,
устареет за часы, и гвардия схемы реестра (раздел A) будет либо ловить
ложные срабатывания на каждом чужом слиянии, либо (что хуже) научится
не проверять актуальность номера и станет тем самым «носителем, который сам
не доказан» — второй пункт проблемы, которую весь этот change призван
закрыть. `file::symbol` резолвится в актуальную строку ТОЛЬКО в момент
рендера человекочитаемого вида (например, в отчёте гвардии обратной
связности, раздел E) — сам реестр номера не хранит и не может разойтись с
кодом при чужом, не относящемся к правилу, слиянии.

**Честная вторая половина цитаты.** Первая версия этого раздела приводила
только `repo_invariants.py:176-179` в пользу символьной формы, не упоминая,
что тот же файл (`:495-502`) явно ОТКАЗАЛСЯ от символьной формы для
инварианта 5 («Два открытых task-issue ссылаются на один и тот же
file:line») — измеренная причина отказа: `pulse_guard.py::escalate`
оказался ложным совпадением между задачами #244 и #201, потому что имя
часто используемой функции встречается во многих несвязанных контекстах, а
точное совпадение `file:line` — достаточно редкое совпадение, чтобы быть
сигналом именно ТАМ. Это не противоречие, а разные задачи с разными
требованиями к сигналу, и раздел обязан показать обе, а не одну удобную:
инвариант 5 решает «две НЕЗАВИСИМЫЕ задачи случайно сослались на одно и то
же место» — здесь совпадение имени функции ложноположительно, потому что
имя может встретиться где угодно, а точная строка — редкое совпадение
именно из-за номера. Реестр правил решает другую задачу — «эта ОДНА,
заранее известная ссылка продолжает указывать на реальный код спустя
время и чужие правки» — здесь, наоборот, номер строки ложноотрицателен
(гниёт от любого чужого слияния над тем же файлом), а имя символа
стабильно, потому что это тот же файл/тот же автор ссылки, не совпадение
с посторонним контекстом. Итоговая позиция: согласен с намерением задания
(носитель обязан указывать точное место), не согласен с буквальной формой
поля — `file::symbol` достигает той же цели без унаследованного и уже
документированного в этом же репозитории дефекта, для ЭТОГО конкретного
случая использования (не для случая инварианта 5, где выбор верно
остался числовым).

## Что мы НЕ делаем и почему

- **Не заменяем `repo_invariants.py`/`test_*_guard.py` новым единым
  движком проверок.** Реестр — слой ССЫЛОК на существующие носители
  (`carrier` указывает на уже написанный код), не переписывание этого кода
  под новый интерфейс. Оба существующих уровня (снимки состояния / гвардии
  по исходнику) остаются собственными файлами со своей логикой; реестр не
  знает, КАК устроена проверка внутри, только ГДЕ она лежит и КАКИМ
  мутантом доказывается.
- **Не переносим в реестр архитектурную прозу `AGENTS.md`** («Что здесь
  строится», таблица трёх слоёв, объяснение free-плана). Реестр — только
  для проверяемых утверждений (правил), не для контекста, объясняющего,
  почему система устроена так, как устроена. Граница уже проведена в самом
  `AGENTS.md` заголовками разделов — раздел B использует именно эту
  границу, не изобретает новую.
- **Не пишем сами 40 файлов реестра в рамках этого change.** Design
  проектирует формат и порядок; фактический перенос текста 40 правил —
  содержание задач tasks.md для будущих исполнителей, каждая — отдельный
  новый файл, без пересечения по файлам между агентами (см. tasks.md).
- **Не трогаем ни один из файлов, перечисленных как занятые параллельными
  агентами** (`cf-worker/**`, `.github/workflows/{deploy-worker,
  inbox-issue,repo-ci}.yml`, `scripts/lib/{review_labels,
  test_pagination_guard,exec_bit_guard,orphan_test_guard,
  test_pr_body_label_release_reachable}.py`, `scripts/orchestra/
  {contract_check,pulse_guard,repo_invariants,scheduler}.py`, `scripts/
  review/{ai_review,check_pr}.py`, `docs/agents/LABELS.md`, `dsh-edge/
  {verify-ingest-allowlist,smoke-edge-plugins}.mjs`) — точки подключения к
  ним названы явно (workflow-шаги, `check_*`-функция), но правка — задача
  tasks.md для исполнителя ПОСЛЕ того, как эти файлы освободятся, не
  предложение менять их сейчас.
- **Не вводим второй ratchet для `proof` (мутационно доказано / нет).**
  D специфицирует храповик ровно там, где просит задание — на
  `carrier_status: pending` (16 правил без носителя). Отдельный счётчик
  «носитель есть, мутации нет» (17 правил, раздел «Миграция», п.3) —
  честно виден в реестре полем `proof: none: ...`, но не гейтится ростом:
  превращать это во второй обязательный храповик — расширение задания,
  не его буквальное исполнение; если владелец захочет — это узкая
  следующая задача поверх уже работающей инфраструктуры.
- **Не решаем, какой конкретно мутант писать для каждого из будущих 40
  правил.** Раздел C фиксирует формат и механизм запуска; содержание
  каждого `.diff`-файла — задача, требующая понимания конкретного
  инварианта, решается по одному правилу за раз в tasks.md, не пачкой
  здесь.
- **Не механизируем направление «правило → текст» для ЛЮБОГО места
  репозитория.** Раздел F даёт узкий, явно перечисленный список файлов
  под проверкой (`PROTOCOL.md`, `task.sh`, `dsh_task.sh`) и явно признаёт,
  что дублирование текста правила в местах ВНЕ этого списка (в первую
  очередь — весь `docs/agents/PROTOCOL.md`, весь
  `openspec/specs/journal-tasks-hands.md`) остаётся возможным и не
  ловится механически этим change. Общий детектор «любая новая
  нормативная проза где угодно» эквивалентен классификации намерения
  текста и не решается регэкспом/AST — честно называем это пределом, а
  не проектируем то, что не умеем гарантировать.
- **Не переносим доставку правил в реальные промпты в это же предложение,
  вместо этого ссылаемся на предшествующую задачу.** Первая версия
  design ставила подключение генератора к `AGENTS.md`/трём промптам
  (раздел «Миграция», было пп.9–10) сразу после первых восьми пунктов
  миграции — то есть самая дорогая измеренная дыра (ноль байт правил у
  исполнителя, proposal.md п.3) закрывалась бы позже всего в очереди этого
  change. Отдельная, более узкая задача решает именно эту дыру раньше:
  измеряет фактический бюджет промпта и, если текст `AGENTS.md`+
  `PROTOCOL.md` влезает целиком, вшивает оба файла в три канала
  конкатенацией плюс гвардия присутствия текста (раздел «Миграция»,
  предпоследний абзац). **Рассмотренная и отвергнутая альтернатива — считать
  эту задачу достаточной и закрыть реестр целиком как избыточный.**
  Отвергнута, потому что решает только ОДНУ из четырёх находок
  proposal.md («правило не доходит ни до одного канала», п.4), а не
  остальные три: «носителя нет вовсе» (п.1) — вшитый текст не создаёт
  гвардий; «носитель сам не доказан» (п.2) — вшитый текст ничего не
  доказывает мутацией; «одно правило — три формулировки» (п.5) — вшитый
  текст ПОДТВЕРЖДАЕТ дублирование навсегда (три копии становятся частью
  трёх зашитых блобов), вместо того чтобы свести их к одному источнику.
  Другими словами: предшествующая задача чинит «правило не доехало», этот
  change — «правило доехало, но им можно было бы соврать/забыть/не
  доказать» — разные дефекты одного класса, оба реальны, только первый
  дешевле и предшествует по порядку.
- **Заводим GitHub issue, но не открываем PR этим change.** Первая версия
  design (v1, ветка `design/rule-carrier-registry`) была написана БЕЗ
  задачи пула — нарушение контракта (`scripts/lib/task_ref.py::
  _BRANCH_TASK_RE`, `scripts/orchestra/contract_check.py`,
  `scripts/git/pr-create` — все трое требуют `agent/<N>-<slug>` с числом

  issue (`scripts/gh/issue-create`, задача #648), арендует её
  (`claim_task.py claim 648`) и работает на ветке
  `agent/648-rule-carrier-registry-v2` — по прямому указанию постановки
  задачи, PR всё ещё не открывается этим change, его открывает владелец.
