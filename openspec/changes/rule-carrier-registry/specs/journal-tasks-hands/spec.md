## ADDED: Реестр правил — ходячий скелет (правило → носитель → доказательство одной мутацией)

47. Нормативное правило репозитория может иметь запись в машиночитаемом
    реестре — один файл `docs/agents/rules/<id>.md` на правило (YAML-шапка
    + текст), а не строка в общем списке. Шапка несёт РОВНО пять
    обязательных полей: `id` (совпадает с именем файла без `.md`),
    `statement` (короткая формулировка), `carrier` (`file::symbol`
    исполняемого носителя ИЛИ `"none: <причина>"`), `proof_test`
    (конкретный pytest node id, не файл-гвардия целиком — файл может
    нести не относящиеся к правилу тесты — ИЛИ литерал `"none"`) и
    `status` (`proven`/`unproven`/`none`).

    47.1. Значение `status` определяет допустимые формы `carrier` и
        `proof_test`: `proven` требует `carrier` в форме `file::symbol`,
        где и файл, и символ реально резолвятся, и `proof_test`,
        резолвящийся РОВНО в один собранный pytest-узел (`pytest
        --collect-only -q <node>`, код выхода 0, ровно одна строка узла
        в выводе); `unproven` требует `carrier` в форме `file::symbol`
        (носитель есть, мутация ещё не доказана; формы `"none: …"` при
        `unproven` нет — носителя нет, это `none`, три статуса имеют
        непересекающиеся тела записи),
        `proof_test` — резолвящийся node id, если уже известен, иначе
        `"none"`; `status: none` требует `carrier` в форме `"none:
        <причина>"` и `proof_test` строго `"none"`. Валидатор отклоняет
        запись, где `id` не совпадает с именем файла, любое из пяти
        полей отсутствует или пусто, в шапке есть поле ВНЕ пяти
        известных, `status: proven` при отсутствующем файле мутанта
        `docs/agents/rules/mutants/<id>.diff` («proven» без
        воспроизводимого доказательства), либо пара полей не
        соответствует этой таблице.

    47.2. `carrier` хранится в форме `file::symbol` (имя функции, класса
        или константы верхнего уровня, резолвится через AST-разбор
        исходного файла), не `file:line` — номер строки не хранится в
        реестре и не может разойтись с кодом при чужой, не относящейся к
        правилу правке того же файла (частая ситуация на файлах с
        несколькими параллельно открытыми PR). Резолвинг реализован
        только для Python; форма для носителя, являющегося шагом
        workflow (у которого нет символа языка программирования), не
        входит в эту версию — правило, ссылающееся на такой носитель, не
        может быть заведено с `status: proven` до появления этой формы.

    47.3. Реестр, чья директория `docs/agents/rules/` отсутствует, пуста
        либо содержит файлы правил при нуле успешно загруженных и
        распарсенных записей, — всегда красный результат (отсутствие
        инвентаря либо поломка загрузчика, не «правил нет»),
        независимо от режима проверки, которым запущена загрузка. Окна
        «реестра ещё нет и это валидно» не существует: загрузчик и
        первые записи приезжают одним деревом, молча зелёный режим на
        отсутствующей директории — тот же «тихий ноль». Запись —
        `*.md` верхнего уровня директории, кроме `README.md`;
        файл-кандидат, не распарсившийся, — громкая ошибка с именем
        файла, не тихий пропуск: загрузчик, молча переживший ошибку
        разбора, делает битую запись отсутствующей — директория с двумя
        валидными и одной битой записью даёт `total == 2`, зелёный
        `--check` и правило, исчезнувшее из реестра без единого сигнала,
        и пол «нуля распарсенных» этого не видит.

## ADDED: Доказательство носителя — мутация одного правила

47.4. Правило со `status: proven` доказывается мутационным прогоном:
     на здоровом (немутированном) дереве объявленный `proof_test` обязан
     завершаться кодом `0` — иначе состояние «носитель нездоров» (находка
     о самом измерительном инструменте, не о правиле, отдельная от
     «доказано»/«мутант выжил»). К дереву применяется объявленный мутант
     (unified diff, нарушающий инвариант, который называет правило),
     нацеленный на файл и символ, указанные в `carrier`, — не на файл,
     указанный в `proof_test`: мутация, патчащая измеритель вместо
     носителя, не признаётся доказательством (самопроверка теряет смысл,
     если можно снять проверку внутри самого теста). После применения
     мутанта `proof_test` обязан завершиться РОВНО кодом `1` (тесты
     собраны, хотя бы один упал), а не любым ненулевым кодом; применённый
     мутант отменяется после прогона по факту «патч был применён»; на
     путях, где применение патча провалилось, reverse-откат не
     выполняется — откатывать нечего; отказ отката на пути, где патч был
     применён, — отдельный громкий ненулевой исход, не молчаливое
     оставление мутированного рабочего дерева.

    47.4.1. Коды выхода pytest, отличные от `0` (здоровое дерево) и `1`
        (доказанная мутация) — `2` (прервано), `3` (внутренняя ошибка),
        `4` (ошибка использования, включая несуществующий путь/узел) и
        `5` (ни одного теста не собрано) — не засчитываются ни как
        «доказано», ни как «мутант выжил»: отдельная категория «харнес не
        смог провести проверку», названная явно в результате прогона.

    47.4.2. Патч, переставший применяться к текущему дереву, — красный
        результат сам по себе, категория «мутант устарел», отдельная и от
        «харнес не смог проверить», и от «мутант выжил».

    47.4.3. Запрос доказательства для правила, отсутствующего в реестре
        (опечатка в идентификаторе или ещё не заведённая запись), —
        явная ошибка с перечнем известных идентификаторов и ненулевым
        кодом выхода, не молчаливый успешный результат.

    47.4.4. Состав мутанта проверяется ДО его применения (`git apply
        --numstat`, патч не применяется): каждый затронутый патчем файл
        совпадает с файлом `carrier` и ни один не совпадает с файлом
        `proof_test`. Нарушение — категория «мутант устарел» (патч не
        соответствует объявленной записи реестра — правит чужой файл
        или измеритель), отдельная от «доказано» и от «мутант выжил»:
        без этой проверки дифф, ломающий сам `proof_test`, давал бы на
        «мутированном» дереве код `1` и ложное «доказано».

    47.4.5. Запрос доказательства для правила, присутствующего в реестре,
        но не находящегося в `status: proven` (у такой записи `proof_test`
        может быть литералом `"none"`), — явная ошибка с ненулевым кодом
        выхода («доказывать нечего»), БЕЗ запуска `proof_test`: прогон
        литерала `"none"` дал бы `exit=4` и ложную категорию «носитель
        нездоров», которая про красный существующий измеритель, а не про
        его отсутствие.

47.5. Проверка схемы реестра (47.1–47.3) и мутационное доказательство
     (47.4) объявленных правил подключены к непрерывной интеграции
     репозитория в том же изменении, которое их создаёт, файлом каталога
     гвардий `scripts/ci/guards/rule-carrier-registry.sh` — регистрация
     гвардии это данные (файл каталога, #749), исполняемый общим
     шагом-перебором: новый тестовый файл не может существовать в дереве
     без соответствующего файла каталога. Связь «proven ⇒ гоняется
     мутацией в CI» не живёт ручным перечнем id в файле каталога:
     каталог вызывает режим `--all-proven`, перебирающий ВСЕ proven-
     записи реестра, — proven-запись, добавленная при миграции, без
     файла мутанта или с дырякой схемой красит CI сам, без правки
     каталога.
