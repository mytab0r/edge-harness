# Дельта-спека: журнал (journal-tasks-hands) — реестр правил: носитель, доказательство, доставка

**Нумерация.** `openspec/specs/journal-tasks-hands.md` заканчивается на
37 на момент этого design; минимум четыре открытых change уже претендуют
на 38, по одному — на 39 и 40 (proposal.md, «Риски»). Коллизия номеров —
системная, решается на архивации (кто архивируется первым, занимает
число; остальные перенумеровывают свою дельту при архивации, по образцу
уже наблюдаемого в репозитории поведения — четыре независимых change
сегодня претендуют на 38). Эта дельта сведена к МИНИМУМУ top-level
номеров (2, не 5, как в первой версии) — детализация уходит в подпункты
`NN.1`…`NN.N`, которые не участвуют в межфайловой коллизии номеров.
Итоговые номера ниже (41, 42) — рабочие, подлежат перенумерации при
архивации (tasks.md, п.18).

## ADDED: Реестр правил (правило → носитель → доказательство → доставка)

41. Каждое нормативное правило репозитория (`AGENTS.md`,
    `docs/agents/PROTOCOL.md`) обязано иметь запись в машиночитаемом
    реестре — один файл `docs/agents/rules/<id>.md` на правило (YAML-шапка
    + текст), а не строка в общем списке или общем индексе секций.
    `AGENTS.md` и три промпта исполнения — не первоисточник текста, а
    генерируемая проекция реестра.

    41.1. Шапка несёт обязательные поля: `id` (совпадает с именем файла),
        `statement` (короткая формулировка), `scope` (НЕПУСТОЕ
        подмножество `{human, worker, reviewer, hands, system}` —
        отсутствие или пустота поля отклоняется валидатором, не
        трактуется как «все каналы» по умолчанию), `section` и `order`
        (целое; определяют позицию правила внутри секции документа —
        порядок секций задают маркеры внутри самого генерируемого файла,
        отдельный файл-индекс секций не заводится: правило, ссылающееся
        на `section`, для которой в целевом файле нет маркера, — находка
        валидатора, не молчаливый пропуск), `carrier` (`file::symbol`
        исполняемого носителя ИЛИ `"none: <причина>"`), `carrier_status`
        (`proven`/`pending`/`infeasible`), `proof_test` (конкретный
        pytest node id, обязателен для `proven`, не файл-гвардия
        целиком — файл может нести не относящиеся к правилу тесты), и
        `proof` (`mutation:<путь к .diff>` ИЛИ `"none: <причина>"`).
        Сужение `scope` относительно `{human, worker, reviewer, hands}`
        целиком (то есть не включающее все четыре человеко-ориентированных
        канала) требует непустого поля `scope_reason`, кроме записей с
        `scope: [system]`.

    41.2. `carrier` хранится в форме `file::symbol` (имя функции, класса
        или константы для кода; `path.yml#step-id` с обязательным `id:`
        у самого шага — для носителя-шага workflow, у которого нет
        символа языка программирования и который не может резолвиться по
        имени, гниющему так же, как номер строки), не `file:line` — номер
        строки резолвится только при рендере человекочитаемого вида, не
        хранится в реестре: правки не относящихся к правилу мест того же
        файла (частая ситуация на файлах с несколькими открытыми PR
        одновременно) не обязаны обновлять номер строки в реестре.

    41.3. `carrier_status: infeasible` допустим только с непустой причиной
        в теле файла правила, объясняющей, почему автоматическая проверка
        невозможна или неоправданно дорога. Число записей с
        `carrier_status` в `{pending, infeasible}` СУММАРНО (не только
        `pending`) не может расти относительно того же множества файлов на
        `origin/main` (храповик долга, проверка на каждый push/PR через
        `git show <base>:<путь>` по каждому файлу реестра): перевод
        `pending → infeasible` не уменьшает и не увеличивает эту сумму —
        честная переклассификация, не способ обнулить долг одной строкой
        причины. Отдельно, число файлов реестра (`total_count`) не имеет
        права УМЕНЬШАТЬСЯ между тем же `base` и `HEAD` — удаление файла
        правила без явного обоснования в теле PR останавливает push/PR тем
        же храповиком, симметрично росту `pending`/`infeasible`. Сообщение
        отказа называет id всех затронутых правил (не голое число).

    41.4. Отдельный храповик защищает ДОСТАВКУ: для каждого канала
        `c ∈ {human, worker, reviewer, hands}` число записей реестра с `c`
        в `scope` не может уменьшаться между `base` и `HEAD` — падение
        числа правил, доставляемых в канал, останавливает push/PR с
        именем правила, у которого сузился `scope`, если это не отражено
        объявленной причиной в `scope_reason` записи (п.41.1).

    41.5. Гвардия схемы отклоняет запись реестра с отсутствующим
        обязательным ключом, пустым или отсутствующим `scope`,
        несогласованной парой `carrier_status`/`proof`/`proof_test` (по
        таблице: `proven` требует `carrier` в форме `file::symbol`,
        `proof_test` — резолвящийся РОВНО в один pytest-узел, и `proof` в
        форме `mutation:...`; `pending`/`infeasible` требуют `carrier`
        либо в форме `file::symbol` без мутанта, либо `none: <причина>`),
        конфликтующим `order` внутри одной `section`, или ссылкой
        `carrier`/`proof_test`, не резолвящейся в реально существующий
        файл/символ/тест на момент проверки.

    41.6. Носитель (гвардия по исходнику, `check_*`-функция инвариантов
        состояния репозитория), не упомянутый ни одной записью реестра
        как `carrier`, — находка отдельного инварианта обратной
        связности; тот же инвариант находит и удаление файла правила при
        живом коде носителя (не только изначальное отсутствие записи).
        Носитель, рождённый расследованием инцидента без отдельного
        абзаца в `AGENTS.md`, получает запись реестра с `scope: [system]`
        и не обязан порождать прозу в `AGENTS.md` — сама запись реестра и
        есть требуемый инвариантом след. Этот инвариант включается в
        обязательную проверку CI по объявленному условию (ноль находок в
        течение трёх дней подряд после того, как известные на момент
        миграции носители-сироты получили свои записи), не по
        неопределённому «когда-нибудь».

    41.7. Узкий, явно ограниченный носитель обратного направления
        («правило → текст вне реестра») сканирует ЗАКРЫТЫЙ, явно
        перечисленный список файлов (не весь репозиторий) на совпадение с
        опциональным полем правила `duplicate_signatures` (список regex,
        которыми известно, что правило независимо переформулируется в
        конкретных местах) — находка красит проверку с указанием
        файла:строки и id правила, которое там продублировано. Общий
        детектор произвольной новой нормативной прозы где угодно в
        репозитории вне scope (эквивалентен классификации намерения
        текста) — не проектируется.

## ADDED: Генерация — проекции реестра, не первоисточник

42. `AGENTS.md`, `docs/agents/WORKER-PLAYBOOK.md`,
    `scripts/review/ai_prompt.md` и файл-преамбула канала рук
    (`scripts/hands/RULES-PREAMBLE.md`) несут секции, генерируемые из
    реестра фильтрацией по `scope` (`worker` → плейбук воркера, `reviewer`
    → промпт ревьюера, `hands` → преамбула рук, объединение `worker` +
    `reviewer` + `hands` + `human` → `AGENTS.md`); правило со `scope`,
    состоящим только из `system`, не печатается ни в один из
    человекочитаемых/промптовых файлов — оно существует в реестре только
    для машинной сверки (п.41.6).

    42.1. Генератор поддерживает режим сравнения: сгенерированный вывод
        сверяется с закоммиченным содержимым внутри объявленных маркеров
        каждого из перечисленных файлов; расхождение — отказ обязательной
        проверки с именем команды, которую нужно запустить и закоммитить
        результат (тот же класс гейта, что применяется к lock-файлам
        пакетных менеджеров). Режим сравнения не заводит промежуточного
        «частичного» состояния для ещё не мигрированных секций: до
        полного покрытия реестром генератор не подключается к реальным
        файлам вовсе (сравнение пустого/частичного множества с самим
        собой всегда совпадает и маскирует непроверенность как «всё в
        порядке» — тот же класс тихого нуля, что и в п.43.3).

    42.2. Ручная правка текста правила напрямую в одном из четырёх файлов
        (в обход соответствующего файла реестра) не сохраняется:
        следующий прогон генератора-сравнения находит расхождение и
        требует правки исходного файла реестра, а не сгенерированной
        проекции.

## ADDED: Доказательство носителя — мутационный харнес

43. `carrier_status: proven` требует воспроизводимого факта: на здоровом
    (немутированном) дереве объявленный `proof_test` обязан завершаться
    кодом `0` — иначе состояние «носитель нездоров», отдельное от
    находки о правиле (постоянно красный тест иначе доказывал бы любого
    мутанта одним фактом, что он и так был красным). На это же здоровое
    состояние применяется объявленный мутант (unified diff, нарушающий
    инвариант, который называет правило) к изолированной копии дерева на
    текущем коммите (не к рабочей копии, в которой ведётся разработка);
    после применения `proof_test` обязан завершаться РОВНО кодом `1`
    (тесты собраны и хотя бы один упал) — не любым ненулевым кодом.

    43.1. Коды выхода pytest, отличные от `0` (здоровое дерево) и `1`
        (доказанная мутация), — `2` (прервано), `3` (внутренняя ошибка),
        `4` (ошибка использования, включая несуществующий путь) и `5`
        (ни одного теста не собрано) — не засчитываются ни как «доказано»,
        ни как «мутант выжил»: это отдельная категория отказа «харнес не
        смог провести проверку», названная явно в результате. Без этого
        разведения переименование файла-гвардии (даёт `exit=4`) или
        синтаксическая ошибка импорта (`exit=2`) необратимо превращали бы
        состояние правила в `proven`.

    43.2. Патч, переставший применяться к текущему дереву (код-носитель
        изменился несовместимо с мутантом), — красный результат сам по
        себе, отдельная категория «мутант устарел», не молчаливый
        пропуск и не смешение с «харнес не смог проверить».

    43.3. На каждый push/PR мутационная проверка запускается только для
        правил, чей `carrier`-файл входит в список файлов, изменённых
        этим PR относительно базовой ветки (выборочный режим), за
        исключением правил с измеренным (baseline) временем выполнения
        `proof_test` выше объявленного порога — они доказываются только
        по расписанию (см. 43.4), выборочный режим печатает явное
        сообщение о пропуске, не молчит. Полный прогон по всем
        объявленным мутантам, включая «тяжёлые», выполняется по
        расписанию (не реже раза в сутки), независимо от того, что
        изменилось в конкретном PR. Ноль правил, подходящих под
        изменённые файлы, — обычный, не красный исход выборочного режима
        (типичный PR не трогает carrier-файлы вовсе); ноль правил при
        НЕЗАГРУЖЕННОМ реестре (директория отсутствует/пуста при
        непустом ожидаемом множестве, либо парсер вернул пустой список
        по ошибке загрузки) — красный результат в обоих режимах,
        выборочном и полном: пустой реестр — это поломка загрузчика, не
        законный «нечего проверять».

    43.4. Полный прогон по расписанию заводит/комментирует задачу пула
        при красном результате (объявленный потребитель сигнала, не
        просто красный статус workflow, который никто не обязан
        открывать).
