# unhealthy-pulls-narrow-match: сопоставление PR → задача только по ветке

Задача: #286.

## Проблема

`unhealthy_pulls` (единственный путь возврата задачи в пул после вердикта
«нужны правки», `scripts/orchestra/scheduler.py`) сопоставляла PR с задачей
через `pr_references_issue` — тот же матчер, что и у `reap_stale`: любое
упоминание `#N` в теле PR, не только имя ветки. Для `reap_stale` эта широта
безобидна (задача просто провисит дольше при ложном срабатывании), но
`unhealthy_pulls` по найденному PR **снимает исполнителя и замок** —
упоминание номера задачи контекстом в прозе (а не декларацией) снимало
аренду с чужой задачи.

Живая улика: 2026-09-04 задача #90 дважды лишилась аренды, потому что её
номер был упомянут в теле PR #181 («...в том числе #90 — сломанный гейт
ревью...», пример другой проблемы в проброшенном тексте). Собственная
задача PR #181, по имени ветки `agent/179-white-spot-in-pool`, — #179, к
#90 отношения не имеет.

## Решение

`unhealthy_pulls` сопоставляет PR с задачей единственным способом, которым
это уже делает весь остальной код репозитория (`contract_check.py`,
`scripts/review/ai_review.py`) — через `task_ref.resolve_pr_task` (номер из
имени agent-ветки, `agent/<N>-...`, #394). PR без ветки такой формы —
«задача не определена», а не «наверное вот эта».

`pr_references_issue` (широкий матч по прозе) остался только у `reap_stale`
— там цена ошибки другая (симметрично докстрингу `task_ref.py`); докстринги
обеих функций, канонический докстринг `task_ref.py` и сообщение гвардии
`scripts/lib/test_task_ref_usage_guard.py` обновлены, чтобы `unhealthy_pulls`
больше не значился легитимным потребителем широкой пары
`extract_task_refs`/`references_task`.

См. `specs/journal-tasks-hands/spec.md` этого change — базовая спека
(`openspec/specs/journal-tasks-hands.md`, п. 17.1) до этого change называла
`unhealthy_pulls` в списке «намеренно широкой» семантики; это правило
сузилось.

## Известная граница (не в этом change)

Тот же класс широты (сопоставление номера по прозе, не по декларации) живёт
ещё в двух местах, обе цена ошибки младше, чем была в `unhealthy_pulls`:

- `scheduler.py::after_merge` — освобождает git-lock (`claim_task.release`,
  НЕ assignee) для каждого номера, упомянутого в теле СЛИТОГО PR. Риск
  младше (assignee не трогается), но `claim_task.py::claim` не проверяет
  assignee — снятый по ошибке лок теоретически позволяет второму каналу
  успешно заклеймить занятую задачу. Осознанная широта, названная в
  докстринге, вне точечной правки этой задачи.
- `scripts/lib/claim_task.py::claim` не проверяет assignees вовсе — фон
  задачи, не предмет этого change.

## Случай «задача PR закрыта или отсутствует в открытом пуле»

`unhealthy_pulls` итерирует `pool` (открытые задачи с меткой `task`, без
`blocked` — снимок, полученный ДО вызова, см. докстринг функции) и ищет PR,
чья `resolve_pr_task` совпадает с номером задачи ИЗ `pool`. Если у PR своя
задача закрыта или не входит в `pool` (`resolve_pr_task(pull)` не совпадает
ни с одним номером в `pool`), PR ни для одной задачи `pool` не совпадёт —
`unhealthy_pulls` его просто не увидит, ни аренда, ни замок не трогаются
(это тот же класс молчания, что и у любой задачи, отсутствующей в pool, до
этого change). Это НЕ чинит и не расширяет случай `dispatch_conflict_rework`
(конфликт-расшивка PR #439, «задача #431 не найдена в открытом пуле,
авто-расшивка недоступна», прогон orchestra 34194073339) — там симптом тот
же («задача не в открытом пуле»), но потребитель другой (расшивка
конфликта, не снятие аренды), и газа на этот случай реестр не называет
вовсе. Остаётся отдельным белым пятном — не расширяется молча в этом change.
