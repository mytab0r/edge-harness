# edge-harness-decommission: функции журнала переезжают в морду, воркер списывается

Задача: #86. Эпик: #77 (вся логика на dsh-edge). Смежное:
[dsh-edge-plugin-system](../dsh-edge-plugin-system/proposal.md) (PoC #80 закрыт),
[runner-sessions-in-dsh-morde](../runner-sessions-in-dsh-morde/proposal.md) (#119),
[dsh-pulse-self-update](../dsh-pulse-self-update/proposal.md) (#73).

## Зачем

Воркер edge-harness (`cf-worker`) задумывался как временное транспортное плечо:
журнал событий, очередь задач hands, heartbeat и пульс оркестрации. С момента
#95 (runner-bridge) и #119 (сессии раннеров в морде) его транспортные функции
закрыты мордой dsh-edge, и воркер остался вторым местом правды: статусы
конвейера пишутся в его журнал, читаются обратно прокси `/api/harness/*`,
источник которого НЕ в репо (#235), а пульс живёт в его DO. Списывание воркера
убирает второй UI-слой, вторую точку деплоя и второй источник правды.

## Что делает

1. **Канал конвейера — сессия морды.** Статусы (`plugin_status`,
   `integration_status`) и жизненный цикл job (hands) пишутся ingest'ом
   (патч 0004) в выделенную сессию `harness-pipeline` воркспейса
   `/workspace/edge-harness` — статусы видны в чате морды и лежат в
   хранилище DO. Писатель — `scripts/lib/dsh-edge-pipeline.sh`; контракт
   события не меняется (task_id/kind/data), меняется транспорт.
2. **Чтение — патч `0005-harness-pipeline-view.patch`.** Маршрут
   `GET /api/harness/events` на воркере морды отдаёт события сессии
   `harness-pipeline` в прежней форме журнала
   (`{events:[{id,task_id,seq,ts,source,kind,data}],has_more,next_after}`) —
   контракт читателей (plugin-manager, integrations) сохранён байт-в-байт,
   плагины не перевыпускаются. Источник прокси с этого момента в репо
   (#235 закрыт по существу: источник есть, цель — не чужой журнал, а своя
   сессия).
3. **Пульс — минимальный инфра-воркер `cf-pulse`.** DO с alarm-цепочкой
   (тот же механизм, что у списываемого воркера): каждые 15 минут диспетчит
   `orchestra.yml` (пульс оркестрации, без него конвейер стоит — GitHub cron
   на репо не тикает) и сверяет версию морды с npm (#73) с тем же троттлом.
   Деплой — `deploy-pulse.yml` с переносом туда гвардии узости
   GH_DISPATCH_TOKEN.
4. **Транспорт задачи для hands** — `client_payload.task_text` (и
   `workflow_dispatch` inputs): текст задачи больше не лежит в журнале.
5. **Списание.** `deploy-worker.yml` и каталог `cf-worker/` удаляются
   (спека/история остаются в git). Воркер из CF удаляет
   `decommission-worker.yml`: по workflow_run после зелёного
   `deploy-dsh-edge` (или руками) он проверяет ПРЕДПОСЫЛКИ и только потом
   удаляет: (а) в активном коде не осталось ссылок на HARNESS_URL/HANDS_TOKEN,
   (б) морда жива, (в) канал конвейера доказан живьем — канарейка пишет
   статус в `harness-pipeline` и читает его назад через `/api/harness/events`.
   Воркера уже нет — зелёный no-op.

## Чего дизайн намеренно не решает

- Инструмент чата «поднять hands по свободному тексту»: цикл
  «задача → раннер → статусы в чате» закрывает runner-bridge (`runner_task` →
  `worker.yml`); hands остаётся на ручном `workflow_dispatch`. Решение и у нас
  в design.md.
- Перенос истории старого журнала в DO: журнал списывается вместе со
  страницей; спека/история остаются в git.
- Чистка vars/secrets репозитория (HARNESS_URL, HANDS_TOKEN, SESSION_SECRET)
  — пост-мерж шаг владельца, список в PR.

## Критерий готовности (по задаче)

- [ ] Цикл «задача → раннер → статусы в чате dsh-edge» работает без
      edge-harness воркера (улика — канарейка канала в decommission-job).
- [ ] Воркер удалён из CF; деплой-путь воркера удалён из репо.
- [ ] dsh-edge чат (DO данные) не затронут: ни один шаг не пишет в чужие
      сессии, сессия конвейера — новая, существующие сессии не трогаются.
