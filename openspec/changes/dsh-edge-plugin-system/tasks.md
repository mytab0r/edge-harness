# Задачи: dsh-edge-plugin-system

Исполнение — через пул Issues. Правила — [PROTOCOL](../../../docs/agents/PROTOCOL.md).
Этот change — дизайн-фаза задачи #78: реализация стартует только после ревью
владельца. Порядок ниже — порядок реализации: PoC руками закрывает самые
рискованные пункты [design](design.md) «Не подтверждено», потом патч-серия и
воркфлоу, потом форж-канал.

## 0. Входы владельца (один раз, до PoC)

- [ ] Название npm-скоупа плагинов (в дизайне — `@edge-harness`, заглушка-решение)
      и подтверждение источника: только релизы этого репо.
- [ ] Политика пина апстрима: кто и когда двигает `dsh-edge/upstream.json`
      (ручной PR; автоматизации нет — design, «Манифест»).
- [ ] Порог роста патч-серии (в дизайне: >6 патчей или любой >100 строк —
      пересмотреть форк против серии) — подтвердить или поменять.
- [ ] Решение по опциональному патчу `0004-model-catalog-const` — делать ли в
      этом слайсе (закрыл бы хрупкую хирургию минифицированного бандла в
      текущем `deploy-dsh-edge.yml`).

## 1. PoC руками: hello-world через весь канал (до продакшн-воркфлоу)

- [ ] Минимальный плагин `plugins/hello/` (сервер: cordis-плагин с тривиальным
      инструментом/сервисом; клиент: `./client` бандл с простейшей
      `dsh.client`-декларацией — design «Не подтверждено» п.8).
- [ ] Локальный прогон схемы сборки на машине: клон апстрима по SHA → патчи
      0001-0003 руками → `pnpm install --frozen-lockfile` → `pnpm add <tgz>` →
      **проверить, что пять pnpm-патчей пережили add** (п.1 «Не подтверждено»);
      провал → план Б из design.
- [ ] Кодогенератор: `plugins.json` → `edge-plugins.generated.ts` +
      `standalone/edge-plugins.json`; пустой манифест деградирует в апстримную
      сборку (доказать оба направления).
- [ ] Пробная сборка: `bundle-standalone direct` — gzip-бюджет (замер запаса,
      п.3), `bundle-meta.json` содержит входы плагина, алиас резолвится
      (патч 0001 работает).
- [ ] `verify-standalone` / `verify-determinism` на сборке со сгенерированным
      файлом (п.2 «Не подтверждено»).
- [ ] Негативный тест изоляции: инсталл, бросающий исключение, → DO жив,
      остальные плагины стоят (п.4); заодно проверить контракт
      `Context.plugin()` при throw.
- [ ] Мутационная проверка гвардии: убрать плагин из бандла (снять
      кодогенерацию) → гвардия состава краснеет; вернуть → зелёная. Снять
      фикс — убедиться, что тест ловит (правило «закрой класс»).
- [ ] Развёртывание в личный воркер: морда поднялась, канарейка 200, в чате
      виден эффект hello-плагина, клиент-часть смонтировалась после reload.
- [ ] Замер сквозной задержки forge→deploy→морда (п.7).

## 2. Состав в репо (после PoC — с поправленными фактами design)

- [ ] `dsh-edge/upstream.json`, `dsh-edge/plugins.json` (+ валидатор схемы в
      кодогенераторе: id, скоуп, sha256, уникальность, релиз существует).
- [ ] Патч-серия `dsh-edge/patches/0001-0003` (+ `0004` по решению владельца)
      и `dsh-edge/PATCHES.md`: у каждого патча причина и `removeWhen`-условие
      снятия, порог роста серии.
- [ ] `dsh-edge/codegen-edge-plugins.mjs`: единственное место, пишущее
      generated-артефакты; громкие ошибки валидации до дорогих шагов.
- [ ] `.github/workflows/build-dsh-edge.yml`: схема «Сборка» из design —
      clone@SHA, `git apply` (громко), pnpm-инсталлы, sha256-сверка tgz,
      codegen, бандл, **гвардия состава** (каждый enabled-плагин в
      `bundle-meta.json` и в `dist/plugins`), verify, deploy, канарейка.
      Секреты не печатаются, веерных `set -x` нет.
- [ ] Судьба текущего `deploy-dsh-edge.yml` (префаб): либо удалить после
      стабилизации сборки из исходников, либо оставить как аварийный префаб —
      решить владельцу в ревью; два автодеплоя одной морды сосуществовать не
      должны (гонка за воркер).

## 3. Форж и канал обновления

- [ ] `.github/workflows/plugin-forge.yml`: workflow_dispatch, вход — путь к
      исходникам плагина; шаги чеклиста совместимости как обязательные
      (запрещённые импорты, нет рантайм-import(), размер вклада в бандл,
      smoke на локальной сборке) — design «Workers-совместимость».
- [ ] Публикация релиза `plugins-vN` (tarball + checksums) из форжа.
- [ ] PR с правкой `plugins.json` (версия, sha256) — ручной или из форжа
      (ветка + PR, не прямой пуш).
- [ ] Статусы: оба воркфлоу постят `plugin_status` в журнал
      (`POST /api/events`, псевдо-задача `plugin:<id>`, seed seq с сервера —
      как hands); отказ поста не валит job молча — финальный статус обязан
      доехать или job краснеет (fail loud: деплой без `ready`/`failed`
      события = silent-wrong).
- [ ] Рендер `plugin_status` в морде журнала — минимальный, как в слайсе
      dsh-streaming.

## 4. Доказательства (критерий #78: дизайн с ревью; реализации — после)

- [ ] PoC-улики приложены к задаче: лог сборки с гвардией состава, скрин/лог
      морды с hello-плагином, замеры бюджета и задержки.
- [ ] Мутационная улика гвардии: снятый плагин краснит сборку.
- [ ] `PATCHES.md` отвечает «почему» и «когда снять» для каждого патча.
- [ ] Отрицательный канал: манифест с чужим URL/битым sha256 → красная сборка
      на валидаторе, а не деплой.
