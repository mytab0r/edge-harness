# Дельта-спека: журнал (journal-tasks-hands) — периодическая саморевизия конвейера (#1025)

Реализация: `scripts/orchestra/self_review.py`, вызывается периодически
workflow'ом `.github/workflows/self-review.yml` (независимо от
`orchestra.yml`/`scheduler.py` — отдельный планировщик, тот же приём
изоляции, что уже применяют `dependabot-alert-watch.yml`/
`checklist-tail-triage.yml`). Пороги — константы модуля `self_review.py`
(одно место правды).

## ADDED: Открытое исследование сырых данных конвейера

Требование: каждый прогон (раз в `SELF_REVIEW_INTERVAL_HOURS = 6` часов)
собирает дайджест за `SELF_REVIEW_WINDOW_HOURS = 72` часа — прогоны
отслеживаемых workflow (`WATCHED_WORKFLOWS`, надмножество
`pulse_guard.WATCHED_WORKFLOWS` плюс `ai-review.yml`/`pr-review.yml`),
churn меток по недавно обновлённым issues/PR, свежие комментарии
watchdog-issue #120, снимки `data/pipeline-health`, сводку пула — и
строит промпт с ОТКРЫТЫМ вопросом («что здесь не сходится, что изменилось
без объяснения, чего мы не ожидали»), БЕЗ подсказки класса дефекта заранее.
Модель (шаг `investigate`, без GitHub-токена, транспорт
`scripts/review/ai_dsh.sh` без изменений) отвечает находками по контракту.

Требование: сбор данных не читает repo-wide `issues/events` без границы
(этот эндпоинт не поддерживает фильтр по времени и отдаёт события от
старых к новым — полный обход читает всю историю репозитория на каждый
прогон, независимо от окна, что подтверждено живой попыткой при
реализации). Вместо этого — недавно обновлённые issues/PR
(`since`-фильтр по `updated_at`, поддерживается этим эндпоинтом) плюс
таймлайн не более `LABEL_CHURN_MAX_ISSUES = 40` из них: цена ограничена
сверху `1 + 40` запросами вне зависимости от размера истории.

## ADDED: Дешёвый второй проход по чек-листу известных классов

Требование: чек-лист известных классов дефектов конвейера читается из
`config/self-review-checklist.json` (ДАННЫЕ, не текст в коде) и вставляется
в промпт ПОСЛЕ открытого вопроса как второй, более узкий проход. Новый
пункт чек-листа не требует правки `self_review.py` — только правки JSON.

## ADDED: Жёсткий фильтр факта — контракт находок

Требование: ответ модели разбирается по контракту (`### НАХОДКА` .. `###
КОНЕЦ НАХОДКИ`, поля ЗАГОЛОВОК/КЛАСС/ФАКТ/ПОЧЕМУ_ВАЖНО/БЛОКИРУЕТСЯ). Блок
без ВСЕХ пяти полей отбрасывается целиком. Находка становится задачей
ТОЛЬКО если её ФАКТ проходит `has_verifiable_fact` — эвристика (длина ≥15
символов И (цифра ИЛИ отсылка к команде/ссылке)); непроверенная догадка без
числа/команды/ссылки отбрасывается ДО дедупа и потолка, не доходит до пула.

## ADDED: Три исхода находки, классифицируемые моделью

Требование: находка несёт `КЛАСС` — `дефект`/`белое-пятно` (обычная задача
пула, метки `task`+`self-review`), `знание` (метка `self-review:knowledge`,
тело задачи требует записи вывода в `AGENTS.md`/`docs/research/`/
`docs/decisions`, не разового фикса кода) или `инструмент` (метка
`self-review:instrument`, тело задачи требует нового измерения
(`scripts/measure/`/снимок здоровья/гвардия) И доказательства на истории,
что оно поймало бы уже известный инцидент — не самого измерения сейчас).

## ADDED: Дедуп в два слоя + суточный потолок

Требование: находка проверяется на дубль ДВУМЯ независимыми способами —
(1) точный отпечаток (класс + значимые токены заголовка,
`duplicate_guard.tokenize`) среди self-review issues в состоянии `state=all`
(открытых И закрытых — закрытая как невалидная находка того же отпечатка
не должна порождать новую задачу на следующем прогоне, класс #962); (2)
токенная похожесть заголовка (`duplicate_guard.find_similar_open_tasks`) по
ВСЕМУ открытому пулу задач (`labels=task`), не только среди self-review
issues — находка может пересекаться с задачей другого происхождения.

Требование: суточный потолок `SELF_REVIEW_DAILY_CAP = 3` — СВОЙ счётчик
(Search API, `label:self-review created:>=<полночь UTC>`), не общий с
`ci-failure`/`auto-detected`/`self-audit` (разные предметные области, тот же
принцип, что уже разделяет `FAILURE_WATCH_DAILY_CAP`/`STALL_DAILY_CAP` в
`pulse_guard.py`). Превышение потолка не тонет молча — эскалация тем же
каналом, что предохранитель конвейера (`pulse_guard.escalate`, issue #120 +
Telegram), отсечённые находки перечислены в тексте эскалации.

## ADDED: Наблюдаемость — почему заведено 0 задач

Требование: каждый прогон `apply` печатает точное число находок на каждой
стадии решения (разобрано / заведено / отброшено без факта / дублей /
отсечено потолком) — молчание без причины запрещено по построению:
`summarize_decisions` всегда возвращает непустую строку, даже когда решений
нет вовсе (текст называет это явно — «модель не вернула ни одной находки»).

## ADDED: Отказ прав/транспорта красит прогон

Требование: если ВСЕ отслеживаемые workflow не прочитались при сборе
дайджеста (403/сеть), `gather` поднимает `GatherTransportError` и
завершается ненулевым кодом — не возвращает пустой дайджест, который
неотличим от «в конвейере всё спокойно». То же — при отказе чтения сводки
пула задач/PR (`gather_pool_summary`). Частичный отказ (не все источники, а
один из многих) остаётся видимым в дайджесте как явная запись `{"error":
...}` на месте недоступного источника, не тихим пропуском.
