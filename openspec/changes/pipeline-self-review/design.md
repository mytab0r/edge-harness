# Design: периодическая саморевизия конвейера (#1025)

## 0. Что уже есть — не дублировать

| Механизм | Файл | Что ищет |
|---|---|---|
| Предохранитель + непрочитанные провалы | `pulse_guard.py::failure_watch` | Красный прогон ИЗВЕСТНОГО workflow, классифицируется закрытым списком сигнатур |
| Простой конвейера | `stall_detector.py` | Устойчивая строка отчёта пульса среди ИЗВЕСТНЫХ регэкспов (`check:red:`, `gate:no-ai-verdict`, …) |
| Регрессия здоровья | `health_regression.py`/`health_audit.py` | Отклонение ИЗВЕСТНОЙ метрики снимка от baseline |
| Алерты Dependabot | `dependabot_alert_watch.py` | Открытый алерт — API отдаёт готовый список |
| Наследование меток хвоста | `checklist_tail_labels.py` | Открытая задача с ИЗВЕСТНЫМ шаблоном заголовка |

Общий признак всех пяти: у каждого есть заранее объявленный список того, что
именно он ищет. Ничто из них не задаёт открытый вопрос над сырыми данными.
Это ROOT CAUSE, который называет владелец: не «нет данных», а «нет вопроса».

## 1. Периодичность — обоснование числа

Три references, уже существующие в конвейере:

- `orchestra.yml` (пульс оркестратора) — каждые 15 минут, **96 раз/сутки**.
  Дешёвый: чтение уже открытых сущностей, без вызова модели по умолчанию
  (вызов модели там — только диспатч `ai-review`, не сам пульс).
- `ai-review.yml` — по событию (после `pr-review`) плюс ручные повторы;
  живой замер владельца в задаче упоминает **~50 дорогих прогонов/сутки**.
  Контекст одного вызова — дифф ОДНОГО PR (килобайты).
- `merge-health-watch.yml` — раз в час, **24 раза/сутки**, но БЕЗ вызова
  модели (чистая арифметика над уже прочитанными Actions/Issues API).

Саморевизия — дороже одного `ai-review` по контексту (весь дайджест периода:
прогоны восьми workflow, churn меток, снимки здоровья, сводка пула — вплоть
до ~60 КБ промпта на живом прогоне, см. §3) и ДОЛЖНА быть реже, чтобы не
удваивать нагрузку на и так занятую цепочку провайдеров (`config/
provider-usage.json`, тот же `default-chain`, что уже несёт `ai-review`/
`worker`/`hands`). Выбрано **раз в 6 часов — 4 прогона/сутки**:

- Меньше 10% от объёма `ai-review` (4 против ~50) — цепочка не удваивается
  ощутимо.
- Окно сырых данных (`SELF_REVIEW_WINDOW_HOURS = 72`) шире интервала между
  прогонами (6ч) на порядок — соседние прогоны перекрываются: пропуск ОДНОГО
  прогона по инфраструктурной причине (403/сеть/квота) не теряет находку
  целиком, она попадёт в окно следующего. Дедуп по отпечатку не даёт
  повторному наблюдению того же факта задвоить задачу.
- 4 раза в сутки — это ~2 раза за обычный рабочий день владельца: достаточно
  часто, чтобы находка не протухла до неактуальности, и достаточно редко,
  чтобы не превратиться во второй `ai-review` по частоте.

## 2. Устройство: трёхшаговый трест-контур

Копирует форму `ai-review.yml` (ADR 0007), не изобретает новую:

```
gather (доверенный, read-only)  →  investigate (НЕ доверенный, DSH, без токена)  →  apply (доверенный, write)
```

Граница доверия — МЕЖДУ job'ами (тот же довод, что комментарий в
`ai-review.yml`): недоверенный шаг `investigate` не получает ни
`GH_TOKEN`, ни `GH_PIPELINE_PAT` — модель обрабатывает уже собранный текст
(данные), не может дотянуться до сети иначе. Всё, что он может испортить
(файлы воркспейса), умирает вместе с виртуалкой job'а. `apply` заново
чекаутит `main` — код, который парсит и решает, всегда доверенный.

`investigate` переиспользует `scripts/review/ai_dsh.sh` БЕЗ ИЗМЕНЕНИЙ:
скрипт уже общий (гоняет `$AI_WORK/prompt.md` через цепочку провайдеров,
пишет `$AI_WORK/answer.txt`), ничего специфичного для ревью PR внутри него
нет — это одна из причин, почему новый workflow не трогает
`scripts/review/*` вовсе.

## 3. Сырые данные: что входит, что нет, и по какой цене

| Источник | Функция | Цена |
|---|---|---|
| Прогоны 8 workflow за окно | `gather_workflow_digest` | 8 запросов (`recent_runs`, по одному на workflow, `per_page=100`) |
| Churn меток | `gather_label_churn` | 1 + до 40 запросов (см. §3.1 — это была реальная находка при живой попытке) |
| Комментарии watchdog-issue #120 | `gather_watchdog_comments` | Постраничный обход одной issue (уже используется `pulse_guard`) |
| Снимки `data/pipeline-health` | `gather_health_snapshots` | 1 запрос (`pipeline_health.fetch_history`, переиспользован, не вторая копия) |
| Сводка пула (счётчики по меткам) | `gather_pool_summary` | 2 запроса (issues+pulls, тот же обход, что `scheduler` уже делает) |

Живой размер промпта на прогоне 2026-09-12 (окно 120ч, см. §5) — **61 332
байта**. Отслеживаемые workflow — надмножество `pulse_guard.WATCHED_WORKFLOWS`
плюс `ai-review.yml`/`pr-review.yml` (их провал/петля не виден предохранителю
конвейера вовсе).

### 3.1. Находка, случившаяся ПРИ РЕАЛИЗАЦИИ, не после

Первая версия `gather_label_churn` читала `GET /repos/{repo}/issues/events`
репозиторным обходом (`review_labels.list_pages`, без фильтра по времени —
этот эндпоинт **не поддерживает `since`**, отдаёт события от старых к новым).
На живой попытке 2026-09-12 процесс не ответил за десятки секунд и был убит
руками (`Stop-Process`) — при истории репозитория в тысячи событий полный
обход постранично читает ВСЮ историю на каждый прогон, независимо от окна.

Исправление — тот же приём, что уже применяет `scripts/measure/
label_churn_203.py` для открытых PR (таймлайн по issue), но с границей:
`GET /issues?state=all&sort=updated&direction=desc&since=...` (этот
эндпоинт **поддерживает** `since` по `updated_at`) даёт до 100 недавно
тронутых issues/PR ОДНИМ запросом, дальше таймлайн смотрится только у
первых `LABEL_CHURN_MAX_ISSUES = 40` — общая цена ограничена сверху
`1 + 40` запросами вне зависимости от размера истории репозитория.

Это ПРЯМАЯ иллюстрация правила «Право достроить себе инструмент» из
задания: гипотеза «нужен репозиторный churn меток» упёрлась в отсутствие
дешёвого способа его измерить, и вместо того чтобы отступить, механизм
получил рабочую, ограниченную по цене реализацию — на этом самом PR, до
того как задача ушла в пул.

## 4. Контракт находок и жёсткий фильтр факта

```
### НАХОДКА
ЗАГОЛОВОК: <фраза>
КЛАСС: дефект | белое-пятно | знание | инструмент
ФАКТ: <проверяемый факт из приведённых данных>
ПОЧЕМУ_ВАЖНО: <фраза>
БЛОКИРУЕТСЯ: <номера или "ничем">
### КОНЕЦ НАХОДКИ
```

`has_verifiable_fact` — эвристика (не доказательство корректности факта,
только формы): длина ≥15 символов И (цифра, либо отсылка к команде/ссылке
— `` ` ``/`http`/`gh `). Живой антипример, ради которого фильтр писан
дословно в задании — issue #962: находка без единого числа/команды/ссылки,
чистая гипотеза, дошедшая до пула и закрытая как невалидная.

Блок без ВСЕХ пяти полей отбрасывается целиком при разборе (`parse_findings`)
— частичный контракт не контракт (тот же принцип, что «вердикт обязан
нести тело», AGENTS.md).

## 5. Доказательство работоспособности: живой прогон 2026-09-12

Команда (реальный репозиторий, не фикстура):

```
python scripts/orchestra/self_review.py gather \
  --repo mytab0r/edge-harness --hours 120 --out /tmp/self-review-proof
```

Вывод: `self-review gather: окно 2026-09-07T13:02:53+00:00..2026-09-12T13:02:53+00:00,
промпт 61332 байт -> ...`

### 5.1. Находит (б) — петля меток на #782 — ЧИСТО

`digest["label_churn"]` (без подсказки номера issue заранее, только правило
«ищи toggles >= 4 за окно»):

```json
[
  {"issue": 782, "label": "waiting:owner", "toggles": 60, "last_at": "2026-09-12T12:25:37Z"},
  {"issue": 810, "label": "stale-unclaimed", "toggles": 14, "last_at": "2026-09-12T00:04:39Z"},
  {"issue": 902, "label": "ai:changes-requested", "toggles": 8, ...},
  ...
]
```

#782 — первая строка списка, отсортированного по убыванию `toggles`, с
отрывом почти в 4 раза от второго места. Открытый вопрос («что здесь не
сходится, одно и то же то ставят, то снимают?») находит это без единой
строки кода, знающей заранее про #782 или про `waiting_owner_guard` —
находка следует из ЧИСЕЛ, а не из совпадения с сигнатурой.

### 5.2. Находит (в) — красный деплой dsh-edge — с оговоркой по счёту

`digest["workflow_runs"]["deploy-dsh-edge.yml"]`:

```
total_in_window: 18, by_conclusion: {"success": 6, "failure": 12}
```

Список `recent` (18 прогонов помещаются целиком, потолок в 20 не срезал
ничего) показывает буквально: успех 2026-09-07T15:38/15:39 → **непрерывный
ряд failure** с 2026-09-07T16:24 по 2026-09-12T03:12 (10 прогонов подряд,
проверено прямым запросом `gh api .../deploy-dsh-edge.yml/runs`) → успех с
2026-09-12T03:51 и далее. Owner-эталон называл «9 прогонов подряд с
2026-09-08» — прямой запрос находит цепочку длиннее (начало 2026-09-07,
конец утром 2026-09-12) и с тех пор деплой уже зелёный. Число не совпадает
один в один со формулировкой эталона (счёт велся в другой момент времени и
восстановление уже произошло), но САМ ФАКТ («долгий непрерывный ряд
провалов, который недавно оборвался успехом») виден в сырых данных
однозначно и без подсказки.

### 5.3. НЕ находит (а) в текущей конфигурации — честно, не подогнано

`digest["workflow_runs"]["worker.yml"]`: `total_in_window: 100,
by_conclusion: {"failure": 58, "success": 39, "cancelled": 2, "in_progress": 1}`.

Агрегат за 120ч — 58% провалов — заметно выше «нормы около половины»
(на самом деле НИЖЕ 50% успеха, само по себе повод для вопроса), но список
`recent` (потолок 20 самых свежих прогонов на workflow, design.md §3)
на момент прогона (2026-09-12 13:02Z) начинается с 2026-09-11T14:33Z —
**не достаёт** до момента регрессии (мерж #878, 2026-09-10T22:54:34Z,
подтверждено `gh pr view 878 --json mergedAt`). Прямым запросом (не через
`self_review.py`, а `gh api` напрямую) подтверждено: сразу после мержа
следующие 6 прогонов worker.yml подряд (00:53:31..06:02:36 UTC
2026-09-11) — все `failure`, прежде чем 07:58:06 дал первый успех. Это
РЕАЛЬНАЯ регрессия, она видна прямым запросом, но НЕ видна в дайджесте,
который строит `self_review.py` в текущей конфигурации, потому что:

1. Потолок `samples[:20]` в `gather_workflow_digest` хранит только 20
   САМЫХ СВЕЖИХ прогонов на workflow — при частоте worker.yml (десятки
   прогонов в сутки) и восстановлении, случившемся раньше конца окна, 20
   самых свежих уже не достают до момента самой регрессии.
2. Дайджест не коррелирует прогоны с мержами (нет поля «что смёржено
   непосредственно перед этим прогоном») — даже сохранись нужные прогоны в
   выборке, связь «сразу после КОНКРЕТНОГО мержа» не была бы явной, только
   заметной по последовательности timestamps.

**Что бы это исправило** (не сделано в этом PR — граница задачи, не
маскировка пробела): (а) увеличить потолок выборки на workflow с 20 либо
хранить не последние N, а последние N ПОСЛЕ каждого success (чтобы стрик
после восстановления не вытеснял стрик до него); (б) отдельное поле —
самый длинный непрерывный ряд failure в окне и его границы по времени, а
не только `by_conclusion`-агрегат. Оба — кандидаты в задачу класса
«инструмент» следующей саморевизии, а не тихо забытый недостаток этой.

### 5.4. Итог честно

Из трёх эталонов: один найден чисто (б), один найден с оговоркой по точному
счёту, но по существу верно (в), один НЕ найден в текущей конфигурации, и
причина названа конкретно, а не общими словами (а). 2 из 3 — не «система
находит всё сама»; названная причина невезения — реальное структурное
ограничение (потолок выборки), а не случайность формулировки промпта.

## 6. Тормоза и газ

- **Суточный потолок** `SELF_REVIEW_DAILY_CAP = 3` — свой счётчик (Search
  API, `label:self-review created:>=<полночь UTC>`), не общий с соседними
  детекторами (тот же принцип, что уже документирован в `pulse_guard.py`
  для `FAILURE_WATCH_DAILY_CAP`/`STALL_DAILY_CAP`: разные предметные
  области, общий счётчик значил бы, что шумный день одного детектора
  выедает бюджет другого). Газ — автоматический, окно 24ч уезжает само.
  Отсечённые находки не теряются молча — эскалация тем же каналом, что
  предохранитель конвейера (`pulse_guard.escalate`, issue #120 + Telegram).
- **Дедуп в два слоя** — точный отпечаток (класс+токены заголовка) среди
  self-review issues `state=all` (открытых И закрытых — не даёт находке,
  однажды закрытой как невалидной, вернуться на следующем прогоне) +
  токенная похожесть по всему открытому пулу (`duplicate_guard.py`, тот же
  инструмент, что уже применяет `scripts/gh/issue-create`).
- **Отказ транспорта красит прогон.** `GatherTransportError` — если ВСЕ
  отслеживаемые workflow не прочитались (403/сеть), это фатальная ошибка
  gather, а не пустой дайджест. Аналогично сводка пула (`gather_pool_summary`)
  падает громко при отказе, а не подставляет нули.
- **Наблюдаемость.** `summarize_decisions` печатает точное число находок на
  каждой стадии (разобрано/заведено/отброшено без факта/дублей/отсечено
  потолком) — молчание без причины исключено по построению (`main` всегда
  печатает эту строку, даже когда создано 0 задач).

## 7. Тесты и гвардия

`scripts/orchestra/test_self_review.py` — 35 тестов, чистые функции (без
сети): контракт находок, жёсткий фильтр факта, отпечаток, классификация по
меткам, дедуп+потолок (`decide_findings`), наблюдаемость, ограниченность
`gather_label_churn` (число запросов, не полная история), fail-loud на
отказ транспорта (частичный и полный). Гвардия — `scripts/ci/guards/
self-review-guard.sh`.

Доказательство мутацией (проведено вручную при разработке, не
автоматизировано в CI — как и у соседних гвардий этого стиля):
- Тело `has_verifiable_fact` заменено на `return True` → 3 теста красные
  (`test_has_verifiable_fact_rejects_guess`,
  `test_has_verifiable_fact_rejects_empty_and_too_short`,
  `test_decide_findings_rejects_finding_without_fact`); возврат тела →
  35 зелёных.
- Тело `fingerprint` заменено на константу → `test_fingerprint_differs_by_class`
  красный; возврат тела → зелёный.

## 8. Не подтверждено

1. Реальный прогон трёхшагового workflow целиком (с настоящим вызовом
   модели через `ai_dsh.sh`) не проведён в рамках этой задачи — воспроизведён
   только шаг `gather` (детерминированный, без LLM) против живого
   репозитория; шаг `investigate` проверен транспортно (тот же скрипт, что
   уже работает в `ai-review.yml` многие сотни прогонов) и не выполнен здесь
   заново отдельно, чтобы не тратить квоту цепочки на ещё один прогон в
   процессе разработки.
2. Ограничение §5.3 (потолок выборки срезает старый инцидент) — названо и
   объяснено, но НЕ исправлено в этой задаче: это осознанная граница объёма,
   а не забытый баг, зафиксированная явно, чтобы следующий прогон
   саморевизии (или человек) мог сам решить, стоит ли заводить задачу
   класса «инструмент» на увеличение окна выборки/добавление поля
   «длина текущего стрика».
