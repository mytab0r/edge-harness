# Дизайн: dsh-in-job

Смежное: [proposal](proposal.md), [ADR 0002](../../../docs/decisions/0002-loop-in-runner-not-do.md),
[архитектура DSH](../../../docs/research/10-dsh-architecture.md),
[dsh-edge как образец](../../../docs/research/11-dsh-edge.md),
[спека журнала](../../specs/journal-tasks-hands.md).

## Форма

```
браузер ──WebSocket /api/events──▶ Durable Object ◀──POST /api/events (батчи)──┐
   │                              │  │ SQLite: журнал, очередь, heartbeat        │
   └──POST /api/tasks──▶ repository_dispatch                                    │
                                    ▼                                           │
                          GitHub Actions job ───────────────────────────────────┘
                            ├─ heartbeat каждые N с
                            ├─ dsh --profile headless "<task>"   (Node 24)
                            └─ после выхода: читает session log, постит события
```

Направления те же, что в скелете: наружу только `DO → GitHub REST` (dispatch),
обратно job ходит обычным HTTP. Ни одного долгоживущего соединения —
[ADR 0001](../../../docs/decisions/0001-push-model-not-tunnel.md).

## Решения

**Точка входа — `dsh --profile headless "<task>"`, не самописный цикл.**
Правило эпика: самодельного агентского кода не пишем. dsh-headless создаёт
персистентного агента, подаёт задачу обычным пользовательским сообщением, ждёт
затишья, флашит сессию и печатает последний непустой ответ ассистента в stdout.
Код возврата 0 только при завершённом `turn/end`. Профиль не открывает портов.

**Установка — tarball'ами с пином версий.** `npm install` пакетов `@deepseek-ai/dsh-*`
даёт 404 при работающих `npm view`/`npm pack` (замер зафиксирован в
[исследовании DSH](../../../docs/research/10-dsh-architecture.md), «Дистрибуция в npm»).
Job делает `npm pack <pkg>@<pin>` + установку из локальных tgz.
Версии пинятся в одном месте — вверху скрипта клиента.

**Провайдер — готовые плагины, не новый код.** Подключаются два собранных артефакта
владельца: `dsh-combo-suite-0.1.0.tgz` (внутри `dsh-combo-router-0.1.0`: виртуальная
модель `combo/auto`, классификация, circuit breaker, failover, режимы
auto/quality/economy) и `dsh-anthropic-oauth-pool-0.1.0.tgz` (пул учёток с cooldown).
Оба собраны 2026-08-28 — они для этого и построены; состав и местоположение
зафиксированы в #215, подключение в раннер — #215 (проводка `PLUGINS_SUITE_URL`)
и #216 (перенос и адаптация).
До их подключения достаточно env-переменных `DEEPSEEK_BASE_URL` /
`DEEPSEEK_API_KEY` / `DEEPSEEK_MODEL`: префикс `DEEPSEEK_` — наследие, значение —
любой OpenAI-compat endpoint (NVIDIA NIM проверен). Секреты — из секретов
репозитория, в логи не печатаются.

**Heartbeat — тот же, что в скелете.** Клиент шлёт отметку вместе с батчем или
отдельно каждые N секунд; «руки живы» = отметка свежее `HEARTBEAT_FRESH_MS`
(константа в `cf-worker/src/config.ts`, единственное место правды). На время
долгого LLM-вызова job не умирает — heartbeat идёт из фонового цикла клиента.

**События сессии — пост по завершении, батчем.** dsh-headless персистит сессию
(DSH session store на диске раннера) и флашит её перед выходом. Клиент после
завершения читает session log, маппит на события журнала, постит батчем в
`POST /api/events` с нумерацией по спеке: seq с 1, уникальные, повторная
доставка не двоит (`UNIQUE(task_id, seq)` на сервере). Морда показывает
разворот сессии и финальный ответ. Живой стрим во время прогона — слайс 2
(кандидат: плагин DSH на событиях сессии → HTTP; не tail файла).

**Приоритет доказательств при конфликте.** Если поведение dsh-headless в job'е
расходится с README, правится документ по факту замера — и только потом код.

## Стык suite (#215) и цепочки провайдеров (#727/#737)

Обе фичи родились независимо и приземлились почти одновременно (#215 —
ротация УЧЁТОК плагином combo-router внутри одного провайдера; #727/#737 —
цепочка автопереходов МЕЖДУ провайдерами по классу отказа, `dsh_run_with_
provider_chain` в `scripts/lib/dsh-ci.sh`). Обе решают один и тот же вопрос
(«кого пробовать дальше, когда текущий не ответил») на разных уровнях, и
общая точка стыка — функция `dsh_patch_profile`, которую цепочка вызывает
НА КАЖДОЙ своей попытке, экспортировав перед этим `DEEPSEEK_BASE_URL`/
`MODEL`/`API_KEY` конкретного провайдера этой попытки.

**Развилка.** Три варианта, которые обсуждались:

1. Suite подменяет провайдера ВНУТРИ одного звена цепочки (комбинация,
   «максимум охвата»).
2. Suite становится ОТДЕЛЬНЫМ звеном цепочки (свой элемент в
   `vars.DSH_PROVIDER_CHAIN`, ссылающийся на combo/auto).
3. Обе фичи взаимоисключающие для одного вызывающего: если оба включены там,
   где нужна цепочка — цепочка выигрывает, suite глушится, и это видно, а не
   тихо.

**Решение — вариант 3, с явным fail-loud, а не молчаливым приоритетом.**
Причина отказа от (1): если бы `dsh_patch_profile` внутри цикла цепочки
переключала `agent-default-model` на `combo/auto`, то а) `DSH_CHAIN_PROVIDER`/
`DSH_CHAIN_TRIED` (атрибуция попытки — «кто фактически ответил») врали бы —
combo-router мог обслужить вызов ЛЮБЫМ из своих внутренних маршрутов, не
обязательно тем, кого цепочка думает, что тестирует; б) реестр подтверждённых
id моделей (#737, `dsh_model_confirmed`) — тормоз, оплаченный 37 минутами
молчания (прогон 34188152283) — НЕ покрывает маршруты
`PLUGINS_SUITE_CANDIDATE_ROUTES`: они прошли бы мимо этой проверки целиком.
Совмещение тихо ломало бы оба уже оплаченных тормоза цепочки. Причина отказа
от (2): элемент цепочки, ссылающийся на combo/auto, не может нести
`secret_env` одного секрета — combo/auto по построению использует МНОЖЕСТВО
учёток сразу; формат `vars.DSH_PROVIDER_CHAIN` (один `secret_env` на запись)
не выражает это без расширения формата ради комбинации, которая сегодня
никому не нужна.

**Реализация решения 3** (`scripts/lib/dsh-ci.sh`):
- `dsh_require_provider_chain` отказывает громко, если `vars.PLUGINS_SUITE_URL`
  и `vars.DSH_PROVIDER_CHAIN` заданы ОДНОВРЕМЕННО — до какой-либо дорогой
  работы, с сообщением, называющим обе переменные и что с этим делать.
- `dsh_run_with_provider_chain` выставляет `DSH_CHAIN_ACTIVE=1` на время
  своего цикла; `dsh_patch_profile` читает этот флаг и ВСЕГДА пишет плоский
  (не combo/auto) патч, пока он установлен — независимо от
  `DSH_PLUGINS_SUITE_ACTIVE`. Это защитный, а не ожидаемый путь (гейт выше уже
  не даёт обеим переменным дойти досюда разом), но не полагается только на
  вызывающего: если суда всё же дойдут обе — печатается `::warning::`, а не
  тишина.
- Практическое следствие: сегодня цепочка (`vars.DSH_PROVIDER_CHAIN`)
  подключена только в `scripts/review/ai_dsh.sh` (ai-review, вызов
  обязателен) — там suite НЕ подключается вовсе (ни `dsh_install_plugins_
  suite`, ни `dsh_mount_plugins_suite`, ни проводка `vars.PLUGINS_SUITE_URL`
  в `.github/workflows/ai-review.yml`). Suite остаётся уделом
  `worker.yml`/`hands.yml` (`scripts/worker/task.sh`, `scripts/hands/
  dsh_task.sh`), где цепочки нет и коллизии не возникает. Если цепочка когда-
  нибудь придёт и в worker/hands — тот же вопрос встанет там; гвардия в
  `dsh_require_provider_chain` сработает автоматически, отдельного решения
  на тот момент можно не принимать заново.
- Гвардия класса, с мутационным доказательством обоих правил —
  `scripts/lib/test/dsh-suite-chain-conflict.guard.sh` (CI: `repo-ci.yml`,
  шаг «Гвардия стыка suite и цепочки провайдеров»).

## Отвергнутые варианты

**Tail session-файла для живого стрима (слайс 1).** Формат файла — внутренняя
деталь DSH, между rc-версиями меняется; клиент, привязанный к нему, ломается
тихо. Слайс 2 пойдёт через объявленный шов (плагин на событиях), не через файл.

**Свой лёгкий цикл «только LLM + bash» вместо dsh-headless.** Прямое нарушение
правила эпика «не пишем самодельный агентский код» и потеря плагинов/инструментов.

**Запуск DSH в контейнере внутри job'а.** Изоляция выше, но отладка тяжелее,
а угроза ограничена: job и так одноразовый, секреты — scoped. Вернуться, если
DSH начнёт тащить системные зависимости.

## Чего дизайн намеренно не решает

- Транзитивные зависимости tarball-установки: резолвит ли npm их из реестра,
  если сами пакеты ставятся из локальных tgz. Проверяется первым прогоном #48;
  фолбэк — полная распаковка dependency-closure.
- Очередь длиннее одной задачи: параллельные прогоны и их раскладка по раннерам.
- Повтор задачи после провала job'а (сейчас — ручной повтор из морды).
