# Дизайн: runner-session-outcome-notes

Задача: #480. Факты о dsh-edge session API — [research/12](../../../docs/research/12-dsh-edge-session-api.md).

## Развилки и выбор

### 1. Можно ли дописывать в уже завершённую (не архивированную) сессию

Факт из кода патча (`dsh-edge/patches/0004-harness-ingest.patch`,
`EdgeSessionStore.appendHarnessEvents`): единственное условие входа —
`persistence.hasSession(id)` ИЛИ `persistence.readBlankSession(id) !==
undefined`. Проверки «сессия закрыта для записи после конца хода» в коде
патча нет вовсе — dsh-сессия не имеет состояния «завершена», только
«существует» и «архивирована» (`workspace.archiveSession` перемещает её из
активного списка, данные не удаляются). `openAgentForTurn` внутри ingest
может вернуть BUSY (409) только при одновременном НАТИВНОМ ходе в той же
сессии (`docs/research/12`, раздел «Не подтверждено») — после конца агента
живого хода нет, конфликта не будет. Вывод: дописывание после факта — тот
же путь, что дренирует транскрипт во время хода, разница только в МОМЕНТЕ
вызова. Живой прод не зондировался отдельно для ЭТОЙ задачи (#480) — это
уже подтверждено интеграционным прогоном `dsh-edge/ingest-integration/check.mjs`
на собранном воркере (батч 1 → батч 2, оба проходят в уже созданную сессию,
включая перенумерацию turn поверх хранимого лога) при каждом деплое
`deploy-dsh-edge.yml`; посимвольная копия прод-контракта, не пересказ.

Была бы дописывание невозможным — альтернатива: отдельный маршрут «хвост
сессии» или новая короткая сессия-ссылка на исходную. Не потребовалось.

### 2. Как формируется заметка: `assistant/message`, не новый тип события

Ingest (allowlist `HARNESS_INGEST_EVENT_TYPES`) не имеет типа «системная
заметка» — добавлять новый тип означал бы третий патч в форк-серию dsh-edge
(порог пересмотра серии — design.md `dsh-edge-plugin-system`, «больше шести
патчей»), ради одной короткой строки текста. Вместо этого заметка кодируется
как обычное `assistant/message` с одним текстовым content-блоком: тот же
тип, что уже несёт ответы агента, рендерится в UI морды без доработок.
`turn`/`step` всегда `1` — перенумерация ingest-маршрута (`baseTurn`,
читается из хранимого лога при каждом вызове) превращает это в «следующий
турн поверх текущего конца лога»; отдельные вызовы `append_session_notes` в
разное время (мерж → приёмка) корректно продолжают нумерацию, не
перезаписывая друг друга.

### 3. Кто дописывает: `scheduler.py`, не воркер/руки

Воркер (`scripts/worker/task.sh`) знает `session_id` только пока сам жив —
факты «слито», «приёмка», «возврат в пул» случаются часы/дни спустя, когда
воркер уже завершился. `scheduler.py` — единственное место, где эти факты
УЖЕ обнаруживаются (мерж — `after_merge`, приёмка — `accept_merged_tasks`,
возврат в пул — `unhealthy_pulls`) как часть существующего одноразового
действия. Связь «номер задачи → session_id» не хранится нигде отдельно:
`session_id = f"harness-{номер}"` — тот же детерминированный вывод, что уже
использует `archive_runner_sessions` (#119).

### 4. Один логин на проход, не на заметку

`_morde_login` — HTTP-запрос с ретраями (в `dsh_edge_login`; здесь без
ретраев, тот же паттерн, что `archive_runner_sessions`). Функция
`append_session_notes(notes: list[tuple[int, str]])` собирает заметки ЗА ВЕСЬ
проход вызывающей функции (например, весь обход пула в `accept_merged_tasks`)
и логинится один раз — по образцу `archive_runner_sessions`, которая тоже
принимает список номеров, а не по одному. Пустой список — ранний выход до
проверки конфигурации и до логина (гвардия холостого хода, тот же приём,
что `stale_ready_pulls`).

### 5. Почему не «PR открыт» и не «вердикт гейтов зелёный»

Названо в proposal.md, «Что вне рамок». Оба случая либо уже видны иным
путём (живой транскрипт), либо требовали бы нового маркера/опроса на КАЖДЫЙ
пульс по КАЖДОМУ открытому PR — то есть ровно тот тип обхода, который
раздел «Цена» задачи #480 запрещает (квота GitHub API и DO rows_read была
на пределе, #320/#325). Негативный вердикт («красный чек» / `ai:changes-
requested`) внутри `unhealthy_pulls` — не новый обход: `unhealthy_pulls` уже
делает его каждый пульс по своим причинам (возврат задачи в пул), заметка
садится на уже оплаченный вызов.

## Форма запроса (напоминание, полная форма — design.md `runner-sessions-in-dsh-morde`)

```
POST /api/sessions/harness-<N>/ingest   (кука владельца; та же кука, тот же логин, что archive)
{"events":[{"type":"assistant/message","data":{"turn":1,"step":1,
  "message":{"role":"assistant","content":[{"type":"text","text":"🔀 PR #9 слит в main."}]}}}]}
→ 200 {"appended":1,"lastSeq":M}
ошибки: 400 (форма — не должно случаться, форма фиксирована в коде),
404 (нет сессии — норма, задача без раннера), 409 (BUSY — не ожидается вне хода)
```

## Не подтверждено

- Визуальный рендер заметки-«assistant/message без предшествующего
  user/message» в UI морды глазами не проверялся — интеграционный прогон
  (`ingest-integration/check.mjs`) проверяет форму/сохранение/replay, не
  рендер. Если владелец увидит кривую отрисовку — беда не в данных
  (allowlist/форма события идентичны уже проверенным), чинится в самой
  морде, не в `scheduler.py`.
- Поведение при ingest в АРХИВИРОВАННУЮ сессию (после `archive_runner_sessions`,
  который уже мог сработать в предыдущем пульсе) — код `appendHarnessEvents`
  не проверяет флаг архива, но живого прогона именно этой комбинации не было;
  `after_merge` дописывает заметку ДО архивации в рамках одного вызова,
  так что для мержа комбинация не возникает. `accept_merged_tasks` и
  `unhealthy_pulls` могут дописывать в уже архивированную сессию (мерж и
  архивация случились раньше, приёмка/возврат — позже) — если морда откажет
  архивной сессии, `append_session_notes` увидит это как HTTP-ошибку
  (не 404) и покажет ⚠️ в отчёте (best-effort, #629 — без хода жёсткого
  сбоя), не потеряв её молча.
