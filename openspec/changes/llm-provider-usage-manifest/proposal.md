# Единый слой конфигурации использования LLM-провайдеров

Задача: не заведена в пуле Issues — это дизайн-предложение по прямому
направлению владельца (2026-09-09), написанное ДО заведения задачи. Заведение
issue пула (метка `task`) — шаг оркестратора/владельца после того, как этот
proposal принят; ссылку сюда (`openspec/changes/llm-provider-usage-manifest`)
issue обязан нести первым абзацем по конвенции
[протокола openspec](../../docs/agents/OPENSPEC-PROTOCOL.md).

Design: [design.md](design.md).

## Summary

Сейчас «кто каким набором LLM-провайдеров пользуется» решается четырьмя
независимыми механизмами без единого места, где это видно и настраивается
разом. Разрыв между ними уже стрелял: воркер получил failover позже ревью на
72 задачи (#727 -> #797), и до его подключения одна и та же квота роняла оба
канала независимо, потому что связи не было видно ни в одном документе,
только в трёх местах кода порознь. Это предложение вводит манифест
использования — именованные цепочки провайдеров + карту «потребитель ->
цепочка» — с источником правды в Settings морды dsh-edge (тот же слот, где
уже живёт provider-registry, #378) и пуш-механизмом в репозиторий, откуда
пайплайны читают его на прогоне без обращения к морде.

## Problem / Motivation

Факт: четыре механизма выбора провайдера, ни одного общего места видимости.

1. ai-review.yml (гейт 2) — dsh_run_with_provider_chain по
   vars.DSH_PROVIDER_CHAIN, подключено в scripts/review/ai_dsh.sh:40-104
   (change llm-provider-chain-failover, #727).
2. worker.yml — та же функция dsh_run_with_provider_chain, подключена в
   scripts/worker/task.sh:31-34,485-534 (#797) — но подключена ПОЗЖЕ ревью:
   до #797 воркер использовал dsh_run_with_retry (одиночный провайдер) и
   падал на квотах, которые ревью уже переживало (живой инцидент, описанный в
   proposal llm-provider-chain-failover: «GLM исчерпан 2026-08-31 — три
   прогона worker.yml красные, конвейер стоит трое суток»).
3. hands.yml — до сих пор dsh_run_with_retry (scripts/hands/dsh_task.sh:13-15,316-318),
   один провайдер, БЕЗ failover; область явно названа незакрытой в
   docs/runbooks/switch-llm-provider.md:96-101 и в llm-provider-chain-failover/proposal.md:43-54.
4. Морда dsh-edge — provider-registry (plugins-src/provider-registry/,
   #378): один слот на провайдера через Settings UI, добавление провайдера
   ручное, единого failover нет (README.md:1-30); переключение штатного
   слота — ручная процедура docs/runbooks/switch-llm-provider.md.
5. combo-router (vars.PLUGINS_SUITE_URL, scripts/lib/dsh-ci.sh:29,136-165,320,551)
   — наложение поверх воркера/рук, сейчас с открытым тормозом без газа
   (issue #790, живая находка 2026-09-09: NO_COMBO_ROUTE роняет job без
   отката при непригодности всех маршрутов suite).

Ни один из пяти пунктов не виден рядом с остальными. Каждый описан в
своём файле кода и своём куске документации; связь «кто чем пользуется»
существует только в голове того, кто читал все пять источников подряд.
Именно поэтому разрыв воркер/ревью был невидим 72 задачи: не было
артефакта, глядя на который кто-то сказал бы «у воркера нет failover, а у
ревью есть» раньше, чем это проявилось инцидентом.

Желаемое состояние. Одно место, где видно и настраивается: какие
именованные цепочки провайдеров существуют и какой потребитель какой
цепочкой пользуется — разным потребителям можно назначить разные цепочки
(явное требование владельца: таски одним комбо, ревью другим). Источник
правды — штатный UI морды (не самодельный), изменение в морде автоматически
попадает в репозиторий версионируемым артефактом, пайплайны читают его на
прогоне без сетевого похода к морде на каждый запуск.

## Scope

### In

- Схема манифеста: именованные цепочки провайдеров (переиспользует форму
  элемента {name, base_url, model, secret_env, max_output_tokens}, уже
  парсимую jq в scripts/lib/dsh-ci.sh, — не новый формат) + карта
  «потребитель -> имя цепочки».
- Источник правды манифеста — settings-namespace в морде dsh-edge, штатным
  Settings UI (тот же генерируемый механизм installSettingsSection, что у
  provider-registry, не написанный руками экран).
- Механизм пуша: изменение манифеста в морде -> коммит версионируемого файла
  в этот репозиторий (путь и техника — design.md), без опроса морды
  пайплайнами.
- Инвариант-гвардия: перечисляет всех потребителей (ai-review, worker,
  hands, морда — для последней только видимость, без chain) и падает, если
  у кого-то из первых трёх нет валидного назначения цепочки.
- Генерируемая таблица видимости по образцу docs/agents/LABELS.md
  (собирается скриптом, сверяется гвардией в CI — тот же паттерн, что
  scripts/lib/collect_labels.py/test_label_registry.py).
- Раздел «Не подтверждено» с явными живыми проверками, нужными до apply.

### Out

- Код: реализация плагина/скрипта/гвардии — это apply-шаг следующего
  change, не этого proposal (аналитик пишет дизайн, не код).
- Задачи на реализацию (tasks.md) — заводятся вместе с change на apply,
  не здесь.
- Подключение hands.yml к failover как таковое (долг рук, #727 «Область») —
  ортогонально: этот change даёт МЕСТО, где такое подключение назначается и
  видно, но не переписывает scripts/hands/dsh_task.sh сам. Если долг рук
  будет закрыт раньше этого change — манифест просто унаследует уже рабочую
  цепочку рук как одну из именованных, ничего не меняя в её механике.
- Починку combo-router (#790, тормоз без газа) — отдельная задача с
  собственным ADR, здесь только фиксируется его нынешний статус (сломан,
  открытый issue) для полноты карты потребления.
- Многопровайдерный слот морды (provider-registry/session-store.ts:243) —
  архитектурно один адаптер на морду, манифест этого не меняет (см.
  «Отвергнутые варианты» в design.md и docs/research/30-rejected-alternatives.md).
- Живой опрос морды пайплайнами на каждый прогон — явно запрещённый
  владельцем паттерн («не сделать из всех пайплайнов вечных дёргателей
  конфигов»); push-по-изменению — единственный рассматриваемый механизм.

## Impacted domains

- Новый домен openspec/specs/llm-provider-usage/spec.md (заводится на
  apply вместе с delta-спекой этого change — сейчас не создан, см. «Out»).
- Косвенно: openspec/specs/journal-tasks-hands.md (морда, settings,
  диспатч) — раздел о settings-механике реестра провайдеров уже там не
  описан явно (сам dsh-edge-provider-registry тоже не слил дельту в
  центральный файл, см. docs/agents/OPENSPEC-PROTOCOL.md:122-142 — общая,
  не только эта, незакрытая практика репозитория).

## Acceptance criteria

Acceptance здесь — критерии готовности дизайна (это change без кода),
проверяются чтением, а не прогоном:

- [ ] Схема манифеста (цепочки + карта потребитель->цепочка) описана с
      примером JSON — design.md, раздел «Схема манифеста».
- [ ] Названы все известные потребители (ai-review, worker, hands, морда) и
      для каждого — как он читает свою цепочку (файл:строка текущего
      хардкода, который заменяется чтением по id) — design.md, раздел
      «Потребители».
- [ ] Механизм пуша называет конкретный существующий прецедент кода
      (file:line) и объясняет, чем он отличается от прямого копирования
      (токен, метод API) — design.md, раздел «Механизм пуска».
- [ ] Инвариант-гвардия и генерируемая таблица описаны по аналогии с
      существующим механизмом docs/agents/LABELS.md (не изобретаются с
      нуля) — design.md, раздел «Видимость».
- [ ] Раздел «Не подтверждено» называет минимум: (а) доступность
      GH_DISPATCH_TOKEN из контекста плагина/сервиса морды, (б) поведение
      Contents API GitHub при частых коммитах от морды (rate limit), (в)
      способ штатного Settings UI морды принимать произвольную схему нового
      namespace без кастомного клиентского кода.
- [ ] Проверено по docs/research/30-rejected-alternatives.md: ничего из
      двенадцати отвергнутых вариантов не предлагается заново (см. сверку в
      design.md, раздел «Сверка с отвергнутыми вариантами»).

## Risks / unknowns

- Токен пуша. GH_DISPATCH_TOKEN (Contents:RW+Actions:RW,
  docs/decisions/0008-narrow-dispatch-token.md) сегодня читается только
  методами класса EdgeSessionStore в cf-worker/src/harness.ts (this.env.GH_DISPATCH_TOKEN,
  строки 1305, 1326, 1732, 2352) — ни разу из кода DSH-плагина
  (plugins-src/**, доступ там идёт через process.env, отдельный канал:
  plugins-src/provider-registry/server/index.js:145,
  plugins-src/runner-bridge/server/index.js:12-15). Доступен ли
  GH_DISPATCH_TOKEN тем же путём внутри плагинного sandbox — не
  подтверждено; см. design.md, «Механизм пуска» и «Не подтверждено».
- Ширина токена для нового вида вызова. Все текущие использования
  GH_DISPATCH_TOKEN — POST /repos/{repo}/dispatches
  (repository_dispatch). Запись файла манифеста — новый вызов, PUT
  /repos/{repo}/contents/{path}; по документированной модели прав GitHub
  оба относятся к пермишену contents (RW), но GitHub «не интроспектирует
  права fine-grained токена» на уровне гвардии репозитория
  (docs/decisions/0008-narrow-dispatch-token.md:100-103) — фактический
  успех PUT-вызова этим токеном проверяется только живым прогоном.
- Комбо-роутер сломан прямо сейчас (issue #790) — манифест перечислит
  его как потребителя/механизм только для видимости; если он останется
  выключенным долго, соответствующая строка манифеста будет честно пустой
  или помеченной «не активен», а не подделанной цепочкой.
- Долг рук (hands.yml без failover) не закрывается этим change —
  риск, что манифест создаст видимость решённости там, где решения нет;
  таблица видимости обязана отличать «назначена цепочка» от «цепочка из
  одного провайдера» честно, а не одним и тем же зелёным полем.
