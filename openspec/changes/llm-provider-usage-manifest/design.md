# Design: llm-provider-usage-manifest

## Decision summary

Манифест использования — версионируемый JSON-файл в репозитории (путь и
формат ниже), редактируемый ЧЕРЕЗ штатный Settings UI морды dsh-edge (не
руками git, не отдельный самодельный UI), синхронизируемый push-по-изменению
через GitHub Contents API. Пайплайны читают файл из своего checkout'а на
каждом прогоне — без обращения к морде. Реализация — новый серверный
DSH-плагин по образцу provider-registry/runner-bridge, а не правка каждого
потребителя порознь.

## Context

- Четыре независимых механизма выбора провайдера (перечислены в
  proposal.md, «Problem»), каждый со своим форматом хранения конфигурации:
  vars.DSH_PROVIDER_CHAIN (JSON-массив, `scripts/lib/dsh-ci.sh`), env
  DEEPSEEK_* (одиночный провайдер, `scripts/hands/dsh_task.sh`),
  settings-namespace llm-pi-ai морды (`plugins-src/provider-registry`),
  vars.PLUGINS_SUITE_URL (suite ротации, сейчас сломан — issue #790).
- Требование владельца (дословно по вводным задачи): источник правды на
  «кто чем пользуется» живёт ШТАТНО в вебморде, в разделе настроек
  плагинов — не в отдельном самодельном UI; изменение настройки пушит
  версионируемый файл в репозиторий; пайплайны ЧИТАЮТ этот файл на
  прогоне, не опрашивают морду/CF на каждый запуск.
- Прецедент settings-namespace с генерируемым Settings UI без кастомного
  клиентского кода — `plugins-src/provider-registry/server/index.js:325-331`:
  `installSettingsSection(ctx, NS, Config, {providers: {}}, {validate,
  setSource, onChange})`, где `Config` — schemastery-объект, штатный
  Settings UI рендерит карточку по нему автоматически (README.md плагина,
  «Как это работает»).
- Прецедент "морда пишет в GitHub по факту события" —
  `cf-worker/src/harness.ts`: `#createIssue` (строки 1934-1997, вызывается
  из инбокса, задача #20) и `#dispatchOwnerDecision` (2351-2375, вызывается
  из инлайн-кнопки Telegram) — оба: (1) читают токен из `this.env.<ИМЯ>`,
  (2) один `fetch` с `AbortSignal.timeout`, (3) не отдают значение токена
  наружу при ошибке, (4) честный `not_configured`/`*_not_configured`, если
  секрет не заведён, вместо тихого пропуска.
- Токены морды по ADR 0008/0011: `GH_DISPATCH_TOKEN` — Contents:RW +
  Actions:RW, единственный использующий его код — методы класса
  EdgeSessionStore (`harness.ts:1305,1326,1732,2352`), только для
  `repository_dispatch`/`workflow_dispatch`. `GH_ISSUES_TOKEN` — Issues:RW
  ТОЛЬКО, используется в `#createIssue`. Ни тот, ни другой сегодня не
  вызывает Contents API `PUT /repos/{repo}/contents/{path}` (создание/
  обновление файла обычным коммитом).
- Гвардия `scripts/lib/test_dispatch_token_usage.py` проверяет ТОЛЬКО текст
  `.github/workflows/*.yml` (`secrets.GH_DISPATCH_TOKEN` вне
  deploy-worker.yml — красный CI); она не видит и не ограничивает
  runtime-код Worker'а/DO/плагинов, читающий `env.GH_DISPATCH_TOKEN` или
  `process.env.GH_DISPATCH_TOKEN` напрямую — новый вызов из DO-кода этой
  гвардией не поймается ни в плюс, ни в минус.
- Гвардия `scripts/lib/test/provider-default.guard.sh:59`
  (`SCOPE=".github/workflows scripts docs/agents"`) — класс #153, сканирует
  только эти три каталога на зашитые провайдер-литералы. Файл манифеста ВНЕ
  этих трёх путей (например корень репозитория или новый `config/`) под
  сканирование не попадает — это снимает противоречие с решением
  `llm-provider-chain-failover` «хранить цепочку файлом в дереве —
  отклонено» (design этого change,
  `openspec/changes/llm-provider-chain-failover/proposal.md`, «Отвергнутые
  варианты»): та отмена была ПРО каталог scripts/**, а не про репозиторий
  целиком — сам факт нигде явно не написан, стоит зафиксировать здесь, чтобы
  следующий читатель не считал два решения противоречащими друг другу.

## Схема манифеста

Единица цепочки не меняется — переиспользуется существующая форма элемента
vars.DSH_PROVIDER_CHAIN (`{name, base_url, model, secret_env,
max_output_tokens}`), уже разбираемая `jq` в `scripts/lib/dsh-ci.sh`. Манифест
добавляет второй уровень — ИМЯ у каждой цепочки и карту потребитель->имя:

```json
{
  "chains": {
    "review-primary": [
      {"name": "NVIDIA", "base_url": "https://integrate.api.nvidia.com/v1",
       "model": "nvidia/nemotron-3-ultra-550b-a55b",
       "secret_env": "NVIDIA_API_KEY", "max_output_tokens": 131072},
      {"name": "GLM", "base_url": "https://api.z.ai/api/coding/paas/v4",
       "model": "glm-5.3-flash",
       "secret_env": "DEEPSEEK_API_KEY", "max_output_tokens": 131072}
    ],
    "tasks-combo": [
      {"name": "GLM", "base_url": "https://api.z.ai/api/coding/paas/v4",
       "model": "glm-5.3-flash",
       "secret_env": "DEEPSEEK_API_KEY", "max_output_tokens": 131072},
      {"name": "NVIDIA", "base_url": "https://integrate.api.nvidia.com/v1",
       "model": "nvidia/nemotron-3-ultra-550b-a55b",
       "secret_env": "NVIDIA_API_KEY", "max_output_tokens": 131072}
    ]
  },
  "usage": {
    "ai-review": "review-primary",
    "worker": "tasks-combo",
    "hands": "tasks-combo"
  },
  "generated_at": "2026-09-09T00:00:00Z",
  "generated_by": "dsh-edge settings (provider-usage plugin)"
}
```

Разные потребители — разные цепочки (владелец явно хочет: таски одним
комбо, ревью другим) — обеспечено картой `usage`, а не единственным
глобальным списком. `generated_at`/`generated_by` — не часть логики
потребителей, а факт для человека, читающего диф коммита: файл пишет
автоматика морды, а не рука разработчика (тот же смысл, что у
`generated_at` в существующих сгенерированных артефактах репозитория, если
такие есть — проверить перед apply, не считать подтверждённым фактом).

Место в дереве — вне `scripts/`, `.github/workflows/`, `docs/agents/`
(гвардия #153 не видит), кандидат: `config/provider-usage.json`
(новый каталог) или корень репозитория. Выбор каталога — не архитектурное
решение, откладывается на apply; здесь фиксируется только ограничение
(вне трёх путей выше).

## Потребители

Канонический список — источник для инвариант-гвардии (раздел «Видимость»
ниже). Для каждого называется id (ключ карты `usage`) и ТЕКУЩИЙ способ
получения провайдера/цепочки, который заменяется чтением по id из манифеста:

| id | Файл сегодня | Что заменяется |
|---|---|---|
| `ai-review` | `scripts/review/ai_dsh.sh:77-104` читает `vars.DSH_PROVIDER_CHAIN` напрямую | чтение `chains[usage["ai-review"]]` из манифеста вместо переменной репозитория |
| `worker` | `scripts/worker/task.sh:110-112,485-534` читает ту же `vars.DSH_PROVIDER_CHAIN` | то же самое чтение, другой id карты `usage` |
| `hands` | `scripts/hands/dsh_task.sh:316-318` — `dsh_run_with_retry`, одиночный провайдер из `vars.DEEPSEEK_*`, БЕЗ цепочки вовсе | требует сначала подключения `dsh_run_with_provider_chain` (долг #727 «Область», не задача этого change) — до этого момента запись `usage["hands"]` существует, но реально исполняемого failover под ней нет; таблица видимости обязана показывать это отдельным столбцом (см. «Видимость»), а не одним общим «ок» |
| `morda` (dsh-edge) | `plugins-src/provider-registry/` — один слот адаптера через Settings UI, `session-store.ts:243` (штатный provider), плюс любые маршруты, добавленные в реестр | НЕ заменяется: числится в манифесте только для видимости (сколько провайдеров сейчас настроено в морде), failover там технически не помещается (один слот, `docs/research/11-dsh-edge.md`) |

Механика чтения манифеста потребителями ai-review/worker (единственные, у
кого сегодня реально есть `dsh_run_with_provider_chain`) — та же точка входа
`dsh_require_provider_chain`/чтение `DSH_PROVIDER_CHAIN` в
`scripts/lib/dsh-ci.sh`, куда добавляется новый источник (файл манифеста +
свой id потребителя), не переписывание вызывающего кода в каждом workflow
заново. `vars.DSH_PROVIDER_CHAIN` как отдельная репо-переменная становится
избыточной (манифест — новый единственный источник) либо остаётся как
резервный fallback на переходный период — выбор фиксируется на apply, не
здесь.

## Механизм пуска: морда -> GitHub

### Option A — DO-класс EdgeSessionStore пишет Contents API, плагин только уведомляет (выбрано)

Новый плагин `provider-usage` (по образцу `provider-registry`) монтирует
settings-namespace своей схемой (чейны + карта usage) и, как
`provider-registry`, получает hook `onChange` от `installSettingsSection`
(`plugins-src/provider-registry/server/index.js:325-331`, поле `onChange:
sync`). Вместо того чтобы сам плагин ходил в интернет, `onChange` зовёт
инжектированный сервис (по образцу `ctx.get('credentials')`,
`plugins-src/provider-registry/server/index.js:240`) — новый `ctx.get('githubPush')`
или аналогичный, который РЕАЛИЗОВАН в хост-бридже DO (том же коде, что уже
монтирует `installEdgePlugins(storage)` внутри `EdgeSessionStore.initialize()`,
research/11) и потому имеет доступ к `this.env.GH_DISPATCH_TOKEN` ТЕМ ЖЕ
способом, что `#createIssue`/`#dispatchOwnerDecision` уже используют для
своих токенов. Сам вызов `PUT /repos/{repo}/contents/{path}` — новый метод
на DO-классе, повторяющий форму `#createIssue` (fetch + AbortSignal.timeout +
честный `*_not_configured` при отсутствии секрета + текст ошибки без
значения токена), но с телом Contents API (base64-контент, `sha` предыдущей
версии файла для update, коммит-сообщение).

Плюсы: токен `GH_DISPATCH_TOKEN` не покидает код, где он уже проверен и
живёт (методы EdgeSessionStore) — поверхность секрета не расширяется на
плагинный sandbox, который монтирует и апстримные, и будущие сторонние
плагины. Соответствует принципу ADR 0008 «имя секрета = его ширина»: ширина
не меняется, меняется только количество мест, которые его читают (одно и то
же место, новый метод).

Минусы: нужен новый канал сервис-инъекции плагин -> DO (сегодня плагины
получают только `llm`/`credentials`/`attachments`, ничего похожего на «толкни
файл в репозиторий» нет) — это НОВАЯ точка расширения хост-бриджа, не только
новый плагин.

### Option B — плагин сам делает fetch к GitHub из process.env (отклонено)

Прямая аналогия с `runner-bridge` (`plugins-src/runner-bridge/server/index.js:12-18`):
плагин читает `process.env.GH_DISPATCH_TOKEN` напрямую и сам вызывает
Contents API. Проще инженерно — не нужен новый сервис хост-бриджа.

Отклонено: `runner-bridge` использует `GH_RUNNER_TOKEN`, ПРОИЗВОДНЫЙ от
широкого `GH_PIPELINE_PAT` (комментарий `runner-bridge/server/index.js:12-15`:
«the narrow GH_DISPATCH_TOKEN of the edge-harness morde lacks issues
rights»), то есть у ЭТОГО плагина токен и так специально расширен под его
нужды (Issues) — прецедент не про сужение поверхности, а про то, что каждому
плагину с сетевой нуждой был явно проведён СВОЙ токен. Если `provider-usage`
получит `GH_DISPATCH_TOKEN` через `process.env` напрямую, это ВПЕРВЫЕ
откроет токен, ограниченный ADR 0008 методами ОДНОГО класса, всему
плагинному sandbox'у морды — включая любые будущие сторонние/апстримные
плагины, которые окажутся смонтированы туда же. Это расширение поверхности,
которое ADR 0008 прямо называет ценой, требующей явного решения («новое
использование `GH_DISPATCH_TOKEN` вне deploy-пути — гвардируемый redflag, а
не стиль», `docs/decisions/0008-narrow-dispatch-token.md:98`) — принимать
её стоит сознательно на apply, а не по умолчанию из соображений простоты.

### Option C — новый отдельный секрет для этого плагина (не рассмотрен подробно)

По аналогии с `GH_ISSUES_TOKEN` (ADR 0011) — завести четвёртый узкий токен
`GH_CONFIG_PUSH_TOKEN` (Contents:RW), выданный ТОЛЬКО плагину `provider-usage`
через `process.env`. Не отклонено явно, а названо как альтернатива Option A,
достойная сравнения на apply: она следует уже принятому в репозитории
паттерну «имя секрета = роль» строже, чем Option A (не расширяет
существующий `GH_DISPATCH_TOKEN` дальше его текущих потребителей), ценой
ЕЩЁ ОДНОГО секрета, который владелец обязан завести и провести через деплой
(тот же шаг миграции, что у `GH_ISSUES_TOKEN`, ADR 0011 «Миграция»).

## Видимость: инвариант-гвардия + генерируемая таблица

Прямой образец — реестр меток (`docs/agents/LABELS.md`), устроенный ровно
по нужной здесь форме:

- Список НЕ хардкожен в markdown — печатается скриптом
  (`scripts/lib/collect_labels.py`) сканированием кода
  (`docs/agents/LABELS.md:15-17`).
- Гвардия (`scripts/lib/test_label_registry.py`) сверяет вывод сборщика со
  строками таблицы на каждый CI-прогон, красит `test` при расхождении.
- Честный потолок назван прямо в самом файле (`docs/agents/LABELS.md:22-40`):
  проверяется ФОРМА записи («газ назван»), не то, что механизм реально
  работает — этот же честный потолок нужно унаследовать здесь, не
  притворяться, что зелёная гвардия доказывает работающий failover.

Для манифеста — тот же паттерн, новый файл `docs/agents/LLM-PROVIDER-USAGE.md`
(или раздел существующего документа — решается на apply), собираемый
скриптом-аналогом `collect_labels.py`, который:

1. Знает канонический список потребителей (таблица «Потребители» выше) —
   фиксированный список, как `EXPECTED_WORKFLOWS` в
   `scripts/lib/test_dispatch_token_usage.py:66-105` (новый потребитель —
   осознанная правка списка, не тихий пропуск).
2. Читает `usage`-карту манифеста и для каждого потребителя печатает: id
   цепочки, число провайдеров в цепочке, факт «цепочка реально исполняется»
   (да у ai-review/worker, честно «нет — код читает одиночный провайдер» у
   hands до отдельного его подключения) — три состояния, не два, тем же
   доводом, что критерий готовности #158 в
   `openspec/changes/dsh-edge-provider-registry/proposal.md:104-111`
   (`not_configured`/`configured_but_rejected`/`all_providers_failed`):
   лечатся по-разному, значит различаются в таблице, а не сливаются в один
   зелёный флаг.
3. Падает (не наблюдательно, сразу в `CI_GATING`, если инвариант это
   позволяет на момент apply — сверить с `repo_invariants.py`), если у
   потребителя из канонического списка нет записи в `usage` вовсе, или
   запись ссылается на несуществующее имя в `chains` — это и есть класс,
   который пропустили с воркером на 72 задачи (#727 -> #797): «у кого-то
   нет валидного назначения» обязано быть видно раньше инцидента, а не
   после.

## Сверка с отвергнутыми вариантами

По `docs/research/30-rejected-alternatives.md` — ничего из двенадцати
пунктов не предлагается заново:

- Внешний питоновский роутер/чужой гейтвей (пп. 1, 7, 8, 9, 10) — манифест
  не вводит новый механизм МАРШРУТИЗАЦИИ, только КОНФИГУРАЦИЮ уже
  существующих своих механизмов (`dsh_run_with_provider_chain`,
  combo-router); классификация отказов остаётся в
  `scripts/lib/dsh-ci.sh`, не переезжает во внешний сервис.
- Многопровайдерный слот морды как замена одному адаптеру — НЕ
  предлагается; раздел «Потребители» явно оставляет морду с одним слотом
  и говорит «числится для видимости», см. также
  `docs/runbooks/switch-llm-provider.md:103-105` («Морда — вне цепочки
  принципиально»).
- Cloudflare AI Gateway/BYOK как ротатор (п.9) — не рассматривался и не
  нужен: пуш файла в GitHub через Contents API не имеет отношения к
  выбору МЕЖДУ ключами одного провайдера.
- Хранение цепочки файлом в дереве репозитория, отклонённое в
  `llm-provider-chain-failover` — см. разбор в разделе «Context» выше:
  отклонение было привязано к каталогам `scripts/**`/`docs/agents/**`
  (гвардия #153), манифест этого change живёт вне них по построению.

## Не подтверждено

1. **Доступ плагинного sandbox'а к `GH_DISPATCH_TOKEN`.** Ни один
   существующий плагин (`provider-registry`, `runner-bridge`) не читает
   именно этот секрет — `runner-bridge` намеренно использует ДРУГОЙ токен
   (`GH_RUNNER_TOKEN`) именно потому, что `GH_DISPATCH_TOKEN` не хватает
   прав на его нужду. Для Option A это не проблема (токен остаётся в
   DO-классе), но сама возможность добавить новый инжектируемый сервис
   `ctx.get('githubPush')` в хост-бридж, монтирующий плагины
   (`installEdgePlugins(storage)`, вызывается из
   `EdgeSessionStore.initialize()`), — не проверена чтением кода хост-моста
   (файл не открывался в рамках этого design; нужен перед apply).
2. **Поведение GitHub Contents API на частых записях от одного автора.**
   Официальный лимит записи (`PUT contents`) отдельно от общего REST-лимита
   не собран в `docs/research/21-github-actions.md` — не подтверждено, что
   несколько правок манифеста подряд (например, эксперименты владельца в
   Settings) не упрутся в throttling до того, как это станет заметно.
3. **Способ штатного Settings UI принимать словарь цепочек, а не плоский
   профиль.** `provider-registry` монтирует namespace, чья схема —
   `providers`-словарь плоских профилей; манифест этого change просит
   ДВУХУРОВНЕВУЮ структуру (`chains` — словарь МАССИВОВ, `usage` — словарь
   строк). Рендерит ли штатный Settings UI морды вложенный массив внутри
   schemastery-схемы так же гладко, как плоский словарь объектов — не
   проверено; возможно, потребуется представить `chains`/`usage` двумя
   отдельными namespace вместо одного вложенного, что меняет схему, но не
   выбранный Option A пуска.
4. **sha текущей версии файла для Contents API update.** `PUT
   /repos/{repo}/contents/{path}` требует `sha` существующего файла при
   обновлении (иначе 409 conflict) — нужен ли отдельный `GET` перед каждым
   `PUT`, и как это сочетается с гонкой (два быстрых изменения в Settings
   подряд) — не проработано, решается на apply.
5. **Реальный сценарий владельца «taски одним комбо, ревью другим».**
   Правило зафиксировано с его слов в задаче, но не сверено отдельным
   вопросом, что именно должно различаться у `worker`/`hands` — ОДНА ли у
   них цепочка (`tasks-combo` в примере выше) или РАЗНЫЕ; пример манифеста
   выше — рабочая гипотеза аналитика, не подтверждённое требование.

## Verification strategy

Design без кода — верификация здесь ограничена перекрёстной проверкой
цитат (сделано выше построчно, `file:line` к каждому решению) и явным
списком «не подтверждено». Живая проверка откладывается на apply:
юнит-тест на схему манифеста и сборщик таблицы (по аналогии с
`test/registry.test.mjs` у provider-registry), интеграционный прогон Contents
API PUT против тестового репозитория/ветки перед включением в прод-путь
морды, ручная проверка в Settings UI (создание цепочки, назначение
потребителю, проверка, что коммит появился) — владельцем, так как требует
живой куки/аккаунта.
