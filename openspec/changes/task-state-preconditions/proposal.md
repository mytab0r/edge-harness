# task-state-preconditions: проверки на входе вместо гвардий постфактум

Задача: #357.

## Класс закрываемой ошибки

Правило владельца: гвардия, которая часто срабатывает, — это несделанная
проверка на входе. Живой случай: приёмка (`accept_merged_tasks`, #227) закрыла
задачу **#320**, пока по ней был открыт второй PR **#325** — тот немедленно
упал на `contract` («задача #320 закрыта»), хотя работа по нему ещё шла.
Действие (закрытие/аренда/новая ветка) совершалось раньше, чем проверено
предусловие («не занята ли задача уже чем-то ещё») — обнаруживалось это
только ПОСЛЕ того, как работа сделана, а не до неё.

Три места одного и того же класса:

1. `accept_merged_tasks` закрывает задачу по улике одного слитого PR, не
   проверив, не объявляет ли её прямо сейчас ещё один ОТКРЫТЫЙ PR.
2. `scripts/git/task-branch` заводит ветку, не проверив, что задача вообще
   существует, открыта, несёт метку `task` и не несёт `blocked`.
3. `scripts/lib/claim_task.py::claim` выдаёт аренду на задачу без проверки,
   что она открыта.

## Решение

1. `accept_merged_tasks` перед закрытием ищет среди открытых PR (свежий
   `open_pulls(repo)`) другой, объявляющий ту же задачу
   (`task_ref.resolve_pr_task`) — если найден, задача не закрывается, в отчёт
   идёт строка «приёмка отложена». Проверяемая улика по одному PR не отменяет
   работу другого.
2. `scripts/git/task-branch` перед созданием ветки запрашивает
   `repos/<owner>/<repo>/issues/<N>` (owner/repo — из `git config --get
   remote.origin.url`, без сети): задача обязана существовать, быть открытой
   (`state == open`), нести метку `task`, не нести `blocked`. Любое из этих
   условий не выполнено → отказ с внятным сообщением, ветка не заводится.
   `gh` недоступен (не установлен, сеть не отвечает — стерто не HTTP-кодом, а
   транспортной ошибкой) → только предупреждение, ветка заводится
   непроверенной: у агента без сети нет способа спросить GitHub вообще, а
   отказ работать в такой ситуации обходится дороже непроверенной ветки.
   Явный HTTP 404 (задача точно не существует) — тем не менее отказ, это не
   офлайн-случай.
3. `scripts/lib/claim_task.py::claim` перед созданием коммита/ref'а замка
   запрашивает `repos/<repo>/issues/<task>` — `state != "open"` → аренда не
   выдаётся, `ClaimResult(claimed=False, …)` (тот же зелёный no-op, что и
   «занята», не поломка).

## Четвёртое место (аудит, не исправлено в этом change)

`scripts/worker/task.sh` (явный вход `--task N`, строки ~150-156) проверяет
`state == OPEN` и метку `task`, но не метку `blocked` — задачу, отмеченную
`blocked` (эскалация владельцу), можно явно передать воркеру и он возьмётся
за неё. Автовыбор (`scripts/lib/free_task.py::free_candidates`) на практике
не подвержен этому: эскалация оставляет `assignee` на задаче (см.
`task.sh:435`, «назначение осталось»), а `free_candidates` берёт только
задачи без исполнителя — но это побочный эффект другого механизма, не
явная проверка. Найдено при аудите по задаче #357, не исправлено:
исправление явного входа `--task N` не было запрошено этим change'ем и не
входит в него, чтобы не разрастись за рамки трёх мест выше.

## Что вне рамок

- `scripts/worker/task.sh`/`free_task.py` (см. «Четвёртое место» выше) — не
  меняются в этом change.
- Семантика «занята» по assignee/`declared-pr` (доводка существующего PR,
  #245) не пересматривается — эта проверка про состояние ЗАДАЧИ (открыта/не
  заблокирована), а не про то, кто её ведёт.
