# repo-invariants: инварианты состояния репозитория (#244)

Задача: #244.

## Зачем

За 2026-09-02/03 в конвейере нашли ~15 дефектов, и НИ ОДИН не нашла система —
все нашли люди/агенты, читая логи. Два уже существующих механизма ловят СВОЙ
узкий класс отлично (белый спот без `task` — `repo-ci.yml`, #179; реестр
меток — `scripts/lib/test_label_registry.py`, #207) и ничего больше, потому
что каждый инвариант писался отдельно, без общего дома.

## Что делается

`scripts/orchestra/repo_invariants.py` — общий дом для проверок вида «такого
состояния репозитория быть не должно», по образцу `scripts/orchestra/pulse_guard.py`
(чистые `check_*`-функции + тонкая IO-обвязка на `gh()`). Четыре инварианта в
строю (пятый, «расхождение числа свободных задач по двум методам», выведен
из состава ревью — см. `repo_invariants.py`, блок-комментарий на месте бывшего
`check_free_task_count_mismatch`: класс, который он ловил, substring-scan в
`task.sh`, закрыт #247, сравнивать стало не с чем):

1. `check_reopened_after_merge` — открытая задача `task` без исполнителя, чей
   PR уже слит (класс #18/#21/#78).
2. *(retired)*.
3. `check_stuck_review_gate` — `review:ok` без `ai:*` дольше
   `pulse_guard.UNHEALTHY_PR_AFTER_MINUTES` (класс #147).
4. `check_unarchived_complete_changes` — `openspec/changes/<id>/tasks.md`
   полностью отмечен, а каталог не под `archive/`.
5. `check_duplicate_evidence` — два открытых task-issue ссылаются на
   пересекающийся `file:line` в теле (класс #202/#213/#212).
6. `check_branch_protection_drift` (#341) — `enforce_admins`/
   `required_status_checks.strict`/`.contexts`/`allow_force_pushes`/
   `allow_deletions` защиты `main` разошлись с `EXPECTED_*` (класс: аудит
   #341 нашёл `enforce_admins=false` — admin-токен сливал мимо всех
   обязательных проверок, `grep -rn protection scripts/` был пуст до этой
   правки). НЕ подключён к `build_report()`/`CI_GATING` по умолчанию:
   `GET .../branches/main/protection` требует у токена право
   `administration`, которого структурно нет у `GITHUB_TOKEN` (не входит в
   перечисляемый набор permissions Actions) — включается только вручную
   (`--check-branch-protection`, токен с реальными admin-правами). Решение
   о канале автоматизации — за владельцем, см. issue #370.

## Расписание и required-гейт

- `repo-ci.yml` — живой отчёт на каждый push/PR (не блокирует `test` сам по
  себе — состояние репозитория не вина автора конкретного диффа).
- `orchestra.yml` — периодический шаг (cron */15 мин), эскалация через
  `pulse_guard.escalate` для инвариантов 1 и 3 (маркер «один раз на набор
  нарушителей», тот же приём, что `PAUSE_MARKER`/`HEARTBEAT_MARKER`).
- `CI_GATING` (константа в `repo_invariants.py`) — какие инварианты РОНЯЮТ
  обязательную проверку `test`. Решение владельца 2026-09-03: инварианты 3 и 4
  — ноль нарушений на момент замера, включить сразу, чтобы не дать долгу
  появиться заново. Фактически в `CI_GATING` остался только 4 (архивация
  спеки не зависит от такта оркестратора); 3 сужен обратно до наблюдательного
  внешней находкой (не пересмотром решения) — газ `trigger_ai_review`
  зависит от расписания `orchestra.yml`, а такт ненадёжен (#269). Условие
  обратного включения 3 — закрытие #269 (проверяемое, не «когда-нибудь»).
  Инвариант 1 остаётся наблюдательным до стадии приёмки, инвариант 5 — до
  дедупликации по отпечатку (#201/#243). `GATING_RELEASE_CONDITION` в коде —
  одно место правды на «что снимает блокировку», гвардия падает громко, если
  для включённого номера условие не названо (AGENTS.md, «Тормоз без газа не
  принимается»).

## Что вне рамок

- Инвариант «расхождение числа свободных задач» — не воскрешён; появится
  смысл только если возникнет НОВЫЙ независимый от `free_task.py` способ
  занять задачу без её ведома.
- Сведение `repo_invariants.last_review_ok_labeled_at` с идентичной функцией
  в `scheduler.py` в одно место правды — заведено отдельной задачей в
  беклоге (находка ревью PR #249), не блокирует этот PR: обе реализации
  сейчас идентичны и используют общий `review_labels.list_timeline`.
