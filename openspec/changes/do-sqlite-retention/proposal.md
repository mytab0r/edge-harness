# do-sqlite-retention: удержание для `events`/`tasks` в DO SQLite

Задачи: #306 (основная — «Ретеншн для журнала и messages в DO SQLite»), #305
(«Политика удержания для таблицы messages», см. «Площадь» ниже — эта задача её
не закрывает целиком).

## Причина

Инцидент 2026-09-03/05: суточная квота DO `rows_read` (5 000 000) исчерпана
дважды. Острая причина — `#status()` гонял два полных скана таблицы `tasks` на
каждый heartbeat (раз в 20 с) — уже пофикшена индексом `tasks(status,
dispatch_ts)` и кэшем счётчиков в #320/PR #321. Но обе таблицы (`events`,
`tasks`) при этом не имеют ретеншена вообще — растут вечно, и любой скан со
временем дорожает, даже правильно проиндексированный. #321 прямо называет это
вне своих рамок («Ретеншн/удаление старых строк `tasks` — тот же класс, что
#306/#305… требует отдельной политики удаления»).

Фактические размеры на 2026-09-05 малы (оценка по 70 запускам `hands.yml` за
всю историю репозитория — живого доступа для прямого чтения таблиц DO SQLite
нет, см. `docs/research/20-cloudflare-free.md`, «Что не подтверждено», п.10):
`tasks` — порядка 70 строк, `events` — низкие сотни (≈10 событий жизненного
цикла job'а на задачу). Острая часть инцидента #320 была не в объёме данных,
а в частоте полного скана. Ретеншн в этом change — защита горизонта: без него
те же таблицы через месяцы/годы эксплуатации станут большими сами по себе, и
тогда даже проиндексированный запрос снова упрётся в rows_read.

## Решение

Одна конфигурация (`RETENTION_TABLES` в `harness.ts`, пороги в `RETENTION` в
`config.ts`) вместо отдельного кода на каждую таблицу — добавить политику для
новой таблицы (например `messages`, когда сольётся инбокс #20/PR #173) значит
дописать строку, а не новый механизм.

### Политика по каждой таблице (разная, не одна на всех)

- **`events` (журнал)** — по возрасту, БЕЗ разбора по статусу задачи:
  `RETENTION.eventsMaxAgeMs = 14` суток. Job физически не может идти дольше
  6 часов (лимит job'а GitHub Actions, таблица в `AGENTS.md`), поэтому 14 суток
  гарантированно не заденут ни одно ещё живое событие. Ценность журнала —
  отладка конкретного прогона и replay; после недель разбора к нему не
  возвращаются. Теряем: возможность посмотреть журнал прогона старше двух
  недель (postmortem по очень старым задачам). Храним: полный журнал всех
  активных и недавно завершённых задач.
- **`tasks` (очередь)** — по возрасту, но ТОЛЬКО терминальные статусы
  (`done`/`failed`): `RETENTION.tasksMaxAgeMs = 30` суток.
  `queued`/`dispatched`/`running` не трогаем ни при каком возрасте — зависшая
  задача уже видна watchdog'ом (`LIMITS.staleDispatchMs`) и не должна тихо
  пропасть, пока её никто не разобрал. 30 суток дольше, чем у `events`, —
  строка задачи дешевле (5 колонок против журнала) и питает анализ latency
  (ADR 0003). Теряем: `GET /api/task/:id` для задачи старше месяца, закрытой
  больше месяца назад (404 вместо истории). Храним: все активные задачи
  независимо от возраста плюс месяц терминальных.
- **`messages`/инбокс (#305)** — НЕ реализовано в этом change: таблицы
  `messages` в `main` нет, она существует только на ветке ещё не слитого PR
  #173 (issue #20). Механизм (`RETENTION_TABLES`) уже спроектирован как
  конфигурация, поэтому добавление политики для `messages` после слияния #173
  — это одна строка в массиве, а не новый код; сама политика (возраст по
  классу сообщения — `directive` дольше, чем `chat`/`raw`) остаётся решением
  той задачи, когда таблица появится.

### Механизм удаления — дешёвый по конструкции

`DELETE FROM <table> WHERE id IN (SELECT id FROM <table> WHERE <условие> LIMIT
?)` — портируемая форма пакетного удаления: DO SQLite нигде не документирует
сборку с `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`, а вложенный `SELECT ... LIMIT`
работает в любой SQLite. Каждая таблица использует свой индекс —
`events_by_ts` (`events.ts`) и `tasks_status_created`
(`tasks(status, created_ts)`, отдельно от возможного watchdog-индекса `tasks
(status, dispatch_ts)` из #320) — иначе внутренний `SELECT` сам стал бы полным
сканом. `RETENTION.batchSize = 500` строк за тик на таблицу: доли миллисекунды
CPU что на пустой, что на огромной таблице, потому что фильтр идёт по индексу,
а не по перебору. Запускается из уже существующего `alarm()` (пульс
оркестрации, тик раз в 15 мин) — новый таймер не заводится; вызов стоит СРАЗУ
после `setAlarm`, ДО проверки `GH_DISPATCH_TOKEN`/`GH_REPO` — иначе на
инсталляциях без секретов дispatch'а чистка не бежала бы никогда.

### Fail loud — переиспользован существующий канал

Каждая таблица чистится в своём `try/catch`: авария одной не должна скрыть
чистку другой. Полная пачка (`rowsWritten === batchSize`, есть ещё что чистить)
или ошибка чистки — сигнал «не успеваем»; фиксируется как один тик подряд
идущей серии (`#retentionStreak`). `retentionBacklog()` — чистая функция
порога (4 тика подряд, ~час) — тот же приём, что `pulseHealthy`/`pulseStale`
для пульса оркестрации: один полный тик после большого бэклога (первый деплой
этого change'а) не тревога, устойчивое отставание — тревога. Канал видимости —
ТОТ ЖЕ, что уже есть у пульса и watchdog'а: новое булево поле `Status.
retention.backlog`, предвычисленное сервером, и бейдж в морде (`#retention`,
`public/index.html`/`app.js`/`i18n/ru.js`) по образцу `#watchdog`/`#pulse` —
не новый механизм оповещения (e-mail/Slack/отдельный эндпоинт), а тот же
JSON-статус + бейдж, которым уже показываются `stale_dispatch`/`pulse_*`.

Отдельно: подключение `status.retention.backlog` к внешней эскалации
(`scripts/orchestra/pulse_guard.escalate`, как уже читает `pulse_healthy`
`scheduler.py`) в этот change не входит — это Python-сторона оркестратора, вне
слоя cf-worker, которым ограничены #306/#305 буквально. Естественное
продолжение, вероятно, войдёт в #324 (общий сборщик метрик квот), который уже
читает `status.pulse_healthy` тем же способом.

## Дельта-спека

`openspec/specs/journal-tasks-hands.md`, разделы «Журнал событий» и «Очередь
задач» — новый подраздел «Ретеншн» в каждом (не путать с «Watchdog зависших
задач», это про другое: там — обнаружение зависшей задачи, здесь — про
удаление старых).

## Что вне рамок

- Ретеншн для `messages` (#305) — таблицы нет в `main`, см. «Политика по
  каждой таблице» выше.
- Подключение `retention.backlog` к `pulse_guard.escalate`/Telegram —
  Python-сторона оркестратора, естественно ложится в #324.
- Изменение частоты heartbeat/alarm — вне слоя данных, которым ограничен этот
  change.
