# Задачи: dsh-web-on-demand

Исполнение — через пул Issues. Правила — [PROTOCOL](../../../docs/agents/PROTOCOL.md).
Этот change — дизайн-фаза задачи #75: реализация стартует только после ревью
владельца. Порядок ниже — порядок реализации: сначала входы владельца и PoC-прогон
руками (закрывает самые рискованные допущения [design](design.md) «Не подтверждено»),
потом продакшн-воркфлоу.

## 0. Входы владельца (один раз, до PoC)

- [ ] Tailnet: включить MagicDNS и выдачу HTTPS-сертификатов (проверить при PoC,
      см. design «Не подтверждено» п.1).
- [ ] Создать OAuth-клиент tailnet со скоупом `auth_keys` (или, при Tailnet Lock,
      ephemeral reusable pre-signed auth key — design, «Подключение к tailnet»).
- [ ] Завести тег `tag:ci` в политике tailnet (OAuth-клиент обязан тегировать узлы).
- [ ] Секреты репозитория: `TS_OAUTH_CLIENT_ID`, `TS_OAUTH_SECRET` (значения не
      попадают в репозиторий — только имена).

## 1. PoC-прогон руками (до продакшн-воркфлоу; закрывает «Не подтверждено»)

- [ ] Одноразовый воркфлоу-прогон на `ubuntu-latest`: `tailscale/github-action`
      (OAuth-клиент, `tags: tag:ci`, `hostname: dsh-web`, `ping` до машины владельца)
      → узел виден в tailnet, `tailscale status --json` отдаёт `.Self.DNSName`
      (зафиксировать формат: хвостовая точка, каноническое имя).
- [ ] `tailscale serve --bg 3080` + установка dsh tarball'ом + `dsh web
      --trusted-host <FQDN>`: владелец открывает `https://dsh-web.<tailnet>.ts.net`
      из своей сети; UI живой, `/api` не отвечает 403 (fence пропускает).
      Провал сертификата → фолбэк `--http=80`, решение зафиксировать в design.
- [ ] Подтвердить, что web-дистрибутив приезжает транзитивными зависимостями
      `npm install -g` tarball'а (design «Не подтверждено» п.7).
- [ ] Установить плагин через UI (не CLI) → убедиться, что он появился в
      `~/.dsh/profiles/web` и пережил рестарт процесса dsh (design п.5-6).
- [ ] pnpm на раннере: `pnpm config set store-dir ~/.dsh/.pnpm-store` ДО первой
      установки плагина; после restore кэша на «чистом» раннере плагин грузится
      (симлинки живые) — иначе silent-wrong (design, «Засада с pnpm-store»).
- [ ] Env-провайдер в web-профиле: `DEEPSEEK_BASE_URL`/`DEEPSEEK_API_KEY` + патч
      `agent-default-model` (glm-5, maxTokens 131072) → диалог в UI отвечает;
      `dsh --profile web --dump-config` показывает патч (факт монтажа, не догадка).
- [ ] Незавершённый ход: убить процесс dsh посреди хода → resume сессии в новой
      сессии → в логе синтетический `turn/end {interrupted}`; замерить, сколько
      хвоста потеряно (design п.3).

## 2. Воркфлоу «открыть рабочий стол» (после PoC)

- [ ] `.github/workflows/web-desktop.yml`: только `workflow_dispatch`, входы —
      длительность в минутах (дефолт 240, максимум ниже 6-часового потолка с
      запасом на teardown); `concurrency`-группа одна на воркфлоу (второй запрос
      ждёт, design «мульти-сессии»).
- [ ] Шаги: checkout репозитория (cwd сессии = чекаут — привязка работы к репо) →
      restore `~/.dsh` (`actions/cache/restore`) → setup-node 24 → tailscale action
      (`hostname: dsh-web`, `ping`, пин версии) → `serve --bg 3080` → запись патча
      профиля идемпотентно → `dsh web --no-open --trusted-host <FQDN>` под
      внутренним `timeout` с запасом до конца job'а (graceful TERM-фаза, не
      6-часовой SIGKILL).
- [ ] Job summary с URL `https://dsh-web.<tailnet>.ts.net` и временем гашения —
      единственное место, где владелец смотрит адрес (не логи).
- [ ] Громкие отказы (fail loud, каждый со своим сообщением): узел не вошёл в
      tailnet; `ping` не дождался; serve не поднялся; health-check `https://<FQDN>`
      отдал 403 fence (подсказка: проверить `--trusted-host` и DNS-имя); dsh упал
      на старте; кэш пуст (переустрой плагинов с нуля — событие в summary, не тишина).
- [ ] `actions/cache/save` с `if: always()` — сохранение обязано случиться и после
      внутреннего таймаута, и после отмены run'а (кэш-экшен без split не сохраняет
      упавший job — design «Персистентность»).
- [ ] Отмена/конец сессии: post-шаг tailscale action делает logout (эфемерный узел
      удаляется немедленно); `tailscale serve reset` перед выходом.

## 3. Доказательства (критерий готовности #75)

- [ ] Владелец из своей сети открывает полный DSH web UI на раннере; ставит плагин
      через UI; диалог отвечает через GLM-провайдера.
- [ ] Вторая сессия (новый job, новый IP узла): плагин и настройки на месте после
      restore кэша; закладка с тем же именем `dsh-web` работает.
- [ ] Сценарий eviction: кэш вычищен вручную → сессия поднимается с громким
      «переустрой плагинов» и работает.
- [ ] Сценарий обрыва: внутренний таймаут/отмена середины хода → незавершённый ход
      виден как `interrupted` в возобновлённой сессии.
- [ ] Морда и DO: за всю сессию ноль запросов к CF (проверка по логам воркера) —
      дизайн «морда не участвует» доказан, а не заявлен.

## Границы

- Проекция web-сессий в морду, мост событий в журнал — вне слайса (design,
  «Отвергнутые варианты», «мост через боковую дверь»).
- dsh-edge, плагинный конвейер и контракт dsh-headless не меняются.
- Всё, что стоит денег (paid-раннеры, платные планы tailnet, CF Containers), —
  вне change по правилу эпика.
