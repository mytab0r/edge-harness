# task-lease-holder-identity: замок аренды знает держателя

Задача: #1190. Дельта-спека: `specs/journal-tasks-hands/spec.md` (расширяет
`task-lease-claim` и `task-branch-lease`). ADR: [0006](../../decisions/0006-task-lease-git-ref-lock.md)
(не меняется — держатель добавлен ВНУТРИ существующего носителя, коммита
замка, не новым механизмом).

## Класс закрываемой ошибки

`refs/locks/task-<N>` (`scripts/lib/claim_task.py`, #121) хранил только
TTL-коммит и НЕ хранил, кто именно держит замок. Живой случай 2026-09-14
(issue #1190): канал, начавший работу по задаче #1184, увидел занятый замок,
не смог установить, что держатель — другой живой канал, снял его и
переарендовал; вернуть замок законному держателю (PR #1185) механизм не
позволял — единственным действием было снять свой (фактически чужой) замок,
оставив задачу без лока вовсе. Спасла только вторичная защита (контракт «один
PR на задачу»), не будь PR открыт — второй канал остался бы без защиты от
гонки вовсе.

Отклонённая ранее альтернатива («идемпотентный claim по держателю»,
`task-lease-claim`, раздел «Флаг несёт номер, не признак», доводка
`task-branch-lease`) была отклонена ПРАВИЛЬНО для той формулировки: держателем
предлагался `actor` (GitHub-логин) — один и тот же у всех каналов, из-за чего
«этот же прогон взял тот же номер» была неотличима от «другой прогон под тем
же логином только что взял тот же номер». Эта дельта вводит держателя ДРУГОЙ
природы — не логин, а идентификатор конкретного прогона/рабочего дерева
(`current_holder()`) — и та путаница физически не воспроизводится: разные
прогоны получают разные `holder` по построению (CI: `GITHUB_RUN_ID` новый на
каждый job; локально: путь рабочего дерева, устойчивый для ОДНОГО агента по
правилу «одно дерево — один агент», AGENTS.md/`.githooks/pre-commit`).

## Решение

- Коммит замка несёт вторую строку `holder: <id>` (не в первой строке со
  свободным текстом — там уже есть `actor`/`via`, парсить пришлось бы
  неоднозначно). `current_holder()` — одно место правды: `CLAIM_HOLDER` (явный
  override) → `run:<GITHUB_RUN_ID>` (CI) → `tree:<cwd>` (локально) →
  `proc:<hostname>:<pid>` (честный запасной рубеж).
- `claim()` при отказе (422 «already exists») читает держателя текущего
  замка и различает ТРИ исхода: свой (`existing_holder == holder`) —
  идемпотентный успех БЕЗ снятия/пересоздания рефа; чужой — отказ, называющий
  держателя в `detail`; неизвестный (замок старого формата без строки
  `holder:`, живые рефы до этой дельты) — честное третье состояние: отказ
  (безопасный дефолт), но с формулировкой «держатель неизвестен», отличимой
  от «держит вот этот».
- `release()` получает необязательные `holder`/`force`: `holder=None`
  (умолчание) — поведение НЕ меняется, форс-снятие без проверки (пути,
  авторитетные независимо от держателя: post-merge, TTL-сборщик —
  `scheduler.py` продолжает звать `release(repo, task)` без изменений).
  `holder=<id>, force=False` (путь CLI `claim_task.py release <N>`) — снятие
  только если замок держит именно этот `holder`; иначе `ForeignLockError`,
  называющий держателя (или честно — «неизвестен», для замка старого
  формата). `--force` — явный обход для того, кто уверен, что имеет право
  (газ для тормоза, AGENTS.md «Тормоз без газа не принимается»): раньше
  единственным действием при путанице было слепое снятие (сам инцидент
  #1190), теперь оно безопасно по умолчанию, а обход поимённый, не тихий.
- Обратная совместимость: живые рефы старого формата (7 штук на момент
  дельты: `task-904`, `task-925`, `task-1121`, `task-1188`, `task-1192`,
  `task-1200`, `task-1203`) читаются без падения — `holder` для них `None`,
  что и даёт третье состояние; ничего не мигрируется насильно, они просто
  ведут себя как «неизвестный держатель» до естественного снятия (TTL,
  post-merge, ручной `--force`).

## Доказательство

Поведенческий тест на РЕАЛЬНЫХ git-рефах (временный git-репозиторий,
`scripts/lib/test_claim_task_real_refs.py`, не мок): канал A берёт замок →
канал B получает отказ с именем A → A берёт повторно — идемпотентный успех
без снятия. Мутация (`if existing_holder == holder` → `if False`) проверена
прогоном: без фикса тест краснеет, с фиксом — зелёный (см. докстринг теста).
Дополнительно — тот же сценарий для `release()` (чужой holder отказывает,
свой снимает штатно) и юнит-тесты в `scripts/lib/test_claim_task.py`
(мок-уровень: свой/чужой/неизвестный держатель на claim и release, CLI
`--force`, `current_holder()` приоритет источников).

## Что вне рамок

- Носитель замка (git-ref) не меняется — решение ADR 0006 не переоткрывается.
- `LEASE_ALREADY_CLAIMED` (флаг транспорта, `task-lease-claim`) не убирается:
  дешевле не ходить в Git Data API за held-держателем там, где номер уже
  известен из окружения; держатель — ортогональный, дополнительный механизм.
- Автоматическая миграция живых рефов старого формата на новый — не делается:
  они естественно освобождаются существующими путями (TTL, post-merge,
  ручной `release --force`), принудительная перезапись чужого замка ради
  добавления `holder:` была бы риском без пользы.
