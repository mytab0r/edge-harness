## ADDED: Пульс оркестрации (наблюдатель за пульсом планировщика)

38. Watchdog «кто следит за следящим» (`pulse_guard.heartbeat_check`, #120)
    судит о возрасте пульса ТОЛЬКО по прогонам `orchestra.yml` job'а
    `orchestra` (`schedule`/`workflow_dispatch`), не job'а `contract`
    (каждый `pull_request` того же файла — не имеет отношения к пульсу
    планировщика и не должен маскировать его отсутствие частыми зелёными
    прогонами). Отсев — СЕРВЕРНЫЙ, не клиентская фильтрация одной сырой
    страницы: `orchestra_tick_runs` делает отдельный запрос
    `?event=...&per_page=100` на КАЖДОЕ легитимное значение (`schedule`,
    `workflow_dispatch`) и сливает результаты — так `contract`
    (`event=pull_request`) физически не попадает на эти страницы, сколько
    бы его ни было между двумя настоящими тиками (находка ревью #318:
    клиентский фильтр `real_orchestra_ticks` поверх ОДНОЙ сырой страницы
    сам по себе не спасал от труncации при ≥100 `contract`-прогонах между
    тиками — граничный случай доказан тестом
    `test_heartbeat_check_finds_real_tick_past_page_full_of_contract_runs`).
    `real_orchestra_ticks` остаётся как чистый юнит и вторая линия защиты.
    Пустой результат ПОСЛЕ серверного фильтра (оба события отдали 0
    success) — не «выборка коротка», а самостоятельный тревожный случай:
    кричит `🚨 HEARTBEAT_NO_TICKS` (Telegram на каждый прогон, комментарий
    в задачу — один на эпизод), а не молчит `ℹ️`.
