# worker-success-run-evidence: успех воркера требует доказательства работы этого прогона (#876)

Задача: #876. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`pr-merged-is-success` (#539) уже называл этот пробел явно в разделе «Что
вне рамок» своего
[proposal.md](../pr-merged-is-success/proposal.md) (requirement 29
формулируется в его
[specs/journal-tasks-hands/spec.md](../pr-merged-is-success/specs/journal-tasks-hands/spec.md),
но цитата ниже — из proposal.md): «критерий «PR по ветке существует»
превращает такой случай (PR по той же ветке может принадлежать другой,
более старой попытке) из ложного красного в ложный зелёный — отдельная
находка, не устраняется здесь».

Живой инцидент — прогон `worker.yml` 34498185823 (задача #140,
2026-09-10): dsh упал на всех провайдерах цепочки этого прогона (rc=1,
`WORKER_CHAIN_PROVIDER` пусто), но PR #395 существовал с предыдущего
прогона (2026-09-05) — воркер отрапортовал «🤖 Автономный воркер справился
(провайдер: ?)», хотя работы в этом прогоне не было вовсе. Пустой
провайдер в тексте «справился» — само по себе противоречие.

## Что делается

- `scripts/lib/dsh-ci.sh::dsh_worker_run_is_success` — конъюнкция трёх
  фактов ЭТОГО прогона: код возврата dsh (`rc == 0`), непустой
  `WORKER_CHAIN_PROVIDER` (провайдер, ответивший успехом), новый коммит в
  ветке относительно отпечатка HEAD до запуска dsh. Существование PR по
  ветке (`pr_outcome.py`, #413) остаётся необходимым, но больше не
  достаточным условием.
- `scripts/worker/task.sh` — гейт успеха теперь конъюнкция обоих критериев;
  сообщение о провале различает «PR нет вовсе» от «PR существует, но не
  из этого прогона».

## Проверено

- `bash scripts/lib/test/dsh-worker-success-gate.smoke.sh` — 5 сценариев
  зелёные; мутация (гейт всегда возвращает успех) красит сценарий 2 (живая
  форма инцидента), восстановление — снова зелёный.
- `python -m pytest scripts/orchestra/test_repo_invariants.py
  scripts/lib/test_pr_outcome.py -q` — все тесты зелёные.

## Что вне рамок

- Тот же класс у `hands/dsh_task.sh` и `review/ai_dsh.sh` не найден при
  разборе: оба судят исход по `rc`/`DSH_RUN_RC` напрямую, PR-based
  критерий им не нужен — второго места правды не заводится.
