# Дельта-спека: журнал (journal-tasks-hands) — дедуп одновременных прогонов ai-review (#779)

## ADDED: Конвейер (оркестратор)

42. Concurrency-группа `ai-review.yml` ключуется НОМЕРОМ PR для ОБОИХ путей
    триггера (`workflow_dispatch` и `workflow_run` от `pr-review`), не
    id событийного прогона — до этого два триггера одного PR попадали
    каждый в свою группу и не сериализовались вовсе (живой случай #779, PR
    #725: два прогона с разницей 2с, оба симметрично отказали друг другу —
    итог ноль вердиктов, не один). `cancel-in-progress: false`: второй
    триггер ждёт в очереди, не отменяет уже летящий и не теряет его
    вердикт; фолбэк на id прогона — только для форк-PR (`pull_requests[0]`
    пуст, документированное ограничение GitHub).

    42.1. Проверка «прогон этого PR уже летит»
        (`review_labels.other_active_ai_review_runs`) спрашивается ОБОИМИ
        путями триггера в `ai_review.py::cmd_should_run` — эта проверка
        безопасна ровно тогда, когда группа concurrency гарантирует, что
        два триггера одного PR не задают её одновременно (42 — её
        предусловие, не независимая мера).

    42.2. Отказ по занятости и отказ по неизменному отпечатку диффа несут
        РАЗНЫЙ текст для событийного и ручного пути (`manual_dispatch_
        busy_reason`/`event_dispatch_duplicate_reason`,
        `manual_dispatch_skip_reason`/`event_dispatch_skip_reason`) —
        читатель лога различает причину, не гадает между «дубль» и «дифф не
        изменился» (AGENTS.md, «алерт не гадает»).

    42.3. Прогон `ai-review.yml` старше `AI_REVIEW_TIMEOUT_MINUTES` (то же
        число, что `timeout-minutes:` job'а `review`) по `created_at` не
        считается «летящим» ни в одном из трёх мест, что спрашивают
        занятость (`other_active_ai_review_runs`, `scheduler.
        trigger_ai_review`, `repo_invariants.retry_budget_fact`) — GitHub
        сам оборвёт такой job по таймауту, а без потолка возраст мнимой
        занятости не ограничен ничем.

    42.4. Инвариант 3 (`repo_invariants.stuck_gate_fact_line`) называет
        третье состояние бюджета автоповтора явно: бюджет ещё не исчерпан,
        но летящий прогон (`held_back_by_run`) придерживает автоповтор —
        в ОБЕИХ ветках, где бюджет не исчерпан (текущая эпоха и перенос из
        прошлой, #431/#472), а не утверждает «должен сработать на ближайшем
        тике/сработать сам», когда тик на деле сделает `continue`.

## Известные границы (не устранены, названы явно)

- Форк-PR: `run-name` и ключ concurrency-группы деградируют в один и тот же
  fallback (голый `ai-review` / id прогона), из-за чего
  `other_active_ai_review_runs` тоже не находит своих прогонов — на форк-PR
  оба тормоза (занятость и очередь) выключены одновременно. Форк-PR в
  репозитории на момент этой правки нет.
- Статус `pending` (создаётся новым ключом группы) не входит в опрашиваемые
  `other_active_ai_review_runs` статусы (только `in_progress`/`queued`).
  Для `cmd_should_run` это делает схему верной (летящий прогон не видит
  ждущего и публикует первым), для `update_branch`/`mechanical_rebase.py`/
  `trigger_ai_review` — узкое окно, где тормоз не срабатывает.
