# acceptance-reopen-guard: приёмка не должна закрывать переоткрытую задачу заново (#363)

Задача: #363. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

Стадия приёмки (`scripts/orchestra/scheduler.py::accept_merged_tasks`, #227) в ветке
`state in ("ok", "docs")` не дедуплицировала закрытие. Соседние ветки того же обхода
дедуплицируют: `partial_disclaimer` — через `already_marked`, `fail` — через
`already_failed` (обе — #335/PR #342). У ветки `ok`/`docs` признака не было вовсе.

Следствие: задача, переоткрытая человеком или агентом после ошибочного закрытия, на
следующем же пульсе оркестратора снова находится в пуле открытых задач и снова
матчится СО СТАРЫМ уже слитым PR через `merged_pr_map` (мерж — свершившийся факт,
никуда не девается). Улика того PR по-прежнему валидна → `state` снова `ok`/`docs`
→ `accept_merged_tasks` закрывает issue заново, отменяя переоткрытие за 20–80 секунд.

Живой случай: #131 ← PR #132 — переоткрывали три раза за время работы над PR #359,
закрывало обратно каждый раз. Находка оставлена комментарием в PR #359
(2026-09-05T21:57:10Z), воспроизведена трижды.

Отдельный класс от #335 (acceptance-partial-pr-guard): там дефект — задача закрыта
по декларации PR, хотя PR закрывает её лишь частично (ветка `partial_disclaimer`
получает новое условие). Здесь дефект другой: ветка `ok`/`docs` вообще без
guard'а — не про полноту критерия, а про отсутствие дедупликации самого закрытия.

## Что делается

Ветка `state in ("ok", "docs")` перед закрытием проверяет: не закрывала ли приёмка
уже ЭТУ пару (issue, PR) раньше. Признак — маркер-комментарий
`ACCEPTANCE_OK_MARKER`/`ACCEPTANCE_DOCS_MARKER` с номером ИМЕННО этого PR: этот же
маркер приёмка сама оставляет непосредственно перед `PATCH state=closed` при первом
закрытии, поэтому «маркер найден» равносильно «PATCH по этому PR уже прошёл» — это
прямая улика факта закрытия, не косвенная примета.

Рассмотренные и отклонённые альтернативы признака:
- `closed_at` issue позже `merged_at` PR — не говорит о ПРИЧИНЕ закрытия: issue
  могли закрыть вручную по другому поводу уже после мержа, время само по себе
  ничего не доказывает про то, что закрыла именно приёмка и именно по этому PR.
- Событие `closed` в timeline issue — GitHub не хранит в этом событии, каким именно
  PR оно вызвано (в отличие от событий `merged`/`referenced`, у которых есть
  `commit_id`), поэтому такое событие не отличило бы «закрыла приёмка по этому PR»
  от «закрыл человек вручную» или «закрыла приёмка по другому, более новому PR».

Найдя маркер — приёмка молча уходит, не трогая evidence/PATCH/assignee/lock:
переоткрытие человеком или агентом уважается, приёмка с ним не спорит.

Формат маркера дедупликации (`{MARKER} PR #{pr_number}`) сведён в одно место —
`scheduler.py::acceptance_pr_marker` — вместо трёх похожих f-строк по веткам
(`partial`/`fail`/новая `ok`/`docs`), чтобы четвёртая копия того же условия не
появилась рядом с уже существующими.

## Проверено

Другие ветки того же обхода (`pending`, hard-failure escalation, epic) и соседние
функции файла (`reap_stale`, `after_merge`, `unhealthy_pulls`) на тот же пробел
проверены: единственное место, где `accept_merged_tasks` закрывает issue
(`-X PATCH .../issues/N -f state=closed`), — эта ветка; других мест закрытия issue
в файле нет.

Тест на прод-форме (`test_accept_merged_tasks_does_not_reclose_after_manual_reopen`,
`scripts/orchestra/test_scheduler.py`) воспроизводит живой случай: маркер
`ACCEPTANCE_OK_MARKER PR #138` уже стоит в комментариях, issue открыта без
исполнителя (как после ручного реопена), маршруты evidence (`pulls/138/files`,
check-runs) намеренно настоящие — без guard'а тест ловит именно повторное
закрытие (PATCH). Доказано мутацией: снятие guard'а красит тест на реальном
падении (`post_issue_comment` дёргается повторно, эскалируя тестовый `pytest.fail`).

## Что вне рамок

- Полная семантическая проверка «эта задача больше не требует работы» —
  автоматика приёмки лишь не спорит с фактом реопена, решение о докрытии остаётся
  за человеком/следующим PR (тот же принцип, что и `task-closure-after-proof`).
- Разбор существа #131 (сам рендер транскрипта) — отдельно, это только защита
  конвейера приёмки от отмены переоткрытия.
