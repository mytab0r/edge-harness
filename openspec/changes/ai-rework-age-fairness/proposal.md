# ai-rework-age-fairness: очередь доводки ai:changes-requested — возраст, развязка эскалации, инвариант 22 (#1253)

Задача: #1253. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

Написана ПОСЛЕ кода — реализация уже слита в ветку `agent/1253-ai-rework-queue-age`
(PR #1260). Единственная блокирующая находка ai-review на этом PR — отсутствие
именно этого каталога (`docs/agents/OPENSPEC-PROTOCOL.md`: поведенческое
изменение контракта без change недопустимо, прецедент — #588/
`conflict-auto-rebase`). Текст ниже описывает РЕАЛЬНОЕ поведение диффа
(`scripts/orchestra/scheduler.py`, `scripts/orchestra/repo_invariants.py`),
не замысел задачи — расхождения между тем и другим названы отдельно в разделе
«Известные расхождения» ниже, не сглажены.

## Зачем

`dispatch_ai_review_rework` (введена ранее, issue #1027, без собственного
change — часть уже существующего долга «change не заводился», см.
`docs/agents/OPENSPEC-PROTOCOL.md`) страдала тем же классом дефекта, который
`dispatch_conflict_rework` уже решил для очереди конфликтов (issue #588):

- **Голодание по возрасту.** Кандидаты перебирались в сыром порядке
  `open_pulls()` (`GET /pulls?state=open`, новые PR первыми) —
  `scheduler.py:1176-1179`: замер живого репозитория 2026-09-14 — 31 открытый
  PR с `ai:changes-requested`, 15 из них не получили ни одного диспатча
  доводки НИКОГДА (старейший восстановленный случай — PR #261, ~8.3 суток).
- **Эскалация ждала занятости воркера.** Решение «бюджет доводки исчерпан →
  эскалировать владельцу» было под тем же гейтом `dispatched or
  worker_runs_active(repo)`, что и реальный диспатч `worker.yml`, хотя
  эскалация воркер не трогает (только комментарий + `pulse_guard.escalate`).
  Живая цена (`scheduler.py:1232-1241`): PR #804/задача #720 — воркер упал
  честным инфра-отказом 2026-09-12T13:43, авто-повтор без штрафа бюджета
  должен был сработать следующим свободным пульсом, не сработал почти
  двое суток.
- **Белый список неконечных статусов прогона неполон по построению.** Первая
  версия фикса пункта выше проверяла `status in ("in_progress", "queued")`,
  чтобы не эскалировать, пока исход СВОЕГО последнего прогона `worker.yml`
  не известен, — но у GitHub Actions статусов больше (`requested`, `waiting`,
  `pending`, …), и `conclusion` не заполнен ни для одного из них. Ревьюер
  PR #1260 исполнил сценарии `requested`/`waiting` и получил ложную
  эскалацию с текстом «не атрибутирован», хотя атрибуция была — просто исход
  ещё не известен (`AGENTS.md`, «алерт не гадает»: «атрибуции нет» и
  «атрибуция есть, исход неизвестен» — разные факты).
- **Слепая зона любого инварианта репозитория.** `check_stuck_review_gate`
  (инвариант 3) намеренно пропускает ЛЮБОЙ PR с уже вынесенным `ai:*`-вердиктом
  (он про гейт 2 ДО вердикта) — PR с `ai:changes-requested`, которому
  `dispatch_ai_review_rework` ни разу не звонил, был структурно невидим
  никакому существующему инварианту.

## Что делается

**A. Сортировка очереди по возрасту эпизода метки**
(`scheduler.py:1174-1202`). Новая функция `ai_changes_labeled_at(repo,
pr_number)` (`scheduler.py:767-780`) — момент ПОСЛЕДНЕЙ простановки
`review_labels.AI_CHANGES` (max, не min — возраст ТЕКУЩЕГО эпизода вердикта,
не первого за всю историю PR). Общая часть с `conflict_labeled_at`/
`conflict_first_labeled_at` вынесена в `_label_event_times(repo, pr_number,
label_name)` (`scheduler.py:712-726`) — одно место правды на «когда метка
появилась» вместо трёх копий одного цикла по таймлайну.
`dispatch_ai_review_rework` делит кандидатов (PR с `ai:changes-requested` и
БЕЗ `conflict` — та своя очередь) на `unscheduled` (нет задачи в имени ветки —
идут первыми как дешёвый `continue`, сортировкой не платят) и `schedulable`
(сортируются по `ai_changes_labeled_at(...) or parse_time(created_at)` —
старейший вердикт первым); порядок обхода —
`unscheduled + schedulable + [всё остальное]`. При равенстве меток (не
проверено тестами отдельно) сортировка Python стабильна — порядок входа
`pulls` сохраняется для равных ключей.

**B. Развязка решения об эскалации от занятости воркера**
(`scheduler.py:1231-1249`). Ветка «бюджет доводки исчерпан» (`attempts >=
AI_REWORK_MAX_ATTEMPTS`) считает и публикует маркер эскалации независимо от
`worker_runs_active(repo)` — гейт занятости воркера остаётся только у
РЕАЛЬНОГО диспатча `worker.yml` ниже по функции (`scheduler.py:1395-1399`,
`if dispatched or worker_runs_active(repo): continue`). Это два РАЗНЫХ
условия, и в коде (и здесь) они разделены явно — их склейка и была исходным
дефектом.

**C. Признак «исход собственного прогона ещё не известен»**
(`scheduler.py:1279-1310`) — отдельное третье условие ВНУТРИ ветки
эскалации, оценивается уже после развязки (B): перед тем как решить,
эскалировать или нет, код читает `last_worker_run(repo, task_number)` и
проверяет `run.get("status") != "completed"`. Это НЕ перечисление
неконечных статусов (`"in_progress"`, `"queued"`, …) — GitHub Actions
статусов больше, и перечисление неполно по построению; только
`"completed"` гарантированно несёт заполненный `conclusion` (прод-форма
GitHub Actions API). «Атрибуции нет вовсе» (`run is None`) и «атрибуция
есть, но исход прогона ещё не известен» (`run.get("status") != "completed"`)
— разные факты и разные ветки кода: первое ведёт к тексту «не
атрибутирован» (законная эскалация), второе — к `continue` с наблюдением
«эскалация отложена до известного исхода» и БЕЗ эскалации. Это правило
сформулировано как общее (не перечислять неконечные состояния, проверять
только терминальное) — оно шире одного места, поэтому зафиксировано здесь,
а не только в комментарии кода.

Признак «доводка звалась хоть раз, но не помогла» (бюджет
`AI_REWORK_MAX_ATTEMPTS` на отпечаток диффа, `ai_rework_attempts`,
`scheduler.py:1100-1121`) НЕ меняется этим change — A/B/C работают внутри
существующего бюджета и эскалации, не заменяют их.

## Инвариант 22: PR с `ai:changes-requested`, который ни разу не позвали

`repo_invariants.py::check_ai_rework_never_dispatched`
(`repo_invariants.py:994-1050`), реестр — `repo_invariants.py:314-330`.
Наблюдательный — НЕ в `CI_GATING` (`repo_invariants.py:556`) и НЕ в
`ESCALATING_INVARIANTS` (`repo_invariants.py:3409`), проверено тестом
`test_ai_rework_never_dispatched_not_in_ci_gating_or_escalating`. Причина —
свежий инвариант без истории эскалаций, тот же порядок, что у 8/9/10/12/14
(инварианты той же природы уже приняты наблюдательными на этом же основании).

Условие находки: PR несёт `ai:changes-requested` (без `conflict` — своя
очередь), с момента ТЕКУЩЕГО эпизода метки (`ai_changes_labeled_at`) прошло
больше `AI_REWORK_NEVER_DISPATCHED_AFTER_MINUTES` (1440, т.е. 24 часа,
`repo_invariants.py:991`), и ни один комментарий PR не содержит
`scheduler.AI_REWORK_MARKER` (проверяется по ВСЕЙ истории комментариев PR
через `pulse_guard.all_issue_comments`, БЕЗ привязки ко времени начала
текущего эпизода — см. «Известные расхождения» ниже). `labeled_at is None`
(таймлайн не отдал событие) — не находка, инвариант не гадает.

Порог обоснован замером, не вкусом (комментарий `repo_invariants.py:938-957`):
живой прогон 2026-09-14 по 22 открытым PR с `ai:changes-requested` (без
`conflict`) нашёл 17, ни разу не получавших маркер доводки. Возраст текущего
эпизода метки у этих 17 распадается на два кластера с зазором: «формирующийся
бэклог» — 0.2…438.8 мин (~7.3 ч, разгребается сам за часы при серийном слоте
воркера — флагать эту фазу было бы «тормозом без газа» сразу после
внедрения); «реальный многодневный застой» — 2894.0…11899.6 мин (~2.0…8.3
сут). Порог 1440 мин лежит строго в зазоре (> 438.8, < 2894.0). На момент
внедрения даёт 4 находки: #261/#919/#1028/#1033.

## Известные расхождения между описанием и кодом (не сглажены)

Найдены чтением кода, часть — это же нашёл ai-review PR #1260 как
некритичные замечания (не блокирующие слияние), и они НЕ исправлены в этой
ветке — этот change их не чинит, только называет честно:

1. **Маркер доводки для инварианта 22 не привязан к текущему эпизоду метки.**
   `ever_dispatched` в `check_ai_rework_never_dispatched`
   (`repo_invariants.py:1043-1046`) ищет `AI_REWORK_MARKER` по ВСЕЙ истории
   комментариев PR, без сравнения времени маркера с `labeled_at` текущего
   эпизода. PR, доведённый в ПРОШЛОМ эпизоде `ai:changes-requested`, после
   новой простановки метки старше порога никогда не попадёт в находку —
   старый маркер молчит именно тогда, когда повторилось ровно то, для чего
   детектор заведён. Докстринг честно говорит «НИ РАЗУ», но не уточняет
   «в этом эпизоде» — расхождение между замыслом (симметрия с
   `ai_changes_labeled_at`, который сам эпизод-точен) и фактическим кодом
   инварианта (не эпизод-точен).
2. **Сортировка не изолирована от сетевого отказа.** `ai_changes_labeled_at`
   вызывается прямо внутри `sort(key=...)` (`scheduler.py:1198-1200`) без
   `try/except`; один сбойный запрос таймлайна по ОДНОМУ PR роняет
   `RuntimeError` сквозь весь проход `dispatch_ai_review_rework` — вместе с
   ним пропадают и диспатч, и эскалации по ВСЕМ остальным PR прохода. У
   `dispatch_conflict_rework` (`conflict_labeled_at` в ключе сортировки) тот
   же профиль — класс общий, не только этой функции.
3. **Разъехавшаяся нумерация в комментариях (косметика, не поведение).**
   `test_repo_invariants.py:3945` несёт заголовок секции «Инвариант 19» —
   остаток до переномерования в 22 арбитром (`scripts/lib/
   invariant_numbering.py`, коммит `1fcaadf3`); код, реестр
   (`repo_invariants.py:314`) и `build_report` везде используют 22, только
   этот один заголовок комментария не обновлён.
4. **Реестр указывает на неверный адрес.** `repo_invariants.py:330`
   ссылается на «живой замер долга … см. PR #1253» — #1253 является issue
   (задачей), не PR; сам PR — #1260, а замер фактически лежит в комментарии
   над константой `AI_REWORK_NEVER_DISPATCHED_AFTER_MINUTES`
   (`repo_invariants.py:938-957`). Нарушает `AGENTS.md` («утверждение о
   готовом артефакте обязано нести его адрес») в мелком масштабе — адрес
   есть, но неверный.

Ни один из четырёх пунктов не помешал прохождению тестов, перечисленных в
«Проверено» выше — все они про полноту/точность формулировок и устойчивость
к редкому сетевому отказу, не про сломанный основной путь.

## Что вне рамок

  (введена issue #1027, без собственного change) — этот change описывает
  ТОЛЬКО дельту PR #1260 (A/B/C + инвариант 22), не восполняет весь долг
  недокументированной функции целиком.

  кода, не входящие в задачу (код этой веткой заморожен по прямому указанию
  задачи, поставившей этот change); каждый пункт — кандидат в отдельную
  узкую задачу, если владелец сочтёт нужным.
- Issue #1256 (уже заведена по итогам PR #1260) — холостая карусель
  `dispatch_worker` на #257 до простановки `blocked` — не входит: другой
  класс дефекта, найденный тем же расследованием, но не относящийся к
  очереди доводки `ai:changes-requested`.
