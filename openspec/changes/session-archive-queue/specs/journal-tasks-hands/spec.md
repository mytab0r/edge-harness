(Сценарий прежде формулировала дельта
`openspec/changes/runner-sessions-in-dsh-morde/spec.md`; этот change его
заменяет — красный код остаётся сигналом, но больше не единственной записью
о незавершённой работе.)

Требование: архивация сессии раннера — очередь, а не разовая попытка. Факт
«задача ещё не убрана» — durable-метка `session:archive-pending` на задаче,
видимая одним запросом, не строка лога прогона.

Сценарии:

1. Слияние PR задачи → задача ВЕТКИ (`task_ref.resolve_pr_task`, тело PR не
   читается) получает метку ДО попытки архивации и до логина в морду; метка
   снимается ТОЛЬКО после успеха либо терминального `session-not-found`
   (убирать нечего и никогда не будет). Падение в любой точке оставляет
   метку — работу, а не пустоту. Повторная архивация уже архивированной
   сессии безвредна (идемпотентный RPC), потерянная сессия — нет
   (at-least-once выбран сознательно).
2. Каждый проход оркестратора повторяет попытку по всем задачам с меткой
   (`scheduler.py::retry_pending_session_archives`) — без участия человека
   и без памяти о прошлом прогоне; хвост добирается сам после починки любой
   причины отказа. Что осталось убрать — видно запросом по метке.

   **Изменение #1422** (доводка этого же change'а, не новый): красным прогон
   красит НЕ сам факт неудачной уборки, а два конкретных исхода, и каждый со
   своим текстом эскалации:

   - **возраст записи** ≥ `SESSION_ARCHIVE_QUEUE_STALE_HOURS` либо возраст не
     установить вовсе (`labeled`-события не отдались) — «сломана ПРИЧИНА, а не
     уборка». Fail-safe в громкую сторону: неизвестный возраст считается
     просроченным;
   - **метку поставить не удалось** — единственный случай, когда факт работы
     теряется: повторять нечему, очередь номера не знает, лечится руками.

   Неудачная уборка при ПОСТАВЛЕННОЙ метке красным не красит и владельцу не
   уходит: это штатная работа очереди — строка отчёта и повтор на следующем
   проходе. Причина изменения — цена ложного сигнала, измеренная живьём
   2026-09-21: красный прогон orchestra читается `pulse_guard` как «пульсы
   пропадали», то есть «конвейер мёртв», и при исчерпанной квоте DO (#1411)
   владелец получал по два алерта каждые ~8 минут, пока конвейер в те же
   минуты слил четыре PR. Сигнал, который врёт, перестают читать.

   **Частота: эпизод, а не проход.** Алерт уходит владельцу один раз на
   эпизод. Эпизод опознаётся маркером `[статус: очередь архива сессий не
   тает]` в задаче-статусе: новый эпизод — маркера ещё нет, либо последний
   алерт СТАРШЕ самой старой просроченной записи (значит очередь успела
   растаять и набраться заново). Пока эпизод тот же — строка отчёта, зелёный
   прогон, владельцу ничего; факт при этом не теряется (маркер + запрос по
   метке). Парного закрывающего маркера НЕТ сознательно: класть его пришлось
   бы в момент опустевшей очереди, а это сетевой вызов на каждом пустом
   проходе — холостой ход, запрещённый гвардией
   `test_retry_pass_is_quiet_when_the_queue_is_empty`. Возраст записи
   догоняющий проход и так читает, поэтому сравнивать есть с чем.

   Разные жёсткие сбои хвоста мержа НЕ смешиваются в одном тексте: архивный
   флаг возвращается отдельно от остальных (`after_merge`/`merge_queue`/
   `merge_loop`), иначе архивный текст печатается на сбое заметок-итогов и
   утверждает факт, которого нет — это было найдено ai-review на PR #1424 и
   прибито тестом `test_merge_tail_failure_does_not_speak_about_the_archive_queue`.

   Эскалация по-прежнему обещает только то, что механизм выполняет: текст
   «возраст ≥ порога ЛИБО возраст не установить» не утверждает известное
   число, а построчный отчёт прогона называет по каждому номеру, что именно
   из двух. Жёсткие сбои ДРУГИХ механизмов хвоста мержа (заметки-итоги,
   реестр находок) с этим текстом не смешиваются — у них свой, потому что
   лечатся они иначе.
3. Задача пула, лишь упомянутая в теле слитого PR прозой, в архив не
   попадает: гейт вызова — задача ВЕТКИ; PR без agent-ветки ходов в морду
   не делает вовсе.

**Изменение #1432** (доводка этого же change'а, не новый): очередь получает
ВТОРОГО постановщика и терминальное свойство.

До #1432 у входа в очередь стоял ровно один постановщик — `after_merge`. То
есть сессия убиралась только у задачи, чей PR слит. Сессия задачи, чей PR не
слит (конфликт, `ai:changes-requested`, `blocked`, заброшен) или которая до PR
не дошла вовсе (прогон воркера упал), не убиралась НИКОГДА и ничем — не
«иногда терялась», а не была предусмотрена. Замер на живом репозитории
2026-09-22: 100 прогонов воркера за 30 суток, 26 из них не успех, 25 открытых
PR.

У выхода при этом не было признака завершённости: отсутствие
`session:archive-pending` означало одновременно «убрано» и «никогда не
рассматривалось». Вопрос «какие сессии осталось убрать» ответа не имел.

Требования:

4. **Свойство «убрано» — метка `session:archived`**, ставится ПОСЛЕ факта:
   успешной архивации либо терминального «сессии раннера нет» (убирать нечего
   и никогда не будет). Порядок обязателен: свойство раньше снятия очереди.
   Обратный порядок даёт окно, в котором задача уже не в очереди и ещё не
   помечена убранной — невидима обоим механизмам, то есть ровно та дыра,
   из-за которой вопрос выше не имел ответа. Порядок закреплён тестом
   `test_archived_marker_is_set_before_the_queue_entry_is_cleared`; повтор
   архивации уже архивированной сессии безвреден (RPC идемпотентен), потеря
   номера — нет.
5. **Второй постановщик: свип закрытых задач.** Каждый пульс берёт ЗАКРЫТЫЕ
   задачи пула без обеих меток и ставит их в ту же очередь
   `session:archive-pending`. Второго механизма АРХИВАЦИИ не заводится: уборку
   по-прежнему делает `retry_pending_session_archives` — свип только помечает
   и в морду не ходит (закреплено тестом
   `test_sweep_does_not_touch_the_morde_itself`).

   Критерий — ЗАКРЫТИЕ задачи, а не слияние PR и не возраст PR. Выбор из трёх
   кандидатов обоснован так: `session_id` — `harness-<номер ЗАДАЧИ>`, один на
   ВСЕ прогоны задачи. Убрать сессию у ОТКРЫТОЙ задачи значит отнять её у
   следующего прогона, который допишет туда же, — поэтому «возраст PR» и
   «возврат задачи в пул» отпадают оба. Закрытая задача не переоткрывается
   никогда (правило репозитория, принуждается `reject_reopened_tasks`),
   значит её сессия доработана окончательно и единственный момент, после
   которого уборка безопасна, — именно закрытие.

   Запрос поиска кавычит имена меток (`label:"session:archive-pending"`).
   Причина — ЗАМЕРЕННАЯ, а не выведенная из модели парсера
   ([docs/research/21-github-actions.md](../../../../docs/research/21-github-actions.md),
   2026-09-22): `%XX` внутри значения квалификатора Search API **не
   декодирует** — `label:area%3Aprocess` даёт 0 совпадений, тогда как сырое
   двоеточие и кавычки дают по 343. То есть опасен здесь именно
   `label_query_value` (он и подставил бы `%3A`), а двоеточие само по себе
   квалификатор НЕ режет — первая редакция этого абзаца утверждала обратное
   и была опровергнута тем же замером.

   Кавычки выбраны не потому, что без них ломается, а потому, что это
   ОДНОЗНАЧНАЯ форма: она верна и для значения с пробелом, и для значения с
   двоеточием, и читателю не нужно помнить, какие символы движок прощает.
   Одно место правды — `review_labels.label_search_value`; оно НЕ
   взаимозаменяемо с `label_query_value`, и это различение принуждается
   гвардией: суффикс `labels=` требует процентного кодирования, суффикс
   `label:` — кавычек поиска.

   **Потолок `CLOSED_TASK_SWEEP_LIMIT`** — условие включения, а не
   оптимизация: в репозитории лежат сотни давно закрытых задач, и попытка
   пометить все за один проход упёрлась бы в лимит GitHub API. Очередь
   повторяется на каждом пульсе, хвост растает за несколько часов. По той же
   причине запрос одностраничный: страница здесь — не «первая из многих», а
   ВСЯ порция прохода.
6. **Свип вызывается из пульса.** Требование отдельное, потому что без него
   механизм — украшение: все тесты свипа зовут функцию напрямую и её
   отсутствия в `main()` не замечают (исполнено ai-review на PR #1435 —
   замена вызова на пустой список оставляла восемь тестов зелёными).
   Закреплено `test_main_runs_the_closed_task_sweep_every_pulse`.
