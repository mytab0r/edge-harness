(Сценарий прежде формулировала дельта
`openspec/changes/runner-sessions-in-dsh-morde/spec.md`; этот change его
заменяет — красный код остаётся сигналом, но больше не единственной записью
о незавершённой работе.)

Требование: архивация сессии раннера — очередь, а не разовая попытка. Факт
«задача ещё не убрана» — durable-метка `session:archive-pending` на задаче,
видимая одним запросом, не строка лога прогона.

Сценарии:

1. Слияние PR задачи → задача ВЕТКИ (`task_ref.resolve_pr_task`, тело PR не
   читается) получает метку ДО попытки архивации и до логина в морду; метка
   снимается ТОЛЬКО после успеха либо терминального `session-not-found`
   (убирать нечего и никогда не будет). Падение в любой точке оставляет
   метку — работу, а не пустоту. Повторная архивация уже архивированной
   сессии безвредна (идемпотентный RPC), потерянная сессия — нет
   (at-least-once выбран сознательно).
2. Каждый проход оркестратора повторяет попытку по всем задачам с меткой
   (`scheduler.py::retry_pending_session_archives`) — без участия человека
   и без памяти о прошлом прогоне; хвост добирается сам после починки любой
   причины отказа. Красный код прогона при жёстком сбое остаётся (#120), но
   эскалация обещает только то, что механизм всегда выполняет: очередь
   повторяется сама, а что осталось убрать — видно запросом по метке; факт
   «саму постановку метки не удалось сделать» виден отдельной строкой
   отчёта, не в эскалации.
3. Задача пула, лишь упомянутая в теле слитого PR прозой, в архив не
   попадает: гейт вызова — задача ВЕТКИ; PR без agent-ветки ходов в морду
   не делает вовсе.
