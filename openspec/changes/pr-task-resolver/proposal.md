# pr-task-resolver: одно место правды «PR → задача», не чтение прозы

Задача: #259. Владелец назвал это корнем четырёх заблокированных PR за сутки.

## Проблема (замер, не догадка)

`scripts/review/ai_review.py:353` (`task_section`) искал контекст задачи для
AI-ревью так: брал ВСЕ номера `#N`, упомянутые где угодно в теле PR
(`task_ref.extract_task_refs`), сортировал по возрастанию и брал первую
открытую issue с меткой `task`. Живые последствия:

- PR #253 (ветка `agent/227-…`, первая строка тела `#227`) судили по #120 —
  число упомянуто в прозе («issue #120 + Telegram»), а #227 не было
  наименьшим среди всех чисел в теле.
- PR #248 судили по #119 вместо своей задачи, #247 — по #43, #263 — по #4.
  Один и тот же класс: первое попавшееся число вместо реального источника.

При этом у репозитория уже ЕСТЬ надёжный источник — имя agent-ветки
(`agent/<N>-<slug>`), которое может создать только `scripts/git/task-branch`
(enforced-правило с гвардией `.githooks/pre-commit`, подделать номер
случайно нельзя). Он не использовался вовсе.

Проверено (не предположение): ключевые слова `Closes/Fixes/Resolves #N` не
использует ни один из 21 открытого PR — и не может использоваться: контракт
(`contract_check.py`) их прямо запрещает (закрытие задачи — действие
исполнителя после пост-мерж проверки, не GitHub-автозакрытие). Формальная
связь GitHub (`closingIssuesReferences`) поэтому в этом репозитории
структурно пуста — не баг, а следствие уже принятого правила.

## Решение

Один резолвер `scripts/lib/task_ref.resolve_pr_task(pull, closing_issue=None)`
с иерархией источников от надёжного к запасному:

1. Имя agent-ветки (`task_from_branch`) — самый надёжный источник.
2. `closing_issue` — необязательный параметр для формальной связи GitHub,
   если вызывающий код её добыл (GraphQL `closingIssuesReferences`; REST-пути
   к ТОЙ ЖЕ узкой семантике нет, см. design.md). Резолвер сам сети не трогает.
3. Декларация первой строкой тела (`declared_tasks`, уже существовала для
   `contract_check.py`).

Проза по всему телу (`extract_task_refs`/`references_task`) НЕ используется
резолвером вовсе. `task_section` (`ai_review.py`) переведён на резолвер.

## Что осознанно НЕ меняется

`scheduler.py`: `reap_stale`, `unhealthy_pulls` (через `pr_references_issue`)
и `after_merge` продолжают использовать широкую семантику
(`extract_task_refs`/`references_task`) — это заявлено в их собственных
докстрингах как осознанный выбор («не потерять живой PR» / «не снять чужой
замок»; ошибиться в сторону «не трогать» там дешевле, чем в сторону
«занята»). Перевод на узкую семантику снял бы назначение с живой работы или
не освободил бы чужой замок — это была бы регрессия, не улучшение.
`contract_check.py` уже использовал `declared_tasks` (узкая семантика) до
этого change — не трогается.

## Гвардия класса

Докстринг `task_ref.py` уже называл правило «широкая семантика — только там,
где осознанна» до этого change, и это не помешало `ai_review.py` взять
`extract_task_refs`. Поэтому вместо ещё одного абзаца документации —
`scripts/lib/test_task_ref_usage_guard.py`: статический тест, сканирующий
`scripts/*.py` (кроме тестов) на прямые вызовы `task_ref.extract_task_refs`/
`task_ref.references_task` вне явного списка `ALLOWED_WIDE_USAGE`. Новое
место, взявшее широкую функцию по ошибке, красит CI, а не только ревью
докстринга.

## Критерий готовности

- `resolve_pr_task` резолвит PR #253 (прод-форма тела) в 227, не в 120.
- `resolve_pr_task` для dependabot-PR #282 (прод-форма тела) — `None`.
- Обе гвардии (`test_task_ref_usage_guard.py`, тесты резолвера) доказаны
  мутацией: снятая защита красит тест, возвращённая — снова зелёный.
