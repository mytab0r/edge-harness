# Design: pr-task-resolver

Контекст и замер — proposal.md. Здесь — почему источник (б) устроен именно
так и почему REST не заменяет GraphQL для него.

## Источник (б): формальная связь GitHub — GraphQL, а не REST

Задача поручала проверить: доступна ли `closingIssuesReferences` (сейчас
только GraphQL, а GraphQL в этой среде падает чаще REST) тем же REST-путём,
которым уже пользуются остальные скрипты (`gh api repos/.../issues/N`).

Проверено на живом PR #253: `gh api repos/mytab0r/edge-harness/issues/253/timeline`
отдаёт события `cross-referenced` — но с другой семантикой, чем нужна:

- `cross-referenced` заводится на **любое** упоминание `#N` в другом PR/issue
  (нашлись события от PR #247, #270, #278, #248, каждый просто упомянул
  `#253` где-то в тексте) — то же самое «упомянут», что уже даёт
  `task_ref.extract_task_refs`, не формальная связь «этот PR закрывает эту
  задачу».
- У этого репозитория формальная связь и не может появиться: `Closes/
  Fixes/Resolves #N` запрещены контрактом (`contract_check.py`) как
  соглашение — задачу закрывает исполнитель после пост-мерж проверки, не
  GitHub при мерже. `closingIssuesReferences` (и GraphQL, и гипотетический
  REST-эквивалент) для PR этого репозитория будет пуст всегда, это не
  временный пробел.

Вывод: REST-заменителя источнику (б) нет — есть REST-путь к «упоминанию»
(уже покрыт extract_task_refs, не годится по тем же причинам, что и прямой
парсинг прозы), но нет REST-пути к «формальному закрытию». Источник (б)
поэтому:

1. Не встроен в `resolve_pr_task` как самостоятельный HTTP-вызов —
   резолвер остаётся чистой функцией без сети (тестируется прод-формой тел
   PR без gh/сети).
2. Оформлен необязательным параметром `closing_issue`: вызывающий код,
   которому GraphQL всё же нужен (например, будущий консьюмер вне текущего
   change), может попытаться его получить и передать; неудача GraphQL —
   не авария резолвера, источник просто пропускается.
3. Сейчас ни один переводимый потребитель (`task_section`) не вызывает
   GraphQL вовсе — практическая ценность источника (б) в этом репозитории
   нулевая, пока действует запрет Closes/Fixes. Параметр существует для
   честности иерархии из трёх источников и на случай, если правило когда-то
   изменится.

## Почему резолвер не запрашивает GitHub сам

`resolve_pr_task` работает только с уже полученным объектом `pull` (`head.ref`,
`body`). Альтернатива — резолвер сам дергает `gh api .../pulls/N`/`timeline` —
отклонена: тогда «резолвер» и «сетевой клиент» слиплись бы в одну функцию,
которую нельзя протестировать прод-формой тела PR без сети (а именно так
кормится `test_task_ref.py` — см. AGENTS.md, «тест кормит прод-форму данных,
а не пересказ»). Разделение оставляет резолвер чистым, а получение
`closing_issue` (когда/если понадобится) — заботой вызывающего кода.

## Почему guard, а не только докстринг

Докстринг `task_ref.py` уже формулировал правило «широкая семантика — только
там, где осознанна» до этого change (комментарий у `declared_tasks`,
процитированный в proposal.md) — и это не остановило `ai_review.py` от
использования `extract_task_refs` в `task_section`. Постфактум-докстринг не
проверяется при ревью механически, только вниманием ревьюера. Решение —
`scripts/lib/test_task_ref_usage_guard.py`: сканирует `scripts/*.py` (кроме
тестов) на прямые вызовы `task_ref.extract_task_refs`/`references_task` и
падает, если вызывающий файл не в explicit-списке `ALLOWED_WIDE_USAGE`
(сейчас — только `scheduler.py`, где широта заявлена в докстринге каждого
места). Альтернатива «переименовать функции во что-то пугающее» (например,
`extract_task_refs_ANY_MENTION_NOT_FOR_RESOLUTION`) отклонена — такое имя
пришлось бы тащить во все существующие вызовы в `scheduler.py`, раздувая
diff ради синтаксиса, который тест уже проверяет по существу.
