# Дизайн: walking-skeleton

## Форма

```
браузер ──HTTP GET /──────────▶ Workers Assets (статика)
   │
   ├──WebSocket /api/events───▶ Durable Object ──┐
   │                                  │          │ SQLite: события, очередь, heartbeat
   └──POST /api/tasks─────────▶       │          │
                                      │          │
                     repository_dispatch          │
                                      ▼          │
                            GitHub Actions job ──┘
                              POST /api/events (батчами)
```

Одно направление связи наружу: Durable Object → GitHub REST. Обратно job ходит сам, обычным
HTTP. Ни одного долгоживущего исходящего соединения — причина в
[ADR 0001](../../docs/decisions/0001-push-model-not-tunnel.md).

## Решения

**Один Durable Object с фиксированным именем.** Мультитенантности нет, владелец один.
`idFromName('owner')`. Причина не в лени: на бесплатном плане один непрерывно активный объект
съедает 85% дневного бюджета GB-s, поэтому второго живого всё равно быть не может.

**События пишутся батчами, не по одному.** Лимит бесплатного плана — 100 000 записей строк в
сутки. Сессия агента генерирует сотни событий; при записи по одному лимит кончается на
третьей сотне сессий. Job копит события и шлёт пачкой либо по таймеру, либо по достижении
размера.

**WebSocket только на приём, как у dsh-edge.** Браузер получает события по сокету, а
отправляет обычным POST. Так вход в Durable Object остаётся одним, а сокет можно принять
через `acceptWebSocket` и гибернировать — тогда GB-s не капают. Клиент, пишущий в сокет,
заставил бы держать объект живым.

**Heartbeat — строка в SQLite, а не соединение.** Job шлёт отметку каждые N секунд вместе с
батчем событий. «Руки живы» = отметка свежее порога. Это переживает гибернацию объекта и не
требует ничего держать открытым.

**Идемпотентность по номеру события.** Job нумерует события подряд; повторная доставка
батча после сетевой ошибки не должна двоить журнал. Без этого ретрай на стороне job'а
незаметно портит данные — ровно тот silent-wrong, который дороже падения.

## Отвергнутые варианты

**Server-Sent Events вместо WebSocket.** Проще в реализации и достаточно для одностороннего
потока. Отвергнуто с прицелом: UI от DSH использует WebSocket-мультиплексор для токенов
ассистента, и если скелет докажет SSE, то на этапе интеграции DSH придётся переделывать
транспорт. Проверяем сразу то, что понадобится.

**D1 вместо SQLite в Durable Object.** Лимиты те же (5 ГБ, 100k записей в сутки), но
появляется вторая система координат и сетевой вызов из объекта. Всё, что нужно скелету,
лежит в `ctx.storage`. К D1 вернуться, если понадобится читать журнал вне объекта.

**Хранить журнал в R2.** Дёшево по записям, но нет запросов по диапазону, а replay журнала —
основной сценарий чтения. R2 пригодится для больших вложений, не для событий.

## Чего дизайн намеренно не решает

Что происходит, когда задача поставлена, а job не стартовал за разумное время. Скелет должен
это **показать** (задача в очереди, рук нет), но не лечить: сначала измеряем реальное
распределение задержки, потом решаем, нужен ли таймаут и переспавн.
