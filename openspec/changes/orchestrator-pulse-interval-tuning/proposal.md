# orchestrator-pulse-interval-tuning: понизить интервал DO-пульса по измеренной стоимости тика (#812)

Задача: #812. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Боль владельца

Пульс оркестратора (`cf-worker/src/harness.ts::alarm()`) тикал раз в 15 минут
(`cf-worker/src/config.ts::HEARTBEAT.selfOrchestrationMs`). Владелец хочет
чаще — «тикалось часто и быстро». Порядок операций внутри самого тика
(`scheduler.py::main()`, `merge_queue` до `dispatch_conflict_rework`) уже
верный — вне рамок этого change'а.

15 минут были выбраны ради Free-комфорта DO (сам alarm-запрос — 1 request,
дёшево при любой разумной частоте), НЕ из-за лимита GitHub Actions-минут
(репозиторий публичный → минуты бесплатны и безлимитны для standard-раннеров,
`docs/research/21-github-actions.md`). Настоящий потолок — GitHub REST API
rate limit, который и требовалось замерить, а не угадать.

## Замер (issue #812, 2026-09-09)

1. **Стоимость одного тика.** `scripts/lib/rate_guard.py` уже документирует
   ~150-250 REST-вызовов за прогон `orchestra` при непустой очереди (issue
   #443, замер по коду). Живой прогон 2026-09-09 (run 34349635281, ~30-35
   открытых PR — бэклог вырос с момента калибровки #443) показал шаг
   `scheduler.py` длиной ~3.5 минуты — порядок величины в несколько сотен
   вызовов согласуется с оценкой #443 с поправкой на бэклог: `scheduler.py`
   содержит ~8 отдельных проходов по списку открытых PR, часть которых
   делает свой `gh()`-запрос НА КАЖДЫЙ PR (`mergeable_state`, `check-runs`,
   комментарии) — стоимость тика растёт с числом открытых PR, не постоянна.
   Прямого лога «вызов за вызовом» `scheduler.py` не пишет (только финальный
   отчёт) — число не поштучно посчитано, а оценено по документированной
   базе #443 + скорректировано по времени выполнения шага.

2. **Первичный бюджет.** `GH_TOKEN=${{ github.token }}` этого workflow живёт
   в бюджете, общем на ВСЕ workflow репозитория одновременно (`contract` на
   каждый открытый PR, `ai-review`, `worker.yml`) — уже стоило инцидента
   2026-09-06 (`API rate limit exceeded for installation`, PR #428/#453),
   почини́вшегося порогом-предохранителем `rate_guard.py` (300 остатка), не
   увеличением бюджета. Живой замер `gh api rate_limit` в четырёх соседних
   прогонах `orchestra` 2026-09-09 (10:55-12:12 UTC) дал `limit: 5000` —
   **расходится** с задокументированным в GitHub REST API rate limits
   значением 1000/час для `GITHUB_TOKEN` (`docs/research/21-github-actions.md`,
   новый раздел «Live-замер 2026-09-09»). Зафиксирован факт расхождения, не
   причина — не подтверждено, действует ли 5000/час стабильно или это
   особенность момента/репозитория.

3. **Вторичный (content-generating) лимит** — 80/мин, 500/час, документирован
   (`docs/research/21`), но НЕ переизмерен для конкретного набора
   write-вызовов `scheduler.py` (design.md change'а
   `orchestrator-pulse-independence`, раздел 4, п.2, тоже называет его
   непроверенным). Косвенно: типичный тик пишет единицы-десятки таких
   вызовов (живой замер run 34349635281: ~10 write-действий — снятие замка,
   правка меток/ассайни, два `workflow_dispatch`), запас до 500/час большой
   даже при повышенной частоте — вторичный лимит НЕ ограничитель выбора
   ниже, ограничитель первичный бюджет 5000/час.

## Решение

`HEARTBEAT.selfOrchestrationMs`: 15 минут → **10 минут**
(`cf-worker/src/config.ts:104`). Обоснование числом — в докстринге константы
(там же).

Почему 10, а не меньше: при тике ценой до ~400 запросов (консервативная
верхняя оценка при текущем бэклоге) 6 тиков/час (10 мин) — ≤2400/час
(≤48% бюджета 5000/час), оставляя ≥2600/час на `contract`/`ai-review`/
`worker.yml` в тот же час. 12 тиков/час (5 мин) заняли бы до 4800/час —
почти весь бюджет ОДНИМ потребителем, воспроизводя класс инцидента
2026-09-06 чаще, а не реже. Это НЕ грань — запас ~половина общего бюджета
поверх неизмеренного вторичного лимита (консервативное допущение по прямому
указанию задачи: не оптимизировать на грани при непроверенных данных).
Дальнейшее ускорение требует СНАЧАЛА снизить бэклог открытых PR или
стоимость самого тика (число `gh()`-запросов на PR в `scheduler.py`), не
только этот множитель — иначе оценка выше перестаёт быть консервативной.

## Координация с двумя другими механизмами такта (не изменены, только проверены)

1. **CF Cron Trigger (#693, `wrangler.jsonc` `*/5 * * * *`).** Порог
   «alarm подвис» у `pulseStale()`/`pulseNeedsRecoveryDispatch()` —
   `2×HEARTBEAT.selfOrchestrationMs` — читает константу символьно, масштабируется
   автоматически (10 → 20 мин, было 15 → 30 мин). Наихудшее время починки
   резервом при мёртвом alarm: `20 + 5 = 25` мин (было 35). Комментарии
   `wrangler.jsonc` и `docs/research/20-cloudflare-free.md`, несущие этот
   вывод числом, обновлены тем же PR — иначе документация врала бы про
   устаревшее число (найдено при этой работе, тот же класс, что и
   AGENTS.md «Утверждение… обязано нести адрес»/актуальное число).
2. **`RETENTION.backlogStreakThreshold`** (`config.ts`) считает подряд
   идущие ТИКИ, не время — комментарий, ранее хардкодивший «4 тика × 15 мин
   = час», исправлен на честную формулировку («реальная длительность зависит
   от текущего интервала», без устаревшей минутной цифры) — сам порог (4)
   не менялся, это вне рамок.

Новый тест `cf-worker/test/pulse.spec.ts` («интервал alarm согласован с
частотой резерва») доказывает мутацией оба свойства: резерв не срабатывает
раньше порога (не спамит поверх живого alarm) и ловит настоящую аварию не
позже одного cron-тика после порога (не украшение).

## Не подтверждено (перенесено из замера, не выдумано заново)

- Реальный `limit` `GITHUB_TOKEN` для этого репозитория — 5000 или 1000
  (расходится живой замер vs документация GitHub) — см. `docs/research/21`.
- Точная классификация вторичного content-generating лимита для write-вызовов
  `scheduler.py` (PATCH/PUT/DELETE через `gh api`) — не переизмерена нагрузочно.
- Поштучный (не оценочный) счётчик вызовов `scheduler.py` за тик — `main()`
  не логирует вызов за вызовом; число — оценка по #443 + время выполнения,
  не точный подсчёт.

## Что вне рамок

- Порядок операций внутри `scheduler.py::main()` (`merge_queue` до
  `dispatch_conflict_rework`) — уже верный, не трогать.
- Расписание GitHub `schedule` самого `orchestra.yml` (`*/15 * * * *`,
  доставляется ~7% тиков, `docs/research/21`) — отдельный, почти нерабочий
  канал, не источник этого change'а.
- Пересмотр Python-констант `pulse_guard.py` (`HEARTBEAT_MAX_AGE_MINUTES = 45`,
  `INDEPENDENT_PULSE_STALE_AFTER_MINUTES = 60`), калиброванных как «N тактов
  по 15 мин» — это ОТДЕЛЬНЫЕ, независимо захардкоженные Python-константы (не
  читают `config.ts`), которые при уменьшении интервала alarm становятся
  ТОЛЬКО консервативнее (больше тиков умещается в тот же порог минут — риск
  ложного молчания растёт, риска спама нет). Пересчитаны не были: это
  precision-долг, не баг этого change'а, и они относятся к области активной
  параллельной работы (`orchestrator-pulse-independence`, issue #713/#703) —
  трогать чужой раздел без причины запрещено правилами репозитория. Заведена
  отдельная узкая задача-white-spot: [issue #813](https://github.com/mytab0r/edge-harness/issues/813).
- Снижение стоимости самого тика (число `gh()`-запросов на PR в
  `scheduler.py`) — то, что реально позволило бы уйти ниже 10 минут в
  будущем; отдельная, более крупная задача.
