## MODIFIED: Сессия раннера в морде (`dsh_edge_session_begin`, #119/#809)

40. `dsh_edge_session_begin` (`scripts/lib/dsh-edge-session.sh`) при отказе
    `session.create` на запрошенном `session_id` смотрит на текст ошибки:

    - Содержит `failed validation` (морда отклонила ХОЛОДНУЮ ЗАГРУЗКУ уже
      сохранённой, но структурно испорченной сессии — класс #809, живые
      случаи `harness-257/258/215/710/716/140`) → РОВНО ОДИН фоллбэк:
      повтор `session.create`/`session.rename` под новым id
      `<session_id>-r<GITHUB_RUN_ID>`. Успех фоллбэка — обычное продолжение
      работы, исходная испорченная сессия остаётся сиротой (не архивируется
      и не чинится этим механизмом — вне доступа агента, см. design.md).
      Отказ фоллбэка ТЕМ ЖЕ классом ошибки — честный провал (`return 1`),
      второй фоллбэк не предпринимается.
    - Любая другая причина отказа (сеть/деплой морды недоступны,
      конфигурация не задана) — без фоллбэка, провал как раньше.

    stdout функции при успехе — РЕАЛЬНО использованный `session_id`
    (может отличаться от запрошенного): вызывающий обязан читать это
    значение, не подставлять исходный запрошенный id вручную.

    До этой правки ЛЮБОЙ отказ холодной загрузки (не только структурная
    порча из #794, любая будущая причина, дающая тот же класс ответа морды)
    останавливал `worker.yml`/`hands.yml` шагом ДО первого вызова провайдера
    (`exit 1`), держа задачу под арендой до 24-часового TTL-сборщика и вымывая
    свободные задачи из пула — предохранитель диспатча вставал на паузу, хотя
    причина не имела отношения к провайдерам вовсе.
