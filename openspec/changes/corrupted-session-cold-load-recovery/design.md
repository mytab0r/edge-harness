# design.md: corrupted-session-cold-load-recovery (#809)

## Развилка — какой из трёх вариантов #809 (A/B/C)

Issue #809 называет три равноправных направления:

- **(A)** морда дропает битую сессию и заводит чистую под тем же id;
- **(B)** воркер стартует под свежим session-id, если старый не грузится;
- **(C)** миграционный проход, чинящий «голые» `assistant/message` в
  хранилище задним числом (добавить `id`/`source`).

Выбран **(B)**. Причины:

- (A) требует патча серверного кода морды (`dsh-edge/patches/**`) — другой
  деплой-конвейер (`deploy-dsh-edge.yml`, CI-сборка апстрима с патч-серией,
  минуты, не секунды), другой blast radius (затрагивает ВСЕ каналы, читающие
  сессии морды, не только воркер) и требует решения о поведении сервера,
  которое дороже сейчас обосновывать, чем воркер-фикс. Инцидент, который
  этот change закрывает, — воркер стоит НЕДЕЛЯМИ, не морда: минимальный
  фикс на стороне клиента снимает симптом без второго деплоя.
- (C) прямо названа вне рамок агента в `session-note-identified-message/
  design.md` («Восстановление испорченных сессий») — нет доступа к
  сырому `session.jsonl.zstd` в хранилище DO, только к API морды. Решение
  не изменилось с тех пор.
- (B) — минимальный диф, целиком в `scripts/lib/`, без изменения деплоя
  морды: воркер узнаёт о порче ТОЛЬКО через факт отказа `session.create` с
  конкретным текстом, не через отдельный список известных битых id (список
  устарел бы быстрее кода — ровно то, что уже произошло: #809 назвал
  4 сессии, живой прогон нашёл ещё 2 новых за сутки).

## Как отличить «холодная загрузка испорчена» от «сеть/морда недоступна»

`dsh_edge_rpc` (`scripts/lib/dsh-edge-session.sh`) уже различает два класса
неудачи текстом сообщения:

- Контрактный отказ (не сеть): `"::error::Морда отклонила " + code + ": " +
  message` — ретрай тем же вызовом бессмыслен, `dsh_edge_rpc` возвращает 1
  сразу, без внутреннего повтора.
- Сетевой/деплойный сбой: `"::error::Морда недоступна для $method из 3
  попыток (сеть/деплой)"` — уже отретраено 3 раза ВНУТРИ `dsh_edge_rpc`.

Морда оборачивает ЛЮБУЮ причину провала валидации холодной загрузки текстом
`failed validation` (проверено дословно на обоих живых инцидентах —
`harness-716`/seq 13/«lacks an identified message», `harness-140`/seq 2833/
та же форма; апстрим-текст внутренней причины может отличаться — «lacks an
identified message» vs «invalid source», design.md
`session-note-identified-message` «Развилка 1», — но обёртка одна). Матчим
именно на `failed validation`, не на конкретный текст внутренней причины:
уже покрывает оба известных под-случая, не только тот, что видели сегодня.

Сетевой отказ такого текста никогда не несёт — фоллбэк на новый id
запускается ТОЛЬКО контрактным отказом с этой подстрокой. Мутационный тест
(`scripts/lib/test/dsh-clients.smoke.sh`, доказано локально — репозиторий не
даёт CI на Windows-машине разработчика, INFRA-GH.md п.3) отдельно проверяет,
что сетевой класс фоллбэк НЕ запускает.

## Один фоллбэк, не бесконечный ретрай

Если фоллбэк-id (`<исходный>-r<GITHUB_RUN_ID>`) САМ отказывает classом
«failed validation» — это уже не единичная историческая порча, а что-то
системное (например, сама морда сейчас массово отклоняет валидные записи) —
цикл останавливается после ВТОРОЙ попытки с честным провалом, а не
зацикливается в поиске «чистого» id. `GITHUB_RUN_ID` уникален между
прогонами (задан GitHub Actions всегда для реального job'а) — повторный
запуск того же номера задачи получает другой суффикс сам по себе, без
счётчика попыток внутри одного прогона.

## Возврат session_id вызывающему

`dsh_edge_session_begin` теперь печатает в stdout РЕАЛЬНО использованный
id (может отличаться от запрошенного). До этой правки оба вызывающих
(`task.sh`, `dsh_task.sh`) звали функцию с `>/dev/null` и вручную
подставляли исходный `HARNESS_SID` в `DSH_EDGE_SESSION_ID` — рабочий для
пути без фоллбэка, но сломавший бы дрен транскрипта в морду (`dsh_edge_
ingest`/`dsh_edge_verify_transcript` адресовали бы несуществующий/неверный
session_id) в момент, когда фоллбэк реально сработал. Фикс — оба клиента
читают возврат функции.

## Не пересинхронизировано намеренно (Out of scope)

`scheduler.py::append_session_notes`/`workspace.archiveSession`
(`scripts/orchestra/scheduler.py`) продолжают адресовать `harness-<N>`
буквально — не знают о фоллбэк-id, назначенном ВНУТРИ прогона воркера.
Последствие то же, что уже принято в `session-note-identified-message/
design.md` («Развилка 4»): отказ `_morde_ingest`/архивации на испорченную
сессию красит прогон оркестратора предупреждением, не роняет мерж/приёмку —
это НЕ регрессия этого change (то же поведение было и для 4 изначально
известных испорченных сессий ДО этой правки). Пересинхронизация оркестратора
на фактический id потребовала бы либо публикации id куда-то, откуда
`scheduler.py` мог бы его прочитать (новый канал состояния), либо смены
контракта `harness-<N>` на непостоянный — решение владельца, вне рамок
инцидента, который этот change закрывает (воркер не должен стоять, пока это
решается).
