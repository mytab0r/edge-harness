# Испорченная холодная загрузка сессии harness-<N> не бричит воркер/руки

Задача: #809.

Design: [design.md](design.md).

## Summary

Живой инцидент (2026-09-10): предохранитель диспатча (#847/#205) стоял на
паузе 4+ часа — три прогона подряд `worker.yml` падали на шаге «Задача через
DSH headless» с `exit 1`, ни разу не дойдя до вызова провайдера. Причина —
`dsh_edge_session_begin` (`scripts/lib/dsh-edge-session.sh`) пытался
переиспользовать УЖЕ СОХРАНЁННУЮ сессию `harness-<N>`, испорченную ДО фикса
#794 (событие без полной формы `assertMessageEventShape`), и морда громко
отклоняла холодную загрузку. Класс уже описан в #809 (живые пострадавшие —
`harness-257/258/215/710`); этот прогон нашёл ещё двух — `harness-716`
(run 34455120330) и `harness-140` (run 34441499974). Дело не в провайдерах
(`ai-review.yml` на той же цепочке проходит) — падение происходит ДО первого
вызова `dsh`, на шаге создания сессии в морде.

## Problem / Motivation

- `dsh_edge_session_begin` не переживает отказ `session.create` на
  переиспользовании — падает единственным вызовом, без ретрая под другим id.
- Прод-форма отказа (дословно из логов): `Морда отклонила internal: stored
  session "harness-716" failed validation: Error: session event at seq 13
  lacks an identified message` — обёртка морды ВСЕГДА несёт `failed
  validation` независимо от конкретной внутренней причины (нет `id` ИЛИ
  невалидный `source`, design.md `session-note-identified-message`,
  «Развилка 1»).
- Ни один из трёх писателей (`task.sh`, `dsh_task.sh`) не отличает эту
  ошибку от временного сбоя сети/морды — оба падают одинаково, задача
  остаётся ЗАБЛОКИРОВАННОЙ (аренда взята до этого шага, `exit 1` не снимает
  её) до 24-часового TTL-сборщика оркестратора, вымывая свободные задачи
  из пула и держа предохранитель диспатча на паузе.
- Прямая правка сохранённого `session.jsonl.zstd` в хранилище DO — вне
  рамок агента (design.md `session-note-identified-message`, «Восстановление
  испорченных сессий»): нет доступа к хранилищу, только к API морды.

## Scope

### In

- `scripts/lib/dsh-edge-session.sh::dsh_edge_session_begin` — фоллбэк на
  ОДИН новый session_id (`<исходный>-r<GITHUB_RUN_ID>`), когда `session.create`
  на исходном id отказывает именно классом «холодная загрузка» (`failed
  validation` в тексте ошибки); возвращает РЕАЛЬНО использованный id через
  stdout. Любая другая причина отказа (сеть/деплой морды, не настроено) —
  без фоллбэка, честный провал, как раньше.
- `scripts/worker/task.sh`, `scripts/hands/dsh_task.sh` — читают возврат
  `dsh_edge_session_begin`, не подставляют исходный `HARNESS_SID` вручную
  (класс, который раньше терял фоллбэк-id через `>/dev/null`).
- Смоук-сценарий `scripts/lib/test/dsh-clients.smoke.sh` (прод-форма ошибки
  дословно из инцидента), доказанный мутацией.

### Out

- Восстановление/архивация уже испорченных `harness-257/258/215/710/716/140`
  как разовое действие (комментарий/закрытие задач по месту) — не код,
  не эта дельта-спека.
- Вариант (A) морда сама дропает битую сессию на сервере — требует патча
  `dsh-edge/patches/**` и отдельного деплоя, решение и обоснование — design.md.
- Вариант (C) миграционный проход по хранилищу DO — нет доступа снаружи API.
- Пересинхронизация `scheduler.py::append_session_notes`/
  `workspace.archiveSession` на фактически использованный (фоллбэк) id —
  оркестратор по-прежнему адресует `harness-<N>` буквально; отказ ingest/
  архивации туда уже был не фатален ДО этого change (design.md
  `session-note-identified-message`, «Развилка 4») — тем же путём остаётся
  и после.

## Acceptance criteria

- Смоук воспроизводит прод-форму отказа (`failed validation`) на КОНКРЕТНОМ
  session_id — воркер доводит задачу до DSH/PR, `session.create` вызван
  дважды (отказ исходного id + успех фоллбэка).
- Мутация (откат фикса) красит смоук — доказано живым прогоном, не только
  прозой.
- Сетевой отказ морды (без `failed validation` в тексте) НЕ запускает
  фоллбэк — тот же честный провал, что и раньше (не маскирует настоящую
  недоступность морды бесконечным созданием новых сессий).
- Живой прогон `worker.yml` на одной из уже испорченных задач проходит шаг
  «Задача через DSH headless» дальше создания сессии.
