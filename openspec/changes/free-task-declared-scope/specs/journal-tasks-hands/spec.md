26. Пульс оркестратора: если в пуле есть свободная задача (метка `task`,
    открыта, `issue.assignees` пуст — единственный критерий свободы, открытый
    PR на задачу сам по себе её из пула не исключает, `scripts/lib/free_task.py`)
    и нет worker-рана в статусе `in_progress`/`queued` — ровно один
    `workflow_dispatch` `worker.yml` за запуск. Сбой диспатча не роняет
    планировщик: слияния важнее подряда воркеру.

Сценарий: задачу без исполнителя, у которой уже открыт PR, оркестратор
(`scheduler.py::unhealthy_pulls`) вернул в пул, сняв исполнителя с нездорового
PR — старый скан `jq 'scan("#[0-9]+")'` по всему телу открытых PR держал её
занятой навсегда (любое упоминание номера в прозе любого PR считалось
занятостью, класс #187/#195); свобода задачи теперь не зависит от факта
существования PR вовсе.

27. Свободных задач нет → job воркера зелёный без действий: «делать нечего» —
    не ошибка, а штатный простой конвейера.

28. Захват задачи воркером — назначение, подтверждённое фактом на задаче (не
    кодом возврата шага). Два режима, по наличию декларирующего PR
    (`scripts/lib/task_ref.py::declared_tasks` — строка тела, начинающаяся
    с `#N`, обычно первая; то же правило, что использует `contract_check.py`, применённое
    симметрично к своему и чужому PR):
    - декларирующего PR нет — новая ветка `agent/N-slug` от свежего origin/main
      (вход — `scripts/git/task-branch`);
    - есть открытый PR без исполнителя, декларирующий задачу, — доводка: чекаут
      существующей ветки (`git fetch` + `git checkout -B <ветка> origin/<ветка>`)
      с той же гвардией свежести базы, что ставит `task-branch`
      (`git config core.hooksPath .githooks`), второй PR агенту открывать
      запрещено промптом.

    Исполняет задачу в обоих режимах DSH headless; транспорт
    (`scripts/worker/task.sh`) не принимает за агента содержательных решений.

Сценарий: `scheduler.py::unhealthy_pulls` пишет в комментарий «доработай
существующий PR, не переделывай с нуля» и снимает исполнителя — до этой
дельты задача становилась свободна в пуле, но невыбираема: `free_task()`
исключал из пула любую задачу с открытым PR, а явный вход `--task` отказывал
«уже есть открытый PR — доводить его» и ничего не делал. Теперь тот же
сценарий доходит до фактической доводки.

Инварианты, не меняющиеся этой дельтой: два прогона `worker.yml` над одной
задачей одновременно исключены workflow-уровневым `concurrency: group: worker`
(`.github/workflows/worker.yml:27-29`, действует с MVP #91) — очередной
триггер встаёт в очередь, а не гонится за уже назначенной задачей. Атомарная
аренда МЕЖДУ каналами (worker/manual/hands) на ту же задачу-с-PR (например,
воркер и `hands` одновременно решают довести один и тот же PR) закрыта
отдельной, параллельно слитой задачей #121 (`scripts/lib/claim_task.py::claim`,
git-ref-замок `refs/locks/task-N`, атомарность которого даёт сам GitHub):
эта дельта на неё опирается (`free_task()` дополнительно фильтрует пул по
`lease_cli locks`), но не реализует её сама.

29. Итог запуска воркера оценивается по видимому артефакту, а не по коду
    возврата: открытый PR → комментарий в задачу (ссылка + хвост отчёта) и
    Telegram, job зелёный; эскалация по playbook (метка `blocked` — то, что
    есть только у владельца) → комментарий и Telegram, job зелёный; иначе →
    комментарий с хвостом лога и Telegram, job красный. Все наружные тексты
    проходят маскирование секретов до отправки.
