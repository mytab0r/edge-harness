# Дельта-спека: журнал (journal-tasks-hands) — WIP-гейт не врёт про «доработки нет»

Опирается на существующие пп. 15-18 («Конвейер (оркестратор)») и пп. 26-29
(«Автономный воркер (конвейер пула)») — за реализацией см. `scheduler.py`,
`pulse_guard.py`, `scripts/lib/claim_task.py`, `repo_invariants.py`
(issue #948, #951).

## ADDED: Пагинация GitHub API — не-list ответ не молчит короткой страницей

Требование: любой обход страниц GitHub REST API через
`review_labels.list_pages` обязан отличать честную пустую/короткую
страницу (`chunk == []`) от ответа, форма которого не соответствует
ожидаемому списку (dict, `None`, тело вторичного рейт-лимита) — второй
случай поднимает `RuntimeError`, а не трактуется как «страниц больше нет».
Причина: не-list ответ, тихо принятый за пустую страницу, даёт вызывающему
коду искажённый снимок (например, `scheduler.open_pulls`), который
транзитом доходит до решений вроде WIP-гейта (см. следующий раздел).

Требование: все обходы страниц GitHub REST API в репозитории идут через
`list_pages` — второй копии этого цикла быть не должно. Гвардия —
`scripts/lib/test_silent_empty_page_guard.py` (AST-разбор синтаксического
узора цикла пагинации, не текстовый grep — не путает докстринги/комментарии
с живым кодом). Гвардия несёт allowlist известных, ещё не переведённых
инстансов с явно названной причиной отсрочки для каждого — пустой allowlist
означает, что класс закрыт полностью.

## ADDED: Инвариант — WIP-гейт не объявляет ложный ноль

Требование: `repo_invariants.check_wip_gate_false_zero` (инвариант 16,
наблюдательный, не в `CI_GATING`) сверяет последний маркер WIP-гейта
(`scheduler.WIP_GATE_OPEN_MARKER`/`WIP_GATE_CLOSE_MARKER`, комментарии
watchdog-задачи #120) с независимым пересчётом `scheduler.pr_needs_rework`
по свежему снимку открытых PR того же прогона. Маркер старше
`WIP_GATE_FALSE_ZERO_WINDOW_MINUTES` не сравнивается — сравнение с
устаревшим числом было бы гаданием (AGENTS.md, «алерт не гадает»).

Требование: находка регистрируется в ДВУХ случаях (не только в одном):
(а) переворот решения допуска — маркер и пересчёт расходятся в том,
закрывает ли число гейт (`число >= WIP_LIMIT`); (б) буквальный «ложный
ноль» — маркер объявил `claimed == 0`, а пересчёт нашёл `actual > 0`, даже
если оба числа ниже лимита и решение допуска формально совпадает (гейт
остаётся открыт в обоих случаях). Оба числа — факты одного и того же
прогона (маркер + independent пересчёт), не гипотезы.

Требование: ОБА потребителя WIP-маркеров — `scheduler.wip_gate`
(episode-бухгалтерия гейта) и `repo_invariants.fetch_wip_gate_markers`
(инвариант выше) — читают маркеры только от доверенного источника
`pulse_guard.EVENT_ACTOR_LOGIN` (`github-actions[bot]`): опциональный
`trusted_login` в `issue_marker_times`/`issue_markers_any` (#1027, живой
случай watchdog-issue #120 2026-09-12 — комментарий той же формы под
личным PAT с `SCHEDULER_ALLOW_PROD_WRITES=1` читался как официальное
состояние гейта и дал ложный ноль). Различение по токену (job vs личный
PAT), не по «человек/агент»; остальные потребители маркеров не меняются
(дефолт `trusted_login=None`).

## ADDED: Гейт прод-записи `prod_writes_allowed` закрывает два транспорта в обход

Опирается на существующий гейт `pulse_guard.prod_writes_allowed()`
(запись разрешена только в GitHub Actions либо при явном
`SCHEDULER_ALLOW_PROD_WRITES=1`), введённый раньше этого change.

Требование: `scripts/lib/claim_task.py` — общий модуль, которым пользуются
каналы, для которых запись ВНЕ CI штатна (worker `task.sh`, hands
`dsh_task.sh`, ручной `task-branch`), поэтому `claim_task.gh()` не гейтит
себя безусловно. Вместо этого модуль несёт module-level хук
`set_write_guard(predicate)`; `scheduler.py` — единственный канал, кому
нужно решение «писать только в CI» — подключает к нему СВОЙ уже
существующий предикат (`_guard_raw_subprocess_write` →
`prod_writes_allowed`) один раз при загрузке модуля. Второй копии решения
«писать можно только в CI» в `claim_task.py` заводить нельзя.

Требование: `scripts/orchestra/upstream_drift.py::attempt_auto_bump`
(сырой `git push`/`scripts/git/pr-create` в обход `gh()`) читает тот же
`pulse_guard.prod_writes_allowed()` до похода в сеть и при отказе
возвращает честную строку «авто-бамп пропущен: DRY-RUN» — по образцу уже
существующего выхода «ORCHESTRA_PAT не задан», не даёт вызывающему коду
получить `None`/исключение оттуда, где ожидается число (номер PR).

## ADDED: Отказ гейта прод-записи наблюдаем, не маскируется под успех

Требование: `claim_task.gh()` и `pulse_guard.gh()` при срабатывании гейта
(запись вне CI без явного разрешения) поднимают `WriteGateSkipped`
(наследник `RuntimeError`, отдельный класс в каждом модуле — конвенция
репозитория «каждый скрипт — самостоятельная точка входа без пакетной
системы»), а не молча возвращают `None`. `WriteGateSkipped` обязан быть
отличим от `GhError`/обычного `RuntimeError` сетевого сбоя: вызывающий код
не имеет права смешивать «операция не была предпринята» с «операция
провалилась на сервере» — это разные факты, оба требуют разного текста в
отчёте (AGENTS.md, «Fail loud, не silent-wrong»).

Требование: `claim_task.release`/`release_full`/`collect_stale` и
`pulse_guard.escalate` (через `post_issue_comment`) ловят `WriteGateSkipped`
отдельно от прочих ошибок и формируют отчёт со словом «пропущено (DRY-RUN)»
— не «снят»/«снято»/«оставлен». Живой сценарий, который это закрывает:
локальный прогон `scheduler.py` вне CI без `SCHEDULER_ALLOW_PROD_WRITES=1`
печатает «DRY-RUN, изменяющие вызовы пропускаются», но отчёт о конкретном
действии (замок, назначение, комментарий-эскалация) обязан говорить то же
самое про КАЖДУЮ операцию, не только про режим целиком.

## ADDED: Адресный диспатч доводки по находкам ai-review

Опирается на существующий `dispatch_conflict_rework` (issue #474) — тот же
контур, другой триггер.

Требование: PR с меткой `ai:changes-requested` (и без метки `conflict` —
таким уже занимается `dispatch_conflict_rework`) с распознаваемой задачей
по ветке (`agent/N-slug`) — кандидат на адресный `worker.yml`-диспатч на
доводку. Диспатч снимает assignee и замок задачи (через `claim_task`,
гейтится `prod_writes_allowed` тем же путём, что и остальная запись
планировщика) и запускает `worker.yml` с `input[task]=N` — тот же промпт
режима доводки (task.sh, #245), что уже используют conflict/красный чек.

Требование: бюджет — `AI_REWORK_MAX_ATTEMPTS` попыток НА ОТПЕЧАТОК диффа
(`review_labels.diff_fingerprint`), не лайфтайм PR: изменившийся отпечаток
— новая, ещё не пробованная задача. Дедуп «тот же head, тот же отпечаток»
— маркер в комментариях PR не даёт второй диспатч за тот же пульс/
следующие пульсы на неизменном отпечатке, пока бюджет не исчерпан.

Требование: исчерпание бюджета на текущем отпечатке различает ТРИ исхода,
не один (#1027, живой случай PR #1020): (1) последний прогон worker.yml по
этой задаче сам завершился с conclusion из `pulse_guard.FAILURE_CONCLUSIONS`
(инфраструктурный отказ прогона — rc≠0/нет ответившего провайдера/нет
новых коммитов, тот же факт, по которому
`scripts/lib/dsh-ci.sh::dsh_worker_run_is_success` решает на стороне
воркера) — попытка не была честной пробой находок ai-review, в бюджет
эскалации не засчитывается: диспатч повторяется автоматически БЕЗ
эскалации (устойчивый инфра-отказ — квота/окружение — останавливается
ОБЩИМ предохранителем `conveyor_gate`, второй тормоз не заводится);
(2) прогон отработал (conclusion=='success') или
атрибуции нет вовсе — законная эскалация владельцу тем же каналом (#120),
что и предохранитель конвейера — не диспетчит второй раз вслепую; текст
эскалации называет факты как есть, не подменяя их гипотезой («алерт не
гадает», #472): на пути success-эскалации отпечаток диффа не изменился
(сменившийся отпечаток дал бы чистый бюджет), поэтому повторный прогон
ai-review на нём не выполнялся (keep-path) — стоят находки прежнего ревью
того же диффа; атрибутированный conclusion вне success и известных
инфра-отказов (timed_out, startup_failure) называется как есть, не
подменяясь гипотезой про атрибуцию; (3) PR уже закрыт/слит
между снимком `pulls` и перепроверкой — эскалация не нужна вовсе (это не
провал, предмет исчез сам). Перед решением — перепроверка, что метка
`ai:changes-requested` всё ещё стоит и PR ещё открыт (могли смениться
между снимком и эскалацией) — ложная эскалация на уже одобренный/закрытый
PR не допускается.

Требование: идемпотентность — `worker_runs_active`, тот же гейт, что у
`dispatch_conflict_rework`/`dispatch_worker`: воркер один на репозиторий,
пока прошлый прогон жив. Диспатч этого механизма исключает диспатч
`dispatch_worker` в том же проходе планировщика (сигнал — третий элемент
кортежа возврата).
