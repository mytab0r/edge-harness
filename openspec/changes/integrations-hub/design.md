# Design: integrations-hub (#115)

## Сейф-стекло: против отвергнутых вариантов

- **30-rejected п.6 (агент-цикл в DO, 10 ms CPU).** Инструменты делают один
  REST-вызов каждый: I/O-ожидание в CPU-лимит не засчитывается, парсинга
  стрима нет. Тяжёлая работа — по-прежнему `runner_task` на раннер.
- **30-rejected п.5 / плагины в рантайме.** Никакой динамической загрузки:
  плагин едет манифестом `dsh-edge/plugins.json` по конвейеру #80 (релиз +
  sha256 → PR → source-build деплой), состав доказывают дым инсталла,
  гвардия состава и verify-edge-plugins без изменений.
- **MCP-серверы Atlassian/Slack** — отвергнуты, причина и условие возврата в
  [ADR 0010](../../../docs/decisions/0010-integrations-edge-plugin-rest-tools.md).
- **Ограничение владельца (морда = DSH, UI = клиентский плагин).** Соблюдено
  буквально: секция — слот `settings.section` (id `integrations`, order 94,
  рядом с plugin-manager'овскими 95), модули — seed-карта шелла +
  `dsh.client.inject`, никаких отдельных страниц.

## Один пакет, две половины

`server: true, client: true` в манифесте — как hello-world (#80): сервер и
клиент одной темы живут в одном релизе, одной записи манифеста и одном
sha256. Разделение halves по прецедентам сохраняется: сервер —
`server/index.js` + чистая логика `server/core.js` (без импортов — та же
функция тестируется в голом Node), клиент — `src/body.js` + генерируемый
`build.mjs` бандл с вшитым реестром.

## Реестр как единое место правды

`dsh-edge/integrations.json` (форма — `dsh-edge/integrations.mjs`, по образцу
`manifest.mjs`): id, title, summary, tools, credentials.secrets (ИМЯ →
описание «чей ключ»), wired (`morde`/`jobs`), docs. Читатели:

- **build.mjs плагина** — вшивает реестр в бандл и сверяет инструменты
  реестра с `defineTool`-именами серверной половины в ОБЕ стороны (тихий
  минус тулов или тихий минус описания невозможны);
- **deploy-dsh-edge.yml** — синк секретов (`wrangler secret put` для
  morde-интеграций) и снимок наличия для статусов;
- **repo-ci.yml и деплой** — CLI = валидация формы + гвардия проводки
  (каждый секрет реестра упомянут в workflow'е своей проводки).

## Креды и маскирование

Путь значения секрета: репозиторий (GitHub secrets) → env шага деплоя (явные
`${{ secrets.NAME }}` — GitHub не умеет перечислять секреты динамически,
поэтому гвардия проводки и нужна) → `wrangler secret put` → `process.env`
воркера → заголовок запроса. Значение никогда не попадает в: логи job'а
(put печатает только имя), вывод инструмента (каждый текст проходит
`scrub()` со списком масок: значение, его base64-форма и фактическое
значение Basic-заголовка — `base64("user:секрет")` из той же пары, что и
`Authorization`; склейка base64 частей производной не является), ошибки API
(только HTTP-статус + сообщение провайдера, скраб).

Отсутствующий секрет — не красный деплой, а честный `integration_status` =
`not_configured` с именами: «возможности нет» отличается от «сломана», и та
и другая видны в журнале и в разделе UI.

## Статусы: контракт

Псевдо-задача `integration:<id>`, kind `integration_status`, data
`{integration, state, detail?}`; состояния `ready` / `not_configured` /
`failed` + промежуточные `building|built|deploying` (наследуются от
plugin-канала на будущее). Транспорт — общий с `plugin_status.sh`
(`scripts/lib/journal_status.sh`: посев seq с сервера, ретраи, fail-loud
градация финальных статусов). Дельта-спека —
[specs/journal-tasks-hands](specs/journal-tasks-hands/spec.md).

## Почему один инструмент — один REST-вызов

Инструменты агента морды исполняются в DO (архитектура dsh-edge). Критерий
「не тащить исполнение интеграций в DO」 читается по ADR 0002/30-rejected п.6
как запрет на ЦИКЛЫ и CPU-тяжёлую работу, а не на I/O: runner-bridge уже
делает fetch'и из того же места и принят владельцем. Сценарий эпика поэтому
собирается так: чтение Jira (тул) → работа (раннер, runner_task) →
`bitbucket_pr` (тул) → `slack_post` (тул).
