## 1. Требование A — почему «время с последнего слияния», а не сумма локальных таймеров

### 1.1 Отвергнутый вариант: чинить wip_gate/conveyor_gate так, чтобы часы не сбрасывались

Разбирался первым, потому что дешевле нового механизма. Отклонён: сброс
счётчика wip_gate при передаче тормоза предохранителю — НЕ баг, а сознательное
решение против гадания между причинами (находка ревью PR #466, docstring
wip_gate:2335-2343 — иначе через 8ч сигнал говорил бы «доводка не успевает»,
хотя доводки не было вовсе, потому что дело было в предохранителе). Убрать
сброс значило бы вернуть именно ту путаницу причин, которую #466 закрыл. Два таймера ПРАВИЛЬНО не суммируются друг в друга — им нужен третий, независимый
источник истины, который не спрашивает «кто виноват», а считает факт.

### 1.2 Источник данных — переиспользование, не новый запрос

scheduler.py::all_merged_pulls(repo) уже вызывается в main() (строка 4164)
для стадии приёмки — до 500 последних закрытых PR за 1-5 REST-страниц.
drain_gate берёт max(merged_at) по этому же списку (после фильтра merged_at
непуст, что all_merged_pulls уже делает) — ноль новых сетевых вызовов.
Единственный риск: если реально слитых PR больше 500 за интересующее окно
(на сегодняшнем темпе ~1.6-1.8 PR/час, #464 — недостижимо на горизонте
часов/суток, достижимо только если QUALITY темпа вырастет на порядок; не
подтверждено на будущее, честно называется).

### 1.3 Почему не GitHub Search API (`is:pr is:merged`)

Дал бы то же число одним запросом без нужды тащить all_merged_pulls целиком,
но: (а) health_regression.py уже использует Search API для суточного среза
merge_throughput — второй независимый вызов Search на каждый 15-минутный
пульс добавил бы новую точку отказа и новый неизученный лимит (Search API
имеет отдельный, не изученный в этом репозитории rate limit — «не
подтверждено», design.md pipeline-health-self-audit это тоже не проверял);
(б) all_merged_pulls уже в памяти этого же прогона — использовать его дешевле
и не требует нового сетевого контракта.

### 1.4 Причины — перечисление фактов, не выбор гипотезы

drain_gate вызывается ПОСЛЕ conveyor_gate/wip_gate/mark_conflicts в main()
(порядок важен: причины должны быть уже посчитаны этим же прогоном) и читает
их булевы результаты плюс count конфликтных PR с исчерпанным бюджетом
(conflict_rework_attempts >= CONFLICT_REWORK_MAX_ATTEMPTS) плюс наличие
contract:failed среди open_pulls. Текст алерта — список ИСТИННЫХ строк, не
if/elif-цепочка выбора одной (тот же приём, что decide_gate_state уже
возвращает несколько исходов из одного набора чисел без гадания, ссылка на
этот же приём в design.md pipeline-health-self-audit §3.2).

### 1.5 Норма против тревоги

«Открытых PR к слиянию нет» (`pulls` без единого кандидата к merge_queue) —
явная отдельная ветка возврата, не молчаливое «часов с последнего слияния
много, но никто не смотрел» — копия честного разбора issue #194
(«готовых PR нет» — не тревога).

## 2. Требование B — автоматический диспетч pm

### 2.1 Условие запуска

drain_gate держит тревогу дольше PM_DISPATCH_AFTER_HOURS ИЛИ wip_gate держит
свой эпизод дольше WIP_GATE_STUCK_HOURS (уже готовое условие — переиспользуется
маркер WIP_GATE_STUCK_MARKER_PREFIX, второе место правды не заводится). Оба
случая означают одно и то же по существу: беклог, а не приток, требует разбора,
которым занимается pm, а не воркер (воркер пишет код, pm классифицирует).

### 2.2 Развилка: отдельный workflow против переиспользования dispatch_conflict_rework

Не решено окончательно в этом design — две жизнеспособных формы:

- (A) Новый job, аналогичный worker.yml/hands.yml. Изолирует дорогой
  LLM-вызов pm от orchestra.yml (тот же принцип разделения, что уже применён
  к ai-review.yml — «дорогой прогон» не в общем пульсе). Требует: отдельный
  workflow-файл, свой repository_dispatch event_type, доступ к тем же
  инструментам (gh CLI) под тем же PAT, что уже использует worker.
- (B) Расширение scheduler.dispatch_conflict_rework-подобного паттерна
  (снимает assignee+замок задачи, запускает worker.yml адресно на конкретный
  вход) — но pm НЕ работает над задачей пула, а над PR-беклогом целиком, так
  что аналогия неполная: нет одной задачи-цели, есть весь открытый список.
  Ближе к отдельному workflow_dispatch с параметром mode=pm-groom.

Выбор между ними — предмет tasks.md, не решается здесь: критично для
proposal.md только то, что триггер (условие 2.1) один, независимо от формы
исполнения.

### 2.3 Границы автоматического pm — механические, не только словесные

pm.md уже объявляет границы словом промпта (не более 25 закрытий, не трогает
исполнителя/waiting:owner, требует улику в комментарии). Разница
автоматического диспетча от ручного вызова: у ручного вызова разбор
результата делает человек (успел заметить нарушение границы). У
автоматического — некому. Поэтому job-обвязка вокруг pm-прогона считает
ФАКТ (число реально сделанных gh issue close/gh pr close за этот прогон, не
то, что модель сказала о себе) и красит шаг, если факт превышает лимит —
тот же класс решения, что уже применён к check_ai_failed_budget_exhausted/
AI_REVIEW_MAX_ATTEMPTS: бюджет считается по внешнему следу (комментариям),
не по декларации агента.

## 3. Требование C — карантин задачи-отравы

### 3.1 Данные уже есть, атрибуции не хватает

check_recurring_worker_failure (инвариант 10) уже строит отпечаток причины
падения (pulse_guard.last_error_log_line) по N подряд прогонам worker.yml.
Недостающая часть — связать конкретный прогон с конкретным НОМЕРОМ задачи:
воркер печатает «Аренда взята: замок refs/locks/task-N» (см. #794, task.sh)
в лог каждого прогона до старта работы — тот же лог, что уже читает
pulse_guard.last_error_log_line для причины отказа, читается ещё раз для
номера задачи (тот же прогон логов, один проход, не два обхода API).

### 3.2 Полуоткрытое состояние на уровне задачи — по образцу #205, не копия

QUARANTINE_AFTER подряд фатальных падений С ОДНИМ И ТЕМ ЖЕ номером задачи
(не просто с одной причиной — #257/#215/#710/#716/#140 несли РАЗНЫЕ номера
задач при ОДНОЙ причине порчи; карантин здесь про КОНКРЕТНУЮ задачу, не про
класс причины — тот вопрос уже решает check_recurring_worker_failure/
conveyor_gate) переводит задачу в состояние «карантин»: free_task.py
исключает её из oldest_free/free_candidates до пробного возврата. Пробный
возврат — тот же паттерн backoff, что PROBE_BACKOFF_BASE_MINUTES/
PROBE_BACKOFF_MAX_MINUTES у conveyor_gate (переиспользование ФОРМЫ решения,
не общей переменной — у задачи-карантина СВОЙ маркер и своя выдержка,
привязанная к номеру задачи, а не к воркеру в целом).

### 3.3 Отличие от blocked

blocked — ручная, осознанная эскалация с исполнителем (владелец решает).
Карантин — автоматический, временный, обратимый БЕЗ участия человека: если
следующая проба (после выдержки) успешна — карантин снимается сам, задача
снова обычная свободная. Если фатальна снова — выдержка растёт. Только если
карантин продлевается неограниченно (эмпирический потолок — предмет
отдельного порога, не спроектирован здесь) — это сигнал ЭСКАЛИРОВАТЬ, а не
вечно пробовать: газ есть, но и у газа есть потолок, который назван, не
бесконечен.

## 4. Инвариант — независимая проверка «дренаж стоял, а сигнала нет»

repo_invariants.py исторически НЕ доверяет внутреннему состоянию
scheduler.py — пересчитывает независимо из ТРЁХ источников: список слитых PR
(тот же REST-вызов, что all_merged_pulls, но отдельный обход — здесь НЕ
доверяем состоянию scheduler.py на случай, если сам drain_gate упал с
необработанным исключением до публикации маркера), комментарии
WATCHDOG_ISSUE за окно, и ТРЕТИЙ, независимый — открытые PR-кандидаты к
merge_queue (`fetch_open_pulls`, уже читается build_report для других
инвариантов; кандидат — не черновик и не бот, та же дешёвая локальная
проверка, что merge_queue_candidates применяет для нормы drain_gate в §1.5,
переиспользуется, не дублируется отдельным определением). Если «часов с
последнего слияния» превышает DRAIN_STALL_HOURS, СРЕДИ ОТКРЫТЫХ PR ЕСТЬ ХОТЯ
БЫ ОДИН КАНДИДАТ (та же ветка нормы, что уже держит drain_gate в §1.5 — без
неё инвариант красил бы здоровый простой «нечего сливать», который сам же
Требование A объявляет нормой, а не тревогой), а среди комментариев
WATCHDOG_ISSUE за это же окно нет ни одного маркера drain_gate — нарушение.
Кандидатов нет — инвариант зелёный независимо от возраста последнего
слияния, тем же самым решением, каким drain_gate сам не тревожит (находка
ревью PR #870: без этой ветки нормальный простой «беклог вычерпан» дал бы
систематические ложные срабатывания на КАЖДОМ пульсе и КАЖДОМ PR). Наблюдательный
на старте (тот же порядок включения, что у инвариантов 8/9/10 — CI_GATING
только после замера на живом репозитории, нулевых или объяснённых нарушений).

## 5. Честная граница: машина против суждения

### 5.1 Машинно-безопасно (объявляет ТОЛЬКО факт, не оценку по существу)

- Композитный подсчёт часов с последнего слияния (арифметика над уже
  прочитанными данными, не суждение).
- Перечисление истинных в этом прогоне причин (булевы флаги уже посчитаны
  другими функциями этого же пульса — drain_gate не пересчитывает и не
  интерпретирует их заново).
- Условие запуска pm (2.1) — оба порога уже посчитаны существующим кодом.
- Механический потолок закрытий pm-прогона (2.3) — считает факт вызовов gh,
  не оценивает их правильность.
- Карантин по количеству подряд фатальных падений с одним номером задачи
  (3.2) — детерминированный счётчик, как и у conveyor_gate.
- Автоматическое снятие карантина по успешной пробе — тот же критерий, что
  уже применяет #205 для предохранителя в целом.

### 5.2 Суждение (pm-агент как заменитель человека для дешёвых случаев, владелец — для дорогих)

- Закрытие PR/задачи как «дубликат уже слитого в другом месте» — это
  суждение о СОДЕРЖАНИИ (не номере), делает pm-агент (LLM) с обязательной
  уликой в комментарии, никогда — детерминированный код без LLM. Тот же
  вывод, что design.md pipeline-health-self-audit §4.2 уже сделал для
  «мёртвого кода» — намерение автора не выводится метрикой.
- Admin-merge / принудительное слияние чужого PR — необратимое действие с
  обходом гейтов, остаётся ЗА ВЛАДЕЛЬЦЕМ. pm-диспетч этого не делает никогда,
  даже в рамках объявленных границ — граница pm.md («не чинить найденные
  дефекты, не заводить новые задачи») уже исключает это, design явно
  подтверждает: список действий pm — closes только, never merges.
- Повышение/снижение порогов (DRAIN_STALL_HOURS, QUARANTINE_AFTER и т.д.)
  при первых неделях эксплуатации — ручное решение владельца по факту
  наблюдаемых ложных тревог/пропусков, тот же класс, что design.md
  pipeline-health-self-audit §4.3 уже называет для BASELINE_WINDOW_DAYS и
  соседей.
- Окончательное решение «карантин снять раньше срока» или «эскалировать
  вместо новой пробы» при подозрении, что причина не механическая (не
  задача, а инфраструктура) — суждение, не автоматизируется этим design.

## Не подтверждено

1. Пороговые числа (DRAIN_STALL_HOURS, PM_DISPATCH_AFTER_HOURS,
   QUARANTINE_AFTER, PM_MAX_CLOSURES_PER_RUN, backoff-параметры карантина) —
   не выведены из данных этого репозитория, см. proposal.md «Risks/unknowns».
2. Перенос промпта/инструментов pm.md в CI-контекст без доработки — не
   проверено, что Read/Grep/Glob/Bash из формата подагента переносятся в
   workflow-job без адаптации (другой рантайм вызова агента).
3. Верхний потолок продлений карантина (когда автоматическая проба
   прекращается и уходит эскалация) — не спроектирован числом, только
   принцип (§3.3 выше).
4. Достижимость 500-PR предела all_merged_pulls на горизонте роста темпа
   слияний — экстраполяция с текущего темпа (~1.6-1.8 PR/час, #464), не
   измерено на будущее.
