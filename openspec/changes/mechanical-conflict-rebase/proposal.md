# mechanical-conflict-rebase: дешёвый механический git rebase для конфликтных PR (#762)

Задача: #762. Дизайн (выбор параллельности): [design.md](design.md). Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`dispatch_conflict_rework` (scheduler.py, issue #474) расшивает PR с меткой `conflict`
единственным путём — через LLM-агента `worker.yml`, хотя её собственный докстринг
дословно говорит: «PR с меткой conflict почти всегда просто отстал от main… git rebase
origin/main решает это без содержательного решения». Живой замер 2026-09-08: 25
конфликтных PR из 38 открытых, ни один не сливается. При «воркер один на репозиторий,
ровно один `workflow_dispatch` за пульс» это 25 отдельных агентских проходов — 25
запусков LLM ради операции, которая моделью не нуждается вовсе, притом что квота
дефицитного провайдера (GLM исчерпан до 2026-09-10, NVIDIA отвечает примерно в половине
попыток) и есть сегодня узкое место конвейера.

## Что делается

Новый модуль `scripts/orchestra/mechanical_rebase.py` — работает НАД РЕАЛЬНЫМ git-деревом
(в отличие от scheduler.py, который принципиально не заводит локальный git-клон, см.
`openspec/changes/conflict-auto-rebase/proposal.md`, «Что вне рамок» — этот модуль
осознанное исключение, живёт отдельно):

- берёт ВСЕ PR с меткой `conflict` за один проход (новый workflow
  `.github/workflows/conflict-mechanical-rebase.yml`, свой файл — не job внутри
  `orchestra.yml`, причина — design.md, «Развилка 2»: изоляция от `heartbeat_check`),
  пытается `git rebase origin/main` по каждому — БЕЗ модели, без LLM-агента;
- обход — от старейшего эпизода конфликта к новейшему (переиспользован
  `scheduler.conflict_labeled_at`, issue #588 — вторая сортировка не заводится);
- не двигает head, пока по PR летит `ai-review.yml` (переиспользован
  `review_labels.other_active_ai_review_runs` — тот же предикат, что уже использует
  `update_branch`, вторая копия не заводится);
- сошлось — пушит `--force-with-lease`; снятие метки `conflict` остаётся ЗА
  `mark_conflicts` (не заводим вторую точку записи одного факта — `mark_conflicts` уже
  умеет честно отличать «не знаю» от «не конфликт»);
- НЕ сошлось структурно (каталог `.git/rebase-merge`/`rebase-apply` — не текстовый матч
  сообщения git) — PR остаётся кандидатом агентского пути, этот модуль не трогает
  assignee/замок/dispatch: `dispatch_conflict_rework` (НЕ изменён) подхватывает его как
  раньше, теперь только для PR, которые механика не смогла свести;
- сбой НЕ через конфликт (сеть, права, ветка удалена, force-with-lease отклонён гонкой) —
  называется отдельной строкой («infra-error: …»), не путается с содержательным
  конфликтом (AGENTS.md, «fail loud»).

`CONFLICT_REWORK_MAX_ATTEMPTS = 1` (решение владельца, #474) не меняется — остаётся
бюджетом ИМЕННО агентского пути. Дешёвый механический путь своего бюджета попыток не
заводит: он не тратит агента вовсе, а перезапуск на следующем такте — no-op
(«Already up to date») для уже решённых PR и дешёвая повторная попытка для тех, что
остаются конфликтом (см. design.md о том, почему это не расточительно).

## Проверено

- `python -m pytest scripts/orchestra/test_mechanical_rebase.py -q` — 9 тестов,
  реальный git (временный bare-репозиторий, настоящий `git rebase`, не пересказ), FakeGh
  прод-формы для GitHub API.
- Мутация (issue #762, требование 5): `process_pull` возвращён к заглушке
  «всегда `conflict`» — 3 из 9 тестов краснеют (сценарий 5 PR/3 сходятся, отложенный
  ai-review, инфра-ошибка), включая основной сценарий задачи. Восстановление —
  снова 9/9 зелёных.
- `python -m pytest scripts/orchestra/test_scheduler.py -q` — не тронут (0 файлов
  scheduler.py изменено), 4 предсуществующих окружных сбоя (реальный `gh api`/кодировка
  Windows, воспроизводятся на немодифицированном main тем же образом) не связаны с этим
  change.

## Что вне рамок

- Свой бюджет попыток для механического пути — не заводится: путь дешёвый и
  идемпотентный, повторная попытка на следующем такте не тратит ничего дороже нескольких
  секунд git (см. design.md).
- Проактивное снятие метки `conflict` этим же модулем (не дожидаясь `mark_conflicts`) —
  рассмотрено и отклонено: завело бы вторую точку записи одного факта и гонку с
  асинхронным пересчётом `mergeable_state` на стороне GitHub (см. докстринг
  `mechanical_rebase.py`).
