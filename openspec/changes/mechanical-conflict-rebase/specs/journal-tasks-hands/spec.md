# Дельта-спека: журнал (journal-tasks-hands) — дешёвый механический ребейз конфликтных PR (#762)

Опирается на дельту `openspec/changes/conflict-auto-rebase/specs/journal-tasks-hands/
spec.md` («Автоматическая расшивка конфликтных PR», #474) — эта дельта добавляет ПЕРЕД
агентским путём новый, более дешёвый первый шаг; агентский путь (`dispatch_conflict_rework`)
не меняется, только сужается вход, который он видит (PR, которые механика не смогла
свести).

## ADDED: Механический ребейз конфликтных PR без агента

Требование: PR с меткой `conflict` (`mergeable_state=dirty`, обнаруживает
`mark_conflicts`) сначала проходит ДЕШЁВУЮ механическую попытку `git rebase
origin/main` — БЕЗ вызова LLM-агента `worker.yml`. Новый workflow
`.github/workflows/conflict-mechanical-rebase.yml` (СВОЙ файл, не job внутри
`orchestra.yml` — design.md, «Развилка 2»: изолирует `heartbeat_check` от
инфраструктурных сбоев этого шага; тот же триггер, что job `orchestra`: расписание раз
в 15 минут + `workflow_dispatch`) берёт ВСЕ PR с меткой `conflict` за один проход и
обрабатывает их последовательно в одном рабочем дереве (обоснование выбора
параллельности — design.md этого change, «Развилка 1»).

Требование: обход очереди конфликтных PR — от старейшего эпизода конфликта к новейшему
(`scheduler.conflict_labeled_at`, issue #588) — та же дисциплина, что уже применяет
`dispatch_conflict_rework`; переиспользуется, вторая сортировка не заводится.

Требование: перед попыткой сдвинуть head PR проверяется отсутствие активного прогона
`ai-review.yml` по этому же PR (`review_labels.other_active_ai_review_runs` —
переиспользован тот же предикат, что уже применяет `update_branch`, вторая копия не
заводится). Есть активный прогон — PR пропускается этим тактом («ai-review-running»),
без попытки рёбейза.

Требование (issue #764, находка ревью гейта): перед попыткой сдвинуть head PR
проверяется отсутствие активного прогона `worker.yml` ГДЕ УГОДНО в репозитории
(`sch.worker_runs_active` — тот же repo-wide предикат, что уже применяет сам
`dispatch_conflict_rework`, scheduler.py:778,855, вторая копия не заводится).
Обоснование гейта, включая почему repo-wide, а не per-task — design.md, раздел
«Гонка с агентским путём». Есть активный прогон — PR пропускается этим тактом
(«worker-running»), без попытки рёбейза: единственный воркер репозитория может в
этот момент пушить в любую конфликтную ветку, и незащищённый механический
force-with-lease мог бы затереть его коммиты и сжечь единственную засчитанную
попытку агентского пути (`CONFLICT_REWORK_MAX_ATTEMPTS = 1`) вхолостую.

Требование (issue #764, находка ревью гейта): PR из ЧУЖОГО репозитория (форк с
совпадающим именем ветки) или с веткой без префикса `agent/` (включая `main`) не
попадает в очередь этого модуля — фильтр `(pull["head"].get("repo") or {}).get(
"full_name") == repo and head_ref.startswith("agent/")` в `conflict_queue`. Без
фильтра метка `conflict` на PR из форка заставила бы ребейзить и
`--force-with-lease`-пушить ЧУЖУЮ ветку `origin`, приписывая исход номеру PR из
форка.

Требование: рёбейз сошёлся — ветка обновляется `git push --force-with-lease`. Снятие
метки `conflict` НЕ выполняется этим модулем напрямую — остаётся ИСКЛЮЧИТЕЛЬНО за
`mark_conflicts` (одна точка записи факта «конфликта больше нет», не заводится вторая:
`mark_conflicts` уже умеет корректно отличать подтверждённое неконфликтное состояние от
`None`/`unknown`). Известное следствие: между пушем этого модуля и следующим пересчётом
`mergeable_state` на стороне GitHub есть асинхронное окно — `mark_conflicts`, увидев ещё
не пересчитанный `dirty`, может на мгновение вернуть метку `conflict` и текст «PR
конфликтует с main»; следующий же такт механического пути увидит `git rebase` как no-op
(«Already up to date») и повторно (или без изменений) пройдёт тот же путь — поведение
самокорректируется, отдельного тормоза не заводится.

Требование: рёбейз СТРУКТУРНО уткнулся в конфликт — признак: после неудачного `git
rebase` существует каталог `.git/rebase-merge` или `.git/rebase-apply` И в индексе
есть НЕЗАВЕДЁННЫЕ пути (`git diff --name-only --diff-filter=U`) — оба структурных
признака самого git, не текстовый матч сообщения об ошибке (тот протухнет при смене
формулировки, тот же принцип, что `WORKER_GIT_STEP_MARKER`). Второй признак обязателен
(issue #764, находка ревью гейта, требование 1): каталог паузы рёбейза заводится ТАКЖЕ
тогда, когда патч применился без единого текстового конфликта, но `git commit` внутри
рёбейза упал по другой причине (живой пример — раннер без настроенной git identity,
`git rebase` падает с rc=128 «unable to auto-detect email address»); без проверки
незаведённых путей такой сбой ошибочно классифицировался бы как содержательный
конфликт. Рёбейз отменяется (`git rebase --abort`), PR НЕ трогается (assignee, замок
задачи, метка — без изменений) и остаётся кандидатом СУЩЕСТВУЮЩЕГО агентского пути
`dispatch_conflict_rework`, который подхватит его как раньше, без каких-либо изменений
в самом `dispatch_conflict_rework`.

Требование: сбой НЕ через структурный конфликт (сеть, права, ветка удалена на origin,
`git push --force-with-lease` отклонён гонкой с параллельной операцией, отсутствующая
git identity — см. выше) называется ОТДЕЛЬНОЙ строкой отчёта («infra-error: …»), не
путается со структурным конфликтом — разные причины лечатся по-разному (AGENTS.md,
«fail loud, не гадать»). Продакшн-окружение (`.github/workflows/
conflict-mechanical-rebase.yml`) обязано задавать git identity ДО первого рёбейза
(`git config --global user.name/user.email`, атрибуция боту — операция чисто
механическая, авторство исходных коммитов рёбейз сохраняет) — проверка «незаведённых
путей» выше остаётся сетью безопасности для случая, когда identity всё же не задана,
не заменяет эту настройку.

Требование (issue #764, находка ревью гейта, требование 5): рабочее дерево
принудительно возвращается в чистое состояние ПЕРЕД каждой попыткой рёбейза (см.
`ensure_clean_repo`) — если `git rebase --abort` предыдущей итерации сам упал (сеть,
файловая система), следующий PR очереди не должен унаследовать чужую паузу рёбейза
(«you need to resolve your current index first» вместо честного fetch/checkout).

Требование (issue #764, находка ревью гейта, требование 5): если ВСЕ PR очереди этого
прохода завершились `infra-error` (очередь не пуста), процесс завершается ненулевым
кодом — иначе `failure_watch` (наблюдатель `WATCHED_WORKFLOWS`) видит только упавший
ПРОЦЕСС, но не «прошёл и не обработал ни одного PR».

Требование: `CONFLICT_REWORK_MAX_ATTEMPTS = 1` (owner-решение, #474) не изменяется и
продолжает ограничивать ТОЛЬКО агентский путь. Механический путь своего бюджета попыток
не заводит — обоснование (путь не тратит модель, идемпотентен, повторная попытка
дешёвая) в design.md этого change; PR, уже механически резолвленный этим модулем,
естественным образом выпадает из очереди конфликтных PR на следующем такте (снята метка
`conflict` → не проходит фильтр `conflict_queue`), поэтому агентский бюджет им не
тратится вовсе.

Сценарий: PR #601 (ветка `agent/601-…`) получил метку `conflict`, main ушёл вперёд в
файле, которого ветка не касалась -> механический ребейз сходится, ветка обновляется
`--force-with-lease`; как только `mark_conflicts` следующего такта увидит
пересчитанный `mergeable_state` и снимет метку, PR #601 перестаёт быть кандидатом
`dispatch_conflict_rework` (агентский бюджет не расходуется). Дисциплина «этим же
тактом» НЕ гарантирована (найдено ревью, issue #764, требование 3; design.md, «Развилка
2», «Цена решения»): `orchestra.yml` (диспетчер, включая `dispatch_conflict_rework`) и
`conflict-mechanical-rebase.yml` — два независимых workflow-файла на одном
15-минутном кроне без взаимной `needs:` (такой механизм между файлами в GitHub Actions
не существует), поэтому `dispatch_conflict_rework` того же самого тика МОЖЕТ успеть
прочитать метку `conflict` раньше, чем GitHub пересчитал `mergeable_state` после
нашего пуша, — тогда агентский путь диспатчится один раз вхолостую (не вредно: гейт
`worker_runs_active` этого модуля и идемпотентность агентского пути гасят цену), а
следующий такт `mark_conflicts` снимает метку окончательно.

Сценарий: PR #604 (ветка `agent/604-…`) правит ту же строку файла, что и main -> рёбейз
структурно уткнулся в конфликт, отменён; PR #604 остаётся с меткой `conflict` и
попадает в обычную выборку `dispatch_conflict_rework` — расшивка агентом идёт как до
этой дельты, с тем же бюджетом (1 попытка).

Сценарий: PR #609 ссылается на ветку, которая уже удалена на origin (ручное удаление
автором) -> механический ребейз падает НЕ структурным конфликтом (`git fetch` не
находит ветку) — отчёт называет это отдельной строкой «infra-error: …», не «conflict»;
PR всё ещё несёт метку `conflict` и остаётся видимым `dispatch_conflict_rework` (тот уже
умеет сообщать «ветка не называет задачу»/иные случаи недоступности расшивки).
