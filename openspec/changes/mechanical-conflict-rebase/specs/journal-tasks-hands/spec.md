# Дельта-спека: журнал (journal-tasks-hands) — дешёвый механический ребейз конфликтных PR (#762)

Опирается на дельту `openspec/changes/conflict-auto-rebase/specs/journal-tasks-hands/
spec.md` («Автоматическая расшивка конфликтных PR», #474) — эта дельта добавляет ПЕРЕД
агентским путём новый, более дешёвый первый шаг; агентский путь (`dispatch_conflict_rework`)
не меняется, только сужается вход, который он видит (PR, которые механика не смогла
свести).

## ADDED: Механический ребейз конфликтных PR без агента

Требование: PR с меткой `conflict` (`mergeable_state=dirty`, обнаруживает
`mark_conflicts`) сначала проходит ДЕШЁВУЮ механическую попытку `git rebase
origin/main` — БЕЗ вызова LLM-агента `worker.yml`. Новый workflow
`.github/workflows/conflict-mechanical-rebase.yml` (СВОЙ файл, не job внутри
`orchestra.yml` — design.md, «Развилка 2»: изолирует `heartbeat_check` от
инфраструктурных сбоев этого шага; тот же триггер, что job `orchestra`: расписание раз
в 15 минут + `workflow_dispatch`) берёт ВСЕ PR с меткой `conflict` за один проход и
обрабатывает их последовательно в одном рабочем дереве (обоснование выбора
параллельности — design.md этого change, «Развилка 1»).

Требование: обход очереди конфликтных PR — от старейшего эпизода конфликта к новейшему
(`scheduler.conflict_labeled_at`, issue #588) — та же дисциплина, что уже применяет
`dispatch_conflict_rework`; переиспользуется, вторая сортировка не заводится.

Требование: перед попыткой сдвинуть head PR проверяется отсутствие активного прогона
`ai-review.yml` по этому же PR (`review_labels.other_active_ai_review_runs` —
переиспользован тот же предикат, что уже применяет `update_branch`, вторая копия не
заводится). Есть активный прогон — PR пропускается этим тактом («ai-review-running»),
без попытки рёбейза.

Требование: рёбейз сошёлся — ветка обновляется `git push --force-with-lease`. Снятие
метки `conflict` НЕ выполняется этим модулем напрямую — остаётся ИСКЛЮЧИТЕЛЬНО за
`mark_conflicts` (одна точка записи факта «конфликта больше нет», не заводится вторая:
`mark_conflicts` уже умеет корректно отличать подтверждённое неконфликтное состояние от
`None`/`unknown`). Известное следствие: между пушем этого модуля и следующим пересчётом
`mergeable_state` на стороне GitHub есть асинхронное окно — `mark_conflicts`, увидев ещё
не пересчитанный `dirty`, может на мгновение вернуть метку `conflict` и текст «PR
конфликтует с main»; следующий же такт механического пути увидит `git rebase` как no-op
(«Already up to date») и повторно (или без изменений) пройдёт тот же путь — поведение
самокорректируется, отдельного тормоза не заводится.

Требование: рёбейз СТРУКТУРНО уткнулся в конфликт — признак: после неудачного `git
rebase` существует каталог `.git/rebase-merge` или `.git/rebase-apply` (структурный
признак самого git, не текстовый матч сообщения об ошибке — тот протухнет при смене
формулировки, тот же принцип, что `WORKER_GIT_STEP_MARKER`). Рёбейз отменяется (`git
rebase --abort`), PR НЕ трогается (assignee, замок задачи, метка — без изменений) и
остаётся кандидатом СУЩЕСТВУЮЩЕГО агентского пути `dispatch_conflict_rework`, который
подхватит его как раньше, без каких-либо изменений в самом `dispatch_conflict_rework`.

Требование: сбой НЕ через структурный конфликт (сеть, права, ветка удалена на origin,
`git push --force-with-lease` отклонён гонкой с параллельной операцией) называется
ОТДЕЛЬНОЙ строкой отчёта («infra-error: …»), не путается со структурным конфликтом —
разные причины лечатся по-разному (AGENTS.md, «fail loud, не гадать»).

Требование: `CONFLICT_REWORK_MAX_ATTEMPTS = 1` (owner-решение, #474) не изменяется и
продолжает ограничивать ТОЛЬКО агентский путь. Механический путь своего бюджета попыток
не заводит — обоснование (путь не тратит модель, идемпотентен, повторная попытка
дешёвая) в design.md этого change; PR, уже механически резолвленный этим модулем,
естественным образом выпадает из очереди конфликтных PR на следующем такте (снята метка
`conflict` → не проходит фильтр `conflict_queue`), поэтому агентский бюджет им не
тратится вовсе.

Сценарий: PR #601 (ветка `agent/601-…`) получил метку `conflict`, main ушёл вперёд в
файле, которого ветка не касалась -> механический ребейз сходится, ветка обновляется
`--force-with-lease`; PR #601 не попадает в вызов `dispatch_conflict_rework` этим же
тактом (агентский бюджет не расходуется).

Сценарий: PR #604 (ветка `agent/604-…`) правит ту же строку файла, что и main -> рёбейз
структурно уткнулся в конфликт, отменён; PR #604 остаётся с меткой `conflict` и
попадает в обычную выборку `dispatch_conflict_rework` — расшивка агентом идёт как до
этой дельты, с тем же бюджетом (1 попытка).

Сценарий: PR #609 ссылается на ветку, которая уже удалена на origin (ручное удаление
автором) -> механический ребейз падает НЕ структурным конфликтом (`git fetch` не
находит ветку) — отчёт называет это отдельной строкой «infra-error: …», не «conflict»;
PR всё ещё несёт метку `conflict` и остаётся видимым `dispatch_conflict_rework` (тот уже
умеет сообщать «ветка не называет задачу»/иные случаи недоступности расшивки).
