# Дельта-спека: журнал (journal-tasks-hands) — дешёвый механический ребейз конфликтных PR (#762)

Опирается на дельту `openspec/changes/conflict-auto-rebase/specs/journal-tasks-hands/
spec.md` («Автоматическая расшивка конфликтных PR», #474) — эта дельта добавляет ПЕРЕД
агентским путём новый, более дешёвый первый шаг; агентский путь (`dispatch_conflict_rework`)
не меняется, только сужается вход, который он видит (PR, которые механика не смогла
свести).

## ADDED: Механический ребейз конфликтных PR без агента

Требование: PR с меткой `conflict` (`mergeable_state=dirty`, обнаруживает
`mark_conflicts`) сначала проходит ДЕШЁВУЮ механическую попытку `git rebase
origin/main` — БЕЗ вызова LLM-агента `worker.yml`. Новый workflow
`.github/workflows/conflict-mechanical-rebase.yml` (СВОЙ файл, не job внутри
`orchestra.yml` — design.md, «Развилка 2»: изолирует `heartbeat_check` от
инфраструктурных сбоев этого шага; тот же триггер, что job `orchestra`: расписание раз
в 15 минут + `workflow_dispatch`) берёт ВСЕ PR с меткой `conflict` за один проход и
обрабатывает их последовательно в одном рабочем дереве (обоснование выбора
параллельности — design.md этого change, «Развилка 1»).

Требование: обход очереди конфликтных PR — от старейшего эпизода конфликта к новейшему
(`scheduler.conflict_labeled_at`, issue #588) — та же дисциплина, что уже применяет
`dispatch_conflict_rework`; переиспользуется, вторая сортировка не заводится.

Требование: перед попыткой сдвинуть head PR проверяется отсутствие активного прогона
`ai-review.yml` по этому же PR (`review_labels.other_active_ai_review_runs` —
переиспользован тот же предикат, что уже применяет `update_branch`, вторая копия не
заводится). Есть активный прогон — PR пропускается этим тактом («ai-review-running»),
без попытки рёбейза.

Требование (issue #764, находка ревью гейта; СУЖЕНО issue #1032 по замеру
2026-09-12): перед попыткой сдвинуть head PR — гейт `worker_blocks_pr`
(mechanical_rebase.py) по активным прогонам `worker.yml` из
`sch.active_worker_runs` (единственное место правды фетча; булев
`sch.worker_runs_active` трёх диспетчеров сведён к тому же списку): `queued`-прогон
блокирует безусловно (атрибуция невозможна — claim ещё не мог случиться);
`in_progress`-прогон блокирует, если его CLAIM_VIA-след (`sch.run_claimed_task`)
указывает на задачу ЭТОГО PR, либо если он МЛАДШЕ
`sch.WORKER_CLAIM_TRACE_GRACE_MINUTES` и следа ещё нет (след появляется в первые
минуты job'а, не в первую секунду статуса — находка ai-review PR #1033,
требование 2; отказ самоосвобождается: прогон завершается или стареет порога —
газ назван, тормоз не односторонний). `queued`-прогон, зависший в очереди
(возраст по `created_at` старше того же `WORKER_STALL_MINUTES`), из списка
активных исключается — застрявшая очередь раннеров не держит механическую
очередь бессрочно (тот же класс #815, что у зависшего `in_progress`; находка
ai-review PR #1033, круг 3: прежний докстринг `active_worker_runs` ложно
утверждал, что порог к queued «неприменим физически»). Граница этого газа
названа честно (находка ai-review PR #1033, круг 4): исключение снимает блок
ЧИТАТЕЛЕЙ списка, но сам зависший `queued`-прогон никем не отменяется —
`reap_stalled_worker_run` читает только `in_progress`, а у queued нет ни
сессии морды для признака тишины, ни, как правило, взятой аренды. Следствие,
которое обязан знать читатель отчёта: диспатч уходит, но встаёт ПОЗАДИ зомби
в той же concurrency-группе (`cancel-in-progress: false`) и не стартует, пока
GitHub держит очередь — «диспатч отправлен» правда, «воркер поехал» из этого
НЕ следует. Отмена зависшего queued (тот же `POST .../runs/<id>/cancel`) —
отдельная узкая задача, не этот change: здесь она изменила бы контракт
рипера, переписываемый параллельно #827. Обоснование развилки «repo-wide → per-task»
— design.md, раздел «Гонка с агентским путём» (пересмотрен замером #1032: 15 из
28 прогонов не тронули НИ ОДНОГО PR из-за repo-wide блокировки при занятом
другой задачей воркере). Заблокированный PR пропускается этим тактом
(исход «worker-running: <причина>» — сама причина названа фактом, не угадана:
`queued-run` / `young-no-trace` / `unreadable-run` / `claimed-this-task` /
`task-unresolved`), без попытки рёбейза. Атрибуция следа — best-effort, не
доказательство безопасности: гейт сужает окно гонки #764 до случая, где след
аренды указывает на задачу ЭТОГО PR, но не доказывает обратное — воркер над
этой веткой БЕЗ следа (задокументированный путь без аренды: «поломка пути
аренды — предупреждение, ветка создаётся без аренды», PROTOCOL; канал hands
шимом не покрыт) после грейс-порога гейтом не различается, и незащищённый
механический force-with-lease в этом остаточном окне мог бы затереть его
коммиты и сжечь единственную засчитанную попытку агентского пути
(`CONFLICT_REWORK_MAX_ATTEMPTS = 1`) вхолостую.

Требование (issue #764, находка ревью гейта): PR из ЧУЖОГО репозитория (форк с
совпадающим именем ветки) или с веткой без префикса `agent/` (включая `main`) не
попадает в очередь этого модуля — фильтр `(pull["head"].get("repo") or {}).get(
"full_name") == repo and head_ref.startswith("agent/")` в `conflict_queue`. Без
фильтра метка `conflict` на PR из форка заставила бы ребейзить и
`--force-with-lease`-пушить ЧУЖУЮ ветку `origin`, приписывая исход номеру PR из
форка.

Требование: рёбейз сошёлся — ветка обновляется `git push --force-with-lease`. Снятие
метки `conflict` НЕ выполняется этим модулем напрямую — остаётся ИСКЛЮЧИТЕЛЬНО за
`mark_conflicts` (одна точка записи факта «конфликта больше нет», не заводится вторая:
`mark_conflicts` уже умеет корректно отличать подтверждённое неконфликтное состояние от
`None`/`unknown`). Известное следствие: между пушем этого модуля и следующим пересчётом
`mergeable_state` на стороне GitHub есть асинхронное окно — `mark_conflicts`, увидев ещё
не пересчитанный `dirty`, может на мгновение вернуть метку `conflict` и текст «PR
конфликтует с main»; следующий же такт механического пути увидит `git rebase` как no-op
(«Already up to date») и повторно (или без изменений) пройдёт тот же путь — поведение
самокорректируется, отдельного тормоза не заводится.

Требование: рёбейз СТРУКТУРНО уткнулся в конфликт — признак: после неудачного `git
rebase` существует каталог `.git/rebase-merge` или `.git/rebase-apply` И в индексе
есть НЕЗАВЕДЁННЫЕ пути (`git diff --name-only --diff-filter=U`) — оба структурных
признака самого git, не текстовый матч сообщения об ошибке (тот протухнет при смене
формулировки, тот же принцип, что `WORKER_GIT_STEP_MARKER`). Второй признак обязателен
(issue #764, находка ревью гейта, требование 1): каталог паузы рёбейза заводится ТАКЖЕ
тогда, когда патч применился без единого текстового конфликта, но `git commit` внутри
рёбейза упал по другой причине (живой пример — раннер без настроенной git identity,
`git rebase` падает с rc=128 «unable to auto-detect email address»); без проверки
незаведённых путей такой сбой ошибочно классифицировался бы как содержательный
конфликт.

Требование (issue #1032, рычаг 2): над КАЖДЫМ признанным содержательным конфликтом
(unmerged-пути непусты), ДО `git rebase --abort`, механический путь обязан попробовать
свести ВСЮ пачку unmerged-путей этого PR как «две независимые вставки в одну точку
общего реестра» (`additive_conflict_merge.try_resolve`) — класс, разобранный на живых
PR 241/395/408/542/567: main и ветка НЕЗАВИСИМО дописывают новый элемент в одну и ту
же точку файла (`git rebase` сам эту форму не сводит — нет общего 3-way-контекста на
строке вставки, хотя блоки семантически совместимы). Критерий безопасности КАЖДОЙ
стороны каждого хунка — единственный ходовой признак «два независимых добавления, не
правка одного»: обе стороны синтаксически ПОЛНЫ и самостоятельны (.py — `ast.parse`
каждой стороны ПО ОТДЕЛЬНОСТИ, первая непустая строка без отступа; .md — только строки
таблицы формы `| ключ | … |`) И НЕ определяют одно и то же (пересечение имён верхнего
уровня для .py — функции/классы/присваивания; ключа строки таблицы для .md).
Поддержаны `.py`, `.md` и `.sh` (третья форма — итерация #1383, требование с
её ОСЛАБЛЕННОЙ гарантией ниже по файлу).
ЧАСТИЧНОГО решения не существует: отказ ЛЮБОГО
файла/хунка отменяет ВСЮ пачку — ни один путь не попадает в `git add`. Каждая причина
отказа печатается в лог job'а одной строкой `::warning::`, включая хвост вывода
pytest — провал ЗАПУСКА верификации («No module named pytest») различим от «не наш
класс» (AGENTS.md, «алерт не гадает»).

Требование (итерация #1383): третья поддержанная форма — shell, и её гарантия
ОСЛАБЛЕННАЯ, названная вслух, а не умолчанная. Направление выбрано ЗАМЕРОМ живого
прогона `conflict-mechanical-rebase` (35491299405, 2026-09-20T05:17Z): из семи отказов
по типу файла `.sh` дал три, `.yml` — два, `.json` и «без расширения» — по одному.
Язык файла определяется суффиксом, а при его отсутствии — ШЕБАНГОМ первой строки
(`scripts/gh/issue-create` и пять соседних исполняемых скриптов живут без
расширения — `.githooks/pre-commit`, `.githooks/pre-push`, `scripts/gh-shim/gh`,
`scripts/git/pr-create`, `scripts/git/task-branch`; число проверено
`git ls-files` + первой строкой, а не оценено на глаз: всего трекаемых файлов
без расширения семь, седьмой `cf-worker/Dockerfile` — не шелл. Судить файл по
орфографии имени, когда язык написан в первой строке, — отказ не по существу). Критерий
безопасности каждой стороны симметричен питоновскому: `bash -n` каждой стороны ПО
ОТДЕЛЬНОСТИ (оборванная половина конструкции отказывает им, а не самодельным
разбором) плюс непересечение верхнеуровневых имён — функций и присваиваний В НУЛЕВОЙ
КОЛОНКЕ (отступ значит «внутри чего-то»: `local tmp=` двух разных функций не имеет
права давать ложный отказ). Класс имени ФУНКЦИИ — почти любое слово bash (`my-func`, `foo.bar`,
`foo:bar`, `foo@bar`; не принимается только `=` — проверено прогоном), а НЕ
идентификатор в стиле C: узкий класс не видел дефисных имён вовсе, и две версии
одной функции сводились молча (блокирующая находка ai-review PR #1392, раунд 7,
воспроизведена end-to-end; цена широкого класса замерена — на 153 файлах `.sh`
он добавляет одно фантомное имя, и то в сторону ОТКАЗА). Имена ПЕРЕМЕННЫХ
остаются узкими: bash их такими и делает. Строка присваиваний разбирается ЦЕЛИКОМ
и определяет СКОЛЬКО УГОДНО имён — и после ключевого слова (`export A=1 B=2`), и без него (`MODE=fast QUIET=1`):
частичный разбор означал бы, что сторона, правящая второе имя, сводится с молчаливой
победой последнего, то есть ровно класс #883, против которого критерий и существует
(блокирующая находка ai-review PR #1392, раунд 6, воспроизведена end-to-end). Цена —
фантомные имена из значений (`d3=$(REALGH_EXIT=7 …)` даёт и `REALGH_EXIT`): лишнее имя
толкает пачку в ОТКАЗ, не в пропуск, и это названо, а не умолчано. Разбор имён —
ОДНА функция для обоих потребителей (критерий непересечения и подсчёт дубликатов): две
копии уже успели разойтись по направлению ошибки, и это не осторожность, а отложенный
рецидив. Тот же класс по ИТОГОВОМУ файлу: `bash -n` целиком и отсутствие дубликатов
верхнеуровневых имён.

Отдельное требование того же круга — heredoc (блокирующие находки ai-review PR #1392,
раунды 1-4): тело heredoc'а — это ДАННЫЕ, и на них слепы ВСЕ рубежи шелла
одновременно (строка тела стоит в нулевой колонке, верхнеуровневых имён не
определяет, а `bash -n` принимает внутри heredoc'а произвольную прозу и на НЕЗАКРЫТОМ
heredoc'е возвращает НОЛЬ с одним warning'ом). Поэтому отказом заканчиваются четыре
случая: конфликт внутри уже открытого heredoc'а; сторона хунка, открывшая heredoc и
не закрывшая его; итоговый файл, оставшийся внутри heredoc'а; и — отдельно и ГРОМКО —
строка с `<<`, форму которой разобрать не удалось. Закрытие heredoc'а определяется
по правилам настоящего bash, а не по `strip()`: терминатор — строка, РАВНАЯ
ограничителю, для `<<-` — с ведущими ТАБУЛЯЦИЯМИ. Ограничитель читается КАК СЛОВО, со
снятием кавычек и экранирования и до неэкранированного метасимвола (`<<\EOF`,
`<<"EO"F`, `<<EOF-1`, `<<EOF#x` — четыре разных ограничителя, и все четыре проверены
прогоном настоящего bash). Промах мимо ОТКРЫТИЯ опаснее ложного отказа: не увидев
открытия, механизм считает данные кодом и зеленеет всеми рубежами разом, поэтому
нераспознанная форма — отказ, а не тишина.

Ослабленность гарантии `.sh` — в третьем рубеже, которого у неё НЕТ: соглашения
«сосед-тест» для шелла в репозитории не существует (тесты лежат как
`scripts/*/test/<имя>.{test,smoke}.sh` с разными хвостами, и угадывание имени иногда
не проверяло бы ничего, выглядя проверкой), поэтому pytest-аналога для `.sh` не
запускается. Это ПЕЧАТАЕТСЯ в лог job'а отдельной строкой `::notice::`, называющей
файлы, проверенные `bash -n` и непересечением имён, и прямо говорящей, что тестов у
них не запускалось и гарантия слабее питоновской. Там же контракт строки верификации
получает ТРЕТИЙ вариант: пачка без единого `.py` печатает «питоновских файлов в пачке
нет, ast.parse и pytest не запускались» — говорить в этом случае «только ast.parse
итоговых файлов» было бы неправдой, `ast.parse` не звался вовсе (некритичная находка
ai-review PR #1392). `.yml` и `.json` этой итерацией НЕ поддержаны сознательно: у них
«верхнеуровневое имя» — ключ отображения, и правило непересечения там своё.

Требование (находка ai-review PR #1033, круг 5): НЕЧИТАЕМЫЙ вход — это штатный
ОТКАЗ, а не падение прохода. Файл, чей суффикс поддержан, но содержимое не
декодируется как UTF-8 (`UnicodeDecodeError` — наследник `ValueError`, а не
`OSError`), и файл с ОБРЕЗАННЫМИ маркерами конфликта (`ValueError` из разбора
хунков) уходят в тот же `::warning::`-отказ, каждый со СВОЕЙ причиной: «не читается
как UTF-8» и «маркеры конфликта не разбираются» не сливаются ни между собой, ни с
соседним «rename/delete-конфликт?» — лечатся они по-разному.

Требование того же круга, уже КЛАССОМ, а не случаем: один PR не имеет права клинить
весь проход. Обработка каждого PR очереди изолирована — любое неожиданное исключение
становится исходом `infra-error: неожиданное исключение <Тип>: <текст>` этого PR,
проход продолжает хвост очереди и ВСЕГДА строит отчёт. До этого требования
`process_pull` ловил только `RuntimeError`, а per-PR изоляции не было вовсе: одно
исключение роняло job с трейсбеком — отчёт не писался, хвост очереди не
обрабатывался, и крон падал на том же PR каждые 15 минут, пока PR не уберут руками.

Требование (issue #1032): успешное сведение верифицируется ДО `git rebase --continue`:
`ast.parse` ПОЛНОГО итогового текста каждого .py (до единой записи на диск), отсутствие
ДУБЛИКАТОВ верхнеуровневых имён в итоговом .py и ключей строк таблиц в итоговом .md
(находка ai-review PR #1033, круг 3: перехунковый критерий видит «обе стороны одного
хунка», но тот же класс проходит двумя РАЗНЫМИ хунками одного файла — итог содержит
оба определения, молча живёт последнее; проверка по итоговому файлу ловит и форму
«сторона + нетронутая часть файла»), и pytest
соседнего `test_<имя>.py` (или самого файла, если это уже `test_*.py`) каждого
затронутого .py, у которого такая тестовая цель существует (файл без соседнего теста
цели не добавляет — синтаксическую гарантию несёт `ast.parse` выше). Что именно было
проверено, читается ФАКТОМ из лога, а не домысливается по исходу: `::notice::` перед
верификацией называет либо список запускаемых целей, либо прямо «соседних `test_*.py`
нет, pytest не запускался» (находка ai-review PR #1033, круг 5: строка отчёта
заявляла «затронутые тесты перепроверены» и тогда, когда тестовых целей не было
вовсе). Провал любой
проверки — такой же отказ всей пачки. Честный контракт
по состоянию диска на отказе: отказ ДО записи не трогает файлы вовсе; отказ ПОСЛЕ
записи (провал pytest) оставляет файлы слитыми на диске — рабочее дерево целиком
восстанавливает `git rebase --abort` вызывающего кода, второй, независимой точки
отката не заводится. Сведённый рёбейз завершается исходом "resolved-additive" и
пушится тем же `git push --force-with-lease`, что и чистый "resolved" (снятие метки
`conflict` — так же исключительно за `mark_conflicts`).

Требование: конфликт, НЕ сведённый аддитивно (`try_resolve` отказал хотя бы на одном
файле/хунке или провалилась верификация), — рёбейз отменяется (`git rebase --abort`),
PR НЕ трогается (assignee, замок
задачи, метка — без изменений) и остаётся кандидатом СУЩЕСТВУЮЩЕГО агентского пути
`dispatch_conflict_rework`, который подхватит его как раньше, без каких-либо изменений
в самом `dispatch_conflict_rework`.

Требование: сбой НЕ через структурный конфликт (сеть, права, ветка удалена на origin,
`git push --force-with-lease` отклонён гонкой с параллельной операцией, отсутствующая
git identity — см. выше) называется ОТДЕЛЬНОЙ строкой отчёта («infra-error: …»), не
путается со структурным конфликтом — разные причины лечатся по-разному (AGENTS.md,
«fail loud, не гадать»). Продакшн-окружение (`.github/workflows/
conflict-mechanical-rebase.yml`) обязано задавать git identity ДО первого рёбейза
(`git config --global user.name/user.email`, атрибуция боту — операция чисто
механическая, авторство исходных коммитов рёбейз сохраняет) — проверка «незаведённых
путей» выше остаётся сетью безопасности для случая, когда identity всё же не задана,
не заменяет эту настройку.

Требование (issue #764, находка ревью гейта, требование 5): рабочее дерево
принудительно возвращается в чистое состояние ПЕРЕД каждой попыткой рёбейза (см.
`ensure_clean_repo`) — если `git rebase --abort` предыдущей итерации сам упал (сеть,
файловая система), следующий PR очереди не должен унаследовать чужую паузу рёбейза
(«you need to resolve your current index first» вместо честного fetch/checkout).

Требование (issue #764, находка ревью гейта, требование 5): если ВСЕ PR очереди этого
прохода завершились `infra-error` (очередь не пуста), процесс завершается ненулевым
кодом — иначе `failure_watch` (наблюдатель `WATCHED_WORKFLOWS`) видит только упавший
ПРОЦЕСС, но не «прошёл и не обработал ни одного PR».

Требование: `CONFLICT_REWORK_MAX_ATTEMPTS = 1` (owner-решение, #474) не изменяется и
продолжает ограничивать ТОЛЬКО агентский путь. Механический путь своего бюджета попыток
не заводит — обоснование (путь не тратит модель, идемпотентен, повторная попытка
дешёвая) в design.md этого change; PR, уже механически резолвленный этим модулем,
естественным образом выпадает из очереди конфликтных PR на следующем такте (снята метка
`conflict` → не проходит фильтр `conflict_queue`), поэтому агентский бюджет им не
тратится вовсе.

Сценарий: PR #601 (ветка `agent/601-…`) получил метку `conflict`, main ушёл вперёд в
файле, которого ветка не касалась -> механический ребейз сходится, ветка обновляется
`--force-with-lease`; как только `mark_conflicts` следующего такта увидит
пересчитанный `mergeable_state` и снимет метку, PR #601 перестаёт быть кандидатом
`dispatch_conflict_rework` (агентский бюджет не расходуется). Дисциплина «этим же
тактом» НЕ гарантирована (найдено ревью, issue #764, требование 3; design.md, «Развилка
2», «Цена решения»): `orchestra.yml` (диспетчер, включая `dispatch_conflict_rework`) и
`conflict-mechanical-rebase.yml` — два независимых workflow-файла на одном
15-минутном кроне без взаимной `needs:` (такой механизм между файлами в GitHub Actions
не существует), поэтому `dispatch_conflict_rework` того же самого тика МОЖЕТ успеть
прочитать метку `conflict` раньше, чем GitHub пересчитал `mergeable_state` после
нашего пуша, — тогда агентский путь диспатчится один раз вхолостую (не вредно:
гейт `worker_blocks_pr` этого модуля и идемпотентность агентского пути гасят
цену), а
следующий такт `mark_conflicts` снимает метку окончательно.

Сценарий: PR #604 (ветка `agent/604-…`) правит ту же строку файла, что и main -> рёбейз
структурно уткнулся в конфликт; `additive_conflict_merge` ОТКАЗЫВАЕТ (обе стороны хунка
правят существующий код, а не дописывают независимый элемент — критерий безопасности не

меткой `conflict` и
попадает в обычную выборку `dispatch_conflict_rework` — расшивка агентом идёт как до
этой дельты, с тем же бюджетом (1 попытка).
