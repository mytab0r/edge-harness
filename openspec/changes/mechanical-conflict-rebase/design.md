# design: параллельность и размещение механического ребейза (issue #762, требование 1)

## Развилка 1 — параллельность

Обработка N конфликтных PR за один такт (сегодня N=25, замер 2026-09-08) — двумя
кандидатами:

1. **Matrix** — по одному job'у GitHub Actions на PR (`strategy: matrix`).
2. **Последовательный цикл в одном job'е** — один `actions/checkout@v7 (fetch-depth: 0)`,
   дальше N раз `git fetch` + `git rebase` + (`git push` | `git rebase --abort`) внутри
   одного и того же рабочего дерева.

## Числа, на которых принято решение

- **Раннер бесплатен, но не безлимитен.** Репозиторий публичный, standard-раннеры на
  публичном repo НЕ тратят минуты вовсе (`docs/research/21-github-actions.md`, TL;DR
  п.1 — дословная цитата биллинговой документации GitHub) — «дороже по минутам раннера»
  здесь не довод в долларах ни для одного из двух кандидатов. Довод в другом: **Free-план
  даёт 20 одновременных job'ов** (тот же документ, TL;DR п.2). Matrix на N=25 конфликтных
  PR (живой замер 2026-09-08: 25 из 38 открытых) уже превышает этот потолок в ОДНОМ
  батче — 5 задач гарантированно уходят в очередь GitHub, для которой документация не
  называет верхней границы времени ожидания на GitHub-hosted раннерах (`docs/research/
  21-github-actions.md`, строка 66: «гарантированного… нет… может занимать слот сколь
  угодно долго в пределах 35 суток»). Кандидат 2 (последовательный цикл) использует
  РОВНО один слот независимо от N.
- **Конкуренция за тот же самый лимит с обязательными проверками.** Те же 20
  одновременных job'ов делят между собой `contract` (по каждому открытому PR),
  `pr-review`/`ai-review` (по каждому пушу), `worker` — matrix на 25 PR временно вытесняет
  ИМЕННО те проверки, которые решают, готов ли к слиянию любой другой PR прямо сейчас.
  Последовательный цикл — один слот, конкурирует не больше, чем сам `orchestra`-job уже
  конкурирует сегодня.
- **Стоимость фиксированной части (checkout) амортизируется, а не умножается.**
  `fetch-depth: 0` на этом репозитории — 254 коммита, 26 MiB `.git`
  (`git rev-list --count HEAD`, `git count-objects -v`, замер 2026-09-08 в рабочем
  дереве этой же задачи): один клон такого размера на GitHub-hosted раннере (сеть внутри
  дата-центра GitHub) — секунды, но 25 отдельных клонов (matrix) означают 25 отдельных
  оплат этой фиксированной части ПЛЮС 25 отдельных стартов job'а (планирование,
  установка окружения) — накладные расходы, которых кандидат 2 несёт ровно один раз.
- **Гонка форс-пушей.** N параллельных job'ов, каждый со своим `git push
  --force-with-lease` на СВОЮ ветку — редко, но не исключено пересечение с другим
  механизмом, двигающим тот же PR (`update_branch` в scheduler.py, тоже под общим PAT).
  Последовательный цикл в одном job'е даёт по построению не больше одной активной
  git-операции в любой момент времени — тот же принцип, что уже применён к
  `_update_branch_used_this_run` (scheduler.py, слот на проход).

## Решение (развилка 1)

Последовательный цикл в одном job'е (`.github/workflows/conflict-mechanical-rebase.yml`,
job `rebase`). Matrix отвергнут не как «медленнее», а как единственный из двух
кандидатов, который физически не помещается в один батч на Free-плане уже сегодня
(25 > 20) и конкурирует за тот лимит с проверками, от которых зависит слияние остальных
PR.

## Развилка 2 — где живёт workflow: job внутри orchestra.yml или отдельный файл

Рассмотрены оба варианта РАЗМЕЩЕНИЯ (не параллельности) нового шага:

1. Новый job внутри `.github/workflows/orchestra.yml`, рядом с job `orchestra`.
2. Отдельный workflow-файл `.github/workflows/conflict-mechanical-rebase.yml`.

Довод, решивший в пользу варианта 2: `pulse_guard.heartbeat_check` (используется job'ом
`orchestra`) определяет «пульс планировщика жив» по `conclusion` ВСЕГО ЗАПУСКА
`orchestra.yml` (`orchestra_tick_runs` → `run["conclusion"] == "success"`), а GitHub
аггрегирует `conclusion` запуска по ВСЕМ job'ам этого файла. Если бы механический
ребейз жил ВНУТРИ `orchestra.yml` как второй job, его собственный инфраструктурный сбой
(сеть, квота — НЕ содержательная ошибка планировщика) красил бы ВЕСЬ запуск как
`failure`, даже когда job `orchestra` (мерж-очередь) отработал нормально — heartbeat
закричал бы «пульс пропал», хотя конвейер жив. Это ровно тот класс маскировки, что уже
дважды находили и чинили в этом же файле для другого разреза той же проблемы (issue
#303 — `contract`-прогоны маскировали простой job `orchestra`; issue #318 — вторая
находка того же класса, `real_orchestra_ticks`/`orchestra_tick_runs`) — заводить его
снова третий раз тем же PR означало бы чинить то, что уже дважды было найдено дорогой
ценой, обратно. Отдельный workflow-файл делает это архитектурно невозможным: у
`conflict-mechanical-rebase.yml` свой независимый `conclusion` запуска, `orchestra.yml`
его не видит вовсе.

Цена решения — `dispatch_conflict_rework` (job `orchestra`, следующий такт) и
`mechanical_rebase.py` (свой независимый такт, тот же интервал cron) НЕ гарантированно
идут строго друг за другом в рамках одного и того же 15-минутного окна (не заведено
`needs:` — оно работает только внутри одного workflow-файла). Эффект — задокументированное,
самокорректирующееся окно гонки между пушем этого модуля и следующим пересчётом
`mergeable_state` на стороне GitHub, которое читает `mark_conflicts`: `mark_conflicts`,
застав ещё не пересчитанный `dirty`, может на мгновение вернуть метку `conflict`; на
следующем такте механический путь увидит `git rebase` как no-op и не сделает ничего
нового, а `mark_conflicts` следующего такта уже видит верное состояние. Цена — не
худшая латентность (агентский путь сегодня и так резолвит конфликт с тем же порядком
задержки — рёбейз агентом, следующий такт `mark_conflicts`), поэтому решение не
регрессирует существующее поведение, только добавляет к нему дешёвый первый шаг.

`WATCHED_WORKFLOWS` (`pulse_guard.py`, наблюдатель дефектов `failure_watch`) расширен
именем нового файла — catastrophic-сбой ВСЕГО job'а (не рядовая per-PR инфра-ошибка,
та уже видна построчно в его собственном отчёте) остаётся видимым тем же существующим
механизмом, что уже следит за worker.yml/hands.yml/orchestra.yml/deploy-*.yml.

## Свой бюджет попыток дешёвому пути — не заводится

`CONFLICT_REWORK_MAX_ATTEMPTS = 1` — бюджет ИМЕННО агентского пути (owner-решение,
issue #474): он существует, потому что попытка агента дорогая (жжёт квоту LLM) и
неотличима заранее от «зря потраченной» на инфраструктурный сбой. Механический путь не
делит эти свойства:

- он НЕ стоит модели — второй, третий, N-й повтор на следующих тактах не расходует
  ничего дороже нескольких секунд `git fetch`/`git rebase`;
- он идемпотентен по построению: PR, уже механически резолвленный (`mark_conflicts` снял
  метку), больше не попадает в выборку `conflict_queue` по метке — повторной работы над
  ним не возникает; PR, остающийся реальным конфликтом, на каждом такте получает то же
  дешёвое «rebase упёрся → abort» и корректно остаётся кандидатом агентского пути.

Вводить второй лифтайм-счётчик означало бы копировать механизм, оправданный ЦЕНОЙ
попытки (модель), туда, где этой цены нет — решение владельца (#474) для агентского
бюджета этим не пересматривается и не трогается.
