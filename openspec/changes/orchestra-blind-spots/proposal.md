# orchestra-blind-spots: оркестратор не должен производить сигнал без читателя (#887, #888)

Задачи: #887, #888. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Симптом

Два независимых механизма одного класса «сигнал произведён, читателя нет»,
оба вскрыты на живом прогоне orchestra 34506949025 (2026-09-10):

1. **`continue-on-error: true` маскирует реальный провал шага.** Три
   best-effort шага job `orchestra` (гвардии `stale_blocked_guard.py`,
   `waiting_owner_guard.py`, `health_audit.py`) держат `continue-on-error`,
   чтобы не гасить зелёный статус job'а: `heartbeat_check`
   (`pulse_guard.py`, #120) читает conclusion ЗАПУСКА orchestra по
   расписанию как признак живого пульса. Но Jobs API
   (`GET .../actions/jobs/{id}`) отдаёт `steps[].conclusion` — значение уже
   ПОСЛЕ применения `continue-on-error` (всегда `success`), а реальный
   `outcome` существует только в контексте `steps` ВНУТРИ ещё идущего job и
   через REST после завершения недоступен. Живой факт: шаг «Гвардия
   протухшей метки blocked (#334)» — в API `success`, в логе
   `##[error]Process completed with exit code 1`; ни один механизм эту
   разницу не читал.

2. **`WATCHED_WORKFLOWS` — ручной реестр.** `pulse_guard.py::failure_watch`
   (#477) смотрел только фиксированный кортеж из 6 имён workflow-файлов:
   новый `.github/workflows/*.yml` не попадал под наблюдение по умолчанию.
   Живая цена: `telegram-webhook.yml` красный с 2026-09-06 (прогон
   34061911867) — незамеченным, потому что файла в кортеже не было; 13 из
   19 файлов каталога не наблюдались вовсе.

## Что делается

- `WATCHED_WORKFLOWS` вычисляется из `.github/workflows/*.yml` на диске
  (`_discover_watched_workflows`); исключения — явный
  `WATCHED_WORKFLOWS_EXCLUDED` (пара имя→причина, сейчас пуст), сверяется
  с каталогом тестом.
- Каждому `continue-on-error` шагу job `orchestra` — явный `id:`; финальный
  шаг «Свод реальных исходов» (`if: always()`) читает `${{ toJSON(steps) }}`
  и эскалирует по факту (`best_effort_outcome_guard.py`, канал #120+Telegram),
  не превращая job в красный: находка best-effort гвардии job не красит.
- Сломанная проводка читателя — отдельный исход: без `STEPS_JSON`, с пустым
  или не разобранным снимком гвардия выходит 1 с `::error` (красный job —
  честный «читатель исходов сломан», не находка гвардии), а по исходнику
  workflow то же нарушение ловит линт `orchestra_workflow_lint.py`:
  каждый `continue-on-error` шаг обязан нести `id:`, после последнего из
  них обязан стоять проведённый шаг-свод (`if: always()`,
  `STEPS_JSON: ${{ toJSON(steps) }}`), исчезновение job `orchestra` —
  громкий отказ, не молчаливое «здоров».
- Дайджест долга наблюдательных инвариантов 4/5/8/10 (`repo_invariants.py`,
  #888): `DEBT_DIGEST_INVARIANTS` эскалирует снимок счётчиков
  (`escalate_if_new`) при появлении долга или изменении снимка — 🚨-строки
  перестают жить только в `GITHUB_STEP_SUMMARY`.
- Обе новые гвардии зарегистрированы через каталог `scripts/ci/guards/`
  (#749), не рукописным шагом `repo-ci.yml`.

## Вне рамок

- Дедуп эскалации шага-свода насыщается: маркер кодирует множество
  упавших id (максимум 7 состояний), повторный провал того же набора после
  долгой паузы уйдёт в тишину. Газ (повтор по окну свежести, как
  `FAILURE_WATCH_WINDOW_MINUTES`) — узкой задачей-хвостом после слияния
  (замечание ревью PR #888, не блокирует).

## Пост-мерж проверка

Первый живой прогон orchestra после слияния: шаг «Свод реальных исходов»
зелёный при зелёных гвардиях; при искусственном провале одной из гвардий —
эскалация в #120 при зелёном job'е.
