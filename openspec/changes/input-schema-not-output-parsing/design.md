# Design: input-schema-not-output-parsing

Контекст, замер и правило - proposal.md этого изменения. Здесь - развилки
решения и почему выбрана конкретная.

## Развилка (а): schema на входе через параметр запроса к провайдеру

Идея: заставить провайдера вернуть строго валидный JSON через
response_format/json_schema или tool-calling - тогда парсер вообще не
нужен, невалидный ответ провайдер либо не пришлёт, либо это будет одна
ошибка десериализации, а не N эвристик под N наблюдённых искажений.

Цена и статус рычага - НЕ ПОДТВЕРЖДЕНО, а не "дорого" или "дёшево":

- Путь вызова модели у нас не прямой HTTP: scripts/review/ai_dsh.sh
  запускает "dsh --profile headless" (DSH headless CLI), а не делает
  chat-completions запрос сам. Управление идёт через два канала DSH:
  переменные окружения (DEEPSEEK_BASE_URL, DEEPSEEK_API_KEY,
  DEEPSEEK_REASONING - подтверждено docs/research/10-dsh-architecture.md:504-506)
  и settings-слой профиля (cordis.patch.yml, namespace agent-default-model
  - provider/model/reasoningEffort, плюс namespace llm-deepseek с
  maxTokens - scripts/lib/dsh-ci.sh:87-106).
- Ни один из этих каналов не содержит поля под response_format/
  json_schema/tool_choice. Поиск по всему репозиторию и research-докам
  (grep на response_format/json_schema/tool_call) находит эти термины
  только в cf-worker/worker-configuration.d.ts - это типы Cloudflare
  Workers AI, отдельная система, отвергнутая для агентского цикла ещё в
  docs/research/30-rejected-alternatives.md, п.13. К контракту DSH-адаптера
  эти типы отношения не имеют.
- abstract class LlmAdapter с abstract stream() - интерфейс адаптера
  провайдера внутри DSH; глубина этого класса (принимает ли stream()
  параметр форматирования ответа) не изучена в этом репозитории и не
  описана ни в одном research-документе. Это "не подтверждено", а не
  "исключено" - контракт метода можно проверить только чтением исходников
  пакета @deepseek-ai/dsh-llm (lib/types/index.d.ts, упомянут в
  docs/research/11-dsh-edge.md:281, но не тем сечением, которое отвечает
  на этот вопрос).
- Даже если рычаг у DSH есть, второй слой неопределённости - поддержка
  provider+model. Провайдер сейчас integrate.api.nvidia.com/v1 (NVIDIA
  NIM), модель - vars.DEEPSEEK_MODEL. Работает ли structured output/
  tool-calling у конкретной модели за этим эндпоинтом - устанавливается
  только реальным запросом, не чтением документации: NIM даёт доступ к
  разным семействам моделей с разной поддержкой function calling, а
  runbook переключения провайдера (docs/runbooks/switch-llm-provider.md)
  прямо описывает провайдера как заменяемый слот - если рычаг найдётся
  для сегодняшней модели, при следующей смене провайдера его придётся
  перепроверять заново, то есть решение вида (а) хрупко к тому же классу
  изменений, что и текущий регэксп, только на уровень выше.

Вывод по (а): это лучшее решение ПО ПРИНЦИПУ (контракт невозможно
нарушить, а не только можно поймать нарушение), но заявлять его выбором
этого изменения нельзя - нет ни одного факта, подтверждающего наличие
рычага. Investigation этого вопроса (чтение исходников dsh-llm/
dsh-llm-deepseek, живой пробный запрос с response_format через DSH,
если API это пропускает) - выносится отдельной задачей в tasks.md,
не блокирует остальной scope.

## Развилка (б): вердикт как артефакт с валидацией схемой при чтении

Идея: агент отвечает не свободным текстом с меткой в последней строке, а
единственным блоком строгого формата (JSON), который парсится один раз
через json.loads + explicit-schema-check (или jsonschema.validate);
отсутствие валидного блока - это ОДНО состояние "ревью не состоялось",
не разбирается на "нет строки"/"строка не последняя"/"два маркера" отдельными
эвристиками.

Важное уточнение архитектуры, найденное этим исследованием - "артефакт" не
может быть отдельным ФАЙЛОМ, физически пересекающим границу между job'ами.
.github/workflows/ai-review.yml устроен как два job'а на РАЗНЫХ ВМ: job
review (недоверенный DSH-шаг, права только на чтение) и job verdict
(свежая машина, права на запись). Единственный подтверждённый канал
между ними сейчас - steps.outputs (ai-review.yml:57-59 объявление outputs,
123-132 запись text/head в GITHUB_OUTPUT, лимит около 1 МБ на job).
Файл, который агент запишет своим tool-fs в cwd недоверенного job'а
(профиль headless даёт fs-инструменты - docs/research/10-dsh-architecture.md:100),
остаётся на ВМ job'а review и умирает вместе с ней - его не увидит job
verdict без нового механизма actions/upload-artifact + download-artifact.

Отсюда - вариант (б) не вводит новый физический файл-мост, а меняет
СОДЕРЖИМОЕ существующего канала: тот же answer.txt/steps.outputs.text,
только его форма - не "любой текст, последняя строка которого похожа на
вердикт", а "единственный JSON-блок по объявленной схеме (verdict,
опционально reason, опционально tasks)". Состояние "ревью не состоялось"
(файл верно не найден) отличается по коду от "блок есть, но не проходит
схему" (агент ответил, но неправильно) - оба явные, оба не требуют
последовательности региональных regex.

Cхема (набросок для design, не финальный код):

{
  "verdict": "approve" | "rework",
  "findings": "текст (свободная проза - остаётся вне схемы, см. proposal Out)",
  "tasks": [ {"title": "...", "body": "..."} ]
}

Ошибка разбора (JSON невалиден, verdict не approve/rework, поле
отсутствует) - трактуется ОДНИМ путём кода как "error", вместо трёх разных
веток текущего VERDICT_RE + отдельной ветки transport_failed/error_reason
из PR #193. Различение "транспортный сбой провайдера" (rc dsh != 0, файл
answer.txt пуст) от "модель ответила невалидным блоком" (rc == 0, но JSON
не парсится/не проходит схему) сохраняется - это два факта РАЗНОЙ природы
(код возврата процесса vs форма его stdout), не два случая одного текста.

Cтоимость: промпт становится жёстче (просить модель вернуть строго один
JSON-блок без markdown-обрамления вокруг него сложнее психологически для
модели, чем "последняя строка = ВЕРДИКТ: approve"), но проверяется одним
проходом валидации, а не наращиванием regex под каждое новое отклонение.
Миграция промпта и парсера - в рамках существующих файлов
(ai_prompt.md, ai_review.py), новых workflow-механизмов не требует.

## Развилка (в): оставить текстовый контракт, продолжать латать по факту

Цена названа честно, не спрятана: каждое новое наблюдённое отклонение
модели от ожидаемой формы стоит одного PR с новым regex-случаем (три раза
подряд за 2026-08-31 - 2026-09-02 согласно замеру в proposal.md, если
считать наблюдение из п.3 подтверждённым - минимум два раза, если нет).
Плюс скрытая цена: каждый новый паттерн увеличивает шанс, что следующий
паттерн ему противоречит (более терпимый VERDICT_RE легче даёт
ложноположительное совпадение на прозе рассуждения модели - в PR #184 это
уже учтено явной оговоркой "упоминание approve/rework внутри прозы
рассуждения вердиктом не считается", то есть цена уже проявилась как
требование к дизайну регэкспа, не гипотетична).

Этот вариант НЕ выбран этим изменением - он и есть то, что владелец
просил прекратить фразой "почему мы... не проверяем сразу... до того как
оно куда-то запишется".

## Выбор

**Развилка (б) - вердикт как структурированный JSON-артефакт, валидируемый
схемой в момент разбора того же канала (steps.outputs), который уже
существует.**

Обоснование:

1. (а) - лучшее решение по принципу (невозможность нарушить контракт
   сильнее, чем обнаружение нарушения), но не подтверждён рычаг: заявлять
   его выбором сейчас значило бы писать design под непроверенное
   допущение, а это тот же класс ошибки, который правило запрещает
   ("делаем проверки, когда это уже произошло" применительно к
   архитектурному решению, а не только к парсингу).
2. (б) не требует нового физического механизма (upload/download-artifact)
   - использует существующий steps.outputs канал, меняя ТОЛЬКО форму
   содержимого и способ разбора. Это меньший по площади дифф, чем
   (а) требовал бы, если бы рычаг подтвердился, и не создаёт зависимости
   от недоказанной возможности провайдера/DSH.
3. (б) закрывает named class проблемы: одна валидация одним проходом
   вместо накопления regex-случаев, различимые состояния "не состоялось"/
   "невалидно"/"валидно" без текстовых эвристик поверх уже нарушенного
   текста.
4. (б) совместим с (а): если рычаг (а) найдётся отдельным исследованием
   (задача в tasks.md), JSON-схема на выходе останется той же, просто
   провайдер перестанет иногда её нарушать - формат ответа не меняется,
   меняется только гарантия его соблюдения. Значит выбор (б) не создаёт
   работы на выброс при подтверждении (а) - он совместимая база.

**Что делает выбор неверным (при каком новом факте решение нужно
пересмотреть).**

- Если исследование задачи "проверить response_format/json_schema через
  DSH" (см. tasks.md) подтвердит рычаг И покажет, что связка
  provider+model, используемая сейчас, его поддерживает надёжно (без
  разброса по формату при повторных запросах) - схему стоит переносить
  выше, в параметр запроса, а валидацию при чтении оставить только как
  defense-in-depth (не единственную линию защиты). Это не отменяет
  формат JSON, но снижает частоту, с которой модель вообще может его
  нарушить.
- Если владелец сменит провайдера/модель на связку без надёжной
  поддержки строгого JSON-вывода (модель регулярно "разговорчивая",
  оборачивает JSON текстом до/после) - потребуется либо усилить промпт
  явным примером формата, либо признать вариант (в) временно неизбежным
  для этой конкретной связки, честно назвав цену, а не тихо ослаблять
  схему до состояния регэкспа.
- Если найдётся третий подтверждённый случай наблюдения из proposal.md
  п.3 ("вердикт первой строкой, продолжен текстом") - он проверяет ровно
  ту защиту, которую даёт JSON-схема (весь ответ обязан быть одним
  блоком, а не текстом с вердиктом где-то внутри); если такой случай
  будет наблюдён уже ПОСЛЕ перехода на (б) и снова потребует правки
  парсера - это будет сигналом, что даже структурированный формат
  недостаточен без (а), и развилку нужно пересматривать в сторону
  ужесточения (например, повтор запроса при невалидном JSON вместо
  однократного error).

## Контракт "PR - задача": та же логика, другая механика

В отличие от вердикта AI-ревью, здесь схема на входе технически ВОЗМОЖНА
уже сейчас, без вопроса про рычаг провайдера - потому что автор тела PR
это не LLM с непредсказуемым выводом, а транспортный скрипт
(scripts/worker/task.sh), который сам печатает промпт для DSH-агента.
Сегодня transport передаёт правило текстовой инструкцией ("Первая строка
тела PR - ровно \"#$number\"", task.sh:205) и полагается на то, что
DSH-агент её выполнит - тот же паттерн "просим соблюсти форму, проверяем
постфактум contract_check.py".

Два honest варианта для этого случая (не альтернатива схеме, а способ её
поставить):

1. **Собирать тело PR программно вокруг агента.** Транспорт не просит
   агента писать "#$number" вручную, а сам подставляет "#$number\n\n"
   перед тем, что вернёт агент (--body-file собирается конкатенацией:
   заголовок формируется скриптом, остальное - решение агента). Это
   разводит "то, что обязано быть формой" (номер задачи) и "то, что
   решает агент" (описание работы) на уровне транспорта, а не промпта.
   Устраняет зависимость от того, скопирует ли агент инструкцию дословно.
2. **Оставить сборку агенту, но проверить ДО открытия PR.** DSH headless
   не даёт транспорту перехватить `gh pr create` изнутри агентской сессии
   (агент решает сам, когда и как его вызвать) - значит "проверка до
   записи" здесь означала бы пост-обработку внутри самого прогона DSH,
   которой сейчас архитектурно нет (агент делает gh pr create сам,
   транспорт узнаёт результат уже после). Это дороже варианта 1: требует
   либо нового шва управления (agent-tool hook), либо повторного открытия
   PR при неудаче - что contract_check.py и так частично делает через
   fail() с меткой contract:failed, то есть JavaScript этого пути уже
   написан, просто пост-факту.

Вариант 1 дешевле и достаточен: он не устраняет possibility того, что
агент откроет PR руками мимо шаблона (эскалация, ручное вмешательство
владельца) - для этих путей contract_check.py остаётся законной
финальной страховкой (defense-in-depth), но для штатного автономного
пути (task.sh) схема ставится на входе программной сборкой, а не текстом
инструкции. Задача на это - в tasks.md.
