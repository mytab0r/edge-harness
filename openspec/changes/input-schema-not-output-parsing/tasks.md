# Задачи: input-schema-not-output-parsing

Порядок задач учитывает зависимость: исследование (0) не блокирует
остальные, но его результат может изменить приоритет T2 после T1.

## 0. Исследование (не блокирует остальной scope)

- [ ] Проверить рычаг `response_format`/`json_schema`/tool-calling через
      DSH: чтение исходников `@deepseek-ai/dsh-llm` (`lib/types/index.d.ts`,
      контракт `abstract stream()` у `LlmAdapter`) и `dsh-llm-deepseek`
      (адаптер провайдера) - установить, пробрасывает ли DSH такой
      параметр из `cordis.patch.yml`/env в реальный HTTP-запрос к
      провайдеру. Видимый результат: запись в
      `docs/research/10-dsh-architecture.md` (или новый research-файл)
      с фактом «рычаг есть, вот где» ИЛИ «рычаг отсутствует, вот что
      проверено» - не молчание.
- [ ] Если рычаг подтверждён - живой пробный прогон `ai-review` с
      `response_format`/`json_schema`, выставленным через найденный канал,
      на текущей связке `integrate.api.nvidia.com/v1` + `vars.DEEPSEEK_MODEL`:
      проверить, действительно ли провайдер+модель возвращают валидный JSON
      без обёртки. Видимый результат: лог прогона с ответом модели,
      приложенный к issue или комментарию задачи.

## 1. Контракт вердикта AI-ревью: JSON-схема вместо VERDICT_RE

- [ ] `scripts/review/ai_prompt.md` - переписать контракт ответа: точное
      описание JSON-схемы (`verdict`, `findings`, `tasks`), запрет текста
      вне блока, допустимость fenced-обёртки как единственной
      нормализации. Видимый результат: диф файла, ревью подтверждает
      формулировку однозначна (нет места для двух трактовок).
- [ ] `scripts/review/ai_review.py` - заменить `VERDICT_RE`/`parse_verdict`
      на разбор JSON: один проход `json.loads` (с извлечением fenced-блока
      как единственной документированной нормализацией) + explicit-схема
      проверка обязательных полей и допустимых значений `verdict`. Функции
      `parse_tasks`/`findings_of` адаптируются под чтение полей `tasks`/
      `findings` из распарсенного объекта вместо построчного разбора
      прозы. Видимый результат: `parse_verdict`/преемник не содержит более
      одного regex/эвристики на форму ответа (acceptance criterion 3
      proposal.md).
- [ ] `scripts/review/ai_review.py::cmd_verdict` - `error_reason`/
      `transport_failed` сохраняют различение «транспортный сбой» (по
      `dsh_rc.txt`) от «невалидный ответ модели» (по результату разбора
      JSON), но само определение невалидности - через схему, не текстовые
      эвристики. Видимый результат: `error_reason` не растёт новыми
      текстовыми паттернами при следующем наблюдённом отклонении формы -
      либо ответ проходит схему, либо явный `error` без диагностики по
      подстроке.
- [ ] `scripts/review/test_ai_review.py` - тесты на прод-форме: архивные
      ответы прогонов 33567380398/33513671645 (markdown-обрамление,
      PR #184) и 33572445063 (транспортная HTTP_404, PR #193) переведены
      на новый формат ИЛИ, если исходные тексты были в старом текстовом
      контракте, добавлены их JSON-эквиваленты как новые прод-кейсы (с
      пометкой, что реальный прогон на новом контракте ещё не снят -
      честно, не выдавать миграцию тестов за живой прогон). Плюс новые
      кейсы: валидный JSON, JSON с лишним текстом вокруг, невалидный
      `verdict`, отсутствующее поле, fenced-обёртка. Видимый результат:
      мутация - откат валидации схемы красит все новые тесты (доказательство
      по стандарту PR #184/#193, acceptance criterion 5 proposal.md).
- [ ] `.github/workflows/ai-review.yml` - канал `steps.outputs` (answer/head)
      не меняется структурно (лимит ~1 МБ достаточен для JSON-блока меньше,
      чем текущая проза с задачами), но комментарий workflow обновляется,
      если меняется предположение про формат ответа. Видимый результат:
      живой прогон `workflow_dispatch` на тестовом PR даёт `ai:ok`/
      `ai:changes-requested`/`ai:failed` корректно на новом формате.

## 2. Контракт «PR - задача»: структурная сборка тела

- [ ] `scripts/worker/task.sh` - шаг 4 промпта (сейчас: текстовая
      инструкция «Первая строка тела PR - ровно "#$number"») заменяется
      на программную сборку: транспорт формирует `--body-file` сам,
      подставляя `#$number\n\n` перед содержимым, которое пишет агент
      (агент описывает работу в отдельном файле/выводе, транспорт
      склеивает). Видимый результат: PR, открытый автономным воркером,
      имеет `#N` первой строкой независимо от того, что написал агент в
      своей части - проверяется тем, что `contract_check.py` проходит без
      обращения к тексту, который сочинил агент, для этой конкретной
      проверки.
- [ ] `scripts/orchestra/contract_check.py` - остаётся финальной
      страховкой (defense-in-depth) для путей, не идущих через
      `task.sh` (ручное открытие PR человеком/другим агентом) - не
      убирается, но комментарий в коде уточняется: «для автономного
      воркера это второй рубеж, первый - структурная сборка в task.sh».
      Видимый результат: обновлённый docstring/комментарий, без изменения
      логики самой проверки (она остаётся нужна для не-воркерных путей).
- [ ] `.github/PULL_REQUEST_TEMPLATE.md` - уже содержит `#N` первой строкой
      (подтверждено, файл существует) - остаётся как подсказка для
      человека, использующего веб-форму; отдельно проверить (задача, не
      предположение), актуален ли текст инструкции-комментария после
      изменения task.sh (не должен противоречить новой механике).

## 3. Ревизия остальных мест разбора чужого текста регэкспом

- [ ] Составить перечень мест конвейера, где ответ модели/чужой системы
      разбирается regex/эвристикой без схемы на входе (кандидаты по
      данным этого исследования - `scripts/review/ai_review.py::TASK_OPEN_RE`/
      `TASK_CLOSE`/`FACT_RE`/`FENCE_CLOSE_RE`: блоки задач и шапка-факты
      комментария парсятся тем же классом построчного разбора, что и
      снятый в задаче 1 `VERDICT_RE` - решить для каждого отдельно, стоит
      ли переносить в ту же JSON-схему или оставить текстовым форматом
      осознанно, раз findings - объявленно свободная проза, см. proposal.md
      Out). Видимый результат: список в этой задаче или в отдельном issue
      с меткой `task`, по каждому пункту - решение «схема» или «оставить
      текстом, потому что...», не молчаливый пропуск.
- [ ] Для каждого места из списка, где решение «перенести в схему» -
      завести отдельную задачу пула (issue с меткой `task`), не расширять
      scope этого change бесконечно. Видимый результат: issue созданы,
      со ссылкой на этот change как источник правила.
