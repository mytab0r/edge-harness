## MODIFIED: Контракт ответа AI-ревью

~~Требование: ответ модели содержит машиночитаемую ПОСЛЕДНЮЮ строку ровно
`ВЕРДИКТ: approve` или `ВЕРДИКТ: rework` (маркеры markdown-обрамления
терпимы при парном совпадении); маркера нет, их два или он не последний -
вердикт `error`.~~

Требование: ответ модели - единственный блок валидного JSON по объявленной
схеме (поля: `verdict` - строго `"approve"` или `"rework"`; `findings` -
строка, свободная проза находок; `tasks` - список объектов `{title, body}`,
может быть пустым). Блок не сопровождается текстом до или после (весь
stdout DSH после обрезки служебных префиксов обязан парситься как один
JSON-документ). Разбор - одним проходом `json.loads` + явная проверка
обязательных полей и допустимых значений `verdict`; ответ, не прошедший
разбор, - вердикт `error` без дальнейших попыток эвристического
восстановления.

Сценарий: ответ модели - `{"verdict": "approve", "findings": "...",
"tasks": []}` без окружающего текста → вердикт `approve`, метка `ai:ok`.

Сценарий: ответ модели обёрнут в markdown code fence (` ```json ... ``` `)
→ извлечение fenced-блока перед `json.loads` предусмотрено разбором как
единственная явная, документированная нормализация (не эвристика под
наблюдённый случай, а часть объявленного формата: указано в
`ai_prompt.md`, что фенс - допустимая обёртка).

Сценарий: JSON невалиден, отсутствует обязательное поле или `verdict` не
равен `approve`/`rework` → вердикт `error`, метка `ai:failed`, без
попытки распознать вердикт по подстроке текста.

## MODIFIED: Различение транспортного сбоя и невалидного ответа модели

~~Требование: `error_reason`/`transport_failed` определяют по коду возврата
DSH и содержимому answer.txt, был ли вызов модели (rc dsh, пустой файл) или
модель ответила не по контракту.~~

Требование: два факта разной природы остаются раздельными полями, не
шагами последовательного разбора одного текста: код возврата процесса
`dsh` (`dsh_rc.txt`, записан `ai_dsh.sh`) определяет, был ли вызов модели
успешным на транспортном уровне; содержимое `answer.txt`, если вызов был
успешным, парсится по схеме JSON выше. `error` от невалидного JSON и
`error` от транспортного сбоя остаются различимыми в тексте комментария
PR (как и до этого изменения), но оба определяются проверкой на входе
(код возврата - факт до чтения текста; схема - факт при чтении текста),
а не последовательностью текстовых эвристик над одним и тем же answer.txt.

Сценарий: `dsh` вернул код 1 (транспортная ошибка провайдера, например
`HTTP_404`), `answer.txt` пуст → вердикт `error`, причина в комментарии -
«ревью не состоялось: сбой вызова модели», метка `ai:failed`.

Сценарий: `dsh` вернул код 0, `answer.txt` содержит текст, не являющийся
валидным JSON по схеме → вердикт `error`, причина в комментарии - «модель
ответила не по контракту», метка `ai:failed`; текстовое различие
сообщений об ошибке сохранено, механизм получения различия - разные
источники факта, не разные регэкспы над одним источником.

## ADDED: Схема ответа объявлена в промпте, а не только в парсере

Требование: `scripts/review/ai_prompt.md` содержит точное описание
ожидаемого JSON-формата (имена полей, допустимые значения `verdict`,
запрет текста вне блока) как часть контракта, который модель обязана
выполнить - формат объявлен на входе запроса к модели, а не выводится
парсером из наблюдённых прецедентов задним числом.

Сценарий: промпт правится (новое поле схемы, изменение формулировки) →
парсер и промпт меняются одним PR-диффом (одно место правды на оба конца
контракта), рассинхрон между тем, что промпт просит, и тем, что парсер
принимает, виден в ревью диффа, а не только в проде.

## ADDED: Тело PR - структурная сборка номера задачи

Требование: транспорт, открывающий PR от имени автономного воркера
(`scripts/worker/task.sh`), формирует тело PR так, что первая строка
`#N` подставляется программно (конкатенация номера задачи с текстом,
который сочиняет агент), а не входит в текст, который агент обязан
воспроизвести дословно по инструкции промпта. Контракт `#N` первой
строкой становится структурным свойством тела, которое транспорт
собирает, а не просьбой, которую агент может исполнить неточно.

Сценарий: воркер открывает PR на задачу #42 → тело PR начинается с `#42`
независимо от того, упомянул ли агент номер задачи в своей части текста;
`contract_check.py` проходит без дополнительных попыток агента угадать
формат.

Сценарий: агент открывает PR не через штатный путь транспорта (ручная
эскалация, нештатный сценарий) → `contract_check.py` остаётся
финальной страховкой (defense-in-depth), гейт слияния не ослабляется.
