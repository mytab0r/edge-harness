# Propose: контракт с чужой системой - схема на входе, не разбор на выходе

## Summary

Три раза за сутки (2026-08-31 - 2026-09-02) латали один и тот же регэксп
VERDICT_RE в scripts/review/ai_review.py, потому что контракт ответа
AI-ревьюера - свободный текст с последней строкой "ВЕРДИКТ: approve|rework",
и каждое новое отклонение модели от ожидаемой формы (markdown-обрамление,
пустой ответ, порядок строк) обнаруживается только постфактум, разбором уже
записанного текста. Правило, которое фиксирует это изменение: контракт с
чужой системой задаётся схемой на входе, а не проверкой на выходе; если
схему на входе поставить нельзя - результат оформляется артефактом с
валидацией в момент записи/чтения, а не свободной прозой с разбором потом.

## Problem / motivation

### Замер (класс проблемы, не единичный баг)

scripts/review/ai_review.py:56, VERDICT_RE = re.compile(r"^ВЕРДИКТ:\s*(approve|rework)\s*$")
- требует точную строку последней в тексте. Наблюдённые живые отказы одного
и того же класса ("модель ответила не в ожидаемой форме, парсер узнал об
этом только разобрав готовый текст"):

1. PR #159, #138 -> задача #183 -> PR #184 (2026-08-31/09-01). Модель
   отвечает "звёздочки-ВЕРДИКТ: approve-звёздочки" в markdown-обрамлении -
   исходный VERDICT_RE не совпадал, гейт ставил ai:failed без вины автора.
   Улика недетерминизма: прогон 33567380398 дал ai:failed, следующий прогон
   на той же голове - ai:ok. Исправлено расширением регэкспа: терпит парные
   маркеры обрамления (backreference), терпит точку в конце.
2. PR #190 -> задача #192 -> PR #193 (2026-09-02, тот же день, что и #184).
   dsh упал с транспортной ошибкой HTTP_404 (rc=1, прогон 33572445063),
   answer.txt остался пустым; verdict-шаг разобрал пустоту как "строки
   ВЕРДИКТ нет вообще" - тот же диагностический текст, что у нарушения
   контракта моделью, хотя причина другая (провайдер/транспорт, а не
   поведение модели). Исправлено новыми чистыми функциями transport_failed/
   error_reason, которые различают состояния ПОСЛЕ факта - снова разбор, не
   предотвращение.
3. Наблюдение владельца, 2026-09-02: вердикт написан первой строкой ответа,
   а затем модель продолжает текст. Живой случай на прогоне того дня -
   не подтверждено номером PR/issue: попытка найти PR #178 в трекере
   привела к другому PR ("Логин в морду dsh-edge не идёт по редиректу 303",
   #174/#178, не про вердикт); в трекере отдельного issue под это
   наблюдение не найдено. Формулировка правила ниже не полагается на этот
   пункт как на доказанный факт - он приведён как мотивирующий контекст с
   пометкой "не подтверждено", а не как третья закрытая улика.

Итог: два независимых latch-фикса регэкспа/постпарсинга за 2026-08-31 -
2026-09-02, оба устраняют симптом (парсер не узнал форму) после того, как
недоверенный ответ уже записан в файл и его пришлось разбирать. Третий
случай не закрыт уликой, но напрашивается в тот же класс по описанию.

### Второй пример того же класса: контракт "PR - задача"

scripts/orchestra/contract_check.py:79-102 - та же архитектура: требует,
чтобы строка тела PR начиналась с #N, и обнаруживает нарушение уже ПОСЛЕ
того, как PR создан (красная проверка на существующем PR, комментарий
fail() с меткой contract:failed). Отличие от вердикта: здесь подсказка
на входе частично уже есть - .github/PULL_REQUEST_TEMPLATE.md существует
(файл на диске подтверждён: find нашёл .github/PULL_REQUEST_TEMPLATE.md)
и содержит #N первой строкой с комментарием-инструкцией. Но фактическое
открытие PR автономным воркером идёт не через веб-форму (где GitHub
автоподставляет шаблон), а через "gh pr create --body-file файл" - тело
собирает сам DSH-агент по текстовой инструкции в промпте
(scripts/worker/task.sh:205: первая строка тела PR - ровно "#номер"),
не программно из аргументов скрипта. То есть подсказка на входе есть, но
это текст, который агент всё равно может проигнорировать/исказить - а
единственная страховка снова постфактум, contract_check.py на уже
созданном PR.

### Обратные примеры - как выглядит правильно (образец, не изобретать заново)

- scripts/git/task-branch - ветку физически нельзя создать от протухшей
  базы: скрипт сверяет git ls-remote с локальным origin/main ДО
  git switch -c и падает, если сервер разошёлся с локальным состоянием.
  Проверка входа блокирует некорректное действие, а не находит его после.
- .githooks/pre-commit - коммит от устаревшей базы не проходит: хук
  сверяет origin/main с текущим HEAD (git merge-base --is-ancestor) ДО
  того, как коммит попадёт в историю, а не после.

Оба примера проверяют условие ДО записи (создания ветки / коммита), а не
разбирают историю репозитория постфактум в поисках нарушения.

## Правило

Контракт с чужой системой задаётся схемой на входе (запрос заранее
ограничивает форму ответа так, что нарушение контракта становится
невозможным или структурно обнаружимым сразу), а не проверкой на выходе
(эвристика/регэксп разбирает уже произведённый свободный текст и гадает
о намерении автора). Если схему на входе поставить технически нельзя -
результат оформляется артефактом с валидацией в момент записи/чтения
(строгий формат, разбираемый одним проходом без эвристик, невалидный
разбор - явная ошибка, а не "попробуем ещё один паттерн"), а не свободной
прозой с последующим разбором.

## Scope

### In

- Контракт вердикта AI-ревью (scripts/review/ai_review.py,
  scripts/review/ai_prompt.md, scripts/review/ai_dsh.sh,
  .github/workflows/ai-review.yml): перевод с регэкспа по последней строке
  свободного текста на структурированный формат с валидацией в момент
  разбора.
- Контракт "PR - задача" (scripts/orchestra/contract_check.py,
  .github/PULL_REQUEST_TEMPLATE.md, промпт воркера
  scripts/worker/task.sh:205): распространение того же принципа - сборка
  тела PR из аргументов/шаблона там, где это возможно программно, вместо
  расчёта на то, что агент правильно скопирует инструкцию.
- Ревизия остальных мест конвейера, где чужой (модельный) текст разбирается
  регэкспом/эвристикой без схемы на входе - перечислить и решить по каждому
  отдельно (задача в tasks.md), не переписывать всё разом в этом изменении.

### Out

- Миграция промпт-инженерии находок ревью (текст замечаний, задач в
  беклог) - сама проза findings остаётся свободным текстом, схема нужна
  только вердикту и структурным полям (verdict/reason), не содержательному
  тексту ревью. Замена структуры прозы на схему увеличивала бы стоимость
  промпта и не решает названный класс.
- Замена провайдера/маршрутизация LLM - вне рамок, курс закрыт (см.
  docs/research/30-rejected-alternatives.md, п.1/п.7/п.8/п.9/п.10).
- Chat-completions response_format/json_schema/tool-calling как прямой
  рычаг через DSH - не подтверждён (см. "Риски / неизвестности" ниже),
  поэтому не входит в объём как гарантированное решение; design.md
  рассматривает его как развилку, а не как принятое решение.
- Устранение расхождения openspec/specs/journal-tasks-hands.md с кодом
  (заявленный в proposal.md ai-review-gate раздел "AI-ревью (второй
  гейт)", п.30-34, в спеке отсутствует - файл обрывается на п.29). Это
  отдельное белое пятно, найденное по ходу этой работы, не чинится здесь -
  см. tasks.md, пункт про issue с меткой white-spot.

## Acceptance criteria

1. Живой прогон AI-ревью с ответом модели, обрамлённым markdown
   (воспроизводит форму PR #138), проходит валидацию без latch-фикса
   регэкспа: проверяется прогоном тестов на прод-форме ответа
   (scripts/review/test_ai_review.py, кейс на архиве ответа прогона
   33567380398) - тест зелёный без специального терпимого regex-паттерна
   под конкретную форму обрамления.
2. Пустой/транспортно-битый ответ (форма прогона 33572445063, HTTP_404,
   answer.txt пуст) и "модель ответила, но не по контракту" дают разные,
   различимые на входе состояния без специального различающего кода в
   verdict-шаге постфактум - формат ответа сам обязывает наличие поля
   reason/кода ошибки, не текстовая эвристика по хвосту.
3. Невалидный по схеме ответ (например, вердикт не последним полем, лишнее
   поле, обрамление) - отклоняется ОДНИМ проходом валидации (jsonschema/
   json.loads + explicit schema check), без последовательности "попробуй
   паттерн A, потом паттерн B" - проверяется тем, что parse_verdict (или
   его преемник) в финальном коде не содержит более одного regex/эвристики
   на форму ответа.
4. contract_check.py для одного из проверяемых случаев (тело PR не
   начинается с #N) сопровождается механизмом, который либо не даёт этой
   ошибке случиться (программная сборка тела PR из номера задачи в
   scripts/worker/task.sh, не текстовая инструкция), либо ловит её раньше
   открытия PR (pre-push/pre-create проверка) - выбор фиксируется в
   design.md с обоснованием цены.
5. Мутационное доказательство для новых валидаторов: откат схемы/валидации
   красит специально добавленные тесты на прод-форме (как это уже сделано
   в PR #184/#193 - тот же стандарт доказательства, распространённый на
   новый код).
6. docs/decisions/ получает новый ADR с зафиксированным правилом и ссылкой
   на этот change - правило видно не только в коде, но и в месте, где ищут
   архитектурные решения.

## Risks / unknowns

- Не подтверждено: управляем ли мы через DSH параметрами
  response_format/json_schema/tool-calling запроса к провайдеру.
  Проверено: dsh-llm-deepseek читает из env только DEEPSEEK_BASE_URL,
  DEEPSEEK_API_KEY (+DEEPSEEK_REASONING) - не читает и не пробрасывает
  ничего похожего на response_format (docs/research/10-dsh-architecture.md:504-506).
  Выбор модели/maxTokens - через settings namespace agent-default-model и
  cordis.patch.yml (scripts/lib/dsh-ci.sh:87-106, dsh_patch_profile), там
  тоже нет структурного параметра формата ответа. abstract class LlmAdapter
  с abstract stream() (docs/research/10-dsh-architecture.md:114) - контракт
  метода stream() глубже не изучен: не исключено, что адаптер сам
  поддерживает это внутри, но ни один research-документ, ни код в этом
  репозитории такого рычага не называют. Названо "не подтверждено", не
  "невозможно" - см. design.md, развилка (а).
- Единственный физический канал между недоверенным job review и доверенным
  job verdict в текущей архитектуре - steps.outputs
  (.github/workflows/ai-review.yml:57-59,123-132), лимит около 1 МБ. Файл,
  записанный агентом инструментом tool-fs в cwd недоверенного job'а, НЕ
  пересекает границу ВМ без явного actions/upload-artifact/
  download-artifact - это новый механизм, которого сейчас нет. Профиль
  headless даёт агенту fs-инструменты (tool-fs, tool-str-replace-editor,
  docs/research/10-dsh-architecture.md:100), то есть технически агент
  МОЖЕТ писать файл - вопрос только в том, как этот файл долетает до
  доверенного job'а. Развилка (б) в design.md разбирает оба варианта
  честно, с ценой каждого.
- Прогон, подтверждающий наблюдение "вердикт написан первым, продолжен
  текстом" (PR #178), не идентифицирован уликой - см. Problem, пункт 3.
  Если владелец найдёт номер прогона/PR, стоит добавить его как третий
  замер после проверки.
- Поддержка структурированного вывода зависит от провайдера И модели.
  Провайдер сейчас DEEPSEEK_BASE_URL=https://integrate.api.nvidia.com/v1,
  модель - vars.DEEPSEEK_MODEL (repo var, значение не читано этим агентом
  намеренно - не задача этого исследования проверять текущее значение).
  Поддержку response_format/json_schema этой связки провайдер+модель
  нельзя установить без реального запроса - не проверено и не проверяется
  в рамках propose-фазы (кода не пишем).
