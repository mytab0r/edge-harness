## MODIFIED: Конвейер (оркестратор)

~~15. PR сливается только при: зелёные обязательные проверки, метка
    `review:ok`, отсутствие конкурирующего открытого PR на ту же задачу.~~

15. PR сливается только при: зелёные обязательные проверки, ОБА
    вердикта-метки ревью — `review:ok` И `ai:ok` (два независимых гейта,
    ADR 0007: детерминированное ревью и AI-ревью; формулировка гейта — одно
    место правды `review_labels.merge_label_gate`), отсутствие
    конкурирующего открытого PR на ту же задачу.

Уточнение, не смена поведения: `merge_label_gate` требовал оба вердикта уже
с ADR 0007 (задача #18) — этот пункт спеки называл только первый гейт и
разошёлся с кодом до данной дельты. Явная формулировка нужна здесь и
сейчас: новый п.17 (ниже) ссылается ровно на это условие «оба вердикта
зелёные», и без него описывал бы правило, которого сама спека нигде не
формулирует.

    проверки; behind-ветки обновляются из main токеном с правом зажигать

17. PR без задачи из пула не проходит контракт; исключения — метка
    `orchestra:skip`; PR от dependabot проходят без задачи, их судьбу решают
    проверки; behind-ветки подтягиваются из main серверным токеном (с правом
    зажигать проверки) ВЫБОРОЧНО — только PR, у которого либо уже стоят оба
    вердикта из п.15 (`review:ok` И `ai:ok` — он реально близок к слиянию),
    либо PR помечен `conflict` (подтягивание может расшить конфликт).
    PR без обоих вердиктов, в доработке или с `ai:changes-requested`
    автоматически не подтягивается — одно место правды предиката,
    `review_labels.should_update_branch`, общее для обеих точек вызова
    (после слияния и при `mergeable_state == "behind"` в очереди слияния).

    Газ (обязателен, автоматический): предикат не хранит состояния — он
    читает текущие labels PR при каждом прогоне оркестратора. Как только PR
    получает оба вердикта из п.15 или помечается `conflict`, САМЫЙ
    СЛЕДУЮЩИЙ прогон снова начинает его подтягивать без ручного
    вмешательства.

Сценарий: раньше подтягивание было безусловным — до 96 раз в сутки
(`orchestra.yml`, cron `*/15`), каждый раз push-ем (merge-коммитом) в чужую
ветку, что триггерило `pull_request: synchronize` → снятие всех `ai:*`-меток
→ повторный дорогой прогон `ai-review.yml`, даже когда содержимое PR не
менялось вовсе. Точный подсчёт по окну, которое называет issue #252
(2026-09-02T20:00 → 2026-09-03T10:30, 14.5 ч): 142 прогона `ai-review.yml`
(`gh api ".../actions/workflows/ai-review.yml/runs?created=2026-09-02T20:00:00Z..2026-09-03T10:30:00Z"
--jq .total_count`). Пока эта дельта была в работе, слияние #246 вызвало
волну ~19 одновременных прогонов на один ключ провайдера и рейт-лимит
(`ai:failed`, `RATE_LIMIT: Rate limit reached for requests`) у шести
открытых PR — тот же класс дефекта, живое подтверждение. Критерий свободы
задачи (п.26-28) и контракт (первая половина этого пункта) этой дельтой не
меняются — меняется только условие подтягивания behind-веток.
