# selective-branch-update: выборочное подтягивание веток из main (#252)

Задача: #252. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`scheduler.update_remaining_pulls` и `merge_queue` (ветка `mergeable_state
== "behind"`) безусловно вызывали `gh pr update-branch` для всех открытых
недрафт PR — до 96 раз в сутки (`orchestra.yml`, cron `*/15`). Каждый такой
вызов — push (merge-коммит) в чужую ветку → GitHub шлёт `pull_request:
synchronize` → `pr-review.yml` перезапускается и снимает все `ai:*`-метки
(`ai_verdicts_to_drop`) → при сохранившемся `review:ok` через `workflow_run`
стартует дорогое `ai-review.yml`. PR, которому рано сливаться (нет
вердиктов, в доработке, `ai:changes-requested`), от подтягивания не
выигрывает ничего — только теряет валидный вердикт и жжёт AI-квоту
вхолостую. Точный подсчёт по окну, которое называет issue #252
(2026-09-02T20:00 → 2026-09-03T10:30): `gh api
"repos/mytab0r/edge-harness/actions/workflows/ai-review.yml/runs
?created=2026-09-02T20:00:00Z..2026-09-03T10:30:00Z" --jq .total_count` →
142 прогона. Пока эта дельта была в работе, слияние #246 действительно
породило волну ~19 одновременных прогонов на один ключ провайдера и
рейт-лимит (`ai:failed`, `RATE_LIMIT: Rate limit reached for requests`) —
живое подтверждение того же класса дефекта.

`openspec/specs/journal-tasks-hands.md` расходится с новым поведением в
двух пунктах, а не в одном:

- п.17 прямо фиксирует старое поведение: «behind-ветки обновляются из main
  токеном с правом зажигать проверки» — без всякого условия. Не поправить
  его значит оставить документированное разрешение вернуть безусловное
  подтягивание законно, со ссылкой на спеку.
- п.15 описывает гейт слияния как «`review:ok`» — только первый гейт, хотя
  ADR 0007 и код (`review_labels.merge_label_gate`) требуют ОБА вердикта,
  `review:ok` И `ai:ok`. Новый предикат `should_update_branch` стоит именно
  на этом двойном условии («оба вердикта зелёные» = «близок к слиянию») —
  если спека продолжает говорить только про `review:ok`, она описывает
  правило, которого в коде нет уже давно (ADR 0007 датирован раньше этой
  задачи), и новый пункт 17 будет ссылаться на условие, которое сама спека
  нигде не формулирует верно.

## Что делается

Одно место правды — `scripts/lib/review_labels.py::should_update_branch(labels)`
(рядом с `merge_label_gate`, где уже живёт правда о вердиктах):

```python
def should_update_branch(labels) -> bool:
    names = _names(labels)
    if CONFLICT_LABEL in names:
        return True
    return merge_label_gate(names) is None
```

- **п.17** переформулирован: behind-ветка подтягивается СЕРВЕРНЫМ токеном
  только если PR либо помечен `conflict` (подтягивание может расшить
  конфликт), либо у него уже стоят оба вердикта (`review:ok` И `ai:ok`) —
  он реально близок к слиянию, и подтягивание готовит его к следующему
  обходу очереди. Тот же предикат применяется в `update_remaining_pulls`
  (после слияния) — не две копии условия.
- **п.15** уточнён явной ссылкой на оба вердикта (`review:ok` И `ai:ok`,
  ADR 0007) вместо одного `review:ok` — спека начинает совпадать с тем, что
  уже год как проверяет `merge_label_gate`, и на чём стоит новый п.17.
- Газ объявлен текстом в самой спеке (не только в коде): как только PR
  получает оба вердикта или помечается `conflict`, следующий прогон
  оркестратора снова подтягивает его без ручного вмешательства — предикат
  не хранит состояния, читает labels заново при каждом вызове.
- `docs/agents/LABELS.md`, строка метки `conflict`: добавлено следствие —
  метка теперь дополнительно делает PR кандидатом на серверное подтягивание
  (второй, самостоятельный газ у той же метки, помимо `mark_conflicts`) —
  и находка того же ревью (#270): раньше метку только ставили, не снимали
  никогда, из-за чего этот газ был односторонним; `mark_conflicts` теперь
  снимает её по `review_labels.CONFLICT_CLEAR_STATES` (`null`/`unknown` не в счёт).

## Что вне рамок

- Направления 1 и 3 из issue #252 (пропуск AI-ревью при неизменном диффе;
  перенос вердикта на голову, изменённую только merge-коммитом) — не
  реализуются, issue явно называет направление 2 (выборочное подтягивание)
  самым дешёвым и достаточным для устранения причины.
- Гвардия на содержательно пустой/отрицательный PR (раздел issue «Отдельно»)
  — независимая задача, пересекается с #217, не входит в эту дельту.
- `scripts/orchestra/stall_detector.py`, `scripts/orchestra/repo_invariants.py`,
  `scripts/review/ai_review.py` — не трогаются, их правят другие агенты.
