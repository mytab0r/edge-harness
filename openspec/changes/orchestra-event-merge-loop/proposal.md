# orchestra-event-merge-loop: уйти с schedule `*/15` на событийный триггер и цикл слияний внутри прогона (#297)

Задача: #297. Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Симптом

`.github/workflows/orchestra.yml` держит `cron: "*/15 * * * *"` (96 прогонов/
сутки формально), но живая доставка расписания на этом репозитории измерена
в **~6.7%** (31 из ~465 за 116.3 ч, `docs/research/21-github-actions.md`,
раздел «Замер schedule на этом репозитории»). Пульс из Durable Object
(`cf-worker/src/harness.ts::alarm`) дублирует расписание собственным
`workflow_dispatch` и даёт основную массу реальных прогонов — но это тоже
периодика, разница только в канале, и она зависима от здоровья самого DO
(2026-09-05 пульс вставал на часы из-за исчерпания квоты `rows_read`).
Одновременно `merge_queue` сливает ровно **один** PR за запуск (сериализация
намеренная — после слияния меняется база остальных PR). Комбинация «редкие
прогоны + один PR за прогон» означает, что готовый к слиянию PR ждёт часами
даже когда конвейер формально здоров.

## Что делается

### 1. Событийный триггер — `workflow_dispatch` из самого конвейера ревью, не `labeled`

Вариант «пометить PR и слушать `pull_request: types: [labeled]`» отвергнут
ФАКТОМ, а не предположением: этот же репозиторий уже измерил (2026-08-31,
`docs/research/21-github-actions.md`, раздел «Метка, поставленная
GITHUB_TOKEN, не создаёт событий») — `check_pr.py` ставит `review:ok`
токеном job'а, `on: pull_request: types: [labeled]` на PR #138 НЕ сработал
(антирекурсия GitHub: события от `GITHUB_TOKEN`, кроме `workflow_dispatch`
и `repository_dispatch`, не создают новый run). Тот же документ называет
рабочий обход для этого класса: `workflow_dispatch`/`repository_dispatch` —
единственное подтверждённое живьём исключение (`scheduler.py` уже дёргает
`worker.yml` тем же способом, и раны происходят).

Поэтому: `pr-review.yml` (job `review`, ставит `review:ok`/
`review:changes-requested`) и `ai-review.yml` (job `verdict`, ставит
`ai:ok`/`ai:changes-requested`/`ai:failed`) получают по одному
дополнительному шагу — `gh workflow run orchestra.yml --ref main` под
`GH_TOKEN: ${{ github.token }}`. `orchestra.yml` уже слушает
`workflow_dispatch` (не менялось) — новых триггеров в самом файле не
требуется, будит его сторона, которая меняет метки. Диспатч безусловный
(не только при `*:ok`): `review:changes-requested`/конфликт тоже может
разблокировать очередь (например снять `conflict` у другого PR при
подтягивании), а `orchestra.yml` сам дёшево решает, есть ли что сливать.

`schedule` остаётся как страховка на случай, если событие потерялось
(сетевой сбой на шаге диспатча, ручной пуш без обоих workflow) — **но на
него больше не рассчитывают**: следующий, кто читает этот файл, не должен
«чинить» интервал `*/15`, это сознательно оставленный резерв, а не рабочий
канал (записано явно в шапке `orchestra.yml` и здесь).

### 2. Цикл слияний внутри одного прогона

`main()` планировщика раньше звал `merge_queue()` (сериализация «один PR за
проход») ровно один раз. Теперь — `merge_loop()`: слить готовый → подтянуть
следующего (`update_branch`) → дождаться его проверок → слить, пока есть что
сливать. Два потолка, обе константы — одно место правды в
`scripts/orchestra/scheduler.py`:

- `MERGE_LOOP_MAX_MERGES = 5` — потолок числа слияний за один прогон;
- `MERGE_LOOP_TIMEOUT_SECONDS = 20 * 60` — общий бюджет времени цикла (не
  всего `main()`); между проходами, где что-то обновилось, но не слилось —
  пауза `MERGE_LOOP_POLL_SECONDS = 30` перед повтором.

Останов цикла — любое из: потолок слияний, таймаут, проход без прогресса
(не слил и не обновил ветку — без нового внешнего события следующая попытка
прямо сейчас даст тот же результат).

### 3. Сериализация не сломана

`merge_queue()` по-прежнему обновляет НЕ БОЛЬШЕ ОДНОЙ ветки за один свой
проход (инвариант #252/#288 не тронут — тест
`test_merge_queue_two_behind_prs_share_one_update_branch_slot` не менялся).
Слот `update_branch` раньше сбрасывался один раз в начале `main()` (одно
обновление на весь прогон); теперь сбрасывается заново КАЖДЫЙ проход цикла
(`reset_update_branch_budget()` внутри `merge_loop`) — цикл способен
обновить несколько РАЗНЫХ PR подряд, но не больше одного за проход. Это
осознанно ослабляет старое ограничение «одно обновление на весь прогон»
(#252, третий заход): причина, по которой оно было строгим (в 2026-09-02
подтягивание сбрасывало `ai:ok` БЕЗУСЛОВНО на каждый пуш), больше не
действует — `ai-verdict-survives-merge` (#252/#294, уже слито) сохраняет
`ai:ok` при чистом подтягивании main без изменения диффа PR.

## Что вне рамок

- Причина, по которой сам DO-пульс (`cf-worker`) не должен больше быть
  единственным источником регулярности, не устраняется этой дельтой —
  #297 убирает ЗАВИСИМОСТЬ цикла слияний от периодики вообще (событие
  вместо такта), не чинит DO/квоты `rows_read` (отдельная тема, не эта
  задача).
- Egress GitHub API из воркера морды (#133) — не входит: событие в этой
  дельте создаёт GitHub Actions job (`gh workflow run` из `GH_TOKEN` внутри
  уже идущего рана), не морда напрямую.
