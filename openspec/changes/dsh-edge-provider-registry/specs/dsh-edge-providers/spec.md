# Спека: реестр LLM-провайдеров морды (`llm-pi-ai`)

Источник поведения: серверный плагин реестра по образцу `runner-bridge`
(`plugins-src/runner-bridge/`, `server: true, client: false`), монтируемый
существующим `installEdgePlugins` (патч 0002 серии `dsh-edge-plugin-system`,
которая этим плагином не расширяется), settings-namespace `llm-pi-ai`, шов
`ctx.llm` ядра DSH (`@deepseek-ai/dsh-llm`,
`registerAdapter`/`registerConfigurableProviders`).
Домен отдельный от [journal-tasks-hands](../../../specs/journal-tasks-hands.md)
(журнал/задачи/руки); эта спека — про то, как морда управляет провайдерами
модели, не про доставку событий. Проверяется тестами `dsh-edge/` и живым
Settings UI морды.

## Namespace и схема

1. Морда обслуживает settings-namespace `llm-pi-ai` со схемой
   `providers.<route-id>`: `baseURL` (обязателен, http(s) — иначе транспорт
   молча подставил бы свой эндпоинт по умолчанию и унёс ключ на чужой адрес),
   `models[]` (каждый элемент — `id` обязателен и уникален в маршруте,
   `name?`/`contextWindow?`/`maxTokens?` опционально), `displayName`?/`api`?/
   `apiKeyEnv`? — опциональны: штатный UI пишет частичные профили, а
   отсутствующие поля выводятся (имя — из directory-каталога, протокол —
   единственный `openai-completions`, ссылка ключа — производная
   `<ROUTE>_API_KEY`).
2. Namespace обслуживается собственным кодом морды (не пакетом
   `dsh-llm-pi-ai`/`@earendil-works/pi-ai`) — обязано соответствовать
   контракту, который ожидает штатный клиентский Settings UI апстрима
   (создание провайдера пишет буквально в namespace `llm-pi-ai`).
3. `apiKeyEnv` в записи `providers.<route-id>` — ссылка на credential ref,
   разрешаемый существующим механизмом `edge-credentials.ts`; значение
   ключа никогда не попадает в settings-namespace и не сериализуется в
   ответ API настроек.

## Регистрация адаптеров

4. На старте и на каждое изменение namespace `llm-pi-ai` система строит по
   одному инстансу переиспользуемого OpenAI-compat адаптера на каждую запись
   `providers.<route-id>` и регистрирует его отдельным вызовом
   `ctx.llm.registerAdapter([route-id], adapter)` — хук `options()` адаптера
   не получает provider-аргумент, поэтому один инстанс не может обслуживать
   разные эндпоинты. Directory-канал (то, что читает Settings UI) подменяется
   атомарно одним вызовом `DirectoryRegistrationHandle.replace`; отказ
   регистрации одного маршрута не мешает остальным и не роняет морду.
5. Существующий провайдер `deepseek-official` монтируется отдельным штатным
   вызовом, код его монтажа этой системой не изменяется; коллизия route-id
   реестра с `deepseek-official` или с другим route-id реестра —
   `DUPLICATE_ADAPTER`.
6. Коллизия provider id не имеет права молча выигрывать/проигрывать.
   Основной слой — отказ ПРИ ЗАПИСИ: validate-хук settings-namespace
   отклоняет `settings.mutate` с текстом, который штатный UI показывает в
   карточке. Остаточные слои: раздел, не прошедший schema+validate, валит
   регистрацию namespace целиком при монтировании (fail loud, инсталл-статус
   `failed` пишет патч 0002); раздел, прошедший schema+validate, но
   нерезолвимый в соединение, пропускается при старте с громким `console.error`,
   остальные маршруты продолжают работать, DO не падает.
7. Изменение состава провайдеров (добавление/удаление через UI) — атомарная
   подмена набора directory-записей у уже существующего хендла
   (`DirectoryRegistrationHandle.replace`), без гонки «часть старых маршрутов
   ещё жива, часть новых уже есть»; сами адаптеры снимаются/поднимаются
   поштучно, правка настроек живого маршрута доходит до запроса без
   перерегистрации (живое соединение перечитывает раздел на каждую операцию).
8. Провайдеры, для которых можно создать конфигурацию, но которые ещё не
   настроены, публикуются через directory-канал (`registerConfigurableProviders`)
   отдельно от списка уже смонтированных адаптеров.
8a. Смена набора провайдеров (`handle.replace`) и смена состояния провайдера
    между `configured`/`configured_but_rejected` публикуются событием
    журнала — переход между провайдерами обязан быть видимым (в
    журнале/сессии), не тихим; логика выбора, КОГДА переключаться
    (failover/cooldown/приоритет), остаётся вне рамок этой спеки (см. «Вне
    рамок этой спеки»), реестр публикует только факт смены.

## Устойчивость к отказам

9. Некорректный `baseURL` или недействительный ключ у одного провайдера не
   останавливает морду и не мешает работе остальных провайдеров; ошибка
   видна владельцу в Settings UI.
10. Состояние каждого провайдера реестра — одно из трёх текстуально
    различимых значений, не двух: `not_configured` (route-id не заведён
    владельцем), `configured_but_rejected` (провайдер заведён, но ход к нему
    отвечает отказом — 401 либо явный лимит квоты вида
    `RATE_LIMIT: Weekly/Monthly Limit Exhausted`), `all_providers_failed`
    (все заведённые провайдеры одновременно в `configured_but_rejected`).
    Различение обязательно, потому что три состояния лечатся тремя разными
    действиями владельца: `all_providers_failed` — громкое и текстуально
    отличимое состояние от «провайдер не настроен» (fail loud, не
    silent-wrong), не подтип общей ошибки.
11. Настройки namespace `llm-pi-ai` переживают рестарт Durable Object без
    участия владельца (хранение — DO storage, тот же механизм, что у
    остальных настроек морды).

## Креды

12. Ключи провайдеров реестра хранятся исключительно в DO storage/секретах
    воркера; ни один шаг обработки (регистрация, экспорт для раннеров,
    логирование ошибок) не кладёт значение ключа в репозиторий или в
    диагностический вывод, видимый вовне.
13. Механизм кредов (`edge-credentials.ts`) обслуживает провайдеров реестра
    без специальной ветки под конкретный ref — существующий generic
    `resolve(ref)`/`set(ref, value)` покрывает произвольное число
    провайдеров без изменения кода.

## Раннеры

14. Раннеры (`scripts/lib/dsh-ci.sh` и потребители) используют тот же набор
    провайдеров и тот же приоритет, что видит владелец в морде; расхождение
    «в морде один набор/порядок, в раннере другой» не может возникнуть по
    построению (единственный экспортируемый источник правды, не два
    независимых канала чтения одного значения).
15. Отсутствие или неполнота экспортированного набора при старте раннера —
    громкий отказ, а не молчаливая работа с частью данных или зашитым
    дефолтом.

## Гвардия завязки на клиентский литерал апстрима

16. Деплой морды проверяет присутствие строкового литерала `"llm-pi-ai"` в
    собранном клиентском бандле и падает громко с диагностическим
    сообщением, если апстрим переименовал этот литерал в новом релизе —
    класс «кнопка создания провайдера тихо умирает после бампа пина»
    закрыт мутационно проверенной гвардией, а не наблюдением постфактум.

## Вне рамок этой спеки

- Маршрутизация между провайдерами, виртуальная модель `combo/auto`,
  cooldown, приоритет как исполняемая логика failover — отдельный домен
  (плагин владельца), эта спека описывает только реестр, из которого он
  берёт данные.
- Потолок токенов как свойство модели (`models[].maxTokens`) — поле в
  схеме существует, но перенос текущей глобальной константы в него не
  описывается этой спекой.
