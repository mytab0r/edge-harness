## 1. Ядро: settings-namespace + реестр адаптеров

- [~] **Тонкий сквозной разрез** — закрыт #114 КРОМЕ живого хода. Серверный плагин по образцу `runner-bridge`
      (`plugins-src/runner-bridge/`: `package.json`, `server/index.js`,
      README), запись в `dsh-edge/plugins.json` (`"server": true, "client":
      false`, релизный тарбол + sha256-пин), монтируется существующим
      `installEdgePlugins` из патча 0002 — **НЕ новый upstream-патч**
      (design «Форма носителя»: патч-серия и так у порога `PATCHES.md`,
      точка монтажа уже есть). Плагин читает settings-namespace `llm-pi-ai`
      (изначально с ОДНОЙ тестовой записью `providers.<id>`), строит
      `DeepSeekAdapter` из её `baseURL`/`apiKeyEnv`, вызывает
      `ctx.llm.registerAdapter([id], adapter)` +
      `ctx.llm.registerConfigurableProviders([...])`. Доказательство: в
      собранной морде (source-build, не npm-префаб) провайдер виден в
      пикере моделей и отвечает на реальный ход. Это разрез через все слои
      (namespace → плагин → реестр → пикер → живой ответ) раньше, чем любая
      из задач ниже. **Отдельная строка доказательства (design «Форма
      носителя», допущение блокера 2):** плагин монтируется в хвосте
      `initialize()` ПОСЛЕ штатного монтажа `dshLlmDeepseek`
      (`session-store.ts:243`) — тот же прогон обязан подтвердить, что
      порядок монтажа (штатный провайдер раньше, плагин реестра позже) не
      мешает пикеру видеть оба провайдера одновременно.
- [ ] Схема namespace `llm-pi-ai.providers.<route-id>` полностью: `displayName`,
      `api` (`openai-completions` для OpenAI-compat), `baseURL`, `apiKeyEnv`,
      `models[]` (`id`, `name?`, `contextWindow?`, `maxTokens?`) — по
      `docs/research/10-dsh-architecture.md`, раздел 10.
- [x] Цикл регистрации на N записей: один `DeepSeekAdapter` на route-id,
      `registerAdapter` с полным списком provider id, `registerConfigurableProviders`
      с directory-записями для незанятых (кнопка «Add» становится активной).
      (#114; отклонение по форме вызова — design «Девиации», п.1: N вызовов
      `registerAdapter([route], adapter)` + атомарный `directory.replace`.)
- [ ] Изоляция коллизии `DUPLICATE_ADAPTER`: id из реестра, совпавший с
      `deepseek-official` или с другим id реестра — громкий `console.error` +
      статус `failed` в DO storage (прецедент `dsh-edge-plugin-system`,
      «Рантайм: инсталл и изоляция»), инсталл остальных продолжается, DO не
      падает.
- [x] Реакция на изменение namespace (владелец добавил/удалил провайдера
      через UI) — `handle.replace(providers)`, без пересоздания хендла.
      (#114: directory.replace атомарен; адаптеры — dispose/register по маршруту,
      правка baseURL/ключа доходит до запроса без перерегистрации — живой
      `options()` перечитывает раздел.)
- [~] Существующий провайдер `deepseek-official` — код монтажа
      (`session-store.ts:243`, `session-store.ts:115`) не меняется вообще;
      регрессионный тест: после добавления второго провайдера первый
      по-прежнему отвечает на ход с прежним provider id. (#114: код монтажа
      не тронут; интеграция доказывает active+каталог deepseek-official рядом
      с zhipu; сам ход — за #158.)
- [ ] Регрессионный тест на `edge-credentials.ts`: ноль строк diff в файле;
      креды нового провайдера читаются/пишутся через существующий generic
      `resolve(ref)`/`set(ref, value)` без новой спецветки.
- [ ] Три различимых состояния провайдера (spec.md требование 10, design
      «Три различимых состояния отказа, не два»): `not_configured` /
      `configured_but_rejected` (401 либо `RATE_LIMIT: Weekly/Monthly Limit
      Exhausted`) / `all_providers_failed` — текстуально разные значения
      статуса, не подтипы одной ошибки; `all_providers_failed` вычисляется,
      когда все заведённые провайдеры одновременно `configured_but_rejected`.
- [ ] Событие видимости перехода (spec.md требование 8a, design «Видимость
      перехода»): смена набора (`handle.replace`) и смена состояния
      провайдера между `configured`/`configured_but_rejected` публикуются
      событием журнала — не логика failover, только факт смены.

## Границы

- Носитель реестра — серверный плагин по образцу `runner-bridge`
  (`server: true, client: false`), не новый upstream-патч; патч-серия
  `dsh-edge/patches/000N-*.patch` этим change не расширяется (см. раздел 1,
  design «Форма носителя», «Отвергнутые варианты внутри change» — «пятый
  upstream-патч»).
- Плагин владельца `combo/auto` (маршрутизация, failover, cooldown) — не
  часть этих задач; реестр только предоставляет `llm.providers` и
  экспортированный приоритет как данные.
- Свой клиентский DSH-плагин (вариант б) — не создаётся в рамках этого
  change; условие возврата — гвардия раздела 2 покраснела на реальном
  апстримном релизе, не по прогнозу.
- #157 (потолок токенов как свойство модели) и #155 (дефолтная модель из
  морды) — не закрываются здесь; раздел 1 создаёт поле `maxTokens` в схеме,
  не переносит в него существующую константу.
