## Форма носителя: серверный плагин, не upstream-патч

Реестр монтируется как серверный плагин по образцу `runner-bridge`
(`plugins-src/runner-bridge/`: `package.json`, `server/index.js`, README),
запись в `dsh-edge/plugins.json` — `"server": true, "client": false`,
релизный тарбол + sha256-пин, тот же конвейер `installEdgePlugins`, что уже
несёт `hello`/`runner-bridge`/`plugin-manager`. **Не новый upstream-патч.**

Причина выбора: точка монтажа владельческих плагинов уже смонтирована
патчем `0002-edge-plugins-module.patch` — `installEdgePlugins(storage)` в
хвосте `EdgeSessionStore.initialize()`, ПОСЛЕ штатного монтажа
`dshLlmDeepseek` (`session-store.ts:243`); плагин получает `ctx.llm` уже
доступным через `this.context.plugin(entry.plugin)`. Патч-серия при этом уже
стоит у собственного порога: `dsh-edge/PATCHES.md` объявляет предел «больше
шести патчей или любой патч >100 содержательных строк», патч 0004 уже на
уровне ~120 строк («при первом же расширении шва — выносить в отдельный
модуль или пересматривать серию против форка»). Реестр провайдеров по объёму
(~250-400 строк) не патч у порога, а 2.5-4× сверх него — пятый патч такого
размера был бы прямым нарушением собственного правила репозитория, при уже
существующей точке входа, которая не требует патча вовсе. См. «Отвергнутые
варианты внутри change» ниже — «пятый upstream-патч».

**Допущение, которое это решение делает и которое проверяет задача 1
tasks.md:** пикер моделей видит адаптеры, зарегистрированные плагином,
смонтированным ПОСЛЕ штатного монтажа `dshLlmDeepseek` в хвосте
`initialize()` — то есть порядок монтажа (сначала штатный провайдер, затем
плагин реестра) не мешает видимости обоих в `llm.providers`. Это тот же
тонкий сквозной разрез, что уже описан в tasks.md раздел 1 (namespace →
плагин → `registerAdapter` → пикер → живой ход), отдельной задачи не нужно —
явная строка доказательства добавлена туда же. Порядок монтажа плагина
относительно видимости в пикере ранее нигде не проверялся живым прогоном —
см. «Не подтверждено», новый пункт 6.

```
Settings UI морды (штатный, БЕЗ изменений)
  │ ProviderEditor.applyOnce(): ns = namespace.ns (динамический!) → api.settings.mutate({ns, ...})
  │ CustomProviderCard: NS$1 = "llm-pi-ai" (жёсткий литерал клиента)
  ▼
DO storage: settings namespace "llm-pi-ai" ── providers.<route-id>: {displayName, api, baseURL, apiKeyEnv, models[]}
  │
  ▼
наш серверный плагин (installEdgePlugins, хвост EdgeSessionStore.initialize(),
                       после монтажа dshLlmDeepseek — прецедент runner-bridge)
  │  читает namespace "llm-pi-ai" при старте и на изменение
  │  на каждый route-id: new DeepSeekAdapter({baseURL, apiKeyEnv: <ref>})
  ▼
ctx.llm.registerAdapter([route-id], adapter)   ──▶  ctx.llm.registerConfigurableProviders([...])
  │  коллизия id → LlmError DUPLICATE_ADAPTER (all-or-nothing)
  │  смена набора на ходу → handle.replace(providers)
  ▼
llm.providers  (пикер моделей штатной морды; кнопка «Add» активна для незанятых)

edge-credentials.ts (БЕЗ ИЗМЕНЕНИЙ — уже generic по любому ref)
  storage.get/put('dsh-edge:credential:' + ref)
```

## Решения

### Занимаем namespace `llm-pi-ai` своей реализацией, не тащим пакет

Это главное решение change. Точные условия раздвоенного поведения штатного
Settings UI апстрима (путь записи «правка существующего провайдера» берёт
namespace динамически из ответа сервера — сработает с любым именем; путь
«создание нового провайдера» жёстко зашит на литерал `NS$1 = "llm-pi-ai"`,
и кнопка «Add custom provider» мертва для любого другого имени namespace)
задокументированы один раз в
[`docs/research/11-dsh-edge.md`](../../../docs/research/11-dsh-edge.md)
(коммит `b8c0b2d`, ветка #153) — здесь не дублируются построчно, только
вывод: **кнопка создания провайдера оживает только если имя namespace
буквально `llm-pi-ai`.** Выбрать своё произвольное имя (условие «свой
namespace с произвольным именем» из issue) не работает по той же причине.
Значит единственный путь получить штатную кнопку создания без правки
клиента — самим объявить схему по адресу `llm-pi-ai.providers.*` и
обслуживать её своим кодом ядра (`registerConfigurableProviders` +
`registerAdapter`), не устанавливая пакет `dsh-llm-pi-ai`.

Динамический путь записи (правка существующего провайдера) заведён на тип
directory-записи `LlmConfigurableProvider.settingsNs`
(`@deepseek-ai/dsh-llm/lib/types/index.d.ts:156` — тот же пакет ядра, что
даёт `registerAdapter`/`AdapterRegistrationHandle` ниже; точный путь файла
внутри пакета не сверен отдельно от имени пакета, см. «Не подтверждено»),
которую `targetOf()` клиента читает как `ns` перед мутацией — для правки
годится любой наш namespace без совпадения имён с чужим литералом.

**Цена решения, названная честно.** Это завязка на приватный строковый
литерал чужого клиентского бандла (`NS$1`), не на публичный контракт. Апстрим
может переименовать его в любом релизе без semver-сигнала — для клиента это
внутренняя деталь UI, не API. Гвардия деплоя (см. tasks.md) переводит этот
риск из «тихая порча однажды» в «громкий красный деплой сразу» — тот же
класс дисциплины, что у патчей `dsh-edge-plugin-system` к строкам апстрима.
Альтернатива этой цены — свой клиентский плагин (вариант б, вне рамок этого
change, см. proposal «Вне рамок»): дороже по объёму, но не зависит от
литерала. Решение владельца — идти вариантом (а) сейчас, откладывать (б) до
факта боли.

### Переиспользуем `DeepSeekAdapter`, не пишем свой транспорт

Класс экспортирован публично (`dsh-llm-deepseek/lib/index.js:1817`) и уже
доказан живьём с z.ai и NVIDIA NIM (issue #158). `DeepSeekAdapterOptions`
несёт одну пару `baseURL`/`apiKeyEnv` (`lib/types/adapter.d.ts:86-102`) — то
есть один инстанс класса обслуживает ровно один provider route; N
провайдеров = N инстансов с разными опциями, не N реализаций транспорта.
Своя работа change — цикл регистрации и чтение settings-namespace, а не SSE,
files-api или сериализация: они переиспользуются целиком тем же классом.

Node-only импорты пакета — `node:crypto`, `node:fs/promises`, `node:path`
(`lib/index.js:8-10`). Сверено вторым проходом ворот
([analyze-2026-09-01-pass2.md](reviews/analyze-2026-09-01-pass2.md)):
`mkdir`/`readFile`/`dirname`/`join` вызываются только внутри класса
**`DeepSeekUploadIndex`** (`lib/index.js:539-646`) — дефолтного файлового
upload-index, которым морда не пользуется (`session-store.ts:241-242` создаёт
свой `DurableObjectUploadIndex`). А `createHash` лежит ШИРЕ: `lib/index.js:494`,
функция `deepSeekFileScope()` объявлена вне класса и зовётся из
`DeepSeekFileStore` (`:733`, `:762`, `:814`, `:825`, `:874`) при каждой сборке
upload-scope, независимо от переданного индекса.

Вывод для нас не меняется — `node:crypto` штатно доступен под `nodejs_compat`, —
но держится он именно на `nodejs_compat`, а не на «путь недостижим». Files-путь
этот change не трогает вовсе.

### Регистрация N провайдеров: цикл, коллизии, замена на ходу

Наш плагин на каждый запуск (старт DO + реакция на изменение
settings-namespace `llm-pi-ai`) строит список провайдеров из
`providers.<route-id>` и вызывает:

```
handle = ctx.llm.registerAdapter(
  providers.map(p => p.routeId),
  makeAdapter(providers)   // один адаптер отвечает на несколько id — см. ниже
)
ctx.llm.registerConfigurableProviders(providers.map(toDirectoryEntry))
```

Существующий провайдер `deepseek-official` (const `EDGE_PROVIDER`,
`session-store.ts:115`) продолжает монтироваться отдельным штатным вызовом
`context.plugin(dshLlmDeepseek, ...)` (`session-store.ts:243`) — этот change
его не трогает и не переносит в свой namespace: «существующий провайдер не
ломается» (критерий issue #158) означает буквально «код монтажа
`deepseek-official` не меняется», а не «переезжает под новую схему». Наш
реестр отвечает только за провайдеров, добавленных владельцем через
`llm-pi-ai`; коллизия id между `deepseek-official` и записью реестра с тем
же route-id — ошибка `DUPLICATE_ADAPTER`, all-or-nothing регистрации
(`index.d.ts:227-229`) — она обязана дойти до владельца как громкий отказ
инсталла (тот же прецедент изоляции, что у `dsh-edge-plugin-system`:
`console.error` + статус, DO не падает), а не тихо выигрывать/проигрывать.

Изменение состава (владелец добавил/удалил провайдера через UI) обслуживает
`handle.replace(providers)` (`index.d.ts:174-192`) — атомарная подмена
набора маршрутов без пересоздания хендла и без гонки «часть старых
маршрутов ещё жива, часть новых уже есть».

`LlmAdapter` требует ровно один метод — `stream()` (`index.d.ts:168`,
«The only required method»). У `DeepSeekAdapter` он уже реализован;
дефолтные реализации прочих методов интерфейса (если есть) наш код не
переопределяет — см. «Не подтверждено».

### Три различимых состояния отказа, не два

Живой случай, породивший change (`RATE_LIMIT: Weekly/Monthly Limit
Exhausted`, proposal «Зачем»), — это не «провайдер не настроен» и не
абстрактный «все провайдеры упали»: провайдер настроен и отвечает отказом.
Спека (требование 10) и критерий issue #158 («Отказ ВСЕХ провайдеров —
громкий и отличимый от "провайдер не настроен"») требуют текстуально
различимых состояний, не одного общего «ошибка»:

- `not_configured` — route-id не заведён владельцем в `llm-pi-ai` вовсе;
  штатное «нечего пробовать», не ошибка.
- `configured_but_rejected` — провайдер заведён, но ход к нему отвечает
  отказом уровня транспорта/аутентификации (401) или явным лимитом квоты
  (`RATE_LIMIT: Weekly/Monthly Limit Exhausted`) — тот же класс, что и
  живой случай.
- `all_providers_failed` — все настроенные (не `not_configured`)
  провайдеры одновременно в состоянии `configured_but_rejected`: сигнал,
  что владельцу нужно действовать (сменить креды/дождаться сброса квоты),
  не «тихо продолжаем без модели».

Каждое состояние лечится своим действием, поэтому обязано быть текстуально
своим значением статуса, не подтипом одной общей ошибки. Задача — раздел 1
tasks.md; доказательство — раздел 4.

### Где живут креды

Нигде не меняется. `edge-credentials.ts` уже generic по любому `ref`:
`storage.get/put('dsh-edge:credential:' + ref)` (`:107-109, :64-69`).
Единственная спецветка — фолбэк на env-секрет для ref `DEEPSEEK_API_KEY`
(`:44-49, :15`) — относится к существующему провайдеру, не к реестру.
Штатный UI уже кладёт ключ правильным путём:
`api.credentials.set({ref: deriveKeyRef(route), value})`
(`client.js:1121-1124`), `deriveKeyRef` = `<ROUTE_UPPER>_API_KEY`
(`client.js:477`). `apiKeyEnv` в конфиге провайдера — это имя ref'а
(`docs/research/10-dsh-architecture.md`, раздел 10), не значение ключа: он
никогда не попадает в settings-namespace, только в DO storage под ключом
кредов. Ноль строк нового кода в этом файле — задача change здесь: не
трогать его и подтвердить тестом, что он не тронут (регрессионная гвардия
в tasks.md).

### Раннеры: тот же набор провайдеров, тот же приоритет

Сейчас раннер читает провайдера/модель из `vars.DEEPSEEK_BASE_URL` /
`vars.DEEPSEEK_MODEL` репозитория (`scripts/lib/dsh-ci.sh`, решение #153) —
единственное место правды на сегодня, но оно оперирует ровно одним
провайдером и не знает про реестр морды вообще.

**Развилка:** после реестра источник правды о наборе провайдеров —
DO storage морды, а не `vars`. Два варианта синхронизации:

1. **Раннер спрашивает морду** (HTTP-вызов к `/api/*` за списком
   провайдеров/приоритетом перед стартом DSH).
2. **Реестр экспортируется** (морда пишет производный артефакт — например,
   в `vars`/`repository variable` или в файл — при каждом изменении, раннер
   читает его как сегодня читает `vars`).

**Выбор: экспорт (вариант 2), не живой опрос (вариант 1) — с оглядкой на
#155.** Обоснование:

- **Состояние факта на сегодня (2026-09-01), не прогноз.** В main раннер
  сейчас молчаливо фолбэчит на зашитую модель:
  `DSH_MODEL="${DEEPSEEK_MODEL:-glm-5}"` (`scripts/lib/dsh-ci.sh:67`,
  подтверждено чтением `origin/main`), тот же зашитый `glm-5` продублирован в
  `worker.yml:97`, `hands.yml:57`, `ai-review.yml:109` как дефолт `vars`.
  Громкого отказа при пустом источнике в main нет. Свойство «читает `vars`
  до дорогой работы, падает громко, если пусто» появляется вместе с функцией
  `dsh_require_provider_env`, которая существует только в ветке
  `agent/153-single-source-provider-default` (`dsh-ci.sh:27`), это открытая
  задача #153 / открытый PR #154 — **этот change наследует свойство «громкий
  отказ» только после их слияния, не сегодня** (blocked by: #153/PR #154).
  При выборе между вариантом 1 (живой опрос) и вариантом 2 (экспорт) довод
  «раннер уже так устроен» относится к будущему состоянию раннера, не к
  текущему коду main.
- Независимо от исхода #153, выбор в пользу экспорта (вариант 2) обоснован и
  без опоры на уже существующий громкий отказ: живой опрос вводит новую
  сетевую зависимость раннера от морды на критическом пути старта (морда
  недоступна/DO спит/холодный старт → раннер либо ждёт, либо падает по
  причине, не связанной с провайдером) — класс отказа, которого при
  варианте 1 просто не существовало.
- #155 сам по себе — вопрос «откуда раннер берёт дефолтную модель», и его
  разрешение этим change не в рамках (см. proposal), но выбор архитектуры
  синхронизации обязан быть с ним совместим: экспортируемый артефакт — то
  самое естественное место, куда #155 сам сведётся при закрытии (одна
  переменная/файл, которую читают оба потребителя — морда для дефолта показа
  и раннер для факта работы), тогда как живой опрос плодит второй канал
  чтения того же значения.
- Формат экспорта — не выбирается этим design окончательно (это заготовка
  реализации, не propose-фаза): кандидаты — `gh variable set` из
  DO/воркера в реакции на изменение namespace `llm-pi-ai` (тот же механизм,
  что уже гоняет `deploy-dsh-edge.yml`/`worker.yml` через `vars`), либо
  публикация артефакта событием журнала (прецедент `plugin_status` в
  `dsh-edge-plugin-system`) с чтением его раннером при старте. Выбор между
  ними — задача реализации (tasks.md), не архитектурная развилка данного
  design: обе формы удовлетворяют «раннер не зависит от живой доступности
  морды в момент старта».
- Приоритет провайдеров (в каком порядке пробовать при failover) — часть
  экспортируемого артефакта, а не отдельный канал: одно место правды на оба
  потребителя, иначе снова возможен класс «в морде один порядок, в раннере
  другой», который явно назван недопустимым в критерии issue #158.

### Отвергнутые варианты внутри change

**Пятый upstream-патч (форк-серия `dsh-edge/patches/000N-*.patch`).**
Технически осуществимо — по образцу существующих четырёх патчей. Отвергнуто:
`dsh-edge/PATCHES.md` объявляет порог пересмотра «форк против серии» (больше
шести патчей или патч >100 содержательных строк), патч 0004 уже у этого
порога (~120 строк); реестр провайдеров занял бы ~250-400 строк — 2.5-4×
сверх лимита. Точка входа для владельческих плагинов уже существует
(`installEdgePlugins`, смонтирован патчем 0002) — патч создавал бы вторую
точку монтажа там, где первая уже решает задачу без расширения серии. См.
«Форма носителя» выше.

**Смонтировать `dsh-llm-pi-ai` целиком.** `@earendil-works/pi-ai@0.84.2`
тянет `@aws-sdk/client-bedrock-runtime`, `@smithy/node-http-handler`,
`http(s)-proxy-agent`, `@google/genai`, `@anthropic-ai/sdk`, `openai`; поля
`browser` в пакете нет — это активный HTTP-транспорт, не мёртвый код,
вырезать пришлось бы форком самого `pi-ai`. Бюджет бандла морды —
900 KiB gzip (`docs/research/11-dsh-edge.md`). Апстрим сам отказался от
подключения по той же причине: заметка
`.agents/notes/implemented/architecture/2026-08-22-dsh-edge-v0.4-multi-provider-vision.md`,
раздел Excluded.

**Свой namespace с произвольным именем (не `llm-pi-ai`).** Формально проще
(не завязан на приватный литерал), но кнопка «Add custom provider» не
оживёт: `protocolChoices` читает ровно ключ `llm-pi-ai` из карты
namespace'ов (`client.js:1847`), любое другое имя даёт `undefined` →
`protocolChoices(undefined)` → `[]` → кнопка мертва независимо от
`writable`. Цена этого варианта — тот же объём кода, но без критерия
«кнопка создания провайдера работает», то есть не закрывает issue.

**Свой клиентский UI сразу (вариант б).** Ниже архитектурный риск (не
зависит от литерала апстрима), но дороже по объёму (React/TS в слот
`settings.section`, двойная поверхность правки настроек) и не даёт ничего
раньше первого факта боли. Решение владельца — откладывается до факта:
апстрим переименовал `llm-pi-ai`/`NS$1`, гвардия покраснела, штатный UI
перестал оживать.

### Видимость перехода — обязанность реестра, не плагина владельца

Proposal («Критерий готовности») требует: «реестр обязан дать плагину
видимый, а не тихий переход». Это не логика failover (она — плагин
владельца, вне рамок), а обязанность самого реестра публиковать факт смены
активного provider/model событием журнала (тот же класс события, что
`plugin_status` в `dsh-edge-plugin-system`) при каждой смене набора
(`handle.replace(providers)`) и при каждой смене состояния провайдера между
`configured` / `configured_but_rejected`. Плагин владельца читает эти
события, реестр их только публикует — граница та же, что в «Вне рамок»
proposal: реестр даёт данные и видимость, маршрутизацию поверх них строит
плагин владельца.

## Чего дизайн намеренно не решает

- Маршрутизацию/failover/cooldown/приоритет как исполняемую логику —
  плагин владельца поверх `llm.providers`, реестр только предоставляет
  список и приоритет как данные (см. proposal, «Вне рамок»).
- Потолок токенов как свойство модели (#157) — этот change создаёт поле
  `models[].maxTokens` в схеме namespace, но не переносит в него текущую
  константу `131072` и не трогает `dsh-ci.sh`/деплой-патч морды под
  существующего провайдера.
- Судьбу #155 — называет совместимую точку (экспортируемый артефакт), не
  закрывает вопрос.
- Свой клиентский плагин/UI — откладывается явно, не проектируется здесь.
- Формат конкретного экспортируемого артефакта для раннеров (repository
  variable vs событие журнала vs что-то третье) — оставлено задаче
  реализации в tasks.md, это не архитектурное решение уровня design.

## Девиации реализации (#114, 2026-09-03)

Реализация раздела 1 tasks.md (тонкий сквозной разрез + слой ядра) и раздела 2
(гвардия литерала) внесла четыре осознанных отклонения от текста дизайна. Ни одно
не меняет архитектуру (носитель — серверный плагин, namespace `llm-pi-ai`,
переиспользование `DeepSeekAdapter`, хранение в DO storage), все — контрактные
уточнения, найденные при работе с живыми пакетами:

1. **N×`registerAdapter([route], adapter)` вместо одного вызова со списком.**
   Текст дизайна рисовал `registerAdapter(providers.map(routeId), makeAdapter(...))`
   — один адаптер на несколько id. Контракт `LlmAdapter` этого не позволяет:
   хук `options: () => DeepSeekConnectionOptions` не получает provider-аргумент
   (`adapter.d.ts:86-102`), то есть один инстанс физически не может мультиплексировать
   разные `baseURL`/`apiKeyEnv` по маршрутам — все маршруты одного инстанса ходили
   бы в один эндпоинт. Апстримный `dsh-llm-deepseek` делает так же: один вызов на
   один маршрут (`lib/index.js:1801`). Атомарность подмены набора, ради которой
   рисовался один вызов, обеспечена по-другому: registration-хендлы снимаются/поднимаются
   поштучно, а directory-канал (то, что читает UI) подменяется атомарно одним
   `DirectoryRegistrationHandle.replace(entries)`.
2. **Коллизия route-id с `deepseek-official` отказывается при записи, а не статусом
   в DO storage.** У плагина нет доступа к сырому DO storage (патч 0002 пишет статусы
   сам, монтируя плагин с `storage`; cordis-плагин получает только `ctx`). Коллизия
   отсекается на входе: validate-хук settings-namespace отказывает `settings.mutate`
   с внятным текстом (клиент показывает его в карточке — громче статуса в DO storage,
   который владелец не видит). Отказ при инсталле тоже многослоен, и слои честно
   названы: (а) раздел, не прошедший schema+validate, по контракту апстримного
   `SettingsProvider.register` валит РЕГИСТРАЦИЮ namespace целиком (fail loud:
   apply падает, патч 0002 пишет `failed` в DO storage) — поштучной изоляции
   невалидного хранимого документа нет и не предусмотрено контрактом апстрима;
   (б) поштучный `console.error` + пропуск маршрута в sync() покрывает остаточный
   класс «документ прошёл schema+validate, но не резолвится в соединение»
   (например, `apiKeyEnv` вне grammar credential-ref, который validate не
   проверяет); (в) невалидный раздел у ЖИВОГО маршрута (прошёл запись, перестал
   резолвиться) — last-good + один громкий лог на версию раздела. Инсталл-статус
   `failed` в DO storage при падении всего apply пишется патчем 0002 как раньше.
3. **Directory — статический каталог из четырёх маршрутов** (`zhipu`, `nvidia-nim`,
   `openrouter`, `deepseek`; единственное место правды —
   `plugins-src/provider-registry/directory.json`, импортируется в
   `server/index.js` как `DIRECTORY`, тот же файл читают юнит-тесты,
   `dsh-edge/registry-integration/check.mjs` и канарейка деплоя)
   плюс все настроенные маршруты (включая произвольные из CustomProviderCard — иначе
   строка и кнопка Remove у них не появились бы). Дизайн называл directory «что можно
   настроить», состав не определял; выбраны провайдеры, названные в документах
   репозитория (runbook переключения провайдера, research/30 п.13), расширение — PR.
4. **`api` — union из одного значения** (`openai-completions`), а не список протоколов
   апстримного pi-ai (`openai-completions`/`openai-responses`/`anthropic-messages`).
   Переиспользуемый транспорт говорит только OpenAI chat-completions
   (`/chat/completions`); предлагать в селекте протоколы, которые маршрут потом не
   осилит, — тихий отказ на ходе. Один элемент union валиден для клиента:
   `protocolChoices` фильтрует `list[].value`, непустой список включает кнопку.

Кроме того, зафиксирован выбор, который дизайн оставлял реализации: **потолок ответа
маршрута** — env воркера `DEEPSEEK_MAX_OUTPUT_TOKENS` (то же место правды, что кормит
штатного провайдера морды; в деплое 131072 — потолок GLM), при отсутствии — 131072;
на модель — `models[].maxTokens`. Дефолт адаптера 256000 текущий провайдер отклоняет
(runbook переключения провайдера).

## Не подтверждено

1. **Поведение `layoutOf()` для namespace вне двух известных литералов**
   (`client.js:1354-1358`) — третий случай (не `llm-deepseek`, не
   `llm-pi-ai`) рендерится как `unknown` по прочтению кода; как именно
   выглядит рендер `unknown` в реальном UI (визуально) не проверено живым
   прогоном. Наш случай использует ровно литерал `llm-pi-ai`, поэтому по
   заявленному дизайну не должен попасть в эту ветку — но не проверено на
   собранной морде.
2. **Побайтовая схема Config, которую ожидают `protocolChoices`/
   `ModelListEditor`.** Сверялась по типам `@deepseek-ai/dsh-llm-pi-ai@0.1.2-alpha.3`
   (`lib/types/config.d.ts`, `provider.d.ts`, `catalog.d.ts`) и по
   клиентскому бандлу (`client.js`), не по рантайм-исходнику
   `lib/index.js` пакета `pi-ai`/`dsh-llm-pi-ai` — то есть подтверждена
   форма данных, которую читает UI, но не полный набор рантайм-инвариантов,
   которые пакет мог бы проверять при загрузке (мы его не монтируем, эти
   проверки просто не выполняются никем — риск в том, что UI ожидает
   побочный эффект такой проверки, которого не видно по типам).
3. **Дефолтные методы `LlmAdapter` без переопределения.** Контракт называет
   `stream()` единственным обязательным (`index.d.ts:168`), но не читано,
   есть ли у интерфейса необязательные методы с дефолтной реализацией,
   которые `DeepSeekAdapter` мог бы переопределять специфично для
   DeepSeek — используем класс как есть, поведение необязательных методов
   для наших route-id не проверено отдельно.
4. **Связка `edgeFileStore` → `resolveFiles`.** Найдено вторым проходом:
   `session-store.ts:241-242` кладёт `DeepSeekFileStore` в контекст как
   произвольное свойство (`context['edgeFileStore'] = …`), а в
   `buildEdgeLlmPluginConfig` (`session-store.ts:1606-1619`) поля `resolveFiles`
   нет. Читает ли плагин `ctx.get('edgeFileStore')` при построении резолвера —
   не проверено. Следствие: утверждать «морда обходит дефолтный upload-index
   штатным контрактом» можно лишь до уровня «стор создан и положен в контекст».
   Workers-совместимость при этом держится на `nodejs_compat` (см. «Форма
   носителя»), а не на недостижимости пути, поэтому для этого change пробел
   не критичен: Files-путь мы не трогаем.
5. **Формат и механизм экспорта набора провайдеров для раннеров** (см.
   «Раннеры: тот же набор») — какая конкретно форма (`gh variable set` из
   воркера vs событие журнала vs иное) технически осуществима в рамках
   прав токена, которым располагает воркер (`GH_RUNNER_TOKEN`/
   `GH_DISPATCH_TOKEN`, узкие по #114/ADR 0008) — не проверено; решается в
   первой задаче соответствующего раздела tasks.md.
6. **Порядок монтажа плагина реестра против видимости адаптеров в пикере.**
   Установлено по чтению патча 0002, что `installEdgePlugins(storage)` стоит
   в хвосте `EdgeSessionStore.initialize()`, ПОСЛЕ монтажа `dshLlmDeepseek` —
   отсюда допущение «пикер видит адаптеры плагина, зарегистрированные позже
   штатного провайдера» (design, «Форма носителя»). Живым прогоном на
   собранной морде это допущение не проверялось отдельно от общего тонкого
   сквозного разреза; закрывается той же первой задачей tasks.md раздел 1.
   **Закрыто #114 (2026-09-03):** интеграция реестра на собранном артефакте
   (`dsh-edge/registry-integration/check.mjs`) показывает `deepseek-official`
   активным и `zhipu` активным одновременно в `llm.providers`/`llm.models`
   на одном DO — порядок монтажа видимости не мешает.
