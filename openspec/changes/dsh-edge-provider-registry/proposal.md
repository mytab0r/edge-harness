# dsh-edge-provider-registry: реестр LLM-провайдеров в морде через штатный UI

Задача: #158. Смежные: #114 (кнопки провайдера мертвы — вероятно закрывается
этим change), #155 («дефолтная модель из морды» — пересмотреть), #157 (потолок
токенов зашит под GLM — становится свойством модели в реестре). Смежное:
[design](design.md), [задачи](tasks.md), дельта-спека
[specs/dsh-edge-providers/spec.md](specs/dsh-edge-providers/spec.md).

## Зачем

Требование владельца 2026-09-01, дословно по смыслу: «не хочу каждый раз
перенастраивать `DEEPSEEK_MODEL`/`DEEPSEEK_API_KEY`/эндпоинты вручную, когда
исчезает квота; хочу, чтобы автоматически использовалась заранее указанная мной
модель из списка доступных, у тех провайдеров, чьи креды я задал».

Живой случай, который держит конвейер: квота GLM исчерпана 2026-08-31
(`dsh: RATE_LIMIT: Weekly/Monthly Limit Exhausted`, сброс 2026-09-04 20:54),
три прогона `worker.yml` красные, конвейер стоит трое суток — оживить может
только владелец руками. Сейчас в морде смонтирован единственный LLM-адаптер
с захардкоженным provider id (`session-store.ts:243`, `session-store.ts:115`),
и кнопки добавления провайдера в штатном Settings UI мертвы: «Add» —
`addable.length === 0` (единственный провайдер уже `configured`,
`client.js:2015, 1844`), «Add custom provider» — `protocols.length === 0`,
потому что namespace `llm-pi-ai` не смонтирован вовсе (`client.js:2029, 1847,
488`). Задача разбивается на две роли, которые нельзя путать:

1. **Реестр провайдеров** — владелец добавляет провайдера и его креды через UI
   морды, видит его модели в пикере. Это роль `llm-pi-ai`. Закрывается этим
   change.
2. **Маршрутизация** — виртуальная модель `combo/auto`: failover по
   исчерпанной квоте, cooldown, приоритет моделей поверх подключённых
   провайдеров. Плагин владельца, НЕ штатная возможность DSH и не работа этого
   change — реестр только даёт ему набор провайдеров, над которым он работает.

Курс подтверждён владельцем 2026-09-01: внешний питоновский роутер в цепочке
не используется вовсе (`docs/research/30-rejected-alternatives.md`, п.1 и п.8).

## Что меняется

- Носитель — серверный плагин по образцу `runner-bridge`
  (`plugins-src/runner-bridge/`, запись в `dsh-edge/plugins.json`:
  `"server": true, "client": false`, релизный тарбол + sha256-пин), не новый
  upstream-патч: патч-серия и так стоит у собственного порога размера
  (`dsh-edge/PATCHES.md`), а точка монтажа владельческих плагинов уже
  существует — `installEdgePlugins(storage)` из патча 0002, в хвосте
  `EdgeSessionStore.initialize()` (design, «Форма носителя»).
- Свой тонкий плагин `ctx.llm.registerAdapter()` на N провайдеров: по одному
  инстансу переиспользуемого `DeepSeekAdapter` (OpenAI-compat транспорт) на
  провайдера, вместо единственного захардкоженного адаптера.
- Settings-namespace `llm-pi-ai` со схемой `providers.<route-id>` —
  реализован своим кодом (без пакета `dsh-llm-pi-ai`/`@earendil-works/pi-ai`),
  чтобы штатный Settings UI (правка существующего провайдера и создание
  нового) заработал без изменения клиента.
- `registerConfigurableProviders()` — directory «что можно настроить», чтобы
  кнопка «Add» стала активной для незанятых провайдеров.
- Ноль изменений в `edge-credentials.ts`: механизм кредов уже generic по
  любому `ref` (design, «Где живут креды»).
- Гвардия деплоя: литерал `llm-pi-ai` в собранном клиентском бандле
  обязателен — переименование апстримом обязано ронять деплой громко, а не
  тихо возвращать кнопки в мёртвое состояние.
- Раннеры (`scripts/lib/dsh-ci.sh`) получают тот же набор провайдеров и тот
  же приоритет, что и морда — расхождение «в морде одна модель, в раннере
  другая» закрывается по построению (решение — в design).

## Вне рамок

- **Маршрутизация** (`combo/auto`, failover, cooldown, приоритет моделей) —
  плагин владельца, отдельная работа над реестром этого change, не часть его.
- **Свой клиентский UI** — задача решается штатным Settings UI апстрима;
  собственный DSH-плагин в слот `settings.section` (прецедент
  plugin-manager, ограничение #114) откладывается до факта боли: апстрим
  переименовал литерал `llm-pi-ai`/`NS$1`, и штатный UI перестал оживать.
- **Потолок токенов как свойство модели** — #157, отдельная задача; этот
  change лишь создаёт место (`models[].maxTokens`), где он в итоге будет
  жить по одному на провайдера/модель, а не переносит существующую логику.
- **#155** («дефолтная модель из морды») пересматривается по факту этого
  change, но сам пересмотр — не задача change; названо как последствие.
  **Признанный конфликт формулировок:** `gh issue view 155` дословно описывает
  механизм «раннер перед стартом спрашивает модель у морды» (живой опрос) —
  ровно вариант 1 синхронизации раннеров (design, «Раннеры»). Этот change
  выбирает вариант 2 (экспорт) по причинам, изложенным в design, и явно НЕ
  реализует формулировку #155 как есть. Закрытие #155 в этой формулировке —
  не задача change; текст #155 требует пересмотра владельцем после того, как
  этот change заработает, а не молчаливого расхождения с ним.
- Пакет `dsh-llm-pi-ai`/`@earendil-works/pi-ai` не монтируется (design,
  «Отвергнутые варианты»): Node-only транспортные SDK не влезают в бюджет
  900 KiB gzip морды.

## Критерий готовности (из issue #158, дословно)

- Владелец добавляет провайдера и его креды из UI морды; провайдер и его
  модели видны в пикере; настройка переживает рестарт DO.
- Ключи новых провайдеров — в DO storage/секретах воркера, не в репозитории.
- Существующий провайдер не ломается: добавление не перетирает настроенное.
- Кривой base URL/ключ не роняет морду — ошибка видна в Settings.
- Раннеры подхватывают тот же набор провайдеров и тот же приоритет.
- Исчерпание квоты одного провайдера не требует действий человека — но сам
  failover реализует плагин владельца поверх реестра этого change, не сам
  change (см. «Вне рамок»); реестр обязан дать плагину видимый, а не тихий
  переход (переключение видно в журнале/сессии).
- Отказ ВСЕХ провайдеров — громкий и отличимый от «провайдер не настроен»:
  три различимых состояния — `not_configured` (провайдер вообще не заведён),
  `configured_but_rejected` (настроен, но отвечает отказом — 401 или
  `RATE_LIMIT: Weekly/Monthly Limit Exhausted`, живой случай — см. «Зачем»),
  `all_providers_failed` (все настроенные провайдеры в состоянии
  `configured_but_rejected` одновременно). Три состояния — потому что
  лечатся по-разному: первое чинится настройкой через UI, второе —
  сменой/ожиданием квоты, третье — сигнал владельцу «действовать сейчас».
