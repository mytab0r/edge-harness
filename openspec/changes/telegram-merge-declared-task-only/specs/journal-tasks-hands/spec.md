# Дельта-спека: «выполнена» — только об объявленной задаче (#404)

Уточняет `openspec/changes/telegram-pr-open-merged-reports/specs/journal-tasks-hands/spec.md`
(требование «Telegram о слиянии в main — after_merge»); по сложении в
базовую спеку — п. 29 и раздел «Конвейер (оркестратор)».

## MODIFIED: п. 17.1 — широкая семантика в after_merge скоупится на замки и напоминания

Базовая спека, п. 17.1 (хвост абзаца): «Правила `reap_stale`/
`unhealthy_pulls`/`after_merge` намеренно продолжают использовать широкую
семантику упоминания — сужение там было бы регрессией, не улучшением».
Безусловная формулировка противоречит этому change: «выполнена» в канале
владельца — узкий вопрос об объявленной задаче (#259, #404). Отдельно
(#286) `unhealthy_pulls` уже вышел из списка широкой семантики целиком —
там та же широта била в «сняли аренду ЧУЖОЙ задачи», не в «не тронули
вовремя» (симметричная, но не тождественная причина сузить). При
сложении п. 17.1 переформулируется: широкая семантика упоминания в
`after_merge` остаётся ТОЛЬКО для освобождения замков (`claim_task.release`)
и напоминаний о пост-мерж проверке — там ошибиться в сторону «не трогать
живую работу» дешевле; утверждение вида «этот PR выполнил задачу N»
(выбор задачи для Telegram-сообщения о слиянии) — узкая семантика
`declares_task`, как у приёмки (#227).

Тот же хвост абзаца правит и активная дельта `unhealthy-pulls-narrow-match`
(#286). Обе дельты несут ОДИНАКОВЫЙ текст замены (см. ниже), чтобы
сложение с базовой спекой не зависело от порядка, в котором они
архивируются: какая бы из двух ни применилась последней, результат — один
и тот же полный текст, не половина. Замена хвоста абзаца:

> Правило `reap_stale` и `after_merge` (освобождение замков, напоминания о
> пост-мерж проверке) намеренно продолжают использовать широкую семантику
> упоминания — сужение там было бы регрессией, не улучшением. `unhealthy_pulls`
> (#286) в этот список не входит: сопоставление PR → задача там — ТОЛЬКО
> `task_ref.resolve_pr_task` (имя agent-ветки, тело PR не читается), та же
> узкая семантика, что уже использует `contract_check.py` и
> `scripts/review/ai_review.py`. PR без agent-ветки нужной формы не
> сопоставляется ни с одной задачей вовсе — «задача не определена», а не
> «наверное вот эта». Утверждение «этот PR выполнил задачу N» (выбор задачи
> для Telegram-сообщения о слиянии) широкой семантикой тоже не является —
> это узкий вопрос о декларации (`task_ref.declares_task`), как у приёмки
> (#404).

## MODIFIED: Telegram о слиянии — задача берётся из декларации, не из прозы

Требование: задача в сообщении «задача #N выполнена — слито в main» —
ТОЛЬКО задача, объявленная этим PR первой строкой тела
(`task_ref.declares_task`, узкая семантика #259 — тот же предикат, по
которому приёмка #227 собирает карту закрытия). Упомянутая в прозе задача
(в том числе более старая открытая, перебивающая сортировкой упоминаний)
не попадает в сообщение ни номером, ни заголовком: канал не заявляет
«выполнена» о работе, которую этот PR не делал.

Требование: объявленных подходящих задач нет (dependabot, orchestra:skip,
декларация не открыта/без метки task) — сообщение не отправляется вовсе.

Сценарий: тело PR — `#79` первой строкой и «поправил соседний баг из #78»
в прозе, обе задачи открыты → в чате одно сообщение про #79; #78 в
сообщении отсутствует.

Сценарий: PR dependabot без декларации → Telegram молчит, замки и
напоминания по широкой семантике работают как раньше.
