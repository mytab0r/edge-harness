# Design: auto-wire-declared-deps

Контекст и правило — `proposal.md`. Здесь — развилки и почему выбрана
конкретная, включая явный пересмотр решения предыдущего change.

## Развилка (а): почему решение design.md #361/#371 «человеческий путь
остаётся ручным» пересматривается именно сейчас

design.md #361 (развилка б) отклонил автоматический перенос для
человеческого/шаблонного пути формулировкой «форма не структурная для
программных создателей issue — GitHub не валидирует содержимое поля на
сервере». Это утверждение верно и не отменяется — но оно отвечает на
другой вопрос. Автоперенос этой задачи не полагается на серверную
валидацию формы вовсе: он читает УЖЕ СОЗДАННЫЙ, уже отрендеренный GitHub
markdown тела issue (`### Чем блокируется\n\n<ответ>`) и разбирает его
структурно по заголовку секции — тот же приём, что #387 уже применил для
детектора предупреждений (`_FORM_FIELD_RE`), просто до этой задачи находка
только предупреждала, не писала. Различие с #361 существенно: там речь
шла о ДОВЕРИИ к содержимому (могло ли поле быть произвольным текстом без
структуры) — здесь используется тот факт, что GitHub рендерит ответ формы
предсказуемо, а разбор — по структуре рендера, не по доверию к содержимому
самого ответа (ответ либо валидные `#N`, либо «ничем», либо мусор — мусор
даёт пустой список, не ложную связь).

Второй факт, разблокировавший пересмотр: #387 сделал поле ОБЯЗАТЕЛЬНЫМ.
До #387 поле могло отсутствовать в множестве старых issues (структурного
факта для переноса не было бы у большинства). После #387 каждая НОВАЯ
issue из шаблона несёт его гарантированно — авто-перенос перестаёт быть
«может сработать иногда» и становится «работает для каждой новой задачи
пула, заведённой через форму».

## Развилка (б): где живёт единый цикл переноса — `task_deps.py` или
`file_tasks.py`

Два вызывающих: `file_tasks.py::wire_declared_dependency` (существует,
путь АИ-ревью) и новый `declared_deps.py::auto_wire` (путь формы). Оба
делают ОДНО И ТО ЖЕ: пропустить номер вне открытого пула с меткой `task`
или ссылку на себя, иначе `task_deps.add_dependency` + лог. Заводить
третью копию цикла — прямое нарушение «Одно место правды» (AGENTS.md).

Кандидата два: (1) вынести в `task_deps.py` (граф — уже единственное
место правды на ЧТЕНИЕ/ЗАПИСЬ связи, естественно и на цикл переноса);
(2) вынести в `file_tasks.py`, `declared_deps.py` импортировал бы оттуда.

**Выбор (1), `task_deps.py::wire_dependencies`.** `task_deps.py` не
зависит ни от `file_tasks.py`, ни от `declared_deps.py` — оба модуля уже
импортируют `task_deps.py` (тот же приём `importlib.util`, что
`declared_deps.py::_load_task_deps` уже делает). Обратная зависимость
(2) создала бы цикл импортов или заставила `declared_deps.py` тянуть
`file_tasks.py` целиком (включая AI-ревью-специфичный код, ему не нужный).

## Развилка (в): где стоит запись — пульс оркестратора или `repo-ci.yml`

Тот же вопрос, что design.md #371 уже решил для ДЕТЕКТОРА (только
предупреждение) — здесь то же решение переносится на ЗАПИСЬ, по той же
причине цены, усиленной свежим фактом: `orchestra.yml`/`scheduler.py` —
уже самый дорогой потребитель квоты GITHUB_TOKEN в репозитории (150-250
REST-вызовов за прогон при непустой очереди, #443) и уже ронял чужие
обязательные проверки живым прогоном 2026-09-06 (#454, PR #428/#453),
из-за чего перед ним теперь стоит ранний отказ по квоте
(`scripts/lib/rate_guard.py`). Добавлять туда ещё один проход по пулу
(GraphQL, свой бюджет, но тот же общий лимит 1000 запросов/час на токен)
на КАЖДЫЙ 15-минутный тик расписания — умножать нагрузку на то же узкое
место, которое сегодня уже требует защиты.

`repo-ci.yml`, напротив: один проход на `push` в main (не по расписанию),
использует уже существующий шаг детектора рассинхрона (тот же
`fetch_pool(include_body=True)`, тот же репозиторий бюджета) — новый шаг
не добавляет второго обхода пула, только дополнительный вызов
`declared_deps.py wire` после уже сделанного `check`.

**Выбор: `repo-ci.yml`, шаг после существующего детектора рассинхрона,
только на `push`.** Не на `pull_request`: связи графа зависимостей —
общерепозиторное состояние, не относится к диффу конкретного PR; запись
на каждый параллельный PR-прогон умножала бы мутирующие вызовы к общему
токену без выгоды (идемпотентность спасает от ДУБЛИРОВАНИЯ связи, но не
от лишнего сетевого вызова на КАЖДЫЙ open PR при каждом push в них).

## Развилка (г): permissions `repo-ci.yml` — job-level или workflow-level

`repo-ci.yml` до этой задачи держит `issues: read` на уровне ФАЙЛА
(осознанно, комментарий у блока: «шаг ниже не пишет») — принцип минимума
прав. Новый шаг пишет (`addBlockedBy`), значит job `test` обязан нести
`issues: write`.

Поднимать это на уровне ФАЙЛА означало бы, что `archive-fixup` (второй
job) тоже получил бы это право по умолчанию — но `archive-fixup` уже
объявляет СВОЙ `permissions:` блок (`contents: read`, без `issues`),
переопределяющий файловый целиком (семантика GitHub Actions: job-level
`permissions:` заменяет, не расширяет) — значит поднятие на уровне файла
физически не задело бы `archive-fixup` в любом случае.

**Выбор: явный `permissions:` блок именно на job `test`**, не на уровне
файла — не потому что это меняет фактическое поведение `archive-fixup`
(не меняет), а потому что явная точечная запись честнее показывает
ГРАНИЦУ поднятия прав тому, кто читает файл: элевация — свойство ОДНОЙ
job, а не всего workflow, и это видно из diff без необходимости сверять
семантику переопределения соседней job.

Остаточный риск, названный прямо: на `pull_request`-прогонах `test` job
формально несёт `issues: write`, хотя пишущий шаг не исполняется (см.
развилку в) — токен шире, чем требуется для конкретного прогона. Это
принято, а не упущено: ни один шаг `test` job не подставляет
непроверенный текст PR в `run:`-блок с интерполяцией (`${{ }}` внутри
`run:` только для доверенных значений — `github.token`,
`GITHUB_REPOSITORY`), поэтому расширенный токен не создаёт нового вектора
инъекции — он просто не используется на этих прогонах.

## Что делает выбор неверным (пересмотреть при новом факте)

- Если частота заполнения поля вырастет настолько, что за один push
  накапливается заметное число новых связей одновременно (десятки) —
  можно пересмотреть частоту (стоит ли гонять на каждый push или
  достаточно раз в N) — но не раньше отдельного измерения нагрузки.
- Если владелец явно решит переносить и «Что блокирует» (обратное
  направление, `task.yml`) — потребуется отдельная развилка: писать
  `addBlockedBy` с перестановкой сторон или полагаться на то, что граф
  двусторонний по построению (GitHub сам показывает `blocking` как
  производную от чужого `blockedBy`, второй мутации не требуется) — из
  сегодняшнего объёма вынесено намеренно (proposal.md, Out).
