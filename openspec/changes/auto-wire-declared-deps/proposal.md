# Propose: автоперенос поля «Чем блокируется» в граф — для всех путей заведения задачи

## Summary

Задача #529 (владелец, 2026-09-06), прямое продолжение #361/#371
(`scripts/lib/task_deps.py`/`declared_deps.py`) и #387 (обязательное поле
«Чем блокируется» в `.github/ISSUE_TEMPLATE/task.yml`/`white-spot.yml`).

Замер на день внедрения (`task_deps.py pool`, живой прогон): 135 открытых
задач с меткой `task`, из них ровно ОДНА (эта самая, #529, заведённая перед
реализацией) несёт секцию `### Чем блокируется` в теле — остальные 134
заведены до появления обязательного поля (#387 смёржен только что) и его не
несут вовсе. Итог: перенос поля в граф для человеческого/шаблонного пути
сегодня даёт 0 новых связей — это не дефект механизма, это факт возраста
поля, честно зафиксированный здесь, а не подан как немедленный эффект.

## Problem / motivation

- #371 автоматизировал перенос ТОЛЬКО для одного поставщика пула —
  `scripts/review/file_tasks.py` (автозаведение из находок AI-ревью,
  контракт `БЛОКИРУЕТСЯ: …`, `wire_declared_dependency`). Для остальных
  путей (веб-форма шаблона, ручной/агентский `gh issue create`) перенос
  оставался ручной командой `task_deps.py block` — design.md #361/#371
  прямо называл это сознательным решением («форма не структурная для
  программных создателей issue»).
- #387 сделал поле «Чем блокируется» ОБЯЗАТЕЛЬНЫМ на входе в оба шаблона.
  Обязательность входа без автоматического переноса результата —
  наполовину закрытый класс: ответ есть в каждой новой issue, но он
  остаётся человекочитаемым следом, не фактом графа, пока кто-то не
  наберёт команду руками.
- `scripts/lib/declared_deps.py` уже содержит СТРУКТУРНЫЙ разбор этого
  поля (`_FORM_FIELD_RE`, добавлен ревью PR #387) — используется только
  детектором предупреждений (`find_desync`/`declared_candidates`),
  ничего не пишет.

## Правило

Значение обязательного структурного поля «Чем блокируется» (issue-формы
`task.yml`/`white-spot.yml`, рендер GitHub `### Чем блокируется\n\n<ответ>`)
переносится в нативный `blockedBy` АВТОМАТИЧЕСКИ на ближайшем прогоне
`repo-ci` после push в main — без ручной команды `task_deps.py block`.
Явный ответ «ничем» — валидный ответ обязательного поля, не создаёт
предупреждений/находок. Разбор — по заголовку секции (структура формы),
не по любому `#N` в теле: ложная связь опаснее отсутствующей (то же
правило, что для АИ-ревью-пути в #371).

## Scope

### In

- `scripts/lib/task_deps.py` — `wire_dependencies` (новая функция):
  единый цикл «пропустить номер вне открытого пула с меткой task/ссылку
  на себя, иначе `add_dependency` + лог» — переиспользуется ОБОИМИ
  вызывающими (АИ-ревью-путь и новый авто-перенос формы), не третья копия
  одного и того же кода.
- `scripts/review/file_tasks.py::wire_declared_dependency` — тело функции
  сведено к вызову `task_deps.wire_dependencies` (поведение и тексты
  предупреждений не меняются, покрыто существующими тестами).
- `scripts/lib/declared_deps.py` — `form_field_numbers` (структурный
  разбор ответа поля, отдельно от `declared_candidates`, которая мешает
  прозу и форму для предупреждения) и `auto_wire`/CLI `wire` (обход
  открытого пула, перенос недостающих номеров через `wire_dependencies`,
  идемпотентно — уже проставленные номера не трогает повторно).
- `.github/workflows/repo-ci.yml` — новый шаг «Автоперенос поля «Чем
  блокируется» в граф», выполняется ТОЛЬКО на `push` в main (не на каждый
  `pull_request`) — граф зависимостей общерепозиторный факт, не относится
  к конкретному PR; permissions `test`-job точечно поднят до `issues:
  write` (было `read`) с объяснением в комментарии рядом.

### Out

- Пульс оркестратора (`scripts/orchestra/scheduler.py`/`orchestra.yml`) —
  РАССМОТРЕН и отклонён как место автопереноса: это уже самый дорогой
  потребитель квоты GITHUB_TOKEN в репозитории (#454, ронял чужие
  обязательные проверки живым прогоном), добавлять туда ещё один проход
  пула на каждый 15-минутный тик — то же самое узкое место, только хуже.
  `repo-ci.yml` уже делает один такой проход на push (детектор рассинхрона,
  #371) — авто-перенос пристроен к нему же, не заводит второй.
- Массовая повторная миграция 132 старых задач без поля — НЕ строится:
  разовая миграция #371 уже показала, что подтверждается чтением ~1 из 20
  кандидатов эвристики; расширять её вручную вне объёма этой задачи.
  Авто-перенос сам подхватит любую из старых задач, если на неё позже
  добавят поле руками (`gh issue edit`) — отдельного действия не требуется.
- Поле «Что блокирует» (обратное направление, есть только в `task.yml`) —
  не переносится этой задачей: инструкция владельца называет только «Чем
  блокируется»; расширение на обратное направление — отдельное решение
  (граф пишется только со стороны `blockedBy`, `blocking` — производное
  поле того же ребра, второй записи не требует).
