# ai-verdict-survives-merge: вердикт AI не сбрасывается, если дифф не изменился (#252)

Задача: #252 (направление 1+3, оставленные вне рамок предыдущей дельты
`selective-branch-update`). Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`selective-branch-update` (та же задача #252, направление 2) сузила круг
PR, которые вообще подтягиваются из main — но для PR, который ДЕЙСТВИТЕЛЬНО
подтягивается (у него уже есть `conflict`, либо он близок к слиянию),
проблема осталась: `check_pr.py` при каждом пуше безусловно снимает все
`ai:*`-метки (`review_labels.ai_verdicts_to_drop`), не различая «дифф PR
изменился» (сброс обязателен) от «в ветку влили main, а дифф относительно
base — тот же набор патчей» (сбрасывать нечего, ревьюер видел ровно этот
код). Сама задача #252 явно называла это направление 3 («не терять вердикт
при подтягивании») и направление 1 («не запускать второй гейт, если
содержательный дифф не изменился») — `selective-branch-update` их не
реализовывала, зафиксировав это разделом «Что вне рамок».

Замер 2026-09-04: слияние #288 → оркестратор подтянул #292 → `ai:ok`
слетел → слияние #292 не состоялось на этом же обходе, PR ушёл на новый
круг ai-review, хотя дифф #292 относительно `main` не изменился ни на
байт (подтверждено ниже).

## Диагноз (проверено на реальных данных репозитория)

PR #292: два коммита — собственный (`659b518`) и один `Merge branch 'main'`
(`5432ce5`) без конфликтов. Список файлов и их blob-sha в ответе
`gh api repos/.../compare/<merge-base>...<sha>` ДО слияния и ПОСЛЕ —
побайтово идентичны (9 файлов, те же имена, те же sha). Значит: чистое
подтягивание main меняет только head PR, а не патчи относительно base —
дифф, который ревьюер видел, это ровно тот же дифф, что и после
merge-коммита.

Контрпример (тоже реальные данные, PR #253, без единого merge-коммита):
между двумя настоящими пушами автора список файлов дифф-а меняется
(с 8 до 7 файлов) — здесь сброс обязателен.

## Что сделано

- **Отпечаток диффа** — `scripts/lib/review_labels.py::diff_fingerprint`:
  sha256 по отсортированному списку `имя_файла:статус:blob-sha` из
  `gh api pulls/{n}/files`. Не число строк — blob-sha содержимого, поэтому
  две разные правки одинакового размера получают разные отпечатки (класс,
  который явно назвала issue #252), а порядок страниц API и переименования
  не путают сравнение (сортировка + статус в строке).
- **Хранилище отпечатка** — переиспользован существующий механизм: поле
  `diff:` в шапке ревью-комментария AI (`ai_review.py::build_comment`,
  та же шапка `pr:`/`head:`/`reviewer:`, которую уже читает
  `file_tasks.py`). Второго хранилища не заведено.
  `review_labels.py::latest_ai_comment` листает комментарии PR (та же
  постраничная логика, что и `file_tasks.latest_review_comment`) и
  возвращает последний с решающим `reviewer:`.
- **Решение** — `check_pr.py::ai_verdict_keep(labels, stored_fp, current_fp)`:
  чистая функция, true только если на PR уже есть ai:*-метка И отпечаток
  совпал (`review_labels.diff_unchanged`). Нет сохранённого отпечатка (старый
  комментарий без поля diff, сеть отказала, комментария нет вовсе) —
  трактуется как «изменился»: гейт не ослабляется, при сомнении — сброс.
- Гейт не тронут ни в одну сторону кроме этого условия: любая реальная
  правка файлов PR по-прежнему меняет отпечаток и снимает метку.

## Что вне рамок

- Направление 1 issue #252 («не запускать второй гейт, если содержательный
  дифф не изменился») закрыто этой же правкой как следствие: раз метка не
  снимается, `ai-review.yml` (триггер `labeled:review:ok`) не перезапускается
  повторно на неизменном диффе — отдельного условия в workflow не требуется.
- Гвардия на содержательно пустой/отрицательный PR (раздел issue «Отдельно»,
  пересекается с #217) — независимая задача, не входит в эту дельту.
- `scripts/orchestra/scheduler.py`, `should_update_branch`, `mark_conflicts`
  (направление 2, уже сделано в `selective-branch-update`) — не трогаются.
