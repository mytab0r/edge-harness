# ai-verdict-survives-merge: вердикт AI не сбрасывается, если дифф не изменился (#252)

Задача: #252 (направление 1+3, оставленные вне рамок предыдущей дельты
`selective-branch-update`). Дельта-спека:
[specs/journal-tasks-hands/spec.md](specs/journal-tasks-hands/spec.md).

## Зачем

`selective-branch-update` (та же задача #252, направление 2) сузила круг
PR, которые вообще подтягиваются из main — но для PR, который ДЕЙСТВИТЕЛЬНО
подтягивается (у него уже есть `conflict`, либо он близок к слиянию),
проблема осталась: `check_pr.py` при каждом пуше безусловно снимает все
`ai:*`-метки (`review_labels.ai_verdicts_to_drop`), не различая «дифф PR
изменился» (сброс обязателен) от «в ветку влили main, а дифф относительно
base — тот же набор патчей» (сбрасывать нечего, ревьюер видел ровно этот
код). Сама задача #252 явно называла это направление 3 («не терять вердикт
при подтягивании») и направление 1 («не доводить второй гейт до дорогого
прогона — чекаута pr-head/gather/DSH, — если содержательный дифф не
изменился») — `selective-branch-update` их не реализовывала, зафиксировав
это разделом «Что вне рамок».

Метрика направления 1 — число ДОРОГИХ прогонов (дошедших до шага gather),
не общее число стартов `ai-review.yml`: триггер `workflow_run` не тронут и
никогда не был целью правки — workflow стартует на каждом успешном
`pr-review`, как и раньше (см. правку ниже, «направление 1 закрыто
отдельно»).

Замер 2026-09-04: слияние #288 → оркестратор подтянул #292 → `ai:ok`
слетел → слияние #292 не состоялось на этом же обходе, PR ушёл на новый
круг ai-review, хотя дифф #292 относительно `main` не изменился ни на
байт (подтверждено ниже).

## Диагноз (проверено на реальных данных репозитория)

PR #292: два коммита — собственный (`659b518`) и один `Merge branch 'main'`
(`5432ce5`) без конфликтов. Список файлов и их blob-sha в ответе
`gh api repos/.../compare/<merge-base>...<sha>` ДО слияния и ПОСЛЕ —
побайтово идентичны (9 файлов, те же имена, те же sha). Значит: чистое
подтягивание main меняет только head PR, а не патчи относительно base —
дифф, который ревьюер видел, это ровно тот же дифф, что и после
merge-коммита.

Контрпример (тоже реальные данные, PR #253, без единого merge-коммита):
между двумя настоящими пушами автора список файлов дифф-а меняется
(с 8 до 7 файлов) — здесь сброс обязателен.

## Что сделано

- **Отпечаток диффа** — `scripts/lib/review_labels.py::diff_fingerprint`:
  sha256 по отсортированному списку `имя_файла:статус:blob-sha` из
  `gh api pulls/{n}/files`. Не число строк — blob-sha содержимого, поэтому
  две разные правки одинакового размера получают разные отпечатки (класс,
  который явно назвала issue #252), а порядок страниц API и переименования
  не путают сравнение (сортировка + статус в строке).
- **Хранилище отпечатка** — переиспользован существующий механизм: поле
  `diff:` в шапке ревью-комментария AI (`ai_review.py::build_comment`,
  та же шапка `pr:`/`head:`/`reviewer:`, которую уже читает
  `file_tasks.py`). Второго хранилища не заведено.
  `review_labels.py::latest_ai_comment` листает комментарии PR (та же
  постраничная логика, что и `file_tasks.latest_review_comment`) и
  возвращает последний с решающим `reviewer:`.
- **Решение** — `check_pr.py::ai_verdict_keep(labels, stored_fp, current_fp)`:
  чистая функция, true только если на PR уже есть ai:*-метка И отпечаток
  совпал (`review_labels.diff_unchanged`). Нет сохранённого отпечатка (старый
  комментарий без поля diff, сеть отказала, комментария нет вовсе) —
  трактуется как «изменился»: гейт не ослабляется, при сомнении — сброс.
- Гейт не тронут ни в одну сторону кроме этого условия: любая реальная
  правка файлов PR по-прежнему меняет отпечаток и снимает метку.

## Что вне рамок

- Гвардия на содержательно пустой/отрицательный PR (раздел issue «Отдельно»,
  пересекается с #217) — независимая задача, не входит в эту дельту.
- `scripts/orchestra/scheduler.py`, `should_update_branch`, `mark_conflicts`
  (направление 2, уже сделано в `selective-branch-update`) — не трогаются.

## Правка после вердикта AI-ревью PR #294: направление 1 закрыто отдельно

Первая версия этого раздела ошибочно считала направление 1 issue #252
(«не запускать второй гейт, если содержательный дифф не изменился») уже
закрытым как следствие сохранения метки — формулировка предполагала, что
`ai-review.yml` триггерится меткой `labeled:review:ok`. Это неверно (см.
шапку `ai-review.yml`): единственный рабочий триггер — `workflow_run` от
`pr-review`, потому что события от `GITHUB_TOKEN` (которым ставит метки
`check_pr.py`) не создают триггеров по меткам (антирекурсия GitHub).
Предохранители job'а `review` (успех `pr-review`, наличие `review:ok`,
совпадение head) все зелёные и при чистом подтягивании main — дорогой
прогон стартовал вхолостую, критерий приёмки не выполнялся.

Уточнение метрики (находка вердикта ai-review PR #294, критика самой
формулировки критерия, не только реализации): `workflow_run`-триггер эта
правка не трогает и не могла тронуть — `ai-review.yml` стартует на КАЖДОМ
успешном `pr-review`, как и до неё; это не число, которое правка обязана
снижать. Правильная метрика — число ДОРОГИХ прогонов, то есть дошедших до
шага «Сбор фактов и промпт (доверенный шаг)» (`gather`) job'а `review`, а
не общее число стартов workflow. Запрос для подсчёта (владелец снимает
число «после» сам после слияния — за то же окно, что и «до»):

```
# Все старты ai-review.yml за окно (НЕ метрика экономии — не убывает):
gh api "repos/mytab0r/edge-harness/actions/workflows/ai-review.yml/runs?created=<окно>&per_page=100" \
  --jq '.workflow_runs | length'

# ДОРОГИЕ прогоны — job review дошёл до шага gather (conclusion не skipped):
for id in $(gh api "repos/mytab0r/edge-harness/actions/workflows/ai-review.yml/runs?created=<окно>&per_page=100" \
  --jq '.workflow_runs[].id'); do
  gh api "repos/mytab0r/edge-harness/actions/runs/$id/jobs" \
    --jq '.jobs[] | select(.name=="review") | .steps[]
          | select(.name=="Сбор фактов и промпт (доверенный шаг)") | .conclusion'
done | grep -vc '^skipped$'
```

Починено: `scripts/review/ai_review.py::cmd_should_run` (подкоманда
`should-run`) вызывает `review_labels.should_run_ai_review` — то же место
правды, что читает `check_pr.py::ai_verdict_keep` — из нового шага
`fingerprint` в `ai-review.yml`, ДО чекаута `pr-head`/`gather`/DSH. Диффу
не изменился и вердикт уже окончательный (`ai:ok`/`ai:changes-requested`) —
шаг отдаёт `go=false`, и job `review` останавливается до какой-либо дорогой
работы (шаг gather и все последующие получают `conclusion: skipped`, но сам
job и workflow всё равно стартуют и завершаются — метрика правки в числе
дорогих прогонов, не в числе стартов). `ai:failed` из этого правила
исключён: его автоповтор по таймеру (`scheduler.py::trigger_ai_review`,
#196) не должен зависеть от того, менялся ли дифф — иначе совпавший
отпечаток немо отнял бы газ, которым чинится 84% ручных перезапусков (#207).
