# Дельта-спека: журнал (journal-tasks-hands) — AI-ревью как второй гейт

## MODIFIED: Конвейер (оркестратор)

~~Требование: PR сливается только при: зелёные обязательные проверки, метка
`review:ok`, отсутствие конкурирующего открытого PR на ту же задачу.~~

Требование: PR сливается только при: зелёные обязательные проверки, метка
`review:ok` (детерминированное ревью, `scripts/review/check_pr.py`), метка
`ai:ok` (AI-ревью, `scripts/review/ai_review.py`, #18) и отсутствие
конкурирующего открытого PR на ту же задачу. Формулировка гейта по меткам —
одно место правды: `scripts/lib/review_labels.py::merge_label_gate`.

Сценарий: PR с `review:ok`, но без `ai:ok` (AI-ревью не закончено, вернуло
`ai:changes-requested` или `ai:failed`) — оркестратор пропускает его с
причиной в отчёте, слияния нет.

## ADDED: AI-ревью (второй гейт)

Требование: после успешного завершения детерминированного ревью с меткой
`review:ok` запускается AI-ревью диффа (workflow `ai-review`, триггер
`workflow_run` по завершению workflow `pr-review` — GITHUB_TOKEN-метки
событий не создают, research/21): содержательное ревью агентом DSH —
соответствие ADR/спекам, скрытые регрессии, предложения задач в беклог.
Истиной о «гейт открыт» остаётся метка `review:ok`, проверяемая доверенным
шагом (успешный pr-review может ставить и `review:large`). Итог — ревью-комментарий в PR
и метка-вердикт `ai:ok` / `ai:changes-requested`; инфраструктурный сбой
(модель недоступна, ответ без валидного контракта) — `ai:failed` и красный
job: гейт закрыт, повтор — workflow_dispatch с номером PR.

Сценарий: ответ модели без машиночитаемой последней строки
«ВЕРДИКТ: approve|rework» (нет, две или не последняя) — вердикт `error`,
метка `ai:failed`, публикация «одобрено» невозможна; двусмысленность никогда
не одобряет.

Требование (trust-zone #18): граница доверия — между job'ами workflow
`ai-review`. Недоверенный DSH-шаг живёт в job'е с правами только на чтение
и без GitHub-токенов; всё, что агент может испортить (файлы воркспейса,
общие env/PATH), умирает вместе с виртуалкой job'а. Вердикт публикует
отдельный доверенный job на свежей машине из чистого чекаута GitHub: ответ
ревью и head переезжают между job'ами выводами доверенных шагов (данные,
не код), номер PR — из выводов доверенного шага фактов (у workflow_run
pull_request-контекста нет).

Сценарий: попытка агента запостить/запушить из ревью-job'а проваливается по
отсутствию прав и токенов; дописанные агентом файлы/env не влияют на
исполняемый доверенным job'ом код — он чекаутится из GitHub заново.

Требование: вердикт AI привязан к head — применяется только если head PR не
изменился с момента сбора фактов; детерминированное ревью при каждом запуске
(каждый пуш) снимает все `ai:*`-метки до постановки своего вердикта.

Сценарий: новый пуш во время AI-ревью — летящий вердикт не применяется
(проверка head), метки `ai:*` сняты, новое ревью запускается само по
завершению нового прогона pr-review; слияние по протухшему вердикту
невозможно. События уже отгоревших PR (миграция, сбои) не восстанавливаются —
повтор ручным `workflow_dispatch` с номером PR.

**Суперсессия (2026-09-05).** Требование выше — «каждый пуш снимает все
`ai:*`» — заменено изменением `ai-verdict-survives-merge` (#294): снятие
`ai:*` стало условным, по отпечатку диффа PR относительно base
(`review_labels.diff_fingerprint`/`diff_unchanged`), а не безусловным на
каждый пуш; шапка ревью-комментария AI получила поле `diff:` для хранения
этого отпечатка. См.
`openspec/changes/ai-verdict-survives-merge/specs/journal-tasks-hands/spec.md`
и `docs/decisions/0007-ai-review-gate.md` (раздел «Дельта 2026-09-05»). Текст
требования выше не переписан — оставлен как принятый исходно.

Требование: ревью-комментарий несет шапку-факты (`pr:`, `head:`,
`reviewer:`) первыми строками до первого пустой строки и канонические блоки
предложенных задач; задачи заводятся в пул одной командой
`python scripts/review/file_tasks.py --pr N` (issue с меткой `task`),
идемпотентно по заголовку открытой задачи.

Сценарий: ревью предложило задачи → команда завела их в пул; повтор команды
не создаёт дублей (совпадающий заголовок открытой задачи — пропуск).
