# Дизайн: ai-review-gate

Задача #18. Контекст и отвергнутые альтернативы —
[ADR 0007](../../../docs/decisions/0007-ai-review-gate.md); здесь — механика
и «почему именно так» по частям, которые не очевидны из кода.

## Поток одного ревью

```
PR получает review:ok (check_pr.py, первый гейт)
        │ pr-review завершается (GITHUB_TOKEN-метки событий не создают —
        │ research/21; событийный вход — workflow_run)
        ▼
job review (права: только чтение; ВМ умирает вместе с недоверенным шагом)
        ├─ 1. Факты PR (GH_TOKEN): номер (head_branch+владелец из события)
        │      + head-sha + решение «ревьюим?» (метка review:ok) → step-outputs
        ├─ 2. checkout main — доверенный инструментарь для шагов с токеном
        ├─ 3. checkout head PR → pr-head: дерево-ДАННЫЕ для агента
        ├─ 4. gather (GH_TOKEN, скрипты из main): дифф-пак, задача пула, промпт
        ├─ 5. DSH headless (БЕЗ токенов, cwd=pr-head): ответ → answer.txt
        └─ 6. Доверенный мост: answer + head (step-output фактов) → outputs
                        │
                        ▼
job verdict (свежая ВМ, права: pull-requests:write, чекаут main)
        └─ 7. verdict: контракт → комментарий + метка ai:* (текущий head PR
               сверяет сам через API; номер PR — из outputs доверенного шага)
```

Оркестратор (тик ≤15 мин) сливает только при зелёных проверках, контракте,
`review:ok` и `ai:ok`.

## Trust-зона: граница — отдельная виртуалка, а не дисциплина промпта

Разрез «по env в одном job'е» отвергнут живым ревью PR #137: шаги одного
job'а делят workspace, `$GITHUB_ENV` и PATH — непрямая prompt-инъекция через
ревьюимый дифф могла дописать переменные/файлы так, что доверенный шаг
исполнил бы переписанный агентом код уже с токеном. Поэтому:

- недоверенный шаг живёт в job'е с правами ТОЛЬКО на чтение — даже уцелевшие
  после чекаута временные креды физически не могут постить;
- доверенный код — ВСЕГДА из main: шаги с GH_TOKEN исполняются из чекаута
  main, ревьюимое дерево лежит рядом (pr-head) и является для агента
  данными. PR физически не может подсунуть скрипт под токен (живой прогон
  на PR #108: gather упал на ветке без скриптов — и вскрыл класс);
- всё испорченное агентом (файлы, env, PATH) умирает вместе с ВМ job'а;
- verdict исполняется на свежей машине из чистого чекаута GitHub —
  переписать исполняемый код нельзя;
- ответ и head момента gather переезжают между job'ами выводами доверенного
  шага (`$GITHUB_OUTPUT` шага закрывается на момент чтения — дописать в
  чужой step-файл нельзя): это данные, не код;
- номер PR verdict берёт из outputs доверенного facts-шага: у workflow_run
  pull_request-контекста нет вовсе, а outputs поздней записью не подделать.

Промпт по-прежнему сообщает «ты не публикуешь результат сам», но гарантией
служит архитектура, а не инструкция. `DEEPSEEK_API_KEY` в окружении
недоверенного шага нужен адаптеру модели; DSH вырезает env
`*TOKEN*/*KEY*/*SECRET*` из model-shell вызовов — агент и его не видит.

## Гонки и как они закрыты

1. **Слив до первого AI-ревью.** Окна нет: `ai:ok` не существует, пока
   AI-ревью не прошло, а merge_queue требует обе метки.
2. **Слив по протухшему `ai:ok` после нового пуша.** Два независимых замка:
   check_pr.py выполняется на каждый пуш и снимает все `ai:*` до постановки
   своего вердикта; verdict применяет вердикт только при head, совпадающем
   с зафиксированным в gather (head едет через outputs доверенных шагов,
   не через общий GITHUB_ENV).
3. **Параллельные ревью одного PR.** Возможны и осознанно разрешены: группа
   привязана к породившему pr-review-рану, а новый пуш даёт новый ран (новую
   группу). Отмены нет — летящее ревью дообрабатывается и умирает на
   head-сверке вердикта; ценой являются минуты DSH, не потерянный вердикт.
4. **Скипнутый run убивает летящее ревью.** `labeled`-событие любой метки
   создаёт run группы (job-if его скипает, но место занимается) — поэтому
   `cancel-in-progress` НАМЕРЕННО выключен: отмена таким run'ом погасила бы
   ревью без автоперезапуска. Потеря экономии минут против потерянного
   ревью не равноценна; протухший вердикт всё равно не применяется
   сверкой head.
5. **Модель ушла в бесконечность.** `timeout` в ai_dsh.sh (60 мин) +
   `timeout-minutes` job (70); пустой ответ = `error` → `ai:failed`, гейт
   закрыт, job красный.

## Триггер: workflow_run, а не labeled (замер)

Метки, поставленные GITHUB_TOKEN (так ставит review:ok сам check_pr), не
создают workflow-событий — антирекурсия GitHub. Поэтому событийный триггер
ai-review — завершение pr-review (`workflow_run`): conclusion=success плюс
проверка МЕТКИ review:ok в доверенном facts-шаге (успешный pr-review может
ставить и review:large). Номер PR в событии workflow_run отсутствует —
разрешается по head_sha завершившегося рана; раны без открытого PR или без
review:ok завершаются зелёным no-op (это нормальные гонки, не ошибки).
Отгоревшие события (миграция открытых PR) не восстановить — только
workflow_dispatch.

## Ограничение платформы: новый workflow не самоприменяется (замер)

Файл workflow, существующий только на ветке PR, не получает `pull_request`-события
этого PR (подробности и улики — research/21, раздел «Новый workflow-файл в PR»).
Поэтому «ревью собственного диффа до мержа» невозможно конструкцией, а не ошибкой
настройки: проверка живьём — пост-мерж (dispatch на открытые PR, чей триггер
отгорел, и первый следующий PR). Это же ограничение делает обязательной миграцию
открытых PR при добавлении нового условия слияния (см. tasks.md).

## Контракт ответа и его разбор

Паттерн владельца из Harness (pr_loop.py + prompts/pr_review.md), сохранён
дословно по смыслу: последняя непустая строка — ровно `ВЕРДИКТ: approve|rework`
(единственная). Реализация `parse_verdict` повторяет `cli_verdict` Harness:
маркеры собираются по всем строкам, «ровно один и он последний» — иначе
`error`. Двусмысленность не одобряет и не разваливается в rework — ревью
повторяется (workflow_dispatch).

Блоки задач (`ЗАДАЧА: … КОНЕЦ ЗАДАЧИ`) парсятся строго: незакрытый или
безымянный блок отбрасывается целиком — полузадача в пуле дороже её отсутствия.

## Комментарий-вердикт как носитель состояния

Шапка-факты (`pr:`, `head:`, `reviewer:`) — первые строки до первого пустой
строки; `header_facts` читает только эту зону, поэтому проза и фенсы задач не
могут притвориться фактами (в Harness ту же роль играл блокцит `> `). Задачи
переносятся транспортом в канонические фенсы ```` ```задача ```` — их читает
`file_tasks.py`. Идемпотентность заведения — по заголовку открытой issue:
повтор команды не дублирует пул.

## Маскирование

Всё, что публикуется (находки, тела задач, диагностический хвост при
`error`) или пишется в публичный лог job'а (хвост stderr DSH в ai_dsh.sh),
проходит `redact` из `scripts/lib/dsh-ci.sh` — тот же sed, что у
bash-транспортов (python вызывает его subprocess'ом, паттерны не
дублируются на второй язык). Первый гейт уже не пускает секреты в дифф, но
модель может их синтезировать — публикация от имени владельца обязана быть
чистой по построению.
