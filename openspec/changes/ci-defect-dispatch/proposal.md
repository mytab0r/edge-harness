# ci-defect-dispatch: немедленный адресный диспетч починки вместо очереди пула (#552)

Задача: #552. Код: `scripts/orchestra/scheduler.py::dispatch_defect_rework`
(вызывается из `main()` рядом с `dispatch_conflict_rework`), пороги —
`scripts/orchestra/pulse_guard.py` (`DEFECT_DISPATCH_MAX_ATTEMPTS`,
`DEFECT_DISPATCH_MARKER`, `DEFECT_ESCALATION_MARKER`). Строится поверх
`failure-watch` (#477, задача #488, на момент этой задачи ещё не слита) —
дельта здесь предполагает её код (`failure_watch`, `FAILURE_WATCH_LABEL`,
`classify_failure_cause`) уже доступным.

## Зачем

`failure_watch` (#477) заводит задачу на дефект CI и на этом всё — чинит её
человек вручную, из общей очереди пула (~130 задач), пока владелец не
заметит и не почешет вручную (замер: 20–40 минут вручную на инцидент).
Дословно владелец: «В чём прикол мониторинга ошибок, который нихуя не
исправляет?»

## Что делается

- **Адресный диспетч немедленно** — `dispatch_defect_rework` каждый пульс
  ищет в уже прочитанном пуле (`pool`, без второго обхода Issues) задачи с
  меткой `FAILURE_WATCH_LABEL`, ещё без исполнителя и без метки `blocked`, и
  запускает `worker.yml` адресно (`inputs[task]=N`) — тот же путь, что уже
  доводит открытые PR (#245/#394) и авто-расшивает конфликты
  (`dispatch_conflict_rework`, #474).
- **Приоритет над остальным диспетчем этого пульса** — вызывается ДО
  `dispatch_conflict_rework` и ДО обычного `dispatch_worker`: сломанный
  конвейер важнее одного конфликтующего PR и важнее подбора новой задачи.
  Идемпотентность «один `workflow_dispatch worker.yml` за пульс» — тот же
  флаг `dispatched`, что уже прокидывают `dispatch_conflict_rework`/
  `dispatch_worker`.
- **Мимо WIP-лимита (#464) целиком** — адресный прогон на конкретную задачу,
  не подбор новой: `wip_gate` в цепочку вызова не входит вовсе (тот же довод,
  что уже применяет `dispatch_conflict_rework`).
- **За тем же предохранителем (#120)** — если `conveyor_gate` уже держит
  паузу (класс «сам worker.yml нездоров»), адресный дефект-диспетч тоже не
  уходит: не добавляем новых прогонов воркеру, пока конвейер и так красный.
- **Один лифтайм-бюджет попыток на задачу** (`DEFECT_DISPATCH_MAX_ATTEMPTS`
  = 1, маркер-комментарий на самой задаче — тот же приём, что
  `CONFLICT_REWORK_MARKER` на PR): исчерпан, задача всё ещё открыта и без
  исполнителя — эскалация владельцу тем же каналом (#120 + Telegram),
  идемпотентная по номеру задачи (`DEFECT_ESCALATION_MARKER` + номер).
- **`blocked` не переэскалируется** — если воркер сам решил по
  WORKER-PLAYBOOK, что чинить нечего его силами (эскалация по плейбуку,
  метка `blocked`, PR не открыт), дефект-диспетч эту задачу не трогает: она
  уже видима владельцу, вторая порция шума не нужна.

## Чего изменение не делает

Не меняет классификацию причины (`infra`/`stale_base`/`defect`) — она
целиком в `failure_watch` (#477). `infra`/`stale_base` не заводят задачу
вовсе, адресовать нечего. Не решает за воркера, «поддаётся ли дефект
починке»: это решает сам воркер по WORKER-PLAYBOOK (эскалация `blocked`,
если нет) — дефект-диспетч только запускает его раньше очереди, не
подменяет его суждение.

## Тормоза и газ

Нового тормоза для остального конвейера нет: адресный диспетч тратит тот же
единственный слот `workflow_dispatch worker.yml` за пульс, что и раньше.
Тормоз "не сошлось за одну попытку" — эскалация владельцу (комментарий #120
+ Telegram), не бесконечный повтор; газ — решение владельца после эскалации
(починить руками/переформулировать задачу/закрыть как неактуальную).

## Отвергнутые варианты

Второй, независимый предохранитель (аналог `conveyor_gate`, но по классу
дефекта CI) не заводится — бюджет попыток по маркеру на самой задаче
(тот же приём, что `CONFLICT_REWORK_MAX_ATTEMPTS`) уже даёт нужное
поведение «один раз, потом эскалация» без второй копии порогов правды.
Эвристика «дефект фиксится автоматически / требует решения владельца» до
попытки не вводится (никакого способа отличить их по строке `##[error]`
нет, а гадать между гипотезами запрещает AGENTS.md) — различает сам воркер
по факту работы, эскалируя `blocked`, если не может.
