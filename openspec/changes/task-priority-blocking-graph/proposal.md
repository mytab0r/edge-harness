# Propose: приоритет пула — граф блокировок (нативные GitHub-зависимости), не дата создания

## Summary

Задача #361 (владелец, 2026-09-06). Воркер выбирает свободную задачу
`scripts/lib/free_task.py::oldest_free` строго по номеру issue (proxy даты
создания) — старейшая первой. Владелец хочет другой порядок: (1) задачи о
самом процессе работы — всегда первыми; (2) внутри уровня — по числу
ОТКРЫТЫХ задач, которые блокирует эта (больше блокирует — раньше); (3) при
равенстве — по дате создания (номер issue как proxy).

Носитель зависимости — нативный GitHub GraphQL `blockedBy`/`blocking`
(`issueDependenciesSummary`), НЕ прозопарсинг: строка «Зависимости» в теле
задачи (документирована в `docs/agents/PROTOCOL.md` до этого change) — тот
же запрещённый класс, что уже чинили #251/#259 (task_ref.declared_tasks:
первая структурная строка, а не любое упоминание `#N`).

## Problem / motivation

### Замер (сделан этим change, не домыслен)

- `scripts/lib/free_task.py::free_candidates` сортирует
  `sorted(free, key=lambda issue: issue["number"])` — единственный критерий
  порядка внутри пула. Приоритет = дата создания, без исключений.
- Граф блокировок ФАКТИЧЕСКИ ПУСТ на день замера (2026-09-06): живой запрос
  `Repository.issues(states: OPEN, labels: ["task"], first: 100)` с полем
  `issueDependenciesSummary { blockedBy blocking }` по всем 103 открытым
  задачам не находит НИ ОДНОЙ с ненулевым значением. Метка `blocked` стоит
  на 2 задачах из ~104 (#216, #6) — это ДРУГОЙ механизм (эскалация владельцу,
  не граф зависимостей между задачами пула).
- Документированная в `docs/agents/PROTOCOL.md` («Зависимости — два
  механизма») конвенция «строка «Зависимости» в теле блокирующей задачи,
  один раз» — это прозопарсинг: тот же класс, что `task_ref.py` уже закрыл
  для контракта «PR → задача» (#251, #259) и «первая строка теста» вместо
  «любое `#N` в тексте» (#187, #195). Считать вес по прозе значило бы
  повторить закрытый класс бага в новом месте.
- Нативная альтернатива живая и проверена этим change (не по документации):
  GraphQL `Issue.blockedBy`/`Issue.blocking`/`Issue.issueDependenciesSummary`
  и мутации `addBlockedBy`/`removeBlockedBy` существуют и работают на этом
  плане (round-trip на issue #350↔#320: связь поставлена, прочитана, снята).
  REST `repos/{o}/{r}/issues/{n}` этих полей НЕ отдаёт (только
  `sub_issues_summary`, для декомпозиции) — подтверждено тем же запросом:
  GraphQL — единственный носитель этих данных.

### Почему не расширяет #224

#224 («Порядок работ объясним») явно исключает из объёма «изменение способа
фиксации зависимостей (он уже выбран и задокументирован)» и держит низкий
приоритет по прямому слову владельца («после более критичных тикетов»).
Но выбранный на момент #224 способ — прозопарсинг, запрещённый классом
#251/#259/#355 (владелец сослался на них прямо, ставя эту задачу). Эта
задача правит НОСИТЕЛЬ (первый шаг, обязательный до вычисления веса); #224
остаётся про диаграмму/роль поверх готового графа и не трогается.

## Правило

Зависимость «задача A блокирует задачу B» — факт графа GitHub (нативный
`blockedBy`/`blocking`), не текст. Приоритет считается ТОЛЬКО по этому факту
и по метке происхождения (мета vs прикладная); чтение прозы для решения
«что кого блокирует» в вычислении приоритета не участвует.

## Scope

### In

- `scripts/lib/task_deps.py` (новый) — единственное место правды на чтение/
  запись нативного графа зависимостей GitHub через GraphQL: пагинированная
  выборка открытого пула с `labels`/`assignees`/`blockedBy`/`blocking`,
  подсчёт «сколько ОТКРЫТЫХ задач блокирует» на issue, CLI для ручной
  установки связи (`block`/`unblock`), заменяющий прозо-конвенцию.
- `scripts/lib/free_task.py` — приоритет вместо чистого номера: три уровня
  (мета-метка → количество блокируемых открытых задач → номер issue как
  proxy даты). Публичное имя `oldest_free`/CLI-глагол `oldest-free`
  сохраняются (третий уровень при пустом графе и без меты вырождается в
  прежнее поведение — обратная совместимость поведения, не имени).
- `scripts/worker/task.sh` — сборка пула для `free_task.py` идёt через
  `task_deps.py` (GraphQL), а не `gh issue list` (REST не отдаёт зависимости)
  — одно место фактического получения пула, не два расходящихся запроса.
- `docs/agents/LABELS.md` — новая метка `area:process` (мета-классификатор,
  «про то, как ведётся работа», а не про продуктовую фичу) с проверяемым
  критерием; заодно закрывается found white-spot (см. ниже) — `area:*`
  вводятся как полноценные строки реестра (было 0 из 5).
- `.github/ISSUE_TEMPLATE/task.yml` — `area:process` добавлен в дропдаун
  «Площадь» (пятое значение к четырём существующим).
- `scripts/lib/collect_labels.py` — сканирование `options:` дропдауна
  шаблонов issue (было: сканировался только `labels:` фронтматтера — все
  `area:*` были невидимы гвардии реестра меток, находка этого change).
- `docs/agents/PROTOCOL.md` — раздел «Зависимости — два механизма»
  заменяется третьим: нативный `blockedBy`/`blocking` через `task_deps.py`
  вместо строки «Зависимости» в теле (для отношения «блокирует», не
  декомпозиции — sub-issues не трогаются).
- Проставление `area:process` по текущему открытому пулу — по критерию,
  названному в LABELS.md.

### Out

- Автоматический workflow, конвертирующий текст задачи в связи графа при
  создании issue (`issues: opened`) — не строится: большинство задач пула
  заводится не через веб-форму шаблона (`gh issue create -f body=`, минуя
  валидацию GitHub), значит серверная валидация формы не была бы
  enforced ни для одного реального создателя пула. Вместо неё — единый
  CLI (`task_deps.py block/unblock`), тот же паттерн, что уже принят для
  sub-issues (`docs/agents/PROTOCOL.md`, ручной `gh api ... sub_issue_id=`).
- Обратное заполнение графа для существующих ~104 открытых задач —
  требовало бы предметного суждения по каждой паре, не механизируется;
  граф пуст осознанно, это измеренное текущее состояние, а не дефект.
- Диаграмма Ганта / оценка длительности задач, «критичность от заказчика»
  как отдельная метка происхождения приоритета (кроме area:process) —
  весь остальной объём #224, отдельная задача с явно низким приоритетом.
- Исключение заблокированных задач из пула (`blockedBy` открыт) — это
  ORDERING-фича (приоритет), не EXCLUSION-фича; исключение — уже
  существующий, отдельный механизм метки `blocked` (эскалация владельцу),
  не трогается и не смешивается с новым графом.

## Impacted domains

- `scripts/lib/free_task.py`, `scripts/lib/task_deps.py` (новый).
- `scripts/worker/task.sh` (сборка пула для выбора задачи).
- `scripts/orchestra/scheduler.py::dispatch_worker` — найденный по ходу
  дефект «два места правды» (не отдельная задача, тот же класс): локальная
  сортировка по номеру дублировала `free_task.py` для строки отчёта «какую
  задачу возьмёт воркер». Заменена на вызов той же приоритетной функции —
  иначе отчёт планировщика и реальный выбор воркера немедленно разошлись
  бы после этого change (отчёт продолжал бы называть старейшую по номеру,
  воркер — приоритетную по графу).
- `docs/agents/LABELS.md`, `docs/agents/PROTOCOL.md`,
  `.github/ISSUE_TEMPLATE/task.yml`, `scripts/lib/collect_labels.py`.
- `openspec/specs/journal-tasks-hands.md` (п.26/28, «Автономный воркер»).

## Acceptance criteria

1. Живой запрос доказывает: `addBlockedBy`/`removeBlockedBy`/`blockedBy`/
   `blocking`/`issueDependenciesSummary` работают на этом плане — round-trip
   в PR (issue-пара, связь поставлена и снята), не только документация.
2. `scripts/lib/free_task.py` выбирает по трём уровням: тест на каждый
   уровень + смешанный случай (мета с одним блокируемым обгоняет
   прикладную с десятью открытыми блокируемыми).
3. `area:process` определена в `docs/agents/LABELS.md` с проверяемым
   критерием (не «на глаз») и проставлена на подходящие открытые задачи —
   число и признак названы в PR.
4. Пустой граф (или мета-статус не проставлен ни у одной задачи пула) даёт
   видимый сигнал (stderr предупреждение в `free_task.py`), не молчаливое
   вырождение в дату создания без объяснения.
5. Закрытие блокирующей задачи снимает её из счёта «сколько блокирует» у
   блокирующей БЕЗ ручного действия следующим запуском (живой перерасчёт,
   не кэш) — тест с мутацией (закрыть → пересчитать → счётчик меньше).
6. `scripts/lib/collect_labels.py` видит `area:*` из дропдауна шаблона;
   `test_label_registry.py` зелёный для всех пяти `area:*` меток без
   специального исключения.
