# Design: task-priority-blocking-graph

Контекст, замер и правило — `proposal.md`. Здесь — развилки и почему выбрана
конкретная.

## Развилка (а): носитель зависимости

Три варианта на выбор были названы владельцем: нативные sub-issues, поле в
шаблоне issue (обязательное, валидируемое), метка + отдельное поле.

**Sub-issues — отвергнуты для отношения «блокирует».** `docs/agents/PROTOCOL.md`
уже различает два механизма не случайно: sub-issues — для декомпозиции
(родитель — зонтик, не отдельная работа сам по себе), «блокирует» — для
порядка выполнения между двумя РАВНОПРАВНЫМИ задачами. Смешивать их значило
бы использовать граф декомпозиции (`totalCount`/`completed`, проценты
выполнения родителя) для семантики, которую он не выражает — задача,
блокирующая другую, не является её «родителем». GitHub сам развёл эти два
понятия на уровне схемы: `subIssues`/`subIssuesSummary` (декомпозиция) и
`blockedBy`/`blocking`/`issueDependenciesSummary` (порядок) — отдельные поля,
отдельные мутации (`addSubIssue` vs `addBlockedBy`). Смысл дропа sub-issues
здесь не архитектурный вкус, а то, что GitHub уже провёл это разделение за
нас.

**Метка + отдельное поле — избыточны при наличии нативного графа.** Если бы
`blockedBy`/`blocking` не существовали или были REST-only (нет), пришлось бы
городить свою метку и хранить номера в теле — ровно прозопарсинг, который
это изменение обязано закрыть, не воспроизвести под новым именем. Раз
GitHub уже даёт структурированную, машиночитаемую, валидируемую GraphQL
связь — заводить параллельную «свою» разметку значило бы два места правды
на один факт (запрещено `AGENTS.md`).

**Живая проверка, не документация.** Introspection (`__type(name: "Issue")`)
подтвердил поля `blockedBy`, `blocking`, `issueDependenciesSummary` и
мутации `addBlockedBy`/`removeBlockedBy` в схеме; round-trip на паре
issue #350↔#320 (`addBlockedBy` → чтение `blockedBy.nodes` → `removeBlockedBy`
→ повторное чтение подтверждает 0) доказал, что мутации реально исполняются
на этом плане/токене, а не только объявлены в схеме. REST
`repos/{o}/{r}/issues/{n}` при этом отдаёт `sub_issues_summary`, но НЕ
`blockedBy`/`blocking` ни в каком виде — что закрывает вопрос «может, проще
через существующий REST-код»: нет, только GraphQL.

**Выбор: нативные `blockedBy`/`blocking` через GraphQL, единственное место
доступа — `scripts/lib/task_deps.py`.**

## Развилка (б): как связь ПОПАДАЕТ в граф (создание/редактирование задачи)

Задача явно требует: «заведение задачи должно требовать ответа... механизм
должен делать пропуск невозможным, а не напоминать о нём». Разобраны три
пути.

**(1) GitHub issue form validation (`required: true` в `task.yml`).**
Технически валидирует ТОЛЬКО заполнение веб-формы
(`github.com/.../issues/new?template=task.yml`) или интерактивного
`gh issue create` с выбором шаблона. Проверка ЖИВЫМ замером этого change:
прочитаны тела issues #6, #148, #355, #357 (все явно заведены через
`gh issue create -f body=...` или API) — ни одно НЕ содержит секций
«Площадь»/«Правила» дословно в форме, которую рендерит GitHub для формы
(GitHub рендерит поле формы как `### <label>\n\n<ответ>\n`, здесь везде
`## Цель`/`## Критерий готовности` — конвенция агентов, воспроизводящая
СМЫСЛ полей вручную, не факт прохождения формы). Значит `required` в
YAML-форме НЕ enforced для реального большинства создателей пула — это
клиентская валидация браузера/интерактивного CLI, а не серверная проверка
GitHub API. Ставить единственной защитой её нельзя: она защищает путь,
которым пул почти никогда не наполняется.

**(2) Workflow `issues: opened`, конвертирующий текст тела в связи графа.**
Технически возможен (Actions поддерживает триггер), но раз GitHub API не
проверяет форму при создании (см. (1)), тело issue, созданной программно
(`file_tasks.py`, будущий инбокс), не будет содержать ожидаемых секций —
воркфлоу либо молчит (0 связей — граф остаётся пустым, тот же результат,
что и без воркфлоу), либо приходится ЗАСТАВЛЯТЬ каждого создателя issue
(включая `file_tasks.py`, включая ручной `gh issue create` любого агента)
знать и соблюдать формат тела — то есть снова прозопарсинг с шагом
валидации, просто отложенным на post-create хук. Это не убирает класс
проблемы, только двигает его.

**(3) Единый CLI, тот же паттерн, что уже принят для sub-issues.**
`docs/agents/PROTOCOL.md` уже документирует sub-issues как РУЧНОЙ шаг:
`gh api repos/.../issues/<родитель>/sub_issues -F sub_issue_id=<id>`,
выполняемый тем, кто заводит эпик — не автоматика, не парсинг тела. Это
работает, потому что связь ставится ТЕМ, КТО ЗНАЕТ факт зависимости, в
момент, когда он его знает — а не выводится задним числом чтением текста.
`task_deps.py block <заблокированная> <блокирующая>` — тот же паттерн для
«блокирует»: исполнитель/владелец, заметивший реальную зависимость, ставит
её одной командой. Не enforced на 100% (как и sub-issues сейчас не enforced
— ничто не требует от заводящего эпик обязательно проставить sub-issues),
но НЕ создаёт иллюзии автоматической защиты там, где её физически нет.

**Выбор: (3), с (1) как дополнительной подсказкой (не единственной
защитой).** Шаблон `task.yml` получает `area:process` в дропдаун «Площадь»
(классификация, требует ответа от того, кто РЕАЛЬНО идёт через форму) —
это дешёвая, честная подсказка. Механическое «пропуск невозможен» для
факта зависимости не достижимо без переписывания ВСЕХ путей создания issue
в этом репозитории на единый программный вход (что само по себе отдельная,
крупная задача — не по масштабу этого change, `file_tasks.py` заводит из
AI-ревью, инбокс из директив владельца, агенты — вручную; единой точки нет
и её создание не входит в scope). Честная граница признаётся явно в
`proposal.md` (Out), а не маскируется под «сделано».

## Развилка (в): что делает `free_task.py`, если граф пуст

Замер `proposal.md` показал: граф пуст на 103 из 103 задач на день внедрения.
Два варианта: (i) тихо вырождаться в сортировку по номеру (было раньше,
пользователь не узнает, что приоритет не работает), (ii) явно предупреждать.

**Выбор (ii).** `free_task.py` считает `graph_is_empty(issues)` (все
`blocking`-списки всех кандидатов пусты) и печатает в stderr предупреждение
«граф зависимостей пуст — приоритет сведён к дате создания» при выборе —
видимый сигнал вместо молчаливого факта. Не жёсткий отказ (rc=2): пустой
граф — легитимное (хоть и деградированное) состояние на старте внедрения,
не поломка инструмента; коды выхода 0/1/2 несут другой смысл (нашла/пусто/
сломано, контракт `free_task.py` не меняется).

## Развилка (г): порядок — тайбрейк по номеру issue как proxy даты

Владелец просит «по дате создания». GitHub API отдаёт `createdAt` и через
REST, и через GraphQL — технически можно брать его напрямую. Решение: НЕ
брать — использовать номер issue (уже используется как тайбрейк в
`free_candidates`, все существующие тесты на нём построены). Номера GitHub
issues строго монотонны по времени создания в рамках одного репозитория
(следующий issue всегда получает больший номер, что подтверждено самой
механикой GitHub — независимого способа создать issue «задним числом» с
меньшим номером не существует) — значит «меньше номер» ⟺ «создан раньше»
без исключений, тот же факт, только без лишнего сетевого поля в ответе
GraphQL. Экономия: одно поле меньше в запросе, полная обратная совместимость
с уже зелёными тестами `test_oldest_free_picks_lowest_number_not_newest`
и т. п. — старое поведение оказывается ЧАСТНЫМ СЛУЧАЕМ нового (мета=нет
у всех, blocking=0 у всех → тайбрейк по номеру → тот же результат).

## Что делает выбор неверным (пересмотреть при новом факте)

- Если GitHub добавит серверную (не клиентскую) валидацию полей issue-формы
  для программных создателей (REST/GraphQL creates провалидируют по схеме
  шаблона) — развилка (б) пересматривается: (1) станет реальной защитой,
  не только подсказкой для веб-формы.
- Если граф перестанет быть пустым НАСТОЛЬКО, что тайбрейк по номеру
  перестаёт быть частным случаем правила (например, появится потребность
  сортировать несколько задач с равным `blocking`, где порядок реального
  создания важнее монотонности номера — этого не бывает по построению
  GitHub, риск чисто гипотетический) — не ожидается, зафиксировано для
  полноты.
