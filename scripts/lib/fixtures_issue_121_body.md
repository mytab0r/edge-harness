## Цель
Запрос владельца 2026-08-31: «механизм, который не позволит двум пайплайнам делать одну работу. Когда всё автономно — некому смотреть». Сегодня защита дырявая по построению:
1. free_task: check-then-assign (TOCTOU между чтением пула и назначением);
2. проверка «занята не воркером» бесполезна: ВСЕ агенты — один GitHub-логин (mytab0r), назначение не различает «кто»;
3. канал hands/runner-bridge вообще не берёт GitHub-аренду — морда-агент может заказать работу по задаче, которую уже делает воркер;
4. живой случай 2026-08-31: ручной dispatch + пульсный dispatch — дубль прерван человеком, в автономе никто не прервёт.

## Дизайн (скелет для исполнителя, сверять с ADR)
- **Claim = атомарная операция на сервере**, не check-then-act. Носитель: git-ref замок refs/locks/task-<N> (push нового ref атомарен: повторный claim отклоняется сервером) или имя ветки агента (создание ветки атомарно). Выбор носителя зафиксировать в ADR.
- **Один вход**: scripts/lib функция claim_task(N) — единственный способ начать работу; каналы worker.yml (auto/manual task=N), hands (runner-bridge #95), будущие пайплайны зовут только её. Отказ claim = зелёный no-op «задача занята», не красный job.
- **TTL**: замок протухает (порог в часах, одно место правды); протухший замок снимает оркестратор (у него уже есть обход пула), снимающий оставляет след в задаче.
- **Release**: слияние PR (post-merge хук оркестратора) или явный drop при blocked-эскалации.
- **Видимость**: замок/аренда видны в задаче (метка или комментарий при claim), чтобы человек видел «кто держит» без копания в refs.

## Критерий
- Два параллельных claim на одну задачу: ровно один выигрывает, второй получает зелёный отказ (доказать тестом на прод-форме: гонка двух claim_task).
- Все существующие каналы диспетча проходят через claim_task (worker auto/manual, hands) — в коде нет второго пути выбора задачи.
- Протухший замок снимается оркестратором, задача возвращается в пул (эмуляция TTL).
- При живом замке повторный free_task не возвращает задачу как свободную.
